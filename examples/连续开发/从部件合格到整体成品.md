# 从部件合格到整体成品

本例把[原成品族作者JSON](../成品形态/model/family.json)、[原规则合同](../成品形态/规则合同.md)与组合、变换接纳接在一起。真实作者文件不复制、不增加新kind或公共参数。F/G仍使用[局部实现替换](局部实现替换与成品接合.md)的有限区间含义；本篇的候选、信用状态与IR都是实现设计情景，不是声称产品已经运行。

## 1. 作者已经决定什么，实现还有什么自由

Family在一份`transform`主体上采用Normalize，向六个不同Delivery主体要求Library、Command、Worker、HttpHandler、Plugin和Panel。各公开边界已在原合同定义，同型Delivery不合并实例。实现者可以共享合格的不可变方法代码，不能把输入、会话或状态合并。

作者没有选择队列容量、确认协议、临时表或Pass顺序。具备合格直接TS方法时可以先采用；同步Library不为其它根创建工作器。增加一个更快实现并不会要求作者把algorithm字段补进所有JSON。原targets为空表示本范本尚未绑定生产目标，下面给出以后取得真实方法时必须完成的接合，不编造profileRef或安装成绩。

## 2. 联合选择第一次会遇到哪些问题

从同一准确内容取得以下候选：

| 部分 | 候选能力 | 不能从单项合格推出的结论 |
|---|---|---|
| 纯变换G | 按原精确整数、输入错误和相接合同返回完整结果 | 不替UI或工作器证明有界响应和关闭 |
| 窄核F | 只在实际i64/布局/线程条件下适用 | 不能缩小Normalize原合法域，也不自动合格于同步Library |
| 工作器P | 取得信用后开始处理并返回带请求身份的结果 | 不能假定启动时信用已经存在 |
| 面板/接收端C | 收到可接纳结果后确认，按原输入代更新界面 | 不代表永远不读的消费端仍能无条件完成 |
| 可选变换O | 声称保留公共行为并优化某段目标表示 | 退出0和合法目标类型不证明保持，也不证明旧分析还有效 |

组合器不把五个BoundaryView的保证立即标真。它按当前消费根取得具体前提，区分固定事实、上游条件保证、实际宿主进口、运行检查及尚未闭合的内容。P和C之间的等待是运行关系，不是作者模块依赖或编译前置图。

## 3. 反馈的错误方案与正常方案

### 错误方案：双方等待对方先开始

P规定“获得一个信用后才接受请求”；C规定“看到结果以后才发出信用”。初始信用为0，又没有独立的合法授信动作，两方都不启用。把P/C各自的条件保证相互连接，只说明“如果对方先行动，我就会行动”，不能满足工作器正常接收和产出。

编译器应返回具体等待分量、初态及被阻塞的进展义务。它不能仅因这个实现方案死锁便宣布原作者要求逻辑矛盾；可以选择另一合格供给。也不能为了通过检查伪造一次用户点击、一次外部确认或一个结果。

### 正常方案：明确的初始容量和逐项结算

若原交付合同允许内部流控，可由队列拥有者在启动成功后授予实际预留的容量K，且K至少为1。每次接受请求把一个free移到pending；一次可接纳结果把一个pending移到delivered；准确确认再把它移回free。各请求的确认身份来自原会话/请求合同，迟到和重复不二次返还信用。

稳定边界的不变量是三项非负且`free + pending + delivered = K`。K=1的正常有限轨迹为：

```text
已就绪：(1,0,0)
接受一项：(0,1,0)
结果已交付待确认：(0,0,1)
确认结算：(1,0,0)
```

该协议可以说明有界缓冲不被重复计数，不能独自说明实际计算必结束或用户一定确认。工作器和面板之间没有采用该确认协议时，不能强行将它装入公开接口；可由内部适配拥有信用，或者选用已符合原协议的队列。对无限不响应的环境，给明确取消/终结语义和责任，不能宣称正常进展。

关闭期间停止新准入，保留原已接受工作；对象、回调与结果的最后释放继续遵守[跨实现寿命](../../docs/运行/跨实现调用与数据寿命.md)。返回了结果但底层仍访问数据的情形，不靠信用数量推断已停止。

## 4. 相同代码，也可能不能并行装配

设两个相交任务各有48 MiB私有暂存，实际允许使用64 MiB。各自能执行，不说明二者能同时执行。共享的不可变代码只计实际一份，两个私有缓冲不能按字节相同去重；输入快照、待交付结果与收尾空间还要另外计算。

原消费合同允许排队、无相交硬截止且不影响顺序时，可以串行处理；这属于实现自由，不要求修改作者JSON。如果要求两项真实并发或串行后违反期限，应改用合格低内存方法、其他资源配置或准确缺项，而不是藏掉原要求。

数字只用于设计反例；实际容量、成本和调度前提必须从被选环境取得。只测纯G内核的耗时不能替整个Panel、编码、队列和关闭作性能结论。

## 5. 一次目标变换如何失败，而不污染已经合格的结果

假设原目标IR为I0，已有读者和分析。某个成熟可变Pass O准备更新一段函数：先取得只涉及该段及准确边界引用的私有工作区I1，再变换；不能直接在共享I0上修改。

如果O修改了半段后失败，I1的结构可能不完整。接纳器不把它作为新根，不在I1上直接运行备用实现；可丢弃I1，沿仍有效的I0使用原合格方法。若选择的是不保留旧内存的私有所有权转移路线，则须从准确固定内容重建I0或停止，不能声称无依据的回滚成功。

O是可选优化且I0仍满足任务时，返回准确未优化结果及优化失败；明确固定O的任务则保留不满足。一个优化失败不回滚另一个已独立生成的根。若共同发行涉及共享配置，仍按共同成员条件判断整体是否完成。

这项恢复保护的是编译内容，不替代外部进程、文件写入或设备任务的真实收尾。私有结果被放弃以后，其仍在运行的外部工作必须按原执行协议停止或移交。

## 6. 一次常量变化怎样使旧分析失效

另外考虑编码链的有界例子：x属于0至255，C1的y=x，C2的y=x+16。调用签名和控制流图没变，但范围由`[0,255]`变成`[16,271]`。

保留控制流与相关支配分析可以合理；保留旧精确范围不合理。依赖旧范围的u8专用方法资格、守卫删除、容量和成本结论要重新判断，而无关函数解析和另一个独立根无需全部重算。若一个旧保守范围仍覆盖新值，可以作为同样保守的结论迁移，但不能声称精确。

若C2来自作者明确改要求或参数，保留该新要求并选择覆盖全部合法输入的实际方法。原需求没有饱和条件时，不自动Clamp；没有通用方法时不把入口偷偷改成0至239。若O声称保持C1行为却擅自改成C2，问题是变换改义，更新缓存也不能让它合格。

普通优化仍可成功。例如合格规则证明替换一段表达式在其输入域、溢出、错误和作用条件下等价，且CFG、类型和别名确实不变，便保留这些分析；值域或成本需要更新时只更新对应项。不能反过来要求每个无变化Pass都重建全工程。

## 7. 候选验证和生产采用的实际区别

F或O缺少某项保持证据，可能正需要生成被测产物进行检查。此时可以固定它们的准确实现、输入、目标和剩余命题，形成验证用途的UseBinding，经类型/结构及真实隔离准入生成候选。不能要求先有这次运行产生的证据才能生成它。

检查结果回到assurance后按实际范围评价；有限样例不自动证明全域，方法签名相同也不自动获得相同资格。没有真实生产目标、需要的宿主或所要求证据时，仍交付准确作者成果与缺项。产物中的tested标签、客户端填写的purpose或插件声明不能改变这个条件。

验证通过且依据适用时，新选择可以被生产消费者采用。已经在运行的旧A仍绑定A的代码、输入和结果释放方法，不能原地热换成B；如果新方法返回不同拥有权或错误形式，重新检查真实适配及所有相交消费者，而不是只刷新一个版本字符串。

## 8. 同一套信息如何避免重复维护

| 独立内容 | 当前唯一维护位置 | 相交变化 |
|---|---|---|
| Normalize及六种消费方式 | [原作者源](../成品形态/model/family.json)与[合同](../成品形态/规则合同.md) | 产品要求变更时改它，不写队列或Pass实现镜像 |
| 值域与F/G适用条件 | [有条件实现](../../docs/编译/有条件实现与公共行为保持.md)及实际方法 | 内核和适配改变，更新真实选择及域证据 |
| 前提、初态、进展与共同预算 | [组合闭合](../../docs/编译/组合前提与进展闭合.md) | 连接、共享状态和环境变化，重核相交支持 |
| 私有变换、结果接纳与缓存 | [变换接纳](../../docs/编译/内核/变换接纳与分析保持.md) | 改动集和方法变化，保留仍有依据的分析 |
| 真实任务、资源、回执 | [运行规范](../../docs/运行/README.md) | 实际执行后按当前协议结算，不从文档推断 |

现有C0—C6和Pass调度图分别解释组合与编译，不把运行反馈和静态导入绘成同一种边。本例补的是两图之间所需的条件、正反路径和准确成果；没有另一份可独立编辑的产品图或作者程序。

该链条的有限模型可以独立检验信用守恒、无种子支持、范围失效和私有结果发布，但模型并未运行真实驱动或优化器。实施验收见[组合与接纳案例](../../docs/运行/验收/作者与组合案例.md#composition-acceptance-cases)，实际代码、宿主及端到端代价仍需各自验证。


## 性质升级、证据拒绝与正常继续

继续使用原Family及其准确主体，不新增作者字段。场景中的更强Claim由已有权限/信息流/数值域合同表达；若该域缺少机器编码，则在原要求中保存准确含义和缺额，不编造可运行JSON扩展。

**C1只有功能要求。** 合格确定性规范化库G可以直接采用。来源锁、精确整数、错误和公开接口仍核对，不要求先安装通用非干扰证明器。

**C2增加明确的保密范围。** 日志、错误可见性及指定的外部时间观察不得区分秘密输入。功能测试仍通过的F，如果按秘密分派造成可观测时间差，不能凭结果相同或源输出子集代签。改用已有保持该Claim的G、采取有依据的隔离/统一方法或保留准确缺额；不能默认把所有任务都停掉，也不能删除C2的保密要求。

**供给者提交一份“通过”报告。** 若其检查器把数学Int改成64位回绕，两边一致仍不满足原域；若公式完全一致却包含未验证公理，结果只提供相应假设下支持；若证书、编码与信任基础都合格，正常消解它真正覆盖的义务。运行检查器的沙箱权限没有被用于签发证据资格。

**优化搜索比较了许多实现。** 一次偶然最小耗时只能作探索依据。冻结候选后在合法的新确认范围比较；失败返回探索但不继续把已暴露数据叫未见数据。没有余量时保持合格已知实现，功能交付和未确认性能分别报告。

**C3加入新的宿主插件。** 同类型接口可能新增重入或共享内存，重核实际上下文；旧A2继续在其原组合中运行，不把新插件存在自动当作旧实例受攻击或一切旧证据失效。新共同发行若缺开放环境依据，旧独立库根仍是准确成果。

**再次修改与退出。** 观察、理论签名或统计确认方法改变，重评相交Claim与选择；原源码字节和未影响的纯分析继续共享。结果已产生、证据被撤销和外部操作完成是三类事实：不重写旧历史，也不用重新执行副作用“补证明”。整个过程的产品作者仍维护真实要求与采用选择，不维护证明指令树、统计样本台账或内部控制流。
