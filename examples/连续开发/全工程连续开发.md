## SEC成品自身的多模块、多入口和两次完整修改

本例以SEC整个本地成品为开发对象：同一Runtime被库调用与CLI使用，拥有原生TS实现、中立作者输入、完整资源及可选调试。它不是另造商业应用，也不是宣称已读取或实现了某份当前仓库。以下路径是[成品物理合同](../../docs/架构/装配/模块与运行实例.md#runtime-assembly-scopes)中的设计落位；真实仓库迁移必须再与实际前像逐点对应。已有Code-OSS源码证据只用于它自己的章节。

### 1. 开发面就是原工程文件，不是全产品的一份巨型图

```text
SEC-product/                         设计中的目标工程；不是本包中的产品实现
  src/
    contracts/                       公共六工具、不可变引用、结果合同
    workspace/                       捕获、唯一来源、项目视图、候选与重基
    semantics/                       绑定、类型/效果、需求与可调用资格
    compiler/                        查询、根计划、降低、成员组合和来源
    assurance/                       原要求、检查计划、分项结论
    application/                     准备、补取、处理器、结果路由
    execution/                       实际操作、调试会话、恢复和结算
    adapters/                        实际文件、目标工具、运行/调试适配
    entry/                           库/CLI/已选协议入口
    bootstrap/                       Runtime装配与解释封存
  package.json                       本原生工程真实依赖和入口；不复制进第二套清单
  tsconfig.json                      实际TS工具配置及其继承输入
  assets/                            实际命令帮助、消息等运行成员
  docs/                              独立规范/使用文档；非运行输入默认不进制品
  generated/                         仅实际生成成员；不是另一个作者目录
```

目录不是必须逐一创建的发布包。已有路径可保留其正确责任，小规模实现可以合并物理文件但不能合并本来不同的状态。若某个纯方法以后选择中立作者自用，它只有一份.sec，生成TS只进入受管区域；不同时保留可编辑TS副本。输入工程中的用户程序又是独立作者对象，不与SEC产品自身源码混成同一个currentCandidate。

同一工程可以请求`library`和`cli`两个目标画像：都是当前TS路线，不是另选一种语言。library公开Runtime工厂与稳定合同；cli额外包含参数/消息/退出行为。两者共同依赖的核心与配置由一个成员组合器协调；只生成library不能删除cli已经拥有的成员，也不能把未更新cli说成已适用新接口。真实根与画像通过既定targets/outputRoots绑定，不用这些显示名代替实际引用。

### 2. 本次完整变化：把“能跑”补成“能停、能查、能继续改”

要求是新增有限交互调试，但保持无调试器时的纯编译、原compute-run行为、原生源唯一性和两个入口语义。不是把所有调试实现写进一个Adapter名字。具体修改组与调用如下；表内函数合同在相应拥有者完整展开，产品代码尚未生成。

| 设计文件/承担者 | 本次具体修改及其消费者 |
|---|---|
| `contracts`的operation/query联合解码 | 原v2保持；只对已协商sec.debug-session/1接收启动、附加、控制和debug-targets查找；CLI和库调用共享相同解码 |
| `bootstrap/create-runtime.ts` | 接受实际DebugDriver注册与精确画像；未配置时不创建调试进程、不影响compile；关闭按拥有关系释放 |
| `entry/session.ts`及CLI参数映射 | 取得受信调用上下文及返回槽；把真实引用传给原operation；终止/分离和普通取消不混同 |
| `application/prepare-job.ts` | 固定当前制品或runtimeTargetRef、目标/调试画像及当前准入；不读取全局最后产物 |
| `application/present-result.ts` | 返回真实phase与逐断点结果；晚到回复只能更新原请求或历史，不能抹掉另一客户端的当前状态 |
| `execution/debug-session.ts` | 拥有会话/配置/暂停代，串行接收控制与真实事件；命令先记录再发，失联查询原意图，不再发一次next |
| `adapters/debug` | 实际launch/attach、能力协商、按源全量配置、栈和值读取、结束与查回；缺能力明确返回，不把任意协议消息放行 |
| `compiler`的来源组合 | 把所有实际转换的源/目标位置链随制品固定；旧运行使用旧源，不因工作树已改就重新算栈位置 |
| `workspace`的作者/目标草稿 | 调试定位到原生源直接改，定位到中立源改真正作者；映射不唯一时保全目标草稿，不猜逆变换 |
| `assurance`的当前能力检查 | 分别检查解码、源定位、暂停前提、无代码读取、结束和原功能；仅存在DAP端口不能签发全部保证 |
| `assets/`、帮助与文档 | CLI必须解释“命令已发送”“暂停已确认”“会话结束而进程仍在”；未支持语义不能显示绿色成功 |
| 原生工程出口和所需构建配置 | 库入口和CLI都导入真实新实现/公开合同，配置/类型/资源进入实际成员；check与运行各选准确制品 |

这覆盖跨模块完整变化，而非要求所有工程使用调试。具体D0—D5由[调试运行算法](../../docs/运行/发布运行与资源生命周期.md#debug-driver-lifecycle)拥有；源定位由[准确来源绑定](../../docs/编译/表示/目标运行与观测.md#debug-source-binding)拥有。没有这些真实方法时本例处于已设计未实现，不声称装配表自动生成了主体。

### 3. 第一轮开发、构建与运行的准确请求

下面的C0/C1、A1、B1、p1等是设计叙述中对**服务实际返回引用**的简写，不是可粘贴使用的真实身份。完整文件批次由实际文件内容构成，本例不填空文件假装已交付实现。编辑器已经保存源时，工作集捕获得到C1；内存编辑则通过已有propose(files或edits)得到C1。随后请求：

```json
{"candidateRef":"C1","methods":["types"]}
```

这是`sec.check`，只作作者语义检查。库目标和CLI目标分别进入同一编译器：

```json
{"candidateRef":"C1","target":"library","return":"summary"}
```

```json
{"candidateRef":"C1","target":"cli","return":"summary"}
```

这两条是`sec.preview`。target必须是C1上下文中已有的准确画像键；不足时返回缺项，不按显示名猜。分别得到A1-library和A1-cli及共同成员。若任务要求两者都可交付，它们构成AND义务；CLI缺消息资源时，library可以单独返回，但整个任务仍未完成。需要目标类型检查时传对应artifactRef，不使用“最后一个产物”。

已获准并已有可用工具时，对准确CLI产物构建：

```json
{"action":"start","kind":"compute-build","artifactRef":"A1-cli","requestId":"build-c1-cli","return":"outputs"}
```

构建返回实际可运行B1。它包含精确成员/工具结果，不从generated目录再搜一遍凑包。新调试以B1的实际入口和类型化输入启动：

```json
{"action":"start","kind":"debug-launch","artifactRef":"B1","entryRef":"entry-cli-B1","argumentsRef":"args-smoke-1","debugProfileRef":"debug-profile-bound-1","breakpoints":[{"sourceRef":"source-dispatch-B1","byteOffset":0,"required":false}],"requestId":"debug-B1-1","return":"state"}
```

示例offset=0只是合法源边界，不保证可执行；实际结果可以unmapped或relocated。需要保证停在某一真实可执行位置时，先从来源查询取得准确位置并设置required=true，不能把此示例的0当作真实断点。强保证缺能力时拒绝/保持未完成，普通不必需断点未验证不能阻止用户看到它未生效。

运行真的暂停并返回p1后，读取栈与某帧：

```json
{"at":"p1","view":"state","limit":20}
```

```json
{"at":"frame-p1-0","view":"state","limit":20}
```

这两条是`sec.query`。对安全读取不支持的属性返回opaque/不可用，不执行getter。然后对实际threadRef单步：

```json
{"operationRef":"op-debug-B1-1","action":"debug","command":"next","expectedPauseRef":"p1","threadRef":"thread-p1-0","requestId":"step-p1-1","return":"state"}
```

命令送出但响应丢失时，查询原operation，而不是换requestId再单步。p2出现后旧帧/值/游标过期，不能用p1的同号底层句柄显示p2数据。

### 4. 第二轮是原工程的共同改变，不是重建演示

现在把断点策略从“默认允许未验证”改成“某些启动任务要求在目标执行前已验证”。只需由已有required字段与准确任务决定承载，不能增加全局safe=true、第二套工具或改写所有程序。真正需改的是请求构造/既有任务默认、prepare阶段对所选Driver能力的判断、配置完成后是否允许继续、逐断点返回、CLI消息和期望案例；compiler源坐标、类型/效果与普通compute-run在无相交改变时保持。

两个开发者并发：甲在C1基础修改上述策略，乙已把CLI帮助文本改为C2。甲的计划读取帮助文本旧内容时必须重核该读集；完全无关的文档变化保留并产生C3，不把整个C1覆盖C2。若乙更改了调试启动含义/字段，属于真实冲突而非“文件不同即可合并”。新的C3生成A3/B3；C1的慢预览只能返回C1历史结果，不能覆盖C3当前结果。

旧op-debug-B1-1仍运行B1；C3的调试采用新B3/new requestId。必须原地升级正在运行的调试器或热替换目标时，这超出有限合同，需要单独定义状态迁移和暂停边界，不能以本次源码变更隐含执行。旧运行合法结束后，可按拥有关系移除旧生成成员；未验证停机前不清理其仍需资源。

### 5. 文件写回、缺口及退出的全工程结果

用户只要设计/预览，所有上面实际执行步骤都保持为未执行计划。用户明确保存内存候选时，`save-source`消费当前目标前像；已由编辑器保存则跳过。只有要求目标落盘时使用`write-output`，按[旧成员/新成员/实际现场](../../docs/编译/目标/成员布局与完整产物.md#artifact-membership-reconciliation)协调。现场generated文件存在手改时保留草稿/冲突，不能“重新生成就修好”。

CLI目标失败、library成功时分根交付；缺一个调试器不使源检查失败；强断点要求不满足又不能把较弱配置伪装合格。结束attach会话不自动杀用户已有进程；结束launch的进程归属、子进程及连接分别结算。全部这些结果关联原准确请求和制品，而不是最终返回一个未经限定的success。

本例可以直接作为对应文件/函数的实现设计输入，但不能证明完整产品源码已经存在。要宣布成品已实现，需对应实现、真实入口和[全工程接合案例](../../docs/运行/验收/实现与运行案例.md#whole-project-acceptance)的实际符合性；其他领域未被此例使用的独立语义并未被省略或验证。

## 一个图工具的反向查询、当前预览与全工程共同修改

本例不增加业务包、语法或平台模块。已存在一个本地图工具：保存有限有向简单图，提供正向访问与可重算预览，拥有原源码、README和实际图标。当前开发任务是：**增加准确的反向查询；让预览只发布当前修订的结果；保持原正向接口、节点身份和未改资源。** 本次只设计/生成，不运行这个应用去修改真实数据。

### 1. 作者要改的内容与不该出现的新内容

原有`src/graph.sec`拥有图与正向更新；`src/preview.sec`拥有会话和预览发布；`src/main.sec`组合入口；assets与README按原拥有者保存。新功能放回这些现有责任，不要求新增requirements.json、四层意图程序、框架包装或全局block目录。小工程可合并文件；这里按实际变化职责命名。

需求投影绑定图关系R、节点域V、反向结果及预览修订。它不要求作者选择数组、字典或线程。独立要求沿原接受来源保存；语义已有准确定义就引用。实际拥有的短源、函数值和省略的类型继续保留，推导结果不写回源；现有TS区域同样不为此迁为.sec。

### 2. 固定有限域与当前实现选择

V是本次已固定的唯一节点身份序列，显示次序由其稳定rank决定；E是V×V中的有限无重复边集合，允许自环和多前驱。无效端点或重复身份先按原输入位置报错，不能为索引方便重分配身份。一次边更新不修改V；增加节点属于明确的新变化，必须同步索引域。

要求`pred(v)`返回所有满足(u,v)∈E的u，按V中rank排序；当前选择用稠密内部rank表与邻接桶，外部身份不变。定位为O(1)，枚举为O(indegree(v))，**返回k个前驱不能承诺总时间与k无关**。rank的建立与原身份解码单独计成本。当前基线用完整新代重建反向桶，时间O(|V|+|E|)、额外索引空间O(|V|+|E|)；不是每次更新都O(1)，也不先实现复杂动态图平台。

生成器可在单一串行实例下原地更新，只有在读者隔离、失败恢复和所有已接受观察保持时才可采用；本有限方案先选择不可变新代和一次发布，以便准确维护两种查询与异步预览。现成供给满足同一合同则直接使用，以下算法定义所需行为，不要求重写全部容器。

### 3. 关系实现与发布算法

```text
buildRevision(base, edgeDelta):
    核delta引用的原图/节点域，得到一份私有新边集合E'
    检查全部端点、唯一性及原任务的结构约束
    为每个v建立空pred[v]；保留原succ的合法顺序要求
    按V的rank从小到大访问u：
        对E'中每条(u,v)把u附加到pred[v]
    构造不可变GraphRevision(V, E', succ, pred, newRevision)
    返回完整新代，或准确错误；不修改当前已发布图

publishRevision(expectedBase, next):
    在当前会话唯一串行发布点核currentGraph.revision == expectedBase
    不相同：返回过期更新，重新按新基础合并或冲突
    相同：一次替换完整GraphRevision，并建立新预览请求
```

扫描每个u只一次，简单图中一个u对某v最多附加一次，因此pred同时完整、无重复并符合rank顺序。图更新和反向桶不能分别发布为G1和来自G0的I0；资源预算不能同时容纳旧读者与新代时，应延迟新代、释放可重建数据或准确失败，不能先回收还在使用的旧桶。

新预览请求的键绑定本次确实被消费的`(graphRevision, selectionRevision, displayPolicyRevision, programRevision)`，并不固定要求所有程序都有这四项。只改普通窗口尺寸且计算不读取它，便不使计算结果无条件失效。输出同时引用它真正计算使用的GraphRevision与反向桶。

输入变化时保留一份最新pending，旧任务失去发布资格但持有资源到真实停止。完成后由同一串行拥有者原子检查当前键并更新可见结果；若实际显示适配是异步通知，消息带该键，消费者再次核当前键后安装，不能把“已入通知队列”当成已经显示。比较成功到最终使用之间的可重入回调不得绕过这个检查。

### 4. 开发计划如何形成真实文件变化

现有`bindIntentScope`得到逆关系、原正向接口保持、预览安全与条件进展。计划器复用已定义的关系与发布方法；没有这两个方法实现时，向当前开发AI交付有限主体缺口，而不是假称已安装graph/latest插件。

`EditPlan`联合修改graph的读取/更新和preview的结果接受；`main`只接真实新入口。反向查询的假设必须来自完整新代，而发布方法必须按真实新代检查，二者是一个共同检查组。计划记录这些读取前提、改动主体、必要类型/资产和待核义务；没有新增SDK、公开工具分支或运行数据库。

materialize在当前源C1上检查原计划C0的语义读集。只有README被修改时保留新README，继续构造候选C2；若C1把简单图改成多重图，原“不计重数”计划已失效，必须重新选择集合或重数合同，不能因为改的是另一个文件而自动合并。

C2的短声明先得到类型形状，主体随后取得调用/状态效果，再封存可调用头。compiler按已固定TS目标生成普通数据、访问器及会话代码；类型、状态和任务图不进入目标程序作为通用解释器。Assurance分别检查索引关系、输入/资产保持和发布进展；仅生成pred访问器但未修改更新路径不算完成。

### 5. 固定反例与连续变化的书面预期

| 情形 | 必须得到的结果 |
|---|---|
| G0的边为a→c、b→c | pred(c)=[a,b]，不是单一prev |
| 从G0删除b→c，增加b→a成为G1 | pred(c)=[a]，pred(a)=[b]；正向查询同时来自G1 |
| G1预览先完成，G0后完成 | 只显示G1；G0仍结算原资源 |
| G0计算读取旧索引，G1已经发布 | 允许G0继续用完整旧快照，不得混用G1输入与I0 |
| 两次更新都基于G0 | 先采用者得到G1；后者重基或冲突，不沿旧边删除新关系 |
| 用户同时改图标 | 新图标按现有资产候选保留，索引功能不能回填旧图标 |
| 新要求保留平行边重数 | 这是关系语义变化，需改输出与维护规则，不只改索引布局 |
| 只将反向结果显示顺序倒序 | 修改显示/排序政策及其消费者，保留边关系与身份 |
| 输出名仅在目标改动 | 沿准确EditCorrespondence回到已有控制/源位置，不填满原省略类型 |
| 输入最终稳定且计算结束、资源和调度可用 | 最终给出当前结果或当前错误；永不发布不能通过任务 |

这些是由定义得到的预期，不是实际执行成绩。完整实现仍需适配真实源码/图API、有限运行状态和目标；但是输入、所有者、算法、组成前提、源变化与第二次修改已经明示，实施者不必自行决定最基本的数据一致性。

### 6. 本例检验的全系统接口

要求形状、简洁作者和编译器不是三套互相替代的方案。这里同一任务需要关系和时序组合，落为既有源文件的联合变化，经同一类型/效果流水线生成，目标运行再维护自己的GraphRevision。源Candidate修订、图数据修订和预览请求键分别比较；单个全局version不能替代三者。

首条交付可以只在本地单进程、固定线程预算内实现这些算法；不要求第二语言、远程调度或持久事件平台。完整图形界面亦非前置：已有客户端可对当前数据与结果接口作操作；需要生成某个UI目标时由对应供给负责。复用同一机制不意味着用这个图工具取代全部产品范围。

<a id="cross-software-author-example"></a>
## 跨软件开发主面：关系、保持与行为修改

本节检验的不是某行业库名，也不是省略了多少类型注解，而是同一套开发机制如何表达**结果变化、结构关系、时序、资源与工程修改**。下面的中文投影是`query(view="contract")`等既有接口的阅读结果，不是新增可执行DSL、必填表或独立需求文件。代码/关系节点由真实定义、原要求和类型取得；自然语言尚未准确绑定时只作为候选保留。

主协议由[跨软件意图合同](../../docs/作者/组合/跨软件需求合同.md#cross-software-intent-contract)拥有。当前范本的语义和算法是设计交付；没有宣称已安装名为“万能意图”的软件。

### 1. 首次创建软件能力，与立刻运行该能力不同

请求：“给这个本地工具增加批量改名能力；保留文件内容，发生目标名冲突时不要覆盖。”

实际作者阅读面应先给：

```text
对象：所选文件的名称映射
输入：当前选择集、命名规则
结果：每个输入身份对应一个目标名；所有目标在宿主比较规则下无冲突
保持：文件内容、未选文件和未请求的工程行为
运行策略：先生成可读预览，只有明确执行时才修改文件
待明确：后缀处理等真实命名政策（已有定义能确定时不再询问）
```

它可以与文本替换、AST改写、数据映射复用“论域→关系→保持→结果”骨架，但文件身份、路径碰撞和现实作用由文件方法解释，不能照搬纯列表map。

本例固定一种有限命名政策：同目录普通文件，输入给出旧名中的stem与suffix，更新为`stem + tag + suffix`；分割由已选文件名规则承担，不从最后一个点猜所有平台语义。不跟随目录与符号链接，不更改内容；更广文件类型由实际合同另行处理。大小写折叠、规范等价与宿主保留名按已取得宿主能力校验。

**实现过程：**取得所选文件身份和名称基础；对全部输入计算目标名；检查目标合法、内部单射、未选占用与范围；形成有前像的只读改名计划；返回原名/新名和冲突。命名谓词错误或某条目标不合法时，不开始实际改名。打开预览不读写无关文件内容，更不获取目录外权限。

真正执行时重新核所需前像与权限。目标被本批另一源占用的，建立名字占用依赖，先处理可腾空部分；循环使用有权目录中实际预留且无冲突的临时名。每次移动记录当前可恢复的前后像。不同文件系统操作并无全局事务时，不能承诺故障中途从未变化；必须如实返回完成、未完成和恢复责任。重试按真实已发生状态继续，不能盲目再次执行全部rename。

**两个反例：**A→B且B→A，不能顺序覆盖；A→`x`且B→`X`，在不区分大小写的宿主上不是两个独立目标。`ForEach`形成规则不意味着各元素无共享约束。

后续要求将tag从`-old`改为`-done`时，只改原命名参数并重算映射。后续要求增加“覆盖目标”则改变破坏性政策和恢复要求，不能把一个false改true以后不检查旧约束。此时仅在开发目标软件功能，不会实际改名SEC工作区；如果本次另已要求试运行或执行，才进入原operation/execution。

### 2. 不同软件共同的“只显示当前结果”，不是一个布尔开关

编辑器分析、文本搜索、图像预览和交互仿真可以共享如下时序要求：

```text
对象：当前输入修订及显示结果
触发：输入改变
结果：只发布与当前输入修订相同的成功结果或错误
保持：旧计算不得覆盖新结果，工作者停止前输入不能回收
进展：输入最终稳定且计算终止时，最终给出该修订的结果或明确错误
```

这里选择“新输入替换可重算的旧请求”，不覆盖付款、文件提交或每次都必须处理的命令。相同界面外形不构成省略旧命令的权限。

**有限运行数据：**当前修订`g`；最多一份最新待启动输入`pending`；在途集合`active`（使用已有执行预算，而非预设全球并发数）；显示槽`visible`；每次计算自己的固定输入和资源持有。计算结果同时携带请求修订及其实际子数据修订。数据来自目标程序的会话，不进入SEC的每个作者候选。

**输入变化：**建立新修订和稳定输入，将其置为pending；使旧结果失去发布资格；对旧可取消任务发出请求。旧任务的执行槽与缓冲仍保持，直到实际停止或完成。空闲且有预算时启动当前pending，只取最新输入，不为每次键击累积一个必跑队列。

**完成：**先取得真实结果。比较`g`与该结果来源，并在同一逻辑串行点完成“仍为当前＋发布”；不能比较成功后解锁，再覆盖这段时间出现的新修订。过期结果不发布，但必须完成自己的释放与错误结算。释放出容量后，再调度最新pending。

**UI默认：**可保留上一幅画面以避免闪烁，但必须标示它属于旧输入、当前在处理中；不能把保留旧图算成已发布当前结果。当前失败显示当前错误，是否继续保留旧图属于可见展示政策，不由异常处理器猜测。

**退出：**停止新准入，取消或转交在途责任，最后结束会话。长时间不响应取消的工作者不能被一份过期令牌物理终止；容量耗尽时等待、隔离或按预算失败，不能无限启新线程。

输入g1、g2先后出现，g2先完成则显示g2；g1后完成只结算。不响应取消的g1使全部容量占用时，pending保留g2，但不承诺它在没有可用环境的条件下一定按时开始。未声明硬期限不能用一个任意毫秒阈值充当保证。

后续开发操作“允许显示逐步改进的部分结果”改变了允许轨迹：同修订内还需要单调进度或结果修订。之前的一次完成协议不能直接复用为任意流。工具应定位和修改发布关系及消费者，而不是只改“latest=true”。

### 3. 数据结构需求：反向查询，不等于必须增加一个prev字段

请求：“保持原来的正向访问和节点身份，新增反向查找，并在所选输入范围内保证相应查询复杂度。”

先确定现有逻辑关系R。共同要求是：

```text
pred(v) = { u | (u,v) ∈ R }
正向关系、节点身份与原有次序保持
任何插入、删除与重定向之后，上式继续成立
```

如果输入真是单链：每个节点至多一个后继、至多一个前驱，且满足所选首尾、连通与无环规则，那么prev可为可空单引用。如果合法输入允许a→c、b→c，反向结果应为{a,b}，一个prev字段会丢信息。若原任务只是当前只向前的链，增加反向索引不要求把所有其他数据结构都转成双向链。

**表示选择：**只提供反向查询，可以扫描R；需要每键常数级定位且允许额外内存时，可以建立哈希反向索引，但最坏界／均摊界及哈希前提必须明确；固定编号且域界合格可以直接数组；有确定最坏界要求时选择相应索引，不把普通哈希期望代签最坏常数。树节点和多重边还需要决定集合还是重数。

**本例有限实现选择：**已知节点域有稳定可用的密集编号，单链场景用并行`next[]/prev[]`数组，额外空间O(V)。`link(u,v)`同时验证u旧后继、v旧前驱和禁止环要求；修改发生在同一串行写所有者内，或构造不可变新代后原子发布。撤销旧(u,w)边要清对应反向项，增加(u,v)要设置两侧。当前数据规模需要动态环检查时，该验证成本属于更新，不冒充全部操作O(1)。允许移动子链、重接多个节点时形成联合变化，不通过顺序单改对外展示不一致状态。

单后继更新的准确差额为：先固定旧`next[u]=w`及其反向关系；在私有候选中移除旧边(u,w)，加入所请求的新边(u,v)（无目标时只移除）；检查v是否已经有不相容前驱、是否违反所选环/连通政策；修改next[u]并同时处理对应prev[w]/prev[v]。任何检查失败则不发布该候选。多个重接需要同时成立时，先在一份候选关系上检查，不让中间状态影响外部读者。发布前再核旧版本；版本已变则重新合并或冲突，不能沿旧w删除新边。

**中立与目标：**共享的是逻辑关系及代价要求；私有数组、指针或索引由后端/运行库承担。资源、地址或ABI本来是可观察合同的节点，不能无声换表示。新建反向索引也不能扩大读取原图的权限。

后续要求“保留循环列表”改变了形状约束，不是更换渲染图；后续要求“公开节点地址稳定”会收紧表示自由；只改反向视图布局不修改R。工具将三者路由到不同消费者，而不是按都叫“图”采用同一种动作。

### 4. 三个实例进入同一套开发与实现接口

| 阶段 | 批量改名 | 当前结果发布 | 反向关系 |
|---|---|---|---|
| 绑定对象 | 所选文件及名称基础 | 会话输入与发布修订 | 节点域与已有R |
| 组合要求 | 全集映射＋单射＋保持＋作用条件 | 安全轨迹＋条件进展＋资源 | 逆关系＋结构不变量＋代价界 |
| 选择实现 | 已有文件能力与当前政策 | 原状态/任务方法与调度预算 | 原数据结构、索引及联合更新 |
| 作者变更 | tag或规则、真实入口 | 输入政策、发布条件、生命周期 | 查询接口、保持条件、表示控制 |
| 产物 | 目标函数、预览与授权执行入口 | 局部状态与发布/结束逻辑 | 访问器、索引/布局和更新规则 |
| 再次修改 | 重算目标及冲突，不提前改文件 | 同输入代际与子结果修订一起核 | 新边关系重算索引，保持身份 |

三个实例复用的是现有Requirement绑定、组合检查、变化计划和来源回写，不要求新建rename/latest/prev三种核心关键字。它们的领域算法必须存在或完成实现；不能仅因可以归入表格就称已经编译生成。

### 5. 同一请求怎样成为可编辑的作者结果

用户从自然语言提出上述任务，开发AI从原要求和当前工程绑定准确含义；工具将可实例化的语义定义、实参和独立保持项放在原定义或现有Requirement来源。已有合格供给直接绑定；需要新的局部政策，则写本项目主体。不存在通用任意自然语言→完整软件的确定编译步骤。

使用者可以只改一个已知参数，也可以直接修改表达式、状态表或关系投影。准确映射均回到同一作者来源。开发AI看到的是当前受影响对象、要求差异、保持范围、实际实现和未决，不需要抄写上述完整分析字段。新增结构编辑处理器没有完成前，正常文本修改仍可使用，不能以此宣称结构修改也已支持。

维护时依次反查：同一个要求在不同软件中能否复用共同含义；是否有缺失的保持或进展导致伪成功；是否把表示选择偷换成需求；是否仅隐藏了仍需重复维护的内容；第二次修改能否落到原槽而非全工程重写。类型标注少、代码行数少和有一张图都不能独自通过这些检查。

## 一个信息变更如何贯通规范、实现与实际发行

给定一条维护任务：让工具的资产操作支持需要真正空目录的工程，同时保证文档、实现、测试与发行可以准确查证。这个例子展示设计后的操作，不声称以下构建或运行已经发生。

先从[资产规范](../../docs/作者/工程源/资产与非源码.md)取得三个put分支，从来源条目取得Git前端与空tree的范围，从原U032取得现实格式和宿主的剩余。名称都带directory不表示它们提供相同能力。维护者只需要提交独特语义要求，不必自己填写每个知识图节点。

现有propose的draft层可以包含如下**结构例**；`<真实候选引用>`必须由本次实际工程替换，下面不是可直接作用的真实请求。它只是已经定义asset-change的一个directory分支，不创建新工具：

```json
{"kind":"asset-change","base":"<真实候选引用>","entries":[{"op":"put","kind":"directory","path":"assets/empty-input"}]}
```

同一条目增加contentRef、linkTarget或encoding就不再合法。草稿合法只证明字段符合，形成候选还需真实base、当前路径前像和目标能力；实际创建仍通过原apply/operation准入。存Git时必须另外取得该工程的真实目录持久方案，不能默认往里面塞占位文件。

接口变更的消费者包括真实读写器、序列化/校验、错误说明、适配器、构建与交付成员以及测试。只有修改规范和书面案例时，状态是设计已定；没有实际代码与环境就不填“实现通过”。若随后在有授权任务中产生代码提交C、工具链T、锁L与制品B，InformationSelection将它们和规范N固定；真实测试E只支持对B的明确Claim与环境。资料论文、D理由和U剩余可在多个任务入口显示，但不自动成为B的运行依赖。

发行时核目录成员、文件字节、权限与实际安装/重建语义。旧发行继续固定旧选择；新文档默认不改变它。若只保存了检查报告而丢了不可重建的源或环境，报告可读不等于能复验；若尚有失败创建/保存操作需要前像，资料清理不得释放其恢复根。后续需求改为“不再需要该目录”时，要同时核还在使用它的旧发行和实际删除前像，而不是删规范一句话就清理所有实例。

从一个入口可以沿有类型关系找到完整链，但没有哪条导航边会执行构建、授权部署或让所有历史永久保活。相同事实可在作者、审查和运行入口出现，仍只维护其实际拥有者。

<a id="completion-development-change"></a>
## 同一工程的并行完成、分页、数值与发布恢复修改

这是在本范本既有库/CLI多根工程上的连续开发情景；不是已编译的参考工程，也不声称所有模块默认运行AD或接远端发布。作者只使用已有源和方法选择，不填写TaskExit、RetryBasis、页缓冲或导数错误通道；这些在实现与检查中产生。某次纯库修改不使用下面某分支，就不为它实例化任务、队列、tape或持久存储。

**初始C1。** 任务是维护已有生成器，输出library与cli两个TS根，并在CLI提供一次跨两资料源的确定排序查询。另有一个独立数值工具入口需要有限JVP；发布是单独授权的operation，不藏进preview或compute-build。原生TS作为唯一可编辑源的区域继续直接修改；已有中立定义只在其真实范围生成，不补一份TS镜像。

**改动的实际写集。** 开发者先用原query定位相关源与方法合同，再用files/edits或generated-edit形成一份C2。相交写集包括：原任务装配/执行适配、资料Provider页适配及CLI消费者、流方法的选择/目标映射、AD所选规则/目标适配、结果消息与本例的验收期望；恢复修改还要纳入operation消费者与其状态说明。拟定文件职责见[完成边界接合](../../docs/架构/装配/能力接合与文件责任.md#completion-physical-seams)。不是只改一份错误标签或给CLI增加一个“重试”按钮。

**路径一：两根成功或一根失败。** library与cli的临时输出各自先登记后启动，成功Own先归完成槽。CLI先成功不宣布整组成功；library随后成功才按作者根顺序领取两个结果，交ArtifactSet封存。library失败而CLI成功时，保存实际单根状态；若任务选择all整体不采用，则清理尚未被领取的CLI临时Own，但不能删除先前已发行的CLI。若该子结果已合法发布为另一独立任务成果，它不再属于本组合的未采用临时值，不能回收。还在写缓冲的工作者保持占用直到真的停止；调用方切换C3不使其资源变成C3的资源。

**路径二：跨资料源分页。** A返回[a,c]，B暂未给出可比较下界。默认要求全局升序首屏时，不先把[a,c]标成首屏；可等待或给明确的A局部预览。B取得[b,d]后，limit=2返回[a,b]，未展示c,d保留在本查询续页；下页从c,d开始，而不是拿A/B已经前移的游标越过它们。B的快照过期时，不能把它的新版本混进A旧版仍标同一完整查询；退化成明确分项视图或取得一份新的完整选择。一个来源被撤权，旧缓存仍可供其他有权用途，但不能继续向该主体披露其内容/计数。

**路径三：处理顺序流。** 数值工具可消费按序输入，但不是靠任务all的“先观察错误”替代mapOrdered合同。0还在计算、1已失败时，若0成功就先发布0再失败1；若0也失败则失败0。紧随0/1接受的watermark保存cut，不越过在途数据关闭窗口；最后End等待有界Final输出实际发出。当前credit余额为0时暂停数据交付；不继续申请只会在旧额度消费后暂停，request(0)不能撤回旧额度且是协议错误。要停止在途通知须走实际取消/结算，不用更换一个计数伪造。

**路径四：数值规则回归。** 仍按已有JVP方法给函数、x和seed。对x=1、dx=1e308、函数依次求2*x与1/(x-x)，C2的目标必须先保存切向数值故障，再发现原值除零而返回PrimalFailure；把函数改为只有2*x才得到NumericFailure。实际源码定位指向各自阶段，不在观察面把它们都压成“运算失败”。C3后来只改CLI消息，旧数值运行仍绑定C2及其方法修订，不从当前C3标签猜旧结果。

**路径五：发布与恢复。** 获准发布精确产物后响应丢失，query当前目标为旧值。开发者继续用同operation查询，不创建新业务键。真实目标提供持续有效同意图去重时可按原载荷继续；否则先关闭旧尝试并取得其后无效果观察，再发新尝试。无法取得这两种依据时，界面给出当前观察、在途未知与独立可用制品，不谎报未执行，也不把用户点击重试当作旧尝试已关闭。暂存编译可以重做；已发外部通知不能跟着一起重放。

**第二次修改和较小路线。** C3可以把并发降为1或只查询单一本地Provider，只要不改变用户选择的排序/失败/覆盖保证就仍是合格替代；未要求AD的工具不装载AD实现。将首屏改成“各源分组预览”是需求与消费者的明确变化，不是在旧强结果下自动降级。规则修订让相关计划/缓存失效，源字节与独立根仍按真实依赖复用；原六工具的字段和保存前像规则保持。

验证不能只看成功屏幕：需要记录任务拥有/领取与清理、已发流前缀/控制cut、primal与导数阶段、Provider页绑定/缓冲、外部尝试实际终结和源版本。具体固定输入及反证在[CPL接合案例](../../docs/运行/验收/信息与完成边界案例.md#completion-boundary-cases)。本范本没有调用真实Provider、运行编译器或把任何情景标为已通过。

### A. 第一版作者文件、生成形状与完整的本地消费者

在实际选择该纯模块自用中立源时，`src/entry/exit-policy.sec`是唯一作者；既有Native-only实现也合法，不能两份同时维护。此文件的全部内容为：

```sec
export type ReplyFacts = {
  inputValid: Bool,
  finalReceived: Bool,
  goalMet: Bool
};

export fn exitCode(f: ReplyFacts) -> Int =
  if !f.inputValid then 2
  else if !f.finalReceived then 3
  else if f.goalMet then 0
  else 1;
```

输入由真实客户端解码/传输和请求目的产生，不接受目标程序往stdout打印这三个布尔值作为权威结果。 finalReceived表示客户端取得该次请求的最终响应，不表示异步目标已经停止；domain-result的requestSatisfied按原请求目的判断。只请求启动且已可靠受理可为true，同时响应仍保留运行中；明确要求完成时才要求相应终态。该纯模块不获得写进程、文件或网络的权限。所选TS Int画像使用bigint时，对应`generated/entry/exit-policy.ts`的完整目标形状如下；它是设计预期，不是本轮编译器运行产物：

```ts
export interface ReplyFacts {
  readonly inputValid: boolean;
  readonly finalReceived: boolean;
  readonly goalMet: boolean;
}

export function exitCode(f: ReplyFacts): bigint {
  return !f.inputValid ? 2n : !f.finalReceived ? 3n : f.goalMet ? 0n : 1n;
}
```

`src/entry/exit-status.ts`是原生调用方，可独立维护，完整内容为：

```ts
import { exitCode } from '../../generated/entry/exit-policy.js';

export type CliFinish =
  | { readonly kind: 'invalid-request' }
  | { readonly kind: 'no-final-result' }
  | { readonly kind: 'domain-result'; readonly requestSatisfied: boolean };

export function processExitCode(finish: CliFinish): 0 | 1 | 2 | 3 {
  const code = exitCode({
    inputValid: finish.kind !== 'invalid-request',
    finalReceived: finish.kind === 'domain-result',
    goalMet: finish.kind === 'domain-result' && finish.requestSatisfied
  });
  if (code === 0n) return 0;
  if (code === 1n) return 1;
  if (code === 2n) return 2;
  if (code === 3n) return 3;
  throw new Error('EXIT_POLICY_OUT_OF_RANGE');
}
```

最后的有限检查只防真实交接超域；不能把任意Int直接截断成进程状态。该函数返回值，不调用process.exit；由原CLI拥有者先结算/移交必要运行责任、交付结果，再按宿主退出。函数内部异常归客户端失败，不改造成目标程序断言失败。真实TS构建必须支持所选模块与bigint画像；缺条件先返回不支持，不用Number精度转换掩盖。

原生消费者新全文为：

```ts
import { exitCode } from '../../generated/entry/exit-policy.js';

export type CliFinish =
  | { readonly kind: 'invalid-request' }
  | { readonly kind: 'no-final-result' }
  | { readonly kind: 'domain-result'; readonly requestSatisfied: boolean;
      readonly coverageComplete: boolean };

export function processExitCode(
  finish: CliFinish,
  purpose: { readonly requiresCompleteCoverage: boolean }
): 0 | 1 | 2 | 3 {
  const code = exitCode({
    inputValid: finish.kind !== 'invalid-request',
    finalReceived: finish.kind === 'domain-result',
    goalMet: finish.kind === 'domain-result' && finish.requestSatisfied,
    requiresCompleteCoverage: purpose.requiresCompleteCoverage,
    coverageMet: finish.kind === 'domain-result' && finish.coverageComplete
  });
  if (code === 0n) return 0;
  if (code === 1n) return 1;
  if (code === 2n) return 2;
  if (code === 3n) return 3;
  throw new Error('EXIT_POLICY_OUT_OF_RANGE');
}
```

新增字段必须由真实query覆盖/检查目的和调用上下文映射，而不是输入请求多一个任意safe=true。无coverage概念的请求，其purpose不要求完整；覆盖未知不能当true。额外还要改所有processExitCode消费者、结果解码/任务目的传递、CLI消息、测试期望和公开类型出口。缺一个调用方时可以保存草稿，但不能用上一版A2证明A3可用；如果公开库API变化需其兼容与接受范围，不静默破坏第三方调用。

对应新增期望：完整覆盖且正常→0；局部查询且目的允许局部→0并保留partial；要求完整但partial→1；未知结果仍→3；非法请求仍→2。此变化可以只影响结果策略及相关类型，不必重跑无关所有领域算法。

### E. 并行、审查、运行和退出

甲在C2改策略，乙改帮助消息和另一公共结果字段。帮助内容同一写位置或共享协议变动需协调，不能因为.sec和.ts不同文件就自动合并。工具保留两组改动，形成C3并重查实际读集；没有语义冲突的注释改动可以保留，不全局归零。只暂存策略不暂存消费者时，S3与C3不同，不能贴C3类型通过或测试结果。

需要修改生成TS中的某一条件可走generated-edit并回到这份唯一.sec，不能直接把目标手改当作新作者；映射不唯一先保留目标草稿。查看旧运行的退出仍绑定旧B2，C3新构建对应B3。真实运行/调试/profile按任务分别请求，不因为测试或生成自动发生。

交付时给准确源、目标成员、已执行检查、仍未执行范围和可用文档；本机Runtime临时planRef不放进跨会话说明冒充可恢复材料。可直接交付作者文件及依赖信息，或由真实保留提供者保存引用；旧操作有未结算责任时继续按其拥有者处理，不能通过退出CLI假装取消。这个完整会话的后续产品案例见[DF验收](../../docs/运行/验收/开发面案例.md#developer-surface-cases)。

## 同一意图采用原生供给、修改并退出生成的完整轨迹

本例继续使用[区间成品规范](../成品形态/规则合同.md)，不另造同名行为。假定工程确有一个可取得的原生TS实现包和适用检查依据；它们是例子的显式前提，不是本包已安装的产品。

**初次采用：** 产品方在结构源固定覆盖、顺序、精确整数与错误要求；实现维护者继续修改已有TS文件和它的原生依赖锁。两者通过同一使用点绑定关联，不复制算法到JSON或`.sec`。原库已经符合公开同步调用时直接重导出；CLI只产生真实文本协议、预算、错误与退出适配。产物目录、环境依赖和所需许可证由实际成员合同决定，不能从范本文件名推定。

**实现缺陷修复：** 只修改原生主体并重新捕获、检查对应需求和全部实际使用该主体的根。结构意图不必改写；原需求接受来源不移到新测试期望上。旧运行继续绑定旧制品；修复发布与是否替换运行按原协议执行。

**要求升级：** 将相接策略改为KeepTouching时，先检查既有供给的真实可选参数。已有能力满足则改变绑定实参和相交生成；否则取得新方法或受委派创作，保留准确缺项。不能让实现缺能力迫使作者改回MergeTouching，也不能仅凭两个接口同形宣布适配成立。

**目标增加：** TS根可继续交付；没有第二目标的合格供给时，新增根未完成。不能把TS源换后缀当作跨语言实现，也不要求先翻译当前全仓才允许继续TS维护。

**选择手改生成适配：** 差异先是目标草稿，能唯一映射则回到适配拥有的作者决定。明确接管时，在候选中转移该区域编辑责任并取消相交生成声明；原生文件成为唯一写源，独立需求与余下生成区域保留。持久应用失败沿实际前像与结果恢复，不允许一半接管、一半仍被生成器无条件覆盖。

**不需要结构层的独立工具：** 一个只有单目标、没有独立意图关系需求的小修复，可直接用原生文件、原框架和原测试完成。不得为保持示例整齐强塞一份结构镜像；这不改变结构意图在需要它的新产品中的首选地位。
