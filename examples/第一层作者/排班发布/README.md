# 排班发布：同一份内容上的硬关系与确认行为

本例把[值班安排和排班发布台](../开发面V1意图稿.md)接到[持续确认](../持续确认/README.md)的准确作者源。产品决定的是：一份固定资料下，每班恰有一人、只安排可到场人员、同人班次不重叠；预览和发布保持用户选择的那份安排。它不要求开发者写排班搜索器、监听器或发布阶段函数。

## 唯一资料与同一内容

[排班关系](schedule.module.json)定义普通有限资料及`ScheduleFeasible(data, content)`。人员是整数身份的非空有限集合；班次是带唯一整数id、start/end的有限记录集合；区间左闭右开、end>start，端点使用同一固定时间轴上的精确分钟。人员与班次的身份不由显示顺序产生。可到场与安排透明采用原确认模块的`Content`，即原有person/shift配对集合，未另造同形但不同身份的Pair。

[发布装配](publication.module.json)只采用一个原`ConfirmationSession`。系统要求在一个`dataset`实参处固定全部人员、班次、可到场；该值在整个会话采用中不变。它不是可变资料服务的别名，也不是Edit.revision：后者仍是文档内容修订。资料变化形成新的产品采用/会话，旧确认责任沿旧资料结算；本例没有暗许热换资料。

同一`FeasiblePublication`要求同时约束真实editsView和previewsView。每个被接收编辑和每个可见预览的content都应用同一个硬关系；两个观察发生地址都指向装配中的同一个publication组件。根、事件或观察的名称相似不构成此关系。[Project](../scheduling.project.json)捕获原确认模块、时间与源发生合同及本例目标合同；没有复制确认行为体或改变其四类事件。

静态资料遵守唯一[静态值解释](../../../docs/作者/结构化源码.md#typed-static-literal-codec)：整数限于该JSON精确可表示范围，集合用无重复元素数组承载，record按具名字段；顺序不改变集合含义。元素不合型、重复班次id、非法区间、空人员或悬空可到场对均拒绝，不能靠删掉该项“修复”。生产Reader/静态值codec资格尚未实现，结构Schema本身不证明这些语义。

## 从要求到发布的完整推导

记固定资料为D、硬关系为H(D,C)、原确认合同为K。H先检查资料有效，再检查：安排所有对属于人员×班次且可到场；每个班次恰有一个安排；同一人员的不同班次区间不相交。覆盖范围包含资料中全部班次，空班次时唯一安排为空；不是从已有安排反推“应当覆盖”的班次。

组合保持`K ∧ ∀e∈Edits.H(D,e.content) ∧ ∀v∈Previews.H(D,v.content)`。后一项既明确产品责任，也使观察旁路直接暴露；不能只把预览“恰好来自某编辑”写在解释文字里。原K对每个v要求实际匹配e并保持相同content/revision，因此输入满足H时可推出预览满足H。对每个生效a，原K给出真实确认c及它所指的预览v，并保持对应修订；原观察合同又把该修订绑定到不可变内容及真实文档作用。因此发布的是H合格的v.content。这里依赖完整观察与修订—内容一致性，不能仅凭一条application消息推出真实发布。

上述推导对任意满足这些前提的会话历史成立，不依赖两人两班样例。它没有保证环境会确认，也没有把未来会话关闭或后来非法输入用作免除已发生责任的理由。原因果期限证明继续需要方法能力；排班验证成本必须计入同一响应预算，不得把验证结束时刻倒当编辑发生时刻。

## 偏好不能改变已经给定的内容

“降低最大个人总工时”比较的是系统尚可选择的合格安排。精确代价为`cost(D,C)=max_{p∈People} Σ_{(p,s)∈C}(s.end-s.start)`，空和为0；人员非空保证max有定义。固定用户C后，检查的是H(D,C)，不能因另一个C'代价更低而改预览或发布内容。

有限候选域可以通过每班选择一个人员完整枚举；H剔除不合格候选。在资料有效时，合格配对集合与满足全部限制的“班次→人员”全函数一一对应：覆盖和唯一性给出函数，范围与可到场给出合法值，不重叠限制相同；反向取函数图得到原集合。该映射覆盖所有有限人员/班次输入，包括空班次和无解，不只覆盖例子。候选有限且每个代价为非负整数，非空可行集必有最小值；不能据此宣称求解便宜、已实现或给定用户方案必须是最优。

这里借鉴成熟约束建模对固定参数、决策变量、满足问题与优化问题的区分；MiniZinc的官方说明给出了这种分离。Gift本例复用自己的关系、采用与观察语义，不把模型代码放到一个未知解释器后面。[MiniZinc基本建模](https://docs.minizinc.org/en/2.10.1/modelling.html)。

[有参测量工程](../有参测量/README.md)现已给出Goal.prefer的准确测量实参、真实峰值定义、有限Set普通供给及修改比较依据的源码。它独立描述候选建议，未把优化偏好升格为本发布组件的预览硬要求。优化Method、建议Target与本产品的采用、生产Reader和真实运行仍未实现；有限最优存在证明不代签这些交付。

## 再次修改及反例

[收紧可到场](changes/remove-availability.json)只撤去人员2对班次12的可到场对，保留人员、全部班次、确认组件和期限。它针对固定前像形成新修订；原会话不被重解释。旧安排若含该对，在新采用下不合格；不含该对且仍满足覆盖/不重叠的安排保持合格。

两人、两个相接的四小时班次：一人两班与一人一班都硬合格，峰值分别为八小时和四小时；系统形成候选可偏好后者，用户明确给定前者仍可预览并确认。删去某班唯一可到场人时无解，不能漏班；加入未知人员或班次、重复同班分配、同人重叠、将旧预览换成新优化结果均违反相应合同。拒绝非法草稿必须明确原因和修正位置，不从已接收观察域删除失败项来获得通过。

## 交付边界

本例是准确源码与组合证明，结构/有限模型检查只证明对应输入。生产Reader、类型与来源资格、编辑准入UI、实际观察、方法、目标降低、运行和物理期限未执行。资料输入的权限、多人协作、同会话资料切换、持久化和灾难恢复也不由本单用户内存会话推导获得。后续扩大产品域时明确修改相应合同，不能先把未知问题当成功。
