# 开发面V1连续意图稿

这是[通用语言开发面](通用语言完整设计.md)中的实际作者记法实例，固定构造见[对象、要求、选择](../../docs/作者/第一层语言.md#intent-author-core)。各段表示连续开发时看到和修改的同一份意图；不是要求同时维护多个版本，也不是已经可执行的文本语法。前两节使用已有含义的短视图，后面给出没有预置业务能力时的准确写法；两种视图编辑同一内容。

## 初次形成

```text
意图「整理次序」
  对象：本次待展示的条目
  结果：按优先级从高到低排列；同优先级保留原次序
  保持：全部条目及重复出现；条目内容；原序列

采用「整理次序」于「待办页」的筛选结果
采用「整理次序」于「导出预览」的筛选结果
偏好：在全部要求满足时，减少额外内存
```

项目上下文确定条目、优先级及筛选范围。缺少会改变结果的信息时，形成过程只取得该必要区别；不会要求作者提供比较函数、公开类型、ID或完整内部规格。多个关系同时约束各采用处的同一个结果。

## 只改一个采用处

```text
修改「导出预览」本处
  将「排序依据」改为：创建时间从新到旧
  其余有效要求沿用
```

该编辑在有权的范围内形成明确局部修订，不改共享定义与待办页。修改后当前意图呈现为：

```text
采用「整理次序」于「待办页」的筛选结果
采用「整理次序」于「导出预览」的筛选结果
  本处修订：排序依据为创建时间从新到旧
偏好：在全部要求满足时，减少额外内存
```

本处修订保留同键原序、成员和重复出现、条目内容及原资料；真正依赖旧排序决定的派生说明重新形成，不盲目沿用。原定义未开放该参数时，界面标明局部含义已修订，不把它伪装成未改定义的普通参数。

## 查看有效含义与来源

```text
导出预览
  当前范围：本处筛选结果
  当前结果：创建时间降序，同时间保留原次序
  仍然保持：全部条目及重复出现、条目内容、原资料
  来源：本处排序修订＋「整理次序」的保持关系＋本处筛选范围
  待办页：未改变
```

这是同源查询视图，不另保存一份可写摘要。隐藏的是可推导和实现细节；没有隐藏独立约束或未定决定。

## 放开偏好

```text
撤去本处「减少额外内存」偏好
```

本例的“本处”指当前包含两处采用的作者意图。只删除该偏好，不删除任何结果或保持关系。若焦点不明确，界面先定位本次作用范围，不能把相同文字的其他偏好一起删除。

## 在新领域继续组合

```text
意图「报名名额」
  对象：同一场次的申请与名额
  结果：合格申请在本次判定时名额足够则接受并分配，否则明确说明资格或缺额原因
  保持：成功分配总量不超过本场次的总名额；同一业务请求不重复占用

产品「报名工作台」
  名额处理：采用「报名名额」，网页与现场共享同一场次名额
  申请列表：采用「整理次序」，对象为当前筛选的申请
  共同保持：列表只呈现相应版本的报名结果，不因排序改变报名状态
```

本例报名期间总名额固定，可用名额是总名额减去已成功分配的数量；累计分配受总额约束，本次申请是否足够则判断剩余量。新业务含义仍用对象、关系、保持、范围和采用表达；内部技术机制不变成作者字段。申请身份和结果版本由已有上下文继承或在形成时取得必要决定，不能凭名称猜定。此例说明跨需求组合的含义，没有实现库存服务、用户界面或运行时同步。

<a id="new-intent-without-catalog"></a>
## 没有现成能力时，直接创作新意图

开发者输入：“把本周班次均衡地分给有空的人员。”本例固定人员为非空有限集合，班次为有限集合，时段左闭右开且结束晚于开始；可到场是已有人员与班次的关系。不是要求开发者先定义排班函数。

```text
意图「值班安排」
  对象：
    已有 人员、班次、可到场 = 本次排班资料
    求得 安排：人员与班次之间的分配关系
  要求：
    每个 s 属于 班次：恰好一个 p 属于 人员：(p, s) 属于 安排
    每个 (p, s) 属于 安排：(p, s) 属于 可到场
    每个 (p, a) 属于 安排：每个 (q, b) 属于 安排：
      若 p = q 且 a ≠ b 则 a与b的时间区间不相交
  选择：
    偏好：减少 人员中个人总值班时长的最大值
```

时长为结束减开始，个人总时长为所分班次时长之和，空和为0。因人员非空，最大值有定义。时间区间不相交展开为`a.结束 ≤ b.开始 或 b.结束 ≤ a.开始`；“或”是任一的行内写法。安排的范围只有人员×班次，没有额外人员或虚构班次。这里“均衡”已被具体化，普通重建不重新解释这个词。

小例：甲、乙都可到场，两个不相交且各4小时的班次。一人两班的最大个人时长是8小时，一人一班是4小时，当前偏好选择后者；哪人先上仍开放。若某班次无人可到场，不能悄悄删掉该班次使结果成功。

再次修改只写独立差异：

```text
修改「值班安排」本处
  增加要求：每个 p 属于 人员：数量({s 属于 班次 | (p, s) 属于 安排}) ≤ 2
```

它与全部旧要求共同成立；不重写可到场和覆盖规则。若只有甲一人且有三个班次，结果是要求冲突，不是自动把第三班漏掉。撤回这条尚未采用的增加只撤去两班上限，不撤去原来的要求和偏好。

## 持续交互使用同一套构造

本例为单文档、单用户的内存编辑会话，环境保证本地会话可继续运行，暂不承诺磁盘持久化或断电恢复。编辑发生由用户输入，预览与生效发生由产品给出；编辑的修订与内容由原作者对象取得，不要求人填写机器ID。每次确认指向用户实际看到的一份预览；本例选择允许确认旧预览，多个确认按用户会话次序生效。

```text
意图「确认后生效」
  对象：
    已有 文档 = 本会话编辑的同一文档
    外来 编辑：本会话内带修订及内容的合法编辑发生
    外来 确认：本会话内对已展示预览的用户确认发生
    求得 预览、生效：本会话内的产品可见发生
  要求：
    每次 e 属于 编辑 后 1秒 内：
      存在 v 属于 预览：全部 { v.编辑 = e; v.内容 = e.内容 }
    每次 c 属于 确认 后 1秒 内：
      存在 a 属于 生效：全部 { a.确认 = c; a.修订 = c.预览.编辑.修订 }
    每个 a 属于 生效：存在 c 属于 确认：全部 {
      a.确认 = c; a.修订 = c.预览.编辑.修订; a.时刻 ≥ c.时刻
    }
    每个 c 属于 确认：至多一个 a 属于 生效：a.确认 = c
    每个 a, b 属于 生效：
      若 a.确认 在会话次序上早于 b.确认 则 a 在生效次序上早于 b
```

每个v在对应编辑之后展示，文档只因生效发生切换为该发生的修订；这些是本例“预览/生效”发生的准确对象含义。查询事件集合时只含当前观察点已发生的成员，不能用未来的预览满足当前期限。`1秒`是本例主动选择的可观察期限，不是语言默认；环境不足时保留不能保证期限的事实，不能把无限迟延声称为通过。普通运行错误和断连若纳入产品支持域，应沿同样构造补其允许出口，不能悄悄用任意错误响应代替本例承诺的成功路径。

这段约束的结果可以核对：编辑A→预览A→编辑B→确认预览A，生效的是A；没有确认就没有生效；两次编辑各自有预览义务；某次确认一直不生效违反进展。未发生确认时，产品不需要虚构用户最终会确认。

它没有规定监听器、消息队列、锁、事务、缓存或生成代码组织；前后顺序来自产品交互本身。若只想把反馈期限从1秒改为500毫秒，只修本处对应时间值；若要“只能确认最新预览”，须明确修改确认接受关系与旧预览被拒绝的正常响应，不能仅追加一个禁令让旧合法确认永久悬空。

[持续确认工程](持续确认/README.md)给出这一意图以有限配对集合为内容的实际模块、产品根、四类事件/观察、准确供给、期限后继及条件性因果策略证明。单根和双实例采用同一参数化组件/Goal/关系，分别在真正采用处配置期限并保持独立会话；普通快照与逐评价点观察域明确区分。[排班发布工程](排班发布/README.md)进一步把固定资料和硬关系接到真实编辑、预览及同一确认发布；[有参测量](有参测量/README.md)给出候选建议的准确测量输入、峰值解释与修改比较依据。优化Method及真实执行仍未实现，不以样稿或有限检查签整个通用语言完成。

## 组合成一个产品，再修改一个使用处

```text
意图「排班发布台」
  对象：
    已有 人员、班次、可到场 = 本周资料
    已有 文档 = 排班文档
    外来 编辑：本会话内内容满足排班硬要求的编辑发生
    外来 确认：本会话内对已展示预览的用户确认发生
    求得 预览、生效：本会话内的产品可见发生
  要求：
    采用「确认后生效」(文档 = 文档, 编辑 = 编辑, 确认 = 确认, 预览 = 预览, 生效 = 生效)
    每个 v 属于 预览：
      满足「值班安排」的硬要求(人员 = 人员, 班次 = 班次, 可到场 = 可到场, 安排 = v.内容)
```

本组合把可进入预览的编辑域限定为满足排班硬要求的版本；这是此产品创建时明确选择的输入域，不改变通用编辑意图的原定义。界面草稿可暂不满足，但必须在进入本确认会话前给出区别与修正位置；不将无效草稿直接当成本例承诺成功预览的输入。准确源将硬关系命名为ScheduleFeasible并复用，而不是把含偏好的完整定义默默当成硬谓词。排班偏好用于系统形成候选，用户已经指定的合格安排不因存在更优安排被偷偷替换。发布的安排正是确认预览的安排，不能重新优化出另一份再发布。

需要在另一个场景采用时，绑定不同文档和资料即可；共享资料必须绑定同一对象，配置相同不会隐式共享。只改排班发布台的本处期限，不改变其他采用「确认后生效」的位置。共享定义的修改则显示全部实际采用处的影响。

<a id="whole-engineering-control-example"></a>
## 同一工程中直接控制架构、源码、资源与升级

这里展示工程控制，而不是重新定义整个检索业务。输入是一个已有查询/索引产品的准确业务合同、公共API修订、源码及资产边界；这些均由原工程取得。下面的组件名是本项目角色，不是Gift核心能力。查询核接受已给定的查询和数据快照，返回该合同规定的结果；数据取得、身份权限和外部通信分别由相应边界承担。`工程`指同一候选工程，组件、源码、运行及迁移关系都关联它，不能各自挑不同版本通过。

```text
意图「检索工程的结构与交付」
  对象：
    已有 原工程、业务合同、公共API、非受管资产 = 本次固定的原工程上下文
    已有 工作负载、内存计量口径 = 本产品已接受的运行条件
    求得 工程：保持业务合同并具有命令行入口、查询库和管理界面的完整工程
    求得 查询核、服务入口、数据访问、管理界面：工程内分别承担查询计算、服务边界、索引访问、管理交互的组件
    求得 命令行产物、查询库产物、界面产物：工程内分别承载服务入口、公开查询核、管理界面的目标产物
    求得 服务实例：工程部署方案中承载服务入口及其查询核、数据访问的进程实例角色
    求得 服务进程资源：服务实例共用的资源预算，内存维度按已有计量口径解释
    求得 禁止的实现：工程实际使用的全部界面、网络、存储实现所组成的集合
  要求：
    工程满足业务合同
    工程的组件包含 {查询核, 服务入口, 数据访问, 管理界面}
    查询核的编译期可达依赖 与 禁止的实现 不相交
    查询核的运行调用 仅经过 本次公开的输入值与查询策略边界
    每个 s 属于 工程的可变索引状态：其写入所有者是 数据访问
    工程的公开查询API与公共API在已承诺使用域内兼容
    工程对非受管资产的输出行为是保留其原始字节
    在规定工作负载中：按已有口径计入服务进程资源的服务实例总峰值内存 ≤ 512 MiB
    每次查询取消完成后：该查询的独占临时资源已经释放
    每个共享索引：仍有使用者时不得回收，最后使用者退出后最终释放
    每个升级前已确认的索引提交：升级后仍可按其原合同读取
    采用「可替换查询策略」(主体 = 查询核, 共同预算 = 服务进程资源)
  选择：
    固定 命令行产物与查询库产物的目标语言 = Rust
    固定 界面产物的目标语言 = TypeScript
    固定 公开入口的结构政策 = preserve
    固定 查询核私有实现区域的结构政策 = reorganize
    交由系统：满足全部要求的私有算法、数据结构和源码内部组织
```

以上求得声明为本候选引入角色，原工程对象保留为输入；构建候选可以沿来源保留合格原组件，但不能把候选直接当成已修改的原工程或已部署实例。产物承载、服务实例中的组件成员及预算共享都是声明范围内必须成立的关系，不只是显示名称。命令行产物含服务入口并使用查询库；界面产物通过业务合同中的服务边界交互，不进入查询核的运行实例。`禁止的实现`必须从实际成员及其准确供给职责取得完整集合，包括原有和新增实现，不能自行挑子集、改标签或仅依目录判断。公开入口的控制范围为工程对应公共API的实际源码成员；私有范围为查询核不属于该公共表面的实现区域。

模式采用是一份包含结构与实现控制的普通定义应用，按原Pattern/Control进入有效要求；它不是执行某个策略。其两个角色及准确含义由[第一层语言](../../docs/作者/第一层语言.md#whole-engineering-intent)给出：主体绑定本候选查询核，共同预算绑定服务实例的同一资源预算；每个已接收查询固定一次策略绑定，同次处理中不切换，全部策略保持相同查询、错误、取消与资源合同并共同计量。模式名不能替代这些内容；要求某个Rust trait/类层次时可以再固定源码形态，未要求时不强制产生该结构。

“结构政策”绑定原`generation.structure-policy`及其scope，不新增同名字段协议。公开入口与私有区域由原源码拥有关系选定，范围重叠时先报告冲突而非以后写覆盖。兼容按原API的调用、结果、错误及生命周期观察核验，不能仅比较名字和类型。非受管资产保持的是原始字节，不靠重新格式化后的文本相等代替。

内存计量口径必须明确进程边界、共享内存如何计入及允许的观测误差；本例512 MiB是硬要求，不是配置值即达标。共享预算包含所声明的索引、缓存、输出缓冲和基础运行占用，不分配四个独立的512 MiB。取消完成表示资源责任已结算，取消请求发出或用户停止等待不能代签；无法释放时保留取消未完成及准确失败，不允许永远伪装完成。无使用者后是否保留共享缓存由所选寿命合同决定，本例明确选择最终释放。升级新增的未被旧版理解的数据或不可逆外部作用另核其迁移，不能把已确认索引保持泛化成任意版本无损回退。

### 一次真实的跨层修改

作者修改：“服务内存上限改成256 MiB，公开API继续保持，其余选择不变。”只产生共同预算这一项的作者差异。系统需要重新查看共同占用及生命周期：若当前四个组件各需200 MiB且峰值重叠，组合不合格；若可分时或共享，仍须保持查询的并发、取消及响应合同，不能偷偷串行化所有请求。

可采用候选必须说明实际发生的变化，例如在既有查询合同允许时减少缓存或改变索引表示；公开源码保持范围、API和非受管字节继续不变。没有合格方案时保留预算与被冲突要求，给出准确不足；不能把256 MiB放回一个未被消费者读取的配置字段后报告成功。生成后的源码与运行证据以后各自检查，本稿不冒充已满足物理预算。

作者也可以只替换查询策略，不改组件和公开API；改变共享定义时展示所有实际使用者，而只修改某一采用处时保留其他实例。若改动影响共同状态，系统必须显示跨组件影响，不能用“本处”一词宣称物理上已经隔离。

### 这只是一个工程控制实例

分布式拓扑、设备资源、模型假设、隐私、视觉/交互布局、证据目标、费用和演进等继续沿相同作者组合进入各自准确拥有者，不局限于此例的四个组件。源控制、运行要求和实际部署分别生效；表达架构不要求现在部署，声明资源保证也不是已取得保证。完整边界见[全工程作者面](../../docs/作者/第一层语言.md#whole-engineering-intent)，不能用本例的存在证明所有大型工程都已完备覆盖。
