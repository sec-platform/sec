# 通用第一层意图语言V1：开发者行为设计

这一版设计的是**开发者怎样创造、理解、组合、控制和修改产品意图**。本轮先完成这一层抽象及其可使用的表达；内部编译、类型出口、绑定、供给与目标代码不在本版交付范围。它们可能必要，保留到后续设计，不能因前台不展示就删除。

语言定义由[第一层语言](../../docs/作者/第一层语言.md#intent-language-v1-formation)拥有。现在的主例是[完整作者工程](完整作者工程.md)：实际定义资料/关系/组件，建立两个独立采用与共享连接，固定真实公共入口，给出目标源码交付责任，并逐项展示局部修改、共享政策修改、抽取复合体与撤去实现控制。[意图稿](开发面V1意图稿.md)继续承担不同领域的有限边界例，[自举表达样本](自举表达样本.md)检查语言能否定义编译器的绑定与改名职责。记法是当前可审查的语言设计载体，不宣称已有文本Reader或IDE实现；未来文本与可视入口仍应修改同一份源码。

## 同一份源码里实际有什么

作者可以直接写`定义`形成内容，用`成员 = 采用`和`连接`构造工程，在这些内容上写`要求`，有必要时写`实现`控制，再直接修改这些同源内容。定义体仍按结构、关系、计算或组件各自解释，不把所有内容解释成函数调用或约束表达式。定义架构与连接是构造，禁止跨层依赖是要求，选择私有文件位置是实现控制；三者相关但不能混成一个资源表。

完整工程不是先填写五栏才能开始。比如“主视图和预览共享资料，各自调阈值”已经给出了独立信息，系统应形成两个采用位置和一个共享来源的准确候选。作者查看或编辑时能追到这些真实内容；没有给出的筛选算法、私有类和中间表示由系统承担。公开行为、错误政策、共享身份与生命周期不会被藏在黑箱能力名后。

系统落实的目标是完整源码工程：每个真实入口有相应实现，源成员、资产、依赖及构建入口相接，或者明确缺少哪项承接。修改参数只改该采用处，修改共享定义列出全部受影响使用，修改目标预览必须回到相应源或控制。生成文件不是第二份长期可写源码。本版只固定这些作者行为和交付结果，未交付生产生成器或证明任意关系都能自动合成。

有限构造与开放定义让领域内容可以继续扩展，不要求语言内置所有业务名字；准确专业解释仍有创作成本。这套有形成规则、含义与组合的开发语言可以称为编程语言，但它把开发者的常规责任放在必要区别和关系上，不要求把流程语句换个拼写再维护一次。自举要由第一层表达并实现自身相关编译职责；本版已有具体表达见证，未取得完整编译器源码、自生成或自编译证据。

这一路线已有需求工程、形式语义、精化、程序合成及表示评估的基础；[理论对应](../../docs/作者/第一层语言.md#intent-language-theory-and-claims)明确各自能支持什么。[集合核对](表达依据与集合核对.md)已经给出可消去短写的实际式子、关系片段与有限工程结构的构造证明，以及新建/修改时独立决定的来源核对。作者入口的几种行为不是已经证明最小的语义原语；保留易读短写不等于增加独立语义，开放专业定义也不等于预先拥有全部现实知识。

## 这套语言控制什么

意图描述可接受的产品结果、对象关系、保持项及允许的选择空间。开发者可以给它命名、限定范围、与别的意图组合、在多处采用、局部修订。业务词汇开放，不限于一个能力菜单；共同规则固定这些表达怎样取得含义和共同成立。

人只补系统从当前上下文、已有合同、推导和有效委派中仍不能取得的独立信息。没有“每个项目先定义类型、接口、能力库，再写Goal”的前置。内部需要准确类型，不等于作者要填写类型目录，更不等于产品默认导出具名类型。

| 表达 | 人真正控制的区别 | 不要求人决定 |
| --- | --- | --- |
| 对象与结果关系 | 指谁、要什么、哪些结果才合格 | 内部类、变量、数据布局 |
| 范围、条件、数量与时序 | 对哪些输入/成员、何时必须成立 | 执行阶段、调度与遍历算法 |
| 保持与允许变化 | 什么不能丢、什么可变、哪些选择开放 | 为每个保持项建立检查接口 |
| 定义、采用、组合与局部差异 | 复用哪份含义、哪些共享、只改哪里 | 手工复制规则、同步多个产物 |
| 必须条件、偏好与主动限定 | 合格门槛、偏好、确实要固定的细节 | 在没有独立需求时选择后端或算法 |

表中每项都可省略，前提是当前上下文已经确定其含义；省略不是删掉约束。人可以主动下钻控制算法、精度、布局或外部接口；系统负责显示它影响的产品范围和与既有要求的冲突。本版不把可下钻能力变成顶层必填项。

## 一次实际开发怎样进行

开发者先写：

> 整理待办条目：优先级高的排前面；优先级相同保持原次序。保留全部条目及重复出现，原数据不变。

系统从项目上下文取得“条目”和“优先级”的准确含义，形成下面的有效意图。没有这些上下文时，只指出会改变结果的缺项；例如缺失优先级排前还是排后。已获委派时可形成并固定明确选择，不要求开发者填写完整内部模型。

```text
意图「整理次序」
  对象：本次待展示的条目
  结果：按优先级从高到低排列；同优先级保留原次序
  保持：全部条目及重复出现；条目内容；原序列
```

这份表达关心的是输出与输入的关系，不要求开发者写排序过程。“保留全部条目”按出现次数保持，两个内容相同的条目不会被去重；“原序列保持”不禁止产生新的排列。系统可把整句表达与这种展开视图互相对应，不能让展开视图变成第二份手工源码。

接着使用与组合：

```text
采用「整理次序」于「待办页」的筛选结果
采用「整理次序」于「导出预览」的筛选结果
共同保持：展示不修改原资料
偏好：在全部要求满足时，减少额外内存
```

“筛选范围”“排序”“全部条目及重复出现”共同限定每个采用处的**同一个结果**，没有生成几份结果分别满足。“同时”不指定先filter再sort的执行步骤；实现只要满足这些关系即可。两个采用处复用同一含义，仍使用各自的输入；复用定义不自动共享可变状态。

## 第二次修改不重做工程

开发者说：

> 只把导出预览改成按创建时间从新到旧，同时间保持原次序。待办页不变。

实际意图差额是：

```text
修改「导出预览」本处
  将「排序依据」改为：创建时间从新到旧
  其余有效要求沿用
```

“修改本处”指向该采用处，不按同名全文替换。若排序依据是已开放参数，采用局部特化；若原定义固定了优先级排序，形成明确的局部修订，原共享定义和待办页仍保留。界面必须显示语义确实发生改变，不能把产品变更伪称实现优化。

开发者应直接看到：

| 比较项 | 修改前 | 修改后 |
| --- | --- | --- |
| 导出预览排序依据 | 优先级降序 | 创建时间降序 |
| 同键次序 | 原次序 | 原次序 |
| 筛选范围、全部成员及重复出现 | 保持 | 保持 |
| 原资料 | 不修改 | 不修改 |
| 待办页 | 优先级降序 | 不变 |

展开“当前有效含义”则显示：导出预览处理本处筛选结果的全部条目，按创建时间降序，同时间保持原次序，保留重复出现且不修改原资料。排序依据来自本处修订，成员保持和稳定性来自原定义，筛选范围来自该采用处。开发者不必从一堆内部文件的diff推断这些事实。

“修改定义”是另一件事，会影响真正采用它的所有位置，必须展示各处影响。撤销尚未采用的修改与变更已经运行的产品也不同：前者可以回到原稿，后者不能自动抹去历史。源变更默认形成新修订；本版不默认要求热切换运行状态。

## 控制、放开和冲突

开发者可以加一个偏好：“在既有要求全部满足时，尽量减少额外内存。”它不允许丢条目、去重或破坏同键保序。也可以主动固定一个准确算法或输出形式；那是进一步限定选择空间，系统说明相交影响，作者不用因此接管全部实现。

撤去本处偏好/限定，只放开那项选择；不删除“原资料不变”等产品义务。系统可推导的绑定、命名与实现选择保持隐藏；不可省略的产品决定、独立约束和真实未知不能隐藏。

两个要求冲突时，用区别例解释。例如一个输入含两项不同优先级的条目，同一个结果既被要求严格降序又严格升序，无法共同成立。系统指出这两项要求及范围，保留其他有效内容。仅当前实现暂不支持则应说明支持差额，不能要求用户先弱化产品目标。

## 同一套抽象怎样跨领域

换领域时换的是对象和关系，不是重新注册一套核心业务能力：

```text
意图「报名名额」
  对象：同一场次的申请与名额
  结果：合格申请在本次判定时名额足够则接受并分配，否则明确说明资格或缺额原因
  保持：成功分配的总量不超过本场次的总名额；同一业务请求不重复占用

采用「报名名额」于「网页入口」与「现场入口」
  共享：同一场次名额
```

这仍是在指称对象、规定结果、保持关系和采用范围。本例报名期间总名额固定，可用名额是总名额减去已成功分配的数量；累计分配不能拿剩余量作上限。两个入口共享的是同一名额对象，因此容量约束共同成立，不能各自使用一个同配置副本。申请身份、数量和名额若已由项目合同确定就继承；真正未定且改变结果的部分才需要形成决定。这里不引入数据库、锁、事务字段或调用观察接口。

两个领域还可以在一个新产品内组合：

```text
产品「报名工作台」
  名额处理：采用「报名名额」
  申请列表：采用「整理次序」，对象为当前筛选的申请
  共同保持：列表只呈现相应版本的报名结果，不因排序改变报名状态
```

这段不是两个孤立模块的摆放：列表与名额处理共享明确的申请/结果关系，排序只改变呈现次序，不能改写报名状态。相同组合规则可以继续嵌套和复用；若需要时效、历史或更强一致性，表达真实产品所需的观察区别，不让用户先选一种内部实现。

## 从短输入到准确表达，而不是从功能目录选择

共同栏目与可嵌套构造由[第一层语言核心](../../docs/作者/第一层语言.md#intent-author-core)唯一规定。`对象`区分已有、外来和求得；`要求`组合准确关系；`选择`表达固定、偏好及委派。`结果/保持`是有范围的短视图，`「」`只界定名字。

开发者说“把这些班次均衡分给有空的人员”，不先选择“排班能力”。系统绑定实际人员、班次和可到场资料，形成“覆盖全部班次、不可分给无法到场的人、一个人不同时覆盖相交班次”的关系，再把本次“均衡”明确成降低最大个人总工时。完整写法在[连续意图稿的新意图](开发面V1意图稿.md#new-intent-without-catalog)；所有内容都由共同的成员、数量、时间区间和偏好构造表达。是否改为“轮换机会”是产品政策变化，而不是换一个神秘的能力名称。

若已有委派包含该政策，系统可形成并固定它，不逐项请人确认；若没有且候选之间会改变接受结果，才向作者呈现这个实际差异。接受后源码保存确定含义，重新构建不重新猜“均衡”。用户可以只改“每人最多两班”，系统将它与原覆盖、可到场及不重叠关系联立；不能为了满足新上限自动删班次。

持续交互也使用同样构造。连续稿中的“编辑—预览—确认”约束每次编辑的预览、每次确认的答复及生效版本。先预览A、再编辑B、最后确认旧预览A时，生效内容仍须是A，不能只凭“某次预览曾发生”提交B。需要拒绝旧预览时，明确改变确认政策并保留拒绝出口；这才是产品选择，不要求用户编写版本比较处理器。

两类意图可在同一产品采用：把排班结果绑定为待预览内容；仅当一个满足排班要求的版本被确认时才能发布该版本。关系定义与采用不制造执行顺序；“确认后发布”是本产品明确要求的可观察顺序。系统负责内部数据组织、算法和调用安排。

## 架构、代码形态、模式和资源也由作者直接控制

第一层对象不限于业务值和交互历史。[全工程作者面](../../docs/作者/第一层语言.md#whole-engineering-intent)明确承接组件边界、源码/公开API、实现模式、状态与资源、部署及演进；直接定义与连接、附着要求及实现控制共同构成源，对象/要求/选择只是其中的任务视图。各种对象与关系仍有准确的专业解释。没有架构要求时可委派形成，有明确结构要求时必须保留，不能以“输入输出相同”忽略它。

[工程控制连续例](开发面V1意图稿.md#whole-engineering-control-example)把已存在的业务与公共合同绑定到同一工程，直接规定查询核依赖边界、状态写入所有者、Rust/TypeScript产物、保留的公开结构及非受管字节、共同内存预算、取消释放与索引升级保持。模式是可展开的普通定义，源码形态使用已有结构政策，均不新增中央能力菜单。把512 MiB改成256 MiB后，系统沿实际共同占用检查缓存、并发与响应条件；不能只改变配置文字或削掉另一项要求。

大工程通过层级定义、真实边界及共同义务组合；局部编辑仍可能产生广泛影响，系统必须展开相交部分。开发者可以先固定架构，再补行为，也可以先规定行为，再让系统提出架构并局部接管。两条创作顺序共享同一作者源，没有“必须先把所有行为写成逻辑公式”的前置。

## 正常开发面与完成边界

同一份意图支撑新建、理解、组合、局部编辑、共享定义编辑、比较、检查、结果预览、协作与版本采用。最常见视图是“当前产品会怎样”和“这次改了什么”；完整准确含义及来源可以展开，内部推导和代码按需下钻。显示少不等于隐藏必须维护的信息，也不等于删除内部必要机制。

本版先固定表达和开发行为，理论依据是关系/约束描述、参数化组合、作用范围及语义编辑均有明确可实现路径。无需本轮选定内部IR、求解器、Reader或LLVM后端。成熟编译原理可支持后续落实，开发者不必通过理解LLVM来写产品意图。

本版不声称已经实现自动理解、精确回写、求解、生成或开发工具，也不声称任意需求都能自动实现。尚未做的是：内部架构和真实实现、语言载体及交互工具落地、用户使用验证、全工程迁移与运行等价。此前的内部源码/Schema/目标代码草稿保留为未采用研究材料，不计作本轮成品或验收要求；ripgrep仍只是后续检验通用抽象的案例。

本轮判断设计好坏的标准是：作者是否能用同一套表达完成上述连续行为；是否保持其关心的区别；是否只承担必要决定；是否能明确查看变化和未变部分。内部字段齐全、类型检查通过或目标代码存在，不替代这些标准。
