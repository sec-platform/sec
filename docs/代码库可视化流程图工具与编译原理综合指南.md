## 🛠️ 1.10 本项目 Vibecoding 工具链配置（2026-05 实测）

> 目标：用最少工具覆盖「看懂结构 → 发现重复 → 守住架构边界」三大需求，最大化 AI 辅助编码效率，减少人工 review 依赖。

### 三件套 + 一脚本 + 外部 graph provider

实际命令事实源是 `package.json` scripts 与 `.github/workflows/architecture-tools.yml`；本文只说明能力边界，不复制底层命令参数。

| 角色 | 工具 | 接入方式 | 核心能力 | 检测层级 |
|------|------|----------|----------|----------|
| **可视化 / IDE evidence** | Graph-It-Live (VSCode 插件 + MCP + CLI) | `.mcp.json` + IDE/MCP | File Graph + Symbol View + Live Call Graph，适合 AI 上下文探索 | IDE/graph evidence |
| **重复检测** | jscpd (CLI) | `bun run jscpd` | Token 级重复检测，HTML/JSON 报告 | L1 文本级 |
| **架构规则** | dependency-cruiser (CLI) | `bun run depcruise` | 依赖方向校验、循环依赖检测、自定义规则 | Architecture boundary |
| **结构重复** | discover-all.ts (脚本) | `bun run discover` | AST 归一化哈希，检测变量名不同但结构相同的函数 | L2 结构级 |
| **repo query graph** | GitNexus provider | `bun run gitnexus:analyze` / `bun run gitnexus:status` | call chain、execution flow、impact、dependency cluster 等只读索引 | external graph evidence |
| **knowledge graph** | Graphify provider | `bun run graphify:update` / `bun run graphify:extract` | code/docs/diagram knowledge graph export；使用 PyPI `graphifyy`，不是 npm `graphify` | external knowledge evidence |

GitNexus 已安装为 `gitnexus@1.6.3` devDependency；其 npm license 是 PolyForm-Noncommercial-1.0.0，只能放在开发期 evidence 流程，且本仓脚本固定 `--skip-agents-md --no-stats` 防止 provider 改写 agent 指令文件或制造 volatile stats。Graphify 已确认真实 CLI 包名为 PyPI `graphifyy==0.7.10`，本仓通过 `uvx --from graphifyy==0.7.10 graphify` 固定版本运行；npm 上的 `graphify` 是随机图生成器，不是这里要接的知识图谱工具。

### jscpd 配置与使用

**npm script**（已配置在 `package.json`）：
```bash
bun run jscpd
```

**报告位置**：`report/jscpd/html/index.html`（浏览器打开）

**当前扫描结果**不在文档中手工维护；以 `bun run jscpd` 生成的 `report/jscpd/**` 为准。

**已知边界**：
1. `--reporters` 参数由 package script 统一维护，文档不复制底层参数。
2. jscpd 只覆盖 token/text clone，不能替代 L2/L3 或 review judgment。
3. raw report 只能作为 draft evidence，经 adapter 归一前不是治理事实源。

### dependency-cruiser 配置与使用

**配置文件**：`.dependency-cruiser.json`（项目根目录）

**当前架构规则**：
| 规则 | 含义 | 严重级别 |
|------|------|----------|
| `shared-no-reverse-deps` | shared/ 不得反向依赖 compiler/cli/orchestrator/dev-runner/upgrade/ | error |
| `no-circular` | 禁止循环依赖 | error |
| `no-registry-to-compiler` | registry/ 是纯数据，不得依赖 compiler/ | error |

**npm script**（已配置在 `package.json`）：
```bash
bun run depcruise          # 校验架构规则
bun run arch:check         # 架构规则 + 重复检测
```

**当前扫描结果**不在文档中手工维护；以 `bun run depcruise` 的实时输出为准。

**已知边界**：
1. 底层 dependency-cruiser 版本和参数由 package script 统一维护。
2. `tsConfig` 配置项必须是 `{ "fileName": "./tsconfig.json" }`，不能是字符串。
3. 依赖边界 finding 只能进入 architecture-boundary evidence，不能直接修改 graph lock 或 Workbench 主图。

### 重复检测三层能力

| 层级 | 检测方式 | 能发现什么 | 本项目覆盖 |
|------|----------|-----------|-----------|
| **L1: 文本级** | jscpd | 复制粘贴后微调的代码块 | ✅ `bun run jscpd` |
| **L2: 结构级** | discover-all.ts（AST 归一化哈希） | 变量名不同但结构相同的代码 | ✅ `bun run discover` |
| **L3: 语义级** | Engineering Pattern Graph / 逻辑链路分析 | 「读取→校验→构建→写入」「查询→判空→映射→返回」等意图模式 | 预留；当前仍需 AI review |

### discover-all.ts 配置与使用

**npm script**（已配置在 `package.json`）：
```bash
bun run discover            # L2 结构级重复检测，输出到 report/discover.json
```

**原理**：用 ts-morph 解析 AST → 提取函数体 → `normalizeBody`（变量名→`_`，字符串→`"_"`，数字→`0`）→ MD5 哈希 → 相同哈希 = 结构重复。

**与 jscpd 的区别**：
| | jscpd | discover-all.ts |
|---|---|---|
| 检测层级 | L1 文本级 | L2 结构级 |
| 能检测 | 逐字相同的代码块 | 变量名不同但结构相同的函数 |
| 不能检测 | 变量名不同但逻辑相同 | 语义等价但写法不同 |
| 输出 | HTML 报告 | JSON 报告 |

### AI 事前审查流程

**一键全检**：
```bash
bun run preflight           # depcruise + jscpd + discover
```

**本地增量验证**：
```bash
bun run check:affected       # typecheck + 已改或受影响 fast tests；默认不做 broad fast-suite fallback
bun run check:full          # typecheck + 完整慢门禁，允许 Next build / Playwright
```

`check:affected` 是默认本地闭环，优先运行 git 变更命中或 impact contract 选中的 fast tests；未映射源码变更默认只提示不回退整套 fast suite，避免普通代码改动反复扩大验证范围；若变更本身落在 slow test、runtime verification、registry/contract 关键路径，必须显式使用对应定向测试、contract freeze、reference check 或 `check:full`。

**AI 写代码前的审查步骤**：
1. `bun run preflight` — 跑完所有检测，确认当前状态
2. 检查 `.trae/rules/project_rules.md` 通用函数索引 — 避免重复发明
3. 用 Graph-It-Live 查看目标文件的依赖关系 — 理解上下文
4. 写代码 — 遵循 docs/05 §9 代码压缩原则；新增第三方依赖必须用 `bun add <pkg>@latest` 或 `bun add -d <pkg>@latest`，并优先用新库替换现有手写实现，而不是只增加包装层
5. `bun run check:affected` — 对变更做快速闭环；涉及慢门禁时升级到 `bun run check:full`
6. `bun run preflight` — 确认没有引入新的重复或违规

**jscpd 能力边界**：

| 能检测 | 不能检测 |
|--------|----------|
| 逐字/逐 token 相同的代码块 | 变量名不同但逻辑相同的模式 |
| 复制粘贴后微调的代码 | 结构相同但数据不同的模板模式 |
| 跨文件的完全重复 | 语义等价但写法不同的逻辑链路 |
| 指定阈值（minLines/minTokens）内的重复 | 需要抽象提取的「相同逻辑链路」 |

> **结论**：jscpd 只能检测**文本/token 级重复**，无法发现**语义级重复模式**。语义级重复需要 AST 分析（扩展 `scripts/discover-all.ts` 的 `normalizeBody`）或 AI review。

### 工具组合是否“最优”的判断

结论：当前“四件套”不是每个单项能力的全球最强组合，但对 PJC 当前阶段是合理的最小闭环：

| 目标 | 当前选择 | 为什么保留 | 可替代/补充候选 | 何时换/加 |
|------|----------|------------|-----------------|------------|
| L1 复制粘贴检测 | jscpd | 本地、便宜、报告清晰，适合 preflight | SonarQube duplication、Fallow、DeepScan | 需要团队级质量平台、趋势看板或复杂质量门禁时 |
| L2 结构重复 | `scripts/discover-all.ts` | 可控、可嵌入 PJC contract，能按项目语义演进 | similarity-ts、ts-morph 自定义规则、Tree-sitter | 需要更成熟的 AST similarity 算法时 |
| 架构边界 | dependency-cruiser | JS/TS 成熟，适合 CI 规则和 DOT/HTML 输出 | Madge、Nx graph、ESLint boundary rules | 需要 monorepo project graph 或更轻量循环检测时 |
| IDE/AI 图探索 | Graph-It-Live | 开源、VSCode、MCP、CLI、file/symbol/call graph 覆盖面广 | CodeQL、Joern/CPG、Sourcegraph/Cody、IDE 原生 call hierarchy | 需要数据流/安全查询/跨语言深度语义分析时 |
| repo/call/impact provider | GitNexus | 适合补 call chain、execution flow、impact、dependency cluster 等只读索引 | Graph-It-Live、Sourcegraph、CodeQL/CPG | 作为 optional provider adapter 接入，不作为事实源 |
| code/docs knowledge graph | Graphify | 适合补代码、文档、图表混合知识图谱 export | Graph-It-Live、定制 Tree-sitter/LLM extractor | 作为 optional provider adapter 接入，不作为事实源 |
| L3 语义模式 | PJC 自建 Engineering Pattern Graph | L3 必须理解 PJC 的 block/slot/provenance/contract，不适合完全外包 | CodeQL/CPG/Joern、semantic clone 研究、LLM reviewer | 作为 evidence 或离线分析接入，不作为事实源 |

选择原则：外部工具做 evidence provider，PJC 的 Engineering IR / Explain Graph / Review Summary 做事实归一。Graph-It-Live、GitNexus、Graphify、jscpd、dependency-cruiser、discover 输出都不能替代 `source/app.yaml`、block manifest、contracts、graph lock、provenance 或 review summary。

### Graph-It-Live 客观评价（2026-05 核验）

公开仓库：`https://github.com/magic5644/Graph-It-Live`。仓库近期活跃，package 描述为 “AI-first dependency graph & code intelligence for VS Code”，声明支持 VSCode、Open VSX、npm CLI 与内置 MCP Server。

**优势**：
- 开源，package 声明 MIT；latest release 已到 v1.9.1，仓库 topic 明确包含 MCP、VSCode、AI agent、dependency graph。
- 覆盖 File Graph、Symbol View、Live Call Graph、AI-friendly codemap、dead code、breaking change/impact analysis 等方向。
- README/package 声明 MCP Server 暴露约 21 个工具，可给 Copilot、Cursor、Claude、Windsurf、Antigravity 等 AI 客户端使用。
- 技术栈包含 AST、Tree-sitter、ts-morph、SQLite、Cytoscape.js；支持 TS/JS、Python、Rust、C#、Go、Java、Vue、Svelte、GraphQL 等多语言层级。

**边界与风险**：
- 它适合 IDE 实时探索和 AI 上下文查询，不适合作为 PJC 的权威 graph source。
- Live call graph、MCP 工具、跨语言 symbol 深度在大型仓库和本项目环境下仍需实测。
- C#/Go/Java 等语言的符号级能力可能弱于 TS/JS；数据流/安全语义查询不是它的主强项。
- MCP 输出必须经 PJC evidence contract 归一，不能直接回写 `source/app.yaml` 或 `control/**`。

本项目可视化/Workbench 方向并非孤立发明，相关研究线包括：

|------|----------------|--------------|------|

PJC 的差异点应是：把这些线索收束为工程编译器闭环——`source/contract → block/pin/slot → Engineering IR → generated project → provenance/review/verification → Workbench graph → structured mutation → source/contract`。图不是旁路文档，而是可审查、可回写、可验证的操作面。

## 🧠 二、构建统一代码标准化/重构系统：可行性论证

### 2.1 核心目标

设计一个**同语言中应对任何书写风格，都能重构为标准格式、实现单一事实归一化（Single Source of Truth）且高可扩展**的代码架构。

### 2.2 已有成功案例

- **LLVM** – 统一中间表示（IR），支持多前端语言，实现一次优化多架构受益。
- **Babel** – JavaScript AST 转换，插件化架构，成为 JS 工具链标准。
- **Tree‑sitter** – 增量解析库，输出统一的 AST/CST，支持多语言。
- **Roslyn** – .NET 编译器即服务，提供语法树、语义模型、重构 API。
- **GRAALVM** – 多语言运行时，提供通用 AST 与 polyglot 互操作。

> 这些系统证明：**构建一个跨语言/单语言的通用代码标准化系统是可行的**，核心难点不在技术上，而在**语义等价规则的定义与社区生态**。

## ⚙️ 三、编译原理基础与优化（深度扩充版）

### 3.1 编译流程全景（含 IR）

```
源码 (.ts, .py, .c)
    ↓ Lexer (词法分析)
Token 流
    ↓ Parser (语法分析)
AST (抽象语法树)
    ↓ Semantic Analyzer
带类型注解的 AST
    ↓ IR 生成
中间表示 (IR)  — HIR / MIR / LIR (三阶段)
    ↓ 平台无关优化
优化后 IR
    ↓ 平台相关优化 & 寄存器分配
汇编 / 机器码
    ↓ 汇编器 / 链接器
可执行文件 / 库
```

#### 什么是 HIR、MIR、LIR？
- **HIR (High‑level IR)**：与 AST 接近，保留控制流结构（循环、条件）。
- **MIR (Mid‑level IR)**：控制流图 (CFG)，基本块之间的跳转已显式化。
- **LIR (Low‑level IR)**：接近目标架构，引入虚拟寄存器、具体指令。

LLVM IR 通常介于 MIR 与 LIR 之间，兼具低级性与架构无关性。

### 3.2 编译器产出物对比

| 类型 | 输入 | 输出 | 说明 |
|------|------|------|------|
| 传统 AOT (C/C++/Rust) | 源码 | 机器码 / 汇编 | 可直接执行 |
| LLVM 架构 | 源码 | LLVM IR → 优化 → 目标机器码 | 跨平台后端 |
| JIT 编译器 (V8, JVM) | 字节码 / 源码 | 运行时编译为机器码 | 可动态优化 |
| 解释器 (CPython, Lua) | 字节码 | 逐条解释执行**（不编译到机器码）** | 无编译阶段 |

> 📌 **修正**：现代 JavaScript 引擎（V8, SpiderMonkey）属于**JIT 编译器**，不是“解释型语言”。它们混合了解释器和编译器：初始用解释器快速启动，热路径编译为优化机器码。

### 3.3 不同 CPU 架构的汇编差异（真实案例）

**C 代码**：
```c
int result = a + b;
```

**x86-64 未优化（-O0）**：
```asm
mov    eax, DWORD PTR [rbp-4]     ; 取 a
add    eax, DWORD PTR [rbp-8]     ; 加 b
mov    DWORD PTR [rbp-12], eax    ; 存 result
```

**ARM64 未优化**：
```asm
ldr    w0, [sp, #4]               ; a 到 w0
ldr    w1, [sp, #8]               ; b 到 w1
add    w0, w0, w1                 ; w0 = a+b
str    w0, [sp, #12]              ; 存 result
```

**x86-64 优化 (-O2)**：
```asm
lea    eax, [rdi+rsi]             ; 一条指令完成加法和结果存入 eax
ret
```

> 优化后的汇编简化非常多，因此**看汇编必须注明优化级别**。

### 3.4 典型 TypeScript/Deno 编译路径（修正版）

```text
.ts 文件
   ↓ Deno 内部使用 SWC (Rust 编写的 TS 编译器)
等效 AST → JavaScript 源码 / 字节码
   ↓ V8 引擎
JIT 编译为当前 CPU 架构的机器码
   ↓ 执行
```

Deno **不使用 tsc**，而是内置 SWC 以获得更高编译速度。因此生产效率与 tsc 无关。

### 3.5 LLVM 优化能力边界（详细）

| 优化类别 | 能做 | 不能做 |
|----------|------|--------|
| 内联小函数 | ✅ | 内联递归函数（受限于深度） |
| 常量传播 | ✅ | 跨编译单元的常量（LTO 可缓解） |
| 循环向量化 (SIMD) | ✅ | 非循环结构（手动 SIMD intrincs 需要） |
| 死代码消除 | ✅ | 不可达分支因动态分发无法消除 |
| 指令调度，重排 | ✅ | 改变算法复杂度（O(n²)不会变O(n log n)） |
| 内存布局优化 | 局部 | 跨对象重排（需 alias analysis 支持） |

**结论**：LLVM 不能“修复”糟糕的算法选择，但能显著降低抽象层的额外开销。

### 3.6 代码组织方式对 LLVM 结果的影响（实验验证过的结论）

- **会被消除的差异**：
  - 函数声明 vs 箭头函数（C++ lambda vs 普通函数）
  - class 方法 vs 自由函数（优化后 call instruction 相同）
  - 多层嵌套调用（内联展开后扁平化）
  - 无用临时变量（DCE 移除）
- **无法消除的差异**：
  - 动态派发（虚函数、反射调用）
  - 间接分支（函数指针、跳转表）
  - 不同分配模式（多次 `new` vs 一次大数组）
  - 抽象层过深导致的编译时间增长（但运行时代码量相近）

> **核心结论**：只要算法和业务逻辑相同，代码组织方式（语法糖、命名、结构）对最终机器码的影响极小。所以**不必为性能而牺牲可读性**。

### 3.7 汇编的生成时机

- 传统流程：`IR → 汇编文本 → 汇编器 → 机器码`
- 现代 LLVM：`IR → 直接生成机器码`（MC Layer），汇编文本仅用于调试输出或手动优化。

## 🗂️ 四、深度概念讨论与补充

### 4.1 过度抽象 (Over‑abstraction) 与 YAGNI

**过度抽象的特征**：
- 只有一个实现类的接口
- 每个类型都要配套工厂
- 抽象层纯粹转发，不加逻辑
- 依赖注入用于全局单例工具（不必要）

**判断公式**：  
`抽象收益 (可测试性 + 可替换性 + 可读性) < 抽象成本 (理解 + 维护 + 编译)`

**YAGNI 原则**：“你不会用到它”。传统方法要求等到真正需要时再添加抽象，并配合密集重构。

### 4.2 AI 时代对 YAGNI 的再思考（观点性内容）

| 时代 | 代码增长速度 | 抽象维护成本 | 主要维护者 | 建议原则 |
|------|------------|--------------|------------|----------|
| 传统 | 慢 | 高 | 人类 | 严格 YAGNI |
| AI 辅助 | 极快（AI 生成） | 降低（AI 可辅助重构） | 人 + AI | 适度抽象，但保持人类可理解 |

**核心观点**：AI 能快速生成并维护抽象层，但 **AI 无法理解业务边界**，过度抽象仍会导致人类开发者的认知负担和调试困难。因此推荐 **“刚刚好的抽象”**：能减少重复代码、清晰表达意图即可，不过度提前设计。

### 4.3 Token 流与中文“词元”译法

- **Token**：编译原理词法分析的最小单元（例如 `int`、`main`、`(`、`)`、`{`、`+` 等）。
- **Token 流**：字符串源码经过 Lexer 产生的有序 Token 序列。
- **词源**：古英语 *tācen*（标记/符号），并非拉丁语 *tokenus*（后者为网络误传）。1960 年代在编译器文献中正式标准化。
- **为何 AI 圈用“词元”**：在大型语言模型（LLM）中，Token 不一定是完整单词，可能是一个子词（subword）或字符，对应“元”即基本单元，避免与“单词”混淆。中文社区在 2022–2023 年后大量采用“词元”翻译。

## 🔍 五、常见疑问解答（FACT-CHECKED）

### Q1：现代编译器全都是 LLVM 吗？虚拟机和解释器不用 LLVM？

**不**。编译器格局：

- **LLVM 家族**：Clang (C/C++/ObjC)、Rust (rustc)、Swift (swiftc)、Julia、Zig
- **传统阵营**：GCC (多语言)、MSVC (Windows)、Oracle 编译器
- **VM 运行时**：JVM (Java)、.NET CLR (C#) —— 它们有自己的 IR (JVM 字节码、CIL)，不基于 LLVM
- **解释器**：CPython, Ruby MRI, PHP 等 —— 主要是字节码解释器，不涉及 LLVM

> 例外：Node.js 的 V8 引擎完全不使用 LLVM，其内部有自己的 JIT 编译器 (Ignition + TurboFan)。

### Q2：库会针对 LLVM 做优化吗？

**一般不会**。库作者优化的是算法效率和底层实现（如手写 SIMD、避免动态分配），这些优化对任何编译器都有效。LLVM 只能优化调用方式（内联、常量传播），无法改变库的内部算法。

### Q3：为什么需要 IR（中间表示）？

三个核心理由：
1. **复用后端**：多个前端语言可共享同一个优化器和代码生成器。
2. **跨平台**：一份 IR 可以编译到 x86、ARM、RISC‑V 等多种架构。
3. **优化独立**：优化可分为平台无关（多数）和平台相关（如指令调度），IR 层做前者。

### Q4：最终生成的汇编都一样吗？

**不**。不同 CPU 架构（x86‑64, ARM64, RISC‑V）的指令格式、寄存器数量、寻址方式差异巨大，因此汇编代码完全不同。即便是同一架构，不同的优化级别（-O0 vs -O2）也会产生截然不同的汇编。

### Q5：JIT 和 AOT 有什么区别？

- **AOT (Ahead‑Of‑Time)**：执行前一次性编译为机器码。启动快，优化可深度，但无法利用运行时信息。
- **JIT (Just‑In‑Time)**：运行时编译热点代码。可采集运行时 profiling，进行激进优化，但启动延迟较高。

现代大型应用常**混合使用**：AOT 编译核心，JIT 编译动态部分。
