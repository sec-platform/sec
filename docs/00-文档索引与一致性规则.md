# 文档索引与一致性规则

本文定义 SEC 工程文档的职责、权威顺序和维护规则。目标只有一个：**同一工程事实只维护一次**。

## 1. 权威规格栈

| 文档 | 权威职责 |
| --- | --- |
| `00` | 文档治理、冲突处理、维护规则 |
| `01` | 问题定义、核心概念、长期命题 |
| `02` | 产品定位、总体架构、系统边界 |
| `03` | 当前阶段、里程碑、开发顺序、进入/退出条件 |
| `04` | 自主开发 Agent 的仓库执行规则 |
| `05` | 编译器实现栈、Workspace、公共 API、Schema/代码生成基础规则 |
| `06` | Registry、Block、Pin、Slot、Contract/Generator 打包协议 |
| `07` | Compiler Pass、状态机、错误域、恢复边界 |
| `08` | Verification、Artifact Provenance、Explain/Review 治理投影 |
| `09` | AI Runtime、Task Envelope、Context Packet、语义操作授权 |
| `10` | Upgrade、Migration、Override、Rollback |
| `11` | Workbench、Semantic View、多投影、View Mutation UI 与 Semantic Mutation adapter |
| `12` | 编译与行为数据流图；只画当前权威架构 |
| `13` | CLI 独立分发、公开包边界、发布流程 |

| `goals/SEC-Engineering-Workspace-Compiler` | 用户长期产品 Goal 的稳定仓库投影；不保存当前 SHA、PR、CI 或 active task |

## 2. 事实归属

| 事实 | 唯一权威位置 |
| --- | --- |
| 产品是什么、不是什麽 | `02` |
| 当前阶段与长期主线顺序 | `03` |
| 当前 exact 工程事实 | `work/current-state` |
| 当前 active manifest 选择 | `work/active-work-package` |
| 当前正式执行闭包 | 选择器指向的 `work-packages/<id>` |
| 当前包与近期候选 | `work/rolling-plan` |
| `source/app.yaml`、Workspace、公共编译器 API | `05` |
| Block/Pin/Slot/Contract/Generator 协议 | `06` |
| Pass 顺序和失败恢复 | `07` |
| Verification、Artifact Provenance、ExplainGraph、ReviewSummary | `08` |
| Task Envelope、AI 权限、Context Packet | `09` |
| Upgrade/Override/Migration | `10` |
| Workbench 视图、View Mutation UI 与 Semantic Mutation adapter | `11` |
| Engineering IR、Semantic Fact、Fact Delta、Impact Propagation、Semantic Mutation canonical contract | `14` |
| SEC-TS 后续 IR 与 Lowering 规划 | `architecture/sec-ts-ir-layers` |
| Engineering Workspace 多域 IR 规划 | `architecture/engineering-workspace-ir` |
| Brownfield Import 与 Source Program Model 规划 | `architecture/brownfield-import` |
| Nexus Census/Parity/Retirement | `governance/nexus-absorption-and-conformance` + ledger/report |

其他文档只允许写一到三句摘要并链接权威文档，不得复制字段表、完整命令矩阵、枚举或状态机。

## 3. 冲突优先级

1. 对实现字段，`05–11` 与 `14` 高于 `01–04`。
2. 对产品边界，`02` 高于实现文档中的背景描述。
3. 对阶段和顺序，`03` 高于任何历史计划。
4. 对 AI 仓库执行方式，`04` 约束开发 Agent；对产品内 AI Runtime，`09` 为权威。
5. 对测试/CI，三份测试文档分别在各自职责内优先。
6. 代码已经形成公开合同且文档明显过期时，先以代码合同判断当前事实，再同步修正文档；不得静默让文档长期漂移。
7. `main` 是能力与完成的唯一正式工程事实；Issue、PR、branch、计划、报告与聊天只提供导航或证据线索。
8. `work/**` 只拥有易变事实与近期执行，不得复制 `03` 的长期阶段合同；`03` 也不得保存易变 SHA、PR/CI 列表或 Work Package 过程日志。

## 4. Canonical 与 Projection

以下关系必须长期保持：

```text
Product Intent / Existing Workspace
  → Canonical Workspace Input Snapshot（Authoring Source + Imported Evidence）
  → Semantic Frontend / workspace domain builders
  → Engineering IR + independently validated workspace domains
  → Validated Engineering Workspace Snapshot
  → Application IR
  → Behavior IR
  → Target Program IR（SEC-TS v1 为 TypeScript Program IR）
  → Validated target Compilation Snapshot
  → Compiler / Verification / AI Runtime
  → Source / Test / Docs / Gate / Agent / Release Projections

Engineering IR + Governance Artifacts
  → ExplainGraph
  → ReviewSummary
  → SemanticView
  → Workbench / CLI / IDE / MCP

Semantic Mutation Request
  → platform-owned authorization / source adapter / isolated staging
  → canonical rebuild / Fact Delta / Impact / Verification
  → CAS publish or verified rollback
  → Authoring Source
```

- `Engineering IR` 是工程语义统一表示。
- `ExplainGraph` 是治理解释投影，不得成长为第二套 IR。
- `ReviewSummary` 是 Review 聚合合同，不得自行反推业务语义。
- `SemanticView` 是 UI/AI 消费投影，不是事实源。
- 外部 graph/provider 输出只能作为 Evidence/Overlay。
- Engineering Workspace Snapshot 组合多个独立 validated domain revision；它不是把所有域塞进一个 optional object，也不替代 Engineering IR。

## 5. 概念边界

- **Block**：Registry 分发、版本、信任、升级和资产封装单位。
- **Semantic Responsibility**：架构理解、职责、状态所有权和影响传播单位；可位于一个 Block 内，也可跨 Block。
- **Semantic Entity**：IR 中可被引用的工程对象。
- **Semantic Fact**：`subject + predicate + object` 形式的最小工程事实。
- **Artifact Provenance**：说明文件/产物从哪里来。
- **Fact Provenance**：说明工程判断为什么成立、由谁声明或推导、证据是什么。
- **Semantic Mutation**：受版本化 operation registry、source ownership、CAS、实际 Fact Delta、Impact 与 Verification 约束的 Authoring Source transaction；不是 IR/Projection patch。

## 6. 文档状态

- `active`：当前权威或当前执行文档。
- `stable`：事实稳定，仍是权威。
- `draft`：尚未冻结，不得被实现当作既定协议。
- `historical`：决策记录或历史计划，不维护当前事实。
- `archive`：原始材料，仅供追溯。

`docs/superpowers/**` 只保留历史设计/实施记录，不得覆盖 `00–14`。
`docs/archive/**` 只保存原始材料和抽取记录，不参与实现决策。

## 7. 修改规则

- 新产品决策：先改 `02`；影响阶段时同步 `03`。
- 新 IR Entity/Fact/Predicate：先改 `14`，再改类型和构建器；影响 Block 输入时同步 `06`。
- 新公共 Schema/CLI：改对应实现文档并增加 Contract Test。
- 新 Workbench View：改 `11`；若新增稳定产物，同步 `08` 与 CI artifact contract。
- 新 Semantic Mutation operation：先改 `14` 的 operation registry、source ownership、expectation、transaction 与 Contract Freeze，再由 `09` 增加 AI 授权、由 `11` 增加 UI/adapter；不得在 consumer 文档另建 mutation schema。
- 新 Target Profile/Type Algebra/Application/Behavior/TypeScript Program IR：先改 `architecture/sec-ts-ir-layers`，再为对应独立 domain 冻结类型、validator、revision 与 tests；不得修改 `14` 建立第二套 Engineering IR。
- 新 Workspace domain：先改 `architecture/engineering-workspace-ir`；Nexus-specific value 进入 Policy Pack/Adapter/fixture，不进入 Core。
- 新 Brownfield Provider/阶段：改 `architecture/brownfield-import`；provider output 只能成为 Evidence/candidate。
- Nexus Census/Parity/retirement：只更新 canonical ledger/report；未满足硬门时必须标记 incomplete。
- 近期控制面的 lifecycle/recompute taxonomy 只由 `04` 维护；`work/**` 只保存当前选择与计划内容。
- 新 AI 操作授权：改 `09`；必须定义 allowed operations、write bounds、must-preserve facts 和 verification minimum，且不能覆盖 `14` 的派生风险、路径、rollback 或 verification 要求。
- 新 pass：改 `07`，并明确输入、输出、是否确定性、失败语义和重入规则。
- 新历史设计方案：不得复制当前规范，写 ADR 式背景、决策、结果和当前权威链接。

## 8. 文档质量门槛

每份活跃文档必须：

1. 用中文正文；代码、API、领域标准术语保留英文。
2. 开头说明职责，不重复产品宣言。
3. 区分“已实现”“当前开发”“规划/预留”。
4. 不把设计目标写成已经具备的保证。
5. 表格只用于稳定枚举和职责映射，不用来堆重复信息。
6. 示例必须说明是示意还是冻结 Schema。
7. 不维护会频繁变化的计数、完整脚本对象、suite 列表和工具热度。
