# 文档索引与一致性规则

本文是 SEC 文档权威图的唯一入口。目标只有一个：**同一工程事实只维护一次；动态状态、稳定规范、历史证据、审计结果和外部分析不得混成第二事实源。**

## 2. 事实归属

- 产品是什么、不是什麽：`02`。
- 稳定阶段顺序和完成定义：`03`。
- 当前 exact 状态：`work/current-state.yaml` 的稳定输入加 live resolver 结果。
- 当前正式闭包：`work/active-work-package.md` 指向的 `work-packages/<id>.md`。
- 当前包和近期候选：`work/rolling-plan.md`。
- Engineering IR 与 Semantic Mutation canonical contract：`14`。
- 后续 TS IR/Lowering：`architecture/sec-ts-ir-layers.md`。
- Engineering Workspace 多域 IR：`architecture/engineering-workspace-ir.md`。
- Brownfield 与 Source Program Model：`architecture/brownfield-import.md`。
- Host Runtime、Toolchain Provider、Target Runtime Profile、package/runtime layout 与公开分发：`13`。
- Agent行为 owner、全仓审计、启发式抽取、架构演进和V19续跑：专用 governance owner、`platform/shared/agent-skill-contract.ts` 与 `scripts/codex/repository-audit.ts`。
- 外部工具/MCP/Provider：external capability policy 与 ledger。
- Nexus Census/Parity/Retirement：Nexus conformance 文档、ledger、report。

其他文档只能写一到三句摘要并链接 owner，不得复制完整字段表、状态机、阶段表、命令矩阵或 Skill 执行闭包。

## 3. 冲突优先级

1. `main` 中代码、公开合同和适用验证证据决定当前实现事实；发现文档漂移后必须同步修正文档。
2. 产品边界以 `02` 为准；稳定阶段和完成定义以 `03` 为准。
3. Engineering IR/Mutation 以 `14` 为准；下游 Projection、Workbench、AI、Provider 不得反向拥有语义。
4. Agent 仓库执行方式以 `04` 为准；行为 owner、Skills、全仓审计与Kernel架构以专用governance owner为准；产品内 AI Runtime 以 `09` 为准。
5. `work/**` 只拥有动态状态与近期选择，不得复制长期 Goal、阶段合同或完整架构。
6. Issue、PR body、branch、聊天、审计报告、代码图和 LLM 摘要只提供导航或证据线索，不能单独证明完成或 authority。
7. 外部 Provider 的共识不构成多数票升格；authority 仍需明确 owner/policy 裁决。

## 4. Canonical、Projection 与 Evidence

产品主链只由 `02-工程编译器-MVP-PRD与架构稿.md` 定义；Engineering IR、Workspace domains、Target IR/Lowering 与 Brownfield 的实现级边界分别由 `14` 和三个 `architecture/**` owner 定义。本文不复制数据流、字段表或状态机。

所有其他表面只允许窄投影：ExplainGraph、ReviewSummary、SemanticView、Workbench 与文档索引不拥有新事实；外部 graph/provider 只提供 Evidence/Overlay 或 Source Program Model candidate；Semantic Mutation 只能回写 Authoring Source，再由 compiler 重建 canonical IR 与 projections。Agent Skill只是启发式可执行投影；repository audit只是 exact-revision Evidence，二者都不拥有新的产品、Gate、权限或状态事实。

## 5. 文档状态

- `active`：当前权威或当前执行文档。
- `stable`：事实稳定，仍是权威。
- `draft`：未冻结，不得作为既定协议实现。
- `historical`：历史决策或旧计划，只用于追溯。
- `archive`：原始材料，不参与当前实现决策。

## 6. 修改规则

- 新产品决策先改 `02`；影响阶段时同步 `03`。
- 新 IR/Predicate/Operation 先改 `14`，再改类型、validator、builder和 contract tests。
- 新 Target/Profile/Type/Application/Behavior/Program IR 改 `architecture/sec-ts-ir-layers.md`。
- 新 Workspace domain 改 `architecture/engineering-workspace-ir.md`。
- 新 Brownfield Provider 或阶段改 `architecture/brownfield-import.md`；输出不得自动成为 authority。
- 新 Host/Toolchain/Target runtime 决策、package/runtime layout 或公开分发合同先改 `13`；Target IR 的 lowering 细节仍由 `architecture/sec-ts-ir-layers.md` 拥有。
- 修改 canonical authority、公共合同、identity/revision、状态所有权、pipeline或跨 owner边界，先执行 `sec-architecture-evolution`；冻结唯一owner、机制、不变量、迁移和退出条件后再进入实现。
- 新Agent启发式入口先确认canonical owner，再由 `sec-heuristic-governance` 判断能否下沉为确定性合同；不能下沉时登记行为 owner并创建或扩展唯一Skill。不得只在Markdown、prompt、注释、测试或脚本中孤立出现。
- 用户明确要求全仓分析、重大架构变更前或出现系统性漂移时执行 `sec-repository-audit`；报告绑定 exact revision，发现进入独立 Work Package 前不升格为 authority。
- 新外部工具、MCP、Provider、版本升级和退役改 external capability policy/ledger。
- Nexus Census/Parity/Retirement 只改 canonical conformance/ledger/report。
- 动态状态变化只更新 `work/**`；长期规范不得记录当前 SHA/PR/CI 流水。
- 引入新文档前必须说明独立职责、消费者、Gate、更新触发和退役条件；否则归入现有 owner。

## 7. 禁止的重复体系

以下路径或同类结构不得成为 active authority：

- `docs/goals/sec_document_system_v4/**`；
- <docs/goals/SEC_Document_System_V4_Combined_Reference.md>；
- 任何再次复制 `00–14`、长期 Goal、路线、Skill执行闭包或 Nexus 规范的“合集”；
- 只能依靠聊天解释用途的状态报告；
- 外部工具自动生成的第二套 AGENTS/Skills/Host rules；
- 在测试注释、PR模板、脚本说明中维护与 canonical Skill 冲突的 Agent 指令。

迁移材料与历史执行闭包在完成使命后，必须删除或移入 `archive/`（如 `archive/work-packages/`），绝不允许在 `work-packages/` 目录下长期积压并列。

## 8. 质量门

每份 active/stable 文档必须：

1. 有 frontmatter、唯一 H1、职责说明和权威链接。
2. 明确区分已实现、当前开发、规划和历史。
3. 不把目标写成现有保证，不把旧 Evidence 写成新 revision 证明。
4. 不维护会频繁变化的版本、计数、PR/CI状态，除非该文档就是相应机器账本或动态控制面。
5. 任何绝对路径、外部版本和动态事实必须有范围、日期与失效条件。
6. 全部 tracked Markdown必须被分类；活动authority/projection必须有Skill coverage；已登记启发式运行面必须解析至少一个Skill owner。
7. 每个 repository behavior只有一个Skill owner，每个Skill必须拥有一个真实行为；候选隐藏行为由全仓审计列出并交给启发式治理裁决。
8. `docs-doctor` 必须同时保有 legacy frontmatter/status、`file:///`、active repo path 与 deprecated-token诊断，并检查 required canonical owner、每份 active authority 的唯一 H1、retired V4实体、NFC/U+FFFD path、显式 Markdown link、唯一 active Work Package 与三控制面的共享 parser/binding，以及非当前活跃包归档。`00`可定义和引用禁用路径；其他 active authority 不得把它们重新引用为有效 owner。Frozen historical Work Package 的 inline code path 只表示当时输入、禁止面或未来输出，不冒充当前链接；显式 Markdown link仍须解析。

`docs/scripts/docs-doctor.ts` 属于 verifier trust root。扩充这些检查必须建立独立 frozen Work Package、保持 legacy诊断语义超集并通过人工 bootstrap；不能在普通文档替换中静默改写后用同一 CI revision自证。
