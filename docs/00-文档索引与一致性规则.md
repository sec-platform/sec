# 文档索引与一致性规则

本文是 SEC 文档权威图的唯一入口。目标只有一个：**同一工程事实只维护一次；动态状态、稳定规范、历史证据和外部分析不得混成第二事实源。**

## 1. 文档域与唯一职责

## 2. 事实归属

- 产品是什么、不是什麽：`02`。
- 稳定阶段顺序和完成定义：`03`。
- 当前 exact 状态：`work/current-state.yaml`。
- 当前正式闭包：`work/active-work-package.md` 指向的 `work-packages/<id>.md`。
- 当前包和近期候选：`work/rolling-plan.md`。
- Engineering IR 与 Semantic Mutation canonical contract：`14`。
- 后续 TS IR/Lowering：`architecture/sec-ts-ir-layers.md`。
- Engineering Workspace 多域 IR：`architecture/engineering-workspace-ir.md`。
- Brownfield 与 Source Program Model：`architecture/brownfield-import.md`。
- 外部工具/MCP/Provider：`governance/external-capability-and-provider-policy.md` 与 ledger。
- Nexus Census/Parity/Retirement：Nexus conformance 文档、ledger、report。

其他文档只能写一到三句摘要并链接 owner，不得复制完整字段表、状态机、阶段表或命令矩阵。

## 3. 冲突优先级

1. `main` 中代码、公开合同和适用验证证据决定当前实现事实；发现文档漂移后必须同步修正文档。
2. 产品边界以 `02` 为准；稳定阶段和完成定义以 `03` 为准。
3. Engineering IR/Mutation 以 `14` 为准；下游 Projection、Workbench、AI、Provider 不得反向拥有语义。
4. Agent 仓库执行方式以 `04` 为准；产品内 AI Runtime 以 `09` 为准。
5. `work/**` 只拥有动态状态与近期选择，不得复制长期 Goal、阶段合同或完整架构。
6. Issue、PR body、branch、聊天、报告、代码图和 LLM 摘要只提供导航或证据线索，不能单独证明完成或 authority。
7. 外部 Provider 的共识不构成多数票升格；authority 仍需明确 owner/policy 裁决。

## 4. Canonical 与 Projection

```text
Product Intent / Existing Workspace
→ Canonical Workspace Input Snapshot
→ Engineering IR + independently validated workspace domains
→ Validated Engineering Workspace Snapshot
→ Application IR
→ Behavior IR
→ Target Program IR
→ Validated target Compilation Snapshot
→ Source / Test / Docs / Gate / Agent / Release Projections
→ Verification / Provenance / Workbench
→ Semantic Mutation / Atomic Publish / Rollback / Recovery
```

- Engineering IR 是工程语义 canonical representation。
- Application/Behavior/Target Program IR 是独立 validated lowering 层，不重新解释上游 authority。
- 实施阶段可让现有 validated Engineering IR作为 provisional target-lowering input；完整 Workspace domains进入后必须由唯一 snapshot builder原位 reconcile并使旧 target snapshot失效，禁止双 loader、双 writer或双 revision authority。
- ExplainGraph、ReviewSummary、SemanticView 和 Workbench 是投影，不拥有新事实。
- 外部 graph/provider 输出只进入 Evidence/Overlay 或 Source Program Model candidate。
- Semantic Mutation 只回写 Authoring Source，再由 compiler 重建 IR；禁止直接 patch IR/Projection。

## 5. 文档状态

- `active`：当前权威或当前执行文档。
- `stable`：事实稳定，仍是权威。
- `draft`：未冻结，不得作为既定协议实现。
- `historical`：历史决策或旧计划，只用于追溯。
- `archive`：原始材料，不参与当前实现决策。

## 6. 修改规则

- 新产品决策先改 `02`；影响阶段时同步 `03`。
- 新 IR/Predicate/Operation 先改 `14`，再改类型、validator、builder和 contract tests。
- 新 Target/Profile/Type/Application/Behavior/Program IR 改 `architecture/sec-ts-ir-layers.md`。
- 新 Workspace domain 改 `architecture/engineering-workspace-ir.md`。
- 新 Brownfield Provider 或阶段改 `architecture/brownfield-import.md`；输出不得自动成为 authority。
- 新外部工具、MCP、Provider、版本升级和退役改 external capability policy/ledger。
- Nexus Census/Parity/Retirement 只改 canonical conformance/ledger/report。
- 动态状态变化只更新 `work/**`；长期规范不得记录当前 SHA/PR/CI 流水。
- 引入新文档前必须说明独立职责、消费者、Gate、更新触发和退役条件；否则归入现有 owner。

## 7. 禁止的重复体系

以下路径或同类结构不得成为 active authority：

- `docs/goals/sec_document_system_v4/**`；
- <docs/goals/SEC_Document_System_V4_Combined_Reference.md>；
- 任何再次复制 `00–14`、长期 Goal、路线或 Nexus 规范的“合集”；
- 只能依靠聊天解释用途的状态报告；
- 外部工具自动生成的第二套 AGENTS/Skills/Host rules。

迁移材料完成逐项归位后必须删除或移入 `archive/`，不能长期并列。

## 8. 质量门

每份 active/stable 文档必须：

1. 有 frontmatter、唯一 H1、职责说明和权威链接。
2. 明确区分已实现、当前开发、规划和历史。
3. 不把目标写成现有保证，不把旧 Evidence 写成新 revision 证明。
4. 不维护会频繁变化的版本、计数、PR/CI状态，除非该文档就是相应机器账本或动态控制面。
5. 任何绝对路径、外部版本和动态事实必须有范围、日期与失效条件。
6. 当前 `docs-doctor` 必须继续保有 frontmatter/status、`file:///`、广义 repo path 与 deprecated-token诊断；缺失 canonical owner、非唯一 H1、重复 V4实体和“policy owner可提及禁用路径但其他 active文档不可引用”的 differential negative fixtures属于后继 trust-root hardening，未进入 `main` 前不得宣称已经自动执行。

`docs/scripts/docs-doctor.ts` 属于 verifier trust root。扩充这些检查必须建立独立 frozen Work Package、保持 legacy诊断语义超集并通过人工 bootstrap；不能在普通文档替换中静默改写后用同一 CI revision自证。
