# 文档索引与一致性规则

本文只定义 SEC 文档的**唯一职责、冲突顺序和生效边界**。它不是开发流程副本，也不拥有产品字段、当前进度或具体 Gate。

## 1. 五类工程信息

| 类型 | 唯一事实源 | 禁止混入 |
| --- | --- | --- |
| 当前实现事实 | 最新 `main` 的代码、公共合同和适用测试 | 计划、PR body、聊天、旧报告 |
| 稳定产品/架构 | 对应 canonical owner 文档 | 当前 SHA、PR、CI、临时任务 |
| 动态状态 | `docs/work/**` 加 live resolver | 长期架构、完整能力清单、执行流水 |
| Agent 启发式 | `.agents/skills/**` 与行为 registry | 产品事实、Gate 实现、动态状态 |
| exact-revision Evidence | `docs/evidence/**`、CI 日志与产物 | 新 authority、长期保证、跨 revision 证明 |

规则只有被类型、Schema、parser、validator、test、Hook 或 CI 实际观察并拒绝时，才是**硬合同**。必须由 Agent 判断触发、工具、回退或停止的规则属于**启发式**，只能由一个 Skill 拥有。仅存在于 prose 的目标、比例和口号不构成 merge gate。

## 3. 冲突顺序

1. 当前实现事实以最新 `main` 代码、公共合同和适用测试为准；文档漂移必须修正。
2. 产品边界以 `02` 为准，阶段与完成定义以 `03` 为准，Engineering IR 以 `14` 为准。
3. `work/**` 只拥有动态选择，不得覆盖长期 Goal、架构或验证语义。
4. `04` 只拥有稳定 Agent 协议；具体行为以唯一 Skill 为准；产品内 AI 以 `09` 为准。
5. Issue、PR、branch、聊天、代码图、审计报告和外部 Provider 只能提供导航或 Evidence。

## 4. 修改协议

- 改产品边界：先改对应 canonical owner，再改类型、实现、测试和投影。
- 改公共合同、identity/revision、state owner、pipeline 或跨 owner 架构：先执行 `sec-architecture-evolution`。
- 新增 Agent 判断：先判断能否下沉为机器合同；不能时由 `sec-heuristic-governance` 归入唯一 Skill。
- 新增文档：必须有独立职责、消费者、更新触发和退役条件；`docs/**/*.md` 未登记时 fail closed。
- 动态状态只改 `work/**`；能力是否完成不得由人工清单单独证明。
- 历史执行闭包完成使命后进入 `archive/work-packages/`；Evidence 不升格为 authority。

## 5. 质量门

每份 active/stable Markdown 必须有合法 frontmatter、唯一 H1、明确职责和有效链接。`docs-doctor` 负责结构、路径、Unicode、生命周期和控制面一致性；Agent governance 合同负责 Markdown 分类与 Skill coverage；二者都不能仅靠关键词出现证明规则语义正确。

禁止恢复 `docs/goals/sec_document_system_v4/**`、`SEC_Document_System_V4_Combined_Reference.md` 或任何再次复制 `00–14`、长期 Goal、Skill、路线和动态状态的合集。
