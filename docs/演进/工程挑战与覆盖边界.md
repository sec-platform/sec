## 目标到义务的自主发现主循环

本节拥有设计阶段的自主发现算法。它把已经存在的目标、约束、反例与问题登记接成当前可执行的工作方式，不要求用户先指出哪个模块有问题。运行产品只在真正请求设计评审时消费相交规则；一个普通编译请求不加载全产品问题库。

当前采用**目标—义务关系图＋单一问题登记＋按任务投影的工作前沿**。总表是供人和AI浏览、排序、过滤的视图，不是唯一能够表达关系的结构；没有新建在线管理平台、数据库或独立计划选择器。当前用Markdown条目、稳定锚点和准确引用即可维护。

### A0 固定本次目的而不是跟着最近一个例子走

先读实际入口、用户持续约束、当前任务与父版问题。取得三项结果：当前必须交付什么；什么动作没有授权；哪组长期产品目标仍然成立。把每项来源标为用户要求、已接受产品目标、设计推导、外部观点或待确认事实。外部规范不是自动生效的本地要求，助手选了一个MVP也不因此删除长期目标。

对已经明确的条件不重复追问。缺失条件先区分会影响幅度与会反转方案的变量；可安全建立基线时说明假设并继续设计，涉及授权与不可逆作用时保留真实边界。用户的目标、偏好和权限作为任务约束，其事实或因果判断仍需独立检验；技术提醒只产生比较义务，不自动成为采用决定。

当前根目标及全部已知问题的关联由[目标总览](../状态/前沿与登记规则.md#目标到问题的总览)保存。G编号只是本设计的归并索引，不进入作者语言或每次开发请求；它不声称已经逐字取得用户全历史。新要求无法归入某项时，保留独立来源并更新问题地图，不强塞进旧目标。

### A1 从接受结果倒推必要义务

对每个实际目标，写一个合法成功情形，然后问：为了这个结果成立，作者、解释、实现、目标和采用分别需要什么事实与能力？逐层得到**必要结果和接口义务**，不要直接从“要快”跳成“必须分布式”，从“要自由”跳成“必须新增关键字”。

不能以标签重述作为第一性依据。对决定方案的约束，说明改变它为何会改变结果、可检验的作用链、适用范围、绕过与失效条件，以及在多约束下是否真正控制结果。对相交链继续检查间接效应、反馈、时滞、阈值、累积、不可逆点和成本转移；证据显示约束或分类不成立时，返回本阶段重建，而不只补一个例外。

每条派生义务记录父目标、作用对象/范围、激活条件、可观察的完成结果和推导理由。其必要性来自：外部硬要求；父结果的逻辑前提；已经选择的架构引入的义务；或明确选择的优化。后两类必须标明：换了架构可能移除该义务，优化也不自动成为全局必须。

例如“支持中立源生成TS与Java”导出各目标的数值、错误、模块和ABI保持；并不导出“所有高级语言今天都完整实现”。“支持不覆盖用户修改”导出前像、作者归属、冲突与可恢复写回；不自动导出一个分布式数据库。未选方案的后续实现不取并集，已经产生的恢复责任却不能按未选优化删掉。

### A2 用有类型的关系代替一棵纯树

| 关系 | 判定含义 | 对下一步的影响 |
|---|---|---|
| AND共同满足 | 父结果需要全部列出的子义务，并满足它们的接口组合 | 单个子项绿色不足以关闭父项 |
| OR合法替代 | 某一满足范围的方案足够 | 选定一条后只激活它的真实依赖；保留其他方案的适用范围与重开条件 |
| 条件激活 | 条件为真时才引入义务 | 未知条件保留待判定，不能自动当不适用；运行事实与设计选择分开 |
| 硬前置 | 开始指定动作前必须已满足 | 只阻断该动作与真正依赖它的后继 |
| 协同设计 | 两个接口要共同裁决，但无需等待对方软件已实现 | 可以作为一个设计单元，不伪造先后环 |
| 不可兼容 | 同一范围下两个选择不能共同满足 | 返回真实冲突与最强替代，不能平均或最后写入覆盖 |
| 产生/消费/验证 | 产物或声明有实际生产者、使用者和对应方法 | 孤立文件、无消费者机制和没有义务的检查进入必要性复审 |
| 失效/替代 | 前提变化使旧判断重开，或新决定明确取代旧决定 | 更新新图及旧消费者；不把旧问题悄悄删除 |

这些关系可以包含共同原因和多方不变量，所以根目标不是文件夹树，工作顺序也不是按行号排序。所选执行动作在解决真正循环后形成可调度图；整个知识和设计关系本来可以有反馈。

### A3 追到可交付叶项，而不是一直拆到代码行

一个设计叶项要能够明确交付：负责规范、输入和前态、当前数据/算法/接口、正常结果、保持范围、失败分支、资源与进展、验证设计、替代与重开条件。已有规范已经承担它时引用其具体位置，并写清当前调用方传入/返回及异常处理。

出现以下情况应继续拆分：同一条里混了可独立完成的决策；责任归属相反；激活条件不同；一个问题阻塞了另一个本可独立的结果；关闭条件无法判断。出现这些情况则合并：拆分只产生重复字段或重复审查，边界之间没有独立含义、消费者或失败路径。

叶项可以是一个算法、一个构造规则、一个适配合同或一次明确的设计决定。只设计任务不必拆成函数实现和产品测试文件；图中的叶项粒度也不等于作者源节点、线程、文件或服务粒度。

### A4 从现有设计反向检查多余、遗漏和错误前提

对当前每一项机制反查其目标和义务：确无来源也无被接受的推导时，先列更小替代或删除候选，不以“行业最佳实践”直接保留。对每个目标反查它是否有完整的交付链，只有一个标题或一个类型名不能算完成。

再检查输入输出、失败、资源、版本和作用的连接：某个消费者依赖的保证有没有生产者；一个动作是否假定了没有声明的全局状态；两个分别合法的组件组合是否增加义务；只读任务是否被写回、签名或部署记录阻塞。

缺少路径是**追踪缺口**，不自动证明软件功能不存在；有路径也不证明含义正确。模型或静态工具只能发现候选，仍需阅读相交正文作语义裁决。NASA的要求管理同时要求双向追踪和检查派生要求是否真正完整满足父项，也明确处理无根据的额外需求。本包借用这组检查，不复制其全部组织审批流程。[依据](https://www.nasa.gov/reference/6-2-requirements-management/)。

### A5 每个重要边界主动生成反例，不等用户提示

先保留合法成功路径，再依次改变该边界上最可能导致质变的条件：删除最后一个支持；将未知当空值；新增约束但原对象不变；相同结果换来源；改变阶段或责任；让旧响应迟到；两个任务争一份资源；恢复库和主库一起回退；把一个可选优化当全局前置；把一个局部完成当整组成功。

单一扰动揭示耦合后，再组合相关扰动，例如“取消＋远程失联”“规则升级＋旧缓存”“管脚改写＋外部原文变化”。不是盲目生成所有轴的笛卡尔积，也不把成对覆盖误称全部高阶组合证明。新反例揭示新对象或新约束时，回到A1/A2重建相交图。

必须同时尝试最强竞争方案：不用新增机制是否足够；直接成熟工具是否更小；保留原生资产是否更合适；中立作者的同等保证能否以更少决定表达。反证当前最强方案，而不是只收集能支持它的案例。

### A6 两个独立入口轮换，减少目录和最近问题的锚定

一条入口从目标正向推导；另一条从一个具体使用过程、成熟系统机制或真实失败倒推当前合同。比如，从“线程池里所有父任务都在等子任务”倒查，就会发现仅有DAG和线程安全不足以保证进展。

还要从已有设计删除一整类设施，观察目标是否仍能完成。纯计算去掉数据库、设计请求去掉产品执行、结构编辑去掉人类GUI，都应各有合法路径。某领域不在本次实施，不等于在设计发现中禁止检查它对核心的约束。

这些是不同审查视角，不宣称同一模型换两个角色就取得了两个独立证据源。外部资料、独立方法与真实观测的共同原因另行保留。

### A7 有缺口先保存，再立即能裁决的就裁决

已知问题进入[单一主登记](../状态/前沿与登记规则.md#已知问题主登记)，有完整方案后也只关闭对应设计子项。每项标明来源、目标、必要性、当前方案、剩余义务、直接依赖、决策范围和关闭条件。缺方案时保存最小可复核反例、当前安全或可用路线、下一份要形成的规格，不能等想好后才登记。

在当前授权内能补的设计，不转交为“以后让agent分析”。当前任务不授权实现，所以实施前像、产品运行与外部账号事实仍保留具体取得路径，不伪造。这种区分不能成为回避纸面算法和接口设计的理由。

### A8 按真实依赖和优先级推进，然后回扫消费者

使用[实施前沿与优先协议](实施/主线前沿与准入.md#问题优先级与当前可推进前沿)选择当前工作，不按问题编号、出现先后、代码行数、最容易写或者最后一条用户消息决定。

一个根前提改动，先修它的规范拥有者，再检查调用方、文法/模式、实例、目标、检查、迁移、理由和问题状态。几份文档分别看似正确仍可彼此矛盾。必要时把原来的依赖关系标为失效并回到A2，不能只在新段落写“以本章为准”。

结束前做一次逆向检查：每个关闭结论有范围和依据；每个原开放问题有当前去向；新条件激活的义务被纳入；未读取内容没有被写成已审；本次修改没有增加未经授权的执行或作者负担。

### A9 交付的是当前闭包与开放前沿，不是绝对穷尽宣言

本次输出包括：已固定目标；已展开义务；实际读取与未读范围；修订与反例；尚开放且有具体下一步的前沿；当前优先顺序及其理由。对已有有限、固定、可枚举的范围，可以检查所有节点/边/分支；它不自动成为开放现实的全部问题。

默认停止条件不是“已经写了很多”，而是当前授权和工具范围内，有依据的队列已被处置，重要攻击不再改变当前结论，或遇到明确的能力/权限/平台边界。尚未展开的邻域保持未审并指出怎样继续。没有新产出的重复搜索、同义拆分和无机制猜测不继续生成问题。

再次收到“继续”时，先读取本节、当前目标与就绪前沿，选择未解决的上游问题并主动扩展相交区域；不要求用户先给下一个关键词。没有跨会话常驻执行器时，该行为发生在实际任务中，不承诺离线后台一直工作。

## 从一个目标完整推导到具体工作

以“局部作者修改后生成仍合法且尽量稳定的源码”为例，目标不是一句`少改`：

| 派生义务 | 为什么需要 | 当前处置与已知问题 |
|---|---|---|
| 当前作者来源与精确基础 | 不知基于哪份内容就不能识别这次变化 | 源/结构拥有权、候选前像；U001、U006、U050 |
| 本次真正改变的含义 | 参数、要求、实现选择和目标形态有不同后果 | 要求关系与控制；U031、U042、U047 |
| 真实影响与共同约束 | 局部字段可能影响多个消费者 | 查询删除/新增与组合；U012、U043 |
| 布局连续性输入 | 没有明确历史基础就只能规范重生 | 既有布局政策；U053 |
| 并行的共享名字和输出拥有者 | 各模块分别选名或争写文件会制造不稳定 | U063、U064 |
| 原生区、资源与其他文件保持 | 小源码修改不能覆盖人工文档或图标 | U032与原资产合同 |
| 产物资格与真实写回 | 可生成不等于当前工作区前像仍相同 | U017、U018、U051 |
| 退路和采用收益 | 不可保持时应解释重组，整体成本也可能不划算 | U015、U019、U045 |

其中选择`canonical`规范重生可以不依赖历史布局，但它不能满足明确的严格历史结构保持。选择只预览可以不依赖写回恢复，但它也不宣称已写文件。总表因此必须保留AND/OR和条件，而不是将上表每项变成所有任务的统一前置。

派生到U063时，采用的具体设计为：先固定全组公共符号与布局，按输出拥有者分派独立打印任务，冲突由协调者在实际发布前拒绝。这个义务不是用户先说了“命名竞争”才存在，而是从目标、并行方案和两个生产者的组合直接推出来的。

## 覆盖判定怎样避免自我认证

**目标覆盖**检查每个接受目标是否有承担它的义务和验收。

**边界覆盖**检查已选择组件之间的输入、输出、错误、版本、资源与作用是否接合。

**生命周期覆盖**检查该对象的产生、使用、变化、故障和退出；不适用项要有实际原因。

**扰动覆盖**记录实际分析过的删改、并发、失联、默认变化和恢复情形。

**实现/现场覆盖**只在实际取得对应证据时记录，不由文档覆盖代签。

当前分母来自固定版本中已声明的目标和边界。如果后来发现遗漏目标，分母也要变；不能用100%完成旧表证明世界完整。存在新问题不表示所有旧设计无效，旧表全绿也不阻止继续发现。

## 完整语言体系的主动补位

从“作者能定义任意独特行为”推导语言、资源和工具义务，不只从最近收到的名词开始。语言新增或修改时使用[三十类能力裁决与C0—C5](../作者/需求关系与能力边界.md#4-完整语言能力的当前裁决)，沿共享存储、绑定、控制、阶段、错误和输出检查组合。二元检查发现同一对象同时受第三条规则控制时继续追踪，不能因表格只预设两轴而截断。

当前明确的主动反例包括：var经闭包返回导致位置外逸；公开效果隐藏后内部两个调用被合并；let绑定的函数隐藏共享可变状态却被多态化；return已求值但close失败；close失败还留子任务使用父缓冲；目标finally/defer改变主错误；编译期函数读取未绑定环境。它们的处理归控制、语言、编译和验收规范，不在此重复算法。

每个反例先检验当前规格是否已经解决：已经解决则使用相应规则，不再创建同义U项；确有缺口则改拥有者和消费者。研究所用原始规范沿[来源协议](../依据/来源/设计依据与资料边界.md#研究结论的保存复用与失效协议)更新，不把提问者当成补齐资料的唯一触发器。

## 根设计反例的可重复生成方式

从一个能成功完成的完整任务开始，固定要求、输入域、实际来源、所选实现和输出。每次只扰动一个会改变结论的关系，再检查原因能否定位到准确责任，而不是重新列行业名单。之后组合两项相关扰动，检查局部结论是否仍可组合。

| 扰动 | 必须观察到的正确设计行为 |
|---|---|
| 修改候选前置使难输入不再合法 | 原任务接受域不变，产生要求违反或新的目标变更候选 |
| 两模块类型相同、值域不相容 | 产生具体连接义务，选择明确修复而非默默Clamp/截断 |
| 两组件互相引用保证，没有初态或归纳规则 | 留下开放假设，不自证；合法递归仍可采用对应方法 |
| 删除局部较慢但布局不同的方案 | 检查支配前提，保留真实可能更优的完整路径 |
| 源数值未变，设备/布局或证据前提改变 | 值消费者可复用，预算/资格消费者重新判断 |
| 合并两个旧独立分区的新约束 | 在新图范围联合检查，不只重算一个旧分量 |
| 运行任务被取消但异步借用未结束 | 保留真实资源和恢复责任，不将取消标记当释放 |
| 新方案只通过转移费用或风险取得低分 | 保留主体和不可补偿要求，拒绝错误标量比较 |
| 更优候选不断出现 | 有范围比较与显式切换，不在活跃操作中抖动 |

反例期望分别来自已接受要求、公开方法合同或本规范的可复核推导。此表不证明全部问题已经发现，也不是待执行的产品测试代码。检查原合法任务仍能结束：未知只阻断对应保证，设计、纯生成或独立根仍应得到准确结果。详细机制由其各自规范拥有，不在本篇重复字段与算法。

## 世界工程机制覆盖矩阵

### 1. 覆盖原则

本矩阵是检查不同工程形态能否复用共同约束的设计索引，不是已执行验证；领域完整知识与运行支持需要对应资料和证据。

| 工程形态 | 关键机制 | SEC 共享内核 | 领域扩展 |
|---|---|---|---|
| 编译器/语言 | 类型、IR、pass、lowering、增量 | identity/relation/constraint/action/evidence | 语言 dialect/backend |
| Web | 模板、DOM、CSS、浏览器 | source/semantic/effect/verification | web dialect/browser provider |
| 数据库 | 事务、隔离、schema、恢复 | state/transition/resource/evidence | data dialect/store provider |
| 分布式 | 消息、分区、复制、共识 | identity/epoch/authority/recovery | distributed profile |
| 云平台 | 资源、部署、伸缩、区域 | capability/allocation/effect/support | cloud provider adapters |
| 嵌入式 | 实时、硬件、物理安全 | target/resource/claim/risk | hardware/real-time dialect |
| AI/ML | 模型、数据、漂移、工具 | candidate/provenance/authority/evidence | model provider/eval profile |
| 安全 | principal、trust、attack、incident | authority/effect/evidence/evolution | security policies/providers |
| 业务工作流 | actor、decision、compensation | operation/state/contract | domain definitions |
| DevOps | build/test/release/rollback | action/evidence/delivery/evolution | tool providers |
| 文档知识 | source、translation、projection | identity/provenance/invalidation | documentation domain |
| 组织治理 | role、policy、approval、appeal | authority/stakeholder/decision | organization profile |

### 2. 反特化判据

普通新业务应以用户定义、组合和绑定表达，不要求通用编排层增加一个场景分支。领域编译器、后端或适配器自然可以处理本领域的操作与类型，不能仅凭出现领域名就判定架构错误。真正的新语义揭示公共接口不足时，允许有理由地修改核心；必须说明旧接口遗漏了什么不变量、保持条件或能力，不能为维护“核心永不变”的叙事把语义藏进字符串。

### 3. 未覆盖声明

矩阵不证明具体法规、设备、协议或框架已经支持。真实支持由相应 DomainDialect、Provider、TargetProfile、conformance corpus 和 SupportClaim 证明。

## 全景工程问题分类与生成规则

### 1. 生成而不是记忆

工程问题空间通过关系和反事实生成。每次分析从目标和对象出发，沿生命周期、主体、依赖、权限、资源、尺度、环境、失败和演进展开。

### 2. 对象轴

源码、配置、数据、模型、文档、依赖、制品、进程、设备、凭证、用户、组织、权威、证据、恢复资产和外部系统。每个对象检查身份、状态、owner、接口、消费者和物理绑定。

### 3. 生命周期轴

创建、发现、采用、使用、并发、变化、迁移、失败、恢复、支持、撤销、删除和历史解释。只设计正常运行而没有创建/退出会留下系统性漏洞。

### 4. 主体轴

调用者、owner、执行者、审批者、验证者、付费者、数据主体、受影响第三方、维护者、攻击者和未来继任者。检查谁获益、谁付成本、谁承险、谁可申诉。

### 5. 约束轴

物理、数学、逻辑、信息、时间、资源、权限、法律、资金、认知、组织、生态和路径依赖。区分硬不可补偿约束与可权衡目标。

### 6. 依赖轴

上游、下游、平台、供应链、共享资源、替代品、互补品、外部性、共同原因和恢复依赖。特别攻击“主系统与恢复系统共享同一故障域”。

### 7. 尺度轴

单对象/全局、单用户/多租户、正常/峰值、短时/长期、本地/跨区、平均/尾部、正常/恶意、静态/持续变化。

### 8. 失败轴

错误输入、沉默错误、假成功、超时、取消、竞态、资源耗尽、部分完成、丢句柄、恢复失败、监控失败、供应商退出、法律变化和黑天鹅。

### 9. 反事实问题

- 删除某对象会怎样？
- 替换 Provider 会怎样？
- 输入在检查后变化会怎样？
- 同一操作执行两次会怎样？
- 权限在执行中撤销会怎样？
- 恢复系统也失败会怎样？
- 新旧版本同时存在会怎样？
- 未观测部分恰好包含反例会怎样？
- 最强攻击者能控制哪些输入？
- 哪个未知一旦确认会反转结论？

### 10. 停止条件

只有新展开不再产生独立机制、根约束、owner seam、关键反证或反转条件，并且 remaining frontier 有 owner 和触发器，才关闭当前分析代际。

## 反过度设计与最小适用性

### 1. 最大化设计不等于最大化运行复杂度

本设计库持续扩大有机制依据的问题空间，但不声称存在已完成的最大集合。每个具体请求按已选择路线处理适用依赖；无相交影响的能力不进入运行和默认阅读路径。决定某能力“不适用”所需的选择信息本身仍可能是依赖，不能先删掉它再声称没有影响。

### 2. 过度设计信号

- 没有真实 consumer 的字段/服务/registry；
- 为没有真实消费者的内部临时对象创建发布流程或迁移层；持久化、跨边界交换的合同即使只有一个实现，也需要明确版本；
- 每个任务默认全仓扫描；
- 所有项目加载 browser/container/AI；
- 文档元数据反向控制产品；
- 把外部产品 topology 原样复制；
- universal helper 吞掉领域语义；
- 证明成本长期超过避免的问题；
- 未来假设占据当前 critical path。

### 3. 最小准入

新增机制需要真实问题、不可由已有模型表达、独立 consumer、可观察 failure、owner、生命周期和退出条件。否则采用现有 relation/binding、延后 trigger 或删除。

### 4. 画像裁剪

纯库、本地 CLI、团队服务、云平台、AI 运行、实时嵌入式分别选择适用领域。Core 保持相同，但 deployment 和 assurance 不同。

### 5. 反欠设计

最小化不能省略可达的权限、Effect、资源、恢复、数据和用户结果。简单系统不是把未知默认掉，而是有更小的真实闭包。

### 6. 性能证据

任何治理机制需要测量它减少的返工、事故、重复执行和认知成本；如果长期净负担更高，收缩、自动化或退役。

## 开放世界工程问题空间

### 1. 目标

SEC 不把“所有工程问题”理解为一张永远不再变化的清单。现实会继续产生新的语言、平台、组织、法律、攻击、硬件和业务约束，任何静态清单都会失效。SEC 的产品身份仍是通用工程工作区编译器；本篇的开放世界问题分析是其可选设计/评审机制：组织当前已接纳问题的处置，显式记录覆盖边界，并在新事实出现时定位缺口、受影响闭包及重新验证义务。不能据一次搜索宣称已吸收世界全部知识。

```text
现实事件、用户目标、事故、标准、代码变化
→ 有界观察
→ 问题候选
→ 机制还原
→ 现有模型映射
→ 已覆盖 | 缺口 | 冲突 | 未知 | 不适用 | 延后触发
→ 设计修正或领域扩展
→ 本次目的要求的设计交付或获准的后续工作；实现、验证、迁移和退役不自动启动
```

“世界上某项目使用了某项能力”不自动构成 SEC 缺口。只有存在真实消费者，而且缺失会使身份、正确性、权限、效果、恢复、验证、发布或支持没有唯一答案时，才形成设计义务。

### 2. 八类根故障

以下八类是当前发现索引，不是已证明完备的分类定理。异常不能自然归类时，保留独立问题与机制，再修订分类，而不是塞进“其他”或强行改名：

| 根类 | 含义 | 典型表现 |
|---|---|---|
| 目标错误 | 目标、非目标、主体或价值函数错误 | 做对了没人需要的东西；局部指标伤害终局结果 |
| 观察错误 | 没看到、看错、看旧或混合现实 | 多文件混合快照；外部状态漂移；监控盲区 |
| 语义错误 | 身份、关系、状态、单位、上下文或边界错误 | 路径当身份；自由字符串当类型；不同状态机共用枚举 |
| 决策错误 | 候选不完整、硬约束漏检、未知被压扁 | 先按流行度选库；把不支持当低分候选 |
| 准入错误 | 无权、无能力、无资源或前像已变化仍执行 | 过期授权；错环境；资源配额未知却继续 |
| 执行错误 | 部分效果、竞态、重复、失控和结算失败 | 写到一半崩溃；重试重复扣款；子进程残留 |
| 证明错误 | 未执行、错环境、自证、覆盖不足或证据过期 | 跳过测试显示绿色；候选修改验证器后自证 |
| 演进错误 | 兼容、迁移、切换、恢复或退役不完整 | 永久双写；旧解析器继续是竞争事实源 |

### 3. 反例生成与跨边界追踪

发现轴沿用上面的对象、生命周期、主体、约束、依赖、尺度和失败，不再把同一份列表乘成貌似完备的数学张量。它们用于产生问题，不是固定输出目录或有限分类证明。

先固定本次判断的目标、对象、时间、环境、支持范围和真正消费者，列出当前采用的基线假设与最容易使结果反转的假设。沿每个关键接缝画出输入、解释、授权、依赖、实际作用、读回与恢复。检查同一个词在不同阶段是否实际上指不同主体、版本、物理对象或集合。

随后对机制施加有依据的变化：删除最后一个外部支持；改变条件但保持结果值；在检查与提交之间加入新规则；让旧响应迟到；让授权先后变化；同键重复与不同载荷碰撞；让恢复系统和主系统一起回退；增加无法取消的任务；让两方各持一半资源；恢复过期备份或离线删除前的副本。产生新决定性主体或约束时，回到上游重建适用范围，不只在原结论末尾加例外。

每个重要设计同时构造最强替代：不用新增机制能否成立，采用更小本地协议是否足够，已有原生工具能否承担。若某复杂机制只在团队或不可信宿主成立，保留该条件实现，不把成本强加纯库。若无法证明可以安全剪除某个影响，也不自动要求无限探索：标明未审范围、影响未知及需要进一步读取的条件，不把未探索记为不适用。

发现状态至少区分：已复现的文本冲突、有明确步骤的逻辑反例、缺少合同的接缝、已经处理的机制、仍待环境证据的假设，以及无独立依据的猜想。可以在正文以文字和表格表达，不要求为每条想法创建数据库对象。只有关键未知会影响本次实际动作或声明时才限制那个范围。

对重要反例保留初始状态、事件顺序、失效不变量、现行防线、修订后判断、残余前提和反转条件；不能只记录“存在竞态”或“一定要有测试”。有限书面推演是设计证据，只有真实执行并保存其输入/方法/结果才称运行实验。

### 4. 问题记录

```text
EngineeringProblem = exact {
  problemRef,
  observedSubjectRefs,
  intendedOutcomeRefs,
  observationAndCoverageRefs,
  violatedOrMissingConstraintRefs,
  causalMechanismRefs,
  affectedStakeholderRefs,
  effectAndRecoveryRefs,
  strongestCompetingExplanationRefs,
  unknownFrontierRefs,
  existingOwnerOrGapDisposition,
  verificationAndReversalRefs
}
```

上面的结构是需要持续追踪时的概念记录，不要求每次审查创建全字段实例。稳定引用由记录拥有者分配；机制、主体和作用域用于判断是否归入同一问题族，不假定存在一个从自然语言自动算出唯一根因ID的函数。确认同源的记录可以合并并保留各自证据；尚不确定时保留候选关系。相同报错可能有不同根因，同一根因也可能产生不同报错。

### 5. 缺口判定

建立新抽象前必须同时满足：

1. 有现实或已接受未来消费者；
2. 现有语义无法无损表达；
3. 缺失会导致可观察错误或无唯一裁决；
4. 能指出 producer、consumer、状态转移或故障证据；
5. 新抽象具有独立身份、合法性、失效、生命周期或权限语义；
6. 说明相对更小替代的预期收益、概念/实现/迁移/维护成本及关键假设；有实测时采用实测，无实测时只作可逆条件选择，不伪造精确净收益。

若只是新的品牌、产品实例、文件类型或 Provider，通常只增加实例、绑定或领域扩展，不修改核心。

### 6. 当前审查的结束与重新打开

不存在“问题世界永久完成”。本次可以交付的条件是：在已声明的输入与检查范围内，已经发现的独立问题都有处置或明确未决状态；重要接缝和相反条文已沿所属规范检查；至少一轮有竞争解释和反例的复核不再改变当前主要设计；剩余前沿有可执行的读取、规范细化或环境取证方向。

这种结论是审查范围内的暂时稳定，不证明没有未知缺陷。不能把有限时间里“没有想到新例子”写成普遍完备定理；工具、权限或平台边界到达时如实记载已做到哪里。新事故、新消费者、新机制、新环境、相交约束或旧拥有者退出会重新打开相应问题，不要求所有无关设计重做。

### 7. 禁止的伪闭包

- 用文档数量、Issue 数量、测试数量或领域名数量证明覆盖；
- 把“暂未找到证据”直接解释为不存在；
- 把所有异常塞进 `other`；
- 为未知世界预建巨大 optional schema；
- 每发现新变量就加入全局版本号并使全仓重算；
- 把外部案例或标准直接提升为 SEC 权威；
- 把所有未来问题预先实现，导致当前产品无法形成最小闭环。

## 未来问题发现、架构攻击与回退协议

### 1. ChallengeLoop

完整发现流程由[自主发现主循环](#目标到义务的自主发现主循环)拥有。旧入口保留为导航：变化触发A0—A9，先形成设计裁决与相交修订；实现、运行验证、迁移和退役仅在实际任务另有授权时启动。发现一项缺陷本身不授权执行产品。

### 2. ChallengeRecord

记录预期与实际结果、参与主体、环境、因果链、潜伏条件、失效控制、二阶效应、未知、owner 映射、反证、可证伪条件和结论反转条件。

### 3. 回退层级

- 事实缺口：回到 Observation；
- 表达缺口：回到 Semantic Kernel/Dialect；
- 候选/约束错误：回到 Design/Resolution；
- 前像/权限错误：回到 Admission；
- 事务错误：回到 Runtime；
- 证明错误：回到 Assurance；
- 兼容/退出错误：回到 Evolution；
- 目标错误：回到 Product/Stakeholder。

不能在已失效下游末尾加例外维持旧模型。

### 4. 来源多样性

持续轮换真实事故、用户失败、性能、Security/Privacy、标准、论文、语言、平台、嵌入式、分布式、AI、组织、运营和成功但高成本路径，避免一个技术文化自证。

### 5. 停止和重开

当前 epoch 在独立搜索不再产生新机制/根约束/反转条件且 frontier 有界时关闭。新 evidence、consumer、environment 或 owner retirement 自动重开相关部分。

## 真实事故机制与系统反例

### 1. 使用方法

真实事故只作为机制证据和架构攻击，不直接成为 SEC 权威。每个案例提取：预期、实际、因果链、缺失约束、失败控制、恢复和可验证设计义务。

### 2. 维护操作扩大故障范围

一个获授权的维护命令使用错误参数，移除的容量远超预期；恢复又因规模和控制面依赖变慢。设计义务：参数化 Effect scope、blast-radius cell、capacity safety ceiling、独立控制面、操作前模拟和真实恢复时间。

### 3. 合法规则触发最坏复杂度

规则语法合法，但特定正则使 CPU 饱和并被快速全局发布。设计义务：算法复杂度检查、资源预算、staged rollout、即时 rollback、规则作为可执行语义而非普通配置。

### 4. 备份存在但恢复失败

误删除只是触发，多个备份和恢复步骤不可用扩大为数据损失。设计义务：RecoveryCapability、restore drill、独立凭证和存储、唯一恢复副本保护、RPO/RTO Evidence。

### 5. 复用软件的环境假设失效

旧系统中无害的数值转换在新运行域溢出，冗余通道共享同一软件错误。设计义务：Target/environment assumption、range proof、common-cause independence 和系统级验证。

### 6. 配置/模板与运行消费者不匹配

内容字段和 runtime expectation 不一致，静态检查未覆盖真实组合。设计义务：typed producer-consumer contract、版本绑定、runtime validation、分阶段发布和 rollback。

### 7. Plan 与现实漂移

计划生成后外部状态变化，执行仍基于旧前像。设计义务：PurePlan 与 Admission 分离、apply-time reobservation、CAS、actual delta 和 recovery-required。

### 8. 持续调和与外部修改

控制器不断比较 desired/current；一次成功写入不保证持续收敛。设计义务：controller contract、idempotency、hysteresis、single writer、drift provenance 和 bounded oscillation。

### 9. 删除需要 finalizer

对象被请求删除，但外部资源和清理义务尚未完成。强制移除 finalizer 会留下孤儿。设计义务：typed retirement obligation、operational terminal/physical clean 分离、不能手工擦除未知义务。

### 10. 供应链与自动更新

签名或更新渠道被利用时，合法发布机制成为攻击放大器。设计义务：source/build/artifact provenance、multi-party promotion、staged rollout、revocation、rollback 和 behavior verification。

### 11. 统一吸收

这些案例分别攻击目标、观察、语义、决策、准入、执行、证明和演进。新案例若只重复机制，不需要新增 Core；若出现新不可表达状态律，才演进领域方言或内核。

## 边界、极端故障与黑天鹅场景

### 1. 极端不等于不可设计

无法预测具体事件，不代表无法设计对未知的响应。系统可以限制 blast radius、保持未知、提供恢复、记录来源和避免不可逆承诺。

### 2. 复合故障场景

1. 主数据库故障，同时备份凭证过期；
2. CI 平台故障，同时候选修改本地 verifier；
3. 网络分区期间授权撤销；
4. 磁盘满发生在 journal 写入后、Effect 前；
5. Provider timeout，实际操作已完成且 readback 最终一致；
6. 新旧 schema 混合，旧节点从备份恢复；
7. 安全事件要求紧急修复，但主分支保护不可用；
8. 监控与被监控服务共享故障域；
9. 多个 AI reviewer 共享同一错误模型；
10. 低概率尾部输入触发算法指数爆炸；
11. 用户在自动迁移期间手工修改同一对象；
12. recovery cleanup 删除唯一 forensic Evidence；
13. 法域变化使跨区 failover 变得不合法；
14. 供应商突然撤销关键服务和数据导出；
15. 时间回拨使 lease/expiry 判断错误；
16. 大规模自动修复形成正反馈并扩大故障。

### 3. 共同设计响应

- 关键状态和恢复路径独立故障域；
- prepared-before-effect；
- exact preimage、idempotency 和 readback；
- unknown/partial 状态；
- bounded blast radius 和 safe/degraded mode；
- recovery reserve；
- break-glass with expiry；
- content-addressed evidence；
- external/provider exit plan；
- common-cause analysis；
- incident-driven maturity downgrade。

### 4. 黑天鹅协议

当新事件无法映射时：冻结不可逆 Effect、保留原始 observations、扩大 affected frontier、建立最小问题 identity、寻找最高错误前提、形成 temporary safe policy、由有权 owner 修正模型、迁移并验证。

### 5. 验收

系统不要求在未知事件中自动成功，但必须做到：不撒谎、不丢证据、不扩大权限、不重复未知 Effect、不删除恢复资产、给出有界安全下一动作。

### 2. 每条需求最低结构

这里定义现有Requirement的语义信息，不是要求开发者为每个函数手填的公开Schema。先固定对象、含义、强度、适用性与接受来源；其他责任只有真实发生时存在。

| 内容 | 准确角色 |
|---|---|
| 对象及范围 | 约束哪个输入、定义、实例、目标、状态或轨迹；数据域及版本 |
| 含义与条件 | 引用已绑定的有类型关系、帧、时序与激活；尚未解释时保留真实原要求及未解释状态 |
| 强度与选择 | 硬约束、偏好、可接受默认、委派与例外，不从语气词猜权限 |
| 来源与接受 | 独立要求来自哪里、由谁在哪个范围接受；文档作者不是天然授权主体 |
| 需要时的关联 | 稳定requirementRef、相关结果与主体、依赖/冲突、规划顺序和演进/退役 |

精确含义和组合由[跨软件意图合同](../作者/组合/跨软件需求合同.md#cross-software-intent-contract)拥有。`Assurance.plan`再产生验收义务与检查请求，方法与结果不属于每条需求的必填含义。检查可以引用相同要求，但不能因选择了有限方法而把原要求缩为有限样例。已有持久来源按其实际格式和解释绑定读取，不通过改概念表静默迁移字段。

### 3. 需求质量

检查必要、准确含义、适用范围、一致性、可行性、可追踪与可修改性；逐项说明可用的检查办法和覆盖。只有笼统愿景而尚无准确行为时保留Goal并继续细化；已有准确要求但当前没有足够方法时，要求仍然存在，检查状态保持未知，不自动降格或删除。

### 4. 非功能需求

“高性能”“安全”“易用”必须分解为场景、主体、刺激、环境、响应和度量；没有 baseline 时不编造阈值。

### 5. 裁剪

由 ProductProfile、TargetProfile、DeploymentProfile、Stakeholder、Data/Effect 和 risk 关系证明 required/not-applicable/deferred。没有实现不能反推不适用。

### 6. 冲突

能够确定的硬约束冲突返回真实冲突关系；只有相应求解实际给出时才称unsat core，未最小化不称最小核。未确定不代表相容。偏好按已委派的有依据策略比较；主体权利冲突保留其范围及有权处置，不能由实现选择器裁决。

### 7. 变化

需求 revision 只使实际消费者 stale；解释、设计、实现、测试和支持通过 traceability 传播。

## 问题发现怎样收敛为一次可裁决的设计

本节旧的简版步骤合入[自主发现主循环](#目标到义务的自主发现主循环)，不再维护第二套退出算法。研究先产生当前可裁决的方案与反例；主登记保留还需设计、实现和现场证据的范围。完整机制、调用方与对应失败路径一同改回正文，不能仅在工作报告中宣布优化。

## 机制研究的输入范围输出与停止条件

研究服务于一个要作出的设计决定。当前不将“读取世界上所有语言的所有关键字”作为作者面或MVP实施前置；这类集合开放、版本变化且高度重复，无法从词表推导类型、效果、资源或成本。也不因不做全词表普查，就放弃对相交机制的深入比较。

### 研究输入与已选机制表

每个研究问题先给：当前要求/使用场景、要决定的对象、当前候选机制、最强反例、需要保持的观察和允许的资源。优先查实际规范、工具实现及失败材料；同一语法词在不同语言中先归入机制问题，再比较语义，不按单词数量投票。

| 机制轴 | 必须回答的具体问题 | 当前设计方向 | 何时必须重开 |
|---|---|---|---|
| 作者与模块 | 原文、命名空间、导入、未完成草稿和多文件编辑怎样一致 | 直接中立文本、限定导入、单一作者、工具解析 | 必须手填第二模型、重命名丢身份或导入隐式执行 |
| 值与数值 | 整数域、浮点、文本、缺失和表示如何映射 | 明确公共值域；后端保存含义，特殊数值另画像 | 同名类型值域不等、悄悄溢出/规范化 |
| 类型与推断 | 哪些局部可推断，公开接口与泛型是否可检查 | 当前显式公开签名、局部推断、相交高级规则 | 普通表达要重复类型，或推断替换了业务要求 |
| 函数与效果 | 求值顺序、闭包捕获、错误和契约怎样保留 | 基础函数与效果分离，真实调用条件不丢 | 传递函数后检查消失、所谓纯优化改变失败 |
| 结构与高层表达 | 重复模式能否组合、自定义和局部具体化 | 库与显式领域构造使用同一基础 | 只能改模板开关、普通新算法要改核心 |
| 内存和资源 | 值、布局、别名、生命期及异步完成怎样关联 | 逻辑值不规定每步复制；保持条件后复用 | 取消就释放仍在用的内存、独占被误当原地合法 |
| 并发与时间 | 通信、顺序、等待、取消和期限是什么合同 | 具体域明确模型，不将所有状态做事务 | 数据竞争/死锁/实时被一个标签认证 |
| 编译与证明 | IR、优化、编码是否保持同一个对象和含义 | 多层表示按需派生，转换条件具体 | 证明器和后端对数值/文本解释不同 |
| 生态与目标 | 接口、包、初始化、ABI、调试与迁出怎样成立 | TS工程深度往返先行，Java暂缓；C/Rust及其他目标均以实际需求为入口，不预定第二语言 | 目标换了要重写公共语义、包装代替真正生成 |
| 工程控制 | 候选、绑定、权限和实际操作何时决定 | 按对象和时点分开，已绑定重建不重新猜 | 当前选项改写旧操作，保存被当部署 |
| 使用成本 | 冷/暖上下文、变更、诊断和退出的总工作 | 同库同保证完整任务比较 | 仅词数少却总任务更贵、删测试制造优势 |

这张表是研究者的输入分类，不是用户源文件，也不是每个任务都执行十一轮检索。某机制已经由规范明确且当前反例不改变它，就保留选择；新证据改变其前提，再回到相交规则。

### 一轮研究怎样交付

先从当前规范抽出可否证主张；确定备选实际在何处不同；读取原始机制；构造至少一个能区分方案的输入/轨迹；选择当前默认并说明最强替代；把正常路径、错误、资源、兼容与验收写回唯一规范。若关键环境事实缺失，选择有界可逆默认或写明特定阻断，不能把所有备选永久并列。

关键词研究服务于具体机制选择：Python 的软关键字只在特定上下文解释，Rust 的关键字按 edition 演进；关键词数量不能代替完整能力比较。MLIR Toy 先定义作者程序、数据与语义，再描述 AST；这一顺序可用于闭合作者路线，不要求 SEC 采用其张量结构。具体来源与适用边界见[资料目录](../依据/来源/设计依据与资料边界.md)。

研究对当前决策的停止条件是：已排除明显不合格者，当前默认具有明确机制与边界，最强已发现反例已处置，剩余不确定性不会改变当前相交接口或已有处理分支；未来新反例可以重开。它不是穷尽世界知识的证明，也不能以任意网页数、关键词数或一个月限期作为充分性依据。需要运行才能判断的内容转入明确实验设计；在只设计任务中不据此运行产品。

## 以源语言能力和全工程文件复核覆盖

针对“已有语言支持的能力”，审查同时取得关键词/符号入口和完整语义：声明、类型、运行、初始化、错误、资源、模块与工具链。选定语言的规范是索引，不只是抄一份词表；没有相应控制或转换的能力明确列缺项，不以图灵完备抹去。最强反例应包含同名不同义、异名可等价、运行反射阻止改写、初始化依赖和隐藏元数据。

相交实现按[能力映射](../作者/需求关系与能力边界.md)分别验证默认自动选择、显式硬控制、可覆盖偏好与重置。普通新库不要求核心增关键词；普通新函数不被迫做“大功能意图”。保持语义、按指定形态生成和精确往返是不同目标，不能只验证其中一个。

全工程审查还要选一项不是代码的必需内容：资源、配置、构建脚本、数据或外部引用。检查它从读取、修改、生成、打包到退出是否保持字节、解释、权限和关联。未知格式能否保全；已解析格式是否有正确写回；闭包是否漏掉副产物或真实成员；删除是否抹掉已有责任。完整要求在[资产规范](../作者/工程源/资产与非源码.md)，不为每种文件再建设一套产品。

## 从本次发现到持续存在的已知问题

发现流程的产物必须有可继续处理的位置，而不只是报告尾注。先与[主登记](../状态/前沿与登记规则.md#已知问题主登记)对照：已经存在的机制补充反例与受影响范围；新机制建立条目；尚无完整方案仍然登记。优先级用于安排，不用于删掉低频但独立的反证。

完成一次设计变化后反查：原问题是否只改名；接受要求有没有被悄悄削弱；当前不处理是否误写为不适用；新方案是否给合法输入留下完成路径；同一源能否连续修改；别的领域是否被强加当前例子的前置。证据与结构检查都分别标范围。

问题数量只说明记录粒度，不能证明发现过程绝对穷尽。新增资料、目标、用户要求和实际反例继续回到对应上游设计；不因主登记存在就停止研究，也不把全宇宙未知都变成当前任务阻塞。
