## 安全工程、威胁建模、审计与响应

### 1. 安全进入每个阶段

需求、设计、实现、依赖、构建、测试、部署、运行、支持和退役都产生安全义务。发布前扫描不能替代生命周期控制。

### 2. ThreatModel

```text
ThreatModel = exact {
  assetsAndSecurityObjectives,
  trustBoundariesAndPrincipals,
  attackSurfacesAndCapabilities,
  threatScenarios,
  controlsAndResidualRisk,
  verificationAndMonitoring,
  incidentAndRecovery,
  scopeAndRevision
}
```

### 3. 控制

最小权限、能力代理、输入验证、沙箱、秘密管理、网络分段、供应链控制、审计、限流、备份和安全默认值。每个控制都必须绑定可执行的强制证据。

### 4. 审计

记录有意义的 authority/Effect/decision/readback，而不是复制所有数据。日志 tamper-evident、受限、可关联且有 retention。

### 5. 漏洞流程

发现→确认→遏制→修复→验证→发布→监控→披露。紧急修复仍保留最小不可跳过的 identity、scope、Effect 和 readback。

### 6. 响应

隔离、credential revoke、evidence preservation、用户影响、恢复和长期设计修正。事故不能只关闭 ticket。

### 7. 验证

威胁建模与滥用情景、提示注入、供应链失陷、权限提升、秘密泄露、审计旁路、事故演练和紧急修复。


## 性能测量、基线、剖析、预算与回归

### 1. 先测真实关键路径

实现前不预填永久秒数。选择真实用户操作和代表性仓库，记录 orientation、observation、compiler、verification、provider、cleanup 和 readback 阶段。

### 2. Instrumentation

复用 operation/action identity，记录开始、阶段转换、结束、CPU、RSS、I/O、queue、cache、physical starts、reused/joined/invalidated。长时间无输出的阶段仍须有有界心跳和已耗时；父阶段覆盖子进程、等待与结算，最终给出墙钟总时长，不能把多个并行阶段耗时相加冒充总时长。日志是可关联的进度投影，不签发 Action、权限或通过结论；高基数和敏感数据受限。计时缺失或子进程无终态须显示 unknown，不把未观察时间记成零。

### 3. Baseline

绑定 exact workload、environment、toolchain、revision 和 correctness outcome。冷/热、cache-off、Windows/Linux 和不同规模分别。

### 4. Budget

预算既有安全 ceiling，也有 SLO target。超预算可以取消、降级或排队，但不能跳过 required correctness。恢复/cleanup 保留独立资源。

### 5. Regression

使用统计和实际重要性阈值；样本不足为 inconclusive。优化必须有 equivalence、failure、rollback 和 retirement。

### 6. 优先次序

消除重复 observation和Action；复用 exact key；增量；并行；最后考虑 native/Rust/Go/remote 等更快机制。

### 7. 验证

长会话、历史增长、冷/热缓存、并行竞争、资源压力、观测开销、测量缺失、前后对比和正确性等价。


## 持续集成、合并授权、主分支健康与发布

### 1. 平台入口必须不可绕过

本地 Hook 和脚本可改善反馈，但不能证明服务器端 enforcement。受支持 merge/push 路径必须经过同一 VerificationSession 或旁路后使主分支进入 locked/degraded。

### 2. CI 分层

```text
cheap exact-identity orientation/preflight
→ compile RequiredClosure ∩ MissingOrStale
→ affected deterministic selection for narrowed profiles only; full inventory bypasses selection
→ physical/provider actions
→ independent review
→ exact-head authorization
→ merge expected tree
→ main-only readback
→ release artifact verification
```

### 3. 单一状态

多个 workflow/check 只投影一个 Session；不靠事件时序、PR body 编辑和 check 名称互相发现。动态状态保存在 machine registry/journal。同一 exact candidate 的 Gate、依赖与检查结果依各自 ActionKey、环境及有效期复用或 join；不同入口名称、日志或同树但不同有效输入都不能制造第二份结果，也不能让不适用的 selector 成为全量验证的前置。

### 4. Branch protection

required checks、review、expected head、no force/direct push、admin/break-glass 策略、merge queue/automation 和 ruleset 通过平台 readback 证明。平台能力缺失时诚实限制 support scope。

### 5. MainHealth

没有 hosted checks 不等于健康。本地 trusted provider 可以产生 exact receipt，但 selector 不隐式启动验证。provider 冲突时 fail closed。

### 6. 发布

source verification、artifact build/install、promotion 和 deployment 分离；同一 artifact 跨环境提升，避免重新构建。合并只消费其确实要求的候选源码验证、独立审查及集成合同；发布制品构建属于合并后独立动作，除非某个冻结 Claim 明确要求该制品作为合并前证据。测试内部构造的临时 fixture 不等于发布构建，也不得把发布部署偷偷设为普通合并的前置。

### 7. 验证

检查缺失、管理员旁路、工作流模式漂移、自审、基线失败、合并响应丢失、树不匹配、合并后主分支失败和制品失败。


## 测试责任、Provider 与 Verification 收敛

本节只拥有实施接合，不建立第二套 Verification 语义。通用 owner 与方法选择由[验证方法与故障设计](../../运行/验收/方法与独立证据.md#验证责任所有权与方法选择)拥有；TestCase 细节由[测试生成与形式方法](../../运行/验收/测试生成与形式方法.md#testcase-的适用边界与责任)拥有。

### 1. 目录与 runner 不承担证明语义

`unit/`、`contract/`、`integration/`、`e2e/` 可以用于维护定位和局部 proof role，但不能同时暗含速度、资源、owner、重要性、平台、requiredness 或 Evidence 资格。`fast/slow`、suite、path、title 和 timeout 同样只是执行/定位投影，不是 TestCase identity。

新增验证前先判断 Method。若仓库事实可由 Source Program、module graph、architecture rule、type checker 或其他 canonical static owner 直接检查，则生产路径直接运行该检查；只用 TestCase 校准 checker 的正反例与失败语义。禁止为了“所有验证都能由 test runner 发现”而把每条静态规则复制成第二份 test。

### 2. TestResponsibility 单写与发现

长期 retained case 至少具有稳定 test/family identity、owner、obligation bindings、Failure Meaning、observation boundary、真实 environment/resource requirement、Oracle/independence、impact relation 和 retirement。责任与 executable definition 只有一个写源；source census、runtime discovery、suite inventory、Test Impact 和报告均为只读 projection。

迁移期 raw `test()/it()` 允许存在，但必须可发现并显式 unresolved。Source-side registration 与 Provider runtime discovery 是独立观察面：

```text
source registration census
        ×
selected Provider runtime discovery
        ↓
inventory confidence / unresolved frontier
```

静态已解析但 runtime missing、runtime discovered 但 source responsibility 未解析、动态 family 无稳定 instance key、重复 stable identity 或重复 locator 都不能静默进入完整 inventory。

### 3. VerificationAction 编译

从 exact candidate/semantic delta、Claim/Proof Obligation、applicability、Evidence freshness、environment capability 与真实 resource requirement 编译去重 Action DAG。Narrowed profile 的 affected closure 需要传播 witness；unknown 只能扩大 closure 或降低结论，不能变成零选择 PASS。Full profile 直接从完整 required closure 编译，不再为了证明“全部”重复执行 affected selector。

测试 runner 只执行已选 Action，不拥有 Test Impact、Claim、Evidence 资格或 Result truth。执行参数、进程数、shard、历史耗时和当前队列不进入 TestCase/Claim semantic identity；它们属于 Provider/Execution policy。

### 4. Provider 采用规则

SEC 采用成熟 Provider，但只把其真实保证接入相应 capability；Provider 不取得 Requirement、Claim、Impact、Evidence qualification 或 Verdict authority。

| Provider/机制 | 当前设计位置 | 采用与退役条件 |
| --- | --- | --- |
| Bun Test | 普通 TS/JS TestCase 的当前主要 execution Provider | 对 exact SEC corpus 证明行为、发现、隔离、失败、资源与结果 parity 后，优先使用其原生 parallel/isolate/shard/timings/reporter/retry 等机械能力，并删除被替代的 SEC 自研 scheduler/table |
| Vitest | 候选 Test Provider，不是默认迁移目标 | 只有 exact SEC corpus A/B 证明其 metadata/collection/reporting/维护收益在正确性、Host surface、依赖与迁移成本后仍显著，才进入正式 Provider adoption；切换不得长期双 primary |
| Playwright | **仅 Browser owning cell** 的候选 Provider | 没有 Browser capability Claim 时不得安装、下载 Chromium、准备 browser fixture 或启动 browser Gate；真实 Workbench/browser Claim 出现后再按 owning environment 接入 |
| fast-check 等 | property/metamorphic/model/fuzz 生成能力 | 只有相交 obligation 需要生成与 shrink 时采用；generator 不拥有 domain Oracle |
| Stryker 等 mutation 工具 | 测试敏感性的抽样/低频校准 | 不作为默认产品质量分数或普通 fast Gate；只对高价值 obligation 校准，结果仍需解释等价 mutant/不可达代码 |
| Testcontainers/真实服务 fixture | DB、queue、network service 等真实 external-service capability | 只有真实 consumer 出现时采用；container lifecycle 不能替代 SEC 的 resource ownership/settlement |
| CodeQL/solver/其他静态工具 | 各自静态/形式 VerificationMethod Provider | 输出 finding/proof/unknown，不直接签发产品、merge 或安全总 Verdict |

“工具更多”不是成熟度。没有真实 Claim consumer 的 Provider 不进入默认 dependency、启动路径或 Gate。

### 5. slow 不是语义类别

长期模型不保存“这个测试天生 slow”的第二真值。执行成本和资源需求至少拆成：

```text
semantic obligation
environment/capability requirements
exclusive/shared resource requirements
observed cost distribution
provider execution policy
```

普通 file-level parallelism、isolation、sharding、duration balancing、worker scheduling 与 reporter 优先交给已采用 Provider；SEC 只保留 Provider 无法表达且由真实物理不变量要求的约束，例如独占 repository writer、Windows AppContainer、不可共享外部租户、真实 process-tree settlement 或有权外部状态。

手工 `parallelSafe`、永久 slow-file list、按文件拍定 timeout 和重复 suite balancing 都是迁移输入，不是终态 authority。它们只有在尚未被 resource/capability owner 与 measured cost 替代时临时存在；替代完成后必须 consumer-zero 并删除。

### 6. Test corpus 的 Proof Economy

每个现存 case 依据必要 observation 而不是历史路径裁决：

```text
KEEP
REWRITE
MERGE
DELETE
UNKNOWN
```

- **KEEP**：仍提供独立、必要且未被严格覆盖的 observation。
- **REWRITE**：Claim 有效，但测试依赖源码文字、私有布局、同源 Oracle、弱 fixture 或错误层级。
- **MERGE**：多个 case 的必要 observation 可以由一个更强 proof 或参数化 harness 无损覆盖。
- **DELETE**：Requirement/Claim 已退役、genuine not-applicable，或存在经证明的 strict observation superset 且无未知 consumer。
- **UNKNOWN**：owner、obligation、Oracle lineage、consumer 或 replacement coverage 不足；unknown 不得为清理方便降为 DELETE。

routing/presentation 等重复骨架优先抽取共享 harness，但 domain-specific observation 仍单独保留；巨型 test owner 按 Claim/obligation、状态机和物理边界拆分，以提高 affected precision、独立 retirement 和并发资格。文件数量下降不是目标，必要 Evidence 的重复与维护成本下降才是目标。

### 7. Verification 语义的物理归位

现有实现按十责任收敛，不新增第十一个 testing 模块：

- Claim、Proof Obligation、method qualification、Evidence applicability/coverage/Verdict → `assurance`；
- Source Program、依赖与可静态计算的 impact facts → `compiler`/其真实分析 owner；
- 用例协调与返回 → `application`；
- Action admission、资源、并发、deadline、settlement/readback/recovery → `execution`；
- Bun、Git、GitHub、CodeQL、TypeScript、solver、browser 等具体能力 → `adapters`；
- CLI/API projection → `entry`，具体组合 → `bootstrap`。

因此当前物理路径若把 Test Impact policy、VerificationAction 业务真值、Result qualification 或 Source Program 语义整体放在 `adapters`，应按 owner 迁移；真正 Adapter 只保留对内部 port/capability 的现实实现。迁移必须同步 import policy、module declaration、consumer、测试与文档，并删除旧 alias/第二 writer。

### 8. 实施收敛单元与完成边界

以下是当前设计要求的实施单元，不是第二永久 roadmap；实际激活、并发与排序仍由现有 WorkSelection/Verification Control Plane 决定。

| 单元 | 必须取得的产品结果 | 完成边界 |
| --- | --- | --- |
| Verification ownership closure | Claim/Requirement/ProofObligation 的 owner、revision、subject/applicability 可追溯，Provider 与 Verdict authority 分离 | 不再依赖自由 claim 字符串或 runner 成功码推断最终真值 |
| TestResponsibility adoption | retained TestCase/TestFamily 可发现并具有最小稳定 proof identity、owner、obligation/Failure Meaning | source census × runtime discovery 的 supported forms 闭合；未解析项显式 unknown |
| verification de-testification | 可静态/直接检查的 repository facts 由唯一 checker 对真实候选求值 | 删除对应源码镜像/路径 tombstone 第二真值，只保留 checker calibration tests |
| runner/provider convergence | 普通 runner mechanics 由已采用 Provider 承担 | exact corpus parity 后删除重复 scheduler/sharder/timing/reporter tables；不长期双执行 |
| resource/cost convergence | speed/resource 与 Test identity 正交 | manual slow/parallel/timeout 表被 resource owner + measured cost + Provider policy 取代并退役 |
| proof-economy convergence | 重复、同源 Oracle、假 contract/E2E、实现布局锁定被机器发现并有 disposition | DELETE/MERGE 有严格替代证据，UNKNOWN 不被清理吞掉 |
| physical owner convergence | Assurance/Compiler/Execution/Adapter 责任与物理模块一致 | `adapters` 不再成为 Verification/Source Program 语义垃圾桶，旧 owner consumer-zero |
| legacy Program convergence | 历史 Program 按 current main 重新裁决 implemented/absorbed/partial/obsolete/still-canonical | 已实现或被吸收的 Program 关闭/标明 supersession；剩余 gap 提炼为有退出条件的 focused work |

### 9. 验收

至少验证：

- 同一 Claim 可由 test、静态分析、形式方法或 runtime readback 等不同方法支持，而不会改变 Claim identity；
- Provider 退出 0/green 不会在 Evidence 不足时制造 Claim PASS；
- 可静态判定的 repository violation 由生产 checker 直接发现，checker tests 只校准规则实现；
- 无 Browser Claim 时没有 Playwright/Chromium preparation；
- runner Provider cutover 前后 TestCase responsibility、Failure Meaning、result/evidence 资格保持；
- resource conflict 会限制物理并行，普通独立 case 不被 SEC 自研串行表阻塞；
- zero selection 有 not-applicable/reuse witness，或保持 unresolved；
- Test rewrite/merge/delete 不丢失独立 observation；
- owner 迁移后旧 import、旧 registry、旧 suite/table 和兼容写路径确实 consumer-zero。



## 配置、密钥、环境与部署画像

```text

SecretBinding

RuntimeObservation
```

### 2. 配置优先级

每个字段定义 owner、scope、default、override、validation、secret status、restart/reload、revision 和 provenance。优先级图无环且可解释。

### 3. 环境变量

只作为 Host adapter 输入，解析为 typed config 后不在 Core 四处读取。absence、empty、invalid 分开。敏感值不进入 logs/digests。

绑定 Host、OS、filesystem、runtime、network、storage、identity、resource、region、security、observability 和 support cell。环境名 `prod` 本身没有语义。

### 5. 动态配置

需要热更新时定义 consistency、atomic snapshot、validation、rollout、rollback、watch failure 和 old consumer。普通常量不因此进入配置服务。

### 6. 验证

## 错误码、接口模式与兼容策略

### 1. 稳定错误身份

错误文本用于人类，不用于控制流。每个公共 failure 有稳定 code、类别、subject、effect state、retry/recovery 和 schema revision。

### 2. ErrorEnvelope

```text
ErrorEnvelope = exact {
  errorCode,
  errorSchemaRevision,
  operationAndSubjectRefs,
  failureClass,
  effectState,
  retryabilityAndPrecondition,
  recoveryActionRefs,
  diagnosticArgs,
  causeRefs,
  disclosureLevel
}
```

### 3. 兼容

新增错误 code 通常 additive；改变既有 code 含义是 breaking；文本可本地化但 code/args 稳定。unknown code 按 fail-safe 类别处理，不能默认 retry。

### 4. Cause chain

保留结构化 cause，不复制敏感内容。底层 errno/provider error 映射为 domain failure，同时保留原始受控 reference。

### 5. 验证

Provider 文本变化、本地化、未知错误码、嵌套原因、部分效果、重试前置、旧客户端模式兼容和错误脱敏。
