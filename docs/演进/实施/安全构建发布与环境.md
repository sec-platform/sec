## 安全工程、威胁建模、审计与响应

### 1. 安全进入每个阶段

需求、设计、实现、依赖、构建、测试、部署、运行、支持和退役都产生安全义务。发布前扫描不能替代生命周期控制。

### 2. ThreatModel

```text
ThreatModel = exact {
  assetsAndSecurityObjectives,
  trustBoundariesAndPrincipals,
  attackSurfacesAndCapabilities,
  threatScenarios,
  controlsAndResidualRisk,
  verificationAndMonitoring,
  incidentAndRecovery,
  scopeAndRevision
}
```

### 3. 控制

最小权限、能力代理、输入验证、沙箱、秘密管理、网络分段、供应链控制、审计、限流、备份和安全默认值。每个控制都必须绑定可执行的强制证据。

### 4. 审计

记录有意义的 authority/Effect/decision/readback，而不是复制所有数据。日志 tamper-evident、受限、可关联且有 retention。

### 5. 漏洞流程

发现→确认→遏制→修复→验证→发布→监控→披露。紧急修复仍保留最小不可跳过的 identity、scope、Effect 和 readback。

### 6. 响应

隔离、credential revoke、evidence preservation、用户影响、恢复和长期设计修正。事故不能只关闭 ticket。

### 7. 验证

威胁建模与滥用情景、提示注入、供应链失陷、权限提升、秘密泄露、审计旁路、事故演练和紧急修复。


## 性能测量、基线、剖析、预算与回归

### 1. 先测真实关键路径

实现前不预填永久秒数。选择真实用户操作和代表性仓库，记录 orientation、observation、compiler、verification、provider、cleanup 和 readback 阶段。

### 2. Instrumentation

复用 operation/action identity，记录开始结束、CPU、RSS、I/O、queue、cache、physical starts、reused/joined/invalidated。高基数和敏感数据受限。

### 3. Baseline

绑定 exact workload、environment、toolchain、revision 和 correctness outcome。冷/热、cache-off、Windows/Linux 和不同规模分别。

### 4. Budget

预算既有安全 ceiling，也有 SLO target。超预算可以取消、降级或排队，但不能跳过 required correctness。恢复/cleanup 保留独立资源。

### 5. Regression

使用统计和实际重要性阈值；样本不足为 inconclusive。优化必须有 equivalence、failure、rollback 和 retirement。

### 6. 优先次序

消除重复 observation和Action；复用 exact key；增量；并行；最后考虑 native/Rust/Go/remote 等更快机制。

### 7. 验证

长会话、历史增长、冷/热缓存、并行竞争、资源压力、观测开销、测量缺失、前后对比和正确性等价。


## 持续集成、合并授权、主分支健康与发布

### 1. 平台入口必须不可绕过

本地 Hook 和脚本可改善反馈，但不能证明服务器端 enforcement。受支持 merge/push 路径必须经过同一 VerificationSession 或旁路后使主分支进入 locked/degraded。

### 2. CI 分层

```text
cheap orientation/preflight
→ affected deterministic checks
→ physical/provider actions
→ independent review
→ exact-head authorization
→ merge expected tree
→ main-only readback
→ release artifact verification
```

### 3. 单一状态

多个 workflow/check 只投影一个 Session；不靠事件时序、PR body 编辑和 check 名称互相发现。动态状态保存在 machine registry/journal。

### 4. Branch protection

required checks、review、expected head、no force/direct push、admin/break-glass 策略、merge queue/automation 和 ruleset 通过平台 readback 证明。平台能力缺失时诚实限制 support scope。

### 5. MainHealth

没有 hosted checks 不等于健康。本地 trusted provider 可以产生 exact receipt，但 selector 不隐式启动验证。provider 冲突时 fail closed。

### 6. 发布

source verification、artifact build/install、promotion 和 deployment 分离；同一 artifact 跨环境提升，避免重新构建。

SEC 仓库自身的发行以一个共同 release set 作为最小可提升单位，而不是让运行时代码包和文档包各自寻找“当前版本”。release set 的 runtime 与 documentation 成员必须来自同一精确 Git commit/tree；两份成员各有独立文件清单、内容摘要和许可身份，根 `release-set-manifest.json` 再绑定成员 manifest 摘要、文件数量、共同 package version 与 source identity。runtime 使用 MPL-2.0 边界；documentation 使用 CC-BY-4.0 边界并包含许可文本与规定署名。任一成员 revision、manifest、实际文件读回或许可合同不一致时，不形成可接受的共同发行。

构建顺序允许先完成 runtime 再完成 documentation，但第二成员必须显式接受第一成员已经冻结的 source identity；不能第二次把 `HEAD` 当成未经比较的新事实。最终共同目录只在两份成员都读回成功后发布。CI 的 release 验证在 exact trusted main head 上完成 full verification 后构建该 release set，再核对根 manifest 的 commit/tree 与工作流已解析的 trusted head/tree，最后上传整组制品；上传必须包含隐藏成员，因为 `.documentation/**` 属于文档发行边界。单独的本地 documentation package 可以用于检查或消费，但没有共同根 manifest 时不得冒充完整 SEC release。

### 7. 验证

检查缺失、管理员旁路、工作流模式漂移、自审、基线失败、合并响应丢失、树不匹配、合并后主分支失败和制品失败。


## 测试目录、责任元数据与验证动作编译

### 1. 目录不承担全部语义

`unit/`, `integration/`, `e2e/` 可作组织，但不能同时暗含速度、资源、owner、重要性、平台和 requiredness。

### 2. TestResponsibility

```text
TestResponsibility = exact {
  stableTestRef,
  owningClaimAndInvariantRefs,
  testCaseAndFailureMeaning,
  proofMechanism,
  environmentAndResourceRequirements,
  independenceAndOracleRefs,
  impactSelectionRelations,
  lifecycleAndRetirement
}
```

### 3. Discovery

source census 与 runtime discovery 对齐；raw `test()` 在迁移期标 unresolved，不可遗漏。title/path 是 locator，不是 test identity。

### 4. VerificationAction 编译

从 changed delta、claims、applicability、environment 和 resource 生成去重 Action DAG。测试 runner 只执行，不拥有选择和结果真值。

### 5. 外部 runner

优先使用 Bun、Playwright 等成熟执行机制，但 SEC 保留 Test Responsibility、Impact、ActionKey、Evidence 和 Result。采用后删除重复 scheduler。

### 6. 退役

测试删除需证明 claim 不再 required、replacement 覆盖或产品非目标；测试烦人和当前失败不构成删除理由。

### 7. 验证

运行时发现与源码发现等价、零选择、平台跳过、测试标题变化、稳定标识重复、资源冲突、运行器缓存、失败含义和测试退役。


## 配置、密钥、环境与部署画像

### 1. 配置分层

```text
ProductProfile
DeploymentProfile
EnvironmentBinding
SecretBinding
UserPreference
RuntimeObservation
```

这些对象不能合并为一个自由环境变量表。

### 2. 配置优先级

每个字段定义 owner、scope、default、override、validation、secret status、restart/reload、revision 和 provenance。优先级图无环且可解释。

### 3. 环境变量

只作为 Host adapter 输入，解析为 typed config 后不在 Core 四处读取。absence、empty、invalid 分开。敏感值不进入 logs/digests。

### 4. DeploymentProfile

绑定 Host、OS、filesystem、runtime、network、storage、identity、resource、region、security、observability 和 support cell。环境名 `prod` 本身没有语义。

### 5. 动态配置

需要热更新时定义 consistency、atomic snapshot、validation、rollout、rollback、watch failure 和 old consumer。普通常量不因此进入配置服务。

### 6. 验证

优先级冲突、未知字段、秘密暴露、动态配置陈旧、部分更新、环境错误、画像不匹配、离线模式和回滚。


## 错误码、接口模式与兼容策略

### 1. 稳定错误身份

错误文本用于人类，不用于控制流。每个公共 failure 有稳定 code、类别、subject、effect state、retry/recovery 和 schema revision。

### 2. ErrorEnvelope

```text
ErrorEnvelope = exact {
  errorCode,
  errorSchemaRevision,
  operationAndSubjectRefs,
  failureClass,
  effectState,
  retryabilityAndPrecondition,
  recoveryActionRefs,
  diagnosticArgs,
  causeRefs,
  disclosureLevel
}
```

### 3. 兼容

新增错误 code 通常 additive；改变既有 code 含义是 breaking；文本可本地化但 code/args 稳定。unknown code 按 fail-safe 类别处理，不能默认 retry。

### 4. Cause chain

保留结构化 cause，不复制敏感内容。底层 errno/provider error 映射为 domain failure，同时保留原始受控 reference。

### 5. 验证

Provider 文本变化、本地化、未知错误码、嵌套原因、部分效果、重试前置、旧客户端模式兼容和错误脱敏。
