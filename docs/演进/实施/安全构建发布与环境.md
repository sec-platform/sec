## 安全工程、威胁建模、审计与响应

### 1. 安全进入每个阶段

需求、设计、实现、依赖、构建、测试、部署、运行、支持和退役都产生安全义务。发布前扫描不能替代生命周期控制。

### 2. ThreatModel

```text
ThreatModel = exact {
  assetsAndSecurityObjectives,
  trustBoundariesAndPrincipals,
  attackSurfacesAndCapabilities,
  threatScenarios,
  controlsAndResidualRisk,
  verificationAndMonitoring,
  incidentAndRecovery,
  scopeAndRevision
}
```

### 3. 控制

最小权限、能力代理、输入验证、沙箱、秘密管理、网络分段、供应链控制、审计、限流、备份和安全默认值。每个控制都必须绑定可执行的强制证据。

### 4. 审计

记录有意义的 authority/Effect/decision/readback，而不是复制所有数据。日志 tamper-evident、受限、可关联且有 retention。

### 5. 漏洞流程

发现→确认→遏制→修复→验证→发布→监控→披露。紧急修复仍保留最小不可跳过的 identity、scope、Effect 和 readback。

### 6. 响应

隔离、credential revoke、evidence preservation、用户影响、恢复和长期设计修正。事故不能只关闭 ticket。

### 7. 验证

威胁建模与滥用情景、提示注入、供应链失陷、权限提升、秘密泄露、审计旁路、事故演练和紧急修复。


## 性能测量、基线、剖析、预算与回归

### 1. 先测真实关键路径

实现前不预填永久秒数。选择真实用户操作和代表性仓库，记录 orientation、observation、compiler、verification、provider、cleanup 和 readback 阶段。

### 2. Instrumentation

复用 operation/action identity，记录开始、阶段转换、结束、CPU、RSS、I/O、queue、cache、physical starts、reused/joined/invalidated。长时间无输出的阶段仍须有有界心跳和已耗时；父阶段覆盖子进程、等待与结算，最终给出墙钟总时长，不能把多个并行阶段耗时相加冒充总时长。日志是可关联的进度投影，不签发 Action、权限或通过结论；高基数和敏感数据受限。计时缺失或子进程无终态须显示 unknown，不把未观察时间记成零。

### 3. Baseline

绑定 exact workload、environment、toolchain、revision 和 correctness outcome。冷/热、cache-off、Windows/Linux 和不同规模分别。

### 4. Budget

预算既有安全 ceiling，也有 SLO target。超预算可以取消、降级或排队，但不能跳过 required correctness。恢复/cleanup 保留独立资源。

### 5. Regression

使用统计和实际重要性阈值；样本不足为 inconclusive。优化必须有 equivalence、failure、rollback 和 retirement。

### 6. 优先次序

消除重复 observation和Action；复用 exact key；增量；并行；最后考虑 native/Rust/Go/remote 等更快机制。

### 7. 验证

长会话、历史增长、冷/热缓存、并行竞争、资源压力、观测开销、测量缺失、前后对比和正确性等价。


## 持续集成、合并授权、主分支健康与发布

### 1. 平台入口必须不可绕过

本地 Hook 和脚本可改善反馈，但不能证明服务器端 enforcement。受支持 merge/push 路径必须经过同一 VerificationSession 或旁路后使主分支进入 locked/degraded。

### 2. CI 分层

```text
cheap exact-identity orientation/preflight
→ compile RequiredClosure ∩ MissingOrStale
→ affected deterministic selection for narrowed profiles only; full inventory bypasses selection
→ physical/provider actions
→ independent review
→ exact-head authorization
→ merge expected tree
→ main-only readback
→ release artifact verification
```

### 3. 单一状态

多个 workflow/check 只投影一个 Session；不靠事件时序、PR body 编辑和 check 名称互相发现。动态状态保存在 machine registry/journal。同一 exact candidate 的 Gate、依赖与检查结果依各自 ActionKey、环境及有效期复用或 join；不同入口名称、日志或同树但不同有效输入都不能制造第二份结果，也不能让不适用的 selector 成为全量验证的前置。

### 4. Branch protection

required checks、review、expected head、no force/direct push、admin/break-glass 策略、merge queue/automation 和 ruleset 通过平台 readback 证明。平台能力缺失时诚实限制 support scope。

### 5. MainHealth

没有 hosted checks 不等于健康。本地 trusted provider 可以产生 exact receipt，但 selector 不隐式启动验证。provider 冲突时 fail closed。

### 6. 发布

source verification、artifact build/install、promotion 和 deployment 分离；同一 artifact 跨环境提升，避免重新构建。合并只消费其确实要求的候选源码验证、独立审查及集成合同；发布制品构建属于合并后独立动作，除非某个冻结 Claim 明确要求该制品作为合并前证据。测试内部构造的临时 fixture 不等于发布构建，也不得把发布部署偷偷设为普通合并的前置。

### 7. 验证

检查缺失、管理员旁路、工作流模式漂移、自审、基线失败、合并响应丢失、树不匹配、合并后主分支失败和制品失败。


## 测试目录、责任元数据与验证动作编译

### 1. 目录不承担全部语义

`unit/`, `integration/`, `e2e/` 可作组织，但不能同时暗含速度、资源、owner、重要性、平台和 requiredness。

### 2. TestResponsibility

```text
TestResponsibility = exact {
  stableTestRef,
  owningClaimAndInvariantRefs,
  testCaseAndFailureMeaning,
  proofMechanism,
  environmentAndResourceRequirements,
  independenceAndOracleRefs,
  impactSelectionRelations,
  lifecycleAndRetirement
}
```

### 3. Discovery

source census 与实际runtime discovery对齐，不遗漏原生`test()`。上述TestResponsibility是能够准确引用或推导的逻辑责任，不要求作者为每例手填全部字段或全局ID；普通私有案例可由模块合同与具体失败语义解释。无法确定的责任/发现范围保留unresolved，不把正常原生测试语法本身当作无效。title/path是locator，不自动成为跨修订test identity。

### 4. VerificationAction 编译

从 changed delta、claims、applicability、environment 和 resource 生成去重 Action DAG。缩小的 quick/affected 闭包需要可靠影响与 ownership 证明，未知则拒绝缩小；full 闭包由完整测试目录和责任预算直接编译，不能为了证明“全部”再执行 affected selector。已选全量 fast 与全部 slow suite 时，另一个 affected-tests Gate 只有独立 Claim 才可保留，且必须说明它证明了什么新增性质。测试 runner 只执行，不拥有选择和结果真值。

### 5. 外部 runner

采用下文正式构建后端与原生测试提供者分工。SEC保留已有Test Responsibility、Impact、ActionKey、Evidence和Result；原生工具拥有其准确子图的物理调度与报告。删除的是同一子图的重复调度权，不是取消执行准入、恢复或证据接纳。

### 6. 退役

测试删除需证明 claim 不再 required、replacement 覆盖或产品非目标；测试烦人和当前失败不构成删除理由。

### 7. 验证

运行时发现与源码发现等价、零选择、平台跳过、测试标题变化、稳定标识重复、资源冲突、运行器缓存、失败含义和测试退役。


## 配置、密钥、环境与部署画像

### 1. 配置分层

```text
ProductProfile
DeploymentProfile
EnvironmentBinding
SecretBinding
UserPreference
RuntimeObservation
```

这些对象不能合并为一个自由环境变量表。

### 2. 配置优先级

每个字段定义 owner、scope、default、override、validation、secret status、restart/reload、revision 和 provenance。优先级图无环且可解释。

### 3. 环境变量

只作为 Host adapter 输入，解析为 typed config 后不在 Core 四处读取。absence、empty、invalid 分开。敏感值不进入 logs/digests。

### 4. DeploymentProfile

绑定 Host、OS、filesystem、runtime、network、storage、identity、resource、region、security、observability 和 support cell。环境名 `prod` 本身没有语义。

### 5. 动态配置

需要热更新时定义 consistency、atomic snapshot、validation、rollout、rollback、watch failure 和 old consumer。普通常量不因此进入配置服务。

### 6. 验证

优先级冲突、未知字段、秘密暴露、动态配置陈旧、部分更新、环境错误、画像不匹配、离线模式和回滚。


## 错误码、接口模式与兼容策略

### 1. 稳定错误身份

错误文本用于人类，不用于控制流。每个公共 failure 有稳定 code、类别、subject、effect state、retry/recovery 和 schema revision。

### 2. ErrorEnvelope

```text
ErrorEnvelope = exact {
  errorCode,
  errorSchemaRevision,
  operationAndSubjectRefs,
  failureClass,
  effectState,
  retryabilityAndPrecondition,
  recoveryActionRefs,
  diagnosticArgs,
  causeRefs,
  disclosureLevel
}
```

### 3. 兼容

新增错误 code 通常 additive；改变既有 code 含义是 breaking；文本可本地化但 code/args 稳定。unknown code 按 fail-safe 类别处理，不能默认 retry。

### 4. Cause chain

保留结构化 cause，不复制敏感内容。底层 errno/provider error 映射为 domain failure，同时保留原始受控 reference。

### 5. 验证

Provider 文本变化、本地化、未知错误码、嵌套原因、部分效果、重试前置、旧客户端模式兼容和错误脱敏。

## SEC自身仓库的正式构建与测试组织

本节整合已选测试终态的物理分工，仅针对SEC自身工程；不把Bazel、pnpm或特定runner强加给SEC生成/维护的每个用户工程。以下是目标选择，不是当前package、依赖安装或CI已切换的报告。

### 原生事实分别拥有，一类事实写一次

| 原生拥有者 | 所维护的事实 | 与SEC相接但不被替代的责任 |
|---|---|---|
| Bazel BUILD/模块与工具链定义 | 真实构建目标、输入输出、目标依赖、工具链和对应动作子图 | SEC固定候选/作用请求并接纳结果；不在另一个Nx/Turbo/自制队列再调度同一动作 |
| pnpm锁与rules_js物化 | JS第三方依赖精确解析及其消费 | 目标只保留一个活动JS解析权威；Bazel规则/工具链锁是另一依赖域，不是第二份npm求解结果 |
| tsconfig与固定TypeScript供给 | TS解释选项与实际编译器能力 | BUILD目标依赖投影必要项目引用/输入输出；不手写两套references，也不每个target重跑全仓tsc -b |
| 原生测试源码与runner配置 | 案例、fixture、oracle和实际发现/报告机制 | assurance保持适用义务、CasePlan/casesRef、证据有效性和范围结论 |
| 原架构module描述/Source Program | 声明归属、能力与静态结构事实 | 原生构建依赖不能代替语义责任或权限；推导需要准确解释环境 |
| 原状态/内容/执行提供者 | 已准入attempt、原生operation、准确输出及结算 | 缓存命中不是当次物理执行，更不自动满足原保证义务 |

选定Bazel为正式构建与动作后端；共享计算画像使用Buildbarn的REAPI/CAS供给，本地画像遵循同一合同。Bun保留产品运行时，不再作为第二个活动JS包解析器。可移植TS行为使用Vitest，Bun特有接口使用bun:test及真实Bun产物，真实浏览器使用Playwright；fast-check、Stryker、Testcontainers、MSW、tsd、发布包检查、性能及模糊测试按各自适用方法接入，不把所有工具装进每个普通用例。

原生TypeScript CLI与用于Source Program的TypeScript API包分别固定能力/版本；相同品牌不代表语法和API等价。新CLI可接受而API无法解释的输入，不能由类型检查成功填补影响分析未知。Rust目标接原生Rust工具/构建规则，不要求把SEC核心重写为Rust。

### 物理包、测试组与解析边界

Bazel的BUILD包边界不能从架构module目录直接推断。新增子目录BUILD会改变包包含范围；目标可以消费其他包的源/产物，但不得使同一输出由两个目标拥有。移动文件时同步处理目标label、依赖、visibility、runfiles和原生配置；不能靠宽泛glob误把生成目录或新测试吸入产品目标。相交原生事实应由生产者投影或机械核对，不维护第三份通用files.json。

局部代码/测试可以相邻但属于不同构建目标、工具链和依赖闭包，测试支持不能泄漏到发行包。类型检查单元按真实公开声明/模块边界形成；私有实现变更只有在下游确实只依赖未变声明且其他解释输入未变时，才能复用下游类型结果，不能推导运行测试也不受影响。global augmentation、路径别名、环境和生成声明进入真实输入闭包。

物理执行按共享fixture、初始化、隔离、平台和成本形成稳定执行组，而不是每例一个进程或全仓永久一个target。组内runner只使用父动作授予的预算；SEC、Bazel、Buildbarn和runner不能各自无上限满核。原生action digest、SEC ActionKey、Candidate、attempt和CheckRecord保持不同含义，通过准确plan/invocation/输入输出映射关联，不强制同一个hash。

实际代码/配置/目录枚举、此前不存在的路径、解析环境、工具链及oracle/fixture变化共同决定失效。未知影响可保守扩大；本地冷检查可绕过选择/结果缓存验证它们，不从同一selector的输出自证全集。必要范围、选中、实际执行、复用、跳过与未报告必须对账。

### 工具接合、失败与切换验收

薄adapter只交接固定executable、argv、CWD、环境、输入输出、工具身份和原生结构化报告，不实现另一个依赖求解器或runner。必须执行的发现/安装/下载经execution；报告解析有大小、深度和外部实体限制。Bazel/BEP与runner事件分别提供相应粒度，报告缺例、截断、隐藏retry、无终止、输出摘要不符不能由exit 0盖过。非精确case能力允许组级证据，不能编造细粒度身份。

解析锁切换必须同时处理旧活动锁的退役、安装入口、相关脚本/CI/缓存键、实际依赖布局和消费者；不长期同时写Bun lock与pnpm lock。Bun运行兼容、ESM/CJS及条件exports、原生扩展、生命周期产物、真实平台和选定规则/worker组合须相交验证。BUILD是原生构建隔离，不自动是恶意代码安全边界；不可信测试不能得到宿主秘密、无界网络或跨任务可写缓存。

远端恢复绑定持久原生operation和原attempt，失联先查回；未知非幂等效果不盲重发，旧代结果不能推进新候选。缓存/worker不可用只影响是否能取得所需证据，不修改产品要求。不具备某平台或粒度时明确保留缺项，不能把Linux/Node模拟结果代签Windows/Bun。

正式采用门槛是原工具组合的发现/选择/报告符合性、干净消费者产物、类型与真实运行、缓存失效和冷核对、取消/清理/未知恢复及权限边界。没有这些实际结果时只能称目标合同已定；实施顺序可以按真实消费者推进，但不另造待日后废弃的临时架构。
