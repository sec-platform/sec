## 公开复现语料与隐私

### 私有工程不是公共测试集

SEC 能观察一个工作区，不表示上游可以接收它。缺陷报告、性能基线、AI 评测和支持材料分别请求所需最小数据；默认不上传原始源码、路径、模型、提示、凭据、内存快照或生成产物。

用户选择公开材料时，清楚展示将发送的文件和元数据，支持先导出到本地检查。自动脱敏是辅助工具，不能把“通过扫描”说成已经排除全部重新识别风险。

### 复现包合同

| 项目 | 内容 |
|---|---|
| 问题 | 预期行为、实际行为、影响范围，不包含未经证实的根因 |
| 输入 | 最小授权输入及其摘要；删减关系和不能公开部分 |
| 环境 | OS/架构、工具和依赖版本、相关配置，秘密用角色引用替代 |
| 触发 | 真实命令或协议、顺序、并发、资源与失败条件 |
| 证据 | 最小日志、错误码、制品差异与观察时间 |
| 随机/并发 | 种子、调度线索、重试次数和不能固定的因素 |
| 权利 | 提交资格、可分发范围、是否涉及第三方数据 |

仓库地址、分支名、用户名、租户 ID、时间、业务唯一值和少量源码也可能泄露信息。文件名脱敏后仍检查文件内容、日志、压缩附件和关联链接。保存原始输入的授权与发布脱敏输入的授权分开。

### 最小化但保留故障

最小化器在授权副本上删除无关内容，每一步验证原故障性质仍成立；不能把程序简化成另一类错误。对崩溃使用相同故障签名和关键状态，对语义错误使用独立预期，对性能错误保留工作负载和统计方法。成功缩小后提供保留属性，而不声称还原全部用户环境。

故障只能在私有输入重现时，允许保密分析或有界远程检查，不强迫公开整个项目。公开记录可以保存不能公开的原因和脱敏结果，但不得发布可访问私有数据的令牌。

### 语料分割与质量

回归集、基准集、示例集与保留评测集不同。规则根据已公开样例优化后，再在同一集上报告成功率不证明泛化；AI 评测需记录模型、工具、预算、人工帮助和泄漏控制。负样本、边界条件、错误修复和最小化结果保留独立来源关系。

新增语料要绑定许可证、格式、可再分发范围、生成方法和敏感字段处理。合成数据不自动代表真实分布；真实数据脱敏后也可能破坏原故障条件。

### 默认遥测

本地编译、导入和重建不要求把工程内容发送上游。必要本地诊断可保存在用户控制的目录；上传遥测需明确选择、字段说明、保留和撤销。即使指标没有源码，也要评估路径、罕见组合和项目指纹。

### 验收

对源码、日志、归档嵌套、URL 查询令牌、内存转储、生成注释和模型上下文做泄漏负例；验证匿名化后故障仍可重现；授权撤销停止后续上传；删除请求按分发副本与备份策略处理，不能承诺已经传播的公开数据一定可撤回。

### 理由

全量诊断提高复现率但扩大泄露和许可风险；只报错误文本又可能无法定位。先本地最小化、展示差异、显式共享并分级处理，能够同时保留可复现性和用户控制。

## 发布与支持契约

### 发布单位

发布绑定源码 revision、规则与模式版本、工具链、目标平台、精确制品清单、许可/来源、验证结果、文档版本和已知限制。版本标签只是名称，不是这些输入的替代。

SEC 工具发布、扩展发布、目标运行库发布和用户工程发布是不同操作；上游工具发布权限不授予用户部署权限。文档修订包也不是 SEC 可安装软件发行版。

### 发布状态

```text
准备候选 → 构建 → 验证与审查 → 签署/批准 → 发布 → 渠道读回
                ↘ 不合格，修订候选             ↘ 不确定发布，读回再裁决
发布 → 支持维护 / 撤回新分发 / 安全撤销 / 支持终止
```

每次修改源码、打包规则或依赖形成新候选，不复用不再覆盖该候选的证据。签名绑定最终受支持载荷；签名不能证明没有缺陷。发布响应丢失后先按版本与内容读回，不能覆盖既有版本重发不同字节。

### 最低发行材料

| 材料 | 必须说明 |
|---|---|
| 源码与开发入口 | 获取方式、精确 revision、真实可执行的构建与检查步骤 |
| 环境描述 | 工具版本、锁定依赖、网络输入、相关环境变量与目标平台 |
| 发布清单 | 每个受支持文件的角色、大小、摘要及构成 |
| 验证 | 已执行和未执行项、目标矩阵、独立复核与已知失败 |
| 许可与通知 | 实际权利、依赖与生成模板义务 |
| 版本与迁移 | 输入模式、插件 API、输出运行库和旧数据路径 |
| 支持声明 | 支持维度、责任、期限、弃用与安全处理方式 |
| 用户文档 | 本版本可用功能、错误恢复、限制及与开发版区别 |

### 可重复构建

相同源码、环境和构建指令应产生声明范围内逐字节一致的载荷；范围不默认包括墙钟日志和随机签名附件。签名载荷单独定义，不能让比较器悄悄忽略任意差异。

本机同环境双构建只证明该环境中的确定性；独立参与方从公开输入重建并比对，才提供更强的可重复性证据。两者都不证明源码无漏洞。定义依据见 [Reproducible Builds](https://reproducible-builds.org/docs/definition/)。

### 兼容维度

分别记录输入工程模式、领域模块接口、Provider 协议、插件 ABI/API、生成运行库、命令行/机器输出、内容格式及历史证据解释。SemVer 或产品大版本不能替代这些矩阵。

增加可选字段是否兼容取决于旧读取器规则；新增枚举值可能破坏穷尽匹配；更严格校验可能拒绝旧工程；改变默认算法可能改变输出；修复安全漏洞也可能需要兼容例外。每个变化给出精确读/写方向与迁移策略。

### 支持与下游

`Preview`、常规支持、LTS、只读历史解释是不同承诺；不宣布没有维护资源支持的时限。社区维护不自动附带商业 SLA。下游发行者可以打补丁，但应标明来源与差异，不冒用上游对不同字节的保证。

弃用先公布替代、影响、检测方法和迁移路径。上游没有遥测不等于没有离线消费者；退役评估包括已公布支持窗口、格式解释工具和可取得的下游反馈。用户可以拒绝自动升级，SEC 不借支持声明修改其工作区。

### 验收

干净源码构建、独立环境重建、篡改包拒绝、依赖消失、镜像返回旧制品、签名撤销、发布响应丢失、客户端版本错配、被隔离的测试、文档与版本不符及回移修复都需有明确结果。只读设计包按自身发布清单复验，不套用未实现二进制分发步骤。

## 安全响应与信任恢复

### 受理与披露边界

项目需要发布可用、有人负责的安全报告入口、备用联系路径、加密材料及受支持版本范围。正式上线前验证入口可达、权限正确、备用人员能够接续；本设计不虚构安全邮箱、响应时限或正在运行的团队。

功能缺陷可以公开讨论；可能暴露秘密、越权路径、未修复利用链或用户工程的材料先限制披露。报告者可提交最小触发条件和影响，不要求在公开渠道上传完整私有源码。

### 状态与最小记录

```text
接收 → 分类 → 复现与范围判定 → 遏制/修复 → 验证 → 发布与通知 → 后续复核
          └→ 非安全缺陷或无法复现（保留理由与重开条件）
```

记录事件身份、来源、受影响组件/版本/模式、可复现条件、泄露范围、可信边界、修复与回移、披露决定和剩余风险。输入恶意样本在隔离环境分析；处理报告不会自动执行其命令。

### 三类处理对象

| 对象 | 需要回答 |
|---|---|
| SEC 自身漏洞 | 哪些宿主、入口、权限或存储受影响；哪些生成结果可能被污染 |
| 生成规则或运行库漏洞 | 哪些历史目标制品继承错误；是否需重新生成、替换运行库或迁移数据 |
| 项目信任根失陷 | 哪些签名、构建者、账户或审查结果不再可信；如何从最后可信输入恢复 |

只修复最新编译器，不能自动修复已经分发的目标源码和运行库。影响关系必须按规则版本、构成清单和证据定位，不能仅按文件名搜索。

### 紧急通道

紧急修复可以缩短常规排期，但不能省略精确候选、最低独立复核、来源验证、受影响范围、回退/前滚方案和发布后读回。需要更高权限时签发限定主体、范围、期限和用途的临时授权；事后复核不使不合法操作追溯合法。

对无法完成全部测试的紧急版本，显式公布未执行范围与风险处置，不能写成完整通过。暂时撤回发布或关闭高风险入口，也是有效遏制措施。

### 恢复信任

先限制新发布与敏感写入，再撤销旧令牌、轮换签名与受影响秘密、隔离缓存和构建输出。恢复从独立核对过的源码、工具链与策略开始；相同被污染环境中的第二次构建不形成独立保证。

已发布摘要和签名保留历史记录，通过撤销声明改变资格，不覆盖同一版本号下的字节。用户需要知道哪些版本、哪些生成模式和哪些配置受影响，以及采取更新、重新生成、迁移还是隔离。

### 与一般缺陷和供应链连接

安全问题可能由依赖、插件、模型、模板、示例、文档构建脚本或测试夹具进入。对外贡献没有发布凭据；安全修复测试不泄露受限样本。支持分支各自确认是否受影响，不能只假设代码相同或不同。

Python 项目的安全指南提供了报告分类、私下修复、公告和回移的实际结构；本设计吸收责任分离，不声称采用其组织或时限。OpenSSF 安全基线用于检查项目控制覆盖，不等于 SEC 已获得符合性认证。见[外部依据](../依据/来源/构建分发与迁移.md#构建内容分布式与迁移)。

### 验收与成本

验证报告入口故障接替、恶意报告输入、泄密最小化、签名撤销、规则漏洞反向定位、旧版本回移、公告与制品一致性、紧急授权过期以及从干净环境恢复。保密处理会增加协调成本，但公开未修复细节可能扩大伤害；记录必要决定和期限，避免无限保密掩盖项目风险。

## 开放使用与交付就绪

### 项目开放性与功能成熟度分开

开源许可、公开开发、可独立构建、可替换工具链、社区维护和功能完备分别评估。源码可见不等于已经开源；开源不等于有生产 SLA；设计完整不等于所有后端受支持。

SEC 的主流程应在没有中央在线目录或模型服务时重建已经采纳且依赖闭合的工程。首次 AI 设计、未缓存外部依赖或远程 Provider 可以需要网络，但必须声明该需要；不能把网络可用性变成所有本地查询的隐含前提。

### 公开前的责任清单

| 决定或控制 | 完成证据 | 未完成时行为 |
|---|---|---|
| 许可布局 | 权利人采纳、实际许可文本、第三方与模板构成检查 | 不宣称已授予开源分发权 |
| 贡献政策 | 来源声明方案、审查责任、实际贡献入口 | 仅接受明确授权的设计候选 |
| 安全渠道 | 入口读回、负责角色、备用接续、支持范围 | 不虚构安全服务已运行 |
| 发布权限 | 平台策略、密钥保管、独立复核与撤销演练 | 不发布“已强制保护”声明 |
| 干净构建 | 实际公开源码和环境可重建 | 不提供未经验证的安装承诺 |
| 支持矩阵 | 版本、功能、平台、证据和维护责任 | 限定为已验证范围或实验性 |
| 用户指南 | 已执行步骤、错误恢复、命令与版本对应 | 保留设计说明，不冒充教程 |
| 生成产物权利 | 模板、运行库、依赖、输入与输出义务明确 | 阻断不合格分发，不阻断有权本地草稿 |
| 诊断隐私 | 导出预览、脱敏、授权与保留流程 | 默认本地诊断，不上传工程 |

此表定义验收，不宣称本包已经完成所有平台设置。实际状态绑定发布 revision 的证据清单，不能从正文标题推导。

### 首次贡献和首次使用

设计阅读从项目范围进入；开发贡献从实际环境和检查入口进入；插件作者从机器合同与符合性开始；用户从已经可运行的用例进入。四类读者共用事实源，但不应被迫通读相同文档。

首次使用需解释将读取哪些文件、是否执行工具、是否访问网络、输出放在哪里、如何撤销、哪些目标仍不支持。首次导入默认不改原工程；实际写回独立授权；退出 SEC 后，原生生成目标只依赖明确目标运行库和工具链。

### 可持续性与维护负担

新规范、新工具和新检查需要责任人、维护成本和失败恢复。没有实际消费者或质量收益的重复 Gate 应合并或退役；关键检查有性能预算和故障降级策略，不能因检查基础设施失败把未验证制品变绿。

社区贡献数量、文档篇数和生成代码量不是项目质量的替代指标。比较同需求下正确完成率、未发现缺陷、人工决策负担、回归与恢复成本、修改影响和可重建性。没有工作负载时不造目标数值。

### 交付形式

产品源码、SDK、运行时、设计文档和支持服务是不同交付对象。设计包可以不含任何可执行物；软件发布则必须满足其所声明的安装、构建、运行、许可和支持合同。不能用一个文档 ZIP 冒充可直接安装的软件。

### 反例与复核

若用户必须购买某个模型或连接中央服务才能重新编译已采纳内容，独立重建边界失败。若一个插件无法通过公开合同开发，只能依赖未公开内部接口，生态边界失败。若项目通过重复自动生成文档满足数量指标，却无人能理解状态机和恢复路径，应减少展示噪声并补足真正合同。

## 扩展生态与符合性

### 接入对象与权威

前端、领域库、生成规则、目标后端、Provider、验证器与编辑入口可独立发布。目录只记录发现和分发信息；官方收录、签名通过、下载量和模式合法都不自动证明语义正确或授予执行权。

扩展名称由命名空间管理，绑定包内容、合同版本、入口、所需能力与目标范围。避免用作者显示名或可变下载链接识别实现。同名替换、依赖混淆和目录镜像差异必须被精确身份检查发现。

### 兼容与符合性

接口兼容表示能对话，符合性表示满足所声明语义，运行资格表示在特定环境和策略下允许使用。三者分别记录。一个签名已知的 Provider 仍可能不满足取消、幂等或资源结算合同。

符合性套件包含：最小正例、非法输入、未知字段和版本、边界数值、重复/乱序/取消、状态迁移、资源残留、源映射、生成确定性、跨宿主差异和独立业务预期。哪些用例适用由扩展角色和承诺决定，不能让不适用机制变成通用启动成本。

### 权限与隔离

纯扩展接收不可变值和能力受限的接口；访问文件、网络、进程或秘密时声明相应能力，通过宿主执行层取得受限权限。校验器也可能恶意或有资源耗尽缺陷，不能因为名称是“验证器”就绕过隔离。

目标工程数据属于使用者。上游插件作者不能通过更新扩展自动取得历史模型、源码或遥测。凭据只交给真正需要它的绑定，不写入生成清单、缓存键或公开诊断。

### 升级与撤销

锁定扩展和依赖内容后再开始编译；注册表变化不热改当前执行。升级按候选资格与风险选择独立检查或适用影子比较，并在用户范围执行必要迁移与读回。旧版无法解释新模式时明确拒绝，不静默丢字段。

安全撤销阻止新绑定并定位相关历史制品；运行任务根据风险进入取消、结算或隔离，不任意删除恢复资产。已声明兼容不免除真实版本测试，兼容矩阵必须有方向、模式和证据范围。

### 官方与社区边界

“官方维护”表示项目承担定义的维护与支持责任，不代表零缺陷。社区扩展不被强迫转移所有权才能使用公共协议；其发布者自行提供来源、支持和安全渠道。互操作规范、测试向量和错误合同应可以独立取得。

认证或认证等级只有在公开规则、可重复评估、申诉和撤销存在后才使用；当前设计不宣称已建立认证机构或任何成熟度徽章。

### 设计取舍

中央扩展目录便于发现但带来供应链与准入集中风险；完全无目录增加身份和更新难度。采用可离线的精确锁定和可替换发现源，让编译器不依赖单一在线目录。正式接入以接口、隔离和符合性为边界，而非品牌白名单。

### 验收

至少验证同名异内容、恶意元数据、未知版本、未声明 I/O、依赖混淆、被撤销签名、扩展卸载残留、旧任务迟到、供应商退出与完全离线构建。结果保存到具体扩展/目标范围，不扩大到整个生态。

## 维护权责与技术决策

### 目标与边界

本合同设计 SEC 上游项目的开放协作方式，不规定用户目标工程必须采用相同组织制度。维护者可以决定接收哪些上游改动，不能因此拥有用户仓库、部署环境或私有数据的授权。代码使用权由实际许可证确定，不由合并权限、贡献者身份或云服务账号决定。

当前这是治理设计：它不任命人员，也不声明实际仓库已启用保护规则。公开发布前需要把责任落实为可验证的账号、角色和接替记录。

### 权责划分

| 角色 | 可以决定 | 不可单独决定 |
|---|---|---|
| 贡献者 | 提交候选、复现材料与设计建议 | 自批候选、读取他人私有工程 |
| 组件维护者 | 组件技术审查、接口变更建议、回归处理 | 绕过跨组件兼容或发布政策 |
| 审查者 | 对指定 revision 和声明给出意见与证据 | 用审查身份修改候选后的证据 |
| 发布责任人 | 对已满足发布条件的精确制品执行发布 | 以打标签替代构建、许可和安全检查 |
| 安全响应人员 | 限制披露、协调修复、建议撤销信任 | 无记录地永久冻结技术讨论 |
| 基础设施管理者 | 托管、权限和密钥运行维护 | 将平台管理员权限等同代码正确性 |

同一人在早期可承担多个角色，但独立性按操作和具体参与者检查。无法获得非作者审查的核心信任变更可以作为草案保存，不宣称已满足独立复核发布要求。

### 技术决定流程

局部修复沿用已接受合同；公开接口、持久模式、生成行为、默认权限或支持范围变化需要决策记录。记录先写触发问题、用户影响、兼容和更小修法，再写方案，不以篇幅或支持人数代替论证。

```text
提出候选 → 影响与替代审查 → 修订候选 → 决议
                                    ├→ 接收并记录理由
                                    ├→ 延后并记录重开条件
                                    └→ 拒绝并记录反例或范围原因
```

普通改动的默认设计要求至少一名非作者审查；提升审查规则、签名权限、发布自动化、敏感数据出口或迁移破坏性变更，需要两个不同责任视角的复核。人数不是独立性证明，仍要检查共用 Oracle、环境和利益冲突。该数量是拟采用的项目策略，不是普适工程定律。

### 异议与利益冲突

技术否决需要给出被破坏合同、具体反例或较小替代，不能只有个人偏好。作者不能通过拆分 PR 隐藏同一破坏性变更。与商业雇主、供应商或本人实现有直接利益关系时公开关联，必要时回避最终决议。

维护争议先记录双方可检验主张，再交未直接参与的维护者复核；仍无法形成合法决定时，保留现行合同并发布解释。申诉有受理角色和记录，但不要求冻结无关安全修复。

### 社区行为与保密申诉

技术争论允许批评设计与证据，不允许骚扰、威胁、泄露私人信息或利用维护权限报复报告者。公开讨论记录技术理由；人身安全、私人资料和保密举报只交给获授权的响应角色。明确的行为准则、举报渠道、回避规则、处分范围、申诉方式与资料保留策略应作为项目政策发布，不能用本技术文档替代真实受理机制。

维护者同时是投诉对象时不得独自处理。临时限制权限应说明保护目的、范围与复核期限；恢复或永久处置均留可审计决定。行为处分与技术方案优劣分开，既不能因技术贡献大就免除行为责任，也不能用行为程序封锁正当技术反例。

### 持续性与退出

维护者接替要转移组件知识、未解决风险和恢复步骤；授予新权限后验证访问，再撤销旧权限。账号失陷先限制新写与发布，不能删除历史证据。长期无人维护的组件降低支持等级、停止新增资格声明，并提供迁移/独立维护选项。

治理文件、代码所有权和平台 ACL 定期比较；“文档列为维护者但没有权限”与“有权限但未登记责任”都应进入修复。重大行为规则变化保留旧版本及生效时间，不追溯改变已发生贡献的含义。

### 权衡与验收

全部由创始人直接裁决最省协调，但形成失联和信任单点；复制大型基金会委员会又增加早期负担。这里按真实责任分权，不预设复杂组织树。验收包括作者自批被拒、权限撤销生效、关键决议可复查、维护者失联仍可执行恢复，以及独立使用与 fork 不需要向上游逐次申请。

### 治理设计的生效协议

治理可以先完整设计，实际生效需要另一个事务。记录 `PolicyRevision`、适用仓库/制品/服务、要求的角色、实际主体绑定、授权来源、独立性约束、平台配置前像和恢复联系人；角色定义不包含个人姓名，部署时再绑定真实账号。未取得账号不阻止写政策和验收，只阻止声称该账号已经拥有或失去权限。

状态为草案→有权接受→配置候选→已配置待读回→已验证生效；失败进入待修复/暂停/撤销。顺序不能跳过：内容审批不等于ACL配置成功，API成功不等于远端状态已生效。执行前绑定实际平台前像和有权操作者，先保存恢复材料；执行后独立读取角色、保护规则和发布授权，比较精确期望，再签发生效记录。

每次至少验证拒绝路径：作者不能自行改变Oracle后发布，旧维护者撤权后不能继续签发，配置失败不能留下无人负责的发布通道，维护者失联时恢复角色能在记录授权内恢复。测试在隔离仓库/环境先跑，不能拿生产权限冒险试探。紧急恢复可以是预先授权且范围收窄的另一条流程，不允许将故障变成永久管理员旁路。

单人项目没有第二独立人时，允许非发布草案和本地实验；政策也可以明确选择不宣称双人保证的低风险交付画像，但不能把同一人的两个账号算作独立复核。核心信任或危险效果确实需要独立主体时，保持该动作阻断并保留所有其他工作。

退役时冻结新授予、迁移未完成责任与恢复材料、验证接替账号、撤销旧凭证并读回。人员退出、平台迁移和密钥轮换分别产生证据，不用删除旧用户名代替授权失效。

## 许可证、来源与生成制品

### 设计目标

开源不只是可以浏览源码。发布许可必须覆盖使用、修改、再分发和衍生工作等权利边界；具体要求以实际许可文本及适用法律为准。本文是工程上的权利追踪和发布准入设计，不代表权利人已经为 SEC 选定或授予许可证。[OSI 开源定义](https://opensource.org/osd)提供术语依据。

公开发布前，项目权利人必须接受一套实际许可布局，并将有效文本、范围和必要通知放入发布源。不能依据项目名称、文件公开可读或本设计包中的文字，推断当前所有材料已经获得同一许可。

### 六种不能合并的权利对象

| 对象 | 需要追踪的来源 | 主要风险 |
|---|---|---|
| SEC 编译器与工具源码 | 作者、贡献认证、第三方片段与依赖 | 上游无权再许可 |
| 文档和图表 | 作者、引用范围、图像或规范文本许可 | 复制标准全文或图表未获授权 |
| 生成模板 | 原模板、拷贝进输出的内容及其许可 | 生成结果携带未披露通知义务 |
| 目标运行库 | 链接/打包方式、版本、修改与许可证 | 工具许可被错误外推为运行库许可 |
| 输入工程与数据 | 用户权利、可分享范围和内容分类 | 导入被误当向上游公开贡献 |
| 模型、扩展与测试语料 | 提供方、训练/使用限制、再分发资格 | 仅支持调用却被随包分发 |

生成动作不会自动清除来源义务，也不会仅因经过 SEC 就自动让输出继承 SEC 工具的许可证。实际义务取决于输出包含或链接了什么以及相应许可；需要按具体构成审查。

### 来源随生成传播

每个逻辑制品记录输入作者区域、生成规则、复制模板、链接运行库、打包依赖及通知来源。纯结构推导、原文复制、源码改写、动态链接、静态合入与外部服务调用用不同关系，不用一个 `generatedFrom` 隐藏全部事实。

```text
输入与规则来源 → 制品构成清单 → 许可识别与证据
                                ↓
                     目标分发方式与政策检查
                                ↓
                  合格 / 需审查 / 拒绝本次分发
```

SPDX 标识与表达式用于可交换地记录许可，不单独证明内容匹配、兼容性或法律结论。[SPDX 许可资料](https://spdx.dev/learn/areas-of-interest/licensing/)明确区分许可信息表达、分析与政策执行。

### 发布资格

发布前核对许可文本、版权/通知、源代码提供义务、修改声明、依赖与生成模板构成、再分发渠道和目标对象。来源未知的必要组成阻断该制品分发资格；不因此禁止保存草稿或进行有权的本地分析。

多许可组合按精确表达保存。不要把 `A OR B` 当成必须同时遵守，也不要把 `A AND B` 当成任选一个；最终适用解释保留来源与审查决定。生成器不能自动去掉原通知来获得“干净输出”。

### 工具许可选择的取舍

宽松许可通常降低下游接入阻力；互惠许可可以要求某些派生分发继续开放，但影响不同集成模式；模板或运行库的专门许可安排可以减少输出义务歧义，却增加维护成本。当前不凭实现偏好替权利人选定，也不承诺不存在专利或其他权利问题。需要比较 SEC 作为工具、可嵌入 SDK、生成模板与目标运行库的实际分发路径后决议。

### 私有输入与上游贡献分离

用户使用开源 SEC 处理私有工程，不自动授权上传该工程，也不自动成为贡献者。错误报告和复现包遵守[公开复现与隐私](#公开复现语料与隐私)。许可证服务异常不能绕过隐私授权；缓存的许可结论绑定输入构成和适用政策版本。

### 撤销与迁移

发现来源错误时，识别受影响制品和支持版本，停止新的不合格分发，保留取证，替换或重新授权。不能改写已发布版本的历史通知来掩盖错误。合法持有的历史材料如何保存、解释和继续分发分别判断，不能由“删除旧缓存”代替处理。

### 验收

至少测试复制模板进入目标、运行库单独链接、不同版本许可变化、未知许可证、自定义 LicenseRef、组合表达、源通知保留、私有输入隔离和重新打包。技术检查只能证明记录和政策执行；正式许可采纳及个案解释仍需有权主体。

### 许可方案可先设计，授权不能代签

当前可实现权利清单、构成关系、通知生成和分发准入，即使最终许可证尚未采纳。拟定候选布局分别覆盖工具、SDK、模板、目标运行库、文档和测试数据；比较时固定目标分发方式、来源权利和所需下游权利。由有权主体接受具体文本与范围后，才将候选升级为有效许可记录。

运行协议为：精确构成清单→来源/许可识别→政策评价→未决项清单→有权决定→发布前回查→通知与回执。未知必要来源只阻断相关分发动作；仍可开发替代实现、处理有权访问的数据、生成不包含该来源的候选制品。最小失败分支包括替换来源、移除依赖、取得授权或不分发相应输出，不能默认“以后补许可”。

这些工程协议不代替具体许可证选择或真实权利人的授权。检查程序可验证记录和动作前提；许可文本适用与权利来源必须由真实材料支持，不能用Schema或签名格式伪造。

## 贡献流程与 AI 辅助贡献

### 贡献单位

贡献可以是设计修正、实现、测试、文档、翻译、复现语料或维护工具。接受标准由修改对象决定：文档修复无需证明整个系统性能；生成规则变更则要检查受影响制品、独立预期与兼容范围。

一个可审查贡献包含具体问题、修改范围、原行为/新行为、验证方法、未验证范围和来源。安全缺陷进入[安全响应](#安全响应与信任恢复)，不要求公开利用细节。

### 从贡献到采纳

1. 在明确 revision 上准备最小可验证改变；涉及多个合同的改动说明依赖顺序。
2. 运行所需检查并提交实际日志位置、环境和命令；不将没有运行的检查标绿。
3. 自动检查在无发布秘密、无受信写权的环境处理外部候选。
4. 审查者核对输入差异、测试 Oracle、兼容、隐私和维护成本。
5. 候选修改后，按受影响闭包使旧审查或执行结果陈旧；真正内容不变的运输变化可按既定规则复用。
6. 合并绑定所审内容；合并结果重新观察。失败进入修复或撤回，不靠改报告解决。

文档、测试或配置也是可执行供应链的一部分。Markdown 中的命令、图形声明、测试构造和构建插件按不受信输入处理，CI 不从评论文本直接执行指令。

### AI 使用政策

允许 AI 帮助理解、设计、实现、检查和文档工作，但提交者仍须理解关键机制、确认来源权限、重现验证并回答评审。声明使用 AI 的实际范围，不收集无必要的完整聊天记录或私有上下文。不得把用户代码、秘密、漏洞细节或未获授权数据上传给外部模型。

AI 生成实现、AI 生成测试和 AI 复核可能共享同一错误前提。关键变更保留独立需求、手写/既有 Oracle、差分或性质证据；几个相同模型的一致意见不是独立验证。未经人工理解的大量自动提交可以被要求合并、缩小或停止，依据是可审查性与风险，不以工具名称作歧视。

### 来源声明与贡献协议

贡献需要有权提交的来源声明。DCO 1.1 可作为来源认证机制，CLA 则是另一种权利安排；不默认同时强加两者。项目权利人选定实际方案后，在贡献入口给出原文和适用范围。本文不代签 DCO，也不创造贡献许可。[DCO 官方原文](https://developercertificate.org/)解释的是提交者的来源与授权认证，不是测试正确性。

自动生成的依赖锁、规范投影或格式化结果标明生成器与命令；原生创作、复制模板与纯生成结果分别记录。未知来源的片段不能因“AI 写的”而免除检查。

### 开发入口合同

正式开发指南应从干净 checkout 到首次检查给出真实支持的命令、版本、预期输出、可选网络访问和失败恢复。当前设计包不发明尚未在仓库验证的安装命令。命令清单由实际 package scripts/工具入口导出并经干净环境执行后发布。

贡献者不应先阅读整个研究目录；入口按“模型与接口”“前端”“生成规则”“运行”“保证”“文档”提供最小阅读范围、代码位置和检查选择。范围选择减少负担，但不能删去真实共享依赖。

### 合并失败与长期维护

修复可复现缺陷时先保留复现用例；若用例涉及隐私，按脱敏与保密流程处理。测试被隔离时记录原因、原覆盖、代替检查和恢复条件，不能删除测试来恢复绿色。变更作者不可达后由组件责任人接续，不把维护责任无限绑定原贡献者。

### 理由与验收

禁止 AI 会损失合法生产力，完全放行会转移审查成本；以可理解性、来源和证据评估贡献更接近实际风险。验收包括不受信贡献不能读取 CI 秘密、越界脚本被拦截、作者能解释修改、旧证据正确失效、报告不含私有目标代码，以及普通文档修改有轻量路径。

## 库发行与内部自用的支持承诺

库生命周期先允许本地模块，真实需要分发时才建立包出口与版本；公共注册中心不是使用自己的库的前置。[库规范](../作者/组合/模块封装与复用库.md#9-库使用抽取包装和发布的正向过程)拥有打包、发布、升级与退出协议。本章承担分发方的许可、支持窗口、安全响应和责任归属，不再定义另一份包字段。

公开合同兼容、目标工具支持、平台能力和持续数据兼容分别声明。只修私有实现但改变错误行为时，不得以patch标签掩盖；公开类型表示、生成的内联产物与恢复需要的旧解码器要纳入通知范围。恶意版本可以立即限制新采用，仍保存必要的隔离恢复路径。

SEC自用或自举通过不自动产生公开发布资格。维护者仍核对原任务、方法、分发物、签发主体与支持范围；如果只作为内部库采用，应准确保持该状态，不虚构公共社区或完整生态已经存在。

## 开发变更进入CI、发行与迁出的实际路径

开发完成从准确提交/合并候选开始，而不是工作树最后一次绿色截图。协作系统读取真实基础、选定变更、消费者和检查范围，形成集成候选；CI按该候选及准确工具/配置/目标矩阵运行，提交后hook改了内容则产生新输入，先前结果不可贴到新字节。签署/发布需当前资格，但不为普通本地源码变更增加默认审批链。

交付成员从ArtifactSet封存，不遍历当前目录捡遗留文件。已知许可、秘密、来源、平台入口、配置/资源、安装和迁移说明按本次发行义务检查；代码签名、构建通过、案例通过和用户采用互不替代。真实渠道操作按原requestId与目标回执查回，超时不换身份重发，保留可交付的独立平台但不宣布全矩阵成功。

打包/安装用相应Provider的真实路径、权限和恢复能力；下载成功不证明载荷完整，解压成员不越出目标，执行安装/升级脚本是单独获准作用。工具自身升级与用户工程依赖升级分开，新工具不能未经迁移改写所有作者文件。需要回退时区分新分发停止、已安装版本、数据前后兼容与实际用户效果；不会用删除制品来假装撤回外部消息。

开发者迁出时取得自己有权的原生/中立作者源、必要依赖与许可证、稀疏控制/角色、生成源码和可解释对应，保留运行/恢复责任与秘密边界。目标源码可独立构建不必自动具备任意受管回源能力；继续中立开发需要相应语言解释与合法供给，依赖缺失准确列出。项目不应为了打开源必须重新登录一个可选服务；真正受限依赖也不能被出口承诺抹去。

分支、PR、CI、发行渠道或外部工单的自动写入只在本任务明确授权后进行。设计示例的路径不冒充已读取远端仓库；本设计包的ZIP不是产品安装包。
