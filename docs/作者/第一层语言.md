# 第一层语言

> 设计候选；与既有规范共用作者身份、语义与执行责任。生产实现与正式采用分别取证。

<a id="intent-language-product"></a>
## 交付对象：通用意图开发语言

Gift 第一层的产品是可用于创作不同工程的**通用意图语言及其开发面**。语言规定人怎样表达必要区别，表达怎样取得准确含义、组合、精化和持续修改，以及系统怎样据此形成完整源码工程。具体工程的作者源是语言的使用实例；ripgrep 等成熟工程提供真实要求、组合压力和反例，不拥有语言定义，也不能凭案例合同齐全取得语言版本完成资格。

这里的“语言”包含构造、形成规则、含义和组合规则，不以另造文本语法为前提。降低作者责任是设计目标：人不必重写可继承的含义、可推导的信息或已委派的实现；需要精确控制时仍能表达。JSON 是当前结构载体，其字段数、压缩程度和可解析性不决定抽象是否成立。“不是普通编程语句换皮”不能被解释为禁止设计通用语言、禁止形成新抽象，或必须先补齐所有案例再设计共同规则。

### 现有语言设计怎样构成一个整体

以下定位已有构造及其解释责任，不新增一套语法、Kind 或作者必填表。领域含义可以开放扩展；一次语言版本须明确实际固定的规则和仍待闭合的接合，不能用“可扩展”代替当前解释。

| 作者可进行的表达或改变 | 准确含义与原规则位置 | 组合后必须保持什么 |
| --- | --- | --- |
| 给对象和值命名，引用或实例化已有定义 | [定义、抽象与实例化](组合/抽象与开放定义.md)，[结构作者源](结构化源码.md)；有类型的参数、词法绑定和公开签名 | 域、身份、作用域和发生点；同配置不合并运行状态，引用不执行也不授予权限 |
| 规定结果关系、保持条件及允许变化 | [需求含义](需求含义与实现责任.md#open-intent-expression-closure)；Definition/Meaning/Requirement 承担相应准确解释 | 合法输入、正常结果、错误、效果、帧和进展；关系可以保留多个实现，不必写成阶段函数 |
| 组合条件、备选、量化、时间和承诺 | [本章的论域与策略](#first-layer-denotation-and-realizability)及需求含义原合同；Goal 模态仅承担相应承诺 | 同一主体和共同见证、量词次序、选择时点与可得信息；逻辑合取不指定顺序或并发 |
| 封装复合定义，连接多个使用点 | [开放定义与组合](组合/抽象与开放定义.md)，[跨领域接合](#first-layer-composition-admission) | 复合结果可继续组合；真实连接保持身份、前提/保证、作用、寿命及进展，不靠同名端口猜接线 |
| 局部特化或控制实现，再撤去控制 | 原 Control、精化及同源编辑合同 | 只限制相交实现自由；不缩小应支持输入、不删除硬要求，也不产生第二份可写实现源 |
| 创作新含义，固定后生成并再次修改 | [编译承接](../开发/第一层编译承接.md)及[同源编辑](紧凑结构与同源编辑.md) | 创作形成并接受准确内容；普通构建确定消费；后继修改回原含义和实际依赖，系统更新派生结果 |

这些机制的闭包由开放定义中的有类型构造与组合解释承担，不由此表的行数证明。语言设计者应主动检查空域、绑定、递归、共享、时间、失败及不同机制的相互作用；不必等待某个案例先失败才允许修正不完整的公共构造。提出的新增机制仍须说明已有构造为什么不足、保留什么独立区别及谁消费它，避免从某个目标语言逐条复制语法。

语言版本的验收归[通用语言交付](../运行/验收/第一层开发面.md#intent-language-delivery-acceptance)。本页及其引用是当前通用设计所在；案例中的 PRODUCT、库合同或局部 JSON 都不能代替这组规则及其落实闭包。尚无生产 Reader 或生成链时可以交付完整设计，但必须分别指出未闭合的设计与未执行的实现验证。

<a id="intent-language-v1-formation"></a>
## 第一版开发面：开发者怎样表达和改变产品

本阶段交付开发者行为与意图抽象。确定人能表达什么、组合后意味着什么、如何控制和再次修改，并给出合理的理论可行依据；内部Reader、类型出口、绑定表、求解器、目标代码和运行机制另行设计，不作为本阶段完成前置。开发者不需要先理解或维护这些内部对象。准确类型在内部可能必要，是否对外导出具名类型则由真实接口需要决定，不能把两者混为一谈。

完整使用设计在[开发面V1](../../examples/第一层作者/通用语言完整设计.md)，实际作者记法在[连续意图稿](../../examples/第一层作者/开发面V1意图稿.md)。记法表达下述固定概念，不声明当前已有文本Reader，也不要求先发明新文本格式；文本、表单或图形视图应编辑同一份有效意图，不各自维护规则。

### 表达的共同对象

一份意图规定在给定范围内哪些产品结果、关系和行为可接受，以及哪些区别仍留有选择空间。它可以只是一句话，也可以命名后被采用、嵌套和组合；完整有效含义包括当前明确要求、适用的既有合同与已接受的选择。人只补当前上下文无法取得、推导或在委派内决定的独立信息，不必填写下面每一行。

| 可组合的表达 | 开发者实际决定什么 | 组合含义与边界 |
| --- | --- | --- |
| 指称对象与结果关系 | “这些条目怎样排列”“这两个地方使用同一份资料”“不得出现什么结果” | 同一对象、独立副本、一个值和一个有状态对象不同；名字只用于指称，不指定执行步骤 |
| 限定范围与承诺 | 对哪些输入/成员、在什么条件或期间必须达到、持续保持或禁止什么 | 所有与至少一个、一次达到与始终保持、适用条件与产品输入域不同；不能偷偷删去已承诺输入 |
| 保持与允许变化 | 哪些既有内容保持，哪些区别允许系统决定或改变 | 允许不是必须；省略保持不自动授予现实修改权；正常结果和失败时的既有责任仍须说明 |
| 定义、采用与局部差异 | 给准确含义命名，在别处采用；只改一个采用处或改变共享定义 | 采用继承完整含义，不复制一份手工维护的源码；同配置不自动共享状态；局部差异不悄悄改全局 |
| 必须条件、偏好与精确限定 | 哪些结果才合格，在合格者中更喜欢什么；确有需要时固定局部选择 | 偏好不抵消必须条件；业务关系与实现选择分开；撤去选择只放开相应自由 |

这是共同表达的责任划分，不是固定业务功能名单，也不是五张必填表。新领域使用自己的对象和关系，仍按这些规则组合；没有预制“任务整理”“库存”或“搜索”能力时也可创作。需要的新含义须能用明确关系、条件和区别例说明，不能只有一个名字；系统承担形成和维护准确内容，人不被要求先建设能力库。

### 同一套表达怎样组合

“同时成立”使各项要求约束同一被指称对象及同一结果；不是各找一份不同结果，也不规定执行顺序。“任一方案”允许一个完整分支成立；分支内的保持和失败责任一起保留。“当条件成立时”只限定该项义务，不能把未知条件当作不成立。嵌套组合的结果仍是一份意图，可以继续命名、采用和组合。

“每个”“至少一个”“同一个”保留数量、身份与共享区别；“之前”“之后”“期间”“直到”只规定开发者关心的可观察时序，不要求写阶段函数。若用户关心预览必须先于确认生效，这就是产品交互要求；若只是实现内部先扫描还是先排序，通常由系统选择。允许多个正确结果时，不强迫开发者指定唯一结果。

组合时先确定对象范围，再把各关系代入同一范围。待办页“只展示筛选范围”与“保留其中全部重复条目”可以共同成立，不能把后者错误应用到筛选范围之外，也不能把展示筛选解释成删除原资料。不同采用处默认保持各自实例；只有明确共享或既有合同确定共享时，才共同约束同一资源。

冲突应以产品后果呈现：例如同一对不同优先级条目既须严格按优先级降序，又须严格升序，无法共同满足。系统指出相交要求和区分例，保留其他内容；不得擅自删要求，或让开发者从内部类型/供给错误中猜原因。含义未定、要求冲突、当前尚无支持分别呈现，不能统称“做不了”。

### 实际作者记法与省略

```text
意图「整理次序」
  对象：本次待展示的条目
  结果：按优先级从高到低排列；同优先级保留原次序
  保持：全部条目及重复出现；条目内容；原序列
```

这里“对象/结果/保持”标明含义角色，不是要求作者手填完整模型。原上下文已确定“本次待展示条目”时可省略对象行；已有准确保持合同时不必重复保持行。用户先用一句话表达时，系统应形成同一份意图，而不是要求用户先转换成这份排版。被接受后的准确含义稳定，不能每次重建重新猜原话；人随时能查看省略后仍有效的内容及其来源。

```text
采用「整理次序」于「待办页」的筛选结果
采用「整理次序」于「导出预览」的筛选结果
偏好：在全部要求满足时，减少额外内存
```

两个采用处各使用自己的筛选结果，继承排序、保序和成员保持；偏好只在满足这些要求的方案间比较。没有让人写filter/sort步骤、比较函数、导入表、ID、观察接口或目标类型。人主动要求特定算法、精度、布局或接口形式时可以进一步限定，但这些不是正常创作的默认前置。

### 修改是语言的一部分

| 开发者行为 | 对原意图的准确影响 | 必须能看到的结果 |
| --- | --- | --- |
| 补充要求 | 与所指范围的既有要求共同成立；不自动覆盖旧要求 | 新增条件、作用范围及可能冲突 |
| 只改此处 | 改当前采用处的明确决定；开放参数直接特化，否则形成可辨认的局部修订 | 此处改变了什么、继承了什么、其他采用处未变 |
| 修改定义 | 修订共享含义，检查真正采用它的位置 | 所有受影响处和各自后果，不能只显示一个文本diff |
| 固定/放开选择 | 固定一项原可选自由，或撤销本处有权撤销的限定 | 合格选择空间怎样变化；独立硬要求不被删除 |
| 重组而不改意图 | 移动、命名或抽取共同内容，保留含义和独立来源 | 前后行为无变化；不能借整理丢失隐藏条件 |
| 接受新版本或撤销未采用修改 | 形成新的准确修订，或回到仍可取得的原修订 | 当前采用版本与尚未采用草稿清楚分开 |

例如“只把导出预览改为创建时间降序，同时间保留原次序”改变一处排序决定。若共享定义未开放该参数，界面明确显示这是该采用处的局部修订，不伪称原定义从未改变；待办页继续优先级降序。非本处有权改变的独立合同不能被同名后写覆盖，因旧决定推导的说明也须重新形成，不能机械照抄。

改变源默认产生新修订，不隐含把正在运行的旧对象立刻切换政策、改写历史或撤销已发生作用。是否采用到运行对象属于明确的后续开发/发布行为；本阶段只固定开发者可理解的区别，不为一次编辑预造热切换开关。用户修改目标代码也不应默默产生第二份权威意图；是否能准确回到所求关系，或改由作者接管，必须明确显示。

### 开发面怎样反馈

正常入口应提供当前有效意图、所选范围、来自哪里、仍可选择什么、哪里未定，以及本次修改的产品差异。系统形成的内部类型、引用、推导和实现可以按需查看，默认隐藏的是可推导和实现细节；不能隐藏独立约束、失败含义、未定选择或长期维护责任。没有必要的内部机制不应增加；必要但开发者无需触及的机制不应因此删除。

同一来源支撑新建、理解、组合、编辑、比较、检查、结果预览、协作和版本采用。不同视图不成为多份源码。相同语句在上下文中有多个会改变结果的解释时，呈现具体区别并只取得必要决定；有有效委派时系统可以作出并明确固定选择，不把全部内部槽位变成问卷。

本版的可行依据是已有的关系/约束表达、参数化与组合、结构编辑和语义差异方法能够承载这些行为；实际采用哪种表示、分析方法或生成后端留给后续内部设计。此阶段不以写出目标TS/Rust、安装Reader或完成ripgrep迁移取得资格，也不宣称任何意图都已能自动求解。验收直接观察开发者是否能完成上述连续任务，以及是否只承担必要决定。

## 固有合同与作者差异：完整意图不等于逐条手填

意图是此次希望成立的结果、关系、保持项和允许变化；完整有效意图包含已选定义的合同、适用的独立要求及当前差异。**只写差异**约束的是新增作者负担，不把意图本身重新定义成补丁。引用一个已有完整定义、绑定调用对象和必要参数，本身就能表达意图；没有独立差异时不新建同义Goal，不让作者逐条重写库保证。第一次新建也可以复用现有定义，不要求先拥有一份旧产品才能使用差异式创作。

“不能重复扣款”“库存分配不得超过可用量”在准确的支付或现货分配合同已选定时，应由该合同继承。它们仍是完整产品必须满足的性质，却不是每个应用作者需要重新选择的开关。行业名字、一个方便的函数名或看似合理的常识不足以取得该合同；没有已知定义时，系统按已有委派形成准确含义和实现候选，不把未取得的语义伪装成内置能力。

### 同一个性质的来源、约束强度和履行证据分别保存

以下是对现有Definition、Requirement、Profile、Method、Observation及接受关系的归属说明，不增加公共枚举、合同数据库或作者必填表。一个有效要求可以有多个来源；相同来源类别也可能提供不同强度或用途的内容。

| 已有来源 | 自动承接什么 | 不能顺带推出什么 |
|---|---|---|
| 所选基础语言或数学理论 | 值域、类型、相等、运算、绑定与组合的准确含义 | 真实资源存在、外部数据正确或任意程序可判定 |
| 选中Definition/Pattern/Profile的公开合同 | 在实际Use与参数下的输入、正常/失败、帧、不变量、进展和允许变体 | 引用已经构成实现证明，或所有导入但未使用的定义均被激活 |
| 有条件的上游或Provider保证 | 在其真实假设、版本、对象和环境内成立的保证及剩余前提 | 前提已在现场成立；名字相同的另一Provider也有同样能力 |
| 已接受产品要求、接口与外部政策 | 适用主体、时域、来源和权威下的独立承诺 | 被引用便可由本地作者撤销，或转成可后写覆盖的默认 |
| 明确可覆盖的默认与已接受Profile参数 | 省略时采用的确定值、适用范围和版本 | 合同不变量也可reset；默认冲突可以由后端悄悄换值解决 |
| 当前独特要求、显式控制或有效委派 | 本次新增含义与剩余合法选择权 | 无限制搜索、安装、披露、真实执行或修改他方义务的授权 |
| 运行输入与现实观察 | 其取得阶段、身份、时效、覆盖及内容 | 稳定业务政策、全部未来事实或作者已接受新语义 |

取得定义要同时取得真正适用的公开合同：对象与类型、身份/重数/单位、合法输入及环境、正常保证、失败和结果未知、允许效果与帧、时间/进展、资源/寿命、配置槽和覆盖规则、版本来源及实现/证据责任。各项由原owner的字段或引用承担，纯函数只激活其实际责任；无需为它伪造事务、持续监控或一套永久合同记录。具体如何形成同一有效义务集合，见[编译承接](../开发/第一层编译承接.md#inherited-contract-elaboration)。

采用有条件保证A⇒G时，系统继承的是这个条件合同及对A的相交取得责任。只有A和该保证在本用途的资格成立，才可将G用于后继判断；对开放环境可以交付明确的条件性设计。把G同时当作证明A的唯一依据、把候选自己的承诺当外部事实，或仅从合同名称推导G，均不能消解义务。已经具备适用证据时复用，不要求每个应用重新证明整个库；缺证据也不反向要求产品作者重写算法。

### 合同适用与可配置性不由字段名字决定

合同在选中的Root/Use、词法实参、主体和有效条件下实例化。导入只提供可见定义，不自动实例化全部库要求；未选备选不变成执行前置，未知条件不当作false删除其义务。独立已接受的硬要求仍在共同根范围内，不能通过不选择其Goal或删除输出根规避。两个使用点可以共享无状态分析，但不同实例、不同发生、独立接受和恢复责任不合并。

固有不变量属于选定含义的组成部分。允许配置的行为必须有已定义的变体、参数或政策槽；默认仅决定该槽在省略时取什么，不改变其值域和组合规则。硬条件冲突报告来源及相交范围，不用“局部更具体”“后写优先”或“更严格者赢”替代裁决。真正变更合同须形成有权的新定义、变体或修订，并检查已有消费者和状态迁移；不能将删掉一项不变量伪装成换实现。

已有独立要求与被引合同恰好同义时，可以共享检查及解释显示，仍保留各自接受、撤回和失效来源。由被引合同派生的重复文字不再成为另一份可写规则；若原来源本来是独立验收依据，就不能为去重删除它。省略与显式固定当前同值也不同：前者跟随已接受的默认修订，后者保留主动冻结意图。

### 应用作者控制的是实际剩余决定，不限于算法

系统先继承完整合同、取得已有事实、严格推导并使用有效默认或委派，再判断本任务尚缺什么。只有一个当前出口真正需要的选择仍未固定、会改变接受结果且不能在有效委派内决定时，才向相应有权主体提出具体差异。多个都合法的实现不是缺语义；合同有意允许多个结果也不等于必须选唯一结果。运行时参数尚未取值可以正常生成接收该参数的程序，不能一概变成编译期问卷。

应用作者可以只选能力和参数；新产品行为需要时可定义新的关系、规则、接口和政策；确实创造或指定算法时可直接规定计算方法、精度、复杂度、顺序、布局或ABI。三种工作沿同一作者体系，角色可以由同一人或获委派AI承担。库作者定义一次的公共合同、编译器派生的绑定以及应用作者此次差异不能全算成应用作者必须手写的内容。

主动指定算法是有范围的控制，须与产品合同共同满足。只指定“用算法X”可能已经通过X的准确合同确定行为；存在未定输入域、错误、单位或外部效果时仍须由其真实来源闭合。算法名、复杂度标签或函数签名本身不能替代缺少的含义。没有主动限定时，在合格空间选择算法是系统工作，不因解释详尽而再把选择退给作者。

广泛设计委派可以包含产品政策选择，系统应在授权内形成并固定有后果的决定，而不逐项要求人工确认。决定一经接受且改变产品公开行为，就归作者/政策语义，不再由每次构建的后端随机选择。已委派实现自由仍由Compiler/Resolver拥有；声明、真实事实、Evidence和Grant的权威边界保持。

### 付款、库存和纯计算的区分见证

**支付身份与重复作用。** 若所选合同规定一个有权支付意图仅允许一次捕获，重传该意图不新增扣款义务，最多一次效果由合同承接。不同购买、账期、分期或被明确授权的多次捕获可以是不同合法行为；不能以订单号、金额相同或相同请求字节自动合并。领域Definition须规定真正的操作身份、发行域、载荷匹配、允许捕获范围与重放期限；Method负责相应持久去重、并发提交和Provider接合。超时不证明未扣款，重试须有真实幂等/读回依据，超出Provider保持范围时保留结果未知或采用另一个合格方案。退款是新的效果，不能将“扣两次再退一次”当作原先从未重复扣款。已经选定这份合同的应用不再填写`avoid duplicateCharge`。

**库存与履约模式。** 本包预留库只约束固定pool/epoch、同单位可替代数量及合法分配。现货分配可继承不超过可用数量的保证；预售接受订单、第三方直发、数字权益和可负数的记账余额各有不同含义，不能按一个inventory字段混同。预售不通过关闭现货分配不变量实现，而是选择正确的订单承诺与后续分配关系。实际库存、损耗、补货和外部交付仍由运行事实及环境合同取得；模型内守恒不制造实物。共享库存的两个Use须联合检查同一资源，不能把局部合法分别当成整体不会超配。需要这些不同模式时只改变真实政策或绑定，不把锁、队列、事务日志和恢复算法重新交给应用作者。

**计算合同与新差异。** 已选稳定排序定义自动带入排序、重数与同键顺序，作者只给比较关系和必要输入；普通排序没有承诺稳定性时，不能凭习惯追加独立硬要求。区间范本引用CanonicalTouch就取得覆盖、升序、合法错误及合并相接区间的关系；改用CanonicalOverlap改变的是相接边界的产品含义，排序扫描或树结构仍可自动选择。选择精确数学整数后，其目标实现不能为方便改成安全Number子域；位宽、舍入或近似若真正被要求，沿原数值合同明确表达。

这些是可检验的语义情形，不发布新的Payment或Commerce标准包，也不假设已安装服务。具体源与二次修改继续使用[预留例](../../examples/第一层作者/reservations/README.md)、[区间例](../../examples/第一层作者/interval/README.md)及[验收合同](../运行/验收/第一层开发面.md#inherited-contract-acceptance)。

<a id="first-layer-author-language"></a>
## 开发者第一层：用同一语言规定结果、关系与可接受变化

“第一层”是产品作者的常规责任边界，不是再增加一种IR，也不是限制用户只能使用一句自然语言。作者在这一层提出、组合、精化和修改需要成立的含义；系统负责取得精确解释、形成可持续作者源、选择或创作实现、生成完整成品并解释其真实结果。对象细化与定义嵌套仍属于同一作者层，不要求作者沿编译阶段逐层下沉。

本节以[共同需求合同](组合/跨软件需求合同.md#cross-software-intent-contract)和现行Definition、Requirement、Goal、Pattern、Use、Control为基础，规定它们怎样构成一个可实际使用的开发主面。六模态、类型规则、组合解释和执行协议仍由原拥有者定义；下表不是新增Kind、JSON键或固定业务枚举。

### 作者必须决定的含义，与系统必须完成的工作

作者只承担不能由已接受内容、实际材料或有效委派取得的独立信息：目标是什么、哪些现实对象或使用者相关、哪些区别必须保留、哪些结果不可接受，以及确实只由其掌握的偏好或事实。作者可以委派符合原要求的设计取舍，不必决定每个尚无具体值的槽位。真实权限由受信授权渠道取得，不能从一句“全部自动完成”补造。

系统必须承担准确名称与身份解析、声明生成、可确定类型/单位/效果推导、依赖发现、接口与模块安排、合格供给复用或创作、算法/存储/并发策略选择、目标降低、构建配置、运行资产、来源映射、必要检查和已授权作用的恢复。其失败不能被改写为“开发者必须自己填写Method、IR或目标源码”。系统能力不足时保留原要求、具体缺口和已经成立的结果；不得以伪实现、空成功或静默降级冒充代劳。

同一个人可以主动成为算法作者、库作者或原生维护者，但这是额外选择，不是普通产品需求进入系统的门票。用户明确要求某算法、布局、ABI或语言时，该选择在第一层成为有范围的约束；编译器仍负责将其落实，不要求用户代写下面几层。

### 第一层需要承接的独立含义

这些是表达发现入口，既非每个项目的必填表，也非通用性的数量证明。一个实际要求可以同时涉及多行；未激活的机制不生成占位服务。

| 作者真正描述的内容 | 必须保留的区别 | 系统承担的落实 |
|---|---|---|
| 对象、角色与身份 | 类型、实例、集合成员、同一对象/不同对象、公开角色与真实资源不混同 | 作用域、绑定、实例化与来源；不按显示名合并 |
| 值、结构与单位 | 数学值域、记录/变体、可选与空值、集合/多重集/序列、单位与精度 | 合格编码、类型推导、必要转换和目标表示；未知不转默认值 |
| 输入到输出的关系 | 合法输入、正常结果、非法输入与错误、结果唯一或有意保留选择 | 复用或形成满足关系的真实算法，而非只生成签名 |
| 全称、存在与依赖选择 | 完整论域、量词顺序、见证共享、选择者及取得信息的时点 | 有类型绑定、覆盖和相应方法；不将开放域当已枚举有限集 |
| 状态与历史 | 初态、状态变化、历史观察、可重复/不可重复动作、保留期 | 状态拥有者、存储和变化协议；终态相同不抹掉过程差异 |
| 交互与协议 | 输入输出方向、调用/事件、会话、身份、取消、错误与兼容 | 接口、编解码、适配和真实生命周期，不只创建端口名称 |
| 时间与进展 | 先后、最终、持续、期限、迟到、时钟域及环境公平性假设 | 调度、计时与进展保持；永拒、永等和空时域不成为成功 |
| 逻辑组合与运行组合 | all/any/when/量化与顺序/并发/反馈各有含义 | 合法共同见证、执行方法和耦合检查；逻辑合取不等于并发 |
| 保持项与变化边界 | 不写入、值不变、行为兼容、表示保持与允许变化各自独立 | 影响分析、帧、隔离和检查；不能由一次结果相等证明无写入 |
| 共享、并发与分布 | 共享状态、原子性要求、可见顺序、离线、分区与共同故障 | 选定一致性和恢复方法；不因两个根分别成功声称共同成功 |
| 资源与寿命 | 容量、吞吐、内存、能耗、占用、借用、最后使用和关闭 | 真实分配/调度/释放与预算；不靠堆内对象名称证明物理上限 |
| 规范与授权 | 应履行、可被允许、被政策禁止与实际上不发生分别解释 | 规范冲突与执行准入各归其owner；permit不自动产生Grant |
| 不确定性与概率 | 世界事实未知、证据冲突、随机分布、相关性和统计误差 | 真实观察、概率/统计方法与资格；不以单轨迹结果代签 |
| 连续、空间与物理对象 | 坐标、单位、连续模型、离散近似、几何关系、设备与安全范围 | 相应领域方法、误差及设备边界；模型回滚不撤销物理作用 |
| 学习与自适应 | 数据范围、学习目标、允许更新、评价与部署后约束 | 数据/模型/运行版本和监测；训练分数不替代实际接受 |
| 人类活动与责任 | 分派、理解、接受、履行、移交、期限与撤回 | 可追踪交接和未结责任；发送通知不等于已接管 |
| 成品与使用环境 | 库、命令、服务、交互产品、插件、设备或其他公开消费边界 | 完整成员、依赖、配置、资产和宿主接合；不以shape标签代签 |
| 质量、偏好与成本 | 硬阈值、软比较、不同主体、量纲、工作负载及不确定性 | 在硬合格集合内按已接受政策比较，不把未知成本填零 |
| 开发变化与演进 | 新增、替换、局部特化、共享定义修改、迁移、退役及外部消费者 | 同源候选、精确影响和相交重新生成；不要求作者手改派生物 |

新含义不能被这些分类截断：先尝试已有定义和有类型组合；确有独立观察无法保持时，沿原语义扩展责任形成准确解释。不能把“不在表中”当作拒收理由，也不能把“已收下原文”当作已经理解。

### 一套构造规则，而不是一份业务能力菜单

第一层使用现有构造形成任意有限合法作者结构：命名定义与词法绑定、引用与应用、类型化参数、关系公式、Requirement组合、Goal承诺、公开封装及局部控制。定义可以继续组合定义；模块和公开出口负责复用，不要求每一层另发包。一个组合结果只要具有合格公开合同，就可作为同类定义在下一组合中使用。

新业务词优先成为普通定义、名义类型、关系或参数化组合，不成为编译器中央switch中的一个行业分支。新的“排队公平”“同一患者”“保持视觉顺序”等词必须得到其实际论域、观察及可区分语义，不能只把字符串放进一个任意JSON载荷。已有共同构造足够时，由系统形成这份定义；真正需要新专业解释器时，保留其支持缺项和实现责任，不要求应用作者先维护插件框架。

Goal的achieve、maintain、avoid、oblige、permit、prefer继续承担原有不同承诺。它们不代替类型、逻辑和专业关系，也不要求每个定义套Goal。复杂公开比较、因果、跨轨迹或规范关系不因Goal短字段不足而被删除，应复用原Requirement/Meaning结构。表示较短不是语义优先级。

编译期选择、目标运行时选择、人与环境的选择分别解释。例如“每次输入后选一个符合规则的输出”和“事先选一个能应对全部输入的固定策略”不同；不能交换量词和信息到达次序来制造可实现性。动态条件未知不直接取else，跨运行保证不降成每次调用分别通过。

### 精细控制仍在第一层，不变成强制下沉

作者可在一个局部发生点规定实现、布局、目标、资源或输出结构，也可撤去这项控制返回已有委派。它们沿原Control与作用域规则进入同一候选，不复制成第二套程序。明确的业务含义不能由实现控制覆盖，局部覆盖不能撤销独立接受的上层硬要求。

有相同公开保证的多个实现不是“需求不完整”。系统在委派范围选择并固定，只有本次必须由作者决定的独立公开差异才需要说明或询问。固定实现不等于永久锁死：重新优化可以改变实现绑定，但须保持原观察、保证及真实运行责任；原请求要求稳定布局或固定库时也须保持。

一个参数需要完整算法才能定义其含义时，系统可以形成算法/关系的精确作者内容；这不是要求开发者提供目标语言代码。作者主动提供的精确算法本身具有独立价值时必须保留，不能以“高层更好”为由改写其结果、复杂度、顺序或资源要求。

<a id="first-layer-solution-choice"></a>
### 当前方案的取舍：统一作者含义，不统一成一个万能求解器

采用“单一结构作者源＋开放有类型定义＋分域解释/实现方法＋受控创作＋同源编辑”。JSON继续承担准确持久结构，第一层可以直接使用它，也可以使用映射到它的输入视图。系统承担建立下面的表示与实现；这不是一个要求用户顺序完成的五层开发流程。下表比较的是完整产品路线，不把给既有系统添加第三种入口的成本当成对所有替代方案的反证。

| 路线 | 可以保留的价值 | 不能独自承担当前主面及本次裁决 |
|---|---|---|
| 原话直接交给模型生成目标代码 | 新定义解释、实现创作、原生维护和候选发现 | 缺少固定接受含义时，下一次生成容易重新解释旧要求；目标代码不会自动提供原需求、来源或回源。作为受控能力保留，不作为唯一真源。 |
| 普通框架/宿主语言/嵌入式DSL | 成熟类型检查、生态与实际实现；作者主动提供算法时有价值 | 将所有业务作者义务改成编写宿主控制流，不满足本题的第一层；强制宿主表达也会把其值域/效果带成公共默认。作为供给和可选作者区域保留。 |
| 预置业务Block目录与固定流程模板 | 反复出现的准确需求可低成本复用 | 目录不能决定表达上限；未命中时必须继续开放定义，不能要求改中央业务枚举。 |
| 所有目标先转成一个通用逻辑，再让统一求解器找最优实现 | 在明确理论、候选域和证据规则内，适合局部约束、搜索与合成 | 时间、权限、概率、开放观察、运行策略和目标支持各有不同资格；统一公式外形不带来统一可判定性或成本保证。保留有界专业求解，不作为所有任务强制前置。 |
| 每种领域独立作者源，靠脚本互相生成 | 单域工具可以非常成熟 | 同一个对象/硬要求若在多处各自维护会产生竞争写权。保留原生区域和专业适配，不双写同一语义事实。 |
| 单一精确结构源，所有细节都让作者手填 | 容易明确校验对象、定位与修订 | 只是把IR外露，不能降低独立作者工作；采用同一结构，但系统补齐可推导与合法委派的细节。 |
| 本节采用的组合 | 固定含义可重建，已有工具能直接复用，新含义可扩展，局部精确控制仍可达 | 代价是解释、来源、资格与更新机制必须真实实现；没有实测不宣称时间/Token更少，不能承诺任何任务都自动正常完成。 |

选择依据是本次硬要求能否同时保持：第一层可持续创作、独特语义不丢、系统承担下层、成熟成果能复用、固定重建、精细控制、明确权限和第二次修改。只有满足这些条件的方案才进入成本比较。沿既有T/B/I和已接受的比较政策评价实际完整路线；其默认尺度和权重只在原定义适用时使用，不暗中把业务质量、不同主体的权利或硬限制折算为同一分数。

反转条件是具体反例：同等任务和保证下，某成熟作者工具已经完整承担这些责任且适配成本更低，则直接采用其能力；某公共构造丢失独立观察，则修该构造；某中间表示只有重复维护而无消费者，则移除该重复。不能因已有文档投入锁死方案，也不因一次失败否定所有已成立的合同。

<a id="first-layer-denotation-and-realizability"></a>
### 一个要求究竟约束什么：论域、观察与可实现策略

固定一个要求时，系统从原Definition/Requirement、Goal roles、实际Root/Use、解释映像及观察合同中取得：合法输入和环境、责任对象、可观察结果/历史、选择归属、可用信息、必须成立的保证及任务出口。这是对已有字段与引用的联合解释，不新增一个所有作者都要填写的“七元组JSON”。

在适用的经典、无矛盾、含义已经固定的模型内，可用下式表述实现资格：存在同一个获准实现或策略p，使其面对约定环境集合E中的每个环境，都满足硬要求H及进展P，且其决定只依赖在决定时实际可得的观察。E、H、P分别来自实际被接受的合同，不由候选实现自行缩小或改写。统计、概率、跨轨迹及专业规范的要求继续由原专门解释负责，不能全部偷换成单条布尔执行轨迹。

必须分别判断以下性质。关系非空，表示至少有一个数学满足对象；逻辑一致，表示指定逻辑下没有相交矛盾；可实现，要求存在遵守输入/输出时序与信息限制的同一程序/策略；有效构造，要求当前方法能取得该程序；目标支持，要求该程序在所选语言、环境和资源中保持性质；实际采用，则还需真实资格与作用结果。一个无解搜索不证明其余全部不存在，某个满足赋值也不证明有可运行策略。

**见证必须共同。** “有一种实现满足A”与“有一种实现满足B”不能拼成“有一种实现同时满足A和B”。Requirement合取使用同一绑定和同一实现世界；明确的备选保留整支条件及其见证，不能分别从两支挑最便宜的字段拼成第三个未被接受的方案。多个根各自可行，也可能因共同配置、资源或发行要求而不可同时采用。

**选择的时点有含义。** 构建时选择一个长期策略、每次调用在输入后选择结果、在事件到达前先动作、环境自主选择和用户临时选择都不同。原roles/Context、Observation时钟、Workflow依赖、静态参数和Runtime Input共同说明这些关系；缺少相交信息时不能把编译期变量标作运行输入来“解出”方案。离线存在的输入输出关系不自动授权在线观察未来。

**约束不等于任意数据可合并。** 对同一论域、同一主体和同一用途的纯硬约束，组合取共同允许范围；硬要求冲突不得按文件、加载或时间顺序覆盖。这个规则不适用于顺序效果、别名资源、带优先级规范、概率耦合、不同身份对象或并发提交。CUE的格/合一提供了纯约束合并的成熟参考，但其顺序无关结论不能替Gift证明外部作用、时间或授权也顺序无关。[CUE语言规范](https://cuelang.org/docs/reference/spec/)的适用借鉴止于该边界；本设计不新增CUE产品依赖或替换JSON。

<a id="first-layer-assumptions-and-success"></a>
### 假设不能成为消除义务的出口

系统将需要的前提逐项定位到原假设、观察、上游保证、输入合同或环境合同，并保留取得它的责任和用途。没有独立依据的候选自身承诺，不能转成证明该候选正确的环境假设；“在程序没有出错时保证正确”也不满足正常行为义务。

同一目标内相互矛盾的环境假设不能用蕴含前件为假取得整项完成。合法输入确为空时，某项全称性质可以空真，但若任务同时要求至少一个可消费结果、合法调用或实际履行，其进展/存在义务仍未满足。普通源/子模块可以没有运行需求，不为所有定义强造一份非空世界证明；仅对所请求完成声明检查其真实存在/进展前提。

有限纯计算可在固定完整输入上成立；长期运行的前提则可能随观察、权限、容量或外部政策变化。编译时冻结内容不冻结现实。系统依据原控制合同选择：在使用前取得当前证明；在运行中按要求监测并停止不合格的新准入；提供已获准的较弱行为或补偿；确实无法保持时报告相交保证失效。监测只能支持其覆盖的观察，不能替代“违例绝不发生”的预防能力。

异常处理也必须保持正常成功路径。结果类型允许失败，不等于可以让全部合法输入立即失败；资源界要求绑定真实适用输入、工作负载和环境。候选可以证明某一有限支持域，不得将该域私自替换成用户原本要求的更大域。跨主体假设、时钟、失败恢复与已发布承诺变更，继续走原接受/兼容责任，不由一次优化隐含接受。

<a id="first-layer-intent-disambiguation"></a>
### 解释和澄清：减少问题，而不是减少必须保留的区别

先从准确选择、文件、接口、已接受定义及真实上下文取得含义，再用原待问消简算法处理缺省和委派。每个仍不明确的差异都要说清“改变哪个公开观察、适用于哪些输入、谁有权决定”；只是同样合格的内部组织方式不同，不构成必须提问的理由。

系统可以用一个具有区分力的输入/场景展示不同解释。找到反例足以证明两种解释不等价；没找到反例不证明等价，也不允许偷偷选一个涉及独立公开差异的解释。用户已委派的取舍可由系统按原政策作出并固定，不要求人确认每个自动填充字段。没有被委派且会改变法律/业务义务、数据披露、破坏性作用或公共兼容的选择，仍须由其真实权威处理；这里列的是后果类型，不凭关键词自动作安全判断。

主观目标如“更好看”“方便”“公平”也能接纳，不因难量化而丢弃。系统先取得已选风格、示例、使用者、比较维度与可执行接受方式；可形成有出处的候选和明确偏好顺序，不伪造精确评分、唯一形式定义或自动最优证明。例子可以是有限测试、典型意图、禁止反例或全部有限域，其角色须固定；不能把三个例子自动解释为全域规范，也不能把作者明确要求的全部例子降成建议。

缺失项分为没有给出、显式为空、还不知道、可推导、有源默认、已委派、运行时取得和明确不适用。各项仍使用原字段/定义和Need表示；不把它们压成一个null或新增所有Schema都要携带的状态字段。重新取得答案、上下文或基础后要撤掉已经可推导的问题，同时保留仍然独立的差异。

<a id="first-layer-composition-admission"></a>
### 跨领域组合的最小接合责任

公开类型相同只是接合条件之一。每个真实连接还检查实际对象身份和单位、输入条件与输出保证、读写/效果范围、时序与进展、资源和寿命、错误与取消，以及该用途所要求的证据。只激活与此连接相交的责任，不强迫纯值函数建立事务、监控或永久注册。

生产者保证覆盖消费者前提时才可直接接线；只覆盖一部分时，系统可以在获准范围选择有正常成功路径的适配、显式分支或合格实现。更窄的实现输入不能被反向写成更窄的作者输入；少数样本能通过也不证明前提包含。需要单位、坐标、时间、编码或标识映射时，映射必须说明哪些性质保持、哪些损失、适用域和误差；结果同名不代表关系同义。

环的处理归原语义：普通递归保留调用；声明循环由既有链接规则处理；纯单调有限域可由合格固定点方法解释；删除、否定、非单调或现实反馈不能直接沿用旧的单调结论。互相引用的两个保证不能仅凭循环支持成为成立，必须有真实初始支持、保持方法及请求的进展依据。循环求解消耗的预算仍归同一个任务，不能每次补全重置。

跨域误差和资源按真实组合传播。两个局部方法各低于某上限，不意味着并行共享同一资源时总量仍低于上限；两个随机输出各自边际正确，不意味着联合分布正确；两个组件各不披露数据，不意味着共享缓存和时序不可观察。系统必须保持本次独立观察要求，不能把它们变成一个笼统“组合PASS”。

### 第一层的完成条件

一次设计/开发任务的出口由所请求结果决定。作者表达已固定、实现已取得、产物完整、检查适用、已获准保存和真实运行分别成立。设计任务可以止于准确规范；产品生成任务不能以准确规范代替源码和必需资产。

第一层的使用闭环必须允许：提出一个无现成目录项的新需求；系统形成其准确解释；完成首次生成；只在原意图上改变一个独立要求；查看真实影响；由系统更新全部相交下层成果。只有首次解释而没有第二次修改，或者每次修改又要求开发者重填锁、IR和供给表，都不满足本节合同。

规范允许保留准确未知，但不以未知为借口撤销正常成功路径：能从现成内容确定的现在确定，能在授权内取得的由系统取得，能在既定范围创作的由系统形成候选；仅不可由它决定的实际差异、事实或权限交还相应主体。通用表达目标不等于已经存在一个对所有请求都保证成功及最优的实现。


<a id="first-layer-source-simplicity-decision"></a>
### 原生VS Code与真实短源共同作为日常主面

用户的实际宿主是现有VS Code，不是Gift自行发行的开发平台。扩展消费同一作者合同；原生编辑、搜索、导航、差异、终端、SCM、测试与调试继续使用宿主能力。产品界面、状态图和专业预览可以是某个被开发成品或按需辅助投影，不成为另一套全屏开发环境。

本轮选择“JSON稀疏结构作者源＋确定展开＋既有专业语义”，不是只缩进更紧或把长树藏在控件后。机械外壳消除，唯一可推导字段省略，真正重复的定义用精确引用；独立接受、身份、公开接口、单位、时间、默认固定和失效关系仍保留。新短写是明确的编码修订候选，不把现行`/2`文本静默重解释。其完整规则由[结构化源码](紧凑结构与同源编辑.md#vscode-sparse-author-source)拥有，宿主行为由[编辑与客户端](../开发/VSCode原生接合.md#vscode-native-author-surface)拥有。

结构JSON并不具有“相对每一种文本语言都最短”的性质。仅仅表示一个局部算术或布尔表达式时，专门文本语法通常少很多载体字符；这不等于应让所有产品作者退回手写普通实现。现在先保留已选JSON和同一语义体系，去掉不承载区别的重复；复杂实际算法沿原可选计算画像或原生拥有者接合，应用作者未主动承担的实现仍由系统取得。若真实同域任务表明即使复用、推导和稀疏结构后仍不合格，再在现有表示owner按等价能力、持续修改、诊断与生态成本重新裁决，不无限增加晦涩缩写。

<a id="universal-language-claim-boundary"></a>
## 通用性的可检验合同：开放而不缩域，不能用保存或拒绝冒充理解

“通用”在这里要求：已有精确含义可以直接保持；新的业务可用已有定义组合；确有新的公开区别时有明确专业解释接合；同一作者可以持续修改并选择目标。它不等于有一个固定业务菜单，不等于某份Schema能存任意payload，也不等于对每个请求必须返回同一类成功。表达、组合、方法取得、目标保持与实际支持分别有可被反例推翻的出口；不能把原任务改名为“成功保存字符串”来宣称实现。

本轮能论证的具体保持性是：在固定的旧作者解释及其有限合法源域D内，新codec的精确原形分支能表示每个d∈D，且恢复同一个d。专业短写是这个域内有条件的同义表示，不把新编码变成更窄的业务子集。这个语法保持性不证明所有新概念已有解释，也不证明全部程序可自动实现或全域最优；遇到真正新的概念，按下述解释接合处理，而不是抹去其原要求。

### 三种扩展不能混淆

**定义增长。** 新业务、参数化规则、算法、类型与复用块已有构造可表达时，创建正常Definition和Use，不修改中央kind枚举。声明递归通过原SCC/签名规则；运行递归仍是调用，不等于编译期无穷展开。无限流通过有限的生产者、状态与时间/背压合同描述，不要求把无限成员保存成JSON数组。

**专业解释增长。** 只有实际公开区别不能由已选构造保持，才使用原`extension:definition`。它的真实字段仍是`dialectRef/bodySchemaRef/payload/bindingRef`及原允许的qualifiers。精确载荷Schema、名称/绑定环境、类型/效果/资源、组合前提、目标贡献、证据消费、编辑/迁移分别由原方言供应和解释绑定拥有；没有这些资格，载荷只能保全，不能按同名猜义或执行。安装插件、注册Schema与获得执行权限不同。对合法新概念缺某个实现方法，是系统的相交工作，不要求应用作者写宿主补洞。

**表示增长。** 一种更短文本、表格或图只有在能保持同一对象、编辑和错误定位时才是表示选择。它不修改领域含义；按D02与真实成本比较，不以“暂时保留完整结构”证明永远不需要更好的表达，也不为追求短字符串取消精确JSON基线。重复的通用结构应优先抽成可复用定义；各业务独有的信息不能靠重命名消失。

### 跨轨迹、概率、连续域与真实对象不被普通Bool吞掉

设两个执行具有相同公开输入、不同秘密，分别输出不同可见值；每次执行都能通过“输出是合法整数”这一单轨迹检查，但没有保持不泄漏秘密。专业非干扰要求比较**同一已固定系统的可接受执行集合**，固定公开相等、观察者、攻击能力、调度/环境及解密政策，再对相关轨迹作关系判断。单个布尔返回值可以是这种方法的结论，不能代替它的论域；供给方法也不能任取两条方便的轨迹当成全称证明。有限确定模型可逐对检查或用关系不变量，较大域复用合格关系证明/专业方法；模型之外保持准确未知。Hyperproperties研究提供了这类跨执行区别及多种逻辑的成熟依据，不意味着统一采用HyperLTL即可表达所有知识、概率或分支性质。[来源：Finkbeiner 2025](https://arxiv.org/html/2501.08063v1)。

概率保持仍分别处理支撑、边际、联合、条件分布与随机源关系；两次公平输出不能默认共用一个随机位。连续模型、精确实数和数值近似分别绑定表示与误差；表达一个准确关系不表示浮点输出无条件等于它。需要可观察近似时，误差、稳定性、采样/时间和目标工具由已选领域承担；不能静默将“精确”降为“足够接近”。物理装置身份、资源实例及运行状态也不由内容哈希创造。

内部标识符的ASCII文法不限制外部文字和协议键的字节域。`客户编号`、空字符串、斜线和转义字符可以是外部数据；需要带静态字段合同的外部格式时，由原格式/原生映射拥有准确外部名到内部成员的单射绑定及往返。不把替换成ASCII名字当无损映射，也不因同一显示名称就合并两个对象。已有Map/Text或原始资产可以承担其实际范围，但不能用“字节可保存”冒称已经完成带类型的字段适配；缺该适配时具体报告，不擅自向当前Field加未知字段。

### 组合闭包还要保住绑定和实例

模板内的局部变量x，不能捕获使用者提供表达式中的自由x。展开按已解析binder身份替换，必要时α重命名；从相同文本得到相同名字不能证明是同一绑定。类型参数、值参数、作用域/区域参数各守原kind，合法高阶定义保留函数和约束，不通过JSON字符串插值生成程序。普通库与宏的规则都要对应相同性质、来源和重开条件。

同一组件定义引用两次，默认是两个Use发生点；共享资源必须由实际绑定明确。两条连接可在接口类型相同的情况下仍因共用配额、状态或权限耦合；每项真实身份和独立约束继续保留。内容共享和公共函数合并不能自动共享运行实例，反过来也不强迫本来只需一份共享值复制两次。

新要求被现有机制处理，属于正常组合而非新缺陷；已有合同缺乏实现/宿主证据，不自动再发明同义规则。出现改变基础的反例时重算受影响的选择与接受，不只在旧结论后附一个例外。本次采用仍是单源开放语言与专门方法，没有增加世界模型数据库或第二求解内核。


<a id="business-intent-party-world-closure"></a>
## 业务通用性：参与者、承诺、现实作用和观察必须共同进入含义

当前作者层不是“把所有业务都编码成纯函数”或“以一张行业表决定支持范围”。既有纯关系、状态/协议、规范、资源、连续/概率及专业解释各有职责。本节补齐它们在多方业务中最容易被遗漏的接合：谁表达目标、谁承担义务、谁能执行、谁取得结果、谁能证明结果，以及变化从哪一时点生效。它们可以是不同主体；系统只在真实需求相交时取得这些信息，不向普通纯函数增加角色问卷。

**表达的开放性与完成的资格分别保证。** 新业务可成为普通Definition及有类型组合，不因没有行业目录项而被语言拒收；无法由已选构造保持的新公开区别进入原专业解释责任，系统负责形成准确规则和消费者。支持不足不能靠原生透传、保存任意payload或全部拒绝伪装成理解，但没有实际证据也不能自称完整实现。每个进入原任务的独立要求必须有真实定义/绑定/消费者，或保留准确残余；同一对象上的矛盾要求不通过改换对象偷偷消失。

### 多方意图不是一个隐含的统一利益主体

发起开发的人可以有权修改产品源码，却未必有权代表最终使用者、资源所有者、数据主体或外部提供者接受义务。产品的“希望某人做什么”、该人的规范义务、该人已经接受、系统有权发送请求及行为真的发生，分别由现有Goal、Norm/Policy、接受关系、Grant和实际观察承担。人名、组织名、Actor字段或一个根目录都不授予这些权力。

系统先固定参与的实际范围及已有权威关系，再判断共同硬要求；没有权威基础的来函只是资料，不能制造合同。对已成立的多方义务，不以发起者的偏好删除他方保证；对真实谈判中的备选，可以保留不同参与者的条件、反对和接受位置。没有实际相交利益时不推造一个委员会，也不把任意第三方都加入每个纯计算。

两种不同的“冲突”尤其要分开。A要求同一交付结果x、B要求互斥结果y，是共同要求或接受范围的问题；A偏好x、B偏好y，却都接受二者，是比较政策问题。后一种仍有正常交付路径，不能误报不可实现。将多方偏好合成为一个权重向量，必须来自被接受的比较政策，不默认平均、按加载顺序或按模型自选权重。

一个完整有限反例：甲偏好x>y>z，乙偏好y>z>x，丙偏好z>x>y；逐对多数得到x>y、y>z、z>x，没有多数关系下压倒所有其余方案的唯一赢家。系统可在授权内采用已接受的轮转、抽签、优先级、协商或其他明确规则，但不能把选出的结果描述成“所有人都认为最佳”。改变议程、拆分身份、虚报偏好或增加候选可能影响具体机制；若任务要求抗操纵或激励性质，必须成为独立Claim及其信息/行为假设，而非由类型正确推出。

对私人偏好，服务可以在真实权限内使用它，但公共解释不能暴露个人内容、未公开候选数量或私有约束。没有合格的保密决策途径时保留依赖缺口；不能为了形成漂亮的统一目标而复制秘密到作者源。

### 规范生效、事实发生、观察到达和此次判断不是同一时刻

一个预留请求可按旧政策被接受，随后政策升级，旧回执再迟到。新规则不能倒改已经发生的接受或物理作用。源修订、规则生效范围、动作发生顺序、实际观察时刻及当前权限分别绑定；这里只消费原时间/来源/Operation合同，不新增一种所有文件都要携带的时间信封。

政策变化至少区分对新申请生效、对尚未被接受请求重判、对现存对象显式迁移、对先前事实追加新判断和有权追溯规则。默认不是把旧状态强行改成当前源码期望。新硬约束确需影响旧业务时，系统生成迁移、接管、补偿或停止新准入的方案，说明受影响主体和不可逆部分；不能把它伪装成格式化或缓存刷新。

补偿与原操作互为不同事件。释放未使用的预留可以恢复配额；已经消费的资产、已发送消息、已公开数据或已做物理加工，不能因后来增加一条反向记录而成为“从未发生”。补偿可建立新的义务、费用、权限和失败路径；应实际满足原任务允许的恢复定义，不偷换全局回滚。

违反禁止后履行补救义务，也不自动证明从未违反。当前规范已区分permit/deny/oblige与实际行为；本节把违例、补救、解除和剩余责任接回原条款。ODRL的Permission、Prohibition、Duty及consequence/remedy是成熟的区别参照，不把ODRL文字或本设计自动当成宿主权限或法律事实。[ODRL 2.2](https://www.w3.org/TR/odrl-model/)

### 目标涉及“使某结果发生”时，相关性不能替代因果

预测一个结果、用某动作改变结果、解释若当时采取另一动作会怎样，分别是不同Meaning及其资料资格，不能都变成“输出同一个概率”。已有仿真/实验规范继续拥有模型、观测、干预和累计风险；此处不建立新因果数据库，也不要求每个普通应用都有完整世界模型。

可复算的有限反例：U是等概率的0/1。模型M1规定X=U、Y=X；模型M2规定X=U、Y=U。两模型的所有观测分布相同：只有(0,0)、(1,1)，各占一半。但主动把X设为1后，M1中Y必为1，M2中Y仍各占一半。对原本观察到X=0,Y=0的对象，反事实改变X也会分别得到Y=1和Y=0。因此相同数据和同样准确的预测，不能决定行动效果。

系统保留真实结构假设、适用总体、可干预变量及取得依据；已有模型足够时使用合格因果方法，资料只支持观察时交付观察结论和可核候选解释，不把缺识别性冒充没有任何有用信息。新实验涉及现实作用时仍受原准入和预算控制。作者要求“提高完成率”等目标时，系统不能只找到一个与完成率相关的字段就将它改高并宣称实现。

### 主观、创作和探索意图也有正常的准确出口

“更有趣”“符合我们的风格”“先探索三种不同方向”不因没有唯一数值函数而被语言排除。系统可固定真实参考、使用者/评议主体、必要差异、不可接受反例、此次交付集合和已有委派，形成可继续修改的候选。没有额外产品需求时不建设评分平台；单主体的明确选择可以直接完成对应的接受动作。

区别在于完成声明：交付三种满足硬条件的候选、被指定主体在给定版本接受、在某调查样本中更偏好，以及所有未来人群都会更喜欢，是四种不同结论。前几种可正常完成，最后一种不能借示例/代理评分代签。后继偏好改变时形成新接受与版本关系，不将旧评价改成当时未发生。系统可以解释或试验，不让应用作者被迫先写一份万能审美算法。

### 复用业务机制而不偷换其计量与对象

预留、确认、释放可复用于名额、库存、许可次数和若干作业配额，但不是所有东西都应被转成一个整数余额。同种可替代单位才可求和；独特座位/设备用真实集合与互斥身份；带时段的预约还需区间重叠；多币种、温度、像素、概率和人员权利不能直接相加。下文的精确整数库只承诺一个固定pool/epoch的有限可替代单位，扩展时保持原单位、对象、时间和作用含义，而不是改几个显示名就宣布覆盖新领域。

收益目标与业务硬保证也不能互相抵消。重复投递去重、配额守恒、选择公平、隐私和及时性各有自己的观察；单一业务KPI上涨不证明这些条件成立。需要适应或学习的策略，仍在原允许动作/信息/预算内运行；越过原承诺时是新要求或新资格，不是普通自动优化。


<a id="observation-completion-and-intent"></a>
## 不完整观察与持续意图：范围可以开放，结论必须有实际依据

已有Goal公式、四态证据、关系反连接和流Frontier已区分未知与否定。本节不重建它们，也不将全部业务转成知识库；补充的是这些机制进入第一层数量/存在/不存在要求、后继更正及现实作用时必须共同满足的接合。日常作者表达“至少三项”“全部通过”“没有匹配项”即可；系统从原Source/Observation/Domain/Meaning/Claim取得范围与依据，不要求用户填一套完备性表。

### 所见为空、可见域为空和所求域为空分别成立

需要固定的不是抽象“全世界是否已知”，而是这次量词的准确论域、谓词、对象相等、时间范围和所消费修订。例如“我的查询没有匹配”可能只涉及已取得页面、我的可见记录、某一快照的所有记录，或某时间窗内的所有真实事件。四个域不同，结果不能借相同文字互换。缺权限、截断、超时、源失败、解析失败与准确空结果分别保留；禁止以过滤掉失败分区、忽略不可读取对象取得一个看似完备的空集合。

没有观察到P，不等于有证据证明非P；也不能反过来要求任何结论都必须先知道整个域。已经有相应范围的可靠见证时，存在性与部分数量下界可以成立；全称真、存在性假、精确计数等依赖的覆盖通常更强。固定且已完整捕获的有限作者值保持普通闭世界计算路径，真实开放资料按其实际覆盖解释。W3C OWL 2 Primer明确区分缺失事实与否定；这里借鉴这个区别，不采用OWL作为Gift必需引擎，也不把它的全部逻辑默认搬进本语言。[原始说明](https://www.w3.org/TR/owl2-primer/)

### 同一需求的精确判断与保守近似分开

对固定解释、对象与观察切面，可用与这些合格信息相容的完整候选世界集合W说明判断意义。只有W非空且该性质对W内所有候选成立，才能获得相应的必然结论；全部候选违反时获得对应反证；两种均有时仍未定。实际算法可以使用更小的专门模型、界或已有定理，不要求枚举世界，也不新增可写WorldModel数据库。前提不相容导致W为空，不能用全称空真同时批准性质及其否定；按原冲突/解释缺项处理。

本包的有限计数画像使用整数区间[L,U]，或缺有限上界的[L,∞)作**可能总数的保守包络**，L非负、有限U不小于L。∞只是数学记号，实际源用Unbounded(unit)，不是JSON非有限数。它不表示现实本身已经有无限条记录；所选有限快照可以有任意大但有限的基数。有效性只要求真实总数在这个包络内；包络内每个数未必都现实可实现。

| 要求，k为非负整数 | 包络能保证成立 | 包络能保证违反 | 其余 |
|---|---|---|---|
| N≥k | L≥k | U有限且U<k | 未定 |
| N≤k | U有限且U≤k | L>k | 未定 |
| N=k | U有限且L=U=k | k<L，或U有限且k>U | 未定 |

这些条件对所声明的连续整数区间模型是完备判定，对更复杂真实候选域只是健全近似。例如实际可能数仅为{0,2}，包络[0,2]对N=1返回未定，但更精确专业方法可以证明它不成立；不能把包络的精度缺额说成原语义无法表达。反之，获得一个样本值不允许将包络缩成那个单点。

源中给出AllSatisfy、AllViolate、Undetermined、InvalidInput四个**本库的普通业务变体**，分别描述该纯查询的结果。它们不是旧T/F/BOTH/NEITHER的别名，不新增全局状态词表。正确返回Undetermined可以完成“判断这些范围支持什么”的查询，但不能完成“保证业务数量达到阈值”的独立要求。任何结果都不能直接签发HostGrant。

### 一项新观察到底是在缩小未知，还是纠正旧依据

同一语义和固定论域中，以合格信息把非空包络缩小，已成立的必然结论不会反转；这是集合包含关系的直接结果。但撤回旧记录、纠正重复身份、发现错时钟/错分区、改变统计范围、更新比较含义，都可能使新候选集合不再是旧集合的子集。此时不得沿用“信息只会更多”的单调假设。旧结果保留为对旧切面的真实历史，当前结论沿相交依赖失效并重算。

至少三条稳定见证可以提前支持N≥3；如果所谓三条后来被发现是同一条的三次投递，则原下界从来没有相应资格。若旧判断只对当时已固定快照作出，它仍可以作为历史查询记录；若旧物理观察被反证，其真实性评价须修订。历史记录不删除，不等于继续保留原合格状态。

长期保证还需声明追加、删除、更正与身份修订的允许范围。关闭一个事件时间窗口，只能关闭其已选协议所保证的域；不自动禁止以后对该窗口作合法更正。新政策适用范围与原事实更正也不同，不能用新政策将旧动作改判为当时未发生。

### 相等关系是业务含义的一部分，不是通用去重按钮

复用既有ValueOps、名义类型与源身份规则。值相等、同一业务实体、同一次输入出现、相同原文字节、标准化键相等和近似相似必须各用真实关系；它们不能因为结果都是Bool就互换。两个源各报告三条，联合唯一对象数未必为六：对象可能完全重叠、部分重叠或确实互斥，需要相应身份/不重叠依据。

相似关系也未必是等价关系。实数上的|x−y|≤1满足0与0.75相似、0.75与1.5相似，但0与1.5不相似。不能拿它作为去重字典的equal。连通分量聚类、代表点范围和全对距离约束是三个不同要求；有合格定义时都可正常完成，不默认按输入顺序选一个代表就称含义相同。

字符的标准化同样有准确用途。NFKC会把①与1折到同一结果，原字节和一些文字意义区别随之丢失；这种键可以按明确政策用于特定查找，却不能默认重写所有作者原文、签名输入或外部协议键。Unicode规范明确提醒兼容正规化不应盲用于任意文字。[UAX #15](https://unicode.org/reports/tr15/)。采用标准化键时仍保留原件及代表选择的规则；两键冲突需要实际裁决，不以“标准化后相同”证明是同一个现实主体。

### 第一层升级必须说明对谁兼容

保留已有兼容迁移owner的保证，进一步明确方向：对旧消费者替换提供者时，旧允许输入必须仍被新提供者接受；在这些输入及原环境下，新结果必须满足旧公开保证，且不能增加未获接受的效果、资源、权限或时序前提。源文本更短、方法签名相同或版本名更高，均不签发这项关系。

回调方向会反转普通输入直觉：原服务只以0..10调用用户回调，新服务改为可传20，即便顶层输入范围不变，也可能破坏仅承诺处理0..10的旧回调。新增输出字段可能被严格旧解码器拒绝；新增返回变体可能破坏穷尽match。若旧协议明确接受开放字段/未知变体，则按该范围取得兼容，不一概拒绝扩展。修改“至少k”为“恰好k”是新需求，不因为参数/结果类型不变就自动替换所有已发布消费者。


<a id="audited-expression-convergence"></a>
## 表达审计的统一采用结果

本次26项按原含义分流，不把所有缺项都改写成“缺方法”。旧规则与精确名称由源码拥有者补齐；已有参数/查询/缺省能力采用确定短写；策略、知识、类型、概率、规范等需要专业解释时，使用原extension边界给出完整输入、语义和消费者。具体而非同义的规则唯一维护在本包[表达收敛合同](../../schema/author/first-layer/SEMANTICS.md)，逐项范围见[本次设计裁决](表达范围与专业接合.md)。这里不增加一份永久U台账。

统一的是可持续作者身份、要求、来源、组合与修改，不是让四态证据、经典逻辑、稳定默认否定和概率强制相同。需要不同逻辑时在准确Use固定其解释；不从相同JSON字段名推等义。原27种分派不能充当所有未来机制的封闭目录。专业画像的定义由系统/专业库承担，应用作者仍可只引用公开需求；复杂概念的真实成本不能靠隐藏空Meaning转嫁或掩盖。

指定反例的设计可以关闭，但不能从“本轮没有新反例”推出所有未来意图已穷尽。完整声明、可求解、可在目标保持、有权作用与现场证据分别成立。


## 专业含义的实际采用：声明不等于完成

已有专业模型现在可通过[model-contract](../../schema/author/first-layer/SEMANTICS.md#model-contract-use)成为原Rule声明，再由真实req:composite在同一service上require。应用作者表达的是“始终存在恢复路径”或“最终必然恢复”，而不是填写图映射或证明记录。模型本身真/假不决定一个尚未选择的产品是否满足；规范图可为实现选择保留自由度，候选仍须同时履行全部独立承诺。

共享源与共享计算不合并独立要求，同一主体也不能为不同条款偷偷替换成不同候选。改要求、换实现、资料更新和撤权沿各自真实责任发生；准确设计不因此授予安装、运行或业务权限。新require消费者并非新的产品根已经生成。
