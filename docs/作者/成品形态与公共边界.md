# 作者成果与成品边界

本篇拥有“开发完成后作者维护什么、消费者取得什么、哪些内容由工具派生”的共同合同。它不增加万能产品类型、专属运行容器、作者语言或新的工程清单。结构写法由[结构化源码](结构化源码.md)拥有，产物封存由[目标成员](../编译/目标/成员布局与完整产物.md)拥有；本文给两端共同的判定和使用方式。

## 1. 先看独立决定，不按源码后缀判断抽象层次

作者成果的合格标准不是文件短、节点少或使用了多少高级术语，而是：独特的可观察决定只维护一次；普通复用不迫使调用者读私有实现；新行为可以组合或局部扩展；失败能定位到实际缺项；目标交付仍可被独立消费者使用。所选目标根、保证和真实依赖同等时，才比较作者负担。

同一成熟定义在别的语言中也可以一行调用。SEC的差异必须由保持语义的目标选择、局部变更、完整资产和可取得的解释证明，不能拿自己的短调用与别人从零造库的成本对比。任何新管理对象、转发层、语法或文件都必须有当前消费者；强保证所需的快照、边界校验和恢复成本也不能藏到“自动”后面。

对本体系采用以下判断，而不假设所有优秀开发者有同一种偏好：

| 检查对象 | 当前选择 | 会改变选择的条件 |
|---|---|---|
| 层次与耦合 | 同一变化原因和不变量由一个拥有者维护；私有细节不升成所有调用方参数 | 边界确有独立发布、替换、信任或资源责任时才拆分 |
| 默认与自由 | 无歧义、固定且公开的值可省略；硬条件、权限和未知不能被默认填造 | 某个默认实际影响独立接受要求时，固定该决定或报告冲突 |
| 小任务 | 可使用固定上下文中的单定义或导入根，不强制项目、账号、守护进程和数据库 | 持久复用、分发、长任务或真实恢复要求出现才增加相应资产 |
| 错误与退出 | 允许保存未完成作者源；返回准确缺额和受影响根，不制造空实现 | 请求明确要求全部根完成时，不能把局部成功作为共同发行 |
| 工具与工程 | 优先复用真实库、框架和工具，独特差额才生成 | 许可、表示、效果或部署条件不相容时改选，不用包名代替检查 |
| 性能与维护 | 保持未变来源和公共输出，按实际读集重算；无证据不因“优化”重排全工程 | 实测瓶颈或真实依赖变化需要扩大重算或更换布局 |

这些不是用户额外必须填写的质量表，也不是“顶级开发者一致认可”的经验证据。它们是可用具体反例推翻的设计取舍。

## 2. 作者成果有三种实际情形，而不是三个互斥项目类型

**完整复用。** 已有公开定义、原生库或成熟总成满足要求，工程可以只有准确引用、输出选择和必要配置。允许直接输出导入根或重导出，不要求一个无意义的自有主体。完整依赖仍可取得、可解释、许可允许；短引用不是实现已取得的证明。

**只写差额。** 行为已足够，只需改变参数、公开名、输入输出边界或目标形式，作者只维护这个差额。一个导出重命名不强制生成运行转发函数；编码、资源和错误不同则确有适配责任，不能当成零成本的箭头。

**新行为。** 现有关系和规则能表达时，作者写结果、状态、连接、保持和进展条件，由供给侧组合或创作实现。现有含义表达不了的新观察先扩充所属语义合同；不把任意字符串登记为已支持。作者明确要研究算法、接管实现或维护原生代码时，仍可使用对应程序表示，但不是创建产品的强制补洞。

三种情形可以同时出现在一个工程。定义包、计算库、应用、插件和部署组合不应被目录名强行分成互不相通的系统。

## 3. 必须分开的四个公共边界

| 边界 | 真实拥有者 | 不能自动推出 |
|---|---|---|
| 作者模块的公开定义 | `sec.author-module/1.exports` | 该定义立即成为运行函数、远程端点或外部写权 |
| 需求定义公开的逻辑主体 | 复合定义的`exposes`或已固定画像中的准确映射 | 主体已构造、一个主体等于一个进程、全部私有成员可被访问 |
| 目标程序的调用/交互接口 | 所选需求、实现方法与目标画像共同确定 | 相同参数类型就有相同错误、顺序、资源或保密保证 |
| 发行包及宿主依赖 | Artifact成员与导入要求 | 文件存在就已安装、库必须自带宿主或动态安装所有依赖 |

结构化作者的公开定义名、`exposes`中的槽名和目标符号名可以有明确映射，但不是默认相同。显示标签不是它们的身份。导出一个需求定义仍然可以只是分发规格，完全不要求存在目标运行函数。

可复用组件的外部依赖分为**保留给调用者满足的公开导入**和**本次交付应内部解决的依赖**。库留下有合同的宿主进口可以是完整库，不是未完成应用；请求独立运行应用时，必需进口必须真实提供或明确成为部署前提，不能作为隐蔽TODO留下。选定目标不是某个环境包名的同义词。

WIT的world区分组件提供的接口与所需进口，同时明确接口并不定义内部行为。SEC借用这种边界分离，不采用WIT作为作者语言，也不以接口吻合替代自己的行为、资源与证据义务。出处见[成品合同的外部校准](../依据/来源/表示编辑与协议.md#deliverable-boundary-sources)。

## 4. 形态由多个正交选择确定，不是一个万能mode

应分别确定：本次交付对象（定义、实现、配置、资源、数据或组合）；消费方式（链接、调用、启动、加载、交互或安装）；目标语言/平台；公开边界；生命周期；依赖封闭程度；观察与证据范围。已有项目、根和目标画像保存相交信息；不增加每个产品都必须填满的七列表或第三工程文件。

一个定义可以产生多个目标变体；一个发行也可以包含库、CLI、文档与资源。反过来，同一语义根的两个目标不必共享同一种物理布局。按消费者的真实属性及合同选择，不从`lib/desktop/fast`名字猜；没有唯一合格绑定就给选择或能力缺额，而不是按文件顺序决定。

### 当前已展开的成品家族

下表是按真实消费边界组织的设计路由，不是核心枚举、已实现能力清单或所有软件的封闭全集。各行保留自己的完成与失败条件。

| 成品 | 作者真正维护的内容 | 必须交付的边界与成员 | 不能算完成的情况；独立故障/恢复 |
|---|---|---|---|
| 可复用需求、策略或模型包 | 参数、主体、关系、公开定义与接受条件 | 可解析出口、定义及所需解释；必要依赖锁 | 没有目标实现仍可完成规格分发；不能标成可运行应用 |
| 纯值、配置或静态资源结果 | 精确值/关系、格式及消费者条件 | 所需字节、单位、编码和来源 | 类型合法不证明业务值适合；旧值与新值切换按真实消费者完成 |
| 表达式/函数或上下文补丁 | 独特行为、环境及插入约束 | 完整所选语法单位与必要导入；准确目标前像 | 脱离外层控制、捕获或ABI即失去等义资格；冲突保留草稿 |
| 库、SDK或协议客户端 | 公开行为、类型、错误、资源与可保留的宿主进口 | 调用入口、类型、实现与准确依赖；公开文档 | 只有声明文件无实现不满足可用库；不强生main、服务和数据库 |
| CLI或一次性批任务 | 输入协议、编码、输出、退出和取消 | 程序入口、依赖、必要帮助和资源 | 输出中途断裂不能报完整；执行副作用的重试须有独立依据 |
| 长时服务或请求处理器 | 协议、并发、隔离、状态及健康/结束条件 | 处理入口；需要自托管才含监听/生命周期 | 有handler不等于已监听；取消一个请求不关闭共享服务 |
| 工作器、嵌入组件或插件 | 宿主接口、能力需求、实例寿命、贡献与卸载 | 加载入口、版本合同、实际实现、清理 | 入口同形不证明宿主合格；不默认建商店、账号、全局注册服务 |
| Web/桌面/移动交互产品 | 视图、状态、事件、资源与可访问性及平台条件 | 真实界面、消息、资源、入口和交互行为 | 只有后端接口或静态截图不算；旧异步结果不得覆盖新输入 |
| 多应用与产品族 | 共享定义、独立主体、变体及共同发行约束 | 各根和共享成员、每个目标的完整结果 | 一个根成功不代签全族；共用状态或互斥版本须联合处理 |
| 查询、批数据与持续流 | 数据域、关系、顺序、窗口、迟到与丢失政策 | 执行计划、必要算子/连接、输入输出合同 | 有限批证明不代签无限流；检查点/重放必须保持外部效果 |
| 数据或配置迁移 | 源/目标版本关系、保持量、拒绝/回填条件 | 完整迁移方案、校验及所需工具 | 幂等与可逆分别说明；回退代码不自动回退已变数据 |
| 编译器、分析器及生成器 | 输入语义、变换、目标与诊断 | 合格阶段/库、实际工具入口和资源 | 能打印不等于保持；生成环必须有真实种子与前置 |
| 模型、概率或优化组件 | 分布、损失、候选域、误差、模型/数据绑定 | 算法/权重/数据及实际评估与运行条件 | 一份样本不证实分布保证；缺权重/不允许取得不得报完整 |
| GPU、设备核、固件或实时目标 | 数值、布局、时钟、截止、资源与外设合同 | 核/镜像、启动/装载与真实接口 | 代码生成不等于刷写或满足硬时限；停止与安全状态单独设计 |
| 安装包、发布束或部署组合 | 成员、兼容、环境、健康、配置及秘密引用 | 完整可分发成员和部署前提 | 包签发不等于目标采用；未知安装结果沿原操作查回 |
| 被选择的现有工程变化 | 精确修改及必须保持的外部行为/区域 | 可审阅候选、按任务生成的完整相交产物 | 逆向不是其他成品的前提；未知区域不自动重写或清理 |

小范围先实现可用，不因表中其他家族未有实际方法而阻塞。不支持的领域必须有明确缺额，不能生成名叫该形态的空目录。

## 5. 作者配置不是实现自我证明

“接收有限精确整数并规范化区间”是行为；“公开同步函数”与“作为HTTP处理器”是不同公共消费边界；“用排序扫描还是树”通常是实现自由；“用户点运行”是实际开发动作。不能把这四者统统写成一个`mode`然后由字符串猜语义。

标准组合可以提供默认策略；应用只写差异。默认选择需要在定义处有准确值与来源，不从环境、历史回话或求解失败处补造。明确原值和沿默认得到原值的行为当时可能相同，但再次升级时的选择来源不同，仍由工具保留。

需求中同时出现多个允许交付形式，表示多候选；实际选择两份独立产物则形成两个输出，不能偷换。自动选择可以在已委派的等义候选内进行；公开协议、宿主能力或运维责任不同，不因实现成本低就静默切换。

## 6. 编译器交付一个最小且完整的消费边界

原P0—P7按本次目标确定哪些内容必须闭合。A0取目标根及公开边界；A1收集相交行为与公开进口；A2选择真实供给和宿主画像；A3消解内部进口、保留明确允许的公共进口；A4生成最小适配与成员；A5分别检查行为、目标、资产与依赖；A6封存所选根；A7仅在请求时进行保存、运行和交付。阶段可以复用或融合，不形成新的强制工具流程。

输出至少能被回答：哪个入口可被谁调用；输入/输出和故障是什么；初始化及退出由谁承担；哪些依赖交给消费环境；哪些文件与符号是公开的；不满足什么会失去资格。它们来自真实合同、目标与成员，不要求作者重复填一份结果表。

若既有函数已经完全满足公开接口，直接导入或重导出；只在编码、错误、初始化、隔离、ABI或稳定公共门面确有差额时生成适配。转发函数本身不是安全边界。跨独占资源、时钟、错误顺序和共享状态的适配要有真实方法，不能只画一条线。

改变一种交付不应重新创造业务算法。新的CLI适配只重核I/O、依赖和目标；共同的关系规则改变才重核全部消费根。检查工具配置、运行环境或假设变化也属于真实依赖，不因正文“看起来没变”而复用旧结果。

## 7. 面向使用者的四个视图与再次修改

**作者视图**显示公开定义、当前参数、共享主体和独特决定；**解释视图**可下钻完整关系、来源、继承默认与固定选择；**实现视图**显示实际供给、适配、产物和剩余进口；**运行视图**绑定真实制品、参数、状态和未结算责任。四者不是四份可写模型，已知操作可直接修改唯一源。

修改默认不改写锁定旧定义的消费者；只有采用新定义、且未显式固定该值的使用点继承新默认。改公开接口：检查名字、类型、错误、资源、时序、数据及消费方，不以返回类型相同代替兼容。只改私有算法：公开调用不变；内联或生成依赖仍更新。源码合法却缺目标：交付准确作者成果和缺额，不把错误推回作者要求其写整套底层实现。

版本升级、下钻与回源是产品能力。当前这套设计文档只维护融合后的规范，不保留历轮链接、修订树或新的作者过程台账。

## 8. 具体范本与当前边界

[一项关系的多种成品](../../examples/成品形态/README.md)给出共享区间行为及库、CLI、工作器、HTTP处理器、插件、交互面板和共同发行的完整结构JSON；每个已使用规则均有字段、正常/失败、资源和方法合同。完整工作台仍由[原范本](../../examples/结构化工作台/README.md)承担，两者不互相取代。

本篇是共同边界，不以家族表代替细节。原16个家族分别由[成品详解](成品/README.md)中的36个确定选择承担，其作者源、默认、公开接口、正常和失败行为、生命周期、资源、最小成员、方法和验收必须共同成立。设备ABI、复杂异步资源、分布式时间、开放模型和全IDE语义仍沿原领域逐项设计，不用一张路由表宣布全部闭合。真实实现、端到端性能和可用性需要各自验证；目录、JSON和接口名称不作为产品运行证据。

## 作者载体不是成品消费形式

同一结构意图可以由已有原生库满足，也可以由选定中立计算实现降低。一个原生源码工程同样可以直接交付库或CLI，不先登记全局意图镜像。是否采用结构表示，取决于本任务需要维护的独立关系、实现选择和持续修改收益，而不是输出文件数量。

JSON保存什么，与最终给消费者什么是两个问题。产品作者不必手写目标适配，但系统必须交付实际差额；普通源码原本已满足要求时允许零新增适配。`.sec`计算语义只在被选中使用时成为依赖，其存在不提高所有项目的入门门槛。表示选择、原生接合和退出机制分别见[作者表示](可替换表示与适用范围.md#作者载体实现供给与原生工程的选择)与[混合接合](../开发/原生维护/导入观察与原生资产.md#mixed-author-supply)。

## 原生供给与性能后继

产品作者保存独立决定；已有原生源码满足要求就直接采用，不复制同义.sec体。多种实现形式与高性能后继按[实现供给与替换](../架构/实现供给与替换.md)统一资格；新目标只扩大相交能力，缺实现不能倒逼产品作者手写全栈。同步接口、错误、精度、寿命和公开进口不得被“更快”的方法静默改变。

## 同一作者要求与局部性能供给

本产品的完整输入域不因某原生方法只能接收窄整数、某设备只支持固定shape而自动缩小。编译器可在合格的[条件组合](../编译/有条件实现与公共行为保持.md)中选择专用与通用分支，作者不新增分派文件。公开同步、错误、隐私、资源和成品依赖必须共同保持；无法满足则保留准确缺项而不改要求。

库、工作器和面板可以采用不同实际方法，仍共享同一行为定义。普通已有源码和成熟实现继续直接使用；引用名不是代码已存在的证明，也不要求为每个原生算法再写一份.sec。完整路径见[局部实现替换范本](../../examples/连续开发/局部实现替换与成品接合.md)。


## 设计完整不能被结构合法代替

一个成品名字、字段目录或Interface并不闭合原意图。对已选择的交付，应能直接找到完整定义、全部独特参数、真实输入/输出/错误、正常可进展路径、关闭/恢复、依赖与资产以及实现保持责任。可按产品家庭组合这些定义，不需手填展开计划；缺项应回到确切拥有者完成，而不是循环返回“以后有插件”。[字段与数据](成品/共同数据与完整性.md)、[具体作者源](../../examples/开发成品/README.md)及[目标发射](../编译/目标/成品消费合同与发射.md)共同承担这条交接。
