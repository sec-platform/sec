# 紧凑结构与同源编辑

> 设计候选；与既有规范共用作者身份、语义与执行责任。生产实现与正式采用分别取证。

<a id="first-layer-source-and-editing"></a>
## 第一层的持久源、输入视图与无损编辑

[第一层作者合同](第一层语言.md#first-layer-author-language)不引入第二套作者语义、顶层工具、意图数据库或必须实施的文本DSL。本轮明确修订的是同一作者语言的日常结构编码：采用下文[稀疏短写设计](#vscode-sparse-author-source)，不把完整节点外壳当作者负担。现行`/2`及未经授权迁移的旧作者源仍按准确旧解释保全，不能宣称旧Reader已支持新拼写。Goal/Requirement/Pattern及专业含义继续由原owner承担，展开只读且可重建，不另存一份可写长源。

### 作者输入、作者含义与派生物分开

允许直接编辑准确结构源，也允许用户通过自然语言、结构字段或图中对象提出一个变更。输入视图本身不成为与正式源竞争的另一真源。尚未解释的原文留在原Task/来源；解释完成后的独立作者含义经真实接受关系进入同一Definition/Requirement/Control。原文是来源，不得在每次固定重建时重新作为隐式程序执行。

系统自动填充模块身份、局部标识符、导入/导出、准确引用、类型化值和明确可推导结构。名称和格式字段由系统形成不等于其携带的语义获准：新增公开约束、默认业务行为或有后果的选择仍必须由原委派或接受关系覆盖。源是谁敲出的，与其语义写权归谁，不是同一个问题。

**经接受而由系统形成的意图文件属于作者源。** 它不能仅因字节由生成器写出就进入不可编辑的generated sourceScope。由它进一步生成的IR、实现计划、锁定结果、目标程序和来源图才按各自派生/作用责任维护；原生实现被用户真实接管时才转移相应写权。项目Schema对generated范围的限制继续成立，不通过修改其枚举来掩盖归属错误。

### 字段如何出现，如何不再要求重复维护

| 已有结构中的内容 | 初次由谁形成 | 下一次修改的规则 |
|---|---|---|
| moduleId、Definition ID、条款ID | workspace/作者物化过程；已有身份优先保留 | 改显示名、排序或文件位置不凭空换身份；复制实例与修改定义分开 |
| imports、exports与Ref | 由准确所用定义及公开范围生成，可接受作者显式选择 | 不使用全局latest或搜索顺序；实际发布出口有独立后果 |
| roles/typeRef/基数 | 来自真实输入域、绑定与合格推导 | 唯一可推导时不问；不同单位、身份或集合含义保留冲突 |
| clauses及独立Requirement | 作者意义或获委派解释产生 | 改这一处意义；不另外修改实现副本来掩盖旧承诺 |
| 常量、默认和局部控制 | 只有独立决定保存在相应唯一源 | 推导常量不另设可写副本；null、缺省、reset及动态输入不混用 |
| Meaning/Pattern公共合同 | 直接引用已有内容，或由系统创作新的准确内容 | 接受后固定解释；语义升级是明确变更，不是读取器自动换义 |
| 检查主体、方法绑定、IR与目标映射 | compiler/assurance派生 | 普通作者修改不要求手动同步；旧证据只在仍适用时复用 |
| Grant、secret引用及现实观察 | 原受信权限/资料提供者 | 不从JSON填值或规范permit产生；当前资格另核 |

`authorNotes`及任意annotations不承载会改变执行含义的隐藏程序。已有正式字段无法表达的独立信息须进入相应真实定义或未解释来源，不能把它塞入自由文本后仍声称严格读取器能够确定重建。

### 同源编辑投影的准确合同

第一层视图是当前候选上有来源和权限范围的投影，不是另一棵可单独发布的树。复用原SourceRef、candidateRef、语义编辑及返回槽；不增加公开EditProjection协议或持久字段。本节的操作记法仅描述这些既有责任。

读取视图时，固定候选、解释、所选对象及可披露范围，返回当前可改的独立含义、继承/推导的来源与真实未决。隐藏内部导入、长类型或派生节点不删除其信息，也不把它们计作已经节省的作者维护成本；需要人工维护的独特定义仍属于真实负担。

回写按以下顺序执行：绑定原candidate及对象身份；解释用户此次差异；取得相交保持项；将差异翻译成原source/files/edits或已协商的结构变化；共同补齐必要声明、导入及引用；形成同一新候选；核对结果的公开含义及未选区域；最后按当前任务选择预览、检查或保存。首次创建不依赖预先存在的Facet，完整新源可走原files分支；`intent-action`仅在其Facet已经准确提供时使用。

必须满足以下有限保持条件，不承诺任意自然语言或任意原生源码均有可计算逆变换：

- **无变化保持。** 读取后不作语义修改，再确认同一含义，不得凭视图重建偷偷改默认、升级解释或重新选业务政策；普通排版动作按其原合同另算。
- **写后可读。** 对已经支持的编辑映射，新视图应呈现这次被接受的含义，而不是只显示旧缓存或“请求已提交”。派生附带变化明确给出来源。
- **省略保全。** 视图未展示的独立约束、私有内容、未知扩展及接受关系不会因回写而消失；只有明确有权的删除/替代才能撤销相交作者内容。
- **身份与范围保持。** 修改一个使用点参数不修改被共享定义的默认；修改定义则重核全部实际消费者。新的同名对象不继承旧对象的许可或状态。
- **陈旧拒绝与重基。** 旧基础不覆盖新源。若能按原B/L/U合同重基，产生新候选并重新核相交含义；不能保持时保留两边和具体冲突。
- **支持不足时不猜写。** 一个视图编辑对应多个不等义源变化，且无委派能裁决时，保留准确选择。无法回写的展示应标为只读，而不是另存一份竞争JSON。

这些是语义和源保持条件，不能仅通过JSON往返相等证明。普通确定编辑可以满足固定输入下的确定性；涉及创作时先形成候选并接受，再进入确定读取与编译。

<a id="first-layer-source-representation"></a>
### 精确源不是先JSON.parse再补类型

源捕获先保留准确字节、解码合同和来源位置，再按所选解释检查重复键、编码、数值词元、字段以及预算。重复键不得依赖解析器的前值/后值规则；数字尚未无损读取时不得进入身份、比较、范围或默认推导。既有后继计算Int/UInt字面量采用规范十进制字符串；Requirement/Intent中已经规定精确数学整数的直接数字则继续按原准确词元读取。结构位置/长度等已有限制的安全整数仍守原范围。这里不以一个统一字符串迁移撤销旧合法编码，也不更改全局canonical身份算法。

RFC8785的JCS限定数字可由IEEE754双精度表示，并建议更大数值采用字符串；它不能直接为Gift原有精确大整数JSON数字签发无损身份。采用任意规范化器前必须匹配对象自己的编码画像，不能先舍入再哈希后声称确定性正确。[RFC8785 §3.1及附录D](https://www.rfc-editor.org/rfc/rfc8785.html)仅支持这个限制，不证明本项目已实现相应Reader。

现行`/2`的局部Definition/import/export ID遵守其原ASCII Identifier合同；本候选的Unicode名称与结构Ref按专业解释章节明确迁移，不能倒改旧Reader。中文或其他语言的显示、说明和开发输入不必成为内部ID。系统为新对象分配并保持准确ID，通过已有来源/显示责任关联名称；别名、翻译、Unicode正规化或改标题不能自动合并对象。若要求本身涉及公开原生符号、文件名或协议字段的准确Unicode字节，那是产品语义，不得把它降成一个非语义显示名；需由准确目标/编码合同承担，当前画像不支持时保留缺项。

源中的顺序按字段责任判断：JSON对象成员不是默认执行顺序；有序Expr字段、参数、序列或步骤规则保留各自顺序。排序、去重与压缩仅在对应语义允许时进行。默认值与字面量是否同值、源字节是否相同、作者对象是否同一及现实对象是否同一，分别由原身份责任判断。

<a id="first-layer-partial-source"></a>
### 草稿可保存，未知不能混入已认可语义

自然语言尚未解释、JSON编辑尚未闭合、某专业Kind尚无Reader、或合法定义尚缺Method，属于不同缺口。用户应能保全其真实草稿；这不要求错误JSON先成为合法Module，也不允许未知字段通过严格解码。未解析字节只由原编辑/来源存储保全，不贴Validated品牌，不作为授权或执行输入。

能够安全解析的区域，可在准确依赖和源边界下继续做局部分析。未知区域影响某公开接口或被选根时，相交根保持Incomplete/Needs；独立根只有其全部实际依赖和独立接受条件已闭合时才继续。不能把“这个文件看起来无关”代替读集和消费者判断，也不因一个可保全扩展存在就允许其payload执行。

完整新源继续走propose的source/files或原准确文件捕获；语义修改仅使用已协商的操作集合。`semantic-change/1`没有的通用创建操作不能凭本节杜撰；一次创建需要共同改变定义、引用和导出时，由同一候选承接完整files差额。验证、语义资格和获准保存分别判断，不能把严谨解码变成无法保存草稿的产品限制。

<a id="first-layer-edit-complement"></a>
### 无损编辑需要原源余部，不能只依赖两条往返等式

同源视图的实现保留原SourceSnapshot/候选中的未投影部分及准确位置对应；这些内容继续属于原源，不建立第二个可写“补集库”。写回从原基础应用一项有范围的语义差额，而非从短视图重建整个对象后替换。新增的派生结构也必须能解释其来源及受影响消费者。

仅有“没改视图就不改源”和“写回后读到新视图”仍不足以保住被隐藏字段：一个错误写回器可以在任何非空编辑时删除所有隐藏约束，同时满足这两条。Retentive Lenses研究明确区分这种保留义务与通常往返条件；本设计采用其问题区分，而不宣称本项目已经实现或证明一个通用lens。[Retentive Lenses](https://arxiv.org/abs/2001.02031)

实际更新同时约束三项：本次有权选择的含义发生预期变化；未选择且未被允许撤销的独立作者内容保持；由变化必然影响的派生结果按真实依赖失效/重算。若保留项与新目标冲突，返回相交冲突而不是删保留项；“省略保全”不表示旧证据和旧生成代码必须逐字保留。

对不可披露内容，保存仍可由有权服务检查完整源，但不得把隐藏字段、差异或冲突细节泄漏到无权视图。最多给出该主体获准知道的拒绝或待授权信息；是否能继续修改取决于真实服务是否能够在不泄露的情况下证明保持。读取权限不是全对象修改权，知道ID也不赋予权限。无精确原基础或安全局部操作能力时，不进行全对象盲替换。

文本层不冲突也不代表语义层不冲突。B/L/U重基先保持原对象身份和来源，合并实际改变的作者含义，再核单位、类型、独立承诺、共享引用和实际目标；两个分支分别改变“分钟数值”与“改成秒”时，不能将其机械组合成另一个未接受数值。重基所得新候选重新取得相交接受与作用资格，旧批准不能只凭无文本冲突复用。

<a id="first-layer-decision-persistence"></a>
### 默认、委派与已接受选择的持续语义

定义默认、实际发生点实参、编译推导、实现自由、运行输入和客户端偏好继续存放在各自原拥有者。省略只触发该准确定义与所选画像允许的缺省规则，不从空字符串/null/0推断“使用默认”。默认演进不追溯改变旧锁定引用；对既有发生点是否迁移由原接受关系决定。

系统完成推导时保留推导关系，不再要求作者双写派生值；系统在委派下作出有独立语义后果的选择时，固定其实际接受内容与政策依据，不能将其伪装成逻辑必然。普通重建不重新抽签或改选业务含义。只有真正不改变公开保证、且当前请求允许重新选择的实现自由，才进入再优化。

Auto、Pin、Forbid、Profile、reset继续消费原控制语义。Pin只限制相交实现或值，不赋予权限；reset仅撤去有权撤销的该层控制，不能清掉独立硬约束；Auto也不得越过上层Forbid。目标专用控制不会因切换目标被当成无约束通用默认，须区分不适用、缺映射、仍生效与真正撤销。联合出现的不同偏好没有默认加载顺序裁决；按已接受比较合同处理。

判断控制是否可复用时，既看请求值，也看它所控制的真实对象、解释、作用域、目标和发生点；显示值相同不证明绑定未变。上述判断由系统消费原锁/来源/决定投影，不让开发者维护一份额外控制台账。

<a id="first-layer-closed-meaning-carrier"></a>
### 可闭合的小型Meaning载体，与未提供的实现严格分开

一个完整的设计示例应尽可能提供自身所引用的定义，而不只写一个看似正式的URI。有限布尔选择例在[连续开发范本](../../examples/第一层作者/连续修改与反例.md#first-layer-closed-boolean-example)给出完整语义、当前字段映射及二次修改：`core:type Bool`、纯`core:function RelationBody`、`domain:meaning KeepRelation`与`intent:goal KeepGoal`都属于同一`gift.author-module/2`。所有local引用都有实际定义，无外部std函数、原生库或虚构业务模块。

`domain:meaning.body`使用当前必需的`category/parameters/result/interpretationRef`；每个角色使用现有`name/type`，本例基数明确为one。`RelationBody`只是判定一个给定输入/输出三元组是否满足关系的纯解释，不是待生成的业务实现。它返回Bool、无外部效果，使用literal/var/if；if的实际字段是`condition/then/otherwise`，不能用普通语言习惯造一个`else`键。Goal沿当前roles/typeRef和call/meaningRef/bindings消费同一关系。

源内引用闭合不代表解释已经被生产系统认可。专业接纳仍核签名、值域、观察完整性、终止、错误、用途和所选Reader/Method/Target；本例可以用四个输入组合及两个输出选择的完整有限论域给出数学依据，不能由此推到真实世界观察永远准确。没有生产Reader或目标方法时，此作者源仍是有完整本地引用的设计样本，不是已经能生成产品的证明。

有限布尔样本只闭合自己的定义。区间例的解释库在本包已另行给出，见前述实际源与完整范本；其关系源码闭合仍不替代生产Reader、实现选择、目标资格及Library/CLI完整产物。两例各保留自己的类型、结果和证据范围。

## VS Code 日常源码：稀疏结构，而不是展开节点树

本节是本轮拟议的作者编码修订。唯一语义仍是现有Definition、TypeTerm、Goal、Requirement、Use与控制；不另造意图IR、求解器、必需文本DSL或私有编辑格式。当前已发布/已选解码合同不会自动改变。样本使用显式实验标记`gift.author-module/compact-design-draft`，它不是注册/发布的协议版本，更不是现行`gift.author-module/2`能读取的内容。正式采用必须固定准确编码修订、Reader及一次授权迁移；一个工程只有一个活动作者Writer，不能并列维护长源和短源两份真源。

### 四类冗长，四种不同处理

第一类是纯载体冗余：`kind/body`、`op/items`、同名exports映射、unit事件的重复payload。这些按确定的语法规则压缩，不改公开意义。第二类是唯一可推导内容：同一常量的期望类型和literal类型、使用点唯一可知的参数形状。它们可在已选规则下省略，但显式作者注解若承担兼容、固定默认或独立接受义务，不能因为当前恰好等于推导值就自动删除。第三类是可复用语义：一项已有关系在多处使用，引用准确的定义，不复制整段解释。新关系仍需系统形成其真实定义和实现，不通过一个假库名隐藏缺口。第四类是看似相同但独立的要求：不同来源、撤回权、适用范围或条款身份，保留其独立性，最多共享计算。

缩进、换行、折叠和控件不是前三类处理的替代品。把80行排成10行、把长JSON藏进Webview、让AI每次重写整棵AST，均没有减少源码的重复事实。

### 作者源、充分展开和运行协议的边界

```text
VS Code 中真实保存的短作者源
    → 严格解码＋确定展开＋已有类型/语义检查
    → 既有声明结果/绑定/Engineering IR/生成贡献
    → 目标源码、依赖、资产及所请求的检查
```

上图不是四份需要编辑的文件。充分展开仅是可重建的只读检查结果；可以临时查看，不能被默认写回短源或加入sourceScopes。执行信封中的candidateRef、operationRef、前像、授权、回执与检查证据不进入作者模块。原生TS/Rust、package清单、媒体与原格式配置保持自己的拥有者，也不整体装进JSON。

一个由机器形成并被接受的短作者文件仍是作者源。区别在于它是否承担持续可改的作者含义，不在于最初由谁按键。自然语言原话保留为来源；完成接受后，固定构建不重新猜测它。

### 模块与定义的确定短写

保留`schema/moduleId/imports/definitions/exports`这些已有含义，避免为缩几个字符另造一套术语。精确schema标记和模块身份由工具形成，但仍在文件中可检查，不从文件名、显示名或内容哈希猜身份。

| 位置 | 拟议写法 | 准确展开与限制 |
|---|---|---|
| Definition | `"CanPublish": {"intent:goal": {...}}` | 唯一kind键替代`kind`和`body`外壳；现有27种kind仍有原职责。原Definition合同允许的其他字段在同级原位置保留，并按该kind检查；短写不新增任意qualifier。不得同时出现两个kind。 |
| 同工作区导入 | `"logic": {"workspace": "module:surface_logic"}` | 展开为`mode:"workspace",moduleId:...`。这里的workspace不是网络发现、最新版本选择或写授权。 |
| 已锁依赖 | `"rules": {"locked": "module:rules"}` | 仍需真实绑定锁与内容闭包；不能只有这个字符串就认定锁已存在。原constraint等独立字段继续保留。 |
| 同名公开导出 | `"exports": ["Task", "CanPublish"]` | 每项映射到同名本地Definition；必须存在、不得重复。省略exports不自动公开全部定义。 |
| 公开别名/转导 | 原exports对象；本地值可写定义名字符串 | `{"Public":"Private"}`展开为定义引用；跨模块转导继续显式import/export二字段，不猜消费者。 |
| Goal单一角色 | `"editorApproved":"logic:Bool"` | 精确缩写`typeRef:"logic:Bool",cardinality:"one"`。需要其他基数、bindingLevel或额外约束时使用原角色对象。 |
| Goal条款 | `"clauses":{"sufficient":{"achieve": F}}` | 字典键是原稳定条款id；achieve/maintain/avoid键下F是原formula，原horizon/scopeRef留同级。oblige/permit/prefer按下述专业条款规则，不强行转成formula。 |

achieve/maintain/avoid条款的短键承载公式；oblige、permit、prefer短键则承载原条款去掉id/modality后的完整专业对象。oblige保留actorRole、trigger、fulfilment以及deadlineRef与temporalMode的恰一时间制度；permit保留actorRole/actionRef及实际作用域；prefer保留qualityRef/direction。嵌套trigger/fulfilment按同一Formula规则展开，其他字段原样解释。规范义务、许可与偏好不是三个布尔谓词，不能用一个F吞掉它们。assumptions/observations保留原结构与独立id/来源，只在其真实Formula槽位应用公式短写。

Goal条款列表的顺序不表示优先级，此处才能转成以id为键的对象。源编辑位置改变必须更新对应关系，不能把JSON Pointer当永久身份。其他具有顺序、重复或优先语义的列表绝不能套这个规则；重复JSON键在构造对象前就拒绝。

有相同body的两个定义也不自动合并身份。重构更名涉及内部引用、公开出口、外部消费者和来源连续性；F2不能只做字符串替换。同名导出短写仍然是公开合同，不是无后果排版。

### Goal公式：保留命名参数，去掉重复节点外壳

这里的短写仅适用于Goal Formula位置，不适用于任意数据JSON、计算Expr或效果请求。带冒号的已限定Meaning引用与无冒号的逻辑构造键使用不同命名空间，不依据名称猜含义。

```text
Formula := { QualifiedMeaningRef: NamedRoleBindings }
         | { all: NonEmptyArray<Formula> }
         | { any: NonEmptyArray<Formula> }
         | { not: Formula }
         | { implies: [Formula, Formula] }
         | { iff: [Formula, Formula] }
         | { quantify: 原量词对象去掉op }
         | { temporal: 原时态对象去掉op }
```

例如`{"logic:Both":{"left":"editorApproved","right":"reviewerApproved"}}`准确展开为现有`op:call/meaningRef/bindings`；实参仍然具名，不能为了省字改成无法审查、会被参数调序破坏的位置数组。bindings值在这个位置是角色/绑定变量引用，不是自然语言、字符串常量或待执行表达式。外部Meaning必须已经导入、公开并具有相符签名。

`all/any/not/implies`分别展开为原构造；`implies`二元数组的顺序固定为前件、后件，这种两个角色已由语法明确的固定元组与任意函数的未知参数次序不同。量词保留原binder/domainRef/predicate/count/完备性和作用域，时态保留原operator/item/clockRef/boundary/rangeRef/完备性；只删op外壳，不能以短写省掉会改变判断的域、时钟或计数。all/any仍非空，count仍精确整数，until/since仍须boundary。

新增`iff(A,B)`仍精确展开为`all(implies(A,B),implies(B,A))`，不改旧四态代数，也不表示因果双向成立或比较证据记录相等。完整、无冲突的经典Bool谓词沿相应经典关系解释；其他情况只能先报告实际代数投影。特别是NEITHER与BOTH代入会得到仅支持结果，因此“投影为T”不单独签发验收或动作许可；所用推导、假设、准确观察与一致性由原Claim接纳者核验，详见编译承接的证据接纳修正。独立合格证据可完成一个无冲突备选，不要求所有未使用分支均已知。短写不授权合并不同观察、重排效果或只执行一次本来具有独立时刻的作用。展开结构采用保持发生点的纯项共享，避免嵌套iff重复复制产生指数膨胀；无共享资格的真实调用仍保留次数、顺序与实际资源责任。

这里没有把表达式塞进`"a && b"`字符串。源仍可由JSON工具解析；符号、绑定、错误位置和引用可由语言服务理解，不依赖隐式eval或正则替换。

### 条款身份：旧工程短写与新工程简写不能混为一次格式化

迁移上一包的publication时，`sufficient`和`necessary`两个条款保留。`examples/第一层作者/proposed/design/publication.module.json`就是这份迁移候选；展开后仍有原两个id和原两个方向的关系。它不删除独立接受记录，也不把旧证据自动绑定到新源字节。

新建规则可以在一条`decision_relation`条款中使用iff，完整样本在`examples/第一层作者/new-author/publication.module.json`。这是新作者表达，不是声称旧两个条款已经无损合并。旧工程要采用这种语义重构，必须显式处理旧id的消费者、接受、诊断定位和证据适用；仅证明两个公式在Bool域上合取相同，不足以证明所有来源责任可丢弃。

### 类型和常量：不是所有信息都能靠推导删掉

在TypeTerm槽位中，`"bool"/"text"/"unit"`准确表示相应scalar；`"local:TaskId"`等限定引用展开为原nominal引用。不把陌生短名自动搜索成某种类型。有限标量的位宽、溢出、精度、单位等独立区别仍显式给出；例如`{"uint":{"bits":32,"overflow":"checked"}}`。

只有core:type原body恰好只有type字段时，短payload直接是TypeTerm，不再套这一层。若原body存在独立字段，则保留原body对象及其type槽位，不丢字段；完整TypeTerm仍以明确tag形式可表示，不猜任意对象是类型。记录用`{"record":{字段:字段规则},"open":false}`；只有裸类型的字段规则准确展开为`{type:...}`，具有optional/mutable的字段仍写原字段对象并压缩其中的TypeTerm；当前/2的Field只接受type、optional、mutable，不把default或说明字段暗加到这个合同。其他专业定义拥有的默认与说明留在其原合法位置。本轮不发明字段名末尾`?`或`!`的隐式小语法，也不将optional改成nullable。open保持显式，开放余部类型和行约束继续按原完整TypeTerm表示；不为了短写把开放记录一律闭合。

常量短写`{type:T,literal:V}`只替代声明期望类型与literal类型已经确定相同、且value确为字面量的情况。V按T的既有精确编码解释，数学整数/uint32示例仍是规范十进制字符串。复杂计算继续使用原value表达式，literal与value不能同时存在；字符串不会被偷偷当作代码。

显式用户类型约束与本次推导结果恰好一致，不代表约束冗余。删除它可能在以后库升级时改变可接受范围；只有本次有权的源码简化明确允许撤销该固定语义时才能删。推导失败、名义歧义、递归签名或未知导入，不默补Any、零、空效果或无穷资源。

### 状态规则：常见表可以短，守卫、优先和活动不能被压没

对载荷精确为unit且没有附加内容的事件，可使用事件名字符串。否则继续显式事件对象，保持payload、身份、注解及专业合同。

无守卫、无动作、无优先级且每个(source,event)唯一的转移，用`transitions.table`表达`source → event → target`。源状态表、初态、未匹配策略继续明确；不能由第一行猜初态，也不能用缺转移推断“忽略”。复杂转移使用`transitions.rules`中的原有完整记录数组，保留真实顺序、守卫、动作和条款身份。table与rules互斥，不存在把重复事件覆盖成最后一条的读取规则。源表中无顺序/重复/注解责任的分支才可变表；若旧消费者按数组位置签发独立定位或顺序合同，则保留rules，不能只因条件互斥就删除其真实身份。新表的序列化/展开顺序固定且不影响这类无冲突迁移含义。

本包的JobLifecycle可完整短写；这不证明层级状态、并行区域、entry/exit、历史与真实取消也能被这张表代替。那些已有合同保持。某状态叫Cancelled，不提供现实任务已经停止的证明。

### 全部专业构造继续可达，不强制扩成低层JSON

27种Definition保留其语义拥有者。统一的kind-key外壳适用全部合法kind；专业body只有本节或原owner已经给出准确等价规则的位置才缩写，其余保持原完整body，不用任意any逃过语义检查。函数、接口、Meaning、流、workflow、API、关系数据、UI、资源、并发、政策、effect、观察、质量、产品、部署、原生供给、扩展、Pattern与Requirement的独立信息都不因本轮未给其每个字段专门缩写而被删除。

应用作者优先引用实际已有公开定义、绑定差异和独立约束，不将整套被引库复制到每个使用点。供给作者的完整函数/算法体仍是有价值内容：可以沿已选计算画像或真实原生拥有者维护；系统代劳用户没有主动选择承担的下层工作。并非“JSON短不了，所以用户自己写Rust”。

复杂Body的每项缩写须由其原owner给出语义规则及正常/边界实例，不能写一个通用删字段函数。当前明确短写已经覆盖模块、定义、导出、导入、Goal角色/条款/逻辑、常见类型/记录/常量和有限状态表；没有声称全部高级专业语法都已经达到最短。

### 严格读取、确定展开、位置与恢复

先捕获实际字节和编辑器版本，拒绝重复键、编码问题、词元损失与预算越界，再按选中的准确codec解释短形。不要先JSON.parse成有损对象再补语义；Schema的default是注解，验证本身不会替系统补字段。[JSON Schema annotations](https://json-schema.org/understanding-json-schema/reference/annotations)只支持这项事实。本节的role one、unit事件等是显式语言缩写规则，不是借Schema default偷补业务决定。

确定展开仅补已定义常量和结构，不调用模型、不联网、不读环境变量、不挑某个业务方案。短字段对应原语义节点/条款与原文本range；派生内容说明来自哪条展开规则。诊断优先落在真实可改源，查看展开只读。短写没有对应的精确反向编辑时，在原源呈现明确候选或准确不支持，不输出一份竞争展开源。

格式化只改变语法允许的空白/排版，不把短源打印成长树，不按对象键排序改变具有独立显示/演进用途的源顺序。JSON对象语义无序不等于编辑器可以无条件重排整个文件；语义有序数据继续用数组。注释不是严格JSON的语法；本轮不假称已有JSONC Reader。`authorNotes`等已定义说明可保留，但不承载暗中执行的政策。JSONC若以后实际采用，应有独立准确codec和迁移理由，不为消除逗号或花括号无限扩语法。

同一工程迁移时，先固定全部相关源、解释、引用和接受关系，生成短源候选及对照映射，核独立身份/约束、符号、正常/边界行为，最后由一次授权采用切换Writer。失败保留原源，旧在途操作继续按其旧解释结算。候选格式未被生产消费者支持时维持旧格式可编辑，不因新设计出现先损坏用户工程。

### 简洁性的实际判断

分开测：用户必须决定什么、手写结构大小、保存的真实源码、给模型的实际输入/输出、检查/生成/失败恢复与后继维护。减少字节不自动减少相同比例的Token，更不自动加快编译；把一万字藏进刚生成的私有库不能算免费。

本包按同样的无空白JSON编码比较上一包4份完整模块与其保义短写，包括全部原语义库；结果随相应交付的独立核验回执保存，不作为源协议事实。原项目文件也单列计入总源量。未把换行、折叠、删除条款、换算法、未提供库或未做工作当作压缩。新单条iff范本单独报告，不与保留两个独立条款的旧工程混算。这些是文件度量和固定样本核对，不是编译器/Token/运行收益测试。

## 短编码的完整域保持与精确分派

### 精确原形是同一codec中的保全路径

在Definition位置，以下两种形状按互斥规则读取，而非尝试猜测后任选成功者：

```text
ExactDefinition = { "kind": KnownKind, "body": ExactOwnedBody, ...该kind原本允许的字段 }
ShortDefinition = { KnownKind: OwnedPayload, ...该kind原本允许的字段 }
```

存在`kind`键就只读精确分支，额外kind-key视为错误；不存在`kind`时必须恰有一个本codec认识的kind-key，不允许两个kind或任意兄弟字段。KnownKind消费准确解释修订中的原Definition集合；专业增长用已有extension:definition，不把任意冒号键直接当可信新内核。qualifiers只在原分支允许时接受，例如当前core:constant/core:function不能凭通用外壳添加原本不合法的qualifiers。

精确分支保持全部原Body及其语法，不在内部擅自应用短写；这提供每个旧合法对象的确定嵌入。短分支只在下表明示的位置展开；无专门规则的Body必须保持原完整形状。两者都是同一模块的一份作者源，不要求同时保存旧文件、展开文件和短文件。复杂专业定义仍然可用，不因没有更短拼写丢能力。

固定旧Reader解释版本R、合法对象d与包装函数E，把d的原Definition直接放入新模块的精确分支、保留模块元数据、准确导入/导出及其解释绑定；确定解码C满足C(E(d))=d。对每个有明确同义规则的短构造，再按子结构归纳保持。这里d是有限规范对象，不把文件排版、来源接受、运行历史或外部权限也声称相等；这些分别保留其准确身份和迁移关系。旧无效输入不因新形状绕过准入。

### 按槽位解释，而不是递归搜索特殊键

| 槽位 | 判别和动作 | 必须不做的事 |
|---|---|---|
| Module | 检查格式标记及固定codec内容，分别处理imports/definitions/exports；namespace/dialects/annotations保留原合法位置 | 不把全部嵌套对象都作为模块扫描 |
| import/export | import有mode时只读原形，否则恰选workspace或locked；exports的原映射/重导出对象完整保留，数组或同名别名仅是明定短写 | mode与短键混用、同名重复或未知字段不靠分支回退接受 |
| Definition | 上述kind互斥分派；精确分支交原Body Reader | 不在解码失败后降成“未知但有效” |
| core:type短payload | 有明确type字段时是原Body，其他完整Body字段按原规则；否则是Type槽位 | 不将任意对象猜为record或丢typeParams/visibility |
| Type | 有tag或原合同明确的无tag构造（例如packElement）则原形读取；其余只接受已定义scalar/ref/record等短构造，字段集合须互斥 | 不把所有带冒号字符串都当引用；只在此槽位识别 |
| Field | 有type字段时按精确Field读并递归其Type；否则仅能是裸Type短写 | 不给optional自动增加null，不接受原合同不存在的default |
| Goal角色 | 字符串是typeRef+one；原对象保持全部原字段 | 不自动创造现实角色或授权 |
| Goal条款 | keyed map的键作为原条款id；值恰一个模态，按该模态专业字段展开 | 不把所有模态变成formula，不能覆盖同id |
| Formula | 有op则完整原形；无op恰一个已定逻辑键或准确QualifiedRef调用，实参按原绑定合同 | 不把公式当宿主命令，不将数据中的all/not误解为逻辑 |
| 状态事件与转移 | unit字符串及table仅在原先列出的无歧义画像使用；rules保留原记录 | 不从对象枚举顺序产生调度或优先级 |
| 常量value、literal载荷、annotations、扩展payload及其他业务数据 | 由相应精确数据codec读；未经它声明，不作语法展开 | 不把含kind/op/all/tag的普通JSON数据变成代码 |
| 其余专业Body | 只使用原owner已明确的准确形状与引用语义 | 不靠通用递归删字段声称支持全部专业语法 |

原形Type不能误简化为“必须有tag”：候选/2还包含`packElement`等明确的原生分支，它们必须按原精确合同识别，并继续核参数包、kind和作用域；不由这个例外放开任意无tag对象。

同一个对象`{"all":[1,2]}`在数据槽是数据；在Formula槽必须符合公式数组而不能悄悄接受为原始JSON。字符串`"local:X"`在Text值中仍是文字。数据构造可以保存带kind或op键的值，诊断不能只搜索词形判断权限。Schema身份相同不保证内容修订相同；新codec须由已有解释映像/绑定固定准确内容，旧`compact-design-draft`材料按取得时的修订解释，不能随“补文档”静默升级已接受项目。当前包不是正式Reader迁移。

未支持区域保留原字节与只读未知节点；它没有合法类型、目标资格或可作用状态。用户仍能编辑草稿，其他完全独立且已确认不依赖它的根可以继续。要参与语义链接的扩展不能仅依赖opaque payload；需要真实binding和专业验证。

### 顺序、显式选择与引用更新不被压缩丢失

类型记录的字段集合与`Expr.record.fields`的有序初始化列表不同：前者可以用字段对象，后者必须按每个初始化恰好一次和原列表次序执行。两个字段初始化各有作用时，即使最终字段名相同，调换顺序也可改变观察；不可通用改成对象字典。JSON对象成员顺序不提供该语义，数组才保留顺序。[RFC 8259](https://www.rfc-editor.org/rfc/rfc8259)。重复键按解码后的名字判断，因此`"x"`和`"\u0078"`也不能覆盖；拒绝发生在构造无损对象之前，不依赖普通解析器最后写者胜。

显式`effects:[]`是对闭合效果的约束，缺省effects在当前函数合同下可能请求推导；二者当前结果相同仍可能在后继修改时不同。显式空根、空结果绑定、缺值、None、Absent与Present(None)同理。源缩写只压载体，不能用“当前看起来一样”删除这些作者决定。

只有不承载独立位置或顺序义务的状态表才能从原列表变表。诊断节点、批准、来源和注解引用旧条款id时，移形也必须保持映射；格式化不作这种语义迁移。两种合法源形式可以有不同字节身份，不能仅凭解码语义相同重用要求精确作者修订的批准。

### 源位置和回写都有准确基础

编译内部区间记录准确源修订、文件身份、字节起止与对应发生点；VS Code接口边界使用其UTF-16坐标，LSP按协商编码转换，不能拿一个未标单位的offset通用。对`A😀中B`中B的起始位置，UTF-8字节偏移是8、UTF-16单位是4、Unicode标量序号是3；JSON字符串原文写成转义后，源字符数又不同。先按原文/CST定位，再转换宿主坐标；不能用解码后的字符串长度回写源文件。

替换不得截断代理对、转义序列或CRLF；坐标越界和版本不符诊断或重新定位，不钳到最近位置后强写。一个建议从定义版本R得到，文件换名或用户继续输入后，要重新求实际对应和前像，不能照旧range修改别的内容。相同名字和hash不提供跨次作者身份，旧引用的移动/重命名走原语义编辑。


<a id="stateful-business-source-ownership"></a>
## 有状态业务源码：角色绑定到真实边界，不把状态和回执交给调用者自报

本轮业务范本继续使用原Definition、domain:meaning、intent:goal和短codec。源码只有一份；`before/request/outcome/after`是准确关系中的四个角色，不是客户端必须填写的四份表。它们用于表达一次已知业务状态变化，编译器的实际方法须按下表绑定消费者，不能从变量拼写猜测。

| 角色 | 合格生产者 | 允许的使用及不能替代的事实 |
|---|---|---|
| before | 实际状态拥有者在所选原子边界/版本下取得的状态 | 不接受调用者提交任意余额或预留表作为权威；纯设计查询可使用明确假设的模型状态 |
| request | 经协议解码且已绑定任务/主体/对象的业务输入 | 不因带poolId、epoch或key就获得权限；运行尝试身份另属原Operation |
| outcome | 已采用方法对该次请求作出的结果及相应真实结算 | 计划可行不作为已提交结果；Observed表示观察已有状态，不表示再次执行 |
| after | 同一结算边界的实际新状态或有资格的纯候选 | 其他副本/稍后读到的偶合状态不自动证明本次作用；未知结算仍保持未知 |

Pure Meaning仅判断这四项是否满足规则，不读数据库、不执行Reserve，也不签发Grant。一个方法若承诺提交后返回Created，必须把判断、发布和回执归入其真实一致性范围；控制面的preview可返回候选而不能复用同一个“已发生”标签。源码中的relation是要求，不是由任意四个自述JSON制造执行证据的入口。

### 请求身份、资源身份、对象修订和业务标识分别保持

范本的poolId与epoch限定一个计量和发行域，Entry.key是该域内稳定的业务预留身份；Operation/Attempt身份决定一次实际作用、重试与恢复。它们不能互相替代，也不能直接由内容哈希统一。两次同内容的新申请可以是两个不同预留；同一个key的不同quantity是冲突，不是覆盖；另一epoch的相同key不继承旧作用资格。

本库给出**成功预留/状态转换的业务幂等性**，并没有独立提供外部请求回执数据库。不存在的key因容量不足被拒绝，不产生新的成功预留；以后容量变化再申请可能得到不同判断，这是新的决策观察。若具体API承诺同一operation无论成功失败都重复返回原结果，必须由原持久Operation/receipt保持那项结果与payload绑定，不能仅靠业务key达成。重试协议究竟复用原尝试，还是发起新准入，要从原作用合同取得，不能由客户端随意删id决定。

Entry保留Released终结信息，因此同一key随后Reserve相同quantity只观察Released，不重新激活。物理实现可使用map、索引或紧凑tombstone，前提是维持这项可观察语义；将Released行按固定TTL删除会再次接受旧key。安全压缩须证明原重试/观察窗口和未结责任已经终结，或有权切换发行域并在入口明确拒绝旧epoch。不能为了有限内存伪称无界历史的去重永久有效，也不强迫无重放义务的纯短查询维护永久日志。

### 原需求改变时，保存的是政策差额，不是改写运行表

随包第一层仅引用`reservation:NoOversell`。新的要求“以后至少留一单位余量”将其改为`reservation:KeepOneFree`；定义、角色、条款与公开模块身份保持。旧预留记录不是作者源码，不因编辑这个引用而删除；已经被接受的在途操作继续按其原解释和当前可执行权限结算。

这两种Meaning使用同一纯关系及参数headroom，分别固定0与1。留出余量约束的是新的成功Reserve，不是无条件要求当前已有业务状态立刻满足新的余额阈值。Commit和Release继续承担原责任。若用户明确要求对所有现存对象立即满足新阈值，这是另一个包含迁移/补偿和接受变化的任务，不由这一行引用自动完成。

### 结构源、派生对照和运行实例不混放

`examples/第一层作者/reservations`的活动源只包含`design`和`library`，两者都选择同一compact设计编码。关系库使用该codec的完整Definition形状，应用使用短Goal，二者是同一作者语言。`derived`是只读的/2结构对照，`changes`是后继比较，不进入sourceScopes，也不形成第二Writer。完整库不是模型上下文的默认附带载荷；编辑一个Meaning引用只需取得其准确签名、差额及所需语义，专业维护时仍能读取全部主体。

公开名与内部实现可不同。诊断要区分“改了哪条业务规则”“实际绑定到哪个pool/epoch”“本次是否只改源码”“哪个旧运行继续使用旧政策”。这些均由原SourceRef、UseBinding、Operation和决定投影提供，不在模块中增加一个全局currentState字段。

### 现有区间样本的名义结果类型接合

区间库原先公开`Outcome`并由Goal/interface使用其引用，但CheckOutcome、TouchBody、OverlapBody及两个Meaning的参数又复制匿名variant。对具有名义身份的结果类型，布局相同不能作为默认强制转换依据。本轮将这五个参数统一为`local:Outcome`，保留原类型声明、变体载荷、函数体、关系规则、模块/条款身份和公开出口；只修同一结果在实际消费者之间的类型对应。派生`/2`对照同步，应用仍只修改原Meaning引用。此为源码合同一致性修订，不宣称此前已运行并发生了产品故障，也不追认前包有限引用/结构检查为完整类型系统验证。


<a id="observation-source-and-qualified-range"></a>
## 数量与缺席意图的实际作者源，以及源中不能自签的资格

`examples/第一层作者/observation-bounds`提供完整CountRange、CountQuery、Evaluation及AtLeast/AtMost/Exactly关系；应用使用短Goal，专业库继续使用同一codec的精确Definition。它只扩展普通定义，不新增kind、核心语法或运行许可字段。完整应用及接口见范本；改AtLeast为Exactly只修改所选Meaning引用，源身份保持，语义与相交证据变化。

### 纯值包络与真实观察资格分开

CountRange的lower是总数的下界，upper是Finite(Int)或Unbounded(unit)。它不是“已看到多少行”的不加条件别名；例如去重、可撤回证据及未知谓词会改变可成立的下界。CountQuery包含range和非负threshold；Evaluation是AllSatisfy、AllViolate、Undetermined或InvalidInput。非整数字节、字段缺失属于原解码错误；结构合法但负阈值、负下界、有限上界小于下界，得到本库InvalidInput。故意保留这项区分，而不是将每项原始错误都揉进一个结构变体。

普通纯API可以分析调用者给出的假设范围。把它用于现实Claim时，系统必须从原Observation/Source/Domain/Claim取得合格范围及其依据：对象/计数语义、源修订与分区集合、所选谓词/时钟/时间窗、精确已取得成员、未覆盖上界或闭合证明、允许的修订、实际读取与披露范围。它们是既有边界需要的实际信息，不在每个作者模块新增一组必填字段，也不另建可写范围台账。客户端自填`lower:3`或伪造`complete:true`不能取得三条现实见证。

数量、权限和元数据的可披露范围分别判断。有权检查隐藏资料的服务可以内部完成更强判断，但不可把隐藏数量、对象存在、阈值两边或错误细节通过悬停、补全、搜索计数泄露。无法安全给出更多内容时返回该主体有权知道的结果，不通过假装“为零”隐藏访问失败。

### 传输结束不是论域结束

`nextCursor`为空只能在准确提供者合同下说明这次查询分页的结束；limit、隐藏过滤、快照变化、断线或不受支持的行仍需要各自范围判断。完整成员清单、固定分区前沿、精确的按键否定索引或已有适用定理均可提供较小且充分的依据，不要求所有任务扫描全数据库。两次遍历结果相同不自动证明非合作写入或ABA期间的全局快照。

本包project只扫描design和library。derived是只读的/2对照，changes只保存比较材料，mathematical-inputs.json是数学见证记录；它们都不被装载成第二作者模块，也不是实际Provider输入/证明协议。

### 回写不会把派生观察变成可写政策

作者改的是阈值、量词、时间范围、身份准则或明确接受的输出政策；当前数量、覆盖上界、源进度、是否已收齐及已经发生的动作由实际拥有者返回。CodeAction不能为了通过门禁把lower直接改高、将未知upper改成单点、把估计水位改成严格前沿，或者删除迟到/失败分区。

语义diff必须区分三类变化：用户要求变更、对现实的新增/更正观察、底层收集与计算方法替换。第一类更新被接受的承诺；第二类更新相交认识与证据，不自动重写源；第三类需要保持既定公开关系。它们可以共同发生，但不能通过一句“更新计数”混淆权威。

### 唯一作者源中保留具体用途的相等与兼容

本轮不更换canonical数据编码或默认Text相等。需要业务标准化时，由实际定义和已有ValueOps/格式适配承接；保留原字节及规范化键的不同来源。格式化不做Unicode正规化、大小写折叠、单位换算或近似去重。图/表视图展示同值也不合并不同Source/Use身份。

公开接口升级沿原接受与迁移机制。扩大输入、缩小输出、改变回调、增加错误/变体、修改缺省和扩大效果，各自定位到真实方向的使用点；旧客户端未理解的字段不在读回中被删掉再签成“已迁移”。生产Reader尚未实现新能力时维持准确不支持，本包没有借同一个draft marker静默改变已接受工程的解释。


<a id="source-expression-convergence"></a>
## 新候选的准确名称、旧声明与专业结构接合

在本轮候选`gift.author-module/design-converged`中，采用[精确Unicode名和结构引用](../../schema/author/first-layer/SEMANTICS.md#names)、[旧requirement声明的同构读取](../../schema/author/first-layer/SEMANTICS.md#legacy)及[短写确定规则](../../schema/author/first-layer/SEMANTICS.md#surface)。它们是相对于前述compact草案的明确修订，不宣称旧/2 Reader已经支持。旧协议原义保持，同一工程只有完成有权切换之后才写新源；包内独立旧范本并不是同一工程的多个活动Writer。

完整/短写只在各自准确语法位置分派。扩展profile的机器结构由`schema/author/first-layer`拥有；普通Text/JSON payload中相同键不被误当引用。已经保存的不可理解区域保全原文，不能通过“结构正确”签发实际解释资格。三份新Schema分别检查专业Body、有限短例及本次新模块外壳；它们不代替完整旧Schema集合，也不成为第二作者IR。

原压缩、顺序、求值次数、四态接纳、项图共享、未知帧、同源编辑和原文余部规则继续成立。旧完整表达通过原解释接入，不能先换schema再假定兼容。


## 模型合同源码与规范事件身份的本次接合

新专业载荷`model-contract`保留subjectTypeRef及每项requirement的id/specificationRef/claim；同一Interpret根据profile返回原Rule声明角色。其真正使用点沿旧require/fields，未增加公共工具或另一份可写Claim。源码、Schema、签名和完整[源例](../../examples/第一层作者/model-contracts/README.md)相互对应；示例比较映射不在活动源范围。

规范事件修正了原义务与补救的引用混淆：[补救结构身份](../../schema/author/first-layer/SEMANTICS.md#norm-identity)使用remedyOf和deadline，转移引用实际acceptanceEvent，接受固定from和generation。旧含糊样本不能通过替换版本标签追认正确；缺失决定性区别时保全原源/解释，明确阻塞相交迁移。

解释供给继续以准确内容及revision绑定，不让同一个schema/profile名称覆盖旧运行。所有当前范本的语义变更、后继补丁与供给摘要本轮同步；这不是生产Reader已经切换。
