# 实现语言与机制演进

本篇拥有SEC自身实现的语言比较、数据表示边界和改模成本判据，细化[实现供给与替换](实现供给与替换.md)，不新增运行owner、决策内核或目标语言。TypeScript与Rust的目标计划、SEC自身实现语言、参考模型语言及外部工具语言分别选择；采用一种目标不授权迁写编译器。

## 语义设计、参考方法与最终机制分开验证

必须尽早明确的内容是对象身份、含义、允许观察、责任、阶段前后置、依赖、失败、恢复、权限和保证。具体算法、表示、索引、分配与调度也由各owner控制，但不因“需要控制”而全部成为全局公开参数。现有[类型化控制](../作者/组合/稀疏控制与目标限定.md#control-actuation-contract)记录实际选择范围；选项的定义、选择、作用与观察均须有消费者。

规范、代数推导、可执行参考算法、状态模型、随机生成、真实实现和运行测量各提供不同证据。参考方法不要求先做一套完整TS编译器，也不要求与生产实现异语言；有限穷举、全量重算和直接解释可以在最容易审查的表示中存在。其职责是给出可核结果和反例，不承担全部生产缓存、UI、发行、调度与兼容义务。

最终机制改变时，语义正确并不自动证明性能、取消、生命周期或并发正确。对象图改成紧凑表、全量改成增量、进程内改成RPC、GC改成显式寿命，均需检查各自新增约束。先在与生产相符的最简单机制中建立纵向路径，可以避免验证一个完全不会用于最终系统的完整中间架构；这不是为了避免迁移而拒绝必要的参考模型。

设计允许普通单线程、显式拥有数据、简单集合与不可变输入先成立；已知规模、宿主或硬保证直接要求另一机制时，从第一份正式实现使用该合格机制，不强制先制造慢版本。反之，不把没有工作负载依据的锁自由、分布式、SIMD、全局泛型化或零拷贝作为“完善架构”的条件。

## 四种身份及其存储边界

[信息引用](../信息/对象关系与配置基线.md)拥有持久对象解释；本节只规定其在内存与互操作中的映射。

| 身份 | 回答的问题 | 不可替代的边界 |
|---|---|---|
| 语义实体身份 | 这是哪个定义、事实或长期对象 | 文件改名、重新排序和压缩不自动换实体；新建同名对象也不自动继承 |
| 修订／内容身份 | 是哪一版含义、字节或固定输入 | 同一实体的后继不能承接旧证据；同字节不同解释仍需上下文 |
| 运行句柄 | 在本次进程、arena或快照中如何取得对象 | 局部索引不是可持久引用；槽位复用、跨arena和旧句柄分别校验 |
| 物理定位 | 字节或对象目前在哪里 | 路径、偏移、地址和服务端locator不证明身份、版本或权限 |

例如`NodeId(u32)`只能在明确拥有者与快照下作为紧凑索引。需要删除和槽位复用时，可用带代的句柄或不复用策略；跨arena查询还需归属检查。代计数回绕必须拒绝复用、扩大表示或完成可证明的整体退役，不能静默恢复旧句柄有效性。内部句柄可在封存时映为持久引用，但须保存准确映射并核跨修订关系。

内存表示、交换编码、磁盘格式和外部ABI是四种合同。内部`struct`增加字段不应强迫所有历史快照按当前内存布局读取。持久格式固定自己的版本、字节序、数值域、引用编码和完整性；读取先有界解码并校验，再构造内部类型。零拷贝只在对齐、范围、寿命、可变性、可信度与格式兼容全部成立时采用；否则显式转换，不让性能优化暗中锁死长期格式。

Rust的默认表示并不承诺声明顺序就是字段布局，布局相同也不足以承诺函数ABI相容，见[语言机制依据](../依据/来源/语言编译与目标工具.md#implementation-language-sources)。换摘要算法也不是换一个hash函数：内容用途、编码、算法标识、外部协议、持久引用和双读迁移分别处理；Git OID及外部指定摘要遵守其真实格式，不用平台偏好统一替换。

## 可替换边界必须保留完整合同

值关系可以通过ID访问，使长期语义不依赖某种对象指针拓扑；局部实现仍可正常借用、采用不可变视图和编译器检查。不禁止所有lifetime、trait或共享引用，而是禁止无必要地把跨所有owner的存储寿命、锁策略和具体容器暴露为公共合同。

局部闭合状态适合明确的代数类型与穷尽分支；开放领域扩展通过现有类型化定义、方法接口和固定解释映像接合。不能用一个枚举列出所有未来控制项，也不能用`Map<String, unknown>`放弃领域校验。静态组合、泛型、enum分派、虚调用与协议边界按实际调用粒度选择；不要求所有机制运行时可插拔，避免将配置组合、代码体积和构建成本无条件扩大。

以下替换演练分别检验不同责任，不能以其中一个通过证明全部可替换：

| 变化 | 理想的相交修改 | 发现合同不足时的正确动作 |
|---|---|---|
| Map到紧凑表／arena | 存储owner、句柄映射及相交遍历 | 若迭代顺序或引用寿命可观察，显式保持或迁移该合同 |
| 全量到增量查询 | 缓存、依赖观测与失效owner | 用全量结果与读集反例校准；负候选、删除和同值新依赖不能漏 |
| 串行到并行 | 合法依赖、调度和结果归并 | 顺序相关推导、共享可变状态或资源竞争是语义问题，不能仅排序输出 |
| 内存到分页／远程 | 存储与取得边界 | 若新增I/O失败、取消、部分覆盖或异步，必须升级相交接口 |
| 当前Schema到新解释 | 解码、迁移、解释及消费者 | 未知旧内容不自动获得新效果；旧读者与恢复路径分别处理 |
| 同语言到原生／Wasm／进程 | 选定计算区域及其适配 | 固定数字、Unicode、错误、回调、寿命和构建条件；不强制全工程迁写 |
| 扩展一项领域控制 | 定义、真实消费者、反例及投影 | 没有新的跨域区别时不改所有通用Pass；确有新区别则改相交共同合同 |

分页／远程查询有两条不同合法路线：在纯计算前取得完整且固定的所需快照，或明确暴露可失败、可取消、可能不完整的查询结果及其修订覆盖。不能一边承诺纯同步引用、一边在任意访问时隐式联网。新旧页没有同一切面时，不拼成一个“完整快照”。局部查询依赖全图性质时，影响范围可能就是全图；可演进不保证所有修改永远小。

## 语言候选的机制比较

语言选择的单位是具有真实owner和交付边界的实现区域，不是“整个平台必须同一种语言”。下表给出应验证的机制与条件，不是已经跑过的排名；引用资料只证明语言或工具具有相应特征。当前TS实现及有效成果不因比较自动退役，也不把它作为未来所有正式核心必须重复实现一遍的原型。

| 候选 | 值得利用的机制 | SEC需要实际验证的代价与反转条件 |
|---|---|---|
| Rust | 代数类型、名义句柄、借用／拥有及显式布局，适合紧凑存储和原生区域 | 跨owner借用拓扑、泛型体积、编译增量、插件ABI与维护成本；静态类型不证明算法、授权和迁移正确 |
| Go | GC管理图、直接原生程序、统一工具与并发设施 | 复杂变体／名义区别如何表达，GC与峰值内存、实际并行、FFI和模块分发；不能把语法少等同整条机制更简单 |
| OCaml | 变体、模式匹配、类型推导和直接语义变换 | 与大图、并行、原生依赖、部署和工具环境的接合；不因有GC就预先否定性能，也不因适合语义就忽略运行机制 |
| F#／C#与.NET | 判别联合／类型建模、值与引用表示、运行时及调试分析工具 | 热路径分配、表示和AOT／JIT环境、原生互操作与发行；成熟运行时可以是优势，不用“托管”替代测量 |
| Kotlin／Java／Scala与JVM | 封闭层次／模式建模、成熟运行时及生态；具体特征按所选语言判断 | 冷启动、GC、对象与紧凑数组、堆外使用和部署；同属JVM不意味着三种语言的类型与构建代价相同 |
| TypeScript／JavaScript宿主 | 当前集成、结构化数据、Web／IDE接口和生态复用 | 运行时数值、集合／对象分配、隔离与共享并发；TypedArray和原生库可改变成本，不能按语言标签推出固定倍率 |
| C++ | 成熟编译基础设施、原生生态、表示和分配控制 | 生命周期、未定义行为、ABI、模板／构建与安全审查；合格既有组件可直接复用，不因不选全核C++而重写它 |
| Zig | 显式分配和低层互操作的可观察机制 | 内存责任、工具链／库及平台支持，版本更新造成的工程成本；不将显式分配误当自动内存安全证明 |
| Haskell | 纯变换、代数建模和参考语义组织 | 惰性求值的实际空间／严格性、并行、外部作用与发行；需要堆分析而非仅看纯代码简洁 |

这些候选不意味着九条生产实现线。已有库承担的内部机制优先复用；只有新收益或硬约束确实不能由当前合格实现覆盖时才承担新语言的工具链、包管理、供应链、调试、发布和长期消费者成本。形式验证也不绑定生产语言：有限集合推导、状态模型、SMT／证书或小型解释器按命题选择；不用一种工具包装全部问题。

## 编译器执行内核的当前物理方向：Rust 单一生产 owner

这里裁决的是 **SEC 自身编译器的执行内核**，不是 Rust 目标后端，也不是把整个仓库改写成 Rust。长期方向固定为：Canonical Engineering IR、Semantic Contract、稳定身份／修订、确定性查询与变换的**语言无关合同保持权威**；承担这些合同的纯编译执行区域逐能力收敛为 **Rust 的单一生产 owner**。现有 TypeScript 实现仍是已经存在的正式实现，只有某一能力完成后述切换门禁后才失去该能力的生产所有权；没有通过门禁之前不得以“Rust 方向已定”冒充迁移已经完成。

这项裁决不以“Rust 必然更快”为依据。性能收益必须沿[查询增量与性能](../编译/查询增量与性能.md)的真实关键路径和同口径负载测量。选择 Rust 的结构理由是：内核长期需要闭合代数状态、名义句柄、显式拥有／借用、紧凑存储、并行读取和原生 Provider 接合，同时又必须持续增加新状态、新控制和新失败而不把运行对象拓扑固化成公共语义。Rust可以在局部物理实现中直接表达这些约束；语义真值、交换格式、权限和 Provider 资格仍由各自 owner 决定，Rust 类型系统不替代它们。

### 哪些责任进入 Rust 内核，哪些明确不进入

| 区域 | 长期生产责任 | 不得由该选择偷换的事实 |
|---|---|---|
| 语言无关权威 | Semantic Contract、Canonical IR schema、Entity/Fact/Revision、效果与责任、Pass 前后置、诊断／provenance 含义、Target/Implementation Binding 合同 | 不以 Rust enum、trait、内存布局或 crate 路径作为长期产品真值 |
| Rust compiler kernel | 已冻结输入的有界解码与校验、稳定句柄／索引、纯语义查询、依赖与失效计算、显式 fixed-point/SCC、语义 diff/impact、纯变换、确定性 lowering plan、结果摘要及相交 provenance 组装 | 不自行读网络、Git、环境变量、墙钟、当前分支、临时路径或未声明目录来补语义 |
| TypeScript/Bun 产品与控制面 | Workbench、IDE/交互、AI 协作、任务编排、Git/文件/网络 Provider 接线、权限与准入、Mutation/Journal/Recovery 的效果编排、产品 UI | 继续存在不表示 TS 是第二套语义内核；跨边界按粗粒度 request/result 或固定 snapshot 传递 |
| 外部／原生 Provider | rustc/Clang/LLVM/MLIR、GPU/设备 SDK、目标构建器、包管理器和其他成熟工具 | Provider 自己拥有目标语言合法性与工具行为；SEC 只拥有固定输入、能力、调用、结果、证据和失败边界 |

同一寿命、同一热路径的大图和查询应留在一个 Rust 执行区域；不得把 IR 每个节点做成 TS↔Rust FFI/RPC 往返。跨区域传递的是版本化 snapshot、批量请求、结果和诊断。内存表示、交换编码、磁盘格式和外部 ABI 继续分开；默认 Rust layout 或 `extern "Rust"` 都不能成为长期接口。需要进程／语言边界时使用有版本的 canonical encoding 或另行固定且验证的稳定 ABI。

### 查询内核不复制一个新的巨型全局 Context

增量编译仍只有一套语义。生产查询至少绑定 query kind、真实 subject identity、所有影响结果的输入／语义／Pass／TargetProfile／ImplementationBinding revision；无关线程数、临时目录和 wall clock 不得进入语义键。查询返回不可变结果，并暴露实际 read/dependency set、诊断和 provenance；取消、超时和资源耗尽是本次执行状态，不得缓存成“语义上不存在结果”。

查询只能通过显式只读 view／capability 取得依赖；opaque Provider 结果先被固定成带身份的输入，再参与纯查询。循环依赖由领域允许的 SCC／fixed-point 合同处理，不靠递归查询碰巧终止。局部 owner 可以使用 arena、索引、借用和内部缓存，但不存在一个可被所有 crate 任意读取和修改的 god-context；新增控制或数据源时必须落到真实 owner 和依赖边，而不是给 Context 再塞字段。rustc 的 query DAG 和增量 fingerprint 是机制参照，不授权复制其具体全局组织。

### 未来控制维度不通过“更多模式开关”进入内核

这里修正一个容易出现的过度设计：**不新增全工程 `auto / guided / manual` 三态语义。** 现有[稀疏控制合同](../作者/组合/稀疏控制与目标限定.md#control-actuation-contract)已经允许同一任务里一处 Pin、另一处 Require/Forbid/Prefer、其余决定委派系统；“guided”可以是 Workbench 的交互呈现，不应成为改变编译含义的全局模式。

所有实现、算法、缓存、并行、布局和目标控制都先由其 owner 定义类型化描述符，再由实现选择形成冻结的 Binding/Decision 输入。手工 Pin 不能绕过硬合同、权限、能力与验证；自动选择不能替用户作未经委派的价值取舍。Rust kernel 只消费**已经解释并冻结**的类型化决定，不按未知字符串猜未来控制。新控制若只有某领域理解，由领域扩展拥有；只有出现真实跨域共同区别时才上提共同接口。

### 从当前 TS 到 Rust 的逐能力切换门禁

迁移不是翻译目录，也不是并行维护两套永久编译器。每个能力按同一顺序收口：

1. **K0 合同冻结。** 固定该能力的输入／输出 schema、身份和 revision、顺序或无序观察、诊断、provenance、**依赖／read-set 的语义与健全性要求**以及失败；不把某个实现当次产生的具体 read set 冻成跨实现相等字段。交换字节不引用 TS 对象身份或 Rust 内存布局。
2. **K1 独立 Oracle。** 以已采用规范、独立推导、小域穷举／性质模型、回归样例和现有生产行为共同建立预期。若当前 TypeScript 行为违反 K0，K0 仍是 authority：修复或隔离实现与错误 fixture；只有独立设计裁决确实修改了规范时，才提升合同 revision 并从 K0 重新冻结，不能为了保留旧 bug 反向修改权威合同。
3. **K2 Rust 只读 shadow。** shadow 的**执行权限**与**生产输入捕获／复制／披露权限**是两个独立 capability；“read-only、不写生产”只约束 Effect，绝不自动授权把私有源码、凭据、tenant 数据、用户内容或之后被删除／撤回的数据复制到另一存储域。默认只在已经按原 owner 合法冻结且仍在 retention authority 内的 snapshot、明确为 Verification 捕获的 recorded input、合成／去敏 fixture 或隔离验证环境中离线执行。任何 live production shadow 或新增 recorded-input capture 必须在读取／复制前同时取得数据准入与资源准入：数据准入绑定 capture purpose、精确 source/tenant 与采样范围、数据分类和允许字段、秘密／凭据处理或替代 capability、不得降低保护级别的 storage/transport、tenant isolation、允许访问主体、retention deadline、删除/撤回传播、派生输出及日志的披露范围；资源准入继续绑定 CPU／memory／queue／I/O 预算、隔离、取消优先级、排队上限与 backpressure。生产 TypeScript owner 始终保持服务优先级；资源压力先跳过／丢弃／取消 shadow。数据 authority 不可证明、目标存储保护不足、删除义务无法传播或输出可能越权披露时，不捕获真实输入，只能使用合成／经授权去敏输入或跳过 shadow。shadow 结果只作为 parity／Evidence 候选，不直接替换生产结果；Evidence retention 也不能反向延长原始输入的保留权限。依赖／read set 不要求与 TypeScript 原样相等：分别用依赖突变、删除／新增负依赖、同值新依赖、clean/full 重算与增量结果差分验证健全性；若合同允许保守超集，两份不同但健全的 read set 都可合格，漏掉真实依赖则失败。
4. **K3 单 owner 生产切换。** 只有声明范围内结果 parity、依赖健全性、负例、取消／资源、跨边界寿命，**以及该能力已经依赖的生产性能／容量合同**均通过，Binding 才把生产 owner 切到 Rust。性能资格使用代表性的 cold、warm、incremental、large-project／high-cardinality 和相交并发负载，绑定实际 TargetProfile、硬件／宿主与预算；如果现有生产能力只有依靠 memo、增量失效、arena、并行或持久缓存才能满足已声明 latency／throughput／memory budget，则这些机制必须在 K3 前取得正确性与性能资格，不能先用 clean-only Rust 接管再等 K4 补救。没有既存硬预算的能力不虚构统一阈值，但切换前至少证明不会越过已知资源上限或造成相对现状不可接受且未经授权的退化。同一请求不存在 TS/Rust 双写、失败后临时重选或“谁先完成用谁”。
5. **K3R 切换后恢复。** 生产切换后若出现只在真实负载／平台发生的回归，先隔离相交 capability、停止继续扩大错误结果并结算在途请求；随后由有权 owner 生成新的 ImplementationBinding revision。若旧 TS 实现仍保留、仍满足同一冻结合同且迁移前像可读，可以显式**单 owner 回绑**到 TS；否则前向修复 Rust 或回退到已验证的 Rust release。每次恢复都保存原因、影响范围、失效 Evidence、状态／缓存处置和切换后 readback。禁止按请求动态 fallback、双 writer 或用异常路径偷偷重选 owner。K5 已完成后旧 TS 不再被假定可恢复；只能从正式保留的可验证 release／源码重新取得资格，或前向修复。
6. **K4 切换后的进一步优化。** K3 前已经包含满足生产资格所必需的增量、memo、arena、并行或缓存机制；K4 只承担在不改变已冻结合同的前提下继续优化、扩大规模包络或降低成本。任何新优化仍先保持 clean/full 与 incremental/parallel 等价，再按实测引入或替换 memo、arena、调度和必要持久缓存。持久缓存保存稳定编码和依赖身份，不保存 Rust 指针／layout；dependency-mutation、代表性性能基线与 clean/full oracle 持续作为资格门禁。
7. **K5 退役重复生产实现。** consumer-zero、恢复策略已不再依赖旧 TS writer 且保留正式前像／readback 后，删除旧 TS 生产 writer、兼容接线和迁移探针；独立 Oracle、golden/property/model fixtures 可长期保留，但不重新成为第二 authority。

游戏、图形、HPC 等高频场景可以暴露增量、并发、紧凑存储和 Provider 接合的瓶颈，因此是这条迁移的强压力样本；它们**不**证明游戏运行时、用户目标代码或所有 Provider 也必须用 Rust。游戏联合画像由[领域组合](../演进/领域组合与扩展条件.md#game-realtime-pressure-profile)拥有。

### 新增内核能力直接走最终物理方向

对于**已经有 TypeScript 正式生产 owner**的能力，使用 K0—K5 是为了在不中断现有产品事实的前提下安全换 owner。对于此裁决之后新增、尚无生产 owner 的 compiler-kernel 能力，不再强制制造“TS 原型 → Rust 重写”：

- 语义仍先由语言无关合同、例子、反例、有限模型／性质和可执行 Oracle 校准；
- Oracle 可以使用最便于审查的 TS、Python、模型工具或朴素 Rust，但它不是另一套完整生产编译器；
- 一旦边界、输入和失败已经足以实施，首份生产实现直接进入 Rust kernel；如果语义仍未知，做 `spike/*` 或参考模型，而不是把未知架构伪装成正式 TS owner；
- 需要比较另一种机制时只实现能区分关键问题的纵切面，不为“公平”建设第二条长期产品线。

因此“最大化设计和验证”与“减少重写工作量”并不冲突：提前冻结的是**可验证合同和替换边界**，不是提前冻结所有数据结构；必须实验的实现细节留在局部 owner，生产代码从第一次就按长期物理方向写。

### Rust 内部的长期物理纪律

这里不固定未来 crate 名称，但固定依赖职责，避免几年后再次靠大重构恢复边界。

| 责任 | 物理纪律 |
|---|---|
| protocol／exchange | 只拥有语言中立 request/result、schema/version、canonical bytes 和能力协商；不导出 Rust 对象图或借用 |
| identity／validated model | 语义 ID/revision 与运行 handle 分离；构造后优先不可变，索引／arena 只能在所属 snapshot 内解释 |
| query／dependency | 只读输入、显式 read/dependency、memo/cancel/fixed-point；executor 是执行机制，不成为语义 owner |
| transform／lowering | Pass 接窄 view 与冻结 Binding，返回新值／Delta/Plan、诊断和 provenance；不从全局单例偷读状态 |
| host bridge | 批量交换、错误／取消／完成、资源寿命和能力；把 Git/fs/network/Provider effect 留在宿主一侧 |
| native boundary | 需要 `unsafe`、FFI 或目标 SDK 的代码隔离到窄边界；内核纯区域默认不靠 unsafe 绕过身份和寿命合同 |

### 核心生产语言预算：长期只默认两条主语言域

SEC 不把“能用某语言写”升级成“应永久增加一个核心生产语言”。当前默认长期组合只有两条主语言域：

- **Rust compiler kernel**：承担前述纯编译执行、紧凑状态、依赖查询、变换与 lowering 等单一生产 owner；
- **TypeScript/Bun product/control plane**：承担 Workbench、AI/开发控制、Provider orchestration、Git／文件／网络效果编排和产品交互。

C/C++、Go、Python、OCaml、Lean、TLA+ 或其他语言／工具仍可作为目标、成熟 Provider、参考模型、验证器、生成器、隔离服务或局部实验，但**不会仅因生态现成、已有库、某个 benchmark 更快或某个子系统常用，就自动变成第三／第四条长期核心生产真源**。新增核心生产语言必须证明一个真实责任区域存在当前两条主语言域和可替换 Provider／FFI／Wasm／进程边界都无法合理覆盖的结构性收益，并同时承担工具链、依赖锁、供应链、调试、发行、跨语言边界、人员认知、迁移和最终退出成本。

这不是不可突破的“两语言上限”。如果未来出现硬平台约束、可验证保证或全生命周期证据足以反转某个具体区域，按该 owner 的 ImplementationBinding 重开局部选择；没有这种证据时，默认拒绝语言数量自然增长。成熟 C/C++ 编译基础设施可以继续原样作为 Provider，Python 可以继续承担小型 Oracle／分析脚本，形式工具可以继续承担证明方法；这些用途都不要求把对应语言升级成 SEC 核心生产实现。

### 形式方法与 Rust 内核：三类证明对象，不是一套第二编译器

[形式证明、模型检查与可信边界](../运行/验收/方法与独立证据.md#形式证明模型检查运行时保证与可信边界)仍是唯一 assurance owner；本节只规定 Rust 物理方向与证明工具如何接合。证明方法按 `ProofObligation / VerificationMethodSelection / Evidence` 选择，不建立 `FormalEngineeringIR`、第二 Semantic Contract 或永久必装的“Verus + Lean + TLA+”工具栈。

| 证明对象 | 合适的 Provider 角色 | SEC 的采用边界 |
|---|---|---|
| Rust 实现级不变量 | Verus、其他 Rust verifier、Miri／sanitizer／property tools 等可按义务竞争；Verus 当前能静态验证带规格的 Rust 子集并支持部分低层代码证明 | 只证明其实际支持并建模的 Rust 程序／性质；不因 verifier 通过就证明 Semantic Contract 正确、外部 Provider 行为或生产二进制映射 |
| 语言无关语义与算法定理 | Lean 4、其他 theorem prover 或独立小 checker 可证明 canonicalization、有限代数、fixed-point 条件、编码保持等 | theorem/model 与 SEC canonical contract 之间必须有显式 mapping；proof kernel／版本／公理进入 TCB 和 Evidence，工具升级或 soundness 修复会使相交证据重新判定 |
| 并发／分布式／恢复协议模型 | TLA+/TLC、其他 model checker 或有限状态枚举器可检查 transaction、journal、lease、generation、fencing、rollback／recovery 等 safety/liveness | 模型检查只覆盖声明的状态空间、fairness、故障和环境假设；它不替代 Rust 源码证明、真实部署 failure injection 或 main/readback Evidence |

同一义务可以组合多类方法，但不能用“工具数量更多”制造独立性：若它们共享错误 specification、翻译器或假设，仍属于共同故障域。形式结果的 producer identity、工具版本、配置、模型／程序 revision、假设、checker 和实现映射继续由 assurance owner记录；Rust crate、Lean theorem 或 TLA+ spec 都只是该 Evidence 图中的主体／方法，不获得运行 authority。

外部插件不使用不稳定 Rust ABI 作为长期生态协议：仓库内同工具链扩展可以静态组合；跨版本、第三方或不可信扩展使用已有版本化协议／隔离机制，必要时选择 Wasm 或进程边界。Cargo feature 只承担真实的构建能力组合，不把互斥 TargetProfile、用户策略或未来所有控制维度编码成 feature 爆炸。

工具链本身也进入可复现输入：正式 Rust 区域固定可解析的 toolchain/target、Cargo lock 与构建配置；build script、proc-macro、代码生成器和 native link 都作为供应链／构建 effect 管理。没有真实需求不把 nightly、全局 allocator 技巧、零拷贝或 unsafe 当成“更底层所以更先进”的默认；需要时由相交 owner 给出收益、失败和退出证据。

### 反转条件仍然真实

Rust 已作为长期默认物理方向，不再每次任务重新“比较所有语言”；但这不是不可证伪信条。真实纵切面若显示 Rust 在同一合同下无法满足必要平台／工具／增量反馈／维护边界，或另一机制在完整迁移、供应链、调试、发行和退出成本下有决定性优势，就重开**受影响区域**而不是重开全平台语言战争。单次微基准、代码行数、个人熟悉度或某后端用 Rust 都不足以反转；同样，沉没成本也不是继续错误路线的理由。


## 同口径纵向验证与改模实验

比较前固定一份足以暴露真实机制的任务：持久实体与revision输入、带删除的快照、全量／增量依赖查询、有约束的候选选择、带来源的结果与一次局部修改。输入包括字符串／类型重复、稀疏和密集关系、长链／递归分量、负依赖、冷暖缓存、失败与取消；规模和硬预算来自实际目标，不在本文虚构统一节点阈值。

保持同一允许行为、错误、数值、观察、工具环境和输出资格，再比较初始实现、类型检查／编译反馈、正常与尾延迟、峰值存活内存、分配与复制、并发、启动、编码／FFI／IPC、崩溃恢复和发行。运行成本与开发改模成本分别记录；行数少、编译错误少和一次最快样本都不是完整维护收益。

至少演练新增状态、新控制、旧格式读取者、存储替换和一项新增失败。记录实际改变的公共合同、owner、消费者、证明义务、测试与迁移，而不是给package数量设武断阈值。穷尽match暴露遗漏有价值，但通配分支、未检查反序列化、unsafe、动态载荷或错误的旧模型仍可留下漏洞；“编译通过”不能等价为“影响已经全部闭合”。

已确定的硬条件可提前排除不合格路线，不必为了形式公平完成所有语言原型。缺少区分证据时保留合格现状或限定试验，不编造迁移百分比、固定收益倍数或团队速度。结论发生反转时更新对应实现决定与所有真实消费者，仍正确的语义、Oracle、案例和来源继续保留。

## 实现接合与正常退出

选定原生核心时，把共享同寿命数据的连通计算留在同一执行区域；跨边界传准确快照／请求／结果或粗粒度查询，避免每节点往返完整IR。一次性嵌入、可选暖服务、原生扩展与隔离进程均按实际调用成本和信任选择；不预设永久守护进程。接口须有输入版本、支持能力、取消／完成、诊断归属和结果寿命，不把零拷贝指针当永久跨进程引用。

TS产品面可以继续存在；实现语言的选择不改变目标代码的运行性能承诺，也不要求重写目标语言前端、完整类型检查器或成熟工具。复用某编译器的CLI不等于其嵌入API兼容；版本、Host读取、解析／类型／发射能力分别接入。动态特性必须区分规范存在、实现存在、API可用、默认启用、指定平台测试及安全维护，不能只写supports=true。

整个演进遵循[七类变化](../作者/组合/语义扩展与领域接合.md#mechanism-evolution-classes)和原S0—S8采用链：先固定语义与机制差额，再取得有范围的证据，形成后继绑定／迁移，处理旧调用与资源，最后退役旧消费者。纯参考模型可以长期保留为Oracle；临时重复生产内核、未受支持的插件版本和只能靠聊天解释的运行入口不因此获得永久保留资格。
