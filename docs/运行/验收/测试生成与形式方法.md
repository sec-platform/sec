## 实验、灰度发布、现场证据与因果推断

### 1. 上线观察需要因果边界

指标变化可能由季节、流量、用户构成、外部事件和其他发布共同造成。相关性不能自动证明新设计有效。

### 2. ExperimentPlan

```text
ExperimentPlan = exact {
  hypothesisAndClaim,
  populationAndEligibility,
  assignmentMethod,
  treatmentAndControl,
  primaryAndGuardrailMetrics,
  sampleAndDurationPolicy,
  contaminationAndInterferenceModel,
  stoppingAndRollbackRules,
  privacyAndRiskConstraints,
  analysisMethod
}
```

### 2.1 分配、求值、曝光与指标不是同一个事件

实验分析不能把“部署了某制品”“被随机分配到treatment”“运行时flag/variant求值为treatment”“用户实际经历了会受该变化影响的路径”“随后产生某指标”压成同一事实。至少保留下列关系：

```text
Deployment / Availability
→ Assignment
→ RuntimeVariantDecision
→ ExposureOrTriggerObservation
→ MetricObservation
→ CausalAnalysis / Verdict
```

每条箭头都可能不成立：客户端可能离线、配置缓存可能陈旧、用户可能从未进入相交路径、运行时Provider可能失败/回退、曝光日志可能丢失、指标可能来自另一个设备或产品。Assignment由实验设计拥有，运行变体由实际Provider/配置拥有，Exposure只是运行Observation，最终因果判断仍由预先声明的analysis method承担。

```text
ExposureObservation = exact {
  experimentAndAssignmentRefs,
  runtimeVariantDecisionRef?,
  subjectOrCohortRef,
  artifactEnvironmentAndConfigRefs,
  exposureDefinitionRevision,
  observedInteractionOrTrigger,
  observedAtAndTimeBasis,
  coverageAndMissingness
}
```

`subjectOrCohortRef`按隐私和实验需要选择，不要求把个人身份复制进平台；只需聚合的任务可保存充分的分群/计数证据。曝光定义本身有revision，例如“加载页面”与“真正渲染新组件”不是同一exposure。

### 2.2 分析人群与estimand必须预先对应

默认随机分配产生的因果资格不能靠事后只保留“treatment中真正看见功能的人”维持；实际曝光常受用户行为影响，直接在一侧按结果后变量筛选会破坏原随机化。需要triggered/affected分析时，方法必须预先说明目标estimand及怎样在control侧定义可比较人群，例如使用能在两侧同义判定的trigger规则、counterfactual logging或其他有依据方法。

Intent-to-treat、triggered/affected、per-protocol等不是一个可互换标签；每种分析保留population、selection rule、missingness、interference和能支持的Claim。主分析与探索性分群分开，不能看到结果以后换人群再把新结果冒充原primary hypothesis。

跨产品/设备join同样保留未匹配率和join方法。只有Product Y有日志的Product X treatment用户不能代替Product X的完整assignment population；数据缺失、客户端不上报和隐私限制分别记录，不能把join失败变成“没有行为”。

### 3. 灰度

canary/ring/feature flag 限制 blast radius，但必须代表关键环境和用户。只选健康内部流量会低估风险。

### 4. 干扰

用户之间、服务之间和缓存/模型共享会违反独立样本假设。需要 cluster assignment、switchback、时间序列或其他适当设计。

### 5. 守护指标

性能收益不能以错误率、安全、隐私、可访问性、成本和长期维护恶化换取。硬边界触发立即停止。

### 6. 现场证据

现场 evidence 有时间、版本、环境、流量和选择偏差。它可以升级或降级 SupportClaim，但不能无边界外推。

### 7. 验证

样本比例不匹配、提前停止、指标操纵、新奇效应、组间溢出、数据缺失、分群伤害、回滚失败和并发发布。


## 性能、容量、尾延迟、资源与成本真值

### 1. 性能 Claim 必须绑定场景

```text
PerformanceScenario = exact {
  userOrOperationGoal,
  exactInputAndScale,
  environmentAndResourceClass,
  correctnessAndVerificationOutcome,
  workloadShape,
  concurrencyAndArrivalPattern,
  warmColdState,
  measurementMethod
}
```

### 2. 指标

wall、CPU、RSS、I/O、网络、queue、startup、materialization、execution、cleanup、readback、cache hit/miss、physical starts、cost 和 energy 分开。平均值不能替代 P95/P99、最坏界和长尾。

### 3. 样本

单次样本不能产生 percentile。分布需要样本量、稳定环境、异常值政策和置信范围。跨环境不可直接比较。

### 4. 容量

容量模型结合 arrival rate、service time、并发、资源 pool、burst、backpressure、failure/retry 和 recovery reserve。CPU 充足不代表 memory/IO/lock 可用。

### 5. 优化 Claim

```text
OptimizationClaim =
  baseline + mechanism + expected critical path change
  + correctness equivalence
  + new state/cache/provider
  + failure/recovery
  + before/after evidence
  + rollback/retirement
```

### 6. 成本

云费用、开发时间、认知、维护、迁移、退出和事故成本保留为向量。价格和供应商条件有 revision 和地域。

### 7. 验证

冷缓存、热缓存和禁用缓存；小规模与大规模；高并发、资源压力、尾延迟、长会话、失败恢复、跨平台、前后等价和回归阈值。


## TestCase 的适用边界与责任

TestCase 不是所有 Verification requirement 的默认物化形式。先由[验证责任、所有权与方法选择](方法与独立证据.md#验证责任所有权与方法选择)确定 Proof Obligation 与 VerificationMethod；只有当 obligation 需要通过可执行 case 区分行为、状态、故障或真实入口时，才建立或复用 TestCase。可由类型系统、Source Program、架构规则、静态安全分析、形式方法、运行 readback 或有权人工判断直接支持的 Claim，不应为了统一成“测试”再包装一层 `.test.ts`。

对于仓库自身规则，生产 checker 直接检查当前仓库；TestCase 只校准 checker 的正例、反例、边界、解码和失败含义。这样一条规则只有一个生产定义，不再同时维护“规则实现 + 当前源码字符串镜像测试”两份真值。

```text
Claim
→ ProofObligation
→ MethodSelection
→ [method = TestCase] TestResponsibility / TestFamily
→ VerificationAction
→ Provider execution
→ Evidence
```

TestResponsibility 至少能表达：

```text
TestResponsibility = exact {
  stableTestRef,
  ownerRef,
  obligationBindings[
    claimOrRequirementRef,
    failureMeaning,
    observationBoundary
  ],
  proofMechanism,
  environmentAndResourceRequirements,
  independenceAndOracleRefs,
  impactRelations,
  lifecycleAndRetirement
}
```

这些语义只保存一次；source census、runtime discovery、Test Impact、runner suite 和报告均为 projection/observation。路径、标题、`unit/integration/e2e`、`fast/slow`、suite 名和 runner 参数不是 TestCase semantic identity，也不能单独决定 requiredness、重要性、owner 或资源需求。

## 性质、模型、故障、模糊、变形、差分与突变测试

### 1. 测试机制分工

| 机制 | 主要发现 | 不能单独证明 |
|---|---|---|
| 单元/契约 | 局部示例和接口 | 未枚举输入与组合 |
| Property | 普遍不变量的随机/生成样本 | generator 未覆盖空间 |
| Model-based | 状态机和序列 | 模型本身正确 |
| Fuzz | parser/边界/崩溃 | 业务语义完整 |
| Metamorphic | 无 oracle 时关系性质 | relation 选择正确 |
| Differential | 多实现不一致 | 哪个实现正确 |
| Fault injection | 故障、恢复和 residue | 未注入故障类别 |
| Mutation | 测试能否杀死人工缺陷 | mutant 代表真实故障程度 |
| Formal/model checking | 有界状态和性质 | 现实环境完整性 |

### 1.1 Instrumentation、coverage与动态分析资格

coverage、sanitizer、fuzzer和symbolic/model-checking结果都进入现有VerificationAction/Evidence，不建立新的“工具绿色”真值。每次方法运行至少固定：被测subject/artifact、工具及revision、编译/插桩profile、environment、输入/语料、预算、实际覆盖和输出资格。

```text
VerificationInstrumentationProfile = exact {
  subjectAndArtifactRefs,
  compilerToolAndRevisionRefs,
  instrumentationKindsAndOptions,
  instrumentedAndUninstrumentedRegions,
  optimizationAndDebugMapping,
  runtimeAndEnvironmentRefs,
  expectedOverheadAndBehavioralPerturbation
}
```

**Coverage。** line/region/function/branch/condition/MC/DC等是不同指标；百分比必须绑定其instrumented subject、mapping revision、实际运行集合和excluded/uninstrumented范围。没有插桩的库不是“0% covered”，而是该报告不覆盖；100% line或branch coverage也不证明输入域、状态空间、异常、并发或Claim已经完整。

**Sanitizer。** ASan/TSan/MSan/UBSan等是带插桩的动态检测方法。finding绑定实际触发输入、线程/进程、instrumented binary、tool revision和symbolization；无finding只支持“在本次实际执行与工具检测域内未观察到相应错误”。插桩可能改变性能、内存、调度和布局，因此sanitizer run不能直接作为生产性能/实时Evidence；未插桩模块和外部组件保留coverage gap。

### 1.2 Fuzz campaign不是“跑了多久”

```text
FuzzCampaign = exact {
  targetHarnessAndSubjectRefs,
  fuzzerAndInstrumentationRevision,
  seedCorpusAndDictionaryRefs,
  mutatorAndGeneratorConfiguration,
  randomSeedAndWorkerTopology,
  inputAndTimeResourceBounds,
  sanitizerAndOracleRefs,
  coverageFeedbackDefinition,
  discoveredCorpusGeneration,
  failureArtifactRefs,
  stoppingReasonAndCoverage
}
```

corpus是可演进测试输入资产，不是产品Evidence本身；“新coverage feature”只是该fuzzer反馈定义下的新信号，不是业务状态空间覆盖比例。并行worker共享corpus时，发现顺序和总corpus generation进入可重复解释；时间到、runs到、OOM、timeout、crash和用户取消是不同停止状态。

crash/timeout/OOM reproducer固定原input、subject、环境和failure identity。minimizer/shrinker只有在重放仍触发同一根failure时才能替换为更小reproducer；把ASan UAF缩成另一个assert失败不能称同一故障最小化。修复后reproducer可进入回归集，但“旧crash不再出现”不自动证明漏洞根因或全部同类输入已经闭合。

### 1.3 Symbolic execution、model checking与solver结果

形式/符号方法固定模型/程序翻译、property、assumptions、bound、search strategy、solver/checker revision、资源限制和result kind。`sat/counterexample`首先是对该模型/编码的见证；映射到真实实现需要另外证明source/IR/target correspondence。`unsat/proved`只在实际逻辑、假设与界限内成立；bounded model checking没有资格越过bound声明全状态安全。

timeout/resource-exhausted/unknown与proved/failed分开。solver自己的成功码不能独自成为顶层Oracle；有proof certificate/independent checker时可缩小可信计算基，但certificate checker本身仍有版本和输入资格。多个solver一致只增加独立Evidence，不能把共享错误编码投票成真。

### 2. TestCase 元数据

每个长期保留的 TestCase/TestFamily 绑定稳定 identity、唯一责任 owner、一个或多个 obligation binding、每条 binding 的 Failure Meaning、真实 observation boundary、所需 environment/resource、Oracle/independence、impact relation、lifecycle 与 retirement。字段由真实 consumer 驱动，不为“完整表格”制造无人消费的 metadata。路径和标题只是 locator；文件移动、标题润色和 suite 重排不能产生新的证明身份。

Failure Meaning 属于 **TestCase × Obligation proof edge**：同一 canonical obligation 可以有纯算法 proof、物理 provider proof 等不同独立观察，并分别暴露不同 failure class。replacement/merge 比较的是 obligation coverage 与 observation independence，不要求不同 proof 使用相同错误文案。

<a id="snapshot-golden-oracle"></a>
### 2.1 Snapshot、Golden与Visual Baseline是Oracle资产

snapshot/golden/approval/visual-regression测试把一个固定期望Artifact作为Oracle的一部分。实际输出、比较器、baseline和“接受新baseline”的决策必须分开；测试失败不能通过同一动作自动把actual写成expected。

```text
SnapshotOracleBinding = exact {
  testAndObligationRefs,
  baselineArtifactAndRevision,
  baselineEnvironmentProfile?,
  serializerRendererAndComparatorRevision,
  normalizationMaskAndToleranceRules,
  actualObservationRef,
  diffArtifactRefs,
  oracleAuthorityAndAdoptionRefs,
  provenanceAndInvalidationTriggers
}
```

**Baseline是作者/验收资产。** 新增或更新baseline形成普通Candidate/Mutation，说明是需求有意变化、平台基线变化还是测试本身修复；真正采纳走原review/authority。`--updateSnapshot`、`--update-snapshots`等runner动作只能生成候选baseline及diff，不能因当前测试失败获得修改Oracle的权限。首次运行自动产生golden时也只是候选，除非该测试方法有独立可信生成规范能够直接确定期望。

**比较规则属于Oracle。** serializer、字段排序、时间/ID scrubber、mask、pixel threshold、color space、font/render profile和数值tolerance改变都会改变“通过”的含义，因此有revision并使相交Evidence陈旧。为消除噪声新增mask/tolerance必须验证不会遮住被测Claim；把每次不同的字段全部忽略可以让测试永绿但没有资格。

**Visual snapshot绑定环境。** browser/OS/font、viewport/DPR、color profile、GPU/render backend、locale/theme、animation/clock和accessibility preference都可能改变像素。可以选择规范化/容器化环境或按明确环境维护多个baseline；不能运行失败后挑一张最接近的baseline。像素相同也不证明DOM、AX、交互或业务语义相同；视觉Evidence只支持相交视觉Claim。

**Snapshot差异不是根因。** actual与baseline不同只说明在比较器范围内不等；来源可以是产品bug、合法需求变化、环境漂移、serializer升级或baseline本身错误。先定位变化，再决定修产品还是提baseline candidate。旧baseline的历史Evidence不因新baseline采纳被改写。

**独立性。** 用被测实现本身在同一输入上生成baseline，再拿当前输出与它比较通常不能成为独立正确性Oracle。Golden可以来自规范手工值、独立实现、已验证历史release、固定参考数据或其他合格方法；来源和独立性进入Evidence。

未使用/孤儿snapshot的删除同样先确认TestCase/历史回归/支持版本消费者和保留义务；当前一次test discovery没列出它不等于永久无消费者。

### 3. Generator 和 Shrinker

生成器必须覆盖有效、无效、边界、冲突和未知。shrinker 保持 failure identity，不得缩成另一故障。

### 4. Fault Model

故障族至少覆盖：输入损坏、并发、超时、取消、资源耗尽、进程 crash、网络分区、存储失败、权限变化、provider drift、恢复失败和攻击。

### 5. Mutation 使用

突变测试只用于校准测试敏感性，不能把 mutation score 当产品质量。mutant 生成规则、等价 mutant 和不可达代码需要显式处理。

### 6. 验证

测试框架自身要通过 seed 可重放、clean environment、cache-off parity、oracle integrity、fixture isolation 和长时运行污染检查。


## 恢复演练、备份可恢复性与灾难验证

### 1. 有备份不等于可恢复

恢复能力要求备份内容、身份、完整性、可访问性、密钥、工具、人员、时间和目标环境都可用。

### 2. RecoveryCapability

```text
RecoveryCapability = exact {
  protectedSubjectAndObjectives,
  backupAndJournalRefs,
  backupGenerationAndRetention,
  encryptionKeyAndAccessRefs,
  restoreProcedureAndToolchain,
  targetEnvironment,
  RPOAndRTOClaims,
  drillEvidence,
  dependencyAndCommonCauseRefs,
  operatorAndEscalationRefs
}
```

### 3. Drill

定期在隔离环境从零恢复，并验证业务不变量、权限、数据完整性和可运行性。只校验压缩包可解压不够。

### 4. Common Cause

备份、控制面、密钥和文档不能全部依赖同一账号、区域、存储或软件。恢复路径需要独立性分析。

### 5. 失败状态

备份缺失或损坏、密钥不可用、模式或工具不兼容、恢复时间目标超限、部分恢复、外部依赖不可用和操作员状态未知。

### 6. 删除与恢复冲突

法律删除和用户遗忘要求必须传播到备份；恢复旧备份后使用墓碑/删除 ledger 防止数据复活。

### 7. 验证

随机恢复演练、区域不可用、凭证撤销、旧工具链、大规模恢复、写入期间备份、恢复中断、租户错误和旧数据复活。


## 测试生成、选择与故障体系

### 1. 从声明到验证，再到测试

测试不是按目录全跑的脚本集合，也不是所有 Claim 的强制中间层。完整流程是：

```text
Requirement / Claim
→ Proof Obligation
→ Applicable VerificationMethod
→ [需要 case 时] TestResponsibility / TestFamily
→ VerificationAction 或纯静态求值
→ Evidence qualification / coverage
```

每种方法说明能证明和不能证明什么。只有方法已经选择为 TestCase/property/model/fault 等 case-based verification 时，本节后续的测试生成、选择、fixture 与 runner 规则才适用；类型、架构审计、静态安全、形式证明、runtime readback 和人工有权判断保持各自方法身份。

### 2. 测试层次

| 类型 | 主要证明 |
| --- | --- |
| 类型/Schema | 各自声明片段的结构/类型约束；普通JSON结构不自动提供名义身份、真实引用或行为闭合 |
| 单元 | 纯函数和局部规则 |
| 属性 | 幂等、往返、单调、增量等价 |
| 契约 | Port、Adapter、Provider、协议 |
| 集成 | 文件、进程、存储、网络组合 |
| 端到端 | 用户目标到重新观测闭环 |
| 故障 | 崩溃、超时、资源、重复、乱序 |
| 对抗 | 越权、污染、欺骗和边界绕过 |
| 性能 | 工作负载和资源目标 |
| 运行 | 部署读回、SLO 和恢复演练 |

### 3. 影响选择

测试选择输入：

- 精确 `SemanticDelta`；
- 反向依赖；
- 声明覆盖；
- 目标画像；
- 风险和变更类型；
- 历史失败；
- 迁移阶段；
- 政策。

零新增执行要逐项解释：全部适用义务已被当前合格结果覆盖，则返回复用/满足及其证据；确无适用动作时返回`NoApplicableAction`及范围依据；二者都不足才返回覆盖缺口。不能以空列表自行签发通过，也不能否定已经有依据的合格复用。

### 4. 测试生成

可生成：

- 边界值；
- 状态机路径；
- 类型和 Schema 实例；
- 约束反例；
- 变形关系；
- 随机/属性样本；
- 并发交错；
- 故障注入点；
- 跨后端差分输入；
- 安全恶意输入。

生成器也需 revision、seed、覆盖和缩减回执。

### 5. 故障模型

统一故障类别：

```text

Timeout
Cancellation
ResourceExhaustion
PartialWrite
ResponseLoss
Duplicate
Reorder
Partition
ClockSkew
PermissionRevocation
ProviderDrift
DataCorruption

LateWriter
```

每个持久状态机对相关故障定义期望下一步。

### 6. Flake

Flake 不是简单重跑后忽略。系统区分：

- 测试本身非确定；
- 被测系统竞态；
- 环境污染；
- 外部依赖波动；
- 时序门槛不稳定；
- 数据共享。

确定性失败可复用；瞬态失败按分类重试并保留首次证据。

### 7. 测试隔离

测试环境绑定：

- 候选摘要；
- 工具链；
- 依赖；
- 配置；
- 数据集；
- 秘密和权限；
- Host 能力；
- 网络模拟；
- 清理回执。

环境无法清理时销毁，不把污染状态复用给其他租户或候选。

### 8. 覆盖

覆盖不只统计代码行，还包括：

- Claim；
- 状态和转换；
- 错误分支；
- 权限正负路径；
- 资源边界；
- 目标画像；
- 数据版本；
- 故障；
- 迁移阶段；
- 不透明边界。

### 9. Test Oracle

Oracle 可来自：

- 明确定义；
- 参考实现；
- 形式模型；
- 多实现一致；
- 变形关系；
- 目标系统权威读回；
- 人工有权判断。

被测实现不能独自生成 Oracle。

### 10. 验收

- 每个高风险 Claim 有匹配方法；
- 影响选择无漏测；
- 空选择不通过；
- 故障点覆盖每个非终态；
- 属性失败可缩减；
- Flake 分类和隔离；
- 环境可复现；
- Oracle 独立；
- 测试自身有契约和版本；
- 运行证据可追到测试定义。
