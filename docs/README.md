## 把整套设计作为一个可用成果

**现行权威不是某个历史ZIP或这张路线图，而是同一提交中各责任文件的完整集合。** [系统架构](架构/总体设计.md)拥有系统协作，[产品要求](产品/产品要求与工作约束.md)拥有必须满足的目标，[作者含义](作者/第一层语言.md)与[结构作者源](作者/结构化源码.md)拥有可维护的工程决定，[编译](编译/README.md)与[运行](运行/README.md)分别拥有生成和真实作用。横向导航不复制字段、算法或错误码；局部正文独立使用时仍具有完整的适用条件与失败处理。

### 一个工程决定在整套规范中的去向

| 本次实际工作 | 从哪里开始 | 输出或必须核对的下一责任 |

这张表的顺序是**责任传递的读图方式**，不是每项请求必须运行八步的时间流水线。一次查询可以在取得合格结果处终止；只要求设计、源码、构建、部署或长期运行时，分别在自己的完成边界结束。完整系统中的输入、结果、失败及修订实例见[总体架构](架构/总体设计.md#cross-domain-intent-closure-case)，细节在上表各原拥有者，不用本表取代。

### 按三种角色直接使用

- **工程作者 / AI 客户端**：用[作者入口](作者/README.md)明确本次真正要决定的内容，并查看[真实作者范本](../examples/README.md)；不手填内部IR、研究维面或可推导的默认值。编辑与审批进入[开发主链](开发/需求到交付主链.md)。
- **实现者 / 维护者**：从[实际模块装配](架构/装配/README.md)、[编译与目标](编译/README.md)进入所需真实合同；把设计选择、实现、已执行测试和部署状态分别记录。不能用名称相同的历史原型替代当前协议。
- **设计审查 / 交付者**：按[REQ](产品/产品要求与工作约束.md)→[当前设计与D理由](决策/README.md)→[U未决](状态/README.md)→[独立验收方案](运行/验收/README.md)核相交消费者；缺最新原件时保留证据边界，不把索引齐全写成完整保义。

### 取得一个离线、单文件的完整阅读版

需要一份可连续搜索、展开全部当前设计正文与图的交付件时，**不要人工复制第二套可改规范**。从同一准确Git提交检出当前文档和生成工具，执行[阅读构建](维护/阅读构建.md)已规定的命令。以下命令只在拥有该提交的完整仓库工作区运行，输出在源树外：

~~~sh
python -m pip install -r tools/documentation/html-requirements.txt
python -B tools/documentation/build_html.py --output ../Gift.html
~~~

若目标文件已经存在，遵守该构建器的 `--replace` 规则；图缓存须与当前Mermaid图源严格一致，不能以旧渲染冒充新图。**HTML是同版本完整正文的只读派生，不是另一份规范、已经运行的软件或“所有来源已融合”的证明。** [全文与目录](内容索引.md)、[阅读构建的失败条件](维护/阅读构建.md)和[文档身份](维护/文档身份与重组协议.md)共同限定实际输出范围。

历史研究、冻结的未采用方案及精确原件从[历史来源入口](../alternatives/本地草稿封存/README.md)按需要另读；它们不是完成现行设计阅读的前置包。需要提出“全部历史都已吸收”的结论时，仍须先取得精确原件并核对独立规则、消费者与恢复责任，参见[归档准入](维护/交付材料与归档.md#source-archive-admission)。
