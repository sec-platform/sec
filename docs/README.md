先确定产品范围与系统边界，再按问题进入子系统。本文只负责导航，完整定义、字段、算法与失败条件由各主题的唯一正文维护。

## 系统层

[产品范围与约束](产品/README.md)说明要交付什么；[总体架构](架构/总体设计.md)说明系统与环境、责任协作、状态与部署；[装配与实现接合](架构/装配/README.md)进一步定位模块、接口和生命周期。系统架构不隶属于某一个编译阶段。

## 子系统与专门机制

| 主题 | 回答的问题 |
|---|---|
| [作者](作者/README.md) | 工程含义怎样表示、组合、固定选择并持续修改？ |
| [编译](编译/README.md) | 怎样解释准确输入、取得合格实现并生成完整目标产物？ |
| [开发](开发/README.md) | 人、AI和工具怎样编辑、检查、协作与继续开发？ |
| [运行](运行/README.md) | 真实作用、权限、资源、结果和恢复怎样结算？ |
| [领域](领域/README.md) | 不同计算、状态、时间、关系和数值机制怎样精确定义？ |
| [信息](信息/README.md) | 工程内容、来源、版本、查询和保留怎样管理？ |
| [演进](演进/README.md) | 怎样扩展、实施、迁移、兼容和退出？ |

这些是文档责任，不规定同数量的进程、服务或产品模块。具体模型名称、协议字面量和表示格式在相应主题内定义；不从阅读到某个例子推定整个产品必须采用它的内部结构。

## 判断、范本与维护

[决定](决策/README.md)保存选择与代价；[状态](状态/README.md)保存尚未完成的范围；[依据](依据/README.md)保存来源和反例；[维护](维护/README.md)只负责本库的组织、修改与交付。它们不是每次操作必须逐页通过的手续。

## 快速查找：用了什么、为什么不用其他方案

长期产品决定从[决定与理由](决策/README.md)进入；具体机制的采用、拒绝、平台限制和重开条件保存在各自正文，不另建第二份决定台账。仓库执行接合可直达：

- [GitHub 凭证与异步传输的方案、替代与测试入口](开发/AI协作/规则装载与任务恢复.md#github-credential-transport-decision)
- [严格零写观察与测试进程的反例、采用边界和待验证方案](开发/AI协作/规则装载与任务恢复.md#repository-observation-runtime-decisions)

“采用”是设计决定，“候选／待验证”不是已具备能力；运行证据与发布状态按准确对象另查。
工程执行中的设计、实现、验证、审查、提交／集成与恢复怎样选择规则和Skill，见[工程行为路由及实际接合边界](开发/AI协作/规则装载与任务恢复.md#engineering-behavior-routing)；客户端角色配置不自行签发权限或证明规则已装载。
