### 001-008（行 3-2988）

抽取状态：已分段抽取，待逐条去重与映射。

- 功能块 / 文件组织应作为 AI 时代的工程单元，而不是普通代码目录切分。
  - 功能块面向用户能力组织，例如登录、租户、客户、工单、附件，而不是按 controller/service/model 等实现层拆分。
  - 功能块需要携带 manifest、接口、依赖、验收、来源和可组合信息，才能成为 AI 可理解、可复用、可验证的单元。
  - 开发者关注点应从“实现测”转向“用户能力是否成立”，但实现仍要可追踪、可覆盖、可回退。
- 与 n8n 的边界被反复区分。
  - n8n 更像 workflow/API glue/automation runtime。
  - 本项目目标是生成和维护一个真实代码工程，并对 block、slot、graph、acceptance、provenance、upgrade 形成工程级治理。
  - n8n/OpenClaw 可被当作后续 runtime adapter 或 strategy backend，而不是第一版产品核心。
- 与 vibecoding / AI agentic IDE 的关系。
  - 用户直觉是：这可能像 vibecoding 时代的新开发者语言，但不应退化为“更强聊天式代码生成”。
  - IDE + AI agentic 工具能提高编辑效率，但缺少项目级 contract、来源、验收和升级治理时，会继续依赖整仓搜索和自由改代码。
  - 本项目更接近“工程编译器 / 受控 AI 编程 / 规格驱动项目生成”。
- 官方/社区模板、开源与商业化。
  - 官方 block 提供稳定、可验证、可维护的高质量基础能力。
  - 社区 block / template 可形成生态，但必须有 trust、version、provenance、policy、upgrade 约束。
  - 商业化不应只卖模板，而应卖可验证的能力供应链、行业包、治理控制台、企业私有 registry 和升级保障。
- 高性能、高并发、高可用、低延迟能力的处理方式。
  - 不应让 AI 临场手写所有专家级基础设施代码。
  - 更适合沉淀为 Strategy Pack / Infra Pack / Kernel Boundary，由平台通过 pins、constraints、benchmarks 和 adapter slot 组合。
  - 这类能力可减少 AI token 和不确定性，但不会消灭专业工程判断。
- 对 AI 智能和 token 的影响。
  - 平台不是让模型“变笨”，而是减少模型需要猜测和全仓搜索的范围。
  - 通过 block graph、manifest、pin、slot、acceptance、provenance，把上下文从“全代码仓库”压缩为“任务相关因果上下文”。
  - 模型仍需处理开放 slot、局部业务逻辑、接口适配、修复解释和设计建议。
- 对程序员和架构师的影响。
  - 项目可能减少重复造轮子和重复商业代码逻辑。
  - 程序员不会消失，但工作重点会从重复 CRUD、样板集成、胶水逻辑，转向规格、验证、治理、行业能力沉淀和异常处理。
  - 架构师价值会从口头设计转向可执行 block、contract、policy 和 graph。
- 前人类似思路与失败原因。
  - 低代码、脚手架、模板市场、框架、SDK、组件库都覆盖过局部，但通常缺少完整工程生命周期和 AI 时代的上下文控制。
  - 失败或未成型的原因包括：源码所有权不足、验收不可执行、模板不可升级、生态质量不可控、缺乏 provenance、AI 未成熟、开发者不接受黑盒。
- 最可行 MVP 方向。
  - Git-native Capability Registry + Composer + Acceptance Runner 是更小切口。
  - 第一版不追求完整工作台、实时图编辑器、全行业 registry 或复杂 runtime。
  - 用覆盖最广的多租户 B2B SaaS 母例来验证：登录、租户、客户、附件、CSV、主验收链路。
- IR、复制代码、skill、SDK 的区别。
  - 即使存在 IR，落地仍可能复制或生成源码；关键差异不是是否生成源码，而是生成前后的 contract、provenance、verification 和 upgrade 语义。
  - Skill 更像给 AI 的操作知识或流程提示；Block 是可安装、可组合、可验证、可治理的工程资产。
  - SDK 提供调用能力，不能自动解决项目组合、验收覆盖、来源追踪和演进治理。
- AI 不必细写与仍需细写的代码。
  - 不必每次重写通用登录、租户隔离、基础 CRUD、标准权限、标准导出、基础附件等成熟能力。
  - 仍需实现业务特定 normalization、adapter、policy 细化、字段映射、边界胶水、局部 UI/交互和异常修复。

### 009-018（行 2989-5645）

抽取状态：已分段抽取，待逐条去重与映射。

- 飞轮与文件复制。
  - Registry 中的 block 越多，AI 和开发者越倾向复用已有可验证能力，进一步推动 block 沉淀。
  - 第一阶段可以通过文件复制 / scaffold 落地，但必须同时生成 lock、manifest、provenance 和 acceptance，否则只是普通模板复制。
- MVP 代码量与边界。
  - MVP 应压缩为一个母例、三类核心 block、一个 slot、一条 acceptance 主链路。
  - 编译器、registry、生成项目、验收、报告和 CLI 的代码量可控；不应第一版就做完整平台和生态。
- TS / Java 选择。
  - 新项目在 vibecoding / agentic 时代更适合选择 TypeScript/Next.js 这类全栈样例，便于端到端演示和快速 dogfood。
  - Java 仍适合成熟企业生态、高并发后端和强治理团队，但第一版母例不必选 Java。
  - 资深 Java 工程师也可以用 TS 路线做出第一版，只要把 contract、验证和边界设计好。
- 开源模板与官方方案复用。
  - 可以参考官方 starter、社区模板、框架最佳实践，但不能把它们直接等同为 capability block。
  - 只有补上 manifest、pins、acceptance、policy、provenance、version 和 upgrade 语义后，模板才接近可治理 block。
- 源码 100% 可控与快速搭建工具边界。
  - 生成源码必须留在用户仓库中，允许开发者阅读、调试、修改和接管。
  - 但源码可见不代表源码是唯一权威；权威还包括 spec、graph、lock、manifest、acceptance、policy 和 provenance。
  - 项目不能只定位为快速搭建工具，否则会失去长期维护和治理价值。
- AI 介入时机与任务控制。
  - AI 应在 compile/adapt/repair/review/upgrade planning 等受控 pass 中介入。
  - 每次 AI 任务都应有 task envelope、allowed paths、required symbols、forbidden operations、tests 和 budget。
  - 不能让 AI 作为系统主循环自由决定新增 block、改验收或改 generated artifacts。
- 编译器类比。
  - app spec / block graph / pins 像业务源语言。
  - resolved graph / install plan / lock 像项目 IR。
  - generated project 像编译产物，但仍是人类可读可调试源码。
- 为什么过去没人做到。
  - 单靠模板、低代码或框架缺少 AI 补 slot 的弹性。
  - 单靠 AI 缺少 deterministic contract 和验收闭环。
  - 单靠平台缺少源码所有权和开发者信任。
  - 三者在 AI 时代才更容易组合成可运行闭环。
- 开源、代码审查和系统方案经验。
  - 开源有助于建立 block 生态和可信度，但需要先有足够清晰的核心 contract。
  - 快速增长项目不可能所有细节都人工审查，因此需要 machine-checkable contract、policy gate、verification report 和 provenance。
  - `vibe review` 不能只看代码 diff，应逐渐转向语义 diff、acceptance coverage 和 provenance diff。
- 前后端范围。
  - 早期不能只做后端，否则用户能力链路不完整。
  - 但前端能力也不必一开始做成通用 UI builder，可先做 Next.js 页面、表单、登录、列表、工作区等母例。
- 不使用 Elysia。
  - 第一版不引入 Elysia，避免增加 runtime 变量。
  - Next.js/TypeScript/Prisma/SQLite 更适合作为 v0.1 可演示全栈闭环。
- 全栈开发式微与 Agent 分工。

  - 项目编译器比传统编译器难在需求语义、外部系统、长期演进、组织约束和不完全形式化。
- 项目上下文远超 AI。
  - 全源码不等于全上下文，项目真正上下文包括需求、历史决策、约束、运行行为、事故、组织规则和未写下的业务知识。
  - AI 遗漏上下文会导致错误堆积。
  - 平台应成为 AI context compiler，把任务相关的全信息熵组织成 context packet。
- Context Packet 内容。
  - 应包含 task、affected graph、blocks、pins、policies、writable anchors、readonly anchors、cannot_modify、must_preserve、verification、provenance、issue classification、runtime evidence。
  - 目标是减少对全代码仓库的依赖，让 AI 先处理因果上下文，再必要地下钻源码。
- Review 方式变化。
  - Review 不应只看代码 diff。
  - 应看 engineering semantic diff：能力变化、block 变化、policy 变化、acceptance coverage、provenance、runtime impact、upgrade impact、risk class。
