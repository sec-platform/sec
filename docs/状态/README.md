各主登记的采用决定和结构/执行落点直接读取原条目；旧实现、真实宿主输入及验证未取得时仍然保留其剩余，不能批量标成“已完成”。共同方法见[供给](../架构/实现供给与替换.md)、[强制](../架构/约束强制与整体一致性.md)及[扩展语义](../领域/扩展语义与适配合同.md)。

本页只定位已有问题；采用、准确状态、剩余义务、关闭和重开条件直接读取各 U 条目，方案与算法沿条目进入真实责任正文。实施顺序由[主线入口](../演进/实施/主线前沿与准入.md)按所选能力和依赖安排，问题数量不能作为完成率或排程。

## 如何区分剩余

同一问题可以同时包含以下剩余，不按 U 强制分成互斥类别：

- **条件性设计：** 当前有限合同已经成立；只有新的独立观察、接口、失败/恢复路径或现有矛盾被真实需求激活时，才扩展相交设计。触发前保留正确小方案，不预建完整世界模型、占位服务或“未来通用”类型。
- **事实、测量与具体供给：** 已定方法仍需要实际工具、Provider、成本、格式、平台或发行输入。继续写抽象规则不能代替这些事实，也不能从收益未知推导设计未定。
- **实现、符合性与证据：** 当前设计已定的范围直接进入获准实现、适配、运行、验证、迁移或收益测量；未运行、未部署、未测性能、SDK未取得不单独证明缺设计。实施反证确实改变前提时再回原 owner 裁决。

新发现先定位原 U/owner；已有合同能处理的反例仍归原项，不增加同义问题。条件扩展须在原处写清触发输入、有限方案为何不足、需保持的新观察和目标消费者，不能只把标题改成“支持更多”。有限子范围完成就移除对应活动剩余；只有父问题仍有独立未满足义务时继续开放。稳定主题、常设规则和未触发扩展不自动构成待办，旧尝试、真实作用、恢复和退役责任仍须结算。
