# 用户能力模块化开发主题整理稿

> 来源说明：本稿基于导出对话录 [用户能力模块化开发.md](D:\Project\pjc\docs\用户能力模块化开发.md) 重组而成。原文件保留为唯一原始材料；本稿用于统一概念、边界和判断。

## 核心命题

### 已定结论

- 这套方法不是“让 AI 帮人写代码”，而是把软件开发的基础单元从“代码文件/函数”改成“能力模块/功能包”。
- 开发者主要操作的对象应从实现细节转为工程规格：选择哪些块、块如何连接、哪些位置允许 AI 介入、什么验收才算合法。
- 系统的第一性输入应是 `spec / block graph / slot 定义 / acceptance`，而不是最终源码。
- 最终仓库源码仍然需要可见、可改、可审查、可提交，但它应被视为编译产物，而不是权威来源。
- 这套方法的目标不是做“更智能的脚手架”，而是做一种工程编译器：人写工程规格，系统装主干，AI 只填被声明的洞位。
- 开发关注点应从 implementation-first 转向 outcome-first：主验收标准是用户是否完成任务、链路是否闭环，而不是单个实现细节是否“优雅”。

### 工作假设

- 真正可用的能力模块应是“功能包”而不是代码片段，至少要携带：功能说明、输入输出契约、依赖关系、文件组织、运行入口、配置项、示例数据、验收规则、异常边界、可替换实现。
- 长期来看，开发者角色会从“低层实现者”转向“问题定义者、约束设计者、模块抽象者、验收治理者、例外处理者”。
- 如果规格层、块层和验收层稳定下来，软件知识的沉淀方式会从“分散源码经验”转为“可升级的模块与策略资产”。

### 待验证

- 这套方法是否能从窄栈场景扩展到更广的软件工业范畴，需要以后续真实项目复用率、升级成本、故障率来验证。
- “源码地位下降、规格地位上升”是否会被团队自然接受，需要在实际协作流程中观察。

## 为什么不是 n8n / SDK / Skill / 普通模板

### 已定结论

- 它不是 n8n 一类的节点编排。n8n 的粒度更接近动作级实现单元；这里的粒度是“用户可感知能力”，例如登录、客户管理、工单流转、合同信息提取。
- 它不是 SDK 复用。SDK 复用的是接口能力；这里复用的是“完整落地片段”，包括代码资产、配置、契约、测试和验收。
- 它不是 Skill。Skill 主要是 AI 侧的任务配方；这里要做的是 repo 侧的资产系统，负责解析、安装、接线、升级和验证代码资产。
- 它不是普通模板市场。模板通常解决“从零起步”；这里要解决的是“按规格装配、按约束连接、按验收验证、按版本升级”。
- 它不是单纯的“快速搭项目工具”。如果系统不能在没有模型参与时确定性地装配大部分模块，它就会退化成模板加 prompt。

### 工作假设

- 真正的差异点在于中间两层：`IR / 装配计划` 和 `Composer / 安装器`。没有这两层，就无法从“模板”提升到“编译系统”。
- 模块化软件生产的核心价值不在“少写代码”，而在“降低决策熵、降低不确定性、减少上下文负担”。

### 待验证

- 不同栈里的现成资产能否稳定映射成统一的 capability block，需要以后续 registry 设计验证。
- “模板之上的编译层”能否形成明显于现有脚手架和 codegen 的产品差异，需要真实用户测试验证。

## 系统主循环

### 已定结论

- 系统主循环应是：

```text
用户目标 / 工程规格
  -> 解析为装配计划
  -> Resolver 解依赖与冲突
  -> Composer 安装代码资产
  -> AI 填受控 slot
  -> Acceptance Runner 跑验收
  -> 产出可审查项目与锁定图谱
```

- 系统里至少有六个核心部件：
  - `Registry`：存放 capability blocks、strategy packs 等资产。
  - `IR`：把用户目标与约束编译成装配计划。
  - `Resolver`：根据 `requires / provides / conflicts / install order` 求解组合。
  - `Composer`：安装文件、合并依赖、生成注册表与骨架。
  - `Adapter Generator`：只在必要洞位让 AI 补适配层和业务规则。
  - `Acceptance Runner`：跑用户验收，而不是只看编译是否通过。
- 第一版不要理论化通用 IR，也不要做复杂 patch engine；应优先证明主循环成立。
- 这套系统的飞轮不是“prompt 越写越熟”，而是：
  - 早期：沉淀少量官方块与主验收链。
  - 中期：块、策略、验收一起复用。
  - 后期：升级、治理、私有 registry、可视化与 provenance 形成平台壁垒。

### 工作假设

- 真正可持续的飞轮来自“块资产 + 验收资产 + 版本图谱”的联合沉淀，而不是单独的 AI 生成能力。
- 长期版本里可以在主循环上增加 interface alignment、visual graph、repair pass 等增强层，但它们不应抢走 MVP 的优先级。

### 待验证

- `IR` 最终是否需要独立成显式文件，还是由 `graph.lock.json` 承担第一版职责，后续再验证。
- resolver 的约束求解能力何时需要从最小规则升级到更完整的 capability graph，也需要实践反馈。

## AI 在系统中的位置

### 已定结论

- AI 不是仓库主程序员，也不是自由游走的 agent；它是编译链里的受限 pass。
- AI 介入点必须是编译时声明的 slot，不能在仓库里随意“看到哪里缺就改哪里”。
- 合理的 slot 类型至少包括：
  - `Adapter Slot`：块与块之间的映射和适配。
  - `Policy Slot`：审批、校验、定价、权限等规则。
  - `UX Slot`：贴近产品语义的局部交互。
  - `Repair Slot`：验收失败后的局部修复。
- 第一版应该进一步收缩：只保留一个 slot，证明“AI 是 slot filler，不是主程序员”。
- 开发者对系统的控制权应体现在规格层：决定块选择、连接关系、AI 可动范围、验收规则、覆写边界，而不是要求每一行代码都手写。

### 工作假设

- 最理想的分工边界是：
  - 让系统稳定复用基础设施接线、重复功能壳、架构策略实现、固定契约周边代码。
  - 让 AI 负责业务规则、块间适配、局部交互细节、历史包袱与例外场景。
- AI 的价值不在整仓生成，而在把“剩下那一小段非确定性工作”从人工编码变成受控综合。

### 待验证

- 后续是否需要把 `Interface Alignment Agent` 单独产品化，需要等 MVP 跑通后再判断。
- 是否需要实时图形化显示 `Block Graph / Pin & Slot Graph / Provenance Overlay / Acceptance Coverage`，属于后续增强能力，暂不纳入第一版。

## 价值与风险

### 已定结论

- 这套方法对大模型应用开发和 agentic 开发的直接帮助是：把开放式生成转成约束式综合，减少上下文负担，把验证提前成主流程，并让 agent 真正拥有稳定的工具面。
- 它真正削弱的不是“程序员”这个角色本身，而是低层重复实现劳动。
- 它最有机会先在重复度高、规则明确、验收可编排的场景起效，尤其是多租户后台业务系统。
- 第一版不应支持 Java、多语言、多后端栈、多框架适配，也不应把 Elysia 当作首发后端目标。首版需要的是最少变量的全栈闭环。
- 游戏行业并不缺模板、kit、引擎模块，缺的是“模板之上的编译层”。如果以后切游戏，更合理的方向是玩法系统、内容管线、LiveOps/后台工具，而不是引擎主循环、手感、渲染和复杂同步。

### 工作假设

- 如果这套方法成立，软件生产成本曲线会继续下降，软件质量中位数会提高，重复造轮子的比例会下降。
- 对职业分工而言，它更接近“工程系统设计与治理工具”，而不是基础模型训练或 agent runtime 替代品。
- 它可能改变“代码的合法来源”：团队会更愿意接受“来自规格、模块和验收的产物”作为正式工程输入。

### 待验证

- 真实项目中能压掉多少不确定性、节省多少 token、提升多少吞吐和验收通过率，需要指标验证。
- “世界级潜力”“行业范式迁移”属于愿景判断，不应在现阶段当作既成事实。
- 游戏、复杂企业 Java 系统、跨栈平台化等更大领域，暂时只应作为扩展方向，不应提前写入 MVP 承诺。

## 开源与商业边界

### 已定结论

- 第一阶段不应立即开源平台和接收社区整块代码贡献。
- 第一阶段更合理的策略是：只维护少量官方块，先证明主闭环成立，再考虑生态开放。
- 如果要开放社区贡献，早期更适合开放 manifest、测试样例、文档、局部 patch，而不是让社区一开始就提交整块实现。
- 商业化边界可以放在托管运行时、验收与观测、团队私有 registry、权限与审计治理、块市场等层面。

### 工作假设

- 开源适合承载规格、接口、示例块和最小编译器；收费更适合承载团队治理、私有资产、运行托管、审计和高质量官方块。
- 生态形成的前提不是“先有社区”，而是“先有足够窄、足够稳的官方母路径”。

### 待验证

- 私有 registry、升级服务、可视化治理和托管运行时中，哪一项最先具备付费意愿，需要等 MVP 之后看用户反馈。
- 社区是否真的会围绕 block 契约而不是直接围绕源码提交进行协作，也需要实际试验。

## 待验证问题

- 第一版跑通后，最先增加的是第四个官方块、升级机制，还是 provenance/可视化层，需要根据真实痛点排序。
- `graph.lock.json` 是否足以承担第一版锁定与追踪职责，还是应尽快补显式 provenance 文件，待实现后验证。
- 当块数量增加后，`requires / provides / conflicts` 是否足够表达所有实际约束，待 registry 扩展时验证。
- 后续是否需要支持第二后端目标栈，例如 Elysia 或 Nest，应在第一个闭环完成后再决策。
- 后续是否切入 Java 企业系统、游戏玩法系统、LiveOps、内容管线，应以“已有主循环是否稳定”为前置条件。

## 新增整合：问题定义与必要性

### 已定结论

- 本项目要解决的不足，不是“行业没有模板、SDK、低代码或 AI builder”，而是缺少一层能把现成能力可靠编译成系统的工程层。
- 现有方案已经覆盖大量单点能力：starter 解决开工，SDK/API 解决接口调用，shadcn 一类 registry 解决源码块分发，n8n 解决工作流运行时编排，Lovable/Spark 解决自然语言到应用的生成体验。
- 真正反复消耗团队的是跨模块拼接、业务编排、胶水逻辑、验证和长期升级；这些通常仍停留在团队内部经验、脚本、模板和手工接线里。
- 项目的必要性成立于五个条件同时成立：
  1. 功能块有严格接口，而不是一堆模板文件。
  2. AI 只填受控 slot，而不是自由改仓库。
  3. 系统能编译出真实项目，而不是只生成骨架。
  4. 有验收与 provenance，而不是只看起来能跑。
  5. 同类项目能持续复用和升级，而不是一次性演示。
- 因此，正式 Problem Statement 可以写成：现有模板和功能解决方案已经覆盖大量单点能力，但中大型项目仍反复消耗在跨模块拼接、业务编排、胶水逻辑和复用失效上；本项目要把这部分从手工劳动变成工程编译。

### 工作假设

- 项目真正产品化的是“组装 + 编排 + 验证 + 复用”，不是重新发明认证、支付、搜索、工作流等单点能力。
- 市场上现成能力越多，越需要一个能够选择、连接、治理、升级和验证这些能力的编译层。

### 待验证

- 是否能在一个窄母例中证明：相比 starter + AI IDE + 手工集成，工程编译层能显著降低返工、验收成本和维护复杂度。

## 新增整合：项目形态与适配边界

### 七类项目形态

1. 一次性小工具：脚本、内部小页、数据处理、个人效率工具。
2. 标准业务后台：登录、权限、CRUD、审批、报表、文件、通知。
3. 面向客户的产品型 Web/App：前台体验、支付、内容、运营、增长实验。
4. 平台型系统：多租户、插件化、工作流、规则引擎、开放接口、权限治理。
5. AI/Agent 产品应用层：聊天、RAG、copilot、自动化工作流、多工具调用、人类审核。
6. 高性能核心系统：交易、风控、实时游戏核心、超低延迟服务。
7. 基础设施 / 运行时 / 底层平台：数据库、中间件、推理服务、训练平台、agent runtime、编译器后端。

### 适配判断

- 最适合：2、3、4、5。
- 可用但偏重：1。
- 不是第一刀：6、7。
- 从产品视角可重分为三类：
  - 可编译型项目：功能块可定义、接口可收敛、验收可写。
  - 半可编译型项目：主干可编译，体验层、创新层或热路径需要人和 AI 补。
  - 当前不可编译型项目：价值主要在底层实现、极端性能或实时细节。
- 一个项目若满足以下四条，就适合工程编译器：
  1. 80% 的功能能说清输入输出。
  2. 重复能力很多，不值得每次重写。
  3. 大部分价值在系统拼装和治理，不在底层极限优化。
  4. 可以用验收场景定义成功。

### 六七类项目的进入方式

- 高性能核心系统和底层平台不是不能用本工具，而是不能按业务后台的整段装配方式使用。
- 正确方式是“系统编译与治理外壳 + 手写核心内核”：
  - 冷路径、控制面、配置面、治理面交给工程编译器。
  - 热路径、核心循环、性能关键内核保持手写或极窄专用生成。
- 三种接入模式：
  - `Outer Shell Mode`：只编外围壳层、后台、控制台、配置、文档、测试、观测。
  - `Hybrid Kernel Mode`：核心手写，外围编译，规则和适配 slot 化。
  - `Spec-to-Harness Mode`：核心不能生成时，也生成测试、benchmark、operator、dashboard、control API、docs、SDK。
- 性能承诺不能写成“不会受影响”，应写成：普通业务系统性能影响通常可接受；高性能/底层系统默认只编译外围，不碰核心热路径；若触碰热路径，必须有性能预算与基准验证。

## 新增整合：软件芯片化与项目编译器语言模型

### 软件芯片化

- 硬件能芯片化，是因为接口硬、变化贵、标准强、验证重。
- 软件长期难以同等封装，是因为边界软、语义重、变化快、耦合深、验证弱。
- 软件已有很多“半芯片”：库、SDK、API、SaaS、UI 组件、Terraform module、工作流节点、模板、微服务。
- 这些半芯片通常缺少系统级组合规则、行为验收、升级兼容、管脚语义和 provenance。
- 本项目要推动的是把软件能力从“可调用模块”提升为“可编译器件”：功能块 + 管脚 + slot + block graph + acceptance。

### 项目编译器语言模型

- 传统编译器检查的是程序语言是否合法并可执行；项目编译器检查的是业务规格是否合法并可落成系统。
- `app spec / block graph / pin / slot / policy / acceptance` 是项目世界里的源语言或规格语言。
- `resolved graph / graph.lock.json / install plan` 更像项目级 IR。
- 生成源码是下游产物，不是唯一权威输入。
- 项目编译器能检查的是业务系统结构逻辑：功能块连接、输入输出契约、权限约束、状态流转、事件依赖、生命周期要求、验收条件和不变量。
- 它不是万能业务裁判；商业策略、产品市场判断、推荐效果等无法自动证明，除非也被形式化进规格。

## 新增整合：AI 维护方式与 Issue 分层

### 默认工作流变化

- 目标不是消灭源码层，而是剥夺源码层作为默认问题入口的地位。
- 未来 AI 修改项目应遵循：读工程规格 -> 理解块连接 -> 推演数据流/事件流/权限流 -> 判断问题层级 -> 精准定位到 slot 或源码文件 -> 局部修改 -> 回跑验收。
- 这样 AI 从“代码考古学家”变成“工程规格执行器”。
- 大量说明性文档会被结构化规格吸收；仍需保留的文档主要是产品意图、业务背景、决策原因、迁移说明和架构原则。

### Issue Layering Model

- `Spec Issue`：块选错、连接错、pin 未对齐、约束缺失、slot 描述不完整、acceptance 定义错误。
- `Composition Issue`：resolver、compose、patch、生成顺序、adapter contract 或安装规则问题。
- `Slot Issue`：AI/人工填的局部逻辑错误，需要改 slot 描述、契约、重新综合或改 slot 源文件。
- `Kernel Issue`：块内部实现、性能、状态机、算法、存储、并发等源码层问题。
- 约束越硬，越多 issue 会先暴露在源码之上，但总有一部分 issue 仍需下沉到源码层。
- 新系统会减少接错模块、漏权限、漏租户上下文、漏审计通知、样板不一致、AI 满仓误改等问题；也会新增 pin 设计不合理、slot 粒度错误、acceptance 不完整、compile contract 漏洞、provenance 丢失、override/升级冲突、graph 复杂等新型问题。

## 新增整合：相邻物种、竞品与差异

### 相邻物种

- `JetBrains MPS`：最像规格高于源码的哲学层，但它是语言工作台/DSL 平台，不是现代全栈项目的功能块编译器 + AI slot 综合器。
- `Backstage Software Templates`：最像模板与组织层，但粒度仍偏 skeleton/template，不具备严格 capability interface、slot、acceptance 和 provenance 编译。
- `shadcn registry`：最像源码块分发层，但主要解决代码块安装，不解决项目级接口、图谱、验收和升级。
- `Smithy / OpenAPI Generator`：最像合同驱动代码生成层，但边界主要是 API/contract，不是完整全栈项目编译。
- `GitHub Spark / Lovable`：最像 AI 全栈生成层，但更偏对话式 app builder，而非规格、功能块、slot 和验收驱动的编译系统。
- `Encore`：最像后端/基础设施编译器，但不是全栈能力块 + UX + slot + 验收编译器。
- `Cedar / TLA+ / Alloy`：证明窄域可验证语言可行，尤其权限、协议、状态机，但没有覆盖整个业务项目。
- `Palantir Ontology / Camunda / Temporal`：分别覆盖组织语义层、流程层、可靠执行层，但不是面向 repo 的工程编译层。
- `OpenClaw / Claude Code / Managed Agents`：更像 agent harness、skills、tool surface、session、sandbox 和权限系统，不是项目编译器。
- `n8n`：更像确定性 workflow automation + AI nodes，可成为运行后端或被部分上吃，但不是源码项目编译层。

### 差异定位

- 相似者很多，完全同类者目前未见到成熟主流产品。
- 本项目的空位是：严格 capability interface、源码级块分发与安装、AI 只在受控 slot 内综合、验收/回归作为编译成功条件、项目源码作为编译产物、provenance 与升级成为默认能力。
- 如果只做聊天式生项目、更高级脚手架、一堆模板拼接，就会落入 Spark/Lovable/Backstage/shadcn 的影子。
- 如果把 block graph、slot、acceptance、provenance、upgrade 做成一等公民，才是新的工程抽象层。

## 新增整合：命名、产品形态与交互原则

### 命名

- 产品名建议：`SpecEngineer`。
- 方法论：`Spec Engineering` 或 `Project Harness Engineering`。
- 技术范式：`Spec-Driven AI Engineering`。
- 核心对象可叫：`Spec Harness`。
- 对外口号：`From vibe coding to harnessed engineering.`
- 中文表达：从氛围编程到受控工程综合。

### 产品形态

- 最终形态不是单纯 IDE，也不是单纯插件，而是软件平台。
- 四层结构：
  - `Compiler Core`：spec parser、resolver、graph builder、composer、slot runner、verifier、provenance engine。
  - `Registry / Control Plane`：官方块库、私有块库、版本、migration、policy、acceptance templates。
  - `IDE / Plugin`：graph 可视化、pin 对齐、slot 编辑、影响分析、验收状态、provenance。
  - `Workbench / App`：desktop/web/self-hosted control plane，用于管理项目、图谱、编译、验证和运行后端连接。
- 插件是主控台，不是监狱；视图是主入口，不是唯一入口；代码文件是产物和逃生层，不是默认工作台。
- 交互原则：视图优先，源码可达；任务优先，聊天辅助；规格为源，源码为产物；默认在图谱层工作，必要时下钻到代码。

## 新增整合：模型、算力与 Benchmark 边界

- 本平台不是提高基础模型裸智商的工具，不直接提升模型在高难数学、前沿科学、多模态理解等 benchmark 上的能力。
- 它更可能提高现有模型在 SWE-bench、GAIA、MLE-bench、PaperBench 等真实工程闭环任务上的成功率、稳定性和 token 效率。
- 核心机制是把高自由度工程任务变成受约束执行，降低搜索空间、上下文负担和误改范围。
- 结构化后，普通模型可用性会上升，强模型的有效产出密度也会上升；强控制会缩小模型差距，但不会抹平模型差距。
- 对端侧/小模型的意义：如果确定性装配覆盖 60%–80%，小模型就有机会在终端完成 slot、字段映射、adapter、影响分析、本地 explain、局部修补等 20%–40% 的受控任务。
- Frontier 模型仍会继续用于前沿推理、科学研究、开放世界长时 agent、多模态现实操作、大规模企业编排、runtime 与基础设施优化。

## 新增整合：学习成本、采用与长期影响

### 开发者采用

- 学习成本能否换来更低心智负担，取决于新增的一层是否稳定替代原来反复做、反复忘、反复审、反复修的那一层。
- 程序员会接受新方式的前提：高频场景里明显更省事、不黑盒、可渐进引入、AI 更可控、复杂度上移、能兼容 git/IDE/PR/CI/测试和源码调试。
- 最危险的是：多一层配置、术语、图和生成器，但调试、升级、验收没有本质变好。
- 产品必须可逃逸、可裁剪，允许团队先半接受，再逐步进入 compiler-first workflow。

### 影响力层级

- 如果成功，本项目更接近 Git / Docker / Terraform / Kubernetes 这一类“改变工程表达、装配、交付和协作方式”的抽象层创新，而不是 Linux / CUDA 那类底层运行底座。
- 它的上限不是“更火的 app builder”，而是重新定义软件工程输入与装配方式的工程范式创新。
- 失败风险主要来自：块接口不够硬、升级维护做不成、验收/provenance 不够强、找不到一个窄场景先赢。

### 世界变化

- 如果 SpecEngineer 成立，最大变化不是“满世界更多无意义大项目”，而是软件项目从一次性手工工程变成可组合、可编译、可验证、可持续演化的产品线资产。
- 可能出现的新需求：高质量功能块、行业块包、验收套件、规格工程师、项目变体管理、自维护服务、AI 成本压缩、企业软件现代化。
- 外包/咨询会从卖人天写代码转向卖行业块库、验收模板、迁移服务、治理合规、复杂业务建模和长期运营。

## 新增整合：自举、自维护与终极愿景

### 自举

- 自举应作为长期设计约束尽早纳入视野，但不应在早期全量实现。
- 正确路线是分层自举、逐步吞回自己：宿主语言实现内核 -> 工程语言描述 spec/block/acceptance -> 官方块库语言化 -> 平台外围语言化 -> 有限核心自举。
- 适合采用混合式自举：底层 parser、核心 IR、compose engine 长期保留宿主实现，上层规格、块库、规则、UI 和外围逐步由工程语言描述。

### 自维护

- 本平台天然适合作为自维护系统的编译层和控制面基础，因为它有 block / pin / slot / acceptance / provenance，可定位层级、限制改动并验证结果。
- 完整自维护还需要补齐：观测、诊断、执行权限、回滚/补偿、治理审计。

### 终极愿景

- 工程编译器是第一层：把工程规格编译成软件系统。
- 软件产品线编译器是第二层：编译一族项目、行业包、客户包、变体、override 和升级矩阵。
- 组织编译器是第三层：把角色、权限、流程、数据、规则、审批、agent 和软件界面编译成组织协作系统。
- Venture / Reality Compiler 是更远端：把商业想法或现实目标编译成软件、agent、人类角色和外部服务组成的行动网络。
- 当前阶段不能直接做 Reality Compiler；必须先证明项目可以被规格编译，再证明项目族、组织流程和商业意图可以逐级编译。

## 新增整合：可迁移到其他领域的模式

### 可迁移公式

```text
隐性专家劳动 -> 结构化规格 -> 标准模块 -> 管脚连接 -> AI 填 slot -> 验收验证 -> 可持续维护
```

### 候选领域

- 组织流程编译器：把组织目标、角色、权限、流程、表单、审批、通知、agent 和系统编译出来。
- 合规 / 安全编译器：把 GDPR、SOC 2、HIPAA、金融风控、租户隔离等要求编译成策略、约束、测试和审计证据。
- 数据产品编译器：把业务指标规格编译成数据流、表结构、pipeline、dashboard、数据质量验收。
- Agent 团队编译器：把 agent 角色、工具权限、memory schema、流程、审批、审计和绩效指标编译出来。
- 行业 SaaS 变体编译器：用行业包 + 通用平台块 + 客户定制 slot 支撑诊所、律所、教培、物流、物业、维修等垂直系统。
- 游戏玩法系统编译器：编译技能、Buff、装备词条、卡牌效果、任务、对话树、掉落、成就和 LiveOps 活动，但不替代引擎热路径。
- API 集成编译器：把 connector、webhook、字段映射、幂等、重试、死信、审计和同步 dashboard 编译成可维护工程。
- 知识系统编译器：把知识结构、来源、权限、RAG、引用验证、过期检测和回答验收编译出来。
- 教育课程、法律合同、机器人/IoT、云基础设施、研究实验、个人生产力系统、内容工厂等也符合类似模式，但进入顺序应晚于主母例闭环。

### 优先方向

1. 行业 SaaS 变体编译器。
2. Agent 团队编译器。
3. 合规 / 权限 / 安全编译器。
4. 数据产品编译器。
5. API 集成编译器。
