# 用户能力模块化开发主题整理稿

> 权威边界：本文件是概念总纲，用于统一问题定义、概念边界和长期愿景；实现级 schema 与协议以 `05-10` 为准。
>
> 来源：基于原始对话录 [用户能力模块化开发.md](用户能力模块化开发.md) 重组。

## 1. 核心命题

这套方法不是"让 AI 帮人写代码"，而是把软件开发的基础单元从"代码文件"改成"能力模块（Block）"。

| 维度 | 传统开发 | 本方法 |
| --- | --- | --- |
| 基础单元 | 代码文件/函数 | 能力模块（携带接口、依赖、测试、验收） |
| 主要操作 | 写实现细节 | 选块、连管脚、定义 slot、声明验收 |
| 权威输入 | 源码 | spec / block graph / slot 定义 / acceptance |
| 源码地位 | 唯一事实源 | 可审查、可修改的编译产物 |
| AI 角色 | 全仓程序员 | 编译链中的受限 slot filler |
| 开发关注 | implementation-first | outcome-first（链路闭环 > 实现优雅） |

### 目标转化链路

`隐性专家劳动 → 结构化规格 → 标准模块 → 管脚连接 → AI 填 slot → 验收验证 → 可持续维护`

### 长期愿景

- 开发者角色从"低层实现者"转向"问题定义者、约束设计者、模块抽象者、验收治理者、例外处理者"。
- 软件知识从"分散源码经验"沉淀为"可升级的模块与策略资产"。
- 飞轮不是 prompt 优化，而是：沉淀块资产 → 块+验收+策略一起复用 → 升级+治理+provenance 形成平台壁垒。

## 2. 与相邻物种的边界

| 相邻系统 | 差异 |
| --- | --- |
| 模板/脚手架 | 模板解决"从零起步"；本产品覆盖组合、验证、来源追踪、升级、override、重复编译 |
| 低代码 | 低代码锁用户在运行时和 UI 编排器；本产品输出真实源码 |
| 自由 AI 编程助手 | AI 助手直接面对整仓；本产品要求 AI 先面对结构化规格 |
| SDK/库生态 | SDK 复用代码调用点；本产品复用工程能力块、接口合同、验收和升级协议 |
| n8n/Camunda/Temporal | 偏运行时/流程编排后端；本产品位于其上的工程编译层 |
| Claude Code/MCP/Skills | 强执行与工具基座；本产品是项目级 harness 和工程规格层 |

## 3. 系统主循环

```text
用户规格 → 解析为装配计划 → Resolver 解依赖与冲突 → Composer 安装资产
  → AI 填受控 slot → Acceptance Runner 跑验收 → 产出可审查项目与锁定图谱
```

六大核心部件：`Registry` → `IR/装配计划` → `Resolver` → `Composer` → `Adapter Generator/AI Slot` → `Acceptance Runner`

后续增强层（不抢 MVP 优先级）：interface alignment、visual graph、repair pass 等。

## 4. AI 在系统中的位置

- AI 不是主程序员，是编译链中的受限 pass。
- 介入点必须是编译时声明的 slot，不能在仓库里随意改写。
- Slot 类型：`adapter`（块间映射）、`policy`（审批/校验）、`ux`（局部交互）、`repair`（失败修复）。
- 开发者控制权体现在规格层：块选择、连接关系、AI 可动范围、验收规则、覆写边界。
