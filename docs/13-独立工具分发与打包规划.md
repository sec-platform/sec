# 运行时权威、包布局与独立 CLI 分发

本文是 SEC runtime authority、公开包布局和独立 CLI 分发的唯一稳定 owner。它区分语义、执行宿主、工具链和生成目标；类型、构建器、路径 resolver 与发布 Gate 只能投影本文合同，不能建立第二套 runtime 判断。

## 1. 五个不可合并的轴

| 轴 | 唯一职责 | 是否进入 canonical 语义 |
| --- | --- | --- |
| Semantic Core | Engineering IR、identity、revision、contract、lowering、projection 与 Explain 的确定性语义 | 是；必须 runtime-neutral |
| Host Runtime | 执行 SEC CLI/Workbench/adapter 的进程，当前候选为 Node 或 Bun | 否；只进入 host Evidence |
| Toolchain Provider | install、test、typecheck、bundle 等工程命令的精确 executable/version authority | 否；只进入 toolchain Evidence |
| Target Runtime Profile | 生成项目的 runtime family、version range、module system、package manager 与 capabilities | 是；属于 target 编译输入 |
| Optional Capability Adapter | FFI、native helper、AppContainer、平台属性等非公共基线能力 | 否；缺失时必须显式 capability error |

禁止从任一轴双向推断其他轴。Node Host 可以调用 Bun Toolchain；Node Target 可以选择与 runtime family 独立的 package manager；Bun 下成功也不能证明 Node 成功。`process.execPath` 只标识当前 Host，不得被当作 Bun Toolchain authority。

## 2. 当前决策与真实能力状态

- Semantic Core 的公共类型、builder、validator、identity/revision 与纯 lowering 不得 import Node/Bun adapter。
- 公开 TypeScript CLI 的 compatibility baseline 选择 Node LTS：最低 Node 22，参考 Node 24。
- 该选择于 2026-07-28 根据 Node 官方 release schedule 复核：22 处于 Maintenance LTS、EOL 为 2027-04-30；24 处于 Active LTS、2026-10-20 转 Maintenance、EOL 为 2028-04-30。进入真实 smoke 包时若 schedule 或安全支持状态变化，必须重新裁决。
- 仓库 install/test/build 的唯一 Toolchain Provider 仍是 `.bun-version` 与 `packageManager` 共同固定的 Bun 1.3.14；这不使 Bun 成为 Semantic Core 或唯一公开 Host。
- Bun 是一等优化 Host/Target 候选；Bun-only API 只能存在于显式 Bun Toolchain、Bun Target 或 capability adapter 边界。
- 当前 `main` 尚未满足 Node 公共静态图、portable lease、独立 Bun executable、clean package smoke 和 Node 22/24 Gate，因此不得声明 Node 已受支持。

能力声明分五层，后层不能由前层替代：

```text
authority declared
→ implementation entered main
→ exact physical tests passed
→ packaged/deployed surface passed
→ actual support claim enabled
```

## 3. 公共 runtime 合同

`platform/shared/runtime-authority.ts` 只拥有以下正交合同：

- `HostRuntimeIdentity`：family、version、executable、platform 与 architecture，属于 Evidence。
- `ToolchainProviderIdentity`：provider、version 与独立 executable，属于 Evidence。
- `TargetRuntimeProfile`：版本化 canonical target 输入，至少包含：

```yaml
family: node | bun
versionRange: string
moduleSystem: esm | commonjs | hybrid
packageManager: npm | pnpm | yarn | bun
capabilities:
  filesystem: boolean
  subprocess: boolean
  nativeAddons: boolean
  workerThreads: boolean
  webStreams: boolean
  serverApi: string
```

- `RuntimeExecutionEvidence`：同时记录 Host 与 Toolchain identity，但不得进入 Target profile revision。

Target profile 的生成项目投影属于后续独立 Work Package；本合同存在不代表 scripts、types、dependencies、lockfile 或 container 已按 profile 生成。

## 4. Package 与 runtime asset 布局

一个执行实例必须解析出唯一 `CompilerRuntimeLayout`：

| 路径 | 职责 |
| --- | --- |
| package root | 安装包根、`package.json`、外部 dependency resolution 与可重建 toolchain/cache state |
| executable module | 当前源码 module 或公开 `dist/index.js` |
| runtime asset root | official registry、policies、templates 与随包资源的唯一基准 |
| repository source root | 仅源码开发模式存在；公开包运行时为 `null` |
| caller workspace root | CLI 显式参数或 `cwd` 指向的用户 workspace；绝不参与 compiler package/resource 定位 |

当前两个合法 profile：

```text
source:
  module = <package>/platform/shared/runtime-layout.ts
  packageRoot = runtimeAssetRoot = repositorySourceRoot = <package>

bundle:
  module = <package>/dist/index.js
  packageRoot = <package>
  runtimeAssetRoot = <package>/dist
  repositorySourceRoot = null
```

未知 module layout 必须 fail closed。`compilerRoot` 在迁移期只是 package root 的兼容名称，不能继续同时表示 source root 和 runtime asset root。official registry/policy 的 `location: compiler` 以 runtime asset root 为基准；package metadata、dependency generation 与 toolchain state 以 package root 为基准。

任何自包含的隔离 compiler package 只要执行 bundled core，也必须复用同一个 `bundle` profile，不能建立伪 source layout 或第三种 resolver mode。Semantic Mutation staging 中 package root 为 `.isolated-compiler`，可执行 module 为 `.isolated-compiler/dist/index.js`，runtime assets 位于 `.isolated-compiler/dist/platform/**`，而 `package.json`、`node_modules` 与可重建 toolchain state 继续留在 package root。Verification-owned bootstrap/loader 只是启动边界；loader 到 core 的 import 必须从两个 canonical relative path 派生，不能依赖同目录 basename、caller `cwd`、环境变量、祖先搜索或全局注册。

## 5. 公共 CLI 与 Bun 合法边界

默认公共 CLI 的静态可达图最终必须禁止 `from 'bun'`、literal `import('bun')`、`bun:ffi`、`Bun.*` 与 `bun:test`。动态 import 本身不构成隔离证明：公共命令可达 capability 时仍须有显式 adapter 或 actionable unsupported error。

以下表面允许保留 Bun API：

- `bun install/test/build` 与 repository Dev Runner/Hook；
- release builder 的显式 Bun Toolchain adapter；
- 声明为 Bun 的 generated Target；
- development/verification-only Gate；
- 与 common public graph 隔离的 Bun/native capability adapter。

`platform/shared/workspace-write-lease.ts` 的 common authority 不得依赖 `bun:ffi` 或其他 Bun Host API。满足下述 portable protocol 只移除 mutating Node Host 的一个严格阻塞；即使 HTTP host 或 `--help` 可在 Node 加载，也不能据此声明可变 CLI/Workbench 路径受支持。

### 5.1 Portable workspace lease authority

`platform/shared/workspace-write-lease.ts` 是 common write authority 的唯一 owner。portable protocol 使用同一 workspace 内的 append-only generation ledger：

1. `.sec/workspace-write-lease/` 是永久 protocol root；固定 `protocol.json` marker只声明protocol revision，不声明active owner。旧v1 `owner.json` residue必须fail closed，不得在无法证明旧进程完全退出时自动迁移。
2. Marker先在canonical `holders/` 根以完整、fsynced immutable candidate形成，再以Node标准`fs.link()`原子发布为`protocol.json`。正常路径删除candidate；若进程在link成功后、candidate删除前崩溃，只允许收敛一个精确拓扑：marker必须内容/version合法且`nlink === 2`，`holders/`直属目录中恰有一个名称匹配canonical protocol candidate pattern、为普通非symlink文件且与marker的bigint `dev + ino`完全相同的alias。恢复必须在unlink前重新读取marker并复核target/alias identity与link count，随后只unlink该exact alias、fsync `holders/`与protocol root，再复核marker内容、identity与`nlink === 1`。alias缺失、多个、名称非canonical、位于其他目录、identity不等、target变化或任一步无法证明时全部fail closed；禁止按内容、mtime、size或猜测名称删除。
3. 每个contender先在非权威holder目录完整写入并fsync immutable owner与初始heartbeat，再以Node标准`fs.link()`将owner原子发布为下一个generation的owner record。Immutable publication必须显式区分`not-published`、`published`与`durability-unknown`：只有link失败后再次证明target不存在时才允许删除prepared holder；一旦link成功，或target identity证明prepared owner可能已发布，即使随后protocol-root fsync失败也必须保留完整holder并返回typed retry/recovery failure，由重启从generation ledger收敛。目标已存在且identity不同只表示contention；禁止`exists → rename`、覆盖、复用generation或在durability不确定时递归删除holder。
4. 没有terminal record的最高generation是唯一active owner。Token与commit fence同时绑定workspace identity、generation、owner file identity、process nonce与lease id；较旧generation即使文件仍保留也不能恢复所有权。
5. Heartbeat只更新该generation绑定的holder state。只有同hostname、超过stale window且PID被证明dead的最高generation可以recovery；foreign、live与unknown liveness全部fail closed。
6. release与recovery都只把完整、不可变、绑定exact owner identity的terminal record hard-link到当前generation。terminal一旦存在，后继contender竞争下一个generation；recovery不rename、unlink或复用active/successor owner，因此延迟recovery actor不能移除后继writer。
7. 崩溃发生在marker publication alias清理前按第2项精确收敛；发生在owner link前且target absence已证明时只留下可删除的非权威holder；发生在owner link后或publication durability不确定时必须保留完整holder，由heartbeat/liveness恢复；发生在terminal publication后已形成完整terminal state，任一后继contender都可继续下一generation。Terminal candidate alias不参与active owner或quiescence判定；只有共享publication机制能证明其非权威性时才可清理。Marker收敛不得删除或修改generation owner、terminal、holder directory或heartbeat。历史terminalized generation允许有界压缩，但最高generation与active generation不得删除。
8. `platform/shared/workspace-write-lease.ts` 同时拥有唯一read-only v2 inspection contract。任何Gate、recovery census或审计只能消费它返回的stable summary、authority paths与state digest，不得手写`owner.json`、token字段、generation filename、holder identity、link-count或legacy分类。Inspector不创建、修复或terminalize状态；它以同一protocol validator验证active、released、recovered、malformed与legacy-v1拓扑。Namespace walker把整个lease root视为一个由inspector拥有的原子子图，不能把owner hard link误报为未知alias，也不能递归建立第二套parser。

该机制的物理接受面是 Windows 本地文件系统与 Linux ext4/WSL2 上的真实 Node跨进程竞争、owner crash与recovery；Bun下的单元测试、类型通过或文档声明不能替代这些证据。该 authority 迁移只移除 common lease graph 的 `bun:ffi`，不会删除显式 Bun Toolchain、Bun Target、AppContainer/native capability或development/verification Gate中的合法 Bun API，也不会据此声明 Node CLI 已受支持。

## 6. Build、pack 与资源

Release Builder 必须消费共享 layout 常量：

1. Bun Toolchain 从公共 CLI entry 构建标准 ESM `dist/index.js`。
2. official registry 与 policies 复制到 `dist/platform/**`。
3. 依赖声明从 package root 解析，运行时资源只从 runtime asset root 解析。
4. executable shebang、ESM、权限和 Windows launcher 由 clean package Gate 验证。
5. 构建不得依赖 caller `cwd`、私有 docs、本仓 `.sec/**` 或未打包 source layout。
6. Verification 的自包含隔离物化必须消费同一 runtime resource inventory 与 bundle asset-root 规则，不能独立拼写 registry、policy 或 template 目的路径。

共享 layout contract 与 builder 投影不拥有 `package.json`、公开依赖裁剪、`engines`、pack/install 或 Node smoke；这些能力必须由后续显式 Target 与 release Gate闭合，不能用 metadata 冒充支持。

## 7. 公开镜像、隐私与许可

公开镜像必须由可验证白名单从 clean release workspace 生成；不得把私有仓库配置第二 Remote 后 force-push，也不得吞掉 publication failure。

以下默认不进入公开包/镜像：

- `docs/**` 私有设计资料、Agent/IDE 配置与会话数据；
- `.sec/**`、私有 Registry/Project Source；
- 仅供开发/验证且许可证或 native closure 不属于公共 runtime 的 Provider。

可选 Evidence Provider 缺失不得阻断核心编译链。发布前必须证明 package surface、resource location、license/dependency closure、clean install、Node 22/24、Bun common bundle、Windows invocation 与 failure nonzero。

## 8. 依赖顺序与支持声明

```text
runtime authority + package layout
→ portable atomic workspace lease
→ common Node host + Bun Toolchain separation
→ generated Node/Bun target profiles
→ optional native capability adapters
→ cross-host determinism + release matrix
```

只有最后一个闭包通过真实 Node/Bun clean-package 与 cross-host canonical output Gate 后，产品表面才可声明 public Node baseline fully supported。各中间包必须准确列出已实现、已测试和仍阻塞的路径。
