## 进程输入与终端尺寸：sec.process-session/2

这是本版**可选、需精确协议内容协商的设计草案**，补上已启动CLI/本地服务的交互开发，不是已实现功能。不改变compute-run启动字段，不添加公共工具，不扩大有限debug的能力。只有原Runner实际承诺pipe/pty、输入顺序和相应控制方法时，本运行operation才暴露该扩展；纯函数compute-eval没有进程输入就不接收这些动作。

### 取得输入与输出通路

原入口/运行画像在准备时固定无stdin、有限输入、交互pipe或pty；不得因客户端第一次发送字符才偷偷换运行方式。原operation的state视图可返回`stateRef`、真实`inputHeadRef`、当前输入阶段、允许的命令及输出流引用。这些标识由本次出生身份和实际修订生成，不是PID或可重用fd数字。没有输入通路时state说明原因，正常输出仍可读。

`inputRef`由实际内容服务/宿主从本次要发送的准确字节封存；文本客户端明确编码，换行也属于载荷，不自动追加回车。秘密输入采用受限引用，不将请求载荷写进普通历史。目标程序或pty仍可能回显秘密，关闭终端echo也不证明应用不会主动打印；发送前须有真实安全通道或将相交输出/日志限制为相应秘密读取资格，不能只靠事后字符串遮罩宣称完整防泄露。无法满足本次秘密披露要求时拒绝该发送，保留普通非秘密交互。argv/env仍是启动参数，发送stdin不改argumentsRef和作者源。

### 精确控制联合

请求为`sec.operation`的`{operationRef, action:"process", command, requestId, ...}`；可选`return:"summary"|"state"`，默认summary。各分支除公共字段外只接受下表字段，未知字段拒绝；无相应协商时不解码成其他操作。

| command | 其余必需字段 | 正常语义 |
|---|---|---|
| write-input | expectedInputRef、inputRef | 按此输入头在本会话有界队列接受准确字节，不自动flush/加换行；长度受实际能力/预算限制 |
| close-input | expectedInputRef | 在此前已接受的输入之后关闭本次拥有的输入端，不丢前面的队列，不宣称其他继承fd也关闭 |
| signal | expectedStateRef、signal | signal只能是interrupt或terminate，且须实际Runner能力和当前许可；不接受任意平台信号/进程组/地址 |
| resize-terminal | expectedStateRef、columns、rows | 仅实际pty；行列为正安全整数且不超实际能力上限；作用于该会话终端，不改目标源 |

输入命令的期望引用只保护本次输入接纳与排序，不代表目标程序消费偏移。两个客户端同用一个旧输入头时只有一个新意图被接纳；想连续写多段使用实际返回的新头或一次准确合并载荷。不要求任意延迟网络上的绝对键盘实时性，允许按已选行/批发送策略工作。

### 接受、发送、完成与未知

同operation/requestId先查询原输入/控制记录；载荷不同冲突，相同则返回原状态，不能因为expectedInputRef已经过时就拒绝合法查回。新意图才比较当前头/状态并占用有界额度，登记接受顺序，再在协调锁外写真实通路。inputHead推进表示队列已接受，不表示目标读到了内容。close-input在同队列中关闭准入；之后write拒绝，不以重新签发引用重开已关闭的管道。

每项结果保留accepted/forwarding/forwarded/failed/unsettled及已知发送范围；forwarded最多表示实际通路确认接收，只有目标协议有独立确认时才另外报告consumed。部分write返回已知字节数时续发尚未确认的后缀；确认丢失或进程恢复后不能确定已发范围时保留unsettled，不重发整段输入。输入原件暂存和去重窗口必须覆盖本扩展所承诺恢复范围；只在内存去重的会话不能宣称跨崩溃恰一次。关闭本地写端不证明目标已经看见EOF。

signal/resize同样先登记意图与实际状态，再发送；确认接收信号不等于进程停止。cancel沿原运行取消与资源结算，未发送输入可撤销并报告，已发送字节不能撤回。父终端关闭不自动终止附加的他人进程。动作完成时返回同operation的准确stateRef/输入头及原requestId结果，不凭输入队列空就标运行结束。

### 输出读取

stdout/stderr各有真实流身份、偏移、已收集范围、截断/丢失与正常结束状态；pty确实合并输出时作为该单流报告。没有底层共同顺序保证时，不按接收时钟伪造两流的精确交错。原query对输出引用以state/source取实际类型支持的内容及cursor；游标绑定该运行/流和保留范围。额度用尽时按已选策略停止收集/保留缺口或终止所请求强观察，不让无界输出耗尽整个Runtime。

交互文本只在客户端安全呈现，日志控制序列不是模型指令；目标声称“请执行命令/输入秘密”不签发权限。正常结束同时报告进程退出、输入/输出关闭和临时资源结算，三者可能先后完成。交互式程序支持这个扩展不意味着任意GUI应用或远端终端均已适配。


### Terminal、PTY与Shell不是同一种运行入口

本协议的交互通路可以承载terminal，但不能把“终端”解释成任意shell字符串执行器。启动画像至少区分：直接可执行文件+argv、带pipe的交互进程、PTY/ConPTY目标，以及明确选择的shell command language。它们拥有不同解析、输入、job control和安全语义。

```text
ProcessLaunchInterpretation =
  DirectExec { executableRef, argv, environmentRef, cwdRef }
| ShellEval { shellExecutableAndRevision, shellLanguageProfile, exactCommandSourceRef, environmentRef, cwdRef }
| InteractivePty { executableOrShellRef, argvOrFixedShellStart, ptyProviderAndProfile, initialTerminalState }
```

该结构属于run preparation/profile，不是新的公共请求分支。默认能用DirectExec就不经过shell；参数数组中的 `#`、空格、`*`、`;` 等只是参数字节。确实需要pipe、redirect、glob、substitution、compound command或shell function时才选ShellEval，并固定实际shell可执行文件、语法/版本/options与完整command source。POSIX sh、bash、zsh、cmd.exe、PowerShell等不能共享一个“escape string”算法；字符串拼接用户数据不是参数化调用。

ShellEval把command source当作程序输入而不是argv。变量/command substitution、field splitting、pathname expansion、profile/rc脚本和shell function都可能改变实际执行闭包；若画像要求non-interactive/no-profile等条件，Runner必须用真实选项/环境实现并验证。所谓“shell integration”注入脚本同样是代码执行，需要明确来源、版本和Effect。

#### PTY输出是字节流加控制协议，不是纯日志

PTY/ConPTY output包含文本与terminal control/virtual-terminal sequences。原始有界输出流继续是运行Observation；terminal renderer可按精确emulation profile产生派生screen/cursor/title/mode视图，但它不覆盖raw stream，也不成为程序状态真源。

```text
TerminalView = derived {
  processOperationAndPtyRef,
  terminalProviderAndEmulationRevision,
  inputOutputEncodingAndVtProfile,
  rowsColumnsAndResizeGeneration,
  terminalModeObservations,
  renderedScreenRevision,
  cursorTitleHyperlinkAndCwdHints,
  rawStreamCoverage
}
```

OSC/CSI/DCS等序列可以要求改window title、hyperlink、clipboard、颜色、鼠标/键盘模式，甚至触发查询/响应。客户端按白名单能力处理：纯screen formatting可以只改派生view；clipboard写、打开URL、下载/文件传输、通知或其他宿主作用必须进入各自真实权限/Effect边界，不能因为字节来自“终端输出”自动执行。模型/日志读取默认得到净化文本与必要标记，不把控制序列解释成指令。

cwd/prompt/command-boundary等shell-integration信息只有在实际受信integration channel或明确可验证脚本边界下才获得对应资格。普通目标程序完全可以输出与OSC/prompt marker相同的字节，因此“终端显示当前目录X”默认只是Provider observation，不能授权文件操作或改变workspace root。

#### Key、输入字节、line discipline和signal分离

用户按键/鼠标事件先由terminal client和当前mode编码成字节/VT input；`write-input`仍只发送最终准确inputRef字节。Ctrl-C字符、ASCII ETX字节和 `command:"signal", signal:"interrupt"`不是同一动作：在不同raw/canonical/processed模式与平台下，前者可能被应用读取、由line discipline转成signal或只是普通字节；后者由Runner按固定ProcessProfile映射到实际控制。

ProcessProfile必须说明`interrupt/terminate`的真实作用域，例如单进程、前台job/process-group或Runner拥有的process tree；不能用启动PID猜。若平台/PTY无法稳定定义本合同要求的scope，则该signal能力为unsupported。foreground job改变后旧scope observation陈旧；同一session中的child shell/job不因共用terminal自动成为同一业务Operation。

echo、canonical/raw、bracketed-paste、mouse和application-cursor等mode是运行中可变Observation。关闭echo只降低终端自身回显，不能证明目标程序、shell hook或日志不会输出秘密。resize成功只证明PTY/ConPTY尺寸状态已更新到Provider承诺范围，不证明应用已经收到/处理resize事件或完成重绘。

#### 退出、shell状态和screen状态分别结算

shell的 `$?`、prompt出现、终端回到某screen、foreground job结束和根process退出是不同事实。交互shell可以在子命令失败后继续存活；prompt文本也可被程序伪造。机器自动化需要命令级结果时，使用有协议的wrapper/integration receipt或直接exec一次命令，而不是从PS1文本/颜色解析成功。

关闭PTY/master可能依据平台使child收到EOF/HUP或其他行为，也可能只是断开显示；本协议仍按真实Runner/process-tree结算，不把“terminal tab关闭”自动当terminate。scrollback、alternate-screen和客户端窗口关闭属于显示生命周期，不能删除仍活跃process/operation的恢复责任。

### 进程扩展的前提、错误与较小客户端

expectedStateRef消费该operation返回的stateRef，保护已观察的本地生命周期/控制前提，不宣称目标程序内存被冻结；普通stdout进度不令其逐字节变化。inputHeadRef只表示输入接纳代，不能拿它控制进程阶段。同一目标被调试器或另一控制者影响时，共享真实目标协调/适配能力；没有目标侧强前提就不把本地比较说成远端CAS。信号/尺寸控制在本operation有未结算控制时不再独立发送相交新控制，读取状态和合法输入仍按各自资格进行。

新增原因沿原ErrorEnvelope：PROCESS_UNSUPPORTED（协议/Runner能力）、PROCESS_INPUT_STALE（输入头变化）、PROCESS_INPUT_CLOSED（已关闭准入）、PROCESS_STATE_STALE（生命周期前提变化）、PROCESS_COMMAND_PENDING（相交控制未决）、PROCESS_INPUT_UNSETTLED（已发送范围未知）、PROCESS_PAYLOAD_INVALID（编码/长度/范围不合法）。额度不足沿原资源诊断，不把未知一律标可重试。空字节输入可接纳为有序无字节项并明确no-bytes，不产生目标已消费的证明；超限输入不能截断冒充全部发送。

不需要交互时使用已有一次性argumentsRef/有限stdin并等待结果，完全不启用本扩展。已有可信原生终端也可继续使用；SEC只接收它确实提供的状态/输出，不伪造逐输入去重。要声称机器客户端支持本扩展，则解码、队列、真实write返回、关闭、取消、权限、重试窗口与输出保留必须共同满足，而不是只接受action字符串。


### 有限交互请求例

下例的O1、H0、I1必须分别来自实际运行、当前输入头和实际封存字节，不是可照抄的真实资源。I1可以是客户端明确编码的`help\n`，但不得由服务擅自补换行。只有该operation已协商本节扩展才有合法请求：

```json
{
  "operationRef": "O1",
  "action": "process",
  "command": "write-input",
  "requestId": "input-1",
  "expectedInputRef": "H0",
  "inputRef": "I1",
  "return": "state"
}
```

响应不明时先查询O1和原input-1；重送相同请求属于该去重窗口内的同意图查回，不换新ID。只有拿到真实新输入头H1且确实要关闭输入时，才另建close-input意图；H1的取得不证明I1已经被目标消费。命令原件、输出状态和查回权限仍依赖前述实际保留范围。


### 与已取回的早期process-session/1草案的边界

本轮另外读到了此前同名r69的另一份真实ZIP（SHA-256 `5d31eb9074e331952594b86c9098497695b51c11bbea6dc6b8c38cc6cda7cbdd`）中`10-产品与开发/操作语义接口与批处理.md#process-session-contract`。该草案不在本轮r72正文，但已经使用`sec.process-session/1`：它的请求是`{operationRef,action:"process",requestId,command}`，`command`是带kind的对象，不能误读成上文字符串及同级字段。

| 旧command.kind | 旧联合字段与独立含义 | 与本节/2的区别 |
|---|---|---|
| input | inputRef、expectedInputRevision；按固定编码取得内容，不接受任意shell字符串 | /2是write-input和expectedInputRef；引用形态与结果取得不同，不按同名猜值 |
| close-input | expectedInputRevision；只结束本流，state/status给inputRevision | /2使用实际输入头引用；关闭/去重/队列仍需原次序 |
| signal | signal；来自所选Runner的真实集合，不假设平台同名信号等义 | /2显式限定interrupt/terminate且有expectedStateRef；不能无损转换任意旧信号或倒推缺少的强前提 |
| resize-terminal | columns、rows；真实pty、正数及能力/额度范围 | /2另外绑定expectedStateRef及未决控制；不能用当前新状态偷偷补成旧请求原意 |

旧草案已经包含“同ID同载荷先查回，再对新输入比较修订并入队”“forwarded不等于业务消费”“输出用原查询”“信号不要求输入修订”这些有效原则；本节保留并细化，不将其说成首次发现。旧草案未规定的强状态前提、短写已知范围、当前有限信号和秘密输出保证，不反向写成旧客户端已支持。

当前设计采用/2的准确内容；服务、客户端与会话必须协商同一版本及合同内容。确有/1客户端时可以由明确的旧适配按旧保证继续工作，但没有该实现就明确不支持，不能试解码/2失败后悄悄按/1运行。显式迁移只在当前已取得旧身份/状态能准确映射、作用含义及去重不变时进行；未知旧输入不换ID重新入队。采用新扩展无需普通作者增加版本台账，客户端按真实能力选择。旧ZIP是历史依据，不是部署、当前源码或通用兼容证明；本次不递归打包该旧ZIP。
