## 游戏与实时交互系统的机制依据

以下资料于 2026-09-27 核对。它们用于证明时间轴、预测重演、线程／GPU 边界和资产代际等机制在成熟引擎中真实存在，不证明 SEC 已采用 Unity、Unreal Engine 或 Godot，也不把某个引擎的默认值升级为 SEC 的通用默认。

### Godot：固定 physics tick、render frame 与线程边界

**来源：** [Godot latest：Physics interpolation introduction](https://docs.godotengine.org/en/latest/tutorials/physics/interpolation/physics_interpolation_introduction.html)；[Thread-safe APIs](https://docs.godotengine.org/en/latest/tutorials/performance/thread_safe_apis.html)。

**核对范围：** 页面明确将 physics tick 与 rendered frame 分开；physics/game logic 采用固定 tick 时更易保持一致，presentation 可在 tick 间插值。线程文档说明并非整个 engine thread-safe，active scene tree 不能无条件从线程修改，与 RenderingServer/GPU 同步可造成 stall。

**采用限制：** `latest` 页面本身标记为不稳定文档，不能代表某个 stable Godot 版本已经提供全部页面能力。SEC 只采用“多时基必须区分”“线程/GPU authority 有真实边界”这两个机制事实，不采用 Godot scene tree、默认 tick rate 或其 API。

**使用位置：** [实时交互多时基](../../领域/计算基础/计算结构与算法.md#interactive-time-determinism)、[游戏实时压力画像](../../演进/领域组合与扩展条件.md#game-realtime-pressure-profile)。

### Unity Netcode for Entities：prediction、rollback、partial snapshot 与结构变化

**来源：** [Netcode for Entities 1.5.0-exp.101：Introduction to prediction](https://docs.unity.cn/Packages/com.unity.netcode%401.5/manual/intro-to-prediction.html)、[1.5.0-exp.2：prediction edge cases](https://docs.unity.cn/Packages/com.unity.netcode%401.5/manual/prediction-details.html)、[1.5.0-exp.2：Optimizing your game](https://docs.unity.cn/Packages/com.unity.netcode%401.5/manual/optimizations.html)；另以[1.0.12 Prediction](https://docs.unity.cn/Packages/com.unity.netcode%401.0/manual/prediction.html)核对较早稳定系列的基本 rollback/resimulation 机制。

**核对范围：** client prediction 在收到 authoritative snapshot 后校正并从旧 tick 重演到当前；高延迟可使一帧执行多个 simulation tick。1.5 实验文档明确 partial snapshot 只回滚收到的 predicted ghosts，并给出 history/input queue 边界；结构增删 component 可使 prediction history 失效并触发更昂贵的回滚／物理重建。

**采用限制：** 1.5 引用是 experimental 版本，具体 queue 常数、组件名和优化选项不成为 SEC 合同。采用的是“重演成本是帧预算的一部分”“局部 snapshot/结构变化会改变 rollback closure”“一次性效果需识别重演上下文”的机制要求。

**使用位置：** [游戏实时压力画像](../../演进/领域组合与扩展条件.md#game-realtime-pressure-profile)。

### Unreal Engine 5.8：Network Prediction 的 tick policy 与服务分解

**来源：** [ENetworkPredictionTickingPolicy](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/NetworkPrediction/ENetworkPredictionTickingPolicy)、[NetworkPrediction API](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/NetworkPrediction)、[FNetworkPredictionSettings](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/NetworkPrediction/FNetworkPredictionSettings)。

**核对范围：** 5.8 API 区分 Independent 与 Fixed ticking，Fixed 支持 group rollback；NetworkPrediction 将 input、tick、rollback、interpolate、smoothing、finalize 等职责作为不同服务暴露，并分别保存 fixed/independent 的输入与插值缓冲设置。

**采用限制：** Unreal 的服务/enum 不是 SEC 需要复制的类层次，只用于反驳把“网络实时”折成一个布尔开关。具体 API、默认缓冲和未实现路径仍属于 Unreal 5.8。

**使用位置：** [游戏实时压力画像](../../演进/领域组合与扩展条件.md#game-realtime-pressure-profile)。

### Unreal Engine 5.8 与 Unity Addressables：asset cook、patch 与运行中代际

**来源：** [Unreal Engine 5.8 Asset Management](https://dev.epicgames.com/documentation/unreal-engine/asset-management-in-unreal-engine)、[Cooking and Chunking](https://dev.epicgames.com/documentation/unreal-engine/cooking-content-and-creating-chunks-in-unreal-engine)、[How to Create a Patch](https://dev.epicgames.com/documentation/unreal-engine/how-to-create-a-patch-in-unreal-engine)；[Unity Addressables 3.0.0 Content update build settings](https://docs.unity.cn/Packages/com.unity.addressables%403.0/manual/content-update-build-settings.html)。

**核对范围：** Unreal 将 source/editor asset 转成目标部署需要的 cooked/chunked content，并在 patch 时与保留的 released cooked baseline 比较；package 是该流程中的实际更新粒度之一。Addressables 3.0 的 Unique Bundle IDs 允许新旧 bundle 在内存中并存，但可能扩大依赖重建、更新尺寸与构建成本。

**采用限制：** 不推导 SEC 必须使用 pak、AssetBundle、某种 chunk 规则或某个 CDN。采用的是 source／derived／cooked／released／resident generation 分离、依赖失效、baseline 保留和 mid-session coexistence 需要显式 identity/lifetime 的机制事实。

**使用位置：** [游戏实时压力画像](../../演进/领域组合与扩展条件.md#game-realtime-pressure-profile)、[资产与非源码](../../作者/工程源/资产与非源码.md)。


### Unreal Engine 5.8：大世界坐标、跨子系统精度与坐标空间

**来源：** [Large World Coordinates](https://dev.epicgames.com/documentation/unreal-engine/large-world-coordinates-in-unreal-engine-5)、[LWC Rendering](https://dev.epicgames.com/documentation/unreal-engine/large-world-coordinates-rendering-in-unreal-engine-5)、[Coordinate System and Spaces](https://dev.epicgames.com/documentation/unreal-engine/coordinate-system-and-spaces-in-unreal-engine)。

**核对范围：** UE5 的 LWC 为核心数据引入 double 精度，但渲染/HLSL与 Niagara 等子系统可以采用不同高低精度／tile 表示；world/local 等坐标空间具有不同 origin 和变换。官方页面同时标注 LWC 为 Beta，并提示升级时可能出现 precision-loss 边界。

**采用限制：** 不要求 SEC 或目标游戏采用 UE 的 DoubleFloat、WORLD_MAX 或 tile 尺寸。采用的是“逻辑空间身份、坐标frame、表示精度和目标子系统布局必须分层；origin/representation变化不能重命名语义对象”的机制事实。

**使用位置：** [游戏实时压力画像](../../演进/领域组合与扩展条件.md#game-realtime-pressure-profile)。

### Unreal Engine 5.8：PSO precache、permutation 与运行时 hitch

**来源：** [PSO Precaching](https://dev.epicgames.com/documentation/unreal-engine/pso-precaching-for-unreal-engine)、[Rendering Settings：Shader Permutation Reduction](https://dev.epicgames.com/documentation/unreal-engine/rendering-settings-in-the-unreal-engine-project-settings)、[Common Memory and CPU Performance Considerations](https://dev.epicgames.com/documentation/unreal-engine/common-memory-and-cpu-performance-considerations-in-unreal-engine)。

**核对范围：** PSO precaching会收集并异步编译潜在运行状态；官方统计区分 hit、missed、untracked、too-late、used，且预编译/保留PSO存在启动、CPU线程与内存成本。项目设置还明确存在shader permutation reduction，改变相关选项会改变需要编译的permutation集合。

**采用限制：** 不采用UE的console variable、20ms示例阈值或具体RHI作为通用默认。SEC只保留variant/permutation closure、工具链/设备/配置身份、runtime hitch与precache资源成本之间的真实取舍。

**使用位置：** [游戏实时压力画像](../../演进/领域组合与扩展条件.md#game-realtime-pressure-profile)。

### WebGPU：device loss 与资源代际

**来源：** [WebGPU Specification](https://gpuweb.github.io/gpuweb/)，Device与Device Loss章节。

**核对范围：** 规范将GPUDevice作为其创建对象的owner；device被lost/destroyed后其对象不可继续使用，设备可能因外部事件被撤销，恢复需要重新取得device并重建相关资源。异步promise除规范列出的边外不能任意推导完成顺序。

**采用限制：** WebGPU只是一条明确公开的设备生命周期证据，不代表所有图形API具有完全相同的错误协议。SEC采用device generation、资源owner、完成同步、loss/readback和重建边界，不把任一Web API变成目标前置。

**使用位置：** [游戏实时压力画像](../../演进/领域组合与扩展条件.md#game-realtime-pressure-profile)。

### Unity Smart Merge：scene/prefab需要结构感知合并

**来源：** [Unity 2018.3 Manual：Smart Merge](https://docs.unity3d.com/2018.3/Documentation/Manual/SmartMerge.html)。

**核对范围：** UnityYAMLMerge用于scene和prefab文件的语义合并，并区分clean merge与需要进一步解决的冲突；可接第三方版本控制。

**采用限制：** 这是一份历史版本资料，只证明“结构化场景内容不能可靠地以普通文本无冲突代替语义无冲突”这一长期机制，不证明当前Unity版本、文件格式或Perforce/PlasticSCM行为。SEC不采用UnityYAMLMerge作为自身依赖。

**使用位置：** [游戏实时压力画像](../../演进/领域组合与扩展条件.md#game-realtime-pressure-profile)、[结构编辑与身份保持](../../作者/组合/结构编辑与身份保持.md)。

### Android／iOS：前后台、暂停、挂起与资源生命周期

**来源：** [Android Activity lifecycle](https://developer.android.com/guide/components/activities/activity-lifecycle)、[Apple Managing your app’s life cycle](https://developer.apple.com/documentation/uikit/managing-your-app-s-life-cycle)。

**核对范围：** Android明确区分create/start/resume/pause/stop/destroy并说明进程被回收风险随状态变化；Apple区分foreground/background/suspended，系统可以断开background/suspended scene回收资源。恢复到前台因此不是“原循环无缝继续”的等价事件。

**采用限制：** 两个平台的callback/API不成为SEC统一平台状态机；目标画像只保存任务实际依赖的lifecycle capability、允许的后台工作、保存/恢复责任、资源generation和外部Provider事实。

## 呈现调用、物理结果与用户体验的证据边界

**核查日期：** 2026-09-27。以下补充只支持相交机制，不代表安装图形 Provider、执行真机测试或完成用户研究。

### Vulkan：呈现调用的接受、同步义务与实际显示不同

**来源：** Khronos [vkQueuePresentKHR 参考页](https://github.khronos.org/Vulkan-Site/refpages/latest/refpages/source/vkQueuePresentKHR.html)。

**核对范围：** 呈现请求的队列操作不包含 presentation engine 对图像的实际处理；该调用定义 device-lost、surface-lost、out-of-date 等不同结果。部分 surface／out-of-date 拒绝仍被视为已入队，相关 semaphore 等待仍有义务；只有具体合同明确保证未入队时，才可据此签发无副作用结论。队列 host synchronization 的要求不是 OS／driver 不会异步撤销设备的保证。

**采用限制：** 此处采用 generation-qualified attempt、接受／完成／显示分层和按真实错误结算的机制；不将 Vulkan、某个错误码集合或“任意 API 都有原子 present”设为 SEC 通用前置。页面为 latest，实施 Provider 必须另行固定实际 API／扩展／驱动画像；WebGPU 的异步设备失效依据继续见本篇已有条目。公开规范与参考页不代替所用 Provider 的符合性证据。

### W3C WAI：用户参与评价与技术符合性相互补充

**来源：** [Involving Users in Evaluating Web Accessibility](https://www.w3.org/WAI/test-evaluate/involving-users/)，页面最后更新于 2024-04-30，本次于 2026-09-27 读取。

**核对范围：** 相应用户执行具体任务能发现仅凭技术检查不易发现的问题；参与者经验与辅助技术会影响结果。少数参与者不代表全部用户，用户评价也不能单独证明无障碍技术符合性；应报告评价范围并与技术检查合用。

**采用限制：** 该资料针对 Web 无障碍，直接支持“真实用户任务证据不能被技术检查替代、反向也不成立”的方法边界；不证明任意游戏或 XR 的舒适、安全、手感或标准符合性。游戏画像据其自身体验 Claim 选择代表性任务／设备／cohort，仍需取得本产品证据，不把 Web 方法名当成游戏验收已通过。

**使用位置：** [游戏实时压力画像](../../演进/领域组合与扩展条件.md#game-realtime-pressure-profile)的使用点呈现、未知结算和真实设备／网络用户验收。
