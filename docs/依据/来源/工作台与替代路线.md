**支持的命题：** kernel process/session与client session分别有身份；execute request/reply、IOPub side effects、busy/idle和execution_count分别传递。execution_count属于kernel执行历史，IOPub还广播stdout/stderr/debug等副作用。

**采用与不能推出：** 用于Notebook/REPL的source/kernel/attempt/output分型；消息parent关系不产生作者ownership，execution_count不成为cell revision，idle只说明相应消息处理边界，不证明任意外部Effect完成。

### Development Containers

**来源与版本：** [Development Containers Specification](https://containers.dev/)及[metadata reference](https://containers.dev/implementors/json_reference/)；动态规范，本次核对2026-09-22。

**支持的命题：** devcontainer.json用于描述如何访问或创建开发容器及工具/runtime stack，并允许Features和工具customization等开发环境配置。

**采用与不能推出：** 配置读取不等于环境已创建；Feature、image、mount、脚本、secret和host能力按实际实现进入Provider/Effect边界。支持该规范的工具名不证明两个环境generation等价。

## 协作收敛与一等冲突的边界

### Automerge collaborative state and conflicts

**来源与版本：** [Automerge Text](https://automerge.org/docs/reference/documents/text/)、[Conflicts](https://automerge.org/docs/reference/documents/conflicts/)；动态官方文档，本次核对2026-09-22。

**支持的命题：** CRDT可以把并发文本/结构变化合并到收敛副本；同一属性并发写在没有自然合并结果时，Automerge会确定性选择可见winner，同时保留冲突值供调用者检查。

**采用与不能推出：** 用于校准“副本收敛≠语义裁决”。Provider内部actor/op/head只属于协作命名域；可见winner不证明业务意图优先、程序类型正确或冲突已经由有权规则解决。

### Jujutsu first-class conflicts

**来源与版本：** [Jujutsu First-class conflicts](https://docs.jj-vcs.dev/latest/conflicts/)及[Working copy](https://docs.jj-vcs.dev/latest/working-copy/)；动态官方文档，本次核对2026-09-22。

**支持的命题：** Jujutsu可把逻辑冲突记录进commit，rebase/merge可以成功而冲突继续存在；冲突随后还可继续rebase/merge/back out，working copy只负责把逻辑冲突物化成可编辑标记。

**采用与不能推出：** 支持SEC允许未决conflict成为候选事实而不强迫立即裁决；Jujutsu commit/conflict表示仍只是VCS Provider事实，不自动成为SEC语义冲突、权限或验证Verdict。

## Local History 与 Merge Queue 的恢复/稳定性依据

### JetBrains Local History 2026.2

**来源与版本：** [IntelliJ IDEA 2026.2 Local History](https://www.jetbrains.com/help/idea/local-history.html)；本次核对2026-09-22。

**本轮实际支持：** Local History独立于VCS自动记录有意义的工程状态变化，可以恢复删除文件、整文件或局部内容，也可添加标签；官方明确说明它不是长期版本控制，记录受retention和size影响并可能被清除。

**采用与不能推出：** 用于把本地历史定义为recovery layer而非作者/发布authority。历史记录存在不证明内容可编译、已测试或被采纳；TTL存在也不允许违反本产品已经承诺的恢复窗口提前删除相交recovery asset。

### GitHub stale reviews 与 merge queue

**来源与版本：** [Managing a branch protection rule](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule)、[About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)、[Managing a merge queue](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)；动态官方文档，本次核对2026-09-22。

**本轮实际支持：** protected-branch策略可以在新代码push或merge base变化后使approval stale；merge queue把PR与最新base及队列前序变更组成临时merge group，并在该组合上执行required checks后再合入。

**采用与不能推出：** 用于ReviewRecord与QueuedIntegrationCandidate的稳定性边界；GitHub的具体review/queue policy不是SEC唯一政策，原PR上的approval/check也不能自动证明新组合树。queue check通过不等于最终target ref已经CAS更新。

## Run Configuration与复合任务的外部依据

### JetBrains 2026.2 Run/Debug Configuration

**来源与版本：** [Application run/debug configuration](https://www.jetbrains.com/help/idea/run-debug-configuration-java-application.html)、[Run compound tasks](https://www.jetbrains.com/help/idea/run-debug-multiple.html)；2026.2/2026.1帮助，本次核对2026-09-22。

**本轮实际支持：** JetBrains run configuration把runtime、main/entry、program args、working directory、target environment等保存为命名配置；Before Launch按顺序执行build、其他configuration、external tool等任务，Compound用于并行启动多个configuration。

**采用与不能推出：** 用于校准DeveloperLaunchProfile和顺序/并行编排需求；IDE中配置存在不证明前置任务纯、ready成立、cleanup完成或拥有执行权限，GIFT不复制任意external-tool字符串作为可信运行合同。

### VS Code tasks 与 compound launch

**来源与版本：** [Integrate with External Tools via Tasks](https://code.visualstudio.com/docs/debugtest/tasks)、[Debugging configurations](https://code.visualstudio.com/docs/debugtest/debugging-configuration)；动态官方文档，本次核对2026-09-22。

**本轮实际支持：** tasks支持`dependsOn`的并行/顺序组合；debug compound可并行启动多个configuration，并支持preLaunchTask和stopAll等组合行为。

**采用与不能推出：** 用于说明开发者确有复合启动/前置任务需求；具体VS Code task/launch JSON、problem matcher和terminal语义不成为GIFT执行模型。后台任务“ready”仍需真实Provider/观察定义。

## 可视图编辑与插件生命周期的外部依据

### JetBrains 2026.2 Diagrams / UML class diagrams

**来源与版本：** [Diagrams](https://www.jetbrains.com/help/idea/diagrams.html)、[UML class diagrams](https://www.jetbrains.com/help/idea/class-diagram.html)、[Diagram toolbar](https://www.jetbrains.com/help/idea/diagram-toolbar-and-context-menu.html)；2026.2帮助，本次核对2026-09-22。

### VS Code Extension Marketplace 与 runtime security

**来源与版本：** [Extension Marketplace](https://code.visualstudio.com/docs/configure/extensions/extension-marketplace)、[Extension runtime security](https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security)；动态官方文档，本次核对2026-09-22。

**本轮实际支持：** VS Code明确区分安装、enable/disable、update、uninstall，并支持不同extension版本；Marketplace签名用于安装时校验package来源/完整性，恶意扩展可进入blocklist。官方也明确extension通常具有与VS Code本身相同的权限，因此publisher trust/Workspace Trust等是重要安全边界。

**采用与不能推出：** 用于把package、installed、enabled、loaded/active和actual permissions分开；Marketplace签名/评分/安装量不证明扩展安全或正确。

### JetBrains plugin signing / compatibility / update

**本轮实际支持：** JetBrains Marketplace/IDE具有plugin package signing与验证，plugin update还需要IDE compatibility检查，可分channel发布，并存在install/update/enable-disable等实际生命周期。

**采用与不能推出：** 签名、兼容验证、Marketplace review和运行时资格分别处理；已下载或已加载实例不会因为listing改变自动从内存和外部状态中消失。

## Snapshot与Visual Baseline更新的边界

### Jest 30 updateSnapshot

**来源与版本：** [Jest 30 CLI](https://jestjs.io/docs/30.0/cli)；本次核对2026-09-22。

**本轮实际支持：** Jest `--updateSnapshot/-u`会重新记录本次运行中失败的snapshot，因此runner具备直接改写测试期望资产的能力。

**采用与不能推出：** 用于证明“更新snapshot”不是普通只读test action，必须在SEC侧作为Oracle/baseline候选修改受控；Jest成功写snapshot不证明新期望正确。

### Playwright Visual Comparisons

**来源与版本：** [Playwright Visual comparisons](https://playwright.dev/docs/next/test-snapshots)；Next文档，本次核对2026-09-22。

**本轮实际支持：** Playwright首次运行可以生成reference screenshot，后续按baseline比较，也提供`--update-snapshots`；官方明确提醒browser rendering会因OS、version、settings、hardware、power/headless等因素变化，并建议在与baseline相同的环境中运行。

**采用与不能推出：** 用于把visual baseline、render environment、comparator/tolerance和实际输出分开；截图相等或baseline成功更新不证明DOM、accessibility、交互或业务Claim。

## Formatter配置解析与Import整理的补充依据

### Prettier配置与EditorConfig

**来源与版本：** [Prettier Configuration File](https://prettier.io/docs/configuration)、[Prettier API](https://prettier.io/docs/api)、[EditorConfig specification](https://spec.editorconfig.org/)；动态/EditorConfig 0.17.2文档，本次核对2026-09-22。

**本轮实际支持：** Prettier从被格式化文件位置向上解析配置，支持JSON/YAML/TOML以及JS/TS等可执行配置，并可消费`.editorconfig`；EditorConfig定义indent、EOL、charset、final-newline等文件样式属性。Prettier API还显式提供`resolveConfig(filePath)`和formatWithCursor等编辑器集成能力。

**采用与不能推出：** formatter结果必须绑定实际文件位置、配置解析、formatter/plugin revision；可执行配置不能因“只是格式化”被当纯数据加载。EditorConfig/Prettier设置也不自动授权覆盖作者未请求的字节。

### TypeScript Organize/Sort/Remove Imports

**来源与版本：** [TypeScript 4.9 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html)及[TypeScript import preservation notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-5.html)；本次核对2026-09-22。

**本轮实际支持：** TypeScript把Organize Imports描述为“删除unused imports后排序”，并另提供只Sort、只Remove命令；TypeScript文档同时说明某些框架/eval等场景下静态分析可能看不见实际值import使用，并提供保留相关import的编译选项。

**采用与不能推出：** `organize imports`不是纯排版；删除/转换import需按实际语言/框架/side-effect语义形成普通候选，不能仅凭编辑器命令分类自动应用。
