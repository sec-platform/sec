## 反馈控制、稳定性与适应性风险

<a id="1-根裁决-2"></a>

### 1. 根裁决

持续调和、自动修复、自动扩缩、策略优化和 Agent 自纠都属于反馈控制。控制器即使每一步局部合理，也可能：

- 振荡；
- 放大噪声；
- 追逐陈旧目标；
- 争夺同一资源；
- 在未建模动态下失稳；
- 把局部改进转移为其他频段、其他资源或其他主体的恶化；
- 因执行器饱和、积分累积、时延和丢包产生不可预期行为。

因此“观察 Current → 写向 Desired → 重复”不是充分架构。

### 2. ControlLoopContract

```text
ControlLoopContract = {
  controlledSubject,
  desiredSignal,
  observationModel,
  actuationModel,
  plant/environmentModel,
  disturbanceModel,
  samplingAndDelay,
  controllerLaw,
  stabilityOrBoundednessClaim,
  saturationAndRateLimits,
  hysteresis/deadband,
  antiWindup,
  conflictArbitration,
  fallbackAndManualMode,
  monitorAndTripConditions,
  assumptionsAndUnknowns
}
```

没有这些字段的 controller 只能是实验性 automation。

### 3. 必要多样性与模型容量

控制器必须具有足够的响应多样性来应对环境扰动；但增加策略数量也增加状态空间、验证成本和误动作表面。正确目标不是无限策略，而是：

```text
required disturbance classes
→ minimum sufficient response repertoire
→ bounded decision policy
→ unhandled disturbance frontier
```

无法覆盖的扰动使对应自动策略的保证失效时，停止相交动作，保留观察和恢复责任；由实际有权主体按已接受政策选择降速、隔离、改方案或其他处理，不继续输出无依据的高置信动作，也不默认把人工介入设成所有任务前置。

### 4. 水床效应

在受限反馈系统中，某一频段或某一指标的误差降低可能迫使其他频段误差增大。工程含义：

- 降低平均延迟可能恶化长尾或恢复；
- 强化缓存命中可能增加陈旧风险；
- 提高自动修复速度可能增加误修；
- 收紧安全门槛可能降低可用性；
- 降低局部资源使用可能增加网络或人工成本。

任何“全面提升”声明必须检查被转移的代价。

### 5. 未建模动态与鲁棒性

真实 plant 可能包含：

- 隐藏状态；
- 非线性；
- 时变参数；
- 传感器偏差；
- 执行器延迟；
- 人和攻击者的策略反应；
- 控制器之间的耦合；
- 结构突变。

自适应控制不能仅依赖在线拟合；必须有鲁棒包络、参数投影、速率限制和失稳检测。

### 6. 多控制器冲突

两个 controller 分别拥有不同目标时，可能形成：

```text
autoscaler 增加实例
cost optimizer 删除实例
repair controller 重建实例
security controller 隔离实例
scheduler 重新放置实例
```

需要：

- 一个作用于相同 state/effect 的仲裁协议；
- 目标优先级和不可补偿约束；
- writer/fencing；
- 控制回路组合分析；
- 共享资源预算；
- 防止互相把对方动作视为 drift。

### 7. 不应自动化的条件

当以下任一成立时，SEC 应输出 `manual-only` 或 `architecture-refused`：

- plant identity 或 observation 不稳定；
- 效果不可逆且无可控试验；
- 关键动态未知且无法安全包络；
- 控制器对同一状态没有合法仲裁；
- 失稳检测和紧急停止依赖同一故障域；
- 反馈延迟大于安全响应窗口；
- 人工接管无法在时限内完成；
- 目标本身随控制动作发生不可识别变化。

### 8. 运行时稳定性保证

```text
StabilityOutcome =
  | FormallyStableWithinModel
  | EmpiricallyBoundedWithinEnvelope
  | StableWithRuntimeShield
  | MarginalOrOscillatory
  | UnmodeledDynamicsDetected
  | StabilityUnknown
  | AutomationRefused
```

### 9. 对 SEC 自身的反身攻击

SEC 的自动工作选择、自动修复、缓存、验证优先级和资源管理也是控制器。它们可能出现：

- 工作选择反复改变导致 candidate churn；
- validator 修改使更多 validator 工作产生；
- 追求覆盖率导致问题库无限增长；
- 自动局部修复制造新的全局依赖；
- 性能优化使验证和恢复被饿死；
- 规划器根据自己的产出调整目标。

对于会持续改变系统的控制面，设计须按任务定义复杂度预算、变更窗口、变化速率及有权停止或隔离的路径。停止可以由已授权的自动策略或实际有权主体触发；只有相应政策要求时才必须由人工完成。

<a id="10-验收-2"></a>

### 10. 验收

- 每个持续 controller 有 plant/observation/actuation/stability contract；
- 模拟时延、噪声、丢包、饱和和控制器冲突；
- 检查平均改进是否转移到长尾、恢复或其他主体；
- 控制器目标变化时旧稳定性证据陈旧；
- 失稳时进入预定义的安全、停止或诊断模式，保留恢复责任；人工模式仅在实际政策要求时使用；
- SEC 自身控制器接受相同审查，不享有元层特权。

## 复杂耦合、正常事故与治理复杂度

<a id="1-根裁决-3"></a>

### 1. 根裁决

系统增加更多类型、检查、证据、控制器、恢复路径和审批，不会单调增加安全。复杂交互和紧耦合会产生：

- 无法由任一组件所有的组合故障；
- 事故期间相互矛盾的恢复动作；
- 控制面依赖业务面，业务面又依赖控制面；
- 操作员无法在时限内理解真实状态；
- 防护层之间的共同原因；
- 安全机制本身成为可用性或事故放大器；
- 规则膨胀后无人能证明完整适用性。

因此 SEC 本身也可能成为它试图治理的最大风险来源。

### 2. InteractiveComplexity 与 TightCoupling

```text
SystemCouplingProfile = {
  componentCount,
  interactionTypes,
  hiddenInteractions,
  synchronizationDependencies,
  sharedResources,
  feedbackLoops,
  failurePropagationSpeed,
  recoveryOrderConstraints,
  operatorDecisionTime,
  substitutability,
  isolationBoundaries
}
```

高交互复杂度与紧耦合同时存在时，不能仅靠更多监控和流程解决。

### 3. 治理复杂度预算

```text
GovernanceComplexityBudget = {
  mandatoryConceptsPerOperation,
  authorityEdges,
  requiredHumanDecisions,
  proofAndEvidenceSteps,
  controlPlaneDependencies,
  recoveryBranches,
  compatibilityStates,
  operatorContextSize,
  expectedFailureModes
}
```

新增控制前分别记录被避免/约束的失败、引入的新故障面、协调与认知成本、恢复复杂度和绕过激励。它们没有天然同一量纲，不能直接相加比较。先检查不可补偿约束，再给出可复核的场景比较、支配关系或经接受的同单位损失模型；未知收益标为待测，不能用一个不具单位的公式证明净收益。

### 4. 二阶治理故障

| 控制 | 可能产生的新故障 |
| --- | --- |
| 强制 Evidence | 证据生产成为瓶颈，团队优化证据而非结果 |
| 单一 owner | owner 不可用导致全局阻塞，或形成权力集中 |
| 自动失效 | 失效风暴和重复验证耗尽资源 |
| 强 fail-closed | 无关能力被阻断，诱导绕过和 shadow system |
| 自动恢复 | 恢复器与正常控制器竞争，扩大损坏 |
| 细粒度权限 | 配置复杂度和误授权增加 |
| 多 Provider | 兼容矩阵和共同最低语义扩大 |
| 全面日志 | 隐私、成本和噪声增加，事故信号被淹没 |
| 多层抽象 | 调试时无法定位真实 effect owner |

### 5. SimplificationCompiler

SEC 需要可执行的删减流程，不只是添加机制；下列分析记录不要求另建一个名为 SimplificationCompiler 的常驻服务：

```text
SimplificationCandidate = {
  subject,
  currentConsumers,
  failurePrevented,
  failureIntroduced,
  derivability,
  replacement,
  observabilityLoss,
  migration,
  retirementProof
}
```

优先顺序：

```text
删除无消费者结构
→ 合并真正同义机制
→ 使用成熟 Provider
→ 缩小适用闭包
→ 隔离而非统一
→ 最后才增加新的中央抽象
```

### 6. 架构拒绝与系统拆分

当一个候选系统出现以下状态，SEC 应建议拆分或拒绝中央自动化：

- 任何局部变化都触发全局失效；
- 单一 authority 成为无法替代的事故点；
- 控制面无法独立于业务面恢复；
- 操作员无法在安全时间内理解状态；
- 相互作用数增长快于可验证能力；
- 没有可证明的故障隔离单元；
- 所有恢复路径共享同一依赖；
- 每项新功能要求修改核心；
- 制度、法域或组织之间不存在合法统一权威。

可能结果：

```text
PartitionSystem
ReduceAutomation
IntroduceManualGate
IsolateCriticalCell
RemoveFeature
RefuseArchitecture
```

### 7. 正常事故不是宿命论

“复杂系统可能发生事故”不意味着无需工程。可降低风险的机制包括：

- 降低耦合；
- 缩小 blast radius；
- 设计独立恢复路径；
- 保留安全裕度；
- 延缓不可逆提交；
- 简化操作员模型；
- 事故演练；
- 多样化冗余；
- 局部自治和明确边界；
- 允许系统停止而非继续错误运行。

但剩余风险必须诚实保留。

### 8. SEC 自身的复杂度体检

每个代际至少测量：

- 核心概念和关系增长；
- 一次最小操作需要加载的模型大小；
- 控制面状态数量；
- 验证动作和平均重跑范围；
- 恢复路径数量；
- 兼容层数量和平均寿命；
- 人工批准和误操作；
- bypass 和 shadow tooling；
- 单点 owner/Provider；
- 从零重建时间。

若这些指标长期恶化而 escaped defects 未下降，说明架构正在失败。

<a id="9-验收-1"></a>

### 9. 验收

- 每个新增治理机制有净收益论证；
- 复杂度预算超限可阻止新抽象；
- 系统支持 `PartitionSystem` 和 `RefuseArchitecture`；
- 控制面独立恢复；
- 事故演练包含治理层自身故障；
- 删除机制和兼容层是正常工作，不是最后清理；
- 小项目不加载最大系统复杂度。

## 安全、隐私、公平与多目标不可兼得

<a id="1-根裁决-4"></a>

### 1. 根裁决（安全、隐私、公平与多目标不可兼得）

安全、隐私、公平、可解释性、个性化、准确率、可用性、审计、数据最小化和成本并不总能同时最大化。某些冲突是结构性的：

- 不同公平定义在基率不同且预测不完美时可能无法同时成立；
- 强隐私会限制统计精度和个体化；
- 强认证和审计可能增加可关联性和隐私风险；
- 强安全隔离可能降低可用性和可恢复性；
- 完全透明可能暴露攻击面、商业秘密或个人数据；
- 个性化最优可能违反群体公平或数据最小化；
- 不保存数据会限制事故调查和申诉。

因此不能把这些目标塞入一个权重向量并宣称“最优综合方案”。

### 2. ConstraintCompatibilityAnalysis

```text
ConstraintCompatibilityAnalysis = {
  constraintRefs,
  subjectPopulations,
  mathematicalAssumptions,
  dataGeneratingProcess,
  compatibilityStatus,
  impossibilityWitness,
  relaxableAndNonRelaxableSets,
  affectedStakeholders,
  decisionAuthority,
  monitoringAndReopen
}
```

结果：

```text
Compatible
ConditionallyCompatible
MutuallyExclusive
InfeasibleWithCurrentInformation
NormativelyUnresolved
```

### 3. 公平不是一个数字

至少区分：

- 机会、结果、错误率、校准、排序、代表性、资源分配；
- 个体公平与群体公平；
- 过程公平与结果公平；
- 当前群体与长期动态影响；
- 受保护属性不可用和代理变量仍然存在的情况。

没有上下文和合法决策，SEC 不能自动选择“正确公平定义”。

### 4. 隐私的不可逆性

隐私泄露通常不能通过删除日志完全恢复。攻击者可能结合外部数据重新识别；模型、缓存、备份和派生结果可能保留信息。

```text
PrivacyEffect = {
  dataSubject,
  purpose,
  recipient,
  linkability,
  inferenceRisk,
  retention,
  downstreamPropagation,
  revocationLimits,
  irreversibility
}
```

隐私保护必须建模推断和关联，不只建模原始字段读取。

### 5. 差分隐私不是免费保护

差分隐私在明确邻接关系、随机机制与参数下约束相邻数据集输出分布的可区分程度；不是“泄露字节数上界”或零泄漏承诺。它有组合预算与效用代价，系统必须记录：

- 邻接关系；
- epsilon/delta；
- composition；
- 查询和发布次数；
- 群体和个体用途；
- utility loss；
- attack model；
- 预算耗尽后的行为。

不存在对所有查询和损失函数都最优的通用机制。

### 6. Security–Usability–Recovery 三角

- 更强密钥隔离可能使灾难恢复困难；
- 更严格最小权限可能阻断紧急处置；
- 更强自动锁定可能被对手用来制造拒绝服务；
- 更详细审计可能泄露敏感元数据；
- 更短凭证寿命增加失效和轮换负担。

方案必须展示权衡和故障模式，不用“零信任”“隐私优先”等口号结束设计。

### 7. 非补偿约束与合法裁决

顺序固定为：

```text
legal and rights boundaries
→ irreversible harm constraints
→ safety/security minimums
→ feasibility
→ distributional impacts
→ Pareto/risk comparison
→ legitimate policy decision
```

不可补偿项不能被总收益抵消；但哪些权利和风险属于不可补偿边界本身可能是制度问题，SEC 只能执行已接受规则并保留冲突。

### 8. 无可行解时必须拒绝

例如同时要求：

- 完全匿名；
- 永久可审计到具体个人；
- 零数据保留；
- 任意历史决定可重放；

若没有额外密码、可信第三方或分层披露机制，这些要求可能互相冲突。输出应为：

```text
NormativeConflict {
  minimal conflicting set,
  affected rights,
  technical options,
  unavoidable losses,
  decision authority,
  safe default
}
```

<a id="9-验收-2"></a>

### 9. 验收（安全、隐私、公平与多目标不可兼得）

- 每个公平/隐私/安全 Claim 有主体、范围和定义；
- 对受支持的形式化约束检测/证明不兼容，并保留定理前提；不承诺通用自然语言公平要求的自动完全判定；
- 隐私派生和外部关联进入风险；
- 预算组合和长期使用可审计；
- 不用单一综合分数消除规范冲突；
- 无可行解时停止自动化并提交合法裁决。

## 策略主体、指标博弈与制度反身性

<a id="1-根裁决-10"></a>

### 1. 根裁决（策略主体、指标博弈与制度反身性）

工程系统中的人、团队、供应商、用户、攻击者和 Agent 不是静态输入分布。规则、指标、奖励、检测和建议一旦发布，会改变他们的行为。于是：

```text
policy changes behavior
behavior changes observed data
observed data changes model
model changes policy
```

原来在被动环境中正确的优化器，在策略环境中可能失效。

### 2. Goodhart 与指标异化

当代理指标成为目标时，参与者会优化指标而非真实结果。常见形式：

- 选择最容易通过的测试；
- 把大任务拆成更多 Issue/PR；
- 关闭未知而不是减少未知；
- 优化平均延迟并牺牲尾延迟；
- 通过排除困难用户提升成功率；
- 增加文档数量而不增加设计质量；
- 用更多 Evidence 对象替代更强证据；
- 调整模型输出以通过 evaluator。

### 3. MetricContract

```text
MetricContract = {
  role: objective | acceptance-threshold | observed-measure | proxy,
  intendedOutcomeRef,
  causalRationale,
  numerator/denominator,
  populationAndExclusions,
  measurementProcess,
  gameabilityAnalysis,
  counterMetrics,
  distributionAndTail,
  auditSampling,
  retirementTrigger
}
```

指标须标明是目标、验收阈值、实际测量还是代理信号；实际值与目标值分开。用户可以明确把一个指标作为目标或约束，未经接受的代理指标不能自行替代原任务，也不能成为权限根。

### 4. 策略行为模型

```text
StrategicActorModel = {
  actorRef,
  informationAvailable,
  objectivesAndConstraints,
  actionSpace,
  adaptationTimescale,
  abilityToManipulateObservations,
  collusionAndExternalities,
  recourseAndExit,
  uncertainty
}
```

系统设计至少攻击：

- 单主体规避；
- 多主体合谋；
- 审核者与被审核者共享激励；
- Provider 隐藏失败；
- 用户绕过限制；
- Agent 学会迎合评分器；
- 组织把不可见成本转嫁给其他团队。

### 5. 社会选择与机制设计边界

多个主体对方案的排序可能不同。不存在一套无条件同时满足所有公平、非独裁、效率和策略免疫要求的聚合规则。

因此 `DecisionPolicy` 必须公开：

- 谁有资格表达偏好；
- 哪些权利是不可补偿约束；
- 谁有否决权；
- 如何处理利益冲突；
- 是否允许转移支付或成本分摊；
- 是否可操纵；
- 谁能申诉和重开；
- 决策在哪个法域有效。

系统不能用一个“客观综合评分”隐藏制度选择。

### 6. 预测的反身性

当预测用于改变世界时，训练分布和结果会改变。例子：

- 预测高风险用户后限制其权限，观察到的低事故可能来自限制；
- 自动分配资源后请求模式改变；
- 推荐系统改变用户兴趣；
- 安全检测公布后攻击者迁移路径；
- 工程风险评分影响团队上报行为。

需要 `PerformativeEvaluation`：

```text
pre-policy distribution
policy intervention
post-policy behavior
feedback delay
strategic adaptation
counterfactual baseline
```

### 7. 组织和权力不是实现细节

形式上最优的责任边界若与组织激励冲突，可能产生：

- shadow system；
- 绕过控制；
- 数据不报；
- 风险转嫁；
- 审批疲劳；
- 责任无人承担；
- 安全团队成为瓶颈；
- 紧急权限常态化。

SEC 必须把组织能力、激励和责任接受作为部署条件，而不是假定 Schema 一经定义就会被遵守。

### 8. 策略鲁棒决策

```text
StrategicRobustnessOutcome =
  | IncentiveCompatibleWithinModel
  | ManipulationDetectedAndBounded
  | AuditableButGameable
  | RequiresInstitutionalEnforcement
  | StrategicEquilibriumUnknown
  | MechanismInfeasible
```

### 9. 反自动化边界

当系统无法验证偏好真实性、影响主体没有表达渠道、决策不可逆且规则高度可操纵时，不应由自动架构选择器替代制度裁决。

<a id="10-验收-5"></a>

### 10. 验收

- 每个核心指标有 gameability 分析；
- 指标优化不直接签发成功；
- 对手知道规则后重新测试；
- 检查不同主体的成本分布；
- 决策策略有申诉和撤销；
- 模型上线后评估行为反馈；
- 无法满足策略免疫时公开剩余操纵风险。
