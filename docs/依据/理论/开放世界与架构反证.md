## 不可满足的完美目标与最大诚实保证

### 1. 不可同时兑现的承诺

下列目标作为愿景有价值，但不能同时成为对开放任意工程的无条件产品保证：

```text
发现全部问题
理解全部语义
找到唯一全局最优架构
保证任何未来变化只需局部修改
证明系统绝对正确
自动处理所有冲突
零失败、零泄露、零停机、零误判
对所有主体公平
无限扩展且没有治理成本
```

继续使用这些措辞会迫使系统隐藏未知、扩大假设、伪造精确度或把未满足状态包装成“已设计”。

### 2. 最大诚实保证

下面是诚实与作用边界的不变量，不是已经证明存在唯一的“最强保证”，也不是SEC的全部产品目标。具体工程仍应获得有用的定义、生成、修改与交付能力：

> 对一个明示目的、模型组合、观察切面、故障模型、资源预算、法域、权威、风险包络和有效期，系统不会把未知、冲突、不可判定、无解、未执行、未结算、未验证或越权状态伪装成成功；在允许产生效果时，能够追溯决定、限制影响、读回现实、恢复失败并在假设变化后重开结论。

### 3. 条件化保证结构

```text
Guarantee = {
  claim,
  subjectAndPurpose,
  modelCells,
  observationCuts,
  assumptions,
  dependencyEvidence,
  failureAndAdversaryModel,
  resourceAndTimeBounds,
  authorityAndJurisdiction,
  verificationEvidence,
  physicalValidation,
  validityHorizon,
  residualUnknown,
  falsifierAndReopen
}
```

上述是保证可能需要的字段角色，不要求所有纯函数填写完整世界模型。缺少当前声明确实必要的依据时，保留该声明的未知、条件或未满足状态并说明取得方式；已有明确来源的缺省可依法解析，但不能伪造观察和权威。较弱声明可以作为附加结果单独给出，不能以“降低等级”静默改写任务原本要求的保证。

### 4. 完美的不同含义

| “完美”含义 | 可达性 |
| --- | --- |
| 在有限形式域内证明满足全部约束 | 可以，需闭合模型和证明 |
| 在明示候选空间和目标函数内找到最优 | 可以，需有界可判定 |
| 对声明故障模型实现容错界限 | 可以，需满足模型前提 |
| 对开放现实绝对无错 | 不可保证 |
| 对所有未来工程保持同一根架构 | 不可保证 |
| 同时满足所有主体全部偏好 | 通常不可保证 |
| 消除全部可信根和假设 | 不可保证 |
| 证明未知问题不存在 | 一般不可保证 |

### 5. 产品行为

当用户要求不可达“完美”时，系统必须：

1. 分解请求中的不同完美含义；
2. 识别可形式证明的有限子域；
3. 给出不可能性、冲突或未知的证据；
4. 说明哪些约束可放宽以及代价；
5. 给出可逆实验或低风险子问题；
6. 输出当前范围内有依据的保证、未决与可继续路径；不把未找到更强保证称为已经证明最大；
7. 保留拒绝和重开条件。

### 6. 防止“诚实边界”成为保守借口

未知应标记可用处理途径及前提：新增观测、限制输入域、形式证明、统计实验、有权主体作规范选择，或在可观测且反应来得及的条件下用运行控制限制危害。这些方法可并用，不构成互斥穷尽分类。

理论上可能补证不等于当前预算、权限或时间内可完成。所选输出必需保证尚不满足时，可以返回待补证、超预算或对该输出拒绝；不能把“可以研究”当作立即执行危险效果的许可。独立可交付的安全子域仍应完成。拒绝说明具体障碍、已完成部分、可改变条件和重新准入要求，不把类别不可判定当作当前实例无解。

### 7. 终局标准

最顶级架构不是声称自己没有边界，而是：

- 清楚知道每个结论为何成立；
- 清楚知道哪些结论无法成立；
- 能在边界内尽可能强地证明；
- 能在边界外拒绝伪造确定性；
- 新事实到来时只推翻真正依赖它的结论；
- 根假设被推翻时敢于重建整个受影响模型；
- 不让“完美”口号压倒现实、逻辑和他者权利。

## 辅助设计的不可达结果与人工裁决

### 1. 目的

本候选代数用于辅助设计与高风险动作准入的具体诊断。不同失败原因应保留，但不要求普通源码生成预先证明全部安全性质。结果是否阻断取决于所选输出、必需声明和效果范围。

### 2. 辅助设计结果候选

```text
DesignExplorationOutcome =
  | VerifiedSolution {
      definitionRef,
      solutionRef,
      assuranceRef,
      validityEnvelope
    }
  | BoundedCandidatePortfolio {
      candidates,
      dominance,
      bounds,
      unexploredFrontier
    }
  | ExperimentRequired {
      informationGap,
      safeExperiment,
      valueOfInformation
    }
  | HumanDecisionRequired {
      normativeConflict,
      authorizedDecisionProcedure,
      safeDefault
    }
  | Infeasible {
      unsatCore,
      nonRelaxableConstraints
    }
  | NoGeneralDecisionProcedure {
      propertyClass,
      knownBoundaryRef,
      perInstanceEvidenceOrUnknown
    }
  | ResourceBoundedUnknown {
      partialResults,
      lowerUpperBounds,
      resumeContract
    }
  | ObservationInsufficient {
      missingCoverage,
      safeObservationPlan
    }
  | CoordinationUnattainable {
      failure/synchrony assumptions,
      conflicting guarantees
    }
  | AssuranceInsufficient {
      openAssumptions,
      TCB/frontier,
      missingEvidence
    }
  | NormativeConflict {
      authorities,
      rights/constraints,
      jurisdiction
    }
  | IrreversibilityUnacceptable {
      potentialLoss,
      missingRecovery,
      acceptingAuthority
    }
  | ArchitectureRefused {
      refusalReasons,
      minimumConditionsForReopen
    }
```

### 3. ArchitectureRefusal

拒绝条件不是随意阈值。至少包括：

```text
ArchitectureRefusalReason =
  | ImpossibleRequirementSet
  | UnboundedUnknownOnIrreversibleEffect
  | NoLegitimateDecisionAuthority
  | UncontrolledCrossDomainCoupling
  | RecoveryPathUnprovable
  | SafetyEnvelopeUnavailable
  | StrategicManipulationDominates
  | GovernanceComplexityExceedsBenefit
  | TrustRootUnclosed
  | RequiredCoordinationImpossible
  | PreservationContractUnavailable
  | PhysicalAssumptionsUnacceptable
```

### 4. 拒绝后的产品行为

拒绝不能只输出一句“做不到”。必须给出：

- 最小冲突或不可达证据；
- 哪些需求可保留；
- 哪些条件若放宽可重新打开；
- 是否存在低风险子问题；
- 是否可以只读观察；
- 是否可以做可逆实验；
- 人工或制度裁决需要什么材料；
- 当前最安全状态；
- 可能的系统拆分方案。

### 5. 人工裁决不是万能兜底

`HumanDecisionRequired` 只用于真正不可推导的规范选择。人工不能：

- 使不可实现需求变得可实现；
- 使物理未知消失；
- 用签字代替权限或安全控制；
- 把未执行测试变成通过；
- 接受他无权代表主体的风险；
- 取消法律和基本权利边界；
- 证明未知外部效果未发生。

### 6. 决策材料

```text
HumanDecisionPacket = {
  exact question,
  affected stakeholders,
  candidate portfolio,
  hard constraints,
  irreducible tradeoffs,
  risk envelopes,
  unknowns,
  reversible options,
  dissenting assertions,
  authority and jurisdiction,
  expiry and appeal
}
```

禁止把数百页文档直接推给人类并称为知情批准。

### 7. 安全默认值

按效果分类：

| 效果 | 默认 |
| --- | --- |
| 纯只读、低披露 | 可降级执行并显示未知 |
| 可逆局部变更 | 可做隔离实验 |
| 可补偿外部效果 | 需要 compensation 与读回 |
| 不可逆高损失 | 未闭合则拒绝 |
| 法律/权利冲突 | 保持最小披露和最小效果，交合法裁决 |
| 协调不可能 | 缩小一致性范围、延迟或人工协调 |

### 8. 结果的可组合性

一个子问题 `VerifiedSolution` 不得覆盖另一个子问题的 `Unknown` 或 `Refused`。组合结果按最强阻断关系计算，并保留局部可用能力。

```text
CompositeOutcome = {
  usableSlices,
  blockedSlices,
  crossSliceConflicts,
  overallEffectCeiling
}
```

### 9. 重开协议

每个不可达结果给出：

- 新信息；
- 新能力；
- 约束放宽；
- authority 变化；
- 安全包络；
- 外部系统升级；
- 可逆实验；

中的哪些变化可以重新编译。没有因果变化不得无限重试同一求解。

### 10. 验收

- 所有不可达状态是稳定机器类型；
- UI/API/CLI 保留它们，不映射成 generic error；
- 无解声明提供可检查的不满足证据；只有执行并通过最小化检验时才称最小冲突；
- 超预算保留进度和界限；
- 人工包有最小充分信息；
- 拒绝不阻断无关低风险切片；
- 拒绝和未知不能被 override 静默改为成功。

## 开放世界覆盖不可证明与挑战集过拟合

<a id="1-根裁决-5"></a>

### 1. 根裁决

任何有限问题目录、事故库、测试集和跨域挑战集都不能证明“未覆盖问题不存在”。更危险的是，架构可以逐渐适配已知挑战，形成与机器学习测试集过拟合同构的状态：

- 每个历史事故都有对应规则；
- 每个已知测试都通过；
- 新机制一出现，根模型仍需重写；
- 团队只寻找能被当前 ontology 表达的问题；
- 不可测或不方便的问题被排除；
- 挑战来源共享同一工程文化和假设。

### 2. CoverageClaim 的新定义

```text
CoverageClaim = {
  systemDefinitionRefs,
  challengeCorpusRefs,
  sourceClassDistribution,
  mechanismFamilies,
  environments,
  stakeholderCoverage,
  temporalHorizon,
  searchStrategies,
  independenceAndBlindSpots,
  explicitUncoveredFrontier,
  validityAndReopenTriggers
}
```

只允许声称：

```text
在这些来源、机制、环境、时间和搜索策略下，尚未发现新的决定性缺口。
```

不允许声称：

```text
所有未来问题已覆盖。
```

### 3. 挑战集过拟合检测

需要专门测试：

- 留出领域和事故家族；
- 盲评未参与设计的案例；
- 对机制做名称和表面结构变换；
- 从完全不同学科引入问题；
- 让攻击者专门构造当前 schema 无法表达的状态；
- 对已知案例移除关键词，检查是否仍能识别机制；
- 在不更新 Core 的前提下加入新领域；
- 检查系统是否用 `other/unknown` 掩盖缺口。

### 4. 来源独立性

多个网页转述同一事故只算一个来源 lineage。挑战语料必须轮换：

```text
formal impossibility results
real incident postmortems
negative research results
failed migrations
hardware errata
legal conflicts
user support failures
organizational bypasses
adversarial security reports
field telemetry
unpopular minority cases
successful but extremely costly systems
```

### 5. 未知未知的响应能力

无法预测具体新机制时，仍可设计：

- blast-radius 限制；
- reversibility；
- independent readback；
- residue preservation；
- emergency isolation；
- external challenge intake；
- schema evolution；
- conflict-tolerant knowledge；
- conservative effects；
- post-incident root-model rollback。

这些是未知响应能力，不是未知问题覆盖证明。

### 6. ResidualUnknownBudget

```text
ResidualUnknownBudget = {
  affectedSubjects,
  effectSeverity,
  reversibility,
  observationBlindSpots,
  modelUncertainty,
  commonCauseExposure,
  challengeFreshness,
  toleratedUnknownClass,
  acceptingAuthority,
  expiryAndReassessment
}
```

高风险不可逆操作不能接受无界未知；低风险、可撤销、隔离良好的操作可以在显式预算内运行。

### 7. 分布变化与新攻击

未来环境可能改变：

- 语言和工具链；
- 硬件和微架构；
- 攻击者能力；
- 组织激励；
- 法律；
- 用户群体；
- 资源价格；
- AI 模型；
- 供应链；
- 网络和地缘环境。

旧 Evidence 的有效性必须有时间和分布边界。

### 8. 覆盖关闭的更严格形式

```text
CoverageEpochClosed =
  every admitted challenge has disposition
  and no known critical seam is ownerless
  and holdout challenges do not expose a root-model failure
  and source/discipline diversity meets the declared profile
  and residual unknown budget is accepted and unexpired
  and reopen triggers are active
```

即便成立，也只表示该 epoch 的条件化关闭。

### 9. 反例驱动的根回退

新挑战若推翻：

- identity law；
- authority law；
- observation model；
- effect model；
- assurance composition；
- locality assumption；

必须回到相应根合同重建所有依赖者。禁止只在 challenge 文档末尾添加例外继续维护旧架构。

<a id="10-验收-3"></a>

### 10. 验收

- 挑战集有 holdout；
- 来源 lineage 去重；
- 每轮包含负面结果和失败案例；
- 旧模型可被正式推翻；
- 残余未知有预算和接受人；
- 新分布触发 Evidence 陈旧；
- 不存在 `allProblemsCovered` 状态。

## 最强竞争架构与不建造方案

### 1. 为什么必须比较“不建 SEC”

任何架构评审若只比较 SEC 内部变体，就已经锚定了“必须有一个统一通用工程编译器”。最强反方是：问题可能更适合由现有编译器、领域工具、人工工程流程和小型 AI 助手组合解决；中央语义系统会增加成本、延迟、模式迁移和新的单点故障。

因此 `DoNothingOrUseExistingTools` 必须作为正式候选，而不是被排除在设计搜索之外。

### 2. 竞争架构

| 候选 | 核心机制 | 优势 | 决定性不足 | 适用边界 |
| --- | --- | --- | --- | --- |
| 不建统一平台 | 现有 IDE、编译器、测试、Git、人工审查 | 成本最低、成熟、认知负担小 | 跨工具真值、恢复、权限和长期演进分散 | 小型、低风险、短生命周期工程 |
| Agentic IDE | 模型读取代码并产生补丁 | 交互快、产品闭环短 | 是否缺少相应语义、权限、事务和证据，依据具体合同与必要事实核查；需要实际结果时再测，不能只按品类断言 | 可逆、低风险、人工监督变更 |
| 规则化代码生成器 | 模板、Schema、DSL 到源码 | 确定、易验证 | 只能覆盖预定义模式，Brownfield 能力弱 | 结构规则稳定的领域 |
| 模型驱动工程平台 | 中央模型生成多个制品 | 一致性和复用强 | 容易形成万能模型、人工代码 round-trip 困难 | 受控领域和封闭生命周期 |
| 知识图谱加工作流 | 图存事实，工作流执行操作 | 可查询、来源和协调能力强 | 图不自动提供语义、可判定性和物理事务 | 组织知识和跨系统编排 |
| 证明助理中心 | 规范与证明驱动实现 | 高保证、边界清楚 | 成本高、模型—现实映射和工具链仍需信任 | 小型高风险核心 |
| 微内核式工程服务 | 多个独立工具通过窄协议组合 | 故障隔离、可替换 | 组合保证和全局影响仍困难 | 多团队大型系统 |
| SEC 最小工程闭包及条件扩展 | 工程语义编译、受控效果和保证；需要时加入模型组合 | 统一跨阶段因果链，支持存量与生成 | 复杂、实现成本高，可能过度治理 | 长期、高风险、跨语言、Agent 密集工程 |

### 3. 不存在绝对赢家

候选优劣取决于：

- 工程寿命和变化率；
- 失败后果和不可逆性；
- 语言、平台和 Provider 数量；
- 存量工程复杂度；
- 自动化写入比例；
- 合规、审计和恢复要求；
- 团队规模和认知能力；
- 可接受延迟与成本；
- 是否存在正式模型；
- 外部世界是否可观测和可控制。

因此顶层产品选择本身也是 `PurposeBoundDecision`，不能由 SEC 自身预设自己获胜。

### 4. 何时应拒绝采用 SEC 全栈

满足下列组合时，优先采用更简单方案：

- 单仓、单语言、单团队；
- 修改全部可人工审查且容易回滚；
- 无高风险外部效果；
- 现有工具已经提供可靠静态和动态验证；
- 语义建模成本超过重复问题成本；
- 没有跨语言、跨 Provider 或跨法域要求；
- 系统生命周期短，不需要长期迁移和历史解释；
- SEC 的控制面成为主要故障源。

### 5. 何时 SEC 才可能形成支配优势

- 多语言、多模型和多目标共存；
- 大量存量工程需要重建、采纳和局部治理；
- Agent 或自动化持续产生工程效果；
- 需要跨源码、数据、部署和运行的端到端追踪；
- 错误恢复、审计和不可逆风险很高；
- 传统工具反复产生状态漂移、隐藏依赖和假验证；
- 新 Provider、语言和规则的接入频繁；
- 需要把无解、未知和规范冲突作为产品结果。

### 6. 分拆退出策略

若统一 SEC 平台不能证明净收益，仍应保留可独立采用的组件：

```text
Workspace Observation
Dependency Evidence
Engineering IR
Implementation Resolution
Mutation Transaction
Verification Evidence
Architecture Refusal
Migration and Retirement
```

每个组件使用公开窄合同，能够被现有 IDE、CI、构建系统和人工流程单独消费。统一产品失败不能迫使这些机制一起废弃。

### 7. 比较实验

对同一真实工程任务比较：

```text
现有工具 + 人工
Agentic IDE
领域生成器
SEC 最小闭包
SEC 完整闭包
```

测量：正确性、漏检、假通过、修改范围、返工、认知成本、执行成本、恢复时间、迁移成本、用户完成率和长期维护。SEC 只有在声明适用域内形成非支配或有权接受的净优势时才应被采纳。

<a id="8-架构反转条件-1"></a>

### 8. 架构反转条件

出现以下结果时，终局架构应从“统一平台”反转为“联邦组件库”：

- 通用内核持续增加领域分支；
- 多数真实操作只消费极小子集，却必须承担全局控制成本；
- 模型同步成本高于避免的缺陷；
- 真实工程师频繁绕过控制面才能工作；
- 统一数据库或协调器成为可用性和安全瓶颈；
- 组件组合通过窄协议即可达到同等保证；
- 用户结果没有相对简单方案的可测改善。

### 9. 比较表的证据地位

上述表格是机制假设与实验候选，不是截至当前日期对市场全部产品做过测试的事实表。现有工具可以通过集成补上某些短板，SEC 也可能无法实现预想优势；费用、成熟度、支持能力、实际恢复和用户结果必须使用指定版本与同任务基线验证。未作指定版本与同任务产品实测，不由品类名称直接裁决胜负。

## 未来计算范式与架构反转情景

### 1. 目的

本页不预测某项技术必然发生，而是寻找会使当前 SEC 根假设失效的未来情景。情景只有在带来新机制时才影响架构；品牌和时间表不进入核心。

### 2. 情景 A：自修改和持续学习系统

系统在部署后修改模型、策略、代码或数据表示，导致：

- target 与 current 持续变化；
- 同一输入不再产生同一输出；
- Evidence 很快陈旧；
- 模型能影响验证分布；
- 传统静态 candidate tree 不再覆盖真实行为。

所需修订：行为 envelope、在线版本身份、不可变审计切面、runtime shield、学习权限和回滚数据。

### 3. 情景 B：开放多智能体生态

多个自主 Agent 具有不同目标、私有信息和策略，可能合作、欺骗、合谋或产生新协议。单一 planner 无法拥有完整状态。

所需修订：策略主体模型、机制设计、身份与信誉、协议沙箱、资源和权限市场、共同原因、不可协调结果。

### 4. 情景 C：量子与概率计算成为工程后端

量子、随机和近似算法可能只给出概率分布或置信度，且测量改变状态。相同程序的单次结果不确定。

所需修订：概率语义、重复测量、误差缓解、硬件校准、随机性来源、统计 Verification 和不可复制状态边界。

### 5. 情景 D：模拟、神经形态和连续计算

连续电路、神经形态芯片和物理计算可能没有传统离散指令/状态模型，行为受噪声、漂移和制造差异影响。

所需修订：hybrid/continuous semantics、鲁棒区间、校准、物理 twin、delta-decision 和安全包络。

### 6. 情景 E：生物和可编程材料

工程对象可能生长、变异、扩散、不可完全回滚，并受到生态和伦理约束。传统文件/进程/事务抽象失效。

所需修订：群体状态、概率转移、 containment、不可逆 release、长期监测、外部性和多代影响。

### 7. 情景 F：高度动态法律与数据主权

同一系统在多个地区同时受到冲突的保存、删除、解释、可访问和披露要求。单一系统定义不可合法适用所有环境。

所需修订：法域 ModelCell、目的绑定、数据驻留、冲突决议、退出和局部拒绝服务。

### 8. 情景 G：软件供应链由生成模型主导

大量源码、测试、依赖和文档由相同少数模型生成，形成新的共同原因：

- 表面实现多样，认知错误同源；
- 训练数据污染所有 reviewer；
- 模型更新改变工程风格和缺陷分布；
- 评测被训练吸收；
- 提示和工具链成为供应链输入。

所需修订：模型 lineage、训练/评测隔离、模型多样性、独立形式 oracle、生成来源和长期撤销。

### 9. 情景 H：硬件可信边界碎片化

云、边缘、可信执行环境、GPU、加速器和外部设备拥有各自 firmware 和 attestation 根，无法归约为一个平台 authority。

所需修订：异质信任图、远程证明局限、组合 TCB、硬件撤销、供应商退出和跨根验证。

### 10. 情景 I：环境和能源约束成为硬边界

能源、冷却、水、碳、芯片供应和网络资源可能从成本维度升为不可补偿约束，迫使架构从集中计算转向边缘、延迟容忍或功能降级。

所需修订：能源预算、地理/时间调度、服务降级、生命周期环境影响和硬件替代。

### 11. 情景 J：攻击者能自动搜索整个工程空间

攻击 Agent 可以持续发现配置组合、社会工程、协议状态和供应链路径。静态威胁模型失效。

所需修订：持续对抗、动态攻击面、自动隔离、速率限制、欺骗检测、秘密最小化和恢复优先设计。

### 12. 情景 K：系统规模超过人类可理解闭包

依赖和状态增长到任何个体都无法理解，AI 也无法提供可证明完整摘要。

所需修订：责任分区、局部自治、可组合合同、限制耦合、拒绝中央控制、独立恢复和结构化未知。

### 13. 情景 L：目标持续变化且无法冻结

市场、政策、用户和攻击环境变化速度快于完整编译/验证周期。冻结后即过时。

所需修订：validity horizon、连续保证、分层快速/慢速环、可逆发布、在线 monitor 和目标版本化。

### 14. 跨情景共同原则

这些情景共同推翻“一个静态系统定义永久支配运行”的假设。终局架构必须允许：

```text
多个上下文模型并存
+ 目的绑定编译
+ 有效期和重开触发
+ 运行时保证
+ 残余未知
+ 不可自动化结果
+ 安全停机和退出
```

### 15. 验收

每次引入新计算范式时先检查它是否改变：

- identity；
- determinism；
- observability；
- reversibility；
- resource law；
- authority；
- proof model；
- lifecycle；
- stakeholder impact。

只有出现新不可约语义才修改 Core；否则通过领域扩展和 Target profile 接入。

## 架构反证研究与采用范围

### 1. 审计对象与方法

该研究材料检验下列无条件命题；它们不一定是当前设计作出的承诺，不能先替 SEC 添加一个过强命题再宣称推翻整个架构：

- 一个系统可以拥有单一完整定义；
- 每项事实可以有唯一 owner；
- 输入依赖可以被精确闭合；
- 通用编译器可以为任意工程找到最优架构；
- 形式证明可以闭合整体正确性；
- 组件保证能够自然组合；
- 自动调和总能收敛；
- 挑战语料足够大就能证明问题覆盖；
- 人工批准可以补齐技术和制度缺口；
- 更完整的治理模型总能提高系统质量。

攻击面覆盖计算理论、复杂度、程序语义、分布式系统、控制论、硬件、密码与侧信道、经济学、社会选择、组织行为、人工智能、法律、隐私、安全工程、系统事故和未来计算范式。

### 2. 根级颠覆结论

| 被检验的无条件命题 | 研究裁决 | 原因 | 可采用的机制 |
| --- | --- | --- | --- |
| 全局唯一系统定义 | 推翻 | 多上下文、法域和权威可以合法冲突 | `ModelPortfolio` 与 `PurposeBoundSystemDefinition` |
| 每项事实唯一 owner | 推翻并分型 | 物理 writer 唯一不等于客观真值唯一 | `AssertionSet`、`ResolutionProtocol`、`DefinitionResponsibility` |
| 默认精确观察 | 限定 | 开放世界和分布式现实通常只能获得切面 | `ObservationCut` 与一致性等级 |
| 默认精确输入闭包 | 推翻 | 动态行为、反射、外部世界和不存在性依赖不可普遍完全判定 | `InputDependencyClaim` 与证据等级 |
| 相同 ActionKey 即可正式复用 | 推翻 | key 可以建立在低等级依赖声明或过期假设上 | `ActionKey` 与 `CacheEligibility` 分离 |
| 任意工程存在可找到的全局最优架构 | 推翻 | 不可判定、复杂度、无免费午餐、目标冲突和策略行为 | 有界候选组合、满意解、实验、人工裁决或拒绝 |
| 形式证明能消除全部信任 | 推翻 | 模型、翻译、证明器、编译器、硬件和物理映射仍需假设 | `AssumptionLedger` 与 TCB 图 |
| 组件正确自然推出系统正确 | 推翻 | 环境假设、交互、共享故障和链接上下文可破坏组合 | 显式组合定理与系统级反例搜索 |
| 反馈自动化必然收敛 | 推翻 | 时延、未建模动态、耦合和策略响应可导致振荡 | `StabilityEnvelope` 与人工/监控/停止模式 |
| 有限挑战集可以证明开放世界充分覆盖 | 推翻 | 挑战集可以被过拟合，未知机制不存在性不可证明 | 条件覆盖、保留集、来源轮换和残余未知预算 |
| 人工批准可覆盖剩余缺口 | 推翻 | 人工不能改变逻辑、物理、法律或他者权利 | 只处理合法规范选择，其他情况拒绝 |
| 最大治理总是更安全 | 推翻 | 控制会耦合、失效、制造绕过和认知过载 | 治理复杂度预算、适用性裁剪和控制退役 |

### 3. 最高风险的剩余不可解区域

#### 3.1 完整语义理解

对任意图灵完备工程，系统不能普遍完全决定所有非平凡行为、全部动态依赖、全部影响和唯一正确修复。可行目标是对受限语言片段给出证明，对开放片段给出有方向的近似、运行证据和未知。

#### 3.2 全局优化

评价函数、候选空间和未来分布本身可能不完备或被系统行为改变。系统只能在明示模型中证明局部最优或界限；现实层使用非支配集合、鲁棒满意化、可逆实验和有权决定。

#### 3.3 多权威规范冲突

冲突的法律、权利、组织政策和用户目标可能不存在共同可接受解。系统应定位最小冲突、隔离可用子问题并拒绝越权自动化，而不是用固定优先级伪造共识。

#### 3.4 分布式完成与共同知识

网络分区、延迟和故障使“没有响应”无法等同“没有执行”。某些协调保证在声明故障模型下不可同时满足。系统必须降低保证、改变同步假设、缩小一致性范围或输出协调不可达。

#### 3.5 证明与物理现实

形式证明无法自动覆盖未建模硬件、固件、微架构通道、环境扰动和被污染工具链。最高强度保证仍是带假设和残余信任的保证包，而不是绝对正确。

#### 3.6 反身社会技术系统

指标、规则和预测会改变参与者行为，导致数据分布、激励和攻击面变化。一次静态最优政策不能被永久采纳；需要策略主体模型、审计、随机化、有效期和重开条件。

### 4. 多上下文辅助设计候选

```text
OpenWorldChallengeCompiler
        ↓
ModelPortfolio
+ AssertionSets
+ ResolutionProtocols
+ ObservationCuts
+ DependencyEvidence
        ↓
Decidability / Feasibility / Legitimacy / Risk Preflight
        ↓
PurposeBoundSystemDefinition | NonSolutionIR
        ↓
Bounded Candidate Search and Decision
        ↓
Target / Mutation / Verification Compilation
        ↓
Admission / Effect / Readback / Assurance
        ↓
Monitoring / Reopen / Migration / Retirement
```

这条流程只在多上下文辅助设计适用；明确程序直接进入现有编译链。上述预检执行已知规则，不是判断任意问题可判定性的通用算法。生效程序的确定解释与现实断言的多来源冲突是不同对象。

### 5. 不能自动化的正式边界

对相应请求输出具有真实阻断作用时，下列情况要求限制动作或返回缺口；不使无关编译、草稿保存与只读分析全部停机：

- 硬约束不可满足；
- 请求强制要求的性质未取得所需证据，且没有获准的有界或运行时替代保证；
- 观测等级不足以支持目标效果；
- 无合法主体可解决规范冲突；
- 关键依赖只有未知或未经验证假设；
- 不可逆效果缺少可接受恢复或遏制；
- 所需分布式协调与故障模型不相容；
- 控制器稳定性无法建立；
- 证明可信根无法闭合到可接受范围；
- 治理复杂度和错误表面超过它减少的风险；
- 目标函数无法代表受影响主体或被策略操纵；
- 跨语言保持合同不足以支持目标安全性质。

### 6. 最强竞争解释

最强竞争解释不是另一套更宏大的元模型，而是：**SEC 可能不值得作为通用平台建造。** 对小型、短生命周期、低风险、单语言和单主体项目，成熟编译器、测试、版本控制和受限 AI 工具可能以更低成本取得足够结果。

因此 SEC 的产品成立还需要现实证明：在复杂、长期、高风险、跨语言、存量工程和 Agent 自动变更场景中，它减少的缺陷、返工、恢复成本和未知风险大于自身引入的治理与认知成本。若长期不能证明，该系统应缩小为一组可独立采用的编译器和保证组件，而不是维护统一平台。

### 7. 采用验收

采用相应机制前，需要针对适用部分检验：

- 不可达状态在所有接口中保持类型；
- 多模型冲突不会被加载顺序或 owner 覆盖；
- 低等级依赖证据不能签发高等级缓存复用；
- 无关变化在局部性包络内保持结果；
- 包络破裂时系统能扩大影响而非假局部；
- 候选搜索保留界限和未探索前沿；
- 证明附假设和可信计算基；
- 反馈自动化可被稳定性准入拒绝；
- 架构拒绝不会阻断无关安全切片；
- 至少两个异构真实工程消费同一根协议；
- 与简单工具链相比存在可测净收益；
- 旧无条件根合同的权威消费者清零。

## 硬件物理边界、弱内存、亚稳态与侧信道

<a id="1-根裁决-9"></a>

### 1. 根裁决

软件架构不能把硬件抽象视为绝对真理。真实计算设备受：

- 有限能量、带宽、容量和散热；
- 时钟漂移和测量误差；
- 模拟电路亚稳态；
- 弱内存排序；
- 缓存和推测执行；
- DMA、固件和微码；
- 位翻转、磨损和介质故障；
- 制造差异和环境条件；
- 功耗、电磁、声学和时序侧信道；
- 供应链和物理攻击。

因此物理平台必须作为独立 Target/Host/Assumption profile，而不是一个版本字符串。

### 2. 亚稳态否定绝对同步

异步信号进入时钟域时，触发器可能进入亚稳态。工程可以把失败概率降得极低，但不能保证在任意固定有限时间内绝对完成解析。

这要求：

- 同步器 Claim 使用 MTBF/概率和工作条件；
- 安全关键控制不能依赖“亚稳态绝不发生”；
- 跨时钟域协议使用握手、FIFO 或冗余；
- 需要分析电压、温度、频率和器件 variation；
- 超过证明条件时输出 unsupported。

### 3. 弱内存和编译器重排

源代码顺序不等于其他线程的观察顺序。不同 CPU、语言和 compiler 具有不同 memory model。并发合同必须声明：

```text
atomicity
ordering
visibility
happens-before
fences
compiler transformations
data-race semantics
```

“在 x86 上测试通过”不能证明 ARM/RISC-V 或不同编译器正确。

### 4. 微架构打破抽象边界

推测执行和缓存侧信道证明：架构级权限检查可以正确，仍可能通过微架构状态泄漏信息。系统必须分开：

- architectural behavior；
- microarchitectural behavior；
- timing/resource channels；
- physical channels。

每个 security proof 说明覆盖哪些观察者和通道。

### 5. 物理故障和随机扰动

内存、存储、网络和传感器可能发生：

- silent data corruption；
- torn write；
- latent sector error；
- ECC 可纠/不可纠错误；
- bit rot；
- cosmic/environmental upset；
- sensor drift；
- power loss；
- thermal throttling；
- flash wear。

需要端到端 checksum、冗余、scrub、fault containment、readback 和恢复演练。复制同一错误不是冗余。

### 6. 固件、微码和设备是动态依赖

操作系统和应用证明可能依赖：

- BIOS/UEFI；
- CPU microcode；
- SSD firmware；
- NIC/GPU/device firmware；
- IOMMU/DMA configuration；
- boot chain；
- secure element；
- cloud hypervisor。

这些应进入 platform assurance closure；更新可使旧证据陈旧。

### 7. 物理身份和不可克隆属性

内容摘要不能代表物理器件。某些安全和校准依赖：

- serial/attestation identity；
- calibration state；
- location；
- ownership；
- wear/history；
- physical tamper state。

同型号或同固件不等于同一设备行为。

### 8. 能源和热约束

性能优化可能：

- 提高峰值功耗；
- 触发降频；
- 缩短电池寿命；
- 增加冷却和基础设施成本；
- 改变实时 jitter；
- 扩大侧信道。

资源模型必须允许 energy、thermal、wear 和 acoustic/emission 作为独立维度，而不是只看 CPU time。

### 9. 物理验证等级

```text
PhysicalEvidenceLevel =
  Simulation
  Emulation
  RepresentativeHardware
  ProductionEquivalentCell
  FieldObservation
  DestructiveStressTest
```

低层不能自动替代高层；高层也不能覆盖未测试极端。

### 10. 架构拒绝条件

若系统要求绝对固定时延、零随机故障、零侧信道、任意环境下相同数值结果或无需硬件假设的安全证明，SEC 必须输出物理不可达或要求收窄条件。

<a id="11-验收-1"></a>

### 11. 验收

- Host/Target profile 包含硬件、固件、微码和 memory model；
- 跨平台并发做真实物理测试；
- 侧信道 Claim 声明通道范围；
- 存储和内存验证 silent corruption；
- 设备更新使关联 Evidence 陈旧；
- 能源、热和磨损可成为资源/风险维度；
- 不使用“硬件按规范工作”作为隐藏无界假设。

## 颠覆性攻击矩阵与根合同迁移

### 1. 必须重写的根合同

本页审查的是**下列无条件主张**，不是要求推翻已带范围与证据的有效合同。没有相应旧接口或消费者时不执行迁移；普通已采纳模型编译不以联邦模型为前置。

| 需要撤销的无条件主张 | 反例与修订 | 应保留的有效子域 |
|---|---|---|
| 单一定义覆盖全部上下文 | 合法冲突时使用模型组合和目的绑定 | 单一封闭工程仍可有一个生效定义 |
| 一个组织 owner 使所有断言唯一为真 | 分离来源断言、规范采纳、决议与写权 | 精确对象和作用域内仍须确定活动写权 |
| 所有外部观察天然精确 | 记录观察切面、一致性、覆盖和未知 | 不可变树或受证事务快照可在范围内精确 |
| 任意程序依赖都能精确发现 | 依赖声明附方法与证据等级 | 有限受限域的精确或可靠过近似闭包仍合法 |
| 同一 ActionKey 必然可复用 | 另检缓存资格、权限、有效性和内容存在 | 键表达计算身份，不混入与结果无关的证明元数据 |
| 总能搜索全局最优 | 限定候选域、约束、代价与证据 | 已证明的有限域最优仍可称最优 |
| 证明闭合全部现实正确性 | 显式假设、可信根及模型到现实的证据 | 保留形式模型内的真实证明 |
| 组件通过便保证组合通过 | 检查接口、共同原因和环境兼容 | 满足组合定理前提时可复用证明 |
| 持续调和必然收敛 | 只对真实控制循环要求稳定性合同 | 无持续控制器的静态生成不需要此机制 |
| 挑战集覆盖开放世界 | 保留未探索前沿和复审触发 | 封闭枚举范围可给覆盖计数 |
| 自动化总优于人工 | 比较成本、权限与实际效果 | 已确定且可自动校验的任务不额外要求人工批准 |
| SubjectRef 证明现实同一性 | 区分内部引用与现实绑定、拆分和争议 | 系统内已定义对象的稳定引用继续有效 |

### 2. 迁移顺序

按实际受影响合同构造依赖 DAG，不固定 M0–M12 全链。先定位旧断言、现有读写消费者与不能保持的保证；再修订该合同、版本解释和具体失败结果；随后只增加所需观察/依赖/决议/稳定性机制；通过新旧可比较声明的反例测试后切换真实消费者。

双模型只在两者确实承载需比较的语义时启用；纯文档澄清或内部搬移不需要影子平台。退役只针对被替代且已结束支持的旧合同；精确快照、可靠闭包和有范围的唯一规范拥有者不是退役对象。

### 3. 兼容策略

旧字段不能被静默重新解释：

```text
exactObservation
exactInputClosure
systemDefinitionGeneration
canonicalOwner
optimalCandidate
verified
```

必须通过显式 adapter 映射，并在无法满足新语义时返回低等级或未知：

```text
exactObservation
→ AtomicSnapshot only if proof exists
→ otherwise BoundedSkew/ProviderReported/Unknown
```

```text
canonicalOwner
→ writer owner where applicable
→ scoped normative adoption for accepted definitions
→ resolution protocol only where a decision actually needs it
```

```text
optimalCandidate
→ OptimalWithinDeclaredFiniteModel
→ otherwise BestKnown/NonDominated
```

### 4. 首个纵向切片

选择一个真实 Source/Compiler Action：

1. 建立 `ObservationCut`；
2. 对该动作使用适用的静态、动态和负依赖证据，不要求每种方法都执行；
3. 编译 `InputDependencyClaim`；
4. 生成 ActionKey；
5. 在 `ProvenExact` 和 `SoundOverapproximation` 下验证局部性；
6. 仅有动态样本而未证明覆盖时，不签发安全缓存资格；方法补足可靠封闭条件后可按新证据重新判定；
7. 注入隐藏文件、环境变量、动态 import 和外部 Provider 变化；
8. 对照 clean 全量重算；
9. 输出旧 API 与新 API 差异；
10. 切换实际受影响的旧无等级闭包消费者，不删除有范围的精确闭包接口。

### 5. 第二纵向切片

选择一个有多权威和不可逆效果的场景：

- 用户授权；
- 组织 policy；
- 外部法域；
- 安全否决；
- Provider capability；
- 删除或发布效果。

证明 `AssertionSet → ResolutionProtocol → PurposeBoundDefinition → ArchitectureRefusal/AdmittedExecution` 全链。

### 6. 反向验证

每次迁移后攻击：

- 是否又出现一个隐藏全局 truth；
- 是否把冲突压成优先级；
- 是否把近似闭包命名成 exact；
- 是否把 best-known 命名成 optimal；
- 是否让 candidate 自签 AssumptionLedger；
- 是否让人工 override 消除物理未知；
- 是否让 refusal 阻断无关能力；
- 是否让复杂度对象本身成为新中央平台。

### 7. 完成条件

```text
RootContractMigrationComplete =
  new contracts implemented and independently verified
  and declared affected consumer scenarios adopted and checked
  and actually retired APIs have zero active consumers in their retirement scope
  and no compatibility adapter can issue stronger claims
  and archived Evidence remains historically interpretable
  and performance/governance cost remains within accepted budget
```

## 不可达、冲突、假设与拒绝中间表示

### 1. 目的

本 IR 用于需要设计/证明/准入诊断的分支，表达已证明不可行、当前未知或受限保证。它不把“没找到”写成“没有方案”，也不成为普通确定性编译的强制总返回层。

### 2. NonSolutionIR

```text
NonSolutionIR =
  | InfeasibleIR
  | UndecidableIR
  | ResourceBoundedUnknownIR
  | ObservationInsufficientIR
  | CoordinationUnattainableIR
  | AssuranceInsufficientIR
  | NormativeConflictIR
  | IrreversibilityUnacceptableIR
  | ArchitectureRefusalIR
```

### 3. InfeasibleIR

```text
InfeasibleIR = {
  constraintCore,
  proofClass,
  nonRelaxableConstraints,
  relaxableCandidates,
  stakeholderConsequences,
  reopenConditions
}
```

### 4. UndecidableIR

```text
UndecidableIR = {
  propertyClass,
  inputLanguage,
  knownBoundaryOrReduction,
  decidableSubfragments,
  approximationOptions,
  runtimeOrHumanAlternatives
}
```

### 5. ResourceBoundedUnknownIR

保存已探索区域、incumbent、上下界、resume token、搜索算法和未探索前沿。不能只返回 timeout。

### 6. NormativeConflictIR

保存冲突 authority、法域、权利、不可补偿约束、可选制度程序、安全默认和申诉路径。

### 7. ArchitectureRefusalIR

```text
ArchitectureRefusalIR = {
  refusalReasons,
  unsafeOrUncontrolledEffects,
  failedAssumptions,
  unavailableRecovery,
  governanceComplexity,
  safeUsableSubsets,
  partitionOrSimplificationOptions,
  minimumReopenConditions
}
```

### 8. AssumptionIR

```text
AssumptionIR = {
  proposition,
  source,
  rationale,
  scope,
  validationEvidence,
  confidenceOrProofClass,
  dependents,
  expiry,
  falsifier,
  residualRisk
}
```

假设不能隐藏在自然语言脚注或代码注释中。

### 9. 阶段传播

NonSolutionIR 可以在意图、观测、模型组合、求解、实现解析、验证和执行准入任一阶段产生。下游只能：

- 保留；
- 缩小到无关子切片；
- 通过新事实或合法决议重新打开；

不能把它转换为低置信成功。

### 10. 接口投影

CLI、API、IDE 和 Agent 都必须保留稳定 reason code、主体、证据、可用子集和下一合法动作。人类摘要不能删除不可达证明。

<a id="11-验收-2"></a>

### 11. 验收（不可达、冲突、假设与拒绝中间表示）

- 所有 NonSolution variant 可序列化、往返和版本化；
- 任意阶段都可产生；
- 不会被 catch-all error 覆盖；
- 可以局部阻断而保留无关功能；
- 新信息触发精确重开；
- ArchitectureRefusal 不能被普通 override 消除。

### 12. 类别边界与实例结果分开

`UndecidableIR` 保留的是问题类别的已知理论边界，属于分析元数据，不是某个实例不可编译、不可满足或不能证明的证书。具体实例另记 proved/refuted/unknown 及证据。旧 NonSolution 列表中的该项只作为兼容诊断入口，不得据此把合法输出转为失败；未来线格式若拆出独立字段，必须显式版本迁移。

同理，ObservationInsufficient、ResourceBoundedUnknown 和 AssuranceInsufficient 是当前证据/预算不足；Infeasible 才需要相应模型内无解证据。阻断范围由输出依赖和保证决定，不因一个研究诊断使整项工程停摆。
