# 编译器核心实现规格

> 目标：定义编译器本体的实现栈、schema、文件所有权、幂等要求和基础设施层。实现字段以本文和 `06-10` 为准；产品/架构口径以 `02` 为准。

## 0. 编译器实现栈

- TypeScript + Node.js + ESM + CLI-first + 文件系统驱动。
- Bun 是可选本地执行/测试加速路径，非主规范运行时。核心编译器不得依赖 `Bun.*` 全局 API。
- 规范源以 `tsc --noEmit` 检查结果为准。
- 当前实现必须面向最终形态：核心编译器可以先处理文件装载型 block，但抽象边界必须保留到语义合约型 block、Engineering IR、generator strategy、Review Workbench，不允许把具体业务 block 写成平台 hardcode。

## 1. 标准工件与文件所有权

| Zone | 路径 | 规则 |
| --- | --- | --- |
| Spec Zone | `source/app.yaml`、`block.manifest.yaml`、policy/acceptance/override spec | AI 默认只读 |
| Developer Source | `source/code/**`、`source/model/**`、`source/views/**`、`source/patches/**` | 开发者主工作面 |
| Slot Zone | `source/code/slots/**`（源码）→ `project/custom/**`（runtime 物化） | AI 只写 sourcePath |
| Generated Target | `project/**`（应用源码、测试、generated） | 编译器写入，人工修改 = override |
| Control Plane | `control/state/**`、`control/evidence/**`、`control/provenance/**`、`control/graph/**`、`control/workflow/**`、`control/ci/**` | 只能由对应 pass 或治理 workflow 写入 |
| Local State | `.pjc/**` | 可删除可重建 |

Workbench/IDE 变更 `source/app.yaml` 必须先写 `source/views/mutations/*.json`，通过 `platform workbench mutations apply` 回写。

最终形态下，`source/model/**` 与 `source/views/**` 承载语义合约的开发事实源，`project/**` 只承载降级后的运行产物。任何 pass 若需要理解业务实体、操作、策略或视图，应读取语义合约或 Engineering IR，不得反向解析生成文件作为主要事实源。

## 2. `source/app.yaml` 正式 schema

| 路径 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `app.name` | string | 是 | kebab/snake_case，1-64 字符 |
| `app.stack` | string | 是 | 必须命中 `nextjs-ts-prisma-sqlite` |
| `app.packageManager` | enum | 否（默认 pnpm） | pnpm / npm / yarn |
| `app.mode` | enum | 否（默认 single-tenant） | single-tenant / multi-tenant |
| `registry.sources[].id` | string | 否 | plan 内唯一 |
| `registry.sources[].kind` | enum | 否 | official / private / community |
| `registry.sources[].location` | enum | 否 | compiler / workspace |
| `registry.sources[].path` | string | 否 | 相对 `location` 根目录；禁止绝对路径、盘符、UNC、NUL 与 `..` 穿越 |
| `blocks[].id` | string | 是 | 必须命中 registry block id |
| `blocks[].version` | string | 否 | semver |
| `slots[].id` | string | 是 | plan 内唯一 |
| `slots[].block` | string | 是 | 必须引用已声明 block |
| `slots[].kind` | enum | 是 | adapter / policy / ux / repair |
| `slots[].target` | string | 是 | 必须落在允许写入 zone |
| `slots[].sourcePath` | string | 否 | 必须位于 `source/code/slots/` |
| `slots[].symbol` | string | 是 | 必须匹配目标 slot 合同 |
| `acceptance[].id` | string | 是 | 必须命中已注册 acceptance id |

校验规则：blocks/slots/registry.sources 的 id 不允许重复；`slots[].block` 必须引用已申明的 block；`app.stack` 必须与所有块的 `stackProfiles` 兼容。

## 3. `block.manifest.yaml` 正式 schema

当前 schema 支持文件装载型 block；最终形态必须兼容语义合约型 block。新增实现字段应优先表达工程语义，再由 generator/pass 降级为文件，不得新增面向单个业务 block 的专用 schema 或专用安装器。

| 字段 | 必填 | 类型/约束 |
| --- | --- | --- |
| `id` | 是 | 唯一 block id |
| `version` | 是 | semver |
| `kind` | 是 | capability / strategy / infra / governance |
| `stackProfiles` | 是 | 至少 1 个，当前 `["nextjs-ts-prisma-sqlite"]` |
| `requires` | 否 | capability id 列表 |
| `provides` | 否 | capability id 列表 |
| `conflicts` | 否 | block/capability id 列表 |
| `installs` | 是 | 安装动作（`kind: copy|merge-prisma` + `from` + `to`） |
| `pins.inputs` / `pins.outputs` | 否 | `id` + `type` + `required?` |
| `slots` | 否 | `id` + `kind` + `target` + `symbol` + `inputType?` + `outputType?` + `writableZones` |
| `acceptance` | 否 | acceptance id 列表（可含 `dependsOn` + `covers`） |
| `routes` | 否 | `path` + `file` |
| `contracts` | 否 | 预留语义合约入口，承载 entities / operations / policies / views / events / permissions 等；字段落地规则以 `11` 和 `06` 为准 |
| `generators` | 否 | 预留生成器声明，按工程动作生成 service/API/DB/view/test 等产物；不得按业务 block 名称分派 |
| `upgrade` | 否 | `from: []` + `migrations: []` |

不变量：`provides` 与 `conflicts` 不允许交叉；`slots[].target` 必须落在 `writableZones` 内；`installs[].to` 不允许写入其他块或 `control/**`。

## 4. `graph.lock.json` 正式 schema

必填字段：`formatVersion`、`app`、`resolvedBlocks`、`installPlan`、`slotTasks`、`acceptancePlan`、`passStatus`。

校验规则：`resolvedBlocks[].installOrder` 严格递增唯一；`installPlan[].stepId` 唯一；`slotTasks[].id` 与 `source/app.yaml` 对齐；任一 pass `failed` 后后续 pass 不得 `succeeded`。

`slotTasks[]` 字段：`id`、`block`、`target`（必填）；`status`（pending/generated/filled/verified/failed）；`writableZones[]`（必填）；`sourcePath?`；`provenanceHints?`。

后续 Engineering IR 可以作为 `graph.lock.json` 的衍生产物或扩展区进入 control plane。IR 必须记录 block、capability、pin、slot、entity、operation、policy、view、file artifact 与 acceptance 的关系；文件路径只能是 IR 的降级结果，不能成为唯一语义来源。

## 5. Resolver 与 Composer 实现规则

Resolver（`platform/compiler/resolve/resolve-graph.ts`）：
1. 载入显式声明块 → 2. 校验唯一性 → 3. 校验 stack 兼容 → 4. 汇总 requires/provides/conflicts → 5. 补齐隐式依赖 → 6. 检测冲突 → 7. 检测环 → 8. 拓扑排序（infra > governance > capability > strategy）→ 9. 生成 slot task → 10. 输出 lock。

Composer（`platform/compiler/compose/compose-project.ts`）：
- 使用 `InstallStrategyRegistry` 执行安装（`CopyInstallStrategy`、`MergePrismaInstallStrategy`）
- 并行渲染路由图、并行写入 slot 骨架
- 支持 `Promise.all` 批量 I/O
- 新增 install/generator 能力必须按工程动作扩展，例如 `generate-entity-service`、`generate-api-route`、`generate-prisma-model`、`generate-view`、`generate-acceptance-test`；禁止新增 `CustomerInstallStrategy`、`TicketInstallStrategy` 这类按业务 block 分派的 hardcode。

详见代码实现，本文档不重复算法细节。

## 6. 幂等与重入

- 连续运行 `resolve` 两次，lock 必须一致。
- 连续运行 `compose` 两次，安装结果一致不得重复附加。
- `adapt` 在 slot 未变化时不得生成不同输出。
- 失败后重跑基于当前 lock 判定跳过；未成功 pass 不得伪造成功状态。

## 7. Issue 分层

| Issue 类型 | 判定依据 | 默认处理 |
| --- | --- | --- |
| Spec Issue | plan/slot/acceptance/policy 错误 | 人工决策 |
| Composition Issue | 依赖/冲突/安装路径/版本错误 | align/resolve/compose 层报错 |
| Slot Issue | slot 实现不满足类型/符号/测试 | 进入 synthesize/repair 最小任务闭包 |
| Kernel Issue | perf/correctness 失败 | 返回维护者 |

详见 `07` §4。

## 9. 代码压缩原则

> 适用于 `platform/` 下所有源码（`upgrade-workspace.ts` 除外）。新增代码必须遵守，存量代码在重构时逐步对齐。

### 9.1 数据驱动 > 过程式

- 条件分支超过 3 个且每分支只返回同结构对象时，必须提取为规则表 + `find` 匹配。
- 规则表是单一事实源：新增分支只需加一行配置，不修改匹配逻辑。
- 已应用：`error-protocol.ts`（`ERROR_PROTOCOL_RULES`）、`write-provenance.ts`（`PASS_RULES`）、`reference-check.ts`（`REFERENCE_DRIFT_CODES`）。

### 9.2 通用函数 > 复制粘贴

- 同一文件内出现 2 次以上相同结构的代码块时，必须提取通用函数。
- 通用函数通过配置对象参数化差异，避免过度抽象。
- 已应用：`generate-runtime-host.ts`（`renderEntityApiRoute`）、`format-utils.ts`（`optionalFields`）。

### 9.3 辅助函数消除样板

- `...(condition ? [x] : [])` 模式超过 3 处时，必须使用 `optionalFields` 替代。
- `formatFields` 调用中重复前缀字段超过 2 处时，必须提取共享前缀 + 条件追加。
- 已应用：`formatters.ts`（`formatUpgradeMigrationDetails`、`formatReviewDiagnostic`）。

### 9.4 计算与 IO 分离

- 每个 `write*` 函数必须有对应的 `build*` 纯计算函数。
- `write*` 只做锁获取 → 调用 `build*` → 写文件 → 返回。
- 已应用：`write-review-summary.ts`（`buildReviewSummary` / `writeReviewSummary`）、`write-provenance.ts`（`buildProvenance` / `writeProvenance`）、`write-explain-graph.ts`（`buildExplainGraph` / `writeExplainGraph`）。

### 9.5 复用成熟库 > 自造轮子

- CLI 参数解析：Commander.js（替代自定义 CommandRegistry）。
- 模板渲染：EJS（用于 `write-local-views.ts`）。
- 通用工具：lodash-es（`groupBy`、`uniqBy`）。
- 新增依赖前必须确认项目已引入；未引入时优先评估是否可用已有工具实现。

### 9.6 避免无用抽象

- 差异超过 40% 的代码块不强求通用化（如 customers/tickets 页面的 audit/notification section）。
- 通用函数的参数不超过 15 个；超过时考虑拆分为多个更聚焦的函数。
- 规则表条目不超过 12 条；超过时考虑分层或按域拆分。

### 9.7 工具链保障与 evidence 边界

- **重复检测（L1 文本级）**：`bun run jscpd`，报告见 `report/jscpd/html/index.html`。
- **架构规则**：`bun run depcruise`（依赖方向 + 循环依赖），配置见 `.dependency-cruiser.json`。
- **结构级重复检测（L2）**：`bun run discover`，报告见 `report/discover.json`。
- **一键检查**：`bun run arch:check` = depcruise + jscpd。
- **AI 事前审查**：`bun run preflight` = depcruise + jscpd + discover（三工具一脚本全跑）；raw 输出先保留在 `report/**`，需要进入治理面时由 `tool-evidence-adapters.ts` 归一为 `stableArtifact: false` 的 draft evidence。
- **IDE/MCP 探索**：Graph-It-Live 可用于 VSCode file/symbol/call graph 和 AI 上下文查询，但只作为可选 evidence provider/adapter。
- **L3 语义级重复**：jscpd 和当前 discover 无法完整覆盖，`semantic-pattern-report.ts` 只把 evidence 归一为低置信 review suggestion，例如 read → validate → build → write、query → guard → map → return；不得自动重构。

所有工具输出只能作为 review evidence，不得替代 `source/**`、manifest、graph lock、provenance、review summary 或 contract freeze。若未来新增 `code-quality-report`、`architecture-boundary-report`、`semantic-pattern-report` 或 graph overlay，必须先在 `08` 定义产物稳定性，再在 CLI/contract freeze 中声明消费方式。工具链详细配置与能力边界见 [代码库可视化流程图工具与编译原理综合指南](代码库可视化流程图工具与编译原理综合指南.md) §1.10。

### 9.8 高速开发质量闭环

高速开发默认按“短切口、强边界、快验证、及时提交”执行：

1. 先确认切口所属边界：compiler、registry、generated project、governance、Workbench、quality evidence、runtime verification 不能混写。
2. 每个切口只新增一个稳定能力或一个受控预留 contract；不把无关重构混入功能提交。
3. 修改前查通用函数索引、现有 formatter/builder/registry/workflow，避免重复 helper 和第二事实源。
4. 实现时保持计算/IO 分离：新增 `write*` 必须有 `build*`，CLI 输出必须复用 formatter/compact contract。
5. 本地默认运行 `bun run check:affected` 或明确的定向测试；`check:affected` 会基于 git 变更优先运行已修改或受影响的 fast test，默认不做 broad fast-suite fallback，并排除登记在 test budget 中会触发 Next build/Playwright 的慢测试。
6. 触及 CLI/API/JSON artifact/contract/Workbench/registry/runtime 或需要验证完整生成项目时，升级到 contract freeze、reference check 或 `bun run check:full`；`check:full` 是显式慢门禁，允许触发 `verify --lane all`、Next build 和 Playwright。
7. 每轮修改后提交一个 Conventional Commit；提交前只 staging 本切口相关文件，不混入外部未授权变更。
8. 若连续两轮修复无效，停止扩张，记录失败命令、错误摘要、已改文件、怀疑根因和下一步复现。

这套闭环不能保证代码天然高质量，但会把低质量路径显性化：重复由 L1/L2/L3 evidence 暴露，架构漂移由 dependency/contract gate 暴露，生成与人工改动由 provenance/review graph 暴露，图上操作由 mutation/dry-run/verify 收束。
