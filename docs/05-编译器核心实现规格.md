# 编译器核心实现规格

> 目标：把工程编译器从“架构蓝图”推进到“实现级规格”。本稿定义输入输出、schema、求解规则、装配规则、文件所有权、幂等要求与 CLI 合同。

## 0. 编译器本体实现栈

- `v0.1` 已定：
  - `TypeScript`
  - `Node.js`
  - `ESM`
  - CLI-first 工具形态
  - 文件系统驱动
- 原则：
  - 编译器首先是构建工具，不是 Web 应用壳。
  - `Next.js` 负责被编译出来的目标项目，不负责解析、装配、锁定和本地/CI 执行。
  - 后续可以增加基于 Web 的工作台，但不会替代 CLI 作为底层执行面。
  - 当前仓库中的 `.js` 原型实现不构成长期规范；后续实现应收敛到 `.ts`。

## 0.1 Bun 环境策略

- `v0.1` 主运行时：`Node.js`
- `v0.1` 源码层：`TypeScript`
- `Bun` 在 `v0.1` 的定位：
  - 可选本地运行环境
  - 可选测试加速环境
  - 非默认 CI 规范环境

### 采用 Bun 的优点

- 官方文档明确支持开箱即用运行 `.ts/.tsx`，并内建测试运行器。
- 启动快，适合作为本地工具开发体验优化。

### 不直接把 Bun 设为主基线的原因

- 编译器需要稳定的文件系统、CLI、生态和 CI 规范面。
- 当前目标应用栈和更广的 Node 生态仍以 `Node.js` 为主规范。
- 若过早依赖 Bun 专有行为，会提高后续 Node 兼容和 CI 基线维护成本。

### 强约束

- 核心编译器模块不得直接依赖 `Bun` 全局。
- 测试与运行脚本若提供 Bun 入口，必须保留等价 Node 入口。
- `tsc --noEmit` 或等价类型检查结果应作为源码正确性的规范基线。

## 1. 作用域

- 当前约束覆盖 `v0.1 -> v1`。
- `v0.1` 必须完整实现的对象：
  - `app.plan.yaml`
  - `block.manifest.yaml`
  - `graph.lock.json`
  - `platform init / add / resolve / compose / adapt / verify / lock`
- `v0.2+` 预留但不要求首版实现：
  - `provenance.json`
  - `platform explain`
  - `platform repair`
  - `platform upgrade`

## 2. 标准工件

### 工件原则

- 工程规格、块接口、连接关系、slot、acceptance、policy 和 provenance 是权威工程对象。
- 源码必须真实落地，作为可审查、可部署、可测试、可调试的下游工件。
- UI 视图、slot 视图和 graph 视图不得替代源码产物；它们只能解释、导航和约束源码产物。
- 人工修改源码必须进入 override / provenance / 回写策略，不能静默成为新的权威源。

### 上游输入工件

- `app.plan.yaml`
- `block.manifest.yaml`
- `policy spec`
- `acceptance spec`
- `override spec`

### 中间工件

- `graph.lock.json`
- `install-manifest.json`
- `slot-task.json`
- `verification-report.json`

### 下游工件

- 生成源码
- 测试
- lock files
- provenance
- explain graph

## 3. `app.plan.yaml` 正式 schema

### 顶层结构

```yaml
app:
  name: customer-admin
  stack: nextjs-ts-prisma-sqlite
  packageManager: pnpm
  mode: single-tenant

registry:
  sources:
    - id: official
      kind: official
      location: compiler
      path: platform/registry/official
    - id: private
      kind: private
      location: workspace
      path: platform/registry/private

blocks:
  - id: auth/basic-session
    version: 0.1.0
  - id: tenant/basic-workspace
    version: 0.1.0
  - id: entity/customer-basic
    version: 0.1.0

slots:
  - id: customer_normalizer
    block: entity/customer-basic
    kind: adapter
    target: custom/customer_normalizer.ts
    symbol: normalizeCustomerInput
    description: |
      customer name 必填；
      email 转小写；
      phone 去掉空格和横线；
      company 为空时填 Unknown。

acceptance:
  - id: user_can_login
  - id: user_can_create_customer
  - id: user_can_list_customers
  - id: tenant_only_sees_own_customers
```

### `v0.2+` 扩展预留

```yaml
kernels:
  - id: search-ranking-kernel
    interface: kernels/search-ranking/interface.yaml
    owner: expert-maintained
    perfBudget: p95_under_50ms
    benchmark: tests/bench/search-ranking.bench.ts
    correctness: tests/kernel/search-ranking.spec.ts
```

- `kernels` 用于高性能、底层或专家维护模块的外壳接入，不在 `v0.1` 实现。
- kernel 只暴露接口、性能预算、正确性测试和适配 slot；编译器不得生成或重写 kernel 内部热路径。

### 字段表

| 路径 | 类型 | 必填 | 默认值 | 约束 |
| --- | --- | --- | --- | --- |
| `app.name` | string | 是 | 无 | `kebab-case` 或 `snake_case`，1-64 字符 |
| `app.stack` | string | 是 | 无 | 必须命中受支持 stack profile |
| `app.packageManager` | enum | 否 | `pnpm` | `pnpm` / `npm` / `yarn` |
| `app.mode` | enum | 否 | `single-tenant` | `single-tenant` / `multi-tenant` |
| `registry.sources[].id` | string | 否 | `official` / `private` | 同一 plan 内唯一 |
| `registry.sources[].kind` | enum | 否 | 见默认值 | `official` / `private` / `community` |
| `registry.sources[].location` | enum | 否 | 见默认值 | `compiler` / `workspace` |
| `registry.sources[].path` | string | 否 | 见默认值 | 相对 `location` 根目录，禁止 `..` 穿越 |
| `blocks[].id` | string | 是 | 无 | 必须命中 registry block id |
| `blocks[].version` | string | 否 | latest compatible | 必须是 semver |
| `slots[].id` | string | 是 | 无 | 同一 plan 内唯一 |
| `slots[].block` | string | 是 | 无 | 必须引用已声明 block |
| `slots[].kind` | enum | 是 | 无 | `adapter` / `policy` / `ux` / `repair` |
| `slots[].target` | string | 是 | 无 | 必须落在允许写入 zone |
| `slots[].symbol` | string | 是 | 无 | 必须匹配目标 slot 合同 |
| `slots[].description` | string | 是 | 无 | 最短 1 字符 |
| `acceptance[].id` | string | 是 | 无 | 必须命中已注册 acceptance id |

### 校验规则

- `blocks[].id` 不允许重复。
- `registry.sources[].id` 不允许重复。
- `registry.sources[].path` 不允许穿越出各自基准根目录。
- `location=compiler` 当前只允许 `kind=official`。
- `slots[].id` 不允许重复。
- `slots[].target` 在 `v0.1` 必须位于 `custom/`。
- `slots[].block` 必须引用已经列在 `blocks` 中的块。
- `app.stack` 必须与所有块 manifest 的 `stackProfiles` 兼容。

## 4. `block.manifest.yaml` 正式 schema

### 顶层结构

```yaml
id: entity/customer-basic
version: 0.1.0
kind: capability
stackProfiles:
  - nextjs-ts-prisma-sqlite

requires:
  - auth/session
  - tenant/context

provides:
  - customer/read
  - customer/write

conflicts: []

installs:
  - kind: copy
    from: files/src/app/customers
    to: src/app/customers
  - kind: merge-prisma
    from: files/prisma/customer.prisma
    to: prisma/schema.prisma
  - kind: copy
    from: files/tests/customer-basic.spec.ts
    to: tests/customer-basic.spec.ts

pins:
  inputs:
    - id: tenant_context
      type: TenantContext
      required: true
    - id: actor_identity
      type: ActorIdentity
      required: true
  outputs:
    - id: customer_created
      type: CustomerCreatedEvent

slots:
  - id: customer_normalizer
    kind: adapter
    target: custom/customer_normalizer.ts
    symbol: normalizeCustomerInput
    inputType: CustomerInput
    outputType: NormalizedCustomerInput
    writableZones:
      - custom/

acceptance:
  - id: user_can_create_customer
  - id: user_can_list_customers
```

### 字段表

| 路径 | 类型 | 必填 | 默认值 | 约束 |
| --- | --- | --- | --- | --- |
| `id` | string | 是 | 无 | 唯一 block id |
| `version` | semver | 是 | 无 | semver |
| `kind` | enum | 是 | 无 | `capability` / `strategy` / `infra` / `governance` |
| `stackProfiles[]` | string[] | 是 | 无 | 至少 1 个 |
| `requires[]` | string[] | 否 | `[]` | capability id 或 pin id |
| `provides[]` | string[] | 否 | `[]` | capability id 或 pin id |
| `conflicts[]` | string[] | 否 | `[]` | block id 或 capability id |
| `installs[]` | object[] | 是 | 无 | 至少 1 个安装动作 |
| `pins.inputs[]` | object[] | 否 | `[]` | id 唯一 |
| `pins.outputs[]` | object[] | 否 | `[]` | id 唯一 |
| `slots[]` | object[] | 否 | `[]` | slot id 唯一 |
| `acceptance[]` | object[] | 否 | `[]` | 引用合法 acceptance |

### manifest 不变量

- `provides` 与 `conflicts` 不允许交叉。
- `slots[].target` 必须落在该 slot 允许的 `writableZones` 之内。
- `installs[].to` 不允许写入其他块的 manifest 或 lock 文件。
- `kind=governance` 的块不得声明业务实体输出。

## 5. `graph.lock.json` 正式 schema

### 顶层结构

```json
{
  "formatVersion": "1",
  "app": {
    "name": "customer-admin",
    "stack": "nextjs-ts-prisma-sqlite",
    "mode": "single-tenant"
  },
  "resolvedBlocks": [],
  "resolvedCapabilities": [],
  "installPlan": [],
  "slotTasks": [],
  "generatedPaths": [],
  "acceptancePlan": [],
  "passStatus": {
    "parse": "succeeded",
    "align": "succeeded",
    "resolve": "succeeded",
    "compose": "pending",
    "adapt": "pending",
    "verify": "pending",
    "repair": "skipped",
    "lock": "pending",
    "emit": "pending"
  }
}
```

### 必填字段

- `formatVersion`
- `app`
- `resolvedBlocks`
- `installPlan`
- `slotTasks`
- `acceptancePlan`
- `passStatus`

### 校验规则

- `resolvedBlocks[].installOrder` 必须严格递增且唯一。
- `installPlan[].stepId` 必须唯一。
- `slotTasks[].id` 必须与 `app.plan.yaml` 中的 slots 对齐。
- 任一 pass 一旦标记 `failed`，后续 pass 不得标记为 `succeeded`。

### `slotTasks[]` 最低字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | slot id |
| `block` | 是 | 来源 block |
| `target` | 是 | 目标文件 |
| `status` | 是 | `pending` / `generated` / `filled` / `verified` / `failed` |
| `writableZones[]` | 是 | 允许写入的 zone |
| `provenanceHints` | 否 | 为 `v0.2+` 预留来源提示 |

### `v0.1` 支持的唯一 stack profile

- `nextjs-ts-prisma-sqlite`

### profile 定义

| 组件 | 固定值 |
| --- | --- |
| Web framework | Next.js App Router |
| Language | TypeScript |
| UI | React + Tailwind |
| ORM | Prisma |
| DB | SQLite |

## 7. Resolver 实现规则

### 输入

- 解析后的 `app.plan.yaml`
- 所有相关 block manifests

### 输出

- `graph.lock.json`
- in-memory capability graph

### 算法顺序

1. 载入所有显式声明块
2. 校验 block id 唯一性
3. 校验 stack 兼容性
4. 汇总 `requires / provides / conflicts`
5. 补齐隐式依赖块
6. 检测冲突
7. 检测依赖环
8. 计算确定性安装顺序
9. 生成 slot task 初稿
10. 输出 lock

### 安装顺序规则

排序优先级从高到低：

1. `kind` 优先级
   - `infra`
   - `governance`
   - `capability`
   - `strategy`
2. 被依赖深度小的先安装
3. manifest 中显式 `installOrderHint`
4. block id 字典序

### 冲突优先级

若出现冲突，按以下优先级报错，不自动选择胜出方：

1. stack 不兼容
2. 明确 `conflicts`
3. 同一 capability 被多个不兼容块提供
4. 同一路径安装目标冲突

## 8. Composer 实现规则

### 输入

- `graph.lock.json`
- registry block assets

### 输出

- 安装后的项目结构
- `generated/` 工件
- slot 骨架文件
- `install-manifest.json`

### 允许的安装动作

- `copy`
- `render-template`
- `merge-json`
- `merge-prisma`
- `append-lines`
- `register-route`
- `register-nav`
- `scaffold-slot`

### 路径所有权

| Zone | 所有者 | `v0.1` 是否可人工编辑 | `v0.1` 是否可 AI 编辑 |
| --- | --- | --- | --- |
| `generated/` | compiler | 否 | 否 |
| `custom/` | slot runtime | 是 | 是 |
| `overrides/` | human / later AI | 是 | 否 |
| `src/installed/*` | registry blocks | 应避免 | 否 |
| `tests/` | compiler + block | 允许人工补充 | 否 |

### `overrides/` 默认结构

```text
overrides/
  override-manifest.yaml
  patches/
  rules/
  manifests/
```

- `override-manifest.yaml` 负责把 `overrides/*` 下的文件显式映射到项目目标路径。
- override 当前支持 `compose` 和 `adapt` 两个接入时点。
- override 不得直接覆盖 `graph.lock.json`、`provenance.json`、`generated/*` 或 `overrides/*`。

### 合并策略

- JSON
  - 对象递归 merge
  - 数组去重后稳定追加
  - 原有键冲突时报错，除非 manifest 指定 `replace=true`
- Prisma
  - 只允许 model、enum、datasource、generator 四类块级 merge
  - 同名 model 冲突直接报错
- 路由注册
  - 统一写入 `generated/routes.ts`
  - 不直接改手写路由文件

### slot 骨架规则

- `v0.1` 必须生成：

```ts
export function normalizeCustomerInput(input: CustomerInput): NormalizedCustomerInput {
  throw new Error("Not implemented")
}
```

- 骨架文件需包含机器头注释，标记 slot id、block id、symbol 和 writable zone。

## 9. CLI 合同

### `platform init`

- 初始化项目骨架
- 创建默认 `app.plan.yaml`
- 不调用 AI

### `platform add`

- 只修改 `app.plan.yaml`
- 不执行 resolver 或 composer
- 必须校验 block id 格式合法

### `platform resolve`

- 若 schema 校验失败，返回非零退出码
- 不修改 `src/` 与 `custom/`
- 只生成或更新 `graph.lock.json`

### `platform compose`

- 必须先要求 `graph.lock.json` 处于 `resolve=succeeded`
- 若目标路径被非允许 zone 占用，返回冲突错误

### `platform adapt`

- 必须先要求 `compose=succeeded`
- 只消费 `slotTasks.status=pending`
- 写入成功后将对应 task 标为 `filled`

### `platform verify`

- 必须先要求所有必填 slot 为 `filled`
- 输出 `verification-report.json`

### `platform lock`

- 只有 `verify=succeeded` 时可执行
- 固化最终 pass 状态与版本

## 10. 幂等与重入

### 幂等要求

- 连续运行 `resolve` 两次，输出 lock 必须一致。
- 连续运行 `compose` 两次，安装结果必须一致，不得重复附加依赖。
- 连续运行 `adapt`，在 slot 未变化时不得重复生成不同输出。

### 重入要求

- 失败后重跑时，必须基于当前 lock 和 install manifest 判定哪些步骤需要跳过。
- 未成功完成的 pass 不得伪造成功状态。

## 12. `v0.1` Done 条件

- CLI 可以从空目录产出可运行项目。
- 三个块全部通过 resolver 和 composer 安装。
- 单一 slot 只能写 `custom/customer_normalizer.ts`。
- 主验收链路通过。
- 输出 lock 和 verification report。

## 13. Issue 分层与默认定位

| Issue 类型 | 判定依据 | 默认处理 |
| --- | --- | --- |
| Spec Issue | `app.plan.yaml`、slot description、acceptance 或 policy 表达错误/缺失 | 返回人工决策，不让 AI 擅自改规格 |
| Composition Issue | block 依赖、pin 连接、安装路径、版本或冲突错误 | 在 align/resolve/compose 层报错 |
| Slot Issue | 已声明 slot 的实现不满足类型、符号或测试 | 进入 synthesize/repair 的最小任务闭包 |
| Kernel Issue | 性能关键或专家维护内核的接口、benchmark 或 correctness 失败 | 返回 kernel 维护者或专门 harness，不自动重写内核 |

- Resolver、Composer、Verifier 和 Repair 必须尽量把失败归类到上述层级。
- 只有 Slot Issue 默认允许 AI 写入；其他 issue 需要显式任务信封或人工决策。
