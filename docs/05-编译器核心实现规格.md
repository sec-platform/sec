# 编译器核心实现规格

> 目标：定义编译器本体的实现栈、schema、文件所有权、幂等要求和基础设施层。实现字段以本文和 `06-10` 为准；产品/架构口径以 `02` 为准。

## 0. 编译器实现栈

- TypeScript + Node.js + ESM + CLI-first + 文件系统驱动。
- Bun 是可选本地执行/测试加速路径，非主规范运行时。核心编译器不得依赖 `Bun.*` 全局 API。
- 规范源以 `tsc --noEmit` 检查结果为准。
- 当前实现必须面向最终形态：核心编译器可以先处理文件装载型 block，但抽象边界必须保留到语义合约型 block、Engineering IR、generator strategy、Review Workbench，不允许把具体业务 block 写成平台 hardcode。

## 1. 标准工件与文件所有权

| Zone | 路径 | 规则 |
| --- | --- | --- |
| Spec Zone | `source/app.yaml`、`block.manifest.yaml`、policy/acceptance/override spec | AI 默认只读 |
| Developer Source | `source/code/**`、`source/code/opaque/**`、`source/model/**`、`source/views/**`、`source/patches/**` | 开发者主工作面 |
| Slot Zone | `source/code/slots/**`（源码）→ `project/custom/**`（runtime 物化） | AI 只写 sourcePath |
| Generated Target | `project/**`（应用源码、测试、generated） | 编译器写入，人工修改 = override |
| Control Plane | `control/state/**`、`control/evidence/**`、`control/provenance/**`、`control/graph/**`、`control/workflow/**`、`control/ci/**` | 只能由对应 pass 或治理 workflow 写入 |
| Local State | `.sec/**` | 可删除可重建 |

Workbench/IDE 变更 `source/app.yaml` 必须先写 `source/views/mutations/*.json`，通过 `platform workbench mutations apply` 回写。

最终形态下，`source/model/**` 与 `source/views/**` 承载语义合约的开发事实源，`project/**` 只承载降级后的运行产物。任何 pass 若需要理解业务实体、操作、策略或视图，应读取语义合约或 Engineering IR，不得反向解析生成文件作为主要事实源。

### 1.1 开放实现与 Opaque Module 边界

`source/code/opaque/**` 用于承载平台暂不理解内部实现的开发者代码。它不是第二事实源，也不是 registry block；编译器只能读取边界合同，不得把内部源码反向推断为架构事实。

每个 opaque module 至少应有 `module.yaml` 描述：

| 字段 | 说明 |
| --- | --- |
| `id` | workspace 内唯一模块 id |
| `entry` | 入口文件 |
| `exports` | 对外暴露符号或 endpoint |
| `inputs` / `outputs` | 输入输出类型、事件或命令 |
| `effects` | 数据库、文件、网络、外部服务等副作用 |
| `permissions` | 运行所需权限和 policy 约束 |
| `acceptance` | 证明该模块可用的验收项 |
| `provenanceHints` | 来源、人工 owner、生成器或迁移线索 |

AI 默认不得修改 opaque module 内部；只有 task envelope 明确授权具体路径、符号和验收时，才能按 `09` 的写入控制执行。opaque module 稳定后，应按 `06` 迁移为 private block 或语义合约，而不是长期停留为不可治理黑盒。

### 1.2 自定义管脚 (Custom Slot) 契约开发与接入标准工作流

任何用户自定义或定制化的业务代码，都必须严格通过编译器的**管脚 (Slot) 接口体系**进行 100% 收拢与类型约束。禁止绕过编译器进行直接的文件侵入或硬编码。

标准开发接入生命周期包含以下 5 个核心步骤：

1. **接口契约定义**：
   在 Block 的 `block.manifest.yaml` 中显式声明 `slots` 段落。指定管脚的 `id`、`symbol`（导出的函数符号名）及 TypeScript 输入输出类型：
   ```yaml
   slots:
     - id: ticket_comment_delegate
       kind: adapter
       target: custom/ticket_comment_delegate.ts
       symbol: addTicketCommentDelegate
       inputType: "Record<string, unknown>"
       outputType: "Promise<void>"
       writableZones:
         - "source/code/slots/ticket_comment_delegate.ts"
   ```
2. **连接映射配置**：
   在开发事实源 `source/app.yaml` 的 `slots` 数组中，将上述管脚 ID 与开发者将要编写的物理源码路径 (`sourcePath`) 进行映射连接：
   ```yaml
   slots:
     - id: ticket_comment_delegate
       block: ticket/basic
       kind: adapter
       target: custom/ticket_comment_delegate.ts
       sourcePath: source/code/slots/ticket_comment_delegate.ts
       symbol: addTicketCommentDelegate
   ```
3. **骨架编译生成 (`sec compose`)**：
   运行 `bun run sec -- compose && bun run sec -- adapt`。编译器将自动在 `project/custom/` 下创建类型安全的中间物化桩（如 `project/custom/ticket_comment_delegate.ts`），其自动以 `export * from '../../source/code/slots/ticket_comment_delegate.ts'` 的正交形式代理，确保运行时系统与开发者源码在编译层强绑定，并生成初始的 `source/code/slots/ticket_comment_delegate.ts` 骨架源码文件。
4. **管脚逻辑实现**：
   开发者（或被授权的 AI Agent）在 `source/code/slots/` 下编写自定义的具体业务逻辑，必须保证 100% 匹配 manifest 声明的导出函数 Symbol 与类型规范：
   ```typescript
   // source/code/slots/ticket_comment_delegate.ts
   export function addTicketCommentDelegate(database: any, session: any, comment: any): Promise<void> {
     // 开发者自定义逻辑实现...
   }
   ```
5. **只读漂移校验与哈希锁定**：
   - 运行 `bun run sec -- verify --lane all` 对生成结果进行编译、单元测试及 Playwright 完整验收，确保类型与接口 100% 合规。
   - 运行 `bun run sec -- lock && bun run sec -- explain` 更新工程图谱。此时 `control/provenance/provenance.json` 自动将 `source/code/slots/ticket_comment_delegate.ts` 哈希值作为 **`originType: "slot"`** 进行追踪 and 保护，防止代码静默漂移。


### 1.3 强力约束：严禁非法游离代码与 100% 收拢策略

平台的核心原则是 **"无游离的自由修改代码，严防隐式副作用"**。任何非 Block 内置的自定义业务功能、二次开发逻辑，均不准直接在 `project/` 的生成目标层进行任意修改。所有定制化代码有且仅有两种收拢渠道：

1. **Opaque Module 隔离**（适用于独立的第三方工具集或巨型辅助模块，遵循 §1.1 隔离规则）。
2. **正交 Custom Slot 挂载**（最推荐方式，适用于所有业务逻辑插桩）。

#### 任何自定义逻辑 Slot 化物理收拢开发方式：
- **开发物理落盘**：所有人类手写或 AI 编写的自定义业务代码，其物理源文件必须强制且只允许存放在 `source/code/slots/` 目录下（如 `source/code/slots/my_feature.ts`）。
- **运行时正交代理**：编译器 `sec compose` 在编译目标 `project/` 中组装对应接口层时，会自动生成对 `source/code/slots/` 的正交代理桩（Re-export / Delegate Proxy）。运行时框架通过正交代理导入这些逻辑，绝不会在 `project/` 中产生与源端分离的副本。
- **物理追踪与篡改拦截**：`sec lock` 将把 `source/code/slots/` 里的每一个物理文件，哈希追踪记录至 `control/provenance/provenance.json`。在 CI 或编译阶段，如果检测到任何不属于 Manifest 声明、或者在 `project/` 下被非法注入的“游离文件”或“逃逸修改”，编译器的校验 Pass 会强行报错拦截（错误码 `SLOT-DRIFT-003`），以此确保平台对最终产物代码的 100% 极致安全掌控。


## 2. `source/app.yaml` 正式 schema

| 路径 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `app.name` | string | 是 | kebab/snake_case，1-64 字符 |
| `app.stack` | string | 是 | 必须命中 `nextjs-ts-prisma-sqlite` |
| `app.packageManager` | enum | 否（默认 pnpm） | pnpm / npm / yarn |
| `app.mode` | enum | 否（默认 single-tenant） | single-tenant / multi-tenant |
| `registry.sources[].id` | string | 否 | plan 内唯一 |
| `registry.sources[].kind` | enum | 否 | official / private / community |
| `registry.sources[].location` | enum | 否 | compiler / workspace |
| `registry.sources[].path` | string | 否 | 相对 `location` 根目录；禁止绝对路径、盘符、UNC、NUL 与 `..` 穿越 |
| `blocks[].id` | string | 是 | 必须命中 registry block id |
| `blocks[].version` | string | 否 | semver |
| `slots[].id` | string | 是 | plan 内唯一 |
| `slots[].block` | string | 是 | 必须引用已声明 block |
| `slots[].kind` | enum | 是 | adapter / policy / ux / repair |
| `slots[].target` | string | 是 | 必须落在允许写入 zone |
| `slots[].sourcePath` | string | 否 | 必须位于 `source/code/slots/` |
| `slots[].symbol` | string | 是 | 必须匹配目标 slot 合同 |
| `acceptance[].id` | string | 是 | 必须命中已注册 acceptance id |

校验规则：blocks/slots/registry.sources 的 id 不允许重复；`slots[].block` 必须引用已申明的 block；`app.stack` 必须与所有块的 `stackProfiles` 兼容。

## 3. `block.manifest.yaml` 正式 schema

当前 schema 支持文件装载型 block；最终形态必须兼容语义合约型 block。新增实现字段应优先表达工程语义，再由 generator/pass 降级为文件，不得新增面向单个业务 block 的专用 schema 或专用安装器。

| 字段 | 必填 | 类型/约束 |
| --- | --- | --- |
| `id` | 是 | 唯一 block id |
| `version` | 是 | semver |
| `kind` | 是 | capability / strategy / infra / governance |
| `stackProfiles` | 是 | 至少 1 个，当前 `["nextjs-ts-prisma-sqlite"]` |
| `requires` | 否 | capability id 列表 |
| `provides` | 否 | capability id 列表 |
| `conflicts` | 否 | block/capability id 列表 |
| `installs` | 是 | 安装动作（`kind: copy|merge-prisma` + `from` + `to`） |
| `pins.inputs` / `pins.outputs` | 否 | `id` + `type` + `required?` |
| `slots` | 否 | `id` + `kind` + `target` + `symbol` + `inputType?` + `outputType?` + `writableZones` |
| `acceptance` | 否 | acceptance id 列表（可含 `dependsOn` + `covers`） |
| `routes` | 否 | `path` + `file` |
| `contracts` | 否 | 预留语义合约入口，承载 entities / operations / policies / views / events / permissions 等；字段落地规则以 `11` 和 `06` 为准 |
| `generators` | 否 | 预留生成器声明，按工程动作生成 service/API/DB/view/test 等产物；不得按业务 block 名称分派 |
| `upgrade` | 否 | `from: []` + `migrations: []` |
| `uiPortals` | 否 | 声明式 UI Portal 插槽列表 |
| `uiHooks` | 否 | UI Hooks 注入插槽与数据绑定配置列表 |

不变量：`provides` 与 `conflicts` 不允许交叉；`slots[].target` 必须落在 `writableZones` 内；`installs[].to` 不允许写入其他块或 `control/**`。

## 4. `graph.lock.json` 正式 schema

必填字段：`formatVersion`、`app`、`resolvedBlocks`、`installPlan`、`slotTasks`、`acceptancePlan`、`passStatus`。

校验规则：`resolvedBlocks[].installOrder` 严格递增唯一；`installPlan[].stepId` 唯一；`slotTasks[].id` 与 `source/app.yaml` 对齐；任一 pass `failed` 后后续 pass 不得 `succeeded`。

`slotTasks[]` 字段：`id`、`block`、`target`（必填）；`status`（pending/generated/filled/verified/failed）；`writableZones[]`（必填）；`sourcePath?`；`provenanceHints?`。

后续 Engineering IR 可以作为 `graph.lock.json` 的衍生产物或扩展区进入 control plane。IR 必须记录 block、capability、pin、slot、entity、operation、policy、view、file artifact 与 acceptance 的关系；文件路径只能是 IR 的降级结果，不能成为唯一语义来源。

## 5. Resolver 与 Composer 实现规则

Resolver（`platform/compiler/resolve/resolve-graph.ts`）：
1. 载入显式声明块 → 2. 校验唯一性 → 3. 校验 stack 兼容 → 4. 汇总 requires/provides/conflicts → 5. 补齐隐式依赖 → 6. 检测冲突 → 7. 检测环 → 8. 拓扑排序（infra > governance > capability > strategy）→ 9. 生成 slot task → 10. 输出 lock。
* **`manifestPath` 定位规范**：在 `resolvedBlocks` 中，`manifestPath` 必须是相对于 **Workspace 根目录** 的相对路径（`relativePosixPath(workspaceRoot, entry.manifestPath)`），以便在 Compose 缝合与 Attribution 分析阶段，编译器在 Workspace 根目录下通过相对路径直接执行 `fs.existsSync` / `fs.readFileSync` 即可读取 Manifest 配置。这纠正了此前使用 block 局部相对路径导致的 UI Hooks 丢弃与文件归属推导失效缺陷。

Composer（`platform/compiler/compose/compose-project.ts`）：
- 使用 `InstallStrategyRegistry` 执行安装（`CopyInstallStrategy`、`MergePrismaInstallStrategy`）
- 并行渲染路由图、并行写入 slot 骨架
- 支持 `Promise.all` 批量 I/O
- 新增 install/generator 能力必须按工程动作扩展，例如 `generate-entity-service`、`generate-api-route`、`generate-prisma-model`、`generate-view`、`generate-acceptance-test`；禁止新增 `CustomerInstallStrategy`、`TicketInstallStrategy` 这类按业务 block 分派的 hardcode。

### 5.1 缝合引擎五大编译 Pass (Stitching Pass Details)

在 Composer 阶段，除了基础的块拷贝和安装，还需要执行 5 个增量缝合 Pass 以将 `source/` 中的自定义资源和页面与生成的 `project/` 进行物理缝合与笼罩：
1. **Prisma 模型缝合 (`merge-prisma-template`)**（已实现）：读取 `source/schema/db.prisma.template` 模板中的模型与关系扩展，使用 AST 级别合并器将其追加至已装配的 Prisma schema，最终生成 `project/prisma/schema.prisma`，并触发 `bunx prisma@6 db push --accept-data-loss` 完成数据库同步。详细测试参见 `tests/unit/prisma-merge.test.ts` 与 `tests/integration/prisma-merge.test.ts`。
2. **Opaque 模块自动挂载 (`install-opaque-modules`)**（已实现）：扫描 `source/code/opaque/**/module.yaml`。在本地开发期以软链接形式动态向 `project/package.json` 写入依赖（如 `"opaque-<id>": "link:../source/code/opaque/<id>"`，并自动在 `project/node_modules/opaque-<id>` 创建软链接/Junction），在构建期（即检测到 `NODE_ENV=production`、`SEC_BUILD_MODE=true` 或 `BUILD_MODE=true` 时）对源码进行物理复制（复制到 `project/src/installed/opaque-<id>` 并将 `package.json` 依赖设为 `link:src/installed/opaque-<id>`），以形成完整打包，同时将物理复制的文件路径登记进 lock 文件的 `generatedPaths`。支持自动清理 package.json 中已失效 of `opaque-` 依赖。详细测试参见 `tests/unit/opaque-mount.test.ts`。
3. **Tailwind 主题与样式缝合 (`merge-tailwind-theme`)**（已实现）：读取 `source/assets/theme/tailwind.config.extend.json` 并使用 `ts-morph` AST 深度合并入 `project/tailwind.config.ts` 中的 `theme.extend` 配置（若 `tailwind.config.ts` 不存在则自动初始化）；读取 `source/assets/theme/globals.css` 追加到 `project/app/globals.css`（或 `project/src/app/globals.css`）尾部。详细测试参见 `tests/unit/tailwind-merge.test.ts`。
4. **路由映射与安全布局兜底 (`map-custom-routes`)**（已实现）：将 `source/ui/routes/` 物理复制至 `project/app/`（或 `project/src/app/`）。自动检测自定义路由在 `source/ui/routes/` 的继承链中是否有配对的 `layout.tsx`，若缺少则回退并套用全局布局 `source/ui/layouts/dashboard-layout.tsx`；若两者皆缺失，则抛出编译错误 `SPEC-ROUTE-005` 并中断编译。详细测试参见 `tests/unit/map-custom-routes.test.ts`。
5. **进程内 Prettier 格式化 (`format-output-files`)**（已实现）：在 Node.js 进程内直接通过 Prettier API 配合 `p-limit` 限制并发，执行对生成和修改的文件（来自 `lock.generatedPaths`）的异步格式化，使单文件耗时控制在极低范围内，规避 Shell 调用的冷启动开销。详细测试参见 `tests/unit/format-output-files.test.ts`。


详见代码实现，本文档不重复算法细节。

## 6. 幂等与重入

- 连续运行 `resolve` 两次，lock 必须一致。
- 连续运行 `compose` 两次，安装结果一致不得重复附加。
- `adapt` 在 slot 未变化时不得生成不同输出。
- 失败后重跑基于当前 lock 判定跳过；未成功 pass 不得伪造成功状态。

## 7. Issue 分层

| Issue 类型 | 判定依据 | 默认处理 |
| --- | --- | --- |
| Spec Issue | plan/slot/acceptance/policy 错误 | 人工决策 |
| Composition Issue | 依赖/冲突/安装路径/版本错误 | align/resolve/compose 层报错 |
| Slot Issue | slot 实现不满足类型/符号/测试 | 进入 synthesize/repair 最小任务闭包 |
| Kernel Issue | perf/correctness 失败 | 返回维护者 |

详见 `07` §4。

## 9. 代码压缩原则

> 适用于 `platform/` 下所有源码（`upgrade-workspace.ts` 除外）。新增代码必须遵守，存量代码在重构时逐步对齐。

### 9.1 数据驱动 > 过程式

- 条件分支超过 3 个且每分支只返回同结构对象时，必须提取为规则表 + `find` 匹配。
- 规则表是单一事实源：新增分支只需加一行配置，不修改匹配逻辑。
- 已应用：`error-protocol.ts`（`ERROR_PROTOCOL_RULES`）、`write-provenance.ts`（`PASS_RULES`）、`reference-check.ts`（`REFERENCE_DRIFT_CODES`）。

### 9.2 通用函数 > 复制粘贴

- 同一文件内出现 2 次以上相同结构的代码块时，必须提取通用函数。
- 通用函数通过配置对象参数化差异，避免过度抽象。
- 已应用：`generate-runtime-host.ts`（`renderEntityApiRoute`）、`format-utils.ts`（`optionalFields`）。

### 9.3 辅助函数消除样板

- `...(condition ? [x] : [])` 模式超过 3 处时，必须使用 `optionalFields` 替代。
- `formatFields` 调用中重复前缀字段超过 2 处时，必须提取共享前缀 + 条件追加。
- 已应用：`formatters.ts`（`formatUpgradeMigrationDetails`、`formatReviewDiagnostic`）。

### 9.4 计算与 IO 分离

- 每个 `write*` 函数必须有对应的 `build*` 纯计算函数。
- `write*` 只做锁获取 → 调用 `build*` → 写文件 → 返回。
- 已应用：`write-review-summary.ts`（`buildReviewSummary` / `writeReviewSummary`）、`write-provenance.ts`（`buildProvenance` / `writeProvenance`）、`write-explain-graph.ts`（`buildExplainGraph` / `writeExplainGraph`）。

### 9.5 复用成熟库 > 自造轮子

- CLI 参数解析：Commander.js（替代自定义 CommandRegistry）。
- 模板渲染：EJS（用于 `write-local-views.ts`）。
- 通用工具：lodash-es（`groupBy`、`uniqBy`）。
- 新增依赖前必须确认项目已引入；未引入时优先评估是否可用已有工具实现。

### 9.6 避免无用抽象

- 差异超过 40% 的代码块不强求通用化（如 customers/tickets 页面的 audit/notification section）。
- 通用函数的参数不超过 15 个；超过时考虑拆分为多个更聚焦的函数。
- 规则表条目不超过 12 条；超过时考虑分层或按域拆分。

### 9.7 工具链保障与 evidence 边界

- **重复检测（L1 文本级）**：`bun run jscpd`，报告见 `report/jscpd/html/index.html` 与 `report/jscpd/jscpd-report.json`。
- **架构规则**：`bun run depcruise`（依赖方向 + 循环依赖），配置见 `.dependency-cruiser.json`。
- **结构级重复检测（L2）**：`bun run discover`，报告见 `report/discover.json`。
- **一键检查**：`bun run arch:check` = depcruise + jscpd。
- **AI 事前审查**：`bun run preflight` = depcruise + jscpd + discover（三工具一脚本全跑）；`architecture-tools` workflow 必须委托这些 package scripts，不复制底层命令。
- **外部 graph provider**：Graph-It-Live、GitNexus repo graph provider、Graphify knowledge graph provider 只作为只读 evidence/overlay 输入，边界见 `11`；GitNexus 通过 npm devDependency `gitnexus@1.6.3` 接入（PolyForm-Noncommercial-1.0.0，仅开发 evidence），`gitnexus:analyze` 必须保持 `--skip-agents-md --no-stats` 只读入口，`gitnexus:mcp` 只作为 `.mcp.json` 暴露的只读 MCP 查询入口；Graphify 通过 PyPI `graphifyy==0.7.10` + `uvx` 接入（MIT）。
- **L3 语义级重复**：jscpd 和当前 discover 无法完整覆盖，`semantic-pattern-report.ts` 只把 evidence 归一为低置信 review suggestion，例如 read → validate → build → write、query → guard → map → return；不得自动重构。

所有工具输出只能作为 review evidence，不得替代 `source/**`、manifest、graph lock、provenance、review summary 或 contract freeze。raw 输出先保留在 `report/**` 或外部 provider export；需要进入治理面时由 `tool-evidence-adapters.ts` 归一为 `stableArtifact: false` 的 draft evidence。若未来新增 `code-quality-report`、`architecture-boundary-report`、`semantic-pattern-report` 或 graph overlay，必须先在 `08` 定义产物稳定性，再在 CLI/contract freeze 中声明消费方式。工具链详细配置与能力边界见 [代码库可视化流程图工具与编译原理综合指南](代码库可视化流程图工具与编译原理综合指南.md) §1.10。

### 9.8 高速开发质量闭环

高速开发默认按“短切口、强边界、快验证、及时提交”执行：

1. 先确认切口所属边界：compiler、registry、generated project、governance、Workbench、quality evidence、runtime verification 不能混写。
2. 每个切口只新增一个稳定能力或一个受控预留 contract；不把无关重构混入功能提交。
3. 修改前查通用函数索引、现有 formatter/builder/registry/workflow，避免重复 helper 和第二事实源。
4. 实现时保持计算/IO 分离：新增 `write*` 必须有 `build*`，CLI 输出必须复用 formatter/compact contract。
5. 本地默认运行 `bun run check:affected` 或明确的定向测试；`check:affected` 会基于 git 变更优先运行已修改或受影响的 fast test，默认不做 broad fast-suite fallback，并排除登记在 test budget 中会触发 Next build/Playwright 的慢测试。
6. 触及 CLI/API/JSON artifact/contract/Workbench/registry/runtime 或需要验证完整生成项目时，升级到 contract freeze、reference check 或 `bun run check:full`；`check:full` 是显式慢门禁，允许触发 `verify --lane all`、Next build 和 Playwright。
7. 每轮修改后提交一个 Conventional Commit；提交前只 staging 本切口相关文件，不混入外部未授权变更。
8. 若连续两轮修复无效，停止扩张，记录失败命令、错误摘要、已改文件、怀疑根因和下一步复现。

这套闭环不能保证代码天然高质量，但会把低质量路径显性化：重复由 L1/L2/L3 evidence 暴露，架构漂移由 dependency/contract gate 暴露，生成与人工改动由 provenance/review graph 暴露，图上操作由 mutation/dry-run/verify 收束。

## 11. 零硬编码基础设施脚手架 (Framework Scaffold Separation) 解耦落地

为了彻底消除 `generate-runtime-host.ts` 中针对 Next.js / Playwright / Prisma / tsconfig 等基础设施代码的硬编码拼装，平台在 v0.2.x 中全面落地了基于 **物理模板外置与自定义条件模板引擎 (TemplateEngine)** 的脚手架解耦。

### 11.1 总体设计原则
1. **机制与策略分离**：核心编译器仅作为“连接器和编织器”，仅理解插槽（Slots）与 Portal 缝合机制（Stitching Logic），不包含 Next.js 的路由形式、样式框架（Vanilla CSS 或 Tailwind）或 ORM (Prisma) 的具体代码实现。
2. **外置 Scaffold 模板**：所有的脚手架模板从编译器源码中完全剥离，放置到外置的 Stack 模板目录 `platform/compiler/compose/templates/`。
3. **无冲突条件渲染**：
   - 条件编译语法：`/*#IF variable*/ ... /*#ENDIF*/`（支持取反 `/*#IF !variable*/`）。它使用 TypeScript 多行注释作为边界符，这保证了物理模板在开发阶段依然具备**100% 完美的 IDE 语法高亮与类型检查提示**。
   - 文本插值语法：`__VARIABLE__`，完全规避了 `${...}` 在 React JSX 字符串或 ES6 模板字符串中的多重转义嵌套冲突，实现了 100% 的语法安全。

### 11.2 外置模板目录结构规格
所有模板物理文件均位于 `platform/compiler/compose/templates/`：
```text
platform/compiler/compose/templates/
├── app/
│   ├── layout.tsx.template          # 全局页面 HTML/CSS 骨架，带 suppressHydrationWarning 拦截
│   ├── page.tsx.template            # 动态分派的 Index 页面（含 auth/tenant 重定向或默认路由图）
│   └── ...                          # customers/page, tickets/page
├── app/api/
│   ├── session/                     # 登录/注销/当前会话的物理 API 路由模板
│   ├── customers/                   # 包含条件审计和通知的客户 API 路由
│   └── tickets/                     # 包含工单过滤、导出、汇总的 API 路由与 SLA 数据接口
├── components/                      # LoginForm、LogoutButton、CustomerForm、TicketForm 等 11 个交互表单组件
├── lib/                             # store.ts、session.ts 等状态存储与会话管理器
└── tests/                           # 单元测试与端到端 Playwright 验收流（customer-flow, ticket-flow）
```

### 11.3 核心编译器解耦缝合与生成步骤
1. **载入物理模板**：
   `generate-runtime-host.ts` 从 `lock` 中计算当前启用的特性集（如 `rbacEnabled`, `auditEnabled`, `fileUploadEnabled` 等），定位 `platform/compiler/compose/templates/` 下对应的物理模板。
2. **条件编译与文本插值**：
   调用 `TemplateEngine.render(templateName, context)` 传入选项与插值参数。引擎对模板中的注释条件进行真值判断，抹去非活动代码，保留活动代码，并替换 `__VARIABLE__` 占位符。
3. **输出物化落盘 (Materialization)**：
   将最终拼装生成的源码、测试及配置写入 `project/` 中。

通过该解耦设计，`generate-runtime-host.ts` 自身的代码行数暴跌至 **300 行以内**，所有的死字符串拼装完全移出。这在编译层实现了大师级的架构正交性！

## 12. “编译期模块化单体，运行期降级派发微服务”的终极架构

平台在系统工程学上采用 **“开发期编译模块化单体，发布期降级派发微服务”** 的核心决策。以此实现 AI 0幻觉极速调试自愈与生产部署弹性解耦的完美结合。

### 12.1 物理逻辑隔离

1. **逻辑分区 (Logical Monolith)**：
   - 所有的 Block 的核心服务层必须强制且只准存放在独立的物理模块路径中（如 `src/installed/<block-id>/service.ts`）。
   - Block 之间的代码交互严禁直接进行进程内内存强绑定循环调用，所有跨 Block 接口调用必须通过编译器声明的 `slots`（管脚）或标准 Event/Message Bus 进行解耦通信。

### 12.2 开发与调试期：10s 极速 verify 自愈

1. **共享进程与本地数据库**：
   - 在开发和 AI 修复沙盒（Repair）中，编译器将所有的 Block 组合在同一个 Next.js 单体进程中运行，并且共享同一个 SQLite 本地数据库。
   - 这确保了 affected test、TypeScript 类型分析和 Playwright 端到端全绿测试可以在 **10秒内完成物理反馈**，AI 可以在完全没有网络抖动、延迟或 502 的极纯净沙盒中执行错误修复。

### 12.3 编译发布期：微服务降级（Microservice Lowering）与容器派发

当用户在 `app.yaml` 的 `app.stack` 中声明 target 为 `microservices`，或者运行 `sec build --target microservices` 时，编译器触发微服务降级派发管线：

1. **RPC 代理桩自动包裹**：
   - 编译器扫描 `explain-graph.json` 中的跨 Block 依赖边。
   - 编译器会自动在输出派发时，**为每个 Block 的服务函数生成对应的 Route Handlers (API Endpoints) 以及 RPC 代理客户端桩 (Proxy Client)**。
   - 运行时系统中的跨 Block 本地方法调用，会自动降级为通过 RPC 客户端执行受控的微服务 HTTP/JSON 远程网络调用！
2. **多 Docker 容器自动拆分**：
   - 编译器会自动为每个微服务化的 Block 生成独立的 `Dockerfile` 配置文件，将其打包为高内聚、自闭环的微服务镜像（如 `ticket-service-image`）。
   - 每个容器独立定义其允许暴露的端口（Ports）与可访问的目录范围。
3. **分布式分库与 Schema 拆分**：
   - 编译器通过 Schema Stitching Engine 将统一的 `schema.prisma` 拆分为独立的分库模型，并自动派发到不同的 PostgreSQL 数据库实例上，从物理数据层面实现完全隔离。
4. **编译期自动注入分布式熔断防雪崩代码 (Resilience Lowering)**：
   - 网络调用是不可靠的。编译器在生成 RPC 代理客户端桩时，**会根据图谱上的强弱依赖关系，自动注入熔断、降级与重试（Circuit Breaker / Retry Policy / Fallback）逻辑**！
   - 示例：如果工单服务依赖评论服务，编译器生成的评论服务 RPC Proxy 自动包裹容错重试。一旦评论微服务挂起，代理桩自动触发本地 Fallback 返回空列表，确保工单主页面的绝对可用与防雪崩。
