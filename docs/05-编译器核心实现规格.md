# 编译器核心实现规格

本文定义编译器实现栈、Workspace 所有权、公共 API、基础 Schema 和代码生成边界。Engineering IR 语义以 `14` 为权威。

## 1. 实现栈

- TypeScript + Node.js ESM。
- 仓库脚本和测试使用 Bun。
- `tsc --noEmit` 是 TypeScript 静态检查基线。
- 公共数据边界可使用 Zod；内部对象优先使用 TypeScript 类型和显式 builder 不变量。
- `ts-morph` 用于 AST/代码生成与必要的静态分析。

核心编译器不得依赖 `Bun.*` 全局 API，除非模块职责明确属于 Bun CLI/Dev Runner/Workbench Server Adapter。

## 2. Workspace 与所有权

| Zone | 路径 | 权威/写入者 |
| --- | --- | --- |
| Authoring Spec | `source/app.yaml`、`source/model/**` | 开发者/受控 Mutation |
| Governed Source | `source/code/**` | 开发者；AI 需 Task Envelope |
| Private Block | `source/blocks/private/**` | 工作区维护者 |
| Patch/View/Env | `source/patches/**`、`source/views/**`、`source/env/**` | 对应 authoring workflow |
| Generated Target | `project/**` | compiler/generator；人工修改视为 Drift/Override |
| Control Plane | `control/**` | 对应 compiler pass 或 governance workflow |
| Local State | `.sec/**` | 可重建本地状态 |
| Runtime Dependency Materialization | `.shared-deps/**` | 可重建本地依赖缓存；允许的直接依赖由 `platform/shared/runtime-dependency-spec.ts` 唯一拥有，适用合同只验证物化结果 |

### Governed Source 类型

- `source/code/slots/**`：显式扩展点，适合 adapter/policy/ux/repair 局部实现。
- `source/code/{app,server,ui,shared,integrations}/**`：开发者拥有、通过 Contract 建模的常规应用源码。
- `source/code/opaque/**`：平台不理解内部实现，但必须声明 boundary contract。
- `source/code/lab/**`：实验区；发布前必须提升为受治理源码、Slot、Patch 或 Private Block。

禁止继续使用“所有自定义业务代码只能放 Slot”作为长期规则。Slot 是 extension point，不是所有自由度的垃圾桶。

## 3. `source/app.yaml`

当前正式字段由 `PlanFile` 及 loader/validator 决定。稳定概念：

- `app`：name、stack、packageManager、mode。
- `registry.sources`。
- `blocks`。
- `slots`。
- `acceptance`。

未来语义模型优先进入 `source/model/**` 和 Block `contracts/**`，不无限扩张 `app.yaml` 为巨型业务 DSL。

## 4. `graph.lock.json`

Lock 记录已解析的 Block、安装计划、Slot Task、Acceptance Plan 和 Pass Status。Lock 的职责是**解析与装配状态锁定**，不是 Engineering IR。

约束：

- resolved block install order 稳定且唯一。
- step/task id 唯一。
- pass 失败后不得伪造后续成功。
- 同一 Authoring Input 的重复 resolve 必须确定性产生相同逻辑结果。

IR 可以引用 Lock 中的解析事实，但不能把文件路径或 install step 当作唯一业务语义来源。

## 5. 编译器模块

```text
platform/compiler/
  align/
  codegen/
  compose/
  emit/
  ir/          # Engineering IR frontend/build/index
  parse/
  repair/
  resolve/
  synthesize/
  verify/
  workbench/
```

`platform/compiler/index.ts` 是唯一公共只读门面。具有副作用且不能成为公共 API 的 compiler runtime 只能由拥有对应 pipeline stage 的 production owner 直接导入，并由 `tests/contract/test-architecture.test.ts` 的 exact owner→module allowlist 冻结；除此之外外部模块禁止穿透 import 子目录。

### IR 模块职责

`platform/compiler/ir/` 是 **Engineering IR Kernel** 的实现 ownership boundary；builder、index 与 identity invariant 在此收敛。外部编译模块仍通过 `platform/compiler/index.ts` facade 使用公开能力，不穿透内部文件。

- `build-engineering-ir.ts`：从 Plan、Lock、Manifest、治理输入和后续 Contract 构建 canonical IR。
- `index-engineering-ir.ts`：建立 by-id、by-kind、outgoing/incoming 等只读索引。
- `semantic-plan.ts` / `semantic-lowering.ts`：只从 validated semantic facts + generator declarations 构建 plan 并 lower；不得读取 raw Contract 重复解释，也不得与 ExplainGraph builder 混合。

第一版 IR builder 不直接读文件系统；调用方加载对象后传入，使核心计算可单测、可重复。

## 6. Resolver、Composer 与 Lowering

### Resolver

负责 Block Registry 解析、requires/provides/conflicts、stack compatibility、隐式依赖、环检测、拓扑排序、Slot Task 和 Lock。

Resolver 不解释 `Ticket` 等业务名称。

### Composer

负责执行已经解析的工程动作和当前兼容文件安装。Install Strategy 按工程动作扩展，例如 copy/merge-prisma。

### Lowering / Generator

语义 Contract 进入 IR 后，按工程动作注册 Generator：

```text
generate-entity-service
generate-api-route
generate-prisma-model
generate-view
generate-acceptance-test
generate-policy-check
```

禁止：

```text
CustomerInstallStrategy
TicketInstallStrategy
generate-customer
generate-ticket
```

判断标准：新增同类业务实体应主要新增 Contract/Block，不修改 core business branch。

## 7. 代码生成

`platform/compiler/codegen/code-builder.ts` 是当前 TypeScript/TSX 程序化代码生成公共基础；核心 builder 类为 `CodeBuilder`。

规则：

- import/type/interface/function/class/export 等结构通过 API 构建。
- 函数体允许受控 statement text，但必须经 AST parser 验证。
- Generator 产出应先形成中间 plan/structure，再写文件；计算与 IO 分离。
- 生成结果排序、命名和格式化必须确定性。
- 生成源文件路径进入 Artifact Provenance。

## 8. 幂等与重入

- parse/normalize/build IR：同输入同结果。
- resolve：重复执行不产生逻辑漂移。
- compose/lower/generate：重复执行不得重复追加。
- adapt：未变化 Task 不产生新输出差异。
- verify：只读；除 evidence/diagnostics artifact 外不得修改 authoring/project 语义。
- emit/projection：同 canonical state 产生相同逻辑内容；时间戳等 volatile field 不得参与 semantic identity。

## 9. Opaque Boundary

`source/code/opaque/**/module.yaml` 至少声明：

- id / entry / exports。
- inputs / outputs。
- effects。
- permissions / policies。
- acceptance。
- provenance hints。

Opaque 内部默认不进入 canonical semantic facts；其声明的 boundary contract 可以进入 IR。源码、static/runtime provider 可形成 Evidence，不能静默覆盖 boundary contract。

## 10. 公共基础设施

- `platform/shared/logger.ts`：日志。
- `platform/shared/runtime-dependency-spec.ts` 唯一拥有 runtime package identity；全部 direct runtime dependency 必须固定为精确数字版本，已安装 manifest 的 name/version 必须逐项匹配该 spec。Playwright 还要求已安装的 `@playwright/test`、`playwright`、`playwright-core` 共同匹配同一 exact release。Range、tag、generated manifest漂移、direct package版本漂移或Playwright三包任一漂移都在 readiness、安装发布或计划发布前失败。
- `platform/shared/project-runtime.ts` 唯一拥有 external Node 与项目本地 Playwright browser cache 的解析、锁、安装、超时、abort、进程树清理和可执行文件后置验证。它通过已安装 Playwright registry 产生绑定三包manifest digest、external Node、physical cache、platform-specific executable absolute/relative path的唯一opaque authority；Dev Runner、hook、verifier与isolated planner只能消费该authority，不能实现第二installer、第二browser selector或回退ambient/global cache。Compiler dependency generation的原子发布也只由该模块拥有：Windows仅对`EPERM`、`EACCES`、`EBUSY`执行有界短重试，每次都复核source directory identity与target absence；已完成但返回错误的rename只能由target继承同一identity证明，rollback复用同一原语，其他错误立即fail closed。
- isolated runtime plan把已验证的 external Node、依赖树、opaque browser authority与source identity冻结为同一revision，再物化到staging；staged browser physical path只由该plan的path builder导出。Plan、child、runtime verification、production sentinel与测试不得重新读取`browsers.json`、拼接platform目录、复制relative root或伪造预热cache。
- Windows staging-owned `TEMP` 可使用 namespaced path 解决文件系统寻址边界；这不证明 Chromium/Playwright 能从同一 textual path 启动。
- Browser cache 始终只有一个由 runtime plan 物化并验证的 physical staging authority。Windows host boundary把ambient TEMP只当作不可信分配表面：以不可预测名称原子创建私有root后立即移除继承ACL、绑定当前进程SID并验证owner/DACL，只有该私有root可承载唯一、短期、launch-compatible projection；harden/prove acquisition失败时必须回收已确认为空的私有root，回收失败与primary error以同一`AggregateError`保留，禁止吞错后遗留`sec-h-*`。父级把plan派生的physical cache、exact executable identity与projection绑定编码进固定child命令行；staged runner在Playwright `runCommand.beforeSpawn`的真实启动边界再次验证alias、physical cache和executable identity。projection只进入fixed isolated environment，并在success、failure、timeout或pre-launch rejection后连同私有host root回收；POSIX直接使用physical staging path，不创建projection。
- Isolated acceptance 的 Next 服务生命周期由 SEC verifier 直接拥有：只用 exact staged Node 以无 shell 子进程启动，readiness必须同时观察direct child的bounded `Ready in` marker与loopback `/login`成功，并在执行Playwright前再次确认child未退出。启动前与cleanup后都通过exclusive bind证明端口ownership；只有`EADDRINUSE`属于typed occupation，访问拒绝等其他socket错误保留原始归因。端口仍被descendant或竞争进程占用是typed cleanup failure；execution与cleanup同时失败时必须保留在同一`AggregateError`。生成的 Playwright config 在 isolated mode 不注册 `webServer`，不能把关闭权退给 Playwright 的 Windows `taskkill` fallback；非 isolated 本地开发仍使用原 Bun webServer。
- Production sentinel 的外层测试预算必须从 canonical isolated supervisor deadline 派生，并额外包含 cleanup margin；不得让 Bun test timeout 先于 supervisor 结束后启动 `afterAll` 删除仍在运行的 staging workspace，否则真实生命周期故障会被伪装成 `artifact-read`。
- Staged Verification proof 只绑定会改变验证语义的 project authoring inputs。`.next/`、`node_modules/`、`.runtime-deps.stamp.json` 与 Next 自主管理的 `next-env.d.ts` 是已由 runtime/build authority 管理的派生输出，不得进入 project input digest；`package.json`、配置、源码、测试与其余未分类根条目仍 exact-bound，任何漂移都 fail closed。派生输出排除集只由 `semantic-mutation-staged-project-input.ts` 拥有，不能在 verifier、测试或文档中复制第二份算法。
- `platform/shared/collections.ts`：稳定集合工具。
- `platform/shared/process.ts`：子进程、timeout、retry。
- `platform/shared/yaml.ts`：YAML 读取与 boundary validation。
- `platform/shared/*-contract.ts`：公开机器合同。
- `platform/compiler/codegen/code-builder.ts`：`CodeBuilder` 代码生成基元。
- `platform/compiler/index.ts`：compiler facade。

共享模块避免模块加载时的隐式重副作用；默认实例使用惰性 getter 或显式注入。

## 11. 代码压缩原则

1. 事实表/枚举只维护一处。
2. 计算与 IO 分离。
3. 通用 helper 必须减少至少多个真实重复点，不为“可能复用”抽象。
4. Registry/Builder/Selector 优先于巨大 switch。
5. 类型用于表达不变量，不用 `Record<string, unknown>` 隐藏稳定协议。
6. Projection 不重复 canonical business rule。
7. 新术语必须对应新职责；同义 wrapper 应删除。
