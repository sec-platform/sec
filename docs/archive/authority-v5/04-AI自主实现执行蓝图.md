# AI 自主实现执行蓝图

本文只定义**参与 SEC 仓库开发的自主编码 Agent 的稳定控制协议、事实源分层和行为路由**。具体 trigger、exclusion、permissions、execution、completion evidence、stop/reload/recovery 与 prohibited shortcuts 只存在于 `.agents/skills/**`；产品内 AI Runtime 以 `09-AI Runtime、任务信封与治理规范.md` 为权威。

## 1. 事实源与上下文分层

任务上下文严格按以下层次解析：

```text
live repository / GitHub evidence
→ canonical authority docs
→ AGENTS.md / 本文
→ active Work Package pointer
→ frozen Work Package manifest
→ one Task Envelope
→ relevant types / tests / source
→ exact-head Evidence / merge gate
```

- `main` 是唯一正式工程事实。branch、PR、Issue、聊天、Completion Report、审计报告和代码图只提供导航或 Evidence。
- 新 Work Package 开始时由 `sec-repository-orientation` 唯一负责 resolver 信任、目标 workspace 绑定与一次 current-state 解析；本文不复制其可执行入口。live default ref、PR/Issue、CI/Review、active pointer 或 workspace 任一 unresolved、invalid 或冲突都必须 fail closed。
- 普通 Task Envelope 只装载相关 authority/types/tests/source，禁止默认扫描整个仓库。用户明确要求全仓分析、重大架构演进前或系统性漂移时，改由 `sec-repository-audit` 对全部 tracked paths 做 exact-revision census。
- `docs/archive/**`、`docs/superpowers/**`、旧 PR 描述、外部 Provider 和历史 Evidence 不得替代当前 authority。

## 2. 三个动态控制面

### `docs/work/current-state.yaml`

只保存 live resolver 配置和可跨候选复用的稳定 Goal/capability事实。当前 SHA、PR、CI、Review、失败候选和诊断历史由 resolver 运行时观察，不回写为静态“当前事实”。

### `docs/work/rolling-plan.md`

只保存当前包与后续二至五个条件化候选。它不是永久 Backlog，不证明任务已执行，也不保存每次 commit/run 的流水。

### `docs/work/active-work-package.md`

只保存一个 canonical manifest path、Git blob raw bytes SHA-256 和选择模式。共享 resolver 必须验证：

- candidate manifest bytes 与 digest一致；
- live default branch是否已包含同path + digest；
- default ref是否新鲜且可解析；
- 选择结果是唯一 `active`、`none`、`unresolved` 或 `invalid`。

完整 scope、owner、acceptance、tests 和禁止面只存在于所选 `docs/work-packages/<id>.md`。新 manifest 原子接管 pointer 后，旧 manifest 才移入 `docs/archive/work-packages/`。

## 3. 唯一行为路由

| 行为闭包 | 唯一 Skill |
| --- | --- |
| 建立最小充分仓库事实 | `sec-repository-orientation` |
| 全部 tracked paths、authority、owner、入口、状态与验证审计 | `sec-repository-audit` |
| 确定性规则与启发式行为分类、去重、抽取 | `sec-heuristic-governance` |
| canonical authority、公共合同和跨 owner 架构演进 | `sec-architecture-evolution` |
| 冻结 DAG、candidate、Gate custody与下一 transition | `sec-a0-integrator` |
| 创建、切换、digest绑定和归档 Work Package | `sec-work-package-lifecycle` |
| 把 Work Package 收窄为单角色 Task Envelope | `sec-task-delegation` |
| frozen owner seam 内实现纵向切片 | `sec-worker-development` |
| changed-path impact、focused/affected/Risk选择 | `sec-impact-and-validation` |
| frozen exact head 独立审查 | `sec-exact-head-review` |
| Scope/Verification/merge/readback/cleanup | `sec-ci-and-merge` |
| verifier/toolchain trust-root人工 bootstrap | `sec-trust-root-bootstrap` |
| 失败分类、最小重跑、proof reset和设计回退 | `sec-failure-recovery` |
| 压缩、进程退出、session/worktree切换后的可验证续跑 | `sec-context-resume` |
| 文档生命周期、权威图、链接和重复体系治理 | `sec-documentation-governance` |
| Provider、MCP、外部工具引入/升级/退役 | `sec-external-capability-governance` |
| Bun、依赖、脚本、Hook和配置变更 | `sec-toolchain-and-dependencies` |

`platform/shared/agent-skill-contract.ts` 是行为 ID、Skill ID 与路径投影的机器 registry。新行为不得只写入本文件；必须经 `sec-heuristic-governance` 判断能否下沉为确定性合同，不能下沉时登记唯一 Skill owner。

## 4. A0、Worker 与单写者不变量

- 一个时刻只有一个 formal active Work Package 和一个 candidate epoch。
- A0 独占 DAG、Task ownership、integration、Gate custody、merge、closeout 与 branch hygiene；Worker 不得自授权跨 owner 修改或 hosted Gate。
- 同一 canonical type、revision、builder、pipeline order、状态 owner 或 authority章节只有一个写者。
- 单一纵向切片默认零子 Agent；并行只允许完全不重叠、前置已满足、可独立提交且有明确 reconciliation point 的 write seam。
- 每个 Gate 只有一个 `gate_owner`；结果以 `gate_key + tested head + profile` 唯一标识，输入未失效时必须复用。
- Task Envelope、Reconciliation Delta、candidate invalidation、proof reset 和 stop 语义以对应 Skill 为准，不在本文复制第二状态机。

## 5. Work Package 与分支生命周期

分支是代码演进路线，不是等待机械合并的功能包：

- `feat/*`：正式产品能力。
- `fix/*`：正式产品缺陷修复。
- `refactor/*`：不改变外部语义的结构重构。
- `docs/*`、`chore/*`：文档和工程维护。
- `spike/*`：大型未知架构探索，默认禁止直接合并；成立后提炼为正式变更。
- `integration/*`：只用于两条真实并行产品线的临时总装。
- `validation/*`、`diagnostic/*`：验证、故障隔离和证据采集，默认禁止合并。

禁止长期使用一次性远端测试分支承载 CI 参数。测试分片、suite和Evidence由 Verification Contract、runner、artifact和日志承担。

变化只有同时满足以下条件才可进入 `main`：

1. 仍是有效产品能力、修复或必要维护，且结果未被 main 包含或新实现取代。
2. canonical authority、owner、public contract和迁移边界一致。
3. exact base/head/tree/manifest/profile清楚，required evidence绑定当前 head。
4. 无 unresolved review thread、有效 `REQUEST_CHANGES`、probe、临时日志入口或生成物漂移。
5. merge后对新 main 做产品结果 readback，并完成已证明安全的 branch/worktree/retired入口清理。

Squash merge 后按最终 tree和行为结果判断是否进入 main，不能仅用原 commit ancestry、ahead/behind或分支名判断遗漏。

## 6. 架构与实现不变量

每项产品或架构变化必须明确：

- 权威输入与 canonical state；
- 唯一写 owner与读 consumer；
- canonical、artifact、evidence、projection 的身份；
- identity/revision、确定性、可重入与并发边界；
- failure、rollback、recovery和迁移/退役；
- positive、negative、compatibility、property或runtime证据。

修改 canonical authority、公共合同、identity/revision、状态所有权、pipeline 或跨 owner 边界时先执行 `sec-architecture-evolution`。authority 与 contract 冻结后，再由 `sec-worker-development` 实现；不得先改 Workbench/adapter/容易修改的代码再反推降低 IR 或产品目标。

### Compiler API

`platform/**` 的非 compiler 模块必须通过 `platform/compiler/index.ts` 使用公共 API。副作用 runtime 只有被 architecture contract 显式允许的 production owner 可以直接导入内部模块。

### 代码生成

Compose/Lowering 生成 `.ts`/`.tsx` 时使用 `CodeBuilder` 或正式 Generator API。不得继续扩张大段模板字符串生成；相同 validated input/profile/provider revisions 必须产生相同逻辑 bytes。

### Engineering IR

- IR 类型以 `14-Engineering IR与语义事实规范.md` 和正式 shared types 为权威。
- Entity/Fact identity、revision和排序必须稳定、确定性。
- UI布局、颜色和纯投影字段不得进入 canonical IR。
- ExplainGraph、SemanticView、ReviewSummary 和 Workbench 只从 canonical state 投影。

### AI 与外部 Evidence

AI、GitNexus、Graphify和其他 Provider 输出只能进入 inferred/evidence/candidate 层，不能自动成为 authoritative fact、扩大 allowed paths 或降低 Verification。引入、路由、数据边界、版本和退役由 external capability policy/ledger 与 `sec-external-capability-governance` 唯一拥有。

## 7. 验证事实源

- 测试层级以 `docs/test-architecture.md` 为权威。
- 本地反馈、affected、Quick/Risk/Full、Evidence和hosted执行语义以 `docs/test-feedback-and-ci-lanes.md`、`platform/shared/test-impact-contract.ts` 和 `platform/shared/ci-contract.ts` 为权威。
- changed-path选择由 `sec-impact-and-validation` 执行；Scope/Verification/merge由 `sec-ci-and-merge` 执行。
- verifier trust-root candidate不能用自身实现自证；必须由 `sec-trust-root-bootstrap` 通过旧 base/人工受信环境验证。
- 未运行、skipped、missing、pending、timeout或stale结果不得宣称 PASS。

本文件不复制具体 repository dispatch payload、Gate矩阵、重跑流程和命令清单；这些属于机器合同、测试/CI authority与对应 Skill。

## 8. 完成与报告

完成不能由 Issue、PR body、branch、checkbox、计划、Skill或报告声明证明。必须区分：

- 设计/authority 已冻结；
- 实现已提交；
- required verification 已绑定 exact head并通过；
- 结果已进入 main；
- merge readback与清理已完成；
- 用户可观察能力已现实闭合。

最终报告只陈述 canonical/contract变化、关键不变量、实际执行的证据、unknown/blocker和未实现边界。详细执行步骤、临时推理和普通进度不得另建第二套叙述文档。
