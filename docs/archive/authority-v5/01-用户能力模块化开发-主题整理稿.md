# 用户能力模块化开发：核心命题

本文只定义 SEC 的问题、概念和长期方法论。产品架构见 `02`，实现协议见 `05–11` 与 `14`。

## 1. 要解决的问题

传统软件工程把源码文件和函数作为主要操作对象。大型项目的真实知识却分散在命名、目录、调用链、测试、数据库、运行时行为和开发者经验中。结果是：

- 复用往往停留在库、模板或复制文件。
- 业务能力缺少统一的依赖、验收、升级和来源合同。
- AI 面对整仓源码时需要反复重建上下文，并容易产生架构漂移和隐式副作用。
- Review 主要观察代码行差异，难以直接回答工程语义发生了什么变化。

SEC 的核心命题是：

> 把工程知识从隐式源码经验提升为可声明、可组合、可推导、可验证、可追踪的工程语义。

## 2. 最小模型

```text
隐性专家劳动
  → Authoring Specification
  → Semantic Contract
  → Engineering IR
  → Compiler Pass
  → Artifact
  → Verification / Provenance / Review
```

需要三个不同粒度的单位：

### Block

Block 是分发、版本、信任、升级和资产封装单位。它可以包含 Contract、Generator、Files、Tests 和 Migration。

### Semantic Responsibility

Semantic Responsibility 是架构理解单位，例如 `TicketLifecycle`、`TenantScopeGuard`、`RetryController`。它表达“谁负责什么”，可以位于单一 Block 内，也可以跨越多个 Block。

### Semantic Fact

Semantic Fact 是最小工程事实，例如：

```text
TicketStateMachine OWNS Ticket.status
createTicket EMITS TicketCreated
TicketQuery REQUIRES TenantContext
TenantScopeGuard VALIDATES TenantContext
```

统一 IR 由 Semantic Entity 和 Semantic Fact 组成。图只是其中一种投影方式。

## 3. 与传统开发的差异

| 维度 | 传统工程 | SEC 目标模型 |
| --- | --- | --- |
| 主要事实 | 源码与人工知识 | Authoring Source + Engineering IR |
| 复用单位 | 函数、库、模板 | Block + Contract + Verification + Migration |
| 架构理解 | 文件/模块/调用图 | Responsibility、Ownership、Contract、Effect |
| 变更表达 | 文本 Diff | Source Diff + Fact Delta + Impact |
| AI | 整仓程序员 | 受限 Semantic Operator / Synthesis Pass |
| Review | 行级审查 | 工程语义变化与风险审查 |

源码不会消失。源码仍是可部署、可调试的真实运行产物；变化的是**权威语义和主要工程操作不再完全依赖源码反推**。

## 4. 与相邻系统的边界

- 脚手架/模板：解决初始化；SEC 负责持续组合、验证、升级、来源和语义变更。
- 低代码：通常绑定私有运行时；SEC 输出真实项目源码和标准运行目标。
- SDK/库：复用调用点；Block 复用能力、合同、生成策略、验收与迁移。
- 工作流引擎：编排运行时流程；SEC 位于工程构建与治理层。
- AI 编码助手：擅长源码搜索和修改；SEC 为其提供工程语义、权限边界和验证闭环。
- 代码知识图：从现有代码抽取关系；SEC 的 canonical semantics 优先来自结构化声明和编译器推导，源码/运行时分析只补充 Evidence。

## 5. AI 的位置

AI 不拥有工程事实裁决权。

正确关系：

```text
Compiler builds canonical state
  → Platform projects bounded context
  → AI proposes Source Patch or Semantic Mutation
  → Platform validates authority and bounds
  → Compiler rebuilds IR
  → Verification proves observable behavior
  → New revision is accepted or rejected
```

AI 的价值是综合、对齐、局部实现、修复和解释；平台负责 authority、边界、事实重建和合流。

## 6. 长期飞轮

```text
高质量 Contract
  → 可复用 Block
  → 更准确 IR
  → 更小 AI Context
  → 更强 Verification
  → 更可靠 Upgrade/Impact
  → 更低维护成本
  → 继续沉淀 Contract/Block
```

真正的资产不是 Prompt，而是可演进的 Block、Semantic Contract、Fact Provenance、Verification 和 Migration 历史。

## 7. 成功标准

SEC 成功不以“生成多少代码”判断，而以以下能力判断：

1. 新增常见业务对象主要增加 Contract/Block，而非修改核心编译器业务分支。
2. 平台能解释关键状态、数据、权限、副作用和场景关系。
3. 变更前可计算语义影响，变更后可输出 Fact Delta。
4. AI 在未知代码库中主要读取结构化 Context Packet，而不是反复扫描整仓。
5. 任何自动修改都能追踪来源、授权范围、验证结果和回滚路径。
