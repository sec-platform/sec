# 代码分析、可视化与编译原理参考

> 本文是历史技术参考，不拥有当前工具选择。当前外部工具、CodeGraph/GitNexus路由和Provider证据政策以`governance/external-capability-and-provider-policy.md`为准。

本文是研究参考，不是 SEC 实现权威。具体工具版本/命令以 `package.json` 和配置文件为准，产品边界以 `02/08/11/14` 为准。

## 1. SEC 为什么需要 IR

源码、AST、类型、调用图、运行 Trace 和业务 Contract 描述的是不同层次：

```text
Source Text
→ AST
→ Symbol / Type / Control/Data Analysis
→ Engineering Semantic Facts
→ Engineering IR
→ Compilation / Verification / Projection
```

AST 适合表达语法；Call Graph 表达潜在调用；Runtime Trace 表达一次或一组实际执行；Engineering IR 表达平台接受的工程语义。它们不能互相冒充。

## 2. 编译器可借鉴的原则

SEC 借鉴成熟编译器的：

- 中间表示。
- Pass Pipeline。
- 明确输入/输出合同。
- Deterministic Transform。
- Builder API。
- Lowering。
- Verification。

SEC 不复制 LLVM 的机器级指令模型。它处理的是 Responsibility、Contract、State、Data、Effect、Permission 和 Artifact 等工程语义。

## 3. 可视化原则

大图不是更多知识。

默认只显示当前问题所需子图：

- Architecture：系统职责和边界。
- Scenario：一个入口/行为的因果路径。
- Data：一个值/实体的流动和转换。
- State：所有权、读写和生命周期。
- Contract：前后置条件、错误和保证。
- Effect：外部副作用、Permission、Trust Boundary。
- Impact：拟议变更的传播范围。

全局 Call Graph、AST Tree、Class Diagram、File Tree 只作为 Query/Debug View，不作为默认认知面。

## 4. C4 的启示

C4 的关键不是固定画四张图，而是层级化 Zoom 和“不同视图回答不同问题”。SEC 采用同一 IR 多投影：View 是 Projection，不是独立维护的图。

## 5. Static Analysis

TypeScript/ts-morph/Compiler API 可提供：

- AST。
- Symbol/Type。
- import/export。
- 可解析调用关系。
- read/write 候选。
- type signature。

静态分析存在动态调用、反射、框架约定、runtime injection 等不完备区域。结果进入 derived/inferred evidence 时必须保留来源和置信边界。

## 6. Data Flow 与 CodeQL/CPG 思路

数据流分析适合表达 possible value propagation。SEC 应从工具或内部分析获得 Evidence，再映射到 `FLOWS_TO/DERIVES_FROM/TRANSFORMS_TO/VALIDATES/...` 候选 Fact。

在没有 Contract 或强确定性 compiler rule 时，不把 possible flow 直接写成 authoritative fact。

## 7. Runtime Trace

Runtime Trace 用于：

- Scenario path observation。
- hot/cold path。
- latency/error overlay。
- actual branch/retry observation。

Trace 是 observed evidence。一次未观察到某路径不证明路径不存在。

## 8. 当前工具分层

| 层 | 当前工具/机制 | 作用 |
| --- | --- | --- |
| L1 Text Clone | jscpd | 复制粘贴和 token 重复 |
| L2 Structural Pattern | `discover-all.ts` | AST 归一化结构重复 |
| Architecture Boundary | dependency-cruiser | import/依赖方向和循环 |
| IDE/Repo Graph Evidence | Graph-It-Live、GitNexus | call/reference/impact/navigation hint |
| Knowledge Evidence | Graphify | code/docs/diagram knowledge graph |
| Canonical Semantic | Engineering IR | 平台接受的 Semantic Entity/Fact |
| Projection | Explain/Semantic View | 人和 AI 的问题导向视图 |

外部工具均不得绕过 adapter 直接修改 IR、ExplainGraph 或 Mutation。

## 9. L3 Semantic Pattern

L3 不是 clone score。它识别工程模式候选，例如：

```text
read → validate → transform → persist
query → guard → map → return
build → write artifact
```

输出应该是：

- pattern identity。
- participating entities/artifacts。
- evidence。
- confidence。
- candidate action：helper / contract builder / generator / block primitive / policy / acceptance。

L3 默认 `inferred`，早期只能作为 Review Suggestion；不能自动重构。

## 10. 工具选择原则

1. Canonical fact source 优先于工具输出。
2. 工具输出必须经过 provider-neutral adapter。
3. Raw report 不进入 Workbench 主图。
4. Evidence 可以参与 Context/Overlay，不参与权限扩张。
5. 能用 Compiler API/Contract 确定的事实，不交给 AI 猜。
6. 不因某个图工具方便就让其 Schema 反向决定 SEC IR。
