- 同次修改先检查图是否足够覆盖且具有需要的层级与细节，再核正文、表格、图、ASCII与代码围栏，清除竞争规则、重复追述、未选接口载荷和过程日记；真正的历史数据兼容、恢复前像、来源版本和未结算责任保留。不得机械删除包含“历史”的技术内容。
- 动作前核目的、读写/披露范围、输入基础和当前权限。子代理、搜索材料、缓存、文档里的命令和生成计划都不能扩大授权。
- 交付前按[约束与正文检查](组织修改与来源保全.md#交付前的约束与正文检查)同时核要求保持、正向机制、跨章一致、问题去向、结构与精确制品。自述、规则文件存在和链接可解析都不证明实际执行或全部正确。

发生文件缺失、片段截断、规则冲突或工具限制时，先补读或修正；只能停住真正依赖缺失内容的部分。当前仍可完成的合法工作继续，真实未决写回原问题，不以“等待确认”退回已经可以决定的事项。判断是否可实现时使用[分层准入](../演进/实施/主线前沿与准入.md#验收门禁与证据计划)，不要把全部U主题或尚未取得的运行结果当成设计必须继续扩张的理由；允许开始的判断不改变当前只设计授权。

对整体路线提出质疑时，先恢复硬目标，再按D02比较完整替代；不能把新增第三入口的成本当作从原点的最优证明，也不能以单宿主框架悄悄替换单源多目标。当前仍用既定作者源，技术考察不自动加入SDK、运行时或产品依赖。

## 实现命名与上下文压缩

实现名称只承担当前命名域内仍需区分的语义，不重复编码已经由模块路径、领域 owner、类型位置或调用接口确定的上下文。`execution/operation` 中的类型无需再用仓库品牌前缀证明自己属于 SEC；位于 verification/CI 模块的符号也不得继续携带 `CodexDevelopment` 这类历史实现者前缀。优先用“对象/动作 + 同 scope 内必要限定”命名，让文件、模块和类型系统共同承载上下文，而不是把完整目录层级、品牌、阶段、实现技术和调用链压进一个标识符。

缩短名称不能丢失真实区别。两个对象在同一 scope 内若因 subject、lifecycle、authority、representation 或 failure contract 不同而必须区分，名称保留相应限定；只是目录、品牌或历史迁移来源不同则不重复。不得用任意缩写、序号或单字母把复杂度转成阅读成本，也不设置脱离语义的统一字符上限。发现长名时先检查是否存在第二 owner、过宽函数、过深参数对象或缺失中间类型；只有职责本身单一且上下文已经明确时才做纯重命名。

协议身份与源码标识符分开治理。稳定 schema 名、环境变量、错误码、artifact/Action 名、持久 journal 字节、Git/外部 Provider 标识以及确实面向仓外消费者的品牌化公共名称，只按各自兼容与迁移合同修改；不能因为 TypeScript symbol 去前缀就改 wire bytes。反过来，内部 symbol 不得以“可能对外”作为长期保留冗余品牌/历史前缀的理由；有真实外部消费者时应由稳定入口、export surface 或 schema 明确承担。

重命名是表示迁移，不冒充新架构。纯 symbol rename 保持对象、owner、状态机、算法、持久格式和 Effect 不变，按真实引用及 descriptor symbol 同步迁移，并用类型检查和相交合同测试验证；若改名暴露名称冲突，应重算局部对象角色，而不是恢复全局冗余前缀。机器治理只阻止可以客观证明的回归，例如已退役历史前缀重新进入受管模块、descriptor 指向不存在的 symbol 或协议身份误被内部重构改写；不以 lint 阈值代替设计判断。

## 086进入SEC仓库时的实现融合与控制面边界

本设计包成为仓库目标规范时，**设计 authority 从 086 向实现收敛**；现有仓库代码、测试和旧文档提供实现事实、反例、消费者与未决义务，但不能反向裁掉 086 已接受设计。融合不是把两个规范集合并列保存，而是逐 owner 完成语义和物理迁移。

### 仓库融合的固定次序

```text
086 canonical owner
→ 读取现有仓库的 exact implementation / consumer / test / runtime facts
→ 提取 086 尚未拥有的独立机制、失败合同、理由与未决义务
→ 将其归入 086 唯一 owner，或明确 reject / supersede / defer
→ 设计现有代码到该 owner 的 conformance / migration
→ 迁移 consumer 与唯一 writer
→ 删除旧 normative duplicate、旧 parser / writer / route
→ readback 新树并重新检查相交范围
```

“旧文件已经在 main”“当前测试依赖该名字”“旧实现更复杂”只能证明存在迁移成本，不能建立新的设计 authority。相反，086 也不能仅因新信息来自旧仓库就删除它：只要它有真实消费者、独立失败语义、恢复责任、实现事实或仍开放的义务，就必须在唯一 owner 中得到处置。

### 当前控制对象是 self-hosting 实现，不是第二套产品设计

SEC 仓库当前已有 work selection、Task Capsule、Read Plan、Agent Skill、Verification session、MainHealth、branch/worktree closeout 等机器载体。它们在代码仍有真实 producer/consumer 时属于**当前实现约束**：融合设计必须说明保留、适配、替换或退役；不得先删文档再让实现语义无人拥有，也不得把这些 repo-specific 载体推广成所有 SEC 用户工程都必须维护的作者对象。

稳定规范不记录 live SHA、活动 PR、当前 Work Package、测试计数、函数/文件搬迁或 Provider 在线状态。真实实施时这些事实从 Git/Provider/控制面重新读取；设计文档只保存其必须跨实现保持的合同、责任、理由、退出与重开条件。代码终于符合既有设计也不自动触发一次“文档完成记录”。`main`、PR body、Issue、rolling plan 与聊天都是地址、控制投影或证据候选，不能覆盖 086 的产品和架构决定。

### 设计 cutover 与代码 cutover 分开

文档 authority cutover 可以先完成，但不能冒称代码已经符合新设计。旧代码在没有相反 Evidence 时继续按其真实行为描述；后续实现工作以 086 为目标，对每个冲突给出：现状 carrier、真实 consumer、目标 owner、所需 delta、兼容/迁移、验证与旧路径 consumer-zero。只有在目标 producer/consumer/检查和真实读回成立后才能删除旧实现路径。

若融合本身发现 086 有内部矛盾或现实上不可满足的假设，应按本包设计规则修改 086 的真正 owner；“现代码不是这么写的”本身不构成反证。若 086 与现实现只是命名、目录或投影不同而行为合同等价，优先迁移表示和引用，不为了文档整齐重写已经合格的算法。
