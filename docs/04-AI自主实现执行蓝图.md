# AI 自主实现执行蓝图

本文约束**参与 SEC 仓库开发的自主编码 Agent**。产品内 AI Runtime 以 `09` 为权威。

## 1. 开始任务前

先重新建立 live evidence，再按最小充分上下文顺序读取：

1. latest `main`、open PR/Issue、当前 head/base/merge-base/diff、review 与仍有效 evidence，并把 observed facts 写入 `docs/work/current-state.yaml`。
2. `00`：确认事实权威位置；`03`：确认稳定阶段 DAG 与完成定义；`docs/work/current-state.yaml`、`docs/work/rolling-plan.md` 与 active pointer 分别提供当前事实、近期候选和唯一 active manifest。
3. `docs/work/active-work-package.md` 选择唯一 active manifest；完整闭包只读取它指向的 `docs/work-packages/<id>.md` frozen manifest，以及 Root 签发的单个 Task Envelope。选择器不得复制 manifest envelope。
4. 与任务直接相关的实现规范：`05–11`、`14` 或对应 `docs/architecture/**` / `docs/governance/**` owner。
5. 相关公共类型、builder、contract test。
6. 只有上述结构化合同不足时才下钻实现源码；不得默认扫描整个仓库。

禁止把 `docs/superpowers/**`、`docs/archive/**`、历史 PR 描述或外部 provider 输出当作当前实现事实。

### 1.1 上下文分层与停止条件

自主开发上下文按职责分层，不维护万能提示词：

```text
live repository / GitHub evidence          每轮刷新，只回答“现在是什么”
→ authority docs                           维护产品、架构与阶段事实
→ AGENTS.md / 本文                         维护长期 operating contract
→ active Work Package pointer              只选择一个 frozen manifest
→ frozen Work Package manifest             冻结本次 DAG、scope、owner 与 Gate
→ one Task Envelope                        只描述一个 worker 的单一交付
→ relevant types / tests / source          按需装载实现细节
→ Evidence V2 + merge gate                 机器裁决交付是否可信
```

聊天、Issue、PR body、Completion Report 和 Agent 摘要都只是恢复线索，不得成为上述任何一层的替代事实源。Worker 在 acceptance 与 focused tests 满足后必须停止；新的风险、seam 或任务只能交还 A0 重算 DAG，不能通过继续追加上下文自行扩张 scope。

### 1.2 三个近期控制面的生命周期

- `docs/work/current-state.yaml` 只保存 live resolver配置与不依赖当前 publication identity的稳定事实。当前 `main`/tree、开放 PR/Issue、CI/Review和 active resolution必须通过 `bun scripts/codex/document-control-plane.ts status --json`运行时解析；命令输出才是 current-state 的 resolved view。文件与 resolved view都不得保存未来工作、acceptance、Gate步骤或 Gate prerequisite。
- `docs/work/rolling-plan.md` 保存条件化的当前包摘要与后续二到五个候选，并引用本节的统一重算 taxonomy。它不证明任务已执行，也不要求为每次 merge 追加一个只更新 SHA 的递归 closeout；live resolver返回`none`后，A0直接从最新 resolved facts重算下一包。
- `docs/work/active-work-package.md` 是条件选择器，只保存 manifest path、manifest 的 **Git blob bytes SHA-256** 与选择模式。共享 resolver核对 live platform default head、本地 default ref与candidate/default blob：候选 digest一致且 default branch尚不包含同 path + digest时解析为唯一 manifest；default branch已包含同一 digest时解析为`none`。default ref不可解析或不新鲜时为`unresolved`，candidate digest不匹配时为`invalid`；所有非 active/none异常状态一律 fail-closed。完整 envelope只在所选 `docs/work-packages/<id>.md`。

这三个文件不得保存当前候选最终 commit、当前候选 PR number、最终 Review/CI 或 merge SHA。它们在 candidate tree 中无法无自引用地知道这些值；共享 resolver只在运行时观察这些事实，exact head evidence仍由 Context Capsule绑定。合并后的 live reload可以直接选择下一包，也可以保持`none`；不得为了让已合并 manifest“看起来关闭”再创建同义 post-merge Work Package。测试必须导入共享 resolver，禁止复制 selector算法。

A0 在以下任一事实发生后，必须先刷新 current-state，再从最新 authority/code/evidence 重算 rolling-plan 与 active selector：当前 PR 合并或关闭；相关 SEC/Nexus `main` 变化；新 CI failure、Review blocker、unresolved thread 或 `REQUEST_CHANGES`；architecture/authority/ownership 假设被反证；任务被新实现吸收；Nexus Census 发现新前置条件；用户更新长期 Goal。旧计划不得追加为永久 Backlog，也不得被当成完成证据。

### 1.3 Context Capsule、Task Envelope 与 Reconciliation Delta

A0 为每个 execution batch冻结一个 Context Capsule，至少包含：

```text
base/head + branch
Goal revision + authority refs/revisions
owned/forbidden surface
prerequisite + dependency/reconciliation points
acceptance + required tests
gate_owner + reusable/invalidated evidence
stop condition + reload_if
```

Formal Work Package 的机器 frontmatter只使用当前 parser允许的 schema keys；`branch`、dependency、`gate_owner`、stop、`reload_if`和证据账本写在同一 frozen manifest正文与 Capsule中，不得为方便解析私自扩展 competing schema。每个 worker 的 Task Envelope 必须从 Capsule收窄为一个 task/Issue、current base、branch、architectural goal、ownership、forbidden paths、dependency、acceptance、required tests、`gate_owner` 与 stop condition。

每个 Gate只有一个 `gate_owner`。结果以 `gate_key + tested head + profile` 唯一标识；已有未失效结果必须复用，其他 worker/reviewer只能审计或选择 Gate。每次 reconciliation/stop必须返回 tested head/base、changed files/symbols、public/authority delta、acceptance delta、focused results、reusable/invalidated evidence、new blocker、next ready seam，以及 `inspect_ms`、`implement_ms`、`focused_validation_ms`、`wait_ms`、`reconcile_ms`、`context_reload_count` 与 `duplicate_gate_count`。

## 2. 当前开发主线

**稳定阶段 DAG、阶段依赖与完成定义只以 `03-MVP实施计划与路线图.md` 为权威；当前阶段事实、唯一 active Work Package 与近期执行顺序只以 `docs/work/**` 三个分离控制面为权威。** 本文不维护另一份阶段或优先级列表。

除阻塞性 Bug、CI/性能回归和既有合同修复外，不主动扩张巨型业务 Demo、Workbench 特效、大量文件型 Block 或 ExplainGraph 母图语义。

## 3. 仓库事实与分支生命周期

`main` 是 SEC 唯一正式工程事实。分支是代码演进路线，不是等待合并的功能包。判断变化是否仍应进入主干时，必须交叉检查当前代码、真实 diff、base/head、merge-base、ahead/behind、verification evidence、review thread 和有效 `REQUEST_CHANGES`；不得仅依据分支名、PR body 或历史计划。

Squash merge 后必须区分**代码内容已进入 main**与**原 commit ancestry 已进入 main**。旧分支仍显示 ahead 不代表功能遗漏。

分支职责：

- `feat/*`：新增正式产品能力。
- `fix/*`：修复正式产品缺陷。
- `refactor/*`：不改变外部语义的结构重构。
- `docs/*`、`chore/*`：文档与工程维护。
- `spike/*`：大型未知架构探索，默认禁止直接合并；结论成立后提炼为正式产品变化。
- `integration/*`：仅在两条真实、并行、规模较大的产品演进线需要系统拼装时使用；完成验证后及时收口。
- `validation/*`、`diagnostic/*`：验证、故障隔离、日志和实验事实，默认禁止合并。

禁止长期创建 `validation/case-XX`、`final-exact-*`、`current-*` 等一次性远端测试分支。测试参数、suite 分片和证据采集由 Verification Contract、正式 runner、artifact、status 与日志承担；不得继续把 Git branch 当 CI 参数载体。

一个变化只有同时满足以下条件，才考虑进入 `main`：

1. 承载仍有效的产品能力、缺陷修复或必要工程维护。
2. 当前 `main` 尚未包含其有效结果。
3. 没有被更新、更完整的实现取代。
4. 与当前权威架构一致，或同步修正权威设计。
5. Required Verification Contract 已由可信 executor 实际执行通过，evidence/status 绑定的 exact head SHA 等于待合并 PR 当前 head SHA，且该 PR head 不落后于当前 base。
6. 无未解决 review thread 和有效 `REQUEST_CHANGES`。
7. 已理解提交关系和冲突边界。
8. 不包含临时 probe、日志采集驱动、旧 snapshot 或无意生成物漂移。

大型 integration 历史存在大量实验和验证 commits 时，最终验证通过后优先 squash merge，把经过验证的最终状态作为清晰主干变化。不得为了保留过程噪声污染 `main`。

PR 完成后必须确认产品结果是否真实进入目标分支，关闭废弃、镜像、probe 和 diagnostic PR；工具允许时删除完成使命的远端临时分支和已合并 head branch，并删除 retired diagnostic workflow 与一次性工程入口。工具不支持物理操作时必须准确报告边界，不得把“已审查”“已关闭”“内容已包含”写成“已删除”。

Git branch 负责代码演进路线；Verification Contract 定义门禁；GitHub Actions 是当前 hosted executor 之一，不是验证事实本身的唯一权威。

### 3.1 短反馈开发循环

开发单位是可审查的纵向切片，不是“继续开发整个 SEC”。每个 Task Envelope 执行：

```text
inspect owned seam
→ implement one observable capability or invariant
→ focused local validation
→ commit / update Draft PR and Completion Report
→ stop at the declared reconciliation point
→ A0 refreshes main/review/evidence and schedules the next ready node
```

Draft PR 用于让 diff、head/base、ownership、当前阶段和 blocker 持续可见，但不构成 authority、验证证据或 merge 授权。探索与合同冻结使用 proof mode；合同已经冻结后的实现、测试和机械修复使用 throughput mode。不得在 throughput mode 重新设计 canonical type、revision algorithm、状态机或 authority。

### 3.2 冻结交付点验证

SEC 的 WebChat Worker 可以在任务分支连续提交，但开发过程中的 `push`、PR `opened`、`synchronize`、`ready_for_review` **不得自动消耗 hosted runner**。

Worker 完成 Task Envelope 后：

```text
READY_FOR_INTEGRATION
→ 停止修改
→ A0 静态审查 diff / ownership / dependencies / review
→ rebase current main，并把最终状态 squash/amend 为 current base 上的单一提交
→ 冻结 Work Package、exact PR head SHA、current base SHA 与 manifest raw digest
→ 触发一次 sec-scope-attest-v1 repository dispatch
→ 选择 quick 或 full，触发一次 sec-verify-frozen-v1 repository dispatch
→ 读取 exact-head/current-base attestation、Evidence V2 与 sec/merge-gate
→ merge 或返回 Worker 修复
```

当前 PR hosted verification 不使用 `run-quick` / `run-full` label，也不由 `synchronize` 自动触发。两个 repository dispatch 只由 A0 在 frozen reconciliation point 发出；GitHub 从 default branch 装载受信 workflow，heavy runner 只读 checkout exact head，禁止 head workflow 或脚本自行发布 required status。

A0 在触发前必须计算：

```text
PR verification key
= head SHA
+ current PR base SHA
+ Work Package manifest raw digest
+ verification profile
+ CI verification contract revision
```

Release/full ref verification 不依赖 PR diff，因此 key 为 exact head SHA、full profile 与 contract revision。

当前 verification revision、artifact namespace、selector 与 Evidence schema 只由 `platform/shared/ci-contract.ts` 及其受信消费者解析；本文不复制会随 bootstrap 变化的版本值或历史迁移记录。稳定不变量是：frozen head必须满足当前 base/parent合同，PR head、base、manifest、profile或 revision变化会使旧 evidence失效，命中 verifier trust root 的 candidate 不能用自身实现自证。完整 lane、Evidence 与人工 bootstrap 合同见 `docs/test-feedback-and-ci-lanes.md`。

Draft PR 是早期可见性与短反馈载体，不进入 executable merge-gate matrix。`plan-revalidation` 必须把选中的 Draft-only head 置为 failure，只为唯一的非 Draft same-repository head 分配 runner；共享同一 head 的多个 open PR 必须确定性 failure 且不得分配 runner。正常存在的 Draft PR 不得使 `push / schedule` 全局 revalidator 失败。

Tracked Work Package 的最终 phase 是 `frozen`。`merge-ready` 只能由外部 exact-head scope attestation、Evidence V2、live PR/base 状态、review 状态与 ruleset 推导，不能在验证后再修改 tracked manifest 来宣称 ready。

### 3.3 Actions 经济性约束

GitHub-hosted Actions 的优化目标是：

```text
最小化 billed runner processing
subject to Required Verification Contract 完整满足
```

因此：

- PR 只在 A0 显式发出 `sec-verify-frozen-v1` repository dispatch 时启动昂贵验证；普通 push、PR 事件与 synchronize 不启动 hosted runner。
- scope attestation 先于 heavy verification；两者都绑定 exact base/head/manifest，重复 dispatch 不是日常重试机制。
- 在 checkout/setup/install 前校验 default-branch workflow identity、A0 actor permission、same-repository、current base freshness、单 parent、manifest digest 与 verifier trust-root blob；任一不满足直接拒绝。
- 单个 verification profile 使用一个 hosted runner，只 checkout/setup/install 一次。
- slow suites 在同一 runner 内复用 bounded concurrency；runtime-heavy suites 保持串行隔离。
- release full 不使用 file-granular matrix runners重复 setup/install。
- 不运行无代码变化的 daily full schedule。
- 每 6 小时只运行轻量 merge-gate revalidator，检查 artifact TTL 与 live metadata；它不 checkout PR head，也不运行任何测试。
- 不通过删除测试、跳过失败 gate 或扩大 timeout 伪造经济性。
- 未映射 changed file / impact source 不允许静默视为无测试；hosted verification 必须 fail closed。

## 4. 实现规则

每项改动必须先回答：

- 权威输入是什么？
- canonical state 是什么？
- 输出是 canonical、artifact、evidence 还是 projection？
- 哪个模块拥有写权限？
- 是否确定性、可重入？
- 哪些不变量需要测试？
- 是否新增第二事实源？

### Compiler API

`platform/**` 的非 compiler 模块必须通过 `platform/compiler/index.ts` 使用 compiler 公共 API。不得穿透导入 compiler 子目录。

### 代码生成

Compose/Lowering 生成 `.ts`/`.tsx` 时使用 `CodeBuilder` 或正式 Generator API。不得继续扩张大段模板字符串代码生成。

### IR

- IR 类型以 `14` 和 `platform/shared/engineering-ir-types.ts` 为权威。
- Entity/Fact ID 必须稳定、确定性。
- Builder 输出必须稳定排序。
- 不把 UI 字段、布局坐标、视觉颜色写入 IR。
- ExplainGraph、SemanticView 只从 canonical state 投影。

### AI/External Evidence

AI 推断和 Graph-It-Live/GitNexus/Graphify 结果只能进入 inferred/evidence 层。不得自动升级为 authoritative fact，也不得扩大 allowed paths。

外部工具的 Discovery、A/B、路由、Evidence升格、数据边界、版本与退役只由 `docs/governance/external-capability-and-provider-policy.md` 和 ledger拥有。本文只消费其路由结论：Direct/Daily Context/Architecture/Security模式按任务切换，重叠 Provider不同时常驻；任何未完成 repository-specific benchmark/decision 的候选都不是默认 authority。Graph结果必须回到 current source、exact diff、compiler/tests和适用运行证据复核。

## 5. 修改顺序

新增公共能力按以下顺序执行：

```text
1. 修改权威规范
2. 定义公共类型/Schema
3. 写失败测试或不变量测试
4. 实现纯 builder / pass
5. 接入 facade / orchestrator
6. 接入 artifact / projection / CLI（如需要）
7. 完成 focused local/branch checks并交付 frozen head
8. 由 A0 触发 required verification profile
9. 删除旧重复路径或明确兼容边界
```

不得先改 Workbench 再反推 IR Schema。

## 6. Issue 分类

| 类型 | 含义 | 默认处理 |
| --- | --- | --- |
| Spec | Authoring/Contract 不完整或冲突 | 人工或明确 Semantic Mutation |
| Semantic | IR 不变量、Fact 冲突、identity/provenance 问题 | 修 Semantic Frontend/IR |
| Composition | Block/Generator/Lowering/安装错误 | 修 compiler 或 Block metadata |
| Synthesis | AI/Slot/受限生成结果不满足合同 | Task Envelope 内修复 |
| Verification | 测试、Policy、Acceptance、Drift 失败 | 结构化归因后 repair |
| Kernel | 性能/正确性/基础设施问题 | 维护者处理 |

## 7. 测试与验证策略

- 纯 IR builder/index/selector：`tests/unit`。
- 公共 IR/CLI/JSON shape：`tests/contract`。
- Workspace → IR → projection：`tests/integration`。
- 浏览器只保留生成运行时 smoke；不把 IR 业务矩阵塞入 Playwright。

本地/Worker focused 入口：

```bash
bun run check:affected
bun run check:fast
bun run check:full
```

Hosted verification 入口由 A0 触发：

```text
repository_dispatch: sec-scope-attest-v1
→ default-branch trusted scope attestation artifact

repository_dispatch: sec-verify-frozen-v1(profile=quick|full)
→ scripts/ci-verification.ts --profile <profile> --expected-head <exact SHA>
→ exact-head Evidence V2 artifact
→ default-branch sec/merge-gate
```

`platform/shared/ci-contract.ts` 是 CI logical gates、workflow execution model、repository-dispatch type 与 verification revision 的 canonical contract。`platform/shared/test-impact-contract.ts` 是 source ownership → required test impact 的 canonical contract。

验证信任根包括 verification workflows、`scripts/ci-*`、相关 `platform/dev-runner/**` / `platform/shared/ci-*`、V1 CI changed-path canonicality、active-documentation/test budget/impact contract、Evidence writer、Work Package parser、merge gate 与依赖入口。普通 PR 不得修改这些路径后使用同一 revision 自证通过；此类变化必须建立新 Bootstrap Work Package、升级 revision，由旧 base/人工 integration 验证后进入 `main`。Mandatory sentinel 只决定额外测试，不扩大授权。

## 8. 完成报告

Agent 完成任务时只报告：

- 改了什么 canonical/contract 边界。
- 关键不变量。
- 实际运行的测试结果。
- 尚未实现或仍是规划的部分。

禁止把未运行的测试写成“通过”，禁止把文档设计写成“已实现”。
