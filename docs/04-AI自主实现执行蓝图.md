# AI 自主实现执行蓝图

本文约束**参与 SEC 仓库开发的自主编码 Agent**，定义上下文装载、计划、任务分解、并行协作、验证与收口方式。产品内 AI Runtime、Task Envelope 的产品语义与权限模型仍以 `docs/09-AI Runtime、任务信封与治理规范.md` 为权威。

本文不维护当前产品阶段、当前 Work Package 结论或具体实现协议：当前阶段与顺序以 `docs/03-MVP实施计划与路线图.md` 为准；实现协议以 `docs/05–14` 为准；测试与 CI 以三份测试权威文档及代码合同为准。

## 1. 上下文工程分层

SEC 不使用一个不断膨胀的“万能提示词”。上下文按职责分层，每项事实只有一个 canonical owner：

| 层 | 位置 | 职责 | 不得承载 |
| --- | --- | --- | --- |
| 工程事实 | latest `main`、真实代码、测试、PR/Issue/review/CI | 当前仓库状态与可验证证据 | 未核验的历史结论 |
| 产品与架构 authority | `docs/00–14`、测试权威文档 | 产品、架构、协议、状态机、测试语义 | 当前任务进度 |
| 长期 Agent contract | `AGENTS.md` | 每轮都必须遵守的稳定仓库规则 | 当前阶段、临时 SHA、一次性 blocker |
| 自主开发方法 | 本文 | 上下文装载、计划、并行、验证、收口 | 产品内 AI Runtime 协议 |
| 计划元合同 | `PLANS.md` | 非平凡 Work Package 的计划格式、触发与更新协议 | 当前路线图、产品合同 |
| 当前执行计划 | `docs/work-packages/<id>.md` | 单个 active Work Package 的 DAG、ownership、evidence 与 closeout | 覆盖 `03`、`05–14` 或测试 authority |
| 可复用工作流 | `.agents/skills/*/SKILL.md` | 审计、规划、架构变化、验证、CI、收口流程 | 重复产品事实或角色人格 |
| 有界角色 | `.codex/agents/*.toml` | 只读审查或单一 Task Envelope 执行责任 | 路线图和跨任务长期记忆 |
| 单次任务 | Root 给 worker 的 Task Envelope | 当前目标、范围、禁止项、验收和停止条件 | 全仓长期规则的复制品 |
| 状态表面 | Issue、PR body、Completion Report | exact refs、讨论、阶段、证据链接、remaining gaps | 唯一架构或执行计划 |
| 机器门禁 | types/schema、tests、Contract Freeze、lint、CI | 可机械判定的不变量 | 仅靠自然语言提醒的关键正确性 |

同一种指令应按以下方式归位：

```text
长期稳定规则       → AGENTS.md / 本文
重复执行流程       → Skill
角色与权限边界     → custom agent
当前复杂变化       → Work Package plan
产品或架构事实     → 对应 authority
可机器判定的不变量 → type/schema/test/Gate
一次性目标         → Task Envelope
```

禁止在多个位置复制完整字段表、状态机、命令矩阵或当前任务清单。引用 canonical owner，而不是维护多个近似版本。

## 2. 每轮任务的装载顺序

Root A0 在规划、继续开发、合并或收口前按顺序建立 context packet：

1. 读取 latest `main`、default branch、工作树或远端 head 的 exact SHA。
2. 读取 open PR/Issue、相关 branch base/head/merge-base、真实 diff、review thread、review submission、CI/status 与有效 evidence。
3. 读取 `AGENTS.md`、`docs/00-文档索引与一致性规则.md`、`docs/03-MVP实施计划与路线图.md` 和本文。
4. 读取与任务直接相关的 `docs/05–14`、公共类型、canonical producer/facade 与 contract/invariant tests。
5. 若存在 active Work Package，读取唯一 `docs/work-packages/<id>.md` 和 `PLANS.md`。
6. 只装载本轮实际需要的 Skills 与 custom agents；不要为了“完整上下文”把全部说明塞入任务。
7. 只有结构化合同不足以回答问题时才继续下钻实现源码、历史 ADR 或外部 evidence。

`docs/archive/**`、`docs/superpowers/**`、历史 PR 描述、Completion Report、聊天和外部 provider 输出只可用于追溯或提出候选假设，不得覆盖 current authority、代码和测试。

### 2.1 先审计，后决定是否修改

出现“继续”“持续开发”“解决全部问题”“收口”时，先执行仓库审计并重新计算 DAG。正确动作可能是：

- 继续当前单写者实现；
- 补齐 authority 或 Work Package plan；
- 修复 review/CI blocker；
- 运行仍缺失的最小验证；
- merge、close、archive 或删除临时结构；
- 确认当前状态已经满足门禁，不制造新改动。

不得根据 branch name、PR body、ahead/behind 数量或旧计划自动推断功能遗漏。Squash merge 后必须区分产品结果已进入 `main` 与原 commit ancestry 未进入 `main`。

## 3. 计划与任务切片

### 3.1 路线图与 Work Package

`docs/03-MVP实施计划与路线图.md` 只负责当前阶段、唯一顺序、进入/退出条件；它不展开每个实现 commit。

满足 `PLANS.md` 触发条件的变化必须建立唯一 active Work Package plan。计划按可验证能力和 prerequisite 组织，不按“待修改文件”组织。每个里程碑必须有：

- prerequisite；
- owned files/symbols 与 forbidden scope；
- architectural goal；
- focused acceptance；
- required evidence 与 invalidation；
- reconciliation point；
- failure/recovery/rollback 条件。

计划是活文档。base/head、authority、review blocker、设计裁决或证据状态变化时，由 Root 更新当前事实、Progress 和 Decision Log；不得把完整聊天和已推翻猜测堆入计划。

### 3.2 一个 Task Envelope 只交付一个结果

正式实现 worker 的 Task Envelope 必须包含：

```text
task / Issue
current base and expected head
architectural goal
owned files and canonical symbols
forbidden paths and non-goals
prerequisites and reconciliation seam
acceptance
required tests/evidence
stop condition
```

Worker 不拥有全仓路线图，不自行扩大 canonical surface。完成一个有边界的里程碑后，执行 focused validation、提交、更新 Draft PR、留下 Completion Report 并停止；Root 再决定下一里程碑。

## 4. Root A0、Skills 与 custom agents

Root 是唯一 A0 Integrator，负责仓库事实、DAG、single-writer ownership、计划、验证、merge、closeout 与 branch hygiene。

### 4.1 Skills

仓库级 Skills 位于 `.agents/skills/`：

| Skill | 触发场景 | 主要输出 |
| --- | --- | --- |
| `sec-repo-audit` | 规划、继续开发、合并判断、收口前 | exact repo facts、ownership collision、下一动作 |
| `sec-work-package-plan` | 跨模块、高风险、多里程碑变化 | 唯一 Work Package plan |
| `sec-architecture-change` | canonical IR、identity、transaction、recovery、权限等变化 | owner、contract、不变量、迁移与 DAG |
| `sec-verification-evidence` | 需要判断验证覆盖、复用、失效和最小 rerun | evidence matrix |
| `sec-ci-triage` | GitHub Actions 或 Gate 失败 | 根因、最小修复和后续 Gate |
| `sec-pr-closeout` | merge、supersede、close 或仓库收口 | merge/closeout 裁决与清理清单 |

Skill 只拥有流程，不复制 authority。触发描述必须同时说明适用和不适用场景；流程稳定后再固化，避免把一次性任务包装成永久 Skill。

### 4.2 custom agents

`.codex/agents/*.toml` 提供有界角色：

- `repo-state-auditor`：只读仓库事实审计；
- `architecture-reviewer`：只读 authority、ownership 与 DAG 审查；
- `verification-evidence-reviewer`：只读 evidence freshness 与 rerun 选择；
- `integration-reviewer`：只读 assembled state 与退出条件审查；
- `implementation-worker`：执行一个明确 Task Envelope。

只在任务真实独立时 spawn；不要为了占满线程固定启动全部角色。保持 delegation depth 为 1，普通 worker 不再递归分派。

### 4.3 单写者与并行方式

以下 surface 默认保持单写者：canonical type、identity/revision algorithm、builder/producer、state machine、public facade、Pipeline stage order、authority 章节和 Contract Freeze registry。

并行优先用于：

- read-only architecture/integration/evidence review；
- owned files、canonical symbols、authority 章节完全不重叠的独立实现；
- 独立 worktree 中的正式变化。

两个 agent 不得同时修改同一 canonical surface。共享 seam 变化回到 Root 串行裁决，不机械创建 `integration/*` 拼装。

## 5. 分支、worktree 与进度可见性

分支是代码演进路线，不是 CI 参数或“等待合并的功能包”：

- `feat/*`：新增正式产品能力；
- `fix/*`：修复正式产品缺陷；
- `refactor/*`：不改变外部语义的结构重构；
- `docs/*`、`chore/*`：文档与工程维护；
- `spike/*`：大型未知架构探索，默认不直接合并；
- `integration/*`：仅用于两条真实、并行、规模较大的产品线总装；
- `validation/*`、`diagnostic/*`：验证和故障隔离，默认不合并。

独立写入任务使用独立 branch/worktree；只读 reviewer 可针对同一 exact head 并行。禁止长期创建 `validation/case-*`、`final-exact-*`、`current-*` 等远端测试分支；suite 参数和证据采集由 runner、matrix/job、artifact、status 与日志承担。

预计超过一个 focused cycle、触及 authority、需要 slow/full evidence 或并行 reviewer 的变化，在第一个可审查提交后建立或更新 Draft PR。Draft PR 用于暴露真实 diff、head/base、ownership、当前 phase、evidence 和 remaining gaps；它不是工程事实，也不自动授权 hosted CI 或 merge。

## 6. 架构与实现协议

每项改动先回答：

- 权威输入和 canonical state 是什么？
- 谁拥有写权限和生命周期？
- 输出是 canonical、artifact、evidence 还是 projection？
- identity/revision 是否稳定、确定性？
- 是否可重入、幂等、并发安全？
- error、rollback、recovery 路径是什么？
- 哪些不变量由测试锁定？
- 是否新增第二事实源、旁路或职责泄漏？

新增公共能力的默认顺序：

```text
authority decision
→ public type/schema/state machine
→ failing invariant/contract test
→ pure builder/kernel
→ facade/orchestrator integration
→ consumer/projection migration（如需要）
→ focused validation
→ required verification
→ remove duplicate path / freeze compatibility
→ closeout
```

长期维护以下原则：

- Engineering IR、Entity/Fact identity、Semantic Contract/Responsibility 保持 canonical；
- lowering、projection、reference/fixed-point 和排序保持确定性；
- Pipeline transaction 与其他业务 transaction/recovery 不因名称相似而复用职责；
- provenance、ExplainGraph、ReviewSummary、SemanticView 都是明确投影，不成为第二套 IR；
- Workbench/AI mutation 不能绕过 source ownership、permission、CAS、Impact 和 Verification；
- `platform/**` 的非 compiler 模块通过 `platform/compiler/index.ts` 使用公共 Compiler API；
- IR 类型以 `docs/14-Engineering IR与语义事实规范.md` 和 `platform/shared/engineering-ir-types.ts` 为准；
- AI 推断和外部 graph/provider 结果只能进入 inferred/evidence 层，不能自动升级为 authoritative fact。

重复出现同类问题时，检查 shared abstraction、contract、identity/revision boundary、state ownership、lifecycle、deterministic normalization、test architecture 和 CI Gate；不得持续做同类局部补丁。

## 7. 验证与 Actions 经济性

验证结论必须绑定：

```text
tested head
current base
verification profile
contract revision
Gate/command
scope
result
duration/artifact
invalidation rule
```

旧结果不得伪装成新 head 的 exact-head 结果。允许复用“已验证 baseline + intervening diff impact + delta focused validation”，但必须证明 diff 没有使原 evidence 失效。

本地/worker 从最小相关 Gate 开始：

```bash
bun run typecheck
bun run docs:doctor
SEC_IMPORTS_CHANGED_ONLY=1 SEC_CHANGED_BASE=<base> bun run imports:check
bun test <focused tests> --timeout 180000
bun run check:affected
bun run reference:check
```

只运行被当前 diff 要求的集合，不把列表理解为每次全跑。

Hosted verification 由 Root 根据缺失 evidence 显式触发：

- `run-quick`：正式 PR 默认交付验证，执行 affected/risk contract；
- `run-full`：broad-risk、release、canonical contract/pipeline/test infrastructure 大范围收口。

PR verification key 为 exact head SHA、current base SHA、profile 与 CI verification contract revision。当前 contract revision 以 `platform/shared/ci-contract.ts` 为准；测试 impact 以 `platform/shared/test-impact-contract.ts` 为准。head/base 变化或 contract revision 变化后，旧 evidence 按其 invalidation rule 失效。

失败后读取具体 Gate 和 failure tail，修共同根因并运行最小 sentinel。禁止未诊断就反复 rerun、扩大 timeout、删除测试、跳过 Gate 或把 environment 猜测写成已确认。

## 8. Merge 与仓库收口

一个变化只有同时满足以下条件，才考虑进入 `main`：

1. 仍承载有效产品能力、缺陷修复或必要维护；
2. `main` 尚未包含同等结果；
3. 未被更新、更完整实现取代；
4. 与 authority 一致，或同步修正 authority；
5. Required Verification Contract 对 exact head/current base 实际满足；
6. 无 unresolved review thread 和有效 `REQUEST_CHANGES`；
7. 已理解 base/head、merge-base、ahead/behind 与冲突关系；
8. 不包含 probe、诊断日志、旧 snapshot、无意 artifact drift 或一次性 workflow。

大型 integration 历史包含大量实验噪声时，最终验证后优先 squash merge。门禁满足后及时收口，不为了表现“仍在开发”继续修改正确代码。

完成后：

- 确认产品结果真实进入目标分支；
- 关闭或准确标记 superseded/absorbed/obsolete 的 PR 与 Issue；
- 工具允许时删除完成使命的临时 branch 和 retired workflow；
- 将 Work Package 长期事实归位到 authority，归档或删除 active plan；
- 重新读取新 `main`、open PR/Issue 与 CI 状态；
- 工具不支持的物理操作明确列为未完成，不得改写成已经删除或清理。

## 9. 提示词与决策的持续改进

Codex 出现错误时，先分类，再归位：

```text
单次目标或上下文缺失   → 修 Task Envelope
长期稳定规则缺失       → 修 AGENTS.md / 本文
重复工作流不稳定       → 先改流程；稳定后修 Skill
角色职责或权限不清     → 修 custom agent
产品/架构事实冲突      → 修对应 authority
当前复杂变化失去上下文 → 修 Work Package plan
可机械判断却重复出错   → 加 type/schema/test/Gate
```

审计、架构裁决、方案优化或验证策略只要具有持续工程价值，就必须在同一变化中精炼后归位到 repository Markdown 或机器合同。Issue、PR body 和聊天只引用结果，不保留唯一事实。

Skill 或规则变更应至少检查：

- should-trigger 与 should-not-trigger 场景；
- authority 是否重复；
- path 和 name 是否可被 Codex 发现；
- 是否能由机器校验；
- 是否产生与当前 active Work Package 的 ownership 冲突。

## 10. Issue 分类与完成报告

| 类型 | 含义 | 默认 owner |
| --- | --- | --- |
| Spec | Authoring/Contract 不完整或冲突 | 对应 authority |
| Semantic | IR 不变量、Fact、identity/provenance 问题 | Semantic Frontend/IR |
| Composition | Block/Generator/Lowering/安装错误 | Compiler/Block owner |
| Synthesis | AI/Slot/受限生成不满足合同 | Task Envelope 内 worker |
| Verification | Policy、Acceptance、Drift、Gate 失败 | Verification/CI owner |
| Kernel | 性能、正确性、基础设施缺陷 | 核心维护者 |

Completion Report 只报告：

- 实际改变的 canonical/contract/operational boundary；
- 根因与关键不变量；
- exact head/base 和实际运行的验证结果；
- 文档、计划和收口状态；
- 尚未实现、未运行或工具无法完成的部分。

禁止把未运行测试写成通过、把文档设计写成已实现、把 Draft PR 写成 merge-ready，或把“已审查/已关闭/内容已包含”写成“分支已删除”。
