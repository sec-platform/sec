## 2. 全局实现原则

- 优先实现可重复执行的编译链，不优先实现大而全功能。
- 不允许把系统做成自由 chat 式整仓改写工具。
- 解析、求解、安装、锁定、验证这些基础 pass 必须尽量确定性完成。
- AI 只在 `Align`、`Synthesize`、`Repair` 三个 pass 的受控子任务中参与。
- 任何新增能力都必须明确：
  - 输入来自哪里
  - 输出写到哪里
  - AI 是否允许写入
  - 通过什么测试与验收

### 后续 AI 角色预告

- `v0.1`
  - 只启用 `Slot Synthesis` 能力
- `v0.2+`
  - 增加 `Interface Alignment Agent`
  - 负责 pin 连通性检查、slot 缺口发现、adapter 建议
- `v0.2+`
  - 增加 `Repair Agent`
  - 负责基于失败项生成局部修复任务

### Agent 上下文获取规则

- Agent 默认必须先读取结构化工程对象：`app.plan.yaml`、`graph.lock.json`、相关 `block.manifest.yaml`、slot task、acceptance、verification report、provenance / explain graph。
- 只有当结构化对象无法回答目标文件、符号、测试、来源或失败定位时，才下钻读取源码。
- 禁止把“搜索整个仓库”作为默认第一步；搜索范围必须由 block、slot、acceptance、provenance 或失败报告缩小。
- 对于修改任务，Agent 必须先确认：问题属于 spec issue、composition issue、slot issue 还是 kernel issue。
- 对于 slot/repair 任务，Agent 只能读取任务信封列出的上下文和必要邻近类型，不得引入无关历史对话或大面积源码。

### 执行交互原则

- 任务优先，聊天辅助：Agent 的主输入应是任务、slot、失败项、升级计划或验收缺口，而不是开放式聊天请求。
- 视图优先，源码可达：Agent 应优先产出图谱、来源、覆盖率和风险解释；必要时提供源码路径和最小 diff。
- 默认保守推进：没有明确提升阶段时，不实现后置体验层、托管层、多目标栈或自维护能力。

## 5. 阶段执行顺序

### P0：接口与目录冻结

- 目标：
  - 冻结最小 compile contract。
  - 冻结目录边界与命令壳。
- 必须实现：
  - `app.plan.yaml` schema。
  - `block.manifest.yaml` schema。
  - `graph.lock.json` schema。
  - 目录布局。
  - CLI 命令壳。
- 连续切口：
  - parser 能读取最小 plan。
  - manifest loader 能读取最小块集合。
  - lock writer 能输出空实现级别锁文件。
- 验证口径：
  - parser/resolver 基础单测。
  - `tests/cli.test.ts` 的最小 init/resolve 用例。
- 完成定义：
  - 可以解析一个最小 `app.plan.yaml`。
  - 可以读取至少三个官方块 manifest。
  - 可以输出空实现级别的 `graph.lock.json`。

### P1：Resolver

- 目标：
  - 建立确定性依赖求解与冲突判断。
- 必须实现：
  - `requires`。
  - `provides`。
  - `conflicts`。
  - `installOrder`。
- 连续切口：
  - capability 收集。
  - requires 匹配。
  - conflicts 阻断。
  - install order 固定化。
- 验证口径：
  - `tests/pipeline.test.ts`。
  - `tests/registry.test.ts`。
- 完成定义：
  - 能识别依赖缺失。
  - 能识别显式冲突。
  - 能输出固定安装顺序。

### P2：Composer

- 目标：
  - 把 lock 中的确定性结果落成真实项目资产。
- 必须实现：
  - 复制块文件。
  - 合并基础依赖。
  - 生成路由或注册表。
  - 生成 slot 骨架。
- 连续切口：
  - install plan 生成。
  - 文件复制与冲突检查。
  - generated 路由/注册表写出。
  - slot scaffold 写出。
- 验证口径：
  - `tests/project-runtime.test.ts`。
  - `tests/pipeline.test.ts`。
- 完成定义：
  - 三个官方块可装入空项目。
  - `source/slots/customer_normalizer.ts` 自动生成 slot 源码实现。
  - `custom/customer_normalizer.ts` 由 compiler 物化为 v0.1 runtime target。
  - generated 路由/注册表进入 `generatedPaths`。

### P3：官方块

- 目标：
  - 建立最小官方块母库，并确保组合可安装。
- 基线顺序：
  1. `auth/basic-session`
  2. `tenant/basic-workspace`
  3. `entity/customer-basic`
- `v0.2` 扩展顺序：
  1. `ticket/basic`
  2. `reporting/ticket-summary`
  3. `audit/basic`
  4. `notify/email-basic`
  5. `export/csv-basic`
  6. `rbac/basic`
  7. `table/filter-search`
  8. `file/upload`
  9. `infra/postgres`
- 验证口径：
  - `tests/expanded-blocks.test.ts`。
  - 相关块级 unit/integration。
- 完成定义：
  - 基线三块能独立通过基础测试。
  - 扩展块可按组合安装并通过 verify。

### P4：Slot Runtime

- 目标：
  - 让 AI 写入受限、结果可验证、边界可审查。
- 必须实现：
  - slot task envelope。
  - writable path enforcement。
  - symbol preservation。
  - 任务执行与结果写回。
- 连续切口：
  - task envelope 生成。
  - allowedPaths 校验。
  - requiredSymbols 校验。
  - 写回前后校验与状态更新。
- 验证口径：
  - `tests/pipeline.test.ts`。
  - slot 相关 unit/acceptance。
- 完成定义：
  - AI 只能写授权路径。
  - 非授权路径写入会被拒绝。
  - slot 结果能进入 verify/lock/provenance。

### P5：Verifier

- 目标：
  - 建立可重复执行的 build/test/acceptance 裁决链。
- 必须实现：
  - `Vitest`。
  - `Playwright`。
  - 最小 build/typecheck。
- 连续切口：
  - unit lane。
  - acceptance lane。
  - report/snapshot 汇总。
- 验证口径：
  - `tests/pipeline.test.ts`。
  - `tests/acceptance-coverage.test.ts`。
  - runtime acceptance 基线。
- 完成定义：
  - 基线 unit 通过。
  - 主验收链路通过。
  - coverage/report 可被后续 repair/explain 消费。

### P6：Lock 与基础来源追踪

- 目标：
  - 让安装顺序、generated 结果、任务状态和来源关系可追踪。
- 必须实现：
  - `graph.lock.json` 最终输出。
  - slot task 状态记录。
  - generated path 记录。
  - provenance 基础写出。
- 连续切口：
  - lock 完整字段。
  - generatedPaths 收集。
  - slot 状态持久化。
  - provenance 基础节点/边。
- 验证口径：
  - `tests/provenance.test.ts`。
  - `tests/explain-graph.test.ts`。
  - `tests/review-summary.test.ts`。
- 完成定义：
  - 可从锁文件复现安装顺序。
  - 可看出 slot 是否已生成、是否已验证。
  - 安装、generated、override、repair、upgrade 有统一来源口径。

## 5.1 CLI 合同

如果实现 CLI，默认每条命令遵守以下合同：

- `platform init`
  - 输入：空目录或初始化目录。
  - 输出：母栈项目骨架、默认 `app.plan.yaml`。
  - 不调用 AI。
  - 默认验证：生成目录与默认 plan。
- `platform add <block-id>`
  - 输入：现有 `app.plan.yaml`。
  - 输出：追加后的 plan 文件。
  - 不改其他业务源码。
  - 默认验证：plan 中新增 block，其他路径不漂移。
- `platform resolve`
  - 输入：`app.plan.yaml` + 所有 manifests。
  - 输出：`graph.lock.json`。
  - 若失败则不允许继续 `compose`。
  - 默认验证：依赖/冲突/安装顺序稳定。
- `platform compose`
  - 输入：`graph.lock.json`。
  - 输出：安装后的块文件、generated 文件、slot 骨架。
  - 不直接做 slot 实现。
  - 默认验证：install plan、generatedPaths、slot scaffold 一致。
- `platform adapt`
  - 输入：slot task envelope 或 repairable task。
  - 输出：指定目标文件实现。
  - 只允许写授权路径。
  - 默认验证：allowedPaths、requiredSymbols、verify pending 状态。
- `platform verify`
  - 输入：当前项目。
  - 输出：build/test/acceptance/policy 结果。
  - 不做自动修复。
  - 默认验证：summary/report/coverage 产物存在。
- `platform repair`
  - 输入：失败结果。
  - 输出：repair task 或 repair patch。
  - 只允许局部修复。
  - 默认验证：repair plan、阻断原因、前后 diff、verify pending 状态。
- `platform upgrade`
  - 输入：当前锁状态 + 目标块版本/迁移定义。
  - 输出：upgrade plan、diagnostics、必要 patch。
  - 必须先做 preflight，再允许执行。
  - 默认验证：migration summary、diagnostics、回滚边界。
- `platform lock`
  - 输入：通过验证的项目状态。
  - 输出：最终锁信息和状态更新。
  - 默认验证：slot/pass/generated 状态同步。
- `platform explain`
  - 输入：锁文件、来源信息、测试结果、policy/repair/upgrade 结果。
  - 输出：graph / provenance / local views 摘要。
  - 默认验证：节点、边、local views 与 summary report 一致。

如果命令语义与上述合同冲突，优先修改实现以贴合合同，而不是修改合同本身。

## 6. 写入边界

### 当前阶段允许 AI 修改

- `custom/`。
- 在明确声明为 AI 任务目标的单一文件。
- repair task 明确授权的局部 patch 目标。
- `overrides/` 中明确授权的人工协作回写目标。
- 解释、报告、generated view 这类由命令确定性产出的生成物。

### 当前阶段禁止 AI 修改

- `app.plan.yaml`。
- `block.manifest.yaml`。
- `graph.lock.json`。
- `prisma/schema.prisma`。
- `package.json`。
- registry 官方块源码，除非当前任务就是修改编译器/registry 本体。
- 任何非任务授权路径。

### 写入前检查

- 先确认任务属于：
  - slot issue。
  - repair issue。
  - kernel issue。
  - report/view issue。
- 先确认 `allowedPaths` 或命令合同是否覆盖目标路径。
- 先确认目标文件是否属于 generated、custom、override 或明确授权源码。

### 后续阶段可扩展

- `overrides/`。
- 明确声明的 repair patch 目标文件。
- upgrade migration 执行目标。
- 经审批的私有 registry block 目标。

## 7. AI 任务模板

每个 AI 任务都必须具备以下字段：

```yaml
taskId: fill_slot_customer_normalizer
taskKind: adapter-slot
targetBlock: entity/customer-basic
targetFile: source/slots/customer_normalizer.ts
sourceSlot:
  runtimeTarget: custom/customer_normalizer.ts
  sourcePath: source/slots/customer_normalizer.ts
allowedPaths:
  - source/slots/customer_normalizer.ts
requiredSymbols:
  - normalizeCustomerInput
forbiddenOperations:
  - modify_other_files
  - add_dependencies
  - access_database
testsToPass:
  - tests/customer_normalizer.spec.ts
  - tests/acceptance/customer-flow.spec.ts
```

### 当前允许的任务类型

- `adapter-slot`
- `repair-patch`
- `upgrade-review`
- `report-enhancement`
- `view-enhancement`

### 每类任务必须补充的字段

- `adapter-slot`
  - `targetFile`
  - `requiredSymbols`
  - `testsToPass`
- `repair-patch`
  - `failureIds`
  - `repairScope`
  - `verifyCommands`
- `upgrade-review`
  - `targetVersion`
  - `migrationTypes`
  - `preflightChecks`
- `report-enhancement`
  - `sourceArtifacts`
  - `expectedFields`
- `view-enhancement`
  - `sourceReports`
  - `targetView`

### 默认禁止的任务行为

- 修改未授权路径。
- 引入新依赖。
- 绕过 verify。
- 直接改 plan/manifest/lock 权威输入。
- 把无结构聊天内容当作权威规范。

如果无法满足这些字段，Agent 不应自行发明替代格式。

## 8. 验收矩阵

### `v0.1` 最低验收

- `resolve` 成功输出锁文件。

- `verify` 成功通过主链路。

- policy violation、override、repair、upgrade 影响面能进入统一摘要。

### `v1` 增量验收

- 私有 registry 可用。
- 图谱与双视图可用。
- 团队 CI 可稳定运行全链。
- 多项目可共享 pack、policy 与 block 资产。

## 9.1 默认块资源布局

每个官方块默认采用以下结构：

```text

  block.manifest.yaml
  files/
    src/
    prisma/
```

默认规则：

- `files/` 存真实安装资产。
- `templates/` 只放需要变量替换的骨架。

## 10.1 自主执行规则

- 默认连续推进，不因“可以有更大路线”而跳过当前阶段出口条件。
- 默认按 `spec/graph/lock -> manifest -> slot/acceptance -> provenance/report -> source` 的顺序定位问题。
- 默认把新增能力落到真实源码、测试和报告中，不创建只存在于聊天或 UI 映射里的虚拟实现。
- 默认优先功能实现，其次补必要测试；不要连续做纯 test-only 加固。
- 每轮应优先选择多个低风险、可验证、彼此衔接的切口，而不是只停在单一小点。
- 每轮完成后应同步更新正式路线图中的当前进度。
- 遇到以下情况才应停下并请求新决策：
  - 高优先级文档之间存在硬冲突。
  - 当前阶段缺少无法推导的外部凭据或运行条件。
  - 用户明确改变母例、技术栈或阶段目标。
  - 需要破坏性操作或影响共享外部状态。
- 遇到以下情况不得停下，应自行选择默认实现：
  - 文件命名细节。
  - 内部模块拆分方式。
  - 单元测试组织方式。
  - 报告输出格式中的非关键字段。

不要跳过前置模块去实现后置体验层。

## 13. 失败处理

- 如果 parse 失败：
  - 停止后续 pass。
  - 输出输入错误。
  - 不允许 AI 自行猜测规范补全。
- 如果 resolve 失败：
  - 停止 compose。
  - 不允许 AI 补救架构级缺失。
  - 输出缺失依赖、冲突或 capability 缺口。
- 如果 compose 失败：
  - 只修安装器逻辑。
  - 不让 AI 重写块意图。
  - 保留 install plan 与失败目标路径。
- 如果 adapt/synthesize 失败：
  - 保留骨架。
  - 标记 slot pending 或 repairable。
  - 输出 requiredSymbols / allowedPaths / verify pending 信息。
- 如果 verify 失败：
  - 优先进入 repair pass。
  - 不进入更大范围修改。
  - 输出 failure points、coverage、policy、runtime 相关报告。
- 如果 repair 仍失败：
  - 返回失败报告和最小 diff。
  - 不扩大写入范围。
  - 要说明为什么不可修和谁需要决策。
- 如果 upgrade preflight 失败：
  - 停止执行 migration。
  - 输出 diagnostics。
  - 不伪造成功升级状态。

## 14. 终局方向提示

在 `v0.2` 之后，Agent 的实现重点应依次移动到：

1. provenance 与 explain 统一归因。
2. repair 与 upgrade 的可审查执行边界。
3. private registry 与团队 artifact 合同。
4. policy center 与 dual-view workspace。
5. second target stack。
6. hosted verification and governance。
7. 分层自举与受控自维护。

终局目标不是“让 AI 从零写完整项目”，而是让 AI 在完整工程编译系统中承担可验证、可回放、可限制的局部职责。
