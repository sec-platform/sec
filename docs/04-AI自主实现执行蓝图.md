## 2. 全局实现原则

- 优先实现可重复执行的编译链，不优先实现大而全功能。
- 不允许做成自由 chat 式整仓改写工具。
- 解析、求解、安装、锁定、验证这些基础 pass 必须确定性完成。
- AI 只在 `adapt`（slot synthesis）和 `repair` 的受控子任务中参与。
- 新增能力必须明确：输入来源、输出位置、AI 是否允许写入、通过什么测试验收。

## 3. 当前默认范围

### 阶段

- 当前实施阶段：`v0.2`（工程可持续化）。
- 主链：`init → add → resolve → compose → adapt → verify → repair → upgrade → lock → explain` ✅
- 治理面：provenance、review、explain、policy、repair、upgrade ✅

### 母例

- 基线：Customer Admin（登录后管理 Customer 的最小后台）。
- 扩展：Work Tracking / Ticket SaaS 最小纵切面。
- 当前推荐演示组合：Customer Admin 基线 + ticket vertical + governance 组合。

### 技术栈

- 编译器本体：TypeScript + Node.js + ESM + CLI-first + 文件系统驱动。
- 目标应用栈：`nextjs-ts-prisma-sqlite`（Next.js + React + Tailwind + Prisma + SQLite + Bun/Node tests + Playwright）。
- Bun 是仓库脚本与测试入口的固定执行器；生成运行时的浏览器验收边界由 Playwright 承担。
- 详见 `05` §0、§0.1。

## 4. AI 角色

- 只启用 `Slot Synthesis`（adapt pass）和 `Repair`（repair pass）。
- AI 不是整仓主控制器，是编译链中的受限 pass。
- Agent 上下文获取规则：
  - 必须先读结构化对象：`source/app.yaml`、`graph.lock.json`、`block.manifest.yaml`、slot task、acceptance、verification report、provenance、explain graph。
  - 只有结构化对象不足以回答时才下钻源码。
  - 禁止"搜索整个仓库"作为默认第一步。
  - 修改前先确认 issue 类型：Spec / Composition / Slot / Kernel。

## 6. 执行交互原则

- 任务优先，聊天辅助：主输入是 task/slot/失败项/升级计划/验收缺口。
- 视图优先，源码可达：优先产出图谱/来源/覆盖率/风险解释。
- 默认保守推进：没有明确提升阶段时，不实现后置体验层。
