## 2. 全局实现原则

- 优先实现可重复执行的编译链，不优先实现大而全功能。
- 不允许把系统做成自由 chat 式整仓改写工具。
- 解析、求解、安装、锁定、验证这些基础 pass 必须尽量确定性完成。
- AI 只在 `Align`、`Synthesize`、`Repair` 三个 pass 的受控子任务中参与。
- 任何新增能力都必须明确：
  - 输入来自哪里
  - 输出写到哪里
  - AI 是否允许写入
  - 通过什么测试与验收

### 后续 AI 角色预告

- `v0.1`
  - 只启用 `Slot Synthesis` 能力
- `v0.2+`
  - 增加 `Interface Alignment Agent`
  - 负责 pin 连通性检查、slot 缺口发现、adapter 建议
- `v0.2+`
  - 增加 `Repair Agent`
  - 负责基于失败项生成局部修复任务

### Agent 上下文获取规则

- Agent 默认必须先读取结构化工程对象：`app.plan.yaml`、`graph.lock.json`、相关 `block.manifest.yaml`、slot task、acceptance、verification report、provenance / explain graph。
- 只有当结构化对象无法回答目标文件、符号、测试、来源或失败定位时，才下钻读取源码。
- 禁止把“搜索整个仓库”作为默认第一步；搜索范围必须由 block、slot、acceptance、provenance 或失败报告缩小。
- 对于修改任务，Agent 必须先确认：问题属于 spec issue、composition issue、slot issue 还是 kernel issue。
- 对于 slot/repair 任务，Agent 只能读取任务信封列出的上下文和必要邻近类型，不得引入无关历史对话或大面积源码。

### 执行交互原则

- 任务优先，聊天辅助：Agent 的主输入应是任务、slot、失败项、升级计划或验收缺口，而不是开放式聊天请求。
- 视图优先，源码可达：Agent 应优先产出图谱、来源、覆盖率和风险解释；必要时提供源码路径和最小 diff。
- 默认保守推进：没有明确提升阶段时，不实现后置体验层、托管层、多目标栈或自维护能力。

默认职责分配：

- `align/*`

- `resolve/*`
  - 只负责依赖、冲突与安装顺序。
- `compose/*`
  - 只负责确定性安装，不直接调用 AI。
- `synthesize/*`
  - 只负责构建 AI 任务、执行任务与写回结果。
- `verify/*`
  - 只负责 build、unit、acceptance 运行和结果汇总。
- `repair/*`
  - 只负责失败定位和局部修复任务生成。
- `emit/*`
  - 只负责写锁文件、来源追踪和解释报告。

## 5. 阶段执行顺序

### P0：接口与目录冻结

必须先完成：

- `app.plan.yaml` schema
- `block.manifest.yaml` schema
- `graph.lock.json` schema
- 目录布局
- CLI 命令壳

完成标准：

- 可以解析一个最小 `app.plan.yaml`
- 可以读取三个官方块 manifest
- 可以输出空实现级别的 `graph.lock.json`

### P1：Resolver

必须实现：

- `requires`
- `provides`
- `conflicts`
- `installOrder`

完成标准：

- 能识别依赖缺失
- 能识别显式冲突
- 能输出固定安装顺序

### P2：Composer

必须实现：

- 复制块文件
- 合并基础依赖
- 生成路由或注册表
- 生成 slot 骨架

完成标准：

- 三个官方块可装入空项目
- `custom/customer_normalizer.ts` 自动生成占位实现

### P3：官方块

按固定顺序实现：

1. `auth/basic-session`
2. `tenant/basic-workspace`
3. `entity/customer-basic`

完成标准：

- 三块能独立通过基础测试
- 三块组合后能被 composer 安装

### P4：Slot Runtime

必须实现：

- slot task envelope
- writable path enforcement
- symbol preservation
- 任务执行与结果写回

完成标准：

- AI 只能写 `custom/customer_normalizer.ts`
- 其他文件写入尝试会被拒绝

### P5：Verifier

必须实现：

- `Vitest`
- `Playwright`
- 最小 build/typecheck

完成标准：

- `customer_normalizer.spec.ts` 通过
- 主验收链路通过

### P6：Lock 与基础来源追踪

必须实现：

- `graph.lock.json` 最终输出
- slot task 状态记录
- 基础 generated path 记录

完成标准：

- 可从锁文件复现安装顺序
- 可看出 slot 是否已生成、是否已验证

## 5.1 CLI 合同

如果实现 CLI，默认每条命令遵守以下合同：

- `platform init`
  - 输入：空目录或初始化目录
  - 输出：母栈项目骨架、默认 `app.plan.yaml`
  - 不调用 AI
- `platform add <block-id>`
  - 输入：现有 `app.plan.yaml`
  - 输出：追加后的 plan 文件
  - 不改其他业务源码
- `platform resolve`
  - 输入：`app.plan.yaml` + 所有 manifests
  - 输出：`graph.lock.json`
  - 若失败则不允许继续 `compose`
- `platform compose`
  - 输入：`graph.lock.json`
  - 输出：安装后的块文件、generated 文件、slot 骨架
  - 不直接做 slot 实现
- `platform adapt`
  - 输入：slot task envelope
  - 输出：指定 slot 目标文件实现
  - 只允许写授权路径
- `platform verify`
  - 输入：当前项目
  - 输出：build/test/acceptance 结果
  - 不做自动修复
- `platform repair`
  - 输入：失败结果
  - 输出：repair task 或 repair patch
  - 只允许局部修复
- `platform lock`
  - 输入：通过验证的项目状态
  - 输出：最终锁信息和状态更新
- `platform explain`
  - 输入：锁文件、来源信息、测试结果
  - 输出：graph / provenance 摘要

如果命令语义与上述合同冲突，优先修改实现以贴合合同，而不是修改合同本身。

## 7. AI 任务模板

每个 AI 任务都必须具备以下字段：

```yaml
taskId: fill_slot_customer_normalizer
taskKind: adapter-slot
targetBlock: entity/customer-basic
targetFile: custom/customer_normalizer.ts
allowedPaths:
  - custom/customer_normalizer.ts
requiredSymbols:
  - normalizeCustomerInput
forbiddenOperations:
  - modify_other_files
  - add_dependencies
  - access_database
testsToPass:
  - tests/customer_normalizer.spec.ts
  - tests/acceptance/customer-flow.spec.ts
```

如果无法满足这些字段，Agent 不应自行发明替代格式。

## 10.1 自主执行规则

- 默认连续推进，不因“可以有更大路线”而跳过当前阶段出口条件。
- 默认按 `spec/graph/lock -> manifest -> slot/acceptance -> provenance/report -> source` 的顺序定位问题。
- 默认把新增能力落到真实源码、测试和报告中，不创建只存在于聊天或 UI 映射里的虚拟实现。
- 遇到以下情况才应停下并请求新决策：
  - 高优先级文档之间存在硬冲突
  - 当前阶段缺少无法推导的外部凭据或运行条件
  - 用户明确改变母例、技术栈或阶段目标
- 遇到以下情况不得停下，应自行选择默认实现：
  - 文件命名细节
  - 内部模块拆分方式
  - 单元测试组织方式
  - 报告输出格式中的非关键字段

不要跳过前置模块去实现后置体验层。

## 13. 失败处理

- 如果 parse 失败：停止后续 pass，输出输入错误。
- 如果 resolve 失败：停止 compose，不允许 AI 补救架构级缺失。
- 如果 compose 失败：只修安装器逻辑，不让 AI 重写块。
- 如果 synthesize 失败：保留骨架，标记 slot pending。
- 如果 verify 失败：优先进入 repair pass，不进入更大范围修改。
- 如果 repair 仍失败：返回失败报告和最小 diff，不扩大写入范围。

## 14. 终局方向提示

在 `v0.1` 之后，Agent 的实现重点应依次移动到：

1. provenance
2. explain / graph
3. upgrade
4. private registry
5. policy center
6. dual-view workspace
7. second target stack
8. hosted verification and governance

终局目标不是“让 AI 从零写完整项目”，而是让 AI 在完整工程编译系统中承担可验证、可回放、可限制的局部职责。
