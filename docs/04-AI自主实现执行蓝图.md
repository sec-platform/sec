# AI 自主实现执行蓝图

本文约束**参与 SEC 仓库开发的自主编码 Agent**。产品内 AI Runtime 以 `09` 为权威。

## 1. 开始任务前

先重新建立 live evidence，再按最小充分上下文顺序读取：

1. latest `main`、open PR/Issue、当前 head/base/merge-base/diff、review 与仍有效 evidence。
2. `00`：确认事实权威位置；`03`：确认当前阶段、active next 与依赖顺序。
3. 当前 Capability Run 的 objective / acceptance / event ledger；现有工具需要时，再读取其最终 `docs/work-packages/<id>.md` frozen projection，以及 Root 签发的单个 Task Envelope。
4. 与任务直接相关的实现规范：`05–11` 或 `14`。
5. 相关公共类型、builder、contract test。
6. 只有上述结构化合同不足时才下钻实现源码；不得默认扫描整个仓库。

禁止把 `docs/superpowers/**`、`docs/archive/**`、历史 PR 描述或外部 provider 输出当作当前实现事实。

### 1.1 上下文分层与停止条件

自主开发上下文按职责分层，不维护万能提示词：

```text
live repository / GitHub evidence          每轮刷新，只回答“现在是什么”
→ authority docs                           维护产品、架构与阶段事实
→ AGENTS.md / 本文                         维护长期 operating contract
→ one Capability Run contract / ledger     维护一个能力目标、动态 DAG 与 typed events
→ frozen Work Package projection           只在 integration freeze 投影给现有 Gate
→ one Task Envelope / Context Capsule       只描述一个 owner 的当前可执行交付
→ relevant types / tests / source          按需装载实现细节
→ Evidence V2 + merge gate                 机器裁决交付是否可信
```

聊天、Issue、PR body、Completion Report 和 Agent 摘要都只是恢复线索，不得成为上述任何一层的替代事实源。一次测试失败、fixture 修正或新诊断边界只是同一 Capability Run 内的 event；只有 objective、canonical contract、ownership 或授权边界改变时，才允许建立新的 Run / Work Package。Worker 在 acceptance 与 focused tests 满足后必须停止；新的风险、seam 或任务只能交还 A0 重算 DAG，不能通过继续追加上下文自行扩张 scope。

### 1.2 Context Compiler 合同

当前由 A0 按下列 schema 人工编译最小充分上下文；未来只有在行为稳定且重复后，才将其产品化为工具。每个 Task Envelope / Context Capsule 只携带：

```text
repo identity      cwd + remote + main/base/head + dirty-state ownership
objective          一个用户可观察能力、non-goals、停止条件
authority          canonical owner 链接及其有效 revision/digest
ownership          单写者、allowed symbols/paths、forbidden paths、reconciliation seams
impact             d=1 consumers、关键流程、被 diff 失效的合同与证据
acceptance         可观察 artifact/行为 + 必须保持的不变量
verification       可复用 baseline + 最小 delta Gate + 明确 invalidation rule
budget             允许的上下文扩张、诊断次数、验证时长与外部操作上限
```

每层上下文都必须回答一个尚未回答的问题；一旦 objective、ownership、acceptance、最小验证和停止条件已充分，停止继续装载文件。不得把整个仓库、所有 authority、历史聊天或完整日志塞给 worker。Repo identity 必须在每个 Run 开始时机器或人工验证，防止在错误仓库、错误 worktree 或陈旧 main 上执行。

## 2. 当前开发主线

**当前阶段、active work package、前置依赖与退出顺序只以 `03-MVP实施计划与路线图.md` 为权威。** 本文不维护阶段名称或另一份优先级列表，避免路线图完成状态变化后出现第二事实源。

除阻塞性 Bug、CI/性能回归和既有合同修复外，不主动扩张巨型业务 Demo、Workbench 特效、大量文件型 Block 或 ExplainGraph 母图语义。

## 3. 仓库事实与分支生命周期

`main` 是 SEC 唯一正式工程事实。分支是代码演进路线，不是等待合并的功能包。判断变化是否仍应进入主干时，必须交叉检查当前代码、真实 diff、base/head、merge-base、ahead/behind、verification evidence、review thread 和有效 `REQUEST_CHANGES`；不得仅依据分支名、PR body 或历史计划。

Squash merge 后必须区分**代码内容已进入 main**与**原 commit ancestry 已进入 main**。旧分支仍显示 ahead 不代表功能遗漏。

分支职责：

- `feat/*`：新增正式产品能力。
- `fix/*`：修复正式产品缺陷。
- `refactor/*`：不改变外部语义的结构重构。
- `docs/*`、`chore/*`：文档与工程维护。
- `spike/*`：大型未知架构探索，默认禁止直接合并；结论成立后提炼为正式产品变化。
- `integration/*`：仅在两条真实、并行、规模较大的产品演进线需要系统拼装时使用；完成验证后及时收口。
- `validation/*`、`diagnostic/*`：验证、故障隔离、日志和实验事实，默认禁止合并。

禁止长期创建 `validation/case-XX`、`final-exact-*`、`current-*` 等一次性远端测试分支。测试参数、suite 分片和证据采集由 Verification Contract、正式 runner、artifact、status 与日志承担；不得继续把 Git branch 当 CI 参数载体。

一个变化只有同时满足以下条件，才考虑进入 `main`：

1. 承载仍有效的产品能力、缺陷修复或必要工程维护。
2. 当前 `main` 尚未包含其有效结果。
3. 没有被更新、更完整的实现取代。
4. 与当前权威架构一致，或同步修正权威设计。
5. Required Verification Contract 已由可信 executor 实际执行通过，evidence/status 绑定的 exact head SHA 等于待合并 PR 当前 head SHA，且该 PR head 不落后于当前 base。
6. 无未解决 review thread 和有效 `REQUEST_CHANGES`。
7. 已理解提交关系和冲突边界。
8. 不包含临时 probe、日志采集驱动、旧 snapshot 或无意生成物漂移。

大型 integration 历史存在大量实验和验证 commits 时，最终验证通过后优先 squash merge，把经过验证的最终状态作为清晰主干变化。不得为了保留过程噪声污染 `main`。

PR 完成后必须确认产品结果是否真实进入目标分支，关闭废弃、镜像、probe 和 diagnostic PR；工具允许时删除完成使命的远端临时分支和已合并 head branch，并删除 retired diagnostic workflow 与一次性工程入口。工具不支持物理操作时必须准确报告边界，不得把“已审查”“已关闭”“内容已包含”写成“已删除”。

Git branch 负责代码演进路线；Verification Contract 定义门禁；GitHub Actions 是当前 hosted executor 之一，不是验证事实本身的唯一权威。

### 3.1 Capability Run 短反馈循环

开发单位是一个用户可观察能力的 Capability Run，不是“继续开发整个 SEC”，也不是每遇到一个有限失败就新建 `v2/v3/...` Work Package。Run 只允许一个 active product objective；同一 canonical surface 只允许一个 writer。其状态流为：

```text
objective-selected
→ contract-frozen
→ implementing
→ focused-proof
→ integration-ready
→ exact-head-verification
→ integrated | rejected | recovery-required | superseded
```

`hypothesis`、`implementation`、`sentinel`、`failure-boundary`、`repair`、`review`、`evidence-reused` 与 `validation` 都是 append-only typed events，不是新的进度单位。每个 event 绑定当时的 head/base、changed surface、结果和 invalidation；不得用新的手写叙事覆盖旧失败。

Worker 在同一授权边界内连续执行：

```text
inspect owned seam
→ implement the next observable increment
→ run the smallest focused proof
→ append result / boundary to the Run ledger
→ continue only while acceptance remains unmet and authority is unchanged
→ stop on acceptance or a declared escalation condition
```

只有四类 reconciliation point：能力 acceptance 达成；跨越另一个 writer seam；canonical contract / authority 必须变化；出现无法在当前授权内解释或修复的异常。普通测试失败、fixture 调整和已经定位的实现错误不强制 worker 停工，也不生成新的 Work Package。Draft PR 用于让 diff、head/base、ownership、当前阶段和 blocker 持续可见，但不构成 authority、验证证据或 merge 授权。

探索、identity/revision、权限、recovery、并发/lifecycle 与合同冻结使用 proof mode；合同冻结后的局部实现、测试和机械修复使用 throughput mode。不得在 throughput mode 重新设计 canonical type、revision algorithm、状态机或 authority。相同 failure boundary 连续产生两个诊断 event 后，第三次继续前必须升级检查 shared abstraction、state ownership、lifecycle 或 canonical contract，禁止继续切更小的诊断包。

### 3.2 Capability Run 冻结交付点验证

SEC 的 WebChat Worker 可以在任务分支连续提交，但开发过程中的 `push`、PR `opened`、`synchronize`、`ready_for_review` **不得自动消耗 hosted runner**。

Worker 达到 Capability Run 的 integration-ready 后，才把当前 Run 投影为现有验证工具需要的**一个最终 frozen Work Package manifest**。diagnosis / fixture / repair 不得各自生成新 manifest。随后执行：

```text
READY_FOR_INTEGRATION
→ 停止修改
→ A0 静态审查 diff / ownership / dependencies / review
→ rebase current main，并把最终状态 squash/amend 为 current base 上的单一提交
→ 从 Capability Run 冻结唯一 Work Package projection、exact PR head SHA、current base SHA 与 manifest raw digest
→ 触发一次 sec-scope-attest-v1 repository dispatch
→ 选择 quick 或 full，触发一次 sec-verify-frozen-v1 repository dispatch
→ 读取 exact-head/current-base attestation、Evidence V2 与 sec/merge-gate
→ merge 或返回 Worker 修复
```

当前 PR hosted verification 不使用 `run-quick` / `run-full` label，也不由 `synchronize` 自动触发。两个 repository dispatch 只由 A0 在 frozen reconciliation point 发出；GitHub 从 default branch 装载受信 workflow，heavy runner 只读 checkout exact head，禁止 head workflow 或脚本自行发布 required status。

A0 在触发前必须计算：

```text
PR verification key
= head SHA
+ current PR base SHA
+ Work Package manifest raw digest
+ verification profile
+ CI verification contract revision
```

Release/full ref verification 不依赖 PR diff，因此 key 为 exact head SHA、full profile 与 contract revision。

当前 revision 为 `ci-verification-v5`。v5 不实现多提交 prefix evidence chain：frozen head 必须恰有一个 parent 且等于 live current base，`SEC_CHANGED_BASE` 与 `SEC_AFFECTED_TESTS_BASE` 仍分别表达 PR Risk 和 affected feedback 的责任，但在 hosted freeze 点覆盖同一完整单提交 diff。PR head、current base、manifest digest、profile 或 revision 变化后旧 evidence 自动失效；`main` 推进时必须显式 rebase 并重新 freeze，禁止 merge-style Update Branch、旧绿色状态或落后 head 继续消耗验证额度。

Draft PR 是早期可见性与短反馈载体，不进入 executable merge-gate matrix。`plan-revalidation` 必须把选中的 Draft-only head 置为 failure，只为唯一的非 Draft same-repository head 分配 runner；共享同一 head 的多个 open PR 必须确定性 failure 且不得分配 runner。正常存在的 Draft PR 不得使 `push / schedule` 全局 revalidator 失败。

Tracked Work Package 的最终 phase 是 `frozen`。`merge-ready` 只能由外部 exact-head scope attestation、Evidence V2、live PR/base 状态、review 状态与 ruleset 推导，不能在验证后再修改 tracked manifest 来宣称 ready。

### 3.3 Actions 经济性约束

GitHub-hosted Actions 的优化目标是：

```text
最小化 billed runner processing
subject to Required Verification Contract 完整满足
```

因此：

- PR 只在 A0 显式发出 `sec-verify-frozen-v1` repository dispatch 时启动昂贵验证；普通 push、PR 事件与 synchronize 不启动 hosted runner。
- scope attestation 先于 heavy verification；两者都绑定 exact base/head/manifest，重复 dispatch 不是日常重试机制。
- 在 checkout/setup/install 前校验 default-branch workflow identity、A0 actor permission、same-repository、current base freshness、单 parent、manifest digest 与 verifier trust-root blob；任一不满足直接拒绝。
- 单个 verification profile 使用一个 hosted runner，只 checkout/setup/install 一次。
- slow suites 在同一 runner 内复用 bounded concurrency；runtime-heavy suites 保持串行隔离。
- release full 不使用 file-granular matrix runners重复 setup/install。
- 不运行无代码变化的 daily full schedule。
- 每 6 小时只运行轻量 merge-gate revalidator，检查 artifact TTL 与 live metadata；它不 checkout PR head，也不运行任何测试。
- 不通过删除测试、跳过失败 gate 或扩大 timeout 伪造经济性。
- 未映射 changed file / impact source 不允许静默视为无测试；hosted verification 必须 fail closed。
- 同一 head/base/contract/environment 下失败的昂贵 Gate 不得原样重跑；必须先出现能失效该失败的新 diff、新环境事实或新 hypothesis。
- 组合证据默认采用“最近有效 baseline + intervening diff impact + delta validation”；未被 diff 失效的昂贵 PASS 不重跑，也不得伪装成新 head 的 exact-head 单次结果。

### 3.4 自主开发控制面

控制面只负责把正确上下文、权限、预算和验收交给 Codex；能力边界内允许连续自主推进，只有越权或异常才升级。下列名称表示职责，不要求现在立刻创建七个新模块；只有行为重复稳定后才产品化：

| 职责 | 输入 | 输出 / 强制条件 |
| --- | --- | --- |
| Repo Identity Guard | cwd、remote、main/base/head、worktree | 错仓库、陈旧 base、未知 dirty ownership 直接停止 |
| Context Compiler | authority、ready DAG node、impact、valid evidence | 上述最小 Task Capsule，不复制第二事实源 |
| Risk Router | changed symbols、canonical/recovery/security flags、重复失败 | `throughput` 或 `proof`，并给出原因 |
| Ownership Lease | canonical symbol/path seam、writer | 同面单写者；只读审查和独立写面才并行 |
| Evidence Cache / Gate Selector | contract revision、surface digest、environment、baseline | `focused → affected → required closure`，只运行被失效的 Gate |
| Budget Watchdog / Stop Controller | event ledger、上下文与验证成本、acceptance | 阻止无新信息重跑、无依据扩 scope、验收后继续修改 |
| Control-plane Telemetry | Run events、Gate evidence、PR lifecycle | 度量能力 lead time 与浪费，不用 LOC/PR/token 冒充价值 |

默认控制预算：

- 同时一个产品 objective、一个 mutation operation、每个 canonical surface 一个 writer。
- 相同输入的昂贵 Gate 重跑预算为 0；每次重跑必须指出具体 invalidation。
- 一个 Run 只维护一份机器 event/evidence ledger 和一个最终 Work Package projection；聊天报告不再复制完整证据。
- 优先让只读 impact/security/review 并行；canonical type、revision algorithm、builder、pipeline order、journal 和 authority 章节串行。
- 第三方依赖只有在能净删除自研代码、重复 schema、人工步骤或 CI 成本时进入 critical path。
- acceptance 满足即停止；新增“顺手优化”必须回到 DAG 重新排队。

控制面只跟踪下列结果指标：首次可观察结果时间、Capability Run lead time、A0 handoff 次数、focused/昂贵验证时间占比、evidence reuse、重复 sentinel 次数、每个能力的控制面工件数，以及 `main` 最终获得的用户可见能力。代码行数、PR 数、生成 artifact 数和 token 消耗不是进度。

## 4. 实现规则

每项改动必须先回答：

- 权威输入是什么？
- canonical state 是什么？
- 输出是 canonical、artifact、evidence 还是 projection？
- 哪个模块拥有写权限？
- 是否确定性、可重入？
- 哪些不变量需要测试？
- 是否新增第二事实源？
- acceptance 满足后，什么条件强制停止？

### Compiler API

`platform/**` 的非 compiler 模块必须通过 `platform/compiler/index.ts` 使用 compiler 公共 API。不得穿透导入 compiler 子目录。

### 代码生成

Compose/Lowering 生成 `.ts`/`.tsx` 时使用 `CodeBuilder` 或正式 Generator API。不得继续扩张大段模板字符串代码生成。

### IR

- IR 类型以 `14` 和 `platform/shared/engineering-ir-types.ts` 为权威。
- Entity/Fact ID 必须稳定、确定性。
- Builder 输出必须稳定排序。
- 不把 UI 字段、布局坐标、视觉颜色写入 IR。
- ExplainGraph、SemanticView 只从 canonical state 投影。

### AI/External Evidence

AI 推断和 Graph-It-Live/GitNexus/Graphify 结果只能进入 inferred/evidence 层。不得自动升级为 authoritative fact，也不得扩大 allowed paths。

## 5. 修改顺序

新增公共能力按以下顺序执行：

```text
1. 修改权威规范
2. 定义公共类型/Schema
3. 写失败测试或不变量测试
4. 实现纯 builder / pass
5. 接入 facade / orchestrator
6. 接入 artifact / projection / CLI（如需要）
7. 完成 focused local/branch checks并交付 frozen head
8. 由 A0 触发 required verification profile
9. 删除旧重复路径或明确兼容边界
```

不得先改 Workbench 再反推 IR Schema。

## 6. Issue 分类

| 类型 | 含义 | 默认处理 |
| --- | --- | --- |
| Spec | Authoring/Contract 不完整或冲突 | 人工或明确 Semantic Mutation |
| Semantic | IR 不变量、Fact 冲突、identity/provenance 问题 | 修 Semantic Frontend/IR |
| Composition | Block/Generator/Lowering/安装错误 | 修 compiler 或 Block metadata |
| Synthesis | AI/Slot/受限生成结果不满足合同 | Task Envelope 内修复 |
| Verification | 测试、Policy、Acceptance、Drift 失败 | 结构化归因后 repair |
| Kernel | 性能/正确性/基础设施问题 | 维护者处理 |

## 7. 测试与验证策略

- 纯 IR builder/index/selector：`tests/unit`。
- 公共 IR/CLI/JSON shape：`tests/contract`。
- Workspace → IR → projection：`tests/integration`。
- 浏览器只保留生成运行时 smoke；不把 IR 业务矩阵塞入 Playwright。

本地/Worker focused 入口：

```bash
bun run check:affected
bun run check:fast
bun run check:full
```

Hosted verification 入口由 A0 触发：

```text
repository_dispatch: sec-scope-attest-v1
→ default-branch trusted scope attestation artifact

repository_dispatch: sec-verify-frozen-v1(profile=quick|full)
→ scripts/ci-verification.ts --profile <profile> --expected-head <exact SHA>
→ exact-head Evidence V2 artifact
→ default-branch sec/merge-gate
```

`platform/shared/ci-contract.ts` 是 CI logical gates、workflow execution model、repository-dispatch type 与 verification revision 的 canonical contract。`platform/shared/test-impact-contract.ts` 是 source ownership → required test impact 的 canonical contract。

验证信任根包括 verification workflows、`scripts/ci-*`、相关 `platform/dev-runner/**` / `platform/shared/ci-*`、test budget/impact contract、Evidence writer、Work Package parser、merge gate 与依赖入口。普通 PR 不得修改这些路径后使用同一 revision 自证通过；此类变化必须建立新 Bootstrap Work Package、升级 revision，由旧 base/人工 integration 验证后进入 `main`。Mandatory sentinel 只决定额外测试，不扩大授权。

## 8. 完成报告

Agent 完成任务时只报告：

- Capability Run 的当前状态，以及 `main` 实际获得或尚未获得的用户可见能力。
- 改了什么 canonical/contract 边界。
- 关键不变量。
- 实际运行的测试结果。
- 尚未实现或仍是规划的部分。

禁止把未运行的测试写成“通过”，禁止把文档设计写成“已实现”。
