# Exact-main MainHealth and verification-boundary repair

This one-generation repair is the only write authority while exact `main` is routed `repair-only`.
It repairs the three failures observed by canonical hosted MainHealth run `33109458351` and the two
control-plane defects exposed while reaching that evidence: same-name GitHub Actions jobs could be
mistaken for a registered provider, and a stale local affected-closure receipt had no canonical
supersession operation when stronger hosted evidence disagreed.

The package deliberately excludes the preserved `development-critical-path-spine-v1` implementation.
That full semantic successor remains recoverable at exact commit
`f4f01589bb942f334de7bab89934b12e7a7c191f`; after this repair merges and exact new-main readback
restores `ordinary-only`, the same branch and worktree resume that package under a new authority epoch.

It does not copy the successor's untracked `src/` layout, move unrelated consumers, or depend on a
half-migrated facade; the later repository-layout migration remains one separately closed graph cut.

No compatibility facade is permitted. The misplaced worktree parser moves to its domain owner and all
consumers move with it. MainHealth provider identity is one predicate used both for enrollment and
selection. Evidence retirement is an authenticated state transition. Impact selection gains the missing
physical-universe dependencies instead of compensating with unconditional full-suite execution.

## Systemic closure discovered during exact-candidate review

The repair remains one candidate and one integration writer, but exact static review exposed repeated
instances of the same missing physical/provider lifecycle boundary inside the owned repair surface. The
package therefore closes the root invariant rather than preserving green but bypassable leaf fixes:

1. Windows Git/GitHub CLI concrete versions, artifact identities, layouts and bounded command contracts
   live in one strict EnvironmentSpec. The capability ledger only routes that spec; it cannot certify a
   live executable, credential, repository fact or remote Effect.
2. One live Windows control-CLI session may turn PATH, registry and standard locations into bounded locator
   hints, but it can execute only after the minimal installed executable/root/loader closure, retained
   repository cwd, exact executable identity and version probe all agree. Runtime adoption performs zero
   download, install, extraction and executable-cache publication; missing or ambiguous capability is the
   typed `installed-executable-capability-unproven` state, never a path string or caller digest positive.
3. Generic retained process transport owns neither Git nor GitHub semantics. It consumes only physical
   capabilities and delegates root/descendant/stream termination and readback to the existing observed
   process lifecycle owner. Linux uses fixed advertised child descriptors; Windows must either prove its
   path/handle boundary or report capability unavailable. Timeout, abort, output overflow and child error
   all require terminal tree and stream settlement before capability disposal.
4. Git parsing and repository facts remain with the Git read owner. GitHub credential, principal,
   permission, REST, check/status provenance and remote Effects remain with MainHealth/verification
   owners. No per-consumer Git, GitHub, MainHealth or WorkSelection wrapper may become a second provider.
5. `check:affected --plan` is a zero-Effect query. Dependency bootstrap, handoff and deadline reset are
   forbidden; the plan consumes one immutable snapshot, one absolute deadline and one repository epoch.
   Every later Effect rechecks the same frozen plan immediately
   before mutation.
6. Generated dependency state is governed by immutable, predecessor-linked transition and registration
   records under one owner-local lease. Existing preimages cannot self-sign through `born`; recovery,
   rollover, stage disposal, bridge publication and cleanup require exact retained identities, bounded
   inventories and closed-world topology. Unknown or foreign recovery material is preserved and blocks.
7. Git hook installation binds tracked source bytes, transformation identity, deployed bytes, repository
   lineage and live origin/main/HEAD under durable prepared/effect/readback records. Timestamp/size,
   transformed-byte collisions, ambient Git configuration and linked-worktree ambiguity cannot authorize
   reuse or cleanup.

## Repository module architecture and test-proof reconciliation

Repository architecture is compiled from package-local `sec.module.json` descriptors and the exact source/import
graph. A path inventory, fixed module count, source-name assertion, audit report or caller-authored coverage flag is
not architecture authority and must not be added as a parallel registry. An audit may reveal a migration candidate,
but its output is disposable until the sole module compiler can derive the same fact from the physical repository.

Each migration batch must close one graph cut completely: establish the domain package and public facade, migrate
every exact consumer and test-impact edge, reject forbidden dependency directions, then delete the superseded path
and rule in the same batch. A batch is invalid if it adds a registry, adapter, compatibility route, evidence file or
test without deleting the mechanism it replaces, or if total code/state/test/verification cost does not decrease.
Unknown files, unresolved imports and ambiguous ownership remain typed migration blockers; they cannot be converted
to a fixed count or a hand-maintained exception list.

Tests for this architecture exercise descriptor parsing, physical membership, import-edge compilation and illegal
state rejection. They do not snapshot module IDs, file lists, version strings, line counts or current debt size.
Repository-wide test reconciliation follows the same rule: prove a concrete public invariant or failure boundary,
