## 同一SEC中的产品需求声明：design、use与require

**可选文本表面，未列为当前产品主面或实施前置。** 本节保存`design/use/require/prefer`的完整语法设计供后续比较/适配；旧片段和正反例不删除，但本节不能使该前端被默认为已采用或已实现。结构模块直接使用同一[需求语义](../../docs/作者/需求含义与实现责任.md)与[结构合同](../../docs/作者/结构化源码.md)，不经过这套词法。基础`fn/type/class`属于对应可选计算画像，原生维护保持自愿。

### 为什么允许这次语法扩展

旧计算文法只有函数、常量和端口，没有专用的公开参数化需求声明；这只说明该文本前端缺这个表面，不能否定已有结构模块直接表达需求的能力。保留一个可选`design`声明以及`use/prefer`局部语句的完整设计，复用`require/import/export/type`及已有值表示。明确启用它时承担真实解析/类型/转换成本；未启用时不扩大旧文法，不把三个新上下文词作为当前主面或必要实现工作。

`design`只在模块声明头为关键上下文；`use/prefer`只在design体的语句起始为关键上下文。在函数体、记录键、模块别名等旧位置仍按原Ident解释；现存合法`let design = ...`不被全局保留字破坏。此次不修改旧函数的求值、注解或对象默认。旧模块仍使用锁定解释；没有对应文法能力的读取器准确返回不支持，不能按源里出现一个词自动升级。

### 增量文法与消歧

以下引用本章既有Ident、Params、Type、QualifiedName和StaticExpr。`ModuleItem`是所选文本画像中原Module内声明选择的别名；只有明确启用本候选扩展时增加DesignDecl分支，不改变未启用画像的旧分支。声明名、需求定义名和类型域由绑定决定，但语法不依赖名字是否已经存在。

```ebnf
Module      = {ModuleItem} ;
ModuleItem  = Import | TypeDecl | Function | PortDecl | BindDecl | ConstDecl | DesignDecl ;
DesignDecl  = ["export"] "design" Ident "(" [Params] ")" "{" {DesignItem} "}" ;
DesignItem  = DesignUse | HardRequirement | SoftPreference | DesignConstant ;
DesignUse   = "use" QualifiedName "(" [DesignArguments] ")" ";" ;
DesignArguments = StaticExpr {"," StaticExpr} ;
HardRequirement = "require" [Ident ":"] QualifiedName RecordValue ";" ;
SoftPreference = "prefer" [Ident ":"] QualifiedName RecordValue ";" ;
DesignConstant = "let" Ident [":" Type] "=" StaticExpr ";" ;
```

`require r: q.Rule {...};`中的r是可选源内约束标签，便于诊断与编辑，不是运行结果或自动供给实例。无标签也能依据准确源位置维护身份。`QualifiedName {`直接构造**已绑定需求描述**；不是普通记录块加目标构造器调用，不产生运行对象。`use q.Design(s);`是参数化要求实例化，不是函数执行。只有design体的`let`允许绑定类型合格的被动值与引用；禁止端口、网络、时间、环境及任意函数执行。

所有`require`字段按该准确Rule定义检查：必需/可选、类型、单位、默认与元引用种类均固定；未知字段和重复字段拒绝，不静默传给插件。普通枚举常量在所属模块解析，不能把同拼写Text当作该枚举。`prefer`仅接受公开标记为Preference的规则，本例`quality.Cost`；不能把禁止出网之类硬条件改成偏好。

### 形参与主体

Design形参的Type可以是既有静态值类型，或一个被导入语义定义公开的SubjectSchema。后者表示被约束的对象/事件/集合模型，**不等于类实例、资源句柄或当前机器**。例如`ide.Workbench`公开workspace/documents/search等带类型角色。`s.documents`定位同一个语义主体，允许不同需求共享；不会因被引用两次创建两个文档服务。不同根的s是不同名义实例，不能按schema结构或内容哈希合并。

传入静态值可参数化行为，所有必需值必须由调用或明确默认闭合。当前根导出为`Studio(s: ide.Workbench)`时，输出根选择该定义并为唯一SubjectSchema形参创建一个新的**逻辑根身份**；它不是运行分配。根还有未绑定普通实参时返回NeedsInput，不填默认0。普通`use`按声明顺序求被动实参但不触发运行效果；形参与字段类型必须一致。支持前向引用；直接或间接无界design展开环拒绝并列出环，不把运行时递归规则借给静态需求无限展开。

普通TypeDecl可以组合导入的subject角色形成新的观察模型；同一表面Type仍由使用阶段区分，不将其中静态SubjectRef当作可运行值。SubjectSchema必须明确角色是单一主体、关系集合还是运行集合选择器；模型声明不自动创建服务、线程、表或每个集合成员。

### 原编译对象及输出根接合

启用本候选文本前端时，DesignDecl进入原Definition，体内内容归一为已有RequirementTerm及来源关系；形参代换保存共享主体，完整结果仍是同一个作者ModuleRevision。新的头种类为产品需求根，不登记为CallableIndex函数，不允许compute-eval对它直接调用。preview选择这个根时生成符合要求的完整工程；真正运行仍使用产物内明确的启动入口。

原`sec.project/1.targets.*.outputRoots`仍以moduleId/export选择这个公开定义。生成器核对导出种类为design并使用相应方法，没有新公共工具或另一个roots.json。精确解释仍绑定原context/语言锁；本版没有新造未发布的`sec.intent/1`入口。旧只认识函数根的实现必须报告不支持，不能当成一个零参数函数运行。

硬要求冲突不按文件顺序覆盖；静态合取无执行顺序含义。约束/方法身份与完整类型、效果、目标资格不能由名称“看起来合理”获得。展开查看可以显示归一需求及实现计划；保存不把这些派生物回写成几十个普通函数或手工ID。
