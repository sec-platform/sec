# 统一源码工程与多表示作者协议

> **规范身份与适用性**：这是 Gift 当前**作者工程实际使用方式**的统一入口，拥有作者源选择、工程文件关系、跨表示保持与 SDK 边界的总合同；细节分别由[工程清单模块与绑定锁协议](工程清单模块与绑定锁协议.md)、[结构化作者源码](../结构化源码.md)、[作者工程与输入边界](作者工程与输入边界.md)、[原生来源与逆向边界](../../../80-开发者与接口/原生维护/原生来源与逆向边界.md)、[计算文法](../../../20-语义与组合/基础语义/计算基础/文法类型与求值.md)拥有。本篇不复制其字段枚举成为第二个协议，也不修改其已定义的 `gift.project/2`、当前候选`gift.author-module/2`、历史只读`gift.author-module/1`和 `gift.binding-lock/1` 各自准确的协议身份。它们尚属设计合同，**未发布完整生产读取器**；`gift.project/2`已有有限项目结构Schema，但它不签发真实读取、锁、语义或目标资格。实例、接口草案、可用性与真实发行资格必须区别。
>
> **优先级**：本篇处理作者“用什么写、文件属于谁、表示之间如何选择、谁允许执行、工程如何演进”的跨表示疑义；某种结构格式的具体 `Definition.body` 以该 dialect 精确版本为准；目标、权限与运行以各自原 owner 为准。若存在不一致，不能通过“最新文件覆盖旧合同”自动改变含义，应使相交合同同步修订并保留冲突诊断。

## 0. 不能再被更改含义的总决策

**当前唯一可持久编辑的业务作者格式是 JSON 模块。** 业务意图、需求、Pattern、领域、类型、计算函数、产品结构由 `gift.author-module/2` 及其专业 Body 解释；`gift.project/2` 仅选择发现范围、目标和根。TypeScript/Rust 作为**原生实现源**在自己拥有的 `src/**` 范围可写，提供合格 Method 或宿主边界，而不是一份同步维护的业务 JSON 影子。编辑器的表单、图、树和自然语言辅助输入应落回唯一 JSON 所有者，不能另存竞争版本。

研究中的 `.gift` 文本和 `gift.author-text/1` 静态作者库不属于当前 Writer，也不因安装扩展、后缀或声明 `import` 自动启用。若未来采用文本表达，须先明确替代原结构区域的单一写权转移、准确规范化规则、受控求值与 SourceMap/CAS，而不是把两种格式都作为必须维护的业务源。现行的 `core:function` JSON 计算 Body 不依赖这个可选文本 Profile；作者确需现成算法时也可以通过受资格约束的原生实现取得。


**Gift 通过统一的工程语义、Requirement 组合、实现供给、Target 与持续维护合同管理不同作者形式；不强制以新编程语言为入口。** `Gift Core` 不预装行业、IDE、支付或游戏业务。每个互不重叠的作者区域独立选择结构化 `*.module.json`、原生 `.rs/.ts/...`、现有库/Provider，或在合格 Profile 下使用 `.gift`。这些入口是替代或互补来源，不是强制的连续转写步骤；同一作者区域始终只有一个权威写入者，其余材料提供独立事实、实现供应或只读投影。

**统一单元是已绑定的含义与跨责任关系。** `AuthorModule` 提供逻辑模块容器；`Definition / Requirement / Type / Relation / Effect / Control / UseBinding` 分属不同语义 Owner。严格 JSON 是持久编码，Rust SDK 是可选编辑/构造客户端，`.gift` 目前属于可选计算文本及尚待生产实现的静态作者 Profile。表示能够编码某对象，不代表它已实现该对象所需的语义、执行和保证。

作者体验的评价基准是**完成真实任务的编辑成本、表达覆盖、可追踪性、生态互操作、唯一权威、约束强制、交付完整性及换目标成本**，而非源码外观。比较时固定相同业务要求与成熟供给；Gift 若没有可证实的增量价值，直接原生开发就是合格方案，不强制引入 `.gift`。

## 1. 真实开发者可选的四种工程形式

| 工程场景 | 需要实际编辑什么 | 不要求什么 | 当前资格 |
|---|---|---|---|
| 已有单语言项目 | 原有 Rust/TS/其他源码、原配置和资源；**独立**的新 Requirement 如确实有才加作者模块 | 不要求生成同义 `.gift`、JSON AST、十模块目录或 Gift 自己的包管理器 | 源保持原则和原生适配合同；具体语言能力以已实现适配器为限 |
| 结构化新设计/复用定义 | `gift.project.json`、必要的 `*.module.json`、独立的资产/配置；准确 binding 成立后有 `gift.lock.json` | 不要求编写计算函数、Target 根、空 `main.gift`、生成目录 | 结构合同为正式设计草案；实现/构建资格与源格式合法性分开 |
| 混合作者工程 | 原有算法源码 + 仅承载独立要求、状态/关系或控制的结构模块；每个区域明确 SourceProfile | 不把源代码重复放入 JSON；同一含义不由两者任意改写 | 各原生适配器覆盖范围可能不同，不能推定完整逆向 |
| 选用计算文本 | 必要的 `.gift` 函数、类型、port；工程含义可另由结构模块表达；静态 `gift/author` **只属可选文本候选** | 不要求所有业务变成 `.gift`、改写全部原生代码或再发行完整标准库 | `gift.semantic/1` 有规范；新 `gift.author-text/1` 尚待 Schema/前端/库的生产资格 |

另外还有不持久化完整工程的 **临时函数、片段或定义**：以已固定的 UnitInput/context 运行和返回，只有用户要求保存成长久工程时才生成必要工程清单、模块与锁。缺少 Target 或未决定实现可保存设计；**保存设计不等于生成目标源码**。

### 1.1 结构新项目的最小文件树

```text
studio-design/
  gift.project.json         # 工程身份、范围和可选目标要求，不是“所有业务正文”
  design/
    foundations.module.json # 可复用独立要求定义
    studio.module.json      # 通过明确导入使用 foundations
  assets/                   # 只有真实资产需要时才存在
  gift.lock.json             # 只有完成真实绑定解析后由工具维护；不能伪造
```

`*.module.json` 就是这里的**真实源代码**。其中 `definitions`、`imports`、`exports`、RequirementTerm 及其实际 dialect 语义共同定义所要的软件。不是“占位脚手架”，也不是“非源码”。没有选 Target 时可形成规格/设计包，不可宣称已有可运行程序。进一步细节和可静态核验的样本见 `fixtures/author-workspace/Gift90/structure-first/`。

### 1.2 原生连续维护的文件树

```text
studio-existing/
  package.json             # npm/Bun/TS 的原生配置仍由该生态维护
  src/editor.ts            # 原有功能的唯一实现源
  design/studio.module.json # 只有真正独立于代码的要求才在此保存
  gift.project.json        # 可选持久 Gift 组织；仅打开原生工程时可临时捕获
  gift.lock.json           # 解析后才会出现；不能复制 package-lock.json
```

对一个已能按原生工具构建的项目，**不用 Gift 也能开发**不是故障。Gift 可用时增加的是需求/变更追踪、共同约束、可替换实现、目标规划及证据，而非改变所有源码的合法性。`package-lock` 或 Cargo.lock 对其生态依赖仍为权威；Gift 锁只保存自己的精确解释和依赖来源，不重新解释 npm/Cargo 的 semver。

### 1.3 只使用成熟实现的无应用算法工程

允许未发现本地模块、`sourceScopes` 为空；当前固定导入范围可以通过 `outputRoots` 引用合格的外部模块公开出口。此时工程确实可能没有一行用户实现程序。前提是完整公开合同、实际取得的内容、环境/ABI、目标能力和许可证条件均成立；没有这些供给，**空作者项目不能自动生成一套专业软件**。

## 2. 作者模型：五个分开但可连接的事实

1. **作者事实**：谁接受了什么需求、行为、算法、资源或实现固定选择。持久源可为结构数据或原生源码；它的作用域、Revision 和真实内容必须可定位。
2. **导入与解释**：当前 `AuthorSourceProfile`/语言/dialect/库和 exact resolution；形式合法但 dialect 未取得不等于能理解定义体。
3. **实现供给**：何种有资格的 Method/原生库/Adapter 实现当前要求。供给可承载算法而非由结构 JSON 把算法重复描述一遍。
4. **目标和产物**：当前目标平台、公开根、ABI、源码/配置/资源和完整 ArtifactSet；目标请求缺失不使作者事实非法。
5. **实际效果与保证**：检查、文件提交、运行、发布、远端回执、性能与安全事实，分别有真实拥有者；它们不回写成无条件的 `completed` 作者字段。

独立 Requirement 和它约束的函数允许同时存在：两者不是“同义双源”，因为一者保存**必须满足的要求**，另一者保存**候选实现**。两者关联要保留输入/结果域、前提、失败路径、来源和版本；实现不能自行提高自己的接受标准。相反，把同一个函数实现从 `.rs` 复制为 JSON AST 并让两边各自可编辑，就是应拒绝的双写真源。

## 3. JSON 的真正使用方式：不因冗长取消其权威资格

`gift.project/2` 是项目定位/目标输入；`gift.author-module/2` 是当前候选新业务的唯一模块外壳及其 Definition（`/1` 为历史只读来源）；`gift.binding-lock/1` 固定经真实解析所得的候选选中版本/内容。它们职责不同。**结构化 JSON 是当前唯一业务作者持久Writer，不是仅用于传输或“等待转成 `.gift`”。** 对模块作者，JSON键次序、缩进和空白是保留的原始文字，但不定义需求执行顺序；需要顺序的行为由具体 Term/表达式语义规定。

精确编码规则沿[工程清单](工程清单模块与绑定锁协议.md)和[Requirement结构体](../结构化源码.md)执行，尤其包括：重复键拒绝；未知字段或 dialect 原字节保全且相交消费拒绝；身份不随路径/显示名更换；导入必须经公开导出及绑定锁；数值无损；结构内容不得默示运行顺序；`null` 不代替缺项。读写工具须提供 AST/CST 或等价源跨度映射，局部编辑只提交当前 owner 的字节差异，保留无关字段、注释由外部文档承担、原生资产和未知扩展；不能通过 JSON 全文件重新打印覆写用户独立更改。

**JSON 的成本用编辑器、模块封装和精确补丁解决，不用强制新语言解决。** 日常修改可由手写JSON、表格、AI、SDK 产生局部候选，返回 `CandidateRef`、SourceDiff 和原始前像；写入前需当前 Revision、权限和相交不变量。消费者也不得把全文 YAML/JSON 移进上下文每次重建。

## 4. `.gift` 的地位：已有计算语义与可选作者文本不是一个承诺

`gift.semantic/1` 的基础词法、类型、函数、效果与合同有其独立规范。[计算文法](../../../20-语义与组合/基础语义/计算基础/文法类型与求值.md)是详细 owner；`.gift` 文件只在所选 Profile 下获得解释，**不因扩展名自动激活 `gift.author-text/1`**。第89版增加的 `gift/author` 为明确候选：其工作是用受约束静态表达式构造与结构化 `Definition/RequirementTerm` 等价的逻辑内容。它没有自动增加计算能力、没有替代 JSON、没有证明其作者成本更低，也不是正式已发行的完整语言生态。保留具体设计作为可复用候选，但从全产品**必需前置和首发阻断清单中移出**。

没有足够收益证据时，即便已有 46 条 EBNF 产生式，也不要求实现另一套工程要求文本语法；若将来采用文本作者 Profile，须分别证明它比结构编辑、宿主 SDK 与已有语言的收益，且完整处理静态求值、终止预算、泛型类型、来源、迁移、诊断、版本、可写区域和双向编辑。不允许直接把 `.gift` 当作 Target 编译成功的保证。

## 5. Rust SDK 与结构化输入：两种前端，同一逻辑语义

**SDK 不是新的 Gift 通用语言。** 独立的 `gift-author` Rust crate / TS SDK（实际名称和发布均尚未决定）可以把成熟宿主语言的类型系统、IDE、测试和库用于构造、检查或提交 `AuthorModule` 候选。宿主语言本身表达任何算法，SDK 不重复发明算术、泛型、容器和 async。这不意味着普通 Gift 用户必须写 Rust。

SDK 的允许能力：读取固定 AuthorSnapshot 的合格公开内容、创建 `ModuleDraft` 或结构 Patch、构造类型化 `req:composite/Term/Value`、取得可追踪诊断、生成候选差异、在授权时请求保存；可导出经校验的 `gift.author-module/2` 候选真实 JSON 字节；旧 `/1` 仅允许按原版进行只读输出或获权迁移预览。**SDK 不持有第二个永久作者副本；SDK 构造对象是临时候选。** API 的所有类型化构造必须按与 JSON codec 相同的类型和限定条件解析，不能把 SDK 的某个默认、枚举值或本地时钟秘密增加为共同语义。

有三个严格不同的流程：

- **离线纯构造**：给定显式参数与固定库语义，SDK 返回逻辑候选和可序列化作者字节。工具检查完整内容后按普通流程提交；Rust 构造代码不必成为项目正式依赖。
- **显式执行的代码生成器**：若用户选择“运行 Rust 构造程序产生 JSON”，这本身是一个需授权的外部操作，可能读取文件、网络、环境，必须声明来源、工具链、输入与副作用，再冻结生成的**结果字节**作为作者候选。固定重建消费这些固定字节，不重新执行代码生成器以猜作者意图。
- **运行库绑定**：Rust crate 实现业务能力，通过精确接口、版本、Target/ABI、资源、效果和许可资格被选为 Method。这不是 SDK 生成作者 JSON，也不代表在 TS 目标下已存在等价 TypeScript 实现。

不要因 Rust 构造器类型检查通过便视为 Gift 需求可满足、跨目标可生成、行为等价或生产安全。反过来，JSON 结构模块无需编译一行 Rust 便可以是合法作者输入。

### 5.1 设计级最小 SDK 表面（不是已发布函数）

```text
read_module(snapshot, module_ref) -> ReadResult<AuthorModuleView>
new_module(module_id, namespace, dialect_requirements) -> ModuleDraft
add_definition(draft, stable_definition_id, TypedDefinitionDraft) -> DraftResult
add_term(draft, composite_ref, TypedRequirementTerm) -> DraftResult
export(draft, public_name, DefinitionRef) -> DraftResult
serialize(draft, encoding = gift.author-module/2) -> BytesWithSourceMap
propose(base_revision, changed_bytes, intended_owner) -> Candidate | Conflict | Diagnostics
apply(candidate, expected_source_revision, grant) -> Applied | Rejected | Unknown
```

这里的SDK示意默认Writer为`gift.author-module/2`，旧`/1`只在有条件历史Reader或迁移中使用，不能让SDK默认回退旧Writer。序列化、propose 和 apply 是不同动作；纯 SDK API 不得自行读取 live workspace 或隐式触发网络、下载、Provider。SDK 可以本地提供语法级便利，但真正的跨模块 binding 与检查必须消费相同 exact context；它的 `ModuleDraft` 可不完整，但不得因为已存在对象就伪称已采纳合格含义。真实产品接口复用[六工具](../../../80-开发者与接口/工具协议/六工具与请求.md)，本表不新增第七个正式工具或另一套权限系统。

## 6. 跨表示的合法状态与迁移算法

对于每个 `AuthorRegion`，固定 `owner`, `sourceBytes`, `SourceRevision`, `AuthorSourceProfile`, `language/dialect revision`, `allowed edit operations` 和必要的范围读取；若映射不存在，显示内容可以只读但不能猜回写。跨源迁移不是文件扩展名重命名，按下列有界流程执行：

1. 捕获并冻结原始字节、导入/导出与依赖闭包、全部相交适配器的支持范围，保留无法解码的原片段。
2. 为目标表示生成新候选（可为 JSON→静态文本，或结构模块→宿主SDK编辑结果），但不同时签发两个 owner。
3. 比较精确可判定的结构意义（Definition 身份、参数、默认来源、Required/Preferred/Quantified、公开出口、实际资源/效果）；计算程序的一般等价不可判定，不能把两个 AST 看起来相似当证明。
4. 获取相交消费者需要的额外证据、显式变化接受和冲突裁决；旧格式的未知扩展、注释/布局/原生专有观察不能被无声删除。
5. 用原子作者候选切换该 region 的唯一 source owner；多文件不具备共同原子性时使用已设计的协调/恢复机制，不能先删旧源后写新源。
6. 记录旧 Revision 到新 Revision 的合法映射、保留恢复原字节和必要来源；失效相交缓存/锁/目标制品和保证，不复活旧写权限。

`serialize(parse(bytes))` 可承诺逻辑等价仅限固定的结构 dialect 与完整语义域；字节等价需要原始 CST/patch 保留，JSON canonical form 对注释/次序/未认识字段不是通用替代。纯文本语法到原生业务源码的双向转换需要独立适用证明。迁移失败保持旧 owner 可写、候选可恢复，不让其中任意格式自动取得真正的作者权。

## 7. 可执行与非可执行：共同语义的支持域

存在通用计算模型，不代表任意专业系统的真实行为可以从有限、高层需求自动推导。对于新增领域，优先通过用户 `Definition/Requirement/Type/Relation/State`、已发布库和 Method 接合；普通业务名不进入 Core 枚举。要保证完整软件交付，至少须对每个请求输出根建立：**明确含义与观察域 → 合格的实现或可确定构造 → 固定 Target 与环境 → 成员/资源/依赖的完整集合 → 必要检查/证据 → 实际作用（仅当请求）**。不能因为 JSON 可写、Rust 是图灵完备或 `.gift` 已有文法而省去供给和目标后端。

同一套工程表示可以服务 VS Code 级复杂项目，但只能声明实际定义过的编辑器、进程、扩展宿主、语言服务、存储、权限、调试协议和构建行为。它们是用户领域模型或外部服务能力，不属于核心关键字；允许某些子系统完全由原生实现保管。完整目标布局可由原生构建系统或 Gift `TargetProjectPlan` 产生，**只读蓝图不是第二份作者源**，输出目录不以包名冒充功能。对未知协议、动态插件与受限设备必须注明观测/效应边界，不虚构“VS Code 等价”证明。

## 8. 严格生命周期与失败裁决

| 状态/情况 | 能做什么 | 严禁的结论或副作用 |
|---|---|---|
| JSON 完整但 `dialect` 未取得 | 保存原字节、只读定位、形成待解析 Need | 不能降级为空产品或假定所有 Rule 生效 |
| 结构 Type 和 Need 完整，Method 缺失 | 保存设计、查询实现缺口、继续不相交部分 | 不能因已声明端口就称实现/运行完成 |
| 原生源码可读但适配不支持某语言构造 | 保留真实源码、委托准确原生工具或报告覆盖缺口 | 不得悄悄转成中立黑盒再声称全量语义已检查 |
| Rust SDK 输出两个同名定义或旧前像 | 保留候选与诊断、拒绝冲突保存 | 不能“最新写入获胜”或以路径同名重用已删身份 |
| 结构与 `.gift` 同时可写同一逻辑定义 | 检查 SourceProfile 归属并要求一次有凭据迁移 | 不得称“两种输入都支持”就默许双写真源 |
| 精确锁缺失/已失效 | 返回依赖 Need、允许纯设计和待绑定输入 | 不得按本机 latest 静默选不同版本 |
| 只有目标蓝图，没有 ArtifactSet | 交付蓝图和未完成实现义务 | 不得标记源码生成、typecheck、安装或发布完成 |
| 目标已生成，未检查或操作未知 | 分开公布生成依据、CheckRecord、Operation 残余 | 不得用“生成成功”覆盖未完成检查或外部效果 |

**最小公共写入语义**：`propose` 不写磁盘；`check` 不能暗中提交；`apply` 根据候选/前像/授权校验真正进行原子或可恢复的源修改；`operation` 结算外部作用，未知效果不能盲重试。用户操作面只需看到“修改了什么／影响什么／是否已保存／是否真的运行”，不要求理解每个内部 IR 名称。

## 9. 可实现接口与真实代码责任

- `workspace` 唯一管理 SourceProfile、作者字节、范围/身份、候选、前像与 SourceMap，**不能由 SDK 或编辑器影子模型抢写**。
- `semantics` 按固定 dialect/语言 revision 解析 Definition、类型、关系、约束、效果，并形成可定位的未决诊断。结构解析器不执行用户 Rust `build.rs`。
- `compiler` 消费已冻结的语义和 UseBinding，选择合格 Method、目标根及成员布局；不会仅凭 `author.compose()` 返回一个值就生成未实现的服务。
- `assurance` 判断 Claim/Evidence/Qualifier，严格区分作者要求和实现生成的自检，防止自证循环。
- `application` 用原有六工具协调 `query/propose/preview/check/apply/operation`，不添加 SDK 专属控制平面。
- `execution/adapters` 对真实文件/进程/网络/依赖安装/原生构造器运行实行额外授权与恢复；原生工具的退出码不等于所有保证通过。
- `contracts` 共享标识、必要的结果和诊断类型；`entry` 允许不同语言的客户端，在协议意义上等价，不要求所有作者采用相同文件格式。

真实物理架构继续保持 Rust 纯计算内核、TS/Bun 控制与生态接合，Target 用于生成用户软件，并非“使用 Rust 就只能生成 Rust”。**RUST SDK、RUST 内核、RUST Target、RUST 业务库、原生 RUST 作者源码是五种不同责任。** 出于性能或生态可以把某责任交给成熟技术实现，但不能由使用语言直接推断它的语义或阶段。

## 10. 表示选择、实现优先级和准入验证

**默认决策**：存量工程保持原生；创建高层规格优先结构作者模块；真实算法先复用成熟库或保留现有原生源码；跨目标确实需要中立程序语义且有已实现 Profile 时才写 `.gift`；工具/开发团队希望编程构造模块时使用 SDK，但其结果仍须成为可追踪的单一作者源。不要因为 JSON 长就实施整套新语言，也不要因为 Rust SDK 能编程就让构造脚本进入每次无副作用编译。

**何时重新考虑语言投资**：在相同需求、相同库/Target 下，量测结构编辑或 SDK 无法合理承担的源级声明复杂度、诊断精度、跨目标语义保持、可靠回写或特化成本。文本 Profile 只有取得清楚的净收益和完整语义消费者，才从候选升级为独立发布能力；否则保留为非阻断研究。成熟 Rust/TS 包或框架若满足全部所需观察和维护要求，可以成为实际能力供给，不因“不是 Gift 语言”被排除。

**设计接受条件**：同一工程的五种事实有清楚 owner；每个持久文件字段由现有协议解释；结构/原生/文本前端没有强制循环依赖；候选与源/Artifact 分开；源码导入与真实库完整；冲突、失败和恢复有合法后继；可执行的目标需要真实供给。**现有材料只能对有限支持域检查这些条件，不能从一份文本证明未来任意业务或任意原生程序可无损映射到任何 Target。**

## 相同规则在不同作者表示中的唯一写权

Rule对原生函数的可观察合同是独立要求，并非原生源码本身的镜像。原生实现改变后重验 `callableRef`签名与相交观测，要求仍归作者原文件所有；不允许编译器因实现变差自动缩小Requirement定义域。旧模块、旧运行实例按各自已绑定revision继续解释。

## 可直接生成函数体的简洁编辑投影及其语义来源

当一个作者工程的计算意图属于已支持的有限代数时，作者只表达**自己的事实**：字段结构及值域、数据集合的最大规模、函数入参与结果、条件、运算及关系；无需手写TypeScript循环、校验器、整数溢出防护和文件布局。有限参考纵切允许`shape`、`derive`、`decide`作为`.intent`编辑投影，并允许等价严格JSON作为另一种**互斥作者输入**。`.intent`不是既有`.gift`计算语言，也不是Gift产品必须学习的新编程语言；`derive`中`sum(lines, price * quantity)`等只是合法的有限投影写法，它直接降低到类型化结构运算，不生成第二份可写的AuthorSource。

`derive`中的算法不能从名称推断：`Subtotal`这个名字不意味着折扣含义；`sum`、字段投影与运算表示了真实独立产品事实。若作者只写“最优配送算法”，却未给选择目标、资源/约束、已有合格方法或足够的行为定义，编译器必须返回Need而不是创造似是而非的函数体。对有限Bool/Enum输入，作者可逐格声明完整行为表`decide`而不描述控制流；源项必须恰好覆盖完整笛卡尔积，不能用少量示例冒充完备定义。

本地有限参考解释器位于`fixtures/contract-closure/Gift98/compiler/`。项目不得在同一可写路径同时存放JSON、`.intent`和工作台投影并把它们当作三份独立权威；编辑器显示、结构化存储、内部IR、目标TypeScript分别受SourceSnapshot与读集约束。此参考编辑子集的成功不等于正式`gift.author-text/1`、跨文件Project Codec或现有`.gift`中立文法已发布。
