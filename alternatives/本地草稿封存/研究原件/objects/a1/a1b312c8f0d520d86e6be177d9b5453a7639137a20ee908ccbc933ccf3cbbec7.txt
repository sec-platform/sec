## 2. 实际接合，不是孤立的新 helper

原 `LocalCapture` 仍负责固定物理目录与源捕获，仍保存准确源字节、观察状态、成员和目录身份。现在 file observation 引用已经取得的自有 `Uint8Array`，不再为相同字节先建立额外的 JavaScript `number[]`。

原 `analyzeAuthorModule` 直接调用 `encodeAuthorAnalysisRequest`，而不是保留原序列化路径、另放一个未调用的模块：

1. 在原逻辑调用的 deadline/AbortSignal 下遍历实际请求；精确计算 UTF-8 JSON 消息字节数。
2. 在完整消息缓冲区分配之前检查调用者传输限额及原 64 MiB 硬上限。
3. 只在计数成功后分配目标 Buffer，再直接写入原数字数组线格式。没有把完整源先变成 `number[]`，也不先建立整份 JSON 文本再 `Buffer.from`。
4. 单个元数据字符串的转义继续由标准 `JSON.stringify` 提供；前置计数处理控制字符、UTF-8 多字节、代理对和孤立代理码元，与 JSON 的原编码规则对应。
5. 写入长度不符时拒绝结果，不返回未填满的 Buffer。取消/期限错误沿原异常退出，不伪造空请求或替代结果。
6. 请求仍进入原 `runCommandBytes`；原输入来源检查、返回结果检查、剩余预算续传和进程收尾责任不变。

保留的协议身份仍是 `gift.author-analysis-request/1`。字段含义、观察顺序、可选 interpretation 的有无以及原数字数组载体都没有改成新作者语言。宿主并未据此取得类型正确、方法合格或目标可执行的资格。

这是源代码上消除两类提前分配的改动，不是实测内存/墙钟性能报告。原消息的数字数组扩张仍存在；多轮重传、native 解析成本和宿主整体存活内存预算尚未因此全部解决。

## 3. 实施中纠正了预算接合的一处风险

初稿曾试图把当前 Rust 接收实现的 `4096 + 2 × wireBytes` 和相应 work 公式复制进宿主，提前拒绝原生预算不足的消息。本轮复核后没有采用这条做法。

原因是：当前内核如何收取解析成本，与原 `/1` 线协议的字段及硬传输边界不是同一种合同。宿主允许选择实际内核；把某个实现的内部计费公式固定在宿主，可能让另一个仍符合协议但计费不同的内核遭遇错误拒绝。

最终代码只执行宿主明确拥有的传输分配限额；原生 `work`、`allocation_bytes` 原样传递，既不补满、也不重复扣款。精确的原生接收预测若需要跨进程共享，应由真实版本/能力合同取得依据，不能从一次源码观察升级成永久协议。

未采用的初稿没有进入此次分支提交。对 0 剩余预算的请求，编码器负责准确交换；是否足以执行由原生 owner 裁决，而不是宿主猜测出一个成功结果。
