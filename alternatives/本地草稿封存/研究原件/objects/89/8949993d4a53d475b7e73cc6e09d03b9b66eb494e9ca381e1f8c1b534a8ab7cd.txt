## 1. 核心裁决：开发面可以全面映射到多维结构，但不由维度定义世界

**正确关系**：开发者的操作绑定到原本真实拥有定义/要求/实现控制的准确作者源；通过该源的形成、解释和组合规则产生语义变更；多维问题是对语义变更与后继结果的按需查询、比较和说明；编译器消费真实语义与共同要求，选择合法实现、降低到目标代码并验证。

**错误关系**：把每个 UI 事件都转换成“568维向量”，计算两个向量的距离或差值，以此决定含义变更、行为风险或源代码；把查询回答或标签当成语义和权限的权威。当前568个 D 是异质的查询合同，不是线性独立的数值轴：身份引用、公式、正反证据、时间、执行语义、授权等不能统一相减。一项实际事务甚至可以没有任何现成D编号，只要它有准确的领域形成与解释，也必须能被表示与编译。

现有18域、136组、旧20维面等是查阅方案，可由准确政策/登记归属形成视图；原1786项是历史研究语料和机制线索，不是编译器固定原语；568项则可继续作为高质量可复用的问答和诊断库。对新机制只有实际需要时才补查询，不是先扩全局表。

## 2. 产品的唯一核心契约

设 `A` 为作者源，`κ` 为固定源码语法/解码版本，`K` 为已采用的定义、语义画像、输入/环境、独立要求、版本和必要决定，`θ` 为目标环境与工具链，`ρ` 为源与目标的观察对应：

```text
Decodeκ(source) = A              // 解码准确源，保留 CST、原字节和未知原生边界
K ⊢ A 合法                        // 绑定、类型、角色、效果、实例和作用域检查
⟦A⟧K = (G, AcceptK(A))             // 构造 G 与同一共同实现的可接受集合
p ∈ AcceptK(A)                    // 存在一个实现/策略满足所有接受的硬义务
T ≼θ,ρ p                          // 目标完整制品在准确对应下保持所需性质
A --δ--> A'                      // 授权、前像与保持条件下形成新候选
```

`AcceptK(A)` 不是一个布尔值，也不是所有可能的运行结果的集合；它是满足要求的有型实现/策略集合。系统找不到 `p` 可能是方法缺失、搜索未完成、目标不支持、真实资源不足或已证不可实现，不能合并为一个“失败”。代码生成选择某一个合格 `p`，不要求它与所有其他合格实现算法相同。只有准确源已经具有可执行解释、能取得合格Method、目标完整支持、所需检查通过，才可以作相应范围的“源代码已合格生成”声明。普通世界知识不要求必须编译成程序。

## 3. 数据、语义与权限的真实拥有者：不是七层强制数据结构

| 保留的区别 | 真正的维护责任 | 典型值/结果 | 禁止的捷径 |
|---|---|---|---|
| 作者源码、原生文件与定义 | 原作者源、Definition、Meaning、Requirement、Control、native owner | 源字节、签名、关系、要求、实例连接及版本 | 从UI投影另建一份有独立写权的字段仓 |
| 所指对象和使用发生 | 身份、公开入口、ModuleUse/UseBinding、实例 | identity、Use occurrence、环境/范围 | 同名或同配置就等于同一状态实例 |
| 形式模型和领域事实 | DomainDialect及其真正Provider/Observation | 有型域、转换、模型、记录和适用假设 | 模型内true=现实已经发生 |
| 义务、决定和实现候选 | Requirement/Control、Task、MethodSpec、RealizationBinding | 硬要求、偏好、委派、候选、锁定选择 | 后端擅自改变要求以匹配已有实现 |
| 证明、来源与诊断 | Claim/Evidence/Assurance | 证明、有限反例、支持/反驳、覆盖、时效 | 签名正确或测试通过=原文准确/现实正确 |
| 查询、分类、开发面 | D问题合同、DeveloperDecisionView、派生图/表 | effective/planned/applied/observed，变更影响，Explain | 目录命中=语义具有该性质；客户端有当前写权 |
| 生成、构建、运行与恢复 | 原编译Target、ArtifactSet、Execution/Operation、真正宿主 | 源文件、构建配置、类型检查、运行回执、已生效动作 | 生成文件=部署成功；程序被允许=当前开发任务有执行Grant |

这些是不同内容的责任，不是所有工程必须按此七层持久化，也不要求纯计算有持久Operation、每个变量都有Claim或全域D赋值。

## 4. 开发面的用户行为是一种“有语义目标的事务”

开发面不限于GUI；文本指令、可视连线、结构化编辑、代码重构、CLI/SDK和AI都能进入同一作者/任务操作合同。优先使用既有 `DeveloperDecisionView`，其中 `declaredOrRequested`、`effective`、`planned`、`applied`、`observed` 是派生阶段，真正可写者仍是它引用的原 owner。

正常的入口必须能固定：本次实际主体、真实权限、所指对象与精确修订/前像、目标用途、拟修改的作者区域、操作与参数的意义、所要求保持的内容、任务出口、合法预算/委派。不需要让用户手填这些内部ID；已知内容由客户端取得，不可推定的独立决定才要求作者明确。

**动作合同示意（逻辑结构，不新建一套必须持久化的API）**：

```ts
interface DevActionCandidate {
  target: { ownerRef: string; subjectRef: string; expectedRevision: string };
  authorDelta: unknown;       // 按真正owner的准确EditPlan/源码文法解码，不是any值直接覆盖
  taskRef: string;
  selection: { rootRefs: string[]; semanticProfileRef: string; targetRef?: string };
  expectedPreservation: string[]; // 原Claim/Requirement引用及已接受修改范围
  operationRef?: string;      // 只有真实外部作用或长期事务需要
}
```

一个动作可涉及多项owner并要求原子候选，例如公开函数更名同步更新作者声明、调用者、公开出口与相交资源。无法全部合法应用时保留原候选，不局部发布。对拖动图节点，先确定它是“布局”还是“真实空间部署位置”还是“程序连接端点”；外观事件本身不决定含义。对有损表格的总数由300编辑为400，如果不能确定从哪个来源增加100，则拒绝写回或交给已接受的分配规则，不能猜改。

### 动作到真实含义及后继的路由

| 开发动作 | 直接改变的内容 | 哪些结果可能跟着变 | 哪些不应自动改变 |
|---|---|---|---|
| 新定义／采用已有定义 | Definition与Use occurrence、绑定 | 所有实例化签名、消费者、候选实现与目标源码 | 未采用的库对象、旧运行实例 |
| 连接/断开两个端口 | 具名角色、类型、所有权、传播/调用/效果关系 | 组合约束、可达行为、资源、源/目标使用 | 视觉布局、其他独立连接 |
| 增减“必须满足”要求 | Requirement及其真实对象/时域/输入域 | Accept集合、Method适用性、目标证明、测试 | 原事实与既有真实Grant |
| 固定/偏好/撤销一项实现决定 | 有权Control及当前局部Use | 候选搜索、绑定、目标IR、产物/成本 | 原产品语义及独立硬要求 |
| 编辑共同定义 `≥`→`>` | 该Definition修订 | 采用它的全部有效Use、阈值边界反例、部分目标输出 | 没有引用该定义的对象；源外历史效果 |
| 改纯显示标题、图的自动布局 | Presentation | 视图和可能的可访问性要求检查 | 语义SourceRevision或Claim的含义 |
| 运行/部署/读现场 | 真正Operation及真实Provider回执 | Observed、证据、资格、部分动态决定 | 不写回原作者事实或抹旧历史 |

这里 `authorDelta` 是开发面行为的共同表示，`semanticDelta` 必须由真正的源解释后计算；不是客户端自报“无影响”即可。纯展示动作可以绕过源候选，但产品语义化的展示（安全颜色、公开API名）必须走作者owner。

## 5. “整个多维体系”怎样具体参与每次开发操作

多维结构的正确用法是一个**按需、稀疏、强类型的查询与影响说明空间**。不是为每个对象预先创建568格，也不是一个维度只允许一个选项。一个D合同可以返回类型化集合、关系、模型、公式、判断或有范围的未知；D0560—D0568用于说明该问题的适用性、取得、披露、方法支持、依据、冲突与覆盖等资格。

| 实际操作中要问的问题 | 可复用的已登记D合同（准确举例） | 真正提供答案的拥有者 |
|---|---|---|
| 谁、哪个版本、哪次使用？ | D0008—D0020（身份）、D0018（发生）、D0184/188（修订/前像） | Source、身份与发生图 |
| 定义和端口如何绑定？ | D0033—D0037、D0047—D0052 | Definition、Type、Meaning、Linker |
| 公式/保证究竟是什么意思？ | D0085—D0107（逻辑、模型、证成）、D0108—D0124（类型） | 领域解释、Claim及检查方法 |
| 此次操作是否改变求值、错误、作用？ | D0125—D0147 | 计算/效果合同、真实调用发生 |
| 行为、状态、策略和时间怎样变化？ | D0148—D0183 | 有型状态/行为/时域语义与观察 |
| 哪些依赖失效？能否恢复？ | D0184—D0196，特别D0189/D0190/D0193 | 真实读集、前提/保证、修订及恢复合同 |
| 来源、支持与失败的结论资格？ | D0197—D0233 | Claim、Evidence、独立判断器及覆盖 |
| 作者决定了什么？实现自由还有多少？ | D0294—D0332，特别D0294、D0315—D0319 | Requirement、Control与任务委派 |
| 数据、事务、资源和并发有何影响？ | D0333—D0395 | 相应领域语义、实际资源/交互模型 |
| 谁有权编辑、读取、执行？ | D0396—D0420 | Source owner与真实认证/授权Provider |
| 如何取得实现，生成什么？ | D0421—D0441，尤其D0423/0429/0430/0431 | Method、Binding、工程IR、Target |
| 改动如何回写真正作者源码？ | D0442—D0452，尤其D0444/0445/0451/0452 | EditPlan、SourceMap、native owner |
| 源码怎样构建、交付及运行？ | D0453—D0475 | 工具链/依赖/Target/Artifact/Execution |
| 用户点击到底意味着什么？ | D0487—D0503，特别D0488 | 客户端动作合同与作者含义 |
| 当前答案是否适用、完整、可靠？ | D0560—D0568 | 每项独立资格/覆盖，不能用一个总状态替代 |

维度和值域不是计算的物理根；它们是对当前主体@修订、解释/配置、时间、scope、用途和权限选择的查询。不同D问不同种类对象，不能强行在同一行填写。D0001主题领域和D0558研究覆盖可以形成相关导航，但D0558的覆盖记录不能直接作为D0001所需的`ConceptScheme`参数，这是已发现的不合法直接桥的反例。

## 6. 从用户动作到真实影响：不只是图上顺着边走

**输入**：原准确源、选定根、解释/配置、实际修改前像、权限、适用目标及需要承接的正反证据与完整性切面。

**第一步——语义差额**：按照正确owner解释`A→A'`，区分源字节变但意义等价、定义性扩展、加强/放宽硬义务、改变公共政策、改变模型或观察资格、变更权限、切换实现Binding、目标/工具链变更。只有`SourceDiff`不够；若同一个默认值被改为显式Pin且当前取值未变，未来配置变化时行为仍可能不同。

**第二步——精确依赖**：跨原owner建立带类型、角色和共同条件的联系：定义/采用、变量绑定、共享实例、数据/控制流、调用/效果、前提与保证、资源与寿命、需求与实现、构建与目标、观测与支持、授权与披露、编辑源映射。不是无类型`links[]`。读集须记录正向读取、**缺席/负查找、范围覆盖、默认来源、候选全集、版本/资格、时域和权限**；新增一个对象即使旧文件完全不变，也可能推翻“没有其他候选”的判断。

**第三步——求受影响闭包**：依关系真实失效规律对可能变动的派生值、绑定、证明、目标制品传播；对于支持AND/OR的命题，撤掉一条必需前提只撤销使用它的路径，若另一独立路径仍合格，结论可继续成立。布尔非单调否定、规范优先、资源占用、时间窗、外部读回各使用专业方法。条件性依赖和循环需要正确的固定点/终止规则，不能简单用BFS遍历或“有环就忽略”。

**第四步——计算及比较**：比较真正的有效要求、允许实现集合或其可取得的有限/抽象摘要、候选绑定、目标观察、可追的代码制品、来源资格。区分四种报告：`可能受影响`、`已有证据确认改变`、`已证明在声明条件下不变`、`尚未判断/覆盖不足`。目标输出文本一致不证明来源、依赖或保证未变。

**第五步——有权接受**：只在实际EditPlan的真实owner、前像、范围与权限合格后提交作者修订。编译、证明和物理运行分别使用固定修订；旧实例和在途Operation不被新文件追改。预览产生纯候选，不执行设备动作、安装、发布或数据库写入。

### 可复核的影响结果契约（说明结构，而非新增平行IR）

```text
ImpactResult(
  base, candidate, selectedRoots, interpretationK, targetTheta, permissions
) = {
  changedAuthorDecisions, changedEffectiveMeanings,
  affectedUseOccurrences, dependentClaimsAndTheirQualifications,
  candidateMethodBindings, affectedTargetMembers,
  preservedPartsWithJustification, possibleAffectedButUnknown,
  invalidatedEvidenceAndReason, necessaryAuthorDecisions,
  previewOfSourceAndArtifactDiff, noSideEffects
}
```

一项变更未触及某个目标根，不能因此强制重新生成整个仓库；但“影响可能跨目标”时也不能以局部文件不变作未受影响的证明。缓存键至少覆盖实际读取的源/解释、配置、权限/披露、负依赖范围、目标工具版本和相应资格。

## 7. 实现怎样取得、怎样编译成源码

`MethodSpec`描述实现的功能、允许输入、错误/效果/资源/进展、前提、目标支持和证据；`RealizationBinding`封存一次有权选定的具体实现与版本；`UseBinding`在使用发生点与目标环境下派生实参、接收者、求值次数、ABI、适配与依赖。不能让Target printer自行更换业务算法或偷偷加强要求。

原工程承担完整环节（这是内部依赖而非每次强迫用户走完的固定串行UI）：

```text
已有Task与准确Author Source / native files
  → 原Codec/CST、Linker、Definition/Meaning/Requirement/Type/Expr
  → 选定root/Use，形成有效合同与共同实现义务
  → 方法复用 / 原生绑定 / 允许创作或合成，联合筛选合法候选
  → 固定RealizationBinding与目标使用UseBinding
  → 已有有型工程IR及必要领域方言/边界投影
  → Target lowering（保义、ABI、错误、效果、布局、依赖）
  → 目标语言AST/printer、项目入口/包/资源/构建配置与SourceMap
  → 原生类型检查/构建 + 相交Claim独立核验
  → ArtifactSet及版本化来源；有权限再运行/部署
  → 下一次编辑返回原作者owner，沿影响闭包增量更新
```

核心编译应纯粹消费固定输入；包安装、网络解析、执行测试/部署属于真实获准的外部Operation，不由编译器根据名字暗中运行。外部TS、Java、Rust等语言的完整语义与构建模型可由成熟工具承接；不能要求所有源码必须先变成一种万能图，也不强制已是作者真源的原生代码镜像为一份可写Gift源码。

`p∈AcceptK(A)`表示同一个实现满足共同硬义务。若目标环境`θ`不支持原无限域、整数大小、所有权或作用保证，必须报告具体不兼容或取得已授权的域缩小；不能由降低后的代码回头修改原接受条件。`T≼θ,ρp`按实际观察对应保持公共行为、错误、effects、身份、生命周期、资源、进展及代码资产。方法已找到不代表目标可构建；代码可构建不代表规格真实或现实任务已完成。各状态分别回报。

## 8. 一项完整变更的可检查示例：共享筛选关系 ≥ 改为 >

**准确作者源（示意）**：定义一个对精确整数的公共筛选关系 `qualifies(item, threshold) := item.score ≥ threshold`；视图A和视图B分别采用同一定义但具有自己的输入及阈值，保留列表顺序与重复发生。这是定义和两个独立Use，不是复制两份规则。

**用户动作**：在开发面编辑共享定义的比较符，`≥`改为`>`。客户端取得目标Definition准确修订/前像，显示会改变全部实际使用该定义的Use；若仅要改A，必须形成A局部特化，不得暗改B。由于边界输入`score=threshold`行为改变，属于产品政策变化，不是等义格式化或实现优化。

**语义与影响**：`qualifies`定义新修订，关联到A、B的组合查询/调用、示例断言、源码生成绑定和目标模块。`score>threshold`可以合法作为类型化关系；选根包括A、B时，共同要求仍检查输入有效域、重复、次序、公共出口、错误等完整义务。对`[a(score=5), b(score=5), c(score=6)]`与阈值`5`，旧结果`[a,b,c]`，新结果`[c]`。一项只是显示标题的视图不会进入这条影响路径。

**可能生成的 TypeScript 目标源码（示例说明目标，不宣称目前生产编译器已生成）**：

```ts
// target: TypeScript ES2020+；bigint 保留此模型中的精确整数比较
export interface Item { readonly id: string; readonly score: bigint }

export function qualifies(item: Item, threshold: bigint): boolean {
  return item.score > threshold;
}

export function select(items: readonly Item[], threshold: bigint): Item[] {
  const out: Item[] = [];
  for (const item of items) {
    if (qualifies(item, threshold)) out.push(item);
  }
  return out;
}
```

视图A与B都可调用同一个 `select`，以自己的实际输入和阈值作为实参。该代码展示了给定片段的可实施目标形态；若原需求是面向有小数/NaN/跨线程状态/异步流的输入，不能直接把该函数当合格实现。对`bigint`、输入不修改、顺序与重数分别验证，对不支持目标bigint的环境保留缺口或按合法域重新选择实现。新增/改动的目标文件范围由实际SourceMap与Target依赖决定，不应因为所有根显示相同标签就重写全部工程。

**验收**：旧修订和新修订各自可构建并给出上述边界结果；两个使用点同源；旧运行实例不热改；公共行为的同义/变化部分准确比较；未影响的内容保留；source→target每个受管生成块有可复核映射；若用户撤销的是实现控制而不是产品规则，则应重新选择方法，但查询语义不改变。

## 9. 第二个机制见证：拖动连线 vs 修改共同资源

开发面中看见一个箭头，不知道它是值传递、借用、调用、所有权转移、事件订阅还是纯显示。新连线必须先核端口的真实类型、效果、发生身份、寿命与消费次数。若把两个各占4单位容量的操作接到同一个容量6的共享资源，并且区间重叠，则单项合格却不共同合格；真正的资源方法据相同资源身份、共同时间和数量计算超额。仅改显示布局不改变关系；把两个实例同值配置误作同一资源则会得出错误结论。系统应显示“哪项共同约束破坏、哪些实现选择仍可用、是否需要用户改变公开政策”而不是只报一个红线。

它检验的是同一套身份、端口、组合、效果、共同约束、资格和修改传播机制。不能专门对「资源连接」增加新的通用核心节点；也不能用纯布尔合取代替时序、资源与并发的专业解释。

## 10. 三种运行时层面必须保持不同

| 层面 | 何时有意义 | 合格结果举例 | 不能代签的结果 |
|---|---|---|---|
| 设计/语义 | 作者表达准确且合法，模型与要求可解释 | `K⊢A合法`、可检查合同、准确Needs | 代码必存在，真实世界符合模型 |
| 实现/源码 | 已经选择合格p并保持目标行为/结构 | 完整源代码与资产、构建及相交检查合格 | 发布、运行、设备作用已完成 |
| 运行/现实 | 操作得到真实授权与Provider执行、观察、结算 | 有来源的回执、实际变化或真实失败与恢复 | 来源规则或形式模型因此绝对正确 |

在开放世界下，不可能保证任意新意图都能自动形成真实专业解释、任意规格都有程序实现，或编译器总能决定其合格性。因此完成条件应分“明确支持片段内的正向成功与可信失败”，而非给任何输入都输出某些文件。

## 11. 对现有工作的最小改造顺序（不是另造架构）

**第一个可落实闭环**：挑选原仓库已有作者范本的一组实际共享定义（如共享资料工程），沿真实Codec/Linker/Requirement和SourceMap走通一次“创建/绑定→生成完整可运行TypeScript工程→第二次编辑共享定义→影响精算→增量再生成→构建/独立边界验证→旧版回放”。必须实际生成文件、类型检查/运行，不能只给上述示例代码。

**共同机制推进**：把开发面已有`DeveloperDecisionView`与`EditPlan`绑定到源修订和真实读集，计算正/负依赖、状态与资格；输出的D维只是Explain/筛选和专业问答的投影。把已有关系维护和反例审查接到共同含义/影响/生成消费者，而不是再多放一层全域分类写库。

**目标面与真实生态**：真正目标代码采用原生编译器/包解析器和构建工具；实现搜索必须同时承担输入域、公开ABI、错误、效果、共享状态、成本和安全，Method与Toolchain固定准确版本。超出已支持片段（递归、概率、连续、非单调政策、真实外部权限等）需有真实专业解释或保留准确Needs，不让目标后端私自填默认。

**回归准则**：至少覆盖同名不同身份、同值重复发生、共享定义两处采用、量词顺序、默认→显式同值、D0001/D0558错误直供、义务支持撤回、负依赖变化、源表示等义改动、预算/信息不全、用户无权修改、生成/构建失败、后继影响与恢复；核用户可见的最小决定数与真实生成成功，而不是纯跑大量自洽测试。
