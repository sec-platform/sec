## 1. 本轮结论及适用程度

架构选择不变：TS/Bun 拥有宿主、控制和实际作用，Rust 拥有新生产语义内核；当前新目标工程按已选 Rust 路线交付，旧 TS 能力继续保留；本地 Python 成果作为专业机制、参考和反例来源。改进重点不是增加平台，而是让原有责任通过真实对象、时点与生命周期接通。

本轮最重要的源码事实是：**`gift.author-analysis/1` 是分析报告，不是完整的可降低 IR；真正可复用的类型、主体和效果结构已经在 Rust 内部的 `SignatureResolution` 中。** 因而优先在同一 Rust 任务内继续所选根的资格、方法和目标降低，而不是在 TS 中从报告重建另一套语义，再传回 Rust。

第二项明确风险是宿主传输成本：当前将源字节转换为数字数组，每轮重新序列化全部观察，之后才检查消息上限。现有总量、时限和原预算结算不能被绕过，但它们不等于宿主每次复制之前已经取得内存许可。本轮验证编码量级，没有测到产品内存峰值或墙钟性能，不称其已经造成 OOM。

第三项是将已有的“同代发布、条件提交、失败恢复”规范落实为可检验机制：读者一次持有同代对象；读取保护与回收不可竞争；提交验证实际共享谓词；当前发布同时核准操作代；状态迁移不能仅凭字段形状或代码版本。

这些内容分为四类，不混成一张缺陷清单：

| 类别 | 本轮对象 | 能下的判断 |
|---|---|---|
| 实际接口差额 | 分析摘要与完整 arena 的区别、新源分析与目标生成之间的接合 | 已由准确源码确认；不是报告内容的一个小字段遗漏 |
| 有源码机制的风险 | Array.from、先 stringify 后查大小、全部捕获重放 | 成本路径真实存在；发生频率、峰值和性能影响仍需产品工作负载验证 |
| 已有规范的机制实例化 | 同代读取、共享谓词提交、当前发布、恢复 | 不宣称仓库没有相应规范；模型检查是在说明合格实现必须防住什么 |
| 设计反例与未知 | 旧状态不足以重建新状态、最终 629 成员包未取到 | 反例可复算；没有对应产品实现测试和全量本地代码审计 |

## 3. 真实接合点：保留 Rust 内部语义，不把展示报告升级成 IR

### 3.1 读到的实际数据和调用

`signature_resolution.rs` 中的 `SignatureResolution` 持有原捕获输入，以及 `names`、完整 `TypeArena`、`headers`、`signatures`、依赖、注解环、`BodyAnalysis`、`EffectSummarySet` 和未决/问题。`PreparedAnalysis` 的内部字段是私有的，`close_effects_retained` 返回分析结果和剩余预算；`prepare_input` 消费原 `PreparedInput`。[G02]

`project_input.rs::report_analysis` 只是投影：它输出 `type_count`、签名里的类型索引、主体状态与索引、名称、位置、效果摘要等。它没有输出完整类型节点和全部可降低主体。宿主 `author-analysis-transport.ts` 的 schema 与这个报告对应。[G03,G04]

例如只有 `type_count=1, ty=0`，不能知道节点 0 是 Int 还是 Text。真实完整报告还有输入摘要，摘要能区分来源，但不能从 hash 逆推出缺失类型；保留原输入并重新分析，或者保留对应内部结果，才有解释依据。这是投影信息量的限制，不是声称两个实际完整报告或 hash 发生碰撞。

### 3.2 推荐的最小实现接合

继续复用当前准备/分析职责，形成以下行为链，而不是新设公开工具或万能协议：

```text
准确捕获与解释 → 原 PreparedInput
             → 原 PreparedAnalysis / SignatureResolution ＋剩余预算
             → 本次根、已接受独立义务和共享条件的资格检查
             → 准确 Method / UseBinding 下的专业计划与目标贡献
             → 原产物组合、验证、显示或获准提交
```

关键适配要求：

| 接缝 | 输入和消费者 | 不得偷换 | 失败与恢复 |
|---|---|---|---|
| 准备→共同分析 | 原字节、ModuleUse、准确文法与解释、捕获覆盖、原预算 | 把目录现场或新补取内容偷偷混入旧固定基础 | 冲突/缺项保持；新事实需要明确后继准备态 |
| 共同分析→所选根 | 真实类型/主体/效果、公开终端、要求发生、已接受义务 | 以报告里的索引在 TS 造出另一套类型；按正文名字猜绑定 | 相交未决给原 Needs；独立合格部分可继续 |
| 根→方法 | 实际输入域、角色、数值/重数/效果、准确目标约束 | TypeReady 等于 Callable；参数看起来同形就认可专业含义 | 缺方法/解释/目标分别报告，不补空函数 |
| 方法→降低 | 冻结绑定、受分配结果范围、真实读集、保持条件 | 输出器重新选择语义；正常函数都升级为插件 MethodSpec | 新增源或结构回原形成与检查边界 |
| 内核→宿主 | 所需结果投影、来源、依赖、未决、产物贡献和准确基础 | 将摘要或 `validated:true` 当成 IR/授权凭据 | 严格协议检查；超量、错代、错基础不采纳 |
| 交付→采用 | 当前请求目的、目标前像、完整成员、作用授权 | 生成即运行、当前源码等于已部署状态 | 原事务/操作边界提交，失败保留旧可用状态 |

一次性 CLI 可以在同一 Rust 调用内从原输入重新进入共同分析再降低，不要求立即建设常驻服务。暖 worker 将来有实际收益时，保留内部分析会话；对外句柄必须绑定 worker 实例、输入/解释及代际，重启后失效，不能只传 arena 下标。不要为了共享 `SignatureResolution` 先把它稳定化为永久跨版本 ABI。

`--analyze` 继续其原来的诊断/查询用途，不必增加一份完整 arena JSON。真正的目标请求通过原作用和编译入口取得必要数据。旧 `/2` 有限编译保留准确输入合同；不能把 `design-converged` 改标签或删除未知要求后调用它。

### 3.3 三道检查仍各归原 owner

本轮重读 `semantic-context.ts`，源码明确注明 WeakMap 是本地关联身份，不是 IR 验证或操作授权。它只核 transactionId、对象关联和修订一致性。[G05]

真正的 `validateEngineeringIR` 检查原数据形状、身份、引用、谓词签名、场景缓存及输入/语义摘要，之后 clone/deepFreeze，再构造已验证快照。类型声明中的 unique-symbol brand 也不代替这个运行过程。[G06,G07]

因此接合必须分别满足：专业/IR 语义检查；当前管线对象的真实关联；实际动作与时点的授权/前像。Rust 数据不能被 `as ValidatedEngineeringIRSnapshot` 强转后通过新 WeakMap 登记冒充第一道检查；同样，第一道成功也不能代签第三道。

同时不要把所有新作者 arena 都硬塞进现有 EngineeringIR。公共工程事实按原模型取得合法投影；具体类型、专业计划和目标结构可以留在各自有型表示中。只有真实消费者证明现有规范缺必要区别时，才修改公共模型。

一个具体传输边界是数学整数：现有 EngineeringIR 原图校验拒绝 JS `bigint`，普通 Number 又不能保留任意精度。Rust 中的精确值必须沿相应专业编码或内容引用进入真实消费者，不能任选一个宿主类型后声称已经保义。本文不新增一个与原 Type/值编码竞争的通用数值包装。[G06]

## 4. 资格必须按请求阶段与实际根判定

`prepared` 表示输入准备状态；`type_ready` 和 `body_type_checked` 只说明实现范围内的类型检查。源码本身注明效果、契约、源值画像、捕获和可调用冻结仍有独立责任。[G02] 不能把几个 flag 合成全产品 PASS。

正确的检查单位是“本次请求在准确根、解释和观察范围内需要什么”。只读分析无需构造目标运行证据；生成必须有本次方法与目标合法性；执行另要工具、环境与作用资格。未用到的专业内容可保持未知，但已经独立接受的义务和共同不变量不是‘未被代码引用’就能删除。

附带的布尔模型检查了定义的 128 个组合，发现只看三个准备/类型 flag 会接受 14 个不满足模型生成条件的组合，同时存在无关 Need 不应阻断的组合。这只是说明判定条件不同；这些组合不是已证明全部可达的产品状态，也不是发现了十四个产品 bug。

所有资格复用仍区分两类依赖：纯解释/值结果的依赖，以及本次用途、观察覆盖、授权和新鲜性的依赖。相同计算结果可以继续复用，不意味着仍能发布、披露或执行。资格失效不能反过来把一个历史数学结果改写成错误值。

## 5. 宿主传输：上限必须约束分配之前，而不只是序列化以后

### 5.1 实际路径与现有保护

当前 `LocalCapture` 同时保留 `Uint8Array` 内容和供观察协议使用的 `Array.from(captured)`。根也转换为数字数组。`analyzeAuthorModule` 的每次循环对根、context、全部 observations 和剩余预算执行 `JSON.stringify`，之后才比较 UTF-8 字节数与 64 MiB 上限；每轮启动独立 native `--analyze`。[G04,G08,G09]

已有保护必须保留：根/捕获总量、目录成员和 deadline 有界；请求 scope 有校验；Rust 后继消费上一轮剩余原预算，不能重填；native 入口还为终态保留预算，并在进一步解析前计入请求长度成本。[G03] 不能因为优化传输就撤掉这些边界。

未被这些保护直接解决的是：数字数组、字符串、Buffer 和解析对象在宿主侧已经形成多少同时存活的复制；重复捕获重放消耗多少 CPU/带宽和 native 重新分析预算；消息超限之前是否已有超出允许的宿主分配。当前有总量界，故不能说这是无界增长；但 native 的预算也不是宿主内存预算。

### 5.2 实际可复算的量级

对 n 个三位十进制字节值，紧凑 JSON 数字数组恰为 `4n+1` 字节：三个数字、逗号和两端括号。脚本用四组真实小数据核对长度公式，再按原始规模计算：

| 原始字节 | 这种数字数组，仅载荷 | 与当前上限的关系 |
|---:|---:|---|
| 4 MiB | 16 MiB＋1 | 尚未计协议、上下文、其他源和宿主对象开销 |
| 6 MiB | 24 MiB＋1 | native 的仅请求 2×计费已超过 48 MiB，其他成本还未计 |
| 8 MiB | 32 MiB＋1 | 低于 64 MiB wire 门限仍不代表能进入原 native 预算 |
| 16 MiB | 64 MiB＋1 | 仅载荷已超过 64 MiB wire 门限 |

这是编码条件下的算术，不是宣称真实有效单文件源可以达到这些规模；根本来还有 4 MiB 限制，多捕获、具体字节分布及其他预算也会改变实际门槛。没有从这些数推出 wall-clock 加速或 JS 堆峰值。base64 只在证据中作为编码量比较，不是已采用的协议。

如果每轮只能新发现一个 B 字节源，共发现 d 次，重传旧捕获的这部分累计量为 `B×d×(d+1)/2`，一次传送每份为 `B×d`。当前宿主已经批量取得一轮返回的多个 requests；这里说的是串行依赖发现情景，不能把它泛化为所有工程都按平方增长，也不能把‘每轮批处理’再提成新缺陷修复。

### 5.3 最小修复与扩展门槛

首先在复制和序列化之前核目标 wire 字节上界、host 存活复制预算、native 接收预算及恢复预留；明确原字节、编码字节和运行分配不是同一口径。超限要指明实际阶段，不统一归咎作者语义错误。编码估算须覆盖字符串转义、协议元数据和数组语法；不能只拿 raw byteLength 乘一个未经核验的常数。

随后在允许的真实工作负载中测冷/暖调用、捕获轮数、重复输入量、父子峰值存活内存和中止成本。已有内核 session 能承担时，增量提交新的不可变捕获或内容引用；否则仍可用受管一次性进程和更合适的有界字节传输。迁移传输要版本化并保留明确的旧范围，不让未协商消息被宽松读取。

不默认引入远程服务、共享内存、全量零拷贝或新存储中心。内容摘要用于复用校验，不允许内核凭摘要任意读取外部文件，也不授予跨项目缓存可见性。

## 6. 一致性需要三层依据，不是‘全部有 hash’

第一层是每份捕获字节准确且不可变；第二层是多份内容能否作为任务认可的共同切面；第三层是一次运行读取是否始终使用同一已发布代。

`compileSemanticInput` 的源码已明确：一致读集由调用者负责，独立捕获不会在该函数里变成原子快照。[G10] 因此两份文件 hash 正确并不证明它们曾在现场同时存在。手工构造、编辑器接受的组合候选可以有意义，但其身份是那个候选，不必谎称原子观察到的磁盘状态。

取得共同切面可采用实际平台支持的不可变版本、所有相关写者参加的协调提交或有证明能力的验证机制。外部编辑器不参加锁时，私有锁不能保证它不写；文件 stat 或重读只能取得其真实机制支持的保证。缺少一致性资格时允许历史/受限读取，不签发该用途需要的当前提交资格。

这个区别直接来自已有 D0349 和 U0551/U0836/U1457，不需要发明一份万能 snapshot 元对象。具体来源和本轮接合见第 12 节。[R01]

## 7. 原子发布必须连同读者持有和旧代回收一起设计

### 7.1 原子切换不阻止一次请求混用两代

设活动代 g0 包含 `data0,index0`，g1 包含 `data1,index1`。读者先读 active.data，发布者原子切到 g1，读者再读 active.index，即使每次 load 都原子，也得到从未定义为一个整体的 `data0,index1`。

附带模型枚举保持各方内部顺序的三种历史，朴素设计一种违反同代不变量；一次取得并保持同代对象的方案在这三种中无违反。ArcSwap 官方文档也明确建议相关读取只 load 一次并持有结果，避免不同 load 取得不同对象。[E01]

因此应在原读取上下文中固定一个具体代，其数据、索引、代码布局、状态画像和适用依赖按合同同代解释。不是把整个世界所有资源放到一个对象里，而是把必须共同读取的成员归入实际一致性域。

### 7.2 先拿裸引用、后登记持有仍会竞争

危险顺序为：读者加载旧引用→发布新代→回收者发现无人持有而释放旧代→读者才登记并使用旧引用。独立模型枚举十五种历史，其中一种触发失效。

可接受的设计是在真实同步边界中取得且保护当前代，或者使用已有合格引用/guard 机制；不能手写一个普通指针 load 加稍后计数。模型的修正版在保护时原子重取当前代并登记持有，十五种有限历史中均不使用已回收对象。这不是对 Rust 内存模型、ArcSwap 库或 Gift 实现的全面证明。[E01]

### 7.3 安全持有也会积累成本

持有旧代会延后回收。内存准入必须考虑活动代、仍有消费者的旧代、候选代、共享内容的真实去重和回收工作所需资源。不能通过强删旧代满足名义限额，也不能每轮只看‘当前一个请求’的内存。

模型中的容量 20、每代大小 10 只是合成单位：旧代仍被持有、当前代也存在，再建立一个候选需要 30，必须等待、拒绝或选择合法的更小实现，不能先分配再赌清理。实际保留的是不同内容和生命周期，不应因多份 Arc 引用将共享字节重复计费。

短读取可用短寿命借用；跨 await/长期操作需要真实拥有式引用及相应预算。具体库选型和优化先复用已有机制；没有性能依据，不把无锁结构作为统一前置。公平、最长持有时间、恶意慢消费者和崩溃泄漏需要原操作域的观测与处置；本轮模型只检查安全，不证明最终一定回收。

## 8. 提交串行点：验证真实共同谓词，而不是只比较不同文件

### 8.1 不同文件的 CAS 仍可能共同违规

A、B 分别修改各自的资源预留，容量只有 1。两者同时读到总预留 0，各自拟增加 1；自己那份文件的旧值都没变，因此两次逐文件 compare-and-swap 均可成功，总量变成 2。

六种合法交错中，朴素逐项前像设计四种违反容量不变量；在真实提交点重查共享谓词的设计零种。控制组将容量设为 2，六种历史全部允许两次提交，说明并不需要将一切并行变化全局串行化。

应从实际共享要求决定提交域：公开名称唯一性、同一生成成员的拥有权、容量、跨根 API/状态兼容等。只在该域的短提交动作中验证共同读集/谓词与原前像；昂贵分析和构建在不可变候选上并行。平台已经有可用事务时复用；没有时也不能用独立写锁伪造一个跨域事务。PostgreSQL 对 snapshot 下读写环的说明提供了成熟机制参照，不是要求 Gift 安装数据库。[E02]

### 8.2 先检查、后发布之间仍有空隙

当前资格在检查时成立，源、锁、权限或共享条件可以在发布前改变。要求‘发布为当前结果’的操作必须在实际提交边界重新核其相交基础，不能只携一个曾经通过的布尔。

模型三种历史中，“检查旧基础→源改变→按旧检查发布”触发一次失效；在提交动作中重验则无此失效。这只验证模型里的串行点；真实平台如何让检查与写入不可被相关写者插入，仍须实现和测试。

不是所有源变化都必须撤销历史产物。生成一个钉住旧输入的独立 Artifact 可以合法完成；请求把它设为当前活动结果、写回作者源或执行外部作用，则消费各自的前像和授权。发布当时正确也不表示后续永远保持‘最新’，后续变化需要正常失效/标记旧结果，而不是改写历史成功事实。

### 8.3 字节恢复不让已撤销请求复活

请求 q0 针对 A 开始，后来源改 B 且 q0 被取消；再发一个新请求 q2，源恰好回到 A。旧 q0 的产物 hash 仍匹配 A，不代表 q0 重新拥有发布权。模型在三个交错中找到一种此类失效；比较原请求代/撤销状态后拒绝它。

此处需要的是原操作/请求已有的代际或 fencing，不是把同一业务实体每次重命名。新 q2 可以复用合法的 A 纯值缓存，随后重新取得自己的采纳资格；不要为了防旧请求而清空所有内容缓存。

## 9. 换代码不等于迁移运行状态

原计算保存 `count(all)`，新计算要求 `count(x≥2)`，两者状态格式都是一个整数。输入集合 `{0}` 和 `{2}` 都使旧状态为 1，但新状态分别为 0 和 1。只拿旧整数 1，无论迁移器多复杂，都无法对这两个输入作出不同结果。

脚本枚举 `{0,1,2}` 的八个子集，找到两个旧状态的歧义类。这个有限反例足以反驳‘旧 count 足以普遍重建新 count’，不等于判断 Gift 的实际迁移实现有错。

实际迁移的后继分三类：

| 条件 | 合格操作 | 不合格替代 |
|---|---|---|
| 有保持依据的状态映射，且全部必要信息在原状态中 | 按准确旧/新语义和输入切面构造新状态，验证允许的关系 | 同 JSON shape 就反序列化接受 |
| 原状态信息不足，但有准确原数据/支持结构及固定切面 | 从保留输入重算；必要时处理切面后的已记录变化 | 将当前活数据与历史状态混合，重放外部作用 |
| 所需历史/输入/资格不可得 | 保留旧代或停止相交能力，报告具体迁移缺项 | 猜零、默认值，或悄悄换成另一种语义 |

代码、状态、索引和必要配置要在同一实际切换域关联。持续更新时需要固定起点、准确接续的变更、顺序和终止切换；静止系统可直接使用受控停写窗口，不强迫建设通用流平台。外部作用不随纯状态重算重放。

迁移失败保持旧有效状态；新状态已经取得旧系统不可理解的内容时，不保证可回退旧代码。缓存格式可以丢弃重建，作者决定和不可再生证据不能等同缓存。恢复还需要内容、解释、日志及权限之间一致的切面，不能拼几份各自正确但时间不配的备份。

## 10. 原子可见、持久落盘和业务生效分别结算

命名空间中的原子替换并不自动构成耐断电的多文件提交。Linux `rename` 保证的是其规定的替换可见性；`fsync` 文档明确指出文件持久化不必然持久化包含它的目录项，目录需要相应处理。[E03,E04]

本轮五个抽象崩溃切点模型只说明：若系统承诺 durable，不能在模型仅取得 visible 时就回报 durable。它不是 POSIX/Windows 通用部署配方，也不证明单个目录 fsync 足以覆盖整棵成员树、存储硬件和文件系统故障。

原发布 owner 应明确本次请求承诺的是生成、可见安装、持久安装还是实际业务启用。完整候选的成员先具备所要求的存储条件，再交换活动引用；恢复根据真实操作记录和内容关系解释，而非路径存在即认领。未取得最终持久确认时可报告已可见但持久性未决，不能一律称全部失败，也不能报已经持久。

文件系统提交和数据库/远程 Provider 的业务生效不自动同一原子域。没有真实共同事务时要保留其分别完成、查询和补偿合同，不借一个统一操作 ID 消除物理故障窗口。

## 11. 作者连续修改验收需要拆开三种不同变化

上版选用共享 Definition、两个 Use，其中 A 继承默认、B 显式参数的主例仍然正确。但‘B 固定’只指作者显式固定的那项参数，不冻结共享定义的所有含义。

设共享算法为 `bodyVersion×10 + parameter`，起初默认参数 1，两次使用均返回 11：

| 被明确接受的变化 | A | B | 应解释的差别 |
|---|---:|---:|---|
| 本地共享默认改为 2 | 12 | 11 | B 的显式参数仍为 1 |
| 本地共享算法 body 改变 | 21 | 21 | 二者仍使用被修改的算法，不能以显式参数为由忽略依赖 |
| 远端发布新版本，原锁未改 | 11 | 11 | 新供给出现不等于已接受旧工程升级 |

这是独立算术见证，不是 `gift.author-module` 的已执行 fixture。实际验收应使用仓库现有范本和真实引用/锁，而不是增加上述 toy 表达式作为新语言。

这些例子以新默认本身合法、变更已经准确接受为前提。原规范先检查所有默认的形成、引用与类型：坏默认不能被某次显式实参洗成合法定义；缺键不等于显式 null；列表按整体替换，不默做深合并。把原来省略的参数改为显式相同值，此刻输出可相同，但未来升级的作者选择已不同，不能一律标 NoChange。这些是已经存在的合同，融合应落实消费者，而非再添加同义规则。[G13]

还应检查不同实例不合并、合法历史发行不热改、来源地图更新、未保存缓冲与磁盘前像分别核定。共享定义的语义变化会传播给实际消费者；仅布局或展示变化则按它真正影响的依赖处理，不能都塞进一个全局版本重建。

## 14. 下一轮实施应围绕四个原有责任批次，而不是再造规则

本节是有具体落点的施工设计，不表示本轮已经提交这些修改。每批都保留最小有价值的相交消费者和验证；并行前沿依真实依赖，不能因缺末次 ZIP 阻断全部可完成部分。

**批次一：原 Rust 分析结果继续消费。** 在 `signature_resolution.rs` 的原 retained 分析结果和 `project_input.rs` 的请求处理责任内接通根资格/方法/降低，不修改只读报告为另一份作者源。保留 source、ModuleUse、精确解释、private prepared 边界和剩余预算。验收正例是同一新作者输入经真实方法生成当前选择的 Rust 工程；反例是仅 TypeReady、缺目标 codec 或独立接受义务未满足时不得伪成功。此前 read/names/analyze 与旧 `/2` 准确行为不得退化。

**批次二：宿主捕获与传输准入。** 在 `author-analysis-transport.ts` 原 `LocalCapture.acquire` 和序列化调用点前，落实编码长度/复制/host 预算；错误定位准确阶段。与 native 的原输入账和后继剩余账对齐，不能通过重启回填。先用真实最大支持输入和深导入链测结果，再决定 bytes 载体或 session 差量传输；没有必要立即修改所有工具协议。内核仍不得自行越域读文件。

**批次三：共同目标产物与读取/提交。** 在原产物组合和发布消费者中实现同代数据/索引/代码状态关联、取得保护与回收协议、共享谓词的短提交、请求代检查。现有 `semantic-context` 只继续做本地链接；IR 校验和动作准入不被并入它。按目标平台取得真实路径/进程/文件持久化证据，不以本文模型代签。

**批次四：状态与作者迁移。** 先说明新旧语义改变的到底是源、锁、算法、状态格式还是读集；必要信息足够才映射，否则用准确输入重算或给缺项。三种连续修改必须分别通过。旧模型六代数和本地最新优化仍按原适用域审核，不能因为接缝已通就把算法批量提升为合格。

在这些批次中，冻结候选后再取得所需产品验证，不为每次微编辑运行全部昂贵集合。基线的供应链、独立 oracle、跨平台、回滚/前向修复、版本锁、二进制资产及最终来源恢复都不被本轮的更具体聚焦撤销。
