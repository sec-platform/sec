# 设计与技术文本编修约束

> 此 Skill **不是**任何工程的功能、架构、数据模型、术语、接口或语言规范；不得在此登记项目事实、Kind、字段、版本、阶段状态或实现路径。项目事实只写进项目自己的权威规范。本文件只约束如何研究、决定、设计和书写。

## 工作目标和阶段权限

以本次授权的真实交付目标为准：需要设计时形成可实施的**完整设计文字**，不得把概述、建议、图、测试、检查器或过程统计当作完成。未明确授权实施时，不实现编译器、运行时、自动检查器、测试、CI、性能测量、部署或真实业务副作用。为完成文档而读取、转换、编排和压缩文件，不是产品实现；也不得将机械整理称为完成语义设计。

独立判断现有说法对错，不因为旧稿、用户要求“完美”、主流框架或写作惯性而保留矛盾。接受设计必须指出前置条件、范围、真实机制及适用边界。不能实现的前提必须在设计中明确暴露，不能承诺“通用”“任意”“已闭合”后默默忽略。

## 完整吸收旧文本：内容单位而非文件单位

1. **确定基线**：先取得实际可访问的所有版本、主包、附件和研究源；明确未取得的部分，不能以摘要代替原文。
2. **拆出独立命题**：逐段识别对象、定义、条件、例外、定量参数、关系、算法、操作顺序、失败、恢复、反例、取舍、证据、未知。不以章节标题、H2、文件名或段落数量代表独立内容。
3. **决定位阶**：对每个独立命题判定现行有效、需修正、被替代但含有效部分、历史前提、证据候选、重复或确无用途；尚不能判断的不删。对相反命题依据语义和来源裁决，不让两份“现行”正文同时生效。
4. **迁入唯一正文**：为有效命题指定唯一专业 Owner，融入该 Owner 已有解释流程，保留仍成立的输入条件、特殊分支、参数、完整因果和失败/恢复；调整前后关系与术语，使其不依赖旧文上下文。
5. **处理来源载体**：确认其全部独立意义已有去处后，才删除重复旧载体；保留确需的许可证、外部依据、历史迁移和反例，但与现行规范分离。不能仅因复制到“参考资料”就宣称已经融合。
6. **缺口公开**：如旧资料规模超过实际可精读与融合范围，保存未处理的原文与具体边界，并在交付中直说未闭合；不夸称“全量零遗漏”。

同义的不同说法可合并；不同适用主体、状态、时间、证据强度、异常路径和消费者，即使得出同一建议也不得合并掉差异。高优先级不是低优先级可删的理由。全新发现若有任务价值，反过来更新既有分类和结论。

## 唯一归属的系统设计

先找出业务实际要区分的对象，再区分它的定义、一次引用、实例、所选根、实现选择、构建产物、运行操作、观察和声明的现实结果。关系需注明方向、两端类型、局部/全局作用域、基数、身份、顺序、时间及冲突规则；不能把不同关系塞入万能 `metadata`、`dependencies` 或“全系统对象列表”。共享机制应抽到共同 Owner，专业差异留在各专业合同；复用共用数据形状不等于让共用 Owner 替各专业解释意义。

对于用户能填写的每一个决定，明确谁有权写、必须/可选、默认从何来、是否可导出、什么不能推导。机械可推导值不重复交给作者维护；涉及领域真值、外部授权、算法选择、成本/时效权衡等不可推导事项不由设计师捏造。一个类型/方法/扩展只有拥有语义、消费者和失败行为，才算真的设计了可用接口。

## 具体机制的书写最低要求

必要时覆盖：输入与状态、身份/版本、前置条件、核心转移或映射、输出/副作用、约束、并行与资源、未知/冲突、回滚/补偿/恢复、改动及依赖传播、权限、消费者与替代方案。有实际区别的情形应明确合法、拒绝、未知、需要额外供应三类结果，不把 Schema 形状或名称冒充事实/能力。不能只写“遵守最佳实践”“提供抽象”“未来适配”。没有证据的数值阈值不硬编；可定论的选择不能永久以“方案A/B任选”搪塞。

不同层次不可互相冒充：可写出语法、可精确定义语义、可满足约束、可选择实现、可生成目标、可运行、可取得现实结果，各有独立前提。形式语言的表达能力不自动提供未知事实、权限、外部服务、已供应算法或现实成功。

## 文档信息架构与行文

- **一项权威规范、一处定义**：入口讲职责和链接；详细规则写在该专业唯一规范；交叉引用只陈述对接合同，不复制另一份易漂移的完整定义。
- 按读者与真实操作拆分：开发者源协议、专业机制、跨专业接口、实例、参考证据、历史迁移和工具实现不混在一个散文集合；也不机械按标题行数切文件。
- 段落结构优先“实体/条件 → 机制/判断 → 结果 → 例外”，标题服务于检索；正文尽可能使用定义清楚的领域词汇，不以营销语、含糊形容词、状态宣言和历史版本叠加代替事实。
- 表格适合需要比较相同维度的对象；序列/状态机适合展示有序和反馈关系；公式必须定义变量与单位；示例必须明确哪个规则它表现、哪些条件尚不满足。
- 不重复记录同一个字段在三个文件中的真值，不在工程规范中塞运行日志、计数战报、迁移脚本和每一版历史叙述。
- 文档重构先维护正确语义再追求简洁；内容越多不代表越专业，字节越少也不代表优化成功。

## 审议与交付行为

本阶段用阅读、逻辑反例、条件比较和文档对照来确认设计内涵，不主动开展产品实现测试或编写验证工具。检查写作成品有没有错位和明显缺页属于日常文档编修，不应扩为“验收系统”。对无法确认的旧内容保留并注明用途/未决，不以它可能过时为由删除。交付必须包含实质已修改的现行正文，说明旧知识在何处融合、哪些旧内容确实删去及理由、哪些命题尚未完成裁决。任何未达成的全量覆盖、完备性、执行能力或现实效果都不得声称已经实现。
