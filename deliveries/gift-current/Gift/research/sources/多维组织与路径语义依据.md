# 多维组织、路径语义与来源的依据

本页记录当前共同组织合同采用的直接外部依据及其证明边界；[共同设计][k1]中的组织算法、owner分配和采用选择是Gift的设计，不是这些来源替Gift认证的结论。下列在线文本核对日期为2026-10-04；实际构建必须绑定自己的精确工具链，在线最新版不是旧构建的隐式输入。

## Rust模块路径

[The Rust Reference — Modules][k2]规定mod与逻辑模块树、外部文件查找、path属性和可见名称。未指定path时，外部模块文件路径按模块路径解释；同一模块不能同时用foo.rs和foo/mod.rs这两种外部来源。path相对位置还受包含它的源位置影响。

它支持的判断是：**源码树并非总是无语义的导航**，移动文件必须核实际解释/消费者。它不证明所有源代码移动都会改变业务行为，也不要求逻辑模块与物理文件永久一一对应；可保持解释的移动仍合法。

## Cargo工作区

[The Cargo Book — Workspaces][k3]说明工作区成员、共同锁/构建目录、根配置和成员选择的职责。由此不能把“放进同一文件夹”当成正式workspace成员，也不能让每个生成根各写一份相互竞争的共享配置。这里不采用一个固定resolver版本、edition或feature默认作为所有工程的全局要求。

这支持复用真实Cargo成员/解析合同。它不证明某个Gift包划分已经具有最小构建时间，也不意味着Gift宿主语言必须与目标Rust一致。

## 类型化来源关系

[W3C PROV-DM][k4]是2013-04-30的Recommendation，区分实体、活动、代理、使用/生成/派生、时间与集合等关系。它支持用不同关系保存“谁参与产生什么”和来源，而不是把全部连接都压成一个父子边。

本设计并未决定把Gift内部类型强制改成PROV，也不把一条declared provenance当事实可信或语义保持证明。生成来源、行为保持、观察结果和授权具有不同合同；实际互操作时仍需独立映射与符合性。

## ZIP文件名编码

[Python zipfile文档][k5]说明文件名编码标记以及读取端metadata_encoding的适用范围。这个来源用于解释交付封装检验：正确内容校验不覆盖错误的名字解码。具体前版ZIP是否有此缺陷，由其实际中央目录标记和解码结果证明，不由文档推断。

## 证据不支持的结论

不声明最少层数定理、任意图无损转成一棵树、任意源码可逆、所有当前/未来领域已覆盖、布局搜索全局最优或Gift生产符合性。完整输入上的有限优化若确有证明，可报告其准确目标/候选域/约束；否则只报告已知可行、当前比较和未决。
