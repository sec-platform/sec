# 工程信息组织：来源、采用与边界

本篇保存信息组织设计实际采用的外部命题、固定版本和证据边界。核查日期和版本以各条记录为准；没有逐条日期的早期记录沿用 2026-09-10 的读取范围，不将后续局部核查日期回填整篇。这不是“所有世界资料均已穷尽”的声明。官方功能说明证明公开设计/声明，不证明已部署、实测或独立复现。动态文档后续改变时，仅复核真正依赖改变部分。

资料原文不打包复制；下列都是有限概述与工程采用判断。更广来源管理合同仍在[资料边界][k1]。

## 信息规模、用途与文档组织

<a id="info-source-01"></a>
### 大型工程资料与纯文字规范的不同口径

**来源与版本：** [Boeing：Boeing Moves Huge Volume Of Data To myboeingfleet.com][k2]；2000-07-05公告；事件发生于2000-07-01。

**所读资料支持的命题：** 已读公告正文：新增超过1.5 TB内容，包括数百万工程图、可搜索零件表、超过11,000份部件维护/大修手册及机队报告。

**采用与不能推出的内容：** 仅说明当次新增工程资料的范围，不是当前波音总量，不是纯说明文字大小。Gift容量模型分别计算规范、图纸/媒体、版本和运行资料；不采用公告中的“等价多少本书”作为工程知识度量。

<a id="info-source-02"></a>
### 实验数据不是文档页数

**来源与版本：** [CERN：CERN hits one exabyte of stored experimental data from the LHC][k3]；2025-12-17报道的里程碑。

**所读资料支持的命题：** 已读里程碑正文：LHC经过多年运行累积的已存实验数据达到一EB，长期保存在磁带等存储体系。

**采用与不能推出的内容：** 这不是CERN说明书总量、未过滤传感器全量或当前实际容量实测。Gift将实验/训练/遥测数据路由到其原系统与版本化清单，不能塞进Markdown。

<a id="info-source-03"></a>
### 同一文档关联多个工程而非复制

**来源与版本：** [CERN EDMS：Features][k4]；核对页面所述功能；未实测部署。

**所读资料支持的命题：** 已读Structured data、Lifecycles、Version control、access rights与Search：文档、项目、设备项有分别身份，同一文档可关联多个项目；生命周期和读取权限独立存在。

**采用与不能推出的内容：** 采用多入口对应同一对象、显式版本和权属的机制；不照搬每文档强制审批或单Released版本策略。Gift中运行旧配置与当前新规范可同时合法。文档画像在[同一信息服务多个问题](../../docs/90-治理与参考/维护/文档架构.md#同一信息怎样服务多个问题)保留同对象的多任务入口，并分别保持来源、版本和访问条件；这不表示已经接入 EDMS。

<a id="info-source-04"></a>
### 架构描述按关注点而非唯一图分解

**来源与版本：** [ISO/IEC/IEEE 42010:2022][k5]；仅公开摘要与标准元数据。

**所读资料支持的命题：** 公开摘要区分架构与架构描述，讨论视点、视图及利益相关者关注点；未取得付费完整规范。

**采用与不能推出的内容：** 用于解释为何模块图、时序、部署和信息视图有不同消费者；不声称Gift符合完整标准，也不由摘要制造强制格式。

<a id="info-source-05"></a>
### 按阅读目的组织入口

**来源与版本：** [Diátaxis][k6]；核对范围为体系入口说明。

**所读资料支持的命题：** 页面区分教程、操作指南、参考和解释这几种阅读需要。

**采用与不能推出的内容：** 作为任务导航维度，不复制四份可独立修改的规范。当前尚未可运行的设计范本不能宣称为已验证教程。

<a id="info-source-06"></a>
### 主题和组合映射分开

**来源与版本：** [OASIS DITA 1.3 Part 1 Base Edition Plus Errata 02][k7]；2018-06-19；固定该版本，不声称最新标准。

**所读资料支持的命题：** 已读该版入口、状态及结构目录；它将topic与map作为基础框架，并提供其他专项内容版本。未逐条审计全部子页面。

**采用与不能推出的内容：** 采用独立信息单元与按用途组合的思想，不强迫Gift迁到XML/DITA，也不把普通章节细化成每句一个永久对象。条件化出版不能隐藏对目标仍生效的错误/限制。该约束落在[阅读组合的消费规则](../../docs/90-治理与参考/维护/文档架构.md#同一信息怎样服务多个问题)：先固定选择范围，再保留相交前提、异常和未决；无法判定适用性不冒充“不适用”。这是 Gift 的设计采用，不能从已读 DITA 目录推出本工具已经实现过滤正确性。

<a id="info-source-20"></a>
### 大型源码库不推出人类规范行数目标

**来源与版本：** [Potvin与Levenberg：Why Google Stores Billions of Lines of Code in a Single Repository][k8]；2016 CACM；仅作者机构公开摘要。

**所读资料支持的命题：** 已读机构页面摘要；完整ACM页面未取得。

**采用与不能推出的内容：** 只保留大规模共享源码与工具协同的研究线索。未核到的TB数字、团队效率和成本不得补写；也不能用代码总量推导Gift应该多少行Markdown。

### 采用后的责任位置与竞争方案

[总体信息结构][k9]负责选择及成本边界；[对象与基线][k10]负责身份/关系/版本；[接入与检索][k11]负责解析、覆盖与披露；[保留恢复][k12]接回原GC与持久化合同。这些不是来源文档的自动翻译，更不是对上述标准的整体合规声明。

没有新信息服务、只使用普通目录/Git/现有构建与制品工具，是保留的最强低成本替代。若实测无法减少找错版本、重复维护、恢复缺项和协作成本，就不增加独立平台。相反，跨权属合作、规范变体、不可复验数据、发布/恢复义务确已出现时，普通文件名不能承担这些合同，才增补相应持久元数据和提供者能力。源格式、图数据库、集中服务的具体采用是条件性决定，不升级为长期产品目标。

### 标识、位置片段与版本敏感消费

**读取日期：2026-09-10。** [RFC 3986（2005-01）][k45]第1.2.2节区分标识与交互，第3.5节说明fragment按表示/媒体类型解释，标识存在不意味着发生取回或内容可达。用于本库精确区分文件存在、章节定位和真正消费，不把URI形式当权限、程序正确性或历史内容复现证明。

[W3C Web Annotation Data Model，2017-02-23 Recommendation][k46]第4.2.4—4.2.5节定义文本引用/位置选择及其上下文：位置选择随编辑变化而脆弱，建议用State识别正确表示。用于说明行号、数组位置及摘录不能单独确定跨修订连续性；并不要求Gift采用JSON-LD、该规范全部编码或任何远程注释平台。

固定快照中的结构发生位置与逐根绑定消费按Gift产品合同解释；这两项外部规范支持标识、定位与真实消费的局部区分，不为本设计包建立旧址兼容要求，也不验证全部语义等价或产品实现。当前文档定位见[文档重组][k47]，产品规则见[用途解析][k48]。

## 构建、证据、变化与观察

<a id="info-source-13"></a>
### 构建缓存与来源证明在信息结构中的边界

[Bazel动作缓存与内容存储证据][k49]区分动作键到结果元数据的归属关系与按内容寻址的输出字节；本页只消费这一差别，用于说明“内容相同”不能替代产生关系、输入/工具范围、写入权限或复用资格。缓存字节自洽不自动证明计算归属正确，缓存也不取得作者或执行权威。

### 运行剖析、精确血缘与运行变体标准的补充依据

**所读资料支持的命题：** Profiles在2026-03进入public Alpha，作为与traces/metrics/logs并列的连续性能观测信号；profile承载stack traces及资源/执行值。

**来源与版本：** [OpenLineage Lineage Job Facet 1.53.0][k62]；核对日期：2026-09-22。

**所读资料支持的命题：** Lineage Job Facet允许每个target列出真实sources，明确避免把RunEvent的每个input自动连接到每个output形成虚假笛卡尔积。

**采用与不能推出：** 用于校准数据lineage的有方向精确边；一次run的成员集合、代码调用依赖、schema迁移历史和业务因果仍是不同关系，只有较弱事件边界信息时不能升级为逐output来源。

**采用与不能推出：** 用于反证“feature flag读取天然纯”。只有实际Provider/hook合同排除Effect才可作为纯查询；evaluation、用户exposure和实验因果结果仍分别观察。

### 告警、通知与事故状态的补充依据

#### Prometheus Alertmanager

**来源与版本：** [Alertmanager][k65]与[Alerting overview][k66]；动态官方文档，核对日期：2026-09-22。

**所读资料支持的命题：** Prometheus规则产生alert，Alertmanager另负责grouping、deduplication、routing、silence和inhibition。silence/inhibition抑制通知，不等于改变产生alert的底层条件。

**采用与不能推出：** 用于分离Measurement/Alert/Notification；通知被抑制或成功发送不证明故障恢复、incident关闭或根因成立。

#### Google SRE incident management

**来源与版本：** [Google SRE Incident Management Guide][k67]；动态实践资料，核对日期：2026-09-22。

**所读资料支持的命题：** incident response包含协调与remediation，事故解决后再开展postmortem，复盘影响、过程与改进，并把corrective action继续进入后续工作。

**采用与不能推出：** 用于把Mitigation/Recovery/Postmortem/CorrectiveAction分离；该实践资料不是Gift事故状态机的唯一标准，也不证明任意postmortem中的root-cause结论正确。

### 在线实验的assignment、trigger与exposure边界

#### Microsoft Experimentation Platform：counterfactual logging 与 triggered analysis

**来源与版本：** [Patterns of Trustworthy Experimentation: Pre-Experiment Stage][k68]、[Post-Experiment Stage][k69]、[Data Quality: Fundamental Building Blocks for Trustworthy A/B testing Analysis][k70]；核对日期：2026-09-22。

**所读资料支持的命题：** treatment assignment必须在分析数据中完整且对随机化单位保持一致；并非所有被assignment的用户都会真正受到功能影响。对于triggered/affected分析，Microsoft ExP通过counterfactual logging在control侧识别“如果在treatment是否会被影响”的同类流量，以避免只在treatment侧按实际曝光筛选造成不可比人群；trigger正确性还需通过SRM、triggered complement等诊断。

**采用与不能推出：** 用于把Assignment、RuntimeVariantDecision、Exposure/TriggerObservation、MetricObservation和CausalAnalysis分开。counterfactual flag仍是测量/方法产生的Observation，不自动成为真实用户曝光；triggered分析也不是默认比intent-to-treat更正确，目标estimand、选择规则、缺失与干扰须由ExperimentPlan固定。

### 分布式Trace与Context传播的补充依据

#### OpenTelemetry Trace API 与 Links

**来源与版本：** [OpenTelemetry Tracing API][k71]与[Specification Overview][k72]；动态规范，核对日期：2026-09-22。

**所读资料支持的命题：** Span有SpanContext、零或一个parent、零或多个links、start/end、events/status；links可表达跨trace、batch及scatter/gather等非单一parent关系。Span必须显式end，但该API语义只结束Span记录生命周期。

**采用与不能推出：** 用于把trace parent/link与GIFT真实Request/Operation/Effect关系分开；span end不证明目标工作settled，link也不自动证明业务因果或权限。

#### W3C Trace Context 与OpenTelemetry传播/Baggage

**来源与版本：** [W3C Trace Context][k73]、[OpenTelemetry Context Propagation][k74]、[Baggage API][k75]；核对日期：2026-09-22。

**所读资料支持的命题：** W3C标准化traceparent/tracestate传播并允许在安全边界重启trace；OpenTelemetry明确提醒incoming trace header可能被恶意伪造，外发context/baggage可能泄露内部信息，Baggage可跨进程传播且应避免credential/API key/PII，并要求能够在不可信边界清空。

**采用与不能推出：** trace/baggage只作为可验证或可净化的传播Observation，不成为Principal、Grant、tenant identity或业务operation identity；无法取得span仍不能由采样/传播机制推出实际调用不存在。

### 网络packet、stream与connection关系的补充依据

#### RFC 9293 TCP

**来源与版本：** [RFC 9293 Transmission Control Protocol][k76]；Internet Standard，核对日期：2026-09-22。

**所读资料支持的命题：** TCP以sequence/acknowledgment管理字节流，并通过retransmission处理丢失；duplicate segments可以因网络/TCP重传到达。ACK描述的是TCP序列空间的接收进展。

**采用与不能推出：** 用于反证packet/ACK等于应用request或业务完成；TCP交付字节不证明更高层handler、事务、消息或外部Effect已完成。

#### RFC 9113 HTTP/2

**来源与版本：** [RFC 9113 HTTP/2][k77]；Standards Track，核对日期：2026-09-22。

**所读资料支持的命题：** 单一HTTP/2 connection可以同时包含多条stream并交错frame，每个request/response exchange关联自己的stream。

**采用与不能推出：** connection identity不能代替request identity；抓到一个TCP连接也不能推断只有一次HTTP操作。

#### RFC 9000 QUIC

**来源与版本：** [RFC 9000 QUIC][k78]；Standards Track，核对日期：2026-09-22。

**所读资料支持的命题：** QUIC在connection内提供多条stream，并使用connection ID支持network path migration和NAT rebinding场景；IP/port不是连接稳定身份。

**采用与不能推出：** 用于要求网络Provider区分connection generation、path和stream；地址改变不能单独推出新业务session，相同connection也不能代替其内各application operation。

### Heap snapshot与运行内存观察的补充依据

#### Chrome DevTools Heap Snapshot与Memory术语

**来源与版本：** [Record heap snapshots][k79]、[Memory terminology][k80]、[Memory panel overview][k81]；动态官方文档，核对日期：2026-09-22。

**所读资料支持的命题：** Chrome heap snapshot展示某JS VM可达对象的内存图，官方说明取snapshot会先进行garbage collection；工具区分shallow size、retained size、retainers/dominator、snapshot comparison、allocation instrumentation和sampling。文档也说明DevTools console/debugger本身可能保活对象，JS heap之外还有renderer/native等内存。

**采用与不能推出：** 用于把snapshot方法、root model、retained派生量、instrumentation影响和其他memory domain分开；单次retained size不自动证明leak或RSS可释放量。

#### Chrome DevTools Protocol HeapProfiler

**来源与版本：** [CDP HeapProfiler domain][k82]；协议域标Experimental，核对日期：2026-09-22。

**所读资料支持的命题：** CDP提供collectGarbage、takeHeapSnapshot、allocation sampling、heap-object tracking及HeapSnapshotObjectId/Runtime.RemoteObjectId映射；sampling profile明确是采样统计而非全量分配账本。

**采用与不能推出：** Provider object id只在对应browser/runtime profiler合同内使用，不升级成跨重启/跨运行Gift对象身份；HeapProfiler结果也不能替代native/GPU/外部资源生命周期证据。

### 文件监视器与增量观测的补充依据

#### Node.js 26 fs.watch caveats

**来源与版本：** [Node.js v26 fs.watch][k83]；核对日期：2026-09-22。

**所读资料支持的命题：** Node明确说明`fs.watch`跨平台行为不完全一致，network/virtualized filesystem可能不可靠，callback filename并非总能提供；Linux/macOS按inode watch，原路径删除后重建新inode时旧watch继续观察旧inode。

**采用与不能推出：** watcher事件只能触发重新观测；同路径或eventType不能直接建立对象连续性、当前内容或完整coverage。

#### .NET FileSystemWatcher

**来源与版本：** [FileSystemWatcher Error][k84]、[Created event remarks][k85]；.NET当前文档，核对日期：2026-09-22。

**所读资料支持的命题：** 常见文件操作可以产生多个change/create/delete事件，其他软件也可引入额外事件；大量变化可使内部buffer overflow并丢失目录变化。

**采用与不能推出：** event count不是编辑次数，overflow后必须把增量coverage视为失效并重新枚举所需范围。

#### Watchman clock/since与fresh instance

**来源与版本：** [Watchman query/since][k86]、[clock][k87]；动态官方文档，核对日期：2026-09-22。

**所读资料支持的命题：** `since`查询会在cursor来自不同Watchman instance或不可用时标记`is_fresh_instance`并改变返回语义；clock还提供同步cookie方式等待此前通知被观察。

**采用与不能推出：** 用于设计baseline/cursor/reconcile；fresh instance不是普通增量，也不能把`empty_on_fresh_instance`产生的空列表解释成没有文件变化。
