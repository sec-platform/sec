# 不可达、冲突、假设与拒绝

## 不可达、冲突、假设与拒绝的推理分类

### 目的与规范边界

本节描述设计、证明与准入诊断时需要区分的**推理分类和分析维度**，不是 Gift 的正式 IR、wire schema 或新的持久化真源。它用于防止把“没找到”写成“没有方案”，也防止把当前证据/预算不足误升级成不可满足证明。

如果某个消费者需要可持久、可交换或可版本化的诊断对象，必须由该消费者所属的规范 owner 定义正式 `Result / Assessment / Record / Claim / Evidence` 合同并显式引用这里的推理类别；理论页本身不签发可执行 schema。

### ResolutionBoundaryAnalysis 的类别

一次分析可以落入一个或多个相互不冒充的类别：

| 类别 | 表达的事实 | 最低保留信息 | 不能推导 |
|---|---|---|---|
| `Infeasible` | 在声明的模型和不可放宽约束下已有无解依据 | constraint core、proof class、不可放宽约束、可放宽候选、利益相关影响、重开条件 | 不能推出更强模型/改变约束后仍无解 |
| `DecidabilityBoundary` | 问题类别存在已知可判定性边界或 reduction | property class、input language、known boundary/reduction、可判定子片段、近似和运行时/人工替代 | 不是某个具体实例失败的证书 |
| `ResourceBoundedUnknown` | 当前搜索预算耗尽但仍有未探索前沿 | 已探索区域、incumbent、上下界、resume token、算法与未探索前沿 | 不能写成 infeasible 或 no solution |
| `ObservationInsufficient` | 当前观察覆盖/新鲜度/来源不足以支持所需判断 | 缺少的 coverage、time/source/basis、可取得的新观察与阻断范围 | 不能把缺证据写成反证 |
| `CoordinationUnattainable` | 在给定参与者、同步、故障和通信假设下无法取得所需协调保证 | 失败假设、必要协调条件、允许降级和重开条件 | 不能推广到改变故障/通信模型后的世界 |
| `AssuranceInsufficient` | 现有 Evidence/方法强度不足以支持目标 Claim/Verdict | 缺失 Claim-relative Evidence、独立性/覆盖差额、下一合法验证动作 | 不能写成产品语义错误或运行失败 |
| `NormativeConflict` | 多个适用 authority/法域/权利或不可补偿约束冲突 | authority、jurisdiction、rights、hard constraints、制度程序、安全默认与申诉路径 | 不能由普通偏好或实现评分覆盖 |
| `IrreversibilityUnacceptable` | 可执行动作的不可逆性、恢复能力或损失边界不满足准入条件 | effect scope、recovery boundary、irreversibility、损失主体、替代方案 | 不能只因“能执行”就转成允许 |
| `ArchitectureRefusal` | 体系在当前前提下拒绝承担不可控/不可恢复/治理复杂度过高的能力 | refusal reasons、unsafe/uncontrolled effects、failed assumptions、unavailable recovery、governance complexity、safe subset、partition/simplification options、minimum reopen conditions | 不能被普通 override 消除 |

这些类别是推理分类；它们可以被具体 owner 映射成诊断、Assessment、Claim/Evidence 缺口或准入结果，但映射必须显式，不能让类别名称本身取得 writer authority。

### 假设分析

假设不能隐藏在自然语言脚注或代码注释中。对会影响结论的假设，分析至少保留：

- proposition；
- source 与 rationale；
- scope；
- validation evidence（若有）；
- confidence/proof class；
- dependents；
- expiry/invalidation 条件；
- falsifier；
- residual risk。

这些字段是理论分析维度，不在本页定义任何假设 IR、持久记录或其他当前 wire type。若工程需要可持久假设实体，必须由真正拥有其生命周期的规范 owner 定义身份、revision、writer、失效和迁移。

### 传播与重开

Resolution-boundary 分析可以在意图、观测、模型组合、求解、实现解析、验证和执行准入任一阶段被产生或引用。下游只能：

- 保留其适用 scope 与 basis；
- 证明某个下游切片与该边界无关后缩小阻断范围；
- 通过新事实、放宽/改变合法约束或有权决议重新打开；
- 显式映射成该 owner 的诊断/Assessment/Claim/Evidence 缺口。

不能把 boundary analysis 自动转换为低置信成功，也不能让一个局部未知使无关编译、草稿保存或只读分析全部停机。

### 接口投影

CLI、API、IDE 和 Agent 应保留稳定 reason code、主体、basis、可得证据、可用子集、阻断范围与下一合法动作。人类摘要不能删除已经成立的不可达依据，也不能把 `ResourceBoundedUnknown / ObservationInsufficient / AssuranceInsufficient` 文案写成“无解”。

如果接口需要稳定序列化形式，序列化的是其规范 owner 的正式诊断/Result/Assessment/Claim 引用，而不是由本理论页生成一个通用 `NonSolution` wire object。

### 验收：不可达、冲突、假设与拒绝的推理分类

- infeasible、unknown、insufficient、conflict、irreversibility 与 refusal 在语义上可区分；
- reason/basis/evidence/reopen condition 不因跨层投影丢失；
- 未知与证据不足不会被 catch-all error 或低置信成功覆盖；
- 局部问题可以精确阻断依赖切片而保留无关功能；
- 新事实或合法决议可以按失效依赖精确重开；
- ArchitectureRefusal 不能被普通 preference/override 消除；
- 理论页不声明 Gift IR 或当前 wire schema；任何持久形式都必须回到唯一规范 owner。

### 类别边界与实例结果分开

`DecidabilityBoundary` 保留的是问题类别的已知理论边界，属于分析元数据，不是某个实例不可编译、不可满足或不能证明的证书。具体实例另由其 owner 记录 proved/refuted/unknown 及证据。

同理，`ObservationInsufficient`、`ResourceBoundedUnknown` 和 `AssuranceInsufficient` 表示当前观察、预算或保证证据不足；只有 `Infeasible` 才要求在声明模型内具有相应无解依据。阻断范围由真实输出依赖和保证义务决定，不因一个研究诊断使整项工程停摆。
