# 覆盖不可证明与竞争架构

## 开放世界覆盖不可证明与挑战集过拟合

<a id="1-根裁决-5"></a>

### 根裁决：开放世界覆盖不可证明与挑战集过拟合

任何有限问题目录、事故库、测试集和跨域挑战集都不能证明“未覆盖问题不存在”。更危险的是，架构可以逐渐适配已知挑战，形成与机器学习测试集过拟合同构的状态：

- 每个历史事故都有对应规则；
- 每个已知测试都通过；
- 新机制一出现，根模型仍需重写；
- 团队只寻找能被当前 ontology 表达的问题；
- 不可测或不方便的问题被排除；
- 挑战来源共享同一工程文化和假设。

### Coverage 推理直接消费唯一 `CoverageAssessment`

当前可执行/可交换的字段合同唯一由[覆盖成熟度与验收范围](../../docs/60-保证与证据/保证/覆盖成熟度与验收范围.md#coverageassessment)维护。理论反证直接解释其中的 `purposeAndSystemDefinitionRefs / challengeCorpusRefs / sourceLineages / mechanismFamilies / environmentsAndScales / stakeholdersAndJurisdictions / searchStrategies / holdoutChallenges / blindSpots / residualUnknownBudget / validityHorizon / reopenTriggers`，不再定义 `CoverageReasoningDimensions` 影子对象。

来源类别分布和独立性由 `sourceLineages + blindSpots` 推导；未覆盖前沿属于评估结论/未知预算，不建立第二份可写 frontier 字段；时间边界和重开条件由 `validityHorizon + reopenTriggers` 唯一表达。

只允许声称：

```text
在这些来源、机制、环境、时间和搜索策略下，尚未发现新的决定性缺口。
```

不允许声称：

```text
所有未来问题已覆盖。
```

### 挑战集过拟合检测

需要专门测试：

- 留出领域和事故家族；
- 盲评未参与设计的案例；
- 对机制做名称和表面结构变换；
- 从完全不同学科引入问题；
- 让攻击者专门构造当前 schema 无法表达的状态；
- 对已知案例移除关键词，检查是否仍能识别机制；
- 在不更新 Core 的前提下加入新领域；
- 检查系统是否用 `other/unknown` 掩盖缺口。

### 来源独立性

多个网页转述同一事故只算一个来源 lineage。挑战语料必须轮换：

```text
formal impossibility results
real incident postmortems
negative research results
failed migrations
hardware errata
legal conflicts
user support failures
organizational bypasses
adversarial security reports
field telemetry
unpopular minority cases
successful but extremely costly systems
```

### 未知未知的响应能力

无法预测具体新机制时，仍可设计：

- blast-radius 限制；
- reversibility；
- independent readback；
- residue preservation；
- emergency isolation；
- external challenge intake；
- schema evolution；
- conflict-tolerant knowledge；
- conservative effects；
- post-incident root-model rollback。

这些是未知响应能力，不是未知问题覆盖证明。

### 未知预算的理论解释复用唯一 `ResidualUnknownBudget`

未知预算的唯一结构 owner 是[覆盖成熟度与验收范围](../../docs/60-保证与证据/保证/覆盖成熟度与验收范围.md#residualunknownbudget)中的 `ResidualUnknownBudget`。理论分析不再定义平行字段表：`affectedSubjects / requestedEffects / potentialSeverity / reversibility / observationBlindSpots / modelUncertainty / commonCauseExposure / toleratedUnknownClass / acceptingAuthority / expiryAndReassessment` 直接按该对象解释。

挑战新鲜度不是另一持久字段：挑战来源或环境分布变化使既有 Evidence/预算的 `expiryAndReassessment` 条件触发，并通过来源与 challenge record 判断是否需要重评。所谓 effect severity 也不另造同义字段，归入 canonical `potentialSeverity`，同时结合 `requestedEffects` 判断实际暴露。

高风险不可逆操作不能接受无界未知；低风险、可撤销、隔离良好的操作可以在显式预算内运行。理论页只解释这些变量为何影响可接受性，不签发第二份预算记录。

### 分布变化与新攻击

未来环境可能改变：

- 语言和工具链；
- 硬件和微架构；
- 攻击者能力；
- 组织激励；
- 法律；
- 用户群体；
- 资源价格；
- AI 模型；
- 供应链；
- 网络和地缘环境。

旧 Evidence 的有效性必须有时间和分布边界。

### 覆盖关闭的更严格形式

本篇保留开放世界下“关闭只能是条件化关闭”的推理，不复制第二份 `CoverageEpochClosed` 公式。现行判据由[覆盖成熟度与验收范围](../../docs/60-保证与证据/保证/覆盖成熟度与验收范围.md#条件化轮次关闭)唯一维护：已接纳挑战要有处置、关键接缝不能无 owner、holdout 不能暴露未处理根失败、来源多样性与未知预算必须满足当前声明，并且重开触发仍有效。

即使规范 owner 判定成立，也只表示该 epoch 的条件化关闭；理论页不能用近似措辞签发另一种关闭状态。

### 反例驱动的根回退

新挑战若推翻：

- identity law；
- authority law；
- observation model；
- effect model；
- assurance composition；
- locality assumption；

必须回到相应根合同重建所有依赖者。禁止只在 challenge 文档末尾添加例外继续维护旧架构。

<a id="10-验收-3"></a>

### 验收：开放世界覆盖不可证明与挑战集过拟合

- 挑战集有 holdout；
- 来源 lineage 去重；
- 每轮包含负面结果和失败案例；
- 旧模型可被正式推翻；
- 残余未知有预算和接受人；
- 新分布触发 Evidence 陈旧；
- 不存在 `allProblemsCovered` 状态。

## 最强竞争架构与不建造方案

### 为什么必须比较“不建 Gift”

任何架构评审若只比较 Gift 内部变体，就已经锚定了“必须有一个统一通用工程编译器”。最强反方是：问题可能更适合由现有编译器、领域工具、人工工程流程和小型 AI 助手组合解决；中央语义系统会增加成本、延迟、模式迁移和新的单点故障。

因此 `DoNothingOrUseExistingTools` 必须作为正式候选，而不是被排除在设计搜索之外。

### 竞争架构

| 候选 | 核心机制 | 优势 | 决定性不足 | 适用边界 |
| --- | --- | --- | --- | --- |
| 不建统一平台 | 现有 IDE、编译器、测试、Git、人工审查 | 成本最低、成熟、认知负担小 | 跨工具真值、恢复、权限和长期演进分散 | 小型、低风险、短生命周期工程 |
| Agentic IDE | 模型读取代码并产生补丁 | 交互快、产品闭环短 | 是否缺少相应语义、权限、事务和证据，依据具体合同与必要事实核查；需要实际结果时再测，不能只按品类断言 | 可逆、低风险、人工监督变更 |
| 规则化代码生成器 | 模板、Schema、DSL 到源码 | 确定、易验证 | 只能覆盖预定义模式，Brownfield 能力弱 | 结构规则稳定的领域 |
| 模型驱动工程平台 | 中央模型生成多个制品 | 一致性和复用强 | 容易形成万能模型、人工代码 round-trip 困难 | 受控领域和封闭生命周期 |
| 知识图谱加工作流 | 图存事实，工作流执行操作 | 可查询、来源和协调能力强 | 图不自动提供语义、可判定性和物理事务 | 组织知识和跨系统编排 |
| 证明助理中心 | 规范与证明驱动实现 | 高保证、边界清楚 | 成本高、模型—现实映射和工具链仍需信任 | 小型高风险核心 |
| 微内核式工程服务 | 多个独立工具通过窄协议组合 | 故障隔离、可替换 | 组合保证和全局影响仍困难 | 多团队大型系统 |
| Gift 最小工程闭包及条件扩展 | 工程语义编译、受控效果和保证；需要时加入模型组合 | 统一跨阶段因果链，支持存量与生成 | 复杂、实现成本高，可能过度治理 | 长期、高风险、跨语言、Agent 密集工程 |

### 不存在绝对赢家

候选优劣取决于：

- 工程寿命和变化率；
- 失败后果和不可逆性；
- 语言、平台和 Provider 数量；
- 存量工程复杂度；
- 自动化写入比例；
- 合规、审计和恢复要求；
- 团队规模和认知能力；
- 可接受延迟与成本；
- 是否存在正式模型；
- 外部世界是否可观测和可控制。

因此顶层产品选择本身也是 `PurposeBoundDecision`，不能由 Gift 自身预设自己获胜。

### 何时应拒绝采用 Gift 全栈

满足下列组合时，优先采用更简单方案：

- 单仓、单语言、单团队；
- 修改全部可人工审查且容易回滚；
- 无高风险外部效果；
- 现有工具已经提供可靠静态和动态验证；
- 语义建模成本超过重复问题成本；
- 没有跨语言、跨 Provider 或跨法域要求；
- 系统生命周期短，不需要长期迁移和历史解释；
- Gift 的控制面成为主要故障源。

### 何时 Gift 才可能形成支配优势

- 多语言、多模型和多目标共存；
- 大量存量工程需要重建、采纳和局部治理；
- Agent 或自动化持续产生工程效果；
- 需要跨源码、数据、部署和运行的端到端追踪；
- 错误恢复、审计和不可逆风险很高；
- 传统工具反复产生状态漂移、隐藏依赖和假验证；
- 新 Provider、语言和规则的接入频繁；
- 需要把无解、未知和规范冲突作为产品结果。

### 分拆退出策略

若统一 Gift 平台不能证明净收益，仍应保留可独立采用的组件：

```text
Workspace Observation
Dependency Evidence
Engineering IR
Implementation Resolution
Mutation Transaction
Verification Evidence
Architecture Refusal
Migration and Retirement
```

每个组件使用公开窄合同，能够被现有 IDE、CI、构建系统和人工流程单独消费。统一产品失败不能迫使这些机制一起废弃。

### 比较实验

对同一真实工程任务比较：

```text
现有工具 + 人工
Agentic IDE
领域生成器
Gift 最小闭包
Gift 完整闭包
```

测量：正确性、漏检、假通过、修改范围、返工、认知成本、执行成本、恢复时间、迁移成本、用户完成率和长期维护。Gift 只有在声明适用域内形成非支配或有权接受的净优势时才应被采纳。

<a id="8-架构反转条件-1"></a>

### 架构反转条件

出现以下结果时，终局架构应从“统一平台”反转为“联邦组件库”：

- 通用内核持续增加领域分支；
- 多数真实操作只消费极小子集，却必须承担全局控制成本；
- 模型同步成本高于避免的缺陷；
- 真实工程师频繁绕过控制面才能工作；
- 统一数据库或协调器成为可用性和安全瓶颈；
- 组件组合通过窄协议即可达到同等保证；
- 用户结果没有相对简单方案的可测改善。

### 比较表的证据地位

上述表格是机制假设与实验候选，不是截至当前日期对市场全部产品做过测试的事实表。现有工具可以通过集成补上某些短板，Gift 也可能无法实现预想优势；费用、成熟度、支持能力、实际恢复和用户结果必须使用指定版本与同任务基线验证。未作指定版本与同任务产品实测，不由品类名称直接裁决胜负。
