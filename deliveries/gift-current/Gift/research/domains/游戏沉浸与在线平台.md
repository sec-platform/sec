### 差异压力：游戏模拟回滚与现实购买/资产账目不能共同回滚

客户端在tick 105回滚到tick 101以重新模拟击中结果，这是模拟状态变化；tick 103发出的真实购买或平台积分转移已经越过外部Effect边界，不会因模拟时钟倒退而消失。多人服务器合服时相同用户名不是实体身份，旧客户端仍可能发送上个赛季授权的消息；需要真实代际围栏和资产账目对账。

## 实时交互的联合区别见证

这一节不是“游戏运行时设计”，只保留此前深度压力材料中真正会攻击通用抽象的联合差异。具体引擎、ECS、rollback networking、GPU API、资产系统、账号经济或 live-service 方案都必须由作者、库与 Provider 自己组合，Gift 不预置。

### 多时基不是一个 `realtime` 开关

`InputSample`、`SimulationTick`、`RenderFrame`、`AudioSampleRange`、网络接收时间和持久提交时间可以具有不同频率、抖动、迟到和重采样规则。真正需要保存的是它们之间的映射、允许误差和 authority，而不是给所有对象一个全局 `tick`。固定 simulation tick 与可变 render frame 可并存；输入预测或插值也不能把 presentation 时间改成 simulation authority。

若产品要求 deterministic replay 或 lockstep，必须明确哪一层状态进入 canonical comparison，以及随机流、规则/content/protocol generation、数值环境和允许差异；若产品只要求 server authority + client prediction，则验收的是 correction、acknowledgement 与误差合同，不强加 bitwise client equality。

### 模拟回滚与现实结算不是一种 rollback

预测状态可以回到旧 snapshot 并重算，但文件写入、购买、消息、遥测、处罚、外部设备动作等真实 Effect 是否可重试、补偿或只能读回，由它们自己的 operation/settlement 合同决定。simulation rewind **不能**自动重发或撤销已经尝试的现实作用。

partial snapshot、interest filtering 或结构变化还会造成 rollback closure 不完整：若相互作用对象依赖共同历史，要扩大 closure、保留足够历史或明确接受近似/校正；“收到了某个实体的旧状态”不能证明整个世界处于同一历史切面。

### 内容、代码、运行实例和设备资源具有不同 generation

作者资产、导入资产、cooked artifact、shader/pipeline、代码 revision、save/replay schema、live session state 与 GPU/device resource 不是同一个版本轴。派生物 identity 至少纳入真实源、方法/工具链、配置与目标；热重载代码若改变 live-state schema，需要显式 migration 或重启相交实例。旧 save/replay 的长期可读性也不能为了热重载方便被删除。

设备丢失或 presentation surface 更换只撤销相交 device/resource qualification；除非作者语义明确如此，它不撤销 simulation truth、持久业务事实或已经 settled 的 Effect。反过来，simulation correction 也不能证明旧 GPU/native hold 已安全释放。

### 权利事实与当前可服务性分离

内容 entitlement、账号权利、库存/购买结果等稳定权利，与当前内存、带宽、region、容量、Provider 健康造成的 `available/degraded/unavailable` 是不同事实。资源压力可以改变交付方式或暂时不可服务，但不能把“已拥有”重写成“未授权”；恢复后也必须重新取得实际 availability，而不是只读旧 entitlement。

### 何时值得成为通用机制

上述差异只有在脱离“游戏”名称仍然具有独立可观察含义时，才由对应 Standard Semantics / Core owner 承担，例如：多时基、明确 Effect settlement、generation-aware derivation、资源 qualification、authority 与 capability。matchmaking、quest、inventory、DLC、anti-cheat、camera 等仍属于作者/库层。若一个新游戏需求只能通过给 Core 增加行业 enum 才能表达，应先形成 [distinction witness][k32]，而不是扩充游戏能力表。

### 联机游戏的模拟回滚与真实购买

**关联领域：**[游戏玩法、世界与交互仿真][k1]；[游戏联网、服务与持续运营][k2]；[银行、支付、账户与结算][k33]

**相交规范：**[真实操作的状态机、未知结果与有界恢复][k34]；[分布式合并、全局不变量与离线预算][k35]；[仿真内核族、时间推进与并行事件提交][k36]；[作者组合、公开发行与商业边界的实际控制][k37]

**任务：**完整游戏组合不把经济效果放入可回滚模拟状态。

**具体输入与触发：**预测被服务器纠正并回滚，但期间已经向外部支付服务发请求。

**应保持行为与输出：**模拟事件与外部提交分离；真实交易有独立身份、权限和对账。

**失败与恢复：**回滚只撤销模型变化；已购买按业务补偿处理，不再扣款或抹账。

**验证方法：**网络重排、重复输入、迟到支付、服务器接管与存档恢复。
