# Gift 工程编译器：系统架构与责任边界

本工程当前只有一份**结构化 JSON 作者语言的候选设计**：`gift.author-module/2`；`gift.project/1`声明作者源码发现范围、目标及输出根；旧 `/1` 作者模块按兼容只读解释。内部版本号用于Reader分流，不是每一项领域构造和发生点都要维护的业务版本。自包含作者模块的必要字段只有`schema`、`moduleId`和`definitions`；其余字段按实际跨模块、方言、公开能力才提供。完整文件规范在[工程清单与模块](docs/10-作者与输入/作者源/工程源/工程清单模块与绑定锁协议.md)，完整Kind及其专业含义在[开发者通用定义](docs/20-语义与组合/作者语义/开发者通用定义Profile-类型计算业务与系统构造.md)。

本次目标是**全工程设计与文本专业归属**。通用计算`core:function`、`core:constant`与类型/表达式已经作为**同一语言的可选作者能力**进入设计，不再与业务语义构成一门平行语言，也不要求普通业务作者写计算体。本阶段继续优先普通业务与非计算工程设计，暂停新增计算研究、表达式解释器、递归扩展及新计算后端；已纳入的计算合同仍属于同一设计，不因暂停撤销。领域解释、要求联立、Method供应、Target降低、外部授权各由自己的专业Owner提供资格。计算表达式所需的基础纯运算由[内建纯 `std` 原语](docs/20-语义与组合/基础语义/计算基础/文法类型与求值.md)定义；层级状态直接由原 `state:machine` Body 承载，不另造并行语言。**没有实现或发布通用生产编译器**，不能以Schema或文档数证明能生成任意软件。本包不开发编译器、检查器、测试或性能验收。

语义、编译职责、产品组合、文件/身份/运行状态不强行同构为层级树；所有总视图仅引用实际Owner。工程意义可在一次跨层交接中保持，但其授权、输入与真实运行结果不能合并成一个“统一万能对象”。规范总入口见[详细文档导航](docs/README.md)、[唯一身份与状态](docs/70-工程系统与演进/信息与生命周期/对象关系与配置基线.md)及[严格责任链](docs/00-系统与原则/统一多层工程模型.md)。

## 目标与语义主链

Gift将开发者**已采纳的目标、约束和开放领域意义**经资格化实现转为可维护的目标工程。普通作者优先定义所需业务结果，无需重复编写底层实现；现成计算、查询、规则、流程、优化及原生库可作为专业Method供应。语言构造的可表达性、Method可实现性、运行授权、现实效果和独立证明是不同资格。权威规则见[公共语义](docs/20-语义与组合/共同语义/工程通用语义全域与闭合合同.md#stable-finite-general-semantic-core)与[开放意图](docs/20-语义与组合/作者语义/通用意图语言-意图源与语义组合.md)。

```text
唯一 AuthorSource / 原生作者区域
   ↓ 严格解码、版本/身份/类型/来源资格
已绑定 Meaning、参数化 Pattern、范围内观察
   ↓ 实例化及联立（共同对象、时间、资源、主体）
Joint Requirement / Derived Obligation
   ↓ 合格 Method 供给、前提/效果/异常/进展/精化校核
Qualified Realization Plan
   ↓ 目标合法 Lowering、全部入口根及依赖闭包
Target ArtifactSet（源码、配置、协议、迁移、SourceMap）
   ↓ 构建与独立保证；运行另经 Grant/Operation
实际效果 → Settlement / Readback / scoped Evidence
```

不能在任何阶段以Schema通过、候选存在、生成器自测或效果请求发出，冒充下一层已合格。[逐阶段施工](docs/70-工程系统与演进/工程构造手册/28-抽象到业务系统-统一实施闭包.md#gift121-stable-end-to-end-compiler-contract)。缺事实/方法/权限/观察者时精确产生Needs或受界未完成结果，不猜测目标源码。

## 正交的抽象、责任与执行视图

- **V0–V5业务视图**：V1公共构造、V2开放领域Meaning、V3作者意图、V4复合业务能力、V5整体系统；V0实现供应与其正交。六种意图模态和八种RequirementTerm是不同语法角色；45家族135侧面用于覆盖核查，不是行业Kernel switch。[逐层归属](docs/20-语义与组合/共同语义/工程通用语义全域与闭合合同.md#gift119-semantic-layers-owner)。
- **L0–L6因果职责**：来源、语义、实现解析、制品、执行、观察、保证。它们不是独立服务或每次必经的七道门；读回可以变成下一次来源，保证可能先于发布。[总模型](docs/00-系统与原则/统一多层工程模型.md)。
- **G0–G7工程生命周期**：问题、原则、理论、架构、详细设计、实现、验证、演进；不是编译器IR。[工程准入](docs/00-系统与原则/设计方法/工程全生命周期八阶段与准入合同.md)。
- **S0–S8编译与效果接合**：冻结/读取、语义解释、联立、Method资格、Target装配、构建/检查、现实授权与证据各有明确接口，不应混同为一条全局可写状态表。

## 实现责任、调用和物理安排

Gift设计采用本地优先、可嵌入内核及可选择宿主的拓扑。Rust长期承担严格纯编译Kernel；TS/Bun承载控制/交互及本地协议；TypeScript是先行目标后端，Rust Target是独立待建能力。控制侧和Target侧不因此成为同一套类型系统。[源码分区](docs/70-工程系统与演进/实现与装配/源码分区与机器合同.md)；[本地工作进程](docs/70-工程系统与演进/实现与装配/内核工作进程与交换协议.md)。

| 逻辑职责 | 拥有 | 不拥有 |
|---|---|---|
| `contracts` | 引用、边界值、诊断和结果形状 | 领域解释或操作权限 |
| `workspace` | 来源、作者身份、版本、冻结候选及源定位 | Target实际写入资格 |
| `semantics` | 类型、身份、关系、效果、公开组合及有权Meaning解释入口 | 特定行业政策、全域事实与真实Provider |
| `compiler` | 实现资格协调、联合选择、Lowering、Target成员及源码映射 | 真实运行和发布采用 |
| `assurance` | 有范围的Claim/Evidence及独立性和覆盖评价 | 改写业务验收或授予写权 |
| `application` | 请求、目的、候选、补取、结果和继续能力 | 第二份类型系统或全局current |
| `execution` | 真实准入、资源、Operation/Attempt、结算与恢复 | 不经过Provider的现实效果签发 |
| `adapters` | 原生编译器、文件、数据库、宿主、Provider的真实能力 | 比外部生产者更强的保证 |
| `entry` | CLI/AI/Workbench协议、协商和呈现 | 绕过Source CAS/Grant |
| `bootstrap` | 实际依赖装配及所有权内资源关闭 | 全局Service Locator |

`entry → application → workspace/compiler/assurance/execution`，compiler消费semantics，execution使用受权adapters；`contracts`提供共享边界值。纯查询、解析及证明规划遵循相同冻结basis、依赖/取消和发布原则；有现实作用时跨越Operation边界。逻辑职责不要求各自独立进程。移转Rust生产职责需要真实消费者、等价/错误复核及回退，不能由文档更名直接退役TS/Python余部。

## 数据、变化与目标源码的边界

1. AuthorSource、原生源码及有权候选区各只有准确写者；`IntentIR/Facet`仅作意图发现候选或只读投影，不是已采纳意图的第二真源；文本/结构形式共享语义但不自动共享原始字节身份。SourceSnapshot、派生IR、Index/Cache、Artifact、Operation、Evidence分别保存实际版本和作用域。无原子多文件保存能力不得承诺同时生效。[作者保存](docs/10-作者与输入/作者源/工程源/作者编辑保存与迁出.md)。
2. 一个实体可有多种表示，一个文件可以包含不同来源；树形布局不是所有依赖/权限/证据关系的容器。目标布局根据产品接口、事务、语言和构建规则形成，并保留原作者区域与SourceMap。[布局](docs/70-工程系统与演进/信息与生命周期/多维组织与树形落位.md)。
3. Method适用与正式资格不同，单意图可行与全局联合可行不同；搜索预算耗尽不等于无解，局部可构建不等于完整ArtifactSet。[实现解析](docs/30-实现解析/实现选择/实现解析与候选资格.md)。
4. 保存≠发布、Grant≠已经发生作用、取消≠无作用、超时≠失败。未知效果以原Operation身份读回，再决定恢复/新Attempt/补偿。证据不能反写作者要求，基础失效只传播到真实依赖闭包。[持久恢复](docs/50-执行运行与观测/持久化与恢复/README.md)；[验收](docs/60-保证与证据/验收/意图覆盖与纵向符合性.md)。
5. AI可以解释和提出有来源的候选；只有有权主体接受的意图才是编译输入。确定性编译不能在每次构建时重新猜聊天含义。成熟实现须绑定具体版本、前提、性能、行为和外部条件；库引用或包安装不授予资格。

| 输入或变化 | 所属合同 | 不能推断 |

| 缓冲、磁盘、native区、来源与并发修改 | [作者编辑](docs/10-作者与输入/作者源/工程源/作者编辑保存与迁出.md) | AST相同≠允许丢未知字段或源字节 |
| 已接受要求与候选供应 | [联合需求](docs/20-语义与组合/组合/跨软件需求合同.md)、[搜索](docs/30-实现解析/实现选择/设计空间搜索与求解.md) | 局部候选合格≠全局最优或无冲突 |
| 多模块版本及共同事务 | [配置关系](docs/70-工程系统与演进/信息与生命周期/对象关系与配置基线.md) | 多文件CAS各自通过≠共同一致 |
| Target及其部署根 | [完整装配](docs/40-目标与制品/目标/具体降低与目标输出.md) | 构建成功≠实际运行/部署或业务正确 |

| 运行证据、来源独立性及版本 | [保证](docs/60-保证与证据/验收/接缝符合性.md) | 工具绿色≠所有Claim合格 |
| 查询、候选、差异、交付和恢复 | [开发者主链](docs/80-开发者与接口/需求到交付主链.md) | UI展示≠正式采用与授写权 |
