# 多表示作者与 SDK 源码资格反例

本文件是**反证与验收输入**，不拥有新的规范字面量。准确合同见[统一工程作者源码协议](../../docs/10-作者与输入/作者源/工程源/统一源码工程与多表示作者协议.md)、[编译接合](../../docs/70-工程系统与演进/实现与装配/多表示输入与统一编译接合.md)。这些轨迹应在实际产品编译器/客户端具备时改成可运行测试；此处只给明确条件与要求结果。

| 编号 | 触发与输入事实 | 错误的“统一”行为 | 规范上必须有的输出与恢复 |
|---|---|---|---|
| A01 | 用户打开原生 Rust 工程，只查询符号 | 强制生成 `main.gift`/JSON AST 才允许查询 | 原生源码原地理解；不能理解的 AST 返回覆盖缺额，不改源 |
| A02 | JSON AuthorModule 中只有复合 Requirement | 用 `gift/author` 转成文本才宣称合法源 | 结构模块可保全与解释；不得强制启用可选文本 Profile |
| A03 | `.gift` 静态作者未选语言 Profile | 因 `import "gift/author"` 推断开启新模式 | 旧语言按旧解释；需要显式 Profile，不能自动升级 |
| A04 | 结构 JSON 中旧方言未知字段 | 读取器忽略字段重新打印合法 JSON | 保留未知字段/原字节、相交消费不合格，等待有资格读取器/迁移 |
| A05 | 已经可编辑的原生函数又由结构编辑器生成同义可写函数 AST | 两处更新各自认为成功 | 识别一个 AuthorRegion 的双 owner，阻止采纳或完成一次有凭据迁移 |
| A06 | JSON Requirement 独立约束已有 TS 函数 | 因“两个文件涉及一个行为”一律删除 Requirement | 允许独立义务与实现并存，保留接受来源和观察域，建立检查关系 |
| A07 | Rust SDK 用同名 Definition 提交旧前像 | 默默覆盖当前 JSON 或复用已删身份 | 报具体冲突/身份诊断，保留当前内容与可重基候选 |
| A08 | SDK Builder 内存对象成功构造 | 报告 Gift 检查、目标生成、应用成功 | 只能报告构造结果；另需源冻结、dialect 语义、Method、目标与真实操作 |
| A09 | 未经授权的 Rust `build.rs` 访问网络创建 Source JSON | 在纯编译中执行，再以最新结果作规范输入 | 拒绝隐式外部执行；可显式准入后冻结结果，保留秘密隔离和失败恢复 |
| A10 | TS 目标可以调用某 Rust 库，但要求纯 TS 源码 | 只把 Rust 代码包装为 RPC 仍标“完全原生 TS 等价” | 报原生 TS Method/受支持 lowering 缺口，除非目标显式允许运行桥 |
| A11 | 同一 JSON 源默认值升级，某个消费者显式 Pin 旧值 | 因当前两者同值，把 Pin 当继承 | 保留显式来源与默认来源；分别核升级后的结果 |
| A12 | 目标没有工具链，但只要求设计 | 自动启动 `tsc/cargo build`，把失败标成设计失败 | 设计蓝图按已知信息交付并注明未取证；不生成/检查无请求产物 |
| A13 | 两个目标其中一个 Method 不存在 | 丢掉失败目标，整体标完成 | 独立根可交付，必要组合目标未完成；返回准确 Need/消费者 |
| A14 | 原生源码 opaque 插件可能触发网络 | 静态检查通过后声明“无外部效果” | 保留未知效果、条件性语义覆盖；不得对未知区域颁发纯度保证 |
| A15 | 两个源码区域同名 `Document`，属于不同 ModuleUse | 因名字一样复用身份/缓存或 Grant | 按真实解析域、Definition身份、内容与 Revision 比较，保持隔离 |
| A16 | 在迁移中目标格式不可表达旧语义或不能回写注释/未知字段 | 仍删除旧源并应用新格式 | 迁移失败保留旧 owner 和全部原文，候选/缺额独立返回 |
| A17 | 生成代码手动维护且没有回源映射 | 自动下次生成覆盖手改代码 | 保留 TargetDraft，要求原生接管或真实回源迁移 |
| A18 | JSON 结构静态检验通过，但未取得 Rule/Type codec | 将 JSON Schema 的 PASS 当全部设计可编译 | 仅记录结构 PASS，语义/目标资格不成立，准确显示缺哪个 dialect/codec |
| A19 | 同一函数通过 Rust SDK 实现了一种算法 | 将 SDK 生成 JSON 视为同时提供 Rust Target 后端 | SDK 构造器只提供定义；运行算法需独立 Method/ABI/Target 合法绑定 |
| A20 | 用户不想再安装任何 Gift 组件，只要已生成普通 TS 工程 | 声称生成物必须永久依赖 Gift daemon 才能运行 | 若任务是独立目标，明确所有真实随包 runtime/helper/依赖；无合法独立策略则拒绝独立性声明 |

**重要反向案例**：结构 JSON、原生实现和 SDK 完全可以共同存在于一个项目，只要它们分别拥有独立的要求、算法和候选构造责任；“三种文件出现”不等于冲突。真正的冲突来自同一个语义对象、同一可写作者区域的双重权威，或者绑定时丢失的原来源/作用域。
