# 通用工程表达、设计蓝图、目标等价与开发者面的失败见证

> **材料角色**：用于检查 Gift 当前通用语义、作者控制、目标蓝图、客户端和Assurance是否真的保持了不同的可观察结果。不是当前代码执行结果，也不是第二份正式规范。若某例被现行owner解释过，应以其当前准确机制裁决；本页只记录输入、错误行为、正确区别与重查边界。

## 一、通用表达与作者源

| 反例条件 | 看似合理但错误的行为 | 必须保留的正确区别 | 受影响责任 |
|---|---|---|---|
| U01 图灵完备脚本装全部业务 | 一段 `eval` 能跑就宣称整套工程被Gift理解 | 字节保留与函数执行不等于接口/状态/资源/权限/迁移语义可被分析；声明opaque范围 | 计算语义、原生适配、Assurance |
| U02 新行业名 `Editor/Payment` | Kernel新增强制内置`Editor`节点，否则不允许作者设计编辑器 | 若可由类型/状态/效果/协议和库组合则零Core更改，行业仍由作者拥有 | Core晋级、作者定义 |
| U03 同义作者复制 | UI表单、`.module.json`和目标源均可独立修改同一个保存算法 | 选定可写区域唯一，其他视图只读/回到同一owner；Requirement与实现不同主体可并存 | 作者源、投影、回源 |
| U04 新建项目强制全局JSON图 | 用户要一个函数却创建数千文件/项目锁/数据库 | 片段可以只保留内存作者上下文；复杂工程按相交边界分组，不存在一节点一文件规则 | 作者前端、UX |
| U05 只读取20个文件 | 搜到几个module就称全仓没有其他消费者 | 观察范围、语言适配能力与搜索coverage必须单列；缺失观察不可当权威不存在 | Workspace/query |
| U06 把软件静态代码当运行时事实 | 接口声明启动文件后显示“端口已开放” | 类型/接口合法只规定目标可用模式；真实监听端口需运行回执 | 语义、Effect/Observation |

## 二、专业工程蓝图与完全等价

| 反例条件 | 容易被忽略的错误 | 必须保留的正确区别 | 受影响责任 |
|---|---|---|---|
| B01 美观目录伪装完成 | `src/vs/editor/`、`extensions/`存在但文件都是空类 | 目录只是目标布局；对外行为、算法/库、状态、错误、依赖等仍有Need | Target/Realization |
| B02 共用类型但不兼容协议 | RPC两边有同名`open`方法，却一个需先握手另一个不握手 | 协议版本、顺序、认证、错误和资源生命周期必须匹配 | 组件/协议组合 |
| B03 源码图推断运行图 | 两模块互相import就宣布两个远程进程必须互访 | import、IPC、build-before、runtime ownership是不同边 | 目标多图/运行 |
| B04 TypeScript可解析就称运行可用 | 浏览器目标调用Node `fs` 或本地PTY | 目标环境能力独立；缺Provider必须拒绝或改合法目标，不偷偷改需求 | Target/环境 |
| B05 桌面插件迁远端 | 只移动源文件路径，保持原本本地绝对路径和信任Grant | RPC、URI、身份代理、秘密、网络故障、调试、远端安装必须重新决定 | 实施绑定/运行/安全 |
| B06 需求精化冒充双向等价 | 目标只实现编辑器“只读打开”，却没有用户要求的编辑保存 | 单向合法轨迹可能不足以覆盖全部要求的响应/进展；双向/能力覆盖另证 | Assurance/Requirement |
| B07 完全同源码冒充全等价 | 两版代码字节相同，但运行库/OS/许可证/网络环境改变 | 相同代码不保证同环境观察、延迟、ABI、授权、分发合同 | 环境/Assurance |
| B08 只看单测试通过 | 开/保存文件测试绿灯却丢了撤销栈、屏幕阅读器可达性或远端故障 | 独立要求与非功能量需独立Claim、方法、范围 | Product Assurance |
| B09 原生不透明代码被“清理” | 重生成时删除扩展脚本或构建资源，因为parser不理解 | 原生作者区/资产字节及其语义边界须保留，不明不能视为无用 | 原生保全/Target |
| B10 生成源码不完整仍标完工 | 生成`index.ts`但缺package lock、resources、bundle脚本和API类型 | 完整要按请求的交付用途覆盖依赖、配置、构建和维护；生成与设计分状态 | Artifact/Delivery |
| B11 无条件成本最优 | 自动选择文件数最少方案，却跨安全域共享有状态实例 | 硬约束先验合法，成本只比较合法候选；资源/权限与生命周期优先 | Design Search |

## 三、VS Code级开放状态与多环境

| 反例条件 | 错误处理 | 真实必须区别 | 受影响责任 |
|---|---|---|---|
| V01 文档v8诊断晚到 | 用户已编辑为v9仍把旧`TextEdit`直接Apply | 基础修订和位置映射需可证明；无法重基则冲突 | Source revision/Protocol |
| V02 外部文件监视和UI保存竞争 | 保存缓冲不比较当前磁盘前像，静默覆盖同事修改 | bufferVersion、FileRevision、SourceRevision与写入资格不同 | Workspace/Transaction |
| V03 远端断线后自动重发写入 | 丢失响应后生成新Operation再次覆盖/安装 | 原Effect身份读回，未知是否发生不可当确证失败 | Operation/Recovery |
| V04 插件已安装即激活 | 允许调用未激活或刚崩溃的扩展命令 | installed、activating、active、stopping、failed各有时序资格 | State/ExtensionHost |
| V05 Webview从本地读取密钥 | 因在VS Code窗口内就把作者源码、secret暴露给插件UI | Webview/extension host/remote Grant分离；当前披露要裁剪 | Trust/Disclosure |
| V06 窗口关闭即停止工作 | 客户端断开使远端worker和真实运行资源无主 | viewer/lease与运行Operation、长期Task生命周期分开结算 | Client/Execution |
| V07 项目A的搜索缓存显示项目B的私有路径 | 查询基于相同内容摘要跨租户复用并披露 | 共享计算结果可复用的前提不等于共享可见性与结果身份 | Cache/Permission |
| V08 大文件或无限插件阻断主线程 | 因为语义允许无限循环就默认主界面仍实时响应 | 理论普适不保证有限资源；需要实际异步/进程隔离、配额、取消与恢复 | Resource/Scheduler |
| V09 动态注册后仍使用旧“全集”缓存 | 新扩展出现但编译器仍报告命令不存在或唯一最佳实现 | 正/负依赖、闭合枚举资格和Registry代际必须失效相交结论 | Incremental/Resolution |
| V10 升级前后数据结构可读性猜测 | 新版settings schema写入后旧版程序仍尝试原样读取，回滚损坏配置 | 双向迁移/旧reader保护/不可逆点/回退合同单列 | Evolution/Deployment |
| V11 build成功当用户已更新 | 浏览器service worker、remote server或本地安装仍运行旧成员 | Build/Install/Publish/Adopt/Run/Observe分别判定 | Delivery/Readback |
| V12 存在同名两个ExtensionHost | 把local和remote进程依据同显示名合并，错误交付资源或终止 | 构造身份/实例身份/运行位置/业务用户不同 | Identity/Runtime |

## 四、设计阶段与执行的边界

| 反例条件 | 错误报告/动作 | 合格范围 |
|---|---|---|
| D01 用户只要求设计，助手创建无关库存项目并跑`tsc` | 把无关代码的12/12通过称Gift蓝图验证 | 那只能说明库存代码在对应环境的测试；本轮只允许设计合同、来源保留和静态覆盖检查 |
| D02 模型建议`gift.plan`命令但v2无此字段 | CLI被描述为已经可运行，或偷偷用`preview(return=plan)`覆盖旧协议 | 现行六工具只可使用已经定义的字段；未实现查询投影标Unsupported，确需新接口须版本协商 |
| D03 源码不存在，却把TypeCheck显示PASS | 空案例集被当作成功完成 | 只有 `NotRun/NotApplicable/Unsupported/Need` 等准确状态，不能把零执行冒充证明 |
| D04 文档链接检查全绿 | 宣告任意专业工程均可自动设计/生成并等价交付 | 文档完整性仅证明文档；普适性、实现资格、产品Evidence分别判断 |
| D05 “不回退”被理解为禁止修改错误规范 | 新反例证明旧合同错误，仍为保全文字而保留危险规则 | 保留有用内容与决定依据；修正错误、提供准确迁移、影响和证据缺口 |

## 五、验收分流与停止条件

以上例子的合同读取应回到当前唯一owner。每项记录①触发输入和实际范围，②错误实现仍会“显示成功”的路径，③当前机制为何可以保持区别，④无法取得的证据或新设计缺口。只有真实实现/工具/Provider出现以后才把适用反例转为可执行测试；此文件不是已执行测试报告，不能通过把案例数累加声称全部未知失效路径已穷尽。

当出现真正现有核心无法表达的不同可观察结果，必须构造反例并证明作者组合、开放SemanticModule、原生适配与Target方法都不足，再按核心扩展流程重开；当只是当前工具尚未实现或具体目标供应商无合格实现时，保留独立Implementation/Provider Need，不能从个案反推整个Core不可用。
