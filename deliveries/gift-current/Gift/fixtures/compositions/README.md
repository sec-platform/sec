# 组合研究：完整产品形态怎样由通用机制组织出来

> **研究输入，非现行规范。** [采用、证据与保全边界](../../research/README.md#research-use-boundary)。

本目录保存**非权威的组合研究材料**。这里允许把若干通用语义、Requirement、实现方法、Provider、Target、运行边界和 Evidence 组合成较完整的产品形态，用来回答一个研究问题：在 Gift 不预制该产品类型的前提下，现有开放组合机制能否仍然表达、实现和演进它。

这里不是 Gift Core、Standard Semantic Module、标准库、默认 Profile、官方产品模板、支持矩阵或必须执行的验收套件。IDE、Studio、事务型应用等名字只标识研究载荷；它们不会因为被分析得很完整就取得 `gift.*` 命名空间、默认 runtime、内置业务对象或实现资格。真实产品仍由作者工程、库与 Provider 定义。

研究材料可以保留足以复核组合关系的具体字段、状态、布局和失败场景，但不得反向成为公共合同的 owner。真正跨产品成立的区别应提炼回对应 canonical owner；能否否证公共抽象的少量稳定区别见证进入[跨域区别见证](../../docs/60-保证与证据/验收/跨域区别见证.md)。仅属于某个完整产品的配方继续停留在这里或作者/第三方库层。

## 当前研究载荷

- [IDE / Workbench 需求规则与供给](IDE需求规则与供给.md)：检查开放 Requirement、共享主体、方法选择和 Evidence 能否组合出复杂开发工具要求。
- [IDE 降低与目标布局](IDE降低与目标布局.md)：检查具体交互要求如何在不污染 Core 的情况下落到私有状态、恢复和目标工程。
- [Studio 交互产品](Studio交互产品.md)：检查文件树、编辑、搜索、任务、调试、VCS、扩展、设置等复杂交互能否由作者定义组合。
- [事务型应用组合](事务型应用组合.md)：检查持久对象、规则决定、受控变更、提交后交付和不确定完成的联合边界。
- [状态变更与外部作用](状态变更与外部作用.md)：用较小业务载荷检查状态、权限、幂等、外部 Effect 与恢复是否保持分责。
- [跨产品组合工程](跨产品组合工程.md)：用游戏、后端、数字孪生、医疗、算法库、CAD/BIM 等完整组合研究不同机制的联合边界。

## 接缝反例研究

[接缝反例](../../witnesses/counterexamples/README.md)保存从完整产品研究中提炼出的具体错误构造。它仍属于 Research：没有固定案例编号、没有“全部执行”门禁，也不因一行反例存在而产生 ProofObligation。只有真实 Claim/Requirement 与某个区别相交时，Assurance 才实例化具有稳定身份的 ProofObligation，并选择适当 Method/Evidence。

## 怎样使用这些材料

先从产品的真实作者事实和要求出发，再映射到通用 owner；不要从本目录选一个模板再让业务去适配模板。若研究暴露缺口，按[作者定义组合与核心扩展边界](../../docs/70-工程系统与演进/演进与实施/作者定义组合与核心扩展.md#core-promotion-rule)判断它应留在作者库、成为 Standard Semantic Module，还是极少数情况下进入 Core Kernel。

本目录没有“全部产品都要跑一遍”的完成条件。新增研究材料只有在它带来新的组合结构、失败方式或区别见证时才有价值；换一个行业名字重复同一机制不增加覆盖。
