# 开发者纵向路径：从一次短源到连续修改、保存与受控运行

本篇是**组合验收Fixture而非作者规范或已执行的产品测试**；其字段与状态由[开发者需求到交付主链](../../docs/80-开发者与接口/需求到交付主链.md#developer-implementation-ready-operating-contract)、[六工具](../../docs/80-开发者与接口/工具协议/六工具与请求-工具边界-任务与作者输入.md#v2调用字段与控制动作)、[内核Worker](../../docs/70-工程系统与演进/实现与装配/内核工作进程与交换协议.md#developer-request-worker-boundary-and-real-retry)共同拥有，本文不发明新机器字段。`C1/A1/W/B`是由将来真实服务产生的符号Ref。

## F0 先验与最小用户动作

用户选择：生成TypeScript函数`twice(n: Int) -> Int = n*2`，只想看结果；已拥有确切`gift.semantic/1`入口与有资格的TS Target。没有真实绑定则F0返回`NEEDS_INPUT`，不得为了示例硬造TargetProfile；本Fixture是**条件满足时**的一条期待路径。用户既不需要建目录、手写JSON，也不需要GitHub、模型服务、持久DB。

| 步 | 开发者说/做 | 请求分支 | 结果与来源 | 允许的真实副作用 |
|---|---|---|---|---|
| F0 | 输入函数，选择预览TS | `preview(source,target=typescript)` | 不可变C1/A1与未检查TS字节 | 无工作区写入/运行 |
| F1 | 点击解释类型 | `query`相交位置或`check(candidateRef=C1,methods=[types])` | 只证明源语义、具体诊断；若选择目标类型则给A1 | 按真实所选方法，默认不运行项目 |
| F2 | 改乘数2→3 | `propose(base=C1,edits=[{path:snippet.gift,old:n * 2,new:n * 3}])` | C2准确新作者候选；C1仍存在 | 无 |
| F3 | 比较旧TS | `preview(candidateRef=C2,target=typescript,return=diff,compareTo=A1)` | A2与A1→A2差异；新的完整目标 | 无 |
| F4 | 只保存源 | `apply(candidateRef=C2,mode=save-source,targetRef=W,base=B,requestId=R)` | 新当前源修订或冲突、真实回执 | 经现有Grant的受控作者写入，不包含目标/构建/发布 |
| F5 | 用户再请求写出TS | `apply(candidateRef=C2,mode=write-output,artifactRef=A2,targetRef=OUT,base=BO,requestId=RO)` | 准确已写ArtifactRoot或部分/未知 | 仅当前获准输出位置的真实写入 |
| F6 | 用户选择真实测试运行 | `check`所选methods或已协商`compute-run` | 实测结果和证据适用条件 | 仅明确要求且具有权限的外部工具/运行 |
| F7 | 断开IDE再回来 | `operation(status)`或query当前Project/Source | 当前头与当前Operation证据；不拿C1/A1当最新 | 无新增外部写入 |

**可完成结果**：F0后即可交付代码预览；F4后可交付真实保存的源；F5后可交付目标字节；F6后才能报告请求的运行/检查事实；F7还要核对请求的额外Deliver范围。一个单击可以组合已经获准的步骤，但每段的真实前像、资格、失败和阶段仍分别存在。

## F1 并发与终态反例串接

在F3之后、F4之前，另一个合法编辑者更新作者模块；本次原B不匹配，F4必须是`STALE_BASIS`，C2保留，A2作为旧Candidate产物仍可在其准确Scope阅读；新的C3与C2的冲突/不相交变化由read-set和共同Invariant重新判断。任何实现把F4当作“若旧文件没变就简单全量覆盖”均不合格；不能因为用户点了保存就跳过提交准入。

在F6的工具执行/真实发布中回执通道丢失，只能报告`UNKNOWN_EFFECT`及原Operation身份、已获实测记录、需要核账的剩余范围。不能在UI上画成功绿勾，也不能用新的RequestId盲重发非幂等动作。用户在此时修改C4，不能将旧Artifact/Operation迁移成C4的成功证据。

## F2 两种扩展场景和真实条件

**已有TS服务**：SourceProfile捕获已有`src/orders.ts`及真正相关`package.json/tsconfig`，直接提案源文件Delta；不创建影子业务IR。TS使用Node宿主和Bun control进程不等于TS Target支持；真实构建另核工具链、导入、运行环境与业务测试。不可理解的原生宏/动态加载可以保真变更，但其保证只能限制于实际覆盖。

**订单业务要求**：用户说“先保留库存再调用支付，失败释放”。只有采用合法Order/Stock/Payment定义及精确幂等、余额/库存一致性、超时与失败事务机制后，才能称形成可运行业务；缺关键事实时先形成需求候选和明确Needs，而不是生成`reserve()`空函数。后续真实外部支付效果属于独立Operation，编译成功永不证明实际交易正确。领域库若未实现，其状态是`UNSUPPORTED`，不能因为此示例写出接口而视为已有。

## F3 退出条件

独立测试者必须同时交付：准确作者字节/锁、C1/C2/A1/A2、产生的TS字节、相交检查工具结果、应用前像及文件读回、故障注入结果和终态/恢复身份；至少一次断网/崩溃/过期结果试验。未实现阶段此行保留`NOT_EVALUATED`，不能用本Fixture自身的完整叙事证明实现通过。
