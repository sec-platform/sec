# 状态变更与外部作用组合样本

> **角色：非权威组合研究。** 本页故意使用一个常见业务化状态变更来研究通用 Definition、Requirement、Effect、事务、并发、幂等、恢复与 Evidence 合同。它不是 Gift Core 的订单模型、审批 SDK、事务框架、默认消息方案或业务支持声明；任何名字、状态、阈值和实现方法都不能取得 Core authority。

## 为什么保留这个样本

只写“批准一个订单”会把大量独立工程责任压成一句自然语言：谁可以操作、对象当前是什么状态、作者规则是什么、并发冲突如何处理、状态和审计是否原子、重复请求如何裁决、提交后的外部通知失败又如何处理。若 Gift 只能靠内置 `Order` / `Approve` / `Payment` / `Notification` 等业务概念表达这些差异，就说明开放组合协议失败。

正确路径是由作者或库定义业务身份和规则，再把它们接到通用主体、状态、Requirement、Operation、Effect、Consistency、Recovery 与 Evidence owner。Core 只理解这些通用合同，不认识“订单”这个行业名。

## 具体压力载荷

```text
业务对象：订单
初始状态：待审批
操作：批准
前置：调用者具有审批权限；订单仍为待审批；金额满足作者已采用规则
成功：状态变更与审计事件在同一数据库事务提交
竞争：版本不符则返回冲突，不覆盖他人操作
重复：同一作用域 / 主体 / 请求身份且载荷相同，在当前披露许可内读回先前结果
后续：通知通过事务外发件箱发送；失败不撤销已批准状态
```

该载荷至少要求能够区分：

- **业务身份与通用机制身份。** `订单/批准/待审批` 属于作者定义；revision、capability、operation identity、effect、Evidence 属于相交通用合同。
- **前置与实现自由。** “金额满足作者规则”不是编译器可自行选择的优化自由；实现可以在保持规则的前提下选择算法和 Provider。
- **原子提交与后续作用。** 状态+审计是否共享事务，与提交后通知是否通过 outbox 发送是两份可观察责任，不能因都叫“事务型业务”合并。
- **并发与重复。** revision conflict 与 idempotent readback 是不同失败/恢复路径；二者都不能靠 UI 防重代替。
- **披露与权限。** 即使 operation identity 命中旧结果，也只有在当前授权和披露合同允许时才能返回旧结果。

### 差异压力：状态计算重放却禁止真实副作用重发

模型状态可以从旧快照重算，但真实外部命令在第一次派发后可能已发生。重放恢复应先以原Operation稳定身份对账，再决定是否可以产生补偿新Effect；不能重复使用新幂等键假称“恢复执行”。同时模拟旧写者迟到并检查围栏。

## 研究判别条件

本样本只有在以下条件同时成立时才算“可由 Gift 组织”：

1. 作者可以在不修改 Core schema 枚举的情况下定义订单、状态、审批规则和所需业务值；
2. 通用状态、效果、事务、一致性、幂等、权限、恢复和 Evidence owner 能分别取得准确责任；
3. 选择数据库、消息设施或外部 Provider 不改变业务 Definition 的 canonical identity；
4. 缺少某个 Provider/Target 时返回准确缺额，而不是由 Core 偷偷发明默认数据库、队列或 HTTP 服务；
5. 更换“订单”为完全不同业务主体时，同一通用机制仍可复用，不要求增加新的 Core 业务关键词；
6. 若该业务出现现有通用合同无法表达的不可约可观察差异，必须形成 distinction witness，再决定是否只扩展作者模块、Standard Semantics 或最小 Core，而不是把整个业务模型提升为平台功能。

## 失败信号

以下任一情况都说明边界退化：

- Core 新增 `Order`、`Approve`、`Payment` 等业务枚举才能通过；
- 只因为一个“事务型应用 Profile”存在就自动获得数据库、队列、重试和恢复支持；
- 把业务规则阈值当成实现策略自由；
- 把数据库事务成功等价为外部通知已经成功；
- 用一个通用 `businessData: any` / 自由 JSON 绕开类型、身份、效果和迁移责任；
- 业务样本本身被引用为现行规范 owner。
