# 事务型应用组合压力样本

本篇是**非权威组合研究**，不是 Gift Core、标准语义模块、作者默认画像、已发布 DSL、SDK 或运行时。它把“持久对象—规则决定—受控变更—提交后交付”故意组合成一个较完整的应用形态，用来攻击通用 Definition/Requirement、效果与权限、持久化、Operation/Attempt、恢复、Target 与 Evidence 是否能在没有预制业务框架时共同工作。

下文保留一个假想 `example.transaction-app/1` 及其 `aggregate / decision / operation / subscription` 写法，只作为**局部研究语言**固定组合条件；其中“必须/不得/顺序/字段”等措辞只约束该夹具内部自洽和验收，不签发 `gift.*` 产品命名空间、不要求发行读取器/生成器，也不允许其他规范把它当作现行业务 API。真实产品若需要类似能力，应由作者模块/库用公共原语组合，或在出现不可表达的跨场景区别见证后再提出最小公共语义。

通用事务提交、不确定完成、权限、幂等、交付、恢复等机制的 authority 仍在各自 Core/执行 owner；本篇只把它们组合起来研究联合失败方式。行业对象、工单/订单等例子只是输入数据，不是 Gift 预装模型。

## 研究范围与作者声明

### 命名与适用范围的修订

`example.transaction-app/1` 是事务型应用的可选画像，不是所有工程的默认作者体系。声明、基础表达式及运行规则按精确版本解释；其他或未知编码不能作为隐式别名。确有旧消费者时，先取得其格式与解释，再明确校验和迁移。

本研究载荷中的“业务”指工单/订单这类持久领域规则与作用，不将编译、数值求解、渲染、内存变换都重新命名为业务。`operation`在本压力夹具是有前像和提交合同的持久变更，不是每个算法步骤。计算程序和其他任务的完整出口见[计算结构][k1]及[请求裁剪][k2]。

### 压力样本范围与最小化

一个普通函数仍直接写 `fn`，零工程目录、零数据库、零高层声明均合法。本压力夹具处理具有身份的值对象、纯决定、单根持久变更与提交后投递；需要时可以组成长期业务过程，不让所有算法进入持久工作流。

四种声明是 `aggregate`、`decision`、`operation`、`subscription`。它们只在本压力夹具规定的顶层或条款位置解释为上下文词，不加入基础语言18个保留词，不因导入普通库而激活。其他位置同名标识符保持基础规则。顶层遇到这些词后先按声明头的完整形态判断；基础变量定义仍由let、函数定义仍由fn开头，不依赖运行类型消歧。画像必须由真实上下文或工程语言绑定显式选择；只给文件后缀或遇到陌生词时不静默切换解释。

这些是四类开放构造，不是四种预装业务。订单、工单、库存、审批都是用户定义的类型、规则与实例；增加新业务不修改编译器的品牌或业务枚举。需要分层并行状态、连续时间或跨存储原子事务时，必须采用其真实语义和后端条件，不把本压力夹具冒充全世界语义。

开发者只维护不可推导的行为、约束和选择。对象身份、规则依赖、请求摘要、目标私有名、事件序号和读取前沿由工具或运行协议承担，不能出现在每条作者操作的必填表中。下列完整例是首次定义；第二次变化修改相关条款，不重发整套定义或整本合同。

### 四种声明及其完整责任

| 声明 | 保存的独立含义 | 不意味着什么 |
|---|---|---|
| aggregate | 持久值类型、业务键、每个后像必须满足的不变量、可选事件类型 | 不是一个强制微服务；键不是授权；声明不创建数据库 |
| decision | 有顺序、命中政策、输入输出类型与明确兜底的纯规则表 | 不是任意AI判断；一行返回true不构成证明 |
| operation | 目标、授权依赖、前像要求、纯决定、变更、同事务审计与事件、响应 | 不是立即执行的函数调用；源码不能为自己授予权限 |
| subscription | 已提交事件的选择、绑定端口、顺序、重试与停放政策 | 不保证收件人实际收到；事件不是可以转交的原授权 |

原子组和部署单元不是由声明数量决定。一个服务可以拥有许多 aggregate；一个聚合值可以映射到多张必须共同提交的物理表。对应[领域分区][k3]与[目标源码][k4]。

### 完整的作者例：关闭工单

#### 纯值、规则与存储含义

`model/tickets.gift`：

```gift
import "example/transaction-app" as txn;
import "app/access" as access;

export type TicketState = Open() | Closed(Text);
export type TicketFailure = MissingReason() | InvalidTransition();
export type Ticket = { tenant: Text, id: Text, state: TicketState };
export type TicketEvent = Closed(Text, Text) | Reopened(Text);
export type CloseInput = { id: Text, revision: txn.Revision, reason: Text };

fn validTicket(ticket: Ticket) -> Bool !{} =
  match ticket.state {
    case TicketState.Open() => true;
    case TicketState.Closed(reason) => reason != "";
  };

export aggregate tickets: Ticket
  key (tenant, id)
  invariant validTicket
  events TicketEvent;

export decision closeState(state: TicketState, reason: Text)
  -> Result<TicketState, TicketFailure> hit first {
    case missing: reason == "" => Result.Err(TicketFailure.MissingReason());
    case open: state == TicketState.Open() => Result.Ok(TicketState.Closed(reason));
    else => Result.Err(TicketFailure.InvalidTransition());
  };

export operation close(input: CloseInput) -> Result<TicketState, TicketFailure> {
  target update tickets({ tenant: actor.tenant, id: input.id });
  authorize access.closeTicket;
  expect input.revision;
  decide closeState(before.state, input.reason);
  change { state: value };
  audit { who: actor.subject, reason: input.reason };
  event changed: TicketEvent.Closed(input.id, input.reason);
  reply after.state;
};
```

这份源不写SQL、TS/Java代码、日志插入、重试循环或消息发送的实现。它也没有把一次输入变成另一份手写AST。关闭原因只要求非空标量序列，不暗加trim、大小写转换或Unicode正规化。`validTicket`使所有获准的创建/修改路径都必须维持该状态约束，而不只约束close这一个名字。

`closeState`能像纯函数一样被调用、检查或单独生成；`close`则是 Operation 定义，不能在纯函数里当作普通调用执行。运行客户端或受控执行器在真实环境中调用它，返回分别表示业务结果和系统状态的结果；类型上不能把“投递了一条命令”变成“命令已经完成”。其公开接口由业务签名与运行调用信封共同组成：输入类型不包含凭证，运行信封承载真实主体、幂等请求ID和受支持期限；同步调用可直接返回已结算结果，异步提交另回请求句柄。

`actor`不是CloseInput中的一个布尔值或自填记录。它来自部署绑定的认证上下文；其中tenant和subject是本压力夹具允许使用的受信、可披露视图。创建它的能力不对普通源开放。是否允许跨租户操作属于明确的更强授权画像，本例不支持由input覆盖tenant。

`access.closeTicket`是一个有类型的策略绑定，至少定义请求可见性、对象查找限定、当前行为准入和结果披露；它必须有真实实现。策略可以由普通中立函数表达其业务判断，并由相应身份/数据适配取得受信事实；不是因为出现这个名称就默认已有身份平台。策略所依赖的角色、规则或关系也要有版本/失效条件。

策略引用必须满足本压力夹具的结构合同 `AdmissionPolicy<Row, Input, R>`：前置阶段接收受信上下文、输入和规范键，给出允许读取的限定范围；决定阶段接收该范围内的前像、输入与可信事实，给出准入及其见证；结果阶段判断当前主体能否读取指定历史结果。各阶段可以绑定中立纯函数和已有身份/存储提供者，不要求应用作者手写原生代码。画像负责固定调用槽位、受信事实来源和返回形状；仅有一个返回Bool的未知原生函数不满足完整绑定。具体角色名称是业务定义，不进入编译器枚举。

该策略合同的三个槽位不是三次模型问答，也不是三个必须远程调用的服务：

| 阶段槽位 | 类型化输入 | 输出与含义 |
|---|---|---|
| probe | 受信Context、Input、由聚合key推导的Key | 拒绝，或受限ReadPermit；ReadPermit限定可读键/字段/租户，不是返回给调用者的业务数据 |
| admit | 同一Context、Input、`Option<Row>`前像、已取得的事实 | PermitWitness或Deny；见证绑定策略身份/版本、对象、动作、事实版本和时效，不能是没有来历的Bool |
| disclose | 当前Context、原操作Meta与已授权内部读取的结果 | 拒绝或有类型的R结果投影；投影不改写存储的真实终态与旧请求身份 |

Context、ReadPermit和PermitWitness是宿主签发、不能由普通源伪造的类型；业务比较本身仍可为中立函数。输入类型、动作与Row分别匹配operation和aggregate；有任一槽缺失就不签发完整运行绑定。不公开存在性时，probe/admit的外部诊断合并；内部仍保留实际原因。在只需一个静态策略的本地可信应用，三个槽可以在同一内存实现内完成，不制造多次网络开销。任一外部取得失败返回待决或明确拒绝，不能默认允许。

`txn.Revision`是事务组合夹具提供的版本令牌类型，由读取边界解码与比较；不是公共Int、墙钟时间或源码修订的别名。传入正确格式不代表版本匹配，更不授予权限。它没有把某种数据库版本编码泄露成公共业务含义。

#### 提交后的独立交付

`model/notifications.gift`：

```gift
import "./tickets.gift" as ticket;
import "app/notifications" as mail;

fn isClosed(event: ticket.TicketEvent) -> Bool !{} =
  match event {
    case ticket.TicketEvent.Closed(_, _) => true;
    case ticket.TicketEvent.Reopened(_) => false;
  };

export subscription notifyClosed(event: ticket.TicketEvent) {
  from ticket.tickets;
  select isClosed(event);
  deliver mail.sendTicketEvent(event);
  order aggregate;
  retry transient;
  exhausted park;
};
```

`mail.sendTicketEvent`必须解析到一个有明确效果、输入、结果、幂等和未知完成合同的端口；不允许按函数名推断安全。不请求通知的工程不需要此文件、工作进程或出站适配。选了此subscription而端口缺失时，整个包含通知保证的输出仍有缺项，不能偷偷丢掉订阅并叫完整。

`event changed`记录的是提交后要交付的业务事件，不是生成文件的emit，也不是立即执行网络请求。审计和出站记录与目标状态在同一提交域落下；订阅器随后处理。正常关闭响应不等候邮件服务，明确承诺的是状态已提交且交付义务已记录；发送结果另有身份和观察。

两份源可以生成一个普通模块化应用，不要求应用运行时回连Gift控制面。数据库、认证、通知等真实依赖仍然存在。零原生应用作者不等于零底层实现，也不等于只凭这段源就能使用尚未交付的库或后端。

### 声明的结构文法

本节的事务声明是基础文法之外的显式画像扩展；继承当前已绑定的基础表达式。基础作者语法当前为46项具名产生式，事务组合夹具不能继续以旧45项计数断言表达式原字节不变。`Import`、`TypeDecl`、`Function`、`PortDecl`、`BindDecl`、`ConstDecl`以及`Expr`、`Type`、`Params`、`RecordValue`、`QualifiedName`、`Arguments`、`Ident`引用[基础语言][k5]。声明内部括号、字符串、作用域和普通表达式沿基础规则；不建立第二套表达式解释器。

```ebnf
EngineeringModule = { Import | TypeDecl | Function | PortDecl | BindDecl | ConstDecl | EngineeringDecl } ;
EngineeringDecl = AggregateDecl | DecisionDecl | OperationDecl | SubscriptionDecl ;
AggregateDecl = ["export"] "aggregate" Ident ":" Type
                "key" "(" FieldNames ")" ["invariant" QualifiedName]
                ["events" Type] ";" ;
FieldNames = Ident {"," Ident} ;
DecisionDecl = ["export"] "decision" Ident "(" [Params] ")" "->" Type
               "hit" HitPolicy "{" DecisionRow {DecisionRow} Fallback "}" ";" ;
HitPolicy = "first" | "unique" ;
DecisionRow = "case" Ident ":" Expr "=>" Expr ";" ;
Fallback = "else" "=>" Expr ";" ;
OperationDecl = ["export"] "operation" Ident "(" Ident ":" Type ")"
                "->" Type "{" TargetClause AuthorizeClause ExpectClause
                DecideClause [ChangeClause] [AuditClause] {EventClause}
                ReplyClause "}" ";" ;
TargetClause = "target" MutationMode QualifiedName "(" RecordValue ")" ";" ;
MutationMode = "create" | "update" | "delete" ;
AuthorizeClause = "authorize" QualifiedName ";" ;
ExpectClause = "expect" (Expr | "absent") ";" ;
DecideClause = "decide" Expr ";" ;
ChangeClause = "change" RecordValue ";" ;
AuditClause = "audit" Expr ";" ;
EventClause = "event" Ident ":" Expr ";" ;
ReplyClause = "reply" Expr ";" ;
SubscriptionDecl = ["export"] "subscription" Ident "(" Ident ":" Type ")"
                   "{" FromClause [SelectClause] DeliverClause
                   OrderClause RetryClause ExhaustedClause "}" ";" ;
FromClause = "from" QualifiedName ";" ;
SelectClause = "select" Expr ";" ;
DeliverClause = "deliver" QualifiedName "(" [Arguments] ")" ";" ;
OrderClause = "order" ("aggregate" | "unordered") ";" ;
RetryClause = "retry" ("transient" | "none") ";" ;
ExhaustedClause = "exhausted" "park" ";" ;
```

`absent`在expect中的裸写专指创建的不存在前提；要引用一个同名普通值必须用合格名称，防止两个解释竞争。Operation头的返回Type在类型判断后必须为Result<R,E>；decide必须为Result<V,E>，业务错误类型一致。Declaration名称仍有稳定语义身份，名称和源行不是运行请求身份。

业务前置检查与条款在各自阶段的顺序已经明确，不能按字典顺序排序。运行解析依次为：语言/画像与声明类型、调用信封结构与认证、当前披露/查找限定、对象准入、存在与expect、decide、change与invariant、audit/event/reply、原子提交及结果披露。读取内部数据以判断授权并不等于允许向请求者披露它；权限先于业务错误的规则不表示不读取任何内部事实就能决定权限。未知条款、重复单值条款、重复规则标签和事件槽拒绝；不能因为没有新增全局保留字就把未知内容交给动态执行器。已有声明在基础画像中仍报告画像不支持，不自动联网获取解释插件。

### 决定表：短写法仍有完整求值含义

规则条件必须为纯Bool；规则结果与else结果统一为声明的返回类型。规则标签是该表内的稳定子引用，可以重命名但不能凭同一行号猜身份。表的函数参数按普通调用顺序求值一次；输入被冻结为不可变值。

`first`按作者顺序计算条件，遇首个true只计算该行结果，其后条件和结果不运行。`unique`按作者顺序计算所有条件，零命中只计算else结果，一命中只计算对应结果，多命中产生DecisionOverlap，不因为各行碰巧返回相同值而放行。未知、陷阱、超时不是false；pure也不证明条件总能结束。

unique按当前既定顺序遇到的条件求值错误立即停止，不继续运行后续条件来寻找另一个诊断；成功完成全部条件后才决定零个、一个或多个命中。因此短路与错误优先级是显式语义，不能通过并行计算条件改写。

else在本压力夹具必需，因此零匹配行为无需依赖万能覆盖证明。静态发现可达重叠、遮蔽或不可能条件时给出诊断；声明unique而无法静态证明时可以保留运行检查。`first`中的重叠本来合法，不能误报为全部不可编译；改排序属于可观察变化，不能当排版。

[Camunda的DMN命中策略][k6]明确区分Unique和First，说明不能只说“这是规则表”就推导执行结果。本压力夹具不是宣称实现全部DMN；聚合、多输出、概率和带作用规则须各自扩展，不能偷偷塞入同一两个策略。

### 聚合值、关系和共同不变量

aggregate要求具名、有限可序列化的值记录。key中的字段必须真实存在、无重复并具备稳定相等/编码；本压力夹具不支持将函数或资源句柄作为持久字段。业务键与语义声明ID、物理主键、请求ID和行修订分别处理。默认键在普通update中不可改变；改键走明确迁移，不隐藏成一次属性更新。

invariant解析为`(Row) -> Bool !{}`的纯谓词，对每次合法创建与修改的候选后像执行；谓词自身错误与false分开。没有invariant时只执行类型、键与框架约束，不虚构业务不变量。必需的输入/持久值解码必须区分有限大小、字段存在性、中立数值和未知字段；不把目标数据库的任意JSON自动当成合格Row。events未声明时禁止event条款；声明后每个事件表达式必须符合该类型。声明“所有更新保持不变量”要求所有可写入口都经过对应合同，或由目标约束/权限等价强制。其他应用、脚本、管理员或导入路径可以绕过时，保证只能限定到受控操作，不能从生成器存在推出整个数据库永远合法。外部漂移重新观察与修复仍走有权的新操作。

声明不是表名，也不等于物理一行。小对象可用一行，大的聚合可使用多表与受控子对象，但同一次原子改变必须由一个合格提交域处理。物理布局、索引、拆分和压缩在目标绑定中决定；不要求AI同时维护一份镜像SQL模式。

跨聚合唯一性、外键、额度和集合约束不应伪装成逐行invariant。所选工作集的关系要求由现有Relation/Invariant模型声明，并向计划提供实际的读范围、存在/不存在观察、写集和保护机制。简单键唯一性可以由目标唯一约束承担；跨行约束需要共享根、范围保护或合格隔离。约束不能在本压力夹具中闭合时，准确诊断其范围，不把它丢给后台“尽力保持”。

反例：总额度10，两笔并发申请分别读取剩余额度10、各写入7；它们修改不同记录且各自CAS都成功，整体却超过额度。修订条件必须覆盖控制该不变量的共享事实或查询范围，而不只是每条新行。可以采用额度根的受控版本、同提交域串行化或明确的保留协议；不能通过改成两个微服务解决。PostgreSQL的[事务隔离说明][k7]明确区分可重复快照与可串行化结果；“数据库事务”一词不足以指定这些保证。

跨存储且没有共同提交能力时，不能把一个原子operation静默拆成Saga。Saga或预约—确认本身改变了允许的中间状态、补偿和失败语义，必须成为另一份被接受的业务设计。

### 本章与其余设计的唯一归属

基础值和表达式引用[语言体系][k8]；声明引用和候选采纳沿[身份模型][k9]；关系与领域分区沿[共享语义][k10]；目标代码沿[源码策略][k4]；事务与去重的完整物理边界沿[持久化提交与恢复][k11]；授权沿[权限执行][k12]；源/目标/宿主保证沿[验收][k13]。

本压力夹具完成了这一范围的作者、求值和接合设计，不声称关系查询、通用异步、全生态与所有分布式协议都已经定稿；有限状态图由自己的明确版本合同处理。新增反例改变根条件时修改相交规范；不靠增长库目录、生成实现载荷或给整包贴“最优”标签维持结论。

## 变更、授权、提交与交付

### 变更条款、作用域与结果

| 条款 | 精确责任与默认 | 失败或边界 |
|---|---|---|
| target | 必须显式给create/update/delete、聚合引用和全部业务键；键表达式可读输入与受信actor | 不读取目标前像，也不执行用户端口；无权主体不能借错误详情枚举对象 |
| authorize | 必需策略绑定；处理当前请求、目标限定、行为准入、结果披露 | 源写出策略名字不是授权；外部策略事实必须有明确见证与失效边界 |
| expect | update/delete为目标修订；create为absent | 不用latest覆盖陈旧请求；未知不是不存在；自动重试不能更新作者传入的预期修订 |
| decide | 在当前前像和已取得的事实中计算纯Result<V,E> | Err是业务拒绝；谓词错误、预算和系统失败不混入E；不执行外部作用 |
| change | update为非空、具名字段的稀疏更新；create为完整值记录；delete不得出现 | update保留未列字段而非置空，不能改键；create完整值的键须与target相等 |
| audit | 可选的一条有限纯值记录，与成功变更共同提交 | 省略表示本操作没有业务审计要求，不表示平台可以关闭安全审计；敏感性不能因进入日志而消失 |
| event | 零或多条带唯一标签的类型化业务事件，与变更共同提交 | 标签产生稳定事件槽，不是目标topic；无events声明不接受；不立即发送 |
| reply | 必需的纯返回值R，用于构造成功Result.Ok | 在提交前计算并检查可序列化/披露条件；提交后不能再因计算业务答复失败而假称未提交 |

`before`只在成功读取update/delete的前像后可用，create不能使用。decide为Ok时，`value`绑定其V；update/create按change构造不可变`after`，delete不提供after。audit/event/reply依声明顺序求值，均可用input、受信actor、允许的request事实、before、value及存在的after；任何名字不适用时静态诊断，不补默认值。

operation形参不能命名为actor/request/before/value/after；这些词在操作条款的指定阶段拥有固定绑定，不能被同名输入遮蔽。纯函数内部的局部同名值只服从正常词法作用域，不能通过返回相同外形取得受信身份。subscription的事件参数也不能遮蔽其运行上下文槽。每个新阶段仅增加当时合法的绑定，先用after再定义change必须静态拒绝。

本压力夹具的request只暴露已解析的稳定逻辑操作身份与允许的固定请求事实；不暴露凭证、任意环境或处理器私有状态。时间和随机需要明确的取得点和保持策略，不能在自动重试的decide里每次重新读取。

单个Operation默认是一个变更根及其同提交域衍生记录；delete也必须保留所选版本协议要求的拒旧/墓碑信息，不能因业务值消失而让迟到create或旧操作自动复活。需要多根改变时，使用显式的合并计划与共同不变量扩展；不能在decide调用另一个operation产生隐藏嵌套提交，也不能把Result中的函数或句柄当作延迟写入逃出边界。纯业务函数可以无限定义，外部效果只有在声明的阶段发生。

对读接口，继续采用已有查询/端口合同，不强迫每次读取使用变更幂等表。本压力夹具的create/update/delete不是全部数据库操作的枚举；它是当前已经明确的变更表面。分层状态、复杂空间关系与多根便捷语法尚未因此全部完成。

### 原子提交与重新计算的准确顺序

编译器生成的应用处理器沿以下合同执行；这不是AI每次手填的步骤。

1. 解析受信上下文，核对请求结构、操作版本与允许的目标范围。对原幂等记录的存在性和结果披露按当前权限处理；该记录不能因写权限已经撤销而被误当新请求。
2. 固定原请求内容、逻辑身份和支持的重试窗口。相同主体/作用域/请求ID但内容不同是冲突。已完成且可披露时读取原版本结果，不重跑新版本业务；仍执行中的相同请求采用join/冲突协议，不平行制造第二次业务。
3. 在合格的短事务内加载目标前像、规则与必要授权见证，执行对象级授权、存在/修订检查及纯决定。授权拒绝先于可能暴露原因、状态或修订的业务诊断。目标读取能力与返回给请求者的披露能力分开。
4. 构造候选后像、验证类型/键/invariant及相交关系，计算审计、事件和应答。失败不写业务目标/审计/出站事件。本压力夹具默认保存已进入合法决定阶段的确定性业务Err作为同一逻辑请求的拒绝结果；它可以提交一个只含结果的事务，但不写业务状态/业务审计/事件。保存拒绝结果也需复核其前像与规则，不能发布来自陈旧事务的拒绝。之后原请求返回原结果；想按新状态尝试新业务须显式建立新意图。认证失败、不可披露结果及系统故障不伪装成业务Err，也不要求给未认证者创建无限去重记录。
5. 在同一原子边界内复核前像、规则选择与授权见证，保存状态、业务审计、出站义务和操作结果。提交成功才取得这些记录共同成立的事实；提交确认丢失保持UnknownCommit并查询原身份，不生成新身份重做。
6. 向有权接收者返回已提交结果与实际状态；外部交付由subscription继续，不能把业务结果的commit改写成delivered。

事务重试必须重算读到的状态、规则、授权和由此决定的写入；原请求、预期版本和稳定逻辑身份保持。由于并发更新导致版本不符时，返回冲突，而不是为了成功自行改成新版本。超时、唯一约束和死锁并非所有时候都可重试；按实际原因分类与预算执行。PostgreSQL[序列化失败处理][k14]要求重试完整决定过程，且不保证重试最终成功。

本协议不许把发送邮件、扣外部款项等放进可能重试的纯事务段。数据库序列分配等也可能不回滚；语义中未承诺连续无缺口时可用，不得据此产生“所有失败零可观察变化”的夸大保证。针对业务三组原子记录的保证，不是针对所有监控、分配和调度的全宇宙原子性。

### 授权时点、信息披露与跨存储见证

策略绑定必须声明读取来源、可检查的有效期/版本与撤销含义。默认本地配置采用同提交域的角色和规则版本，或能在目标提交点被验证的受信见证。数据库事务在另一个库提交，不自动原子观察远程身份系统的撤权。

远程权威不能提供跨提交原子保证时，可以采用已被接受的有界授权租约，明确最晚生效时间；需要更强即时撤销时，必须由相应权威/目标端参加协议。不能拿刚才检查过一次的Bool声称“提交瞬间权限绝对最新”。预览、缓存和闭包都不能扩展见证寿命。

对象不存在与无权访问可以按策略返回同一外部结果；内部诊断仍区分但按权限披露。角色改变后是否仍可读取原结果，依当前结果政策判断，不依据历史写权。审计、错误、队列、生成示例和源码映射都继承数据披露要求；只把正文隐藏而把敏感内容写入错误参数并不安全。

策略谓词与业务规则可以共享纯函数，但策略的事实来源和准入责任仍独立。相同租户字符串不是可信认证；源码内创建Actor外形的普通记录不会得到受信actor槽。

### 交付语义、顺序与幂等

订阅from指向聚合已提交的事件流；参数类型必须等于或经显式安全解码符合aggregate的events类型。select省略表示接收全部；存在时为纯Bool，按事件一次评价并记录所用订阅修订。返回false是明确排除，错误或超预算是未完成选择，不当false。

deliver必须解析到一个已绑定端口，参数计算为纯且封闭；实际调用在订阅准入与资源许可后发生。端口得到稳定交付身份，禁止在每次尝试生成随机去重键。逻辑事件身份包含实际运行部署/租户域、逻辑操作身份与事件槽；消费者效果身份再区分订阅实例/交付域。源码revision可以说明处理方法，但普通重部署不能自动产生新业务效果身份。返回成功的确认层次由端口合同决定：请求已接受、提供者已处理与收件人已收到不是同一结果；订阅完成只签发它实际取得的那一层观察。

order=aggregate只承诺同一订阅和同一聚合键的所选事件顺序，不承诺全局排序。分区键和元数据不会自己建立这个保证：投递器必须知道可交付前驱、并发占用和已确认进度。业务行revision可以有无事件变化，不能把序号间隙一律当消息丢失。过滤过的事件不阻塞符合合同的后继；当前未知或parked前驱在有序模式下阻止同键后继，其他键可继续。

retry=transient允许在原总预算中按提供者分类重试。未知是否发生的非幂等效果不能只贴transient就重发：目标有可靠同键去重时可以重试，否则先读回或停放未结算。retry=none表示一个获准尝试，不构成exactly-once。exhausted=park保留义务及恢复资料，不静默丢弃；后续skip、补偿或重新处理必须是当前授权下的明确操作。

默认不承诺邮件只到一次。只有接收方能在其实际副作用和Inbox记录之间原子保持，或外部提供者有相应去重合同，才能获得该范围内的一次效果。应用数据库中的Inbox不能替外部邮件或付款系统签发这个结论。需要严格无重复但目标不支持时，阻断的是该保证，不把任务变成“成功且尽力”。

[Debezium Outbox][k15]用不同字段表达事件ID与聚合键，它们分别服务去重与路由顺序；这不表示必须采用Kafka/CDC，也不替消费者提供副作用原子性。低规模默认可以使用数据库轮询工作器；实际顺序与故障条件仍相同。

### 状态宏步与事务操作怎样共同提交

当operation采用某一固定状态模型时，决定阶段调用纯`advance`，输入是被读取的stable snapshot与准确逻辑输入；它取得新的逻辑快照及待作用计划。准入和集合/修订保护由本章既有协议承担，图里的状态名或actor字段不授予权限。

计算可在锁外完成，提交时重新核前像、授权见证及相交读域。同一原子域保存快照、输入结果和必要待交付命令；未要求审计或外部交付就不生成空表。实际活动不在事务锁内等待。提交前计算失败保持原数据；提交后响应丢失读回原输入；活动结果未知走原提供者协议而不是重放entry。

图到达final可以与取消中的资源同时存在。operation承诺仅“关闭逻辑状态”时返回相应结果；承诺“全部处理完成”时还要等待该任务实际要求的结算，不能因图final就给通知、文件或设备代签。跨根事务和跨存储仍由真实原子能力决定，状态图库不会添加这种能力。

### 差异压力：事务型应用的端到端不可逆分项

订单写入成功、库存预占、外部扣款、物流出库分别有不同回执、隔离和补偿所有者；幂等回执已过期时再发付款不安全。管理员撤销Grant后不能删除既有账目，也不能授权未知效果重试。两个本地事务都提交成功，不证明跨服务全局订单不变量在同一观察切面成立。

## 编译、布局与确定性

### 由四种声明得到可运行工程的编译路径

| 阶段 | 输入和责任 | 明确不做 |
|---|---|---|
| 画像/源读取 | 固定基础语言与本压力夹具，保全源、导入和稳定子身份 | 不执行模块，不因名字猜业务 |
| 绑定与类型 | 聚合键/事件、决定参数、策略、修改字段和端口闭合；纯式与作用边界分离 | 不用字符串字段表代替真正的符号与类型 |
| 业务决定IR | 保留规则标签、命中策略、错误和未定项，绑定纯函数 | 不一开始就展开为失去来源的任意目标代码 |
| 变更计划 | 连接读域/前像、授权见证、决定、候选后像、原子记录与结果 | 不把“事务”命名当成某数据库已符合 |
| 目标资格与绑定 | 选择存储、策略、消息与序列化能力；检查相交不变量和运行画像 | 不静默用Saga替原子事务、不为每行新增服务 |
| 目标降低与布局 | 生成业务纯函数、边界校验、事务处理器、模式/迁移候选、出站/订阅配置和必要连接 | 不把Gift控制面包树复制进应用；不把生成源码再当作者源 |
| 检查与交付 | 对实际语义、目标代码、配置、数据库与效果声明各取所需证据 | 不把目标类型通过当成持久原子或送达证明 |

Operation mapping/plan 使用既有 Operation/Effect/Artifact/Claim 身份与依赖；它只是本作者画像到既有执行合同的派生映射，不取得独立 IR 身份，也不是第二操作账本。纯decision可以单独生成且不加载数据库；未被所选输出根使用的subscription不启动。高级函数泛型、所有领域IR或人类IDE不是这条有限工程路径的全局前置。

示例TS目标可把规则和处理器放在同一功能模块，部署绑定复用现成驱动；Java目标可以使用同含义的类方法与事务适配。两者必须观察同一业务错误优先级、CAS、规则见证和事件含义。SQL方言、字段编码与连接池由目标负责，不能在公共类型里隐藏TS对象或Java反射值。

目标默认是模块化单体。仅在独立故障域、信任、发布和资源需求成立时拆服务；业务原子域不能因团队喜欢微服务而被暗拆。产物不强制包含网络API；函数库、嵌入处理器、服务入口分别按输出请求需要生成。声称“零原生应用作者”的场景，应用业务源不能再藏进未展示的手写Adapter；成熟驱动内部的实现不计作应用作者代码。

#### 何时采用及正常生成

实际任务需要持久状态、版本保护和跨制品一致性时，先固定类型、状态、转换、不变量、错误、授权和提交范围；所选画像允许时生成状态处理、存储与接口。没有审计或可靠通知要求，就不强制生成审计/Outbox；纯计算也不需要证明一次事务应用才能完成工程出口。

一个选定Python/SQLite与TS客户端的目标可生成service.py的业务处理、runtime.py的实际提交能力、schema.sql、api.py、client.ts、openapi.json和必要说明。它们是有真实消费者时的可选布局，不是所有程序的固定文件表。每个文件有来源、拥有者和内容身份；验证义务说明要检查什么，不能凭一个verification-obligations.json称已经通过。

模型合法性先检查：初始/目标状态真实存在、字段与操作名称唯一、值域有序、引用及未知成立范围清楚。随后按照现行合同连接真实提供者、生成相交源码与资源；只有请求实际构建、采用或运行时才执行相应操作。未绑定义务可以留在合法设计中，所选输出真正依赖它时才限制该输出的完整性。

#### 值域、写入范围与重试保持

目标协议若使用JSON数值或宿主定宽表示，先证明实际值域可精确表示；例如非负安全整数范围仅是该传输画像的限制，不定义中立Int。范围不足时采用合格编码或报告该目标缺项；版本耗尽不能回绕。文本解释指定标量与编码规则，字段标识和业务文本分别检查，不能将文本拼成任意SQL、路由或执行代码。

写入集合来自当前operation明确的变更及其生成规则。只声明状态改变时，其余载荷保持；声明金额或算法参数改变时，检查相交不变量并更新对应字段。稀疏修改不隐含整行覆盖，新增字段也不被旧完整记录默认值抹除。

同键重试返回原确定结果，当前披露权限和新执行权限分开。already-target的return-current与reject是公开行为选择；return-current仍核对声明的前提，必要时保存逻辑结果，但不伪造新的状态改变、审计或事件。请求身份、行版本和语言修订不混用。

#### 存储、初始化与迁移

可以采用当前状态表加按需记录，而不建立全局事件溯源。主键、状态、范围和共同约束由真实事务/数据库与应用协议承担；只将载荷存成JSON不能取得全部索引或查询能力。更强查询和多根事务需要相交设计，不通过串联独立操作宣称共同原子。

只有显式初始化任务、合格目标与当前权限满足时，才从空目标建立模式；连接库或读取声明不默认创建数据库。既有库的语义摘要与当前目标不兼容时返回MigrationRequired，选择明确迁移；相同摘要允许按原合同使用，但不自动证明内容无漂移。说明文字变化可不改变运行含义，解释器、字段值域和错误变化则应进入相交身份。

迁移先处理旧状态、数据范围、角色、事件、幂等保留与在途交付，真实旧写者也参与保证范围。管理端口、seed和授权设置只在对应权限内使用，不因不暴露公共HTTP路由就具有系统安全隔离。持有数据库文件的其他进程可能绕过应用协议，需真实宿主保护或限定保证。

#### 保持、失败与退出

源码、API和客户端能生成，不证明网络监听、认证、TLS、通知或部署已经满足。科研任务的状态转换正确，也不证明其中科学算法正确。目标运行可以脱离Gift控制面，但真实依赖和授权仍存在。

当字段扩展侵入事务内核、当前表示无法保持任务或目标能力不够时，修改相应语义/Provider而非增加工单专用中央分支。需要任意计算时直接使用计算作者能力；要求更强消息保证而端点不支持时给准确缺项。退出和恢复沿真实操作、原内容与目标前后像；废弃编码或删除工具不能取消仍未结算的作用责任。

## 演进、结果与检验

### 连续修改、异步业务与旧消息

#### 加一个关闭条件

在decide或相关decision规则中增加图片条件，不重写身份、权限、事务、审计和投递骨架。模型补齐新的输入字段和真实约束；旧来源不足以支持图片事实时，定义所需的读取或声明，不把调用者自报“有图片”当成真实性证明。静态pure不代表事实新鲜。

#### 从同步关闭变成异步复核

这种变化真正增加一个Pending状态，而不是给原操作加async关键字后保持旧承诺。沿已有构造形成：请求复核operation，提交Pending和ReviewRequested事件；subscription向复核端口交付；复核回调进入另一个受权operation，比较活动reviewId、对应内容摘要和期望修订，再关闭、退回或拒绝；取消也通过独立operation竞争同一版本。

reviewId由原逻辑请求与稳定槽位确定或预留并保存，重试不换身份。回调的真实性、来源和披露先检查，payload不自行携带管理员权。旧回调不能完成已经取消/替换的复核。单笔原子事务不跨外部等待；超时由明确调度提供者投递带相同相关身份的事件，在操作中重新判断当前状态，不能靠旧计时器直接覆盖新状态。

这条业务可以在本压力夹具中作为持久状态与消息组合设计，不需要每个短async函数都有工作流记录。有限嵌套/正交状态的作者与反应由[状态图库][k17]承担；实时期限、连续过程、任意动态图与通用durable-await仍各有义务，不能把本例称为所有异步语言完成。

#### 旧实例、旧事件与新定义并存

本次修改默认只影响新请求采用的操作合同。旧幂等结果保留其原合同解码；旧待交付事件保留创建时的schema与业务含义。更新订阅或处理器必须选择兼容旧事件、显式转换、保留旧处理版本、排空或有权停放，不能在部署时自动让旧负载调用新意思。

订阅替换保留原交付身份的连续性；创建新订阅是新的消费义务，其起始快照/偏移必须显式确定。历史重放是新的、有范围的动作，不能因进程重启或subscriber名字相同就重发全部效果。删除一个subscription不自动清空已有未结算消息。安全撤销可以先阻断旧执行，保全与隔离旧待办并不等于继续授权它运行。

新增invariant要决定是仅约束未来写入、立即要求全存量满足，还是通过显式迁移取得更强状态。不能检查一条新数据后宣称整个旧库已经符合；也不能把全库迁移放在不受影响的普通函数之前。

### 整体状态不合并为一个绿色标记

同一需求必须能分别定位：作者候选、被采纳定义、生成物、部署绑定、运行数据修订、逻辑请求结果、消息交付和对应证据。它们共用必要关系，不是同一个revision，也不要求每个表达式都复制这些字段。

operation的成功提交可以与subscription暂时停放同时成立。数据与消息可因后续修订改变，不能倒写历史结果。旧结果披露被撤销也不等于业务回滚；新目标代码通过typecheck不等于旧生产数据已迁移。

AI正常改业务只发送相交源文本或差异；基础画像与所用合同已绑定时不遍历能力目录。大结果按需展开，小结果直接给所需源或差异；依赖追踪、规则标签身份和事件关联都由系统维护。终端若已接入合格的`gift.ai-tools/2`消费者，可按协议读取、修改、生成和检查。该协议的write-output职责只写代码，绝不把它借名用于关闭真实工单或发布应用。

### 样本输出、代价与反转条件

| 当前选择 | 为什么采用 | 何时改选 |
|---|---|---|
| 同一.gift中显式组合压力夹具 | 避免TS绑死与另一本JSON镜像，仍允许短函数零包装 | 如果真实任务不能用当前四类结构保持含义，扩相交画像，不按业务名加分支 |
| 纯decision加持久operation | 缩小事务中的不确定执行，复用业务规则，分开正确性与作用 | 真正需要事务内受控读取时扩大显式读域，而非把任意IO藏进pure函数 |
| 当前单根变更 | 可以明确前像、键、候选后像与提交点，减少首版无界规划 | 跨根不变量需要更大共同域时必须显式扩大，不假装单根CAS足够 |
| 默认模块化单体与一个原子存储域 | 小规模不用维护微服务和分布式事务 | 独立信任/故障/发布/容量收益证据成立时分离，同时重审原子承诺 |
| 出站后投递，有限重试加停放 | 可区分提交与送达，便于恢复，不做盲目重放 | 要求更强一次效果时加入真实目标去重，而非只提高重试数 |
| First/Unique两种决定政策 | 常见顺序与排他决定已经确定，不先实现全部规则引擎 | 实际消费者需要聚合/并行/概率时选择相应新语义与保持方法 |
| 目标库和驱动复用 | 不重复实现数据库、权限平台与消息协议 | 实际接口不能满足不变量或诊断时才增加薄适配，不堆同义wrapper |

这些默认把复杂度放在有真实消费者的位置。与成熟原生框架的公平对照应当同样允许事务辅助库、Outbox库和代码生成；不能把此例的十几行操作与对方被禁止复用的手工实现比较。真正需要观察的是首次引入、连续变更、迁移、定位和恢复的总成本，而不是只数关键词或源码行。

### 书面反例与后续符合性

| 反例 | 必须出现的设计结果 |
|---|---|
| 参数reason为空且对象无权读取 | 先遵守披露策略，不通过错误泄露对象存在性 |
| 更换actor字段但没有真实认证 | 不能创建受信actor；禁止进入业务准入 |
| 两个操作用相同旧revision关闭 | 至多一个适用成功；另一方重新检查后冲突，不自动接受新revision |
| 跨行总额同时超支但每行CAS成功 | 识别约束保护缺口，扩大共同域或选择范围保护，不签发完整保证 |
| 事务因为序列化失败重试 | 重算全部相关纯判断；不重新发送邮件、不改请求身份 |
| 已提交但响应丢失 | 原身份读回结果与事件义务，不再次修改业务 |
| 邮件成功但确认丢失 | 有目标幂等才能同键重试；否则停放未知，不声称未发送 |
| Unique两规则都命中且结果恰好相同 | 仍为DecisionOverlap；不悄悄改成Any政策 |
| 修改事件schema后仍有旧队列 | 旧解释/转换/排空/停放有明确选择，不按latest强解码 |
| 同配置的两个订阅实例 | 独立交付身份，除非有明确接管协议，不因结构相同合并 |
| 旧timer或复核回调晚到 | 根据活动相关身份和当前状态拒绝/忽略，不完成已撤销过程 |
| 改成仅纯函数输出 | 不初始化状态表、审计、消息工作器或Gift控制服务 |

本章定义的是这些结果与处理机制，没有执行测试。未来符合性必须检查作者源、IR、生成器、实际数据库及消费者之间的同一关系；仅测纯状态函数或只通过目标类型检查不足以通过本事务组合夹具的持久变更出口。

## 跨产品现实变更：联合观察而非“全局完成”

这个夹具下面再引入**一次具体维护请求**，仅用来暴露原有合同组合后的非局部失效，不增加新行业原语：某多租户系统的界面、服务和数据库共享“按时间过滤订单，仍保持既有排序”的要求。作者允许修改源、生成候选和运行离线检查；**没有授予联网安装、远程发布或数据库迁移**。固定时点的 `Requirement@r7` 约束排序与隐私，前端与服务消费同一个 `OrderFilter` 模块；数据库仍由旧生产 Provider 负责。

| 时序及新观察 | 实际被影响的责任 | 合格的具体结果 | 必须保留的状态 |
|---|---|---|---|
| T0 客户端发起局部变更 | application/workspace | 捕获当前作者源、未保存缓冲、影响根、禁止发布的 Grant | 被接受的 Requirement@r7 与两处源码修订，不用屏幕行号充当稳定身份 |
| T1 作者候选新增筛选项 | semantics/realization | 解析语义、公开调用/排序保持与精确供给；已知实现可直接采用，否则形成待审核 DesignCandidate | 查询缺失/权限拒绝/Provider 目录尚未遍历完整时不能证明唯一可实现 |
| T2 另一作者同时修改服务排序 | workspace/跨 owner 不变量 | 先核当前字节与公共排序谓词前像，再合并或返回冲突 | 已提交的新排序与未提交的旧过滤补丁分别可追溯，不静默写回旧值 |
| T3 新 Provider 被注册 | resolver/cache | 已采纳决定不必自动撤销，但以负集合完整性作出的最优/唯一判断应失效并重新评估 | 先前仅见范围里的候选记录和旧证据不消失，但不继续作为全集判断 |
| T4 编译生成 UI、API 两个目标根，服务目标检查不通过 | compiler/target/assurance | 输出成功 UI 根、失败服务根与其具体诊断；共同发行条件不满足时不能签发完整 release | 原输入 basis、确实生成的制品、下游需要的检查/证据义务 |
| T5 远程构建先前的旧基础结果迟到 | compiler/remote cache | 比较冻结 Source/Target/Policy/依赖 identity，过期结果被拒绝更新当前候选 | 老结果仅在其旧修订及有权披露范围内保留 |
| T6 用户点“交付”，仍未授权发布 | application/execution | 可导出已验证的本地源码或候选报告，不联网、不执行数据库操作 | 未发布声明、分项覆盖和没有创建现实 Effect 的事实 |
| T7 后续独立授权生产发布，Provider 回执丢失 | execution/storage | 使用真实 Operation/Attempt 身份读回；若既无可靠查证又无幂等保证，返回 `UNKNOWN_EFFECT` 并停放重试 | 已产生费用、未结算资源、可能已生效的部署；不能把 UI 请求超时当回滚 |
| T8 运行中取消、Grant 被撤销 | execution/权限/assurance | 阻止新的未获准 Effect；已接收且不可逆的 Attempt 继续依法/按合同追踪；只对仍满足依据的 Claim 复用证据 | 撤销时点、旧代执行可能晚到、剩余账单、需转移的恢复责任 |

此表不定义所有时间顺序中的唯一工程实现。T7/T8 仅作为**新的获准独立请求**，不由 T0 的只读/写源码授权自动发生；如果没有所列真实产品 Provider，场景停在 T6。T4 的服务检查失败不阻止用户拿到可阅读源候选，却阻止把“UI 成功”写成“完整服务已上线”。数据库迁移如果日后确需执行，还必须按数据库所属事务与 Schema 演进规则，不能重放本夹具里的模拟操作。

**如何把这些情况变成符合性测试**：同一个作者源/Requirement 冻结 basis 上分别注入 T2 双写、T3 负依赖翻转、T4 子根失败、T5 旧回执、T7 Effect 不确定与 T8 真实撤权；观察是否符合各责任 owner 的精确 verdict，并保证 T2/T5 的拒绝不会抹掉合法的 T1/T4 部分成果。Oracle 应包含独立生成的排序样本、Provider 自己的真实读回和发布主体的合格日志，不能全部由同一个生成器推算。

## 联合压力轨迹：权限撤销、编译二根和数据库迁移共存

本例继续使用上文的**假想作者项目**，不把 Ticket 业务纳入 Core。两个源模块 `ticket-core` 和 `ticket-api` 共同引用可更换的作者规则，并生成 `API` 和 `worker` 两个交付根；某个真实运行 Provider 可能发出支付/通知。测试态按 `S(source/lock)`、`C(candidate/binding)`、`A(artifacts)`、`O(operation/attempt)`、`P(policy epoch)` 与 `E(evidence)` 六个维度观察，但它们并不是另一个可写状态表。

| 步骤 | 外部变化与实际检查 | 正确结果 | 错误系统会如何失败 |
|---|---|---|---|
| 1 | 两个作者源与相同锁提交第一代构建 | 两个根分别取得Artifact；只有已通过目标消费者的根可标 `BUILT` | 单根通过即全项目成功 |
| 2 | 作者修改共享字段，但另一个编辑者同时修改共享约束 | 联合读集/共享谓词冲突，未采用的新变更保留候选 | 两个独立文件CAS均成功即同时采纳 |
| 3 | Provider注册表新增候选 | 只有依赖该闭合枚举域的最优性证书失效；旧固定绑定仍按资格保留 | 每次编译随意重选最新库 |
| 4 | 生成两个根，API成功、worker因工具链缺项失败 | API结果可复用；联合部署不可标为完成 | 删除好结果或提交混合ArtifactSet |
| 5 | 旧运行发起对外通知，准入后丢失接受回执 | 保留原 Operation/Attempt、效果未知及对账义务 | timeout解释为没发送，换键重发 |
| 6 | 主体的通知权限被撤销 | 后续新动作拒绝；已接受而不可撤回的尝试进入核对 | 把撤权当作能物理收回旧通知 |
| 7 | 当前规则和物理 schema 升级，新库在最后验证前崩溃 | 不发布半新代；旧合格库和未完成迁移保留 | 删除旧数据库后开始创建新表 |
| 8 | 从旧备份恢复到新机器，旧数据含已删除敏感内容 | 先隔离、重放撤回和拒旧前沿；未通过不得向新用户披露 | 读到备份就自动恢复写和读权限 |
| 9 | 两个不同Provider分别给出第一页，期间某成员加入 | 只能宣称版本向量范围内的观察，不能证明全域不存在 | 拼成一个伪联合快照 |
| 10 | 第二次作者修改只触及API的文案 | 依据实际影响闭包复用未变根；新SourceMap和Artifact与旧运行分代 | 机械重写两个根并把旧运行记录丢弃 |
| 11 | AI会话被取消，但远程Provider继续收费 | `request cancelled` 与 `attempt unsettled` 并存，冻结必要负债 | 取消即资源账归零 |
| 12 | 验收请求要求“设计+产物”，不要求部署 | 不等待真实发布和支付结算关闭其**设计/构建**子请求；已有外部Effect仍单独结算 | 反过来强制全部部署或把遗留Effect隐去 |

同一个样本中可分离的处理不意味着要造一套事务框架：作者提交由Source owner、选择由Resolver、产物由Target、执行由Operation、资格由Assurance掌管。任何一项无法做出正确区分时，直接定位到其原 owner 的规范重开/实现差异，不用再复制“综合事务规范”。
