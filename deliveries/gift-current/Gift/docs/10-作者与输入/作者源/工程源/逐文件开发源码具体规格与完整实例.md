# 开发者工程源码逐文件规范与完整实例


### 先把开发者成本压到业务不能省略的部分

本设计选择同一来源协议：`gift.project.json` 选工作目录、输出目标与产品根；`*.module.json` 定义可复用语义对象及其有类型关系；若作者明确选择原生实现，已有 `.ts`/`.rs` 文件仍是原生作者源，不强行改写成 JSON。普通作者不需要第二份 Intent IR、解释缓存、SourceMap、校验文件、Model/Target 的重复声明。IDE 可编辑其图形投影，但写回同一文件所有者。

作者根格式标识可由工具模板一次填入；Definition 的 `kind` 决定 Body 的专业解释。`namespace`、`imports`、`exports` 和 `dialects` 都不是每个私有模块的强制填写项。ModuleId 是稳定定义容器的逻辑身份，**不以文件路径推导**；文件归属则从 Project 的 `sourceScopes` 扫描获得，**不再由 Project 维护第二份 `modules` Map**。

### 一：一个完全自含的私有类型模块

```json
{
  "schema": "gift.author-module/2",
  "moduleId": "module:notes-model",
  "definitions": {
    "NoteId": {
      "kind": "core:type",
      "body": {"type": {"tag": "scalar", "name": "text"}}
    }
  }
}
```

这里 Definition 的局部 ID 就是 `definitions.NoteId`。它没有跨模块导出、实例化、方法绑定、目标选择或真实计算；增加空 `imports`/`exports` 不提高表达力。文件格式标识中的 `/2` 用于将来识别读取合同，不要求开发者在 Body 每个字段重复写协议版本。

### 二：同一个模块内的纯计算定义

```json
{
  "schema": "gift.author-module/2",
  "moduleId": "module:math-identity",
  "definitions": {
    "Identity": {
      "kind": "core:function",
      "body": {
        "parameters": [{"name": "x", "type": {"tag": "scalar", "name": "int"}}],
        "returns": {"tag": "scalar", "name": "int"},
        "effects": [],
        "body": {"op": "var", "name": "x"}
      }
    }
  }
}
```

此例仅证明统一作者协议中**可以描述一个无副作用、直接返回形参的函数合同**。它不使用尚未正式设计完的标准算术库；不能据此宣称已能写完任意新算法、编出实际目标代码或证明程序终止。以后计算语义逐步闭合仍修改同一 `core:function` 及 Type/Expr 设计，不另建 `.gift` 必学第二套作者语言。

### 三：项目仅选择来源及输出

```json
{
  "schema": "gift.project/1",
  "projectId": "example:notes-editor",
  "sourceScopes": [
    {"root": "design", "kind": "semantic", "editSource": {"mode": "file"},
     "include": ["**/*.module.json"]}
  ]
}
```

这是**尚未选择输出产品根的工程源登记**，不是一个可构建的产品。完整产品还需要 `targets` 指定 Target Profile 与 `outputRoots`，Root 的 DefinitionRef 及业务上下文；每个根的硬需求必须从被接受来源独立保留。真正目标Profile不可由这个例子臆造。`sourceScopes` 扫描的解释必须固定：路径大小写和规范化规则、显式 include/exclude 优先级、符号链接/越界、重复 ModuleId/路径冲突、读写拥有者与文件失败的结果。排序不得改变模块身份。


### 五种开发动作落在哪儿

| 开发者想做的事 | 作者只写的真实决定 | 由哪个 Owner 消费 | 避免的冗余 |
|---|---|---|---|
| 新业务对象 | `core:type` 或数据模型、名义域定义 | Type/Data | 不手填生成结构体和全部派生索引 |
| 新业务目标 | `intent:goal` 的模态/量词/范围与 `domain:meaning` 或有型计算谓词使用 | Meaning/Requirement | 不指定未知 Method、虚假验收 |
| 组成系统 | `product:component` 模板和 `product:system` 实例、端口、外部要求与连接 | Component/Product | 不复制每个组件 Body 或第二实例登记 |
| 规定真实行为 | `workflow:plan` 明确输入、控制后继、效果操作、错误/取消；Component `activationRoutes` | Workflow/Effect | 不用按钮文本猜函数、按数组顺序偷跑 |
| 保留特殊算法或平台 | 可选 `core:function`/`native:implementation`/目标选择或被接受的硬限制 | Compute/Method/Target | 不迫使普通业务作者先写底层库代码 |

**语法短不等于遗漏**：当操作的前提、授权主体、唯一性、持久状态、时间或失败后果在业务上不可推导时，作者仍必须定义或绑定这些信息。可以由有资格供应明确提供的默认值才能省略；省略不是允许系统自行改变业务决定。


### 可以反复组合到多大？

对于所有可被有权领域解释或可定义计算语义赋予意义的有限业务描述，构造的理论路径是：定义名义对象/类型 → 建立关系和有型谓词 → 声明模态/约束及环境 → 引用或定义流程/计算 → 实例化和组合 → 选择系统根 → 合取跨根硬限制 → 通过合格 Method/Target 取得**可实现方案**。这一组合结构不固定行业清单或最大组件数，但其类型系统、计算基础运算、完整动作/时间/错误代数及各领域解释器还有尚未完成之处；目前不能宣称对所有意图已语义无损。

三种必须保留的失败出口：意图虽可记录但无精确Meaning；Meaning明确但方法/目标/实际授权缺失；需求内部自相矛盾或不可计算。不得为了“语言能够表达任意意图”把三种情况都偷偷填入默认实现。更完整的理论边界在[开放语义](../../../20-语义与组合/组合/抽象与开放定义.md)，实际输入、控制和结果合同在[组合代数](../../../20-语义与组合/组合/跨软件需求合同.md#joint-requirement-closed-composition)。


### 与当前复杂范本的关系

`examples/notes-editor` 展示两次同模板实例化和UI至Workflow的明确连接，但引用了尚未供应的外部意义、目标、Issuer等；它是**包含未决依赖的产品源设计案例**，不是一个可以真实运行的 IDE。生产能力在 Method/Target/Runtime 的消费及真实实现完成之后才能得到，不因本文件写出了 JSON 例子而已经存在。

## 同一工程的多根选择和义务独立性

同一 `gift.project/1` 由 `sourceScopes` 发现候选模块；每个 `targets[name].outputRoots[]` 指定被选中的公开模块出口。每个被选根拥有当前目标内稳定 `rootId`；同一 Definition 被选为两个根仍构成两个根发生点，其 ComponentInstance、Requirement和ContextBinding不得仅按导出名字合并。`contextBindings`也不暗含真实外部Issuer或Grant。多根环境发生共同资源、事务或政策约束时，只能通过已证实身份和明确资源关系进行联合求解；相同引用文本不足以确认共享一个现实对象。

目标Root被删除、替换或新增，会改变**该次构建选中的义务范围**；它不修改独立接受的原Requirement，也不意味着被删掉的业务要求从历史和授权系统中消失。生成资格必须在本次目标范围下核对全部被接受硬目标及交叉需求，不能通过移除Root伪称设计要求已满足。历史 Gift130/131 工程范例仅供兼容来源理解，新项目采用 `gift.author-module/2` 和当前项目Writer，不依赖旧Schema检查器或历史假定的 `modules` 表。

## 0. 直接开发的 Gift 工程：哪些文件是源码，谁写，哪些绝不能伪造

本节是开发者实际文件方案的统一实例Owner；各机器字段的唯一解释仍由[工程清单模块与绑定锁协议](工程清单模块与绑定锁协议.md)、[结构化源码](../结构化源码.md)、[意图主源](../../../20-语义与组合/作者语义/通用意图语言-意图源与语义组合.md)与相应真实Dialect负责。**合法JSON、已采用的要求、已合格的Method、可生成目标、已构建产品、真实效果**是六个不同结论。不能靠“文件齐全”越级。

### 实际工程文件分类，不强制每个工程创建全部目录

| 源或结果 | 默认保存位置（允许按清单定位） | 修改权与真实内容 | 存在条件、禁止做法 |
|---|---|---|---|
| `gift.project.json` | 工程根 | 作者固定ProjectId、SourceScope以及按需Target和输出根；Module位置由实际发现的SourceSnapshot派生 | 持久的结构工程需要；片段任务可只用临时Context；无Target合法 |
| `*.module.json` | 任一受选SourceScope内 | 作者保存`gift.author-module/2`、按需的Dialect和Import/Export、类型化Definition | 只有需要独立结构含义时才创建；不得复制原生函数源码成第二份可写AST |
| `intent:goal` | 任一真实Module中的Definition | 角色、MeaningImport、六模态、公式、时间与观察范围 | 不要求每种模态都写；不自行创造Policy和Meaning |
| `semantic:pattern` | 真实Module中的Definition | 可复用角色、共同义务、变元和观察边界 | 有复用必要才抽象；不得因为不同领域都叫“容量”就同一化 |
| `semantic:pattern-use/2` | 真实Module中的Definition | PatternRef、带基数的绑定、Variation和Observer选择 | 所选Pattern与策略须能类型化解释；缺依赖只能留Need |
| `req:composite` | 真实Module中的Definition | 参数、主体、复合Term、公开值 | 8种Term按各自语义解释；require/prefer不改写原目标 |
| 原生TS/Rust/SQL/其他源码 | 原生 `src/` 或其源仓库 | 原生态拥有算法、配置、声明及专有接口 | 只有独立实现才保留；是否可作为Method必须单独资格化 |
| `*.binding.json` | 被清单明确引用的作者/供应选择目录 | 作者选真实源符号、语言Profile与必要名义绑定 | 路径不是授权；选择符号不等于执行合同已证明 |
| Control 文件 | `gift/controls/`等作者选择的位置 | 作者在指定scope、Target下选择`require/prefer`及值 | 要先有合格ControlDescriptor；原生和能力默认不靠隐含数字覆盖 |
| 资产与外部配置 | `assets/`、原生配置与秘密管理系统 | 原格式与其真实owner | 资产不因旁边有JSON自动成为语言规则；秘密不写进锁 |
| `gift.lock.json` | 工程根（生成） | ResolutionOwner固定精确内容、发生位置与依赖 | **绑定真实完成才写；不得手填伪摘要或用latest替代缺失内容** |
| 目标源码、依赖清单、迁移、资源 | 由Target明示、隔离的输出位置 | TargetOwner从合格Plan生成，可有受管编辑区 | 没有合格Method和完整Target不允许声称完整源码 |
| 调用、部署、运行、Evidence | 工作目录外的受管状态/报告 | 实际运行和保证Owner | 不属于作者意图源；Grant与真实效果不得写成要求已满足 |

**最小合法结构工程**：`gift.project.json + design/<至少一个真实模块>.module.json`；模块必须在唯一受选SourceScope中被稳定发现且`moduleId`不冲突，项目范围明确，用户可以只交付设计。不需要空`src/main.gift`、不存在的供应、空锁、空Target或伪装实现的stub。**完整可生成业务工程**则是同一作者工程另取得合格Meaning、Requirement联合、Method、Target和环境闭包，作者不应再手工复制编译结果。

### 成品与源码所有权的实际约定

清单定位只是发现作者材料的**必要而非充分**条件。正式源冻结必须记录：准确工程实例、模块发生位置、SourceRevision、锁定Dialect与Method来源、目标Profile、作用域/权限和实际ReadSet。相同Definition可被多个Target消费；每个消费点有独立的Target条件和资格。生成产物必须保留AuthorRoot/Requirement/Method到目标文件、符号和测试的`SourceMap`，作者二次修改应回写唯一源或进入有声明边界的受管目标区域，不允许重新生成静默覆盖独立原生更改。

## 1. “工程源码”不是一种文件，而是有归属的文件集合

项目是一个有身份的作者工作区，能仅描述设计、也能混合已有原生程序。用户不必在开始一个函数时建立整个目录。持久工程中，每个文件应按以下**实际归属**解释：

| 文件/目录 | 内容与读者 | 创建与写权 | 必需条件 | 不是…… |
|---|---|---|---|---|
| `gift.project.json` | `gift.project/1` 工程身份、SourceScopes、目标请求 | 人/编辑器/SDK 通过授权候选写；工具严格解码 | 需要长期持久 Gift 工程 | Definition AST、执行授权、锁文件 |
| 由SourceScope发现的 `*.module.json` | `gift.author-module/2` 模块身份、定义和必要的显式导入与导出 | 选定 region 的唯一作者；工具局部 patch | 采用结构化作者源的模块才需要 | 派生 IR 或生成的源码镜像 |
| `src/**/*.ts`, `src/**/*.rs`, ... | 原生类型、算法、接口、模块、已有领域逻辑 | 原生文件 owner；Gift 只能按原生适配范围编辑 | 工程本来有这类算法时存在 | 必须重写为 `.gift`/JSON 的材料 |
| `Cargo.toml`, `package.json`, `tsconfig.json` 等 | 真实原生包和构建工具的配置 | 各自生态 owner | 当前技术栈需要时 | Gift 的通用 Meaning 字段表 |
| `assets/**`、SQL、CSS、SVG 等 | 真实资源及其外部消费合同 | 资源/数据库/前端 owner | 有相应资产时 | 一定能由 Gift Core 直接解释的业务定义 |
| `gift.lock.json` | `gift.binding-lock/1` 固定真实语言、依赖、Method、Target 选择及精确字节 | **解析器/工具维护**；用户审查后接受 | 完成真实解析并要求复现时才产生 | 手工复制 npm/Cargo lock、假哈希、自动授权 |
| 由 design SourceScope 发现的 `gift.control-file/1` 文件 | 稀疏、已固定的作者实现/目标 Control | 原 Project owner；有身份、scope、descriptor | 用户真的固定此类决定时才出现 | `null` 默认、运行时 Secret、同义的 Requirement 副本 |
| `.gift` | 合格 Profile 下的可选计算文本作者源 | 该 region 唯一 owner | 显式采用并拥有语言解释时 | 对所有工程必须写的语言 |
| `generated/`, `.gift/cache/`, `dist/` | 已发生的目标、缓存或外部工具产物 | 相应 producer；原则上派生写权 | 真实执行产生后才存在 | 长期作者真源或用户已经部署的证明 |
| `.gitignore`, `README.md`, `docs/**` | 工作方式、教学、操作说明 | Git/文档 owner | 项目按需 | Gift Core 自动赋予执行语义的关键字 |

文件与逻辑模块是两种标识域：项目可只含 `gift.project.json`，也可在大型多语言原生工程中只添加一个独立的结构需求模块。只有被本次 `sourceScopes` 选中、且其文件自身声明了唯一合法 `moduleId` 的模块才进入本次读取闭包；路径、文件数与目录深度均不授予模块身份。

## 2. 项目根目录的完整语义与写法

`gift.project/1` 的必需根键为 `schema`, `projectId`, `sourceScopes`；可选键为 `targets`, `defaultTarget`, `annotations`。原 `modules`、`policyRequests`、顶层 `extensions` 不属于当前 Writer。Reader 必须拒绝未知根键及以 `null` 代替缺席的非法写法。`projectId` 只定义逻辑工程身份；物理工作区实例及其路径由当前宿主捕获，不由此字段推定。

**SourceScope**：一个元素以 `root` 定位受管区域、`kind` 区分 `semantic | native | design | asset | generated`、`editSource.mode` 区分 `file | projection | derived`，`include/exclude` 定义成员筛选。`file` 是当前可写作者来源，`projection` 必须能无歧义回写真实 owner，`derived` 无作者写权。具有交叉匹配的文件不可在没有区域裁决时双写。`root` 必须以当前工程固定根解析，并进行路径规范化、符号链接、权限和成员捕获检查；清单授予的是发现资格不是读文件授权。

**模块发现**：Reader 在冻结的 sourceScopes/include/exclude 成员内读取模块自报的 moduleId，派生只读 ModuleIndex；不维护 Project.modules。重复 ModuleId、冲突文件身份、缺失成员或不明读取范围分别诊断，不能按扫描顺序选赢家。移动文件保持 ModuleId；若新路径已在原范围内只更新 locator/读集，否则共同修改来源范围并重新核权限。目录名和 npm exports 不生成 Gift 模块身份。

**targets**：按目标键保存 `profileRef`、`outputRoots`、可选 `parameters`。每个 outputRoots 项为 `{moduleId,export?,rootId?,contextBindings?}`；export 省略选择该模块的全部合法公开出口，给出时选择单个公开出口。rootId 在当前 Target 内唯一，生成用多根必填，单根历史输入可归一为 main；允许 `[A-Za-z_][A-Za-z0-9_-]*`，最多128字符。contextBindings 只在已支持的 product:system 根按有型角色签名解释。它们从确定解析域解释，不是全球ID；product-root Control 必须以 target/rootId 定位同一 BoundRoot。真正 TargetProfile 及其参数的准确 codec 未绑定时保留 Needs，绝不能通过字符串 `"typescript"` 猜默认后端。没有目标请求时写 `"targets": {}`，不必伪造编译成功。`defaultTarget` 只指当前存在目标键。

有型 Control 的决定仍不是宿主 Grant；`annotations` 不改变业务语义。Control 属于独立可选的受控作者输入，不放到 Project `extensions`，也不为每个参数创建一份 Control。

**文件保存**：读原始字节与解析后的跨度，构造候选、核身份/范围/引用/读集、按 expected revision + Grant 写入。全文件 JSON 重排不应消灭用户并发修改；失败必须返回冲突/未知外部作用，不按最后写入获胜。

## 3. 每份 `*.module.json` 的精确外壳

当前 `/2` 模块根必需：`schema:"gift.author-module/2"`、`moduleId`、`definitions`；`namespace`、`dialects`、`imports`、`exports`、`annotations`按实际意义提供。历史 `/1` 的必填字段和 `extensions` 只属于兼容Reader。

| 属性 | 数据类型 | 逐项解释、验证、变化效果 |
|---|---|---|
| `schema` | 精确字面量 | 仅选择模块外壳，**不**选择全部 Definition 的语义 |
| `moduleId` | 非空不透明字符串 | 由模块自身声明，固定发现快照内唯一；换路径保持身份，删除重建不自动继承 |
| `namespace` | 字符串 | 可选显示/命名投影，不改变模块身份、导入与导出解析 |
| `dialects` | 别名→ `{languageId, constraint}` | `constraint` 是源发布选择符，不是 content hash。锁固定实际内容 revision，未知语言拒绝强语义使用 |
| `imports` | 别名→ `{mode,moduleId,...}` | `workspace` 读同一冻结工作区的 moduleId；`locked` 须有实际锁绑定，不能读最新 |
| `definitions` | 稳定 definitionId→`{kind,body}` | 映射键就是局部定义身份，不重复 name；kind/body 由当前 Profile 及实际方言解释 |
| `exports` | 公开符号→现有本地 Definition ID | 只导出真实本地定义；无隐式全模块公开，不通过猜私有ID绕过 |
| `annotations` | 非语义对象 | 不承载可执行扩展；当前 /2 没有顶层 extensions，未知字段须保全并诊断 |

**当前 /2 通用 Ref** 在 Schema 指定的引用位置使用 `local:DefinitionId` 或 `alias:PublicExport`。Definition/import/export 的对应 JSON 符号段允许 `[A-Za-z_][A-Za-z0-9_-]*`，例如 `local:Order-line`；冒号分隔命名域，普通字符串不自动解释为引用。跨模块依冻结 imports 与真实 exports 解析，找不到语言/导入/出口返回 Needs。当前 exports 只指本地定义。被 /2 复用的版本化 Requirement/Pattern Body 仍按各自 Schema 解释其对象式 DefinitionRef，其中 definitionId/import/export 符号允许连字符，不强制转换为通用字符串 Ref；旧模块的转导合同仅由其原版本 Reader 解释。原生符号及计算局部变量仍服从自己的词法。

**Definition 与引入发生不同**：复用同一 Definition 可以形成两个不同 occurrence；两个相同参数的有状态使用不会自动合并；相同源定义被两个模块使用不生成两份作者实体。只有相交部分失效，非相交正常保留。

<a id="gift130-source-body-routing" ></a>
### `Definition`内的真实语义与数据路由

| `kind` | `body.representation` / 数据Owner | 作者必需决定 | 编译器不得自行补齐 |
|---|---|---|---|
| `intent:goal` | `gift.intent-body/1` | 角色对象、接受的目标/禁止/规范、时间/观察适用范围；仅在该领域无合格默认时提供意义引用 | 未得的世界事实、规范主体、永久保证、真实效果 |
| `semantic:pattern` | `gift.semantic-pattern/1` | 可合法共享的抽象角色、共同断言、Variation槽与保留差异 | 取消不同领域的身份、权威和状态差异 |
| `semantic:pattern-use` | `gift.semantic-pattern-use/2` | 精确Pattern选择、`one/optional/set/bag/sequence`的相应绑定、Variation和观察选择 | 单个`objectRef`代替集合、猜来源证明、跳过强制槽 |
| `req:composite` | `gift.requirement-structure/1` | 真实参数/主体、所用复合Term、需要暴露的接口 | 空列表伪称完整业务、不明确的量词域与规范优先级 |
| 普通类型、函数、状态机、协议和新领域Definition | 所选`dialect`与锁定语义包 | 仅声明其作者独立语义及明确引用 | 把所有专业领域都变成上述4种Body；有限结构Schema不验证未列种类 |

表中前四种是**版本化意图 Body 子集**，由 `/2` 明确复用其 Body codec；不是当前统一模块的全部27种 Kind。数据类型、函数、状态、Relation、UI、存储、事件、外部Port等依其真实`Definition/dialect`或原生源文件表达，不是为它们各加一个强制项目根字段。目标语言和平台被Target Profile解释，项目文件名不决定实际代码语义。业务的抽象层级（公共/领域/意图/业务/系统）可以是同一Module的不同Definition，必要时才按组织和编辑权限分文件。

当前一个 Definition 由局部映射键、精确 kind 与其 Body 构成，显示标题可在非语义注释中保存；`module.exports`映射公开名与真实Definition。跨模块`imports.alias`先固定到一处`ModuleUse`，再经目标模块**公开export**解析；同名、路径及哈希相似均不能代替这条解析边。对`locked`导入如果缺锁，保存源与请求`NeedsLockedSupply`，不得从文件系统随意找到相似模块。跨Dialect的字段引用要求合格Type/Effect转换，不能以JSON形状一致推导兼容。

## 4. `req:composite`：开发者能够直接编辑的完整有限结构

Definition `{"kind":"req:composite","name":"...","body":{...}}` 的 `body` 必需 `parameters`（对象）和 `terms`（数组），可选 `subjects` 与 `exposes`。模块外壳有自己的 `exports`，绝不能混同 `body.exposes`：前者公开Definition，后者公开本复合定义内的逻辑主体。

- `parameters[id]`：必需 `role` (`value` 或 `subject`) 与 `type`；只有 value 可带 `default`。没有显式实参时取已锁定定义上的闭合 default；缺默认就是 Need，不能用零、null或当前环境补全。
- `subjects[id].type`：声明逻辑主体及其类型；不代表启动进程或创建数据库对象。`exposes` 只能暴露真实本级主体或 subject 参数，不能暴露子定义私有主体。
- **Type** 是恰一分支：`{"builtin":"Bool"|"Int"|"Text"}`、`{"list":Type}`、`{"ref":DefinitionRef}`。后者需要实际类型解释；本有限 Requirement 结构不能自行定义通用对象记录的完整 codec。
- **Value** 有 `{"literal":bool|int|string}`、`{"parameter":"id"}`、`{"subject":"id"}`、`{"bound":"id"}`、`{"enum":DefinitionRef}`、`{"typed":{"type":Type,"value":...}}`，及 `[Value,...]` 有序列表。参数值与主体不能同名冒认；Bool 与 Int 不自动相等；Text 不隐式做 Unicode 规范化。
- **默认**仅允许闭合 literal、确切 enum、合格 typed 和它们的有限列表；不接受 parameter/bound/subject、读取文件/时间或执行程序的结果。显式同值与继承默认在未来升级行为上不同，需保留 provenance。
- **Condition** 仅有 `value`、`equal`（正好两个同型且具有纯总相等能力）、`not`、`all`、`any`。这是固定输入的条件，不是每次调用重新计算的运行判断；运行时分支必须由实际程序/状态机提供。

### 八种 Term 的真实编码及其不能推导的额外含义

| Term | 必需原始 JSON 形状 | 精确作用、边界 |
|---|---|---|
| `use` | `{ "use": DefinitionRef, "arguments": {...} }` | 实例化准确复合定义；**不启动函数/服务**；无默认的形参必须实参 |
| `require` | `{ "require": DefinitionRef, "fields": {...} }` | 施加被正式 RuleDefinition 解释的硬要求；没有真实 Rule semantics 不能靠名字硬编译 |
| `prefer` | `{ "prefer": DefinitionRef, "fields": {...} }` | 在硬合格候选间比较，不自动降低 hard；偏好比较必须有可比事实 |
| `all` | `{ "all": [Term,...] }` | 同域合取，空列表无额外义务；不是程序顺序 |
| `any` | `{ "any": [Term,...] }` | 至少一个完整分支可行；空数组不可满足；不能每支取一部分 |
| `when` | `{ "when":{"condition":Condition,"then":[...],"else":[...]} }` | 固定输入的分支；未采用分支仍需有合法结构和类型 |
| `forEach` | `{ "forEach":{"bind":"x","in":Value,"itemType":Type?,"body":[...]}}` | 对有限集合**每个出现**施加要求，重复成员不能简单去重 |
| `exists` | `{ "exists":{"bind":"x","in":Value,"itemType":Type?,"body":[...]}}` | 有限集合中至少一个合法见证；存在搜索预算耗尽≠不存在 |

每一 Term 只能采用一种形状；`terms` 与 `all/when.then/...` 的数组顺序表示来源次序而不规定程序调度。空 `req:composite.terms` **合法但没有附加可观察行为要求**。若“重试次数=3”只是一个没有任何 Rule/Method 消费的参数，它不会神奇地让 Extension Host 真正重试三次。

## 5. 这份完整源码设计必须正视的 Rule 与产品行为边界

Gift 90 的 `req:rule / req:subject / req:value-type / req:enum-value` 已有定义角色和部分字段（例如 rule 的 strength、fields、semantics、implementation），**但尚无统一、正式发布、生产解码器能直接验证的完整 body JSON Schema**。项目清单和 Composite 的结构 Schema 不能代替它。一个完整 Rule 不只是 `{name:"Secure"}` 或一句中文需求，至少需要如下**语义合同**（这张表规定设计信息，而非冒称现有 JSON 字段已定版）：

| 语义槽 | 每个 Rule 定义必须具有的可操作信息 |
|---|---|
| `identity + revision` | 实际 Rule Definition 的稳定ID、准确字节和版本 |
| `subject schema + field schema` | 主体类型/引用角色、字段类型/单位/值域/默认是否允许 |
| `observation domain` | 哪些输入、时间、状态、事件、外部观察和环境参与判断 |
| `normal` | 合法输入上的正常返回和可见状态/效果 |
| `failure` | 非法输入、外部失败、超时、取消、未知结果 |
| `frame` | 未被该操作允许修改的状态、数据与资源 |
| `progress` | 终止、持续进展、可取消、最终可恢复的条件 |
| `realization` | 能履行该义务的方法、必要资源和目标资格；没有 Method 不自动生成代码 |
| `evidence` | 静态论证、构建检查、行为试验、真实运行证据各验证什么 |
| `compatibility` | 后续修订相对旧定义可保持和不能保持的观察 |

**规范化方案**：先在独立的、有准确 `languageId` 和 `constraint` 的 Requirement-dialect 定义中发布 `req:rule` body 的完整 typed codec，并有对应的 Rule 语义解释器；随后结构项目在 `dialects` 中选择它并由真实锁固定字节。不要通过修改现行 `/1` 的未声明字段来偷偷获得功能，也不要用字符串型 `test` 命令充当通用证明。若不发布此合同，完整 Rule 只能保留为 Needs，不能声称专业工程全部生成或等价。这里不凭空创建一个第二套无法对接的 JSON 规则语言。

同样，原生 TypeScript 方法可能真的满足某个用户要求，但它不会因为 `design/requirements.module.json` 中也出现“编辑器”三个字就自动建立已证明的 Requirement→Method 关联。需要真实 Type/Effect、准确符号映射、范围、Method coverage、目标 ABI 和独立证据；不能以同名 JSON 键或注释替代。

## 6. 原生作者源码的文件级维护

在混合工程中：

- `src/editor/document.ts` 的 `replaceRange` 是**唯一**的算法源码：UTF-16 offset、修订整数、失败返回和状态更新由 TS 文件拥有。Gift JSON 不再写第二套可修改的函数 AST。
- `src/editor/history.ts` 的历史列表、undo/redo 和截断策略是原生行为；`historyLimit` 的 Requirement 参数只有被公开接口准确绑定时才真正约束它。
- `src/extensions/host.ts` 使用区分联合表示状态迁移；它不是产生子进程的 Provider，`starting→running` 需要宿主外部效果另外实现。
- `src/remote/session.ts` 管理远程连接的**纯状态模型**，不自动拥有网络或重连事件投递。
- `src/platform/files.ts` 仅公开 `FilePort` 能力接口，实际文件读取、写入、授权与失败恢复需要宿主实现。
- `package.json`、`tsconfig.json` 不因导入 Gift 而被复制到控制模块；本机依赖锁仍由对应工具维护。`assets/theme.json` 是应用消费的数据，不是 Gift 的 Rule Definition。

Native SourceProfile 不是“扫描成功就理解全部语言”。Gift 对未知宏、动态加载、环境专有行为、反射和资源句柄要依据真实原生适配器声明覆盖边界。对当前无法理解的片段，保留原字节并返回范围内不可验证，而不是无声删掉或按黑盒等价宣称全支持。

### Rust 源码独立拥有的另一种真实文本语义

`03-native-rust/src/lib.rs` 的文本区间采用**UTF-8 字节偏移且验证 char boundary**；`02-native-mixed/src/editor/document.ts` 示例采用 JavaScript 的 UTF-16 code-unit offset。即便它们都有 `replace_range` 一类操作，也不能仅凭同名宣称 Unicode 下行为完全等价。若一个 Target 要取代另一个，必须明示 offset/错误/溢出观察转换规则并取得独立验证。Rust `Cargo.toml` 自己拥有 package/edition/dependencies；结构 `req:composite` 不会覆盖 Cargo 包管理器。

<a id="gift130-root-target-and-lock" ></a>
### 作者清单、目标选择与锁：真实文件数据的消费顺序

读取 `gift.project.json` 后，仅对清单明确的SourceScope逐项读取作者源，并对实际模块及外部绑定建立准确`ModuleUse`。在**固定SourceSnapshot与解析域**下处理`dialects`、导入、definitions、exports；然后解析`targets[name].profileRef`和`outputRoots`。省略`export`选当前准确公开导出集合，而不是自动推导`main`，单导出重绑时必须重新核作者要求和控制适用性。

有型 Control 中的 `require/prefer`是用户**请求/约束**，它们不能自行取得文件写权、网络权限和外部执行Grant。作者对实现方向可在已发布的ControlDescriptor里锁死或偏好，但强选没有资格的Method、目标或Provider时必须失败，不能悄悄降级。锁只保存真实解析出的内容地址、修订、依赖和发生位置；`gift.lock.json`不存在时返回Needs，不准自动写一个全0 Digest作为“完整工程范本”。

对于Target为`typescript-service`的实例：它声明了多个正式输出根，但所引的`example.target.typescript-service/1`不是随包发布的生产Profile；不应由此推断将生成数据库、HTTP API或完整TS文件。只有合格的Target/Profile以及所有硬根的Method等条件均满足，编译器才能实例化完整ArtifactSet。纯设计查询可以返回已解析源/未决需求，不应强制先选某个编译Target。

## 7. `gift.lock.json`、Control、Target、生成目录的精确出现时机

**Lock**：`gift.binding-lock/1` 必需 `schema/projectId/resolutionInputs/bindings/nodes`。每个已解析 node 要有 `kind/subjectId/revision/content/dependencies`。`content` 包括实际摘要算法、值、长度、编码/格式等；同名库可以在两个不同导入使用域选中不同节点，不允许单个全局 map 吞掉。只有成功取得语言和库字节并确认完整绑定后才写锁；锁里的 `latest`、伪哈希和“本次取最合适版本”都不合格。

**Controls**：实现固定与普通业务 Meaning 不同。当前只写独立 `gift.control-file/1`，由 Project.sourceScopes 发现，带准确 scopeRef 和目标限定；product-root 必须以 target/rootId 区分根发生点。只有真正人工 Pin/Require/Prefer 的实现决定才创建相交记录；默认/委派是本层无显式覆盖而不是持久写入 `auto=true`。不能把 runtime Grant、密钥或当前部署状态放进去。

**Target**： `targets` 项必须有真实 TargetProfile 引用和实际 `outputRoots`。TargetProjectPlan 是按被采纳作者内容、目标要求、方法供给形成的派生**工程蓝图**；ArtifactSet 是另一阶段产生的真实字节；执行和安装另有 Operation/Evidence。目标画像不存在时 `profileRef` 不是手填魔法字符串。设计-only 项目完全无需 `generated/`、`build/` 或假的 TS 编译记录。

**资源和发行**：只有已发行的 Type、Module、Method、Provider、Target 能够在固定绑定之后声明供给。路径可能包含 README、CSS、SQL、迁移、原生部署配置和 assets；编译器必须收齐实际目标需要的资源集合，不是只有一个 `main.ts` 就宣称“完整专业软件”。

## 8. 命名、路径、字节、编辑、迁移的工程级规则

1. JSON 必须是 UTF-8 严格解码，禁止重复对象键、非法代理字符、非法数值、非标准常量；`true` 不得当整数1，未知根字段与未知 dialect 需按归属拒绝语义消费并保全。
2. 文件路径从冻结 ProjectRoot 解析，禁止目录穿越、符号链接越权、利用不规范路径别名跨 SourceScope；可合法不读取的文件不自动获得访问资格。
3. 路径、显示名、对象键顺序都不等于语义身份；模块/定义/锁节点保持各自作用域内身份，修改 Revision 与其身份区分。
4. 内容摘要只证明相应字节域相等，不是签名、执行许可或业务正确性；来源与精确读取上下文仍须保留。
5. 读取先固定 SourceProfile、模块成员集合和解释绑定；抽取签名→解析 import/exports→类型与默认→有限条款实例化→共同约束→实现供给→Target；缺失部分生成 Needs，不替换为字符串或空内容。
6. 本地编辑、AI、SDK 都形成同一类精确候选。`propose` 不落盘，`apply` 要核前像与权限；两个作者同时编辑同一 JSON key 不能 last-write-wins；跨文件共同不变量必须联合校验并有可恢复的提交协议。
7. 源表示迁移要冻结旧源、构造新候选、比较可判定语义、逐项处理不可保留信息、原子切换唯一写权并保留恢复映射；不能靠改名 `.json → .gift` 把所有内容自动转写。
8. 来源、Binding、Target、Artifact、Operation、Evidence 分别追踪真实适用性；一个失败不能抹除不相交完成结果；一个成功不能签发其他阶段的资格。
9. 所有声明支持某文件的生产端必须发布支持矩阵：哪些 schema/dialect/kind/Term/Type/SourceProfile 可解析、可编辑、可生成及其版本和残余；结构化前端通过不等于独立验证 Rule 语义。
10. 不为求文件少而把整个 IDE 的上百个定义都写进一份巨型 JSON；也不因为模块划分就复制一份同义 Root、Type、Method 或 UI 数据。按稳定复用和独立修改责任拆分。

## 9. 可落实的机器处理状态与结果

| 输入与实际条件 | 可继续做的事 | 必须拒绝的误判 |
|---|---|---|
| JSON 结构完全合法但 dialect 版本字节未取得 | 保全并定位、列出缺少哪个发布内容 | 作为已检查、可编译或可信构建源 |
| 有 `req:composite`、`use` 等但缺 Rule 语义/Method | 处理已知合取结构和参数，形成 Needs | 声称这些名称让软件已经满足重试、审计或安全要求 |
| 定义可解释但未声明 TargetProfile | 交付已明确覆盖的设计/蓝图 | 声称源码、配置或可执行产物存在 |
| 原生函数已存在但没有合格 Source→Requirement 映射 | 保留原生代码、允许独立原生检查 | 仅凭函数名相同授予跨语言等价保证 |
| 用户选择某个 Target 却无实现供给 | 给出准确 Method、ABI、资源及能力缺额 | 生成 TODO 占位然后标为完整 |
| 运行/写入中断、权限撤销、并发修改 | 用 Operation/Attempt、前像、回读证据处理恢复 | 盲目重试、旧缓存代替当前事实、撤权后继续外部作用 |
| 用户只保存作者工程设计 | 保留准确工程事实和变更历史 | 显示编译/检查/发布全部通过 |

### 同一个开发者工程从初次定义到多次维护的完整合法操作

| 开发者意图或动作 | 必须写/更新的作者内容 | 合法的派生结果与失败后继 |
|---|---|---|
| 定义领域Resource/Request或导入领域库 | 由相应Type/Meaning SourceOwner保存Definition/引用；工程模块导入写入`imports` | 无真实库时标记`NEEDS_MEANING`，不发明同名对象的语义 |
| 编写“容量不超额、请求被决定” | `intent:goal`中`roles/clauses/meaningImports` | 派生区分`maintain/achieve`的义务，范围之外不签保证 |
| 抽象跨业务通用模式 | `semantic:pattern`固定公共角色和Variation | 保留差异约束；没有不可归约共性时拒绝伪抽象 |
| 在本业务复用模式 | `semantic:pattern-use/2`绑定角色和差异 | 先核Multiplicity与Variant资格；没有锁和Observer时返回Needs |
| 组合产品和多个目标 | `req:composite`、`targets.outputRoots`、合格的Control | 联合硬约束、规范、时间和共享资源，不能两两可行替代全局可行 |
| 保留自写复杂算法 | 原生 `src/*.ts/.rs` 与必要的真实绑定选择 | 调用原生工具取类型/ABI/效果事实；同名native symbol不等于Method资格 |
| 预览方案 | `propose`返回Candidate与来源Diff；`check`对指定范围签结果 | 不改磁盘、不运行Provider；报告未决及被拒方案 |
| 保存作者修订 | `apply`核当前Revision、作用域、实际Grant并提交新作者字节 | CAS冲突不覆盖别人修改；旧锁与资格按依赖失效 |
| 编译完整应用 | 指定Target、实际锁与完整已合格Method供给 | 合格Target AST、依赖、构建、制品与SourceMap；缺根或未降低操作不得发空壳 |
| 二次修改或更换Target | 只改真实owner所管的作者内容或Target选择 | 精确重新绑定、影响计算、增量/全量对照、受管输出保持和必要迁移 |
| 运行/部署/真实操作 | 仅显式执行请求和独立授权，并有稳定Operation身份 | 超时记`UNKNOWN`，读回/对账/补偿；编译不自动执行 |
| 核验、撤销或升级 | Evidence/Claim及真实观察Owner独立记录 | 精确失效、重新取证；旧运行历史不被新源重新解释 |

**开发者需要决定什么**不是由固定20个字段兜底，而由当前领域的真正不可推导差异决定。可接受目标、不得让渡约束、有权政策、角色/现实对象、必要的质量取舍与实现固定选择属于作者；可合格推导的局部算法、适配、Target布局可由实现供给和编译器选择。一个要求仍有未定义的事实/政策/期限/权威时，系统应明确指出“还缺哪一种合法作者决定或外部资格”，不要求开发者把内核IR手写进去。

## 11. 一次真实改动：从源文件到影响

**变更 A：移动文件而不更换模块**。把 `01-structured-design/design/editor.module.json` 改放 `modules/editor.module.json`，先检查新路径是否已被现有 sourceScopes 包含；只有需要时共同修改 sourceScopes，重新核相关读取/编辑权限并派生新的 ModuleIndex，不创建 modules 路径表；`moduleId` 不变，产品的 `editor:EditorSubsystem` 引用 不应因路径变化自动创建新 Definition 身份。若新路径不在语义 SourceScope 中，保存候选应拒绝或联合修改范围，不允许工作时按文件系统猜位置。

**变更 B：值和来源不同**。`EditorSubsystem.parameters.historyLimit.default.literal` 从 256 改为 512，会影响**没有显式传入该参数的实际使用点**。但是 `Studio` 中的 `use EditorSubsystem` 已显式 `historyLimit=512`，故那个使用点当前有效值不应因为默认改变而变化；默认规则的 revision、回溯与以后移除显式参数的潜在行为仍不同，不能把两个来源合并。

**变更 C：真实 TypeScript 函数修改**。把 `02-native-mixed/src/extensions/host.ts` 的 `running` 状态从 PID 数字改成一个结构体，首先修改原生源码 owner 并由 TypeScript 工具链核合法消费者；独立 JSON `requirements.module.json` 不因显示名相似被复制/覆盖。只有真正存在的跨源 Method/Requirement 映射取得相交依据时，才能进一步声称特定要求得到保持或失效。

**变更 D：选择 TypeScript 目标**。在项目清单中创建 `targets.web.profileRef` 与 `outputRoots` 的候选时，必须先解析真实 TargetProfile、实际代码根的公开身份、Method/ABI/构建与资源供给；若只有本范本这些 Composite，它们并不实现 UI/OS/插件协议。此时结果为 `Needs`，而不是把目录名变成可运行 IDE。

**变更 E：目标完成再修改**。未来任何一版真实 Target 生成源码后，先保留 ArtifactSet 的来源映射；用户直接改生成文件时要区分派生编辑与新作者权切换，不能让两端再次各自为真源。后续二次修改仍从被接受的作者源或受约束的原生 owner 改起，重核受影响 Binding、目标成员和证据。

## 12. 实际交给实现者的最小开发合同

第一个真实产品读取器无需先实现全世界所有语言，但至少必须：

1. 严格项目 JSON Reader（重复键、UTF-8、字段、路径、SourceProfile成员、前像）；
2. `gift.author-module/2` Reader的设计责任（导入、导出、稳定身份、未知Dialect拒绝和原字节保留；旧 `/1` 仅隔离兼容）；
3. `gift.requirement-structure` **有限** Composite/Term/Type/Value/Condition Reader 及固定解析上下文、参数默认与引用解析；
4. 原生 SourceProfile 精确所有权与适配器分工，不以 JSON AST 镜像替代源文件；
5. 锁产生者与检查者按真实发布字节工作；无发布物时明确 `UNRESOLVED_LANGUAGE_BINDING`；
6. 有资格的 Requirement Rule/标准 Type/Method/TargetProvider 后再声称完整生成；
7. 可追踪诊断包含 `file + pointer/span + code + expected + actual + dependency/use basis`；
8. 候选→检查→应用与外部 Operation 明确分离，具备 CAS/权限与跨文件恢复；
9. 针对正式支持子集的成功/失败/迁移双向测试，独立验证“不能默默降级”；
10. 支持矩阵与实际发布物对应，不能把本离线静态校验器冒充生产级 Gift 工具。

**精确未闭合接口**：Rule 生产级 body JSON Codec 与其 observation/predicate 映射、TargetProfile 的实际符号/参数协议、原生 Method 供给注册及 Source→Requirement 稳定链接、标准 Type/Value Codec、长期多文件 CAS 与 Workbench 真实读取器。这些不因本范本把每个文件写满就自动获得实现资格。它们需要由前述原 owner 的后续机器规范与真实实现取得证据；用户的要求是完整工程可用，不能用一份静态示例替代这些能力。

## 跨文件实际正文：一条强要求、一个原生函数和一个 TypeScript 目标

补充可逐字打开的工程样本在 `fixtures/contract-closure/Gift96/example/author/`（演示用候选接口，不替换本章既定完整多工程范本）。其中 `gift.project.json` 持有 `projectId`、semantic/native SourceScope、模块路径、`targets.ts.profileRef` 和两个确切扩展登记；`design/rules.module.json` 唯一拥有 `RevisionMonotonic` 的 Rule body；`design/product.module.json` 通过 workspace import 和 `require` 出现点固定 `minimumDelta=1`；`design/native.binding.json` 只选择原生的 `replaceText` 与 `revisionIncreases`；`src/document.ts` 唯一保存真实函数实现；独立供应方的 `supply/method.json` 和 `supply/target.json` 并非产品作者源。

项目控制记录的完整含义是 `scopeRef={kind:"project"}, target:"ts", controlRef:"example.typescript.module-format", mode:"require", value:"esm"`。Target 对应的 `representation.moduleMode` 必须满足此硬要求；另一个 `req:rule` 的观察 Profile 必须逐字出现在 Target `accepts` 中。代码中 `replaceText(before,nextText)` 的正常返回是新 `Document`，`revisionIncreases(before,after,minimumDelta)` 是另一条被观察谓词；它们的类型匹配不证明所有路径/失败/帧/进展都满足规则。`--emit` 只隔离装配一个保留原生算法字节的 TS 示例，不生成伪 `gift.lock.json`，不把方法的 `residuals` 清成空数组。

开发者需要直接编辑时按以上真实作者文件编辑；需要知道“为什么这样选择”时读取有准确来源的 Control/Binding/Need；需要实际软件时必须另外完成真实 Target lowering、运行和证据链。完整规范内容仍由本章和相交单一 Owner 持有，演示不能成为新的可复写规范副本。
