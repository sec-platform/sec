# 工程清单模块与绑定锁协议


### 唯一写源和文件分工

一个工程通常包含 `gift.project.json`、`design/*.module.json`、可选的 `src/**/*.ts`/`*.rs` 原生实现、以及图片/数据库迁移等资产。开发者不另写意图副本、编译IR、`TargetArtifact`或检查结果。模块职责按业务含义分文件（如 `model`、`rules`、`interaction`、`system`），而不是人为要求每个抽象层建一份相互重复的文件。

| 文件 | 作者亲自决定 | 编译器/工具派生 | 不允许承载 |
|---|---|---|---|
| `gift.project.json` | 工程ID、来源扫描及写权范围、目标选择及根 | 锁定依赖与选择的规范绑定、解析环境 | 再写一套业务Goal、Method能力或产物源码 |
| `*.module.json` | 定义及其有类型Body、导入导出、组件和业务关系 | 实际使用点、类型化义务、Linker图、诊断和SourceMap | 目标临时代码、Provider执行结果、证明缓存 |
| `src/**` 原生源 | 作者保留的真实算法、实现、手工区域 | ABI投影、可签发的Method候选、受控目标调用边 | 假装自己就是已获资格的高层业务意义 |
| `assets/**` | 有权的图片、模型、种子数据、协议等资产 | 内容锁、路径映射、必要构建转换 | 暗藏影响业务语义的任意未声明脚本 |
| 机器锁（工具维护） | 作者可明确升级/Pin策略 | 实际解析的ID、Revision、Digest、供应位置 | 凭锁文件无中生有领域意义/真实Grant |

只需一次每文件格式声明，例如 `"schema": "gift.author-module/2"`。斜杠版本在这里是解析身份，不是业务语义，也不要求每个Definition、接口和字段携带它。`GiftNN` 一类名称只是设计交付包编号，不进入程序协议或工程文件。一般开发者可以由IDE创建文件模板而无需反复阅读格式标识。


### 集合、JSON体量和可编辑性

保留JSON作为结构化写源。长文件通过业务域分模块、以`imports`复用、局部引用和Component模板与实例分离、可读的IDE结构视图、折叠与增量编辑解决。不要用生成一个更长的JSON影子格式优化原JSON；不要把展示Markdown当成第二作者语言。大数组只有在确有顺序语义时使用；按身份访问的定义或绑定优先Map；bag/set/sequence绝不可相互静默转换。每个集合必须说明成员类型、唯一键、作用域、基数、顺序、参与者、拥有者与改动效果，见 [有类型集合归属](../../../70-工程系统与演进/实现与装配/能力接合与文件责任.md)。


### 严格写法与历史Reader

一个未发布Writer只有一套合法字段：旧`wires`、`publicInterfaces`、`behaviorRefScope`、裸`workflowRefs`、组件`arguments`、旧`stateRefs/resourceRefs`等必须由显式旧Reader读入、明确迁移或拒绝，不能新旧并存而要求一个随时维护的“设计检查器”来区分。新作者Schema在本包的设计形状中已经删除明确退役字段。旧Source如果含不可迁移语义，保留原始字节和迁移报告，不假装自动完成；不要求新业务工程永远携带旧版文件。


### 模块导入、公开导出和多文件名义身份

**无条件标准域不是一般依赖。** 当前作者语言把确定性、无外部效果的最小运算签名保留在内建 `std` 域，`Expr(symbol).ref` 如 `std:IntAdd` 按固定语言规范解释。用户不得通过 `imports.std` 重绑它，也无需为最基本的整数运算编写 import 与锁条目。除这一明定基底外，领域库、算法库、目标原生包均须正常导入、锁定、版本及实现资格；不能把 `std` 推广成任何按名字猜到的功能。其他本地引用保持 `local:Definition`，不能因文件路径相同而绕过模块名义身份。

**工程发现与名义身份的闭合规则。** `sourceScopes` 是具有编辑权边界的*候选文件发现规则*，不是另一张模块身份表。每个被发现的当前作者模块应当恰有一个独立 `moduleId`；如果两份有效文件声称相同 `moduleId`，即使字节相同也不得以路径字典序任选一个，更不能把两文件 Definition 合并。大小写折叠、Unicode 规范化、软链接跳出授权根、重复 JSON 键、已排除目录被另一个 Scope 重新纳入等必须分别按路径访问和源身份处理。`include/exclude` 只对发现域生效，不赋予读取更高权限；编译实际读取的内容须冻结到同一修订视图。

一个局部 Definition 的名义身份为 `(moduleId, definitionKey)`；被引用的发生点还须携带 `moduleUse`、`importAlias`、`useScope` 和本次实例/根。公开别名是可见性边，不是定义本体，`exports` 指向同一个本地定义不会建立第二份业务实体。导入重复指向同一模块时允许共用冻结解析结果，但使用发生点仍独立；导入供应变化须使实际相交的绑定失效。显示标题、项目目录和 JSON 对象在文件中的顺序不能充当跨修订稳定身份。

**按需字段的最小含义。** `definitions` 映射键给出局部名称；`namespace/imports/exports/dialects` 无消费需要时不出现。没有实际角色的 `DefinitionUse` 只写 `ref`，未填写 `bindings` 等价于空实参映射；目标定义存在必需角色则是缺实参而不是自动补齐。静态组件参数中只有 `mode=value` 能采用有类型字面值，不允许把引用、业务对象或外部资源值强制转成一段字符串。Project 的 Target 参数需要真实 Profile 解释，不能成为绕开这些强类型边界的万能 `Json` 背包。


导入别名在当前模块作用域唯一；`local:Id` 只引用本模块定义，`alias:ExportName` 必须先绑定精确模块及其公开出口。引用同名不能自动合并不同签发者、模块或根发生点；循环导入若只涉及类型声明可由合格的声明前置规则接受，循环初始化及带效果的模块加载必须明确排序或拒绝。`exports` 是公开稳定接口：内部命名/位置可以更换，但修改公开名义类型、角色、效果、错误或版本承诺属于真实兼容变更。依赖锁应记录真正被选择的包与内容，不让可变版本范围在单次编译的不同读取时刻取得不同意义。

定义 ID、显示名、文件路径和源码 span 不能复用为同一种身份；一个定义在多处使用时，每次 Use 都有独立的发生位置、上下文绑定和修订。映射内定义的 key 已是唯一 ID，默认不再次要求与其相等的 `name`，但语言仍可容纳对开发者有独立价值的展示标题，且此展示标题不能改变 Linker 身份。


### 同一语义的组合位置，而非一条万能列表

模块 `imports` 做显式命名绑定，`exports` 定义可见边界。每个 `DefinitionUse` 只说明一次**具体、带角色绑定的使用**；ComponentInstance 的 `argumentBindings` 是静态模板实参，`contextBindings` 是业务对象实参。`workflowUses` 声明局部流程使用，不表示已启动；`activationRoutes` 把 UI、API、事件、状态或定时的**一次来源**绑定到 WorkflowUse 并投射有型输入。`OperationUse` 精确指定 `portRef + operation + inputs`；没有授予真实执行权。多根同模板不会自动共享运行态。

按专业意义，Data 的 read/write、Event 的 publish/subscribe、Protocol 的 client/server、Resource 的 own/provide/consume、UI 的 render/control、State 的 host/observe、Observation 的 produce/consume/audit、Norm 的 apply/override、Quality 的 hard/soft 必须保持不同字段和消费合同。它们共同使用有类型身份/绑定结构，不意味着需要 `members:any[]`。

**单根与多根唯一选择写法**：原 `gift.project/1.targets[targetName].outputRoots` 数组不变。生成用的多产品根必须在每个元素写 `rootId`（仅该Target内唯一），允许两个不同rootId选择同一个公开 `product:system` 定义并传入不同上下文；单根历史输入可省略并规范化为`main`。新RootId与已生成根的绑定必须经SourceRevision和原选择发生点校验，不能靠数组序号、Definition ID或Context字符串作跨修订身份。缺少所有生成根是待补作者输入，不妨碍保存尚未完成的项目草案。

每个根独立拥有`components[].instance`、成员`useId`、局部事件与部署实例的作用域。不同根的同名`EditorA`不是一个可变运行实例；跨根共用Port/Authority/Resource不能用裸实例名或同一Definition推断。外部共同实体必须经有权Issuer和Scope确认，未确认的同词对象只能是Alias候选。根更名、删除、合并和重排必须按稳定根身份判断真实受影响的接受义务、运行驻留、Artifact与迁移，不因Root名字合法而获得跨根Grant。

`UiNode.actionRef`仅引用`domain:meaning`的`operation`/`event`（用户业务动作的意义）。底层`effect:port`只可由合格Workflow/Method与Execution调用；以FilePort直接填ActionRef的旧范本仍作为**历史证据**保存，但不是本轮新Writer的正确做法。一个按钮唯一的源→Workflow因果关系由`activationRoutes`表达；同一来源到同一Workflow的重复路由应拒绝，不同工作流的合法fanout需独立仲裁/授权，不能简单额外启动。


**当前可写源唯一位置**：组件静态参数仍存`product:system.components[].argumentBindings`，其`mode=value`采用有`source=literal/typeRef/value`的有类型字面值，非value模式维持Kind对应的引用；组件真实业务对象仍存独立的`contextBindings`。组件成员触发关系只存`product:component.body.activationRoutes[]`，源与目标以同一定义内部的显式`DefinitionUse.useId`定位，原因采用五种封闭分支，不新建触发器注册表或字符串DSL。合法形状来自原Schema，实际语义和执行资格来自[作者语义](../../../20-语义与组合/作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#explicit-component-activation-closure)；锁仅保证已声明模块/供应的解析，不代表有权发事件或执行效果。

## 当前唯一作者写源合同（设计目标，而非已经发布）

**采用方案**：新业务工程只有一个结构化作者模块写入目标 `gift.author-module/2`；`gift.project/1` 选择模块、目标和根，Definition的`kind/body`由对应的现行语义Owner解释。模块 `/2` 的标准候选 Kind 在同一Schema内为 **27种形状**：原候选23种加回4种意图/Pattern/Requirement。其中 `core:constant`、`core:function`、`data:query` 分别承载计算值、函数和查询定义，并同其他业务 Definition 共用模块、引用和类型；这三个 Kind 的 Body 与普通业务类型化成员有不同的专业解释，不能以“非计算阶段暂缓”作为最终表达范围。相关计算消费者与目标降低尚未取得生产资格。这些数目是 Schema 判别值，不是24个不可约语义公理或强制输入项。

`gift.author-module/1`继续按原版本**只读**识别旧来源；它的定义体保持原`intent-body/1`、`semantic-pattern/1`、`semantic-pattern-use/2`、`requirement-structure/1`协议。读取旧文件不得静默转写成 `/2`，尤其旧定义键可含冒号、可缺少`exports`、允许顶层`extensions`；新 `/2` 具有不同的命名和严格导出规则。旧源迁移要先验证旧数据，再形成带来源与身份映射的**待采纳新稿**，核对全部角色、目标、语义及公开引用后方可写入；没有足够信息时报告`NEEDS_AUTHOR_MIGRATION_DECISION`，不能擅自重置稳定身份。历史 `/1` 阅读器不是第二套当前作者写入设计。

只选一个完整产品根时，`product:system` 中的 `components`（**组件实例**）、`requirements`（有权接受的系统级义务）、`workflowUses/policyUses/qualityUses`（各自的类型化发生点）、`publicEndpoints`（实例绑定的公开提供端口）、`externalRequirements`（显式外部需供）、`connections`（内部供需端口）、`deploymentRef`（部署定义）分别负责不同事情；组件内亦由特定的有类型参与关系承载业务成员。**不允许**新设`members[]`、`dependsOn[]`万能汇总，也不以文件同处推断归属。完整字段和分工见[唯一非计算语义Owner](../../../20-语义与组合/作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#gift140-typed-product-closure)。旧`workflowRefs/policyRefs/qualityRefs/publicInterfaces/stateRefs/resourceRefs/wires`仍可按旧快照结构只读，但当前Writer全部拒绝；`product:system.behaviorRefScope=include-all-qualified`也不可使全部工作区文件自动成为产品成员。允许多个独立产品根，不能用别的根掩盖任意单根的义务遗漏。缺真实接受记录、领域解释或专业供应必须分别保留Needs，而非靠Ref计数宣称完整。

对于旧候选字段，如`wires`与`connections`、`guard/conditionRef/conditionUse`、`capacity/capacityLiteral`：**当前作者Writer只允许更具体、具有明确类型和证据语义的那一种**；旧表示仅作为有版本的历史输入处理。不能把不同输入表示同时写进一个现行定义并允许其分别生效。解释相等不能只靠结构相似：须有保留身份、范围、四态证据、优先关系及失败路径的显式规范化证明；缺证据时拒绝迁移，而不是机械替字段。

上述只有设计与Schema级约束，没有已实现的统一生产Reader、领域Meaning解释器、联合Requirement求解器或真实Target；不可凭一个统一模块Schema宣称R01–R12产品已完成。

**非计算写源路由（`gift.author-module/2`设计提案；旧Gift135作为历史来源）**：`gift.project.json`仅选择范围、模块、目标和根；`design/*.module.json`现在**也包含**六模态Goal、八Term、Pattern/PatternUse及领域、状态、协议、UI、质量、权限、资源和产品定义；旧`/1`仅为历史读取资料。合法的原生TS/Rust资产仅在确有专业实现时存在。作者不另存计算IR、解析锁或生成源码。本提案为容量、阈值、业务条件和组件参数提供不依赖通用Expr的候选字段；它们的精确解释与拒绝由[通用定义Profile的非计算作者合同](../../../20-语义与组合/作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#gift135-noncomputational-author-closure)唯一规定。`/2`未发布前不得静默将这些字段输入`/1`Reader，缺实际Dialect/Target返回Needs而非构建成功。

## 非计算开发者实际工程文件边界

**当前唯一作者协议设计**：`gift.project/1` 声明工程、SourceScopes 与 Target/outputRoots；模块由 SourceScopes 发现，选定 `/2` 产品根可带实际 contextBindings；`gift.author-module/2`统一保留27种Definition形状（非计算业务与计算/查询共同组成统一语法候选），旧 `/1` 四种意图类仅只读。普通业务作者不再需要并行的旧意图模块。本次只修订算法、函数、查询和其他能力的设计文稿，不实施执行器、求解器或目标编译器。锁只能由有权Resolver从真实依赖导出，作者不能手写假锁。

**最小必需源码**：一个真实`gift.project.json`、被本次目标实际选择并用到的模块，以及必要的作者资产、稀疏Control、真正原生源码。Goal和Product根可位于不同Module，Target Root必须明确选择并共同解释；空复合需求不替代已接受的硬义务。`extension:definition`没有已经绑定的Dialect Body、意义与消费资格时只保留未决，不被模板当作任意行业万能入口。写源语义与完整覆盖见[非计算作者合同](../../../20-语义与组合/作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#gift134-noncomputational-author-contract)。

### 当前输出根的可绑定发生点（同一 `gift.project/1`）

目标中 `outputRoots[]` 的完整形状是 `{moduleId,export?,rootId?,contextBindings?}`，其中 moduleId/export 选择公开定义，rootId 标识本 Target 内独立根发生点；当选择的公开定义确为候选 `/2` `product:system` 时，新增可选 `contextBindings`，值与作者模块的 `BusinessRoleActual` 精确同型，专门绑定被选根的 `body.contextRoles`。**该字段在Project Schema中是有类型跨引用，不是任意扩展键、全局环境默认值或新的project版本**。其引用别名按**选中产品根所属模块的导入表**解释，不允许用Project文件所在目录猜Module。跨Profile目标或不支持上下文的Root不得自动解释这个字段；实际生产Reader必须能证明其所读Profile并拥有明确消费资格。

系统成员必须由 `components[].instance` 局部命名及有类型绑定产生；`target.outputRoots`中两个选择相同模板却不同上下文的根分别生成两组独立Occurrence。`components[].contextBindings` 绑定模板 `contextRoles`；组件局部`DefinitionUse`按组件上下文实际化，根级`DefinitionUse`按根上下文实际化。Producer/Consumer连接与部署节点都使用产品实例身份。旧 `deployment.nodes[].componentRef`、裸`publicInterfaces`或工作区扫描都是**历史读取/未采纳提案**，不能写入当前Writer。名义类型不符静态拒绝，Issuer、scope、权限、Method与Target未证明保持Needs；精确关系见[语义Owner](../../../20-语义与组合/作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#gift140-typed-product-closure)。

## 已选择根的完整消费与单一需求闭包（Gift131，`gift.project/1` 不变）

**唯一输入**：按实际权限取得的 `(projectInstance, SourceRevision, targetKey, fixed selected import/Meaning/Target supply, environment selection, author acceptance record)`。作者 `targets[targetKey].outputRoots` 是这次**目标请求内被明确选择的公开根集合**；一个根可为 Goal、PatternUse、Requirement 或有目标Profile支持的程序导出，根的类型和解释器不能由文件名、导出名字或输出目录猜测。模块中存在但未被根选中且未被根的有效引用传递依赖的 Definition，不自动进入这次目标的接受条件。作者接受的独立要求可能由其它固定来源贡献；必须有准确的并入关系，不能从“工作区文件很多”推断都已选择。

**预处理顺序**：

1. 冻结 `project` 本体、真实 SourceScopes、已声明 ModuleUse、导入发生位置、内容Revision及当前Target选择；权限、符号链接、大小写/Unicode碰撞、重复JSON键、真实路径边界在 Reader 检查，不把字符串路径当访问许可。
2. 对每个 `OutputRootRef`：有 `export` 时只选择该公开边；缺 `export` 时在此快照选择模块**全部当前公开出口**，建立集合依赖，未来新增或删除公开出口触发重新选择。任何外部已锁定根须在当前解析域中实际唯一且可读。模糊或尚未锁定返回 Need，不按目录顺序选第一个。
3. 解析 `(moduleUse, publicExport, definitionId, occurrence)`，保留**选择器与其绑定定义两种身份**。相同导出名后来重绑新的Definition，不能沿用旧证明；同一逻辑Definition经多条选择器被选中，静态根可去重但保留每条作者选择的来源发生位置。Requirement `use` 的发生位置、实例化参数与主体仍各自独立，不能因引用同一Definition而去掉重复业务实例。
4. 沿**已经类型化的语义引用**遍历本地/公开导入，构成 `SelectedDefinitionClosure`；静态文件链接、说明性提及、同名URI不是语义依赖。抽象Pattern的必要差异、Goal的Meaning与时域、Req的Term解释，仍须各自消费者验证。声明环按已发布签名规则处理；执行/初始化/生成环无合格合同则返回 Need 或冲突。
5. 调用TargetProfile的实际根分类/聚合合同，将所有被作者选中并已解释的 Goal、PatternUse、Requirement 及原生实现根组成**一次共同的联合要求**。这里的“联合”不是把全部根转换成同一种Boolean，也不是要求每个根生成一份应用入口；硬义务合取、真实`any/exists`候选、Norm/进展、软偏好各保持原语义。TargetProfile没有声明如何消费某种根时必须返回 `NeedsTargetRootInterpreter`，不能把它当注释忽略。
6. 输出内部 `SelectedRootSet`、`BoundRoot`、语义引用图、选定发生位置、未解释Needs、正/负ReadSet和作用域；然后由原 [Requirement Owner](../../../20-语义与组合/组合/跨软件需求合同.md#gift131-root-aggregation) 联合，Method/Target按原Owner取得进一步资格。这些是**从唯一作者源派生的只读内存值**，不是新增持久 `roots.json` 或正式wire消息。

**完整性与适用范围**：合法根选择的充分性只能相对于有权主体实际接受的根集合及已锁定的独立要求证明；编译器没有办法从所有未选定义中“猜出用户心里认为必须包含的目标”。必须在 preview 显示`selectedRoots / meaningNeeds / unselectedPotentialDefinitions / effectiveHardObligations`的准确受限视图供作者检查。没有解释器时`effectiveHardObligations`不得假报数量或内容。空 `req:composite.terms` 可以合法代表不施加附加业务义务，但**绝不能作为任意安全目标已覆盖或已完成的证明**。

**失效与返回**：

| 变化或异常 | 强制行为 | 不允许的行为 |
|---|---|---|
| 目标列表删掉Goal、改export、改变模块绑定或增加全导出成员 | 将相关`SelectedRootSet/JointRequirement/MethodPlan/ArtifactSet/Claim`按真实读集和ProofDeps失效；新旧根范围作为SourceDiff向作者显示 | 只因新目标仍可构建就沿用旧“容量安全”Claim |
| 引用的外部Policy/Observer/Meaning没有实际锁与解释器 | 准确列出Needs、可独立保留无影响根的设计结果 | 把外部URI或伪digest当已绑定事实 |
| 重复根选择器 | 一份逻辑Root绑定保留多处来源，展示冗余选择；各Req发生实例仍保留 | 双倍算同一静态根的硬条件或误删两个独立Req实例 |
| `req:composite`为空、未引用Goal却只选择该产品根 | 允许保存，表示这次选择没有因此引入目标约束，禁止签发不相干业务保证 | 依项目名、文件名自动把所有Goal并入 |
| Unknown Target Profile/Root kind 或全局求解预算耗尽 | 明确`Need`或`IncompleteSearch`及Frontier | 输出完整成功、将未知当false或声称UNSAT |

**结构门禁与执行区别**：[source/project-1.schema.json](../../../../schema/source/project-1.schema.json)是在本`gift.project/1`字段合同下新增的严格**有限形状检查**；扩展值不由基础Schema解释，且Schema无法证明模块路径安全、root成员绑定、语义含义、目标能力或权限。`fixtures/author-workspace/Gift130/verify_root_selection.py`从真实现有作者项目建立局部静态根闭包并检查删根/重复/重绑反例；它不签发生产 Reader、QualifiedMethod、完整Target或外部作用资格。

## 多模块真实工程的结构读取与引用闭合（R01设计合同）

`gift.author-module/1`的正式工程合同已经允许`imports`；之前的有限`intent-module-mixed-1`结构Schema却只接收模块内Definition，**拒绝带imports的正常多文件工程**。现有设计Schema已补充 `workspace` 和 `locked` 的可选导入形状，保持`/1`外壳、四种有限Body、旧单模块Schema的含义不变。它只是**设计级结构检验**，不是发布了生产读取器、绑定锁注册表或新的公开协议版本。

一个解析发生位置的最小实物是`(projectInstance, sourceRevision, importingModuleId, importAlias, useSite, resolutionDomain)`。结构读取器先核`sourceScopes`及真实路径权限，保持原始字节与CST/Span，拒绝重复键/非法编码/未知解释节点；再从冻结的 `ModuleIndex` 定位真实作者模块，核ModuleId一致和唯一Writer；最后按导入发生位置逐个绑定`workspace`到同一冻结快照、`locked`到精确锁节点。声明环只允许签名阶段有明确规则的环，初始化/生成环不能自动通过。

引用解析必须分离三个判断：①引用形状符合当前Dialect，②所选发生位置存在且目标公开export，③其定义类型、效果、权威、来源和生效条件符合当前消费。只取得前两项不能给第三项签发资格。单模块文件中的`DefinitionRef.definitionId`指向本模块定义；`{import,export}`必须先解析alias再执行可见性检查。未找到外部锁/供给、被拒访问、同域多个候选、同名重绑、要求冲突分别返回可定位的Need/Conflict/Denied，不按最新版本或文件排序取第一项。

面向开发者的默认编辑是把新Definition保存在所属Module，写入准确`imports`和`exports`，必要时由工具维护清单定位；不让用户为了业务目标再写一份解析后的ModuleUse表。真正资格锁在成功取得来源字节、解释版本、环境和发生位置后生成。跨文件移动不改变定义身份但要检查导出与相交Control；复制成独立对象时分配新身份；删除重建不得复活旧运行Grant。范本见[真实多模块工程](逐文件开发源码具体规格与完整实例.md#gift130-source-tree-authoritative)。

## 三份作者文件的共同规则

文档根必须为对象；`schema`选择精确合同版本。必填字段缺失、显式`null`与字段值类型错误分别处理；可选字段仅采用本协议声明的缺省。未知根字段不得在加载和保存时静默删除：保留原始字节并返回未知合同诊断；正式扩展必须通过其所属专业合同与具名 Dialect 解释，而不是插入 Project 的任意 `extensions`。

项目、模块、Definition和锁节点使用各自作用域内不可复用的不透明身份；显示名、文件路径、内容摘要及修订分别记录。工具只在对象需要跨作用域或跨修订稳定引用时分配身份，临时局部变量无需全工程身份。删除再创建同名内容、复制独立对象都获得新身份；引用原对象的普通别名保留原身份。

协议标识必须为非空、不含控制字符的字符串，字段名及保留字面量精确匹配。标识相等按已保存的Unicode标量序列判定，不自动折叠大小写或执行NFC；显示名与机器身份分开。长度、节点数和递归深度超过声明的读取预算时返回资源诊断，不改变合法输入的语言意义。

所有路径都是定位，不是读取许可。来自有型 Control 的政策请求不是授权。所有摘要都说明算法与编码域，不把校验和当签名。承载原生代码的文件保持原编码与语言合同；不把整段代码转写为巨大JSON字符串树。

### 工程清单：唯一模块发现与目标根选择

`gift.project.json` 的业务含义已经由唯一的 `gift.project/1` 作者合同确定；“Project 的模块路径表”和“SourceScope 扫描结果”不能作为两份可同时维护的来源。**唯一选择是 SourceScope 声明可读取区域、模块文件自报稳定 `moduleId`、Reader 对固定文件快照构造派生 `ModuleIndex`。** 不再要求作者填写 `modules`，也不允许从路径名/扫描顺序发明逻辑模块身份。若源扫描只覆盖部分文件，结果是相对于该选中范围的有限发现，不能据此声称其他模块不存在。

| 字段 | 当前作者形状 | 含义及不成立条件 |
|---|---|---|
| `schema` | 必填，`gift.project/1` | 仅供文件格式分派，一次声明；不是每个业务 Kind 的版本字段。 |
| `projectId` | 必填，非空逻辑 ID | 项目的名义身份，不等于工作区物理位置或产品运行实例。 |
| `sourceScopes` | 必填，`SourceScope[]` | 各项给出 root、semantic/native/asset/design/generated 分类、`editSource` 和可选 include/exclude；路径选择不能自行授予读取/写入权限。 |
| `targets` | 可选，键到 `{profileRef,outputRoots,parameters?}` | 各个目标下选择的产品根及目标画像。空数组代表未选择生成根的草稿，不代表完整应用。 |
| `defaultTarget` | 可选，指向 `targets` 的已有键 | 仅在作者/宿主确有此选择时有效，不为含多个目标的工程猜唯一默认。 |
| `library` | 可选，严格 `gift.library/1` 发布描述 | 仅保存包名、发布标签、公开子路径及不可推导依赖/变体选择；字段与迁移由[包公开边界](../../../20-语义与组合/组合/模块封装-包边界与源码布局.md#包描述公开导出和版本绑定)拥有，不复制模块发现表或授予发布权。 |
| `annotations` | 可选，非语义说明 | 显示与写作辅助；不携带隐式业务、权限或生成规则。 |

原 `modules`、`policyRequests`、不受类型约束的顶层 `extensions` **不是现行 Project Writer 字段**；历史 Reader 可以读取准确旧版本，并在迁移时显式处理其信息。确需的独立实现 Control 只使用 `gift.control-file/1` 控制文件；控制请求不是宿主 Grant。库发行选择使用上表的具名严格 `library`，不恢复任意 extensions。确需非标准语言扩展，在使用的作者 Module 中声明有名 Dialect 与合格来源，不在 Project 的万能字典中放任意 `JSON` 代码。机械推导的模块发现索引、锁、ContentHash、目标 AST、产物路径不能第二次由作者写进 Project。

**固定一次输入的解析次序。** SourceOwner 根据 Project 与宿主授权确定可读区域，SourceReader 在固定快照中按已绑定 SourceProfile 识别作者模块或[原生选择文件](#design-a03)的根 Schema 与 moduleId；前者取得作者声明，后者经合格原生 Reader 取得公开视图，共同形成带解析域的只读 ModuleIndex。文件后缀不是唯一分派条件，未取得原生 Reader 时保留准确 Need，不把选择 JSON 当函数实现。两个源独立宣称同一 moduleId、同一源由冲突 Writer 改写、symlink 越界、Unicode/大小写碰撞、import 公开出口不唯一、固定快照未包含需要的源，都不得依枚举顺序选择一份伪造的成功绑定。随后按每次 `imports[alias]` 的实际发生位置绑定同工程模块或锁定供给，并检查目标是否公开。此处 ModuleIndex 是读取结果，不是新增持久注册表；作者移动文件且 moduleId 不变时，只改变其 SourceLocation 与相关有语义的路径消费，不要求给原业务定义换身份。

**目标及根的身份和作用域。** `targets[targetName].outputRoots` 的每个元素选择 `{moduleId, export?, rootId?, contextBindings?}`。`export` 指定公开出口，省略表示选择该模块在固定修订的全部合法公开出口，必须记录集合依赖；空字符串不是省略。生成用多根必须有局部唯一的 `rootId`；只有一根的历史选择可在明确规则下归一成 `main`。rootId 的独立身份域仅限当前 Target，采用 `[A-Za-z_][A-Za-z0-9_-]*`、最多128个字符；它与允许连字符的 JSON Definition/import/export 符号词形相容，但不共享 Definition 身份，也不把其128字符限制加到业务符号。同一产品定义被选两次时，形成不同根实例，拥有各自组件 Instance、Scope、上下文和已接受要求。相同 Definition、显示名、ObjectRef 字符串或 ContentHash 都不足以证明跨根资源共享；真正共享要有有权身份/权限与配额/时间联立。`contextBindings` 依选中定义的角色签名解释，不会让 Project 获得凭空注入任意对象或外部许可的权力。

**被选根与工程义务。** 作者可以选择产品/Goal/Requirement 或有 Target 明确支持的计算导出；存在于工作区但未被选择、未被可达引用消费的定义不自动激活。另一方面，独立已接受的外部硬要求不能因为从源码移除了一个 Goal 就被宣称已满足或被合法撤销。RootSelection 负责固定的使用发生点，Requirement Owner 负责联合义务，Method Owner 负责合格实现，Target Owner 负责实际目标成员。它们不得互相代签。无根/无 Target 的合法编辑草稿可以保留；生成请求必须得到明确的目标、真实受支持的根与必要供应，否则保留 Need、Unsat 或未完成搜索，而非生成空壳假成品。

**最小项目示意（设计中的当前作者语法，不宣称生产 Reader 已发布）：**

```json
{
  "schema": "gift.project/1",
  "projectId": "project:notes",
  "sourceScopes": [
    {"root": "design", "kind": "semantic", "editSource": {"mode": "file"}}
  ],
  "targets": {
    "typescript": {
      "profileRef": "target:typescript",
      "outputRoots": [{"rootId": "desktop", "moduleId": "module:app", "export": "App"}]
    }
  }
}
```

真正能否生成应用仍取决于被选择的 `App`、其每个必需业务成员、领域 Meaning/Method、权限与 Target 的独立资格。这份 Project 没有暗示模块文件已经存在、TypeScript 供应真实可用或者输出已通过构建。

### 输出根选择器、固定绑定与后继变化

`OutputRootRef`是本节`moduleId`加可选`export`的**作者选择器**，不是新的全局稳定实体ID。它在一个已固定的projectInstance及本次解析范围中解释；同一串选择器在另一工程、锁使用域或解释基础上不当然指同一个根。target仍是与选择器正交的生成限定，物理输出路径也不成为根身份。

准备阶段按 `(projectInstance,targetKey,rootId)` 定位本次选择发生点，解析为内部 `BoundRoot`，保留该根键、选择器、基础 SourceRevision、ModuleUse/锁位置、所选公开出口集合及各成员对应的实际 Definition、所选 Meaning、使用目的、成员覆盖及真实 ReadSet。它是只读派生结果，不要求新增根注册中心或第二份文件。**生成用多根 Target 必须在原有每个 `outputRoots[]` 项中使用稳定 `rootId` 区分实际发生点**；既有单根无该字段时规范化为 `main`，而不是在列表重排后用索引代替身份。这是同一选中根结构的局部字段，并不是另一份持久IR。缺导出/身份/权限/解释时返回准确 Needs/歧义；下游使用冻结的 `BoundRoot`，不得重新从 live 名称查询并无声改变目标。

| 变化或用途 | 准确处理 |
|---|---|
| 单一公开导出 | 固定公开名的解析边及实际定义；其他不相交导出增加不改变该选择，但语言级整模块检查仍成立 |
| 省略export的全部公开导出 | 这是明示的集合选择；每个新基础重取准确成员，增加、删除及转导变化进入成员/绑定依赖，不是冻结昨日列表 |
| 同名公开导出改指另一真实定义 | 新基础解析新边，重核原公开要求、控制适用性、类型/效果与消费者；名字相同不保留旧检查、编辑句柄或运行实例身份 |
| 模块移动或公开导出改名 | 模块ID沿合法身份映射保持；改导出名同步相交 outputRoots 并重建 BoundRoot；rootId 未变时 Control 的逻辑键保持，但适用性/资格重核。根 ID 更改须显式迁移相交控制或保留未解析诊断，不能猜名迁移 |
| 删除后新建同名声明 | 新声明有新身份；指向原definition/occurrence的直接控制不自动复活。仍被作者明确保留的公开根选择器按本表重新求值，不声称它保持了旧声明身份 |
| 两条合法解析域均有同moduleId | 分别建立ModuleUse；当前根必须已有明确解析范围。范围仍不能唯一决定时返回歧义，不按版本最大、读取先后或本地优先挑选 |

**集合选择与单一产品实例不能混用。** 一个 BoundRoot 对应一个选择发生点，省略 export 时可以包含多个公开出口成员；成员在该冻结选择内以公开出口名区分，记录其真实 Definition 与来源边，不能把它们压成一个运行实例。重复公开别名仍保留各自公开边，由 Target 的别名/成员合同处理，不按扫描次序任选或伪造跨别名实例共享。集合新增、删除或重绑定均重新核成员与相交消费者。

`contextBindings` 要求该 BoundRoot 的全部选中公开出口中**恰有一个成员且它是 `product:system`**；不是从混合集合里筛出唯一一个 system 后忽略其他出口。显式 export 是常规写法；省略 export 只有在本次冻结模块确实仅导出该 system 时才可使用。公开出口后来增加，即使旧 system 未变化，也必须重新判定并报告上下文绑定范围歧义，不能把原上下文广播给新增成员。恢复方式是作者明确选择 export，或将不同产品拆为独立 export/rootId 选择；未采纳该差异前不自动更改源。

`product-root` Control 的 scope 则是选中根发生点及其完整成员集合，不普遍要求 `product:system`。描述符决定允许的主体种类、集合基数与传播；集合控制有合格定义时可以作用于集合，单符号 public-name 不自动广播给全部成员。成员新增、删除或换绑使相交适用性与有效控制重新求值，不能偷偷筛掉不匹配的出口取得成功。多成员普通库/计算导出仍可由支持集合根的 Target 与描述符消费。

按product-root声明的Control以**target/rootId 标识的选中根发生点**为边界，不能仅用 moduleId/export 作为逻辑键。同一 Target 两个根选择相同导出时仍可独立控制；数组重排不改变控制归属。根发生点保留而公开选择改变时，在新基础重核该根的控制、要求与资格；按definition/occurrence声明的Control约束稳定作者对象。想固定后者时使用直接对象scope，不能拿公开别名当不可换绑的对象ID。任何选择器的后继成员都重新核适用性与当前作用资格，选择器既不继承旧Grant，也不把删除—重建解释为原操作恢复。

<a id="imported-output-roots"></a>
### 导入模块出口可以直接作为生成根

`ModuleIndex`从本工程实际 AuthorSource 派生模块ID与定位，不是要求所有依赖拥有本工程文件。已由当前锁或固定上下文明确导入的模块，可以通过原有`outputRoots`的`moduleId/export`选其公开出口；此时它读取为ImportedModuleView，不写出同义`.gift`模块。外部没有源代码，不等于没有真实定义或实现。

解析顺序固定：先解析由 sourceScopes 发现的本工程模块及导入绑定，按projectInstance、锁发生位置和resolutionDomain建立有来源的模块联合，不压成全工程唯一的`Map<moduleId,view>`。**同一准确解析槽**的同ID分别指向不相容作者和外部内容时才是竞争绑定；不同合法使用域中的版本并存沿[ModuleUse规则](工程准备视图与编译输入.md#module-use-binding-domain)处理。输出根必须位于本次明确可读、可用的绑定范围，并具有实际公开出口；裸moduleId不能从多个可能域中唯一决定时按[根选择器](#output-root-selector-binding)返回歧义。知道某个私有ID或在全局缓存找到同名项，不取得导出/读取权。

没有自有算法的工程可以把 `sourceScopes` 留空（仍是合法的未构建工程草稿），目标根只引用合格的导入出口。新的项目内业务差异出现时，再加入真实源及相应定位。不能先造一个空`main.gift`或无体转发来满足COMP1；也不能将供给引用当成永久锁外查询。

项目的公开名字和目标形式沿既有稀疏控制保存。精确合同/方法/原生模块/工具及使用点在原锁中解析；内部UseBinding从它们派生，不增加新的project根字段、第三个文件或每函数手写模型。相邻库调用的组适配保存在实际方法供给中，共同信息不复制到每个应用。

moduleId 必须能在本次 ModuleIndex 或已固定的导入绑定范围解析。旧读取器实际若仅支持本地模块，应明确报告未支持的导入根能力，不能忽略绑定生成空项目；模式字面量未变不证明所有历史实现自动支持新补齐的算法。语义变更按草案精确内容绑定和版本协议处理。

首次持久保存共同处理：作者字节若有、SourceScope及模块/导入解析关系、已接受的目标要求、语言/供给锁及实际资产；生成目录不进入作者模块的编辑源范围。多目标共用同一公共定义，目标实现各自绑定，不能只锁一个目标再以同名推导另一个目标具备能力。

### 作者模块：唯一当前写源 gift.author-module/2

### Module：开发者可写的最小容器

```json
{
  "schema": "gift.author-module/2",
  "moduleId": "module:notes-model",
  "definitions": {
    "NoteId": {
      "kind": "core:type",
      "body": {"type": {"tag": "scalar", "name": "text"}}
    }
  }
}
```

以上是**无需跨模块公开声明的最小写法**：`namespace`、`imports`、`exports`、`dialects` 都按需填写；Definition映射键就是局部DefinitionId，不重复写`name`。此例仅声明类型，不宣称能生成笔记应用。若要生成产品还需公开行为、状态和根。`moduleId`用于稳定模块身份；可选`namespace`只用于展示/命名投影，不覆盖`moduleId`或产生隐式导入；不能把二者无条件合一（一次包移动不必改变逻辑ModuleId）。`imports[alias]`绑定同工程模块或有锁定依赖，`local:Foo`/`alias:Foo`按词法解析；重命名显示名、改变版本、真正改变定义身份是不同操作。`exports`公开可见边界与可选别名，不复制 Definition Body；未导出者不可被外部任意引用。

标准内建 `kind` 不需要 `dialects`。只有实际非标准解释器参与时才引入明确的`dialects`条目，其ID/版本属于解释能力与供给合同而非普通字段上不断添加的标签。方言未注册或消费者不存在时，保留原源码但其扩展语义**不得静默影响产物**。


| 模块字段 | 当前Writer条件 | 唯一解释及未决情形 |
|---|---|---|
| `schema` | 必需，`gift.author-module/2` | 模块读取合同；不表示每个Definition另有模块版本 |
| `moduleId` | 必需、稳定逻辑ID | Project的SourceScope只发现路径，模块自身保存身份；同Scope重名是歧义，不以文件名补出身份 |
| `definitions` | 必需、至少一个局部Definition | `definitions[localName]`保存唯一局部定义键；Definition只需要`kind`和该Kind的`body`，不二次保存 `name`；Kind的约束由专属Body与语义Owner负责 |
| `namespace` | 仅需要作者显示/名字空间时填写 | 不覆盖ModuleId、Import alias或真实身份；目录改名不自动改变ModuleId |
| `imports` | 仅跨模块消费时填写 | 别名→`{mode, moduleId, constraint?}`；`workspace`定位本次冻结源码，`locked`定位真实外部固定供应；不得靠名字猜版本、私有Definition或跨域权限 |
| `exports` | 仅需要对外公开时填写 | 公开名称→`{definitionId}`，精确指本模块合法定义；无导出时不隐式将全部Definition公开 |
| `dialects` | 仅明确使用非内建扩展语义时填写 | 别名→`{languageId,constraint}`；只标明供应选择要求，精确规则由锁签发，未合格不得解释扩展Body |
| `annotations` | 可选 | 无构造/语义授权意义的辅助信息；不得通过注释逃避定义、约束、导入或Grant边界 |

写作模型是**一模块多种有型定义**，不是每种业务一个文件、每个Kind一套新语言，也不是万能`payload`对象。具体当前27类Definition、19类Type、17类Expr及业务关系分别受[Definition专业归属](../../../20-语义与组合/作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#business-kind-consumer-coverage)与相关计算/数据/状态/产品专业正文约束；数字仅说明现时形状，不是最小性、可计算性或生产实现证明。

**JSON 符号词形。** 当前 `/2` 的 Definition 映射键、imports 别名、exports 公开名/本地定义值及通用 Ref `local:Definition`、`alias:PublicExport` 的对应符号段采用 `[A-Za-z_][A-Za-z0-9_-]*`，例如 `local:Order-line`、`order-api:Place-order` 都可准确解析。连字符是这些 JSON 字符串中的合法符号字符，不是减法。冒号仍只分隔引用域，不成为局部符号；保留域 local/std 仍按原规则处理。版本化 Body 保持其自己的引用结构，例如 Requirement Body 的对象式 DefinitionRef；其中对应 Definition/import/export 符号也允许连字符，不能强制换为通用字符串 Ref。这不修改 `.gift` 计算文本的 Ident、计算局部变量、原生语言符号、路径、URI、ModuleId 或其他不透明身份的语法。rootId 虽允许相同字符，仍按目标内独立身份域与128字符上限校验。

**名字、发生位置和实际绑定**有区别：`Ref`的当前语法是`local:LocalName`或`importAlias:PublicName`，但解析必须先识别被限定的Scope、导入别名及真正的`exports`，随后在SourceSnapshot与锁的发生位置中定位精确Definition内容。普通字符串即便包含冒号也不会自动成为Ref，只有Schema指定的Ref位置才解析。一个模块的导入别名不能越权访问另一个模块的私有Definition。模块间互相引用允许在**仅含可预声明签名**的域形成合法声明环；求值初始化、效果与部署循环另由实际消费者拒绝或定义固定点，不能仅凭导入图判断全部合法。

**可选方言的精确责任**：内建`core:*`、`domain:*`等Kind由唯一公共作者Schema与其Owner直接定义，不需要逐Kind注册Dialects。真正新增语义先声明扩展签名、作用域、类型、效果、具体Reader与目标消费者及供应版本；可以作为专业扩展服务复用。已命名方言或`extension:definition`的存在不代表解释器、Target或外部权限实际可用，也不能通过动态JSON绕开静态专业判断。

**兼容读取与迁移**：历史`gift.author-module/1`可有不同的名称规则、嵌套`name`与旧`dialects`要求，其语义必须由隔离Reader依准确旧规则解释。若迁移为`/2`，必须保存旧来源与新定义的身份映射、可见性、角色和Requirement发生位置；迁移前后的作者采纳义务不按新语法重写而自动变化。当前作者工作台不产生新`/1`，也不要求每次保存两个版本。内容锁记录精确供应和作用范围，普通Module文件与锁均不承担另一方的编辑真源。

<a id="author-module-dialect-composition"></a>
### 同一语言的内建Kind与专用扩展

标准Kind只是 `definitions` 的有型判别分支；它们由唯一当前作者Schema描述合法Body形状、由各自专业Owner解释。计算函数、业务意义、Requirement、状态/工作流、数据/查询、UI/API、资源、权限、效果、产品组合都可在同一模块内声明，**无需先让用户选择“计算语言”还是“业务语言”**。具体种类、发生点身份、角色、拒绝条件只保存在[定义及专业消费合同](../../../20-语义与组合/作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#business-kind-consumer-coverage)，不在本工程清单协议维护第二份平行枚举。

扩展的准入门槛不等于增加内建Kind：普通新行业名词、业务关系和领域类型应优先由 `domain:meaning`、`core:type`、Pattern、组合和有权Method表达；只有既有机制不能保持某种可观察业务差异，才使用`extension:definition`及受控语义供应。真实扩展不仅要有DialectID，还要具有可检查的输入签名、静态/运行解释、合法使用点、冲突、升级、目标和撤回条件。缺任何必要消费者时保存为合法待补全设计，不能以“schema字段存在”授予目标实现资格。

数据模型的Owner是类型与数据语义，Requirement只是消费它定义的类型/关系；业务流程消费它的操作，API消费其公开投影，目标生成适当持久或传输表示。相同产品中出现几个不同用途的投影不表示要复制几个可编辑实体定义。原生TS/Rust等算法源码仍受其源所有者管理，只在有独立供给或互操作需求时，通过精确符号绑定和Method/Target合同进入同一个ProductRoot。

### 数据模型不是Requirement dialect的附属字段

产品自己的record/variant/nominal value、Quantity/Money、资源句柄等数据模型由真正Type Definition/dialect拥有；Requirement侧只消费[结构作者源定义的Type/ref、typed value与`req:value-type`边界](../结构化源码.md#requirement-value-type-boundary)，本清单协议不复制第二套类型目录或codec。

反方向也成立：一个Program record type存在，不自动成为产品Requirement或持久状态；Requirement、state identity、wire/storage/ABI表示仍按各自责任绑定。这样同一数据模型可以被算法、状态、API和Requirement共同引用，而不复制四份结构；module/dialect外壳只负责准确解析与锁定其真实owner。

### 成品边界和结构默认的保存

结构化复合定义的`parameters`、`subjects`、`terms`与可选`exposes`均属于本模块definitions中的body；没有独立接口镜像。value参数的显式default按[有限默认协议](../结构化源码.md#closed-parameter-defaults)解释；module exports仍指向定义，不改成逻辑主体引用。目标请求按准确公开边界与画像选输出，不从文件名推为函数、CLI或服务。

默认使用与显式同值均保留自己的作者来源。省略默认的文件在保存后仍可省略，固定值由准确规则解释/绑定获得；普通参数编辑不为每个条款另建锁节点。升级默认所属定义，检查所有相交消费者；实际采用旧定义或显式固定值的消费者不因目录里出现新默认而改义。

来源未改且只选择另一成品形式时，共同需求模块复用，目标要求、适配和真实配置按根变化。规格包完整、运行库完整与独立应用完整有不同剩余进口条件；同一文件清单不能用一种全局completed包办。当前设计范本的targets为空是明确的目标缺额，不等于它的产品要求被取消，也不得捏造目标引用。

<a id="gift131-binding-lock-node-graph"></a>
## `gift.binding-lock/1`：发生位置绑定与节点完整性的有限机器合同

**锁仍由有资格Resolver生成，不是作者文件。** 当前`schema/source/binding-lock-1.schema.json`只冻结原`gift.binding-lock/1`已有字段的一个有限SHA-256节点结构：`schema/projectId/resolutionInputs/bindings/nodes/extensions`；其中`bindings`每个发生位置键指向一个锁内节点ID，`nodes`每条具有`kind/subjectId/revision/content/dependencies`，`content`记录`algorithm/digest/byteLength/format`及可选有序成员清单。此设计Schema只支持所声明的SHA-256内容摘要结构；其它现有或未来摘要域必须由精确锁定的对应Profile解释，不能凭相同64字符的十六进制字符串互认。更高资格依赖真实内容字节读回、解析发生域和信任检查。

**资格与拒绝算法**：

1. 从真实工程/作者快照、Target、解析政策及使用发生位置构造`resolutionInputs`，它必须能识别当前输入选择和有效环境。单纯“空object”可通过基础形状检查，但没有足够上下文不能发行锁。
2. Resolver将每个被实际解析的`(sourceOccurrence, importAlias, useSite, resolutionDomain)`绑定为`bindings[occurrenceKey]→nodeId`。发生位置键须由真正已登记的编码规则无歧义产生；没有同样的消费规则，旧键不可凭字符串拼接推测身份。相同逻辑包在不同使用域可以有不同node，名字相同不要求强合并。
3. 每个节点实物必须被实际取得，校验内容格式、字节长度、明确Digest算法和值；有成员时按可移植相对路径和约定清单编码检查排序、重复、越界与每项真实字节。`locationHint`只是可变获取提示，不能作为内容身份或读取许可；任何当前不可读、内容不匹配的节点都不得签发成功。
4. 所有binding目标必须在`nodes`存在，全部依赖必须指向已存在节点；依赖环允许在语言/模块签名合同允许的范围内表示，但节点摘要本身不递归包含依赖和锁整体哈希。为锁完整文件取得摘要时在外部生成，不把其摘要写回自身导致循环。
5. 对实际发生位置重新核Dialect、Meaning、SourceProfile、Method、Target/ABI、策略和环境资格，签发有范围的锁及ProofDeps。改变用途或升级版本生成新锁候选，不能“最新版本覆盖”。历史已解析节点仍可审计，不自动继续拥有当前执行或信任资格。

**失败类别**：`INVALID_LOCK_SHAPE`、`DANGLING_BINDING`、`DANGLING_DEPENDENCY`、`UNSAFE_MANIFEST`、`CONTENT_MISMATCH`、`RESOLUTION_CONTEXT_MISSING`、`UNTRUSTED_OR_REVOKED_SUPPLY`和`ENVIRONMENT_INCOMPLETE`必须在相应层分开；它们是本文内部设计类名，最终wire诊断由原contracts Owner签发。缺真实锁不影响作者源保存；完整编译遇必须精确锁的供应则返回Needs而不是回退到本机latest。

**反例**：`fixtures/author-workspace/Gift130/verify_binding_lock_shape.py`在内存中构造一份明确标为测试的合成节点图，仅验证结构、节点引用、成员清单顺序、非法路径和项目ID。它没有产生作者工程的`gift.lock.json`，没有取得真实解析上下文，不能宣称本样例已经锁定Meaning/Policy/Method/Target。

| `nodes` | 必需，节点ID到节点记录的对象 | 内容、精确解释、依赖边和获取位置 |
| `extensions` | 可选，默认空 | 已协商的解析补充，不能自授信任 |

每个节点记录 `kind`、`subjectId`、`revision`、`content` 与 `dependencies`。`content` 包含摘要算法、摘要值、字节长度及格式；取得多文件内容时引用一份排序规则明确的清单，清单列相对路径、大小和字节摘要。`dependencies` 指向本锁内节点ID。获取位置是可替换提示，不把可变下载URL当成内容身份；获取后仍核对实际字节。

节点可以表示语言定义、库、生成规则、后端、目标或工具输入。发生位置不同的同名依赖可以合法选择不同节点；需要共享类型身份或单实例资源时，再由合同要求统一，不能因为名字相同自动去重。节点ID标识锁内记录，不要求等于递归依赖摘要；先定义节点，再定义边，最后对无自摘要字段的整份锁产生外置摘要，因此有环依赖不形成哈希自指。

普通工作区正文修改只改变本次源码快照，不要求每打一个字重写锁。改变导入要求、语言版本、目标或实际影响解析的政策才使对应选择陈旧；重新解析生成一个可审查的锁候选。固定构建不得静默升级依赖。撤销或新证据可使原绑定失去执行资格，但不改写它历史上选择了什么；重新选择必须形成新绑定。

锁不包含原始秘密，也不能保证所有物理环境都已被封闭。实际调用工具的宿主映像、ABI、系统库、环境和外部读取由相应构建输入与证据合同补齐。没有取得这些条件时，可以保存作者工程，但不能宣称已可字节重现。

### 默认语言组合不增加一份手写配置

新建项目或短源上下文由已选发行提供一个语言入口，该入口的精确依赖包含基础和有限对象规则；位置到节点的选择仍由`bindings`维护，构成仍由`nodes.dependencies`维护。结构模块可以通过`dialects`显式描述已固定的解释，普通AI文本请求不重复手填这份闭包。公开格式不增加第二个语言开关表。

首次建立时读取发行的真实默认并固定；以后默认变化不改变旧模块。明确升级形成新锁候选，检查词法、公开类型和消费者。已知签名无需的运行组件不会因语言入口含对象规则而变为产物成员。库导入固定所用符号及语义，不修改当前parser。完整职责见[语言组合](../../../20-语义与组合/基础语义/计算基础/紧凑表示与程序范式.md#合同标识默认语言组合与按需能力)。

## 合同标识的实际存放与读取顺序

合同标识保存在解释和编码的元数据槽位，不作为每个业务文件或类名的一部分。普通文件可叫`src/convert.gift`、`src/threshold.gift`；app/lib仅为可选作者目录，重命名不选择新语言，也不升级规则。以下复用既有字段，不新增配置文件、`intentLanguage`、`defaultLanguage`或每定义一个开关。

| 内容位置 | 真实字段或语句 | 表达什么；谁维护 |
|---|---|---|
| 普通`.gift`作者文件 | 函数、类型、调用和已选构造；无需强制语言头 | 保存程序及独特决定；模块的解释由已固定context或锁绑定 |
| 工具首次输入或初始化 | `context`，需要显式选择时为`sourceLanguage: "gift.object/1"` | 选择解释入口；后续客户端沿固定上下文工作，不能各调用自行升级 |
| 结构作者模块 | `schema: "gift.author-module/2"`；只有非内建扩展实际需要时填写`dialects.s.languageId/constraint` | Schema选当前唯一作者外壳，方言条目仅选择专业扩展语义；常规作者无需填写 |
| 结构定义体 | 既有`body.representation`，如`gift.object-body/1` | 选择该定义体的解码合同，不代替语言语义或当前权限 |
| `gift.project.json` | `schema: "gift.project/1"`、`sourceScopes`、`targets` | 身份、源位置和输出要求；根schema不是对象语言选择，现行根没有第二个语言字段 |
| `gift.lock.json` | `schema: "gift.binding-lock/1"`；`bindings`指向`nodes`；节点含`subjectId/revision/content/dependencies` | 保存实际语言/库/方法绑定及精确内容；初始化器、解析器和保存协议负责 |
| `.gift`中的库导入 | `import "./threshold.gift" as threshold`或已定义模块入口 | 选择要复用的定义；既非文件头语言切换，也非目标底层轮子选择 |
| 发布内容或提供者登记 | 该语义定义及实际方法的既有身份、修订和内容 | 提供规则本身；不能只保存一个代号而没有规则和方法 |

结构片段`{"dialects":{"s":{"languageId":"gift.object","constraint":"1"}}}`只是完整模块的一部分，不是可直接代替整个模块的对象。`/1`是约定的入口/合同标识；分开的`languageId`和选择符按该协议解析，不通过对任意路径字符串粗暴按斜杠切分获得。

**读取过程。** 先取得实际项目/候选或片段上下文；由冻结的模块发现索引定位模块而非猜目录。结构源从自己的语言要求解析，文本源从该模块的语言使用点绑定取得解释。沿`bindings`定位锁节点，核所用规则的revision/content和依赖，再解析作者字节。显式请求与已有源绑定冲突时形成解释变更候选，不覆盖旧源；`body.representation`还要与该语言允许的体合同匹配。

**首次保存。** 只有会话中的语言选择尚不足以让文件长期可重建。保存者把模块定位与语言使用点的精确锁选择共同纳入作者保存候选；不能只保存`.gift`字节后声称环境也已保存。独立短片段不必建立磁盘工程；需要分享并重建时，导出对应的固定上下文/锁内容，或由接收者明确采用自己的解释，不宣称自动等义。

**失效和缺失。** 只有文件而没有解释依据时，可以保全和按明确请求检查；不能按`class`词出现来猜版本。原规则内容缺失时按读取许可取得准确内容，取得不到则返回该依赖缺项；不把同名最新版本当替代。改变语言选择时核词法、类型和消费者；只改作者参数而解释未变，不重写语言锁。公开诊断可同时显示可读名称与精确标识，正常任务不要求作者记忆代号。

**必要成本。** 稳定标识承担可寻址解释和兼容，其存在合理；把它复制到每个定义、源码文件名、应用参数或另一份需求清单则没有这个必要。锁和源的不同责任应保持，所谓一份作者事实不意味着删除构建所需的版本输入。

## 已定义源码与尚未定义的业务行为

最小作者文件在上文Module章节已经给出：`schema=gift.author-module/2`、`moduleId`、`definitions.NoteId.kind=core:type`和其标量文本类型。这个文件能表达有名类型，但不能凭名称生成订单状态机或文件保存服务；**声明类型、指定状态和初始状态、规定事件处理、限制谁能触发、绑定持久化方法，是不同业务决定**，只有实际要求它们时才需要逐项提供对应有型定义或复用已合格的定义。

旧 `/1` 中曾用`wf:state-set`说明“open/closed”状态集。其可复用信息是状态集和初始状态的语义；当前必须用有类型的`state:machine`或确有资格的扩展表示。是否允许close/reopen、谁批准、是否持久化、失败/超时如何恢复、哪个UI/API动作触发，均不能从状态名推断。该历史JSON实例仅属于兼容档，不再作为当前开发者复制的示例。

Workbench、AI或普通作者可以按已接受的真实意图编辑同一模块；持久引用、跨源冲突和保存权限由[作者编辑](作者编辑保存与迁出.md)统一处理。不用为了生成目标再维护一份镜像AST、凭空插入实现stub、伪造来源锁或自动补未知Method。

## 稀疏作者模型与组合展开

作者工程不用在“全部普通代码”和“全部JSON节点”之间二选一。当前默认保留四类不能互相替代的作者信息：不可从实现反推的需求/约束；可复用组合定义与实例参数；独特的中立或自愿原生程序及其他资产；精确解释与实现绑定。它们仍使用前述模块/锁/原生文件，不增加另一套源格式。

一个功能实例引用确定的Gift定义，只写真正差异参数、连接和主动要求；目标实现未被作者固定时由编译器解析并锁定，不要求每个实例填写原生实现引用。由同一组合产生的内部结构、目标代码、关系索引和上下文是派生物；原生函数的AST/实际签名由成熟语言观察产生，不再次要求AI手填同一事实。独立“要求的签名/精度/效果”仍是约束，不能因实现当前不同就自动改成实现状态。

结构化模块不保存每个原生循环和局部变量的镜像；需要具体源码时按符号与范围读取。跨语言或特定领域需要额外表示时，必须声明语义保持与对应关系，不能默认所有目标共享同一个最低共同AST。派生图可以临时很大，是否持久化及驻留由查询与存储策略决定。

生成子对象由实例身份与定义内稳定局部身份定位；列表重排或文件改名不自动重建其业务身份。规则版本变化时，原身份保留、迁移或新建须由规则合同决定。没有持久消费者的临时AST继续使用本次局部身份，不膨胀成独立全局工程对象。

原生源码、组合和共享合同没有三份互相竞争的编辑真相。生成区回源修改，正式接管时转移作者所有权与重建声明。规则不能在每次构建时召唤AI重写自定义算法。原生资产和规则可完整导出，控制日志是否保留取决于尚未结算的作用，不能因“退出编译系统”一并抹掉。

粒度的不同维度由[意图与组合](../../../20-语义与组合/组合/定义与接口.md#意图粒度与可复用功能组合)规定；体量口径由[性能](../../../30-实现解析/增量与性能/性能预算与复杂度.md#作者体量派生体量与模型上下文)拥有。本节不以JSON大小声称工程更省上下文。

## 意图、定义、绑定和观察的同源保存

一个声明的“意图视图”和“语义视图”不是两个独立可写实体：前者解释当前要达成的性质与选择，后者解释同一来源的精确允许行为。正文、类型和实例参数共同形成作者含义；编译IR、边界摘要和依赖索引为派生。语义并不必然等于一份更长的显式树。

| 内容 | 权威来源及存储默认 | 谁可以修改 | 修改后谁需要更新 |
|---|---|---|---|
| 原始请求或独立要求 | 原字节和精确引用；没有独立来源不创建镜像文件 | 当前委派允许的要求修改 | 相交的接受关系、候选检查与结论 |
| 库定义与实例差异 | 对应.gift文件或另一个明确作者区域 | 库作者、项目作者及其授权AI | 使用到该公开或私有内容的分析、展开与产物 |
| 明确目标控制 | 既有控制记录或一个可靠作者表面，二者只选一个 | 控制修改权限与任务允许范围内 | 相交Binding、布局和目标满足检查 |
| 自动得到的类型、关系、有效值 | 可重建内存或缓存；来源指向原定义和规则 | 只能通过重新推导改变 | 声明读取该投影的消费者 |
| 已选实现与解析锁 | 实际选择和精确依赖；不是另一份算法源 | 合法解析、明确重选或升级过程 | 实现/工具/环境相交的产物与资格 |
| 实际运行状态和证据 | 原观察、方法、对象、范围；按责任保存 | 受信观察和结算协议 | 当前资格、诊断与恢复，不反写原要求 |
| 尚未解决的设计问题 | 本设计包中的单一[当前未决义务](../../../90-治理与参考/状态/README.md) | 设计维护者依据反例和处置规则 | 实施范围、相关规范和采用条件 |

原始请求有独立约束力时保留其版本；只提供一份完整源要求生成时，不为证明独立性强制另写同义规范。图形或自然语言摘要修改要产生对真实作者区域的候选差异；生成区不能直接成为第二份作者源。代码、配置、二进制资源和说明文档可以都属于同一候选，但不是它们都必须被改写成同一种语法。

### 采纳、重新解释和跨会话

候选C保存内容；是否接受其某项要求由独立的接受关系决定。新候选可以同时修改行为、控制和资产，保存成功不自动证明它替代旧要求有权，也不表示已部署。只有在实际要求变更被允许时，更新指向相应新片段的接受关系；其他独立要求保持原引用。

语言解释、库缺省或规则升级时，先在旧解释下保留原内容和关系，再生成新解释候选及差异；无法取得唯一映射的部分保留待决。重启会话只重取必要内容、绑定、未决和当前权限，不读完历史对话，也不默用新的latest重演旧决定。当前原生作者、派生内容、外部资产和控制仍由既有合同分别承担，新增视图不等于新增数据库。

## 接受依据与候选源的精确关联

当前作者资产还可能包含要求、政策或独立验收。保存方式不是给每个函数创建一份镜像Requirement，而是在已有声明或文档来源上建立精确版本的采纳关系。原要求与实现源在同文件时，可以引用原片段及其内容身份；实现修改生成新候选，旧采纳关系不会因路径相同而指向新内容。

跨软件关系约束沿同一持久化方式保存：若含义已由函数/状态/关系定义和实参决定，Requirement只引用该固定定义与来源；若原任务还有独立保持或进展要求，保存它的准确源片段和所接受的解释关系。CompletionView与RequirementTerm是绑定后的分析值，不另外生成requirements.json或可独立改写的意图源码。已接受的类型化解释实际参与生成或检查时，其精确方法/参数与源版本必须能由原绑定和记录恢复；不得只保留聊天摘要后每次重猜。

首次还没有正式保存需求时可以在任务内固定，跨会话采用则纳入既有保留根。必要保留的解释不能当作可随时丢弃的普通缓存；但不因此把所有派生检查、全文和本轮过程都永久保存。没有记录到的独立选择保持未定，不从现在实现反向补成历史需求。

创建任务时，受信请求选择使用哪一组现有要求；工具记录对应来源与解释，而不让任意项目注释成为授权政策。没有长期上下文的小函数，仅以本次明确源与请求为基础。需要跨会话继续时，保存最低限度的要求引用、候选关系、实际绑定和未决项；不保存全部聊天或复制全文到每个任务。

候选采用若真的变更要求，要求身份与新内容、采纳主体和相交消费者要在同一逻辑变更里一致，不能先移动“当前要求”指针再用它验证尚未接受的实现。文件写源与数据库写源各有原有提交协议；无持久采用时关系保持内存即可。历史要求仍需在所承诺复现和责任期间可解析，纯可丢缓存不承担这项唯一存储责任。

源身份、内容摘要、契约摘要和使用点边界摘要不等价。增加注释可以改变精确字节而不改变行为；同样结果也可能来自另一种授权前提。缓存只对所声明的等价关系复用；不能用一个“semanticHash”代替未定义的全程序行为等价判断。

## 意图依赖与机器编码

Catalog只消费本协议固定的ProjectView/imports/ModuleUse与准确EngineImage；不向project或lock添加可写意图数据库或动态Provider健康。facet展开形成普通源与Needs，采用依赖/Binding仍走原锁和Decision责任。[物理机器合同](../../../70-工程系统与演进/实现与装配/源码分区与机器合同.md#machine-contract-source)负责本协议的结构源/生成绑定与严格codec，不能将wire/schema升级当持久内容identity迁移。

## 工程源、解析锁与目标绑定的可重建闭包

机器解析输入是 `ProjectResolveBasis{projectSourceRevision,moduleSourceRevisions,sourceProfileRevision,selectedRoots,lockRevision,platformAndTargetRequest,registrySnapshotRefs,policyRevision}`。`selectedRoots` 是本次请求选择器的闭合结果，不等于目录扫描得到的全部可编译文件。解析器先验证 project 中所有 `moduleId`、模块源定位及锁条目的局部唯一性与规范化名称，再按导入图固定版本、feature、条件平台与实际供给闭包；未取到的锁内容不能用同名 `latest` 自动补齐。禁止把 `moduleId`、target artifact path 或 Lock 的供应商显示名混作同一身份。

`resolve(basis)` 的三种结果为 `RESOLVED{boundRoots,exactModuleUses,exactLanguageUses,dependencyClosure,readSet,negativeUniverseSet,lockDeltaCandidate}`、`NEEDS_INPUT{missingRefs,neededCapabilities,partialBasis}`、`REJECTED{diagnostics,affectedRoots}`。`lockDeltaCandidate` 只是下一次作者保存的候选；解析成功本身不能改 `gift.lock`。已选依赖存在不同解析结果时以可见的分叉返回候选，由指定拥有者采纳；不存在不记录来源的隐式全局锁更新。

提交锁变更时比较 project/module/profile 原修订、实际正依赖与负依赖枚举边界、目标/环境条件及有权 writer；对每个共享不变量形成联合冲突域。一个来源被别的编辑者改动、Registry 新增更优供给、权限收窄或 `SourceProfile` 迁移，都可能要求局部重解析。发布后必须由同一锁字节重放出相同模块绑定与诊断；纯换行差异不必使语义结果变化，但原字节前像仍供 CAS 使用。若外部 Registry 不支持固定枚举或源内容不能固定，返回显式 `NOT_REPRODUCIBLE` 及受影响根，不能声称闭合。

验收见证：两个模块使用同名、不同来源的 dialect；依赖注册表在候选冻结后插入新版本；跨平台条件边变化；锁写成功但工程作者源 CAS 失败；目标从 TS 改为 Rust 但源未改。上述各案分别检查绑定身份、重算边界及作者事实不被无授权改写。

<a id="developer-minimum-project-and-real-authoring-files"></a>
## 开发者真正编辑哪些文件：最小工程、原生工程、完整工程

本节按当前 `gift.project/1` 与 `gift.author-module/2` 展示作者操作；字段真值与类型以上文合同为准。历史格式只按明确迁移条件读取，不另造 `gift.project/2`。以下路径和示例是准备实现的作者交互实例，尚无实际产品读取器或TargetProfile验证，不应作为可直接构建成功的发布样例。

### 最少保存成本与三个不同文件集合

- **临时短片段**：只有编辑器缓冲/输入字符串和固定解释上下文；不强制创建一个目录、一份project.json、一份lock、一个sqlite DB或Graph。若需要真实保存，它也可以作为普通原生/文本源保存在用户已选择的目录。
- **已有原生TS/Rust仓库**：原本的`package.json`、`tsconfig.json`、`Cargo.toml`、源码/测试/资源各有作者owner；Gift捕获当前快照和相交Profile/工具链，不自动复制成中立结构Module。只有当用户选择Gift结构作者语义、固定多目标生成或特定长期约束时，才增补真正需要的作者文件与锁。
- **长期Gift结构化工程**：`gift.project.json`提供明确项目范围和模块定位；`src/...`的新业务`gift.author-module/2`保存Definition/Requirement的作者事实，旧`/1`源码只读，稀疏Control仍归其真实控制Owner；`gift.lock.json`只有在绑定解释、供给和目标候选被实际采纳时产生；普通项目业务状态由其**自身程序**拥有，绝不强制塞进Gift控制DB。

一个新项目可以从下列准确格式的**尚无可生成目标**工程清单开始（规范字段示意，真实文件创建仍需经合法保存操作）：

```json
{
  "schema": "gift.project/1",
  "projectId": "example-order-workspace",
  "sourceScopes": [
    {"root":"src", "kind":"semantic", "editSource":{"mode":"file"}, "include":["**/*.module.json"]}
  ],
  "targets": {}
}
```

若作者只建立项目框架，上述清单已足够，不必创建空模块。开始定义订单身份时可增加 `src/orders.module.json`：

```json
{
  "schema": "gift.author-module/2",
  "moduleId": "module-orders",
  "definitions": {
    "OrderId": {"kind":"core:type","body":{"type":{"tag":"scalar","name":"text"}}}
  }
}
```

此时可保存项目及这个私有类型，**不能生成订单应用**：仍无订单行为、公开导出、目标Profile与合格供给。之后增加真正的Definition，使用它所选`dialectAlias:kindName`对应的**已绑定body Schema**，并对导出值进行解析。不能像传统脚手架一样通过创建名为`OrderService`的空类声称订单业务已实现。

当`module-orders`拥有公开名`placeOrder`且当前解释/实现资格均成立，作者可以**选择**目标（下面`target-profile:...`是表示由绑定系统提供的真实Ref的占位符，绝非在产品里可直接解析的固定字符串）：

```json
{
  "targets": {
    "ts-app": {
      "profileRef": "<actual-locked-typescript-target-profile-ref>",
      "outputRoots": [{"rootId":"order-app", "moduleId":"module-orders", "export":"placeOrder"}]
    }
  },
  "defaultTarget": "ts-app"
}
```

必须将上面的两个字段**合并回同一`gift.project.json`的原`targets/defaultTarget`位置**，不是创建另一个目标manifest；结构作者源扩展也不要求每个函数一个`.json`。`gift.lock.json`由实际Resolver依`resolutionInputs`和发生位置产生`bindings/nodes`；用户一般只审阅决策差异，无需手编摘要和依赖图。任一输入未就绪只能保留已接受作者事实和Needs，不能向用户展示假的可运行应用。

### 从用户话语到哪个可写位置：统一写权表

| 用户要改什么 | 真正作者owner | 可能出现的派生视图 | 不可偷偷写入 |
|---|---|---|---|
| 新功能含义、公开契约、业务规则 | 已选择结构Module的Definition/Requirement，或原生代码明确范围 | Needs/Graph/Contract/候选 | `SemanticIR`、索引、缓存、Graph影子JSON |
| 代码中的特殊算法 | 可选文本`.gift`、精确Definition body或既有原生源码 | 中立语义和目标Code | 重复复制同一算法到多个Target手写真源 |
| TS专用布局/性能约束 | 当前真实Target/Control作者事实 | 目标程序计划/代码差异 | 改Rust后端的隐藏全局默认而不记录来源 |
| 语言、第三方库、方法选择 | 已采纳的导入/Target要求与`gift.lock.json`的实际绑定 | Resolved imports/RealizationBinding | 随运行时缓存命中静默升级锁 |
| 运行参数/秘密/部署权限 | 实际Runtime Input、Secret/Grant/Execution上下文owner | 运行Observation | 编译作者源、生成日志、Prompt内容 |
| UI位置、过滤、主题、最近展开 | 客户端显示首选项 | DeveloperDecisionView | Requirement/Definition/编译锁 |
| 校验、构建、执行回执 | Assurance Evidence与Operation/Attempt的实际owner | 状态徽标、历史证据 | 作者源码或“最后成功”全局常量 |

### 保持可持续维护的操作条件

普通修改只编辑相交作者字节；候选可能涵盖多文件但未采纳前不物理写盘。正式应用保存以真实`workspace head/source digest/lock basis`为前像，由单一owner按同一共同不变量提交；多目标分别产出目标产物。第二次修改先比较准确新的作者Revision，再根据read-set与root closure局部失效；未知依赖覆盖不允许宣称安全跳过检查。Native TypeScript源码可在原文件继续工作，目标生成代码若无双向映射则不能自动回写成作者事实。外部package lock及运行时环境不被`gift.lock.json`自动替代；要声称可重现必须闭合实际工具链、目标库、ABI/环境影响。

<a id="whole-system-author-workspace-and-ownership"></a>
## 最终作者工程与目标工程：从空设计到专业项目的准确落位

### 四种合法作者入口

1. **仅提问或短设计**：用户输入/选择的有限作者事实和解释上下文留在受控候选；不强制创建 `gift.project.json`、模块文件、`.gift`、锁、数据库或任何 target 文件。
2. **原生已有仓库**：工程继续由原有 TypeScript/Rust/C++、资源、配置、第三方语言和Git持有作者事实。Gift 的读取是带范围的观察，选定语义区域才能被相应适配器严格修改；不能扫描少量文件就称整个仓库已结构化接管。
3. **Gift 结构作者项目**：采用 `gift.project/1` 工程清单、唯一候选`gift.author-module/2`新业务模块（历史`/1`只读）及需要时才产生的 `gift.binding-lock/1`。通用编辑界面通过受控候选修改实际作者定义；用户不必手写每个 JSON 节点/IR，也不强制一个对象一个文件。
4. **混合工程**：当前工作区把源码、资产、结构模块与可选 `.gift` 的**非重叠写权区域**分别明确列出。Requirement与算法实现是两个不同事实，可以并存；同一算法在两种载体中有两个独立可写副本则不允许自动共享权威。

### 一个 VS Code 级新工程的作者目录示意

```text
ide-author/                         作者选择的工作区，不是Gift强制模板
├─ gift.project.json               只有选用持久Gift项目形态才有
├─ design/                         已采用的领域/系统定义（作者拥有）
│  ├─ product.module.json          工程主体、出口与产品约束
│  ├─ editor.module.json           文本模型、行为和公共接口
│  ├─ workbench.module.json        UI交互要求与服务接入
│  ├─ extensions.module.json       插件接口与宿主协议
│  └─ remote.module.json           连接、工作区和远程恢复要求
├─ native/                         用户选择保留的真实原生源码
├─ resources/                      图标、消息、许可、可访问性资产
└─ gift.lock.json                  实际冻结解释/库/Target绑定后才需要
```

上述文件名只是作者组织的一种可能结构。所有 `*.module.json` 必须是符合已锁定 dialect body 契约的真实定义才能表达其业务；凭文件名就存在的空壳不构成 Editor、ExtensionHost 的实现。模块应由真实消费者、共同不变量和修改局部性决定，不能因为目标系统有 `src/vs/workbench/` 就机械创建一份同名 author 镜像。

作者已决定的跨平台约束、可观察接口和未决定的实现方法由不同 Requirement/Control/Binding 保存；`gift.lock.json`不能代替依赖生态自身的 lockfile，也不能把某个图片/文本的名字提升为能力支持证明。环境密码、签名私钥或生产令牌不保存在可分发源。设计投影的 `TargetProjectPlan`、Graph、QueryIndex、SourceLayoutPlan属于**派生/可重新取得的查看结果**：它们可被导出供人审阅，不能作为与作者模块并行手改的第二份规范真源。

### 两次修改示意（只做设计不执行）

第一次：用户定义“代码编辑器 + 扩展 + 桌面/Web + 远程”。系统可提出组件、边界和布局候选，作者明确接受特殊要求后，形成固定项目定义与若干未决项；选择 `设计/工程蓝图` 出口只取得 Blueprint 和 Needs，**不调用代码生成**。第二次：用户把 ExtensionHost 从本地移至远端。提出的新候选必须保留未保存文本、扩展 API 和已有安全要求；只在有关 RPC、认证、工作区 URI、延迟、恢复、发布拓扑和兼容的作者区域形成变化，给出受影响源、Target 和检查义务。没有基础修订时拒绝错误差异；未采纳的设计候选不能覆盖原作者源。

### 只读设计与真正生成的分界

设计中可选择 `outputRoots` 与 Target 约束，确认未来目标文件角色、编译/构建方法和外部依赖，仍然没有 ArtifactSet。真正要求完整源码时才消费已固定的实现供给并进入 Target lowering/`gift.preview` 的实际产物出口；要写文件、运行、发布分别消费其操作身份和当前 Grant。本节为作者源 owner，不改写六工具公开字段、作用许可或实际Target可用性状态。

## 大规模Control文件定位（Gift 92 可选候选）

少量和大量独立 Control 均只用 `gift.control-file/1`，在同一 Project 的 design SourceScopes 捕获；是否分成多文件只改变物理组织，不改变逻辑键或优先级。无控制可无文件，reset 最后一条保留合法空文件。记录按[唯一控制合同](../../../20-语义与组合/组合/稀疏控制与目标限定.md#control-storage-contract)校验，路径不授予模块、Requirement或目标权限。旧内联与旧登记仅在完整前像、等价映射及共同提交条件满足后迁移；不支持的 Reader 阻断相交生成，不能忽略控制继续。文件布局选择见[大规模工程源码与控制存储](大规模作者文件与控制分片.md)。

## 项目文件、规则正文与目标供给的完整读取顺序

在同一 `gift.project.json` 中，`sourceScopes` 发现实际模块文件并派生 `ModuleIndex`，`targets[x].profileRef` 是**选择目标供应者**而不是目标信息正文，`outputRoots` 选择当前导出。`req:rule` 可来自本工程作者模块，也可来自已明确锁定的公开库出口；原生TS/Rust文件仍由本来的文件owner维护。`MethodSupply`、`TargetProfile` 与`Provider`声明来自外部库/供应者，不复制到每个 `*.module.json`。

固定一次解释时，先捕获项目与相交作者源的真实Revision，再用导入域和公开导出解析Rule、被观察函数和独立谓词，随后解析供给候选及Target引用。没有正确锁、内容摘要或签名时，保留作者设计并返回 `UNRESOLVED`，不能根据 `profileRef` 的字符串是否像 `typescript` 生成空目录；没有所要求目标时不强制填写Target。当前工程仍使用 `gift.project/1`，控制仅由现行 ControlFile 承载；旧内联/扩展登记迁移须按控制 owner 的完整前像、等价映射与共同提交合同处理，不以虚构的 `gift.project/2` 标签替代能力协商。旧 Reader 不支持当前控制发现与消费时阻断相交生成，不能忽略强制控制。

## 原生符号选择文件与严格源闭包：从名义引用到可读取的定义

作者 Rule 中的 `{moduleId, export}` **不是**在磁盘上搜索同名函数的许可。先由项目清单固定唯一原生 SourceScope、实际文件的作者权威及模块/符号选择；SourceProfile Adapter 再从已授权的准确源字节独立解析导出、类型、调用约定与效果。出现别名、重载、泛型实例、重导出、条件导出、宏生成、动态模块或 ABI 边界时，需要该语言适配器明确支持和固定选择规则，否则返回 `NATIVE_BINDING_NEEDS_PROFILE`，绝不按模糊名字或文件路径猜测对应。

以下 `gift.native-binding-selection-proposal/1` 是保留的历史受限候选；现行选择设计在本篇原生实现单源绑定及 `schema/source/native-binding-selection-1.schema.json`，迁移需真实profileRef而非自动换标签。历史候选的原形状为：在已声明 semantic SourceScope 中有一份 `design/native.binding.json`，字段严格为 `schema/moduleId/language/symbols`；`symbols[logicalExport]={sourcePath,nativeExport,role}`。项目 `extensions["gift.native-binding-selection-files/1"].paths` 只登记该源文件，完整的工程中可以使用现有模块/SDK 绑定接口承载同一事实。这里保存的是**作者明确选择哪个现有原生符号**，不保存函数体、推测签名、证明结果或目标生成代码。`sourcePath` 必须落入当前项目的 native SourceScope、无符号链接逃逸，并由 SourceSnapshot 捕获字节；逻辑绑定与原生文件双方都是必要读集。

实际读取次序为：①严格解码项目/扩展并固定源范围；②校验模块文件、公开导出及唯一作者身份；③装载精确原生绑定选择并校验其同一源域；④由对应语言/工具版本读取导出、签名与效果；⑤用所选 Rule 的槽和 Method 供给要求核相容；⑥输出绑定结果或带精确缺项的 Need。任何调用签名变化、原生重导出、SourceScope 变化、扩展重写、目标的编码/ABI 变化，均使相交绑定与消费过期。没有原生 Adapter 的真实读取不得签发 `NATIVE_SYMBOL_BOUND`。

`gift.binding-lock/1` 只有在实际解析/采纳后才写，记录已选择的字节身份、版本、来源与出现点绑定，不复制 `native.binding.json` 作为第二作者源；用户手填 lock 中的“已验证”状态无效。作者项目中省略此可选绑定机制的合法性不受示例限制：仅在使用当前 call-bound Rule 且无法用其他已合格 SourceProfile 绑定时报告 Need。

### TypeScript 原生导出依赖闭包不能在编译器 API 之后才补充

原生 TypeScript 的 `import`、`export … from`、`import()`、import type、CommonJS require 和 `/// <reference>` 都可能使语言服务在分析指定入口文件时继续读取其他源码/类型声明。只有入口 `.ts` 落入 SourceScope **不代表**语义读取限制在这一份文件；原生 SourceProfile 必须预先解析引用，依次在当前 authority 下确定每条依赖的准确唯一 Path/OID、内容身份、允许来源、环境/工具链配置和循环/条件导出解析方式，再把实际读取集合与负依赖一起纳入 SourceSnapshot。未知或越权依赖须在启动完整模块解析之前拒绝；不能在 TypeScript 完成读取后再因为最终导出签名匹配而接受。当前 `Gift96/probe-typescript.cjs` 是有限单文件 Profile，因此主动拒绝全部外部源码依赖，而不是偷偷扫描工程。正式支持多文件时应替换为显式受权依赖闭包和缓存失效，不要求用户永久使用单文件。

<a id="prebootstrap-lock-and-source"></a>
## 自举工程的锁闭包、版本与源资产

自举工程不新增一种平行项目文件：使用相同 `gift.project/1`、AuthorModule 和 `gift.binding-lock/1`。种子编译器源、必要标准库源、SourceProfile/语义供应、Method、Target、原生构建工具和运行库都以当前已有的有类型引用参与闭包；阶段产物另外是 ArtifactSet，不写回为作者依赖默认值。

发布一个语言 profile 的内容摘要，必须包括影响解释的文法/规则及实际消费者版本绑定；仅固定 `languageId` 的名称不能证明兼容。锁节点中 dependency 指向锁内节点 ID，整体锁摘要外置，不能把节点哈希递归定义为“含自己摘要的对象”。循环模块声明通过既有身份引用表示，内容摘要计算不要求无限展开所有被引用内容。

解析默认只消费固定可见快照和锁。需要新包、工具或语义供应时返回 Need，由有权宿主取得字节后生成新快照再解析；不能在类型检查器里临时联网，也不能以离线为由擅自选择另一版本。包名和版本字符串一样而摘要不同必须重新核验或冲突；撤回供应的执行资格与仍可读取其历史源资料分开处理。

工程源保存精确源身份，计算语义摘要只剔除已规定为不影响意义的显示信息，不剔除能改变选择、布局、数值、错误或观测的内容。方法目录的空查询、候选排序前提、缺包和不存在导出都属于会被未来新增内容推翻的负观察，进入对应依赖范围。

作为自举输入的 S 可以是一份尚未被正式采用的冻结候选，不要求先修改当前生产真源。但运行每个阶段时必须使用同一候选内容及其锁；不能一边比较固定点，一边自动更新依赖或接受 AI 改写。结果采用由原控制面独立执行前像检查。

<a id="design-a03"></a>
## 原生实现选择的单源绑定

原生符号选择落在已有 SourceScope/Binding 的来源层，不增加第二个类型或效果声明库。沿用受限选择形状 `moduleId,language,symbols[logicalExport]={sourcePath,nativeExport,role}`；选择记录只指出从何处读取哪个公开符号。`nativeExport` 是被选原生模块系统中的公开导出名而非Gift可任意解释的路径表达式；重导出必须追到实际拥有者。签名、泛型、可见性、调用约定和效果从受资格原生reader或独立桥合同取得，用户在选择JSON里写 `pure:true` 无效。

`gift.native-binding-selection-proposal/1` 保留为历史候选输入，不在正常编译中自动升级。当前设计的正式结构由同一 schema owner 给出；采纳迁移将旧选择转换为带精确语言Profile的 Binding candidate，经签名和来源读回确认后写入下述由现有 SourceScope 发现的选择文件。不维持旧选择和新Binding两个可变权威。产品未实现适配时，保留源并返回 NativeReaderNeed，而不是假称此符号不存在。

绑定键包含实际源快照、原生模块身份、导出符号、language/profile、reader及桥版本、依赖闭包；逻辑显示名不代替键。TS必须控制tsconfig及extends、路径映射、类型导入、重导出、动态导入、三斜线引用、package exports、插件和实际文件读取；Rust必须控制Cargo目标、features、cfg、宏/构建脚本、依赖和目标ABI。纯读取不自动允许运行proc macro、build.rs或TS插件。宿主在解析调用前建立受限文件视图；仅检查根文件后交给可随意读盘的原生工具不合格。

原生实现的内存拥有、异常、线程、回调和外部效果沿FFI合同接入。源/锁/导出签名/ABI任一变化使相交Method和目标绑定失效；原生源码写权不授予生成器。退出Gift时可保留经明确采纳的原生调用与锁定依赖；不能留一个只有Gift后台能解的临时句柄作为公开库接口。

本次采用的选择源判别字段为schema=gift.native-binding-selection/1，必需moduleId、language（typescript或rust）、profileRef（已锁定且与language匹配的来源Profile引用）和非空symbols。symbols只承载callable/predicate角色、sourcePath和nativeExport；符号词法由对应语言Profile核验，不把Rust路径表达式交给TS reader。其它原生角色需要明确扩展，不冒称当前结构已覆盖一切ABI。旧proposal迁移除更换标识还须实际解析profileRef；缺该输入保留迁移候选，不自动猜版本。

### 原生选择文件的发现、身份与再次修改

当前 `gift.native-binding-selection/1` 通过项目已有 `kind:"semantic"` SourceScope 的 include/exclude 发现，以根 `schema` 判别其 Reader；文件名和后缀不构成选择身份。Project 不保存旧 `extensions["gift.native-binding-selection-files/1"].paths`，也不另设注册表。扫描器先捕获获准普通文件与覆盖，再由已绑定 SourceProfile 识别作者模块或选择文件；不可将所有 semantic 文件都强制送入 AuthorModule Reader。未知格式可以保全，但不能作为已解释模块或静默抵消已要求的选择来源。

选择文件的 `moduleId` 标识它对 Gift 公开的原生逻辑模块，`symbols` 的键是该模块的公开逻辑出口；该文件是这些选择的唯一作者源，函数实现仍由原生文件拥有。固定同一项目/解析域后，两个选择文件或选择文件与作者模块声称相同 moduleId 均为竞争来源，即使内容相同也拒绝合并；合法不同解析域继续沿 ModuleUse 区分。Reader 由实际原生符号建立带来源的模块公开视图，未选的原生导出不自动公开，选择声明本身不证明 Method 资格。

`sourcePath` 是相对工程根的普通文件路径，使用 `/` 分隔；不允许空段、`.`/`..` 段、绝对路径、反斜线、NUL或控制字符。每一目标还须落在本次获准 native SourceScope，经过宿主路径别名/链接边界核验，并与选择文件共同冻结。`profileRef` 在该选择文件的来源解释域及锁发生点解析为与 language 匹配的精确 Profile，不按作者模块的 import alias 或目录名猜测。

移动选择文件且 moduleId 不变只更新定位与真实路径依赖；移动原生文件须共同更新 sourcePath、重新读取符号与依赖。删除/改名逻辑出口使相交 Rule、导入、Method 与锁绑定失效；同名新文件或新符号不自动继承原绑定证据。旧 proposal 的 paths 注册只作为迁移输入：保存全部旧前像，建立当前 SourceScope 发现及 Profile 绑定后共同采纳，移除旧活动登记；缺 Profile、源字节、唯一身份或 Reader 时保留待采纳候选，不能先删除唯一来源。

例如项目以 semantic Scope 包含 `design/native.binding.json`、以 native Scope 包含 `src/validate.ts`，选择文件声明 moduleId=`module:validation`、language=`typescript`、已锁定 profileRef，且 `symbols.validate={sourcePath:"src/validate.ts",nativeExport:"validate",role:"predicate"}`。成功路径是冻结两份源及依赖、由该 Profile 取得实际公开签名/效果、核 Rule 槽相容后建立绑定；若只有选择 JSON 而无原生 Reader，结果仍是 NativeReaderNeed。这是设计轨迹，不是已运行实例。

**验证与反例**：反例包括同名不同源、重导出换目标、未授权构建脚本、读取范围越界、签名不变但效果变更、选择记录无法完整解析。

**实际能力边界**：TS/Rust生产reader隔离和完整ABI检测尚未实施；设计接口已确定。

## 身份与变更事件的精确传播

身份域分为源字节快照、AuthorModule、Definition逻辑身份、其revision、源发生项、目标artifact、Operation和租户授权范围。字节相同不合并跨租户的访问权；同名不合并定义；文本位置变化不令引用悄悄指到新数组成员。解释缓存必须包含精确SourceProfile和语义映像，而不是只对JSON格式化后文本哈希。

重命名文件但保持module/definition身份时，只使定位/路径观察及相关构建成员失效；改显示名但未改公开导出路径不自动改变计算意义。复制定义默认新逻辑身份，即使body相同；显式移动保持身份及所有权转移证据。删除产生不可解析引用/历史tombstone，不允许后来同名对象接管旧引用。公开导出改名需要alias迁移或破坏性升级，不能以IDE查找替换假装历史引用未变。

默认来源、方法目录、目标和Grant变化分别影响相应实例/候选/产物/执行准入。已证明的纯数学关系不因无关权限撤销自动变假，但其披露和在当前目标中的适用性可能失效。反向地，语义版本变更不能仅因源字节相同而保留旧证据。每条依赖边记录观察的身份域和投影范围，由该域owner决定比较与失效。

**验证与反例**：构造rename/copy/delete/recreate、同内容跨租户、旧alias、新Method和撤权的变更表；逐类检查引用、缓存、证据、显示及执行不同后继。

**实际能力边界**：生产多版本缓存与授权回读未运行。
