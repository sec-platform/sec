# 大规模工程源码与控制存储：作者实际要写多少、怎么组织

## 定位

本篇拥有**编辑/组织成本及源文件选择规则**；控制的合法语义与`gift.control-file/1`机器字段只归[稀疏控制与目标限定](../../../20-语义与组合/组合/稀疏控制与目标限定.md#external-control-storage-gift-control-files-1)所有。Gift无论支持多少领域，开发者并无需枚举整个可控制宇宙。规模大是**语义信息量、格式开销、读写/版本热点、运行解析、上下文载入和审计规模**六个不同维度；不能用压缩文件体积回答全部。

## 首先判断到底是什么变大了

| 变大的东西 | 正确所有者和手段 | 不应采取的替代 |
|---|---|---|
| 已有算法和库代码 | 直接保留原生Rust/TS/其他源码，准确绑定Method及接口 | 把函数每个局部变量复制为JSON AST |
| 可复用的公共行为、关系或规则 | 一份真实Definition/Profile，实例按差异提供参数，模块公开复用 | 用生成器在每个实例复制整份定义并都可手改 |
| 同一受允许上层范围的设置 | 一个上层硬控制/require；scope传播、共同条件和来源可追踪 | 无条件压成Project层，无视只适用当前对象的限制 |
| 少量不同设置 | 稀疏Control、保留显式Pin与继承默认的区别 | 全量生成所有默认，再通过“值相等”删掉明确Pin |
| 大量**确实不同**的控制 | 可选外部分片`gift.control-file/1`和精确局部编辑；大量读取用索引及按需查询 | 声称换成YAML或短码后这些独立事实消失 |
| 巨型数组、数据、二进制、模型权重 | 版本化资源/数据集、ContentRef、专用二进制格式和真实访问约束 | JSON内嵌base64、巨型AST或隐式远程下载 |
| 机器生成/派生IR/图/锁 | 需要时缓存，按读集增量失效，不成为作者第二写源 | 每个构建把全部图导出成另一份长久可编辑JSON |
| 一次编辑只影响一个字段 | 稳定字段定位、精确diff/CST保留、按对象查询与SourceMap | `JSON.stringify`重写整份文件/删除未知扩展 |
| 用户/AI检索上下文 | 依据source、身份、查询计划读取相交切片与provenance；权限裁剪 | 将所有模块和控制原文重复扔入每个LLM上下文 |

**稀疏不等于缺功能**。真正需要从底层控制的对象仍可沿原有Descriptor、Definition、Method/Target和原生文件owner发现，未暴露快捷开关时给原owner/限制而不是谎称不支持。Normal/Advanced模式只是读取投影，不能改变谁拥有作者语义。

## 三种推荐布局，不能借布局改变语义

### A. 小工程

```text
project/
  gift.project.json          # 项目来源与目标选择
  gift/controls/author.json  # 有独立控制才创建
  design/core.module.json   # 真正作者定义
  src/...                   # 若有原生算法
```

有独立控制时创建一个由 design SourceScope 发现的 `gift.control-file/1`；零控制无需文件，也不生成全量默认。对已有文件 reset 最后一条时保留 `records:[]`，不隐式删除文件。

### B. 规模较大的专业工程

```text
project/
  gift.project.json
  design/editor.module.json
  design/extensions.module.json
  design/product.module.json
  gift/controls/project.json    # 当前确实独立的项目控制
  gift/controls/editor.json     # 当前确实独立的编辑器控制
  src/...
```

项目通过现有 `gift.project/1.sourceScopes` 明确发现受控范围内的独立 ControlFile，每片按唯一 ControlFile 合同保存 records；模块中的Requirement依然由模块自己拥有，不因此移到control文件。分片是**编码/定位方案**，不是新的优先级体系，也不是每一个对象各建一个JSON文件。

### C. 已有大型仓库

保留原来的 `Cargo.toml`、`package.json`、`tsconfig.json`、代码、资产和配置；按实际缺少的独立Requirement新增少量结构模块，必要时启用分片控制。文件系统、API、产品策略、Target映射和真实运行参数仍由各自原生/作者owner承担。不要为了进入Gift先做整个仓库的JSON镜像。

## “默认”“没写”“reset”“显式等值”“未知”的差别

1. 字段缺席：当前作者没有这项显式声明；是否取得默认取决于**已绑定Definition/descriptor**，不是JSON Schema的default自动填值。
2. `reset`：这是编辑操作，删除本层明确声明并重求Effective；不是持久`null`。
3. `Pin`到当前默认：必须保留明确控制，因为后续描述符默认变化时它不跟着漂移。
4. Profile复用：一个有版本及实义的Requirement/Definition bundle展开为贡献；没有语言授权的字符串Profile名不构成约束。
5. `Auto`：只委派仍然合法的实现选择；它不是自动获得权限，也不是`Unknown`、`false`或“让AI随便决定”。
6. 宿主默认：只有目标工具/环境实际绑定该默认的精确规则和版本，才能成为可复核结果；不能在用户源文件里冒充已知值。

文件格式不是产品权威的分类器。关于哪些作者事实应保存为Definition/Requirement JSON，哪些只有稀疏Control才落在控制文件，哪些应保持Rust/TS/数据库/运行输入/证据，及格式迁移的防回退条件，参见[开发者意图控制与存储分配](../../../20-语义与组合/作者语义/开发者意图控制与存储分配.md)。**不因JSON很长而无条件换格式，也不因现有选择是JSON就立法永久禁止其它合格SourceProfile。**

## 选择文本表示时的专业裁决

**默认继续严格JSON**，原因是数据模型和机器协议已存在、校验工具成熟，按文件可以精确修改；JSON的体积负担应先由共用语义、少量记录和按需读取解决。JSONC允许注释和尾逗号但不再是严格JSON，必须单独确定注释CST及重复键语义；不能把`.json`文件默许为JSON5。YAML别名、合并键、标量隐式类型和缩进可能增加解析复杂度，不能把YAML当统一新标准。TOML适合较浅机器配置，复杂RequirementTerm/大量嵌套记录不一定更简。HCL支持人类原生语法与JSON映射，但Gift仍需给每种构造提供固定解释；CUE的合取/默认有自己的逻辑，直接使用会改变当前hard/prefer/reset模型。它们**可以是未来明确资格的可选SourceProfile**，无需由Core先造一门新语言。

若真的开发文本前端，必须回答：精确语法与类型、引用和声明稳定身份、顺序/差异保留、重复定义拒绝、默认Pin、Profile展开、跨scope冲突、源位置到结构节点的往返映射、未知字段保全、版本迁移与前像CAS；只做漂亮打印不能签发`read/write`双向资格。

## 从数据到源码写权的一条不可逆边界

JSON作者源码可以由编辑器、Rust SDK、AI和CLI共同编辑；它们都只能提交**候选**，实际写入按当前AuthorSnapshot、owner和前像。若把JSON导出为HCL/CUE/`.gift`只读投影，不能同时让两种文件自由修改同一Definition/Control。迁出是显式完整迁移：冻结旧所有者、选择新Profile、映射所有身份/引用和原有控制、做语义对照，再切换写权；失败保留原来源可编辑。不是保存一套JSON再用漂亮文本覆盖它。

## 高并发与巨型项目的读取/性能逻辑

读取器分层：**目录清单（小）→ 来源文件（按需）→ 已锁定解释（共享）→ 控制贡献索引（派生）→ 按subject/target查询（按需）**。任务只修改一处分片时，查询只读取其已冻结需要的版本；改变Project硬约束可能影响很多模块，必须传播失效，不能因为物理文件小就假装影响只在这一个分片。跨文件合取和scope传播必须依赖真实对象身份，不依赖路径前缀。

不得为了声称性能做固定`max N file`语义上限；工程可以超过资源预算，但必须返回可理解的`RESOURCE_BUDGET_EXCEEDED`与实际工作范围。缓存可压缩或二进制编码，但对人可写源码不默认转换为不可审计的二进制。对网络传输使用无损压缩不会削减语义信息量；对生产者/消费者加字段协议仍应遵守版本兼容与拒绝未知。

## 仍未能凭设计文本关闭的能力

实际描述符的全部机器Schema、真实AuthorSnapshot原子提交、旧客户端协商机制、跨语言原生适配器、Requirement Rule生产级解码、目标画像/Target供给、运行证据与性能基准，必须按各owner实现验证。本设计只补齐**大规模结构作者源码和控制存储的明确源码合同**；附带验收脚本不具有这些未实现的产品能力。

## 反回退验收

- 结构JSON继续是直接作者源，原生源码和可选`.gift`地位不回退。
- 当前只有 ControlFile 一种持久存储；逻辑键含准确 scope/target，product-root 使用 target/rootId。旧内联仅作为满足完整前像与等价条件的迁移输入。
- 人类想简洁可用结构投影编辑，但回写原真源，不创建平行“友好配置”。
- 迁移要求控制集合**双向等价**、完整来源映射、共同前像与批准写权，不能以JSON语法通过代替。
- 不把默认补齐为数千明文控制；不把原生源码转写JSON AST；不把runtime许可/秘密写进控制文件。
- 不把不同文件/分片视为自动独立事务；独立性由语义依赖、授权与实际写入协议判断。

## 其他编码与超大规模状态的条件选择

- **严格JSON**：现行长期作者源的正常选择；通过模块边界、稀疏差异、分片和局部差异降低管理成本。JSON Schema只负责声明结构和注解，不替代真实默认求值。RFC 8785 JCS只适用于其特定可表示数据域；对Gift的BigInt、精确十进制、位级浮点身份和未知字节必须先选择合适的有类型编码，不能简单把所有number转成IEEE754后哈希。
- **人类友好配置语法**：若高频人工直接编辑已使JSON的括号/引用/嵌套难以维护，未来可针对某一完整、可封闭的Dialect采用HCL原生形式、CUE或其他Profile。真正获得双向写权前，必须验证`parse/encode`、稳定引用、注释与未知字段保全、要求合取及默认Pin的一致性；只支持只读投影时不得把投影文件再次当作者源。
- **JSON Lines/二进制表/SQLite**：只适用于有真实大量**独立**记录、流式处理或事务性随机写需求的情况，属于**新SourceProfile或数据资产类型**，不是把普通JSON在磁盘换一个后缀。需要精确事务、唯一键、快照、索引恢复、schema迁移、协作编辑与可携带导出；没有完整合同不得暗中替换`gift.control-file/1`。
- **性能是实测条件，不是随意阈值**：要在代表性的模块数量、记录分布、频繁修改、共同硬约束和同时阅读场景测量打开工程耗时、增量解析、保存冲突率、IDE虚拟化、源文件Diff、人/AI上下文开销。无失效传播的低耗时不算合格。数据量很大时可分读，但本次消费所要求的完整成员与snapshot资格必须准确。

## 外部成熟规范依据与非采用边界

- JSON Pointer RFC 6901 https://www.rfc-editor.org/rfc/rfc6901.html 及 JSON Patch RFC 6902 https://www.rfc-editor.org/rfc/rfc6902.html：定位/补丁可以复用，不能把数组序号当跨修订身份。
- JSON Merge Patch RFC 7396 https://www.rfc-editor.org/rfc/rfc7396.html：`null`具有删除语义，因此并非本控制模型的直接替代。
- JSON Canonicalization RFC 8785 https://www.rfc-editor.org/rfc/rfc8785.html：限制其适用数值域，不能静默丢精度。
- HashiCorp HCL information model https://github.com/hashicorp/hcl/blob/main/spec.md 及 native/JSON语法：可参考多种语法对应一种含义的路线，但不复制其配置求值。
- CUE语言规范 https://cuelang.org/docs/reference/spec/：其合取/默认语义适于对照约束系统，但不与Gift现行Realization Control的hard/prefer/reset等同。

## 巨型结构化源的负载与编辑边界：JSON 留作事实载体，但不要求巨型单文件

大量独立意图意味着真实信息下界；JSON 的额外代价分别来自括号/键名重复、完整解析、单文件争用、格式化差异、查找定位、review 噪声和全局读集。它们是不同约束，不应以“改成另一门语言”统一处理。作者源保持严格 JSON 时，优先按**语义单一 Owner**分模块，控制只保留显式稀疏差异，配置族以版本化 Definition/Profile 引用复用，重复 Occurrence 共享声明而不共享不应共享的 identity。读者可用流式 JSON 解码、可丢弃索引和局部片段装载；这些加速结构不得保存第二份作者真值。

使用独立 `gift.control-file/1` 时，控制文件在现有 `sourceScopes` 中发现并由自己的 `projectId/fileId` 标识，片段采用逻辑键 `(scopeRef,target?,controlRef)` 和有锁描述符版本；product-root 必须含 target/rootId。跨片段出现同键必须拒绝；分片迁移先证明内联与外置在**同一准确 SourceSnapshot、同一 Scope 图及描述符目录**下对所有已覆盖消费点求值相同，再由源 owner 共同提交并切换唯一写权；不允许两种持久源同时成为可写真源。由 Reader 派生的可重建索引保存 `fileId→contentDigest→logicalKeys`，变动时只重算相交 scope 及负依赖；索引缺失或过期时回退权威原件重建。

分片阈值不固定为某个未经测量的文件大小；针对项目规模、编辑热点、磁盘/内存预算及端到端延迟实测选择，发布时明确请求上限、内存占用上界、恶意嵌套/数字/Unicode 拒绝和有界分页。结构化原生算法仍在原生 `.ts`/`.rs` 作者区域；代码本身不是为了统一外观就必须转义进 JSON 字符串。持续的大型事务事件/观测数据仍由本来拥有它们的日志/数据库保存，不误入控制文件。
