# 结构化作者源码

<a id="unified-author-read-canonical"></a>
## 作者读取到有类型语义的唯一交接

**当前写源的准确入口。** 新项目由 `gift.project/1` 的 `sourceScopes` 发现 `gift.author-module/2`，严格读入固定字节和局部定义映射，再依据锁定的进口和 Body 语义创建 `Definition / DefinitionUse / ProductInstance / OutputRoot` 不同的名义对象。旧 `gift.author-module/1` 及 `intent-module-mixed-1` 的结构、Dialect 和样例仅属于有条件兼容读取：它们不能定义新项目的必填字段，也不能把旧 `extensions` 赋义给新 Writer。多个来源 Profile 可在同一工程被读取，但每一个互不重叠的作者区域只有一个实际写源。

读取结果至少区分 `(source-valid, linked, meaning-qualified, implementation-qualified, target-qualified)`，五项可以分别为未完成；这些状态不能合成为一个 `valid` 布尔值。结构读取未理解的 Kind 不能丢弃后继续号称“完整产品”；作者源不完整时可保存草稿，但选中根在任何必要消费者无资格时不得形成伪成功目标。读入产生的语义投影、缓存、IR、优化决策和 SourceMap 均不是新的作者可写文件。


Reader先固定 `gift.project/1` 的 SourceScopes 及发现快照，由模块自报 moduleId 派生位置映射，并读取单个作者来源的实际 Schema 版本。新源码按唯一候选 `gift.author-module/2`严格读取；`/1`历史文件仅在只读来源路径采用原始解码器，输出携带原身份、Body版本、来源和迁移需求的类型化SourceUnit，**不能**直接修改源码或把 `/1` JSON 当 `/2` 校验。再按已解析的`moduleId/export/definition`解析有类型引用，拒绝同名私有导出、错误Kind、不同模块身份或不完整锁。

跨模块的产品根遵循不同边：`requirements`消费Goal/Composite的规范性义务；`workflowUses`消费流程发生点；`policyUses`消费规范政策；`components`实际化组件；`connections`检查实例端口供需，`publicEndpoints/externalRequirements`分别规定产品对外边界及显式外部需求；`qualityUses`和`deploymentRef`独立参与目标保证。只有在这些边及领域Meaning取得相应资格后才能形成有来源的JointObligation，不得仅凭源JSON Schema通过生成完整目标。原有计算Schema保留但不在本阶段扩写。

<a id="gift138-module-profile-version-contract"></a>
## 模块Profile版本不是语言层级：精确读取和跨版本连接

`gift.project/1`、`gift.author-module/1`、`gift.author-module/2`、`gift.semantic-pattern-use/2`和`gift.binding-lock/1`分别属于**不同的协议族或修订**。`/1`、`/2`由各自`schema`或`representation`判别，既不表示抽象层，也不隐含自动升级。即使外观都为`definitions`，读取器必须按准确的族/修订分派，未知或不允许的字段与kind直接拒绝，不能吞掉字段后声称兼容。

现有设计级Schema经结构核对确认：`gift.author-module/1`的四种Kind为`intent:goal`、`semantic:pattern`、`semantic:pattern-use`、`req:composite`；当前统一候选`gift.author-module/2`的27种Kind**包含**这四种，并保留其原Body版本；`/2`的`exports`为按需公开、不是必填；`/1`与`/2`在`extensions`、`imports`规则、名称、默认公开性及定义结构上不同，且`extensions`、`imports`规则和标识符限制不同。因此`/2`在**Kind覆盖上包含旧四种**，但不是旧 `/1` 文件字节的直接兼容解码器，更不是有依据的无损身份迁移。`/1`模块允许`semantic:pattern-use`的定义体以`gift.semantic-pattern-use/2`表示，版本族不同不要求编号一致。

**确定读取合同**：冻结准确源字节和版本，调用对应ProfileReader，得到受源锁约束的Definition/Export/Import结构；由唯一Linker在不改写原文的情况下建立`SourceIdentity`、`ExportedSymbol`和类型化`QualifiedReference`。跨Profile连接必须检查身份、导出、对象角色、类型/基数、意义解释、时间/权限/Requirement语义的实际兼容；适配器缺失时保留`NeedsProfileAdapter`（或对应真实Needs），**不能**按照同名直接联接或将`/1`转存成`/2`冒充原作者决定。此条为设计合同，尚不代表生产Reader和Linker已经实现。

工程组织、种类及数量的[分层图和交叉索引](../../00-系统与原则/开发者源码分层与构造归属图.md#gift-author-source-layer-taxonomy)仅作定位，不作为第二套Schema。


<a id="gift137-typed-author-conditions"></a>
## 工作流选择、规范义务及端口引用的写源不变量

现有候选 `gift.author-module/2` 不增加任何 Definition `kind`。业务作者可以使用 `decision.evidenceOutcomes` 显式区分 `NEITHER` 与 `BOTH`；旧 `onUnknown` 仍为兼容入口，但二者不可同写。多分支须使用 `selectionPolicy`，优先规则必须逐分支显式给出且不重复；排他规则需 `exclusivityRef` 的后续资格。`state:machine.transitionArbitrationRef` 只能申请仲裁资格，不能把两个可能同时启用的转移变成确定状态；`security:policy` 的 `oblige` 必须绑定 `obligationRef`。所有字段结构由同一 [`/2` Schema](../../../schema/author/universal-author-module-2.schema.json) 拥有，解释唯一归[开发者Profile](../../20-语义与组合/作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#gift137-noncompute-decision-and-obligation)。

每个引用必须按模块、公开出口、发生位置、版本与外部锁解析。结构检测器不得把 `exclusivityRef`、`obligationRef` 或 `contractRefs` 的存在本身升格成证据；必须返回准确的 `Needs`。一个业务谓词的 `T/F/NEITHER/BOTH` 是合格证据状态；没有解释器的 `UNQUALIFIED` 属于不同阶段，不得经业务 fallback 偷渡。


<a id="gift136-author-visible-structure"></a>
## 写源结构与语义基元的边界

`gift.author-module/2`仍是**候选**。`kind`是定义类别选择，`body`中的键是固定JSON表示，而独立业务含义由对应的Meaning、Requirement、Pattern和专业合同持有；新增一个JSON字段不等于新增底层计算操作或整个行业的抽象。开发者不必填写全部27种Schema候选Definition；27种Kind属于同一语言设计；普通业务可不使用计算，但需要新算法时可以选择有型计算或有权原生源码；需要什么就声明什么，已有合格定义直接引用。不能用空字符串、任意`payload`或无消费方的标识冒充已表达业务。

- 一条条件只能有一个表达来源：遗留`conditionRef`或新的有角色绑定`conditionUse`（分支为`whenRef/whenUse`），不可同时写。多参谓词必须绑定业务角色；绑定对象和名义类型定义不能互代，未知及冲突有独立后继。
- Definition级`qualifiers`表达应用范围、主体、权威、有效时点及证据要求；它们是待取得的条件，**不是作者自签权威**。专业Body已有的限定仍需共同联合。
- `product:system.connections`指定具体组件实例和供应/需求端口；`wires`为历史有限表示，禁止与非空`connections`并行决定同一连接。

机器结构唯一Owner：[`universal-author-module-2.schema.json`](../../../schema/author/universal-author-module-2.schema.json)；规范性解释唯一Owner：[开发者通用定义Profile](../../../docs/20-语义与组合/作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#gift136-source-structure-vocabulary)。本阶段不扩充计算语义；新字段未有生产Rust Reader与Target资格，不代表Gift已能从抽象描述生成完整IDE。

## 提案作者模块与现行四Kind的严格共存

历史 `gift.author-module/1` 四种已采用 Definition 继续按本页及其各 Body 的原协议进行只读解释；新业务统一在候选 `/2` 写源，保留原Body，不要求双写。新 [开发者通用定义Profile](../../20-语义与组合/作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#developer-foundation-gift133) 的 `gift.author-module/2` **仅为设计提案**：新 `/2` 的27种候选Definition不得交给旧 `/1` Decoder假读；旧Decoder只能识别原 `/1`，四种共用Kind不代表两个模块容器结构直接兼容，也不能通过 `extensions` 字段偷偷生效。项目级Reader首先明确判定模块 Profile；没有安装合格 `/2` Decoder时必须返回 `UNSUPPORTED_AUTHOR_PROFILE` 并保留原字节、诊断及发生位置。已有项目同时含旧 `/1`与新 `/2` 时，旧源只读、单个定义不双写；导入闭包、作者区域写权和目标根必须准确追溯到实际版本及来源，任何跨版本引用只在真实适配/语义保留资格之后生效。设计级Schema验证不能代替该消费者。

## 四Kind混合作者源的正式 Reader 冻结准入（Gift122）

<a id="single-source-author-acceptance-invariants"></a>
### 作者源一份、多个表现与实际写权的冻结合同

普通Gift业务作者的默认、持久设计源采用**结构化JSON**，对过长文本通过模块分区、公共定义、引用、编辑工具和定位视图减轻负担，而不因文件长度静默转换为另一门语言。AuthorModule 是逻辑容器；SourceProfile可在明确获准的工程中读取原生源码或历史格式，但每个不重叠AuthorRegion只能有一个实际Owner/Writer。受控的GUI/AI编辑修改该Region必须经过SourceMap与CAS提交到该Owner；IR、Intent草稿、Target源码和检索表不能同时成为同一决定的第二作者真源。

一次读取必须区分四种结果：`PARSED_TYPED`（所选Profile完整合法）、`UNSUPPORTED_VERSION`（有原字节但不能假读为旧义）、`MALFORMED/AMBIGUOUS`（重复键、跨Kind碰撞、引用未锁定等）、`NEEDS_EXTERNAL_MEANING`（结构合法但领域解释不可得）。前三项由实际Reader/CST/类型Owner判定，第四项交给语义Owner；不能把后二者悄悄置零、默认false或交给目标生成器补业务解释。

每个冻结读取切面必须能回答：当前SourceRevision/内容身份、Definition-kind/version、Import/Meaning/Requirement锁、Region的写权、SourceSpan与公开诊断、保留未知字段策略、被实际接受的作者差异及其接下游的锁定版本。拒绝非法写入时原字节与旧合格视图保持不变；迁移要显式区分旧Profile/新Profile，并证明往返、身份与原义保留。结构化作者文本不能代替真实环境事实、Method供应或运行Grant。


`gift.author-module/1` JSON 的同一模块允许四类已定义 Definition：`intent:goal/1`、`semantic:pattern/1`、`semantic:pattern-use/2`、`req:composite/1`。模块复合只增加入口的可接受定义类别，不隐式升级各 Body 或向旧 `/1` 注入第五类。历史 `intent-module-1` Reader 只消费其原单意图子集；混合 Schema 验证通过不得成为旧 Reader 已实现其余 Kind 的证据。

严格 Reader 的施工判定顺序（这是必需条件，不是已存在的产品Decoder）：

1. 对原始 UTF-8 字节拒绝非法编码、重复 JSON 对象键（包含转义解码后相同的键）、非法JSON数字、资源超限与不支持的版本；保留全部 SourceSpan，失败时不能返回空 Module 假成功。
2. 锁定 Project/Module 与作者SourceProfile、SourceRevision、Dialect清单、导入内容哈希及解释版本；没有对应选定Dialect的Definition不能以其它Kind替代。
3. 先建立完整定义符号表，检查同名、封装、导出、循环依赖及被禁止的递归。之后依唯一身份解析每个局部及外部引用；外部 import 的 `import/export` 字符串本身**不能**作为存在/签名/授权证明。
4. 分别读取四种已选Body的严格Schema，再做跨Body类型/基数/角色/Variation/Meaning/Requirement 连接检查；JSON Schema的`$ref`只保证形状，不解决实际企业、法域或物理Meaning。
5. 生成一次性 `TypedAuthorTree`、准确 SourceMap/ReadSet/NegativeReadSet，明确列出所有无法解释的引用。没有类型化解释的合法作者源允许保存草稿，但必须阻止其被签发为`QualifiedPlan`。
6. 真实编辑通过本区域唯一Source owner实行CAS，并确认未知扩展字段/排序/注释等按被选择的SourceProfile定义处理；纯JSON Profile默认没有注释，不能让重打印凭空篡改已经接受的源码语义。混合文件迁移必须单独显示旧新版本、改动、兼容和回退，而非默默升级。

作者可省略已由锁定Profile合法默认的实现选择，不能省略影响业务结果的必要政策决定。`Preference`不替代`Constraint`，规范`Permit`不发行运行`Grant`，未被有权主体采纳的AI候选不进入作者真源。大型JSON仍使用分片、引用、受控编辑与只读投影管理；这些手段不改变数据语义或作者写权。

## 作者源码的四层验证与业务语义退出条件

解读历史`gift.author-module/1`时，必须在设计中区分：**字节结构**（编码、重复键、Schema与未知字段）、**工程链接**（dialect/import/export/ID/SourceScope/lock）、**语义解释**（Type/Meaning/Policy/Observation与Requirement组合）、**实现与目标资格**（Method/Target/Build/环境）。每层持有自己真实的拒绝/未决记录，不允许后层成功倒填前层未知。`intent-module-mixed-1`只覆盖当前四个意图相关kind的有限Schema；真实开放普通Type、State、Relation、UI、API、算法和Port由其锁定的Definition Dialect或原生SourceOwner处理，不是非法格式，也不因此获得未实现的Reader支持。

一个完整工程可能只有业务意图，没有计算体；也可能只写原生代码而将业务要求放在独立Module。**唯一作者源**约束的是同一个可编辑语义对象的单一写权，不要求项目只有一种文件格式。Creator通过预览确认来源、默认采用和不可让渡条件后，才提交AuthorRevision。CST/SourceMap保留未修改的用户字节，结构投影/RequirementGraph/TargetPlan都不得回写为第二份作者正文；用户显式迁移表示必须先证明被转换的已支持语义范围并保留无法转换的原字节。

## 采用设计：单一混合模块读取与版本兼容（R01）

此处所述历史`/1`样例中，`gift.author-module/1`是其逻辑模块容器；新业务Writer统一使用候选`gift.author-module/2`，且不由旧Reader隐式迁移。[mixed结构门禁](../../../schema/semantics/intent-module-mixed-1.schema.json)只验证目前声明的四种Definition组合，不扩展历史`intent-module-1`的解释范围。正式Reader依`dialect.languageId + dialect.constraint + definition.kind + body.representation`分派；按文件名、单独`kind`或关键词猜测均不合法。对不支持的Definition保留原字节与位置并报告未决；含该Definition的根不能静默忽略后宣称完整编译，独立且不依赖它的根不必加载其插件。

| body选择 | 限定的来源与语义owner | 不能被误当成 |
|---|---|---|
| `intent:goal` + `gift.intent-body/1` | [六模态及公式](../../20-语义与组合/作者语义/通用意图语言-意图源与语义组合.md#stable-intent-modality-semantics) | 普通 `req:composite`，也不能默换成计算体 |
| `semantic:pattern` + `gift.semantic-pattern/1` | [公共模式](../../20-语义与组合/组合/抽象与开放定义.md#stable-pattern-abstraction-operations) | 一份已实例化Method |
| `semantic:pattern-use` + `gift.semantic-pattern-use/2` | [五基数展开](../../20-语义与组合/组合/抽象与开放定义.md#stable-pattern-abstraction-operations) | 老 `/1` 的单对象形状 |
| `req:composite` + `gift.requirement-structure/1` | 本文件后文 `RequirementTerm` 真实codec | 高层Goal的隐式副本 |

### 精确读取合同与阶段边界

1. `capture(bytes, selectedProfile, moduleRevision, authorAcceptance)`: 严格 UTF-8/JSON，拒绝重复键、非法数字、未知**已激活**键、格式/预算损坏；固定真实字节及SourceSpan。语法有效不意味着实例或外部事实可信。当前原包的 `semantic_digest` 局部排序编码**不得**升级为跨语言官方内容hash：使用现有统一Canonical Forms的锁定算法；具体试验可保留原局部hash标签，升级应显式迁移。
2. `decode(module, dialectSelection)`: 验证外壳、语言ID和兼容约束；对每个定义验证 `kind↔representation` 一致。已知但不在选择范围内的Definition保留而不消费；未知语义参与根/目标时返回 `UnsupportedDialectOrRepresentation`。禁止把`semantic-pattern-use/1`作为`/2`宽松解析。
3. `resolve(selection, imports, exports, locks)`: 当前 `/2` 的 `local:Name` 只在模块有效作用域内引用；跨模块 `alias:PublicName` 依托实际 `imports` 和目标 `exports` 依据已固定导入/导出/权限查找，名称同音不构成身份。必须核全部真实语义锁及签名；未被选的库可以懒加载；选中却缺失的库必须Need，不能经网络静默下载。
4. `typecheck(definition, frozenContext)`: 检查角色/真实对象身份、名义类型、单位、量化词法范围、时间/Profile、恰当谓词参数。源的 `typeRefinementRef`、`identityEvidenceRef`等是**请求引用**，由可信受限读取者决定是否可用，不能作为作者签发的真值。
5. `accept(sourceDelta, expectedRevision, actorCapability)`: 实际作者接受需要目标所有者的权限、CAS与来源。编辑器/AI预览是候选，不修改原件；保存到唯一Definition或原有Control/Provider/Native owner，不写派生IR。对原作者源的格式化是显式动作，不影响普通只读parse。

旧`intent-module-1`和`pattern-use/1`在各自旧Profile内仍有效；混合模块目前只是设计Schema，生产Reader尚未实现，应报告`DESIGN_ONLY`。新增Kind或改变Body含义必须通过显式codec/Profile版本及迁移证据进入，不得把新版内容喂给旧Reader并假定兼容。解码须区分字段省略、显式`null`、类型错误、空集合与观察未知；实时Grant、动态事实和目标Method选择不得回写到作者Goal。

### 开发者真正要写的东西与控制权限

普通作者仅接受**不同于复用定义**的主体与角色绑定、公开结果/禁止/规范/偏好、边界及必要的法源和观察选择；表达式、算法、存储事务、并发锁和目标源码由领域作者/合格Method/目标实现承担。Meaning作者可声明新谓词但不得凭URI赋予真实事实；Requirement作者拥有规则和兼容；Method供应者只能声明并验证实现、不能改业务意图；Policy拥有者定义规范许可；运行Grant和外部效果只有相应有权宿主发放与观察；AI仅能提议。`gift.control-file/1`用于明确的实现偏好/Pin、不是另一套业务定义；必要的机器锁由原Binding owner持久化。

**编译资格次序**：读取、版本、引用 → 名义身份、类型、作用域 → Meaning 与观察来源 → 联合义务 → Method 与 Target → 授权与真实效果 → Claim。每个阶段签发自身已检查的范围；前序缺项保留可独立取得的下游结果，但完整交付不能签 PASS。并发独立缺项返回附 SourceSpan、Owner、后继的有型 Needs 集合，不能压成单个 `ok`。二次修改须由有权写入者更新作者源，捕获前后 ReadSet、负依赖和来源位置，所有受影响派生资格重新检查。

## 新增一等意图 Dialect 的单源接合

历史 `/1` Reader保留其 `req:composite` 原解释；所有新结构作者只写 `/2`。本篇继续拥有 Requirement 的原有有限 Term；Gift112 新选设计 `kind="intent:goal"`、`body.representation="gift.intent-body/1"` 由[通用意图语言 owner](../../20-语义与组合/作者语义/通用意图语言-意图源与语义组合.md)和[独立结构示例](../../../schema/semantics/intent-body-1.schema.json)拥有。它是**并列的定义类别**，不是用 `use/require` 重复复制作者的目标，也不是要求转换为一般计算函数。当前附带 `intent-module-1.schema.json` 只演示 Intent-only Module 校验；正式混合 dialect/导入仍须原通用 Module Decoder 接合后发布。

**入口与优先级**：结构 JSON 本身是合法的真实作者源码，而非待转换为 `.gift` 的二级形式。跨 JSON、Rust SDK、原生源码与可选文本 Profile 的设计归属于[统一作者源码与多表示协议](工程源/统一源码工程与多表示作者协议.md)；本篇只拥有 Requirement/Composite 结构 dialect 的具体 fields、Values、Terms 和语义规则。

<a id="结构化意图与block源码"></a>

本章拥有新产品结构作者面的**Requirement/意图组合dialect**：它把已有Definition、RequirementTerm、主体关系、类型化参数与组合放入当前共享的 `gift.author-module/2` 外壳。**它不拥有整个模块内所有Definition body**；计算、对象、状态/关系/流等按[多dialect作者模块](工程源/工程清单模块与绑定锁协议.md#author-module-dialect-composition)由各自真实body合同承担。本章字段表给出本dialect的逻辑结构及严格JSON profile的精确codec；Block是封装角色，意图是被接受的含义，SourceProfile是物理作者表示，四者不同。已有`.gift`计算规则、`gift.semantic-body/1`结构计算体和原生作者区域保留各自明确角色，不成为Requirement入口的依赖。

这里的`gift.requirement-structure/1`是**本包已定案、尚未产品发布的Requirement dialect结构体编码设计**；结构由 `schema/requirements/requirement-structure-1.schema.json` 固定，含义由本篇维护，必须绑定准确内容。生产读取器与真实引用解释尚未因本次定案取得资格。使用一个新格式名称不免除字段、语义、迁移和符合性责任。正文给出完整有限读取合同，其他领域的主体/关系必须有实际定义后才可接入；未知格式只保全，不执行。

<a id="structural-author-primary"></a>

## 作者成果和最小交互

产品作者操作公开的意图定义、外部管脚、实参、关系与必要约束。定义内部的循环、缓存、对象和恢复算法由复用定义或真实供给承担；需要新含义时定义新Block，需要新实现时交给相应实现责任，不要求每个应用作者抄一份。一个标签可以是准确能力的名字，不是无含义口号，也不意味着该能力已实现。

完整持久模块具有身份、导入和导出，但日常“门槛从3改5”“把过期政策改成重显再确认”可以只提交原有`editRef/value`或准确文本差异。工具解析标签、代管身份、保留共享关系并回写同一源。没有GUI也能操作管脚；读取层级与机器分析范围不同。不得把巨型JSON全量灌进每次提示，再声称使用者只改一个值。

使用者可不展开复用定义；维护者可打开一级或更深内部结构。增加一个普通业务定义不改核心枚举，也不强制建包、部署进程或独立长期节点。没有持久消费者的临时发生位置只用局部定位。层级封装可继续组合，没有固定层数；函数递归、静态需求展开和状态反馈分别解释。

<a id="structural-author-vocabulary"></a>
### 结构作者源的真实学习负担：组合操作符、定义形态和schema分开计量

“8个Term标签”只说明组合代数，不等于整个JSON作者格式只有8个关键词。直接手写`gift.requirement-structure/1`时按以下层次理解，Workbench/AI/CLI则可隐藏大部分机械字段：

| 类别 | 当前有限集合 | 普通应用作者是否常用 |
|---|---|---|
| **Definition形态** | `req:composite / req:rule / req:subject / req:value-type / req:enum-value` | 通常只新建/修改`req:composite`；后四类多由领域/定义库维护者提供 |
| **RequirementTerm组合操作符** | `use / require / prefer / all / any / when / forEach / exists` | `use/require/prefer`最常用；其余只在组合/有限条件与量化需要时出现 |
| **Type形态** | `ref / list / builtin`；当前builtin仅`Bool / Int / Text` | 多由定义参数和字段表单生成 |
| **Value形态** | `parameter / subject / bound / enum / literal / typed / list` | 普通作者多直接选参数/枚举/字面值/类型化值；subject/bound主要出现在组合和量化 |
| **Condition形态** | `value / equal / not / all / any` | 只有静态条件组合出现时使用 |
| **DefinitionRef定位** | 当前 `/2` 通用 Ref 使用 `local:Name` 或 `alias:PublicName`；复用的版本化 Body 保留其自身对象式 DefinitionRef | 工具负责解析实际identity；显示名不代替ref |
| **参数role** | `subject / value` | 决定type解释和default资格；两者不能按同名互换 |
| **模块外壳** | 当前 `/2` 必需 `schema/moduleId/definitions`；按需 `namespace/dialects/imports/exports/annotations` | 工具通常维护；直接源码作者需要知道 |
| **Composite body** | `parameters / subjects / exposes / terms`以及各Term自己的`arguments/fields/...` | 工具通常按Definition合同生成/验证 |

这些schema键与判别标签都是当前未发布结构编码的**格式词汇**，不是一门新的文本语言保留字。业务名称、Definition/Profile/Rule名字、字段名和控制descriptor身份属于开放定义空间，不计作核心词表。

Money、Workflow、Simulation、Protocol、Storage 等新增领域能力，默认定义自身 Definition/Profile/Rule/descriptor，不扩充 RequirementTerm。只有证明现有 `use/require/prefer/all/any/when/forEach/exists` 加合格领域 Meaning 仍无法表达一项独立且可观察的组合语义时，才提出新的 Term；须给出反例、解释、迁移与所有现有消费者的兼容处理。

因此词汇成本按角色报告：普通Workbench/AI作者可为0文本关键词；结构源高级作者承担上述schema；定义库维护者还承担Rule/Subject/Value catalog；它们不能混成一个“Gift有多少关键词”的单一数字。

<a id="author-surface-projection"></a>
### 最终作者面：一份真源的渐进展开，而不是要求人手写整棵JSON

本章此处历史 `/1` 文档涉及持久作者合同，但当前 Writer 已收敛为 `/2`；无论哪个来源，均不等于最终使用者必须逐字段编辑的界面。人、AI、CLI或未来Workbench可以把同一修订按任务投影为“含义与公开边界、关系与要求、行为、实现选择、目标/配置、生成对应、证据与历史”等阅读组；这些组只组织已有Definition、Requirement、Control、Binding、资产和Evidence，不增加第二份可写模型。默认视图只显示本次独特决定和真实缺项，高级视图能够沿[信息完整性](../../20-语义与组合/作者语义/作者信息完整性与控制入口.md#author-information-completeness)和[有效控制投影](../../20-语义与组合/组合/稀疏控制与目标限定.md#effective-control-projection)下钻到所有相交细节及其来源。

因此普通产品作者不因编译器内部需要精确Int、Bool、Text、List、函数、控制流、所有权或目标表示，就被要求把这些机制逐项重写进产品模块。一个领域定义已拥有这些细节时只引用Definition并写差异；原生源已准确拥有独特算法时保留原生源；需要中立计算主体时才进入相应计算表示。反过来，隐藏低层字段不能丢掉控制能力：数值范围/舍入/溢出、编码、顺序、资源寿命、线程/时序、布局/ABI、构建和目标专有差异仍须由共同语义、稀疏控制、原生拥有者或明确Unknown承担，不能只因为默认界面没显示就被后端自由改义。

作者结构也不建立不断增长的“容器kind”或业务kind目录。Queue/Stack/Map之类只有在现有Definition或领域合同确实给出稳定可观察含义时才作为可复用封装；实际HashMap、VecDeque、SQL索引、消息队列等由供给与目标选择。公式、约束、决策规则、状态/关系/流、工作流、求解和仿真等已有领域表达能承担行为时优先复用；“写一段自定义Rust/TS”不是结构作者面缺少控件时的默认补洞方式。只有真正独特算法或必须保留的原生专有观察才下钻到程序主体。

编辑器可以把紧凑投影、表格、图、属性面板或自然语言差异降低回本章已有结构编辑与原生资产编辑；接受后只修改真实owner。派生图、effective view和生成源码没有独立写权。无法唯一回写时显示多个真实owner或保持只读/待决，不按最近文本位置、字段同名或“看起来像这个Block”猜写。

<a id="author-decision-persistence"></a>
### 开发设定怎样持久化：按真实owner分流，不把全部东西塞进作者JSON

[完整开发设定面](../../20-语义与组合/作者语义/开发者决策模型与设定面.md#developer-decision-surface)是统一**操作与查看**入口，不是统一**存储**格式。接受一次开发决定后，只有它的真实owner发生变化：

| 决定 | 正确持久位置 | 不应写入 |
|---|---|---|
| 业务/领域Meaning、主体、关系、Requirement、Profile使用 | 当前结构作者Definition/terms/parameters，或明确采用的原生作者源 | binding lock、Workbench settings、运行日志 |
| 实现/目标精细Control | 独立 `gift.control-file/1` 当前稀疏作者记录；旧内联只作有条件迁移输入 | 结构Definition里复制一份同义实现字段；直接手改Binding lock |
| 自动选择的Provider/Algorithm/Method/版本 | machine binding lock / RealizationPlan及其来源 | 产品作者Definition；除非作者显式Pin形成Control |
| Cargo/tsconfig/CMake/platform manifest等原生专有配置 | 对应原生配置owner/managed region | 为“统一”抄进一个工程properties表 |
| env schema、SecretRef、部署policy | 相应配置/部署作者owner；secret真实值由Provider持有 | 普通作者JSON、binding lock、log、AI transcript |
| 每次run/deploy的参数、当前Grant、动态endpoint/credential | Runtime/Provider binding或Operation输入 | 产品Meaning；除非用户明确把一个稳定默认提升成作者决定 |
| Theme、keybinding、Graph layout、filter | Workbench/user/workspace presentation state | Engineering semantic source/hash |
| Applied/Observed/Evidence | Artifact/Operation/Evidence owner | 任何可写“effective config”副本 |

因此一个“All Decisions”表格可能同时显示`Money.scale`、`implementation.provider`、`Cargo target-feature`、`DATABASE_URL SecretRef`和`Graph layout`，但编辑它们会落到五个不同owner。**统一体验不意味着统一文件。**

### Profile、默认与显式差异的保存规则

语义Profile或工程Policy Profile是可版本化Definition/Requirement bundle的引用；使用点保存“使用哪个精确Profile + 自己的差异”，不把Profile所有展开字段机械复制进模块。Profile升级只有在该消费者接受新revision后影响它；显式固定值继续胜任自己的硬要求并可能与新版Profile冲突。

Definition内部公开default仍按[闭合默认](#closed-parameter-defaults)解释；实现侧默认由Control descriptor/target/native tool的真实owner解释。两类default不能互相借名。用户把某个当前默认值“固定”时，要保存来源改变这一事实，而不仅比较当前数值是否相等；否则未来升级会误把Pin当成继续继承。

### 决定的稳定身份

持久化决定引用真实`module/definition/use/occurrence/target`或原生文件区域身份；UI行号、JSON数组序号、TreeItem id、Graph node id都不是持久控制定位。没有稳定occurrence映射时，不允许为了保存一个局部设置发明“第7个调用”的长期身份；可以提升为私有Definition、保持候选临时控制，或返回该粒度当前不可长期固定。

<a id="author-module-logical-container"></a>

## AuthorModule 是逻辑语义容器，不是 JSON 本体

当前`gift.author-module/2`定义模块身份、按需的dialect、definitions/imports/exports与解释要求；历史`/1`另由兼容Reader解释；它的**语义身份独立于具体AuthorSourceProfile**。严格JSON可以直接承载这一逻辑容器，结构编辑器也可以通过该codec读写；但其他合格Profile可以产生同一个AuthorModule/SemanticModel，而无需先打印JSON再重新解析。

本章后续字段表继续定义 Requirement/意图 dialect 的逻辑结构与JSON codec细节。凡只属于JSON编码的重复键、数字范围、对象字段顺序等限制只约束JSON profile；Requirement、Type、Value、Rule、默认/硬要求等语义继续约束所有能够表达本dialect的Profile。新增Profile必须证明相同语义、未知内容保全、SourceMap和往返编辑资格，不能以表面更短为由放宽合同。

## 工程级机器JSON与真正作者源的关系

`gift.project.json`继续使用`gift.project/1`，拥有项目身份、来源发现范围和输出要求；`gift.lock.json`继续使用`gift.binding-lock/1`，记录实际选择的解释、库和方法。Project 是作者决定，锁是 Resolver 派生；两者分别使用有型工程配置/锁 codec，不分别保存“意图全集”和“实现全集”，也不要求普通作者内容采用同一JSON表示。

结构模块中的`definitions`保存真正作者内容。数据、图像、原生源、工具锁和秘密各按原资产角色处理，不强制全部转成JSON。清单不是授权，锁不是安装证明，也不保证未知宿主已封闭。普通正文/参数变更不重写无关锁；解析要求、实际选择或契约变了才重核相交绑定。

冻结的工作台结构范本只是一组固定作者模块、派生目录、工程清单与锁文件的校准实例，用来检查结构模块、导入、复合Requirement和多根关系能否被同一读取链保存。它的模块数量、`Studio`根、目标平台、字段目录和空`targets`都不是当前作者格式的默认值或标准产品定义；现行结构合同由本页拥有，生成任何真实结果仍须取得该工程自己的 Target、方法与 Provider。

<a id="structural-envelope"></a>

## 复用现有模块外壳

当前 `/2` 模块根只需 schema/moduleId/definitions，namespace/dialects/imports/exports/annotations 按需；具体字段由[工程清单合同](工程源/工程清单模块与绑定锁协议.md)维护。Definition/import/export 的 JSON 符号段允许连字符，不改变计算局部变量、原生路径或URI。历史 `/1` 的必填项、extensions 和旧 exports 只在其只读 Reader 中解释。重复 JSON 键、未知字段、非法字符串与超出预算分别诊断；对象键次序不表示运行次序，需要顺序的结构由自己的数组合同承担。

`dialects.req`要求语言身份`gift.requirement-structure`和精确草案约束`1`；可重建快照还需锁定实际合同字节，不能仅凭`/1`标签区分两个同名草案。模块`kind`以`req:`前缀识别本合同。前缀不按业务名自增；新工作台、图工具或编译器通常只是新的`req:composite`定义。

### req:composite 的body

| 字段 | 必需性与精确含义 |
|---|---|
| `parameters` | 必需对象。键为定义内稳定参数ID；每项有`role`（`subject`或`value`）和`type`。value参数可显式声明`default`，规则见下节；subject参数没有默认。参数名变化需保持或明确迁移身份 |
| `subjects` | 可选对象，省略为空。每项有`type`；只声明本定义引入的逻辑主体，不分配运行对象 |
| `exposes` | 可选对象，省略为空。公开边界名映射到本定义subject或subject参数的准确引用及角色路径；只暴露逻辑主体，不复制运行接口或自动导出私有实现 |
| `terms` | 必需数组，可为空。存需求发生位置和来源顺序；合取不因数组顺序改变含义，运行顺序不能由它推导 |

`role:subject`的类型必须是已解析SubjectSchema；`role:value`为明确值类型。`type`是恰一形式：`{"ref": DefinitionRef}`、`{"list": Type}`或`{"builtin":"Bool"|"Int"|"Text"}`。builtin只引用本次准确基础环境中的这三个值类型，不创建同名类型、不接受其他自由字符串；它们不适用于subject角色。ref既可表示SubjectSchema，也可表示已声明名义值类型；有限列表可以包含已明确的值或主体引用，不从名字猜成流。此版本化 Requirement Body 的 `DefinitionRef` 沿自己的对象联合：本模块 `definitionId`，或跨模块 `import/export`，对应符号允许 `[A-Za-z_][A-Za-z0-9_-]*`，只访问公开出口。它不与 `/2` 通用字符串 Ref 混读；本文 Body 示例使用对象式跨模块引用。底层规则可有更丰富类型，但只有已发布对应结构时才进入本编码。

全部外部参数已显式绑定或按下节合法默认完成的导出定义都可以被选择为工程根。带参数的复合定义可继续作为库/模板定义复用；选择为根仍有未绑定必需参数时给出准确缺项，不自动用零/null。根内部声明的逻辑主体只建立语义身份与关系，不构造运行对象；具体主体名字、数量和实现实体完全由该 Definition 及所选供给决定。

<a id="closed-parameter-defaults"></a>
### 明确默认值：省机械重复，不改变硬要求

`parameters[id].default`是可选的Value，只允许闭合literal、已绑定enum、下述闭合`typed`值及其有限嵌套列表。它的类型必须与value参数相符；空列表由参数类型提供预期。`typed`默认必须由固定Type的纯canonical codec在预算内完全解码，不得读取环境、时间、网络或运行Provider。禁止引用parameter/subject/bound、调用或未执行程序结果，也不允许为subject参数提供默认。这一有限选择避免字段次序、默认循环和两个未给主体意外变成同一实例；需要依赖别的参数计算的选择，可由现有复合定义和显式实参表达，不悄悄扩大本字段。

ARG0先收集参数并检查所有默认的结构、引用、类型；ARG1在**定义自己的固定导入环境**解析闭合值；ARG2核显式实参的已知键与类型；ARG3对仅缺少的有默认值参数填入原值；ARG4对剩余缺参返回准确Needs；ARG5保留显式/默认的来源并实例化所有硬条件。坏默认即使此调用显式传值也不是合法定义；未给null不能成为触发默认的另一种写法。lists整体替换，不按位置拼接或隐式深合并。

默认是省略语义，不是候选优化偏好：默认与同域硬要求相冲突时报告冲突，不擅自改成另一个合格值；需要让编译器选择时显式使用已定义的exists/any。prefer仍只比较硬合格实现。定义升级后默认改变，只在真实接受新定义的使用点生效；锁定旧定义、显式固定旧值与继承新默认分别处理。

作者保存仍省略未写出的值；分析投影显示其解析值和来源，不把默认机械回填为长期作者文本。把省略改为显式同值，不能一律返回NoChange：此刻行为可等价，但以后默认升级的作者选择不同。结构、绑定、默认类型和值分别进入相交键，公开参数名或值域变化仍检查消费者。

<a id="logical-public-boundary"></a>
### 公开逻辑边界与目标入口

`body.exposes`可为空或省略；键为非空、无控制字符的公开边界名。值只允许当前定义的`subject`或role为subject的`parameter`及其已定义path；不能用bound、literal、enum，不能伸入另一个use的私有subjects。所有键准确匹配，不从显示name或对象枚举第一项选入口。

它回答“本定义哪一个逻辑对象是公开承诺”，不回答目标函数签名、服务端口或运行时权限。模块`exports`仍只导出DefinitionRef；目标画像再把公开主体与已有Callable/入口合同相接。两个导出槽指同一主体不创建两份状态；不同主体即使类型相同也不会自动连接。

`use`不自动向父边界转导子定义的全部exposes。父级要暴露一项能力，可在本级声明主体，作为subject参数传入子定义，再明确暴露本级引用；这只是同一逻辑对象，不生成中间转发层。无法外传的私有主体必须通过有定义的边界编辑变成参数，而不是读取私有ID绕过封装。

没有exposes的旧式有限源仍合法。供给/画像已有准确且唯一的根角色映射时可以继续消费；多个同型主体且无此映射时，返回具体边界缺项，不能挑第一个或把全部主体自动导出。缺少某个目标映射不阻止保存完整规格或分发可复用定义。

公开边界名变化影响它的真实消费者和目标选择，按原引用与映射处理；不维护文档历史别名服务。冻结的多消费边界范本只校准同一 Meaning 被不同消费者组合时的结构关系。默认与 exposes 是当前未发布编码的有限补全，读入时仍需准确内容和支持协商；只认旧字段的实现必须拒绝未知能力，不按共同`/1`标签静默忽略。

### 条款形状与静态组合

| 条款 | 字段及含义 |
|---|---|
| 实例化 | 恰含`use: DefinitionRef`和`arguments: {parameterId: Value}`；引用一个实际复合定义；不接受未知实参，全部无默认形参必须传入，有默认形参可省略；保持调用出现身份 |
| 硬要求 | 恰含`require: DefinitionRef`和`fields: {fieldName: Value}`；定义必须是允许硬要求的已知Rule，字段按该Rule检查 |
| 偏好 | 恰含`prefer: DefinitionRef`和`fields: {fieldName: Value}`；定义必须是偏好Rule，不经此入口改低硬要求 |
| 同时满足 | 恰含`all: [Term,...]`；在同一外层条件下合取全部子项，空数组为无附加义务 |
| 可选方案 | 恰含`any: [Term,...]`；至少有一个完整子项在其余共同约束下成立；空数组为不可满足，不是空产品 |
| 静态条件 | 恰含`when: {condition: Condition, then: [Term,...], else?: [Term,...]}`；else省略等于空合取，条件按下节固定输入解释 |
| 全体成员 | 恰含`forEach: {bind: id, in: Value, body: [Term,...], itemType?: Type}`；对准确有限列表的每个出现，在其词法作用域内合取body |
| 存在选择 | 恰含`exists: {bind: id, in: Value, body: [Term,...], itemType?: Type}`；在准确有限列表中至少有一个成员使完整body与外部共同要求成立 |

这些键是JSON判别标签，不是新文本关键字、公共工具或独立IR。同一条款只能出现一种形状；除各表声明的可选字段外不接受其他键。`use`只实例化需求，不启动活动或函数。terms、all、then、else和body中的数组均表示合取，不以顺序推导运行先后；来源次序继续保留。需要先后、激活或持续时间时，引用相应计算/事件/流领域的准确规则。

all/any/when/forEach/exists直接映射到原[RequirementTerm](../../20-语义与组合/组合/跨软件需求合同.md#cross-software-intent-contract)的All、Any、When、ForEach、Exists，不增设一种并行语义。表中的量化与条件只覆盖**有限、固定设计输入**，不会因为字段已可写就获得任意运行谓词、无限域或动态发现集合的支持。已有逻辑Rule可继续使用其准确合同；其边界不被有限编码偷偷改义。

### Value的有限精确联合

| 形式 | 含义 |
|---|---|
| `{"parameter":"id"}`，可带`path:[role,...]` | 引用本定义参数。只有主体参数可走角色路径；不能把值参数路径当作宿主属性读取 |
| `{"subject":"id"}`，可带`path:[role,...]` | 引用当前定义创建的逻辑主体及其角色；每段由准确SubjectSchema定义 |
| `{"bound":"id"}`，可带`path:[role,...]` | 引用词法上可见的forEach/exists绑定；只有其元素类型为主体时允许角色路径，不能越出其body |
| `{"enum":{"import":"a","export":"E"}}` | 解析名义枚举值；同名字符串不自动成为此值。本地枚举可用`definitionId`引用 |
| `{"literal": value}` | 本有限编码用于规则明确接收的JSON布尔、标量文本及精确整数词元。整数须按十进制无损解码，不先转宿主浮点；底层读取预算限制词元长度，不改变原数值含义 |
| `{"typed":{"type":Type,"value":jsonValue}}` | 携带一个由精确Type拥有的canonical value codec解释的闭合值；适用于ExactDecimal、Quantity、Duration、URI、坐标、名义record/variant等不应升级成Requirement核心关键字的值。`type`必须与当前位置预期类型相容；`value`只是该codec的有界canonical JSON载荷，不按字段名由Requirement层猜语义 |
| `[Value,...]` | 有限值列表。对应字段声明为集合时按其名义相等去重但保留来源；声明为序列时保持次序和重数 |

### 类型拥有的canonical value codec

`typed`不是任意JSON逃生口。被引用Type或其dialect必须解析到一个版本化value codec合同；该合同随Type/Definition/锁一起固定，至少声明：接受的JSON shape与canonical form、精确解码后的语义值、编码/规范化、纯总相等是否可用、尺寸/深度预算、错误位置、向后读取/迁移和客户端editor schema（若有）。

codec的decode/encode必须纯、确定、无I/O、无当前环境读取、无权限取得和无运行效果；否则它不是作者值codec，而应转到相应Runtime/Provider流程。canonical encode必须满足`decode(encode(v)) = v`的该Type语义等价，且同一语义值只有一个canonical输出；原始非canonical输入若被接受，保存/格式化是否重写必须是显式作者动作，不能在只读parse中改字节。

一个精确Type在一个`gift.requirement-structure`解释修订中**至多有一个canonical author-value codec**。`typed.type`经DefinitionRef/import/export与锁解析到精确Type revision，再由该Type的作者值合同唯一取得codec；作者不再填`codec:"foo"`形成第二个选择点。一个Type若确有两种合法作者字面形式，应由同一codec接受并规范化到一个canonical form，或发布两个语义不同的Type/Profile，而不是让保存结果依当前UI下拉框。

**author-value codec与wire/storage/native serialization严格分开。** 作者codec只负责持久作者值的无损、稳定表示；HTTP JSON、Protobuf、SQL column、ABI struct、GPU buffer等分别由Interface/Persistence/Target实现决定。一个Money作者值可canonical保存为十进制文本结构，但目标存储仍可选fixed-point i128；这不是codec冲突。任何wire/storage选择都不能反向改写作者typed payload的Meaning。

没有canonical author codec的丰富Type仍可以被作者Definition引用、作为接口/主体Type存在，但不能在本结构dialect中构造具体`typed`值或closed default；需要值时返回准确Need/Unsupported，不能临时选某个wire serializer冒充作者codec。

Requirement通用层只知道`type + typed payload`，不硬编码Money/Decimal/Coordinate字段。领域可以发布标准codec，例如ExactDecimal用无损十进制表示、Quantity组合magnitude与单位identity、Duration固定单位和范围、URI固定解析/规范化规则。这些标准Definition可以带高质量表单/文本编辑投影，但其UI hint不进入语义hash。

未知Type、codec缺失、codec revision不匹配、payload非法或预算耗尽分别返回准确Unsupported/diagnostic；若原文件需要保全则保全原JSON字节/结构，但不得把未解码typed value当Text继续编译。codec升级改变语义、canonical form或相等规则时使相交默认、Condition、Binding和Evidence失效，并按Definition/format兼容流程迁移。

通用`Condition.equal`只有在Type公开了纯总相等ValueOps时才比较typed值；没有相等见证就返回该条件表达不受支持，不按canonical JSON字节相等代替领域相等。通用path也不能伸进opaque typed payload；需要字段/成员关系时使用该Type正式公开的Definition/Rule/领域投影。

除path可省略为空之外没有按字段名推导的隐式值。`null`不是通用缺省。正整数priority是排序层次，不是性能分数或隐含32位数；值必须大于零，读取预算另行判断。显式path（包括空数组）只允许用于主体，不能把值参数带空path当成另一种合法写法。布尔与整数不得由宿主的`True == 1`之类行为混合；UTF-8解码、代理字符和深度/总量预算沿原输入规则。

<a id="finite-requirement-composition"></a>
### 条件、量化和选择的精确边界

**Condition的有限联合。** 恰一形态为`{"value":Value}`、`{"equal":[Value,Value]}`、`{"not":Condition}`、`{"all":[Condition,...]}`、`{"any":[Condition,...]}`。value必须为Bool；equal恰有两个同型、具有本合同纯总相等规则的值；基础支持Bool、精确Int、标量序列Text、同名义类型枚举及这些值的有限列表，`typed`值只有其固定Type公开纯总相等ValueOps时才加入；不比较逻辑主体、函数、资源或宿主属性。不同名义类型、Bool与Int之间不强转。equal的列表递归比较次序和重数，文本不隐式规范化。Condition与Term按字段位置解码，不把condition里的any解释成实现选择。

静态条件只读取本次已绑定的值参数、外层量化值和字面值。它不能读未执行程序的输出、当前环境变量、在线权限或工作区扫描结果。需要外部事实时先按既有取得流程固定准确内容，再形成后继输入；没有数据不等于false。库参数未绑定时保存有条件结构；选择为生成根却仍缺少必需的外部设计实参时返回准确Needs。exists引入而尚未选定的有限见证不是外部缺参：先保留带作用域的符号条件，再由联合搜索逐个代入合法成员，不为进入求解而要求作者预填见证；确定分支以前也不跳过其义务。它不是允许作者声明“已授权=true”从而取得执行权。

条件为false只意味着不施加then中的额外要求，**不意味着禁止该功能或资源存在**。需要禁止联网、云同步或某种实现时，要有相应明确禁止规则。运行时每次输入都要判断的条件，应使用有定义的运行领域规则及实现，不把构建时取样代替运行守卫。Condition all/any的空数组分别为true/false；已知短路结果可用于纯静态判断，但仍先完成结构与类型检查，且输入依赖不能少记。

**域与绑定。** in必须是可准确取得的有限列表。元素类型先从已类型化的列表参数/引用取得；直接非空列表必须同型；直接空列表没有预期元素类型时必须给itemType。存在itemType时须与已知元素类型一致，不是覆盖或强转。有限列表可以装已有逻辑主体引用，元素不会因此成为运行期对象。未知或不完整枚举、运行流、未封存的Provider结果不参与本量化的穷尽结论；它们继续有自己的域、时间和覆盖合同。

bind是在该量化body中可见的非空局部标识，不对外导出；不得与仍活动的外层量化bind重名，兄弟作用域可复用。in在引入本bind前解释，所以不能自引用；普通参数与subject使用不同引用形式，不发生按同名捕获。嵌套量化可以使用外层bound的值。use取得已求出的准确实参后进入被引用定义自己的作用域，调用方局部ID不能越界进入被调定义。复制或改名由已有编辑映射维护，不为每个条款要求永久全局ID。

forEach空域为true，exists空域为false；非空exists的空body可由任一成员见证。两个情况都不凭空提供正常功能、合法输入或进展。一项任务确实允许空库时可以成功；要求正常工作的产品仍须有对应义务，不以空域和总失败消除它们。域的成员次序不规定程序调度，但出现次序和重数保留：forEach的两个相同值若各实例化一个带私有subject的use，会得到两个私有主体；显式传入的同一个主体仍共享。可以共享纯分析，不可按字节去重改实例数。

**检查未采用分支。** 所有分支都需有合法结构、局部作用域、类型、Rule身份及字段；false分支不能藏错字段。合格实现的取得只对当前有效义务及已选择路线进行，静态false分支缺目标方法不阻塞独立根。引用的定义含义本身缺失，与已知含义缺实现不同：前者保留语义缺项，不能用条件屏蔽后宣布该模块全部可解释。

**量词次序。** `forEach x … exists y …`允许每个外层设计成员选择自己的y；`exists y … forEach x …`要求一个共同y。它们不得交换。见证仅依赖其词法外层已固定的设计值，选择冻结在原RealizationPlan/Binding及来源对应中，不新增人工锁表。求解分支的选择不是产品运行输入，不允许编译器每遇到未来输入就换一份不相容程序。

**偏好范围。** prefer可在根、use、all及固定输入决定的when/forEach中组合。但any/exists及其传递use的body在本有限编码中只允许硬条款，不允许prefer；检查器先计算传递的偏好出现，不让封装绕过限制。否则实现者可能选中“不带昂贵目标”的分支来删除自己的评价标准。把共同偏好放在选择之外，在同一主体上比较整套合格候选。确需不同候选采用不同评价对象时，须有明确、可比较的共同评价规则；本编码不以暗中跳过来实现。此限制不禁止作者明确选择的静态配置决定是否请求优化。

### 有界实例化、未决与正常输出

读取先检查外壳、形参、类型和全部局部引用；再按固定输入求Condition与有限域，将嵌套组合映射到原RequirementTerm和独立偏好。实例化使用有作用域的环境，缓存键包含根/定义、实际实参、默认来源、公开边界、共享主体身份、外层绑定与规则修订；同一结构在x=A和x=B下不是相同结果。私有主体按真实use出现和量化出现区分，来源合并不得把独立接受关系吞掉。

不先将公式展开为全量析取范式或所有候选的笛卡尔积。保留共享公式与作用域；all传播共同约束，any/exists只在有必要时枚举有限分支，预算记录真实展开、空间和方法成本。all中已证明矛盾的子项可解释整体冲突；any只有至少一个完整分支满足全部共同前提才有可行见证，只有全部有限分支均被可靠排除才可说该范围不满足。未读、无方法、未知、超预算分别保留，不算false；存在一个已验证可行分支也不代表它最优。

这些是具体实现算法的输入和出口约束，不是新增公共状态枚举。正常返回原约束、来源、偏好、读集及义务；错误用原局部诊断；不完整用原Needs/AnalysisIncomplete/PlanningIncomplete。取得外部证据或候选代码走原application/execution，不在探查分支时安装库、运行产品或产生外部写入。源合法、逻辑一致、有可实现策略、具备供给、产物完整及允许执行继续分开。

冻结的多根条件与联合选择实例只用于校准有限量化、不同主体实例与共享定义的关系，不建立 Core `Family` 类型。硬条件允许多个实现并不要求作者写循环；有限语法也不宣称能自动合成任意数学命题、非因果系统或无限动态世界。

## 公开管脚、标签和连接

本定义的`parameters`就是已声明的公开需求管脚；真正计算函数的输入/输出来自其现有签名，事件、流与资源来自各自接口。工具可提供统一边界视图，但不让需求参数、计算返回值和进程句柄相互强转。管脚类型、调用次数、效果与生命周期一并取得，不另建必须人工同步的ports镜像。

逻辑主体的多个引用表达“约束同一个对象”。工作台的编辑、搜索和语言服务共同使用`workbench.documents`，方法不得各自复制一份互不一致文档模型。这个关系不要求同线程或同进程；实现可以是一对多或多个角色共享一组件，只要满足真实身份、作用与一致性要求。

运行中的数据连接表示消费某次计算结果，不自动再次调用生产者；事件连线不默认广播；资源扇出不复制拥有权。激活条件、顺序、时钟与终止来自相应领域。图上两端类型相同不证明跨边界适配无失败，图中一条线也不自动代表RPC。本文的结构模块不是把所有软件压成一个无类型有向图。

### 外延内部参数

增加外部管脚时，先确定内部变化的真实拥有者；新增相应类型形参，只替换被选使用点；所有未变消费者传回原值，原公共行为保持。对新消费者再改变实参。必须同时核别名、默认强度、共享定义与源映射；相同值显式固定和继承默认不是同一意图。只有一个使用点特殊时，参数或局部派生优先，不修改所有使用者的公共定义。

闭合复合定义可再次被引用，其外部边界仍是普通Definition。新增一个应用引用无须复制内部九份定义；跨包发布时才有独立版本/出口责任。实例身份与定义身份分开，相同参数的两次有状态实例不能按字节去重。需求合取的相同项可以复用分析，却须保留两处接受来源。

## 字段目录和完整含义

字段目录采用同一模块外壳的四种定义：`req:rule`（strength、fields、semantics、implementation），`req:subject`（roles），`req:value-type`（当前只拥有本目录的有限名义枚举成员），`req:enum-value`（nominalIdentity）。它们是结构读取所需的合同描述，不是运行时插件注册代码。**`req:value-type`本身不是通用record/variant/quantity类型语言**；更丰富的领域Type由其真实Definition/dialect拥有，并通过上面的`Type.ref`和Type-owned canonical value codec接入。Requirement结构无需为每种Money/Quantity/Coordinate再增加一种Definition kind。

Rule.fields每项明确required、type及含义说明；本有限目录的type区分subject（允许的Subject种类）、enum（准确名义身份集合）、set（元素类型）、positive-integer，及复用已有Type的value。Subject路径映射、名义类型与值不能从同样拼写混用。Rule正文的完整正常行为、失败、帧、进展、条件与方法责任仍由[供给合同](../../20-语义与组合/作者语义/需求规则与供给合同.md)拥有；目录是带准确源码hash的派生视图，不能只改目录放宽义务。真正生产语义实现须把这些规则编码为原Definition/Assurance/方法的实际消费者，不允许每次构建让AI重新解释说明。

Rule/Subject/Value catalog 是**开放定义集合**：当前工程只取得被其模块、导入与锁实际引用的准确 Definition revisions，不存在 Core 固定“35种 Rule”清单。未知 Rule/Subject/Value 只表示当前解释环境缺少其 Definition 或能力，不表示用户无权定义它；新增定义通过正常模块/版本/兼容流程进入。结构读取器验证 catalog schema 与引用闭包，但不会因为某个业务/产品名字常见就内置其字段或实现。

### Rule 实例化的共同主体与默认规则

具体工程/库不得分别维护一份同义的 Rule 外壳。每条 Rule 的主体字段由其 RequirementDefinition 明确定义；复合 Definition 在参数声明处拥有 default，实例化到 Rule 时必须得到全部必需字段的准确值，Rule 自身不复制参数默认。字段类型、required、名义值与 value/subject 区分统一由本章目录合同检查；具体产品只维护自己的 Definition/Requirement 和差异，不复制 Core 的通用结构协议。

### 规则值字段沿同一类型检查

`{kind:"value",valueType:Type}`用于标题、精确整数、布尔和有限值列表；Type就是上面参数使用的builtin/ref/list联合，不建立另一套类型语法。只接收值类型，subject不允许藏在value字段。值从本次准确目录环境解释，enum成员仍必须对应实际名义类型；普通同名字符串不被转换为enum。valueType缺失、未知类型、重复字段和不支持构造均拒绝。

Rule.fields的required决定是否需要给出该字段，不提供运行默认；省略默认仍由复合定义parameters.default唯一拥有。`positive-integer`保持原精确Int且>0的语义，与value(Int)加该规则自己的同一前提等价；不因为新增value就放宽旧规则。set按真实元素类型解释及其名义相等去重，list则保持次序与重数，二者不互换。

校验顺序为：收集类型和公开引用→核 Definition 字段定义→在复合定义检查全部默认→实例化实际值→按 Rule 字段检查类型与必需性→执行该 Definition 的定义域及跨字段条件。类型合法只证明表示可解释，不证明语义约束已满足；`List<T>`、集合、关系、流等仍按各自 Type/Definition 的真实语义区分，不因宿主表示相似而互换。

冻结的多类交付实例只校准 `8a07bdb` 范本中 `use`/`require`/`exposes` 与类型化字段的组合；其产品分类、字段数量和默认值都不拥有现行合同，也不新增另一套 Gift 文本作者前端。当前合同由本节按准确内容绑定；只理解旧字段类型的实际读取器必须返回不支持，不能忽略后宣称所有源码有效。

## 硬要求、默认与偏好

同域硬要求合取，不能按后写覆盖。父级硬要求不能被局部“reset”删掉；重置只删除本层可覆盖默认。改变一个参数前核它承担的是可选择策略还是已独立接受的义务。某个参数恰好与父要求矛盾时必须返回冲突，不能因为格式通过就生成较弱实现。

逻辑矛盾、缺语义、缺实现、缺证据、无权和资源预算结束分别报告。分析未找到矛盾不等于已证明可满足；声明满足安全条件不允许通过永不工作来规避正常功能与进展。完整需求可以在实现未完成时保留，其完成状态是设计而非可运行。

偏好只在合格候选中比较，未知成本不能算零；同优先级的不同量纲不能随意加权。较高优先级未能确定相等或支配时，不跳过它用低优先级代选，具体算法见[分层偏好比较](../../30-实现解析/实现选择/实现解析与候选资格.md#preference-partial-order)。保持已有合格绑定或采用已委派稳定顺序可以是明确选择，但不产生最优结论。普通重建不再搜索整个世界；改变需求、方法失效或明确要求重新优化时才打开相交搜索与创作。

## 直接编译步骤与真实责任

**S0捕获。** 固定模块字节、清单、真实锁/已知缺额与披露范围；严格解码、不运行脚本。身份和解析上下文由workspace提供。

**S1收头。** semantics先取得模块出口、复合定义参数、主体与Rule字段。循环导入不递归计算互相包含的摘要；访问仅沿公开引用。缺定义可保全草稿，不能当空定义。

**S2实例化。** 先按[默认规则](#closed-parameter-defaults)完成准确参数环境，解析[公开边界](#logical-public-boundary)；再对所选根的use及有限逻辑组作卫生代换，按“根实例、定义引用、使用与量化出现路径”定位内部主体；外传subject仍是原主体。按[有限组合规则](#finite-requirement-composition)保留量词顺序、条件、绑定环境与真实来源，偏好独立于供给可选择分支。静态use环没有明确有界展开规则就报告环；不因此禁止运行函数递归或有合法反馈的状态模型。

这里的“使用出现路径”只在**该份冻结源及其解释**中定位发生位置，不是跨修订的永久实例ID。C1中第2项在C2插入一项后变成第3项，不能因数组下标变化把它认成全新主体，也不能把新的第2项认成旧实例。跨次保持依原身份与明确编辑/迁移映射取得；缺少唯一对应则保留待决，不按相同参数或结构哈希猜认。同一复合定义调用两次时，各自引入的内部主体保持不同；显式传入同一subject的两处引用仍共同约束该主体。合取分析可共享，不吞掉发生来源、接受范围及潜在运行实例的差异。此处不增加每个条款必填ID，也不让编译时实例化自动迁移正在运行的状态。

**S3检查组合。** 类型/字段/参数、主体同一性、硬约束/进展/帧与公开资源合同分别检查。无现成判定方法时保留义务，不把任意命题当普通布尔求值。

**S4解析供给。** compiler消费具有作用域的同一要求公式、目标与实际方法，而非丢失any/exists关系的扁平条目表。按[统一实现与选择范围](../../30-实现解析/实现选择/实现解析与候选资格.md#scoped-realization)寻找同一套共同成立的实现；方法给出前提、覆盖、效果/依赖、残余与成员贡献。可以直接采用成熟总成或组合；缺实现按已有委派创作并检查，不把TODO桩作为产物成功。

**S5生成与复核。** 将方法产出的中立/目标片段送回原类型/效果/目标检查，组合必需源、配置、UI/消息/资源、宿主和说明。只输出接口而缺功能时根未完成。绑定不由类名或目录名字猜。

**S6固定与继续。** 原语义映射连接Requirement发生、方法选择、目标位置及独立证据。参数变化使相交义务/方法失效；源格式变换本身不扩大权限。预览与保存/部署分开，真实写入仍由execution承担。

以上进入COMP0—COMP7与十职责：workspace捕获、semantics解码/实例化/检查、compiler方法与目标、assurance义务及证据、application组织、execution真实作用、entry呈现、adapters提供实际能力、contracts拥有字段、bootstrap装配。没有第二编译器、全局BlockManager或强制数据库。

## 两次变化与保持范围

一次作者修改只改变真实 owner 与相交依赖。修改某个 Requirement 字段时，首先形成新的作者 revision；未相交的 Definition、主体和消费边界保持原身份，旧运行实例继续绑定自己的旧版本。编译器沿真实读集/依赖关系使相交 RequirementInstance、RealizationPlan、Target member 与 Evidence 资格失效，不按 JSON 数组位置、产品类别或文件修改时间重建全工程。

增加第二个根时，新根建立自己的逻辑主体和发生来源；它可以复用相同 Definition 与供给，但相同路径/参数/字节不使两个有状态实例共享身份。反过来，同一根内多个 Requirement 明确引用同一主体时必须联合解释。内容去重可以共享纯分析或实现成员，不能吞掉接受来源、实例数、生命周期和状态所有权。

需要开放内部策略时，先完整迁移真实参数/接口边界与全部消费者，再改变所选使用点。用同值迁移只能证明值层结果可能保持，不能自动证明来源、兼容、效果或 Evidence 不变。冻结工作台范本中 `Reject → RebuildThenConfirm` 等变化可作为这些规则的固定回归载荷，但不是现行 Core 的默认策略。

## 格式升级、草稿与退出

未知字段/种类可以逐字节保存为非合格草稿，但不能在执行前忽略；已有合法独立根可继续。读取器声明实际支持的结构构造及准确解释；只识别use/require/prefer的实现遇到有限组合时必须返回不支持，不因共同的草案/1名称假装兼容。正式冻结协议后，扩展按协议协商或新版本演进，不原地改变已发布字段。迁移按明确旧解释读取后构造新源，保存边界映射和待决；不靠同名`/1`套用新含义。直接JSON作者区域不再另外编辑相同含义的`.gift`；旧文本可作明确版本的对照或待迁移输入，一经转成结构真源就停止竞争写权。

导出/退出可取得结构模块、全部必要定义与准确绑定及原生资产；许可限制不能用虚假导出成功掩盖。可重建索引和视图不是必须长期保存的主体，真实在途恢复和保留责任仍按原协议继续。源码写入、采用、目标生成、运行与收益分别报告。

**结构源升级。（消费条件）：** decoder/schema对现有字节新增语义时需要候选差异、前像与回退路线，不能只运行一个自动formatter。 合同归属：[老源解释升级与隐式新效果的采纳资格](../../70-工程系统与演进/实现与装配/源绑定与解释映像.md#gift-source-interpretation-upgrade)。

## 已定义与未取得

当前明确的是上述字段、组合、引用、身份、默认、输入输出、方法责任和完整结构范本。文档校验可以检查实际源、字段、引用和有限展开等性质；没有交付真实语义解释器、目标方法和桌面运行库。更广关系/时间/资源/概率/ABI的结构接口必须由原领域规范逐项明确，不能借一个`kind`字符串冒称已覆盖。已有相关领域成果继续有效；尚未闭合的语言设计由准确领域 owner 保留，产品实现及其符合性分别进入[当前实施闭包](../../90-治理与参考/状态/实施闭包.md)，而不是一律改称只差测试。

## Rule结构体从字段名称到可解码观测的连接

`req:rule` 原有四槽 `strength / fields / semantics / implementation` 不改变；其中 `semantics` 不再允许只放一句自然语言描述后被强编译路径当作已解释。对于**有限call-bound Profile**，详细的数据样本与严格子Schema见 `fixtures/contract-closure/Gift95/`，消费前必须绑定准确Profile内容：

- `observation.callable` 指向带公开签名的真实调用；`normal` 按返回和输入绑定纯布尔谓词，`failure` 单独约束错误与未知结果。每个参数位置应按实际signature检查类型和分支，不能仅凭Schema判断；
- `frame` 说明允许/保持的主体与效果，`progress` 说明终止、进展或待证明义务。某槽 `unresolved` 是合法设计草稿，却阻止将该义务标记为语义已满足；
- `implementation.capabilityRefs` 仅声明所需实现能力，不安装依赖、不赋予权限，也不由该字段生成TS方法。

其它观察类型需显式协商真正的语义Dialect/Profile；旧Reader没有此Profile时保留原字节并拒绝强消费，而不是按 `gift.requirement-structure` 版本字符串相同就放宽。源内容、Rule Definition、引入该Rule的 `require` 发生位置具有不同身份；调用绑定所需的精确签名仍由其语言/原生源owner提供。

## 首个可执行的短作者输入与唯一权威源（Gift 98 有限实现）

用户要解决的是作者只写**真正独立的业务事实和必要控制**，而非亲自展开Record、Map、CAS、StateMachine的每一步。此处落实一份已运行的、**尚未冻结为生产协议**的`gift.author-projection/1`严格JSON SourceProfile。它只是公开Definition/use调用的**紧凑作者codec**；不是新核心语言、第二份可写语义模型或所有业务的新容器kind。示例与执行器唯一坐标：`fixtures/contract-closure/Gift98/`。

单一源文件中`schema/moduleId/target/uses/controls`为必需项；`uses[]`每项有固定的`as`（使用处定义身份）、精确`use`（Definition/方法库身份）和其定义自己的具体参数。当前已实现的**有限业务中立词汇**为四项：`gift.std/VersionedRecord@1`带`key/fields`；`gift.std/FiniteTransition@1`带`initial/states/edges`；`gift.std/TransitionOnRecord@1`带`entity/workflow/field`；`gift.std/AllPredicate@1`带`entity/clauses`，其中每个`field/op/value`按真实Record字段校验，多个子句构成纯合取。它们属于这个试验定义库，**不是 Gift Core 关键字**。换一个项目，把`Task`改成`Stock`并改变字段/状态，不修改编译器核心逻辑。

作者写`fields`时可用`Text`、`Bool`、`SafeInt`、`Enum`；`Text`可显式指定标量字符数上下界，`SafeInt`仅为JavaScript安全整数有界域，不能被宣称等于中立无界`Int`，`Enum`为精确候选集；额外的Money/Date/媒体不是偷偷当Text或Number处理，而是等待准确定义、供给与目标。记录字段必须是纯标量且全部存在；`revision`是方法管理字段，作者不能另建；键是受限ASCII、1至64字符的身份Text，不能以一般Text全域替换。写`key`是当前真实身份决策，不应由字段名字恰巧叫id来推断。

当前SourceProfile的`controls.storage=volatile`与`moduleFormat=esm`只限制可用方法和目标：要求durable、CJS或Rust应给`METHOD_NOT_ELIGIBLE`／`TARGET_NOT_SUPPORTED`，**不得生成看似成功的退化实现**。正式系统中该输入应由源Profile接收，经独立 ControlFile 和工程 Target的真正owner保存控制；当前fixture只在自己的单一作者文件内收窄消费，不宣布这个文件已替代项目清单、binding-lock及所有生产控制codec。

读取器拒绝重复JSON键、NaN、非法UTF-8、未知字段、非法/碰撞标识符、未绑定Definition、坏数值和超预算；当前允许的输入上限是这个局部工具的保护预算，不是Gift全系统的固定规范。对不属于当前SourceProfile的外延信息，读取器**拒绝执行而非丢弃**；实际跨Profile round-trip、精细编辑SourceMap和原生多文件引入尚未由此示例实现。

工具在内存把已检查的每个`use`表示为当前统一 `/2` 定义表中的`req:composite`与`use`、具类型的`spec`实参；这个投影只是一份**有限的解释见证**：在正式安装真实`gift.std.behavior`定义、Type-owned `MethodSpec` codec和全通用Requirement读写器之前，不能把它冒充整个`gift.requirement-structure/1`已实现。唯一真源仍是作者提交的SourceProfile字节；所生成的内部投影与目标源码不反向成为第二份作者事实。

**使用门槛与成本**：编译器的源文件格式可以比用户的默认视图更啰嗦，但用户只编辑有意义的独特值。可选`.gift`通用计算前端依然可用于作者确需的独特算法，本试验不改变既有`.gift`文法；其它更通用表单或完整计算文本仍须独立经过单一owner/编解码/SourceMap门禁，不要求改变这个试验领域定义的含义。

**试验性短文本输入的实际定位（现用 `.intent`）**：`fixtures/contract-closure/Gift98/examples/board.intent`、`inventory.intent`及`bound-methods.intent`被参考工具的`compiler/frontend.py`读取，作为明确受限的`gift-intent-editing-subset/1`源码表示；其`record/flow/compose/policy/bind`只降低到同一个有限作者模型，不能获得已有通用计算`.gift`语言的语法所有权，更不能要求所有开发者改用这个新DSL。等义的`*.intent.json`是演示比较输入，**同一个实际作者区域只能选择其一作为真源**。当前参考CLI为方便例子仅根据`.intent`或`.json`文件名选择对应有限codec，遇到`.gift`明确返回`SOURCE_PROFILE_COLLISION`，不再错误地把计算语言当作试验意图文法；真实工作区必须由项目 SourceProfile 绑定来决定；不能因后缀推断权限。经同一校验与Target发射，等价语义得到逐字节相同目标成员，不同输入字节保留独立`sourceDigest`。此等价只覆盖当前受限域。

**扩展方法供应与作者含义分离**：`bind Alias = demo.math/ClampSafeInt@1`只是作者使用一次准确、不可由名字猜测的外部 Definition/实现绑定；其真实 TypeScript 函数体归独立供应方，并非作者文本“描述算法”后被 Gift 无依据地生成。用于示例的`gift.core/BindCallable@1`不应升级成全系统通用语言保留字。引用是否代表有效语义、是否有需要的效果、资源和异常保证，仍由真实Definition解释者、Method资格与Target负责；当前参考工具将其标明`REFERENCE_ONLY_UNVERIFIED_MEANING`，未提供生产资格。即使语法更短，也不能省略无法从已知定义推导的独立产品事实。

## 结构作者如何承载跨域而不堆砌字段

全域语义的[共同接合合同](../../20-语义与组合/共同语义/工程通用语义全域与闭合合同.md)并不新增 RequirementTerm 或第二份作者真源。作者只在本模块 `use/require/prefer` 准确引用已有语义 Definition、连接主体和记录独特差异；真实效果、证据、Grant 和方法选择仍由各自 owner 负责。`req:composite` 无需附带全域分类数组，更不能通过填写主题标签宣称已合格。

<a id="open-intent-author-surface-106"></a>
## 通用意图作者源如何不把 JSON 变成低层程序语言（Gift106 设计接合）

本节不修改现有 `gift.author-module/1` / `req:composite` 的已定义字段和值，继续使用一个逻辑 Module 外壳，不创建另一种需要双写的固定 IR。**建议的新增作者意图字段应归属于新版本化开放 dialect 的 `Definition.body`**，由锁定的语义模块解释：它描述开放 Type/Predicate/Contract/Method 的含义，不给任意 `kind` 字符串自动赋予世界定律。已有 `req:composite` 仍处理 its published finite terms；开放的无界/动态量化以被引用的语义 Definition 表达，而非扩展现有条件 union 后骗过旧版读取器。

一个无业务含义的容器 `{"definitions":{"myNewBehavior":{"kind":"open:spec","body":{...}}}}` **仅在**模块 `dialects.open` 正确绑定到解释 `open:spec` 的确定版本和内容 hash 时有意义。`kind` 中的 `spec` 是该模块自己的已声明入口，不是 Kernel 内置保留字。形式设计样本见 `fixtures/semantic-universe/Gift106/`：其 schema `gift.open-intent-fixture/1` 与 `gift.intent-open.proposal/1` 是**设计草案/读写见证**，不是已在 Gift105 产品中接受的 dialect 或发布 ABI。

实际开发者先维护最少的可区分含义：一个新 Definition 的公开签名/Observable、必要的 pre/post/invariants/progress，及复用 DefinitionRef；可选择为已验证特性绑定现有库 Method，只有真正独有的计算主体需要编写算法。Type/Function/Requirement/Handler 由各自真实 owner 解释，不得在一个 JSON 文件里为「通用」而并列复制一遍同义的实现树和规格树。严格读取可拒绝未知 dialect，但应保留未破坏的源文字供编辑；**拒绝编译≠禁止保存未知定义**。

### 大文件与大型工程的可扩展规则

逻辑模块按公开职责、权限/目标边界、演进共同性和真实依赖组织，不按每个 `kind` 拆文件；长 JSON 保留为权威作者源，搭配以定义引用定位的结构编辑、折叠/搜索、局部视图、增量解析和源映射。缩进、尾逗号拒绝、重复 key、超大文本/病态嵌套的资源限额按所选 JSON Profile 管理；文件数量不决定语义效率。派生视图不成为第二份需同步的源，不能引入脆弱的「阅读缓存当作权威」和重复投影生成流程。

### 兼容与准入

旧 Reader 遇到 `open:spec` 返回准确 `UNKNOWN_DIALECT` 或 `UNSUPPORTED_DEFINITION`，而不是忽略并宣称编译完成。新 Reader 应在固定 revision 下对每个定义执行完整的类型、引用、效果及公理/前提资格检查；开放 Rule 的 JSON 任意字段在没有 Type-owned codec 时不能被悄悄接受。单纯 schema 合法仍不足以证明其语义等价、生成或效果得到资格。满足当前 Task 的局部生成不要求读取未引用的整个未来世界，但必须保留所有已参与的独立要求。

<a id="prebootstrap-json-author-experience"></a>
## 自由表达保留 JSON 的具体作者体验

常规产品作者只维护公开意图引用、实际参数与不可委派差异；定义/类型/契约正文由被引用库拥有。创建陌生算法时，库作者可在相同 `definitions` 中新增 `s:function`、名义 `s:type` 及实际主体，而不等待 Core 更新业务目录。意图声明没有 expression 时保留其未实现状态；提供算法的 Method 与消费者选择不同层，不让作者复制整个实现到每个调用点。

JSON 变长不触发自动换语言。编辑器提供按 Definition 和真实语义关系展开、补全已锁定导出、按当前版本的局部结构替换、默认来源显示和结构差异。可选文本、图或表投影把操作转换为同一 owner 的增量；它们不是长期双写 JSON 加另一 DSL。批量规则修改按实际目标定义集合生成一份可审阅修改计划，避免几百次手工对象粘贴。

默认值只从已接受 Definition 的固定修订继承；模块升级形成可见迁移差异，不改写旧锁中所有用户意图。省略、显式 null、空列表、false、零和 Hole 是不同状态。数组顺序有语言意义时必须保持；只具有集合意义的字段按其自身合同归一化，不能对所有 JSON 深排序。

`gift.semantic-body/1` 用规范十进制字符串承载任意精度 Int；不能先经过 JS Number 再转回字符串。重复 key、未配对 Unicode 代理、非法数值或未识别解释字段由严格源检查拒绝。受管编辑可以保留未解释草稿字节，但不能同时声称该区域已精确编译。

发布或执行要求的闭合程度高于编辑保存。用户新增一个合同无需立刻有运行 Provider 才能保存；目标需要该合同的方法时才报告具体 Need。编辑视图应将“可保存但未解释”“含义明确但无方法”“源码已生成但未构建”“构建通过但未部署”分开，不用一个红绿点混同。

<a id="design-a07"></a>
## Requirement 八构造编码与解释冻结

采纳本文件已有 `gift.requirement-structure/1` 八种Term的精确设计，schema文件只是它的结构投影，不增加第九个万能表达式。`use/require/prefer/all/any/when/forEach/exists` 的已有字段、局部DefinitionRef及参数词法规则保持；主体默认值仍禁止。普通函数递归、高阶计算与无限逻辑量化走各自Definition/Profile，不能把有限forEach暗改成无界搜索。

默认值先在定义自身的词法环境下全部验证，再接受调用者显式参数，再填仅缺席项并保留来源。显式null、空集合和Hole不当作缺席；一个被调用者覆盖的非法默认仍使定义非法。相同值但来自显式写入和库默认的两次实例，在升级责任上不能合并。默认只允许闭合Value；不能捕获调用者参数、循环bound、宿主状态或代码。

Requirement旧Value的 `literal` 精确整数使用原JSON数值词法，reader必须在任何IEEE754转换前捕获和精确解码；该有限整数词元冻结为 `-?(0|[1-9][0-9]*)`，接受原字节`-0`并解释为整数0而保留源写法；`1.0/1e0`不属于此literal整数形式，须用对应typed值表达，不由JSON Schema的数学integer判断替代。一般计算体中的Int字符串仍沿其原codec；两种表面不能静默互换并重写源。typed值只使用被引用类型锁定的纯作者codec，不由调用者另塞codec选择或执行远程schema。

所有Term分支都进行结构、名称、类型和意义检查；不激活的when分支无需实现已被执行，但不能含不认识的源构造而被忽略。forEach/exists的in在旧环境解析，bind只在本体可见；不遮蔽活动外层绑定。两个量词的先后不换序，有限域顺序/重复发生项按原规范保持。all空真、any空假；forEach空真、exists空假。空数组无法取得itemType时产生TypeNeed，不猜Any。

偏好不改变可行集合，不得通过any/exists的条件分支暗设哪个分支能进入；递归展开后的这些位置仍禁止prefer。只对一个整体硬合格候选计算偏好。枚举预算结束返回Incomplete，不证明false/UNSAT。完整设计格式已固定，产品发布需真实decoder及语义消费者分别取得资格，不能仅改文档的“候选”词就算发布。

**验证与反例**：新增严格schema、词法/局部scope检验和finite-model向量；覆盖bool当integer、丢精度、非法默认被覆盖、量词交换、偏好夹入分支、空量化和外层bound遮蔽。

**实际能力边界**：生产Rust/TS双codec及完整类型/意义解释仍需实现；局部审查器只检查其声明范围。

## 作者只填写不可推导的差异

短纯函数的最小作者包是项目引用及一个模块：模块声明必要的dialect/import和函数参数、结果、body或合同；无需作者另写IR、Method选择表、Proof、Target成员清单或每次构建的Operation记录。沿用已接受库默认时保留来源，不要求复制默认全文。未能从定义取得的业务决定仍显示Need，不能以“低冗余”为由猜测。

中等工程将公共类型/规则/函数置于有公开导出的模块，消费者只写import及参数差异；三个调用点共享一个规则不是把规则内容粘贴三次。大型工程保持一个逻辑AuthorModule可由受支持源Profile组织文件，控制分片仅作用于已选择的控制源；作者主要操作定义视图、引用补全及局部Diff，所有保存仍落到唯一有权原源，不持久化第二份展开JSON图。

编辑器折叠、虚拟化和路径别名仅是视图，不能改变授权及依赖；检索或投影缺行必须标明coverage。任何默认展开的可读副本标为derived/read-only。缺席、null、空List、草稿Hole有不同含义；Hole阻断执行而不阻断合法草稿保存。用户从“只写规格”接管具体算法时增加body/Method绑定并承担相应可观察实现决定；重新委派时保留硬合同而不把旧实现细节暗固化为需求。

**验证与反例**：三个规模以完整project/module/import/control形状核对；比较第一次定义、第二次引用、第二轮修改实际新增信息，不能用格式压缩字节数替用户操作成本。

**实际能力边界**：实际IDE作者时间、可发现性与大型编辑性能尚待实测；本次固定字段责任和三档文件布局。

<a id="gift-pattern-source-encoding"></a>
## 参数化公共业务模式的结构作者源：与 `intent:goal` 同源而非第二模型

此处只拥有**作者输入的字节编解码、声明种类和版本协商**，模式的含义归[抽象和定义](../../20-语义与组合/组合/抽象与开放定义.md#gift-abstraction-calculus)。必须允许工程把业务公共模式作为普通 `Definition` 管理，而不是每个作者改一次逻辑都要扩展 Kernel 枚举。一个公共模式的 `role`、共同不变量、需要领域填充的差异槽、观察边界必须成为有类型的作者信息，不能只在说明文字或模板变量里出现。

**具体选型：** 引入设计中的 `kind="semantic:pattern"` 及 `body.representation="gift.semantic-pattern/1"`；其 Body 的精确 JSON Schema 是[`semantic-pattern-1.schema.json`](../../../schema/semantics/semantic-pattern-1.schema.json)。它放在已有 `gift.author-module/1` 的 `definitions` 内，通过该模块明确声明的 dialect/SourceProfile 解码；不创建第二个持久模式仓库，也不复制一个 `requirements.json` 到旁边。旧版 `intent-module-1.schema.json` 是只接纳 `intent:goal` 的单一画像；未协商该新 Kind 时，读者必须保全原始源码并拒绝执行，不能默默当普通 `intent:goal` 解析或无损忽略。

`roles` 使用名义 `typeRef`、多重性（one/optional/set/bag/sequence）及必要身份/单位来源；`sharedClaims` 在有限谓词场景引用真实 Meaning 和参数角色绑定；更复杂的规范/时序/许可/效果等通过 `requirementRef + roleBindings + scopeRef` 引用原 RequirementDefinition，禁止将复杂含义降为布尔或在模式内再造 Requirement 语法；`variationPoints` 只列会改变合同成立条件的必须输入，且规定它应由哪种权威/政策补足；`observationBoundary` 说明模型/外部观察/抽象合同区别；`meaningImports` 只在直接谓词分支保留相应解释锁；若公共模式只引用 Requirement，锁与含义由被引用定义原权威维护，可以为空，但真实 Decoder 必须验证 Requirement 及其依赖。Schema 验证不检查世界事实、资源公平或行业资格；真正的类型/引用/作用域/Meaning 准入需 Reader/语义消费者二次检查。

**新 Profile 的版本承诺：** `gift.semantic-pattern/1` 对已明确字段的意义不可在同一版本静默变化。Role 参数顺序不依赖 JSON 对象物理顺序，显式列/数组的顺序若具有业务意义则必须保留；重复 JSON 键、非法源字节和未知字段由相应严格 codec 拒绝。未知 Kind/版本可作为作者草稿与原件保全，但不能参与当前实现绑定。当前 `gift.intent-body/1` 的六类子句与旧代码消费者原封不动，模式只通过普通有型 DefinitionRef 复用及实例化，不强制现有程序换格式。

**落地实现顺序：** (1) 新结构体与严格读取器；(2) 逻辑 AuthorModule 声明共存与导入/导出；(3) 名义类型、Role/Mention/Meaning 绑定检查；(4) `PatternInstanceView` 派生但不持久双写；(5) 结构编辑和第二次修改的 stable occurrence/source span；(6) 当前支持范围的正负例、旧 Reader 拒绝与迁移/撤销；(7) 真实联合 Requirement/Method/Target 消费。只完成第一步不得声称新语义已可编译。

完整 Module 外壳与 Reader 兼容性负例见[Gift118 设计样本](../../../fixtures/semantic-abstraction/Gift118/README.md)；原 `intent-module-1` 继续保持 Intent-only 解释，不按 JSON 外观偷接受新 Kind。

<a id="gift119-pattern-use-author-encoding"></a>
## 公共业务模式如何被作者真正实例化（明确的版本化编码）

Gift118 已有 `semantic:pattern` 定义结构，但 `gift.intent-body/1` 的六条款和有限公式**没有**合法字段用于携带 `PatternRef + RoleBindings + 必需VariationSelections`。它不能通过偷偷增加 `patternUse` 键解决，否则旧 Reader 可能把本次业务的核心条件漏读。现采用**新的、需要显式协商的设计载荷** `Definition.kind=semantic:pattern-use`、`body.representation=gift.semantic-pattern-use/1`：它仍位于既有 `gift.author-module/1`，是单一作者源中的一个“对公共模式的实例使用” Definition，不是额外工程清单、第二 Requirement 真源或新的业务内核 keyword。其严格结构见 `schema/semantics/semantic-pattern-use-1.schema.json`，样本见 `fixtures/semantic-abstraction/Gift119/`。目前为**设计/离线检查**，旧 `intent-module-1`、`intent-body-1` 和 Gift117 Reader 不支持时必须准确拒绝；正式接入需独立 SourceProfile/Dialect 选择与相容迁移。

作者最少提供：`patternRef`（沿模块 `DefinitionRef`/import锁解析，不能只按名字），`roleBindings`（角色到有身份的业务对象）、`variationSelections`（全部必需差异槽的定义引用和实际接受来源）、`observationSelection`（本次事实/观察范围）；可选作者注释不影响含义。公共 `sharedClaims`、签名和 Meaning 锁保存在所引用的 Pattern/Requirement，**不允许此 Use 复制或覆盖它们**。

正式 Decoder 的确定算法：①严格读 JSON/重复键与Profile；②在锁定 import 图中解析 Pattern；③比对 `roleBindings` 键集合与 Pattern roles（缺必需角色拒绝，多余角色拒绝，数量和名义类型按真实定义校验）；④比对 `variationSelections` 与 `variationPoints`，缺必需槽拒绝、多余槽或无权/错类型的策略拒绝，不能由 Schema 的字符串值自动创建 Authority；⑤验证 `observationSelection` 真实来源、时效及 Scope、World/Model 意义与 Pattern 观察边界兼容；⑥对 PredicateClaim/RequirementUse 分别沿其有权解释器取得正确的类型化义务，不把法定义务压成 Bool；⑦产生只读 `PatternInstanceView` 和 read-set，保留 `NeedsFact/NeedsMeaning/NeedsBinding`；⑧将派生义务加入已接受的复合业务/系统 Root 时做联合约束，绝不因为 Schema PASS 就产生 Method/Grant/Artifact。

不会为引用模式强制所有作者编写同一份 `intent:goal`：可将已接受的 `semantic:pattern-use` 作为复合 Root 的 DefinitionUse，再与同一 Root 中直接给出的 `intent:goal`、Requirement 共同组合；该 Root 的公开性质沿既有 Definition/Requirement 拥有。模式参考的含义变更必须使相交实例、方法绑定及证据失效；旧 SourceRevision、Operation 和持久状态按迁移方案存续，不能把旧实例静默升级成新规则。

<a id="pattern-use-versioned-encoding"></a>
## 公共模式作者使用的明确版本、文件编码和迁移

此处唯一拥有 `AuthorModule` 文件承载、SourceProfile 与严格解码的规则；公共抽象关系由[抽象语义 owner](../../20-语义与组合/组合/抽象与开放定义.md#pattern-use-multiplicity-refinement-contract)维护。历史候选 `gift.semantic-pattern-use/1` 只有每角色一个 `objectRef`；新设计输入 `gift.semantic-pattern-use/2` 使用 [schema/semantics/semantic-pattern-use-2.schema.json](../../../schema/semantics/semantic-pattern-use-2.schema.json)，同时为 `one/optional/set/bag/sequence` 提供不混淆的结构。**版本号升级不意味着已有产品读取器已发布。**

仍只允许一份当前 `/2` 作者源（历史 `/1` 为只读）：一个定义 `kind=semantic:pattern-use`，其 `body.representation=gift.semantic-pattern-use/2`；由实际启用的 `semanticPatternUse` 方言版本匹配。定义通过 `patternRef` 指向锁定的 `semantic:pattern` Definition；`roleBindings` 仅保存本实例的类型化角色选择；`variationSelections` 仅保存必须明确决定的差异槽；`observationSelection` 保存本次事实/模型观察来源。读者不得把作者提交的 `typeRefinementRef`、选择来源或 URI 当作“证明已通过”。版本化 Body 形状见[当前 Schema](../../../schema/semantics/semantic-pattern-use-2.schema.json)，类型与基数解释见[模式使用合同](../../20-语义与组合/组合/抽象与开放定义.md#pattern-use-multiplicity-refinement-contract)；本包不以已移出的历史实验文件作为可打开的当前作者模板。

`/1 → /2` **仅在全部模式角色的 multiplicity 为 `one`、实际 DefinitionRef/锁均可验证，且没有不明条件性义务**时允许明确、可审阅的结构迁移：每个原 `{"objectRef":X}` 变为 `{"kind":"one","object":{"objectRef":X}}`，其余 `patternRef`/variation/observation 原样保留并重新签本版本作者修订。旧输入、未知版本、重复键、非法额外字段及不存在的方言均不得按兼容默认忽略；旧读者不能接受 `/2`。包内设计 Schema 与通过结构测试不等于生产 Reader 已采用此协议。

真实 Reader 须保存字节/JSON Pointer/修订对应，先严格解析和固定 module/lock，再按所选 `DefinitionRef` 实际 `roles` 执行基数检查；JSON Schema 单独无法知道模式定义中的类型、角色集合或可信证据。出现该错误时返回对应 Need 和源坐标，允许草稿保全；不得把损坏的部分实例编成当前有效代码。
