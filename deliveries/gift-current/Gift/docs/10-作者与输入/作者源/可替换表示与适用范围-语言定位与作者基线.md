# 语言定位与作者基线

## 语言定位与作者基线

### 语言责任与产品范围

公共语言合同首先定义**类型、关系、求值、控制、资源与模块**的语义；选择 `.gift` 文本 Profile 才进一步消费其 Lexer/Parser。结构 JSON 可以直接表达已定义的 Block 与 Requirement，但仍需同一解释与资格检查；低层可计算性、作者成本、目标可实现性和现实许可分别验收。成熟机制只有在当前解释、版本与依赖兼容时才复用。

全体系的当前选择与剩余入口由[能力裁决](../../20-语义与组合/作者语义/能力映射与表达边界.md#完整语言能力的当前裁决)维护，新增机制按其中LANG0—LANG5检查组合。这里继续作为可实施语法与语义的唯一入口，不把新关键词变成日常作者必须学习的全部词表。封装使用者只表达自己的差异；创建独特功能的作者可以使用语言相应能力。

### 作者载体、实现供给与原生工程的选择

当前采用结构化AuthorModule表达产品意图与组合；具体作者区域由合格SourceProfile承载，严格JSON是当前可用结构profile之一，不要求全工程或所有新产品统一成为JSON。表示选择跟随该内容的真实角色、已有拥有者和消费目的；它不是按文件后缀比较哪种语言“更高级”。

| 内容与任务 | 直接维护的来源 | 仍须成立的责任 |
|---|---|---|
| 产品意图、定义复用、共享主体与独立约束 | 结构化AuthorModule；区域选择合格SourceProfile，工具维护可推导机械信息和准确绑定 | 规则有精确语义；Profile/标签存在不能称实现已完成 |
| 已存在且满足任务的程序 | 原生TS/其他实际语言文件、原清单和锁；可以直接导出已有入口 | 固定原语言和环境；检查相交行为、错误、资源与公共边界 |
| 确实需要中立计算定义或语言变换校准 | 明确选择的`.gift`计算画像，或者已有合格中立表示 | 有真实读取、类型/效果、降低与运行供给；本画像不是普通产品作者前置 |
| 已经按原生实现完成的供给 | 实际原生源码/包与相交契约；不翻写一份同算法JSON或`.gift` | 说明它满足哪份要求、在哪个目标与范围成立；函数签名不是行为证明 |
| 文本意图备选 | 包外冻结的比较方案（存在且被明确取得时） | 比较材料，不作为当前已实现入口；其有效区别被采用后应进入当前 owner，而不是把 companion 变成第二规范 |
| 配置、数据、媒体、测试和解释 | 真实格式及原拥有者 | 只在任务相交时读取、修改或交付；不base64进通用作者模型 |
| 目标源码、分析投影和阅读版 | 从准确输入派生；需接管时显式转移区域拥有权 | 不与原作者源双写同一决定；派生成功不等于运行或采用 |

**直接用现有源码不是退化。** 单目标、已有框架/库已表达完整任务，且本任务无需独立意图求解、组合验证或跨目标保持时，直接维护它通常是更小的候选。Gift可只承担获准的工程内容、检查与交付工作；没有额外作用时，工程也可以不使用Gift。比较必须使用同样的库、质量、范围和持续修改，不能把“别人从零写库”与“Gift引用成熟库”相比。这里是按任务选择，不把整个Gift的意图主面换成原生逆向优先。

**JSON 适合作为结构化源，不强制承载全部程序细节。** 其字段、引用和数组规则清晰，但长标识、缺少注释、严格编辑与合并冲突增加人工维护成本；采用局部视图、结构增量和精确回写降低成本，不复制第二作者真源。若普通循环或局部求值需大量逐指令树节点才能表达，则该区域可选择已支持的紧凑程序表示；格式统一不得改变作者已接受的语义。

**不完整需求与选择自由分开。** 已有规则给出完整允许行为并委派实现时，可以从多个合格实现中选择；规则还没说明关键行为时，保持准确未决或按已有委派补充，不能由当前代码倒推成原接受要求。采用一项已有实现不要求它另附同义`.gift`主体；只适用单目标的供给也不自动满足跨目标任务。

独立需求和实现程序可以同时保存，它们不是同一决定的两份镜像：前者是验收依据，后者是满足它的一个实现。派生签名、接口视图、目标代码与同义AST才按原唯一拥有权处理。反过来，没有独立要求的普通文件编辑无需凭空生成一份需求表。具体接合见[混合作者与供给](../../80-开发者与接口/原生维护/语言前端与直接编辑.md#mixed-author-supply)；成本判断仍由[成品边界](../../20-语义与组合/交付语义/交付公共合同.md#gift-unit-501703299c2052ad9d1e9e2adc6ad993)承担。

<a id="source-profile-selection"></a>
### 作者表示的最终选择单位是 SourceProfile，而不是全产品文件后缀

现行裁决从“新产品统一以JSON为主作者载体”收敛为：**每个非重叠作者区域选择一个合格SourceProfile，所有Profile进入同一语义体系。** 严格JSON继续是机器拥有的清单、锁、协议及适合结构编辑区域的合法Profile；可读文本、`.gift`与原生语言在各自任务中同样合法。选择标准是作者负担、无损往返、诊断、diff/merge、稳定身份、所需语义和实现成本，而不是哪种格式更“结构化”。

默认产品创作不把内部SemanticModel或AST完整暴露给作者。结构编辑器可以呈现表单/图/JSON投影，但若其结果最终由Markdown、原生文件或其他SourceProfile拥有，必须通过SourceMap回写该owner；反之，明确选择JSON source的区域就直接修改JSON，不再维护同义文本。Profile迁移是一次有前像、差异、消费者和回退条件的作者权迁移，不是普通格式化。

### 当前作者面实施基线与决策状态

当前成品实现次序先闭合结构化意图源、定义与共享主体、需求/供给组合及目标生成，再接相交操作能力；具体拥有者见[实施路线](../../70-工程系统与演进/演进与实施/实施/主线前沿-作者主线与实现责任.md#language-roadmap)。Gift自身实现语言、作者结构、原生语言、目标语言和FFI是不同决定。**作者／目标交付仍是 TypeScript 目标先行，Rust 属于已选目标语言计划**；目标支持按准确能力逐项交付，不要求首个TS发行等到Rust目标全部完成，但这条目标路线既不授权也不阻断核心迁移。**Gift 自身 compiler-kernel 的当前物理方向由[实现语言与机制演进](../../70-工程系统与演进/演进与实施/实现语言与机制演进.md#compiler-kernel-rust-substrate)独立拥有：长期生产 owner 收敛到 Rust，现有 TypeScript 能力按该文的逐能力门禁迁移。** 原生深维护/逆向有独立价值，但不是新建产品作者面的前置。

**当前交付选择：新建产品用分层意图/Block定义、公开管脚及必要约束表达独特决定；普通新业务只在候选`gift.author-module/2`严格JSON模块写源，旧`/1`为历史只读；原生实现及可选计算区域保持自身合法SourceProfile，具体需求体见[结构合同](结构化源码.md)。严格JSON是可用载体/codec之一而非权限、语义身份、实现或正确性证明。编辑工具代管机械身份和已定义字段，不要求手填展开AST。已有`.gift`计算源、原生源和精确绑定保持其合法角色；新增`design/use/prefer`只保留为未采用的可选文本表面，不是结构编译器前置。实现缺额由真实供给/受委派创作承担，不自动转成产品作者的手写义务。普通新业务不增加核心关键词、服务或并行真源。**

这个选择是设计者在现有目标下作出的方案，不是用户要求必须发明一种语法。用户要求比较某个方案，只增加比较义务，不自动改变产品要求或采用状态。公共语义、输入前端和目标语言分别绑定。

| 决定对象 | 当前必须实施的选择 | 不进入当前交付的备选及原因 |
|---|---|---|
| AI日常操作 | 已知源码直接source/files/edits；已取得局部定位时用现有editRef或结构增量 | 不为变短而强制先查ID，不逐次重发完整树 |
| 新建产品与独特行为 | 产品引用/组合准确Block与需求，必要差异存结构模块；真正新含义由对应定义拥有，实现可由合格供给、领域结构或所选程序表示承担 | 不强制产品作者手写函数，不按标签猜实现，不要求先设计新文本语言 |
| 结构组合 | 使用既有基础结构体和领域模型；维护真实绑定、激活与唯一写权 | 不建立与文本独立可写的镜像图，不要求表达式全部上画布 |
| 已有工程 | 继续原作者来源和精确解释；确需迁移时按已定转换合同进行 | 不因当前默认改变而批量迁写既有区域 |
| 语义与目标 | 固定共同值域/效果/需求关系；TS首目标，Rust纳入计划；新产品直接编译与原生维护/受管回源分别交付，读取、生成、构建、ABI和回源各有支持范围 | 不把逆向或首个宿主设为所有新工程前置 |
| 库与实现 | 普通定义直接封装；已绑定实现继续用；新选择在既有委派内由编译器决定 | 不要求作者点名所有轮子，不为每种业务新增工具 |
| 工程架构 | 使用既定workspace/semantics/compiler/assurance/application/execution及适配责任 | 不因前端备选增加第二套头、权限、编译器和存储 |
| 验证责任 | 成熟实现按前提复用；本系统新增映射、组合和任务满足承担残余检查 | 不将所有上游能力从零证明，也不以尚无性能数据取消当前设计决定 |

当前采用面由[D02](../../90-治理与参考/决策/设计理由-产品作者与语义.md#d02-中立语义与可替换作者表示)确定：共同定义、直接结构输入、合格供给和单源编辑。结构输入不必先打印成`.gift`再解析；`.gift`是可选计算画像，其真实语义/目标义务保留。不存在“结构可编译就永远不用语言语义设计”的捷径，也不存在“要设计语义就必须新增文本关键字”的推论。

现有多目标编译器、语言工作台和引用式前端都是完整替代类别。技术可行不等于已适配：在值域、求值／错误、效果、目标源码与编辑合同相容时，能够接管相应基底或后端；确有全路径成本优势时重开表面选择。现有模块不会因本次比较而自动迁写，没有新增作者SDK、F#/Haxe入口或MPS模型发行。

当前不交付嵌套SDK；普通程序不逐运算写构造器树。这个决定只限定本次供给，不禁止真正可消除重复的阶段化库、成熟宏工具或未来取得资格的前端。新业务优先复用或组合合格供给，真正差额才写普通定义；有实际高层分析价值时才提供附加语义方法。解释、编译与多目标责任仍然存在，不能通过称为框架而取消。

已明确的接口和有限算法可以成为相应实现输入；每项替代须比较整体责任和原硬目标，不通过降低可移植、自定义或无原生补洞要求来制造短期优势。实现、符合性与采用收益继续分开记录。

### 实际作者控制与编译供给的当前分工

当前方案维护一份有确定解释的工程作者源。产品作者主要维护意图定义、管脚实参、主体关系和必要约束；维护者可以下钻实现，但不被迫维护它。`.gift`计算画像承担自身语义责任，JSON结构承担直接读取与对应语义责任，二者在同一区域不得独立双写。原生实现与生成物的回源/接管保持原合同。

当前控制落点由[最小控制](../../20-语义与组合/作者语义/作者信息完整性与控制入口.md#作者实际控制什么以及唯一修改入口)唯一规定：共同含义由定义拥有，使用点改参数，独特逻辑改函数/领域结构，必要目标或实现要求改稀疏记录，实际数据改运行输入。自然语言是创作请求；它不会在source字段中被不确定地解释为代码，也不会在每次固定构建中重新求助AI。真正的新算法需要足以确定行为的定义，不因称为“意图”就变成几句含义不确定的话；它可以由普通主体承担。已有合格算法则使用实际绑定，不为满足这句话再转写一份同义主体。代码可由受委派AI创作，但接受的内容及修改责任仍然存在。

新增功能优先使用现有语法、库和普通组合；本分工不增加关键字、语法配额或强制生成器。只有新的可观察语义确需语言支持时，才设计相交构造与目标保持。独立语法能直接表达宿主难以捕获的控制，并统一诊断和默认；它不能免掉类型、作用域、错误、资源、兼容与源码成本。嵌入式形式也不是免设计捷径。当前不为避免“语言”这个名称改用更长的组合器，也不因为已选择`.gift`就无条件拒绝成熟实现接管。

已有有限作者环境及首个直接TS降低作为当前可实施选择；新比较不成为实现前必经的无界全生态研究。某成熟前端/基底或后端实际满足同一合同且成本更小时，按明确转换替换那段供给；不能以“还没证明任何替代最优”不断暂停当前已定工作，也不能把替换供给当成客户源已全部迁移。

#### 高层主面与底层表达的当前分工

本章提供可选计算文本的准确解释；当前产品作者表示由[结构合同](结构化源码.md)直接承担。开发AI按[需求及操作路由](../../80-开发者与接口/用途与任务范围.md#authoring-route)修改公开参数、局部组合或必要定义。Block是封装角色，SourceProfile是作者载体选择；都不要求全图画布、逐运算节点、继承层次或新增运行对象。

唯一采用的程序仍须有确定含义和真实实现。隐藏内部循环不取消类型、效果、资源和目标责任；没有适用封装时，作者可以正常写自己的主体，并继续纳入同一组合体系。有限组合规则不等于所有业务名称有限，也不是承诺全世界需求存在唯一的原子分解。

### 语言身份与不可替换的目标

**选择Gift中立计算画像时，就是在使用该画像自己的语言语义，而不只是给原生代码加注释。** 该画像规定值域、绑定、求值、错误、契约和效果，`.gift`文本与对应计算结构可以表达它。产品需求JSON引用的规则保留自己的精确含义，不因此被要求先转换成此计算画像。原生区域继续由其实际语言解释；命名为“工程语义”不免除解释责任，也不构成强制采用新文本语言的依据。

“语言无关”限定公共工程语义不由某个输入或输出语言垄断，不表示 Gift 没有明确的作者表示与所选前端合同。实现可以采用 TS/Bun，第一个后端可以生成 TypeScript；它们不定义公共 Int、Text、顺序和权限。原生 TypeScript、Java、Go、Rust、Python 或其他区域保留自身语义，经明确前端与绑定接入；不能把所有原生代码先写成 TS 再声称语言中立。

产品也不等于强制所有工程迁到新语言，更不要求每个新工程保留原生作者区域。AI可以在中立源中完成全部所支持的应用行为；使用库/宿主的目标语言实现不产生第二份应用作者源码。原生作者入口用于用户选择和存量连续性，不是缺少一个高层模板时必须采用的逃生口。具体分界由[原生责任](../../80-开发者与接口/原生维护/原生来源与逆向边界.md#原生作者区域不是必备组成)拥有。每个区域只有一个作者来源。自然语言形成候选，但固定构建不重新让模型猜业务。JSON是清单或结构编码，不是作者必须填写的AST。

<a id="professional-source-experience-language-neutral"></a>
## 像编程语言一样表达一切的真实作者体验与成本边界

计算通用性并不要求作者直接操作某个万能 AST、序列化 JSON 或整数编码的图灵机。Gift 的作者能力按四个**可互通但不强制同形**的入口提供：原生文本源码、已选 `.gift` 计算文本、结构化 Definition/Requirement、由同一 owner 回写的表格/画布。一次具体编辑只修改合法作者源，其余是派生投影；图形位置和界面折叠不进入功能语义。类型、效果和资源义务由已选语言与真实接口解释，不因UI省略而丢失。

一套有限通用计算机制表达可计算行为，不等于一套简短模板能写完整软件。高复杂工程应依赖模块、复用库、默认的可推导关系、声明式组成、局部算法和必要的原生接口，避免把百万行项目重述成百万份 JSON 节点。作者明确选择公开 ABI、内存布局、硬件约束时可下钻物理策略；简单纯函数无需输入部署方案。新领域可以自己定义名义类型/协议和组件；业务词汇不成为 Gift Core 的版本开关。

**观察范围先于结论。** 有一个原生项目可被读取/保留，不等于 Gift 已理解全部语言动态反射、宏展开、运行时插件、构建脚本和权限。前端可以对未知区域保留原生作者字节与真实工具链，用有边界的未知表示下游无法证明的性质；不能删除不理解的源、替换成空桩或强迫全仓迁写后才允许设计。
