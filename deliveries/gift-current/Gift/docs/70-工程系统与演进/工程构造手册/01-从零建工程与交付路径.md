# 01 从零建立完整 Gift 工程：具体目录、入口、构建与交付顺序

## 1. 工程目标与不迁就的限制

新的开发者从零获得一份**能够被真正实现、能够持续演进、能够被其它开发者理解和接替**的施工图：Rust 编译值内核、TypeScript 控制与多入口、本地输入/状态存储、Method/Target 可插拔但受资格的供应，及至少一条自己定义新函数→生成完整 TypeScript→修改再次生成的真实路径。Gift 是通用语义系统，首条纵切是产品验证入口而不是语言能力上限。首条路径不得仅把旧 `.ts` 复制出另一目录或固定模板函数体；目标源码必须来源于被检查的函数主体或有资格的实现绑定。

业务作者不填组件拓扑/Worker/Proof/IR。编译内核不执行外部作用、不直接修改作者工作树、不将意图元数据写入业务数据库。简单工程可嵌入纯库，复杂工程按需启动隔离 Worker、持久化与外部 Provider。

## 2. 真实建设目录与精确职责

目标结构沿 `docs/70-工程系统与演进/实现与装配/源码分区与机器合同.md`，此处追加**如何填入实际内容**：

```text
repo/
  schema/                     # 已发布的结构 schema、冻结的协议输入与生成绑定入口
  kernel/
    Cargo.toml                # workspace 与 package 同时有效；首期一个 crate
    src/lib.rs                # compile_frozen、analyze、lower 的唯一可嵌入入口
    src/main.rs               # stdin/stdout worker；只做帧/派发/生命周期
    src/identity/             # SourceRef, RevisionRef, SnapshotHandle, Digest
    src/protocol/             # Strict codec, budget, handshake, request dispatch
    src/semantics/            # AuthorSource, header, binding, types, effects, contracts
    src/query/                # QueryKey/Result/ReadSet/negative edges, SCC
    src/realization/          # Method catalog, eligibility, choice, Need
    src/lowering/             # CheckedProgramView → TargetProgramPlan, layout
    src/targets/typescript/   # 有类型目标构造、printer、依赖/映射
    src/targets/rust/         # 单独 TargetProfile，不由 Kernel 是 Rust 推导其支持
    src/assurance/            # 纯 ProofObligation 与证据适用性
  control/
    package.json              # Bun 执行画像，但不能假定 Extension 用 Bun
    tsconfig.json
    src/workspace/            # project view、overlay、源CAS、结构编辑与 planSave
    src/application/          # 六工具业务控制与 Candidate/Job 投影
    src/execution/            # grant、操作、attempt、receipt、reconcile
    src/adapters/             # host fs、Git、native toolchain、Provider 端口
    src/entry/                # CLI、IDE/SDK 和同一六工具 API
    src/bootstrap/            # EngineImage、runtime实例及配置组合
    src/workbench/            # 独立发行/宿主的工作台适配
  providers/                  # 仅用于实际独立授权/进程隔离/外部服务的供应
  conformance/                # 真正的协议/语义/Target/恢复/故障见证
  benchmarks/                 # 工作负载及测量工具，不能变成编译时依赖
```

这些目录属于**将来生产工程**；当前 ZIP 的 `docs/`、`schema/`、`examples/`、`fixtures/` 和 `witnesses/` 是设计资产；本包不运输历史 Python 查询/打包工具，它们也不是编译器的先行实现。物理目录允许经准入合并文件；不能合并公开数据所有权、独立的失败/权限或引入循环依赖。

## 3. 第零次施工：建立五条不能混用的依赖

`schema`在构建时派生 Rust/TS 机器绑定，不在运行时取网络 schema。`kernel`可以只依赖普通受信基础库与固定生成绑定，不引用 control 或工作台包；`control`依赖其目标 ABI、协议方法与本地 adapters，不能自己再建类型推导器；`providers`实现接口并接受被授权对象，不能通过导入 kernel 内部私有 AST 读写用户源；`conformance`通过黑盒/公开测试接口取证，不把待测实现自己的判断当唯一期望。

应先完成以下可交付中间物：Schema 校验器和一次双端生成产物；Strict AuthorSource reader（包括非法输入和精确定位）；可嵌入的 Rust `compile_frozen`；没有真实操作的 TS headless 入口；纯 TypeScript Target；独立 Native typecheck/build adapter。随后再有权地把保存、外部效果和复杂工作台接上。

## 4. 本地搭建顺序与可直接作为验收的动作

**E0 目录与构建闭包。** 创建 Cargo package（首期 `lib`/`bin` 共用一个 kernel）、TS 控制包、协议 schema 与本地构建脚本。运行 `cargo metadata`/`cargo check` 和目标版本固定的 TS typecheck，输出固定依赖闭包。不装数据库服务、常驻 agent、远端 runner。固定 Rust toolchain、Bun/Node（按入口）、TypeScript 检查器、宿主操作系统与语言编码版本；版本信息进入构建输入，而不进入业务源。

**E1 原始字节可回读。** 用五份固定输入覆盖合法作者模块、重复键、非法 UTF-8、未知 schema、跨源同名引用。读取者返回保留 byte span 的固定 SourceSnapshot；错误不更新当前作者头。此步不要求运行任何用户代码。

**E2 真实新函数。** 借用已存在且不是业务模板的 `fixtures/prebootstrap/Gift107/` 中公开函数、`identity/compose/partitionBy` 和递归 `occurs`（取本次首次实现实际支持子集）。从结构 JSON 解码定义，声明先行、绑定、类型/效果、正常调用，不通过枚举作者业务名称决定如何降低。第一次可选择足够窄但完整的构造，所有其余合法而暂不支持的构造必须返回 `NeedTargetCapability`/`NeedMethod` 而非假默认值。

**E3 完整 TypeScript 成品。** 内核返回按文件封存的 `TargetProgramPlan` 与 SourceMap；控制层为此次请求建隔离 VFS；工具适配器使用目标锁定 TypeScript 版本真正 check/build（若请求）；结果标明构建环境/工具结果。不得在纯 compile 中偷偷执行 npm install、postinstall 或写用户工作树。

**E4 第二次修改。** 修改同一个作者原值（例如目标除法中的常量、函数签名或公开要求），在旧 Candidate 上形成新 Candidate。检查失效精确性；生成新目标，不覆盖旧原生区域，诊断映射到新 revision。保存采用 CAS，竞争者改了基础则返回冲突，不采用最后写入覆盖。

**E5 真实操作按需接入。** 用户明确要求 `apply`/运行/外部 effect 后，由 control 的 execution 取得当前 Grant、前像及资源；有副作用的 Provider 以 Operation 身份进行 journal→派发→读回→结算。纯函数编译不初始化 `.gift/state/control.sqlite`。

**E6 实现可替代与退出。** 追加一个由现有库提供的合法 ExternalExport（其 ABI/效果资格必须真实取得），及一个作者自行编写的算法；两者均经过相同消费者与 TS Target。使用户能够停用 Gift 后用保留的源码、所需依赖和普通原生构建工具重建生成的成品。

**E7 开放自举。** 从真实仓库读取一个已存在编译职责，取得可迁移的输入/输出与工具链，后续逐职责改由 Gift 源计算承担；这个阶段不是把所有功能预先限定为自举子集。

每一步都必须输出可读代码位置、固定输入、实际命令与结果及仍旧未取得的证据。若只做设计阶段，不伪造 E0—E7 已执行记录。

## 5. 第一个工程选择的详细准入

输入根：一份 `gift.project.json`、至少一份被选中的 `gift.author-module/2` 源及准确导入/锁；历史 `/1` 样例须经专门兼容读取，不能直接照搬为新工程。用户提供：目标平台、输出为函数/库及不可省略的公开结果；工具取得：实际基础与受信库闭包。普通新函数用 `s:function` 和计算体，而非注册一个新的行业 `kind`。

期望输出：完整的 `src/index.ts` 等真实成员、必要配置、公开 `.d.ts`（若目标要求）、构建依赖和用最终字节定位的 SourceMap。若需要库而未提供真实方法，则是一个**有效设计但不能构建**的局部根；可以保存作者源，不产生带 `TODO` 的假可运行源码。

完工演练：①新声明可被另一个作者源引用；②能从作者源码定位一个目标编译错误；③能在第二次修改中保留原生受管外的字节；④输入变化时旧结果不能冒充当前；⑤目标失败不影响无关联的独立输出根；⑥通用内部不读取网络与真实凭证。

## 6. 不同产品和环境的装配分歧

小型纯工具：单进程 embedded kernel+TS 目标打印，`execution`/DB/Provider 不启动。CLI 多工程：本地一个控制进程 + 有期限 Worker + per-project SourceSnapshot，会话不能跨租户重用 SnapshotHandle。含真实效果的应用：在现有路径之外装入受限 ProviderSession、本地持久状态、Grant 与恢复器。大型 IDE：Code-OSS 扩展只消费六工具并保留 view-model；不把 TS/Bun APIs 直接嵌入 webview。多机一致性、移动、设备或硬实时由所选目标与 Provider 提供准确附加资格，不默认进入纯计算路径。

设计替代方法（例如进程内 library 替换 worker、直接 emitter 替换 TS compiler API provider）必须实际保持接口、输入封闭、取消和错误位置，不能只因为运行更快就替换已选方案。本文确认具体工序；通用语义与资格仍由其原责任判断。

## 文件级建设图、依赖参数与首个输入的接线

生产工程的首个 crate 保持一个 `kernel`，其中 `identity`、`semantics`、`query` 等是模块而不是彼此循环的 crate。`src/lib.rs`只导出 `Kernel::new(image, limits)`、`Kernel::open_snapshot(captured)`、`Kernel::evaluate(snapshot, request)` 和 `Kernel::close_snapshot(handle)`；内部自由函数不自动进入公开API。`src/main.rs`只把已解码的Worker方法映射到这些入口。`control`不能因调用不方便直接导入Rust私有节点，也不实现另一个解析/类型权威。

第一组实际文件按数据依赖建立：

| 建设文件 | 必须实现的对象/函数 | 直接依赖与消费者 |
|---|---|---|
| `kernel/src/identity/mod.rs` | 域身份newtype、局部句柄与校验构造器 | 只依赖固定基础库；被全部模块使用 |
| `kernel/src/semantics/source.rs` | `SourceUnit/SpanIndex/ParsedTree` | identity；被decode、诊断与结构编辑消费 |
| `kernel/src/semantics/decode.rs` | `decode_profile(bytes,limits)` | source、锁定SchemaBundle；不依赖Target |
| `kernel/src/semantics/bind.rs` | `collect_headers/bind_bodies` | decode、ModuleIndex；输出BoundUnit |
| `kernel/src/semantics/infer.rs` | `check_signature/check_body/finalize` | bind、TypeStore、义务队列；输出CheckedUnit |
| `kernel/src/realization/resolve.rs` | `instantiate/search/commit_binding` | CheckedUnit、只读目录、纯checker；输出BoundProgram |
| `kernel/src/lowering/mod.rs` | `lower_program/verify_lowered` | BoundProgram、TargetPlan；不读工作树 |
| `kernel/src/targets/{typescript,rust}/mod.rs` | `layout/emit/finish_map` | 降低后的目标节点与固定名称表 |
| `control/src/adapters/kernel/worker.ts` | 分帧、内容、snapshot pin、请求表 | 生成DTO、进程端口；不解Gift语义 |
| `control/src/application/preview.ts` | `capture→evaluate→retain_result` | workspace、worker、返回投影；不apply |
| `control/src/execution/workspace-write.ts` | `prepare/admit/materialize/reconcile` | 有权宿主、实际五表存储及文件适配器 |

首次语言闭包的建设顺序为源→绑定→类型→主体生成；无主体调用才引入Method搜索，显式强保证才引入匹配的证据检查，真实作用才引入持久执行。不能把这条顺序误写成“先给每个函数准备一张Method证书才能编译”。完整设计中的高级画像依同一接缝扩展，首条实现路径并不更改语言可表达范围。

依赖选择记录在真实构建锁中：解析器是否保留重复键和数值词法、大整数运算语义、摘要域、目标打印器接口、SQLite连接与事务API是选库的硬筛选项。首期默认直接实现带位置的严格JSON读取、使用已审查的大整数库、纯Rust目标打印；TS工具链作为外部BuildAdapter。库的具体版本和摘要必须安装并读取后锁定，本设计不填假版本。第三方Schema生成只能产生结构DTO；语义验证、精确整数词法和跨字段不变量仍由对应Rust函数承担。

嵌入式入口与Worker入口消费同一 `EvaluateRequest` 内部联合。批处理先固定根列表；空列表可以作为明确只读枚举请求，但不构造“生成零文件的成功编译”。需要生成的请求若没有有效输出根，返回缺输入。初始化失败只回收本次创建的进程、临时目录和句柄，不杀已借用Worker、不删除已有作者文件；启动代码必须能区分owned与borrowed资源。

本地构建脚本只读取已锁工具与依赖；同步依赖是单独获准动作。`cargo metadata/check`、TypeScript检查器和Bun/Node入口都在实施时记录实际返回，本文仅定义参数与工序，不附伪成功日志。默认不启用Docker、远端runner或CI调试循环。

## 默认首条工程纵切的顺序调整

第一项成功门禁不再是给一种新语言实现一批递归/高级类型，而是**一份已接受业务意图在多意图共享约束下，通过现有有资格 Method/引擎装配得到完整、可二次修改的软件产物**。默认本地无云 runner，纯规则用进程内路径；选择数据库/工作流/外部 Provider 只因真实产品需要。旧编译器参考代码继续保存但不阻断意图系统第一纵切。
