# 23 跨域意图验证：在同一语义机制下保留各领域真实差异

> 本章是实施验收方案而非“全部领域已经支持”。不按行业数量统计通用性；验证新领域是否只需合法 Definition/Method 供应、核心是否无需行业分派、自动组合是否在未知与冲突时正确退出。专业事实、权利和 Provider 不能由有限模拟制造。

## 1. 验收维度和可观察结果

每一个正式支持 Claim 至少具有六个相互独立的资格维度：

1. **表达**：原作者写业务主体、期望、禁令、义务、时间/偏好，而非实现算法；陌生概念能直接定义，未知 Meaning 精确拒绝。
2. **解释**：类型/角色/时点/世界/法域、权利与事实来源无歧义，否定与未知不混淆；跨领域复用需要实际同义的公共部分。
3. **联合规划**：将相交目标、资源、进展和不变量作为一个求解问题；单项合格、整体不合格可被拒绝，截断不称无解。
4. **生成/装配**：复用真实方法/引擎，输出声明完整的制品/依赖/生成源、可维护源码映射与准确未决需求。
5. **运行作用**：在相应真实环境下取得 Grant、Effect、readback/恢复；模拟不能代签生产效果。
6. **独立保证与维护**：按准确 Claim 取得独立 Oracle，检查错误恢复和作者二次修改后的差异；构建通过不证明业务合格。

“支持”不是一个全局 Bool。可以在表达方面支持，却没有求解器或真实执行器；每项 Claim 的资格必须保留实际层次。

## 2. 跨域试验项目

| 新意图/差异 | 可共享的公共机制 | 不能错误继承的领域性质 | 必需反例和退出状态 |
|---|---|---|---|
| 病床/GPU/会议室/库存预留 | 容量、占用、唯一请求、原子操作、时间窗口 | 医嘱资质、预留公平、超售许可、抢占与费用 | 两次各自可行但共同超售；无事实 `NeedsFact`；无原子 Method `NeedsQualification` |
| 支付/订单/退款/积分 | 双方守恒、账本/过账、可重试操作身份 | 第三方清算终局、法域、币种精度、争议和追回 | HTTP 成功不等于已清算；已派发超时 `UnknownOutcome` |
| 订阅与服务取消 | 状态机、时间/事件、规范义务、通知 | 解约时点、账款是否仍合法、送达对象与效力 | 仅设 `active=false` 不履行通知，返回 `Partial`/`NeedsObservation` |
| 游戏胜利/投票/仲裁 | 规则演绎、主体和状态 | 裁判权、作弊信任、公平与撤销权 | 自定义完全新规则不改 Kernel；证据/裁决者缺失时不能签胜利 |
| SQL 与事件流 | 类型化关系、窗口、增量查询、流量背压 | 重数/NULL、event time、迟到数据/回撤 | 相同静态结果掩盖迟到更新；`Unknown` 不当缺席 |
| 排班/路由/资源优化 | 约束、硬/软要求、Pareto/有界优化器 | 最优性口径、时钟单位、不可行证据、外部履约 | 仅可行≠最优；Solver 超时 `IncompleteSearch` |
| 医疗与工业设备 | 观察、控制、资源、进展、安全合同 | 临床/工艺资格、物理设备响应、硬实时、应急 | 仿真通过≠真实动作允许；缺 Grant/设备 `NeedsEnvironment` |
| UI/交互/审美 | 期望体验、组件能力、外部观察 | 输入法、屏幕阅读器、地方化与主观评审 | 只返回 API 不代表可用 GUI；无评审 `NeedsObservation` |
| 隐私/权限/组织协作 | 权利、主体、资源范围、可撤销政策 | 真实发行者、法域/同意、派生数据、跨组织一致 | 只有某个负责人批准不等于全部授权；撤权不消除已发效果 |
| 新数学/科学算法 | 单位、关系约束、求解器/计算方法 | 不可判定、数值稳定、模型误差、仪器事实 | 没有合格 Method `NeedsMethod`，不能强制业务作者写循环 |
| 自定义网络协议/陌生设备 | 事件、接口、错误、时序、效果 | 真实 SDK、设备 firmware、重试/幂等、校准 | 语义可写≠已部署设备 handler，拒绝自动模拟成真实结果 |
| 跨域多主体意图 | 共享身份、类型、资源、时间、规范义务 | 不同授权主体、冲突优先级、个人与整体外部性 | 单项都 PASS、总资源超限、旧事实重放：联合拒绝 |

领域可扩展不意味着用户无须定义领域知识、法律规则或外部观测接口。它意味着在领域知识确切提供后，不必修改业务内核就能组合正确的公共机制。

## 3. Gate 级别与具体失败分类

| Gate | 必须取得的实物 | 不能由什么代替 |
|---|---|---|
| G-Intent | Source/Meaning 声明、类型/角色/观察和作者采纳 | 模型根据一句模糊自然语言自选的政策 |
| G-Interpret | 明确上下文的约束/义务图、来源和 Unknown | JSON Schema 校验或名字词典 |
| G-Realize | 资格/前提/效果/资源/Target 可闭合的整体方法绑定 | 为每个意图分别找到一个看似相似的方法 |
| G-Artifact | 锁定依赖的完整源码或配置、原生构建、Second Edit | 一个 TypeScript 文件打印成功 |
| G-Effect | 有权 Grant、持久操作身份、真实 Provider/前后像、结算与恢复 | 有限模型 `setField`、HTTP 200、工作流 DONE |
| G-Assurance | 与确切 Claim 绑定、来源独立的行为/安全/性能/法域等证据 | 方法自报保证、测试数多、文档工具 PASS |

失败要区分 `NeedsMeaning`, `NeedsFact`, `NeedsAuthority`, `AmbiguousIntent`, `InconsistentIntent`, `NeedsMethod`, `NeedsQualification`, `NeedsTarget`, `NeedsGrant`, `IncompleteSearch`, `PartialPlan`, `UnknownOutcome` 等；不能不加限定地把它们变成同一个 `failed` 或 `success`。高强度证明需要精确可用的 checker，而不是所有普通程序构建都依赖形式证明。

## 4. 比较“减少多少业务开发工作”的正确实验

以同一完整业务公开区别为基准，比较：

- A: 用原生 TS/Rust、现成数据库/库手工实现完整产品；
- B: 只使用现成 BPM/规则/数据库等 DSL 编写与集成；
- C: 使用 Gift Intents + 同一成熟供给（Method Adapter）。

分别记录普通作者的决策数量、需要自己提供的实现细节、需要等待专家/外部事实的事项、实际创建/维持的源码、真实构建与第二次修改工作、功能/安全/性能缺陷和运行成本。必须公平计入 Gift 平台初建/维护成本与外部引擎成本，不能只把作者输入缩短写成总体成本节省。高复用业务可能明显节省作者劳动；高度独特且缺 Meaning/Method 的业务可能不节省，甚至暂时更贵。

不根据无真实基线的猜测给出节省百分比。比较的目标不是消灭编程语言，而是明确 Gift 在可复用语义与现成实现之间建立的新增价值，找到仍不值得使用 Gift 的边界。

## 5. 原样、增量、并发、对抗回归

所有通过的能力须依版本重跑：

- 两个相互独立目标单独满足，组合后因共享资源不满足；反转为容量足够则出现可行计划；输入模块顺序不能改变结果。
- 对已有 Method 的保证/前提/版本改动：负依赖失效，旧 Bindings 与制品不再被报 current。
- 对已有意图更改只一个 Clause：生成物只影响真正依赖它的部分，原生用户代码保持。
- 外部读回未知、授权撤销、网络重复、部分事务提交、掉电、时钟回拨、旧 Worker 迟到均返回准确结算/恢复。
- 升级工具链、目标 ABI、语义内容摘要与包版本：是否保持语义等价必须由实际对照检查，不由名字推断。
- 跨组织授权、含个人隐私的日志/错误路径要有隔离和披露测试；远程执行不是本地优先项目的默认依赖。

这些是相应产品实现后的测试契约。Gift113 历史研究仅覆盖上表的一部分**有限模型联合组合**，本包保留其研究文字而不运输原实现或续签其测试资格；未取得真实商业、法律、设备事实，不伪造全域效果。
