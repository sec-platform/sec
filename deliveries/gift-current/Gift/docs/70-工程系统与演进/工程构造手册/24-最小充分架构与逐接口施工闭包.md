# 24 直接可施工：意图产品最小充分架构、模块接口与分段交付

> Gift 是业务意图系统，不是一门强制用户写算法的计算语言。本章按实际工程实施责任确定怎样把已设计的大系统接通。逻辑阶段不是必须 24 个服务、24 层 IR 或 24 个用户文件；以单进程本地开始，只有需求和证据要求时再独立 Worker/服务。各专业能力的权威合同仍在对应 canonical owner。

## 1. 端到端实例级数据流（明确错误后继）

```text
AuthorSource(JSON) + AuthorApproval
  --strict_read--> SourceSnapshot | DecodeReject | VersionUnknown
  --bind_meaning--> AcceptedIntentSet/MeaningBinding | NeedsMeaning/Fact/Ambiguous
  --compile_joint--> JointObligationGraph | Inconsistent/Incomplete/NeedObserver
  --realize--> RealizationCandidates + Qualification/Needs | NeedsMethod/Target
  --assemble--> ArtifactPlan + Config/GeneratedSource | NeedsDependency/ABI
  --build--> CandidateArtifactSet | TargetBuildFailure
  --publish(CAS)--> PublishedArtifactVersion | Conflict/RecoveryPending
  --authorize--> OperationPrepared | NeedsGrant/Revoked
  --dispatch--> Attempt | UnknownOutcome
  --readback--> SettledOutcome/Evidence | UnknownOutcome/NeedsObservation
```

**实现责任不倒置**：构建成功是源码/依赖层证据，不能跳过作者采纳或变成世界事实；世界签发错误不能由 JSON Schema 放宽来消除。每条失败必须带 source occurrence/revision、涉及对象/义务、实际环境/证据范围和可继续的动作，而不是在 UI 出现一个泛用 Error。

## 2. 最小落地模块与接口

| 责任模块（可以是普通函数） | 输入 | 输出/失败 | 历史研究覆盖与实施缺项 |
|---|---|---|---|
| `author.ingest` | 固定源码快照、SourceProfile、Authority | `SourceSnapshot` + lossless positions；坏 JSON/未知 Profile 拒绝 | 严格示例 reader，缺生产 CST/锁/编辑 |
| `meaning.bind` | 来源/roles/MeaningLibrary digest/context | `TypedMeaningBinding` + ReadSet；NeedsMeaning/Fact/Conflict | Gift112 有有限类型/谓词绑定 |
| `intent.compile_joint` | 多个已采纳意图、共享对象/时域 | 联立 `ObligationGraph`/Needs；不凭同名合并 | Gift113 新增离线有限模型见证 |
| `offer.qualify` | obligation graph、MethodCatalog/Target/env | 资格、前提、效应与证据 Needs；不可知时阻断 | Gift112 仅模拟局部 precondition、未生产资格 |
| `realization.solve` | 联立图 + 合格供给 + Budget | 可行候选、未决、无法证明无解、精确原因 | Gift113 仅有界状态搜索 |
| `assembly.lower` | 确定的绑定/包/引擎/Target | `ArtifactPlan`/受管生成源/配置；缺目标拒绝 | 设计有完整接缝，未从 Gift112 生产真实软件 |
| `target.native_build` | 闭包与 Toolchain Lock | 编译/构建/导入/ABI 实测 | 旧 Gift111 TS 纯计算生成，不是业务意图装配 |
| `workspace.publish` | 批量输出/SourceMap/CAS | 已发布版本或准确冲突/恢复 | 既有设计与局部 fixture，不是通用产品 |
| `host.effect` | Grant + OperationId + MethodBinding | 真实 attempt/receipt/Unknown | 部分本地 SQLite 样本；未实接公共外部 Provider |
| `assurance.qualify` | Claims/Evidence/环境与独立 checker | 只支持已证实范围的 Verdict | 已设计合同，生产跨域证据仍缺 |

表中 Gift111—113 和局部 fixture 是来源版本的受限记录，不代表本设计包运输或重验了那些实现。普通作者当前编码统一经 `gift.author-module/2`；复用旧研究输入必须通过明确版本读取与迁移，不能作为第二当前 Writer。

建议内部 Rust 类型接口（*不是已发布 ABI*）：

```rust
struct SnapshotRef { source_oid: SourceOid, revision: Revision, scope: Scope }
struct IntentRef { definition: DefinitionId, source: SnapshotRef }
struct MeaningBinding { meaning: MeaningRef, revision: SemanticRevision, typed_roles: Vec<RoleBinding>, facts: Vec<FactRef> }
struct Obligation { origin: SourceOccurrence, modality: Modality, formula: FormulaRef, context: ObservationContext, assumptions: Vec<AssumptionRef> }
struct JointGraph { intents: Vec<IntentRef>, obligations: Vec<Obligation>, identity_edges: Vec<ScopedIdentityEdge>, resource_edges: Vec<ResourceEdge>, readset: ReadSet }
struct QualifiedOffer { method: MethodRef, meaning_rev: SemanticRevision, preconditions: Vec<ClaimRef>, guarantees: Vec<ClaimRef>, frame: Frame, effects: EffectSet, qualification: QualificationRef }
struct CandidateAssembly { roots: Vec<IntentRef>, selected: Vec<QualifiedOffer>, target: TargetProfileRef, artifacts: ArtifactPlan, pending_needs: Vec<Need> }
```

字段表达数据与失效责任，不是为了引入一份长期对外二次编码。仅在明确的多消费者协议边界发布版本，内部可以借用/引用原源对象，无需每层复制所有 JSON。

## 3. 从零施工依赖（不是先写完整新编程语言）

**阶段 A：输入与语义解释可用。**实现严格 JSON/SourceMap/Version、MeaningLibrary 锁、角色绑定、Clause 编译和三值事实/未知；新增一个从未写过的业务谓词，依靠定义而不是 Kernel 分支读入。先测新名义对象、未知、冲突/错误绑定、升级。

**阶段 B：多意图和合格方法供给。**按真实共享 identity/time/resource/obligation 生成联立图；用既有库/规则/数据库方法适配器提供精确前置与保证；预算、不同世界事实与负依赖切分；禁止把单目标 plan 直接拼接。

**阶段 C：产物完整装配与用户修改。**先选一条真实本地纵切：新作者业务 JSON→规则+单库存储能力→严格 TS 包/构建→持久前后像→第二次修改→来源和恢复。仅依赖本地 runner。完成后按需增加 Workflow、优化/UI/原生计算方法，而不是为了造一个全能示例启动所有子系统。

**阶段 D：受权外部效果和独立证据。**引入真实 Grant、操作 ID、读回/补偿/恢复，按 Provider/业务环境单独准入。模拟与真实效果必须在类型上分开；多组织授权、支付/医疗/设备取证不能由本地演示代签。

**阶段 E：平台与高并发资格。**在可比较负载、目标和工具链下验证并发隔离、预算、增量、故障、性能与安全。无基线不制造指标；性能优化不得改变硬语义。真正的 Rust 核心、自举 C0—C3 若产品路线仍选择，按实际编译源码依赖逐能力完成，不得抢占业务意图纵切的成果口径。

## 4. 控制面与作者面严格隔离

默认人类作者只填写/接受：业务目标、约束、主体身份、时间/规范例外、观测需求和明确政策。可通过复用版本化 Meaning 省略公共细节。实现选择、引擎版本和方法性能由受授权的软件设计者与供应决定，且必须向用户显示那些会改变公开结果的选择。开放世界不确定项不允许由 AI 在后台自签成为业务政策。

技术作者可独立维护 Method、Target、规则库、SQL、原生程序或 Gift111 计算程序。AI 仅能提出解释/方法候选；所有候选保留来源/版本，且对已采纳的硬意图不能静默改变。业务作者改变需求不会自动拥有迁移 DB、支付或设备动作的授权。

## 5. 失败和恢复结构必须与实现一致

- `NeedsMeaning` 表示定义/观察含义不足，不应请求用户手写算法；`NeedsMethod` 表示方法缺失，可创建/接入供给。
- `NeedsFact/Observation` 表示现实前像或证据不足，不能变成逻辑假或未经采纳的默认值。
- `InconsistentIntent` 需要精确环境/反例支持；有限模型内找不到计划只能叫 `NoPlanInSuppliedFiniteModel`。
- `IncompleteSearch` 是资源/求解边界，绝不能解释成无解或不可能实现。
- `NeedsGrant` 表示真实执行不被授权，不影响作者表达自由或纯编译资格。
- `UnknownOutcome` 需要持久原 ID 下读回，重新编译/重新请求不能凭新 ID 覆盖真实副作用。

恢复流程读取真实状态、真实源版本和受权策略，按污染/撤销/损坏来源各自恢复；旧可信产物可以保留但不能在新政策下作为当前结果。多个进程不得共同持有同一原生源码/作者区域的最终写权。

## 6. 每项完成状态由实物区分

- **已设计**：有明确接口、类型/状态、算法、输入/失败、恢复、兼容和证据责任。
- **离线模型实测**：有限数据/步骤、模拟方法、测试结果；不包含真实 Effect 或全部未来轨迹。
- **真实目标实测**：对实际生成项目运行原生 build/check/behavior oracle。
- **真实 Effect 实测**：在真实授权与 Provider/存储中派发、重试、读回和故障恢复。
- **生产采用与发行**：仓库版本、构建和安全/许可证/平台资格、部署/回滚均有证据。

`Gift113` 完成的是已修订设计和新增多意图**有限模型**，不应填为后面三种资格。当前生产 Rust Kernel、通用 Target/Provider 与完整自动合成依然缺真实代码/环境证明。

## 7. 架构是否真的比普通编程简单：反向检查

若用户只有一个纯函数且已有语言/库很好地表达，它可能根本无需 Gift；若行业语义缺少可信 Meaning、Method 或审批，Gift 应暴露该成本，而不是编造简单。真正的优势仅在多业务共用可版本化意义、已有机制与复杂条件同时保持，并能在修改时更少地重写实现和维护代码。

不以“把业务编程语句改成 JSON”作为产品成功；不把通用软件必然存在的状态、并发、错误成本凭命名消灭。**降低的是业务作者须直接掌握/修改的实现决策数量，成本由有资格的库与平台承担并可摊销**，不是保证任意独特业务无成本完成。
