# 28 通用业务抽象到完整软件的施工级设计：从已接受意图到真实产物

## 每个真实产品必须闭合的因果链

当前产品根实例化时，先由有权 `AcceptedRequirements` 与实际 `SourceSnapshot` 确定被选择根；对每个 `(root occurrence, component instance)` 精确保存参数值、上下文和资源身份。组件内每个有类型 `DefinitionUse` 出现点需检验角色/Kind及引用资格；被 `activationRoutes` 定位的实例成员必须按UI/消息/API/状态/时钟分别验证因果源、工作流目标和精确输入映射。随后连接到真实Effect Port、Provider/方法、结果读回与独立要求证据。**同时属于组件的两个定义不自动构成调用关系；没有可资格化的激活路径不允许通过Target随意补出事件处理器。**

对规模更大的作者工程，不要求把所有未选库Definition建成成品；却必须将产品所接受的所有强制行为路径保留为待履行义务。某一路径需动态请求参数而作者仅定义了一个静态字符串，应由签发的映射Method或合格领域提供，不得将字符串当成请求实例。Root/Method/Target之间不能因各自具有一个 `status=PASS` 就丢失适用Scope、真实输入绑定、失败恢复和观察前提。

跨产品根发生共用同一Resource/Effect/命名数据时需要相交域联合，在确证隔离之前不得为了并行拆成两个相互独立的PASS。缺失者应返回定位到根、实例、路由、MemberUse、要求、Method或Target的 `Needs`；有证明的硬矛盾返回`Unsat`，搜索耗尽返回`SearchIncomplete`，含外部不可逆效果且当前结果未知返回`SettlementUnknown`并按原OperationID读回。不得依赖生成器用LLM临时编造未知Method来掩盖结构缺口；引入新实现需走已有公开Method资格。

## 一个当前作者Profile的完整编译边界

设计取舍已经固定：新业务源码的单一候选写入形状是`gift.author-module/2`（包含原意图Kind、非计算系统构造与按需计算/查询Kind），旧`gift.author-module/1`只作为只读兼容来源。协议版本按**每个家族**分别选择，定义体仍沿用其准确版本。新源码不得通过同时保存`/1`影子和`/2`稿子保持所谓同步。输入端须证明严格解码、唯一身份、公开导出、局部/锁定引用、Kind资格与无损适配；缺一报告Needs并保留原字节。

实现端接受产品根准确可达的`intent:goal/req:composite`、工作流、政策、资源、组件和部署等**有类型使用边**；统一联合前不得默认扫描工程所有Definition或假定某个流程/政策是硬约束。随后依据原R01–R12接口选Method、完成Target及独立保证。本章只规定施工端输入输出与失败后继，不重新定义各个Kind的业务意义，不实施通用计算编译器。

## 同一Project的两代作者Profile：接入合同不是假统一

当Project同时登记`gift.author-module/1`与候选`/2`时，前端应先按**各自准确版本**读取为冻结的模块节点；Linker只处理可验证的Export/Import/Definition引用和签名，不把旧作者源改写成新版本。用内部规范化`SourceIdentity`、`DefinitionKind`、`DeclaredSignature`、`QualifiedUse`衔接；全部保留精确来源Profile、Span/Occurrence、revision与未知字段拒绝结果。跨Profile的Meaning、Goal、Requirement、Product使用只有在适配器提供有向精化及来源/权威/基数/作用域/时间兼容证明时才可组成同一`JointObligationSet`。没有必要Profile消费者、无法解释或不兼容时须在相应阶段停止，不得推断成空要求或假成功。

阶段`SourceAST→BoundDefinitions→DerivedObligations→JointObligations→QualifiedRealizationPlan→TargetProgramIR→ArtifactSet`是设计用的**类型化交接抽象**，不是已经实现的固定IR数据结构数量。作者仅修改唯一工程源；Target不得接受未资格化的定义直接输出完整源码。跨域原语、作者Kind、45家族覆盖索引和COMP/CAP/S编号的区别及全图见[开发者源码归属图](../../00-系统与原则/开发者源码分层与构造归属图.md#gift-author-source-layer-taxonomy)。

### 根选择→组件实例→成员要求→Method/Target的精确交接

设计内部消费者不新增第二套作者JSON：`SelectedProductOccurrence` 持有 `(rootSelector, rootDefinitionIdentity, selectedContextBindings, acceptedHardRecordRef?)`；`ComponentInstanceOccurrence` 持有 `(selectedRootOccurrenceId, componentInstanceName, templateDefinitionIdentity, argumentBindings, effectiveContextBindings)`；`TypedMemberOccurrence` 持有 `(componentInstanceOccurrenceId? or productRootOccurrenceId, field-specific relation, targetDefinitionIdentity, roleActuals, scope, provenance)`；`RequiredPortOccurrence`、`ProvidedPortOccurrence`、`PublicEndpointOccurrence`、`ExternalPortDemand`和`DeploymentPlacement`均通过**实例ID**相连。这些仅为**内存设计接口**，不作为作者第二真源、不添加现行持久IR/wire文件。

流水线必须保留：严格JSON/版型及Writer区分 → 已接受根/外部限制来源 → 模块导入导出与规范身份 → Root/组件/成员实际化 → 有类型内连线/外部端口/公开出口 → 组件及产品发生点的规范联合（含状态/资源/时间/四态证据）→ 完整Method能力需求 → 完整Target程序/部署/源映射 → 有权发布、Grant与独立Readback。`needs`必须包含发生点路径、身份、缺何种专业供应及影响的派生证据；输入变更按ReadSet/负依赖精确失效。

静态可检查重复实例名、错误连接方向、漏接必需端口、未声明外部供应、部署未覆盖实例；不能靠Python有限Checker声称产品已具Method或已生成可维护TypeScript。若两个业务义务来自同一Definition而角色/时域/实例不同，统一求解器必须分别保留，不得按Ref字面去重。作者已接受条件必须来自独立确认记录；无此来源只能`NeedsAuthorAcceptanceReconciliation`，不能从当前Root推出“没有漏掉未表达的要求”。

## 作者非计算复用关系到实际消费者：必需的三类类型化交接

这里只规定产品施工合同，不实现通用计算求值器。新增字段仍属于已有`gift.author-module/2`候选Profile，不能因本地Schema通过自动进入已发布Rust Reader。

| 交接 | 冻结的输入 | 需要校验的事实 | 失败与可恢复后继 |
|---|---|---|---|
| Definition → PredicateUse | `meaningRef`、真实Occurrence、签名角色、`BusinessRoleActual`与来源快照 | 引用唯一公开出口、返回布尔、名义类型和基数、同一使用点绑定完整；外部对象Issuer、时域与Observer必须有资格 | `INVALID_ROLE_BINDING`/`NEEDS_QUALIFIED_MEANING`/`NEEDS_OBSERVATION`；保留已检查的其他定义，不推导真假 |
| Definition → Qualified Context | Definition及`qualifiers`、既有Body内部限制、SourceRevision | scope/subject/authority/validity/evidence的交集与权威；不让不可信作者自授许可、验收证据 | `NEEDS_SCOPE_QUALIFICATION`/`NEEDS_AUTHORITY`，冲突可证明时局部拒绝；不降低到默认全局范围 |
| Components → SystemConnection | 产品根、`instance`、各组件实际`provides/requires`、连接端点 | 端点实例存在、方向正确、签名/版本兼容、资源约束、是否重复供应；连接必须纳入产品Root及全局要求 | `INVALID_CONNECTION`/`NEEDS_PORT_COMPATIBILITY`/`NEEDS_METHOD`，不从同名自动连接 |

**缓存/失效**：键中包含实际Module/Definition/Occurrence、ProjectRoot、SourceRevision、被绑定的Meaning签名、角色槽映射、目标环境与有关Qualifier来源。修改条件绑定的角色、领域Meaning参数、权威或产品实例连线，必须撤销受影响的Requirement、Method、Target资格；在途Operation和已结算外部事实不能因为重新编译而更换身份。正向与缺失/负向依赖都需要按真实作用范围记录；无资格的外部来源不进入成功缓存。

**验收反例**：同名谓词被错误业务角色调用、无资格集合当全集、同端口类型不同、从需要方到提供方反连、多个供应无聚合合同、作者伪造外部权威、结构PASS被当成目标交付PASS。本轮提供的本地结构验证脚本只能拒绝其明确覆盖的静态反例，不能代签Rust产品语义或真实Target。

## RootSelection：可直接实现的纯阶段算法和质量门槛

不增加第十个强制编译阶段。RootSelection是原S0–S3中的一个有类型消费工作，必须在S4联合和S5方法资格前完成：

```rust
// 内存施工草案：名称与布局不构成发布ABI
struct SelectionInput { project_instance: ProjectInstance, source_revision: SourceRevision,
    target_key: TargetKey, root_selectors: Vec<OutputRootRef>, module_uses: ModuleUseGraph,
    source_spans: Vec<SourceSpan>, target_lock: Option<TargetProfileLock> }
struct BoundRoot { selector: OutputRootRef, occurrence: SourceOccurrence,
    module_use: ModuleUseRef, definition: DefinitionRef, semantic_kind: QualifiedKindRef }
struct SelectedRootSet { roots: Vec<BoundRoot>, referenced_definitions: Vec<DefinitionRef>,
    external_needs: Vec<Need>, positive_reads: Vec<ReadKey>, negative_reads: Vec<ReadKey> }
enum SelectionOutcome { Ready(SelectedRootSet), Incomplete { partial: SelectedRootSet, needs: Vec<Need> },
    Invalid { diagnostics: Vec<Diagnostic> } }
```

**确定算法**：冻结工程清单与读取许可 → 严格验证Target选择器与SourceScopes → 从所选UseDomain按公开出口绑定每个Root（含`export`省略时的全部导出成员快照）→ 在类型合格的语义引用边上进行带已访集合的工作队列遍历 → 将外部未锁定供应保留为Need → 产生含来源/发生位置的`SelectedRootSet`及可检查读集 → 根据已锁定TargetProfile的根解释与已资格Meaning/Pattern/Req消费形成带所有硬软、时间、Norm及共享参与者的义务 → 调用原S4联合与后续Method/Target。

`V`为已选和可达定义发生项、`E`为真实有类型引用边时，纯引用遍历可在 `O(V+E)`时间完成（不含JSON解析、跨文件读取、语义求值、求解及供应获取），并非完整编译复杂度上界。导出变化与“未找到某供应”的查询域进入负依赖；根绑定变化使相交Joint、绑定、产物和Claim失效。模块声明环可以在合格签名阶段处理，运行求值环须另有其自己合同，不能让静态图遍历证明运行终止。

**不能从Trace推断的内容**：选定的所有根是否就是作者全部真实意图、外部Meaning正确与否、Req/Goal时域和四态判断是否合格、某种目标Profile是否真实支持root union、Method/Target是否存在、运行Grant或现实效果。`fixtures/author-workspace/Gift130/verify_root_selection.py` 是这一阶段的有限本地结构见证，不能以其固定例子通过代替上述生产消费者。

**编号作用域**：本章的`S0–S8`只属于`stage`施工接合视图，跨文件定位写作`stage:S0`…`stage:S8`。`实现与装配/源码分区与机器合同.md`的`S0–S9`属于`implementation`切片；两者的同号项不是同一状态、IR或必须相同的步骤。原短编号保留以兼容已有文档与历史见证；机器消费者只能依实际阶段合同/版本解析，不能凭字母S数字推导协议身份。

## 完整开发者工程源到完整目标源码：必须实现的有型消费者（R01–R12施工合同）

下文把当前作者源、外部语义、联合约束、实现、源码、真实作用、失效和保证串联成真实消费函数；是**实现前应固定的职责与算法合同**，并非已发布Rust API或已实现全产品。作者直接维护项目/模块/原生区域，Gift不创建同义的第二作者源；所有IR/Stage/索引仅由当前Snapshot派生。`stage:S0–S8`和`implementation:S0–S9`是两套不同编号，不得用同号映射接口。

```text
return ScopedArtifactResult(artifacts, check, source_map, exact_reads, proof_dependencies)
```

每步失败都禁止提交目标文件、重复派发Operation或改写作者源；唯一允许产生的长期状态是由明确请求和相应Owner管理的候选、锁、检查证据或安全可恢复的操作记录。纯设计任务不必请求Target/运行，返回`FrozenSourceSnapshot + Needs`也可以是正确的**设计结果**；但不能叫完整软件。

### 外部世界、修改和绝对边界

同一作者根发生二次修改时，仅重建与发生变化的正读、负读、证明依赖、权限/事实/Target环境相交的派生产物；不能仅看文件摘要，也不能将历史操作按新源自动重派。多文件写入要CAS或事务日志/恢复，生成目录不能覆盖手写区域。若局部资料没有真实Method或Meaning，编译器应准确停在缺口，**没有通用算法能从任意尚未定义的现实意图推出高质量源码**；产品范围应由已取得的领域/方法/目标资格明确扩大。

## 从S0–S8跨阶段传递资格的具体签发和拒绝接口（Gift122）

### 全程检查必须以“可签发的资格”而不是数个PASS布尔串联

`StageCertificate<S>`是某阶段对特定输入、作用域和属性作出的**内部资格判定**，至少关联`stageId、inputDigestSet、issuer/checkerId+revision、scope、qualificationLevel、evidenceRefs、positive/negative/proof deps、timestamp/validity`。它只是本次构建中引用Claim/Evidence的有类型视图，不建立新的持久事实库，也不能由普通插件自填`qualified:true`伪造。`SourceStamp`、`TypeJudgment`、`MeaningInterpretation`、`JointWitness`、`MethodRefinement`和`TargetBuild`分别由相应合格消费者签发，其证据不能互换。

| 上游产物 | 下游可以相信什么 | 不得顺带相信什么 |
|---|---|---|
| 结构/类型合法的 `TypedAuthorTree` | 已选语法、引用形状和本地类型规则通过 | 外部事实/法律Meaning已解释，或Method存在 |
| `DerivedObligationSet` | 来源与参数实例化已按当前解释范围派生 | 联合可行、规范已履行、未来活性 |
| `JointObligationSet` | 声明作用域中所有已解释硬Root被联立且冲突/未知正确区分 | 已有可用程序或者现实Provider授权 |
| `QualifiedRealizationPlan` | 对确定Input/Target/Environment符合Method精化的合格计划 | Target源码已构建或部署后真实效果发生 |
| `ArtifactSet`及Build/Behavior证据 | 当前Target源码/工具链与指定行为的受限资格 | 实际组织Grant、已付款、已结算、长期现实保证 |
| 真实 `Settlement/Readback` | 当前Operation与观察覆盖的实际结果 | 任意未来状态都正确或所有系统调用都不会失败 |

编译失败状态必须区分：`NoEligibleMethod` 是当前已核供应中无合格方法；`ScopedUnsat` 必须附当前联合模型的实际冲突证明；`IncompleteSearch` 是尚未穷尽约定搜索；`NeedsMeaning` 是必要语义未解释；`UnknownOutcome` 表示外部 Operation 尚未结算。S5 遇未解释硬根不得签绑定，S6 有 Stub/未降低操作只出 Partial，S7 构建只证明 Build，S8 超时保留原 Operation 并读回/协调，不自动补发。

### 引用图、快照和并行稳定性

各阶段只消费已锁定且具相应用途资格的 Source/Meaning/Policy/Method/Artifact/Evidence。正 ReadSet 记录真实读取；负 ReadSet 记录在**带版本的查询域**中曾缺失的定义或供应，后续补入时失效相交规划；ProofDeps 则绑定签发者、假设和撤证条件。依赖无法划界就保守重算，增量结果不得获得比同输入全量检查更强的资格。SourceDigest 不包含动态 Grant/世界事实；构建失败不得促使编译器改写作者硬约束。

<a id="gift121-stable-end-to-end-compiler-contract"></a>
## 现行实施合同：稳定有限语义 → 合格完整工程（Gift121）

本章补齐**跨owner端口、阶段顺序、交付判定和失败恢复**，原有完整施工内容不删。60项公共责任的具体类型/判断取[唯一全域owner](../../20-语义与组合/共同语义/工程通用语义全域与闭合合同.md#stable-finite-general-semantic-core)，四种混合定义入口取[作者源码owner](../../10-作者与输入/作者源/结构化源码.md#stable-mixed-author-module-gate)，八种Term的联合取[Requirements](../../20-语义与组合/组合/跨软件需求合同.md#stable-joint-requirement-contract)，Method资格取[方法owner](../../30-实现解析/实现选择/实现解析与候选资格.md#stable-method-refinement-contract)，真实目标取[Target owner](../../40-目标与制品/目标/具体降低与目标输出.md#stable-target-full-assembly-contract)。这不改变 `gift.author-module/1` 的原逻辑模块版本，不增加第二份作者源码，也不要求真正工程运行时保持八个独立文件或进程。

### 四类输入必须分开锁定

1. **作者事实**：带来源字节、修订、授权接受主体和CAS版本的SourceSnapshot；只有作者/有权代理能改变该真源。
2. **语义事实**：Meaning/Requirement/Pattern锁和解释器实例，含schema版本、名义域、单位/时钟、输入输出、观察/证据授权；不能仅由作者填入URI而视为存在或真实。
3. **实现事实**：Method/Target/ABI/依赖/资源/安全许可/可用性及当次获取的独立资格；Method作者不可重写用户业务需求。
4. **运行事实**：真实环境、当前Grant、Observation、Operation ledger、读回与Evidence；不得写回为静态业务源码或在编译时伪造。

### 冻结内部类型端口（施工用Rust近似，不是已发布ABI）

```rust
struct FrozenSourceSnapshot { revision: RevisionRef, roots: Vec<DefinitionRef>,
    source_digest: Digest, selected_dialects: Vec<DialectLock>, accepted_by: ActorRef }
struct ContextLocks { meaning: Vec<MeaningLock>, policies: Vec<PolicyLock>,
    supply: Vec<SupplyLock>, target: TargetLock, assumptions: Vec<AssumptionRef> }
struct DependencyFootprint { positive: Vec<ReadKey>, negative: Vec<ReadKey>,
    proof_deps: Vec<EvidenceRef>, capability_deps: Vec<CapabilityRef> }
struct Qualified<T> { value: T, scope: ScopeRef, evidence: Vec<EvidenceRef>,
    deps: DependencyFootprint, qualification: QualificationLevel }
enum Need { MissingMeaning, MissingRequirementInterpreter, MissingFact,
    IncompleteDomain, MissingRefinement, MissingMethod, UnsupportedTarget,
    MissingEvidence, MissingGrant, IncompleteSearch, TemporalUnqualified,
    NormativeUnqualified }
enum StageResult<T> { Qualified(Qualified<T>),
    Incomplete { partial: T, needs: Vec<Need>, frontier: Frontier },
    ScopedConflict { witness: ConflictWitness, assumptions: Vec<AssumptionRef> },
    Fault { kind: FaultKind, source_spans: Vec<SourceSpan> } }
trait GiftCompiler {
    fn parse_selected(&self, src: &FrozenSourceSnapshot) -> StageResult<TypedAuthorTree>;
    fn elaborate(&self, tree: &TypedAuthorTree, cx: &ContextLocks) -> StageResult<DerivedObligationSet>;
    fn compose(&self, d: &DerivedObligationSet, cx: &ContextLocks) -> StageResult<JointObligationSet>;
    fn qualify(&self, j: &JointObligationSet, cx: &ContextLocks) -> StageResult<RealizationPlan>;
    fn assemble(&self, p: &Qualified<RealizationPlan>, cx: &ContextLocks) -> StageResult<ArtifactSet>;
}
```

这是端口层的**类型草案**；`RevisionRef`、`Digest`、`ReadKey`等依已有owner的身份和编码。尤其 `Qualified<T>` 不是只要有几个 `evidenceRefs` 即自动可信，它必须由具有当前签发权、作用域与实际检查记录的相关Stage获得。若现有Stage的物理API不同，保持其原权威结构，将上面草案映射为等价内存值，禁止制造另一套长期数据库。

### 阶段的精确数据、算法、拒绝和结果

<a id="stage-qualified-handoff-closure"></a>
**S0–S8施工接合的共同回执合同。** 每个实际阶段消费者应在内部返回精确的`producerOwner / inputSelection / subject+revision / profile+target / consumedBasis / producedReference / unresolvedObligations / diagnostic+sourceSpans / proofDependencies / qualificationScope`。这些字段是跨阶段施工**设计清单**，不是要求所有阶段构造一份同结构大对象，更不是新公布的 `gift.*` ABI；纯解析阶段没有Grant/世界效果字段，运行阶段不能伪造静态Method精化证据。

| 阶段交界 | 下游必须验证的不变量 | 阻断与后继 |
|---|---|---|
| S0→S1 | 固定被接受的Source/Profile/内容及有权读写者 | 版本/字节不一致保持前像、准确报Conflict |
| S1→S2 | 合法结构、引用/锁/名义角色、来源定位 | 无Meaning解释保留Source不默写默认 |
| S2→S3 | 合格谓词/类型/基数与时空观察前提 | 集合、条件、四态事实不完整形成局部Need |
| S3→S4 | 所有根及派生义务可回源、未决未被丢掉 | 未知条件不当false；保留量词域与共享参与者 |
| S4→S5 | 联合硬约束可行性/预算/冲突可核，原义不变 | UNSAT、无供应、预算耗尽不同后继 |
| S5→S6 | 具体Target下Method全部精化资格可用 | 不合格Binding不得降低为完整产物 |
| S6→S7 | 根/成员/接口/迁移/依赖闭包，零未降低目标必需项 | 缺成员或Stub拒签完整Target |
| S7→S8（可选） | 实际请求授权、环境前像、Operation身份 | 没Grant不得派发；源码资格不受未授权派发牵连 |

共享错误类别应至少可区分`InvalidSource`、`UnsupportedProfile`、`NeedsMeaning`、`NeedsObservation`、`ScopedConflict`、`NoQualifiedMethod`、`IncompleteSearch`、`UnloweredTarget`、`EvidenceInsufficient`、`PermissionDenied`、`EffectUnknown`；最终对外错误码仍由原contracts/owner发布，不能按这张表直接追加Wire枚举。对任意完整交付的成功判定，必须证明前驱必要义务均闭合，不能由多个局部`PASS`字符串串联推出；只做分析/设计/静态检查的任务可以在取得相应资格后停止，不强制执行S8。


| 阶段 | 输入/消费 | 正常产物 | 必须阻断的条件及后继 |
|---|---|---|---|
| S0 冻结 | 有权SourceRevision + Profile + selections | `FrozenSourceSnapshot`及锁、源码位置 | 不可信接受者/版本/Source digest不一致；返回InvalidSource或Conflict |
| S1 读取 | S0 + 已选择Dialect | 经版本检验的有类型AST（不意味着Meaning已解释） | 重复键/未知字段/跨版误读/无资格ref；保留原字节并给SourceSpan |
| S2 定义与Meaning | AST + 真实引用/名义类型/基数/Unit/来源锁 | 只读绑定与解释请求 | 无Meaning资格/错误Type/不完整枚举/名义冒充 → Need、不得猜 |
| S3 展开 | Pattern + PatternUse + Req + Goal | `DerivedObligationSet`带来源/角色/未解Need | 未赋值必要差异、角色映射冲突、观察不完整；不得当空条件 |
| S4 联合 | 所有当次根及共享身份/资源/时域 | `JointObligationSet` +耦合图/可行性候选 | 全局冲突附作用域和见证；未知范围或超预算返回Incomplete |
| S5 搜索/精化 | 联合义务+锁定Method目录+供应现实+Target | `Qualified<RealizationPlan>` | 无Method≠逻辑UNSAT；前置不覆盖/帧污染/非法证据/成本不可比均暴露 |
| S6 目标装配 | 已资格计划+目标Profile/Artifact owner | `ArtifactSet`，包含完整源码/依赖/接口/迁移/配置/SourceMap | 缺Method/Adapter/构建入口/ABI/未解决Stub → Partial，不能签完整 |
| S7 独立资格 | 实际目标工具链、行为要求、版本锁及独立Checker | 分离的结构/目标/行为/来源/effect资格 | 编译成功不能自动签安全、进展、世界效果或长期负载 |
| S8 可选运行 | 经授权操作/Grant/Provider + durable ledger | 独立Attempt/Settlement/Readback/Evidence | Timeout属于UNKNOWN，原Operation身份进入Reconciling；不能无证重试 |

**惰性优化**：单纯逻辑Method只要求对应到S7，不得强制建立真实Provider；纯查询无需写操作Grant；静态source generation可显式停止于D5/D6资格，未授权不代表源码错误。动态执行或特定运行保证必须进入S8。构建产物并非业务执行成功。

### 保持语义的必要不变量

- **唯一真源**：`SourceSnapshot`/Definition的编辑权只在原作者owner；内部AST、义务/候选/计划和生成源码都只是派生物。生成区修改经真实SourceMap投影回拥有者或成为有权原生源修订；不维护双写真源。
- **各类来源不互相代签**：作者接受、证据支持、Method资格、Target可构建、Provider授予Grant和外部Settlement是不同主体及独立Claim。
- **组合结果不靠局部PASS拼接**：必须检查共享身份、可写状态、资源和时间；对有向依赖作固定点/完整边界资格或保持Incomplete。
- **等价的真正范围**：合法输入覆盖、错误与取消、定量边界、部分失败、正常完成、安全/活性、权责/观察和目标依赖必须纳入实际支持的Claim。证明不了则限制作用域、退回候选或Need。
- **确定性**：固定源字节、语义锁、Target和候选集合时，纯阶段同结果；不将观察到的世界事实和Grant偷偷混成可复现编译输入。安全Hash域、SourceMap和排除原因稳定。
- **增量一致**：凡带Qualified产物的ReadSet/NegativeReadSet/ProofDependencies出现相交变化，应撤回相应签发并重算，结果不得比同锁的全量编译更强；未知影响时必须保守失效。

### 不可省略的联合反例（可作为下游真实测试规格）

A=`{m1,m2}`、B=`{m2,m3}`、C=`{m1,m3}`：pairwise交集均非空，全局交集空；S4必须拒绝将三个局部可行直接标为全局可行。两个容量一请求单独成功、并发合并时违反不变量：S4要将共享资源关联，S5只允许有资格串行/限额/拒绝等作者真正允许的实现。条件谓词未知时不能当false，未获得可信法定义务解释时不能当普通Boolean，获取了Method候选但没有实际Implementation时不能产出完整工程，外部Attempt超时不得自动重新发一个Operation或确认未发生。所有这些反例要保留准确Scope/SourceSpans，不因系统能输出一份TS文件而消失。

### 产品验收与交付状态

本设计**闭合施工接口**不等于闭合产品能力：先以S0–S3有限纯内核构建严格消费证据，再以S4–S7对一份有真实Meaning和Method的完整工程通过源码编译、目标编译、行为/性能/安全及修改传播，再按需要S8取得授权与读回；引入新Meaning不得修改Kernel判别枚举，旧Profile升级必须明确迁移。*本包没有发布上述Rust trait的真实实现、合格Method全目录或完整生产TS Target*；未实现的外部契约继续列在[实施状态](../../90-治理与参考/状态/实施闭包.md#gift121-closure-status)。

> 本章拥有**跨已有责任的实施算法、接口调用、状态和施工验收**，不重新维护基础语义、作者 Grammar、Method 保证、世界授权与证据规则。它们分别由[抽象规则](../../20-语义与组合/组合/抽象与开放定义.md#gift-abstraction-calculus)、[作者源](../../20-语义与组合/作者语义/通用意图语言-意图源与语义组合.md#gift-intent-abstraction-application)、[联合需求](../../20-语义与组合/组合/跨软件需求合同.md#gift-intent-composition-algorithm)、[Method](../../30-实现解析/实现选择/实现解析与候选资格.md#gift-abstract-realization-selection)、[目标](../../40-目标与制品/目标/具体降低与目标输出.md#gift-intent-to-artifact-assembly)及[证据](../../60-保证与证据/验收/意图覆盖与纵向符合性.md#gift-abstraction-and-refinement-conformance)拥有。本章是可执行施工规格，不是新强制 IR 阶段或第二份业务源码。

## 一、完整工程中真正需要建立的模块

现有 `Rust compiler-kernel`、`TypeScript control/CLI/Workbench` 和按需 Provider/Target 的技术选择不变。为通用意图补齐下列**可作为函数/模块实现、默认不必单独进程**的职责；Module 名为施工用逻辑接口，不是永久外部协议名称：

| 施工模块 | 关键函数 | 数据所有权及副作用 | 失败后继 |
|---|---|---|---|
| `source_capture` | `freeze_sources(project, revision, locks)` | 严格读取 JSON/原生，保存唯一 SourceSpan/SourceRevision；不得网络自补缺件 | UnknownVersion、CAS conflict、invalid source 原字节保全 |
| `meaning_resolver` | `resolve_meaning(def, locks, context)` | 只读锁定 Meaning/SemanticModule 的签名/解释、前提及实际读集 | NeedsMeaning、NeedsInterpreter、AmbiguousTerm |
| `pattern_elaborator` | `instantiate_pattern(patternRef, roleAndSlotBindings)` | 从单一 DefinitionRef 派生带来源合同；不创建第二作者源 | MissingVariation、Role/Unit mismatch、UnprovenAbstraction |
| `intent_elaborator` | `elaborate_intent(intentRef, factSelection)` | 输出类型化 Goal/Norm/Observation/Hard/Soft obligations；不改变源 | NeedsFact、ConflictingFact、UninterpretedTemporal |
| `joint_composer` | `compose(acceptedRoots, sharedContext)` | 建立共同主体/资源/时域和冲突/效果图 | TypedConflict、ScopedUnsat、Incomplete |
| `supply_resolver` | `discover_candidates(requirements, catalogSelection)` | 只读已锁定候选；目录变化产生负依赖 | NeedsMethod、UntrustedSupply、UnsupportedDomain |
| `refinement_checker` | `qualify_candidate(method, obligations, context)` | 接纳仅与具体使用点相交的精化证据，保持非空洞输入/进展义务 | FailedHardRequirement、NeedsEvidence、NeedsTarget |
| `assembly_compiler` | `assemble(qualifiedPlan, target, ownership)` | 生成有类型业务逻辑、接口/配置/依赖与完整 ArtifactSet，不写原生作者区 | MissingOperation、ABI mismatch、PartialArtifact |
| `execution_coordinator` | `prepare/authorize/dispatch/readback/recover(operation)` | 仅获授权情况下处理真实作用，原 Operation 身份持久化 | UnknownOutcome、PermissionDenied、NeedReconciliation |
| `assurance` | `evaluate(claim, subject, evidenceSelection)` | 只读取立来源、适用范围、时间及签发资格 | UnsupportedClaim、InadequateEvidence、QualifiedVerdict |

`pattern_elaborator` 是比旧版有限意图编译器多出来的关键职责：Gift117 只按固定有限 Meaning/Method 生成源码，新的公共业务模式要允许用户**不修改核心程序**定义和实例化更高层概念。上表模块默认按需要惰性执行，纯函数应用不必启动 Policy/Provider/DB/Assurance 服务。Rust Kernel 不应为了模式实例化而变成全业务注册表；源捕获/语义/缓存职责的物理 API 与旧章节保持。

## 二、内部有型值：共享字段是身份与条件，不是万能结构

以下是**编译器内部类型草案**；JSON 公共 author 与跨进程协议仍沿其原版本，不把这些接口全文序列化为作者必填表。

```ts
// Logical internal interfaces; names/fields are design-level, not production .d.ts.
type SourceBasis = { sourceRef: string; revision: string; profile: string; digest: string };
type SemanticSelection = { meaningLocks: readonly string[]; policyLocks: readonly string[];
  source: SourceBasis; observationScope: string; timeBasis: string };
type TruthEvidence = { support: readonly string[]; refute: readonly string[];
  completenessRef?: string; scopeRef: string }; // Four epistemic states derived, not stored as a guessed bool.
type TypedRole = { localName: string; typeRef: string; objectRef?: string;
  cardinality: 'one'|'optional'|'set'|'bag'|'sequence'; identityDomainRef?: string; unitRef?: string };
type Variation = { name: string; required: true; role: string;
  selectedDefinitionRef?: string; selectionSource?: SourceBasis };
type Obligation = { id: string; source: SourceBasis; subject: readonly TypedRole[];
  kind: 'hard-outcome'|'safety'|'progress'|'normative'|'preference'|'observation'|'effect';
  meaningRef: string; context: SemanticSelection; dependencies: readonly string[] };
type QualifiedBinding = { requirementRefs: readonly string[]; methodRef: string;
  methodDigest: string; targetRef: string; assumptions: readonly string[];
  evidenceRefs: readonly string[]; scopeRef: string; readSet: readonly string[] };
type ProductRoot = { acceptedDefinitionRefs: readonly string[]; obligations: readonly Obligation[];
  externalInterfaceRefs: readonly string[]; targetProfileRef: string;
  deliveryPurpose: 'source'|'build'|'run'|'deploy'; requestedClaimRefs: readonly string[] };
```

不在此处再发明 `DefinitionId`、`RequirementId`、`OperationId`、`RevisionId` 的持久格式。`SourceBasis` 保留原始版本与身份证据，`SemanticSelection` 记录解释上下文，`TruthEvidence` 防止把未观察到的事实当 False，`QualifiedBinding` 表示已取得范围内的 Method 决定而非已发生 Effect。每条接口实际实现应返回 `Outcome<T> | Needs | Fault` 的有型结果和 read-set；不同阶段的 `Unknown` 必须带原因及后继，而不是一个通用 `status: failed`。

## 三、开放模式 Definition 的读取与类型检查

**读取分流规则**：Pattern Reader 按[共享义务的两条互斥承载路径](../../20-语义与组合/组合/抽象与开放定义.md#gift-abstraction-calculus)解析 `sharedClaims`。有限谓词只在所声明的受支持模态内解释；`RequirementDefinition` 路径必须携带 `requirementRef + roleBindings + scopeRef`，交由相应 Requirement owner 解析、绑定解释版本并检查权限。解释器或绑定缺失时返回对应 Needs，不得把 Schema 结构通过签发为合格语义。

`semantic:pattern` 是现有 Definition 的一个新**设计载荷**，精确结构见 `schema/semantics/semantic-pattern-1.schema.json`（`gift.semantic-pattern/1`）。它将公共角色、来源锁、共享硬义务、必需差异槽和观察边界一次定义。它**不是**独立永久业务库或另一套 Method 包管理器：旧样本的作者源是当时选择的 `gift.author-module/1`；当前业务 Writer 为 `/2`，新 Kind 由当前统一 Schema 和有资格的语义消费者承担，历史模式仍由旧 Reader/Profile 解释；Gift117 的受限 `intent-module-1.schema.json` 仅接受 `intent:goal`，因此当前不能把模式文件说成已被产品编译。结构样例在 `fixtures/semantic-abstraction/Gift118/`，严格 Schema 和局部引用检查只是可施工的正/负形状。

接入步骤是：给 SourceProfile 追加明确选择的 `semantic:pattern` 定义子项支持；读取完整块并拒绝未知键/重复键；解析模式 roles 到已锁定名义 TypeRef；校验 `meaningImports` 及其由受信锁确定的内容版本；校验每一共享 Claim 所引用 Meaning 的实际参数签名与 role bindings；根据 `variationPoints` 检查调用者是否提供有权接受的补充 Definition/Policy/Observation；导出只有一个真实作者原件的 `PatternInstanceView`。差异槽没有提供时只能生成 `NeedsBinding` 候选，不许静默填“常见行业默认”。遇到新的真正原始世界观察/规范/时间语义，不能让 Body 的字符串自动加载任意代码；由语义模块准入和受控执行另核。

对同一个已接受模式，实例化时可重复引用而不复制正文。专业语言实现者可以用本机原生函数/库实现它；普通业务作者只操作已有 DefinitionRef + 角色与必要差异。版本更新时从实际 read-set 精确让受影响实例失效，不要求强行迁移所有旧意图。

## 四、如何真正抽取一个新的业务公共模式

输入不能只有三个行业标题，应包含每个领域的一条或多条实际定义、正反例、观察范围、资源/法源及环境假设。下面是可以作为 `abstract()` 纯分析功能实现的流程：

```text
propose_abstraction(examples, observationSelection, budget):
  1 capture each accepted Definition/Meaning and its actual role/fact/clock selection
  2 enumerate typed candidate correspondences, reject accidental name-only mapping
  3 determine shared predicates, guards, effects and required error/progress observations
  4 for each property mark common | parameter | extension | conflict | unknown
  5 produce variation slots with owner, kind, type and mandatory source (not a default)
  6 check sampled instances in independent evaluators; search strongest counterexamples
  7 if a supported logic/solver domain applies, check mapping entailment under assumptions
  8 return PatternCandidate + sideConditions + residualNeeds + examples + provenance
  9 only an authorized author accepts candidate as Definition; never modify existing roots
```

反向检验尤其重要：新模式能否处理一个**未参与抽象发现**、但符合所声称应用范围的新例；旧领域区别是否仍可完整表达；改变资源为可抢占、加上监管批准、引入支付结算后，哪些槽/方法立即不合格。样本充分覆盖只证明有限样本；无限/现实域需要正式逻辑、公理与外部证据，不能把本算法叫“完美自动发明全世界语义”。

## 五、模式实例化与多意图联合图的具体过程

从 `PatternRef + RoleBindings + VariationSelection` 实例化后取得的是带源的公开需求，不是实际可执行 Method。多个已接受目标结合时先归一**已明确授权的对象身份映射**，再按不可随意交换的组合关系建图。图包含：同一共享主体的属性读/写、共同容量/排他资源、同一外部 Operation 域、规范义务的责任/触发/期限、因果事件/时间前后关系、系统接口与外部观察者、能力供给依赖。再将硬要求一并给相应 Constraint/Solver 域，软偏好留到完整资格后排序。

正确处理五种情况：所有目标已在当前允许状态成立时可以返回零动作计划，但不表示长期义务或外部交付结束；无 Method 时返回具体供应 Need；有合格 Method 但其实际 Frame 未覆盖共享约束时拒绝该候选；求解预算结束时返回 Frontier/Incomplete；有限域有反例证明不可满足时报告作用域和见证，不能推广为所有现实情况都不可行。

示例：医院容量=1，两请求单独规划成功的 `reserveOne` 并不构成联合成功。联合状态检查必须在同一前像内保留 `reserved ≤ capacity`。若病房还要求医生审核，局部方法只写入 `confirmed=true` 不等于已取得医院权限。相同模式用于 GPU 时可能允许抢占，这属于选择新策略的专门化，旧非超售保证不会自动继承到超售实例。

## 六、从合格方法集合产生真正的源代码

目标编译器接收冻结的 `BindingDecision`，而不是作者业务名称。对每个公开 Root，先决定成熟能力能否直接供应：精确查询/事务应优先复用真实数据库；流程/定时/重试优先复用真实工作流供给；匹配/优化由合格求解器；网络/支付/设备仅调用有权 Provider；自定义的有限谓词与状态方法才需要直接生成 TS/Rust 逻辑函数。这样避免“为了能生成源码而重新写一门计算语言”。

`assemble` 先检查 `BindingDecision` 的覆盖闭包。允许把有限 Meaning 的 `eq/lte/gte` 专门化成实际 TypeScript 表达式，允许把已合格的 `set` 操作装入真实事务适配器；但旧 Gift117 的 `semantic_codegen.py` 只支持明确的有限模型语义，不能从此推得任意 SQL/时序/规范都已降低。`oblige/permit/审美/真实外部效果` 若没有对应真正的观察和供给，必须阻断高质量完整应用的声明。业务逻辑生成器与通用事务引擎可共存：输出中哪些文件业务专门生成、哪些依赖现成组件、哪些未覆盖，应在 AssemblyPlan 上一一追踪。

每个生成产物包含源码/配置/依赖、锁摘要、SourceMap、构建结果和可见的 `uncoveredObligations`（若仍存在则不能称为完整合格）。纯源交付不擅自部署；用户需要运行时按准确宿主权限准入。目标源码可以由外部程序脱离 Gift IDE 继续编译，用户修改原生拥有区域不会被生成器覆写。版本改变时进行局部重建并重新核资格；不能为提高速度把旧 Binding 当当前事实。

## 七、持续运行、演进、故障与恢复的实施合同

`Gift116` 的本地运行示例已实现“当前 SQLite 模型状态→每次重规划→同事务提交”。它只说明本地受界画像。正式系统需要把**已接受业务源**与**当前方法/部署版本**分开管理：旧运行使用其真实绑定修订，新请求可在采纳后使用新修订；跨版本的正在履行义务必须有显式迁移/继续旧版政策。对真实外部效果，准备派发、已发送、未知结果、已确认、补偿/人工处理分开持久，读回继续使用原 Operation ID；不能因为 TypeScript 函数返回 `true` 就认为资金/设备已发生。

运行安全与作者语义失效不同：Meaning 修改使涉及它的计划、代码、证据重新资格化；Grant 撤销使未来执行权即时受约束，但不抹掉已发生结算；目标工具更新可能要求重新构建/ABI 检查，而不必强迫修改纯业务 Definition；观察器版本变化使具体 Claim 的证据失效，但不一定使已冻结源字节改变。

## 八、按阶段实施，怎样避免又一次“小样本自证通用”

1. **开放模式结构+Reader（设计已完整，本包没有生产实现）：** 对 `semantic:pattern` 的 Body 采用明示版本，验证角色类型/Meaning 引用/差异槽/必要来源。旧 `intent:goal` 保持原格式，不搞无版本扩展。
2. **抽象实例化/组合的纯消费者：** 实现本文 `instantiate_pattern` 和 `compose`，让床位/座位/GPU 保持相同和不同的观察。用一组独立实例而不是仅重命名业务名称。
3. **合格供应目录及真正的 Method 见证：** 接至少两个不同技术机制（例如 SQLite 原子状态更新与纯规则判定/工作流），提供不同但准确可比较的效果/错误/资源合同；目前不存在的实现维持 `NeedsMethod`。
4. **完整产品 Target：** 对有资格范围生成可持续修改的 TS 工程及全部依赖，严格构建和独立运行；Rust Target 仍按自身合格构造推进，不由 TS 成绩代签。
5. **版本、权限、真实效果与恢复：** 首先完成本地安全故障域，再使用明确 Grant 接入真实 Provider；对未知结果、重放、幂等、并发和撤权实行故障注入。
6. **独立对照与非退化门禁：** 跨领域更多样且有反例的场景、二次修改、全量/增量差异、实际开发输入成本以及受明确定义工作负载的目标质量。独立 Oracle 不能与生成器共用同一个硬编码业务真相。

施工中只在对应真实能力存在时签发行内门禁，不能把“文档已包括操作步骤”“Schema 已能接受 JSON”或“程序能生成 TS 字节”写成上述所有阶段的 PASS。后继正式仓库采用仍需从真实代码/CI/环境读取并有权修改，离线文档包不代表主仓库已部署。

## 九、形式化和现实可验证的五种结论

- `Expressible`：给定已锁定解释模块，该业务区分可被精确描述；不代表 Method 存在。
- `ConsistentWithinScope`：给定假设/时间/模型，其硬规则未被求出矛盾；不代表保证可行或无限域已证明一致。
- `RealizableWithinScope`：有覆盖输入、行为、进展、效果/权限前提和目标的合格 Method/Assembly；不代表部署或真实作用。
- `BuiltAndRunWithinScope`：准确代码、编译工具、平台及工作负载发生了经记录的实际执行；不代表外部业务事实自动为真。
- `ObservedAndAssuredWithinScope`：有合格观察/证据支持明确 Claim，特别是世界作用及责任实际结算；不代表其他版本、环境或全部未来输入。

对任何不属于这五种结论的状态，返回可追踪的 `Needs` 或明确的分析/事故结果，不统一叫做“语义完成”。工程目标是减少业务作者需要指定的实施决策，同时最大限度保留公开区别，而不是追求一个未经定义的“所有业务一键正确生成”。

结构与完整 AuthorModule 外壳的对照样本、旧版 Reader 不接受的边界见[Gift118 样例](../../../fixtures/semantic-abstraction/Gift118/README.md)；模式 Schema 已登记 `schema/design-schema-catalog.json`，该记录不是产品 schema 发布资格。

## 十、从空项目到完整产品的具体模块接口与运行判据（Gift119）

**技术选择与编译责任：**普通新业务作者用严格JSON的 `gift.author-module/2` / `intent:goal`（旧`/1`只读），复用 `Definition/Requirement`，不强制 `.gift`/新计算语言；Rust compiler-kernel 承担签名/绑定/抽象实例/约束和目标编译的长期实现，TypeScript control/CLI 与 Code-OSS extension 负责交互和源码保存，首个正常用户 Target 为 TypeScript，Rust 用户 Target 另行资格化。首发执行机制选择本地 SQLite 作可确认的单库事务与重放，世界 Provider 为显式可插拔的受权 Adapter，不把 SQLite 本地状态当真实外界。现有 Gift111 Python 参考计算器和 Gift112—117 有限模型是参考见证，不是长期必须维护的第二区域业务真源。无外部服务的纯函数产品无需常驻数据库/Worker/证明器。

本实现主入口与返回职责：

```text
capture(projectRoot, expectedSourceRevision, permittedReaders)
    -> SourceSnapshot | SourceConflict | UnknownProfile
resolve(snapshot, meaningLocks, policySelection)
    -> TypedDefinitionSet | NeedsMeaning | InvalidBinding
instantiate(patternRef, roleBindings, variationSelections, snapshot)
    -> TypedRequirementUses | NeedsBinding | MissingInterpretation
compose(acceptedRoots, identityEquivalences, factSelection, scope)
    -> JointProblem | ScopedConflict | IncompleteMeaning
solve(jointProblem, methodCatalogLock, targetLock, budget)
    -> QualifiedBindingSet | NeedsMethod/Fact/Evidence/Target | IncompleteSearch | ScopedUnsat
assemble(qualifiedBindings, targetProfile, ownedGeneratedRegions)
    -> CompleteArtifactSet | PartialArtifact | UnsupportedTarget
publish(artifact, expectedWorkspaceRevision, authorizedScope)
    -> PublishedRevision | Conflict | RecoverableUnknown
execute(operationId, publishedBinding, runtimeFacts, grantSelection)
    -> LocalCommit/ExternalReceipt | UnknownOutcome | PermissionDenied
observe(operationId, claimRef, realEvidence)
    -> ScopeBoundVerdict | UnknownObservation | InadequateEvidence
```

以上返回名是有型实现接口的**判定责任**，不是自动发布九套公共 RPC。每次转换携来源和实际读到的正负依赖。`capture` 后绝不能动态根据网络结果补签逻辑来源；`resolve` 保留来源位点；`instantiate` 缺领域变化槽不得给默认值；`compose` 不按相同显示名偷合并主体；`solve` 若预算用完不称无解；`assemble` 未覆盖完整要求不得签完整；`publish` 不能覆盖无权区域；`execute` 的 Unknown 与 `observe` 的 Unknown 分开。失效范围按 Source/Meaning/Method/Target/Grant/Observation 的具体变化传播。

**一条能真正证伪“通用”的纵向验收：**准备两种此前未登记的领域定义（例如具体座位分配与一次性证件批准），另加一个涉及规范履行而非仅 Bool 的案例。先让其在没有业务名称分派的 Reader 中通过类型检查；让相同公共 `CapacityAllocation` 模式对两个不同资源策略保留超售/审批差异；在共享容量为1时正确拒绝两个同时达成的目标；绑定两个真正技术不同的 Method（例如单库事务与已资格化的流程/规则执行器），至少有一次因条件变化而换 Method；生成所有目标成员并由不依赖内置业务模板的消费者严格编译、运行、二次修改；用准确 Operation ID 注入冲突、重试及恢复；分别取得本地状态、外部作用和独立保证的结果。缺现实 Provider 或复杂规范解释器时必须返回准确 Need 而不是伪造成品。

**施工闭包与阻塞分开：**当前已设计清楚主要调用责任，但 `semantic:pattern` 仍无生产 Reader、开放 Norm/Time 无完整解释、Method 目录无生产资格/现成引擎 Adapter、没有完整 TS/Rust 生产 Target、真实世界 Grant/Provider 和独立保证也不完整；完整产品必须逐责任实施和实测。C0—C3 自举用一项真实编译器源码职责的独立闭包推进，不是业务抽象全部实现的前提，也不因生成一个 TypeScript 函数就宣称自举成功。

<a id="pattern-elaboration-implementation"></a>
## 公共模式实例化组件：可编码接口与异常恢复，不生成玩具系统

施工目标是**真实编译器中的一个可复用语义阶段**，不是再生成一个医院/订单应用。输入为 `FrozenSourceSnapshot`、作者 `semantic:pattern-use/2` 定义、锁定 `PatternDefinition`、 `ObjectRegistry` 与版本化 Meaning/Requirement、类型精化资格解释器、观察者与预算；输出为派生义务和准确 Need。这个阶段应移入最终 Rust `compiler-kernel` 的已选语义 owner，TS Control 只传递由 Rust 解释器接受的来源和结果，不新增第二套 TS 语义真源。

建议的 Rust 内部职责签名（**施工接口，不是已编译/发布的 ABI**）：

```rust
fn elaborate_pattern_use(
    source: &FrozenSourceSnapshot,
    use_ref: DefinitionRef,
    locks: &LockedDefinitionSelection,
    objects: &dyn TypedObjectReader,
    meanings: &dyn MeaningResolver,
    refinement: &dyn QualifiedRefinementReader,
    observation: &dyn ObservationReader,
    budget: &mut CompileBudget,
) -> Result<DerivedObligationSet, ElaborationNeed>;
```

必要算法，不可合并成 `dict.update()`：

1. 严格读取声明的方言/作者区域/SourceRevision，拒绝重复键、未知版本、未授权导入；取得已锁定模式 Definition 并验证内容摘要，建立本轮实际依赖的 `ReadSet`，绝不在纯编译时联网获取缺件。
2. 从模式 `roles` 取**精确全集**，与使用处 role 键集合比较；逐角色校验 `one/optional/set/bag/sequence`。set 按已解析规范身份去重，bag 保留精确计数和身份唯一性，sequence 保持次序，缺席 optional 是显式值；无匹配消费者不得简化为一元 Bool。
3. 每个对象由可信宿主 `TypedObjectReader` 取得实际身份、类型、单位和身份域。名义不同时必须调用范围受限的 `QualifiedRefinementReader` 对当前角色及实际消费的 Meaning/Requirement 判定，不得相信使用处自填 `typeRefinementRef` 的字符串。
