# 19 开放业务意义：从作者意图到可检查语义对象

> 本章是[意图作者源](../../20-语义与组合/作者语义/通用意图语言-意图源与语义组合.md)的实施面，不产生第二真源或新的必须填写的文件。`Gift112` 的离线 Schema 是当前输入示例，本文列出的内部结构及未来能力不能冒充已实现的 Schema Profile。

## 1. 问题不是收集所有业务词，而是赋予新概念可组合意义

一个业务词 `confirmed` 可以表示 UI 展示已确认、资源已预留、负责人已签发、资金已结算等不同事实。概念成为可执行语义，至少需要**有名义身份的实体与关系、观察域、时间含义、冲突/例外、主体资格、解释方法和版本范围**。只收集词条得到的是目录，不是可编译语言。

建议的内部 Meaning Graph 不让用户每次重复填写：

```text
MeaningDefinition {
  definitionId: DefinitionId,
  revision: SemanticRevision,
  parameters: typed ordered roles with nominal identity,
  denotation: Relation | StatePredicate | TransitionRelation |
              TemporalFormula | NormativeRule | ExternalObservation,
  validContext: {world/model, jurisdiction?, population?, time?, assumptions},
  logicalPolicy: {open|closed facts, missing|false, conflict/retraction policy},
  observation: {source, freshness, coverage, authority, error, provenance},
  equivalences: witnessed/refinement relations with conditions,
  qualification: supported interpreter & checkers, evidence, failure boundary
}
```

**这是一张不可变、由已锁定 Definition 派生的内部图，不要求所有字段一股脑出现在每份作者 JSON。**无真实解释的 `meaningRef` 是悬空含义：保留草稿，但不能把 URI 转成 Method 名、布尔值或真实执行许可。已有库提供共同含义，作者仅指定差异、主体和采纳的政策。

## 2. 语义生成构造：相互联系但不能合成一个 `kind`

| 构造与状态 | 真实职责 | 必须防止的错误 |
|---|---|---|
| Entity、Identity、Quantity、Value | 对象、群体、可转移资源、单位、主体生灭与等价 | 名字相同不构成同一物理/法律身份；钱和普通 Int 不等价 |
| Relation、Property、DerivedFact | 状态、关系、范围、函数依赖、集合/袋/序列区别 | 数据库字段值不能自动代表权威世界事实 |
| Event、Transition、History | 可导致变化的事件、前像后像、资源变化、历史顺序 | 状态最终满足不证明路径合法或中途安全 |
| Goal、Invariant、Prohibition | 应达到、保持和禁止的可观察结果与作用 | 静态结果不能代签进展、无干扰或无超限的全时域主张 |
| Obligation、Permission、DutyHolder | 谁何时必须行动、例外、期限、许可的法理来源 | 规范许可不是当前 Grant；已经安排不等于已经履行 |
| Observation、Knowledge、Uncertainty | 观察方法、可信度、闭合域、未知/冲突事实 | 缺记录不等于否定；无法观察不等于失败 |
| Time、Probability、Preference | 时钟、窗口、公平性、概率声明及优化依据 | 可行不等于最优；终将发生需环境进展前提 |
| Interaction、Artifact、Interface | 可访问性交互、交付的产品、布局、协议承诺 | 拥有 API 不等于拥有可用 GUI、文档或可靠运行 |
| Effect、Authority、Recovery | 签发、派发、读回、幂等和补偿责任 | 计划/生成/请求已发送都不等于现实完成 |

这些是开放生成体系的维度，不是穷举未来行业谓词。新规则通过已有类型、关系与模态构造表达时只增加领域 Definition；无法归约的原始观测/行为含义，需要新的可版本化 SemanticModule，不能在 Kernel `switch` 增行业字符串分支。

## 3. 使业务陈述可解释的准确过程

输入为不可变 `SourceSnapshot`、已接受的 `intent:goal`、锁定的 Semantic Library、明确的世界/模型和作者 Authority。按顺序：

1. 对 JSON 使用严格编码检查；保留源位置、重复键、未知版本和作者写权。提取 `roles` 与 `meaningImports`，不从显示名称推断身份。
2. 名义类型化绑定各角色；检查领域对象身份、来源、量纲及对应主体权限。不同模块引用同一 `objectRef` 才是共享对象；否则不通过猜测合并。
3. 对 `MeaningRef` 锁定 `DefinitionId + revision + 语义摘要 + 解释 Profile + 时效/模型`；版本漂移拒绝并触发相交查询/方法资格失效。代码签名一致不是业务意义等价。
4. 将每条 `ClauseOccurrence` 转成带来源的 `Obligation`: `Achieve`, `Maintain`, `Avoid`, `Oblige`, `Permit`, `Prefer` 不得互相替代。`oblige` 必含 duty holder、触发、时限、例外和履行证据；`permit` 不产生 Grant。
5. 编译条件和谓词，区别有限三值模型计算、关系查询、时间监测、规范解释及外部观察。未知或未受支持含义返回具体 Need，不生成自动的 `false`、空集合或动作。
6. 生成用于求解的派生 `ObligationGraph`、`ReadSet`、观察需求和不能自行消除的作者决定，保留稳定来源 ID 与当前 Source Revision。

返回形态应当分离 `AcceptedIntent`, `SemanticBinding`, `AnalysisResult` 与 `ExecutionReceipt`。接受一份作者意图不代表编译成功；编译成功不代表现实观察合格。所有自动发现的作者政策变动必须经过准确权限采纳。

## 4. 计算性意义、规范意义、世界观察的接口不同

- **局部可计算**：`capacity >= reserved` 可以在已知、完整且一致的局部快照上作为观察候选计算；前提是字段含义、单位和是否允许超售已锁定。
- **跨状态轨迹**：`永不超售` 需要对所有实际中间状态和并发操作给出安全合同/监测覆盖；有限模型逐步检查只提供所探索路径的见证。
- **规范义务**：`取消后 24 小时内通知` 涉及义务主体、时间源、交付方式、合法例外和送达事实。修改 `notified=true` 本身不是足够证据。
- **真实世界作用**：`银行结算成功` 需要特定 Provider、授权和读回，不因外部 SDK 返回 HTTP 200 即成立。
- **主观/开放评价**：`艺术作品好看` 需要选择评价主体、样本和方式；不能把生成器自我打分转换成客观硬要求。

## 5. 推理与事实边界

默认谓词采用精确三值 `true/false/unknown`，但这是有限观察 Profile 内的结果，不是所有逻辑的单一完备语义。开放世界事实的未记录保持 Unknown；封闭世界的否定只有在明确闭合的领域/时间窗口内可成立。互相矛盾的可信输入进入 `EvidenceConflict`，不能以字符串排序决定哪条事实为真。关系递归、默认规则、可撤回推断、统计假设与时间观察各自有具体解释者。

因果贡献也不可等同于状态相关：要从某 Method 的状态变化判断它能实现目标，需要其后置条件、帧、环境和有效观测支持；在真实世界可能有其他行动者同时改变同一状态。外部证据及规范权威由实际有权主体提供，编译器不能发明。

## 6. 开放领域的供给接缝与示例

新增陌生的比赛胜负规则：作者定义名义 `Round/Player/Score`、公开关系 `wins(rule,round,player)` 和有限规则/观察；可由已有规则引擎解释，不必添加 `game.win` 到内核。若规则要求人类裁判认定，Meaning 需绑定实际裁判观察，规划仅能得到 `NeedsObservation/NeedsAuthority` 而非自签。

同一个共享资源容量 Meaning 可以用于 GPU、病床、席位；但病床资质、患者临床批准、抢占与超售政策不能因为三者有 `capacity` 而被隐式导入。这是最小公共机制复用与不可压平领域差异并存的条件。

## 7. 编解码、升级与验证

结构 Schema 证明形式，不证明真实意义。产品中新增意义版本必须明确向后兼容还是需要迁移；旧作者源不能自动接受改变业务结果的默认解释。meaning 锁与方法资格、缓存、映射和现有执行历史相关；改含义后不得重解释已发生的旧 Effect 原因，应保留其原版本前像。

独立反例至少包括：同名异义、单位不匹配、闭合/开放世界混用、静态快照冒充长时段不变量、权限撤销、时间源改变、未知旧版本、同一业务规则的两份不相容解释、缺少专业观察，及合法新业务 Definition 不改 Kernel 的实际读取。
