# 业务意图直接生成源码：受界降低与有限合成

本文保留 Gift117 研究中的具体 lowering 与有限合成算法；本包不运输原脚本或重验历史运行证据。现行作者须按 `/2` Owner 读取；下述 `/1` 有限输入属于版本化研究画像，不能成为第二 Writer。

## 所解决的确切缺口

用户的目标是：陌生业务的作者直接描述公开结果、规则、约束和行为，而非书写控制流或目标语言代码；Gift 根据已知、可检查的 Meaning 和实现供应生成完整可维护源码。Gift116 的 `build_replanning_app.py` 原先只是冻结合同，将预写的 `runtime.ts` 替换一次 SHA 后复制到目标工程；业务谓词和 Method edits 在目标程序里仍是动态 JSON `op` 分派。**这证明了带意图数据的通用执行器可运行，不能证明业务语义已按其实际含义生成目标源码。**

此降低设计以 Gift112 的版本化作者意图、Meaning、Method、模型输入为受界画像，语义代码生成器按以下步骤工作：通过 Gift116 的 schema/类型/引用/资格门禁取得不可变合同；对每个 `intent:goal` 的 clause 和每个供应 Method 按本体结构递归降低成目标 TypeScript；编译输出 `src/logic.ts`，包含针对本次业务的 `compiledObserve`、`compiledPrecondition`、`compiledEdits`。`src/main.ts` 仅保留通用 BFS、操作身份、SQLite 状态与原子事务，没有运行时业务表达式解释器。所有名字都作为安全编码的字符串被引用，而不是作为可注入的 TS 源代码片段。

这依然是**小范围 lowering 设计**：只接纳 `gift.intent-body/1` 的 `achieve/maintain/avoid`、`finite-model-expression` 的 `literal/field/eq/lte/gte/all/any/not`、公式的 `call/all/any/not/implies`，及 `set/addInt` 的有限本地模型 Method；其它语义不得因为存在相同名称就自动转换。

## 所用数据和实际算法

编译器依次读取用户模块、内容摘要锁定的 Meaning、Method 供应和有限模型。固定每一个函数/谓词参数的类型及作用域；所有 `meaningRef` 经真实导入与摘要解析；若谓词解释仅提供名字或真实世界 Observer，停止为 `NeedsMeaning/NeedsObserver`。将 clause 的业务角色绑定成当次对象引用，将 Method 的参数角色绑定到执行时选择的对象；在编译期将 `call(meaningRef)` 内联为具体表达式及参数绑定。**不以行业标题推断逻辑**。

表达式 lowering 示例（仅说明真实编译结果的形式，不是额外作者语法）：

```text
Meaning: cap-within(resource) := resource.reserved <= resource.capacity

compiled TS:
  toTruth(lteVal(
    field(model, "bed-1", "reserved"),
    field(model, "bed-1", "capacity")
  ))
```

`lteVal` 使用精确 BigInt 并在缺值时保留 `unknown`；不能经 JS Number 静默丢精度。`eqVal` 保留 Bool/Text/IntString 基础类型区别。`allTruth/anyTruth` 使用原参考的三值演算并强制保留原求值结构，不用 JS `&&`/`||` 静默改变 `unknown`。Method edit 按作者顺序生成实际赋值或加法，执行后由现有通用目标代码验证名义类型、字段、公开不变量和状态修订。这些检查属于局部执行，不证明现实副作用。

目标产物组成：

| 产物 | 内容拥有者与修改规则 |
|---|---|
| `contract.json` | 编译器派生、锁定意图/Meaning/方法/模型，不是新作者输入 |
| `src/logic.ts` | 编译器根据本次 Meaning 和 Method 真正生成的专用业务函数；不得手工写成第二份权威 |
| `src/main.ts` | 可复用的有限搜索和 SQLite 协调基础设施；不能将其复制行为冒充语义合成 |
| `package.json`, `tsconfig.json`, `build-manifest.json` | 编译产物，严格 TypeScript、Node 运行范围与当前源 digest 绑定 |

发射以目录存在检查和同文件系统临时目录写完后改名为原子工作区的最佳可用发布形式，不覆盖已有受管/原生工作区；生成成功仍须独立 `tsc` 和执行核验。

## 在没有显式 Method 时，什么能真实自动获得

有限合成器只采用一类**限定范围的构造性方法合成**：若有明确 `achieve P(entity)`，且 P 的实际解释是 `entity.field == true/false`，对象字段是 Bool，且外部本地模型 capability 明确允许对该类型字段执行 `setBool`，则生成对应赋值 Method；可选守卫也必须来自已锁定的 Meaning，被编译为前提。目标方法仍重新通过来源、类型、前提和局部效果门禁，由联合规划器检查全部 `maintain/avoid` 才能作为模型方案。具体方法的源码不是预写的业务模板。

此能力与任意算法合成**不是一回事**。想让 `capacity` 的占用与所有请求状态一起变化，就必须提供相应资源业务不变量和可用动作的语义；只写“请求确认”不能推知是应该增加计数、发通知、调用第三方系统，还是取得人工许可。想要真实发布文档时，必须有发布渠道、授权签发、前像及读回，写入 `published=true` 的本地字段只是在模拟事实。没有这些供给，正确行为是准确返回缺口。

这说明“通用语义”和“自动实现”是两个独立维度：开放定义保证新意义可接入；实现发现、规范约束下的组合或有限合成决定是否有可用程序；Source Lowering 保证已有合格实现被转换成目标源码。**不能从第一项推导第二项，也不能从可编译的目标源码推导现实效果**。

## 必须独立取得的针对性反证

实际实现须在文档、共享容量（病床 + 计算任务）及独立引入的 `SignalCase` 新类型上编译运行，且无 `if hospital/doc/signal` 分派。文档场景中已审批允许生成本地发布状态，未审批时守卫阻止；删除写权限则返回 `NeedsImplementation`。新类型的 goal/Meaning/guard 不改代码生成器，也能生成字段专用 TS 和执行。

负例还必须继续覆盖：未绑定 Meaning；没有可写范围；无可用 Method；错误类型；预算中断；未经批准的模型动作；联合安全失败；相同目标但不同输入副作用；竞争提交；改变 Meaning 内容但复用旧摘要；及不被有限模型涵盖的真实授权需求。只有实际执行后，这些特定输入才取得对应证据；不能据此证明任意可能需求的可满足性与最佳实现。

## 根问题的完整解决还需要的工程（未冒充完成）

1. **Meaning 的开放表达与可组合语义。** 不应把原本不存在的商业对象、角色、关系、时间、流程、收费、权责和实世界观察缩为当前 Bool 状态机；需要定义这些对象的解释、作用范围、版本、与旧定义的兼容及错误。
2. **实现供应的真实索引和能力资格。** 现成数据库、规则、SQL、求解器、工作流、UI、原生服务和领域包，需有可机检的输入/输出、错误、效果、授权、环境、数值与资源前提；不是仅登记一个名称或 `verified=true`。
3. **带全局条件的方法选择/组合与合成。** 方法合成只对已给定语义和有界、可求解的子域承诺结果。冲突、不存在合格实现、预算耗尽、缺事实、缺权、没有观察者必须可区分；只要新意图使用旧构造，不要求改内核业务分派。
4. **真正的产品架构与目标。** 支持生成多个业务服务、数据库模式/迁移、适配器、API、交互、发布器和测试/证据，而非把每个应用都塞入一个固定的状态机运行器。组合型程序中的跨效果、失败恢复和版本升级必须检查全局不变量。
5. **开发者的作者负担必须测量。** 对已资格化业务习惯，开发者不必反复写方法和算法；对新现实义务必须指出必须由哪个有权主体给出哪项事实/实现。自动选择不应掩盖需要作者控制的行为差异。
6. **生产证据与取舍。** 与真实成熟实现对比源码质量、维护成本和长期修改；观察部署、真实效果读回与恢复。没有实测不能称高质量或一键通用。实际自举取决于这些真实能力的消费闭包，而非目录或开发语言的名字。

因此这里保留的是**受界且可独立核验的语义到源码生成机制**，其算法的明确性不表示当前已有通用意图编译器。它应该成为后续可扩展 Target Lowering 的具体参考，而不是让持续运行、缓存或自举替代核心任务。
