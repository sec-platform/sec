## 从业务意图开始的产品主施工路径

优先实施[第17章：意图解释、合格方法匹配与装配](17-意图优先解释与现成方法装配.md)，再按真正被选中方法的需要调用第02—15章相交模块；第16章一般计算编译器是专业方法作者的可选供给路径，不作为普通业务作者入门或意图自动化必需前置。离线参考见[Gift112](../../../fixtures/intent-language/Gift112/README.md)。有限模型示例不代替真实 SQL/规则/工作流/求解/AI/Provider 的资格。

这不是在现行语义规范上再建立一套规范，也不是项目管理待办。**本目录只拥有工程施工设计：源代码应建立什么、接口如何连接、每一步按什么算法执行、输入输出存在哪里、失败后怎么恢复、怎样把有限能力交给用户。**规则的唯一语义 owner 仍在同包的作者、语义、编译、目标、执行、保证和演进文件。若施工说明与原 owner 语义冲突，先按实际机制修订责任文件及这里的实现方案，不让实现者自行择一执行。

本手册是完整 Gift108 的增量施工投影。`kernel/`、`control/` 等是**目标工程目录**而非 ZIP 已有编译器源；源码仍应先核对真实仓库，不能把本包的 Python 查询工具当成编译器。所有下述 Rust/TypeScript 形状都是**待实现的内部 API 设计**；已公开的 `gift.*` 机器协议沿原 owner 与 `schema/`，不能拿本目录示例代替发布 schema。GitHub 历史路径只作为迁移事实，不能提升为 Gift 公共语言语义。

## 施工文档的通用阅读约定

- **作者字节和源码身份**由 workspace 接管，**意义与类型**由 semantics 接管，**方法选择与生成**由 compiler 的对应职责接管，**外部动作**由 execution 接管，**是否成立的保证**由 assurance 按独立证据判定。Application 负责协调，不作为第二实现者。
- 函数、字段、表名若已公开，以相交原 owner 为准。本手册中的 Rust 结构和 SQL DDL 是落实该 owner 所需的**内部实现形状**，不擅自新增对外协议；凡有冲突，先精确定位和修订，而不是混用两个版本。
- “必须做的检查”不等于每次用户编译都必须触发。纯函数预览可以无持久状态；效果执行、授权和持久账本只在相关请求进入时装配。结构冻结与产品级行为测试分开。
- 设计中给出目标工序、完整算法、状态、异常、资源和验证位置，不承诺任何未实现模块已运行。尚无当前仓库/工具链/真实 Provider 证据处保留 `UNKNOWN`，不能靠默认值填平。
