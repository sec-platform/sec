# 12 Gift 如何从真实源码进入可信自举：选择消费者、桥、C0—C3与撤回

## 1. 明确自举范围，不把原生透传算语言自用

工程自用：Gift 管理自己工程的作者源、构建和某些原生源码；不自动形成语言自举。语言自举：Gift编译器的一项实际算法/编译职责确实由Gift作者计算语义写出，再由早期编译器编译成目标程序，与原真实消费者对接。可信自举：进一步获得固定种子、独立编译/比较、污染追查和回退证据。这三层各有实际不同的产物、失败和资格，不能由一条“自托管：是”字段代签。

目前 Gift108 已选择只读观察到的 SEC 仓库 `sec-platform/sec` 版本 `0536dca0da634fe26fe175bc4694883f966ae356` 中 `src/compiler/resolve/manifest-graph.ts` 的 `resolveManifestGraph` 及其真实消费 `prepareManifestResolution` 作为**已选定的首个部分自举迁移职责**。这只是当时观察的坐标：实施前必须回读当前准确commit、owner/consumer、脚本和所选Node/TS版本，不能用本设计ZIP宣称仓库已合并或生产迁移已完成。

## 2. 此职责实际需要实现什么

`resolveManifestGraph(explicitEntries, catalog)`的输入是经过上游校验/捕获的ManifestEntry集合，不负责读任意磁盘或安装依赖。它必须保持原消费者观察到的：选中条目唯一性/版本冲突、要求能力提供者闭包、无提供者/歧义诊断、全部已选provider依赖边、冲突要求和**在动态就绪集合中持续选择最小rank**的拓扑次序。rank按kind优先级与UTF-16码元比较决定；不能把图按层级粗排序替换，因为两者在动态新节点就绪时可能生成不同序列。

图中存在环时，旧行为携 `blockedBlockIds`，其中可能有受环阻塞的后继，而不保证列出的每个点都在环内，更不能将其称为最小环见证。输入和这些既有可观察错误都必须由迁移的Gift算法保留，目标运行已被明确限制的行为才允许提升为新要求，不因为换语言而随意改错码或顺序。

## 3. 从旧实现提炼无损的 Gift 作者工程

施工如下：

```text
1. 读取真实版本的source、依赖、测试、消费者和运行目标，固定不可变baseline。
2. 建立适用的 SourceProfile/Type/Function Definition；将公开数据类型和错误码保留为可引用身份。
3. 在Gift通用计算体中实现集合闭包、provider选择、图与heap/排序等实际算法；
   如某构造尚不被语言支持，选择真实Method/合法ExternalExport或开发相交语言能力，
   不把整个函数原生TS源码嵌在字符串里冒充Gift实现。
4. 用Gift的新source生成目标TS函数/模块，保留公共入参、返回、错误、依赖与源码位置。
5. 用同一冻结输入比较旧函数和生成函数：选取合法/非法输入、枚举的边界图、动态rank变化、冲突、循环与错误。
6. 成功且具资格后，接到真实prepareManifestResolution消费者；留下可立即切换的旧版本。
7. 重复不同输入及工具链条件，把新算法/消费者的真实覆盖计入自举台账。
```

代码落点：当前仓库原文件需经实际上游迁移计划映射到未来`kernel/src/semantics`或`kernel/src/realization`相关职责；不能把 SEC 的历史TS物理结构直接宣称是 Gift 最终项目树。新函数引用的标准库严格按实际使用根闭包取得：List/Map/Set/Option/Result、比较、priority ready-set、错误、函数值及必要整数/文本，**不为了自举预先加载医疗、金融、UI或设备Provider**。同理不能因首个自举函数只用图算法就把语言限制成图语言。

## 4. 种子与固定点的实际可操作算法

固定 `S`：Gift写的编译器作者源及必要库，`D`：方法/解释/库/target绑定，`H`：原生构建工具及运行库，`P`：目标三元组、优化选项、路径/时间规范、平台与比较政策。在同一个冻结输入上执行：

```text
C0(S,D,H,P) -> artifact A1 ; build_H(A1) -> compiler C1
C1(S,D,H,P) -> artifact A2 ; build_H(A2) -> compiler C2
C2(S,D,H,P) -> artifact A3 ; build_H(A3) -> compiler C3
```

分别比较A2/A3的真实全部目标成员，C2/C3二进制在声明范围内的比较并单独记录可接受/已调查的构建噪声。源码/二进制相同不能代替编译器语义正确、目标安全或现实系统合格；若只证明一项部分编译职责，则自举声明必须只覆盖它。C0及配套工具来自实际可信来源而非文档模板；没有真实种子时只能提供待取得的数据字段，不编一个看起来完整的hash。

## 5. 新语言能力的桥接升级

若当前C0还不认识作者源所需要的新构造X，不能用X写一个“验证C0能够读X”的测试让它给自己签成功。正确路径是先用旧语义B实现能检查或翻译X的bridge，得到实际可运行的新消费者后，采用含X的作者源，再走真正的stage比较。bridge的源、工具、能力、构建结果和退出条件全部留在依赖闭包，不能简单把新语法schema添加到旧文件就认为旧Compiler能理解。

## 6. 可回滚迁移与采用顺序

首先以 `prepareManifestResolution` 的旧TS实际调用为准建立兼容墙；迁移的新Gift编译职责并排输出预期数据，保留旧实现单独可构建。生产切换采用明确一个写者与某一时点的调用绑定，失败时可以回到仍合格旧消费者；切换后发现新旧语义不等价时不靠“自举已完成”拒绝修复。旧依赖退役需以实际import/consumer、CI及源码版本读回证实，不能靠文档路径删掉历史正确代码。

## 7. 能够宣布哪一种结果

- 仅生成漂亮TS源码：`target source example`，没有实际替换或自举。
- 生成并独立编译运行且满足有界测试：`qualified first responsibility within observed scope`。
- 真实消费者迁到由Gift编写并生成的算法：`partial language self-hosting`（计入所覆盖实际职责）。
- C0—C3全阶段通过加独立挑战：可以报告准确条件下的`stage fixed point`和额外可信证据，仍非任意意图合成/绝对安全证明。

这份设计不主张当前仓库已被修改。任何施工时实际新反例需要返回原 `确定性与自举.md` / `仓库迁移与自托管.md` 更正公共机制，再修本蓝图。

## 自举职责的作者分解、适配参数与阶段产物比较

`resolveManifestGraph`仍是已选定的首个部分自举迁移职责，而不是整个语言能力定义。当前包继承的仓库坐标是一次历史观察；本轮没有重新读取远端状态。进入真实替换时，先比较函数源、上游校验和真实消费者是否仍匹配；变化只使迁移适配重新核对，不撤销“必须由真实Gift计算承担职责”的选择。

作者模块按算法真实数据分成：`manifest-types`定义Entry/Capability/Conflict/ResolutionError；`provider-index`负责每条manifest内能力去重和倒排索引；`closure`负责显式选择、唯一候选递进与版本冲突；`order`负责构边、rank和最小ready堆；`resolve`组合上述定义并导出原责任函数。它们是普通作者模块，不是增加五个Kernel业务种类。输入的`ManifestEntry`仍来自已校验的旧reader；新函数不夹带文件读取或安装行为。

闭包算法的状态明确为`selectedById, selectedProviders, pendingEntries, catalogProviders`。先按原显式输入次序接纳：相同ID且原规范相等的条目只保留一次，不等即冲突；每次接纳把其去重provides加入selectedProviders，追加队列。按队列顺序逐requires：已存在选中provider则继续；否则在目录找，零个缺失、多于一个歧义、恰好一个但该ID已有不提供所需能力的旧版本则冲突，不能静默升级。合法唯一新条目进入队列。队列耗尽后检查选中条目宣告的ID冲突与能力冲突。

排序将所有选中条目按原kind优先级和UTF-16码元ID比较一次得到唯一rank。每一需求对**所有已选provider**建立provider→consumer边，排除原合同规定的自边且去重；以入度零的rank建立小根堆。每次弹最小rank并递減后继入度，刚成为ready的低rank可立即先于早已ready的高rank输出，不能改成层序。未排完时返回全部未调度ID的原口径，不声称它们全部在环上。其复杂度为索引/构边实际规模加排序和堆操作成本；能力的多provider会扩大实际边数，不把边数假定为manifest条目数。

跨语言适配保留原生输入观察：未知且未消费的字段可由原上游reader持有，新结果返回对应被选输入条目的稳定索引或受限引用，适配器据此重建原entry，不凭JSON重新编码丢掉原字段。对象引用身份是否属于消费者可观察要求必须实际检查，不能因值相等就当然保留。ID比较使用显式UTF-16码元迭代，不以Rust默认Unicode标量比较替换；错误代码、相关ID、歧义候选顺序依原合同。原Reader继续拥有任意输入验证，新算法的较窄受权输入边界应出现在适配签名。

`BootstrapInputs`是阶段构建的内部捕获对象，字段为`sourceClosure, dependencyLock, seedBinary, seedOrigin, nativeToolchain, buildTriple, hostTriple, targetTriple, invocation, allowedEnvironment, comparePolicy, recoveryRef`。缺实际值返回输入缺项，不在源码里预填假hash。build表示运行构建命令的环境，host表示所得编译器运行环境，target表示它生成的代码环境；交叉编译阶段要分别选择能运行的编译器，不可直接在build机器运行异构host二进制。

StageRunner接收固定输入与上阶段编译器，只做`materialize read-only input→invoke compiler→capture target source set→invoke native build→capture binary set→record observation`。每个阶段用新owned staging和独立输出路径；失败不把上次stage残余文件混入本次成员。比较先核完整成员集合，再逐成员字节；可归一化的时间、路径等必须在开始前写入comparePolicy并说明为何不改变意义，禁止失败后临时增加排除项。源码集合与二进制集合分别比较并记录差异位置，不能用其中一种一致代签另一种。

标准库从这些真实模块的调用闭包建立：精确整数、序列遍历、显式比较、Map/Set所需Hash/Eq或有序比较、Result和错误构造、heap内部函数。Map/Set的哈希种子可以是内部防攻击策略，但返回的公开序列不随哈希迭代随机化；需要确定顺序时显式排序。标准库函数可用合格原生实现，不因此把整个编译职责算成原生透传；清单必须分别记录实际Gift计算和原生余部。

迁移采用双实现只读对照阶段时，副本不能执行真实安装或其它效果。比较失败保留旧生产调用；匹配且其它准入成立后，原调用点只选择一个有权写者。切换和撤回均固定到真实源码/依赖/工具链版本；旧reader、旧恢复程序与回退产物在确认不用后才退役。设计本身不创建分支、提交、runner或部署。
