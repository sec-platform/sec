# 22 意图产品：生成、装配、二次修改与真实恢复

> 本章是实际交付施工；作者源与 `Definition` 仍是单一权威，Artifact/SourceMap/Grant/Operation 的身份与现行 owner 保持不变。下面的源码构建步骤是待实施设计，不是 Gift113 已存在的 TypeScript 生成器。

## 1. 不是“把意图句子编译成一大段代码”

一个真实产品通常同时需要：数据对象及迁移、规则/策略、对外服务端口、状态/工作流、用户界面、权限、可观测性与打包。Gift 应依据实现供应选择进行**合格目标装配**，而不是强迫所有业务变成 Gift 内部通用计算 AST、再重新发明库与执行器。

```text
Author Intent / Meaning & Policy locks
    → JointObligationGraph (+ authenticated world facts, pending Needs)
    → Qualified Capability/Method Plan
    → Deployment/Target Assembly Graph
      {existing packages, configurations, generated wrappers,
       data schema and migrations, required UI, runtime service ports,
       effect provider bindings, observability, emergency policy}
    → Complete ArtifactSet + dependencies + SourceMap
    → target-native build/check + independent behavior/fault qualification
    → explicit authorization & publish / runtime monitoring
```

**完整产物**是其声明的交付根可独立构建/运行，并包含实际需要的所有依赖；不要求包含作者未请求的 UI、数据库、后台守护进程或 Remote Runner。已有合格方法以配置/绑定方式复用，必要的生成代码尽可能只承担接口转换、注册和可维护 glue。不得输出 TODO/stub 而宣称目标完整。

## 2. AssemblyPlan 最小机器合同

```text
AssemblyPlan {
  sourceSnapshot: exact SourceRef/Revision,
  intentRoots: immutable accepted Intent refs,
  semanticBindings: Meaning refs/digests/scopes,
  realizationBindings: selected Method/engine/version/qualification refs,
  targetPlan: target triple/runtime/version/dependency locks,
  components: [
    ExistingPackage, AdapterBinding, RuleBundle, QueryBundle,
    StateAndWorkflow, GeneratedSource, DataMigration, UIComponent,
    DeploymentConfig, ObservationAndRecovery
  ],
  obligations: remaining build/authorization/effect/assurance Needs,
  provenance: per output occurrence/source ownership & readsets,
  publication: atomicity scope, candidate digest, rollback/reconcile policy
}
```

上述节点是*按需的逻辑组件类别*，不是所有项目必有的服务或独立进程。`Method` 的实现可以直接由原目标编译器编译、由 SQL 引擎解释、由工作流引擎执行、由规则引擎求值；只有支持声明目标的具体 Target Adapter 实际接纳其节点，才能进入完整 ArtifactSet。

## 3. 一个产品的具体装配示例：共享容量预留与取消

作者意图：合格用户可预留有限容量；总占用不超额；同一请求不会重复占用；取消后应释放资源，并根据业务规则通知有权主体。业务角色是 `request`, `resource`, `actor`, `subscriber`，依附准确 Meaning 和对象身份。

Method 选择可组成：

- 资格查询：已锁定规则引擎/数据库关系查询；权限由真实 Host Grant 查询；未知资格不能当允许。
- 占用：单 DB 的原子预留适配器，返回 `Granted/Denied/Unknown` 三类受类型结算；重复操作使用原 ID 的 receipt。容量是该事务实际保持的硬条件，不是只在规划器观察一次。
- 取消：有权者发起且有清晰退还/释放规则；无法证明前像时必须读回；费用补偿/通知是另外的具名效果。
- 可用界面：若意图要求 UI，生成路由/状态绑定到选择的 UI 组件及可访问性合同；若只要 API，则不得凭默认模板强迫生成前端。
- 观测：记录每次操作的来源、事务版本、外部主体回应、未决和重试范围；不把工作流状态 `DONE` 等同于第三方现实执行已发生。

产物可以是已有 SQL migration + 业务规则模块 + API 适配器 + host 授权与事件记录，**不必再通过 Gift111 的泛型递归语言**。生成的 TS/Rust wrapper 严格依据选中能力的公开签名/ABI 生成，任何未知输入名或 Method 缺失应在构建前拒绝。

## 4. 具体编译/构建接口

```text
lower_assembly(assembly, target, lockSnapshot):
  validate all selected Method/Meaning/Target revisions and their actual consumers
  expand only the selected component dependencies; reject cycles outside legal contracts
  for each component:
    if existing native package: emit pinned package binding and ABI adapter
    if query/rule/workflow: emit target's qualified declarative artifact
    if generic glue needed: emit typed source with precise input/effect contracts
    if unsupported target construct: return NeedsTarget, not placeholder
  generate SourceMap from each target member to original Intent/Method source
  verify dependency/import closure and all emitted members have one owner
  run target-native build/check, compare any applicable semantic/effect oracle
  produce CandidateArtifactSet with manifest and exact digest
```

Rust Kernel 的源分析与 TypeScript 目标的输出不能因为都用了 AST 就共享不合格的内存/错误/线程假设；源文件可使用已有原生代码，保持用户区域不可覆写。目标输出必须显式定义 SourceMap、调用错误转译、兼容性、持久化和真实运行宿主，不能只通过 `tsc --strict` 就签业务目标正确。

## 5. 二次修改的必需行为

修改一个 Clause（例如“允许超售”改为“绝对禁止超售”）时，流程不是全量重写代码，而是：

1. CAS 更新唯一 AuthorSource，保存新旧词义锁及来源 Diff；未授权修改拒绝。
2. 重建相交 `Meaning/ObligationGraph/Capability` 查询；撤销失效方法/证据及受到影响的目标成员，保留未变的计算/原生用户文件。
3. 在新的完整联合要求下重新选择方法。旧方法可能从合格变为不合格；若找不到替代，精确 `NeedsMethod`，不会在已有运行实例上悄悄改政策。
4. 生成候选成员、逐文件源映射和迁移计划。数据格式改变必须有可执行迁移、旧进程共存/回退边界；不能把设计中的“可兼容”当作已验证现势事实。
5. 构建、差异观察、用户/批准者采纳后发布。已经发生的外部操作仍以旧语义/方法/授权版本结算，不能重新编译即抹除历史。

生成区的手改只允许受资格反向改写或显式迁出为原生源；没有资格不覆盖。原生来源、作者源、运行状态和证据是不同所有权，不通过字符串替换同步。

## 6. 事故与恢复：候选、提交、效果并非一步

区分纯计划、已构建候选、候选发布、外部授权、已派发未知、已读回结算。

```text
Draft -> AcceptedIntent -> QualifiedAssembly -> CandidateBuilt
  -> PublishedVersion
  -> (GrantChecked -> OperationPrepared -> Dispatched -> Reconciled)
                                                \-> UnknownOutcome
```

- 多文件原位覆盖不天然原子；使用目标支持的版本目录/指针切换或有快照的事务方案。对非合作写者和符号链接目标必须明示隔离边界。
- 外部 effect 调用先固定持久 operationId、authorizer、输入/Method/Policy 版本、前像与幂等范围；重复调用按原身份读回，不重新派生 ID 盲试。
- `UnknownOutcome` 不能在消息传输成功后改标为 `SettledSuccess`；只允许受权读回/独立观察使状态前进。补偿不是回滚，而是新的受权 effect。
- 取消与资源释放需等待实际底层回调/引用生命周期，不能因为 UI 不再等待就提前卸载原生代码/释放锁持有者。
- 失去 Grant 的后续执行被禁止；旧状态已发生事实不被撤销。秘密不应被诊断和 SourceMap 泄露。

## 7. 正式验收边界

纵切工程应能用同一 AuthorSource 产生完整可构建目标、至少一种真实局部状态操作、读回/恢复和第二次规则修改，再独立核对运行是否符合合同。Method 换引擎后在相同声明观察范围做对照；同一 Artifact 不能靠生成器自己验收自己。

本轮 `Gift113` 仍只有模拟联合计划，没有把外部数据库、工作流、Target/Provider 接成真正生产制品；这些是实际编码与环境资格事项，不应以文档增量宣称完成。
