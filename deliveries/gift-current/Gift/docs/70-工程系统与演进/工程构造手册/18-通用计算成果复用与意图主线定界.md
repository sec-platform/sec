# 18 通用计算成果的真实复用、退出与意图主线

> 工程施工与资产裁决。本章回答此前为 Gift 编写的通用计算设计是否有用，以及何时不应再继续实现一门新计算语言。产品作者意图主源仍由[通用意图语言](../../20-语义与组合/作者语义/通用意图语言-意图源与语义组合.md)唯一拥有；实际计算语义继续由原基础语义 owner 维护。

## 1. 核对真实连接，而非根据概念相似臆测

现有 `fixtures/semantic-universe/Gift111/giftcore/{core,interpreter,emit}.py` 是独立的作者 `gift.semantic-body/1` → 类型/合同/解释 → TypeScript 参考实现，拥有自己的 CLI/样本/测试。`fixtures/intent-language/Gift112/intent_reference.py` 独立解释 `gift.intent-body/1`、Meaning Library、有限对象快照和模拟 Method Offer；**未调用 Gift111 的 `giftcore`**。因此，不能把 Gift111 的测试通过推成 Gift112 已拥有的通用意图到源码能力。

已投入的设计资产按*真实消费者、未来可替代供给、继续建设的必要性*处理：

| 计算或工程资产 | 与意图直接相关的复用 | 当前真实实现 | 后续技术取舍 |
|---|---|---|---|
| 名义/结构类型、参数签名、模块引用、身份、版本和词法绑定 | 验证意图主体/观察参数/模块版本，阻断错绑、同名异义 | 两套参考程序有各自局部检查，并非统一生产读者 | **基础必需**，复用成熟 JSON/类型工具和既有设计，不等于全部 Gift111 语法要进前端 |
| 逻辑谓词、关系、有限量化、单位、表达式求值 | 定义可观察业务含义、方法前置/保证、硬禁令及校验 | Gift112 有受限表达式与三值快照解释；更完整逻辑体系主要是设计 | **基础必需的可选解释后端**；为每个适用域锁定完备性/读集/未知，禁止一个万能布尔求值器 |
| 数据模型、查询、规则/约束与优化 | 查询事实、评估条件、决定/组合方法 | 有设计、已有若干局部样本，无全产品 Method/Provider | **优先复用现成引擎**；Gift 维护 Meaning→引擎能力的资格适配，不重复手写执行引擎 |
| 普通函数、递归、高阶函数、ADT、模式匹配 | 缺少已有能力时实现一种新的算法或自定义 Method | Gift111 实测有限纯计算与 TS Lowering | **可选专业工具**，只在实际被选方法需要时装配，可由原生 Rust/TS 等替代 |
| 效果、任务、内存/寿命、并发和错误传播 | 对接真实效果、服务调用、事务、回滚、资源与工作流 | 有完整设计；Gift111 不实现外部效果 | **必要的契约层**，主要交给宿主及成熟 Runtime/库执行；不需要所有作者编程这些细节 |
| 通用编程语言全编译器、高级类型、自己的 LLVM/机器码、自举 | 当且仅当 Gift 实际要发布和自编一种通用计算语言/自举功能 | 目前不是已部署 Gift 产品能力 | **退出意图产品默认关键路径**；不因历史投入追求补齐功能计数 |
| JSON→TypeScript 目标生成、SourceMap、增量与受管更新 | 生成必要的胶水、适配器、产品模块，并确保第二次修改可维护 | 分散局部生成器，缺完整业务意图产品输出 | **需要建设的工程能力**，但不表示所有业务必须经过通用计算 AST |

## 2. 三种“可用”的严格区别

1. **概念资产可用**：类型、契约、确定性、目标兼容等推导可直接指导意图平台；不等于现有 Python 函数被调用。
2. **代码复用可用**：在准确输入/版本/权限下，通过适配器实际调用并取得结果；这轮现有意图参考未接 Gift111，必须标记“待接入”。
3. **生产产品可用**：生产 Rust/TS 消费者、目标构建、授权、现实执行/观察、修改和恢复均有独立证据。此前的 fixture 不支持这一结论。

过去并非完全白做：`Gift111` 的名字解析、精确整数、泛型与纯函数生成已帮助暴露实现边界。**但相同功能若由现成库提供，更理性的产品决策是使用库，不让业务作者或 Gift 重新学习/维护这整套语法。**对原设计正确内容采取保留和定位，而非删去事实或追随沉没成本。

## 3. 最小的计算接合标准

实现供应方必须发布一个被 `CapabilityOffer` 引用的 `ImplementationHandle`：

```text
ImplementationHandle {
  owner: library/package revision & content digest,
  interface: typed input/output + effect + error + ABI profile,
  callable: native-symbol | interpreted-rule | sql-query | workflow | solver-model | gift-compute,
  environment: exact toolchain/engine/runtime and deployment constraints,
  assurance: independently supported claim(s) and assumptions,
  lifecycle: cancellation/retry/idempotency/readback/upgrade where relevant
}
```

- `gift-compute` 是**可选的一种方法实现语言**。其函数由旧 `giftcore` 读取还不够：要有从受类型 Intent Meaning 到此函数的**显式语义适配与资格**；不能按函数名称启发式匹配。
- `native-symbol` 与 `sql-query` 不应首先转成 Gift111 的递归 AST 再发射目标；保留原生态优化/所有权及 ABI，Gift 只生成必要的绑定/胶水。
- Method 的 `ensures` 并非自报即可通过；精确覆盖范围需要可重复检查或足够的有权合同及运行证据。`NotQualified` 不能以 `compiler emitted code` 替换。
- 类型检查能确认签名，不能凭此推导任意业务事实、真实权力或算法满足要求。未解决时输出 `NeedsMeaning/NeedsMethod/NeedsQualification` 等准确层级。

## 4. 不需要制造一门完整新编程语言的替代实现

假设作者要求“合资格请求可预留一项资源且总占用不超容量”：

- Meaning 层定义资格、请求、容量和不变量，规范层定义归属和观察；
- `SQL` 适配器可选择合格的事务 CAS/行锁方法；在只能访问外部资源 API 时选真实 Provider 并确认幂等/读回；
- 需要复杂时间与人工任务时选耐久工作流引擎；需要最小成本排班时选有资格的约束求解器；
- 只有现有引擎无法提供必需业务运算时，才由专业作者以现成 Rust/TS 或 `gift-compute` 实现新方法。

算法选择不是让业务作者填写 SQL 方言、线程锁或 Rust 函数；**业务性质确定，实现是可更换、可拒绝、可比较的供给**。

## 5. 投入、退出和未来重开条件

意图平台的默认实施里程碑以“未见过的新业务概念能否描述—正确绑定—自动复用合格现成能力—装配可维护产品”为中心。不得把 Gift111 新增多少 AST 节点、支持多少高级类型或通过多少编译器 fixture 当作业务意图完成率。

真正需要重开通用计算语言投资的条件：现成生态无法表达明确且频繁需要的 Method 功能；自定义 DSL 能取得有依据的可验证、性能或维护收益；替代实现/迁移成本已实测；且仍须保持原生方法可互换。否则冻结计算语言新特性的默认优先级，仅修复已被真实消费者使用的部分。

**不删除任何正确历史成果。**Gift111 fixture 在包内保持原有身份、代码和验证说明。Gift113 新的联合意图模型不依赖它，不是否定旧计算原理，而是把产品执行责任重新放在正确层次。
