# 03 严格作者源读取、版本身份、锁解析、结构化编辑与无损保存

## 1. 实际输入不是只有一个JSON对象

用户项目可能同时含 `gift.project.json`、若干当前 `gift.author-module/2` 的 `*.module.json`（旧 `/1` 仅读取），研究性 `.gift` 文本（不具有当前业务 Writer 资格）、已有原生 TypeScript/Rust 文件、资产、`gift.lock.json`、控制文件、目标配置和尚未保存的编辑器缓冲。每份文件都有独立的 owner/SourceProfile；一个 JSON 文件并不因文件名包含 gift 就一定是Requirement。**不得把整个仓库扫描后所有JSON扁平化为一个巨对象**。工程清单通过 sourceScopes 发现模块，模块的 moduleId 是其身份，已选锁固定解释供应；缺失锁是待固定解释或重锁意图，不得自动从网络抓取最新版补齐。

输入对象的顺序是：来源发现→源权限及根目录隔离→一次一致读取或明确非一致拒绝→strict lexing/decode→外壳 schema→锁与语言映像绑定→模块语义解析。不同错误要指向相应拥有者，不让非法UTF-8被替换字符静默“修复”。

## 2. source capture的可直接实现算法

建议 `workspace::captureProjectView(projectRef, buffers, sourcePolicy)`：

```text
1. 固定ProjectRef和本次身份/允许读取的SourceScopes，获取工作区基线与用户缓冲修订。
2. 读取项目清单的原字节及文件系统元信息；限制总文件数、目录深度、单文件/总字节、时间与挂起IO。
3. 用严格UTF-8读取清单，检查BOM/重复键/深度/字段/精确schema profile；拒绝不受支持的封闭根字段。
4. 按清单确切的module/asset/target引用枚举相交文件；路径校验只允许指定根内实体，核symlink/硬链接别名、平台大小写折叠及已授权sourceOwner。
5. 读取文件的真实字节或指定editor overlay字节；记录每份文件来源、原始摘要、所见OS revision/epoch及未取得的状态。
6. 对需要同一个修订闭包的文件执行宿主snapshot/读前后源epoch复核；若无法取得一致视图，不假称原子，只返回可重试的SourceDrift/NeedsSnapshot。
7. 将字节写入不可变内容库并建立有域的ProjectView。未解释模块先原样保留，完成读取本身不等于语言或目标资格。
8. 锁内容与本次确切使用的SemanticModule/Method/Target配置互证，解析导入和公开身份；没有权威含义时返回NeedsMeaning/NeedLock，而不是猜schema字段。
9. 按SourceProfile路由至相应parser/CST或结构树。原生语法不认识时保留原生字节及读取的公开合同，不让通用JSON reader改写原生文件。
```

在 Windows 文件系统上，逻辑相对路径要做可移植冲突检查；不能只通过Path.resolve在一次读取里“看起来没有越界”，随后用未绑定的原字符串再次打开文件。目录和文件权限须在实际IO时重新确认，尤其针对并发替换、符号链接和编辑器缓冲。

## 3. Strict JSON codec 的具体要求和数据流

需要有一个带位置的tokenizer而不是简单先`JSON.parse`再验证。词法扫描器跟踪原byte span、行首索引、深度、unicode合法性、数字原拼写；构建对象时记录当前对象已有键并拒绝重复键（例如`"a"`重复两次）。键采用明确的Unicode解码后比较；不能让转义写法不同的同一键绕过重复检测。`__proto__`只是普通数据键还是不允许控制目标，应按源字段语义精确判断，任何对象拷贝都不能触发原型赋值。

对于 `gift.semantic-body/1` 的数学`Int`，按已有合同从规范十进制字符串解析到 arbitrary-precision 整数，不经JS Number；Requirement有限 `Integer` 词法按它自身的规则验证，不能将两者暗中统一。`null`/省略/空集合/Hole分别保留；JSON Schema default注解不得自动变成已接受作者值。

解码后结构 validator只处理已发布 vocabulary 可完整检查的结构； `$ref` 必须来自被冻结的 schema bundle，不能顺着URL临时访问网络。语义 validator再负责导入可见性、绑定ID、作用域、类型、效果、授权。未知kind/dialect可保存未解释源及诊断，不能安全地发射未知行为。

## 4. 工程/模块/锁的实际关联

`gift.project.json` 是项目拥有者，列 projectId、sourceScopes、modules、target roots等已采用字段；`*.module.json`的`moduleId/namespace/dialects/definitions/imports/exports`属于各模块；`gift.lock.json`按照`gift.binding-lock/1`固定语言、库、方法、目标与其content+revision依赖。目标方法的缓存命中不能根据同名最新版库绕过锁。要更新解释版本，应是显式Rebind Candidate，并展示受影响的公开含义与消费者，不能暗中把旧序列化输入当新版解释。

锁图解析：先收集节点头，核每个node id唯一、必要字段和内容摘要；按依赖引用检查闭包和合法版本；真实库包来自已授权可读、摘要匹配的本地捕获；并行获取的可变文件需要统一检查snapshot。图允许普通编译声明递归，但锁内容闭包不能通过递归自含文件摘要制造不可终止的哈希环。缺失的内容必须返回确切Need，不让解析器用“内核已有同名字定义”补上独立供应。

## 5. 编辑器缓冲、结构补丁与候选的完整链

- `readCurrent`: 只取得当前视图（可能与磁盘不同），记录buffer revision与owner；不能自动保存。
- `forkCandidate(base, edit)`: 只对确切拥有的SourceRegion编辑；要求 `expectedRevision` 与被替换span的已固定preimage一致。
- `validateCandidate`: 全量或局部重新读取已改模块及受影响的导入/方法与目标，返回诊断和Needs；未请求执行不产生Operation。
- `planSave`: 固定每个目标文件的当前preimage、expected source revision、拟写bytes和owner，产出仅可用于这个candidate的计划。
- `commitSave`: 在受控实际工作区执行CAS/多文件恢复协议；竞争冲突时保留原Candidate及最小Diff，不能覆盖竞争者。工作区读回不一致保留已知与未知状态。

长JSON编辑的核心是**不要求作者手写一长串重复中间信息**：只编辑自己定义/要求的差异；公共模板、已锁定Definition、默认与展开的DerivedView按需显示。结构编辑器对CST的最小区间构造replace，不应把整个文件pretty-print后吞掉作者原空白/键顺序（前提是这份源的SourceProfile承诺保留）。若文件已被外部改动，只有在语义与字节冲突可判明时可构造建议重基，不能先合并后隐藏冲突。

## 6. 三类源冲突必须分开返回

**区域冲突**：两条编辑命令都试图写同一AuthorRegion；同值也不能自动产生第二写权。**版本冲突**：源字节或基线变了，但目标不一定语义冲突，需要重基/重新读取；原请求的preview不变成新基线已验证结果。**语义冲突**：两个编辑的含义约束矛盾，必须回类型/规则/要求 owner 解释，不能仅靠JSON Patch最后写入裁定。

生成区的处理更严格：若文件处于受管`managed`区域，作者在原文件直接修改后的唯一合法路径是明确拒绝覆盖、经已有合格reverse-edit方法还原进作者源，或经授权采用为原生owner并改变生成责任。不能同时保留“源JSON是唯一真源”和“生成TS编辑被长期保存”两套可写含义。

## 7. 操作级伪代码和失败矩阵

```ts
async function saveCandidate(candidate, sourceGateway, journal): Promise<SaveResult> {
  const plan = planSave(candidate);                    // 只读，完整列出本次有权目标
  const fresh = await sourceGateway.capturePreimage(plan.targets);
  if (!matchesSourceAndOwner(plan, fresh)) return conflict(plan, fresh);
  const op = await journal.admit(plan, fresh);        // 需要的持久化/资源准入
  try {
    await sourceGateway.stageUnderOwnedTempNames(op);
    await sourceGateway.commitBySelectedProtocol(op); // 不假设跨文件atomic rename
  } catch (e) { return journal.markUnknownAndReconcile(op, e); }
  return journal.readbackAndSettle(op);               // 不能以写调用返回代替读回
}
```

这里给出实现调用结构，并不授权所有保存都必须建长期数据库：单文件、同步内存工程可选更轻机制，但若该产品宣称跨重启恢复，实际journal不能为省事删掉。不同文件系统的CAS/锁/rename/fdatasync/目录fsync支持要以适配器为准，无法提供某保证时明确降低Claim或拒绝该请求。

必须验证的异常：非法代理项/重复键/深层恶意输入；锁的同名不同内容；symlink并发替换；两个不同缓冲修改同一来源；删掉一份结构分片而没有迁移项目清单；第二次修改後旧 span错误定位；被作者编辑的generated区；跨平台大小写碰撞。每例分别期待非法源/Needs/冲突/需恢复，不能一律显示“解析失败”。

## 严格读取器与最小编辑的可编码程序

严格读取器的输入为`(raw UTF-8 bytes, source revision, exact SourceProfile, limits)`，输出`ParsedUnit`或带位置的错误。使用显式栈而非以宿主函数递归处理任意深JSON。扫描状态为`Value/ObjectKey/ObjectColon/ObjectAfterValue/ArrayValue/ArrayAfterValue/Done`；对象frame保存当前键集合、成员起点、父节点和期望状态，数组frame保存元素序号与分隔符位置。先检查总字节、深度、token数量和字符串预算，才增长arena。`Done`之后只接收合法空白；尾随逗号、多个顶级值、注释均按所选严格Profile拒绝。

字符串的raw span和解码后的Unicode序列同时保存。转义代理项必须合法配对；键相等按解码值判断，故`"a"`与`"\u0061"`重复。BOM处理不猜测：本结构Profile采用无BOM UTF-8，存在BOM返回带修复建议的非法源，不能静默删除后用旧摘要。数值token先保留原拼写，由字段codec检查整数/小数域；不先转double再判断整数。Math Int字符串与有限Requirement整数的各自规则不改。

每个节点记录`valueSpan`；成员另外记录`keySpan/colonSpan/separatorSpan`。JSON Pointer只作同revision内的结构定位，构造时`~→~0`、`/→~1`。数组下标不是跨修订身份。单值替换只替换valueSpan；删除成员时，非末项删除本项至下一个键之前的逗号边界，末项优先删除前一个分隔逗号；空对象/数组独立处理。插入使用相邻的换行/缩进样式，若原区域不存在可推导样式，采用该Profile的固定formatter，仅格式化本次插入片段。

一个结构补丁包含准确基础、节点定位、预期raw片段摘要与新片段。先在内存校验全部修改互不重叠；按byte start降序应用，避免前一次变化偏移后一次坐标。多个补丁涉及父子区域时拒绝或先合成为一个明确父修改，不能依赖应用顺序吞掉子修改。应用后重新严格解析并重建受影响span；未触及原字节逐段保持。结构合法而语义不完整可保留草稿，不能在失败后把上次合法源当作“本次已编译的缓冲”。

重基使用base/ours/theirs三方对应：稳定DefinitionId及字段键可对齐；数组元素只有明确稳定身份时按身份对齐，纯位置数组用内容编辑区间且保留移动/重复歧义。同一成员两方改动、删除与引用新增冲突、相同ID不同定义均返回具体冲突；同字节相等可以消去同义差异，但不能产生第二写权。重基后的candidate必须重新检查合同与输入闭包，不能继承旧check的current资格。

锁解析先建有向节点表，再校验引用与捕获内容；锁的身份与源内容摘要不递归自含。依赖环以包/声明SCC和单独锁manifest摘要封存。一个模块的非法必检声明即使未被某函数调用也按原Profile阻断相交模块；仅存放在工作区但未被选中/加载的模块不被强行纳入。初次依赖未锁时返回包含具体供应槽的Need，当前纯preview不得自动下载或写锁。

文件系统适配器输出`CaptureConfidence`，区分真实不可变snapshot、受同一合作锁保护的捕获和仅尽力观察。读两遍文件都相等不能推导全工程原子快照。客户端宣称需要原子捕获而宿主只提供尽力观察时直接返回能力缺项；不得把更弱的读取结果交给相同强保证路径。
