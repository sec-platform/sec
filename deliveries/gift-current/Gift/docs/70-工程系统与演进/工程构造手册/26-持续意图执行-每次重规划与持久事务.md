# 持续意图执行：每次重规划与本地原子持久事务

**工程责任与证据范围。** 本文负责从 Gift116 研究保留的**持续有限模型执行算法**，不占用[意图源和 Meaning 的唯一语义责任](../../20-语义与组合/作者语义/通用意图语言-意图源与语义组合.md)，也不代替[生产运行授权与外部效果恢复](../../50-执行运行与观测/持久化与恢复/事务提交-外部效果与幂等交付.md)。[Gift116 研究记录](../../../fixtures/intent-language/Gift116/README.md)标明来源；本包不运输其原源码与测试。以下是施工与验收设计。Gift114 单次冻结算法只用于比较，不作为持续运行的替代合同。

## 解决的现实缺口

Gift114 以 `ModelPlanCandidate` 编译时的初始快照生成一次性计划。新请求即使只涉及其它对象，第一次提交后的 `state_revision != 0` 也会拒绝；其结果是一个可校验的一次性迁移程序，不能视为长时间运行的业务应用。

Gift116 在**不要求业务作者写循环/线程/事务/Rust/TS**的前提下，将原来的静态高层意图和合格本地方法装配为可以持续运行的程序：新操作到来时，重新对当前持久事实求解，实际应用步骤与所有维持/禁止约束一起受事务约束。这并不自动产生新的 Meaning 或真实 Provider。

## 从输入到源代码的确定施工步骤

该版本化研究画像的输入使用 `gift.author-module/1` + `intent:goal`、`gift.intent-meaning-library/1`、`gift.intent-model-supply/1`、`gift.finite-model/1`，其中最后一项明确说明 `explicit-offline-simulation-only`。这些历史输入由对应 Reader 解释并显式承接到当前 `/2` 作者合同，不建立另一种日常作者文件；生成的 `contract.json` 是**编译产物**，不是可手工修改的权威源。

构建入口 `assemble(modules, libraries, methods, snapshot, output, depth, bindingBudget, nodeBudget)`，默认深度 4、方法绑定上限 300、探索工作额度 600。本参考拒绝不受支持的模态、外部观察、错误含义摘要、未声明字段、未固定 Method 和初始 `maintain/avoid` 不成立的快照。合法但当前无法达到目标时**允许生成程序**，运行时准确返回 `NeedsMethod`／`NoPlanInSuppliedFiniteModel`／`IncompleteSearch`；不能把编译成功等同目标已有执行资格。

读取器首先按既有 Schema、词法、类型、作用域检查模块/方法/意义；建立每项 clause 的 `identity`、`intentId`、roleType/object、可评价谓词；根据实际引用的**对象类型**寻找所有相关方法并检查导入摘要、参数、前提、编辑及 scope。若方法使用 `external-observer`、真实世界效果或未绑定新操作，拒绝该 profile。随后用 [机器派生合同 Schema](../../../schema/semantics/intent-local-replanning-contract-1.schema.json) 检查结果，固定源文件大小与摘要、版本、类型、Meaning、方法、全部意图、初始有限快照、限制。按相同输入固定排序生成 `contract.json`、`src/main.ts`、`tsconfig.json`、`package.json`、`build-manifest.json`；在包外同文件系统临时目录写完后改名发布，不覆盖已存在的任何目标工程。生成 TypeScript 需要独立严格 `tsc` 构建，完成源码发射本身不代表严格构建已执行。

## 运行机、控制命令与事务边界

目标运行时完全在生成的 `main.ts` 内，不因医院、文档、计算配额等业务名称变换代码分支。拟实现消费者的 CLI 形状：

```text
init DB
status DB
plan DB [intent-id...]
apply DB operation-id [--expect N] [intent-id...]
```

- `init`：拒绝外部已有不受管表；原子建立三个自身拥有的表，插入初始对象、修订0、状态摘要；重复初始化只验合同与数据，不重置。
- `status`/`plan`：只读打开数据库；缺库拒绝而不创建。显式 `BEGIN` 建立一次只读事务，使 `meta`、对象、回执在同一 SQLite 读快照内解释，完成后 `COMMIT`，异常则对仍活动的事务 `ROLLBACK`。否则并发写者可能恰好在两个 SELECT 之间提交，使一致的两个版本被误判为状态损坏。读取状态和修订后核对固定合同与 `state_digest`；`plan` 在本次读取模型上运行预算有限的规划器，不写数据或回执，结果不是未来提交担保。
- `apply`：从确切合同与操作 ID 验证入手；`BEGIN IMMEDIATE` 串行竞争写者，读取对象、验证数据摘要，先以 `(contract SHA, 排序后的 intent IDs, expectedRevision 或 null)` 计算 `requestDigest`。旧回执的摘要完全相同则精确重放；有一项不同必须 `OperationConflict`。对新操作才判断 `--expect` 与当前修订是否相同；没有显式值则**在当前事务中重新规划**，不会盲用早先 preview。
- 规划器产生 `ModelPlanCandidate` 或 `ModelAlreadySatisfied` 后，按步骤在私有快照逐步重新检查前提和**所有意图**的 `maintain/avoid`，最终检查本次选中的全部 `achieve`。只有完成后才更新实际变化对象与 `state_digest`/修订，再写操作回执并提交。无实际变化的目标写一张 `LocalModelAlreadySatisfied` 回执但不虚增状态修订。
- 失败：计划未知、合同/存储不一致、预算耗尽、前像版本变化、SQL 语句或 COMMIT 失败，均不宣称成功；活动事务仍存在时回滚。已提交回执属于原操作身份，不因客户端超时自动换新的操作 ID；但这不涉及真实远程 Provider 的未知结算，因为实际世界 effect 数始终为0。

本画像的三个*本地模型*表与边界：

| 表 | 关键字段与写入职责 | 失败语义 |
|---|---|---|
| `gift116_meta` | 单行合同 SHA、作者模型 revision、单调非负整数 `state_revision`、`state_digest` | 合同不匹配、非法修订或摘要不匹配，禁止读取为当前可信模型 |
| `gift116_object` | `id` 主键、固定名义类型、JSON 字段；仅本次合格方法可更新已声明字段 | 对象身份集合改变、类型/数值越界、外部无修订修改拒绝 |
| `gift116_receipt` | `operation_id` 主键、`request_digest`、已结算 JSON 结果 | 重放只匹配同请求；不同选择或版本的旧 ID 不能伪装同操作 |

`state_digest=SHA256(按固定键序表示的 objects)` 只是当前完整数据与上次本运行器提交的一致性探测；拥有 SQLite 原始写权限的攻击者可同时修改数据和摘要，故不得作为安全签名或多租户权限。目标没有跨应用迁移，任何生产 Schema 迁移必须重新设计并取证；不自动采用旧单次合同表。

## 有限规划算法、资源与错误类别

在每次已验证快照上：先计算所有 `maintain/avoid`（三值结果不可将 unknown 当 true），再从指定意图选择目标 clauses；若已满足，直接返回空轨迹。然后从选定角色的实际对象类型形成可绑定候选（同一次方法中的两个形式参数必须绑定不同对象是**本有限 profile 的决定**，并非通用 Gift 语义法则）。按方法 ID、形式参数和对象 ID 稳定排序枚举，超过 `bindingBudget` 返回 `IncompleteSearch`。

广度优先搜索使用 `canonical(objects)` 去重，预算包含候选绑定和状态数，受 `maxDepth/nodeBudget` 限制。每条候选须前提确定为 true，模拟类型化 `set/addInt`，重新评价全部安全 clauses；只有完成所有选定 achieve 时才返回计划。有来源未知的分支与界限耗尽分别记为 `NeedsFact` 和 `IncompleteSearch`；后者**优先于**把未见到解误报为不可能。确实穷尽了供应的有界搜索图才可返回 `NoPlanInSuppliedFiniteModel`，这不是对其它 Method 或现实环境的不存在证明。

当前状态的多次提交可以经不同操作 ID 组合，但不能得出无限期容量合规、无死锁、强实时性能或法定业务可靠性结论。本地同步 `node:sqlite` 只有取得相应宿主证据后才具有所声明的 SQLite 原子范围，并不支持生产多节点吞吐假设。

## 可复算验证与独立读回

验收应从空工作目录按固定作者输入生成 TS、严格构建并在独立目标进程运行，再用独立数据库读取器检查对象、修订和回执；代表性状态另外与受限纯模型 Oracle 对照，不能由生成器自报相同结果代替。反例覆盖双意图联合与分步提交、容量不足时第二项拒绝、并发两个进程只有一个获准、计划预览无写、修订冲突、重用不同参数的 operation ID、无事可做的回执、不可信库/改动、已有外部表、注入 SQLite 更新触发器后整笔回滚、预算不足不能冒称无解。

历史重放脚本不在本包。未来验收若缺目标编译器、类型依赖或运行环境，相应构建/运行结论就未取得，不能用 Schema 形状通过代替。真实生产实现仍需多租户授权、模型实例动态入场、运行时角色绑定、新 Meaning 可信发布、Provider、跨版本迁移和独立系统保证。这些义务不以 Rust Kernel、自举或云系统提交代替。

## 与专用业务源码生成的接合

本节有限执行算法作为受界行为对照保留。后续 [Gift117 语义源码 Lowering](27-业务语义直接降低与有限合成.md)将 `clauses`、Meaning 表达式、方法前提和写入编译为 `src/logic.ts`，保留通用的有限规划和 SQLite 事务外壳。这解决了原 `runtime.ts` 以固定解释器处理业务规则、却被误当作直接业务源码生成的局部缺口。它不会因此自动获得未提供的算法、现实权限、长期时序性质或生产 Target。
