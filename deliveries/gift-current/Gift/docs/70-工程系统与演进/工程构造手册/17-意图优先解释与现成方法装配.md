# 17 意图优先的 Gift：从业务目标到可实现软件的施工设计

> 本章是实现指南。意图作者主结构的唯一 owner 是[通用意图语言](../../20-语义与组合/作者语义/通用意图语言-意图源与语义组合.md)。本章的 Rust/TS 内部接口是可施工方案，不是已经发布的接口或实际编译器资格；已有证据/授权/Target 原 owner 不改变。

## 零：替换错误的工程优先级

实现次序以**开发者能用一份声明性意图得到真实业务成果**为导向，不再以“编译器先支持泛型/互递归/更多 AST Tag”为主线。后者只在实现方法确需通用计算时安排。选取成熟解析、规则、存储、工作流、UI、数值与目标语言生态；Gift 自身最需要的不是重新发明这些引擎，而是对接受的目标实施**有源事实与有界自动化的语义连接、方法资格、组合、可逆修改和效果验收**。

最低有效纵切：一个产品作者根 `IntentDefinition`、两个可复用 MeaningRef、两个相互交叉的硬约束、一个真实受约束的 Method 目录、一个可观测的模拟环境、一个生成/装配目标、两个正例和两个逆向反例及一次用户二次修改。它必须跨至少两种不相关业务用途复用相同**公共方法合同**，而不是只换方法名的模板。真实 Provider 不在纯模拟门禁范围；不能用模拟宣称支付或物理动作。

## 一、主要数据结构与唯一身份

```rust
// 内部设计：字段名表示职责，不是已部署的 Rust struct
struct IntentDefinition {
  id: DefinitionId,
  origin: SourceOccurrence,
  roles: TypedRoleBindings,
  clauses: Vec<IntentClause>,
  meaning_uses: Vec<MeaningUse>,
  assumption_refs: Vec<AssumptionRef>,
  observation_needs: Vec<ObservationNeed>,
}

struct MeaningUse {
  ref_id: DefinitionRef,
  resolved_revision: SemanticRevision,
  interpretation: InterpretationHandle,
  scope: SemanticScope,
  observable: ObservationContract,
}

struct ObligationNode {
  origin: ClauseOccurrence,
  modality: ModalOperator,
  subjects: BoundSubjects,
  formula: ScopedFormula,
  horizon: Option<TemporalScope>,
  assumptions: Vec<AssumptionRef>,
  evidence_need: EvidenceNeed,
  readset: ReadSet,
}

struct RealizationOffer {
  method: MethodRef,
  covers: Vec<ObligationRef>,
  requires: Vec<AssumptionOrCapability>,
  ensures: Vec<QualifiedPostcondition>,
  modifies: FrameRef,
  failures: Vec<FailureContract>,
  effects: Vec<EffectContract>,
  targets: Vec<TargetProfileRef>,
  qualification: QualificationRef,
}
```

这些字段是**实现端只读解析表示**。作者真源仅存 `IntentDefinition` 外壳与 Body，`ObligationNode` 为可重建的派生图，`MethodRef/RealizationBinding` 归原实现 owner。声明文本修改采用现有 SourceProfile/CAS/SourceMap，不能让索引成为第二写者。一个模块没有使用资源、方法或时间窗，不必分配不相关的服务实例和持久对象。

`MeaningRef` 不能从裸标签自动执行 Python/SQL。公开意义若是布尔谓词，必须给类型、所有可解释参数、可观察域与解释供应；规范义务及时间规则由对应受信语义解释者消费。禁止没有注册来源的 `kind` 在 Kernel `switch` 中动态获得真值。

## 二、接入算法：从用户声明到有效义务

```text
resolve_intent(snapshot, definition, locked_modules, author_authority):
  strict_decode_and_preserve_source(definition)
  bind_roles_and_meanings(locked_modules)
  for clause in definition.clauses:
    resolve all references, types, clock domains and applicable principal
    ensure that modal operator has full interpretation contract
    normalize into obligation retaining origin & assumptions
    if missing semantics or unaccepted ambiguity: report exact Need
  join obligations by exact subject/scope/time/owner references
  detect local contradictions supported by known rules & proof limits
  return ObligationGraph + ReadSet + Diagnostics + unresolved Needs
```

**限制**：本函数不能访问在线价格、账号或外部网络去“补齐”缺的业务含义。作者已锁定的词义与角色是权威；不同用户租户、法域或时间适用范围不同，不因符号字符串相同被合并。`Goal` 不自动转换为事件—条件—动作规则：目标可由现有多个策略满足，并不唯一决定下一步。

冲突检查应包含来源、共享主体、时间/世界域、逻辑前提和最小化可复核反例。若理论/求解器不具完备性，返回 `Unknown`/`IncompleteSearch`，不能签定无解；偏好只在硬约束合格之后比较。同一个功能的两种 Method 可以产生不同非功能保证，编译器不得默默牺牲作者的硬时限、隐私或成本上界。

## 三、从义务到候选方法：不是模板匹配

```text
solve_realization(ObligationGraph G, MethodCatalog C, TargetProfile T, Budget B):
  todo := all unresolved hard obligations
  candidates := index offers by certified semantic effect, type and context
  frontier := [{goals: todo, assumptions: G.assumptions, plan: [], costs: []}]
  while B permits and frontier not empty:
    select a frontier node under deterministic ordering of locked C
    choose a goal that has an actual observation/meaning contract
    enumerate compatible offers with qualified guarantees, not name similarity
    for each offer:
      unify roles, resource identities and semantic versions
      test its known preconditions; recursively introduce legitimate subgoals
      add effect, frames, failure/rollback and authority obligations
      detect loops, conflicts, shared-resource oversubscription and ABI gaps
      only after all hard goals eligible: compare preferences and costs
      if complete: output candidate plan and its unresolved evidence obligations
  return best eligible plan or accurate Needs/IncompleteSearch
```

不能只按每个 goal 找最近似实现，再把局部实现拼在一起。举例：A 方法锁定 8 单位库存容量，B 方法也锁定 8，而总容量 10；分别合格但联合不合格。必须在共享资源和效果关系上求整体可行，再谈偏好。外部确认是否有效还取决于实际观察和签名/法域，不能由规划器自我证明。

**降低方案不等于成功执行**。对于 `Rule` 使用已有决策引擎；对于 `Query` 使用合格关系查询/SQL；对于 `State/Workflow` 使用状态机/耐久工作流引擎；对于时间/优化使用调度器/求解器；对于 UI 用目标平台组件；对于设备/资金使用具有当前 Grant 的真实 Provider。后端私有表示独立，用户不需维护它们。目标代码生成仅在需要包装、装配、适配和缺少可复用能力时发生；同一意图根可产生多个模块/进程/目标，但必须具备精确来源、测试与恢复。

## 四、观察及证据从结果中分离

运行不能被当作一次纯函数调用：

```text
accepted intent
  → planned change (no external effect)
  → authorization (precise actor/operation/scope)
  → durable dispatch intent (same operation identity)
  → effect attempt
  → provider readback / independent observation
  → settled success | settled absence | partial | unknown
  → claim qualification in its precise environment
```

模拟中的观察结果最多支持模型内特定属性；没有时间覆盖或权威证明就不能把“当前真”提升为永远真、不能把状态 `confirmed=true` 当资金已清算。外部超时不重新造一个操作 ID 执行相同作用；补偿是新的、受权的 Effect。`permit` 的规范允许与宿主当前 Grant 独立判断。撤权不会改写已发生的历史事实，但阻断新动作和相交披露。

## 五、为什么可以显著简化作者输入（含成本检验）

需要比较**同一业务公开区别**的描述成本，而不是单纯比较源文件字符数。某个高阶资源预留库被一次认真定义并资格化后，十个行业里的用户只需引用该定义，并填写本行业真正不同的容量、时间、超售策略与权威。用户不用复制十遍 SQL、锁、消息去重和日志恢复。若业务不同义，复用必须停在真正共同的不变量处。

测试用例应记录：业务作者输入的高层约束数、真正需要用户裁决的未知项、自动取得的合格供给、保留的未决效果、改变一项业务规则导致的受影响源、意外强迫用户填写的技术参数。任一工程若必须由普通业务作者编写大段函数和目标语言代码才能表达已被普遍理解的结果，就是对 Gift 高层目标的失败证据。只在没有可资格化 Method 时才允许明确转给实现供应。

## 六、对五类典型意图的实际处理

### 库存或病房预留

`maintain` 总预留≤可用容量，`achieve` 合法请求最终获确认或得到明确拒绝；`avoid` 重复作用。库可提供受约束预留 Method；领域政策分别处理候诊优先权、超售、人工批准和紧急撤销。同构的容量不变量不能覆盖法律差异。

### 订阅取消

`achieve` 取消在准确生效时点之后不再产生新收费义务，`oblige` 有权方通知并结算已发生账款。支付结果未知不能直接被标记退款完成；计费源和合同法域是独立输入。可以组合周期计费规则、定时状态机、支付 Provider 和审计证明。

### 游戏规则

`maintain` 没有非法行动、`achieve` 按游戏作者自定义判定达到胜利、`prefer` 延迟/资源开销。游戏胜负 Meaning 完全由作者创建，不能从 `winner` 标签推出公平或反作弊。方法可以来自规则/状态引擎，网络版本需服务器权威和回放资格。

### 生成作品和用户体验

`achieve` 在声明观察范围满足输出格式、可访问性和版权边界；审美/“好看”属于需真实评价者或模型证据的偏好，不是能够从 JSON Schema 得到的真值。AI 可以提出内容/界面候选，但作者评价结果独立记录，不能把生成成功代替已满足主观目标。

### 优化调度

`achieve` 所有任务有可行分配，`maintain` 时间/资源硬界，`prefer` 总行程或延迟最小。可行、最优性有证、已运行、实际执行成功是不同状态；选择已部署 MILP/CP-SAT 等合格引擎无需 Gift 自己重造通用编程语言。求解预算结束保留未定，不冒充无解。

## 七、与现有工程角色的精确关系

| Gift 现有部分 | 新定位 | 本次必须保留 |
|---|---|---|
| 当前业务作者`gift.author-module/2`；旧`/1`只读 | 唯一候选新业务模块，承载高层Intent/Requirement/产品定义；可选计算沿同一作者语言解释，生产资格另核 | 严格JSON、模块/修订/写权、显式迁移门禁 |
| `IntentIR` 及 Facet 目录 | 非权威草稿、发现、投影和接受建议 | 未确认不晋升业务真值 |
| `Definition/Requirement` | Intent 库所引用和派生的精确业务意义/硬要求 | 身份、类型、共享主体、条件范围 |
| Gift111 `s:function` 与计算子集 | Method 作者可以使用的普通实现工具，而非业务作者必经语言 | 保留已实测代码及精确适用范围 |
| `Method/Binding/Target` | 从合格业务效果到现成机制的供应、组合和目标装配 | 约束、ABI、失败、目标与证据 |
| `Grant/Operation/Readback` | 真正有权主体的世界作用及其持久结算 | 不用模型声明替换执行证据 |
| `Evidence/Claim` | 精确范围的事实及保证 | 不用 schema/tsc 代签外部结果 |

对本工程而言，比继续添加计算表达式类型更优先的，是在**同一份 IntentSource 上**实现准确 Meaning 解析、Goal→QualifiedCapability 的有界匹配、重用现成领域方法、保持联合约束与来源，再将其装配进可维护目标。真正需要通用计算时，直接借助原生 TS/Rust 生态，不给业务作者重复建立一个完整语言。

## 八、实施验收和不适用结论

- 一个用户新业务定义能从作者 JSON 进入准确语义图，不必修改 Kernel 行业分支；
- 两个互不相邻领域复用一个实际同义的公共约束或合格实现，参数差异不会偷掉原有条件；
- `NeedsMeaning/NeedsFact/NeedsMethod/NeedsTarget/NeedsGrant` 均有独立可定位案例；
- 用户只修改一个目标时，能保留原 Method 与无关对象不重写；
- 跨域共享容量、时间及授权冲突能拒绝错误组合；
- 未观测的外部世界仍是 Unknown，一次有限快照不能签无限时序保证；
- 系统能提供代码、受控装配或**准确停在未决实现义务**；用户不必自己从头编写流程/算法来达到已有领域库可完成的要求。

这些验收只在真实消费者实现和证据可得后才能声称完成。包中的结构 Schema 与本地只读示例验证仅证明已把作者语义的必要输入/拒绝边界写成了可检查设计，**不代表已能够从任意行业意图自动生成生产系统**。

## 真实联合业务要求优先于单根演示

单根 `IntentDefinition` 的最小纵切只是入口。正式产品若同时拥有多个当前 Intent，必须按[联合组合施工](20-多意图联合组合-约束与方法搜索算法.md)构造共享对象、资源、时域与权利的一次目标图，再调用[成熟引擎供应与资格](21-现成引擎供给-资格绑定与能力装配.md)取得有效 Method；不能分别产出局部计划后拼接。实际产品装配和第二次修改交由[完整目标施工](22-意图产品生成-修改传播及现实恢复.md)；[Gift113 离线模型](../../../fixtures/intent-language/Gift113/README.md)仅验证有限模型的联合规划概念，不提升至生产软件。
