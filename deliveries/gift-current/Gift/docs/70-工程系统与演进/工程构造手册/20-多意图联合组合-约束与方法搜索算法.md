# 20 多意图联合组合：共享主体、资源与约束的一次解析

> 施工设计。低层约束满足与 Method 资格的唯一正式语义归原[跨软件需求合同](../../20-语义与组合/组合/跨软件需求合同.md)和[实现搜索](../../30-实现解析/实现选择/设计空间搜索与求解.md)。本章不建立第二份 Requirement 数据库。

## 1. Gift112 的真实空缺

Gift112 模型消费者的 `solve` 一次选一个 `intent:goal`，在其有限快照内搜索。这样能够演示“同一个预留方法可用于不同业务”，**但不能证明两个同时有效的意图可以合并实施**。两个独立请求各自面对一个剩余容量时，都可以得到有效单项计划；并发或组合后两项共同成功可能超容量。对真实软件工程而言，修复这个缺口比增加新计算语言语法更重要。

Gift113 新增只读 `fixtures/intent-language/Gift113/joint_intent_reference.py`，实际读取 Gift112 相同作者源、Meaning 和方法目录，并对所有选中的意图**在同一模型状态上逐步评估硬要求**。它仅为有界有限模型见证，未提升原有 `model-only` 供给为真实事务或世界授权。

## 2. 公共求解输入及必须建立的全局图

```text
JointIntentInput {
  acceptedIntents: [IntentOccurrence@revision],
  objectIdentityGraph: exact scoped object IDs & authenticated alias edges,
  meaningLocks: [DefinitionRef, revision, digest, observer/model scope],
  facts: typed snapshot/readback with provenance and observation time,
  offers: qualified Method catalog & versioned negative reads,
  context: principal, tenancy, time, jurisdiction, targets, budgets,
  hardClauses: goals/invariants/prohibitions/obligations + assumptions,
  choices: independent alternatives and permitted preferences
}

JointObligationGraph {
  nodes: claim occurrence + modality + quantifier + time + subjects + observer,
  edges: depends-on, shared-object, may-write, conflicts, compensates,
         authorized-by, observable-through, temporal-order,
  jointContext: assumptions, resource conservation, party authority, horizon,
  readSet: positive + negative + effect/observer/capability dependencies
}
```

**不能**将每个意图的单独计划列表首尾连接就宣称联合可行。多个计划需共用完整前像/资源和并发模型，检查所有中间状态、权利、义务、效果、时间及最终目标。仅比较最终 snapshot 会漏掉中间违规和已不可逆的真实作用。

## 3. 从零实现联合解析和有限搜索

```text
compile_joint_intents(snapshot S, accepted roots R):
  bind every root against exact Meaning version & type/name/role scope
  normalize clauses into immutable obligation occurrences with source coordinates
  merge by authenticated object identity, not by equal field labels
  collect goals, safety, pending normative/time/observation obligations
  reject only proven initial safety violation under declared closed model
  return JointGraph + Reads + Needs + context

search_joint_model(graph G, qualified mock methods M, bound B):
  state := immutable initial model; frontier := [(state, empty trace)]
  collect only candidates whose exact parameters match selected roles/objects
  validate method preconditions & edit types; absent methods => NeedsMethod
  while bounded frontier not empty:
    pop one state (deterministic order, visited key includes actual modeled fields)
    for a bound candidate:
      verify precondition true; unknown => unresolved observation
      simulate on a deep copy (never publish to actual model)
      evaluate *all* maintain/avoid clauses in every sampled state
      if any false: reject candidate transition
      if any unknown: suspend/require fact; never coerce to false
      if all achieve true: return model plan + unfinished normative/time obligations
      else enqueue admissible successor, tracking shared budget
  return IncompleteSearch on cutoff; NeedsFact if unknown blocked determination;
         else NoPlanInSuppliedFiniteModel only for exhausted represented model
```

`PartialModelPlan` 保留未解释的 `oblige/permit/prefer`，不能把计划成功升为这些条件已被履行。时间模态 `eventually/always/until` 必须由相应轨迹检查/运行时监控按精确时间范围处理；有限采样不等于这些无界性质已证。

**可终止的有限搜索 ≠ 普遍无解证明。**只有穷尽被声明且封闭的状态/动作集合、未发生预算截断或未知观测时，才可用 `NoPlanInSuppliedFiniteModel`。反过来，定义可能无限的数值资源域，停止搜索应返回 `IncompleteSearch` 而非“业务矛盾”。

## 4. 实现方法的联立资格，不能只看单个 postcondition

对某个 Method Offer `m`，从其输入参数绑定到共享对象集合；必须检查：

- **语义前提**：输入域、版本、角色、资源身份、前置观察、Method 自身 guarantee/Frame；未证明的 `claimedCoverage` 仅是供应者主张。
- **多目标覆盖**：当前状态到新状态对所有目标、禁止和维持项的影响，不能只比较它自报的一项目标。
- **资源与时间**：两个方法各用 8 单位而总量 10 时，不得局部分别合格后同时接纳；异步时还检查占用/释放的重叠窗口。
- **外部效果与权利**：纯模型 state edit 不等于有权限的事务/设备动作；变更真实状态需当前 Grant 和持久身份/读回。
- **不确定与代价**：候选资格必须先满足硬条件；只在同一可比较成本模型下选偏好。找出可行候选不证明最优性。
- **相互影响的失败路径**：事务只有在精确声明的共同原子范围内可原子提交；跨组织补偿不能冒充自动 rollback。

一个作者新规则能否自动组合，不取决于行业名，而取决于能否提供上述可判定/可检查的精确连接条件。无法取得时返回层级明确的 Needs，不退回任意模板代码生成。

## 5. 同步、异步与环境独立的规划区别

静态纯模型可只存不可变快照，BFS/约束模型在声明的有限域内搜索。真实持久系统必须考虑两个调用者并发领取资源、写入冲突、重试/重复交付、超时/迟到观察和旧 Method 版本。Method 资格要规定实际线性化点、事务边界和反压，不因模型中的串行搜索通过便宣称高并发安全。分布式一致性的成本与 CAP 假设需按实际平台取得，不预写虚假延迟数值。

优先复用成熟的事务与工作流供应；Gift 的工作是把它们的真实前后条件、幂等/读回/故障语义映射到受权的业务目标，并在整体层判断所有来源和保证。

## 6. 新参考程序的真实范围和反例

`Gift113` 的独立有限模型测试包含：两个不相关领域共享同一 Method Catalog、同一容量一份/两份的争用、初始违反安全、缺事实、深度/节点预算、输入顺序确定性、重复意图拒绝、无 Meaning 拒绝、原始快照不变。相同 Gift112 AuthorSource 无须新增一个命令式作者 Profile。

尚未支持且不得借这些测试宣称：完整 temporal 模态、外部 `oblige` 的履行、货币清算、真实权限、生产 Method 资格、跨库并发隔离、证据签发、Target 装配、自举或自动算法合成。下一实施层只在确切使用了这些能力时接入，而非将模拟全部打包成默认运行时。

## 7. 增量与源变更

构建联合图按 `MeaningRevision / object identity / precise SourceOccurrence / qualified MethodCatalog / Target / assumptions` 建查询依赖。某个读集的正依赖或负依赖变化，只使相交根及相关证据失效；原始作者源按 CAS 修改，已结算的现实作用不可用重编译反写。新增能覆盖某目标的方法会使此前 `NeedsMethod` 的**负依赖**失效。改一个对象容量可能影响多个意图，不能按源文件模块边界孤立缓存。

建议验收对照：同场景串行/并行、全量/增量在声明域内相同可观察结果；两单项可行而共同不可行的反例；方法内容变化后的准确失效；拒绝旧快照误发布。达到这些门槛后，才能把有限参照设计迁入生产 `ObligationGraph/Method` 消费者。
