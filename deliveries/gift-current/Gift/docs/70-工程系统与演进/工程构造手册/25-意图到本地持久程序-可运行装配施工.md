# 意图到本地持久程序：有限模型装配算法与合格边界

本文从 Gift114 研究中保留**单次本地持久有限模型**的装配算法、事务区别和资格边界，不改变 [通用意图语义的唯一责任](../../20-语义与组合/作者语义/通用意图语言-意图源与语义组合.md)，也不能取代 [外部作用授权与恢复](../../50-执行运行与观测/持久化与恢复/事务提交-外部效果与幂等交付.md)。[Gift114 研究记录](../../../fixtures/intent-language/Gift114/README.md)用于核对来源，本包不运输其原代码与测试。以下接口与命令描述待实现消费者的行为，不是当前可运行入口。Gift112/113 版本化研究输入与当前 `/2` Writer 不能混读。

## 1. 单次模型画像的输入与输出

输入只有已固定的 `gift.author-module/1` + `gift.intent-body/1` 作者意图、`gift.intent-meaning-library/1`、`gift.intent-model-supply/1` 和一个显式 `gift.finite-model/1` 快照。输入结构由原有 `schema/semantics/` 四份 JSON Schema 校验；`Meaning`/Method 引用还要检查语义摘要、绑定类型、解释树、声明字段和方法前提。该历史画像的 `/1` 输入须经对应 Reader 解释；新作者经当前 `/2` Owner 迁移承接，不因复用有限模型算法而新增日常作者语言，也不强制先学计算。

施工顺序：固定输入 -> 单次模型装配 -> [Gift113 联合模型规划器](../../../fixtures/intent-language/Gift113/README.md) -> 冻结合同与已选方法 -> 通用 TypeScript 本地模型运行层 -> 完整 TS 构建 -> 本地 SQLite 事务。目标产物由 `contract.json`（结构化意义、意图、前像、方法、步骤和来源摘要）、`src/main.ts`、`package.json`、`tsconfig.json`、`build-manifest.json` 组成。`tsc --strict` 构建生成可直接由 Node 运行的 `dist/main.js`。

这里生成的 TypeScript 是**通用的受界执行/装配代码 + 冻结的业务合同数据**，不是为医院、GPU、文档等对象写不同代码模板；它也不是任意新算法合成。业务 Meaning 必须先由具体库提供可解释的表达式，Method 也必须先存在并通过绑定检验。运行层目前解释 `literal/field/eq/lte/gte/all/any/not`、`call/all/any/not/implies`、`set/addInt`，不表示语言整体只允许这些表达式。

## 2. 编译准入：严格拒绝大于当前执行资格的能力

施工接口：

```text
assemble(modulePaths, libraryPaths, methodsPath, modelPath, outputPath, depth, budget)
    -> EmittedLocalSQLiteModelApp { contractSha256, selectedIntents, planSteps }
    | Rejected { code, detail }
```

执行步骤：严格 JSON/Schema -> 构建类型、Meaning、Method 引用 -> 校验所有 selected `intent:goal` -> 联合模拟求解 -> 只接纳 `ModelPlanCandidate` 或 `ModelAlreadySatisfied` -> 排除 `oblige`、`permit`、`prefer` 及所有需要外部观察的 clause -> 验证全部目标方法仍为 `finite-model-only` -> 按有限类型与资源角色冻结输入 -> deterministic artifact bytes/sha256 -> 发射通用本地目标。

`NeedsFact`、`NeedsMeaning`、`NeedsMethod`、`NeedsQualifiedModality`、`NeedsObserver`、`IncompleteSearch`、`NoPlanInSuppliedFiniteModel`、`InitialModelViolation` 不得伪装为可交付。预算耗尽和当前供应下无方案均不代表全世界无解。语义摘要只是依赖固定证据，不证明规则及世界事实真实。

该装配算法禁止业务名分派：选中的医院、GPU 与文档全部用相同的 `gift.intent-body/1`。未来要支持新的业务概念，首先提供新的类型/谓词/合法观察和合格 Method，而不是改 Kernel 的行业列表。

## 3. 目标运行接口与事务逻辑

研究原目标固定为 Node 22.16 的本地 `node:sqlite`，当时该接口属实验范围；选择后续宿主须重新取得目标资格。此有限算法只承担 SQL 单写者串行化及本地 `gift_object/gift_meta/gift_receipt`。拟实现消费者的命令形状：

```sh
node dist/main.js init ./example.sqlite
node dist/main.js status ./example.sqlite
node dist/main.js apply ./example.sqlite operation-001
```

`init` 在 `BEGIN IMMEDIATE` 内建立自有模型、合同摘要与修订 0；已初始化时必须绑定同一合同才能复用，不覆盖旧模型。`apply` 先在事务内查询操作 receipt；同一个幂等键返回已提交的同一结果；不同键若状态修订不再是编译时的 0 返回 `StalePlan`。还要逐对象比较完整模型前像，防止“SQL 被其他写者改了对象但忘记推进修订”的旧计划覆盖。状态来源不完整、字段不在类型声明内或精确整数非规范字节，都拒绝。

`apply` 从当前快照开始，以已锁定 `Method` 顺序逐步检查前提、执行类型化有限编辑、立即重查所有 maintain/avoid；最终检查所有 achieve。仅将实际变化的对象写回数据库，和修订/receipt 在**同一 SQLite 事务内提交**。中途任一步、约束、数据库写入或 `COMMIT` 失败均不得报告已完成；事务仍活动时执行 `ROLLBACK`。本模型不具有外部指令，故无跨系统未知 outcome 与补偿假设；将来加入远端 Provider 时必须回原操作身份、派发记录、读回和权限体系，而不能用此单库事务替代。

`status` 独立进程重新读库，显示修订、实际存储对象和已持久 receipt。错误输出返回非零 exit code；`LocalModelCommitted` 的 `executedWorldEffects` 始终为 0，不称已预订病床或云卡。

## 4. 代表性输入与应观察的结果

- **病床容量模型**：原 Gift112 作者模块，容量 2、初始占用 1、请求合格未确认；生成 TS 后本地提交使占用变 2 和请求确认。重复 `operation-001` 只读回同一 receipt，不加第二次。
- **共享容量与双业务意图**：Gift112+Gift113 原样作者模块，共享容量 2 且初始占用 0，联合找到两个步骤并在同一 SQLite 事务内变成占用 2、两请求确认。容量 1 的相同意图不能被共同接纳。
- **陌生新文档业务**：与容量例不同的 `Document{approved,published,blocked,title}` 名义概念；作者只指定“批准且未阻止才标记为发布”，供应方法只有 `set published=true`。它仍使用同一个类型/谓词解释和目标程序，无需文档专用生成分支；但真实对外发布没有执行。

实际实现后须独立取得严格 TypeScript 构建、SQLite 持久提交/重启读回、操作重放、错误前像、合同篡改与 SQL 中间故障回滚证据。历史记录不能代签当前实现，有限模型测试也不授予生产可信事实与外部 Grant。

## 5. 从此有限消费者走向正式通用产品的具体缺口

1. `Meaning` 解释和 Provider 资格需支持可声明的关系、时序、观察与任意本地新定义；现在只有有限表达式和精确 `Bool/IntString/Text`。
2. 联合规划需接入成熟 SQL、规则、CP-SAT、工作流、UI 和原生实现的*真实*读取器、资格、效果/读回；此画像冻结有限方法，尚没有自动综合任意新方法。
3. 生产 Target 需要能力边界、所有权、可维护源码区域、增量构建、SourceMap、跨版本应用迁移和可配置多实例。当前是可构建通用运行器加数据合同，非任意 TS/Rust 业务源码最佳化。
4. 真正有权的运行需要 `Grant/Operation/Attempt/Provider/Readback/Compensation`，以及认证、隐私、性能与可用性证据。当前 SQLite 仅用于本地模型，不是授权控制系统。
5. 单机数据库性能不能从这些正例推成高并发资格；需目标宿主负载、并行事务、文件系统持久性及故障取证。Node 22 `node:sqlite` 属实验接口，不能视为长期稳定生产支持。

**工程结论：** Gift111 的通用计算参考可继续作为专业 Method 的可选供应，Gift112/113 的意图作者与联合规划为主线，Gift114 提供单次装配与持久提交的受限设计参考。它们没有被强行合并成一门普通新编程语言。
