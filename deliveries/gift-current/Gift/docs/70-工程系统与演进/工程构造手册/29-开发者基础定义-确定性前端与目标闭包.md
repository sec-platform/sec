**有类型根身份施工补充**：Reader保留原`outputRoots[]`元素，单根缺ID时规范化为`main`，多根强制显式`rootId`；Linker的Key不是数组位置，而是 `(ProjectRevision, TargetKey, RootId, ModuleUse/DefinitionIdentity, effectiveRoleActuals)`。对每个Root分别形成实例/成员/端口/部署候选，再仅在具有可能相交的共享资源、Effect、Data或Authority作用域上建立全局求解边。独立Root子图合格不提供全体资格；缺已认证隔离证据按Needs而非默认无冲突处理。多根共用模板可复用代码，但需要独立Context、权限、可变State和目标成员Owner；目标路径冲突/共享文件必须由Target统一规划。

## 作者新构造的实际消费者与资格交接（不增加新流水线）

此处只约定已有Reader/Linker/Meaning/Requirement/Method/Target职责实际应该消费什么，不发行第二套Schema、IR或机器API：

1. **ModuleReader与严格Writer**：同一`gift.author-module/2`设计 Schema读出唯一Kind和嵌套构造；当前Writer额外拒绝历史`arguments` Expr、裸Refs、旧wires/公开接口等，保留旧快照仅只读。静态值只按现有`ComponentUse.argumentBindings`读取；成员局部 `useId` 与激活`id`按稳定作用域解析。对于重名、未导出、未锁定、版本歧义、引用循环且缺少合法固定点规则、源改动并发冲突，应有定位的诊断，不默选最新版本。
2. **TypedOccurrenceLinker**：处理所选OutputRoot集合的每个独立发生点，建立 Template→Instance→MemberUse→ActivationCause→WorkflowUse→RequiredPort/EffectIntent 的有类型因果边；`Definition`同名不代表`Instance`同一，业务对象Ref也不等于有权实体。静态参数按形式模式分别进行Kind校验；mode=value校验`core:type`名义和完整值精化，非value只消费确定Kind Ref。单纯字段非空不能宣布可执行。
3. **Meaning与Norm**：逐有型使用点解释事件与工作流启动的具体业务因果、输入映射、作用域/时域/主体、四态知识、策略例外和强弱要求；未选择的库Definition不产生强制产品义务，已选择发生点不能因Ref相同被消除。
4. **JointRequirement**：将有权接受的实际根集合和实例成员产生的业务义务按时空相交域求解；输入包含已独立锁定接受基线，不能仅把根文件当前书写要求当基线。多个独立根可以并行，但共享对象/资源/效果产生真实全局约束；缺少隔离证据不能把根各自通过推成整体通过。
5. **Method/Target**：为每条实际激活路径选择合格消费实现；区分UI事件产生、消息重放、API响应、状态推进和时钟唤醒的真实Method；覆盖输入映射与失败、资源/权限、Effect读回和Target平台支持。SourceMap必须保留从生成代码到发生点/源修订的反向导航，不能生成双重派发同一个按钮的外部效果。目标不支持、仍有`Need`或缺Method时，不许产出可误认成成品的空实现或声明“高质量完成”。
6. **变化与恢复**：有类型`useId`为重排后尽量保留用户意图稳定身份；局部重命名需显式映射，多个同名路由或跨实例偷用成员必须拒绝。目标文件如有人工原生修改，检查其author-owned区域及源版本CAS；不可自动保留的更改必须明确冲突，不能用旧版Target覆盖作者编辑，也不能以重复执行副作用来验证产物。

下面原有 Rust 内存接口仍是候选；是否拆出某个Activation IR由真实消费者决定，不能因为多了一个作者字段便规定新的内核crate或万能流程引擎。


> **作者范围与施工职责**：普通业务作者优先使用[开发者抽象](../../20-语义与组合/作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#gift134-noncomputational-author-contract)中的Meaning、状态、交互、系统、规范和组合合同；需要自定义算法时，同一作者语言的可选计算构造或有资格的原生Method承担差异。本页保留既有计算前端施工设计，不扩大计算研究，也不证明标准操作、目标降低或生产编译器已完成。

> **状态：实现级设计，而非生产代码。** 开发者Definition的唯一语义定义见[《开发者通用定义Profile》](../../20-语义与组合/作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#developer-foundation-gift133)。本页只拥有**实际消费者怎么施工**，不重复修改当前Definition Body及Type/Expr/QueryTerm的含义。这里沿用已有 `contracts/workspace/semantics/compiler/assurance/application/execution/adapters/entry/bootstrap` 责任，不创建 `Gift133Kernel`、全新并行IR或第二套持久作者源。新 `/2` 仍是未发行提案；下面的Rust/TS是需实现的签名草案。

## 非计算选择、规范义务与组件连接的消费者施工接口

既有 Rust/TS 工程分工不变，本节只规定下一阶段消费者的输入、输出及失效边界，不实现通用计算前端。按现有 Root/SourceRevision 导入闭包和锁定定义后，逐次处理以下有类型判断：

```text
ResolvePredicateUse(meaningRef, roleActuals, scope, observationLock)
  -> QualifiedEvidencePair | NeedsMeaning | NeedsObservation | InvalidBinding

DecideBusinessRoutes(qualifiedEvidence[], selectionPolicy, evidenceOutcomes, disjointnessProof?)
  -> SelectedBranch | Rejected | HumanStep | DurableWait | NoMatchingRoute
     | NeedsExclusivity | EvidenceConflict | NeedsMeaning

ChooseTransition(state, event, qualifiedConditions[], arbitrationProof?)
  -> AllowedNextStateSet | NeedsTransitionArbitration | NeedsObservation
     | InvalidTransition | ConflictWitness

QualifyPolicy(rules, issuerLock, normBindings, scope, time)
  -> PermitDenyJudgment + OutstandingObligations | NeedsNormMeaning
     | ConflictingAuthority | NeedsRevocationStatus

QualifyConnection(providerInstance, providedPort, consumerInstance, requiredPort, target, environment)
  -> QualifiedPortBinding + ProofDeps | NeedsPortCompatibility | NeedsPortSupply
     | IncompatibleInterface
```

输入含确定的 `SourceRevision`、选中根、准确发生位置、锁定的 Meaning/Policy/Norm/Observation/Method/Target；输出保留依赖足迹，不能只返回一个 `bool`。静态 Reader 能判定未知步骤、重复名称、错误端口方向或不合法字段；它不能签发互斥证明、Norm权威、时序进展、端口行为相容或现实效果。

**实现顺序与恢复**：先验证模块/作用域和谓词完整绑定，再取得所需事实的四态证据；只有所有候选具备合格解释才执行分支选择。未合格语义停止于Needs，不可“分支兜底”。规范评价要保持Permit/Deny与Oblige两个结果坐标；Target必须消费所有参与产品根的硬义务，缺绑定返回 `TargetIncomplete` 而不是输出空壳。更新任何 Meaning签名、分支策略、互斥证明、政策来源、端口版本、角色身份或观察快照，须按正/负依赖撤销受影响资格。已派发Operation保持自己的身份和幂等域，不因重新编译被重放。

**独立校验入口**：`fixtures/developer-foundation/Gift137-noncompute-selection-and-norm/verify_selection.py` 可作为负例/结构样本，不是生产运行器；它明确报告未资格化外部依赖。最早允许称为产品闭合的证据，是实际受支持业务根经完整解释、联合Requirement、Method资格、Target构建及独立业务Oracle核验，不能从该脚本的静态通过提前签发。

**一次编译必须显式锁定**：ProjectRevision、所有被读取的Module原字节及正确的Profile、SourceRegion写权、导入域与锁定外部供应、Target/环境/优化控制、Root选择和相关事实版本。固定的字节与合法字符串并不能签发业务意义。

|---|---|---|---|

## 2. Rust内核的内存接口草案

```rust
// 草案：不构成已发布ABI，也不是此次已实现的Rust源码。
struct SourceBlob { path: SafePath, bytes_digest: Digest, revision: SourceRevision,
    region_owner: WriterId, spans: SourceSpanTable }
struct ModuleUse { identity: ModuleIdentity, profile: ProfileLock,
    imports: Vec<ImportUse>, exports: Vec<ExportRef>, source: SourceBlob }
struct DefinitionOccurrence { module: ModuleUseId, id: DefinitionId,
    kind: QualifiedKindRef, raw_body: RawSpan, source_revision: SourceRevision }
struct ResolvedDefinition { occurrence: DefinitionOccurrence, signature: TypeSignature,
    effect_bounds: EffectBounds, authority: AuthorityContext,
    positive_reads: ReadSet, negative_reads: ReadSet }
struct InterpretedDefinition { source: ResolvedDefinition,
    meaning: TypedMeaning, interpreter_lock: InterpreterLock,
    observation_needs: Vec<ObservationNeed> }
struct JointInput { roots: SelectedRootSet, definitions: Vec<InterpretedDefinition>,
    external_facts: FrozenObservationSet, scope: RequirementScope }
struct QualifiedPlan { obligations: JointRequirementSet, bindings: Vec<QualifiedBinding>,
    target: TargetProfileLock, proof_deps: ProofDependencySet }
enum StageResult<T> { Ready { value: T, deps: DependencyFootprint },
    Needs { partial: Option<T>, missing: Vec<Need> }, Invalid(Vec<Diagnostic>),
    Conflict(Vec<ConflictWitness>), SearchIncomplete(SearchFrontier), Unsat(ProofScope) }
```

`RawSpan`为准确原字节/格式恢复；`SourceRevision`不等于业务语义身份；`QualifiedKindRef`必须带Dialect、Issuer、Digest、版本与适用范围。工作区模块导入可有**声明型环**，先收集签名，再检查合法递归；不允许以`visited`跳过必须检查的初始化环、值递归、Method循环或真实运行死锁。

### 2.1 有限源码Reader/Resolver算法

```text
freeze(project bytes, allowed roots, revision)
project := parse_strict_and_validate_project_1()
for each captured module file in the deterministic SourceScope snapshot:
    ensure_path_confined_and_single_writer(path)
    blob := freeze_bytes(path)
    module := select_exact_decoder(blob.schema)  // /1 与 /2不能互相代读
    decode_all_signatures(module)                   // 暂不运行Meaning与供给代码
    index_public_exports(module)                    // 导出名 -> 真实definitionId
for each module-use:
    bind_qualified_imports(module-use)
    for each occurrence_ref:
        resolve local identity or actual public export;
        record positive & negative reads (absence queries as dependencies)
roots := bind_only_requested_outputRoots(project, target, source_revision)
for each reachable definition in roots:
    check selected dialect version, type, effects, visibility, required semantic provider
    produce QualifiedSignature OR structural diagnostics/Needs
return FrozenProject + TypedDefinitionGraph + SelectedRootSet + exact footprint
```

有限引用图遍历的 `O(V+E)` 不包含JSON解码、类型推导、命名库下载、依赖版本求解、一般程序行为判断、全局SMT或编译构建。构造器若递归调用应可表达部分函数，不能由静态有向无环要求排除一般递归；只有有证据声明“必终止”的函数才能获得该资格。

## 3. 类型和值解释算法的强制边界

`TypeOf(expr, Γ,Δ)`按Schema Tag分派到一条实际规则，而不是大字符串switch承认所有业务名。`nominal`引用需查当前ModuleUse与导出；`record`精确检查字段/可选和可变性；`variant`、`result`做分支覆盖；`set`/`bag`检查键等价而不是偷用宿主对象相等；`quantity`的单位、scale和舍入不得丢；`handle`所有权/寿命和FFI资源释放跨Target保留；`future/stream`携带取消/背压/异常；`refinement`不能因证据缺失而忽略约束。

`Expr.literal`的`value`必须按`type`选精确Codec：无界整数使用规范化十进制字符串（JSON数字不可靠），固定宽度整数在该位宽检查；decimal带scale及舍入；浮点指定IEEE表示/误差/NaN/负零Profile；文本的索引单位必须明确；时间戳/Duration要确定时钟域、时区/闰秒或日历/物理时长差异；bytes选择确定编码。**当前Schema只能验证基础形状**，这些是生产Reader应实现的附加校验，不允许借`Json`字段绕过。

`EffectOf(expr)`返回最小可证明效果上界：纯值/局部let只联合子式效果；`call`并入已锁定被调函数签名；`perform`并入所引用外部Port效果，若端口缺资格则Needs；`await`引入异步效果、取消和错误边界；`do`维护效果顺序；`try`不能吞掉无法恢复的外部效果。函数Body的实际效果必须是函数声明效果的子集，公开接口也必须保留该界限。`assumed-total`不得提升成已证明终止；`total`要求可检查递归度量、有限状态排名函数或外部独立证明。

目标结构不按Kind硬编码文件数量。一个函数库可只有`src`、`package.json`与测试；一个IDE可能是`apps/desktop`、`apps/web`、`packages/editor`、`packages/platform`、`packages/workbench`、`packages/extension-host`、`packages/language-client`、`tests`、`assets`等。**这些都是可能的目标布局，不是当前产生的文件**。真实Target必须有：入口根集合、完整传递模块/第三方依赖、正确源码、目标Toolchain、ABI/运行时、必要配置/迁移/资产、SourceMap及每项硬义务的具体实现或精确拒绝。

## 5. 自动生成的合格判断，不是把Name映射为模板

对于规范`R`与选定目标环境`E`，每个`QualifiedBinding`需有实现`M`的真实行为合同，以及特定精化证据，证明在清楚的前提/观察范围下，相关`Behaviors(M,E)`不超出`Allowed(R,E)`，并对进展/活性/输入覆盖、错误和安全另负担相应证明。这个行为包含关系是**条件性正确性目标**，不是自动可判定函数。现实Method搜索可能用有限规则库、SMT、专业求解器、代码合成或人工签发；必须返回准确的ProofScope和预算。不能无中生有供应、法规、性能和外部权限。

**联合示例**：两个并发保存请求即使分别满足“保存成功”，若共用文件且`expectedRevision`不同，目标必须按已接受的冲突/隔离规则处理；不能各自先验合格后直接拼接两份写文件代码。`SaveConcurrency.consistency=serializable`需要与FilePort、DocumentStore及具体工具/数据库共同取得真实资格，不能仅把“串行化”字符串传给TS模板。类似地，UI中按钮通过`actionRef`指向FilePort也不能直接证明拥有写入权限。

## 6. 对现有 `/1`四Kind与新 `/2` Profile 的兼容实现

- 保留旧模块、导出名、Schema和实际读者结果；新版本不回写旧 `/1` Body、自动迁移旧Goal或扩大旧语义。
- 一个`gift.project/1`的`sourceScopes`只描述可发现的来源范围，模块身份由其文件自身声明，`outputRoots`描述目标根集合；即使同时选中一个旧Goal和一个新System，也需要真实跨Profile的RootJoiner。找到了全部引用**不等于**六模态和完整系统之间的Requirement已联合。
- 新Dialect供应必须有内容身份、发行者、版本与BodySchema、类型/effect/语义/组合/降低接口以及独立Evidence。可加载JSON形状不意味着任意供应过程有执行权；未知解释节点保全并显式阻断需要它的Claim。
- 原生TS/Rust供应的公开签名可以被Gift引入，但NativeRegion继续由有权开发者/供应者维护；当Gift受管生成区与作者源码碰撞时拒绝写入，不强制用Git覆盖或丢失未提交的工作。第二次修改按SourceRevision+CAS验证，归属不同的区域独立回退。
