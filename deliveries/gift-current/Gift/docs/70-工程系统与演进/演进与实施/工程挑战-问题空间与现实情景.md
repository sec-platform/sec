# 问题空间、机制与现实情景

## 问题空间、机制与现实情景

### 世界工程机制覆盖矩阵

#### 覆盖原则

本矩阵是检查不同工程形态能否复用共同约束的设计索引，不是已执行验证；领域完整知识与运行支持需要对应资料和证据。

| 工程形态 | 关键机制 | Gift 共享内核 | 领域扩展 |
|---|---|---|---|
| 编译器/语言 | 类型、IR、pass、lowering、增量 | identity/relation/constraint/action/evidence | 语言 dialect/backend |
| Web | 模板、DOM、CSS、浏览器 | source/semantic/effect/verification | web dialect/browser provider |
| 数据库 | 事务、隔离、schema、恢复 | state/transition/resource/evidence | data dialect/store provider |
| 分布式 | 消息、分区、复制、共识 | identity/epoch/authority/recovery | distributed profile |
| 云平台 | 资源、部署、伸缩、区域 | capability/allocation/effect/support | cloud provider adapters |
| 嵌入式 | 实时、硬件、物理安全 | target/resource/claim/risk | hardware/real-time dialect |
| AI/ML | 模型、数据、漂移、工具 | candidate/provenance/authority/evidence | model provider/eval profile |
| 安全 | principal、trust、attack、incident | authority/effect/evidence/evolution | security policies/providers |
| 业务工作流 | actor、decision、compensation | operation/state/contract | domain definitions |
| DevOps | build/test/release/rollback | action/evidence/delivery/evolution | tool providers |
| 文档知识 | source、translation、projection | identity/provenance/invalidation | documentation domain |
| 组织治理 | role、policy、approval、appeal | authority/stakeholder/decision | organization profile |

#### 反特化判据

普通新业务应以用户定义、组合和绑定表达，不要求通用编排层增加一个场景分支。领域编译器、后端或适配器自然可以处理本领域的操作与类型，不能仅凭出现领域名就判定架构错误。真正的新语义揭示公共接口不足时，允许有理由地修改核心；必须说明旧接口遗漏了什么不变量、保持条件或能力，不能为维护“核心永不变”的叙事把语义藏进字符串。

#### 未覆盖声明

矩阵不证明具体法规、设备、协议或框架已支持。真实支持由相应 SemanticDialect、Provider、TargetProfile、conformance corpus 和 SupportCommitment 证明。

### 全景工程问题分类与生成规则

#### 生成而不是记忆

工程问题空间通过关系和反事实生成。每次分析从目标和对象出发，沿生命周期、主体、依赖、权限、资源、尺度、环境、失败和演进展开。

#### 对象轴

源码、配置、数据、模型、文档、依赖、制品、进程、设备、凭证、用户、组织、权威、证据、恢复资产和外部系统。每个对象检查身份、状态、owner、接口、消费者和物理绑定。

#### 生命周期轴

创建、发现、采用、使用、并发、变化、迁移、失败、恢复、支持、撤销、删除和历史解释。只设计正常运行而没有创建/退出会留下系统性漏洞。

#### 主体轴

调用者、owner、执行者、审批者、验证者、付费者、数据主体、受影响第三方、维护者、攻击者和未来继任者。检查谁获益、谁付成本、谁承险、谁可申诉。

#### 约束轴

物理、数学、逻辑、信息、时间、资源、权限、法律、资金、认知、组织、生态和路径依赖。区分硬不可补偿约束与可权衡目标。

#### 依赖轴

上游、下游、平台、供应链、共享资源、替代品、互补品、外部性、共同原因和恢复依赖。特别攻击“主系统与恢复系统共享同一故障域”。

#### 尺度轴

单对象/全局、单用户/多租户、正常/峰值、短时/长期、本地/跨区、平均/尾部、正常/恶意、静态/持续变化。

#### 失败轴

错误输入、沉默错误、假成功、超时、取消、竞态、资源耗尽、部分完成、丢句柄、恢复失败、监控失败、供应商退出、法律变化和黑天鹅。

#### 反事实问题

- 删除某对象会怎样？
- 替换 Provider 会怎样？
- 输入在检查后变化会怎样？
- 同一操作执行两次会怎样？
- 权限在执行中撤销会怎样？
- 恢复系统也失败会怎样？
- 新旧版本同时存在会怎样？
- 未观测部分恰好包含反例会怎样？
- 最强攻击者能控制哪些输入？
- 哪个未知一旦确认会反转结论？

#### 停止条件

只有新展开不再产生独立机制、根约束、owner seam、关键反证或反转条件，且 remaining frontier 有 owner 和触发器，才关闭当前分析代际。

### 开放世界工程问题空间

#### 目标

Gift 不把“所有工程问题”理解为一张永远不再变化的清单。现实会继续产生新的语言、平台、组织、法律、攻击、硬件和业务约束，任何静态清单都会失效。Gift 的产品身份仍是通用工程工作区编译器；本篇的开放世界问题分析是其可选设计/评审机制：组织当前已接纳问题的处置，显式记录覆盖边界，并在新事实出现时定位缺口、受影响闭包及重新验证义务。不能据一次搜索宣称已吸收世界全部知识。

```text
现实事件、用户目标、事故、标准、代码变化
→ 有界观察
→ 问题候选
→ 机制还原
→ 现有模型映射
→ 已覆盖 | 缺口 | 冲突 | 未知 | 不适用 | 延后触发
→ 设计修正或领域扩展
→ 本次目的要求的设计交付或获准的后续工作；实现、验证、迁移和退役不自动启动
```

“世界上某项目使用了某项能力”不自动构成 Gift 缺口。只有存在真实消费者，而且缺失会使身份、正确性、权限、效果、恢复、验证、发布或支持没有唯一答案时，才形成设计义务。

#### 八类根故障

以下八类是当前发现索引，不是已证明完备的分类定理。异常不能自然归类时，保留独立问题与机制，再修订分类，而不是塞进“其他”或强行改名：

| 根类 | 含义 | 典型表现 |
|---|---|---|
| 目标错误 | 目标、非目标、主体或价值函数错误 | 做对了没人需要的东西；局部指标伤害终局结果 |
| 观察错误 | 没看到、看错、看旧或混合现实 | 多文件混合快照；外部状态漂移；监控盲区 |
| 语义错误 | 身份、关系、状态、单位、上下文或边界错误 | 路径当身份；自由字符串当类型；不同状态机共用枚举 |
| 决策错误 | 候选不完整、硬约束漏检、未知被压扁 | 先按流行度选库；把不支持当低分候选 |
| 准入错误 | 无权、无能力、无资源或前像已变化仍执行 | 过期授权；错环境；资源配额未知却继续 |
| 执行错误 | 部分效果、竞态、重复、失控和结算失败 | 写到一半崩溃；重试重复扣款；子进程残留 |
| 证明错误 | 未执行、错环境、自证、覆盖不足或证据过期 | 跳过测试显示绿色；候选修改验证器后自证 |
| 演进错误 | 兼容、迁移、切换、恢复或退役不完整 | 永久双写；旧解析器继续是竞争事实源 |

#### 反例生成与跨边界追踪

发现轴沿用上面的对象、生命周期、主体、约束、依赖、尺度和失败，不再把同一份列表乘成貌似完备的数学张量。它们用于产生问题，不是固定输出目录或有限分类证明。

先固定本次判断的目标、对象、时间、环境、支持范围和真正消费者，列出当前采用的基线假设与最容易使结果反转的假设。沿每个关键接缝画出输入、解释、授权、依赖、实际作用、读回与恢复。检查同一个词在不同阶段是否实际上指不同主体、版本、物理对象或集合。

随后对机制施加有依据的变化：删除最后一个外部支持；改变条件但保持结果值；在检查与提交之间加入新规则；让旧响应迟到；让授权先后变化；同键重复与不同载荷碰撞；让恢复系统和主系统一起回退；增加无法取消的任务；让两方各持一半资源；恢复过期备份或离线删除前的副本。产生新决定性主体或约束时，回到上游重建适用范围，不只在原结论末尾加例外。

每个重要设计同时构造最强替代：不用新增机制能否成立，采用更小本地协议是否足够，已有原生工具能否承担。若某复杂机制只在团队或不可信宿主成立，保留该条件实现，不把成本强加纯库。若无法证明可以安全剪除某个影响，也不自动要求无限探索：标明未审范围、影响未知及需要进一步读取的条件，不把未探索记为不适用。

发现状态至少区分：已复现的文本冲突、有明确步骤的逻辑反例、缺少合同的接缝、已处理的机制、仍待环境证据的假设，及无独立依据的猜想。可以在正文以文字和表格表达，不要求为每条想法创建数据库对象。只有关键未知会影响本次实际动作或声明时才限制那个范围。

对重要反例保留初始状态、事件顺序、失效不变量、现行防线、修订后判断、残余前提和反转条件；不能只记录“存在竞态”或“一定要有测试”。有限书面推演是设计证据，只有真实执行并保存其输入/方法/结果才称运行实验。

#### 问题记录

```text
EngineeringProblem = exact {
  problemRef,
  observedSubjectRefs,
  intendedOutcomeRefs,
  observationAndCoverageRefs,
  violatedOrMissingConstraintRefs,
  causalMechanismRefs,
  affectedStakeholderRefs,
  effectAndRecoveryRefs,
  strongestCompetingExplanationRefs,
  unknownFrontierRefs,
  existingOwnerOrGapDisposition,
  verificationAndReversalRefs
}
```

上面的结构是需要持续追踪时的概念记录，不要求每次审查创建全字段实例。稳定引用由记录拥有者分配；机制、主体和作用域用于判断是否归入同一问题族，不假定存在一个从自然语言自动算出唯一根因ID的函数。确认同源的记录可以合并并保留各自证据；尚不确定时保留候选关系。相同报错可能有不同根因，同一根因也可能产生不同报错。

#### 缺口判定

建立新抽象前必须同时满足：

1. 有现实或已接受未来消费者；
2. 现有语义无法无损表达；
3. 缺失会导致可观察错误或无唯一裁决；
4. 能指出 producer、consumer、状态转移或故障证据；
5. 新抽象具有独立身份、合法性、失效、生命周期或权限语义；
6. 说明相对更小替代的预期收益、概念/实现/迁移/维护成本及关键假设；有实测时采用实测，无实测时只作可逆条件选择，不伪造精确净收益。

若只是新的品牌、产品实例、文件类型或 Provider，通常只增加实例、绑定或领域扩展，不修改核心。

#### 当前审查的结束与重新打开

不存在“问题世界永久完成”。本次可以交付的条件是：在已声明的输入与检查范围内，已发现的独立问题都有处置或明确未决状态；重要接缝和相反条文已沿所属规范检查；至少一轮有竞争解释和反例的复核不再改变当前主要设计；剩余前沿有可执行的读取、规范细化或环境取证方向。

这种结论是审查范围内的暂时稳定，不证明没有未知缺陷。不能把有限时间里“没有想到新例子”写成普遍完备定理；工具、权限或平台边界到达时如实记载已做到哪里。新事故、新消费者、新机制、新环境、相交约束或旧拥有者退出会重新打开相应问题，不要求所有无关设计重做。

#### 禁止的伪闭包

- 用文档数量、Issue 数量、测试数量或领域名数量证明覆盖；
- 把“暂未找到证据”直接解释为不存在；
- 把所有异常塞进 `other`；
- 为未知世界预建巨大 optional schema；
- 每发现新变量就加入全局版本号并使全仓重算；
- 把外部案例或标准直接提升为 Gift 权威；
- 把所有未来问题预先实现，导致当前产品无法形成最小闭环。

### 真实事故机制与系统反例

#### 使用方法

真实事故只作为机制证据和架构攻击，不直接成为 Gift 权威。每个案例提取：预期、实际、因果链、缺失约束、失败控制、恢复和可验证设计义务。

#### 维护操作扩大故障范围

一个获授权的维护命令使用错误参数，移除的容量远超预期；恢复又因规模和控制面依赖变慢。设计义务：参数化 Effect scope、blast-radius cell、capacity safety ceiling、独立控制面、操作前模拟和真实恢复时间。

#### 合法规则触发最坏复杂度

规则语法合法，但特定正则使 CPU 饱和并被快速全局发布。设计义务：算法复杂度检查、资源预算、staged rollout、即时 rollback、规则作为可执行语义而非普通配置。

#### 备份存在但恢复失败

误删除只是触发，多个备份和恢复步骤不可用扩大为数据损失。设计义务：RecoveryCapability、restore drill、独立凭证和存储、唯一恢复副本保护、RPO/RTO Evidence。

#### 复用软件的环境假设失效

旧系统中无害的数值转换在新运行域溢出，冗余通道共享同一软件错误。设计义务：Target/environment assumption、range proof、common-cause independence 和系统级验证。

#### 配置/模板与运行消费者不匹配

内容字段和 runtime expectation 不一致，静态检查未覆盖真实组合。设计义务：typed producer-consumer contract、版本绑定、runtime validation、分阶段发布和 rollback。

#### Plan 与现实漂移

计划生成后外部状态变化，执行仍基于旧前像。设计义务：PurePlan 与 Admission 分离、apply-time reobservation、CAS、actual delta 和 recovery-required。

#### 持续调和与外部修改

控制器不断比较 desired/current；一次成功写入不保证持续收敛。设计义务：controller contract、idempotency、hysteresis、single writer、drift provenance 和 bounded oscillation。

#### 删除需要 finalizer

对象被请求删除，但外部资源和清理义务尚未完成。强制移除 finalizer 会留下孤儿。设计义务：typed retirement obligation、operational terminal/physical clean 分离、不能手工擦除未知义务。

#### 供应链与自动更新

签名或更新渠道被利用时，合法发布机制成为攻击放大器。设计义务：source/build/artifact provenance、multi-party promotion、staged rollout、revocation、rollback 和 behavior verification。

#### 统一吸收

这些案例分别攻击目标、观察、语义、决策、准入、执行、证明和演进。新案例若只重复机制，无需新增 Core；若出现新不可表达状态律，才演进语义方言或内核。

### 系统级验收情景目录

#### 目的

系统验收不由单一测试套件完成。以下情景覆盖正常、异常、并发、恢复、演进、对抗和用户效果，每个具体产品画像选择适用集合。

#### 核心编译情景

1. 新建最小工程，从 Intent 到 verified artifact；
2. 接入存量 TypeScript 工程，保留人工代码；
3. 同一语义目标 lowering 到两个语言后端；
4. 新 SemanticDialect 接入而 Core 零业务分支；
5. 新 Provider candidate 只局部重算 resolution；
6. 无解约束返回最小 unsat core；
7. 歧义意图保留两个分支并阻断不可逆执行；
8. clean/incremental/cache-off 结果等价；
9. rename/move 保持语义 identity；
10. dynamic dependency frontier 被精化。

#### 执行和恢复情景

11. 单文件 mutation CAS 成功；
12. editor/disk divergence 阻断；
13. 多文件第 N 步 crash 后恢复；
14. 外部 API timeout after commit；
15. 资源耗尽和恢复 reserve；
16. cancel 后 child process residue；
17. worktree unregister 后目录删除失败；
18. deployment partial region；
19. data migration partial backfill；
20. rollback 不兼容后 forward recovery。

#### 验证和安全情景

21. required test skipped 不 PASS；
22. candidate 修改 verifier 自证被拒绝；
23. 多 Agent reviewer 共同原因；
24. cross-tenant cache 泄露；
25. prompt injection in PR comment；
26. supply-chain artifact substitution；
27. secret rotation and revoke；
28. restore drill with failed primary region；
29. hazard monitor unavailable；
30. user validation fails despite technical verification。

#### 演进情景

31. IR schema additive update；
32. semantic reinterpretation migration；
33. Provider disappearance；
34. old client mixed version；
35. legal/jurisdiction change；
36. deleted data restored from backup；

#### 完成

每个情景必须绑定 requirements、design owners、actions、evidence、environment、expected result 和 failure meaning；不适用有证明，未执行保持未完成。

### 边界、极端故障与黑天鹅场景

#### 极端不等于不可设计

无法预测具体事件，不代表无法设计对未知的响应。系统可以限制 blast radius、保持未知、提供恢复、记录来源和避免不可逆承诺。

#### 复合故障场景

1. 主数据库故障，同时备份凭证过期；
2. CI 平台故障，同时候选修改本地 verifier；
3. 网络分区期间授权撤销；
4. 磁盘满发生在 journal 写入后、Effect 前；
5. Provider timeout，实际操作已完成且 readback 最终一致；
6. 新旧 schema 混合，旧节点从备份恢复；
7. 安全事件要求紧急修复，但主分支保护不可用；
8. 监控与被监控服务共享故障域；
9. 多个 AI reviewer 共享同一错误模型；
10. 低概率尾部输入触发算法指数爆炸；
11. 用户在自动迁移期间手工修改同一对象；
12. recovery cleanup 删除唯一 forensic Evidence；
13. 法域变化使跨区 failover 变得不合法；
14. 供应商突然撤销关键服务和数据导出；
15. 时间回拨使 lease/expiry 判断错误；
16. 大规模自动修复形成正反馈并扩大故障。

#### 共同设计响应

- 关键状态和恢复路径独立故障域；
- prepared-before-effect；
- exact preimage、idempotency 和 readback；
- unknown/partial 状态；
- bounded blast radius 和 safe/degraded mode；
- recovery reserve；
- break-glass with expiry；
- content-addressed evidence；
- external/provider exit plan；
- common-cause analysis；
- incident-driven maturity downgrade。

#### 黑天鹅协议

当新事件无法映射时：冻结不可逆 Effect、保留原始 observations、扩大 affected frontier、建立最小问题 identity、寻找最高错误前提、形成 temporary safe policy、由有权 owner 修正模型、迁移并验证。

#### 验收

系统不要求在未知事件中自动成功，但必须做到：不撒谎、不丢证据、不扩大权限、不重复未知 Effect、不删除恢复资产、给出有界安全下一动作。

#### 每条需求最低结构

这里定义现有Requirement的语义信息，不是要求开发者为每个函数手填的公开Schema。先固定对象、含义、强度、适用性与接受来源；其他责任只有真实发生时存在。

| 内容 | 准确角色 |
|---|---|
| 对象及范围 | 约束哪个输入、定义、实例、目标、状态或轨迹；数据域及版本 |
| 含义与条件 | 引用已绑定的有类型关系、帧、时序与激活；尚未解释时保留真实原要求及未解释状态 |
| 强度与选择 | 硬约束、偏好、可接受默认、委派与例外，不从语气词猜权限 |
| 来源与接受 | 独立要求来自哪里、由谁在哪个范围接受；文档作者不是天然授权主体 |
| 需要时的关联 | 稳定requirementRef、相关结果与主体、依赖/冲突、规划顺序和演进/退役 |

精确含义和组合由[跨软件意图合同](../../20-语义与组合/组合/跨软件需求合同.md#cross-software-intent-contract)拥有。`Assurance.plan`再产生验收义务与检查请求，方法与结果不属于每条需求的必填含义。检查可以引用相同要求，但不能因选择了有限方法而把原要求缩为有限样例。已有持久来源按其实际格式和解释绑定读取，不通过改概念表静默迁移字段。

#### 需求质量

检查必要、准确含义、适用范围、一致性、可行性、可追踪与可修改性；逐项说明可用的检查办法和覆盖。只有笼统愿景而尚无准确行为时保留Goal并继续细化；已有准确要求但当前没有足够方法时，要求仍然存在，检查状态保持未知，不自动降格或删除。

#### 非功能需求

“高性能”“安全”“易用”必须分解为场景、主体、刺激、环境、响应和度量；没有 baseline 时不编造阈值。

#### 裁剪

由 ProductProfile、TargetProfile、DeploymentProfile、Stakeholder、Data/Effect 和 risk 关系证明 required/not-applicable/deferred。没有实现不能反推不适用。

#### 冲突

能够确定的硬约束冲突返回真实冲突关系；只有相应求解实际给出时才称unsat core，未最小化不称最小核。未确定不代表相容。偏好按已委派的有依据策略比较；主体权利冲突保留其范围及有权处置，不能由实现选择器裁决。

#### 变化

需求 revision 只使实际消费者 stale；解释、设计、实现、测试和支持通过 traceability 传播。
