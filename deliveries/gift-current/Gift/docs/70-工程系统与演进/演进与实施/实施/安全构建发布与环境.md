# 安全构建发布与环境

## 安全工程、威胁建模、审计与响应

**来源与可复现性。（消费条件）：** 工具链、依赖与制品签名是不同的信任链；发布资格必须绑定当前政策下各链的证据，而非仅比较两次输出hash。 合同归属：[来源锁、包身份、构建脚本与被替换的下载终点](../../../50-执行运行与观测/平台生态/依赖与生态解析.md#gift-supply-chain-identity)。

**发行资格。（消费条件）：** CI成功或包已签名仅支持其实际检查与签发事实，不自动证明所有配置、租户或运行环境均可安全使用。 合同归属：[设计能力、代码实现、测试结果与正式支持的阶段资格](../适用性与能力协商.md#gift-epistemic-support)。

**防绕过。（消费条件）：** 防护实际生效点在服务端受信边界与目标执行器，不以client-only检验、README声明或可编辑CI文本作为不可绕过证明。 合同归属：[全体系门禁如何防止自证循环与无关大检查](../../../60-保证与证据/保证/系统不变量与组合.md#gift-guardrail-integrity)。

**远端执行资格。（消费条件）：** 远端只读计算可复用的前提是其真实沙箱、网络、依赖脚本与日志披露经过核验，不凭“远端编译”四个字免除信任审查。 合同归属：[远端编译竞速、等待图和不可信结果的分界](../../../40-目标与制品/递归并行与远程编译.md#gift-distributed-boundary-lease)。

### 安全进入每个阶段

需求、设计、实现、依赖、构建、测试、部署、运行、支持和退役都产生安全义务。发布前扫描不能替代生命周期控制。

### ThreatModel

```text
ThreatModel = exact {
  assetsAndSecurityObjectives,
  trustBoundariesAndPrincipals,
  attackSurfacesAndCapabilities,
  threatScenarios,
  controlsAndResidualRisk,
  verificationAndMonitoring,
  incidentAndRecovery,
  scopeAndRevision
}
```

### 控制

最小权限、能力代理、输入验证、沙箱、秘密管理、网络分段、供应链控制、审计、限流、备份和安全默认值。每个控制都必须绑定可执行的强制证据。

### 审计

记录有意义的 authority/Effect/decision/readback，而不是复制所有数据。日志 tamper-evident、受限、可关联且有 retention。

### 漏洞流程

发现→确认→遏制→修复→验证→发布→监控→披露。紧急修复仍保留最小不可跳过的 identity、scope、Effect 和 readback。

### 响应

隔离、credential revoke、evidence preservation、用户影响、恢复和长期设计修正。事故不能只关闭 ticket。

### 验证：安全工程、威胁建模、审计与响应

威胁建模与滥用情景、提示注入、供应链失陷、权限提升、秘密泄露、审计旁路、事故演练和紧急修复。

## 性能测量、基线、剖析、预算与回归

### 先测真实关键路径

实现前不预填永久秒数。选择真实用户操作和代表性仓库，记录 orientation、observation、compiler、verification、provider、cleanup 和 readback 阶段。

### Instrumentation

复用 operation/action identity，记录开始、阶段转换、结束、CPU、RSS、I/O、queue、cache、physical starts、reused/joined/invalidated。长时间无输出的阶段仍须有有界心跳和已耗时；父阶段覆盖子进程、等待与结算，最终给出墙钟总时长，不能把多个并行阶段耗时相加冒充总时长。日志是可关联的进度投影，不签发 Action、权限或通过结论；高基数和敏感数据受限。计时缺失或子进程无终态须显示 unknown，不把未观察时间记成零。

### Baseline

绑定 exact workload、environment、toolchain、revision 和 correctness outcome。冷/热、cache-off、Windows/Linux 和不同规模分别。

### Budget

预算既有安全 ceiling，也有 SLO target。超预算可以取消、降级或排队，但不能跳过 required correctness。恢复/cleanup 保留独立资源。

### Regression

使用统计和实际重要性阈值；样本不足为 inconclusive。优化必须有 equivalence、failure、rollback 和 retirement。

### 优先次序

消除重复 observation和Action；复用 exact key；增量；并行；最后考虑 native/Rust/Go/remote 等更快机制。

### 验证：性能测量、基线、剖析、预算与回归

长会话、历史增长、冷/热缓存、并行竞争、资源压力、观测开销、测量缺失、前后对比和正确性等价。

## 持续集成、合并授权、主分支健康与发布

### 平台入口必须不可绕过

本地 Hook 和脚本可改善反馈，但不能证明服务器端 enforcement。受支持 merge/push 路径必须经过同一 VerificationSession 或旁路后使主分支进入 locked/degraded。

### CI 分层

```text
cheap exact-identity orientation/preflight
→ compile RequiredClosure ∩ MissingOrStale
→ affected deterministic selection for narrowed profiles only; full inventory bypasses selection
→ physical/provider actions
→ independent review
→ exact-head authorization
→ merge expected tree
→ main-only readback
→ release artifact verification
```

### 单一状态

多个 workflow/check 只投影一个 Session；不靠事件时序、PR body 编辑和 check 名称互相发现。动态状态保存在 machine registry/journal。同一 exact candidate 的 Gate、依赖与检查结果依各自 ActionKey、环境及有效期复用或 join；不同入口名称、日志或同树但不同有效输入都不能制造第二份结果，也不能让不适用的 selector 成为全量验证的前置。

### Branch protection

required checks、review、expected head、no force/direct push、admin/break-glass 策略、merge queue/automation 和 ruleset 通过平台 readback 证明。平台能力缺失时诚实限制 support scope。

### MainHealth

没有 hosted checks 不等于健康。本地 trusted provider 可以产生 exact receipt，但 selector 不隐式启动验证。provider 冲突时 fail closed。

### 发布

source verification、artifact build/install、promotion 和 deployment 分离；同一 artifact 跨环境提升，避免重新构建。合并只消费其确实要求的候选源码验证、独立审查及集成合同；发布制品构建属于合并后独立动作，除非某个冻结 Claim 明确要求该制品作为合并前证据。测试内部构造的临时 fixture 不等于发布构建，也不得把发布部署偷偷设为普通合并的前置。

### 验证：持续集成、合并授权、主分支健康与发布

检查缺失、管理员旁路、工作流模式漂移、自审、基线失败、合并响应丢失、树不匹配、合并后主分支失败和制品失败。

## 测试目录、责任元数据与验证动作编译

### 目录不承担全部语义

`unit/`, `integration/`, `e2e/` 可作组织，但不能同时暗含速度、资源、owner、重要性、平台和 requiredness。

<a id="canonical-test-responsibility"></a>
### TestResponsibility

TestResponsibility 的唯一 machine contract 在这里维护。它描述长期保留、实际会物化 case 的 TestCase／有限 TestFamily 责任；路径、suite、标题和 fast/slow 只作定位或执行投影。一个 case 可以支持多个 ProofObligation，但每个义务的判错含义、观察边界和 Oracle／独立性解释必须随该义务绑定，不能用一个顶层字段替所有 Claim 作解释。

```text
TestResponsibility = exact {
  testRef, testRevision, ownerRef,
  bindings: [{
    proofObligationRef, proofObligationRevision,
    selectionRef, selectionRevision,
    failureMeaning, observationBoundary,
    oracleAndIndependenceRefs
  }],
  environmentAndResourceRequirements,
  impactAndLifecycle,
  retirementConditions
}
```

每组 binding 必须核 `selection → obligation → claim` 的准确修订关系。相同 testRef 对不同义务可以共享一次物理 case 执行，但失败归因、Evidence 接纳和 retirement 逐 binding 评价；不能复制同一稳定 test identity 来逃避多义务关系。字段可由受信测试定义、固定选择和环境合同派生，不要求简单 case 手填完整信封。动态生成 case 无法在所需范围内准确枚举时保持 unknown，并由 Provider 发现与 Source Program census 对照，不以空列表表示完整。

#### 已接受基线责任的源码表示

本仓库的无替代退役只消费**独立采用的 BASE 测试源中已存在**的责任，不允许删除批次重新定义旧义务。

当前有界表示是测试模块顶层唯一的 `const GIFT_TEST_ACCEPTED_RESPONSIBILITIES = [...]`；initializer 必须为严格 JSON 数组（最多 128 项、512 KiB、32 层），每项字段精确为 `schema: "source-program-accepted-test-responsibility-v1"`、`role: "accepted-baseline-test-responsibility"`、`testId`、`registrationContentDigest` 和完整 `VerificationTestResponsibility` 的 `responsibility`。这项显式角色声明表示原责任 owner 接受的完整 binding 集，不是示例对象、运行时计算结果或作者的 `completeness` 自证。JSON 不接受调用、import、spread、getter、计算键、重复键、注释或类型断言；其他同名／多份声明、重复注册绑定、错误 owner 或注册内容均不产生可用接受事实。未声明、歧义或不能严格解码保持 unknown，不能把缺失解释为没有义务。

Source Program 从已封印模型所绑定的准确测试源读取该字面量，核原 registration id、完整注册内容 digest 与测试责任 owner。物理 sourceRevision、测试源 contentDigest 和 definitionInputDigest 由该生产者在外部补齐并进入事实摘要，不能要求字面量嵌入包含自身的源码摘要。Claim 的 subjectRevision 是原已接受语义修订；准确 BASE 物理修订由上述生产关系绑定。Requirement／Claim／ProofObligation 的 owner 来自原 specification，可与测试实现 owner 不同。无替代退役必须逐一处理原完整 binding，不得凭当前删除理由重新缩小旧责任；legacy 未评估测试必须先走独立原 owner 的基线采用工作，不能在同一删除批次补造。

当前删除评论只提交准确 testId 与已观察 acceptanceDigest 的定位／比较引用，不能提供原责任内容。另行的语义退役采用绑定原 specification 中的 canonical requirement 文档引用、旧／新准确 commit、blob 与内容摘要、Claim／义务修订、subject、适用范围及环境画像。仅文档缺失、测试缺失或作者 reason 不证明义务退出。仓库特定 Assurance policy 在已采用受信基线中允许当前 User maintain/admin 为这些准确 owner 采用语义变化，并可与测试作者同一人、同一评论完成；该权限不是产品的通用硬编码授权。仍活跃的 binding 必须保留；范围／owner／原 source ref 不匹配、没有修订或残留 required binding 均拒绝无替代退役。

源码事实和纯条件判断不产生采用权限。反序列化的 retirement facts 仅能生成 `conditional-candidate`，不能恢复 sealed compiler receipt；普通 DELETE 投影仍要求原封印生产者。活宿主须接合真实合格源码 Action／attempt、当前采用解释器与 policy、同仓库 PR 主体及真实评论／角色观察，临近合并／发布效果再次检查 requirement source、policy、主体和权限；撤销／漂移使采用失效。仅评论改变不重跑未失效的源码 Action。生产使用新 v2 评论之前，必须先在原 v1 输入下采用 reader、字面量合同和 policy；候选不能赋予自身权威。此表示只覆盖已有合格基线责任的测试，不宣称已解决所有 legacy 删除。

### Discovery

source census 与 runtime discovery 对齐；raw `test()` 在迁移期标 unresolved，不可遗漏。title/path 是 locator，不是 test identity。

### VerificationAction 编译

从 changed delta、claims、applicability、environment 和 resource 生成去重 Action DAG。缩小的 quick/affected 闭包需要可靠影响与 ownership 证明，未知则拒绝缩小；full 闭包由完整测试目录和责任预算直接编译，不能为了证明“全部”再执行 affected selector。已选全量 fast 与全部 slow suite 时，另一个 affected-tests Gate 只有独立 Claim 才可保留，且必须说明它证明了什么新增性质。测试 runner 只执行，不拥有选择和结果真值。

### 外部 runner

优先使用 Bun、Playwright 等成熟执行机制，但 Gift 保留 Test Responsibility、Impact、ActionKey、Evidence 和 Result。采用后删除重复 scheduler。

### 退役

测试删除需证明 claim 不再 required、replacement 覆盖或产品非目标；测试烦人和当前失败不构成删除理由。

### 验证：测试目录、责任元数据与验证动作编译

运行时发现与源码发现等价、零选择、平台跳过、测试标题变化、稳定标识重复、资源冲突、运行器缓存、失败含义和测试退役。

## 配置、密钥、环境与部署画像

### 相交对象不是一条“配置层级”

部署场景会同时看到Product/Profile要求、DeploymentProfile、EnvironmentBinding、SecretBinding、客户端Preference和RuntimeObservation，但它们属于不同authority、语义与生命周期，**不能排成一条覆盖栈，也不能合并为自由环境变量表**。

| 对象 | 正确角色 | 能否覆盖什么 |
|---|---|---|
| Product/Profile要求 | Author侧Requirement/Profile展开 | 形成部署必须满足的产品条件；不被环境或用户偏好覆盖 |
| DeploymentProfile | 部署owner的版本化部署选择/约束 | 只在其声明的deployment scope和字段合同内贡献 |
| EnvironmentBinding | Host adapter取得并类型化的环境输入 | 绑定已声明的部署字段；不凭环境变量存在创造产品Meaning |
| SecretBinding | Secret/provider authority的capability引用 | 提供可授权秘密，不把secret内容复制进普通配置 |
| UserPreference | Client侧Presentation Preference | 只改变客户端呈现；不覆盖部署、运行或产品Requirement |
| RuntimeObservation | Runtime authority产生的Observed fact | 只读反馈实际生效状态；不能反写成Requested/Required值 |

它们进入[Developer Decision四轴](../../../20-语义与组合/作者语义/开发者决策模型与设定面.md#developer-mental-model)与[DecisionContribution正交合同](../../../20-语义与组合/组合/稀疏控制与目标限定.md#decision-contribution-algebra)后再由真实consumer解释，不创建第二套“部署配置优先级”。

### 字段合并、默认与动态覆盖

每个可部署字段由自己的descriptor/owner定义scope、合法producer、merge/default规则、validation、secret status、restart/reload、revision和provenance。硬Requirement共同成立；Prefer只在合法集合内排序；default只填充该owner明确允许的省略；动态override只有字段合同显式允许且运行consumer能验证、施加、读回时才存在。若某字段确需多个软候选，其优先关系是该字段的**版本化局部偏序/有界选择策略**，不是加载顺序、文件位置或全系统通用source priority；无法比较的竞争贡献返回Conflict/Needs。

### 环境变量

只作为 Host adapter 输入，解析为 typed config 后不在 Core 四处读取。absence、empty、invalid 分开。敏感值不进入 logs/digests。

### DeploymentProfile

绑定 Host、OS、filesystem、runtime、network、storage、identity、resource、region、security、observability 和 support cell。环境名 `prod` 本身没有语义。

### 动态配置

需要热更新时定义 consistency、atomic snapshot、validation、rollout、rollback、watch failure 和 old consumer。普通常量不因此进入配置服务。

### 验证：配置、密钥、环境与部署画像

字段贡献冲突、未知字段、秘密暴露、动态配置陈旧、部分更新、环境错误、画像不匹配、离线模式和回滚；验证必须保留各producer/authority/scope，不能只报告“优先级错误”。

## 错误码、接口模式与兼容策略

### 稳定错误身份

构建、发布与环境 Provider 消费[共同错误与局部结果合同](../../../20-语义与组合/共同语义/规范元模型与结果语义.md#result-algebra-boundaries)，不维护第二套全局错误语义。错误文本用于人类，不用于控制流；构建失败、发布效果未知与发布成功后的健康检查失败是不同对象。

### ErrorEnvelope

字段、版本、cause、脱敏与重试建议的唯一合同是[ErrorEnvelope](../../../20-语义与组合/共同语义/规范元模型与结果语义.md#error-envelope)。本层负责把真实工具/宿主的结构化 code、errno、回执和原始受控引用映射到它，绑定具体 candidate/artifact、环境、Operation/Attempt；不以内嵌字段签发新的执行许可。

### 兼容

Provider/客户端升级先协商实际错误 schema。新增 code 不自动对封闭消费者兼容；无法理解发布效果的旧客户端保留原操作身份并读回，不能默认重试发布、卸载或回滚。已发布的旧 Artifact 与其回执不因新 schema 被重新解释。

### Cause chain

工具返回失败后仍需区分是否留下 staging、部分上传、已切换的发布指针或未关闭的实例。下游健康检查失败不能覆盖“发布指针已切换”的事实；回滚是新的有权操作并关联原发布，不是改写原回执。结构化 cause 和受控 Provider 引用按共同合同保留，秘密不复制到客户端或公共日志。

### 验证：错误码、接口模式与兼容策略

本层取证覆盖 Provider 文本变化、本地化、未知错误码、嵌套原因、部分效果、重试前置、旧客户端模式兼容和错误脱敏；另核提交成功后响应丢失、发布成功后健康失败，及新客户端读旧回执。共同载体通过不代替这些真实 Provider 映射与发布结算的符合性。

## 自举前的安全构建、供应撤回和独立发行

自举候选不得同时拥有挑战规范、核验器、信任根和发行位置写权。构建在固定输入与独立 staging 中进行，验证过程由外部控制面发起并捕获原始结果；发行者检查相交源码、工具链、方法、平台、保证及恢复链，再按有权策略签名采用。签名并不补足失败的行为测试、缺失源材料或不可信种子。

可重建材料至少覆盖实际源快照、锁、生成器/规则、工具可执行来源、必要运行库和精确构建选项；只保存一个下载地址不能保证以后仍可重建。秘密不进入公开源码、目标制品、构建日志和可复现比较输入；需要签名时在冻结制品之后单独执行，签名差异不偷偷污染程序字节固定点声明。

供应被确认污染时停止新准入、撤销相交资格、保留调查与恢复材料，改走独立可信来源；不能自动回退到同一污染链。安全撤回和普通功能回滚的触发/速度可以不同，但都有具体 owner。版本已发行不意味着必须永远启用；仍有在途效果和旧数据时按相应恢复协议保留必要读取与结算能力。

Windows/其它宿主的路径编码、大小写、保留名、长路径、文件共享锁、可执行搜索与动态依赖解析分别检查。打包可移植性与真实安装/运行资格分开；ZIP 路径合法不证明目标工具链可运行，也不保证现场磁盘持久行为。

## 依赖、插件、构建与发行的四重权限

下载/读取依赖文件、运行依赖构建脚本、获得秘密、签发/上传发行制品分别授权。固定摘要只证明所取字节匹配，不证明其正确、安全或许可可用；签名只把字节与签发身份关联。插件的声明权限与实际宿主限制必须同时存在，不能把不可信代码放到同进程后靠接口注释隔离。

构建默认无网络、无用户凭证和不必要宿主写权；缺必要资源通过capture/依赖取得流程单独处理。Cargo build.rs/proc macro、包安装脚本、动态生成工具或原生链接钩子都是实际代码执行，必须记录及受权，不因为属于“编译”阶段就自动放行。输出验证发生在脱离构建写者的只读制品快照上。

许可与来源记录针对实际被分发的源码/二进制/生成模板及修改关系；不能根据仓库许可证名字推导所有第三方文件都可按同一条件分发。具体条款由真实许可证文本和接受政策提供，本设计不替用户作未知法律认定。不能取得许可依据时阻断相交发布，不妨碍不分发的独立设计分析。

发行签名服务/令牌不暴露给待核候选构建；外部release主体依据精确artifact/evidence/授权签发。依赖或工具污染后撤销来源，隔离受影响制品、保留事故证据并从已知可信源重建，不能只把版本字符串改大或清缓存。

**验证与反例**：依赖脚本读秘密、构建器篡改checker、签名即安全的误判、第三方文件许可缺失、污染重建和不相交发布分离。

**实际能力边界**：实际供应链扫描、法律文本判定和release操作未执行；没有创建密钥或CI。
