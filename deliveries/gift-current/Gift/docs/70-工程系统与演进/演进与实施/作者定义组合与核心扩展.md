# 作者定义组合与核心扩展边界

本篇只拥有**作者定义的能力如何组织、如何接入 Gift、何时保持为普通工程/库/Provider、何时确实需要扩展公共语义**的通用合同。它不拥有任何行业的业务对象、流程、策略、模型或默认实现。游戏、仿真、医疗、金融、制造、AI 等材料统一属于领域研究或组合研究：用于发现缺失区别、研究组合能力和设计反例，不是 Gift 自带业务能力，也不自动属于 Assurance。

Gift 的目标不是提供“万能业务平台”，而是提供足够稳定的工程语义、实现选择、目标生成、运行治理和证据机制，使作者能够**自己定义任意业务/领域、组合成熟实现并生成完整工程**。普通新业务不应要求修改 Gift Core；只有现有公共机制无法保持一个真实、跨实现必须可观察的区别时，才进入扩展判定。

## 业务组合与合法承载

### 五个必须分开的层次

| 层次 | 拥有什么 | 明确不拥有什么 |
|---|---|---|
| **Core Kernel** | 身份/修订、Semantic Contract、Requirement、authority/provenance、组合引用、Binding、Target/Artifact 身份、Operation/Attempt、Claim/Evidence 接合、受控变更、恢复与演进等系统级不变量 | 行业对象、业务流程、完整应用 DSL、游戏规则、仿真模型、账务方案；也不默认拥有状态机/流/AD等所有可选语义实现 |
| **Standard Semantic Modules** | 类型/计算、对象与控制、状态、关系、流/时间、数值/AD 等跨业务且可独立组合的公共语义 | 不能打包成某行业或完整应用的 turnkey 方案；不能自己建立第二套 identity/authority/Evidence/permission/runtime control plane |
| **作者工程与库** | 具体业务 Definition、规则、算法、工作流、数据模型、状态组合、资产、产品策略、私有配方，以及跨行业但已经是完整应用形态的复合库 | 不能凭“作者定义”扩大执行权限、降低目标/证据要求或取得 Kernel 写权 |
| **Implementation / Provider / Target** | 成熟库、框架、求解器、引擎、驱动、服务、SDK、目标后端及其精确能力/版本/成本/限制 | 不拥有作者业务含义；Provider 注册不能代替 Requirement 与语义合同 |
| **Assurance** | Claim、Proof Obligation、Verification Method、Evidence、Coverage、Verdict 与资格复用 | 不生产默认业务对象、标准业务模块或运行时；领域研究本身也不代表已实现/已支持 |

上述产品层可以相交，但不能折叠成一个 `Domain Runtime`、业务注册中心或全局插件容器。尤其要防止一种常见漂移：某个复合方案因为“适用于很多行业”就被误升为公共 Core。**跨行业复用只证明值得抽取；抽取结果仍应优先成为普通库或 Standard Semantic Module，只有系统级共同不变量才进入 Core Kernel。**

### 一个具体业务怎样在 Core 外由作者组织出来

一个真实业务能力应从它自己的可观察语义开始，而不是先寻找 Gift 内置行业模板。正常路线是：

1. **定义业务事实与区别。** 用现有 Definition、类型、关系、状态、约束、Requirement、资源、时间和效果表达真正需要保持的内容；无法由已有定义推导的独特规则由作者源码/算法承担。
2. **形成可复用边界。** 稳定公开面进入模块/库/接口；实现细节保持封装。复用单位由真实语义和演进边界决定，不按“一个业务名一个 Block”机械拆分。
3. **声明实现需求。** 只有需要成熟库、Provider、设备、服务或目标专有能力的地方进入 Method/Capability/Requirement；作者可以 Pin、Forbid 或委派自动选择。
4. **解析真实实现。** Resolver 在有限候选中核版本、平台、许可证、能力、成本、目标和保证，产生精确 Binding；候选发现不等于采用。
5. **生成目标工程。** Target backend 消费已固定的语义和 Binding 生成目标源码、配置、资产和构建闭包；不把 Gift 内部模型直接搬进运行产物。
6. **执行真实作用。** 文件、网络、设备、发布、支付等现实作用进入原 Operation/Attempt、权限、资源和恢复合同；业务定义本身不获得旁路权限。
7. **取得与业务要求相交的 Evidence。** 只有实际 Claim 需要的行为、性能、可靠性、安全、现实适用性等才进入对应验证；“能编译”不能代签业务正确。
8. **持续演进。** 作者规则、实现、目标、数据、外部协议或现实环境变化分别失效其真实消费者；不因某一层变化全局重建，也不把旧运行静默改成新语义。

因此“Gift 不直接提供业务”和“Gift 能组织实现任意业务”不是冲突：前者限制 authority 与默认供给，后者要求组合、扩展、实现解析和目标生成足够开放。

<a id="open-composition-closure"></a>
### 开放组合闭包：怎样判断“业务由作者组织实现”真的成立

Gift 的通用性不是靠预先枚举业务种类，而是靠**扩展后仍保持同一条编译、治理和证据主链**。对一个此前从未出现过的业务，若它的可观察要求能够分解到现有公共语义，则整个业务应在不修改 Kernel 的前提下完成；若出现真正新的公共语义，也应先作为可安装、可版本化、可迁移的语义扩展进入，而不是等待中央业务清单增加名字。

一个开放组合系统至少同时满足以下闭包条件：

| 闭包 | 必须成立 | 失败信号 |
|---|---|---|
| **作者定义闭包** | 新业务对象、规则、关系、算法、资产和产品策略能由作者 Definition/Module/原生源表达，并拥有自己的稳定身份和版本 | 每增加一个行业名都要修改 Kernel enum、schema switch 或中央对象表 |
| **要求闭包** | 新业务性质能发布自己的 RequirementDefinition/Profile，并由通用 Requirement 组合、冲突和来源规则消费 | Core 必须预先知道“游戏延迟”“医疗合规”“金融限额”等字段名才能表达硬要求 |
| **语义扩展闭包** | 现有语义不足时，用户可提供版本化 SemanticModule/Dialect，声明类型、规则、效果、保持、迁移及消费者接口 | 只能在 Gift 主仓库手改 parser/pass 才能让一个新语义被理解 |
| **实现供给闭包** | 新算法、库、引擎、设备、服务可通过 Method/Provider 进入候选、资格、Binding 与替换流程 | 新 Provider 需要获得业务 authority，或 resolver 按品牌/行业硬编码选择 |
| **目标闭包** | 新语言、ABI、平台或封装形态可通过[开放 TargetProfile](../../40-目标与制品/目标/README.md#open-target-profile) + lowering/Artifact 合同加入，只影响实际相交根 | 每新增目标都必须修改全部业务 Definition，或目标后端重新决定业务 Meaning |
| **执行闭包** | 新现实作用复用 Grant、Operation/Attempt、资源、readback、恢复和退役，不建立行业自己的旁路事务系统 | 某业务插件可绕过当前权限、未知完成或资源结算 |
| **保证闭包** | 新 Claim 可绑定已有或新 Verification Method，Evidence 与 Coverage 按准确主体/版本/环境取得 | Provider/测试脚本/研究文档可以自行给自己签发“已支持” |
| **演进闭包** | Definition、SemanticModule、Method、Provider、Target 与数据可独立升级、并存、迁移和退役，失效只传播给真实消费者 | 一个插件升级迫使全系统重建，或旧运行被新解释静默改义 |

这里的关键不是“所有未来语义都不改任何公共接口”，而是**新增业务不会因为业务名称本身迫使 Core 改动；新增语义只修改真正需要理解该语义的扩展接口和消费者**。因此开放性有三个层级：

1. **零平台修改**：业务完全由已有 Standard Semantics + 作者 Definition/库组合，最常见。
2. **用户可提供语义扩展**：出现新的可观察语义，需要 SemanticModule/Dialect 与相交 lowering/validator；Kernel 身份、权限、Binding、Evidence、恢复协议仍不改。
3. **Kernel 演进**：只有区别见证证明现有系统级不变量无法安全表达身份、authority、作用、Evidence、恢复或演进，才修改 Kernel。

这也给出一个反向验收：若实现某个新业务必须修改中央 `switch(domain)`、复制一套权限/证据/事务/版本系统、把行业字段塞进 Canonical IR 固定 schema，或让 Provider 名称直接决定业务语义，就说明开放组合闭包被破坏。相反，只是新增 Definition、库、SemanticModule、Method、Provider、Target 或 Claim 并沿既有主链接合，不是“平台又多了一项内置业务”。

#### 组合结果的规范形状，而不是预制产品族

任何完整产品都可以被理解为一组**被实际选择的关系闭包**，而不是从固定 `AppKind` 中挑一个：

```text
Author roots + Definitions + Requirements
  + selected Semantic Modules/Dialects
  + qualified Methods/Providers + exact Bindings
  + Target profiles + Artifact closure
  + admitted Operations / runtime responsibilities
  + requested Claims / Evidence
  -> one concrete engineered product
```

这不是要求持久化一个新的“万能 ProductRecord”；每一项仍由原 owner 保存。上式只是说明完整产品的闭合条件：任何缺项都应以准确 Need/Unsupported/Conflict/Unknown 暴露，而不是由行业模板补默认。Web、服务、游戏、仿真、编译器、设备程序只是这些正交关系的常见组合结果，不是 Kernel 的类型枚举。

### 业务与专业内容的合法承载方式

领域内容无需新的中央 `DomainObject` 或 `BusinessKind`。按实际责任使用现有对象：

- **Definition / Module / library**：领域概念、接口、规则和算法；
- **Requirement / Profile**：某个产品或用途要求的能力、性质与组合条件；
- **Relation / State / Transition / Task / Resource 等已有语义**：仅在其真实含义相同的时候复用，不因名称相似强行映射；
- **MethodSpec / Candidate / Binding**：领域算法或成熟实现的候选与选中结果；
- **Provider / adapter**：外部库、引擎、设备、服务和工具的真实能力边界；
- **TargetProfile / ArtifactSet**：目标平台、ABI、运行环境及完整交付；
- **Claim / Evidence / Coverage**：特定用途下的保证与验证；
- **Operation / Attempt**：真正对外产生现实效果的动作。

若一个业务只需这些既有构造的组合，它就是普通作者工程，不创建新 Core 类型。即使它很复杂、代码量很大、需要多个 Provider，也不能仅凭规模升级为平台原语。

### 组合不是预制业务模板

Gift 可以让作者把多个已有定义、库和 Provider 组合成高层能力，但组合仍遵循真实依赖：

- 同一业务可选不同实现；同一实现可服务多个业务；
- 模块边界按 public contract、生命周期和演进责任确定，不按行业章节数量确定；
- 一个高层 Profile 可选择一组 Requirement/Definition，但 Profile 不是隐藏 merge source；
- 自动装配只能在已声明兼容关系、能力和约束内完成；
- 缺失业务规则时返回 RequiredUnbound/Needs，而不是补默认成功；
- 多个独立作用必须保留各自 Operation/Attempt/结算，不能因属于同一业务事务就假定外部世界原子；
- 业务层可自己定义 Saga、补偿、workflow 或状态机，但 Gift 只保证其使用的公共效果/恢复机制，不预置具体商业流程。

### 实现自由与可控性的共同边界

作者可以只指定业务含义和硬约束，让编译器自动选择实现；也可以对关键库、算法、目标、资源或 ABI 精确 Pin。两者都消费同一 Requirement/Binding 模型：

- **Auto**：只在合格候选集合内选择；
- **Pin**：固定特定实现/版本/策略，同时仍需通过硬要求；
- **Forbid**：排除不接受的实现或能力；
- **Prefer**：只排序，不放宽合法性；
- **Profile**：打包一组可版本化 Definition/Requirement，不取得独立 authority。

未来出现新的需要控制的维度时，先判断它属于 Meaning、Requirement、Realization Control、Runtime Input 还是 Presentation Preference，再由真实 owner 扩展 descriptor；不能为了“以后什么都能调”预建 UniversalConfig。

### 领域库、成熟生态与业务秘密

领域库可以完全由用户/组织自己维护，也可以来自第三方生态。Gift 只需理解其公开合同和实际接入所需的语义，不要求把库源码复制到 Gift Core。实现发现与绑定应保留：

- 来源、版本、许可证和完整性；
- 精确 capability 与不支持项；
- 构建/运行目标和依赖；
- 可观察行为、错误、线程/进程/设备边界；
- 成本与资源模型；
- 需要的 adapter/lowering；
- 相交 Evidence 与适用环境。

私有业务算法可以作为封装库或原生资产接入；“不让使用者看到实现”与“编译器需要知道足够的公开合同”可以同时成立。隐藏实现不能隐藏其效果、资源、错误、权限和可兼容边界。

## 语义扩展与核心晋级

<a id="domain-extension-witness"></a>
### 什么时候才算出现新的公共语义缺口

扩展请求必须先给出**区别见证（distinction witness）**：两个输入在当前 Core 看起来完全相同，但按真实需求必须得到不同的合法性、编译结果、运行行为、失效、恢复或 Evidence 结论。只说“这是一个新行业”“这个库很复杂”“需要一个新的 Block 名字”不构成见证。

有效见证至少回答：

- 区别的观察者是谁，在哪个边界可观察；
- 区别依赖哪些作者事实、运行状态或外部事实；
- 若不表达这个区别，会产生什么错误结果；
- 是否能用普通 Definition/Requirement/关系/算法组合表达；
- 是否只需新的领域库或 Provider adapter；
- 是否必须让 compiler、runtime、assurance 或 editor 理解它才能保持正确性；
- 该区别是领域局部，还是已在多个彼此无关领域以相同语义重复出现。

没有这组信息时，保持普通用户定义，不提前制造 Core 扩展。

### 作者语义扩展的闭包

若确实需要扩展，仍复用[语义扩展与外部定义接合](../../20-语义与组合/组合/语义扩展-声明投影与系统编译.md#extension-closure-contract)的同一闭包。只实例化本次需要的边：

- 身份、版本、解释和未知保全；
- 类型、合法性、效果、资源、生命周期与 Requirement；
- 实现方法、Binding、失败和确定性依赖；
- 目标 lowering、ABI/布局、依赖和 Artifact；
- 若有现实作用，则接回 Grant、Operation、Attempt、资源和恢复；
- 若有保证，则接回 Claim、Method、Coverage 和 Evidence；
- 升级、共存、迁移、消费者归零和退役。

扩展不得建立自己的第二套身份、配置优先级、权限根、Evidence verdict、全局 current pointer 或独立事务系统。只有现有 owner 无法表达的语义才新增；能由已有 owner 承担的部分必须回接原合同。

<a id="core-promotion-rule"></a>
### 从作者语义扩展提升到公共语义与 Core Kernel 的严格条件

一个新区别先判断是否只需作者库，其次判断是否值得成为 Standard Semantic Module；只有还需要所有相关系统边界共同理解的系统级不变量，才考虑进入 Core Kernel。以下条件是公共晋级的共同门槛：

1. **存在真实区别见证。** 不支持它会让编译、运行、恢复或保证产生可证明不同的错误，而不是仅让领域 API 不够好看。
2. **普通用户定义无法封装。** 仅增加 Definition、库、Profile、Method 或 Provider adapter 仍无法保持该区别。
3. **需要跨边界共同理解。** 至少两个独立平台 consumer（如 compiler + runtime、compiler + assurance、editor + compiler）必须用同一含义处理它，而不是一个领域库内部即可完成。
4. **具有跨领域复用。** 至少出现于两个不以同一行业命名、因果机制真正同构的用途，或虽只出现一个领域但属于目标语言/执行模型本身不可回避的基础语义。
5. **能给出稳定合同。** 身份、输入、输出、失败、组合、演进和退出边界可定义；不是尚未理解的问题集合。
6. **不会迫使无关任务付费。** 未使用该机制的工程不加载其运行时、Provider、数据或配置，也不增加必填作者字段。
7. **没有更窄方案。** 成熟标准、外部库、adapter、target-specific lowering 或 Assurance method 不能以更小 Core 成本解决。

满足条件后也只提升**最小跨业务语义差异**，不把整个行业对象树一起提升。例如多个领域都需要“事件时间与水位”时可以成为共同语义，但不会因此把“流媒体”“交易”“传感器”变成 Core 枚举。
公共晋级再分两级：

- **Standard Semantic Module**：多个无关用途都需要同一可观察语义，且 compiler/target/assurance 中至少一个公共消费者必须理解；但未使用它的系统无需该含义，模块可按需装配和演进。例如状态图、事件时间、关系查询、AD 等属于这一类候选。
- **Core Kernel**：没有它就无法安全解释模块身份、要求、绑定、现实作用、Evidence、恢复或演进等系统级关系；该区别不是某种计算/应用功能，而是所有扩展必须遵守的治理或编译不变量。

因此“两个行业都需要”最多证明可以抽公共语义，不能直接证明应进 Kernel；“一个完整应用组合很常见”也最多证明值得做作者库。

### 禁止的核心污染

以下设计默认拒绝，除非有上述提升证据：

- `GameKind`、`MedicalWorkflow`、`FinanceMode`、`SimulationEngine` 等行业总枚举；
- 预置一个“万能业务对象”并用自由 JSON 承载全部未解释语义；
- 每个行业都增加新的 compiler stage、数据库、服务或 Runtime；
- 将某个成熟框架/引擎的数据模型当成 Gift Canonical IR；
- 因为某场景需要队列/事务/GPU/求解器，就让所有工程默认携带它；
- 把示例 Profile 当全局默认配置或支持声明；
- 把领域规则写进 Provider adapter，使作者无法看到、覆盖或迁移；
- 让 coverage 文档、测试 fixture 或研究资料成为生产 resolver 的隐式输入；
- 用“支持该行业”替代逐能力、逐目标、逐 Evidence 的真实范围。

### 一个新领域进入系统时的最小工程算法

```text
Input:
  authored domain definitions / requirements / assets
  selected or discoverable implementation sources
  target(s)
  requested claims / allowed real-world effects

1. Canonicalize only the identities and semantics that are actually declared.
2. Resolve names/types/relations/effects with existing semantic owners.
3. Determine missing capabilities and produce Needs, not invented defaults.
4. Discover finite implementation candidates from allowed sources.
5. Qualify candidates against hard requirements and target constraints.
6. Freeze exact Binding(s) and their provenance.
7. Lower/generate the complete target closure.
8. If execution is requested, admit each real effect through Operation/Attempt.
9. Collect observations/evidence only for the requested Claim scope.
10. Publish result + unresolved obligations + exact provenance.
```

若第2—3步发现现有语义无法区分一个真实必要行为，停止自动补全并进入 distinction witness；若第4步没有实现，保留 RequiredUnbound；若第6步后 Provider/target/environment 改变，重新判断受影响 Binding；若第8步作用结果未知，进入原恢复协议。没有一步需要“先选择行业模板”。

## 演进、支持、研究与组织

### 领域版本与迁移

业务定义、领域库、Provider 和目标可以独立演进。迁移关系必须精确说明：

- 哪些作者语义改变，哪些只是实现替换；
- 旧数据/状态/制品能否读取；
- 新旧运行实例能否共存；
- 升级是否需要一次性转换、双读/双写、停机或兼容 adapter；
- 哪些 Evidence 仍可复用，哪些因前提改变失效；
- 旧 Provider/版本何时消费者归零并可退役。

行业名相同不证明兼容；版本号相近也不证明语义等价。迁移继续由[兼容迁移与退役](兼容迁移/README.md)拥有。

### 领域能力的支持声明

“Gift 能组织实现某类业务”只表示公共机制原则上允许作者定义和组合，不等于正式发行已提供该领域的完整实现。支持声明至少区分：

- 可保全未知内容；
- 可解析/读取某类定义；
- 可静态检查；
- 有合格实现解析；
- 有目标 lowering 与完整 Artifact；
- 可运行/部署；
- 已取得特定 Claim 的 Evidence；
- 可迁移、治理和恢复。

某领域压力材料很详细，也不能越级宣称实现。真实范围由[覆盖成熟度与验收范围](../../60-保证与证据/保证/覆盖成熟度与验收范围.md)和实际发行 Evidence 决定。

<a id="跨领域机制场景与实例化合同"></a>
### 研究输入、区别见证与 Assurance 接合

领域/产品研究只承担**发现候选区别、失败机制和组合接缝**的作用；它不是测试套件，也不定义产品默认业务、支持范围或 Assurance 资格。只有把研究观察提炼为绑定公共合同、具有明确主体/前提/可观察结果的区别见证后，才进入 Assurance。

这条路径严格分成三个角色：

- 领域研究与组合研究：非权威研究输入，用来扩大问题空间、发现反例和高耦合接缝；
- [跨域区别见证](../../60-保证与证据/验收/跨域区别见证.md)：只保存已从研究中提炼出的、会改变合法性/编译/运行/恢复/Evidence 结论的公共区别；
- [全域接合检查](../../60-保证与证据/验收/全域接合检查.md)：把实际需要验证的区别映射到可观察合同和 ProofObligation，不把研究目录本身当覆盖率。

使用研究材料时执行：

1. 只提取具有独立机制价值的观察、失败或反例，不把行业名字转成 Core type；
2. 映射到现有 owner，检查是否已经能够准确表达；
3. 若完全可表达，只新增/使用作者 Definition、库、SemanticModule、Method、Provider、Target 或 Claim；
4. 若现有表达会把真实不同结果混成同一结果，形成 distinction witness；
5. 按[核心提升条件](#core-promotion-rule)判断留在作者/语义扩展层，还是确实需要 Kernel 修订；
6. 只有对实际发行/声明范围有要求时，才实例化相交的 ProofObligation 并取得 Evidence。

研究材料**不以行业数量、案例数量或枚举穷尽为完整性指标**。只有出现新的独立机制、区别见证、反例或边界时才值得新增；仅更换行业名、品牌、数据值、路径或规模而不改变机制的材料不增加设计覆盖。删除某份研究样本也不能删除已由独立规范拥有的公共机制或已被正式化的区别见证。

### 对信息架构的约束

为了不让领域研究反向污染产品设计：

- `docs/20-*` 只拥有跨领域/计算语义及扩展协议；领域行业压力材料不再放在那里取得规范 authority；
- 完整领域/产品组合研究与有独立价值的未采用方案在同包[依据区](../../../research/README.md)保留；旧会话过程不混入规范；它们可以扩展问题空间，但不取得产品能力、验证通过记录或任何 current authority；被采用的独立区别必须回写到准确 canonical owner；
- `docs/70-*` 只拥有扩展、迁移、实施准入和演进规则，不再重复维护各行业业务正文；
- 资料来源仍在 `docs/90-*`，只能支持对应命题；
- frozen 包外历史证据 保持历史字节，不因旧路径曾把领域材料放在 Core 附近而取得现行 authority。

任何未来领域文档若开始定义默认产品 API、runtime service、核心枚举或发行支持，必须先经过 Core promotion 判定；否则只允许作为作者库/Provider 设计，研究材料则在同包依据区保留其原有角色与相交规范指向。只有从研究中提炼出的、绑定具体公共合同的区别见证才可进入 Assurance，且仍不获得业务 authority。

### 重新检查条件

只有出现以下情况才重开本合同：

- 一个真实需求无法由普通 Definition/Requirement/Method/Provider/Target 组合表达；
- 新区别必须被多个 Core consumer 同时理解；
- 领域扩展反复建立平行的权限、Evidence、配置或事务系统；
- 某个 coverage 场景揭示现有 Core 会生成错误行为而不是仅缺实现；
- 现有扩展机制使未使用领域也承担显著运行/作者成本；
- 支持声明无法再精确区分“可组织实现”与“发行已实现”。

其余新增行业、业务和算法，默认走作者工程与生态扩展，不修改 Core。

## 新领域能力的晋级门与逆向退出

新增一个行业名或发现新业务事实都不构成自动修改 Gift Core 的理由。变更提案最少给出 `DomainDifference{owner,observableDifference,sourceOfTruth,inputs,stateTransitions,effects,failures,assuranceMethod}`，并用已有 Definition/Library/SemanticModule/Provider/Target 实际组合一次。按以下顺序得出**有证据的**设计结论：

1. 纯业务规则、资产、参数或案例可由现有作者定义表达：留在业务库及作者源，Core 零变更；必须保持业务知识主体、访问控制、版本、现实责任，不假装 Gift 拥有医学、法律或金融真理。
2. 特定目标/设备/供应商缺能力：只新增一个条件 Target/Provider/Method Profile，并给出失败替代与消费者资格；不把目标特例侵入通用中立类型。
3. 真正跨领域都需要、但既有中立语义不能保持的可观察区别：提出最小 SemanticModule；证明原有语义无法经合法组合保持的反例，再检查编译、执行、恢复、证据及迁移的实际影响。
4. 新要求改变身份/写权/权限/作用/证据等所有模块共享的不变量：须重新审查 Kernel 接口，给出至少一个原有正确实例的回归保持和一个新反例的排除证据。若同样效果能由受管扩展实现，则优先保留扩展。

医疗决策的法律责任、设备失电联锁、现实资金不可逆、仿真时钟耦合、空间坐标基准迁移与材料疲劳各自具有不同的证据和故障主体：不得把它们统一成一个 `riskLevel`。当条件能力不再被任何当前 accepted consumer 使用时，停止新绑定，并依旧运行实例/保存数据的生存期退役；只能在完成迁移/解除外部义务后移除，实现不能仅凭包卸载清理现实债务。研究仍保留证据线索，但不升格当前正式支持范围。

<a id="universal-core-extension-counterfactual"></a>
## 新增领域时零Core改动的反事实与必要升级证明

一种此前没有遇到的业务要求若可以由已选通用类型/计算/状态/协议/端口/资源/条件/Requirement加作者库表达，就必须**不修改Core**地完成其设计表达；不因为现有Target尚无Provider就把实施缺口误判为语义缺口。若所谓“通用表达”实际上只把全部行为保存成 `opaqueScript`，导致无法局部分析接口/权限/资源/变化，则记录作者抽象及语义覆盖缺口；优先通过显式接口、库/方言、原生适配和更好的作者投影解决，而不是将业务名固化到Kernel。

升级判断需要相交的反事实：给出两个输入/环境/目标状态，现有各组合在已要求相同的作者语义条件下产生**不同且不能合法抹除**的观察（如权限归属、Effect完成、资源寿命、语义身份或证据结论）；说明已尝试的用户定义/库/Target/Provider绕行为什么不能保持；给出需要扩大/修改的最小公共不变量、实际消费者、版本和迁移/反例。只有这条证明路径成立，才设计真正的Kernel合同修改。新增可选语义由 `SemanticModule`按精确发生位置与版本接入，旧消费者不理解的新必要语义不得自动降级为旧默认。

开发者体验也构成可检验性能/复杂度约束：能够表达不等于合理表达。若某领域每次小变更都要重写全仓、手工编造数千节点ID或完全重建不同Target的无关区域，应在增量、作者表面和架构组合处给出改善，而不是宣布计算普适性已解决用户问题。正常工程的局部修改成本与查询/索引代价需在实现后取得可比较的测量，不捏造统一理论上的固定性能阈值。

<a id="domain-novelty-composition-check"></a>
## 新业务名称与真正规模限制：何时需要扩展Core

同一`DataShape/Compute`通用类型/效果/降低机制已用于互不相关的计算项目，且这些新Definition无需业务名称分派、行业Runtime或新内核方法：这为“**语义可组合时新业务应零Core改动**”提供有限运行见证；`BindCallable`的已有实现链接和`decide`的有限表格综合是两个不同覆盖来源。新增跨领域基本可观察区别，例如此前没有表示的异步取消、时间事件窗、随机联合分布、持久事务或不可撤销资金操作时，不允许硬塞为纯Compute；应先从现有Requirement/Effect/Method/Provider组合与真实证明寻找可行绑定，仍不足时才按最小公共差异提升新SemanticModule。

作者输入极简不等于任意软件意图信息已充分。若若干不同算法均与同一自然语句兼容且运行结果不同，Gift应指出缺少的目标、约束、观察和选择权；不允许对一种实现主观宣称“最专业、全局最优”。真正的实现优化必须保留错误顺序、数据域、资源与副作用，并在目标场景提供可比较的性能和维护证据。

## 语义家族表不能演变为新增业务的 Core 门槛

[全域接合合同](../../20-语义与组合/共同语义/工程通用语义全域与闭合合同.md)列出的家族是动态的区别发现/责任导航；各家族新实例按现有 Definition/Module 扩展。**没有出现在覆盖样本里不是产品拒绝理由**。只有缺乏实际可解释机制，或现有公共语义无法表达必要观察区别且明确存在多个独立消费者，才按本页核心晋级合同处理。
