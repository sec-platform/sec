# 开放语义模块、跨域解释、方法资格与受管目标发射接口

> **规范归属**：本页维护工程中“开放 SemanticModule → 实现资格 → Target Lowering → Source ownership”的**消费和接合接口**。各具体领域的语义真值、时序、授权、效果和保证仍由原领域 owner 维护，不在此集中重写 45 个家族。这里不建立封闭的万能 `kind` 枚举、不要求作者同时保存两份意图、不把模拟计划升级为现实权限。[有限实验说明](../../../fixtures/semantic-universe/Gift104/README.md)保留原有接合场景；原Gift103解释器和Gift98发布者不随本设计包提供。实验协议不得冒充当前生产Schema。

## 1. 与终极目的有关的工程判定

开发者在有权 `SourceRegion` 中表达已接受目标、自己能够决定的领域意义、硬约束与必要差异。Gift 必须先解析锁定 Meaning、列出无法解释的前提，再通过联合资格选择 Method 并生成与规范一致、可持续修改的目标源码。安全、法律、授权、资源、时间及结算分别保留对应 Owner；函数生成只是合格方法的一种实现形式。

**开放扩展资格**：新业务组合与已有 Meaning 在兼容 Profile 内不要求改 Kernel。新观测规律、外部效果或专有协议通过有类型的 SemanticModule、MethodSupply 或 Target Adapter 提供；缺解释器、实现或证据时返回对应 Needs，并阻止签发完整目标制品。开放表示可扩展性，不承诺零供给条件下自动创造真实能力。

**生产目标接受标准**：在选定作者根、环境、目标、方法和质量要求的闭合读集下，任何已采用的源码成员必须可追到来源语义、实际解释资格、目标工具链、方法资格与相应行为保证。文档齐全、测试退出零、生成源文件和真实生产部署是不同主张，互不代签。

## 2. 真实作者接口：一份 source、不同语义角色

当前候选`gift.author-module/2`管理新业务的唯一 `definitions` 与导出集；旧`/1`在本节Gift104历史范本仍保留原字节；每个 `Definition` 可关联 `cd:flow`、`guard:deadline`、`guard:capacity` 等不同、已锁定的解释器。SourceProfile、AuthorRegion、ReadSet 与写权由现有作者源合同确定。作者不需要并行维护 `.gift`、`.intent`、TypeScript 等同义真源；JSON 只是当前结构表示，不替代所选语义体合同。

被消费的 Definition 必须解析为 `(moduleId, definitionId, semanticProfile, revision, sourceSpan)` 并验证相交导入锁。`kind` 仅是锁定 Profile 下的分派键：同名 Kind 在其他 Profile 中不自动等价；缺解释器或影响行为的未知字段不得忽略。显示名与布局变更仅在获得语义保持的 canonicalization 资格后可独立调整。

[维护操作研究说明](../../../fixtures/semantic-universe/Gift104/README.md)保留一个非生产设计场景：同一业务根交叉使用 **状态转换、策略许可、观察、外部效果意图、时间窗口、容量预算** 的完整作者结构。与其相配的 `request/simulator/guard-witness` 属于各自的调用输入/测试输入，不是第二份权威作者源。

## 3. SemanticModule 接口与执行责任

概念性 Rust/TS 边界（设计签名，**不是本轮 production 实现**）：

```text
register_semantic_module(ModuleIdentity, ContentDigest, CapabilityDescriptor, QualifiedConsumer) -> Registration | Conflict
resolve_definition(SourceSnapshot, DefinitionRef, SemanticProfileLock) -> InterpretedDefinition | Need | Refused
interpret(InterpretedDefinition, ExplicitContext, FixedReadSet) -> SemanticMeaning | Unknown | Conflict
join(ReadOnlySemanticContracts[], RequestedRelation, Assumptions) -> JointObligation | MissingJoinRule | Inconsistent
check(RequirementInstance, ObservableDomain, DeclaredBudget) -> Proven | Counterexample | Unknown | Inapplicable
qualify(RequirementClosure, TargetProfile, MethodCatalog, EnvironmentEvidence) -> EligibleCandidate[] | NoEligibleMethod
lower(SelectedCandidate, ExactSemanticGraph, ExactToolchain) -> CandidateArtifactSet | NeedsTarget | Refused
```

- **注册方**提供精确语言 Profile、可解释的值域/类型、读取依据、解释函数与错误集合、可观察区别、影响的关系/效果、资源上限及版本/兼容关系。注册代码本身是**可执行的受信供应**，不得从未知作者 JSON 中动态加载任意 Python/Rust/JS 代码。
- **Kernel** 负责身份、SourceSnapshot、Profile 匹配、导入闭包、读集、模块依赖、冲突记录、诊断及结果类型；它不能为每个行业写一个业务分派，也不能因插件存在就推断其正确性。
- **Joiner** 处理跨域依赖，必须保留模态和观察域：例如许可规则的 `PERMIT` 与执行时的 `Grant` 是不同类型，模拟时钟窗口满足与当前真实时刻窗口满足也是不同事实。
- **Method Provider** 给出精确的支持语义、前提、资源与错误保持保证、Target/ABI/语言环境及源码生成方式；是否合格由实际消费者和相交证据检查，不由供应文件自称。
- **Target Adapter** 只降低经选择的可消费语义与方法，产生确切源成员、原生类型、ABI/运行依赖、`SourceMap`、工具链束缚和未兑现的义务；不授权现实操作。
- **Assurance** 保留 Claim、证据取得方法、可观察覆盖范围、环境、时间及独立性，不把 Method 的自我声明升级为独立保证。

同一 SemanticModule 可以只提供结构解释或规范判断，完全没有 Target 下沉方法。例如某个新的合规义务可被检查或显示，但缺少合格自动执行方法时应保留设计和失败诊断，不能生成承诺满足该义务的代码。

### 3.1 局部结果，不强迫万能布尔返回值

结果类型按因果职责隔离：事实接口的 `支持 / 否定 / 未知 / 证据冲突 / 不适用` 中，前四种来自支持/反证证据对，`不适用` 则由作用域判定；规范接口的 `允许 / 禁止 / 缺适用规则` 对应规则的有效性；实现资格的 `合格候选 / 附带未履行义务 / 不合格 / 无法判定` 对应方法证据；外部作用的 `未尝试 / 已尝试待结算 / 确认成功 / 确认无作用 / 部分作用 / 完成未知` 对应真实结算。跨域消费必须逐项验证映射前提，不把这些结果统合为宿主 `true/false`。

样本使用 `ModelError.code` 及明确的 `NEEDS_*`/`CONFLICTING_*` 状态，输出总是带 `realWorldAuthorization=NOT_ESTABLISHED`、`externalEffects=NOT_EXECUTED`、`externalSettlement=UNKNOWN`。它没有生产授权或真实读回机制。

### 3.2 受限研究机制与不可继承的实现资格

Gift104 历史实现曾采用以下接口（源码不在本包，当前实施须重新取得证据）： `Registry.register(SemanticModule)`、`compile_author(...)`、`evaluate_bound(...)`；`guard:deadline`、`guard:capacity` 的 body 校验和纯解释来自可注册供应；其他已注册 Dialect 的精确别名/版本也可直接绑定到同一个有界前置条件端口。原有 Gift103 解释器作为固定 `cd` 基础使用，扩展通过**临时视图**提交给原接口；没有产生第二份持久作者源。改变未引用的守卫定义不改变该导出根的语义摘要；改变已引用截止时刻/容量必定改变摘要。

这里的 Registry 仍运行在可信本地 Python 进程内，**不是不可信代码插件沙箱**；新模块必须由受信 owner 提供、取得可信字节和执行边界。该历史记录只覆盖额外两种内置供应的语义可用，及另一外部命名空间的语义注册可通过解释但在缺 Target 实现时被拒绝；尚未实现任意新语义角色的自动跨域合成、正式跨进程 SemanticModule ABI、导入解析、真正的第三方签名/沙箱或 45 个领域的消费端。

## 4. 跨域条件、证据与失效契约

示例的守卫约束是**实质可观察的条件**，不是对状态图增加装饰标签：

| 所需语义 | Definition 直接值 | 现实观察输入（样本仅模拟） | 不成立时结果 |
|---|---|---|---|
| 截止窗口 | `guard:deadline {source, notAfter: UTC}` | 当前时刻与精确 source、aggregate、operation 的绑定 | 缺观测 `NEEDS_GUARD_WITNESS`；晚于期限 `GUARD_UNSATISFIED` |
| 容量预算 | `guard:capacity {source, unit, atLeast: uint64}` | 同单位、同 aggregate+operation 的容量读数 | 缺读数、单位不符、额度不足分别保留诊断 |
| 观察已确认 | 原有 `cd:observation {issuer,claim}` | 明确 issuer/claim/operation 的模拟 attestation | 缺失/否定/冲突分开，不采纳未授权 `untrustedClaims` |
| 策略许可 | `cd:policy` 的 permits/denies | principal roles + 另一个实时 Grant 所需位置 | 规则允许但无当前 Grant => `NEEDS_GRANT` |
| 外部效果 | `cd:effect` 的 kind/settlement/scope | 需要真实 Method、Grant、持久操作与读回 | 当前只能输出带 `NOT_EXECUTED` 的意图 |

有限受测模拟快照的负查询语义仅限显式读取的 `readings`，并非真实世界“没有该资源/没有截止”的证据；不同来源、作用域或操作的读数不能拼接。相互矛盾的同一来源读数必须拒绝，不能把后一个当成真。观察时钟是示例可比较的规范 UTC 秒级表示；真实物理控制要进一步证明时钟可信、容忍漂移、截止点时效、读取-提交之间的竞争、实时调度和设备互锁。容量是快照数量，不是已取得资源租约；**模拟有两个空位不保证真实并发预留成功**。

## 5. 实现资格：方法声明、实际支持、选择和失败

在 G104 受控样本中：

1. `methods.json` 是本地 Method 描述符，声明支持的语义能力、TypeScript ES2022 目标、`PURE_PLAN_ONLY` 等级、最多 64 转换/每分支最多 8 守卫以及实际代码形态 `static-if` 或 `static-table`；不是自签独立证书。
2. `target-implementation.json` 锁定被目标供应实际实现的 capability、**准确 `kind → targetConsumer` 对应表**、允许代码形态，以及**原始语义解释器 `engine.py`、基础跨域解释器 `cross_domain.py`、`emit.py` 和 TS 原生运行库**的内容 SHA-256。仅声称支持 `ts.guard.capacity/1`，但实际使用未知 `quota:fake-capacity` kind 的候选必须拒绝，不能借已有消费者名称绕过资格。**供应声明超出实际登记**、解释器或目标实现与摘要不一致即禁止选择。改变相交解释/生成实现时必须刷新登记和相关测试结果，不能沿用旧资格。本地锁不替代生产来源签名或独立语义证明。
3. `qualify()` 对每个候选记录 `eligible/reasons`。`pin` 指向不存在或不合格候选时明确 `NO_ELIGIBLE_METHOD`，不得悄悄选其他方法；未知 Target 不能从名称推断。
4. 当前 `auto` 对 1—2 条转换选择静态分支、较多转换选择表驱动。这**仅是确定性代码形状启发**，并未取得任何运行性能最优证据。生产质量策略必须先按硬约束和证据筛选，再在合格候选中按**有真实口径的**性能、资源、体积、可读性等偏好比较。并非每个指标都有可比较排序，缺证据时保留未知，不应伪造得分。
5. 同一模型的两种方法保留共同 `semanticRevision`，目标 `index.ts` 不同，原生共享库不变，生成清单记录每项供给摘要、准确的 `qualifiedSemanticKinds`、目标限定和候选筛选。digest 检查解决的是**本地文件一致性**，不解决供应链来源真实性、软件安全或方法跨目标行为等价的独立证明。

正式 `MethodBinding` 至少必须有：`semanticRef/revision、assumptions、observableGuarantee、limitations、targetProfile/ABI、methodRef/revision、supplyDigest、readSet、resourceEstimateBasis、evidenceScope、residualObligations、fallbackPolicy`。被采用方法是否对当前环境有资格，由它的实际 consumer 拥有最终 Gate，而不是 registry 模板。

## 6. 目标源代码与受管修改

该受限目标设计应包含 `src/index.ts`（已编译的领域分支/方法）、`src/plan-runtime.ts`（状态/策略/证据/版本语义）、`src/guard-runtime.ts`（时间/容量的示例解释）及明确的 `package.json`、`tsconfig.json`。无运行时解析原作者 JSON 的隐式解释器；目标实现须由准确版本的TypeScript工具链独立构建，不能由设计文稿预先签发成功。`gift-artifact.manifest.json` 锁定成员字节/方法供给/来源字节/语义修订，不能被视为已部署系统或完整正式 ArtifactSet。

**首次写入**：候选全部字节在目标目录外准备，拒绝已存在的目标目录，然后改名发布；不能把原有用户文件解释为新生成的可覆盖资产。

**第二次写入**：消费[受管来源与再次生成的现行合同](../../40-目标与制品/表示/编辑与受管回源.md)，保持tracked member前像、未受管路径冲突、符号链接、写入日志及中断恢复义务。人工改过目标文件时拒绝覆盖；完全无变化时不反复备份/重写；换方法只更改受影响源码和方法元数据。不使用 CI 作为猜测代码是否有错的内环。

**限制**：这是单写者、可信本地目录下的有限 `rename`/备份日志机制。首次写入时外部并发写者竞态、磁盘断电持久性、跨进程联合事务、网络文件系统、生产 ACL、真实完整源映射、增量构建 DAG、源代码中的人工编辑回写都没有由此得到保证。受管发布者与其接入消费者仍有各自的实现和独立验证责任，不可标为生产事务通用解。

## 8. 成本、边界与失败闭包

- 输入错误：重复 JSON key、非标准 `NaN/Infinity`、非法原生对象、非规范 uint64/日期、非声明 Definition、未知方言、错误引用或超界列表必须拒绝。单次样本最大 JSON 输入 256 KiB、有限定义与转换数；这些是局部防护，不代表一般大项目限制。
- 作者修订/语义修订/方法供给摘要/目标源码摘要**分层存在**；显示改名不应触发业务语义变更，能力合约或目标实现变更不能沿用旧保障。
- 宿主恶意 Proxy、getter、有意篡改 Node 环境、无权限/无环境的真实外部操作，不属于这一有限进程的安全沙箱或实时保证。
- 真正可达的完成条件：在准确可判定的子域，给出正确源码、定位错误、可维护更新与有限范围的证据；在供应/授权/实现缺口处交付可机器消费的 `Need`/Refused，保留原作者 Meaning。未知不是以 `false` 代填。
- 未来 production 迁移必须建立 Rust Kernel 的模块加载、不可变包/锁、typed judge/proof 引用、原生目标 source-map、Method/Target 适用性、可持久 CAS/外部结算、代码安全和独立保证；本地 fixture 中的任何绿色测试都不能关掉这些项。

## 受限真实效果 Method 的跨层接合（本地实验）

旧 Gift104 受限研究样本曾追加**与 TS 纯计划 Target 分离**的 local SQLite Method，见 [真实实现及测试](../../../fixtures/semantic-universe/Gift104/README.md)。该历史样本作者当时只维护单份 `gift.author-module/1`；现行新作者统一使用候选 `/2`，`cd:flow`、`cd:policy`、`cd:effect` 与 `guard:capacity`/`guard:deadline` 共用上述编译结果。两种纯 TS 方法生成的只是只读候选计划；本地 effect Method **不能凭纯计划已成功就获授权**，而必须从现实调用者单独接收有签名的限定 Grant，从自己的单库受检存储中读取状态和容量，再原子写入效果回执。

实际支持的 Method 是 `gift.fixture-local-sqlite-method/1`，准确效果 `reserveOneCapacityLocally`；它依赖 `guard:capacity` 唯一资源、可选 `guard:deadline`（其时钟源仅限定为 `fixture-utc-clock`），明确拒绝未知 guard、未知 effect 或没有真实解释/签名的 `cd:observation`。本地资格锁 `local-target-implementation.json` 绑定实现代码 `local_effect.py`、当前语义引擎 `engine.py` 及基础解释器 `cross_domain.py` 的 SHA-256；变更字节而没有更新资格锁时禁止执行。这仅证明本地候选与已登记字节一致，**不构成第三方安全资格或目标环境广义适用证明**。

**开发者与宿主接口（已实现样本）**：`compile_author(author) -> Bound`；由本地可信操作者 `bootstrap(database, bound, aggregate, state, capacity)` 建立初始单库状态；宿主使用 `execute(database, bound, request, grantEnvelope, trustKey) -> LocalEffectResult | Refused`，无作用读回使用 `readback(...)`。输入 `request.actualState` 是待验证的客户端前像，实际 CAS 以事务内数据库读取为准；提交发生之前 plan 的 `externalEffects` 继续为 `NOT_EXECUTED`，提交后的回执只承诺本地 SQLite 的状态和容量改变。没有真实支付、设备指令、网络通信、独立 Grant 发行者或产品 Rust Kernel。

**两个行业无专用事务分派的纵向见证**：设备维护与课程报名都只通过不同作者定义、状态/策略/资源单位复用同一个 Method；独立验证器为每个工程分别生成 static/table TS 源码、运行 Node 和 Python 差异比较，随后在测试发行者签名下执行本地 SQLite 提交与回执读回。这验证了**已知 Effect 的开放业务组合**，没有证明新 Effect 定律可以不提供 Method 就自动执行，更不证明生成 TS 的过程自身已持有授权。

## 开放意图 Definition 与真实 Method 的资格接合（通用设计）

这里规定 **SemanticModule 的接入条件**，不是新增一个大而全的 module implementation class；先前的 `Gift104/Gift105` 是已跑通的限定实例，绝不能据此宣称任意用户定义或目标已受支持。新业务作者采用唯一候选 `gift.author-module/2` 逻辑模块外壳（本篇早期Gift104/105仍为原`/1`历史见证），选用已明确解释的 dialect、`DefinitionRef`、唯一 SourceSnapshot/Binding 和现有 `MethodSpec`，并维持一条 authority 链。一个业务新功能常常只增加普通定义，**无需**新 SemanticModule；新的不可由现有逻辑组合出的原始观察/世界效果才有对应扩展义务。

### 对扩展模块必须要求的五种信息

1. **所解释的语义**：稳定 `languageId`、compatible revision、精确内容摘要、类型/操作/Rule 的公开 identity、参数和所在的词法/行为域；导入、重导出、实例化和标准库必须沿锁解析，不依赖字符串后缀猜 `kind`。
2. **形式语义与保证边界**：每个公开操作的定义域、输出/异常、前后/帧、终止/活性条件、效果及可观察投影；是否有可执行解释/断言检查、是否只有公理或实验模型要分别声明，不能一概标注 `verified`。
3. **组合规则**：合取、调用、参数实例化、状态/事件联接与效果次序怎样保留，开放类型/跨模块别名怎样计算，哪些规则在共享资源、非纯效果、不同时间基线下失效；不能仅因为输入/输出 Type 一致就声称可组合。
4. **候选方法及资格**：匹配前提/目标/环境/负载/数据域、输入与结果 ABI、目标代码生成者、运行 Provider、证据身份、预算、失败可恢复性；资格约束随实际 Method digest 和 Target version 固定。
5. **撤销及变更**：`Definition revision`、`Method implementation digest`、`Target profile`、`Environment evidence` 与 `Grant` 不互相冒用。发生修订时失效相交 Binding、Proof、目标产物和目标效果授权；无关的作者展示改变不扩大重建范围。

`register_semantic_module` 的形式合同要求用已声明版本绑定封闭解析范围，返回可区分的三种结果：**解释可用**、**有类型但含义待取得**、**结构或定义非法**。其中受信模型执行属于资格和 authority 问题，而不是开发者声明新函数就可以向宿主登记代码执行权限。先前的函数名 `interpret/qualify/lower` 保留各自职责，不在这里重复建第二编译主线。

### 精确编译责任路径与永久缺口

```text
Author SourceSnapshot / concrete DefinitionRef
  -> strict decode + verified imports / profiles / revision pins
  -> source identity and typed bindings (no runtime effect)
  -> semantic interpretation + explicit needs + read set
  -> joined Requirement/Constraint obligations + non-vacuity
  -> candidate supplier: library | existing method | bounded synthesis | authorized author code
  -> hard-contract filter (types, public behavior, frame, effect, target, budgets)
  -> choice policy + chosen Method digest + outstanding proof/evidence
  -> target-specific lowering into real source AST and dependency/binding manifest
  -> build/compile/conformance + source map + frozen accept state
  -> separately authorized actual execution/readback/recovery (if requested)
```

该路径具有五类明确出口，且不新增一种全局数据库：`NeedsMeaning`（模型不知道行为含义）；`NeedsImplementation`（含义固定但无已合格算法/执行 Handler）；`NeedsTargetAdapter`（算法可用但不能保持该 Target 的观察/ABI/效果）；`NeedsEvidence`（实际负载/环境/证明缺项）；`NeedsAuthorization`（真实世界不可擅自调用）。另外保留 `Conflict` 与 `BudgetIncomplete`。工程可在这些出口之前准确地发布合法的设计草稿/源候选，不能把未完成的目标闭包伪造为编译成功。

### Rust/TS 与语言构建生态的关系

语言语义和作者源身份独立于 target；Rust Kernel 若是正式实现架构，应提供 source/semantics/identity/qualification 的确定性子层，TS/Rust Targets 只在自己已合格的类型、效果、依赖、并发与 ABI 范围内把编译图转为源码。通用意图系统不应自动重新实现成熟语言的优化器、类型检查器、链接器、包管理器和安全库；生成源码必须经过原生目标工具链，并将实际依赖和行为差异写回合格资格。

**开放扩展不是允许插件直接获取 Core 权限**：解析合同和实世界执行分域；只读静态解析可以接受未受信的结构数据，但自定义解释代码、动态库、外部工具或 effect method 的加载必须通过既有 application/execution 身份与资源隔离。来源不可信时不能因为模块提供了自己的「证明」便放宽审查；独立保证与可复现构建并非同一类证据。

### 连续修改例子

用户先定义新 `Graph.Path` Relation 和 `Reachability` 语义、后加「路径必须无重复节点」：只修改对应 Requirement；已有 BFS/DFS 候选若在同一观察范围下产生简单路径可继续绑定，否则重新验证并选择；目标源手写区保持原有作者归属。随后增加「遇到带负权边的最短路径」，原只支持非负权的 Dijkstra 不能凭相同 `Graph` Type 被重用，必须改选覆盖负权条件的方法、明确负环政策或报 `NeedsImplementation/NeedsMeaning`。该反例要求**负面适用前提可传播且确实影响 Method 资格**，而不是装饰性文档字段。

引入新远程执行效果时，声明 `sendCommand` 的协议含义可以先保存；没有对应 Provider、Grant、读回或失效恢复时，只能生成模拟或限定的待授权实现。不能因前一步已有一个 SQLite 单事务样本，就把新网络动作按同名 `effect` 执行。

<a id="prebootstrap-semantic-module-abi"></a>
## 开放语义供应的完整消费合同与隔离

### 接口不是只有 register 一个名字

沿原 ModuleIdentity、ContentDigest、CapabilityDescriptor 和 QualifiedConsumer，模块必须交付解释输入域、Type/Meaning 编码、规则版本、调用相位、可读取源范围、返回结果类别与资源预算。注册表仅确认这一供应可被定位；激活还需解释映像和执行策略准入。作者源提供的 `kind`、URI、签名字段不能直接变成动态库路径、可执行命令或宿主对象回调。

现有 `resolve_definition/interpret/join/check/qualify/lower` 继续作为责任边界。每次调用绑定精确 Image/SourceSnapshot/Profile 和请求 scope，返回本层结果、Diagnostics、ReadSet 与未履行义务。返回类型中没有一项 `verified:true` 可以覆盖其它字段；插件自报“已检查”仅是供应声明，真正消费者仍核验内容、范围和对应保证。声明支持一种语义但没有实际消费者的供应不可用于目标生成。

**内置和第三方采用同一公开语义合同。**内置 Rust 模块可经受信静态链接减少 IPC，但不能跳过相同输入/输出资格。第三方解释代码默认不在控制面进程执行；采用有预算的隔离进程或经明确批准的受限执行环境，输入仅暴露所需不可变值/内容引用。隔离方式缺失时可以读取结构资料，不自动激活代码。代码签名证明来源关系，不证明解释定律正确。

### 自定义语义能组合的实际条件

一个派生定义只需引用已有意义和真实计算体；不必升级 Kernel。一个新的原始操作必须提供明确的等式/转换或观察语义及无法归约部分，公开哪些性质可求值、哪些需证明、哪些依赖现实观察。对未定义的组合不自动采用“把结果都 AND 起来”；需要相交 Join 规则，或保留具备类型但未有组合证据的义务。

跨模块返回不得泄漏本地内存地址、可变对象别名或可执行闭包作为可移植 Meaning。长期引用指向内容与语义身份，短时句柄绑定 worker epoch/实例，隔离执行中的失败不制造有效缓存。插件注册的规则不能改变其它未采用 SourceProfile 的词法/意义；更新实际影响规则才使相交解释与资格失效，不全量重新授权所有项目。

### 加载、升级与退出

加载前核验供给字节、支持范围、宿主能力、资源和信任依据；协商通过后形成固定 EngineImage。新任务只能读同一映像，升级形成新映像，不在运行中原位替换函数表。旧请求、闭包和资源释放代码仍引用旧映像时，延后退休或按真实安全停用策略隔离；撤销执行资格不能被“还有缓存引用”无限延后。

解释异常、非法返回、超预算、协议破坏和确定语义冲突分开返回。插件崩溃不得导致 Kernel 把未解释区域当空；重启仅重新计算纯结果，不能重新派发外部作用。恶意供应提供循环依赖、超大类型或伪造证据时，范围与预算在跨边界前检查，而不在已分配巨大对象后再核验。

## 语义模块的版本、隔离与接合

模块安装登记只建立可发现供应，不激活执行。激活由项目选择精确解释映像、版本、许可/权限与预算。模块身份不仅是namespace URI，还包含其实际内容、所用公理/规则和ABI；两个方言同名前缀通过模块锁和词法别名隔离，不能后安装覆盖先安装含义。

`resolve_definition/interpret/join/check/qualify/lower`继续是已有职责接口；返回实际结果、准确ReadSet、诊断及未履行义务。join必须明确输入观察域之间的转换和侧条件，不能用“两个模块都支持Bool”推导其量化/时间意义兼容。不能验证的转换保留JoinNeed，禁止把结果扁平化到最弱类型。

trusted builtin可以静态链接而不用IPC，但不能跳过相同的类型、版本、契约和依赖核对。第三方代码在有界、无环境权限的隔离单元运行；宿主无法隔离时只读描述，不擅自运行它。URI不能直接加载路径/动态库；`verified:true`只是无权声明。进程崩溃、协议超大结果、预算用尽使相交查询失败，不抹掉旧可复核源。

升级新映像先在非current分支重解释受影响定义及join，生成兼容证据后原子切锁；旧任务继续用旧映像直到结束并保持披露权限核验。回退不能让新存储或新ABI被旧消费者盲读。模块撤销时区分数学证据仍成立与当前信任政策不再接受。

**验证与反例**：同URI不同摘要、规则变更、两个观察域假join、模块自报verified、插件崩溃/巨量结果、旧任务持有旧映像分别核对。

**实际能力边界**：真实模块隔离、ABI消费者和供应签发尚未部署。
