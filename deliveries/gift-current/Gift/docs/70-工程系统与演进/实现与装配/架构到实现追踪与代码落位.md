# 架构到实现追踪与代码落位

> **阅读范围**：本篇拥有“设计责任怎样落到真实代码、测试和 Evidence”的映射合同。它不是第二份架构规范、手填 CMDB，也不声称当前仓库已完全实现这些映射。

## 为什么需要映射，而不是再维护一套实现清单

Gift 的设计对象、实现模块、目标生成代码、测试和运行 Evidence 具有不同身份与生命周期。只写“设计已定”不能证明代码已按它实现；只看到某个类/文件存在也不能反推其承担正确的 canonical responsibility。

因此实现追踪采用**可重建投影**：canonical 设计仍留在原 owner；代码事实来自准确源码 revision；测试/Evidence来自其真实记录。映射把这些对象连起来，但不复制它们的内容，也不允许修改投影来改变设计或代码。

```text
canonical responsibility
  → public contract / invariant
  → mechanism owner
  → code owner module
  → crate / package / file / major symbol
  → direct consumers
  → verification obligations
  → tests / checks / Evidence
```

## 不再维护“六个成熟度维度”：设计、实现、采用和资格回各自真源

同一个 concern 不应同时维护“设计深度表、实现成熟度表、采用生命周期表、资格表”四套状态。当前统一为：

- **设计完整性**：由[ASMRVE](../../00-系统与原则/设计方法/设计综合与必要性.md#asmrve-design-closure)判断 A/S/M/R/V/E 哪一段仍有设计缺口；
- **实现存在**：由准确源码/Artifact revision 的现实 Statement/Observation 证明；
- **采用关系**：由 Configuration 选择和相应 Transition 表达；
- **符合性/生产资格**：由 V 中准确 Claim/Evidence 的 scope、environment、freshness、coverage 表达；
- **退役**：由 E 中 consumer、compatibility、recovery 与 retirement Transition 结算。

所以“文档设计闭合”“代码存在”“测试通过”“生产已验证”“当前已采用”始终可以分别成立或不成立，但不再复制成一个新的六格 maturity 对象。

## 映射投影的最小字段

实现工具可以形成类似下列只读投影；字段名称不是当前发布 Schema，责任含义是固定的：

```text
ArchitectureImplementationView {
  concernRef
  canonicalOwnerRefs[]
  invariantRefs[]
  mechanismRefs[]

  implementationRevision
  codeOwner
  packageOrCrateRefs[]
  fileRefs[]
  symbolRefs[]
  consumerRefs[]

  verificationObligationRefs[]
  testOrCheckRefs[]
  evidenceRefs[]

  designClosure {
    architecture
    semantics
    mechanism
    realization
    verification
    evolution
  }

  implementationFacts[]
  adoptionRefs[]
  qualificationClaimRefs[]
  gaps[]
}
```

`implementationRevision`必须是准确源基础，不能写“current/latest”。文件或符号移动只更新物理定位；canonical responsibility未变不要求改设计正文。反过来，代码新增第二 writer、第二 resolver 或改变错误/恢复语义，即使 API 名没变，也必须回到设计 owner 裁决。

## Gift 自身与生成产品复用同一个 Realization 映射

二者不是两种代码架构模型，而是同一个 `SystemSubject → realization → source/build/artifact/runtime/evidence` 模式的不同根。映射器应参数化 subject/configuration，而不是维护 `SecImplementationView` 和 `GeneratedProductView` 两套结构。

```text
SystemSubject + exact configuration
  → accepted semantics / requirements
  → realization plan / bindings
  → source/modules + dependencies/config/assets
  → build/package
  → deployment/runtime（若该形态需要）
  → conformance/evidence
```

`Subject=Gift compiler system`时，具体实现包含 compiler-kernel、control plane、adapter/execution 等Gift职责；`Subject=generated product P`时，具体实现是该业务产品的源码、依赖、构建与运行。自举时Gift可同时作为producer和某个target subject，但identity/configuration仍分开。

必须分别取得Evidence，不是因为架构模型不同，而是因为**subject、claim、revision、configuration和环境不同**：编译器测试通过不能代签某个生成产品；一个产品通过也不能证明编译器对其他输入正确。成熟 crate/npm package/系统 Provider只需记录精确Binding、公开合同、边界适配和本地剩余验证责任，不复制其内部源码。

## 从设计到物理代码的落位算法

**PLACE0 固定 concern。** 取得一个准确 canonical responsibility 及其正常/失败/恢复合同；没有完整 owner 不进入物理落位。

**PLACE1 找最小生产 owner。** 优先复用当前模块；只有出现独立状态、生命周期、权限、并发域、可替换边界或测试责任，才增加新 module/crate/package。不能因文档有一章就机械建一个包。

**PLACE2 定义边界。** 写清输入输出、谁拥有 port、错误、取消、资源、线程/进程边界及可见类型。内部函数拆分不升级为公共 contract。

**PLACE3 放置数据所有权。** 可变的正式状态必须能找到唯一提交/冲突协议及其真正实现 owner；多生产者只能经该协议或已验证的交换合并产生正式版本，不能让进程私有副本各称 current。不可变 snapshot、derived cache、Evidence、runtime handle 分别按原 owner 放置。禁止用一个 GlobalContext/Manager 收容无法解释的跨域状态。

**PLACE4 放置执行路径。** 指定调用入口、实际消费者、并行/异步边界和 effect owner。检查函数不得为了方便偷偷写工作区；生成器不得直接部署目标。

**PLACE5 绑定验证。** 从 canonical invariant 产生相交验证义务；测试按最小真实接口验证，不为了目录对称给每个文件造测试。

**PLACE6 回读。** 对准确源 revision 检查是否出现第二 owner、旁路调用、未声明状态和不一致错误协议；若存在，修实现或重开设计，而不是让文档追着坏代码改。

## 上层设计必须知道哪些实现级事实

上层设计需要消费**会改变合同**的实现事实，例如：

- 目标生态 resolver 的真实版本/feature/lock语义；
- OS/文件系统是否支持所要求的原子性、大小写或隔离；
- Rust/TS/Java 等目标在所有权、异常、ABI、异步、布局上的可保持范围；
- 外部 Provider 的幂等、取消、readback、费用和未知结果能力；
- 真实依赖会不会执行 build script / proc macro / installer；
- 性能、内存、并发和恢复成本是否破坏既定质量目标。

但以下通常只属于实现自由：私有容器、局部函数名、等价循环写法、不会改变外部语义的内部拆分。它们不得反向成为公共 Requirement。

判据是：**若事实改变可观察行为、正确性、确定性、权限、资源寿命、恢复、兼容、可复现性或已承诺成本边界，就反馈上层；否则保持实现自由。**

## 代码组织“好不好”的可反证条件

代码架构不是因为目录漂亮而合格。出现以下任一事实，应视为物理映射缺陷或设计重开候选：

- 同一状态有两个可竞争 writer；
- 同一解析/identity/revision 算法在多个包独立实现；
- 上层模块必须读取下层私有全局或反向依赖才能工作；
- 错误、取消、恢复或资源寿命只能靠聊天说明；
- 一个“Manager/Context/Utils/Common”承担多个互不相干的 authority；
- adapter 可以绕过 application/execution 直接修改作者/目标；
- compiler 生成结果依赖当前 cwd、时间、`latest` 或未冻结环境却没有作为输入；
- 目标生成模块自行修改 Requirement 来让后端通过；
- 测试只能通过 mock 掩盖真实边界，而产品保证需要物理事实；
- 旧实现/兼容层已无消费者却永久留在主路径。

反向也要防止过拆：两个对象若没有独立 identity、writer、生命周期、失败/恢复、消费者或替换责任，不因为“看起来概念不同”就强建两套 service/registry/IR。

## 这份映射怎样长期维护

当前实现映射应由源码/测试/Evidence扫描与少量稳定注解生成或校核，不让维护者手工同步巨表。canonical 文档只保存稳定责任和物理边界；具体 commit SHA、文件统计、当前测试 run 属于准确实现/证据投影，不写进长期正文。

代码移动但责任不变，仅映射变化；责任变化先改 owner 规范，再改代码和相交消费者。实现已符合现有设计时，不为了“同步文档”制造无语义修改。历史映射、旧路径和旧 commit 可在需要审计时从版本库/制品取得，不是当前设计的阅读依赖。

## 组织规划在现有代码责任中的接合

[共同组织合同](../信息与生命周期/多维组织与树形落位.md)不新增全局service或公共节点模型。workspace提供准确源/成员/身份与前像；semantics和原生观察提供公开接口、引用、初始化/效果及可保持边界；compiler的原Realization/SourceLayoutPlan形成合法组件选择、文件与残余关系；application组合用途、输入补取与候选；execution承担真实改写；assurance评价准确Claim；entry/Workbench只呈现与路由。

这些是**设计责任映射**，不是当前仓库符号已存在的断言。进入实现时先从真实代码取得对应符号、调用者、测试和生命周期，能扩原函数则不造新模块。共用只能覆盖真实相同的值/算法差额，不能强迫Rust、TypeScript、文档或部署adapter共用一个万能TreeNode。

持久化只保留作者独特内容、实际Binding/布局政策、跨次身份对应和在途恢复所需记录。可重建排序/导航/分组索引按用途缓存；分析线程不得拥有额外文件写通道。稳定性取决于固定实际输入和规范顺序，不来自把所有对象塞到GlobalContext。

## 所选源码蓝图的实际回读

目标目录、机器源和内部方法映射统一引用[源码分区与机器合同](源码分区与机器合同.md)；本页只从准确仓库revision派生它们是否存在、实际消费者与验证义务。P0—P5是实施依赖路线，不是设计正文可自签的实现进度。迁移仍按逐能力正式owner和Evidence切换，不能因为新目录已设计就删除既有TS生产实现。
