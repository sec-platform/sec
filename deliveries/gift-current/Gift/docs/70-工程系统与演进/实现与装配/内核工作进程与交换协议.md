# 内核工作进程与交换协议

<a id="gift-unit-kernel-worker-protocol"></a>
## 首发画像与不变职责

Desktop/具本地进程能力的headless首发采用 **TypeScript/Bun control Runtime + 本地warm `gift-kernel` Rust worker**。长期会话按需启动并复用；一次性CLI可以借用合格worker或创建短寿命worker。纯Rust库仍可直接调用同一kernel公开方法，单个进程内不强制JSON编解码；其他in-process/native bridge只有在实际需要且保持同一批量合同后加入，不因此复制第二套语义API。

该选择为隔离崩溃/分配器、明确升级和跨语言所有权提供物理接缝，不宣称进程必然最快或天然限制权限。热图/arena/query/read-set留在Rust，control只交冻结snapshot/content/delta和批量任务；禁止每AST节点TS↔Rust往返或在TS维护可独立修改的完整IR镜像。IPC是否成为瓶颈由[性能义务](../../60-保证与证据/验收/意图覆盖与纵向符合性.md)判断，不凭架构图承诺百万行耗时。

Code-OSS本地/远端Node Extension Host与Web Extension是不同宿主。Node侧适配可连接所选control进程，不能假设Extension在Bun里运行。浏览器/WebWorker没有本地原生进程启动能力；纯Web只连接已明确授权且兼容的远端Runtime或显示准确缺项，不偷偷安装后台服务、把项目送公网或把polyfill当原生执行能力。离线/嵌入画像继续按其真实能力成立。

<a id="worker-start-trust"></a>
## 启动、信任、隔离与静态装配

bootstrap从准确已采用worker制品/工具链绑定取得可执行位置、来源、支持协议和启动profile，使用参数数组与真实进程端口启动，不拼shell命令。cwd、环境、可继承句柄、输入通道、临时区域、内存/CPU/日志预算由受信宿主明确设置，不能继承无关凭证或按PATH任意找到同名可执行文件。启动本身是宿主动作，有真实授权与资源owner；不能发生在纯compiler首次访问一个getter时。

control拥有实际外部Effect、操作日志和恢复存储。worker只处理已提供的冻结内容；需要Git/文件/网络/当前环境/秘密时返回输入或Action Need，让application取得并形成后继PreparedJob。worker可有实现必需的内部时钟/资源观察，但它们只影响预算/进度，不偷偷成为语义输入或成功结果键。

只规定“不得I/O”不能隔离恶意代码。受信kernel纯方法依靠准确制品、窄方法与实际宿主限制；不受信插件在具所需隔离能力的Provider边界启动，不能先加载其顶层代码再声称受限。进程组/Job管理与文件/网络/秘密访问控制分别验证，不强制Docker。停止/关闭合同复用[资源与进程](../../50-执行运行与观测/权限与资源/README.md)，不是另外一个沙箱认证。

Provider/方言/目标descriptor在ASM0—ASM4选择、验证和封存；worker握手核准确EngineImage中分派到本worker的实际方法子集，不通过任意module URL下载。EngineImage可合法登记外部Provider、control侧适配和迁移期TS方法；登记不等于必须把它们加载进Rust。请求只在已合格的真实执行位置调用；缺少本worker方法时返回分派/能力缺项，不能偷偷在Rust重写一份替代语义，也不能因为外部方法存在就拒绝整份image。健康/权限/可用额度不入image；需要新image形成新会话/请求，不原地替换旧请求方法表。新能力遵守Rust方向；既有TS生产能力只有经[MIG0—MIG5](../演进与实施/实现语言与机制演进.md#compiler-kernel-rust-substrate)才能切换，不因worker默认画像就当已迁移。

<a id="worker-framing"></a>
## 首发帧与协商

内部能力名采用 `gift.kernel-worker/1`，准确内容revision随[机器合同](源码分区与机器合同.md#machine-contract-source)发布；不是新的作者工具。首发传输用独占二进制stdin/stdout管道：每帧为 **4字节无符号大端payload字节长度 + 该长度的严格UTF-8 JSON对象**。长度只计payload，不含前缀；零长、超过当前接收上限、非法UTF-8、封闭信封重复键/未知字段、预算外嵌套与不完整EOF按协议错误处理，不能返回空成功结果。

首帧仅接受hello协商。握手前的有限frame/depth/string/queue上限由准确可信启动profile提供，不允许对方先发一个巨大限额让自身分配。双方协商的每方向限制不得超过各自硬上限；消息字节数、批次大小、内容占用、并发/排队、诊断/日志和在途结果预算分开。四字节载体上限不是建议给每帧分配4GiB；实现先读固定前缀校验界限，再流式读取有界payload。

hello包含所支持协议/codec准确修订、预期EngineImage/worker制品绑定、能力集合及限制。accepted返回选择的共同协议、真正workerEpoch、连接关联与能力/限额；不匹配明确拒绝，不能任意降版本、忽略未知字段后改义。进程PID存在、管道打开和hello成功分别不等于项目已捕获、snapshot已打开或方法已合格。启动关联来自真实宿主父子/句柄绑定，不凭worker返回的trusted布尔值认证自身。

后续请求的封闭信封包含 `protocolRevision`、`workerEpoch`、`requestId`、`method`、`body`，相交方法还包含准确 `sessionRef/snapshotRef`、`budgetRef` 与取消关联。`budgetRef`指向本连接已准入预算，不给worker升级权限；期限和剩余预算沿原时钟域传播，重试不得刷新原截止。响应包含同一关联、序列/完整边界、typed方法结果或共同错误；进度不冒充最终结果。不同方法保持各自结果代数，协议完成、语义结果、效果观察和清理不压成一套success/failed。

一次只允许一个writer形成完整帧，防止并发前缀/payload交错。stdout只用于协议，stderr是有界且单独持续排空的诊断通道，不能混写日志破坏帧；排空、背压与截断说明仍受预算，不丢唯一的操作/错误关联。请求和结果不能因大内容队列占满而永远阻塞cancel/close：控制帧保留独立预算/调度优先入口，内容分块可中断于完整帧边界，不能把半帧插入取消消息。

<a id="worker-content-snapshot"></a>
## 内容、快照与局部句柄

首发 `content.put` 按准确ContentRef、codec、总长度和分块位置送字节，JSON中二进制块用显式base64；base64表示不是内容身份。准确codec固定其字母表、填充、合法字符与解码长度，并在分配前后按预算验证；不能以schema含有contentEncoding注解当作字节已解码/校验，也不接受会被两端解释不同的宽松变体。总字节预算在接纳首块前预留，单帧限制与总对象大小分别检查。重复块必须同位置同字节，重叠冲突拒绝；按合同可顺序装配，不要求首发支持任意乱序块。只有完整长度、摘要/codec、来源与占用要求通过后才发布可读ContentRef；半成品留私有staging或按准确责任清理，不能让snapshot读到未校验尾部。

内容缓存按内容身份复用，但发现/披露/占用按当前会话权限和真实用途区分；命中相同hash不授权另一个租户读取。wire开销、受保护源、解码缓冲和共享结果都纳入资源预算。以后采用共享内存/文件映射需独立协商尺寸、访问与释放合同，不能由纯worker自己按客户端路径打开文件。

`snapshot.open`输入准确清单：源及内容引用、解释/方法绑定、模块使用域、输出根/配置及请求需要的固定输入。缺内容返回准确need，没有ambient read或网络补取。接纳时一并保护实际依赖，构造后发布不变snapshot及局部handle。delta必须指明准确旧snapshot、原前像/修改集合和新内容；未给的文件不自动删除，不从当前control工作树偷补缺项。

持久对象Ref、内容identity与局部handle分开。handle绑定 `workerEpoch + EngineImageRef + session + snapshot + local-id` 的解释范围；重启后旧短句柄全部失效，相同数字也不复活。重建从合格固定内容和解释重新打开，不能从旧指针/arena偏移反序列化。whole image只管理装配保护，query实际key/read-set仍是原[增量合同](../../30-实现解析/增量与性能/查询固定点与缓存.md)，新增无关模块不强制全部重算。

`snapshot.close`先关闭新使用入口，再等待或移交实际查询/结果/回调占用。结果还借用snapshot内存时，不能先确认释放再交给control使用；可转为独立拥有的编码结果或保留明确pin。close响应分别说明入口关闭、剩余使用和可释放范围，不等于删除内容库、清除日志或结束外部Operation。

<a id="worker-methods"></a>
## 粗粒度方法与依赖闭合

| method | body的责任输入 | 返回与生命周期 |
|---|---|---|
| `hello` | 准确协议/image/制品期望、codecs、能力/限额 | accepted/rejected及连接代际；不代表产品Ready |
| `content.put` | 原ContentRef、codec、总长度、块序号/位置、字节、结束标记 | staging/完整发布/准确错误；原内容/块去重不扩大权限 |
| `snapshot.open` | 固定manifest与内容集合或准确base+delta | 受保护snapshot handle/needs/错误；无可写作者头 |
| `snapshot.close` | 原snapshot、关闭意图 | 停新使用及实际占用结算；未释放不伪称已关 |
| `semantic.analyze` | snapshot、roots、所需查询与预算 | 局部语义结果/read-set/diagnostics/前沿 |
| `requirements.instantiate` | snapshot、根、准确模板/主体/controls | 普通RequirementInstances与卫生贡献/缺项 |
| `realization.resolve` | 实例、准确候选方法索引、控制、目标 | 原Decision/RealizationBinding及合法性/Needs；不安装工具 |
| `target.lower` | snapshot、实际Binding、TargetProfile、输出范围 | 原COMP5—COMP7 plan/贡献/完整产物与保持义务；不调用外部工具 |
| `impact.query` | 两个准确snapshot/对象修订、作用域 | 有覆盖diff/impact/dependencies；未知不是无变化 |
| `assurance.derive` | 准确对象/要求/claim模板与方法基础 | 义务与可用纯支持，不自动取得运行Evidence |
| `cancel` | 原request/scope、取消依据 | 真实接纳/停止/仍在途/不可取消观察；不撤销历史效果 |

该表不是另一套公共SDK，也不建立新COMP编号。若现有 `compileFrozen` 一次能够完成所请求分析/选择/lowering，应以一次批量调用或原方法内组合实现，不为每个表行强制RPC。语义方法发现新的工具输入时返回Need，由control取得合格外部结果后形成后继固定准备态；不“暂停纯方法后偷偷读当前网络”。

<a id="worker-cancel-recovery"></a>
## 请求、取消、重连与恢复

requestId在连接代际内绑定准确method/body/basis。相同身份同载荷可附加等待或返回已保留结果；同身份异载荷拒绝。结果保留/去重窗口到期要返回准确失效，不能在没有依据时重新执行一个声称“原请求”的动作。这里都是纯kernel请求，但重复CPU/内存/费用仍受原singleflight与受管竞速合同，不因纯函数无限重发。

control取消等待、worker接收cancel、方法到达取消点、旧生产者停止、结果发布、缓冲/代码释放和进程回收分别观察。若方法已完成，取消不覆盖其原结论；晚到结果按原basis与当前资格接纳，不装进后继请求。处理器长循环必须有实际有限取消检查或通过具保证的进程边界终止；协议存在cancel方法不证明有界停止。

断线/worker崩溃使短句柄与未确认结果的取得失败或未知；已完整校验且独立持有的纯结果可继续按资格使用，未完成的输入staging不发布。先确认旧进程/实际资源与共享查询责任，再按原重新加入/受管竞速政策重建；不能只换epoch就从预算中抹掉旧工作。无关已完成结果与独立输出不被相交故障删除。

外部Effect永远在control Execution或真实外部Provider owner结算。worker死亡不删除 `.gift/state/control.sqlite`、原operation identity、Attempt、前像或恢复材料；control重启从原持久记录协调已知/未知作用，不能把重编译成功当“重新部署安全”。worker发回未知操作引用不代表执行过：只有真实来源关系可显示，不能补造回执。

升级先准备新准确worker/image并核兼容，切换新请求入口，旧请求保留其解释和占用直到真实退役。安全撤销可限制新执行/披露；保留恢复责任不等于继续许可危险旧代码。关闭拥有的worker与断开借用worker分别处理，不能关一个窗口杀掉其他用户运行实例。

## 实际资格与取舍的复核条件

首发验证需覆盖分片前缀/半帧EOF、非法UTF-8/重复键/过大预算、并发帧不交错、stderr排空、内容完整性、base/delta与未知保全、错epoch/陈旧handle、取消/结果竞态、close借用、重启/旧生产者、当前撤销、多租户缓存、目标工具与Effect隔离。性能记录冷启动、warm batch、内容首传/复用、incremental、并发/高基数、峰值/长寿命/退役积压；不以单个IPC微基准决定全部架构。

满足相同batch/ownership/取消/隔离合同而经证据证明需要原生bridge时，允许显式增补Provider画像；既有嵌入式库也是合法用途。不能为接口统一消灭这些不同部署形态，也不能默认每种已设计画像已可运行。相关外部依据见[语言与目标工具](../../../research/sources/语言编译与目标工具.md#worker-schema-host-evidence)。

<a id="gift-worker-lifecycle-handoff-closure"></a>
## Worker 会话的实际取消、重启、重放与隔离

`KernelSession` 由 host 选择解释版本、能力、source snapshot 和最大资源；worker 只持有本次派生状态。Worker Ready 前握手输入签名、协议、版本、最大内存、CPU、IO/消息预算及已协商方法；退出、信道断开或背压拥塞后，应用必须把未确认请求标成 `INDETERMINATE_TRANSPORT`（纯求值可用固定Basis重算），不能自动将真正的 Provider Attempt 标成业务失败。

请求有 `requestId` 用于响应关联、`evaluationKey` 用于纯结果共享、`operationRef/attemptRef` 用于现实作用结算；这些身份不得混用。共享 query 被多个客户端等待时，一个客户端取消只解除自己的消费/流接收资格，除非所有消费者关闭且没有持久必要才可停止底层 worker。重启后 workspace/application 从持久 owner 获取作者源、正式绑定与 Operation/Attempt 事实，纯缓存可丢弃并重建；worker 的最后一条标准输出不能成为外部效果已完成的唯一证明。

不可信插件运行不能仅凭进程边界得到文件/网络/秘密隔离；若 worker 有宿主权限，必须通过平台实际约束、受限账户、网络和文件能力做威胁模型内的隔离。协议检查对超大帧、递归对象、重复标识、未知版本和超时均有受限处理；退出时进程释放和远端外部作用结算分别验证。测试把 worker 杀在写回前、目标工具返回后、effect接受回执前与流结束前四个切点，比对应有状态及重新取得的作者/运行真源。

<a id="developer-request-worker-boundary-and-real-retry"></a>
## 首条开发者请求怎样跨 TS/Bun ↔ Rust Worker：精确执行接缝

本节补足一条用户可观察的请求与本协议之间的桥接，不新增外层API。下面`Request/Candidate/Artifact`仅为**协议对象角色示例**，具体Wire字段及版本以上文已有`gift.kernel-worker/1`为准；`C1/A1`是实际实现应返回、且与不可变依据绑定的符号Ref，不是固定ID。

### 纯编译请求的有限生命周期

1. `entry`严格解码`gift.preview({source,sourceLanguage?,target?,return?})`或`gift.preview({candidateRef,target?})`的互斥联合。`application`选择当前已被锁定并有权读取的Target/Profile、EngineImage和SourceProfile；没有目标不得假定TS，缺当前受信上下文只能返回需要输入。
2. `workspace`捕获本次源字节、模块位置、导入锁和真实读集；对用户提供的内联snippet只需要in-memory SourceSnapshot。不打开源码保存写入。候选身份必须由固定源内容、解释发生位置与基础等实际条件建立；不能将裸source字符串的hash当跨工程授权。
3. `bootstrap`查找当前准确且经过信任/协议校验的Rust worker制品；若新建进程，stdout按`4-byte BE length + strict UTF-8 JSON`握手`hello`，stderr独立排空。Node Extension不能在无Bun情况下偷偷在Extension线程实现同一语义；无合格worker时返回Unavailable，保留候选。
4. `application`通过`content.put`传入准确内容字节/摘要/codec，并在`content.put`完整结束后调用`snapshot.open`。Worker仅持有已收到的snapshot及本地handle，不根据宿主路径自行读取；多源输入可分批送，来源职责和租户占用由control维护。
5. `semantic.analyze`获得真实语义与Needs；`requirements.instantiate`（有真实要求时）、`realization.resolve`和`target.lower`按依赖调用，可合并batch但必须记录实际producer、消耗的Basis与Coverage。目标后端只写内存/不可变ArtifactSet，SourceMap与目标成员排序在同一准确快照中派生。
6. `application`对当前请求已指定范围出结果：`generated-unchecked`、准确`candidateRef/artifactRef`及返回形式；诊断显示哪些根可用、哪些仍为Needs。此时绝不意味着已执行`tsc`、启动Node/Bun、修改`dist/`或者取得Git权限。
7. 响应消息结果放入control按当前Ref生命周期管理；有缓存命中仍须复核作用域/当期披露、准确修订和权限。撤销改变当前可读资格但不改变历史已计算的真实来源；不得把缓存命中作为匿名泄露接口。

### 超时、竞速、重启与安全边界

- requestId是worker当前`workerEpoch`内协议关联，CandidateRef/ArtifactRef是独立不可变对象；OperationRef只属于真实效果，不能用requestId代替幂等效果身份。同一requestId+不同payload必须拒绝。
- `cancel`到达只证明收到取消请求；在取消检查点前完成的纯计算仍可按原请求基础返回，若当期不再适用不能装进新候选。worker已发结果但通道断线，control未收到完整Frame时只能根据已确认独立内容重新计算或查询，不读取半帧作为最终事实。
- 每个worker restart产生新epoch；旧snapshot-local handle即使数字相同也无效。应用可从固定Source/EngineImage重开快照、重算可共享纯查询，不能重造或清除已启动的真实Operation。`close`结束新使用入口与释放pin不同，不能先解除内存保护再让control读取借用指针。
- 并发请求的帧由单writer串行成完整帧，其他请求可以并行计算；`cancel/close`有单独控制预算，超大结果不能阻塞关闭或无限排队。输入/输出大小、内存、时间、嵌套深度、诊断容量各自限额，不能把4-byte长度范围视为合理单帧预算。
- Rust纯内核不会因Hello声称“无I/O”就自动安全；宿主启动、签名/摘要/来源、进程权限、文件访问和环境隔离分别负责验证。对不可信用户代码的真实执行必须进入独立受控Effect边界；不能在纯preview中运行用户源码寻找宏/配置。
- 一个目标的Lowering失败保留其他可重用目标与失败诊断；跨目标共享不变量需要共同验证的，整体任务只报告partial/blocked，而不是丢弃已完成根或宣布所有成功。

### 两种构建路径的角色不能偷换

**纯编译**：`gift.preview`→`target.lower`返回内存Artifact；**外部检查/构建**：用户后续`gift.check`或已协商run→Execution调用实际`tsc/Bun/Node/Provider`并得到Evidence/Operation。Target方法本身可以使用已固定的纯库生成语法，但不能秘密执行用户安装脚本；若某语言特性确实依赖执行式编译宏或工具，必须声明该Feature需要单独Effect/可隔离Provider，缺它可返回`Unsupported`/Need。**输出保存**：`gift.apply(mode=write-output)`对精确ArtifactRoot及磁盘前像结算真实写入，不能在产物尚不完整时宣布包已交付。

### 实施验收消息片段（按实际codec生成，非可直接发送的发布payload）

```text
host: capture C1/source snapshot + locked TS TargetProfile
host→worker: HELLO, protocol=gift.kernel-worker/1, fixed EngineImage, limits
worker→host: ACCEPT(epoch=E, supportedCapabilities)
host→worker: content.put(bytes, content digest, total length)
host→worker: snapshot.open(frozen manifest, locked profile/ref)
worker→host: snapshotRef=S [epoch E]
host→worker: semantic.analyze(S, selected root)
worker→host: type result/read-set/Needs or typed failure
host→worker: realization.resolve(S, methods, target)
worker→host: eligible binding or Needs
host→worker: target.lower(S, binding, TS target)
worker→host: complete ArtifactSet/source-map or explicit incomplete result
host→developer: C1/A1, generated-unchecked, accurate Coverage
```

校验合格的实现可合并粗粒度处理与结果编码，但不得跳过准确引用、输入固定、实际能力和效果隔离。此处的示例不是宣称这些消息已由当前Gift设计包中的真实产品进程执行过。

<a id="gift95-cross-contract-29"></a>
## Worker对Rule与Target供给的纯计算边界

`semantic.analyze` 只在精确SourceSnapshot/EngineImage下解释Rule、类型、公开调用、Effect及其Need；`target.lower`只在冻结的Binding/TargetProfile下贡献目标成员/残余，不调用系统安装、用户脚本或网络。Method/TargetManifest即使携带 `toolchainRequirements`，也只能向应用层报告获取要求，不能从Worker偷偷启动安装。

Host与Worker之间的结果须携带真实输入基础、已解释Profile/MethodRevision、正常/残余/拒绝状态、受影响根和是否可复用的依赖；Worker崩溃或Transport断连不将已发生外部效果标为失败。

<a id="prebootstrap-worker-admission"></a>
## 自举工作进程的协议保鲜、流控与拒绝

本节不替换既有四字节大端长度加严格 UTF-8 JSON 帧，也不增加每个 AST 节点一次 RPC。控制面交付批量冻结内容和快照，Rust worker 执行粗粒度分析/解析/降低；小内核直链调用可保持同样纯接口，无须被迫启进程。

hello 前即有宿主硬帧/缓冲上限，不能信任对方协商值后才限制首次输入。协议 revision、worker epoch、requestId、method、snapshot/session 与预算按其真实作用域核验；同 requestId 不同请求内容拒绝，旧 epoch 句柄不能命中新进程中同号对象。content.put 先核验长度/编码/摘要与获准内容范围，哈希相同不表示另一租户有读权。

控制帧与大输出数据的调度必须有界，防止数据发送占满队列后取消、关闭和错误永远发不出去。片段结果带范围与完成状态，接收方在完整核验前不发布为完整对象；连接中断保留已确认范围或丢弃未完成 staging，不将半帧当空响应。stderr 独立排空和截断标记，不能与 stdout 协议字节混在一起。

worker 不负责直接发布工程源、签 Grant 或执行世界效果。Needs 返回给控制面，控制面有权取得依赖后生成新 Prepared 输入；禁止 worker 为完成 snapshot.open 自行扫描文件系统或联网。重启可重算纯查询，已有外部 Operation 的重试/结算由其原持久 owner 处理，不因 worker 忘记 requestId 就重新执行。

映像升级时新请求绑定新 epoch，旧请求结果只对其旧快照有效。缓存和句柄生命周期有 pin/release 与资源上界；client 消失不能无限保留所有快照。释放只影响可重建内核缓存，不能使作者源、Effect 回执或唯一恢复证据消失。协议字段未知或必需能力不足时准确拒绝该请求，仍可协商双方实际支持的独立只读功能。
