# 多表示输入与统一编译接合

本篇只拥有**跨表示进入同一工程推导**的应用与物理实现接口，不另建语义代数、作者文件格式或独立编译器。作者真实文件和表示裁决见[统一作者源入口](../../10-作者与输入/作者源/工程源/统一源码工程与多表示作者协议.md)；`AuthorModule`/清单/锁在[现有 owner](../../10-作者与输入/作者源/工程源/工程清单模块与绑定锁协议.md)解释。以下类型示意是实施合同，不是已存在的 Rust/TS 产品源码或已发布网络 API。

## 1. 一个消费图；不同输入不要求先相互翻译

```text
结构作者JSON ─┐
可选 .gift ───┼──> 准入的SourceCarrier + 绑定解释 ──> SourceSnapshot
原生Rust/TS ──┤                                                  │
SDK候选字节 ──┘                   (不是另一份权威源)             ▼
                                  ImportedModuleView / ModuleUse
                                      │   │   │
                   独立 Requirement──┤   │   └── 原生保全的 opaque region
                                      ▼
                   已检查公开语义 + Needs + SourceMap
                         ├── 设计/TargetProjectPlan (只读)
                         └── 合格目标/Method/ABI -> ArtifactSet
                                                          │
                                 CheckRecord -> (明确获准时) Operation
```

`ImportedModuleView`、`UseBinding`和 `EngineImage`沿现有规范建构，不能把它们重新序列化为另一份作者文件。结构体 codec、原生分析器和 `.gift` parser 都只供应有来源的语义观察；不能读取的私有原生部分继续由原生 owner 保留，其分析域可有限而不把源码伪造为已完全理解。

## 2. 最小不可混同的数据边界

```text
SourceCarrier {
  ownerRegion: stable region reference,
  physicalLocator: actual path/buffer/content location,
  sourceRevision: captured content+version reference,
  bytes: frozen exact bytes or authorized content handle,
  sourceProfile: fixed interpreter identity+revision,
  readScope: authorized scope reference
}

ModuleElaboration {
  moduleUse: module identity + resolution domain + occurrence,
  publicSymbols: checked exports only,
  definitions: typed claims with source spans and dialect identities,
  independentRequirements: requirement references with provenance,
  typedDependencies: actual imports/constraints/Method needs,
  unsupportedRegions: exact span+reason+affected consumers,
  evidenceScope: which semantic assertions are justified
}

ProductRootUse {
  outputSelector: project moduleId+optional export under a fixed base,
  boundRoot: actual current module/export+definition identities,
  chosenTarget: qualified TargetProfile or no target,
  requirements: independent applicable obligations,
  realization: eligible methods or explicit Need,
  sourceReadSet: exact source+binding+environment dependencies
}
```

这些是跨边界**逻辑值结构**，没有规定必须增加三个可写 JSON 文件。身份证明、精确 hashing、`Snapshot`、Result 和 `Diagnostics` 仍引用原有 contracts；该代码块只列每个消费者必须可追踪的事实。不能只靠裸 `moduleId` 或字符串 `"name"` 联接：同一名字在不同项目/锁/作用域/版本可合法不同，权限也不由名称给予。

## 3. 捕获、解释、准备和发布的确定顺序

| 阶段 | 消费与动作 | 公开的可用结果 | 必须拒绝的偷换 |
|---|---|---|---|
| CAP0 范围 | 根据任务获准的 project/sourceScopes/editor-buffer/native root 捕获 | 当前可访问成员与各自前像 | 把磁盘`cwd`、工具默认目录或“最近工程”当成用户指定的当前源 |
| CAP1 Carrier | 每个非重叠作者 region 恰配一个已选 Profile，冻结原始字节 | 完整 source set；未知边界保全 | 同一个 Definition 的 JSON 与 `.gift` 竞相可写 |
| CAP2 入口检查 | JSON 严格解码、`.gift` 解析或原生适配按对应真实能力 | typed/partial ModuleElaboration、span、诊断 | 把语法通过、原生工具通过或 SDK 构造成功等同业务符合 |
| CAP3 Import | 按 ModuleUse 发生点和确定解析域查锁/项目公开导出 | 当前公开 API、使用点、依赖图 | 同名第三方库按最新版本临时覆盖旧绑定 |
| CAP4 Semantics | 检查语义、独立要求、Effect/Type/Relation 与共同不变量 | checked portion + Needs + unsupported scope | 将 opaque native 段当作已证明纯、无副作用、任意可移植 |
| CAP5 Realization | 当前目标/使用点核真正 Method/ABI/资源/供给资格 | RealizationPlan 或定位精准的 Need | 缺真实供给时自动生成空壳却称“全工程完成” |
| CAP6 Target | 只有用户请求目标且成员闭包完整时降低成真实产物；设计-only 则给蓝图 | ArtifactSet 或 ProjectPlan，两者状态不同 | 把蓝图文件树标成已生成源文件，或把静态 SDK author 值当运行时 |
| CAP7 Consumer | 所需检查、获准保存/运行、读回、证据结算 | 按根和阶段拆开的结果及剩余义务 | 一次`success`覆盖所有目标、部署、外部回执 |

`CAP0—CAP7`是实现步骤说明，不新建持久状态机，也不要求每个查询必经八次 RPC。增量缓存复用须具备与本次输入/解释/目标及证据作用范围相符的读集；一个源文件修改只失效相交消费者，而非整个工程必须清缓存。固定构建不能运行 arbitrary native builder、拉取 latest 或读取未声明 secret；实际需要的执行走 `Operation`。

## 4. Python/TypeScript/Rust 等成熟语言与 Gift 语义的真实边界

原生适配器可以只提供符号、类型、文档、依赖、公开方法摘要、测试接口或准确局部编辑，而不证明它掌握了原语言全部可观察行为。分别返回`READABLE_TEXT`、`PARSED_SOURCE`、`CHECKED_PUBLIC_API`、`CHECKED_BEHAVIOR_SUBSET`、`OPAQUE_NATIVE_IMPLEMENTATION`等*覆盖说明*；这里名称是概念域例示，具体机器判别联合复用原有结果协议，不能直接当已发布 enum。

当一个 Requirements 模块引用现有 Rust 库时，可以在该准确版本的行为摘要上形成有条件的绑定；库是否能在目标部署环境使用，还需核其编译工具、平台ABI、依赖、许可证和权限；要生成**纯 TypeScript 源码**，必须选择合格的 TS 实现、受支持的 lowering 或合法运行桥。简单包装一个 native crate 不会凭空生成等价 TypeScript 算法。

若应用只要求设计蓝图，原生库没有构建环境仍可显示基于已取得事实的模块/依赖规划；未检查的符号和未知二进制效果必须保留“待核实”。离线查询和选择不应默认下载工具链。

## 5. Rust SDK 的接口与权限归属

可选 `gift-author` SDK 首先是**结构化作者表示的类型化编辑工具**；它不是 Gift 纯语义内核、Target、业务库和主应用 Router 的别名。SDK 可在本地通过 Builder 构造 `TypedModuleDraft`，但不能声明与当前读取模块身份相同而绕过 Revision 检查。调用应用层 `propose` 建立候选，再经 `apply` 在当前授权下按源 owner 回写。它自己的内存树没有第二个可写事实身份。

该接口必须分别满足以下条件：

- 定义所有强类型字段映射到固定 `gift.author-module/1` dialect 结构的规则、默认值来源、错误类型、SourceMap/身份和大小预算，未知结构失败不被静默删掉。
- 保留 `Serialize` 与 `Commit` 的明确差异；单纯构造 JSON 字节是纯操作（除主动读写文件），执行用户宏、build.rs、过程宏、自动发请求属于不同准入。
- 若 SDK 在 Rust 编译时计算新业务/规则，所得**冻结输出**才是进入 Gift 的作者候选；当前 Rust 编译器进程不是 Gift 正式语义的动态隐藏前提。
- 有权主动迁移作者表示时，必须完成一致性检查和唯一 SourceProfile 切换；不能 SDK 写 JSON、编辑器同时改 `.gift`。
- 第三方 SDK 不能自行发布全域实装资格或保证；需要消费者验证依赖、域、失败和证据。

## 6. 一次工程修改的影响路径

使用者在现有 TypeScript 编辑器项目中修改 `src/editor.ts`，并把“撤销动作不得跨文档生效”的要求加入独立 JSON Requirement：

1. 文件内容变化产生新的原生 SourceRevision，要求变化产生另一个有来源的 Requirement Revision，两个源都保持可直接编辑。
2. 当前语言适配器分析有把握的符号、函数或 IPC 边界；无法解释的脚本/插件行为保持未知，并指出对所要求观察的影响。
3. 变更传播检查受影响导入、公开边界、已有绑定、验证任务和目标；不会把原生函数打印成 `.gift`，也不会把同一要求再写进 `gift.project.json`。
4. 若目的是设计-only，提供目标工作区布局、进程接口、数据/状态与影响图及准确不足；不运行 `tsc` 或生成源码作为宣称设计完成的前提。
5. 若目的是提交完整目标，需已取得目标/Method/工具链、执行必要检查并按根交付，应用目标另需授权及恢复；不能凭一个 IDE 文件样例宣称整个编辑器与 VS Code 完全等价。

## 7. 改变作者表示或实现方法的联合失败路径

- JSON 中`req:composite`和可选 `.gift` 声明同一稳定 Definition，两个 SourceProfile 都标为可写：`AUTHOR_OWNER_CONFLICT`类诊断，停止受影响根的采纳，保留原字节。
- SDK 序列化的 ModuleDraft 以当前路径覆盖被另一编辑者改动的 JSON：比较实际 SourceRevision 与 edit read-set，冲突返回新候选/重基建议，不能让旧内容覆盖。
- 只有结构 Requirement 且缺无损数据类型的 canonical value codec：仍可保存要求结构，具体 `typed` 值或受影响默认无资格消费；不改为普通字符串伪装。
- 自定义 Rust build 脚本读取了不在捕获范围的网络结果：若显式授权，可取得结果并冻结证据；固定纯编译不能暗中执行并声称可复现。
- 原生 Rust 能执行、TS Target 没有对应 Method：报告该目标的未满足能力；独立 Rust 目标可以继续。必要共同目标不能按部分成功宣称完整。
- 两个生成产物都通过类型检查，却有同一资源的容量约束/权限竞态未被检查：联合保证仍未通过，不把局部CheckRecord合并成全体保证。

## 8. 对外合同的设计准入

任何新作者前端、结构化编辑器、SDK、`gift/author` 文本 Profile、TS/Rust Target或开发者工作台必须有如下可复核记录：正确的 SourceProfile 范围与拒绝；一个 owner 的保存回写；固定 import/锁；未知内容和非受管字节保全；错误内容定位；必要的临界/并发/撤权反例；准确 Scope；独立结果状态；性能/资源预算；外部工具与实际权限条件。**这不是要求在设计阶段把所有编译器或真实业务代码写出来；它规定未来生产实现不能以“界面看似统一”替代这些基础语义。**

## 规则到目标的具体无双写接线

`SourceCarrier → ModuleElaboration → BoundRoot → RequirementOccurrence → CandidateMethod → RealizationPlan → TargetProjectPlan/ArtifactSet` 使用原有各层owner。增加call-bound Rule时，结构Reader只传准确Rule体与source span，语言/原生Adapter负责Callable和PredicateRef的公开签名，语义内核负责类型/作用与义务，Resolver负责Method覆盖及残余，Target负责真实成员，Execution负责一切写盘/运行，Assurance评价独立Claim。

这些阶段共享一次固定SourceSnapshot和解释绑定；原生Adapter无法证明行为时保留opaque及unknown，不能自动生成它的Gift镜像。Method和Target示例JSON是供应方声明，不进入原项目作者文件，也不替供给者签发可执行资格。

## 原生 SourceProfile 适配与结构 Rule 的闭环位置

结构 Rule 只定义对某个逻辑符号的观测要求；Native Author Binding 仅固定该逻辑符号选择自哪个有权路径与公开导出；语言适配器才能建立实际被读取的 TypeScript/Rust 语法树、类型、效果、版本与导出/导入签名。上述三层分别有不同作者/生产者。适配器报告的 `bindingStatus=READABLE|AMBIGUOUS|UNSUPPORTED|STALE` 不等于 `behaviorVerified`；缺乏合格适配器不允许编译器按方法名把任意源偷偷接入 Target。

接合过程先冻结 semantic/native 同一 ProjectView，映射 AuthorModule/Occurrence 和原生 SourceProfile，再由 RES 将有资格的 Method/Target 候选与 Control/Requirement 取交；Lowering 只消耗已准入的 Binding 和原 SourceSnapshot。只有目标生成器实际产生完整成员和保持义务时进入 Artifact 评价。目标生成的 TypeScript 文件与最初作者 TS 文件同字节，只支持**该实现方法的直通复用**，不证明 Gift 能从全新无算法语义自动合成相同行为，也不允许由复制方拥有源的第二写权。
