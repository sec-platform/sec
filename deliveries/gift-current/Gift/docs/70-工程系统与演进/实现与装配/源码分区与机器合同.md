## 真实作者工程与Gift平台代码的物理边界（禁止把两类src混同）

**业务用户的`project/design/src/assets/gift.controls`**属于其自己的AuthorWorkspace；**Gift平台内部`contracts/workspace/semantics/compiler/...`**属于生产实现代码仓库；**生成的`TargetProject`**是第三种有独立修订和交付契约的制品。即使三者都含`src/`，也不能把用户的原生TS文件作为Gift编译器模块、将平台内核IR作为用户必须写的JSON，或把生成目标源码改为唯一可编辑的源而无归属证明。

| 实际实现层 | 正确代码拥有者和调用 | 不得承受的职责 |
|---|---|---|
| TS/Bun entry、Workbench、CLI/SDK | 请求解码、任务/文件展示、Candidate Diff、已有六工具委托 | 复制Rust语义解析、直接伪造Grant、维护第二套Rule解释 |
| `workspace`及存储适配 | 原字节/CST、SourceRevision、文件读取权限、锁、CAS与可恢复写入 | 判断业务Goal成立、隐式下载未知Provider |
| Rust `semantics` | 模块/型、谓词、Pattern、Requirement、时序/Norm接口与证据边界 | 选择目标语言最省钱Method、写用户文件、执行外部作用 |
| Rust `compiler` | 结合已解释要求做联合求解、Method精化、Target规划、合法降低 | 通过候选声明直接认定外部实现真实或授权执行 |
| `adapters`与Target backends | 受限读取真实TS/Rust等原生项目、目标AST/ABI/构建实际能力 | 修改已接受业务意义、采用不受限的外部最新版本 |
| `assurance` | 检查记录、证明依赖、受限Claim和独立Oracle | 用自己生成的测试证明全部正确、把设计PASS签为D5/D7 |
| `execution` | Grant、Operation ledger、Provider适配、Unknown/reconcile | 因重新编译重派真实动作、以HTTP成功取代结算 |
| `application/bootstrap` | 固定EngineImage、资源寿命、Scope/预算，编排Owner | 第二套AST/源码/命名注册表和万能全局状态 |

实施起点以现有源码分区为准；只有真的存在接口消费时才分离Rust crate/TS package，不为了10个逻辑Owner创建10个网络服务。每个跨语言DTO都要固定消息边界、内容身份、Reader预算、未知版本拒绝和错误映射；任何裸指针、线程内Arena ID、SourceSpan行列猜测都不能作为持久连接键。详细业务作者的全部源码责任见[唯一逐文件规范](../../10-作者与输入/作者源/工程源/逐文件开发源码具体规格与完整实例.md#gift130-source-tree-authoritative)。

## 所选物理蓝图与真实仓库映射

本篇定义Gift自身的预期源码分区与机器接缝；[十职责及运行实例](模块与运行实例.md)另定义逻辑依赖、写权与寿命。这里的目录树是设计蓝图，不能作为线上仓库已存在相应crate、文件或CI结果的证据。实际实施须由[架构实现投影](架构到实现追踪与代码落位.md)绑定仓库Revision及真实package、crate、文件、符号、消费者和检查记录；未回读的部署或实现状态保持未知。

```text
schema/                           机器结构合同源、受限生成配置与准确引用清单
kernel/                           Rust Cargo workspace 与首个 kernel package
  Cargo.toml                      workspace + package；若未来分crate则保持同一责任映射
  src/lib.rs                      可嵌入纯内核公开入口
  src/main.rs                     本地 gift-kernel worker 入口，不含第二语义实现
  src/identity/                   持久Ref与snapshot-local handle、验证值
  src/semantics/                  解码/类型/效果/需求与语义方法
  src/query/                      memo/read-set/失效/固定点/session
  src/realization/                Need/Method/Eligibility/Decision/Binding
  src/lowering/                   中立TargetProgramPlan/贡献与布局
  src/assurance/                  纯义务派生/方法结果与适用性
  src/targets/typescript/         TypeScript目标的已选纯后端方法
  src/targets/rust/               Rust目标的独立纯后端方法
  src/protocol/                   粗粒度worker codec与方法路由
  src/protocol/generated/         schema派生Rust类型；不可手改
control/                          TypeScript/Bun产品/控制进程
  src/workspace/                  固定作者输入、候选、编辑/保存计划
  src/application/                六工具、任务准备、IntentCatalog/Occurrence投影
  src/execution/                  当前准入、资源、Operation/Attempt/恢复
  src/adapters/                   fs/Git/network/native/toolchain等实际端口
  src/entry/                      CLI/MCP/SDK的协议/呈现入口
  src/bootstrap/                  Runtime/EngineImage/Provider装配
  src/assurance/                  外部检查用例编排；纯规则调用kernel而非另写
  src/workbench/                  独立Extension发行与view-model适配闭包
  src/generated/                  schema派生TS类型；不可手改
providers/                        确需独立发行/权限/进程隔离的Provider
conformance/                      真实结构/语义/目标/Provider/意图/故障/迁移向量
benchmarks/                       冷/暖/增量/大规模/高基数/并发测量材料
```

初始`kernel/Cargo.toml`同时定义Cargo workspace和实际package，使`src/lib.rs`或`src/main.rs`归属于可构建crate；若改成virtual workspace，必须另设成员package，不能假定根`src`自动属于某crate。后续拆分crate或合并私有文件须依真实发布和寿命需要更新本篇映射，其他规范不维护竞争目录树。

逻辑 contracts 负责 Schema、跨语言生成绑定和最小类型；纯 semantics/compiler 放入 Kernel；workspace、application、execution、adapters、entry、bootstrap 在 Control 边界；assurance 将纯资格检查与外部取证调度分离，仍维持一个义务与 Claim 体系。真实 Provider 可由 Rust/C++或成熟服务实现，但不能因此成为第三套语义内核。此分区描述职责，不规定每个逻辑单元都建独立 service/package。

Workbench的共用纯view-model/命令编解码仍属于逻辑entry，Code-OSS宿主适配属于adapters，激活/连接属于bootstrap；可为独立发行物在 `control/src/workbench/`聚合这些边界，不能让一个目录吃掉全部写权。`vscode`/DOM/React/图布局依赖只进入Extension闭包，不成为CLI或kernel运行依赖。Extension的Node/Web宿主不是Bun本身；它通过已协商接口连接独立control Runtime，不能把Bun API直接打入webview。

<a id="machine-contract-source"></a>
## 机器结构唯一源与语义验证

首发需要 JSON 编码的**机器拥有工程/锁/六工具/worker 信封及明确选择 JSON SourceProfile 的作者区域**采用 **JSON Schema Draft 2020-12 + 严格 codec + 语义 validator**，不以 Markdown 字段表和两份手写 Rust/TS union 长期并存。其他 AuthorSourceProfile 由自己的语法/CST/SourceMap 合同进入同一 SemanticModel；JSON Schema 不拥有它们的物理作者字节。`schema/`的具体文档按准确协议identity/revision登记，当前Writer须覆盖 `gift.project/1`、`gift.author-module/2` 与现行要求Body；另有独立兼容读取覆盖旧 `gift.author-module/1`、`gift.requirement-structure/1`、`gift.binding-lock/1`、六工具与已采用扩展、内部worker信封及相交交换结构。现有协议名称不因选择JSON Schema而换义；发布前仍需真实decoder、迁移和符合性证据。

源的职责有三层，不能互相抢权：结构schema拥有合法字段/标签/基本值域和结构组合；规范的语义owner拥有身份/类型/引用/效果/权限/跨对象保持要求；codec拥有准确原字节解释、规范内容编码和未知载荷保全。机器源发布后正文以稳定契约/方法和生成来源引用解释，不另手写竞争字段真值；当前尚未发布的设计字段仍由本套规范明确，不假装已有代码生成完成。

机器入口按明示字节、深度、成员和字符串预算严格 UTF-8 解码；对闭合信封重复键、非法数值及原型写入路径，必须在丢失原始区别前拒绝。Schema 作用于已解析 JSON 时不能发现此前被覆盖的重复字段。超过 JS 安全整数、保留小数词法、符号零或原字节的值依字段 codec 精确保存；不得先转成 JS Number 再 Hash 或传 Rust。已有协议对范围的限制仍生效，不能把所有数值机械转换成字符串。

生成器支持的schema vocabularies、`$ref/$dynamicRef`、unevaluated属性、联合辨别和递归范围必须显式固定；不支持时拒绝生成，不把限制静默擦除。引用解析只能消费已固定的准确schema闭包，不能验证时自动联网取URL/latest。`format`的注解行为不是自动断言；关键时间/URI/标识codec由明确验证方法承担。`default`/description/examples是注解与辅助数据，不自动取得作者默认或执行许可。`contentEncoding/contentMediaType/contentSchema`也不能代签内嵌字节或文档的验证；需要解释该载荷时由明确codec按相交预算验证，并分别返回外层结构与内层内容的结果，不能由注解自动触发任意解码/执行。

Rust 与 TS 的**机器交换/JSON profile 类型**从同一准确结构 schema 生成；非 JSON AuthorSource 的 parser/CST 不先生成一份持久 JSON 镜像。任何生成类型检查成功都不等同入站数据已验证。TS入口做有限解码/结构/当前权限控制，公共语义由kernel对应方法判定，领域/Provider边界由真实owner方法验证；不复制一套TS类型推导/实现选择。安全边界需要重复检查当前权限或前像时可以检查，不以“只有一个validator”禁止真实边界核验。

保全型开放业务载荷按其 own schema和 requiredFidelity 处理未知值、出现位置、顺序与重数；封闭命令严格拒绝未知执行字段，二者不能混为“全部忽略未知”或“全部删除未知”。wire帧编码、公开schema修订、规范内容identity和Rust内存布局彼此独立；升级wire或代码生成器不自动重解释历史摘要。

<a id="contract-generation-lifecycle"></a>
## 生成、兼容、采用与验证

一次生成绑定schema闭包、生成器/选项/codec与validator修订，输出类型/路由辅助代码和结构向量；输出只读，更新必须回源。可派生的向量覆盖invalid/unknown/duplicate/bounds/round-trip，但同一生成器同时产类型和期望不构成独立Oracle。语义不变量、强反例与真实工具/宿主结果按[符合性](../../60-保证与证据/验收/意图覆盖与纵向符合性.md)另取得依据。

兼容判断按准确reader/writer/vocabulary/扩展集合与用途，而非文件名中的 `/1` 或“增加字段必兼容”。新码/新分支影响旧封闭消费者时协商或拒绝；原件可读不等于可改写/可执行。未知含义激活与原字段迁移按原扩展/迁移合同，不用schema升级强改全部历史。生成失败不得发布半套Rust/TS类型；作为同一不可变生成制品组检查后采用，失败保留旧合格版本及具体缺项。

真实依赖门禁从当前 package/crate metadata、imports/模块路径和稳定责任注解取得事实，与十职责规则比较；单crate内部也需检查逻辑反向依赖，不能仅Cargo依赖为空就称无旁路。文档不再维护另一份不断追赶imports的真值表。源码移动只改物理投影；违反原契约的实现应修实现，不倒改规范迁就坏代码。

## 首发粗粒度内部接口与实际消费者

下表的方法名是稳定责任的实现定位，不承诺每个方法独立文件或同名公开API。已有 `read/fork/evaluate/plan/assess/run/observe/recover` 可直接承接同义步骤，禁止为了此表包一层空Service Locator。

| 逻辑owner/物理区 | 操作与输入 | 输出、状态与消费约束 |
|---|---|---|
| workspace / control | `captureProjectView(projectRef, buffers, sourcePolicy)` | 不可变ProjectView、实际源/读集/诊断；不执行项目脚本、下载依赖或写工作树 |
| workspace / control | `forkCandidate(base, authorDelta)` | 新CandidateRef及保持/冲突；不LWW覆盖新基础 |
| application / control | `describeIntentCatalog(view, image, queryScope)` | 有覆盖/分页的派生目录；不查秘密/签权限/维护意图DB |
| application + workspace | `proposeIntentAction(base, facetRef, action, typedValues/subjects)` | 原AuthorDelta、候选/Need；展开语义调用准确kernel/库方法 |
| kernel protocol + identity | `openSnapshot(manifest, contentSet)` | 受保护局部handle或准确缺项；无ambient fs/Git/network补取 |
| semantics/query / kernel | `analyze(snapshot, roots, queryBudget)` | 语义摘要、实际读集、诊断和有限前沿；不写作者头 |
| semantics / kernel | `instantiateRequirements(snapshot, roots)` | 卫生的RequirementInstances与贡献关系；不按行业名猜含义 |
| realization / kernel | `resolveRealization(instances, methods, controls, target)` | 原RES的Decision/RealizationBinding或Needs；ImplementationBinding是其合法子类，不能另起选择者 |
| lowering/targets / kernel | `lowerTarget(snapshot, binding, target)` | 原COMP5—COMP7的TargetProgramPlan/贡献/完整产物；需要新选择回RES，不由后端改义 |
| query / kernel | `queryImpact(oldRef,newRef,scope)` | 有范围diff/read-set/影响；资源耗尽不缓存成无差异 |
| assurance / kernel | `deriveObligations(objects,templates)` | 准确Claim/ProofObligation；模板不PASS，纯直接满足不强造运行Binding |
| assurance + application / control | `planChecks(obligations,methods,evidence)` | 可复用依据、纯检查与外部ActionPlan；计划不直接执行 |
| execution / control | `prepareOperation(intent,authority,resources,preimage)` | 原准入/拒绝/已有操作与原因；不得用编译结果授予权限 |
| execution / control | `runAttempt(operationRef,providerBinding)` | 原Attempt及真实观察；不因timeout换效果identity盲重发 |
| execution / control | `reconcile(operationRef)` | 原效果/终局/协调/补偿/资源结算维度；不把当前值等同历史事实 |
| bootstrap / control | `createEngineImage(modules,providerFactories,targetFactories)` | ASM0—ASM6封存的静态准确image；当前健康/权限不入不可变方法表 |

调用链先以ProjectView固定作者输入，语义/实例化/选择保持原 **COMP0—COMP7** 和 **RES**，不引入REQ0/REQ1、第二RES枚举或COMP8/COMP9。工具构建/check/readback在请求需要时走application→Execution→Provider→Evidence；没有真实工具结果时保留该层未知，不生成TODO/panic占位源码冒充完整Target。

<a id="provider-bootstrap-interface"></a>
## Provider描述、观察与调用

ProviderDescriptor沿原Method/Capability合同汇合 `providerRef`、`capabilityDefinitions`、`supportedMethodRefs`、`targetProfiles`、真实静态限制和协议修订；这些是静态声明关系，不是可随意执行字符串的shell。现有 ProviderSession 持有实例/认证/资源寿命，不能与descriptor合并。

`probe(context)`取得有范围/时点/方法的CapabilityObservation；`prepare(plan,grant,budget)`核当前准入与资源，若准备本身有副作用也归原Operation而非假纯预检；`execute(prepared,operationIdentity)`进入原Attempt；`observe(attempt)`产生原Observation/Receipt或取得缺项；`cancel(attempt,basis)`只记录实际取消观察；`close(use)`关闭新入口并结算真实占用。具体各端口结果保留原公共代数和未知/部分/清理状态，不被这个方法表重命名成简单成功/失败。

bootstrap仅从已允许模块/包/隔离Provider协商取得准确内容，在ASM2验证结构、语义、来源/兼容与实际实现，ASM4封存候选索引。新descriptor形成新image；健康、在线、剩余额度、当前权限和信任更新由执行时观察。没有权威读回/去重/事务能力就声明缺项或准确较弱保证；probe成功和prepare成功都不签发exactly-once或效果已发生。

<a id="implementation-dependency-route"></a>
## 实施依赖路线与未取得的现实证据

P0先读取真实仓库并映射十职责/文件/消费者状态，固定核心机器合同、decoder/validator/codegen和原有迁移向量。P1先完成headless纵切：control捕获→Rust worker固定分析/实现选择→TS目标贡献→准确工具链build/check/readback→六工具及按需本地恢复。P2并行接入纯意图投影与首批Identity/Persistence/API/Messaging/Workflow/Security/UI/Search/Audit配方；它们的设计不必等待P1编码完成，真实支持按实际链路取得证据。

P3由Code-OSS Extension消费同一六工具，Graph mutation逐操作通过readiness再开放。P4扩展独立Rust目标、原生/存储/消息/工作流/检索Provider并取得fault/security/performance/migration证据。P5实现和资格化学习/因果/安全等可选方法；其设计合同已独立存在，不以“实现较后”把正确设计退回未定义。仿真/几何/媒体/设备继续库/Provider扩展，只有真正公共不变量不足才演进Kernel。

上述依赖不是每次任务必须顺序运行的流水线，不授权此设计包执行实现或部署。I类缺项的真实资格仍包括strict reader、迁移、TS/Rust目标、Workbench、native/config adapter、工具与Provider版本、跨节点存储、CI供应链、冷暖/增量/高基数/内存包络、故障恢复/安全隔离和多域组合。用[实现映射](架构到实现追踪与代码落位.md)和[符合性](../../60-保证与证据/验收/意图覆盖与纵向符合性.md)记录准确代码/证据，不把路径已设计提升成它们已存在。

<a id="runtime-state-ownership"></a>
## 项目文件、运行对象与本地恢复的接缝

`gift.project.json`拥有项目身份、源范围、模块和输出根；`gift.lock.json`拥有已采用的准确解释/库/方法/依赖绑定，编译结果内的新选择值不自动写回锁。结构作者源、可选`.gift`、原生源码和资产按各自区域拥有事实，不按文件扩展名推断相互镜像。`.gift/cache/`只可保存具合格重建依据的派生项；恢复记录、当前头和不可重新取得的依据不能放入“可删缓存”。

RuntimeHandle拥有已装配工厂、真实资源池、所引用EngineImage及按需控制存储，不能成为作者当前头、编辑器草稿或产品业务状态的第二写者。EngineImage封存准确静态descriptor；ProjectView固定工程/锁/源/缓冲及修订；PreparedJob再固定用途、候选、已绑定输出根/目标、预算和明确输入；KernelSession只持有不可变snapshot和查询依赖/占用。Operation则保留实际效果意图、前像、当前准入、预留、尝试与结算。这些是既有对象的责任投影，不能由同一个session ID互换它们的身份、权限或寿命。

本机跨重启恢复默认仍是原[小型恢复画像](../../50-执行运行与观测/持久化与恢复/事务提交-任务合同与事务读回.md)：`.gift/state/control.sqlite`及所需内容库；`meta/generations/operations/files/events`五类记录的具体职责、同库小载荷和真实事务沿该owner，不复制第二份SQL真源。短纯查询完全内存，不必建立该库；多机一致性要求另选具资格Provider，不能把本机默认当多节点承诺。Catalog/Occurrence允许可丢弃缓存，不得拥有另一份可写意图DB；实际业务产品自己的数据库是合法外部owner，不受这个禁止竞争写者规则误伤。

## 数据合同生命周期：Schema 作者源、解析器、投影与消费者一次归属

任何外露机器协议必须固定 `schemaId + revision + strict decoder + compatibilityPolicy + producer + consumers + trustBoundary`；不能只写一段 JSON 示例后让多个运行时分别自由解释。机器 Schema 是对应原 owner 下的一份事实；语言绑定/CLI 文档/示例是生成物或有显式校验关系的投影，不在不同模块各自手填另一套同名真值。

1. `contracts` 保存唯一的机器形状和字段类型/枚举/版本策略；对已知 schema 中的未知**必要**字段拒绝或保留为受限 opaque，不能静默删掉影响权限、效果或身份的字段。JSON 等交换媒介不自动成为 Gift 作者源形态。
2. `workspace` 消费并绑定真实作者源和 SourceProfile；`semantics` 决定类型/作用/约束；`compiler` 产出 Artifact 绑定；`assurance` 产生对应 Claim/Evidence；`execution` 执行真实外部作用；`entry` 仅适配承载协议。两个模块碰巧接受相同字段名不取得互相取代的写权。
3. codec 的 conformance 包括正例、丢必需字段、重字段/同形不同义、未知版本、旧新版 round-trip、恶意路径/大输入、不同语言解释一致与配置变化。对最小公开字段 `schemaId,subjectRef,basis,status,coverage,diagnostics` 仍必须逐操作声明具体可选性，不强制所有纯函数产生费用/恢复字段。
4. 机器结构的调整先由唯一 owner 修改，再更新派生消费者与版本迁移；运行中的旧消息依原 schema/version 读回，不能用新的默认值反解释过去的 Effect。没有真实生产者或真实消费者的提案保留为候选，不因为写了 schema 就宣称接口已采用。

这一规则尤其适用于 library extension、六工具请求、持久问题引用、Source Program Transition Assessment 和 Provider adapter。物理目录与 TS/Rust crate 分配继续按现有蓝图，不为上述规范另生一个“超级合同执行进程”。

<a id="gift-machine-envelope-closure"></a>
## 主进程、内核和目标后端的最小可互操作 Envelope

每条跨进程/语言消息采用 `WireEnvelope{family,version,requestId,sessionRef,purpose,method,subjectRefs,sourceBasis,capabilityBasis,deadlineOrBudget,payloadEncoding,payloadDigest}`。Response 中必须带 `status,actualProducerRevision,consumedBasis,readSetOrNeed,diagnostics,artifactRefs,operationRefs,evidenceRefs` 的相交字段，并显式区分 `VALUE`、`NEEDS_INPUT`、`UNSUPPORTED`、`INVALID`、`STALE_BASIS`、`CANCELLED` 与 `FAILURE/UNKNOWN_EFFECT`。大载荷使用受控不可变 Blob 引用时，单独验证大小、摘要、租户/会话访问与寿命；不把任意路径注入内核读取权限。

协议协商固定 `family/version/requiredFeatures/offeredFeatures/selectedFeatures/peerIdentity`，忽略未知可选字段只在其不会改变语义与权限时允许；必需效果、授权或幂等字段缺失就拒绝，不进行隐式降级。Rust纯内核只处理固定语义值与派生计算；TS控制层对来源、工作区、真实 operation/资源/授权保持当前 owner。重复请求根据方法区分纯查询可复用与外部效果必须带原 Operation Identity，RPC超时不代表外部没有发生。

内部工程可选择单进程函数调用并复用同一逻辑类型合同，不要求每次都序列化 JSON；持久跨版本对象必须由严格 codec 解码，不能用 TypeScript 类型声明代替运行时校验。每个机器合同记录版本迁移、字段级拒绝、溢出/资源预算、背压和关闭行为，最低验证包含旧/新客户端协商、错误字段、取消与迟到回执、部分结果及内容校验失败。

## 实施起点：三个相互正交的层次视角与可实际编码的纵向切片

本节负责**已选源码蓝图怎样按依赖实施**；它不把内部阶段、产品任务和文件夹混同成同一“分层”，也不重新定义[十个模块的端口、依赖和写权](模块与运行实例.md)。开发者并无需先在自己的工程按下面路径手工建十个文件夹；下面是Gift实现者的源码放置责任。

### 读图时首先分清三套不同分层

| 视角 | 组成 | 用途与强制边界 |
|---|---|---|
| 语义因果 L0—L6 | L0 Source / L1 Semantics / L2 Realization / L3 Target / L4 Effect / L5 Observation / L6 Assurance | 解释一个结论依赖哪些先前事实；不代表七层都要对每个请求调用一次，也不表示七个仓库目录。纯preview可在L3结束，check方法可能只需L1或L6。 |
| 十逻辑职责模块 | `contracts / workspace / semantics / compiler / assurance / application / execution / adapters / entry / bootstrap` | 唯一owner、可依赖Port、事务写权和寿命，不能让`entry`直接实现第二份语义/编译器，也不能让`compiler`实际写工作树。 |
| 两侧部署与物理语言 | `control/` TypeScript+Bun运行时、`kernel/` Rust纯计算、`schema/`共同机器合同、`providers/`受控适配、`conformance/`验收、`benchmarks/`实测 | 是实现部署选择，不创造TS语义层与Rust语义层两个事实。Code-OSS Extension在Node Host，不和Bun混同。 |

### 对外契约与内部owner的唯一责任

| 请求进来后要发生什么 | 首个负责者与内部职责 | 纯/作用分界与传递对象 | 最小拒绝条件 |
|---|---|---|---|
| 解析用户当前请求、CLI/AI/IDE协议 | `entry`严格decode→`application`按请求用途编排 | Context/Request，不取得默认磁盘写权 | 未知协议版本、union重叠、未协商能力 |
| 真实项目/缓冲/模块/锁/原生资产快照 | `workspace` SourceProfile、ProjectView、解析锁与CurrentHead | 只读`CapturedSource`/不可变Snapshot与准确Coverage；保存另经execution | 读取范围外、非唯一source owner、捕获中前像变化 |
| 模块类型、能力、Requirement/Effect、准确引用 | `semantics`及Rust kernel已采用方法 | 已固定snapshot→`SemanticAssessment`或Needs/read-set | 未知必要dialect、未解析重载、预算中断或语义不完备 |
| 实现方法选择、Control与Target资格 | `compiler`编排RealizationResolver与已锁定供给 | `Decision/Binding/Eligibility`，不选许可 | Provider未实际支持、候选不合格、缺冻结目标 |
| 目标降低、代码字节、完整根与溯源 | `compiler`+`kernel` `target.lower`与真实TargetBackend | ArtifactSet/SourceMap/保持义务；生成默认不写出 | 缺目标规则、贡献冲突、部分根被误当完整 |
| 类型、案例、性质、当前保证证据 | `assurance`按已选method编排纯义务或真实执行结果 | Evidence精确绑定candidate/artifact/method/tool/env/basis | 没有执行该方法、旧证据错贴、虚报全面通过 |
| 保存作者源、写生成目标、调用工具、运行部署 | `application`构建ActionPlan，`execution`拥有Admission/Operation/Attempt，`adapters/providers`做具体作用 | **只有在当前Grant与前像成立后**Effect及实际readback | 权限撤销、并发前像冲突、tool缺失、效果未知 |
| 重启、继续、退出、回滚 | `execution`原持久owner与`bootstrap`寿命管理 | 恢复旧operationRef/仍欠义务，工作窗口只订阅 | 旧写者复活、无真实回执、试图新ID重放未知Effect |

上述名字是现有Owner的**接口意图**，不是新增一组强制全局TypeScript方法；机器字段、对象Ref与错误联合由已有Schema唯一拥有。工程实现必须从该表逐项建立真实Symbol→owner→consumer的映射；映射未回读仓库时不能声称现有代码已满足。

### TS/Bun 控制层、Rust 内核与真实目标代码是三种东西

1. **TypeScript/Bun control**接收CLI/SDK/AI/Workbench请求，固定SourceProfile/Workspace/EngineImage；保留当前授权与Provider目录；持久Operation和效果恢复；展示状态及调度。在纯计算阶段不能偷偷生成与Rust并行的可写语义IR。TS控制层本身使用TS，不代表生成的程序必须是TS。
2. **Rust kernel**只消费经真实codec验证并固定的内容、Snapshot/Binding/目标描述，运行类型/语义/增量查询/实现解析/目标降低/纯保证。除受信bootstrap启动受管进程外，不应从Rust纯方法直接读取任意工作区路径、联网、安装依赖、部署或决定UserGrant。
3. **TypeScript Target Backend**是把合格中立语义/实现贡献降低为用户项目的TS/JS/声明/源图/元数据等实际ArtifactSet的编译后端；它可以用Rust实现生成规则，也可以有经准确资格登记的外部真实Target工具链参与效果/检查，但不应被“TS control已经会运行”冒充已经实现。
4. **Rust Target Backend**是另一种用户目标，不能因为Gift编译器用Rust就判为已支持。是否包含本机ABI、所有权、panic/async/unsafe、平台工具链等由其真实TargetProfile核验。
5. **Provider和原生工具**是外部资源/宿主能力：Bun/tsc/node/Git/文件/部署服务按需要、权限和真实工具版本取得，而不是把所有事情塞入Rust kernel后声称可跨环境复现。

### 从第一次真实预览到第二次修订的最短可交付垂直切片

本节的`S0–S9`是**实施计划的局部切片编号**，限定定位为`implementation:S0`…`implementation:S9`，不是[跨阶段编译/现实作用合同](../工程构造手册/28-抽象到业务系统-统一实施闭包.md#gift121-stable-end-to-end-compiler-contract)的`stage:S0`…`stage:S8`。同一标签仅在本节确定项目施工顺序；不能把实施切片的验收与正式编译阶段的资格自动合并。旧编号不直接改写，以保全历史接口、锚点和引用。


| 切片 | 最小交付物与可调接口 | 对外应该证明的行为 | 本阶段不要求提前实现 |
|---|---|---|---|
| S0：仓库/Schema落位 | 在实际代码仓库确定所有owner的现存位置、依赖图及严格`gift.ai-tools/2`/worker协议合同源；机器Schema经生成给TS与Rust | 双端严格解码同一union、未知必要字段拒绝、版本协商一致 | 完整Graph、完整行业库、分布式runtime |
| S1：仅源捕获 | `workspace`实现原生/结构/文本source profile捕获、快照、诊断和源覆盖 | 一个无需`gift.project.json`的短源能形成Candidate；已有TS可只读解释，不被复制成Gift源 | 强制新建项目或运行外部命令 |
| S2：纯内核最小语义 | Rust library与`gift-kernel` worker受管启动、hello、content.put、snapshot.open、semantic.analyze；一种真实最小`gift.semantic/1`函数语义 | Int乘法有可解释类型/引用、语义错误返回诊断；不打开宿主文件、不擅自读网络 | 全泛型/宏/状态机/多Target或AI |
| S3：真实TS目标 | realisation.resolve + target.lower 到TypeScript完整所选函数根，实际目标profile固定布局/依赖/工具版本 | `gift.preview`返回真正代码字节、ArtifactRef、准确输入依据与SourceMap；用户可直接消费所需输出 | `gift.apply`或`tsc`作为纯preview的副作用 |
| S4：二次修订/差异 | `gift.propose(base,edits)`，增量失效，preview compareTo | C1/A1及C2/A2并存；差异正确；检查结果没有跨修订传播；旧引擎句柄不复活 | 打开完整Workbench或持久Runtime |
| S5：相交类型与案例检查 | `gift.check`，按method区分纯语义证明与需要真实TS消费者的工具运行 | 同一A2目标被所选已安装工具实际类型/案例检查；缺工具为Needs/Unsupported，不能返回绿色 | 全球所有Assurance方法或发布资格 |
| S6：源/目标显式应用 | 当前Grant、前像、write-set、requestId与`gift.apply`两种合法mode及完整写入读回 | 不写盘直到明确调用；冲突无覆盖；多文件失败后状态可恢复/可报告；不自动Git commit | 生产云部署、全部持久化模型 |
| S7：已准入运行与恢复 | `gift.operation`现有base和经协商compute-run，具体Provider及本地原Operation存储 | 明确`run`/`cancel`/`status`并取得真实进程/退出和可重复核账；取消不改历史 | 未授权远端运行、分布式强一致承诺 |
| S8：三个客户端 | 同一CLI/SDK/AI工具；Workbench薄Adapter具真实Review/Needs/Operations | 相同请求不同客户端产生相同逻辑candidate/artifact/operation条件，且错误状态一致 | 每个视图独立一套解析/迁移层 |
| S9：拓展与正式资格 | Rust目标、复合行业标准模块、增量并行/远端、运行安全/性能、供应链、自举 | 按条件能力逐项证明，不用首条Int函数成功扩张所有产品Claim | 一步到位承诺世界所有软件类型 |

每个切片只依赖上一阶段**实际使用到的公共契约**，而不是先实现整个通用语言/所有Provider。后续阶段可以并行做独立Owner，但任何公共机器Schema的consumer必须同时对齐；不能以“工作在不同分支”规避类型与状态一致性。对尚未具备的Target/Provider能力以真实`UNSUPPORTED/NEEDS_INPUT`合法退化，不能造stub成功。

### 真正的层间调用和一次请求结束

```text
Host Context + ToolRequest (strict schema, scoped capability)
  → entry.decode (no write, no resolver guess)
  → application.prepare (purpose, EngineImage, SourceProfile, candidate/target binding)
  → workspace.capture [host read with real scope + immutable source bytes + read-set]
  → kernel hello / content.put / snapshot.open [no filesystem privilege]
  → kernel semantic.analyze -> realization.resolve -> target.lower [batchable pure compute]
  → compiler ArtifactSet + layout + origin + exact basis (or Needs/Invalid/Partial)
  → application returns gift.preview projection [NO real effect, generated-unchecked]
optional separate request:
  → assurance.check [selected method, real target tool only via execution]
optional separate authorized request:
  → execution.admit(ActionPlan, current grant + source/output preimage)
  → persist Operation/Attempt -> adapter act -> readback/reconcile
  → application returns precise actual result/unknown/partial/recovery
```

这是**一条可能的调用依赖图**，不是七个永远执行的固定步骤。没有项目和外部检查时，短源preview从指定source直接固定内容即可；缺任何实现绑定时在对应节点生成Needs，后继外部Effect不发生。多个目标并行时分别保留根和结果，只有同时闭合已请求共同约束才给请求整体完成。worker失联只让尚未确认的纯计算请求需要按原Basis重试，不把外部效果标成未发生。

### 先实施时必须立即拒绝的“捷径”

- 在TypeScript CLI内用正则把`.gift`直接翻译成JS来冒充`SemanticAssessment/RealizationBinding`；这会形成第二语义编译器，导致真实规则/来源、扩展与Rust迁移无法保持。
- 为了简化Target，将空占位/生成TODO返回为完整可发行源码；没有真实实现供给时只能返回Needs/partial。
- 使用全局`currentProject/currentCandidate/latestArtifact/lastCheck/lastOperation`作为跨会话确定Ref，或将缓存键直接当授权凭证。
- 让Worker自己访问磁盘、Git、环境秘密或公网来补输入；必须由有权Host捕获、验证并固定内容后再进纯Kernel。
- 让`gift.apply`偷偷编译、测试、提交、push、发布或运行，或以`preview`偷偷落盘来方便IDE展示。
- 把Code-OSS Node Extension Host视作Bun control进程，或把控制层写TS当作已有TS Target。
- 把设计知识工具的41项通过/离线文档包的链接校验当成产品语言、内核、Target或用户工作台已实现的Evidence。

<a id="system-implementation-layer-placement-design-vs-product"></a>
## 通用设计投影在十个模块与 TS/Rust 物理边界中的准确落位

本次增补只完成设计，不改变十逻辑owner和现行TS/Bun、Rust、Code-OSS宿主的既定选择。其接口和责任映射如下；**工作台显示的目标 IDE 组件不应被放进 Gift 自身控制代码树**。

| 现有逻辑owner | 与设计阶段相交的真实生产/消费职责 | 绝不承担的额外职责 |
|---|---|---|
| `contracts` | 共同身份、消息/引用、机器字段、版本与严格解码；支撑 `gift.ai-tools/2`及原已定义交换合同 | 不再复制一份TargetProjectPlan作者Schema或第二套字段事实 |
| `workspace` | 原生/结构/文本的准确范围和revision，候选前像/单一writer、源保存 | 不以目录发现结果自动取得整个仓库写权 |
| `semantics` | 已绑定计算/系统语义解释、类型/效果/状态/协议、Requirement连接 | 不从一句高层意图臆造 Editor、远程服务的全部业务 |
| `compiler` | 纯增量分析、合法实现路径解析、目标计划/布局与明确缺项，未来源码降低 | 不写作者文件、运行目标程序或用真实效果凑编译成功 |
| `assurance` | 对设计完整性和运行证据分别生成准确评价义务/有限Verdict | 不用静态语义文档给未运行产品签现实保证 |
| `application` | 绑定一次用户目的/选中根/环境，把 query/propose/plan视图结果组装成请求范围的结果 | 不在客户端保存第二份工程真源 |
| `execution` | 只有被请求的保存/工具/运行/发布作用才取得有权Attempt和结算 | 不为design-only纯查询自动启动外部进程 |
| `adapters` | 原生源码、Provider、Target工具和Code-OSS宿主接口的真实翻译/兼容 | 不把目标工程VS Code扩展当Gift本身扩展实现 |
| `entry` | 六工具/CLI/AI/Workbench展示、协议协商及权限裁剪 | 不复制业务求值、实现选择、外部写权 |
| `bootstrap` | 准确image、已实际注册的方法/Provider/Target与运行装配 | 不把磁盘上有某个设计文件视为进程已加载/支持 |

**物理进程**： `control/` TypeScript/Bun负责用户请求、source捕获、授权、Operation编排和对宿主连接；`kernel/` Rust处理有明确输入和预算的纯计算、语义、解析、目标计划/生成；`schema/`是机器合同源，生成Rust/TS codec但不成为业务作者语言；`providers/`仅是真实外部适配；`conformance/`是实现后对准确Claim取证的工程。Code-OSS Extension运行在实际Node/Web/Remote Extension Host，与Bun control独立，通过已协商有界协议通信；Webview既没有kernel权威，也不能默认读取工作区全部秘密。

### 设计专用纯调用序列与失败闭包

```text
UI/CLI/AI 提出 design-only 请求
→ entry 校验当前 schema/披露权及请求限额
→ application 固定 Goal、ProductRoot、Source/Lock/Target Basis
→ workspace 返回真实作者内容和未观察/无权范围
→ semantics 解释已选对象，留出缺项/冲突
→ compiler 内部规划能力取得 Realization/Target/Layout 的派生结果
→ assurance 形成设计覆盖/相交限制（不是产品 PASS）
→ query/Workbench 显示 plan、Needs、Impact、owner、可继续编辑点
[STOP；没有 ArtifactSet、源保存、build/run/部署]
```

每一行是一次可能的依赖，不代表十个网络服务或十次IPC。单函数问答可在可满足目的的地方提前结束；已有原生工程可在不重写业务内容的前提下取得局部规划。发生 `NeedsInput` 时返回准确缺项并允许其他独立范围继续；SourceRev冲突只失效有关候选，不重置所有工作区；worker预算超限保留完整已知子结果但不冒称全局已判定；语义同值而引用依赖不同的结果不能按内容相同擅自复用。实现阶段的“第一条TS纵向链”仍是单独工作的工程，不能反向当作设计文档应运行 `tsc` 的义务。

### 接口冻结与变更证明

首期优先锁已描述的机器合同、基础作者语言语义、六工具v2和目标支持轮廓；新方言/Provider/Target按各自能力协商引入。当前设计中的未发布类型/示意 `TargetProjectPlan`只在有真实生产者、消费者、必须跨边界传输时才从现有派生接口提升为机器Schema；不可为了让文档看起来完整预建空类。若现有六工具未直接暴露工程蓝图的必要组合查询，先补现有 contract view 的实生产者/消费者，确需新的公开能力时按公开schema版本和兼容政策另行采纳，不能偷偷扩充同版读写合同。

## 十个逻辑Owner、设计机器合同与生产代码落位

<a id="runtime-owners-and-design-projections"></a>
### 同一责任链的物理实现与资料图谱的权限划分

十个逻辑Owner按状态写权和不可代签的资格区分，不与docs十个主题目录做一一映射：`contracts`拥有正式Wire/类型，`workspace`拥有Source/Profile/CAS，`semantics`拥有Meaning与Requirement解释，`compiler`拥有Method解析/纯降低，`assurance`拥有Claim/Evidence裁决接口，`application`只编排被授权的任务，`execution`拥有真实Grant/Operation/Attempt，`adapters`隔离Provider/工具链/原生能力，`entry`只适配CLI/SDK/AI/Workbench，`bootstrap`负责初始化与关闭顺序。某实现跨Owner调用必须通过有版本和错误语义的接口，不从同名目录或数据结构复用推导权限。

Rust生产内核处理固定输入下的可重复语义、求解与降低；TypeScript作为首个生成目标和可选接入端，不要求普通业务作者手写全部底层算法；实际外部输入与Effects必须通过有权宿主/Adapter进入固定Snapshot或Operation。`ArtifactSet`既不是其当前源码的另一个作者写源，也不能以“成功编译”获取Provider的实时读写权。语言实现可迁移，但合同Owner、权限/恢复/证据边界不随实现语言改变。

结构图、表格/编号索引及包外按需产生的文档导航是**只读知识投影**，不属于上述Rust编译器生产Consumer；不能把由Markdown扫描派生的边转入Method注册、Runtime授权或SourceMap。正式对外协议更新必须由contracts/schema有权生产者发行、实际Reader拒绝未知不兼容版本、消费者迁移及独立验收，不能因本章施工伪类型存在而宣布ABI已发布。


`contracts/`定义已采用Schema判别联合/版本、严格解码器和资格错误；`workspace/`冻结作者源/Lock/多文件提交；`semantics/`解析Rule观察与类型效果；`compiler/`解析Method、目标计划和产物贡献；`assurance/`管理证明义务与证据；`application/`协调六工具与只读蓝图；`execution/`建立Grant/Operation与恢复；`adapters/`拥有真实原生语言、工具链与Provider连接；`entry/`仅薄适配；`bootstrap/`装配受信实现。

`fixtures/contract-closure/Gift95/` 的Rule/Method/Target Schema是**尚未发布的独立字段方案及校验载荷**，不应直接硬编码为公开产品版本，也不代表新增四套状态机。当前设计编码由下文机器结构责任及 `schema/` 固定；正式产品发行前仍须在真实代码仓库完成跨语言严格decoder、版本协商、正反例与Target消费者比对，固定实际content/revision。设计定案不由尚无生产reader阻断，未实现reader也不因设计定案取得发布资格。

## 跨 Owner 读链的实测受限实例与责任落位

可复用的最小程序调用关系固定为：`workspace.captureProjectView` 读取 `gift.project.json`、`AuthorModule`、所有声明的 Native binding 作者选择和真实原生源；`semantics.instantiateRequirements` 绑定 `req:rule`、Occurrence 参数与解释 Profile；`compiler.resolveRealization` 用既有 Descriptor Solver 合取 Target/Profile/Method/Control；`adapters/native` 在受信 TypeScript 版本下读取公开符号与类型；`compiler/target` 仅在具资格的 Lowerer 存在时产生 `ArtifactSet`，否则给出计划/Need；`assurance` 独立取得声明范围和证据；`execution` 仅在有 Grant 时做外部作用及读回。不要把此逻辑序列变成新的强制六步 UI 或第二套实现选择状态机。

现有源码蓝图的生产迁移必须为每个阶段声明 `schemaId/revision/strict decoder/producer/consumers/source basis/negative dependencies/unknown-field policy`；未发布 Native binding selection 只能由当前受限消费者识别，不可在开放扩展中默默忽略。Rust kernel 不得根据收到的相对原生文件路径自行访问主机；TS workspace 解析路径、身份和权限，传不可变有界字节或受保护 Blob，Rust 做纯语义/类型与 Query 计算。实际 TypeScript SourceProfile Adapter 可以位于 TS 控制/Provider 边，只输出可审计的 SourceBindingResult 而不取得由编译器签发的 Grant；未来物理蓝图统一为 `control/src`、`kernel/src`、`kernel/src/targets/typescript`；`contracts/workspace/compiler/...` 是逻辑职责。已读取仓库的 `src/compiler` 等现状不因本地文档变更即被迁移。fixture 使用 Python+Node 不改变算法 owner；不再同时规定 `src/control`/`src/kernel` 为另一套未来布局。

样本的结构快照、ESM 控制、Method/Target Profile 接受性、TS 导出类型和内容摘要在 `fixtures/contract-closure/Gift96` 有真实读取/拒绝测试；仍无通用跨 TS/Rust 产品 codec、真实 Native Target lowering、线上 Provider、持久事务与外部效果恢复。只允许将该测试列为有限契约符合性证据，而非声明真实 `sec-platform/sec` 的当前主分支已采用这些接口。

### 原生 Compiler API 的实际读取能力不得越权 SourceScope

TypeScript SourceProfile Adapter 在类型检查之前先执行无副作用的源引用预扫描；普通 TS 的静态 import、类型 import、re-export、动态 import、三斜线声明引用会使编译器模块图扩展，实际 `ts.createProgram` 能读取比调用参数入口更多的文件。已明确授权的原生依赖可按固定条件递归读取，累计所有解析成功和解析未找到的负依赖，并由适配器严格传入受约束的 CompilerHost/SourceSnapshot；未知依赖不得让默认宿主自由从磁盘查找。有限 Gift96 不提供授权导入图，仅在完整 TS 解析之前拒绝这些语法，再核导出签名。它是机制性安全边界的一种演示，而不是生产沙箱：真实语言服务还须限制 symlink、路径大小写规范、工作空间内外根、生成声明、tsconfig 继承、Node 模块解析、插件和非协作路径替换。

## 自举源码实际依赖的标准库与内核接口闭包

### 最小标准库不是最小业务语言

以下是自举源码的公共库责任，不是 Kernel 必须穷举的业务操作，也不引入一套只有官方能用的作者语言。普通用户可定义相同类型/函数/模块；必要原始操作由精确 Profile 与合格 Method 供应，不能由用户写 `intrinsic:true` 创建权限或可信地位。各模块是否被当前自举根实际引用，由闭包分析决定。

| 责任 | 输入与结果的确定合同 | 最小方法及拒绝边界 |
|---|---|---|
| 字节与 UTF-8 | Bytes 的长度/取片；严格解码为 Text 或带精确字节位置的 DecodeError；不改原字节 | 解码拒绝非法序列与非标量；有界索引检查在访问前，不静默替换 |
| 精确整数与布尔 | 任意精度 Int 的算术/比较、既定向零商余；Bool 严格逻辑 | 零除/资源失败独立；不得用 JS Number 或 Rust debug 溢出习惯 |
| 序列与代数类型 | 不可变 List/Option/Result/记录/和类型，结构递归、map/fold/filter | 保持元素/回调次序；空序列与失败分开，tail 不要求反复复制 |
| 映射与集合 | 键的相等/比较或哈希合同，查找、加入、移除和确定的所需迭代投影 | 哈希布局私有；遍历顺序若影响输出，明确排序/逻辑顺序；不能假设宿主 hash 顺序稳定 |
| 标识与源码位置 | Definition/模块/发生位置的有类型身份，内容摘要与源 span | OID、内容 digest、revision、运行 handle 不互相转换；位置绑定源字节版本 |
| 图与工作表 | 显式节点/边、SCC、拓扑层及循环结果、待处理集合 | 自定义图节点不是数据库行；合法递归不拒绝，循环证据由真实边组成 |
| 类型与环境 | 种类、名义类型、绑定环境、替换、自由变量、有限统一工作表 | occurs/作用域检查；别名环、未知实例和预算未完成分开 |
| 诊断 | 稳定 code/严重性/参数/来源/关联位置和修复候选 | 修复候选不自动写源；机器类别与本地化文本分离 |
| 目标文档/成员 | 有结构的源码片段、稳定名字、导入与输出成员、SourceMap | 打印不能填补未解语义；普通输出独立于编译器内部 AST |
| 宿主桥 | 明确读取/启动/发布请求及结果；原 Worker/六工具/Operation | 纯分析返回数据/Need；文件、进程、网络与签名由有权控制面执行 |

这些责任可由若干普通库/模块共同实现，不要求一行对应一个 crate 或服务。所有库入口沿已有 Definition 与 Method 绑定，不建立新的 `std.*` 隐式全局可执行名字空间。公开身份和签名在库发布时固定；本表是责任和接口意义，不是假称当前已安装的标准库清单。

### 编译器职责与源依赖方向

源解码只依赖值/字节/定位与对应 SourceProfile；符号模块依赖已解码声明和可见域；类型/效果模块依赖固定声明环境；契约模块读取已检查类型及真实谓词/关系定义；方法解析读取固定目录和义务；目标模块消费实际所选方法和类型/效果；诊断与产物计划汇总这些纯结果。跨层共享值通过原公共合同，目标私有 AST 不倒灌成为前端类型真源。

循环通过精确模块 SCC 和声明/主体阶段处理，不把整个编译器强行分为相互独立的树。反射/生成器不得先依赖其尚未生成的消费者；自举所需源子集与 bridge 按确定性/自举规范建立。该依赖图是源码责任设计，不是已读取远端仓库的文件路径证明；真正迁移前取得当前真实 owner 映射。

### 机器合同一次归属

Schema、编解码器、文档投影与测试输入都从同一规范源派生或明确对应，派生物不反写第二权威。允许消费者手写最小可信解码器作独立检查，但其规则版本和差异必须明确，不能两个生成器相互以输出证明彼此语义正确。当前生产接口仍沿原 Envelope 与六工具，不因增加自举设计就新增公共命令、服务或工作流。

<a id="design-a04"></a>
## Rule、Method、Target 的唯一机器结构来源

机器结构归 `schema/` 的协议文件，含义归对应规范，生成类型只读；不让 fixture、文档示意JSON和TS/Rust各自拥有可独立演进的一套字段。Gift95四份proposal保留原字节作为历史设计样本；任何生产reader不能只凭文件名或类似schema URI接纳它们。

Rule 的稳定对象是 Definition 中的规则体，含输入字段类型、允许的require/prefer模式、语义Profile及其观察合同、所需实现能力。Method供给只绑定被实现的Definition、输入域/假设、目标/ABI/效果/进展、资格义务和实际实现引用；实现描述不是作者 Requirement 的第二份可变副本。Target只规定接受构造、表示、完整降低、成员/构建/运行条件和必须提供的证据，不写用户需求或自动执行授权。

本次为 Requirement组合、controls分片、CallObservation、Method供给、Target、原生选择与六工具参数/协商结果视图给出受限结构schema和语义附加约束。结构层中的Definition引用严格区分作者词法引用与已解析模块导出引用，不能把二者无差别合并。`format/default/content*` 不承担授权、默认值求值、远程存在性或代码执行；协议消费者在结构通过后仍必须解析引用、核对相位、精确类型、语义与实际供应。

schema身份和语义解释映像以精确内容摘要锁定。相同短版本号下内容不同不得缓存为同一协议。未知键拒绝解释并保留源字节；只有明确声明的扩展槽容纳具命名空间且受锁定的扩展。结构不变但观察含义改变仍为语义不兼容，需要新Profile身份/迁移，不靠提升实现小版本偷换。

历史 `qualification-envelope` 的 `STATIC_DESIGN_FIXTURE` 只属于测试记录，不成为产品资格协议。新的审查工具也只能输出自己的结构/有限模型检验结果；不能借 `verified` 布尔、脚本成功或文件摘要给Method发全局资格。

**验证与反例**：逐字段责任表、协议shape与semantic-validator的边界在本节和schema目录说明对应；未知版本、错误引用域和静态fixture冒充产品证据均拒绝。

**实际能力边界**：跨语言生产codec和正式发行仍需独立对照；本次发布的是设计材料及可运行结构审查。

<a id="design-a10"></a>
## 首个标准库与自举计算闭包

第一套标准库按普通模块发布，不在Kernel增加业务特权。源模块逻辑身份选 `gift.std.core`、`gift.std.collections`、`gift.std.text`、`gift.std.graph`；短名字不是可信发行身份，实际ModuleId/revision/digest在发布时由真实源捕获，不能用本文示意字符串充当已签版本。导入可以用别名，公开Definition身份升级按原协议。

core固定 `Bool/Int/Text/Unit`、`Option<T> = None | Some(T)`、`Result<T,E> = Ok(T) | Err(E)`、`Ordering = Less | Equal | Greater`、pair及用户名义record/sum。Int为精确整数；`divRemTrunc(a,b)`在b=0返回DivisionByZero，否则满足a=q*b+r、|r|<|b|且r为0或与a同号。Euclidean除法是独立函数，不能改旧div/rem。`checkedToBounded`返回OutOfRange，不截断；`Text.fromUtf8(bytes)`严格返回MalformedUtf8，不以替换字符掩盖源损坏。

collections固定 `List.empty/cons/length/get/map/filter/foldLeft/concat`，get返回Option；map/filter/foldLeft左至右，闭包错误/效果原样传播，不能重复调用谓词。Map/Set参数必须提供一致的equality；hash型方法还需要equal⇒相同hash，不把哈希相同当相等。迭代顺序要么公开稳定插入序，要么明确unspecified并要求输出排序，不能由当前HashMap偶然行为决定。`Map.lookup/insert/remove/entries`、`Set.insert/contains`、`Queue.push/pop`、`MinQueue.insert/popMin`都明确空结果和更新后的拥有权；不要求业务作者选择其树/哈希内部实现。

text提供unicodeScalar与UTF-8字节、UTF-16码元坐标的显式转换，越界和落在编码单元中间返回错误；语言Text默认码点语义，兼容旧清单ID排序显式调用 `compareUtf16CodeUnits`，不能偷换成localeCompare或默认标量比较。类型为普通Text不代表所有排序等价。

graph提供 `topologicalOrder(nodes,edges,compare)`→`Ordered | Blocked`、`stronglyConnectedComponents`、`reachablePath`；节点名义身份和相等比较由参数传入，Blocked中的未调度节点不是全部环节点的证明。首个清单解析器另以普通领域类型定义ManifestEntry、ProviderIndex、ResolveError和kindRank；库不预装任何业务清单种类。图算法在有界宿主资源下返回ResourceIncomplete，不把分配失败说成无环或无路。

自举所需源API闭包由实际callee/constructor/type/codec/比较器/错误/Target support边递归收集；不只扫描函数名。每个必要符号登记实现Method、Target表示、终止/错误观察与依赖；缺一项准确阻断相交根。标准库发布可以分模块，无需为用List的纯函数载入网络、数据库或证明器。

**验证与反例**：以A09真实算法需求核集合、比较器、结果、队列和名义输入；以泛型map/filter与type-tree occurs补高阶/递归边界；版本升级后重新核源闭包及方法资格。

### G0—G7 与真实消费者之间的接口闭合、失败传播和源码质量准入

以下是**生产实现必须满足的接口设计约束**，按前文既有 owner、`SourceCarrier / ModuleElaboration / BoundRoot / RealizationPlan / ArtifactSet / Operation / Claim` 责任分配，不另发布 `gift.workflow-stage/1`、第七个公开工具、第二套可写 IR，亦不将 Gift103 fixture 的 `cd:*` 方言作为正式内核语法。下文签名是**类型与消费行为草案**，并非声称当前 TS/Rust 仓库中已有同名接口；正式落位需复核现有机器 Schema/公开六工具后协同冻结。

#### A. 源头精度：源字节、意义、解析资格、目标及现实修订五者不可混用

| 身份/依赖 | 真实生产者 | 应当精确包含的材料 | 必须失效的情形 | 不应失效的情形 |
|---|---|---|---|---|
| `SourceSnapshotRef` | 有权限的 `workspace` reader | 作者范围、各路径实际字节摘要、Symlink/大小写规范化、导入闭包、读取失败和负查找、冻结时间和权限范围 | 某个被实际消费的作者文件/依赖或其作用域权限改变 | 无关工程文件改变 |
| `SemanticImageRef` | 已绑定且已锁定的 `semantics` reader | 源中被接受的 Definition/Use、精确方言解释器版本/字节、所有会改变语义的 import/约束、跨域作用关系和决定性配置 | 政策规则、观察发行者、事实适用域、状态/效果含义、方言实现或依赖语义改变 | 纯显示名、格式/对象键顺序变化，**仅当**该语义解析器明确证明不影响语义 |
| `RealizationBindingRef` | `compiler` Method 解析 | 完整硬约束、候选方法和资格版本、TargetProfile、环境及其否定依赖、被满足/剩余义务 | 新候选资格影响选择、已选方法撤销/改动、目标 ABI/Toolchain 变化 | 仅作者排版变化且资格与含义不变 |
| `ArtifactSetRef` | 有资格 Target Backend | 目标成员的相对路径、完整字节/摘要、TargetProfile、可追溯 SourceMap、未闭合目标检查义务 | 发射方法、所选实现、目标源码字节、工具链/布局条件改变 | 仅没有被发射消费的研究解释变动 |
| `OperationRef / EvidenceRef` | `execution`/独立 `assurance` | 当前 Grant、真实前像、原子边界、Attempt、实际读回、证据资格和有效期 | Grant撤销、前像变化、现实效果未决、已测 Artifact/Target/Env 差异、证据过期 | 仅在无实际依赖时的无关作者文字变化 |

`SourceSnapshot` 的内容摘要是**原始输入事实**；`SemanticImage` 的语义摘要是**特定解释器及实际导入读集下的派生判断**。不能只对 JSON 删除空格求 hash 就声称意义相等：语义保持需要当前语言语义和有关消费者有资格支持。缓存记录还需要输入及**负依赖**（例如某候选原来不存在）和引擎资格；两份内容不同的源可以产生相同语义，但用于恢复、授权或审计的原始源不能由语义摘要代替。

#### B. 公共读链：不把跨域语义压扁成 `boolean`

严格维持以下逻辑端口（类型字段示意、与现有机器合同编码对齐后才能成为公开 API）：

```typescript
// DESIGN ONLY — existing owners own concrete machine codecs and status unions.
type ScopedRead = {
  frozenSource: "immutable-author-bytes-and-identity";
  readSet: "positive-and-negative-dependency-set";
  authorityScope: "authorized-source-read-scope";
};
type Elaborated = {
  semanticImage: "qualified-and-bound-semantic-image";
  obligations: "typed-local-and-cross-domain-obligations";
  missing: "bounded-needs-by-subject-and-owner";
};
type Joined = {
  assumptions: "per-port-and-environment-assumptions";
  guarantees: "safety-progress-time-resource-effect-obligations";
  contradiction: "subject-scoped-conflict-or-none";
};
type ImplementationPlan = {
  eligibleMethods: "real-candidates-with-evidence-and-cost-basis";
  excludedMethods: "candidate-and-specific-rejection-reason";
  target: "qualified-target-profile-and-environment";
  unresolved: "required-capability-or-evidence-needs";
};
// No host effects until a separately authorized operation is admitted.
```

1. `workspace` 使用用户授权的 `SourceProfile` 冻结**完整**所需读集；无法读取的子依赖成为 `Need`，不能被空集合冒充。Kernel不得自行打开 Host 路径。
2. `semantics` 逐方言做严格 decode、版本协商、符号解析和有界解释；未知方言返回 `UnsupportedInterpreter`，不能借名称映射到附近的`compute`。
3. `semantics` 联合 Policy、State、Observation、Time、Resource、Effect 的实际主体、作用域和可观察结果；需要互相满足的假设列成 Join obligation。开放来源/冲突证据不默选真假。
4. `compiler` 按 Method / Target / Env 与**硬**约束合取后过滤，soft preference 只排序仍合格者；负依赖入选择 Basis。不可实现返回 `Need(Method/Target/Provider)`，不得返回空函数或 `TODO` 充作成功。
5. `target` 只用已绑定语义和实现生成全部受请求根，产出有真实字节的 `ArtifactSet`/SourceMap；无资格的部分可标 `Partial` 但必须列出尚欠的根和义务。
6. `assurance` 将具体类型、安全、时间、性能、故障恢复义务路由到各自合适的 checker/真实环境；**只有确实执行**的检查才能产生对应 `Evidence`。
7. `execution` 保存作者变更、对目标工作区应用/编译/运行以及联系外部 Provider **都是分离的被授权操作**；纯预览、分析和规划不给写权。

#### C. 同一跨域意图的联合保证如何成立

以“支付后预留库存”为例，足够的联合要求不是 `payment=true ∧ policy=true ∧ state=paid`。必须至少保存：支付主体/金额/订单/操作对应关系，第三方支付最终确认的可追溯观察及撤回规则；当前主体对目标资源的**有效授权**；合法状态边与最新读版本；库存扣减的非负/互斥/可线性化或明确的补偿语义；外部动作的幂等范围与真实状态读回。任一缺项只能产生 `Needs/Plan/Inconclusive`，不能伪造 `Completed`。

数据库与第三方系统不共享事务时，不能笼统声称 Exactly Once。合法方案包括：限定数据库本地原子写、持久 outbox、唯一操作身份与外部 Provider 的重试/查询/补偿协议；若 Provider 无可验证幂等或状态读回，超时后效果可能未知，应阻断新身份重复执行并保留人工或授权恢复路径。强一致、最终一致和补偿是**不同保证**，由领域需求与真实供给资格共同确定，不靠自动选择一个听起来更快的方法。

#### D. ActionPlan 与多文件写入的最小可恢复合同

- 作者保存/目标写入须先对全部受管成员取**逐文件前像**，在命令明确授权的根内有明确 `writeSet/deleteSet`、冲突策略与 symlink/目录逃逸拒绝；生成器不会自行覆盖人工编辑。
- 一个 operation 的身份与其 intent、base/source revision、资格和效果目标绑定；重试沿用身份，不能以“上次超时”擅自生成新 ID。`Attempt` 状态须可区分准备、已准入、执行中、已确认、确认失败、**可能已生效**及待核账。
- 本地同一文件系统允许使用有资格的持久 staging/journal 与原子 rename/可追溯 recovery；跨多个文件的可见性仍需明确 commit/reader 规则，不能因为逐文件 rename 原子就冒充多文件事务原子。
- 对远端 API、支付、云存储或硬件效果，必须建立真实外部 Result / Readback / Reconcile，不能用本地文件回滚代替外部撤销。
- `apply` 的完成不自动授权执行 `build/test/run/commit/push/deploy`。Toolchain 检查的来源、版本、权限、执行历史和费用应独立于 ArtifactSet 记录。

#### E. G6 实际保证矩阵：不同义务需要不同独立证据

| 保证种类 | 能够验收的检查与环境 | 不成立的推断 |
|---|---|---|
| 作者源码和身份 | 稳定标识、路径闭包、导入/负依赖、歧义/权限拒绝、哈希复算 | 一份 JSON 能解析 = 正确业务 |
| 语义与跨域组合 | 真正解释器正反例、等价保持、状态/权限/时间/Effect 联合不变量 | `tsc` 无错误 = 业务安全 |
| 目标代码 | 锁定编译器构建、真实生成源码/声明/依赖、目标工具链类型与行为复测 | 生成了 `.ts` = 已上线 |
| 实现方法选择 | 硬约束充分性、真实 Method 资格/Target 供给、替换对照、资源与成本依据 | 选择了两种 Lowering = 世界最快或最优 |
| 多文件与并发 | 两个写者前像竞争、崩溃后 journal 重放、恶意路径/链接、失效传播 | 单进程锁+一次成功 = 多进程安全 |
| 现实作用与恢复 | 授权撤销、真实 Provider 假失败/真实成功、重入、超时未定、崩溃恢复、外部读回 | 本地模拟授权 = 现实 Grant |
| 运行资源与安全 | 给定目标、负载、环境的 CPU/内存/延迟分布及最坏时限、输入攻击与依赖失效 | 演示性几十项单测 = 高并发与无漏洞 |
| 独立保证 | 明确 Claim，消费者绑定 Evidence / 版本 / 时间 / 环境 / 适用域 | 将测试总数累计 = 全域资格 |

#### F. G7 变更演进的具体传播而不是整包无效化

- **显示名/JSON 成员次序变更**：仍保存新源字节身份；仅在有资格的同一语义解释器证明等价时，原纯语义结果可复用，目标/证据按真实依赖判定。
- **政策、观察发行者、状态边、效果含义变化**：失效相交 `SemanticImage`、联合义务、Method资格、计划、相关生成源码与旧 CheckBasis；已执行的现实 Operation 不会因为源码回滚消失。
- **目标 Profile/Toolchain/ABI/Method版本变化**：语义可不变，但已选实现、生成目标、类型检查/性能证据必须逐项失效与重新资格。
- **Grant 被撤销、环境/Provider状态变化**：纯源码与语义不必失效，但新的外部准入不得复用旧权限；效果未定的操作先执行真实 reconciliation。
- **新增领域 Definition 但缺 Interpreter/Method**：保留完整作者输入及已知上下文，在该点返回 `Need`；不要求对不相交的其他业务根重新编译，也不允许自行合成不存在的 Provider。

上述规则把G0—G7的**工作门槛**映射到既有消费者。Gift103的真实局部代码与对照测试只证明**两套跨域作者语义经有限解释器生成纯候选计划**；没有实现这些生产 Owner 的全部合同。具体剩余范围必须随真实产品代码和证据逐项关闭，不能随文档发布自动迁为“已实现”。
