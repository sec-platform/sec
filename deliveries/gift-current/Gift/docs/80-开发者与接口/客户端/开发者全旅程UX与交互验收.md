# Gift 开发者全旅程 UX 与交互验收

本篇拥有人类使用者贯穿一次工作的体验与结果交接，消费现行语义、六工具、作者写权、候选身份、权限和执行状态。它是待实施的 UX 合同；历史交互原型及其内置数据不能证明 Extension、Runtime、Target 或目标工程已经实现，原型也不是本包的交付前置。

## 0. 责任边界、继承事实和判定方法

进入页面或 API 前，用户实际写的是[统一源码工程与多表示作者协议](../../10-作者与输入/作者源/工程源/统一源码工程与多表示作者协议.md)中的 JSON/原生/可选文本。**UX 是对这些真实文件的编辑和阅读投影，不是另一种源语言；Rust SDK 同样属于一个候选生成入口。**

- 布局、五视图、Inspector、状态栏、宿主放置：由 [工作台布局与交互](工作台布局与交互.md#final-workbench-layout) 拥有；本篇只能引用、编排和验收。
- 客户端壳与技术边界：由 [客户端产品与适配边界](客户端产品与适配边界.md#human-workbench-product-selection) 拥有，第一人类客户端为 **VS Code / Code-OSS 扩展**。宿主已有的编辑器、Explorer、SCM、Terminal、Testing、Run/Debug 不重复创建。
- 决策的含义、唯一可写 owner、五阶段投影：由 [开发面与智能投影](开发面与智能投影.md#developer-decision-view) 和 [开发者决策模型](../../20-语义与组合/作者语义/开发者决策模型与设定面.md) 拥有。
- 请求及效果：由 [六工具与请求](../工具协议/六工具与请求.md) 拥有；界面上“点击”不是执行准入、持久成功或后端授权。
- 候选、真实前像、成组保存、冲突、恢复、证据：仍由 workspace/application/execution/assurance 及其现有 owner 负责。
- 任务边界及设计与生成区别：由 [用途与任务范围](../用途与任务范围.md) 和 [需求到交付主链](../需求到交付主链.md) 拥有。
- 本篇新拥有：**从意图到停止点的连续可见工作流、入口空态、每个界面的主操作/次操作/拒绝态、任务上下文与跨屏恢复、产品用语、键盘流程、体验验收场景。** 布局不成为领域写权，投影不成为新的事实源。

开发界面的每一步都应显示操作对象、版本和来源、当前权限、草稿/采纳/执行状态、潜在副作用及下一步门槛。成功路径必须可操作；冲突、离线、取消或缺信息时应保全已接受源与可继续工作，准确显示失败和恢复路径。完成状态由本次请求决定，不把`compile success`作为所有设计、运行或发布任务的统一终点。

## 1. 用户目的与三种正交维度

同一开发者可在原生代码、结构化业务定义、AI候选、图形关系编辑与CLI/SDK自动化之间切换；它们是同一工程的不同输入/投影方式，而非五种项目格式。入口允许新建项目、打开单文件或既有仓库、跨根工程、远程工作区及临时输入，均须保持对应内容的唯一Owner和保存范围。

1. **正在做什么**：理解、表达、修改、检查、使用、交付（六类任务、非六步向导）。
2. **本次希望做到哪里**（Exit / 停止点）：解答/解释、设计蓝图、作者草稿、已保存作者源、生成目标源码、检验结果、运行调试、受权发布/部署。它们是本次任务的 `requestedOutcome`，不是不可逆“项目模式”；可以在下一次请求升级/收窄，但不得自动扩大本次效果许可。
3. **通过什么输入**：自然语言指令、原生文本编辑、结构表单/树、可选图形、导入的已存在工程或精确脚本操作。入口不同，输出为同一准确来源/候选/证据关系。选择不同表示不会改变作者事实。

UX 必须将“本次出口”“候选/作者事实状态”“外部作用状态”分成三个独立标签。**设计蓝图已具备 ≠ 已保存 ≠ 已生成源码 ≠ 真实程序通过测试 ≠ 已部署。** 禁止把它们合并成一个绿色进度条。

### 1.1 角色不是权限层级

- 临时使用者：贴入表达式/函数或选择单文件；无清单、无登录、无强制建工程。
- 原生项目维护者：以现有代码、项目文件和 Git 为真；可只用 Gift 解释或协助一次局部改动。
- 系统设计者：从目标、业务无关的结构/接口/约束定义形成完整目标工程蓝图；不要求同时生成代码。
- AI/自动化用户：通过相同上下文、同一候选和权限合同进入；模型说“完成”不可替代回执。
- 审核者/团队：读只读差异、证据与出处，按实际 authority 审批相交写入；审查意见本身不是修改作者源。
- 运行/发布操作者：使用准确 Artifact/Environment/Operation，单独取得外部操作资格与回执。

允许同一个用户在一次会话中承担多角色；“高级用户”不是更强执行权限。共享视图按披露资格裁剪，不能通过列表数量、搜索建议、通知泄露受限对象。

## 2. 首次进入：立即可用，不逼用户学习 IR

首次启动只在用户点 Gift 容器、命令或调用 API 时激活。默认**不**自动联网、运行项目脚本、安装依赖、扫描全库、复制所有源码到 Gift、创建 `gift.project.json`、启动 AI 或写文件。

首屏最多呈现三个互斥入口，不是拦路问卷：

| 首屏入口 | 用户看到与操作 | 系统默认行为 | 结束点 |
|---|---|---|---|
| **继续当前工程** | 当前 VS Code 工作区根、信任状态；`查看工程` / `描述想做的事` | 读取当前可访问的有限范围、标注覆盖；未发现不代表不存在 | 打开原生文件或当前任务卡 |
| **创建软件设计** | 单句“想做什么”输入，可选目标平台/本次终点 | 本地候选；默认停在**设计/蓝图**（若用户明确要求代码，则如实反映） | 作者草稿与目标设计视图 |
| **快速处理一段内容** | 粘贴或引用当前选区，选“解释 / 修改草稿 / 生成预览” | 临时无项目上下文；无自动保存 | 单段说明、候选或预览 |

若窗口没有工作区、用户只打开一个单文件、目录不受信任、远端不可连或多根归属不清，首屏给出准确不同文案和可做动作。不能把“没有项目清单”当错误，也不能把临时内容暗中写入新工程。

已有项目入口显示 `已发现源 N 个 / 当前扫描范围 X / 未涵盖 Y`，N 和 Y 只有在确知时显示；不以估算冒充“完全读取”。Git 未提交文件、编辑器未保存缓冲和磁盘快照分别标记；用户可选择“以当前缓冲作候选基础”或“以磁盘为准”，不得静默舍弃缓冲。

### 2.1 任务输入的最小表单

默认只包含**一行目标**和**可见的本次完成目标**（推断结果允许用户立即修正），其余在需要时展开：范围/选中的文件，目标环境，已有约束，库/Provider，允许的实际作用，验收要求。没有这些的情况下仍可形成局部有用的草稿/解释，不能编造缺失规格。

当存在**不可从工程、代码或约束推导且会改变结果**的选择（如目标平台、外部身份、不可逆覆盖），提出一项最小问题，附为什么需要、当前已有选项、跳过后的合法结果（例如蓝图仍可输出为部分设计）。禁止重复询问已在作者源中明确的事实。

## 3. 常驻框架：少层级、可找回

依照已定版 Code-OSS 宿主：

```text
Activity Bar / Explorer / SCM / Debug (VS Code 宿主)
└ Gift：Project | Needs | Decisions | Review | Operations （可重排的五视图）
    顶部任务条：工作区与根 / 本次目标出口 / 当前候选 / 设计覆盖 / 恢复提醒
    主 Editor Groups：原生源码、结构编辑、目标工程蓝图、候选对照、证据
    右 Secondary Side Bar：Inspector [对象合同][真实来源][影响][可执行动作]
    底 Panel：Problems / Testing / Terminal（宿主） / Gift 操作凭证与证据
    Status Bar：当前基础、候选状态、当前目标的检查与未知作用摘要
```

`Gift` 容器不把六任务变成六页。Project 显示项目/定义与真实对象；Needs 显示阻断或值得关注的缺项；Decisions 查看固定/自动/候选与来源；Review 聚焦当前候选的差异、连带影响和准入；Operations 查看持续任务与真实外部作用。Assistant 只是一个可选输入入口，可以关闭；关闭不会删除候选或修改真源。

**用户上下文锚点**：任一屏始终可确定当前工作区/root、subjectRef、作者/磁盘修订或候选 basis、本次出口与目标根、访问资格和响应新鲜度。实现可在简略顶条+Inspector分级展示，不要求把哈希打印满屏；快捷“复制定位/查看来源”可展开准确可披露的身份。

### 3.1 主编辑区：选中对象后的默认行为

- 单击对象：选择并在 Inspector 展开摘要与允许动作，保持当前源编辑器不被意外关闭。
- 双击对象：优先打开真实 owner 的原生/结构源；若只有派生物，打开只读合同/蓝图并给 `转到定义`。
- `Why?`：解释为什么当前值/绑定成立，列出所有适用来源和排除原因。
- `Impact`：显示改变会影响的依赖、目标产物、检查要求和跨根对象；不推断未发现对象“无影响”。
- `Edit`：若唯一可写 owner 存在且资格满足，导航至该 owner 或生成候选；否则显示多个可能 owner、只读/未知原因与合法替代。
- `Compare`：选择两个**准确 basis**，默认当前草稿对当前基线；可切历史但不能把旧比较结果标作当前。
- `Graph`：首先只读浏览；绘制线只有在类型规则、真实 owner 与采纳协议具备时才能形成候选。没有安全写回就不显示功能性拖线手柄。

### 3.2 Inspector 内容与简化

客户端默认展示对象名称、角色、简短合同、当前状态和 `编辑定义`／`为什么`；高级视图才展开 Declared/Effective/Planned/Applied/Observed、DecisionContribution、ABI、Target 映射、证据范围和修订历史。作者设置与运行事实不能压成同一“当前值”。未支持、未设置、false、空集合与未知分别呈现；数值/单位须精确编码，不得经 JS 浮点转写丢失。

### 3.3 搜索、导航和大工程

**检索结果与受管编辑的身份不可用行号或分页位置替代。** 工作区、Provider 资源、索引代、文档模型、磁盘修订、查询范围及用户可见命中各有边界。搜索第 3 个结果在分页/权限变更后可能已不是同一对象；跳转前要按原 ResourceKey 和实际内容版本解析定位。检索覆盖不足要显式展示未知，不能用已发现数声称全域总数。旧工作区权限被撤销后，图、建议、检索数量、错误文本与来源映射均需服从当前披露，不只是隐藏文件正文。

默认利用宿主全文搜索；Gift 只增补对象/引用/关系/影响/证据的语义查询。每项查询展示 Scope、是否完整、权限裁剪和分页；大工程按用户选定的有界子图分批读取，折叠和虚拟化不得更换对象身份。重命名后按 canonical identity 恢复选择而非旧显示路径；所有图形交互提供键盘/列表等价路径，不依赖悬停或颜色提示。

## 4. 开发者写什么：一切业务由用户与供给提供

用户维护的作者内容由现实需要决定，**不是 Gift 强制的一套大表**：

| 用户实际创作内容 | 使用方式 | Gift 自动组织的内容 | 没有材料时的合法结果 |
|---|---|---|---|
| 目标与产品行为 | 语言描述、作者结构定义、已有规范引用 | 可追踪 Requirement/Contract、Needs/范围 | 只输出已决定部分，不补假业务 |
| 特殊算法与数据结构 | `.gift` 可选计算文本、原生源码、已有库 | 对应语义/类型与实现约束 | `NeedsAuthorContent` 或候选，不用空实现冒充 |
| 组件、接口和协作 | 表单/文本/关系图/既有代码 | 接口、状态、协议、依赖投影 | 不可解析对象显示为 opaque/部分覆盖 |
| 约束与权衡 | Require/Prefer/Forbid/Pin/Auto/局部 scope | 适用值、贡献来源、候选资格与影响 | 未选时保持自由或明确 Needs |
| 资源与环境 | 项目清单、原生配置、依赖、资产、授权 Provider | 目标规划、运行需求、外部效果计划 | 缺 Provider 保留设计蓝图、阻断执行 |
| 验收与交付预期 | 行为/兼容、性能/安全、接受边界 | 实际检查义务与可得证据 | 设计可交付，运行资格仍未知 |

已有 TS、Rust、配置文件或资产继续保持其原生真源。结构作者源只出现在对工程具有独立价值、且已要求可编辑语义的场景。一次自然语言输入不会自动产生一个与原生代码并行的全仓 Gift 镜像；生成物和运行观察默认只读。若目标编辑不能回源，必须保留“目标变更草稿待决定”，不能暗改 IR 或覆盖源文件。

## 5. 设计专用工作流：完整目标蓝图是明确交付物

**设计是合法独立终点；不自动生成源码、typecheck、安装依赖或测试业务。** 用户入口 `开始设计` 后的流程不是强制流水线，而是下列可直接操作的 UI 能力：

1. `说明目标`：确定系统要做什么/不做什么、平台或能力边界和本次完成范围。展示当前作者事实与新草稿的区别。
2. `组织系统`：选择/新增 Definition、Block、Port、State/Transition、Protocol、Requirement、Effect、Resource、Supply/Binding；按需复用已有库/工程，不需要先定义业务关键词列表。
3. `看工程蓝图`：点击 `目标工程`，默认展示**组件与公开合同 / 目标目录规划 / 运行拓扑**三块；需要时扩展其余方面，不让作者手工填八张表。
4. `定位不足`：Needs 单独指明哪些阻断当前设计出口，哪些不阻断且属于将来实现/现实证据；不把实现未运行列为设计失败。
5. `编辑与对比`：通过真实源或候选结构局部变更；Review 在一屏显示作者变化、语义变化、接口/布局变化、实现供给缺项、验收义务。
6. `设计评审`：审查要交付的目标范围、当前已确定的公开接口、运行限制、风险和兼容性；可保存未完成草稿或标记条件完备设计。
7. `交付设计`：用户可选择 `复制/导出当前有资格披露的蓝图快照` 或 `保存作者源`，二者分开。导出的派生快照带 basis、scope、coverage、limitations，**不构成第二个作者事实源**。

### 5.1 蓝图默认页面内容

默认以可浏览的 `目标工程蓝图 (Target Project Design)` 为标题；顶条必须显示：`工作对象` / `目标平台` / `本次出口=设计` / `基准` / `覆盖` / `缺项` / `生成状态：未请求`。主画布采用三个并列/可折叠切片：

- **系统**：Component/Module/Service/Library、公开 Contract、Port、状态/事件/协议，按跨进程或跨目标边界可见。
- **目标结构**：规划的根、源码/配置/资产/测试/构建清单，显示规划路径、owner、来源；这些是 planned member，不是磁盘上已存在的文件。
- **运行与交付拓扑**：进程/线程/运行域、外部依赖、权限/秘密边界、数据、部署形态、更新和恢复义务；不为未定义的运行环境画绿色可运行标记。

其余五类方面按需标签：`行为/数据`、`实现供给`、`依赖/构建`、`安全与资源`、`演进/保证`。这些是同一 Plan 的不同切片，不是不同的可编辑工程副本。选中列表项时 Inspector 展开出处、缺项、变更影响和合法 `Edit owner`。

**统一读取合同已选定（仍待产品实现与 Schema 资格）：** `gift.query` 是唯一只读入口；新增经明确 capability negotiation 的 `gift.blueprint-read/1` 分支，`view="blueprint"` 返回有版本的 `TargetProjectPlanProjection/1`，分片仍用既有 `limit/cursor` 且绑定准确basis和访问资格。详情及字段边界由[蓝图查询扩展的机器合同](../工具协议/六工具与请求-工具边界-任务与作者输入.md#gift-blueprint-read-extension)拥有。原 `gift.ai-tools/2` 六个查询枚举和 `view=contract` 保持原义，未协商时严格拒绝新 view，绝不把 `gift.preview` 改义成设计预览。**当前设计选择不代表 Gift Runtime 已实现这一新能力。**

### 5.2 目标工程不必是“源码树形等价”

目标规划覆盖**功能合同、代码组织、运行边界、构建/测试计划、资源/部署、兼容和维护**；不是简单输出 VS Code 级目录名。VS Code 级工程可使用 `Editor/Workbench/ExtensionHost/LanguageService/Debug/Remote/Build` 验证通用组合；这些都是用户定义的软件对象，不加入 Gift Core。对于未提交实现的组件，蓝图明确 `已指定行为但无实现供给`；若范围只要求设计，该状态不阻止输出条件完整的设计，但必须留到后续生成能力和 Target 检查环节。

### 5.3 设计“完成”的严格语义

- `DESIGN_DRAFT`：仍有作者目标或需求待明确，但已有可读的部分产物。
- `DESIGN_REVIEWABLE`：当前范围内已有完整可审查的切片，缺项已列举；不等于正式采纳。
- `DESIGN_ACCEPTED_WITH_CONDITIONS`：被指定主体对已披露/有范围的设计接受，条件和后续义务明确；不能覆盖阻断性违反。
- `DESIGN_ACCEPTED`：对**指定范围和明确设计检查方法**无阻断项、审查有准确basis；不代表真实软件存在或已验证现实行为。
- `DESIGN_STALE`：作者/配置/可用供给发生相关变化，旧设计不可继续显示为当前；仍可读历史快照和差异。
- `DESIGN_UNSUPPORTED`：所需语义/目标规划能力没有合格实现；不能借手写空项目规划凑出绿色。

这些是 UX 中展现设计资格的**投影标签**，不直接新增一个允许存储为作者真值的持久 `designStatus` 枚举。正确性由原 Assurance Claim/Evidence/Verification 和当前作用范围决定。即使为“设计已接受”，`Generated/Checked/Run/Deployed`仍须各显示 `未请求/未知`。

## 6. 从设计走向真实实现：用户主动开启，禁止隐形升级

用户选择“生成源码”时，工作台清晰提示**出口已从设计变为制品产出**，并先检查精确 Target、实现供给、生成资格与可用能力。生成预览为纯计算，不自动写盘；`ArtifactSet` 可打开原生Diff与准确成员表，查看哪些计划成员已生成、哪些失败或缺供给。`Save author source`、`Write generated output`、`Build`、`Run`、`Publish/Deploy` 是不同按钮或明确确认的 OperationPlan 子步骤。对缺失能力使用“当前不可生成：缺少 X/不支持 Y；继续编辑设计”并允许继续设计，而非生成占位源。

默认按钮顺序依据本次请求：设计工作中主按钮为`审查设计`或`保存作者内容`，生成工作中是`预览源码`，运行工作中为`运行实际目标`；不在设计默认页摆放危险的一键全流程发布。

## 7. 对候选的交互：何时变化才成为事实

统一变化条必须同时展示：`来自谁/什么（人、AI、已有源）`、`将改动哪个真实作者owner`、`原来是什么`、`本次候选是什么`、`影响哪个范围/目标`、`前像revision`、`可检查内容`、`允许的采纳粒度`、`保存/外部作用是否已发生`。

从 AI、表单、图形或原生文件建议产生的内容均以未接受候选出现。候选 `提出`、`审查通过`、`批准`、`保存作者源`、`生成产物`必须分开。选择“一部分采纳”时共同不变量关联的改变成为一个不可任意拆分的组；若不能安全独立，提示需要整组处理及原因。允许保留未采纳变化，不会把 AI 回复或选项点击当授权签发。

**未保存缓冲与来源冲突：** 来源在审查期间被另一编辑者修改时保全当前候选和人类未保存文本，显示 `当前基础已变化，保存被阻止`，提供查看双向/三向差异、自动可证明的无冲突重基、手动选择、放弃这次写入；不得默认强制覆盖。保存前重新检查磁盘前像、适用授权与组合不变量。Git commit 仍由宿主 SCM 用户操作，Gift 的源保存不代表 Git commit/push。

**设计连续修改案例**：当前蓝图的 ExtensionHost 本地运行 → 用户要求“迁移远端”。WorkBench 不直接给出“已完成”。它应展示 RPC、URI/path、信任与凭据、启动/重连、延迟预算、兼容与打包、远端 Provider/运行分界及被影响的服务，同时标记当前假设之外的必需决策。用户选择方案并采纳到作者草稿后，目标蓝图按新basis重算；旧Editor含义/不相交模块不应重写。设计阶段仍不启动远端宿主。

## 8. 可持续的 AI 与自动化体验

Assistant 进入任务卡时携带**已授权且可披露的准确选中对象和当前范围**；未显式许可的不上传秘密、私有源码、索引、历史或全仓数据。AI 提出的是候选，显示它实际用过哪些来源/能力、哪些推断尚未经验证、哪些决定必须交回作者。低信任仓库文本、网页、代码注释中的“执行指令”不升级为系统授权。`AI 说测试通过`只有实际验证回执可支持，不能自动把证据标签设绿。

多人/多 Agent 并行时，每项工作可单独候选和状态，用户可在任务卡中看到**来源范围、谁可写、被谁占用、当前基线、独立/相交范围、可重基与阻断原因**。不能简单“全部同意”，不能允许一个旧候选覆盖新修订，不能以忙碌动画替代真正的 Task/Operation 状态。关闭会话、重开编辑器、切换客户端只恢复合法的 draft 和受权运行读回，不要求用户记忆内部OperationRef。

## 9. 运行、测试和交付的真实人机语义

执行页面与设计页面共享选中项目，但只在用户明确要求时触发外部作用。`Build` 用准确产物/环境；`Run`、`Debug`、`Tests`、`Publish` 有不同准入，分别在宿主已有工具中表现，Gift 附加 source/target/operation/evidence 对应。执行前的人类确认显示**作用目标、可逆性、权限主体、可能覆盖的文件、外部系统、费用/资源约束、可能未知的结算后果**；不是泛化“继续/取消”对话框。

结果需要分为：`尚未请求`、`等待输入/能力`、`计算已完成`、`生成已有制品`、`某一检查通过/失败/未知`、`作者源已保存`、`外部操作进行中`、`已结算成功/失败/部分`、`效果未知待读回`、`权限拒绝`、`基线过期`。一个目标根通过不绿化其他目标根。发布回执丢失后先读回或恢复，不能立即自动重试未知的非幂等部署。取消是“已请求取消”，并非“外部效果不存在”；退出客户端不等同停止持久 Operation。

用户任一时刻可在 Operations 里查看 `为什么停在这里 / 本次能做什么 / 谁负责恢复 / 读回已知事实 / 产生了哪些不可逆后果`。不能恢复时允许导出脱敏诊断、保留设计与作者成果，不擦除操作账本。

## 10. 异常情境的可用路径（与正常路径同等优先）

| 触发情境 | UI 立即呈现 | 有效动作与限制 |
|---|---|---|
| 空项目或单文件 | 临时任务，无强制工程化 | 解释、编辑候选、复制结果；按请求才建清单 |
| 未信任仓库 | `读取能力有限，执行受限` | 读安全来源/设计；`信任工作区`不自动授权Gift执行 |
| 暂无本地 Runtime / 无 Target | `可编辑设计，暂不能生成/运行` | 保留和导出设计；定位缺少供给，不伪造代码 |
| 作者尚未说明关键需求 | `需你决定：X；影响 Y` | 填最小输入、比较候选、继续部分设计 |
| 目标对象受限/不可披露 | `权限不允许查看此项` | 不显示名称/数量/片段/历史缓存；可请求有权流程 |
| 网络或远程断开 | `离线·当前视图为旧快照` | 只读/本地候选，屏蔽对远端成功的断言 |
| 源在编辑中变化 | `你的候选基于旧版本` | Diff/rebase/重审；绝不默认覆写 |
| 多人提案冲突 | 明确哪组不变量冲突 | 独立片段可部分采纳，相关组保持原子 |
| 大工程只取到部分 | `已覆盖 X，未取到 Y（或未知）` | 限范围、继续获取；不显示“0个问题” |
| Candidate 基础过期 | Review 顶条标 stale | 留候选，重采 basis，重新核影响 |
| AI 无法证明外部执行 | “模型陈述，非工具回执” | 读取 Operation/Verification 真正证据 |
| 撤权/凭据失效 | 即时裁剪派生信息、阻止新效果 | 调整访问，不显示可用的旧操作权限 |
| 执行超时/回执丢失 | `外部效果未知` | 首选 readback/recover，不自动重复非幂等写入 |
| 检查/构建失败 | 精确阶段与诊断，保留旧阶段成果 | 只重做相交检查，不抹去原有效结果 |
| 导出或保存部分失败 | 按文件/root 展示各自状态 | 保留已成功写入的真实事实，提供补偿/继续 |
| 原生源码不可安全回写 | `只读映射/目标草稿` | 编辑原文或另存改动；不伪造成功 roundtrip |
| 重启/多窗口/多根 | 恢复准确 project/window/basis | 显示跨根身份和允许的恢复动作 |
| 手动删除文件、失去源 | `source missing` 与上次快照区分 | 定位 Git/备份/真实源，不由派生缓存代替 |
| 平台/语言支持不足 | `UNSUPPORTED`（限相交构造） | 不全项目标红，保留可用切片/替代方案 |
| 版本/协议不匹配 | `需兼容客户端或升级` | 只读允许范围；拒绝无法理解的写请求 |

**出错后不改变原问题：** `Review` 打开的是同一任务、同一真实候选，不应跳回“新建项目”或清空输入。每个警告必须有可到达的“为什么”和“下一步”，不能只是一句错误码。

## 11. 交互词汇、反馈与显示密度

- 使用“设计蓝图”“作者草稿”“真实源码”“生成预览”“保存作者源”“写出生成物”“检查结果”“运行/发布状态”等可理解名词；`IR、BLAKE3、CAS、OperationRef`只放高级详情和调试复制。
- “已完成”永远带对象与作用域，例如 `设计审查已完成·仅桌面版目标·运行未请求`；不得只显示大绿色 Done。
- 默认只一项最合适的主动作，次动作在同一区域而非隐藏危险按钮。高风险操作必须显式作用摘要，不因“用户点过同一按钮”推定长期授权。
- Needs 优先展示阻断当前**出口**的项，再显示非阻断待补和将来实现需求；不同阶段不同优先级，不能按总缺项数施压用户。
- 只读派生物突出 `编辑来源`；可编辑值显示 `当前值` 和 `来源`；观察与候选不显示为已保存。
- 操作进行中使用阶段/实际回执进度，不给虚构百分比；远端状态在断线时退化成未知，而不被动画维持为成功。
- 开启大型工程只呈现最相关有限视图/搜索，不初始加载所有树、Graph、依赖与 Evidence。支持取消耗时只读查询且不误取消执行任务。

## 12. 键盘、可访问性、国际化与多设备

宿主文本编辑、Diff、SCM、Testing、Terminal 原生复用；Gift 的新视图提供功能等价的**焦点顺序、可见标签、搜索、Enter展开、Escape退出、Tab遍历、触发命令、文本列表导出**。Graph所有节点和边有可访问列表/表格替代；不可通过拖拽独占任何合法编辑。面板可被移动/隐藏/单列重排，窄屏只改变布局，不改变当前 candidate/basis。读屏软件可听到状态更新而不被每次局部刷新抢焦点；错误与成功回执采用 `role=status/alert` 的合适语义。不能只靠红绿区分新鲜/陈旧/成功/未知。

跟随 VS Code 的 light/dark/high-contrast、缩放、减少动效与主题变量；文本方向、Unicode源码定位、双向语言与机器协议字段严格分开。本地化标签不作为机器身份；在中文和英文环境下同一工程签发相同 canonical refs。敏感数据的复制/截图/脱敏报告分别满足准确披露政策。

## 13. UX 输入/输出投影最低合同（非第二 Schema）

所有人机视图共用下列最小信息要求，可由已有owner的强类型结果**组合得出**，不要求新增业务协议：

```text
Context = workspaceRoot(s), scope, selectedSubject?, sourceOrBufferBasis,
          candidateBasis?, requestedOutcome, targetRoots?, capabilitySnapshot,
          trust/disclosure, viewFreshness, queryCoverage
View = subjectRef, displayLabel, role, ownerRef?, contractSummary?, basis,
       freshness, coverage, stageSpecificStates[], needs[],
       availableActions[{actionKind, targetRef, effectClass, admissibility}]
UserAction = preciseSelectedRef + expectedBasis + requestedEffect + explicitInputs
Result = producedCandidate/Plan/Artifact/Operation refs where applicable,
         stage-specific verdict and evidence, nextSafeActions, unmetConditions
```

这是**体验检查字段集合**，不是新 `UXContext.json` 作者文件，也不是已正式发布的六工具机器 Schema。客户端 UI 不直接提交它来修改工程；Runtime 必须在请求接收时重新核 `selectedRef/expectedBasis/permissions/Provider availability`。所有界面只消费有资格的投影，无后台本地 store 取得工程写权。

### 13.1 可见动作到既有公共工具

| 可见动作 | 公共语义（当前/拟实现） | 无副作用默认值与真实边界 |
|---|---|---|
| 查工程/解释/来源/影响/Needs | `gift.query`、原有只读投影 | 读取不修改源/运行 |
| 自然语言/表单/图建立候选 | `gift.propose` 或明确协商的作者草稿扩展 | 候选不自动保存 |
| 浏览目标**设计蓝图** | 经协商 `gift.blueprint-read/1`，`gift.query(view=blueprint)` 读取 scoped TargetProjectPlanProjection | 不等于代码预览；旧客户端不协商就拒绝 |
| 预览目标源码/制品差异 | `gift.preview` | 纯生成，默认不写盘 |
| 查看/运行相交检查 | `gift.check` | 纯检查与外部工具应分开按资格结算 |
| 保存源/写出制品 | `gift.apply` 不同受权 sub-operation | CAS；不能合并成一键写所有 |
| 构建/运行/取消/恢复/发布 | `gift.operation` 与已注册实际 Provider | 不越权；未知效果先读回 |

**产品实现阻塞项：** 这项新的只读扩展已在工具 owner 中明确设计了协议路线和字段义务，但严格机器 Schema、Codec、Producer、权限/分页验证与消费端均未实施。Workbench 在这些实际验收完成前不能将“打开蓝图”标记为已接通，也不能从旧的 `view=contract` 结果猜出完整工程。

## 14. 不同入口的一致性及退出原则

人类编辑器、CLI、SDK、AI 适配统一：同一个输入对象/修订、同一个候选范围、同一个权限主体与外部回执，在不同表面得到相同工程意义和可验证结果。**不是文字或点击次数一模一样**。CLI 可以一步准确发起，GUI 可以展开 Diff；AI 可以组织候选但不能自行签发作者批准。用户卸载扩展或退出 Gift Workbench，已有原生工程仍可由原有工具打开，作者源可用已支持的开放/机器协议导出，生成制品不要求 Gift Runtime 驻留才能运行；不能让 UX 导致用户锁定在某个不可迁出的 UI 数据库。

## 15. 产品验收原则与 UX 交付资格

本篇的 UI 规范需要在实际客户端使用场景中接受**设计评审、原型可用性走查、键盘/读屏走查和真实客户端集成验证**。本次 HTML 只验证部分可见交互的连贯性，不证明 Extension、Runtime 或六工具落地。独立随附 `Gift88-UX-acceptance-matrix.csv` 列出逐屏输入、操作、期望可见状态、禁止副作用和取证方式，供后续验收直接消费。

**起码的 UX 验收**：用户在没有学习 IR 的前提下能识别三类启动入口；在设计-only 与代码交付之间准确选择停止点；知道怎样编辑真实来源、审查候选、找出未完成条件并保全工作；对旧候选/离线/撤权/未知外部效果不会误认为成功；通过键盘或 CLI 完成与可视图相同的合法任务；无需预装某种业务类型；能清楚区分“设计蓝图已审查”和“真实程序已实现并运行”。

## 16. 明确剩余的现实证明，不把设计当实施

已设计：既有壳选型、基础布局、五视图、决定模型、作者写权、AI/人共同候选、设计独立停止点、完整蓝图体验、主要异常恢复与无障碍合同。**尚未实施/验收**：真正的 Code-OSS Extension 和 UI，blueprint 读取 typed-projection 的正式协议采纳，运行时数据生产者与严格 Codec，真实原生编辑接合，真实跨窗口恢复，真实可访问性测试与性能测量。对于任意不可计算的业务正确性或开放世界未给出要求的行为，UX 不能证明所有条件都已知或软件完全等价；应显示当前覆盖范围和需要实际证据的义务。

<a id="gift95-cross-contract-33"></a>
## 真实源码信息而非内部机器状态的开发体验

直接编辑 `design/*.module.json`、原生 `.ts/.rs` 或Scope control时，界面显示用户实际拥有的产品承诺及该项内容当前源文件，Rule正文的 `failure/progress unresolved` 显示为独立待补义务，供给不足显示哪个Method/Target/ABI/成员，不能只提示“JSON没写完整”。

“设计已完成”与“已产生源码/运行成功”应可独立停止，工作台不能因一个类型检查绿灯将整工程标记为Verified。用户拒绝自动建议、选择继续保留原生代码或只要JSON设计，均不应该被迫转换成可选Gift语言。

## 对开发者真正显示的跨契约结果

同一规则在工作台中应以产品语言显示“更新文档后版本递增（最小变化值 1）”，相邻可查项目说明“TypeScript/ESM，实际数据类型、已选实现、未解决的帧/错误/终止条件”；默认隐藏 Target 发行元数据与长 JSON 细节，展开 `Source` 可跳到真实唯一作者文件，展开 `Why` 显示硬控制来源和被拒 Method，展开 `Evidence` 显示类型检查与真实行为证据的不同范围。新发现的 Need 不可被 UI 当自动失败、也不能被 AI 以补全式默认猜测抹掉。

多文件编辑时显示被修改的作者源、联合前像、共享断言与提交状态；未实际保存时只标 Candidate/Preview，部分物化或外部写者冲突时显示精确受影响路径和恢复选项。真实 target 一般无需开发者手工复制 sample output；只有真实 Backend 已具资格才展示可发行 Artifact。Graph 是读取投影，其布局不是产品作者语义；在准确 GraphMutationReadiness 未成立前不让拖拽产生隐藏作者写入。

<a id="prebootstrap-author-journey"></a>
## 从陌生意图到自举工程的同一作者旅程

开发者创建工程后先选择或定义真正产品含义，可以直接编辑 JSON，也可由结构视图/AI 产生同一 owner 的候选。已锁定库负责共同条件，界面只展开当前仍未决定、与要求相冲突或由作者主动接管的部分。用户随时能查看真实 Definition/参数/默认来源/Method/Target 及其作用，不被简化界面锁死在预制业务列表。

建立新函数时可从签名加 requires/ensures 开始，保存后明确显示含义/方法状态；需要自创算法可在同一语言定义 expression，随后发布为库供其它意图复用。不要求业务作者先写 Provider、Effect、Evidence 或生成源码布局；确实缺少语义或有权决定时显示准确缺项，不生成一屏内部哈希让用户自行填。

查看生成结果分别展示源码、原生构建、行为保证、采用与运行事实。预览不是部署按钮已获权；执行时再次检查范围、前像和风险。再次修改沿真实语义关系展示影响：改变业务条件会影响方法/源码，改变显示名称不会重做无关运行；旧诊断/完成结果绑定旧修订，不覆盖当前状态。

大 JSON 操作包括按定义检索、折叠与按需展开、结构补全、局部替换、重命名引用、移动前自由变量检查、批量有范围变更与撤销。普通文字编辑、图编辑和原生代码区各自遵守唯一作者权威，不生成永久镜像文件。撤销仅撤销对应可逆源/界面变更，不能隐含撤销已发生的真实作用。

错误修复应直接定位最小真实责任：非法源定位 key/span；缺义指实际 Definition；无方法显示不满足的硬条件；缺目标指具体构造/ABI；无权限指操作范围而不泄露秘密；自举失败定位阶段与比较差异。用户无需把所有模块重新生成，系统也不通过隐藏失败子根宣称原请求全部成功。

<a id="design-b30"></a>
## 从新意图到第二次修改的作者旅程

作者新建概念时先创建普通Definition及公开输入/结果；编辑器按原SourceProfile保存，不要求选择行业模板。缺参数/类型/Meaning/Method/Target/权限分别定位到当前根的Need，给出实际缺失对象和可行补充动作，不将Kernel术语作为普通作者必须学习的输入格式。

取得Method有三条作者可见路径：选已符合硬义的方法、授权创建候选实现、自己编写通用body；系统不得替作者改输入域、隐私、错误或进展要求。propose只形成候选，preview只产生目标预览，check按明确强度核查；apply再按具体save-source/write-output与前像提交，运行Effect另外受权。短纯函数只需已有默认目标及一项保存/预览交互，不强制把每个内部阶段变按钮。

第二次修改应显示哪些原硬义仍成立、哪些方法/目标需重算、哪些生成区域变更及哪些原生区不受管。失败保留可读源码/候选与逐根结果，回退到旧source不自动撤销已发生效果。用户可展开全部依据、被拒候选及未覆盖范围，但默认界面不一次呈现整个内部IR。

AI与人类走同一权限和候选来源链；自然语言作为草稿/创作输入可以自由，转成可执行意图前必须锁定其正式意义。AI不能将推测默认为用户硬要求，不能自称用户批准外部执行，也不能用自动生成的测试作为唯一独立保证。

**验证与反例**：三个完整旅程：新纯函数→复用→修改，未知谓词→缺Method→受权创作，带Effect→preview成功但未授权运行。

**实际能力边界**：实际Code-OSS交互、用户操作耗时及可用性未测量。

## 业务作者怎样实际使用抽象层，而不是阅读内核术语

普通作者的第一操作是选择已存在的业务能力或提出新目标；工作台展示**公开要实现/维持/避免的结果**、谁的对象、适用时段、哪些限制来自已有库、哪些决定需要作者/领域权威补全。作者使用公共模式时只需选择对象、资源策略、资格/观察来源和差异条件；公共容量关系、事务候选和编译算法由其 Owner 维护。可以按需展开实际 Method、Target、原生源和证据，但没有要求先学完整类型系统、IR 或工作流语法。

每次解释候选在被接受前保留多个会改变合法性的选项。例如用户写“支付成功后发货”，系统应区分支付授权、扣账和清算，展示来源和每种选择对出货时点的影响；不能选择看似最常见的解释并立即生成/部署。被作者选定的 Meaning 有独立锁和 SourceSpan，未来算法更新不能悄悄改变其业务效力。

“All Decisions” 视图按来源展示：作者硬目标和可调整偏好；从模式继承的共同条件；领域特化政策；有权观察与事实缺口；已选 Method/Target；未取得的权限；可复核的质量/保证证据。这只是从原 owner 派生的阅读视图，不能成为第二份可编辑模型。点击一个差异先定位真实拥有者，未授权写入只能产生候选/Need。

在已有产品项目里第一次采用 Gift，可以只为一个业务目标建立 Meaning/意图引用，让原项目源码作为合格 Native Method 接入；无需整体迁移成 JSON。修改业务约束后，用户看到受影响代码、测试、Provider/Grant、历史运行和需要人工确认的变化，保留无关原生文件和已发生的外部操作。独立生成完整系统时，界面同时展示目标运行的交付缺口，避免因产出 3 个 TS 文件便报告业务成功。
