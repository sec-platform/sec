# Gift开发工作台的布局与交互

本篇拥有Gift人类开发客户端的具体布局、导航视图、Inspector、审查、命令和宿主放置。客户端产品选择由[产品与适配边界](客户端产品与适配边界.md#human-workbench-product-selection)拥有；树的出现身份、分页、筛选、选择与刷新由[树形导航与结构投影](树形导航与结构投影.md)拥有。两者复用既有六工具和工程owner，不新建写源。

Gift Workbench 是 Gift 项目的开发客户端；Assurance 研究中的 Studio 被编译目标属于另一个 Subject/Requirement/Method/Evidence 域。两者可共享成熟宿主，不能共享无依据的完成或权限声明。此处 Workbench 仍是客户端设计，实际宿主实现和验收未完成；headless 主链独立可运行。

<a id="final-workbench-layout"></a>
## 最终 Gift Workbench 的具体信息架构与界面布局

人类开发客户端以[Code-OSS / VS Code Extension-first 客户端](客户端产品与适配边界.md#human-workbench-product-selection)为首选宿主。Gift 只实现自身语义投影、精确 SourceMap、决策与诊断交互；Explorer、Editor、Problems、Terminal、Testing、Run/Debug 与 SCM 等现成熟能力通过宿主复用，不再另造完整 IDE。

<a id="six-development-surfaces"></a>

**客户端不授写权。（消费条件）：** UI确认只是经有权后端请求Grant的输入，不能把视觉上的“已同意”直接设置到操作状态。 合同归属：[委派能力收窄、重定向与执行时再检查](../../50-执行运行与观测/权限与资源/授权与执行准入.md#gift-delegation-attenuation)。

**UI侧遮蔽。（消费条件）：** Inspector的受限对象不显示准确数量、诊断片段和路径补全；在不同权限上下文切换时丢弃之前已渲染的私有投影。 合同归属：[派生数据、索引和差分结果的披露资格](../../50-执行运行与观测/权限与资源/工具秘密身份与披露.md#gift-confidential-derived)。

**离线编辑显示。（消费条件）：** 缓存的“已保存”状态只绑定返回它的候选和前像；重连发现另一作者已接受新版本时保留冲突候选，而非自动刷新后覆盖。 合同归属：[并发作者编辑的含义重基、来源保全与冲突切分](../../10-作者与输入/作者源/工程源/作者编辑保存与迁出.md#gift-author-merge-semantics)。

**UI提示。（消费条件）：** 对低信任内容明确显示原始来源及其“提议而非指令”的地位，模型自报已执行不替代工具真实回执。 合同归属：[外部内容注入、候选来源与有权决定的不可传递性](../AI协作/委派安全与持续交接.md#gift-ai-prompt-to-authority)。

**调试呈现。（消费条件）：** 用户本地可见的准确路径和可共享的错误报告是不同投影；复制报告不得默认包含绝对私有路径或敏感SourceMap。 合同归属：[外部材料、作者私有源码与可复现定位的隔离](../../10-作者与输入/作者源/工程源/资产与非源码.md#gift-source-scope-privacy)。

**支持呈现。（消费条件）：** UI中“可配置”与“在当前环境可用”是不同状态，欠缺实际目标Provider时显示明确缺项而非可运行绿色开关。 合同归属：[设计能力、代码实现、测试结果与正式支持的阶段资格](../../70-工程系统与演进/演进与实施/适用性与能力协商.md#gift-epistemic-support)。

**状态栏信息。（消费条件）：** 聚合标记须能打开准确原始阶段、basis及恢复责任；图标显示成功不能遮蔽外部Effect未知。 合同归属：[失败返回的阶段、可继续性与非对称状态](../../20-语义与组合/共同语义/规范元模型与结果语义.md#gift-failure-state-no-bool)。

**局部刷新。（消费条件）：** UI按选中对象和依赖更新需要变化的视图，不以全屏重建替代真实关系，仍要阻止旧请求覆盖新basis。 合同归属：[变动影响的有型闭包与非局部反转](../../70-工程系统与演进/信息与生命周期/对象关系与配置基线.md#gift-relation-invalidation-closure)。

### 六个开发任务面与现有视图的归属

Workbench中的view很多，但开发任务只按六类组织：**Understand / Author / Change / Verify / Operate / Deliver**。这是[完整开发者心智模型](../../20-语义与组合/作者语义/开发者决策模型与设定面.md#developer-mental-model)的任务轴；具体view可以跨面复用，不增加新的Engineering authority。

| 现有UI/能力 | 主归属开发面 |
|---|---|
| Project、Search、Graph、Inspect、Explain、Impact、Provenance、Needs定位 | **Understand** |
| 结构表单/作者Graph、Definition/Profile、Requirement、原生作者源/资产编辑入口 | **Author** |
| Text/structured edit、Refactor、All Decisions、Implementation、Control/Target/Native/Config修改 | **Change** |
| Plan/Review、Diff、Diagnostics、Tests、Coverage、Evidence、Compatibility检查 | **Verify** |
| Generate/Build/Run/Debug/Profile、Terminal/REPL/Console、运行参数和readback | **Operate** |
| Save/Apply、SCM、CI handoff、Package/Release/Publish/Deploy/Migrate/Retire | **Deliver** |

Primary Side Bar固定使用`Project / Needs / Decisions / Review / Operations`五个Gift语义视图，不为了六面机械做六个图标。`Project`同时服务Understand/Author；`Decisions`承载Change中的All Decisions与实现选择；`Review`承载Verify并按需展开Impact/Evidence；`Operations`承载Operate及发布/部署等Deliver效果的真实状态。Deliver中的Git工作树/暂存/提交/分支继续复用宿主SCM，不再造第二个Gift版本控制面。任务分类与导航布局是两件事。

Recovery/Resume横跨六面；Assistant横跨六面；Graph/Text/Table/Artifact只是表示；Explorer/Search/SCM/Terminal/Testing是宿主工具。用户切换这些组件不会切换工程authority或产生新的作者源。

│ Run/Debug    │ Review            │                                │                    │
│ Gift          │ Operations        │                                │                    │
├──────────────┴────────────────────┴────────────────────────────────┴────────────────────┤
│ Panel: Problems | Tests | Terminal | Output | Gift Evidence | Gift Operations          │

Gift不替换宿主Explorer/Search/SCM/Run视图；Activity Bar中的`Gift`容器只放工程语义视图。用户可以移动/隐藏这些view，布局变化不改变任何Engineering revision。

### Gift Primary Side Bar：五个视图

| View | 默认内容 | 正常动作 |
|---|---|---|
| **Project** | output roots、Definition/Block、公开Port、状态/关系/领域结构、Target；按真实hierarchy和bounded slice懒展开 | reveal source、open inspector、open graph、create/retire等仅在已有Operation支持时出现 |
| **Needs** | missing input、ambiguous、unsupported、conflict、stale、permission/resource blocker；按是否阻断当前requested出口分组 | 回到真实owner填写最小输入、选择候选、打开诊断；不能“一键全部默认” |
| **Decisions** | All Decisions高频切片：当前Meaning/Requirement/Control、UseBinding/Supply、Auto/Pin状态、备选及被排除原因、Target/Native/Build/Runtime policy | Edit owner、Require/Prefer/Pin/Forbid/Auto/Reset、compare；派生Binding只读 |
| **Review** | 当前Candidate的Plan、source/semantic/Binding/Artifact Delta、Impact、required Verification、Evidence与compatibility | accept/reject/partial accept、跳consumer、展开witness、选择检查；unknown不能显示成0 |
| **Operations** | build/run/apply/publish/debug等Operation的accepted/running/paused/unsettled/recovery-required/terminal | status/cancel/resume/recover/open receipt；不以关闭view取消Operation |

树节点至少带稳定显示标签、类型/角色、可披露状态和canonical ref/revision的内部绑定。UI id、树顺序和显示名不是canonical identity；重命名后selection通过真实identity继续定位。

### Secondary Side Bar：Inspector 是所有对象的统一下钻，不是万能属性表

Inspector固定按以下组渐进显示；无相交内容的组不渲染空卡片：

1. **Summary**：显示名、对象角色、stable identity/revision、owner、当前source/projection freshness、主要diagnostic。
2. **Contract**：输入/输出、类型、效果、资源/生命周期、公开Requirement与可观察失败；只展示当前对象实际拥有的维度。
3. **Controls**：每个相交控制用 `Requested → Effective → Planned → Applied → Observed` 五列或折叠轨迹显示，并附source、scope、phase、strength、override/conflict和Evidence。
4. **Implementation**：选中Supply/Method、版本、Target资格、依赖/许可/成本事实、为什么入选；自动选择显示`Auto`但仍能展开真实决定。
5. **Targets**：各被请求输出根的mapping、artifact/source members、unsupported/unknown、生成/构建/运行状态；不把一根成功染绿全部。
6. **Evidence**：Claim、Verification、coverage、环境、fresh/stale/unknown；绿色只对应该Claim与scope。
7. **Provenance / History**：author source、binding、generator、artifact、operation与actual readback链；历史只是过去事实，不变当前有效值。

Inspector编辑控件只在一个真实owner可唯一定位且当前Operation/author edit已定义时启用。点击一个值的“edit”首先显示它将修改哪份Requirement/Control/原生配置/作者源；派生值、Observed值和无唯一回源的生成值只读。Reset含义固定为撤销**本层覆盖**并立即预览新的Effective来源，不写`null`冒充通用默认。

控制值不再用一条互相重叠的“来源类型”枚举。紧凑行按需组合正交徽标：**Authority**（Author/External/Compiler-Resolver/Runtime-Execution/Client等）、**Relation**（Direct/Profile expansion/Propagated/Derived/Default rule）、**Stage**（Requested/Effective/Planned/Applied/Observed）及真实`sourceRepresentation`；`Unknown/Conflict/Stale`只属于State，Selected只属于Planned结果。颜色只辅助，不作为唯一信息；鼠标悬停/键盘聚焦能展开[完整DecisionContribution](../../20-语义与组合/组合/稀疏控制与目标限定.md#decision-contribution-algebra)、作用域、传播路径和producer。

<a id="workbench-all-decisions"></a>
### All Decisions：完整开发设定浏览器，而不是另一个settings.json

用户要求“把这个项目所有可控制的东西给我看出来”时，打开 **All Decisions**。它消费[完整开发设定面](../../20-语义与组合/作者语义/开发者决策模型与设定面.md#developer-decision-surface)，把不同真实owner投影成一个可搜索表格/树；它没有独立保存权。

All Decisions 不再用一个混合列表同时表示“决定类型、owner、阶段和错误状态”，也不依赖中央 setting-family registry。采用 **faceted view**：完整集合从相交 canonical owner 的 `DecisionDescriptor` 发现，筛选器对应四轴、真实 owner/模块、Target/Provider、状态及可选 facet。

客户端可以提供一组**纯 presentation 的 saved views**，例如：

```text
Meaning & Requirements
Realization & Target
Runtime & Effects
Assurance & Evolution
Automation & Client
All
```

这些 view 是查询条件，不是新的语义层或兼容身份。例如 `Meaning & Requirements` 可以按 decisionClass 选 Meaning/Requirement；`Runtime & Effects` 可以选 Runtime Input、Runtime-Execution authority、Operation/资源相关 owner；`Assurance & Evolution` 可以选 Assurance authority、Claim/Evidence 和演进 owner。客户端版本可以改变 view 名称、组合和排序，不使任何 Engineering fact、Binding、Artifact 或 Evidence 失效。

任何新 `DecisionDescriptor` 即使没有客户端认识的 facet 或 saved-view 映射，也必须出现在 `All` 与 owner/query 搜索结果里；未知分类只影响展示便利，不得产生 `Unmapped family` 阻断，更不能静默丢行。完整工程主题覆盖另由 [Assurance 工程决策覆盖清单](../../00-系统与原则/设计方法/工程决策覆盖坐标.md)攻击开放模型，不由 Workbench 维护一份机器分类学。

侧边/顶部 facet 分别是：

- **Decision class (A轴)**：Meaning / Requirement / Realization Control / Runtime Input / Presentation Preference；
- **Authority (B轴)**：Author / External / Compiler-Resolver / Runtime-Execution / Assurance / Client；
- **Phase (C轴)**：Declared-Requested / Effective / Planned-Resolved / Applied / Observed；
- **Setting scope (D轴)**：Author-Compile / Runtime / Client及其精确节点；外部authority/Evidence coverage按自己的范围显示，不伪装成D轴继承；
- **Source representation**：直接读取`sourceRepresentation`及其adapter/owner；不再用`derived/external/runtime/client`等authority或关系词伪装成representation枚举；
- **State**：current / unknown / unsupported / conflict / stale / forbidden；
- **Semantic / Domain / Mechanism facet**：由真实 Definition、SemanticModule、机制 owner 或组织分类派生的可选标签；未知 facet 不影响 Decision 存在；
- **Target/Product/owner revision**等普通查询条件。

native representation / authoritative native owner只是一组 `authority + sourceRepresentation` 过滤结果，不是第6种 decision class；`Unknown` 是 state，不是类别；Verification 由 Assurance authority/Claim owner 表达，无需再造 Verification family。

每一行显示相交列：`Decision · Subject · Owner/Facets · Scope · Authority · Declared/Requested · Effective · Source · Planned/Binding · Applied location · Observed · Evidence/Claim · Impact · Actions`。列在该decision不适用时为空，不伪造`N/A`值参与比较。

**默认不是把几千项全展开。** 首页只显示Explicit/Needs/Conflict/Stale和影响当前选中Product的高层Meaning；`Show inherited`、`Show physical`、`Show native`、`Show all applicable`逐层展开。搜索`overflow`、`allocator`、`encoding`、`transaction isolation`、`panic`、`region`等应直接定位真实语义/Control/native config，即使它不在默认卡片里。

对一行允许的动作由owner决定：Meaning进入作者编辑；Requirement提供Require/修改；Control提供Require/Prefer/Pin/Forbid/Auto/Reset中descriptor允许的子集；带native `sourceRepresentation`且可写的行导航到其authoritative native owner；Runtime要求进入运行配置或Secret provider；Presentation只改客户端。Resolved/Observed值默认只读，并提供`Why`和`Change owner`导航。

`Pin`、`Forbid`和`Auto`严格沿[控制UX语义](../../20-语义与组合/组合/稀疏控制与目标限定.md#developer-control-ux)降低，不能由前端直接修改Binding lock。批量修改必须先形成一个candidate/Plan，并显示共享hard requirement、scope expansion、target差异和会失效的Evidence；“Apply all defaults”不是合法快捷键。

### Progressive disclosure 在界面中的四档，不是四份配置

| 档位 | 默认面向 | 显示内容 | 仍可下钻 |
|---|---|---|---|
| **Essential** | 普通业务作者 | 独特Meaning、Needs、公开接口、显式Requirement/Profile | 所有隐藏决定都有来源；不自动固定实现 |
| **Engineering** | 需要精确行为/状态/资源的作者 | 数值、文本、集合、状态、时间、资源、事务、安全、接口等相交工程语义 | 目标/ABI/build仍可Auto |
| **Implementation** | 架构/性能/目标工程 | Supply、provider/algorithm、target、dependencies、storage/runtime策略、成本/资格 | 可继续到Physical |
| **Physical** | FFI/嵌入式/极致性能/原生互操作 | representation、ABI/layout、compiler/build flags、allocator、memory order、native config、runtime topology | 原生无法中立表达的内容仍可Go to native owner |

切换档位只改变可见性，不改变有效值。某个工程可以一直停在Essential并得到确定产物；另一个工程可以只对一个FFI边界展开Physical，而不是全项目切到“专家模式”。

**四档不是语义分类，也不要求中央 family 目录。** 同一 semantic owner 下的不同 Decision 可以处于不同深度：exact/range/unit 通常是 Engineering，runtime representation/bit width/vector ISA 属于 Implementation/Physical；data-locality 可能是 Essential/Engineering Requirement，某 sandbox provider 或 OS capability 则是 Implementation/Physical。客户端按 Decision 本身的 Meaning/Requirement/Control、真实 owner、消费者和当前任务计算默认深度，不因 facet 或主题名把重要 hard Requirement 藏进 Advanced。

默认深度判据为：

- **Essential**：当前Product对外含义、公开边界、作者显式Requirement/Profile、Needs，及若隐藏就会让用户误解“软件是什么/能否交付”的决定；
- **Engineering**：仍与具体实现方法无关、但影响正确性/状态/资源/时间/安全/一致性/兼容/验收的工程合同；
- **Implementation**：满足前两层后，对Supply/Provider/algorithm/target/runtime/dependency/deployment strategy等实现自由的决定；
- **Physical**：目标语言/ABI/layout/toolchain/ISA/allocator/memory-order/native-config等物理实现细节。

一个Decision只显示在其最低必要深度及更深视图；硬冲突/Need无论原深度如何都提升到当前任务可见位置。`Show physical`不会自动Pin任何物理值，`Hide physical`也不会删除已存在的Pin。

### Editor Group 中 Gift 只增加四种专用Editor

| Editor | 用途 | 写入能力 |
|---|---|---|
| **Plan / Review** | semantic delta、source diff、Binding delta、Impact、required Verification在同一candidate基础上联审 | accept/partial accept只生成已有candidate/Operation；不直接写文件 |
| **Graph** | bounded Definition/Block/Port、state/relationship、dependency/Impact/Explain图 | [GraphMutationReadiness](#graph-mutation-readiness)满足前只读；满足后只开放该门已覆盖的 registered typed Operation |
| **Structured Form/Table** | 对有限结构、Requirement、Control或领域表提供更高密度编辑 | 每项编辑必须回真实owner并产生同一Plan |
| **Artifact / Explain** | generated source、artifact members、source map、decision/provenance explanation | 默认只读；需要修改时Go to owner或走generated-edit合同 |

普通源码永远优先打开宿主text editor；源码diff使用原生diff editor，不在Webview复制文本编辑器。任何专用Editor删除/崩溃后都能从canonical state重建。

<a id="workbench-plan-review"></a>
### Plan / Review：一次变化必须在一个屏幕里回答五件事

顶部固定显示candidate/base和当前requested出口。主体按真实变化动态出现：

```text
What changed?        Authoring / Semantic / Binding / Artifact Delta
Why?                 Requirement + source + selected decision
Who is affected?     Impact definite / possible / unknown + witnesses
What must pass?      Required Verification + current Evidence
What can happen?     Apply/Build/Run/Publish effects + authorization state
```

文本diff仍由原生diff editor打开；Plan视图负责把多个物理diff归为semantic change group。部分接受只对真实独立change group启用；共享不变量或相交write set必须一起接受。`Accept`表示接受候选语义变化，不等于Apply/Save/Commit/Publish；具有外部效果的按钮使用具体动词，如`Apply to workspace`、`Build`、`Run`、`Publish`，禁止一个万能“Continue”。

未知/阻塞不统一染成error：Needs Input、Unsupported、Forbidden、Stale、Conflict、Evidence Missing、Operation Unsettled分别显示，并给一个最窄合法NextAction。不可自动恢复时不出现“Retry”按钮。

<a id="workbench-ai-assistant"></a>
### Gift Assistant：AI 是同一工程面的自然语言客户端

由于Code-OSS源码发行不应依赖Microsoft专有聊天产品，Gift提供自己的可选 **Assistant view**。它可以使用WebviewView承载对话，但消息模型仍只是客户端：

- 输入默认绑定当前workspace、selection和用户明确附加的context；不自动读取全部工程、秘密、终端历史或其他窗口；
- 每次回答区分Explanation、Proposal、Needs Input、Operation Request；普通文本不能成为作用授权；
- Proposal卡片必须链接到真实candidate/planRef并能打开Plan/Review；“应用”仍走同一Operation/author edit，不从LLM返回的diff直接写盘；
- 模型建议的库/配置/数字只作为candidate，未被Requirement/Control接受前不进入稳定作者源；
- provider/model、联网/数据披露范围、当前context摘要和token/预算状态可见；secret从不进入transcript；
- transcript默认属于客户端历史，不是canonical工程源；用户明确提炼出的Requirement/decision才写回真实owner；
- 固定重建、正常编译、实现选择与Verification不依赖再次调用LLM。

Assistant view在没有AI Provider时完全可缺席；CLI、结构源和Workbench其他能力仍完整。AI断线不使已接受的candidate/Operation丢失。

<a id="workbench-graph-ux"></a>
### Graph：视觉连接是 typed proposal，不是画线即成功

图默认围绕当前对象生成bounded slice，顶部可切换 `Structure / State / Dependency / Impact / Evidence` projection。默认不提供“全工程一次画完”；用户可按N-hop、root、scenario、relation kind扩大，未加载frontier始终可见。

<a id="graph-mutation-readiness"></a>
#### GraphMutationReadiness：按 Operation kind 激活，而不是全局开关

可写 Graph 的准入是当前设计内的能力谓词，不绑定仓库 issue、里程碑或某个客户端版本。**每一种 mutating Operation kind 独立取得资格**；Connect/Disconnect 只是首批允许申请 readiness 的 kind，其合同设计存在不等于资格已取得，更不会自动让 Create/Retire、任意源码块或第三方节点获得写权。只有下列条件在同一实现修订上同时成立，客户端才显示并接受对应 mutation：

1. **当前投影可安全回源。** node/port 使用 canonical stable ref，携带 source/projection revision；陈旧、歧义、缺 owner 或无法重定位时只读，不把显示 label/path 当身份。
2. **手势只降低为已注册 typed Operation。** 输入、前像、write set、Requirement/Control/Binding 影响和失败类型均由原 owner 合同定义；Canvas 不生成独立 edge truth，不把 renderer state 当作者源。
3. **降低与 headless 路径同源且确定。** 相同 exact basis、请求和已选 adapter 在 Graph、CLI/SDK/普通结构编辑入口得到同义 normalized candidate/Plan；presentation/layout 不进入 semantic hash。
4. **Apply 不旁路既有作用边界。** Plan/Review、权限、前像/CAS、冲突、事务/恢复和 readback 仍由同一 Operation/application/execution owner 处理；Graph 不持有额外 writer 或“直接保存”捷径。
5. **失效与恢复闭合。** source revision、Binding/descriptor、Operation registry 或相交 capability 变化会使旧 mutation proposal stale；重连/崩溃只按 operationRef/readback 恢复，不重放鼠标手势。
6. **相交符合性已取得并绑定准确资格键。** Evidence 必须绑定 `kind + implementationRevision + providerSet`，并覆盖该 kind 的成功、陈旧/非法输入拒绝、应用后 readback/恢复及 CLI/客户端同义性；不能拿另一种 Operation、另一实现修订或另一 Provider 组合的通过结果移植资格。对首批 Connect/Disconnect，Evidence 必须覆盖成功、非法/陈旧拒绝、effect readback/恢复、Inspector owner 写回边界、CLI/客户端同义性和无旁路；任何一类义务都不能由另一类测试代签。新增 mutation kind 必须按其真实语义形成相交 ProofObligation 后再申请 readiness；只有设计存在而未运行时仍保持只读。

因此 `GraphMutationReadiness(kind, implementationRevision, providerSet)` 是逐能力、可撤销的**派生资格**，不是一次通过后永久为真的全局布尔量，也不是 Workbench preference。`providerSet` 必须是实际 mutation 路径所消费 Provider 的**无序规范集合**，成员绑定稳定 provider identity 与 qualification-relevant revision；UI 排序、未相交 Provider 或纯 presentation extension 变化不得制造新资格键，相交 Provider 的能力/修订变化则使旧键失效。资格由既有 capability/Assurance owner 根据注册 Operation、实现/Provider revision 与 Evidence 求值，Workbench 只查询并可缓存带前像的投影，不能自行保存“已解锁”。任何条件变为 Unknown/failed 时，只撤销相交 mutation；Explain/Impact 等可证明只读的投影仍可继续使用。

节点显示stable label + role +最少关键状态；Port同时显示方向、type/contract和multiplicity/生命周期等相交区别。连接状态采用形状+文字而非只靠颜色：

- solid/direct：现有直接兼容binding；
- adapter：需要已知adapter candidate；
- dashed/unresolved：未知或缺实现；
- blocked：明确不兼容/禁止。

拖线只形成 `ConnectPorts` proposal。松开时先做Port/Contract compatibility：direct则产生Plan；需要adapter则展示候选及新增依赖/代价，用户接受后由Implementation Resolution选择；ambiguous/unknown保持Needs；incompatible零写入。Canvas不得静默插入转换代码。

断开连接只形成 `DisconnectPorts` proposal，并绑定**准确现存 relation/binding identity + source/projection revision**；不能仅凭两个端点或画面上的一条线猜要删哪条关系。关系已不存在、存在并行/多重关系而身份不唯一、revision陈旧或相交owner不可定位时保持Needs/Conflict并零写入。Disconnect只移除该关系本身；由它曾选择的adapter、库依赖、共享Definition、生成成员或资源若因此成为潜在孤儿，只进入Impact/cleanup candidate。它们只有各自Retire/Remove Operation取得独立readiness和消费者归零后才可退役，Graph不得把“断线”扩成隐式级联删除。

[GraphMutationReadiness](#graph-mutation-readiness)未满足的 Operation kind，其拖线/创建/删除等 mutating gesture 必须禁用，但 Explain/Impact 等已证明只读的图仍可用。首批**可申请可写资格**的 mutation kind 固定为已有 typed Block/Port 的 Connect/Disconnect；它们也必须逐 kind 满足上述六项条件才从只读提升。Create/Retire 等只有各自 registered Operation 与端到端符合性成熟后逐项申请并开放。任意算法语句、源代码 block 和无类型插件节点不作为图形完成条件。

图的webview参考实现采用React视图；node/port交互优先 `@xyflow/react`，自动layout优先 `elkjs`。两者只负责显示、交互和建议位置：node id由canonical ref投影，layout结果进入presentation state，不进入Engineering semantic hash；删除全部layout必须能重新生成相同语义图。具体依赖版本在实施时锁定并通过许可/安全/包供应链准入。

<a id="workbench-client-state"></a>
### 客户端状态、共享布局与恢复

默认本地持久项只有：窗口/view布局、最近选择、过滤器、graph viewport/layout、折叠状态、最近查询；它们由Extension workspace-local state保存，删除不会丢工程含义。团队需要共享某个diagram布局时，必须显式导出为**presentation artifact**，与canonical author source分开；它可以引用stable IDs但不能拥有它们，也不进入正常编译/Verification输入。

未保存文本仍由宿主document model/backup承担；Gift candidate、Operation、Evidence和恢复责任按各自owner持久化。重启后先恢复宿主文件/缓冲，再用当前source revisions重新建立projection；旧Inspector/Graph cache只可显示stale，不能在latest上继续写。

<a id="workbench-scale-and-accessibility"></a>
### 大工程、响应性与无障碍

所有Tree/Graph/Table默认懒加载、分页或虚拟化；列表不得为显示数量而预先解析全仓。UI线程不运行编译、测试、图全局布局或大Impact闭包；长工作进入Runtime/worker并返回进度与取消语义。100k+对象的workspace也只渲染当前bounded slice，搜索结果显示coverage与截断。

键盘和Command Palette拥有每个核心动作的稳定命令身份；Gift不默认抢占大量全局快捷键。首版只给少量无冲突的宿主惯例入口，其余由用户keybinding映射。所有自定义view必须支持键盘导航、ARIA/屏幕阅读、200%缩放、非颜色状态、焦点恢复和reduced-motion；graph的每个可写动作同时提供列表/命令等价入口，不能要求鼠标拖线才能开发。

<a id="workbench-first-use"></a>
### 首次打开、空状态与Brownfield入口

安装Extension后**不自动改工程、不创建`.gift`/JSON、不安装依赖、不启动项目脚本**。打开窗口时Gift状态只有客户端是否可用；第一次点Gift Activity Bar或执行Gift命令才懒连接Runtime并做安全捕获。根据当前workspace得到三个明确入口：

| 当前事实 | 默认界面 | 用户可做什么 |
|---|---|---|
| 空窗口/无根 | Start Center | `Open Folder/Workspace`、创建纯内存新产品草稿；未选择物理根前不写磁盘 |
| Brownfield已有工程但无Gift作者根 | `Existing project · not adopted` | 只读捕获/Explain/Impact；`Create authoring root`是单独Proposal，预览将新增哪些文件后才Apply |
| 已有结构作者/绑定 | Project + 当前Needs/Target摘要 | 直接编辑真实owner、生成/检查/运行；不再显示“初始化向导”挡住正常工作 |

若workspace处于Restricted Mode，Start Center明确显示“可浏览/可静态分析”和“因trust受阻的执行能力”；不能用一个红色错误把工程伪装成无法打开。若上次有unsettled Operation，只在Operations中显示Recovery Required，并保持正常独立编辑可用；恢复不弹不可关闭的全屏modal。

创建新产品时只问当前无法推导的最小信息：产品/Definition名、当前requested output root/target，及真正的硬Requirement。语言/库/目录细节若已有默认或可以自动选择不在wizard中强迫填写。创建动作先形成结构候选和Plan/Review；用户看到将生成的作者文件/目标计划后才选择保存。

<a id="workbench-command-surface"></a>
### Command Palette 与稳定客户端命令

核心人类动作有稳定的客户端command identity，键盘、菜单、Tree按钮和Assistant卡片复用同一入口；这些是客户端命令，不是第七套Gift公共工具。首版固定以下命令族，未具能力时显示准确Disabled/Needs而不是注册一个会失败的假动作：

| Command id | 人类语义 | 最终降低 |
|---|---|---|
| `gift.openProject` | 打开Gift Project视图并捕获当前安全workspace | query/capture，不产生Effect |
| `gift.showNeeds` | 显示当前requested出口相交Needs | DeveloperView/query |
| `gift.inspect` | 检查当前source/Definition/Port/Binding/Artifact/Operation | query source/contract/origin/state |
| `gift.explain` | 解释当前值/Binding/诊断/生成结果为什么成立 | Explain/provenance query |
| `gift.openImpact` | 打开Review并聚焦当前对象或candidate的Impact切片 | impact query；Impact不是独立顶层view |
| `gift.reviewCandidate` | 打开Review并聚焦当前Candidate的Plan/Diff/Impact/Evidence | preview + existing candidate refs |
| `gift.openGraph` | 打开bounded Graph projection | graph/query；默认只读 |
| `gift.openEvidence` | 查看当前Claim/Verification及覆盖 | assurance/query |
| `gift.openDecisions` | 打开当前scope/selection的All Decisions完整设定浏览器 | derived decision projection；没有独立writer |
| `gift.applyToWorkspace` | 将明确candidate作用到当前workspace | 原apply；重新核前像/权限 |
| `gift.build` | 构建明确candidate/target | compute-build Operation |
| `gift.run` | 运行明确artifact/entry | compute-run Operation |
| `gift.recoverOperation` | 对选中的unsettled/recovery-required Operation读回/继续 | 原operation recovery path |
| `gift.ask` | 打开可选Assistant并附加当前明确selection | 只创建对话上下文；不自动Effect |

不存在通用`gift.continue`、`gift.doIt`或`gift.fixEverything`按钮来隐藏不同Effect。发布、部署、迁移、Git merge等只在具体Provider/任务已注册且可准确命名时出现专用动作；不能借一个万能命令扩大权限。

### 状态栏只显示当前决策需要的四类信号

默认不把内部哈希/ID塞满Status Bar。最多显示：`Gift: Ready/Restricted/Needs/Unsettled`、当前Target、当前候选是否有未应用变化、当前关键Verification摘要。点击分别打开Project/Needs/Plan/Evidence。没有candidate或未请求目标时不显示空占位；后台Operation只在需要注意时显示进行/恢复状态，完整列表在Operations。

<a id="workbench-remote-placement"></a>
### Local / WSL / SSH / Container / Web 的Extension放置

Gift Runtime应与**真实workspace和执行工具所在一侧**同置，而不是永远跟UI进程同机。Code-OSS/VS Code存在local/web/remote Extension Host时，workspace侧adapter负责捕获文件、语言/构建工具和启动Runtime；本地UI只拿已披露projection。WSL、SSH、dev container等场景不能把远程绝对路径当成本机路径，也不能为了UI方便把整个作者源复制到本地缓存后冒充当前workspace。

```text
Desktop local workspace:  local Extension Host → local Gift Runtime
Remote/WSL/container:      workspace/remote Extension Host → colocated Gift Runtime
Web-only client:           web Extension → explicit remote Gift Provider，或降级为无进程的只读/plan-only能力
```

Extension声明和实际运行位置必须与其能力一致：需要spawn、filesystem或native tool的功能不能在web Extension Host里假装可用。连接跨机器时transport/authentication/disclosure成为真实Provider边界，不能沿用“同进程可信”假设。UI和workspace host断线后，旧projection标stale；恢复先重取workspace/runtime generation，再允许mutating action。

<a id="gift-client-view-consistency"></a>


**工作台呈现不混同目标产品。** Gift Workbench 是开发 Gift 工程的客户端；被设计的软件本身可以是 IDE、游戏、机器人控制或无 UI 库。一个 VS Code 级产品的源码图、宿主运行图和发布/目标图应允许各自不同粒度、拓扑和生命周期。展示它们的同源投影不能变成第三份由开发者手写的配置，也不能因使用 Gift Workbench 就默认生成 Electron、插件市场或终端服务。

**交互反馈属于准确操作身份。** 保存、应用重构、运行命令、取消任务、关闭编辑器、重新连接与部署有不同效果和终态；需要在一个界面保留当前操作的授权范围、输入前像、进度、失败恢复和正在结算的远端尝试。“请求已取消”不能显示成“远端费用、任务和实际作用都已终结”。脏缓冲、提交到 SCM 的内容、落盘内容与正在构建的已冻结快照分别展示，不能以同一个绿色图标代表全都同步。

### 离线客户端、分页视图与操作前像的同步

开发面的树、Graph、Inspector、列表和搜索页都是对当前选定工作区/候选/用途的**投影**，不能因为画面显示绿色或选中节点就获取修改权。每个可操作选中项携带准确 `viewBasis`（工作区、候选、revision、过滤/可见性、查询世代、源位置），提交动作由服务端重新解析语义目标及前像；分页游标/索引刷新后不可沿用旧偏移代表同一对象。对象被删除、同名新建或转移authority时返回`stale-target`并保留用户尚未接受的草稿。

离线可允许有限候选编辑并本地积累，但不假报远端持久化、发布或Effect成功；恢复在线时逐项比对source revision、权限、Provider可见性和当前选项的可用性。UI反馈至少区分`queued locally / accepted author candidate / saved / generated / published / action pending or unknown / evidence qualified`，并允许分项交付。仅因图上边被拖动或Inspector表单校验通过，不表示多边联合不变量和目标生成已完成。

## 意图目录、实例追踪与产品交互的分离

[六工具意图扩展](../工具协议/意图发现与候选展开.md)在Project/Author与Assistant中按需呈现Catalog，Occurrence连接现有Decisions/Review/Operations，不新增第六永久主视图。表单/Graph只形成原AuthorDelta，按该动作readiness开放写入；来源不足时反向匹配显示歧义。生成产品自身的[交互语义](../../20-语义与组合/可选语义/产品交互与呈现语义.md)归其产品/Target，不由本工作台的测试或布局代签。

<a id="developer-workbench-implementation-ready-map"></a>
## 实施前冻结的工作台动作—协议映射与异常交互

本节只拥有**人类工作台的可见元素、交互与恢复提示**；命令版本/类型以[开发面CLI与协议适配](开发面与智能投影.md#developer-headless-cli-one-protocol)为准；六工具字段/效果资格不在此另定义。下面为拟实现的客户端设计，不代表目前已存在插件。

### 默认窗口（不同viewport可以重排，不得改变状态）

```text
┌ Project / Needs / Decisions / Review / Operations ┬ 中央 Editor / Diff / Graph / Console ┬ Inspector ┐
│ 可筛选真实源/候选/Operation                         │ 作者文件原位置；候选C2和当前头B；产物A2    │ 当前主体和Owner │
│ Needs：真正待补项与有效支持范围                      │ 增量diff；只在请求时看到生成根与构建输出  │ 修订、来源、权限 │
│ Review：前像、write-set、多根覆盖                    │ 选择：只预览 / 检查 / 保存 / 写出        │ Stage、证据      │
│ Operations：真实运行、未知作用、恢复入口              │ 选择失败不改变候选                      │ Needs、影响闭包 │
└────────────────────────────────────────────────────┴──────────────────────────────────────┴────────────────┘
状态栏：Current Source/Buffer Head | Candidate/Artifact Basis | Requested Gate | Effect/Recovery
```

默认首次打开已有工程时**先呈现真实源**：不要求点击“导入所有源码到Gift”、不自动生成全仓IR、不自动启动Provider/AI/外部构建。若工程非Gift新建，从原生源码、清单及Git观察形成ProjectView；源覆盖不全时在Inspector声明已知/未知，不把小范围扫描显示为“完整工程”。不存在project file时允许直接一个临时候选，不自行保存`gift.project.json`。空工程点击“开始设计”可先形成原地未保存草稿，再在请求保存时形成清单、模块、锁的受控联合写集。

### 每个真实点击及不得发生的隐藏效果

| 用户动作 | 当前视图显示什么 | 传给哪个owner/工具 | 拒绝/不确定状态应该怎样显示 |
|---|---|---|---|
| 选中源码/函数/业务Requirement | 当前已发现的真实owner、版本、公开性与覆盖 | `query`的准确`at/view` | 不能访问时解释拒绝；未知时说明覆盖，而非空白树 |
| 输入自然语言/结构表单/Graph连接 | 尚未接受的Design/Source候选与语义Needs | 合法`propose`或显式`draft`扩展，必须按已协商形状 | 不存在的语言能力不自动转换为可运行代码 |
| 点击预览代码 | 用户选的目标根、Source/Target Basis与可预览Artifact | `preview`纯计算 | `UNSUPPORTED`只影响相交根；未生成不显示为已生成 |
| 点击比较版本 | C1→C2作者差异或A1→A2产物差异，严格注明方向 | 相交`propose`/`preview(return=diff,compareTo=...)` | 没有准确基础，不计算“与最新”伪差异 |
| 点击检查 | 明确methods、时间/环境/输入版本和Evidence覆盖 | `check`，需要运行工具则有实际Execution | 无Evidence为未检查，不能当通过；检查改用新目标须重新适配 |
| 点击保存当前源 | 候选C、物理前像B、写集+锁变动、授权效果范围 | `apply(save-source)` | B已变时显示冲突与可重基编辑，不提供覆写为默认 |
| 点击写生成产物 | 所选完整Artifact与输出根前像、具体覆盖路径 | `apply(write-output)` | 多根部分失败分别显示，不删除无关旧产物 |
| 点击构建/启动/部署 | 即将执行的具体Target/宿主/工具/作用/费用约束 | 已协商compute-run/其他operation及真实Provider | 缺能力明确不可用；确认回执丢失显示待核对而不是失败 |
| 点击取消/退出/恢复 | 取消请求、真实Attempt、可撤与不可撤的剩余作用 | `operation(status/cancel/resume/rollback)`的准确适用分支 | 退出窗口不停止无授权的共享任务，取消不删除已发生效果 |
| 点击重新编辑生成物 | 当前生成物来源与可回写区间及真实目标diff | 原`generated-edit`候选扩展或原生直接修改 | 回源不了就Pending目标草稿；不以自动编辑旧IR替代 |

### 需要冻结的八个界面交互状态

1. `NoProject/AdHoc`：可以预览短源，工作台不能强制建立项目状态库。
2. `Captured`：显示磁盘前像与未保存Buffer属于不同Revision，用户选择哪个作为候选Base。
3. `Proposed`：显示CandidateRef、影响根、接受/未接受项；`候选就绪`不等于可运行。
4. `Previewed`：ArtifactRef与TargetProfile基于哪个候选、EngineImage及成员，检查证据可以缺失。
5. `Checked`：仅给当前methods及对象显示有边界的通过/失败，变更期望不消除失败。
6. `Applying`：显示真实受权写入、当前前像和Operation；页面刷新后由持久Owner恢复进度。
7. `Conflict/Needs/Unsupported/Partial`：不使用一种红色失败遮盖不同恢复动作；用户能保留成果、查看具体对象。
8. `UnknownExternalEffect`：显示原operationRef、已知外部readback与尚未结算义务；首选状态查询/恢复而非执行第二个不幂等请求。

**正常/失败路径可用性**：键盘和屏幕阅读器必须能通过列表、属性与命令完成Graph同一合法编辑；任何可视拖动都只是生成带类型和基准的候选。网络/宿主不可用时，已取得且当前允许披露的源/结果可以阅读；不提供假编辑成功，不把灰色离线展示等同当前授权。Inspector按来源区分用户定义、派生、运行观察和未确认事实。

**无单一“发布绿色按钮”**：`Save source`、`Write output`、`Build`、`Run`、`Deploy`可以在同一个Review屏展示，但必须分别给出所请求的Effect、当前资格、目标根与Stage。可一键编排经授权的多步OperationPlan，内部每步仍可核账，任一步失败时不把前面实际成功步骤回写为不存在。

## 工程蓝图、设计专用模式与具体用户操作面的最终接合

### “设计中的 IDE 工程”不是“Gift 所在的 IDE”

本设计使用 VS Code 两次、且主体不同：①Gift **人类客户端**已采用 Code-OSS/VS Code Extension-first，复用成熟编辑器宿主；②用户所设计的**目标软件**可以是一款 VS Code 级 IDE，作为验证 Gift 通用表达能力的复杂工程案例。第②项会有自己的 Editor、Workbench、ExtensionHost，它们是用户领域对象，绝不能把 Gift 扩展的宿主进程状态当作目标工程的现成实现，也不要求后者依赖 Gift Runtime。

### 选中一个大型项目时，Gift 的实际界面

```text
┌─ VS Code / Code-OSS ─ Gift Workspace: ide-author (DESIGN ONLY) ──────────────────┐
│ Explorer Search SCM Run ┃ Gift: Project / Needs / Decisions / Review / Operations │
├────────────────────┬────────────────────────────────┬────────────────────────────┤
│ Project            │ Target Project Design          │ Inspector                  │
│  • IDE Product     │ [Components] [Ports] [States]  │ ExtensionHost              │
│    • Editor        │ [Source plan] [Build plan]      │ Owner / exact revision     │
│    • Workbench     │ [Runtime topology] [Evolution]  │ Public API / protocol      │
│    • Extensions    │                                │ Local/remote boundary      │
│    • Language      │  Editor ─── Workbench           │ Lifetime / owner / effects │
│    • Debug         │    │           │                │ Known / Candidate / Need   │
│    • Remote        │  Language   Extension Host     │ What changes? → Impact     │
│  Needs             │                   └─ RPC ─Server│ Edit original → Proposal  │
│  Decisions         │                                │                             │
│  Review            │ Selected target: Desktop / Web │ Design: partial/complete    │
│  Operations        │ [Show layout] [Why] [Compare]   │ Generated: NOT REQUESTED    │
├────────────────────┴────────────────────────────────┴────────────────────────────┤
│ Problems / Output / Diff / Terminal (宿主能力)  •  无自动构建、运行、部署           │
└───────────────────────────────────────────────────────────────────────────────────┘
```

在 `Project` 选择主体显示真实接口和其来源；双击可打开原生/结构作者源，单击下钻 Inspector；`Needs` 单独列阻断当前目标的缺项，不把未知能力显示为全局失败；`Decisions` 展开有权的关键选择及合法备选；`Review` 把作者/语义/布局/绑定/兼容变化放到同一候选上；`Operations` 在设计阶段没有新的外部Operation时应为空而不是模拟任务完成。Design-only 是本次请求**允许作用和显示终点的筛选条件**，不是新的作者语言、独立控制存储或覆盖用户既有权限的布尔写键。

### 目标蓝图页不是让人填八张表

用户默认看到可折叠的**产品树 + 选中组件合同 + 目标工程文件规划 + 阻断Need**。只有当前边界有关时才展开系统状态、资源、并发、权限、ABI、包管理、构建、发行与演进；知识索引、候选Graph和所有决策搜索按需派生，避免打开工程即扫描全库/启动全部Provider。切换 `Graph/Text/Table/Plan` 必须保持同一选中Subject与basis；布局坐标不持久成为工程语义。对未实现的Graph写回，在当前版本仅开放只读图或导航到合格源码编辑，禁止“灰色Apply仍写源”的影子通道。

### 一次新建和一次后续变更的真实点击轨迹

新建：`Gift → New design`（客户端**拟议命令文字**，非已注册当前产品API）→ 输入目标/环境 → 查看候选和需要作者决定的边界 → 编辑或接受真实作者定义 → 点击 `Target Project Design` 查看只读蓝图/接口/文件/进程计划 → 结束或按当前授权保存作者源。阶段标识是 `Designed`；不会有代码文件凭空出现。用户可通过同样的文件和工具在无GUI的headless路径完成对应设计，GUI不取得特殊解析或写权。

变更：选择 ExtensionHost → 提出“改为远端运行” → `Review` 看到 RPC/URI/权限/延迟/恢复/部署影响和未变的 Editor 需求 → 对可独立内容部分接受或整组采纳 → 浏览旧、新蓝图；基础已变则重解冲突，不能用视图里同样一条线认定没有影响。`Save source` 必须展示准确写入路径/共享写集/可能的原生文件改动，不连接 Git push/部署按钮。

### 产品体验的失败/恢复细节

Workspace 改变或断网时，设计候选不丢失；已展示“Complete”的过期蓝图要表明其准确历史 Basis，不得重新标为当前。插件宿主崩溃后，从当前有权 source/project 重新建立视图，不能从Webview自己的旧状态恢复真源。没有目标适配器时展示“Target plan only / implementation unavailable”，不得生成全空代码或伪造 `tsc` 成功；权限撤销立即停止新写入并裁剪已取得的敏感派生显示。只读设计无需加载真实目标进程，未来运行/调试发生之后另由原Operation/Instance/Observation owner解释。

## 连续操作与此布局的 UX 接合

本篇仍唯一拥有五视图、编辑区、Inspector及命令/宿主布局；从首次空态、任务出口选择、设计蓝图审查、候选采纳、冲突、离线到交付的**跨视图连续行为与验收**，由[开发者全旅程UX与交互验收](开发者全旅程UX与交互验收.md)统一规定。不能因为某个视图有一颗按钮就绕过相交owner的签发、资格和真实前像；设计蓝图编辑不可变成影子真源。
