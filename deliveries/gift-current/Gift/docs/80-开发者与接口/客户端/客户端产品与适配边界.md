# 客户端产品与适配边界

## 当前范围

首个headless实现闭环以AI/脚本为主，不要求先实现专用图编辑器、属性面板、LSP服务器、拖线或人类交互产品。直接使用现有编辑器、文件或补丁工具是合法入口；这与新建一套人类IDE不同。其内容层、版本及联合捕获沿[文本工作集](../原生维护/语言前端与直接编辑.md#text-workspace-capture)进入共同候选，语义、权限和真实结果不因客户端形式改变。

当前查询、成组修改、诊断、编译与恢复由[共同操作接口](../工具协议/六工具与请求.md)和[AI开发协议](../AI协作/需求与作者上下文.md)拥有。人类读取报告或检查生成代码，不构成开发一套专用交互产品的需求。

<a id="human-workbench-product-selection"></a>
## 人类主客户端的具体采用：Code-OSS / VS Code 扩展优先

最终产品不再把“以后可以有GUI”留成未决定。**人类主客户端采用 VS Code / Code-OSS 的扩展宿主模型；独立品牌的 Gift Workbench 若需要发行，使用 Code-OSS source distribution 预装同一 Gift 扩展和受控默认配置，而不是另写一个 Tauri/Monaco IDE。** 这项选择只确定客户端壳与交互复用；Engineering语义、作者源、Operation、权限、Delta/Impact、Verification 和恢复仍由 Gift headless Runtime 拥有。

当前实现次序仍保持 REQ006：AI/脚本与headless能力不等待GUI。这里完成的是人类客户端目标架构，因此后续实现不再重新比较“自研IDE、浏览器、Tauri、Code-OSS还是插件”作为同级默认路线；只有出现扩展API无法满足已接受硬要求、宿主许可/安全边界不可接受或真实总成本反证时才重开。

### 客户端产品矩阵

| 客户端 | 当前地位 | 负责什么 | 明确不负责 |
|---|---|---|---|
| `gift` CLI | 必须 | 脚本、CI、恢复、精确查询/Operation、无GUI环境 | 不拥有第二套语义或状态 |
| SDK / AI / Agent adapter | 必须 | 机器可读查询、提案、审查、受权Operation | 不因模型或SDK取得额外权限 |
| VS Code / Code-OSS Gift Extension | **第一人类客户端** | 文本编辑接合、结构/控制投影、Plan/Impact/Evidence、运行/调试/测试/SCM接合 | 不直接写canonical IR/source，不复制终端/SCM/调试器 |
| Gift Workbench distribution | 条件发行 | Code-OSS source distribution + 同一Extension + Gift品牌/默认Provider集合 | 不fork出独立语义核心；不依赖Microsoft专有VS Code分发物或专有扩展作为产品必需项 |
| Browser/remote client | 条件 | 查询、Explain/Review、远端只读或plan-only；具备完整远端authority时才可写 | 不把Web session/local state当工程authority |
| JetBrains/其他IDE adapter | 未来有真实消费者再做 | 映射相同客户端合同 | 不作为当前并行必做平台 |

### 为什么不是自研 Tauri/Monaco IDE

Monaco只解决编辑器核心；Tauri只提供桌面窗口/WebView与Rust系统桥。若用它们从零造主客户端，Gift还要长期维护文件树、多根、标签/分组、搜索、命令面板、终端、调试UI、测试树、SCM、快捷键、主题、无障碍、扩展生命周期、窗口恢复和跨平台桌面行为。Code-OSS已提供这些宿主能力及公开扩展面，所以当前复用其Workbench，Gift只实现自己独有的工程语义投影和Operation接合。

这不要求复制整个Code-OSS仓库进Gift，也不允许依赖其private internal API。**第一实现只使用公开Extension API与标准宿主能力。** 只有公开API无法满足某项已接受Gift合同且有实际消费者/测量证据时，才比较独立Code-OSS distribution中的窄patch；patch仍不能取得工程authority。

### Extension 与 Gift Runtime 的进程边界

Extension Host是客户端进程，不成为编译器内核。每个编辑器窗口/多根工作区最多拥有一个由Extension管理的本地Gift client session；首次需要Gift能力时懒启动，普通打开文件不因此启动编译器、联网、安装依赖或执行项目代码。

默认连接顺序为：

```text
VS Code / Code-OSS UI
  → Gift Extension client adapter
  → in-process compatible SDK，若宿主与同版Runtime明确兼容
     或 local warm Gift Runtime process
  → 原 query / propose / preview / check / apply / operation 合同
```

本地warm Runtime只是同一公共工具合同的宿主选择。Extension与子进程之间允许使用版本化、长度有界的本地IPC/stdio framing，但该传输**不新增公共工具、业务字段、权限根或第二JSON-RPC语义**；传输断开后依照已有operationRef/readback恢复。一次性简单命令可直接走CLI/SDK而不维持服务。Runtime crash只使当前连接失效，不把未读回的外部作用改写成失败。

工作区根、SourceRef、CandidateRef、OperationRef等由Runtime签发/解析；UI不得把路径、DOM id、TreeItem id或webview消息id直接当稳定工程身份。多根窗口仍保持各根authority与Provider边界，不因同一VS Code window自动合并。

### 宿主能力复用表

| 用户能力 | 默认宿主 | Gift增加的内容 |
|---|---|---|
| 文本/多标签/分屏/diff | Code-OSS原生editor/diff editor | Source/semantic correspondence、candidate与owner定位 |
| 文件树 | Explorer | Engineering role/owner/unknown overlay；不另造第二文件树作为默认 |
| 全文搜索 | 原生Search + 真实Provider | semantic/reference/coverage另以Gift查询补充 |
| Problems | DiagnosticCollection/Problems | 绑定producer、candidate/source revision、coverage与stale |
| Terminal | 原生integrated terminal | 只显示/关联真实ProcessSession；不重新实现terminal emulator |
| Run/Debug | 原生Run and Debug + DAP adapter | Gift artifact/source/permission/session identity |
| Tests | 原生Testing API | casesRef、artifact/environment binding、coverage/unknown |
| SCM | 原生Source Control | canonical candidate/semantic delta/operation relation；不接管Git真值 |
| Settings | 原生Settings用于客户端偏好 | 工程语义/Control仍回真实author/config owner |
| Gift语义/需求/Binding/Impact/Evidence | Gift Activity Bar views + editor webviews | 本产品独有投影 |

原生宿主能准确表达的内容不再用Webview重画。Webview只用于标准API无法表达的高密度Inspector、Graph、Plan/Impact/Evidence联视和AI对话；全部Webview采用严格CSP、禁止Node集成、消息严格解码、按当前workspace trust/authority重新准入。

### 第一实现的客户端技术栈

为了不把实现阶段再变成前端框架选型，第一Code-OSS/VS Code客户端采用：

- **Extension backend：TypeScript**，只使用公开 `vscode` Extension API；不直接使用Electron/private workbench imports。Extension Host天然运行JavaScript/TypeScript，没必要为了客户端壳再引入FFI。
- **自定义Webview：React + TypeScript**，数据是Runtime签发的immutable/bounded view-model；局部选择、折叠、viewport等只用组件local reducer/state，不引入第二个全局业务store。
- **样式：语义HTML/CSS + VS Code主题变量/Codicon语义**；跟随light/dark/high-contrast和缩放，不硬编码一套与宿主冲突的设计系统。
- **文本编辑：宿主原生TextEditor/DiffEditor**；Webview中**不嵌入第二个Monaco**，避免双文档模型、快捷键、accessibility和undo漂移。
- **Graph：React Webview + `@xyflow/react`；自动layout用`elkjs`**，只在HX5以后进入客户端依赖闭包。
- **Runtime：保持独立headless进程/SDK**；当前TS实现和未来Rust kernel切换只改变Runtime/launcher绑定，不要求重写Extension view-model。

Inspector/Plan/Assistant优先用普通React组件和浏览器原生能力，不为了控件外观引入完整第三方UI组件体系。只有实际复杂表格/虚拟化/无障碍问题证明需要新库时按Supply准入增加；不能让前端框架对象成为Engineering identity。

### Workspace Trust、联网和秘密

未信任workspace默认只允许不会执行工程代码的文本/资产读取及显式安全静态查询；build/run/test/debug、项目脚本、包管理器、未知语言插件和会执行目标代码的发现均显示为受阻，不能因宿主已安装工具自动执行。取得trust也不自动授予Gift Effect权限，只解除相应宿主安全前置。

客户端自身令牌/Provider凭据使用宿主或OS秘密存储能力；工程只保存SecretRef/Provider requirement。秘密不进入结构作者源、普通settings JSON、日志、webview state或AI transcript。联网能力按真实Operation/Provider逐次继承授权与披露范围；Gift Workbench不要求云账号，离线工程的完整本地开发仍成立。

### 独立 Gift Workbench distribution 的准确边界

需要“下载安装就是完整Gift开发环境”时，发行一个基于Code-OSS源码的独立distribution：预装Gift Extension、固定兼容的Runtime和必要开源Provider，使用自己的名称/图标/更新源/扩展来源策略。它仍调用同一Extension/API和Runtime，不在fork内新增业务模型。第三方扩展市场是可选Provider，不是工程重建前提；Microsoft专有VS Code二进制或专有扩展不作为Gift独立发行的必需组件。

若以后实际数据证明Code-OSS壳的启动/内存/隔离/发行成本对目标用户不可接受，才用相同客户端合同比较更轻壳；替换壳不改变作者源与Operation。因此Tauri仍可以作为未来宿主候选，但不是当前并行实现路线。

## 后续客户端只适配不重定义

当前已选的人类主客户端与未来新增的其他客户端都只适配同一作者源、基础修订、语义增量与实际效果合同。Code-OSS / VS Code Extension可以组织自己的光标、选区、展示和撤销组，但不增加独立业务规则、生成器或权限根；未来JetBrains/Web等也必须遵守同一边界。局部显示状态不是业务含义；目标软件本身的布局、顺序或导航可能是业务，仍由对应领域拥有。

不得把编辑器缓冲版本当工程版本，不得把显示的“通过”当真实证据。编辑往返与坐标、注释、未完成草稿和多对一映射由[唯一往返合同](../../40-目标与制品/表示/编辑与受管回源.md#编辑往返的具体合同)承担，不在此重复。

## 采用条件与退出

**客户端目标架构已选定，实施激活仍按真实消费者。** VS Code / Code-OSS Extension-first 不再是待比较候选；但 REQ006 仍要求 AI/脚本和 headless 主链不等待人类GUI。只有当前里程碑确实需要人类客户端或需要验证相交宿主能力时，才实现对应 Extension view、adapter 或独立 distribution；未激活的Graph/Assistant/复杂面板不预建空壳。

每个已激活客户端必须补齐它真实需要的可用性、无障碍、安全、宿主兼容和性能条件。公共Extension API足够时禁止为方便fork Code-OSS private API；只有已接受硬要求在公开API上无法实现且有实际反证时，才重开窄宿主patch。若后续真实测量证明Code-OSS壳总成本不合格，可以替换客户端壳，但同一作者源、Operation、Plan/Delta/Impact、权限和恢复合同保持，因此不会触发编译器核心重构。

人类、AI和脚本不要求完全相同的调用次数、显示格式和本地状态。共同的是被解释的变化、准确基础和效果边界；权限按实际主体，不按“人”或“AI”类别自动相等。移除某个客户端只丢其presentation/local state，不能丢canonical工程内容；退出独立Workbench时应能继续用CLI/SDK或另一合格客户端打开同一工程。

## 客户端产品和开发面能力边界

<a id="developer-entry-unification"></a>
### 开发面完整性不等于把所有客户端做成同一产品

[完整动作面](开发面与智能投影.md#developer-surface-contract)把源、工程控制、测试、运行和交付接到同一架构；新增的是具体消费者和缺少的有限交互输入合同，而非第十一模块或万能工作台。源码/语义批次仍由workspace/semantics/compiler承担，检查由assurance，真实环境、VCS、进程和发布由execution/真实适配承担，entry/application归一并返回。

直接文件编辑、六工具API、SDK辅助和既有原生工具可以共同构成一个开发者可用的完整环境；它们的行为必须准确对应，不能为了声称“一站式”对未注册动作伪造公共API。远端仅提供六工具时，能力边界也必须真实可发现；安装/发行等缺少宿主操作通路的功能不能标已支持。按需接合和故障恢复不改变生成程序独立运行的目标。

开发面优先完善当前所有动作族的正常路径与明确停止点，不把条件能力尚未实现/符合性未取证和GUI宿主选择混成同一个缺项。凡某动作实际激活跨语言、资源重构、强实时等能力，就从准确的[扩展语义合同](../../20-语义与组合/基础语义/扩展语义与适配合同.md)、目标映射和[当前实施闭包](../../90-治理与参考/状态/实施闭包.md)追踪条件能力，分别闭合设计、实现与Evidence；只有出现现有扩展模型无法表达但任务必须区分的新可观察差异，才重新登记核心设计缺口。共同入口设计完成不为条件能力的实现或证据代签。

## 已选宿主下的 UX 与现实实施资格

第一人类客户端继续采用 Code-OSS/VS Code 扩展优先，具体一次工作的入口、连续交互、设计蓝图和恢复验收由[开发者全旅程UX与交互验收](开发者全旅程UX与交互验收.md)规定。**完成 UX 设计不表示插件、Runtime 或 Target 已实现**；在未完成运行时支持与真实验收之前，不给客户端冒充支持的交互。
