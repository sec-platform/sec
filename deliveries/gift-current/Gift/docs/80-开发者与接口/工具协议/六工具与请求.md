## 六工具如何消费真实工程而不暴露内部IR

`query`读取固定真实SourceSnapshot及可访问的依赖范围，返回带来源的已知事实、未决和范围；`propose`把创建/修改目标、Pattern、Requirement或Control转成**候选作者字节差异**，不执行写入；`preview`返回拟改源码、派生影响和当前资格，不因预览自动下载或运行Provider；`check`按声明的目标/阶段消费真实消费者，输出能证明的检查及缺口；`apply`以当前SourceRevision、Scope、Grant做源写入的CAS/多文件可恢复提交；`operation`只运行有独立Grant的实际动作，保留OperationId和Unknown结算。上述是当前六工具的任务分工，精确Schema和版本仍在六工具的各自Owner。

用户只需要看到：**我接受了哪些需求与实现控制、这次改了哪些源字节、还缺什么外部定义/能力、哪些目标真的生成、什么检查已运行、实际外部作用如何结算**。WorkBench/AI可以按任务生成结构Patch、选已有Definition或展示简洁投影；候选不自动获得作者采纳。长JSON的体验通过分模块、局部Patch、语义导航、精确Span和统一保存协议解决，而不是强迫改成另一种作者格式或每次重写全工程。

## 六工具共同的请求状态、权限与错误返回

六个功能角色可以共享 `ToolRequest{requestId,principal,sessionRef,purpose,subjectRefs,exactBasis,requiredCapabilities,declaredEffects,resourceBudget,deadline}`，但各方法拥有自己的输入 Schema、返回资格和允许副作用。`Inspect/Explain/Plan` 默认无 Effect 且只产生可复用派生；`Propose/Modify/Build/Run/Publish` 必须根据真实方法拆分草稿、作者保存、目标写入和外部执行的不同有权边界，不让一个 `run=true` 同时签发所有操作。工具发现是否可用只说明入口注册，不证明宿主可提供所需权限与保证。

结果统一可分项返回 `ToolResult{requestState,evaluations,preparedChanges,artifacts,operations,verification,needs,errors,resumeBasis}`。`NEEDS_INPUT` 说明为完整求值仍需取得什么；`CANDIDATE_READY` 可供人审查但没有作者写入；`SOURCE_COMMITTED` 只说明源写成功；`ARTIFACT_READY` 只说明目标成员构成；`EFFECT_UNKNOWN`/`RECONCILIATION_REQUIRED` 不能压为失败；`COMPLETE_FOR_REQUEST` 必须针对原始请求的精确完成条件合成。非相关子结果继续保留，不能因某个外部 Provider timeout 抹掉全部纯计算结论。

每个方法带所需源/作用权限，拒绝因缺权限触发的自动升级。客户端显式授权可以影响本次准入，但模型提示、注释和旧会话不会变成额外授权。版本降级、未知字段、分页/流资格、取消和重连按既有客户端协议处理。至少用同一请求在 CLI、AI/headless 和 IDE 上产生同一种条件结果，验证没有隐藏的第二写入通道。
