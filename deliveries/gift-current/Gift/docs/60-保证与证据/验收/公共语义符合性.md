# 公共语义符合性

> 本页拥有 Standard Semantic Modules、作者语义与公共编译/运行接缝进入 Assurance 时的**方法中立符合性合同**。它不维护固定数值样例、SRC 编号或逐项测试题库；具体反例保存在公共语义反例研究，只有真实 Claim 与某一区别相交时才实例化 ProofObligation。

## 公共语义符合性的判定原则

公共语义通过的对象不是“某个示例输出正确”，而是准确 semantic owner 在给定 revision、定义域、效果、状态、时间、资源与 Target 下声明的可观察合同被保持。验证方法必须绑定实际主体和解释版本，并区分：

- 结构/类型正确与行为正确；
- 单次值相同与顺序、错误、Effect、资源、身份、进展相同；
- 有限子域证明与开放输入全域结论；
- 语义模型通过与目标 lowering、运行 Provider、现实作用分别通过；
- 文档中的区别见证与已取得的产品 Evidence。

具体方法沿[VerificationMethodContract](方法与独立证据-义务方法与已有知识.md#open-verification-method-contract)选择，不规定每个语义模块必须拥有相同数量的正例/反例。

## 状态、事件与完成语义

状态/事件模块的 ProofObligation 应从其真实合同派生，而不是维护一套固定状态机脚本。会反转结论的区别至少包括：

- 局部区域完成与整体完成；内部完成见证失效后重新形成的新轮次；
- history/恢复点的读取时机与 shallow/deep 等真实恢复语义；
- entry/exit/action 失败时稳定状态、计划和已发生 Effect 的边界；
- 无事件自循环、取消、预算和进展的区别，不能用“仍在运行”冒充稳定；
- 语义完成与 worker/resource 真正停止分离；
- Effect 已提交但响应丢失时沿原 Operation 读回，不创建新命令身份；
- timer/deadline 在重试、重启和不同时钟域中的身份与比较条件。

若新增状态语义只需自己的 SemanticModule/Dialect 理解这些区别，应留在该模块；只有公共身份、Effect、Evidence 或恢复协议本身无法表达时才提升 Core。

## 关系、查询与增量维护

关系/查询符合性必须固定关系身份、presence/absence、null/option、排序、聚合、snapshot/epoch、增量批次与错误语义。类型和最终行集相同不能代签以下性质：

- ON/WHERE、空组/全局聚合、重复出现、同键稳定顺序等真实关系语义；
- 查询回调的求值次数、错误传播和定义域；
- 增量更新在索引、差量、状态校验、引用切换之间的可观察提交边界；
- 乱序、丢失、重复批次和重试是否按原批次 identity 结算；
- Provider/数据库的 codec、角色、快照和排序规则只在实际绑定范围内成立。

没有闭合枚举/快照或实际 Provider Evidence 时，只能保留相应 Unknown/Needs，不从“当前没查到”推出全域不存在。

## 函数、对象、资源与求值保持

重构、抽取、内联、对象 lowering 或目标优化必须保持所有被 Claim 消费的可观察关系，而不只是返回类型或最终值。相交义务可能包括：

- receiver、参数、回调与字段表达式的求值次数和先后；
- 自由 binding、泛型/名义类型、可见性与 opaque 边界；
- 构造前参数 Effect、父子初始化、`this` 逸出、虚派发与私有字段；
- 操作中途失败后的真实状态与已发生 Effect；
- Own/Borrow/句柄/回调的寿命、释放者和跨线程约束；
- 公开 ABI、资源上界、终止和异常边界。

不能因为新 helper、class 或目标函数“能编译”就认定上述合同成立。无法证明保持的变换保留原实现或形成明确残余义务。

## 流、时间、随机、数值与微分

连续/流式/数值语义必须按自己的 Standard Semantic Module 证明，而不是挤进一个通用状态机 Oracle。典型独立区别包括：

- demand/backpressure、元素数与字节预算、早项阻塞、有序发布和 End/cancel；
- event time、processing time、watermark、窗口关闭、late correction 与重放；
- 随机源/seed/分布/采样与确定性声明的作用域；
- 数值表示、舍入、溢出、单位、误差界与不光滑点；
- JVP/VJP、共享变量贡献、检查点、重算与资源/Effect 约束。

有限差分、采样或某个实现输出可以作为 Evidence 方法，但只能在其假设和 coverage 内支持 Claim。

## 语言、Dialect 与 SemanticModule 组合

解释组合必须固定准确 Dialect/SemanticModule revisions；普通 import、安装顺序或同名语法不能偷偷切换解释。符合性至少保持：

- 未用模块不引入运行设施、权限或目标成员；
- 新语法/新 operation 的未知保全与旧 reader 拒绝/迁移路径；
- 多模块符号、类型、Effect 与 lowering 接合不依赖注册顺序；
- 新模块不能因自己注册成功而取得 Grant、Evidence 资格或目标支持；
- 仅换表示而语义相同与真正语义 revision 变化导致的失效范围不同。

开放扩展的正式规则见[语义扩展与定义接合](../../20-语义与组合/组合/语义扩展与定义接合.md)。

## 作者控制、保存、回源与目标消费

作者 Decision、源 revision、候选、保存、Binding、Target 生成和运行状态必须保持分层。一个控制值“已保存”不能证明目标实现已消费它；一次目标生成成功也不能证明文件写入、构建、部署或运行已发生。相交 ProofObligation 应检查：

- 显式值与继承同值的 provenance；reset 删除本层控制而不是写伪默认；
- 控制 scope 与共享 Definition/消费者闭包，不以发起 UI 实例决定作用域；
- 保存期间 source revision 继续变化时，写入回执只更新准确保存基线，不覆盖后继编辑；
- Unknown/Uncertain 保存结果按原 Operation readback，不能盲重试；
- source→target→source 的对应不产生第二份可独立改义作者字段，歧义保持草稿/冲突；
- Target getter、native object、ABI 或运行资源不能被当作中立 record 无条件展开；
- local exception 与共享 ABI/公共语义耦合时，局部控制不能越权修改未授权消费者。

冻结历史中的具体 IDE/Code-OSS 构造只可作为研究校准，不取得当前作者或客户端 authority。

## 作者源与语法接缝

作者源的符合性不再维护 `SRCxx` 清单。真实 Claim 按其使用的语法/结构、作用域、类型、Effect、查询、保存与目标能力派生义务。需要特别防止：

- record/update sugar 改变 receiver/字段求值次数、读取新值而不是旧值、静默接受未知/重复字段；
- 同布局名义类型因结构相同被错误互换，或 opaque/private 字段被外部直接更新；
- Unicode 标量、UTF-16/byte offset、搜索重叠规则等坐标语义被宿主表示偷换；
- query/save/preview 的旧 epoch、ABA 同文本、重开 session 等把 stale 结果重新贴到当前对象；
- 部分 workspace 枚举、隐藏文件或预算取消被报告为完整范围；
- 闭合枚举/本地画像向插件、协同或远程环境扩展时，只给 enum 加名字却没有协议、资源、身份和恢复模型。

具体输入构造仍可从公共语义反例研究选择，但研究行没有稳定机器身份。

## 可复用库与实现基线

高层库合同必须独立于当前实现品牌：输入域、错误、顺序、回调求值、状态/资源和目标保持条件由 Definition/Requirement 拥有；现成库、生成算法或原生实现只是 RealizationMethod 候选。只要实际合同闭合，调用者不必展开内部算法；反之，仅接口可解析、包成熟或 benchmark 更快都不能弥补行为差额。

比较作者成本或实现收益时应在相同目的和保证下比较首次建立、连续修改、维护/迁移、失败恢复与运行成本，不把“示例请求只有两字段”或“测试条目更多”当作系统优势。

## 关闭条件

公共语义符合性可以在某个准确 Claim 上关闭，当且仅当：相交语义区别由 canonical owner 明确定义；所选方法在该主体/revision/环境下具资格；Evidence 足以支持声明的 coverage；目标 lowering、运行 Effect、作者保存等不相交阶段没有被越权代签。

新增反例若只暴露实现错误，应修实现；若现有公共接口已能表达区别，应补接合或 Evidence；只有无法表达且会反转正确性时，才按核心提升规则演进 SemanticModule 或 Core。

## Rule call-boundProfile的正反符合性基准

有限机器Schema验证应该接受准确的Rule四槽及完整五类观察类别；拒绝未知字段、缺正常/失败/帧/进展、错误谓词引用、不合法负索引、重复输入槽、非声明field类型。成功形状仍须返回缺失的签名/Predicate纯性、Method/Target/工具链、进展/失败语义与独立证据义务。

外部语义Profile必须提供自己可检查的相同层次，并声明本文有限call-bound表达无法覆盖的观察区别；不能为了通过一个测试而删除高复杂度语言所需的状态/时间/随机/设备合同。

<a id="compositional-source-acceptance"></a>
## 新业务计算的端到端可判定验收与不变量

同一一般计算子集的正例不得只用“能生成源码”证明产品合格：至少区分作者语义与JSON投影等价、准确类型和读集、完整决策表行为、实际TypeScript严格构建、Node运行的独立期望对照、边界与失败拒绝、第二次改意图的相交目标成员变化。目标样本分别覆盖购物车、传感器、数值及角色决定，不能将多个同类断言数量乘成多个独立领域。参考纵切的样本门禁只支持这些实际领域和资源上界。

必须有针对性的反例包括：值域不合法、字段缺失/多余、Unicode孤立代理、列表超上限、安全整数中间溢出、零除、条件或集合元素类型错误、未知函数/未限定原生调用、互相递归/无终止合同、静态操作成本超预算、有限行为表重复或遗漏/枚举值越界，及不相交输入仅重排引起的虚假增量变更。编译器拒绝不等于产品级安全审计；不受控制的JS Proxy/动态原生供应、数据库/网络、进程崩溃、分布式并发和无界算法均需独立保证与更强方法。

## 非计算语义也必须有明确反例

[全域语义共同合同](../../20-语义与组合/共同语义/工程通用语义全域与闭合合同.md)区分知识的开放/封闭、规范允许/现实授权、过程开始/完成、状态/外部结算、时间/物理误差、声明/观察/证据等对。在进行模块符合性或跨目标保持验收时，只验证当前实例实际使用的语义及相交闭包；不能以大量纯计算通过掩盖无消费者的效果、安全、社会义务与实际保证。
