# 开发面符合性接缝
<a id="noncomputational-author-negative-witness-qualifications"></a>

<a id="gift141-multiroot-and-action-evidence-boundary"></a>

验收需要覆盖实际产生的设计边界，不只数测试场景：多根缺rootId/同名rootId、一个根合法另一根绑定无效、第二根接受义务被第一根代签、共享资源被误判独立、`UiNode.actionRef`指向底层Effect Port、相同动作和相同Workflow被两条Route重复启动，以及同一动作扇出到不同Workflow时缺有权多播/去重。相同字符串对象只证明需要审核的别名候选，不能做系统去重的Oracle。有限本地Checker只对预置范本及其Mutation签局部Schema和引用判断；不存在针对任意多行业/多产品的需求求解、Target真实输出或独立运行验收。


## 开发者可写设计的独立反例与未取得资格

必须分辨：`(a)` 单一Schema合法/唯一当前Writer；`(b)` 全部被选Root、实例及MemberUse无悬空；`(c)` 真实Meaning和本次动态输入有效；`(d)` 独立接受的硬要求在全局联合中没有被删改；`(e)` Method保持允许的状态/事件/权限/资源/效果；`(f)` Target/运行/独立证据满足被接受范围。这六种结论不是单一比例或单一绿色状态。

不可绕过的反例包括：同模板双实例拥有不同文档；一个输入只有UI成员而无明确激活；一个按钮同时直派Effect与经Workflow派同一Effect；后台订阅无处理/审计责任；资源参数被静态字面值伪造；mode=value偷用暂停Expr；同名成员Use在不同局部容器/真实发生点不等；一个产品根通过但共享跨根资源耗尽；删除已接受Goal后当前源码静态PASS；API响应需要动态字段却没有合格映射；有Schema与SourceMap但生成文件只含TODO/Stub。任何检查必须对应具体证据范围，能拒绝这些错误才有资格证明其相应的局部不变量；无法取得条件时返回`Need`，而非悄然退化到无事件、空处理或硬规则削弱。


本页只检验开发者入口在**身份、Authority、阶段、Effect、证据和恢复**相交处的语义保持。每个当前产品从实际启用的客户端、Target、Provider 与 Requirement 实例化其相交 ProofObligation；无相交能力不运行无关案例，也不以用例条数代签产品完整性。

冻结 `8a07bdb` 中的旧开发面案例矩阵保留历史推演细节，但它是校准材料，不是当前必须逐项执行的套件，也不拥有现行客户端、协议或产品支持范围。当前规范由其各自 canonical owner 拥有。

<a id="developer-surface-acceptance"></a>
## 开发面最小符合性义务

开发者通过 Workbench、CLI、AI、SDK、原生文件或其他宿主进入 Gift 时，至少保持下面这些跨入口不变量。它们是**语义边界**，不是固定测试 ID。

| 接缝 | 必须保持 | 典型错误 |
|---|---|---|
| Author source ↔ projection | 作者源、生成投影、编辑器缓冲、磁盘副本和运行制品各自绑定真实 revision；投影不成为第二真源 | 用旧磁盘诊断覆盖未保存缓冲；手改 generated 文件后反写错误作者位置 |
| Query ↔ Effect | 搜索、补全、解释、预览默认不取得写工作区、网络、安装、发布或外部工具执行权 | 为“发现测试”导入任意模块；补全 command 在 query 中偷偷安装依赖 |
| Candidate ↔ adoption | AI/工具生成的是候选；只有明确采纳路径才能成为作者事实 | 子代理说“已修复”就修改主源；预览结果自动提交 |
| Revision ↔ stale result | 每个诊断、建议、检查、运行和调试结果绑定它真正读取的 source/candidate/artifact/runtime revision | C1 的慢结果贴到 C2；旧 pause/source map 被解释成当前源码 |
| Provider locator ↔ canonical identity | LSP/BSP/SCIP/CI/Agent 等外部 ID 只定位 provider 对象；Gift identity 另行绑定 | target/session/name 相同就当同一 Artifact、Subject 或 Evidence |
| Decision ↔ enforcement ↔ Effect | policy/AI/规则的决定、实际准入、真实作用与 readback 分开 | `allow` 被当操作已发生；发送 200 被当目标已收到并完成 |
| Capability ↔ current grant | 长会话、缓存、agent task、debug session 不携带永久权限；Effect 前消费当前相交 Grant | session/task id 恢复后复活已撤销权限 |
| Local edit ↔ semantic closure | 文本不重叠不代表语义独立；签名、初始化顺序、effect、public consumer 和共享约束必须按实际依赖判断 | “不同文件”自动可合并；删 unused import 时删掉初始化作用 |
| Discovery ↔ completeness | 部分索引、懒目录、动态发现或零结果只能证明声明覆盖内的结果 | “没搜到”升级成全工程无引用；exit 0/零测试升级成需求已验证 |
| Check ↔ Evidence | 检查运行结果只支撑其对象、方法、环境与 coverage；不能自己改验收期望来通过 | 更新 snapshot/阈值后仍称原 Claim 已证明 |
| Operation ↔ outcome | request/attempt/Effect identity、accepted、completed、unknown、settled 分开；未知完成先 readback | 发布响应丢失后换新 ID 重发；signal sent 就释放仍在用资源 |
| Local state ↔ shared state | worktree、index、远端 ref、共享配置、缓存和宿主资源具有不同并发域 | stage-all/reset 清掉无关用户内容；目录隔离被当完全资源隔离 |
| Build ↔ load ↔ run ↔ publish | 构建成功、目标加载、进程运行、发布可见、部署采用分别观察 | 浏览器仍跑旧 bundle 却显示“当前已运行”；store upload 当用户已可用 |
| Secret/identity ↔ disclosure | secret 只以受限引用参与 Effect；认证身份、业务 Principal、role/Grant 和结果披露分开 | 证书字段直接变 Admin；缓存结果绕过当前披露权限 |
| External event ↔ occurrence | event record、delivery attempt、业务 occurrence 和派生 Effect 分开 | broker 重投递被记成两次现实事件 |
| Client lifecycle ↔ work lifecycle | 页面/连接关闭只撤自己的借用与等待；持久 operation、共享任务和未结算资源继续由 owner 管理 | 关 UI 就把后台作用标 cancelled/settled |
| Presentation ↔ meaning | viewport、排序、折叠、saved view、facet 是客户端投影；业务 Definition/Requirement/Decision 不因 UI 分组改变 | 新 descriptor 因“不在已知分类”被隐藏或丢弃 |
| Assisted path ↔ direct path | 辅助工具是可选能力；普通源、库或结构作者路径不能被 IDE/Graph/调试器强制前置 | 一个小函数被迫建立 Graph、启动数据库或安装 IDE 才可生成 |

这些义务应该由现行 source、operation、authority、assurance、runtime 和 delivery 合同直接满足。若某一行需要在这里重新定义字段，说明 owner 仍放错位置；本页只负责用交叉反例检查它们是否在组合时失真。

## 高价值接缝反例

具体实施时无需“把历史矩阵全跑一遍”。优先选能同时击中多个 owner、且错误实现很可能仍返回成功码的反例：

1. **未保存缓冲 + 迟到分析。** C1 磁盘检查晚于 C2 缓冲修改返回。结果必须继续绑定 C1，不覆盖 C2 当前事实。
2. **外部索引部分覆盖 + 否定查询。** 搜不到引用只能得到 `not-observed-within-coverage`；没有封闭全集不得签发全局“无消费者”。
3. **动态发现带 Effect。** 测试/插件/config 的发现若会执行用户代码、I/O 或安装，必须走独立 Operation；query 本身保持无作用。
4. **补全附带结构编辑 + stale base。** import/rename 等附加编辑与主修改作为同一候选按原 base 校验；base 变化后重解或冲突，不能偏移硬贴。
5. **检查期望被候选修改。** AI 同时改代码和 snapshot/threshold/fixture 时，期望变更成为独立作者候选；不能用它证明原 Requirement 已满足。
6. **远端未知完成。** push/publish/外部 Effect 响应丢失后，先按原 operation identity 读回；不能用新 ID 重发来“确认”。
7. **当前 Grant 撤销。** Agent/debug/session 仍存在，但新 Effect 必须重新准入；历史结果按当前披露规则返回或净化。
8. **相同 provider id、不同 canonical revision。** LSP/BSP/CI/模型 registry 的同名 locator 不允许覆盖 Gift 的稳定主体和历史 Evidence。
9. **不同文件、共享语义。** 两个候选修改不同路径但共同影响 public interface/Requirement/资源约束，必须联合检查，不以文件边界证明独立。
10. **相同文件、真正独立。** 两个修改虽在同一文件，只要 read/write/constraint closure 可证明独立，也不应被“同文件”策略无条件串行化。
11. **运行产物落后于作者源。** B1 正在调试时已有 C2/B2；pause、stack、profile 继续绑定 B1，当前源码不能冒领旧运行观察。
12. **共享任务一方退出。** 一个客户端关闭只释放自身租约/订阅；其他消费者、真实 operation 和资源的终态不因此改变。
13. **认证成功但授权/业务身份不同。** mTLS/SPIFFE/OIDC 等只建立其真实认证事实；业务 Principal、role、Grant 和 on-behalf-of 另行解析。
14. **event delivery 重复。** 同一现实 occurrence 的重复 delivery 不自动产生第二个业务 Effect；反之两个外部 event id 也可能引用同一 occurrence。
15. **build 成功但目标没有采用。** 浏览器、设备、插件宿主或 rollout 仍使用旧 generation 时，只能报告新 Artifact 已构建，不能报告当前实例已更新。

当前反例集中检验六类独立退化：身份错贴、Authority 非法提升、阶段资格合并、未知效果误判、证据覆盖不足及辅助路径被强制。新 Provider 或客户端只有增加独立可观察的失效模式时才增加用例；不能仅按品牌、协议或单独工具名复制同义回归。

## 开发任务与 Decision 投影

开发者目的仍由 Understand / Author / Change / Verify / Operate / Deliver 等可组合任务意图表达；Recovery、Security、Assurance 和 lifecycle 横切它们，不因新增面板再造第七、第八种业务层。真实可写性由 semantic owner、authority 和当前 operation 决定，不由 UI 标签决定。

`DeveloperDecisionView` 必须从相交 owner 的 `DecisionDescriptor` 派生；一个新 descriptor 即使没有已知 facet，也必须能在 All/owner 查询中发现。Facet、saved view、排序、折叠和高级/物理视图只帮助导航，不成为 Decision identity、Binding、权限、兼容或 Evidence 的输入。

直接作者路径同样是一等公民：普通产品作者可以只维护结构化作者源/原生源并让工具投影需要的界面；只有明确选择 `.gift` 计算文本、Requirement dialect、FFI/Target 或其他高级 owner 时，才承担其专门词汇和合同。不能为了让 Workbench 看起来统一而要求所有工程先双写隐藏 IR、Graph 或机器台账。

<a id="多种交付形态的正常与失败压力接受"></a>
## 交付根的压力选择

Gift 不维护固定“16 类/36 类产品家族”。验收应从作者实际选择的交付根及其正交合同生成：调用方式、生命周期、状态、Effect、并发、Target/ABI、Artifact、资源、恢复、发行和 Evidence。下面只给**机制差异**，不是产品枚举：

| 根的差异 | 正常义务 | 必须区分的失败 |
|---|---|---|
| 纯同步调用 | 输入/错误/返回/资源寿命明确 | 不擅自变异步；getter/参数不能多求值 |
| 异步或消息调用 | request/attempt/result/cancel identity 明确 | timeout/unknown 不盲重发；重复 delivery 不等同 occurrence |
| 长寿命交互实例 | session/state/资源 owner 和退出清晰 | 客户端退出不等于实例已结算；旧 generation 不贴当前 source |
| 多输出根共享实现 | 共享代码与各根 host/Artifact 责任分离 | 一根缺项不抹去其他根成功，也不冒充联合完成 |
| 外部 Provider | capability、版本、authority、readback 真实绑定 | provider “supports” 自报不能给自己签符合性 |
| 可发布/可部署根 | package/sign/publish/install/deploy/adopt 分步结算 | upload success 不等于发布或实例已采用 |
| 原生/设备根 | ABI、lifetime、thread/device qualification 与资源释放准确 | device loss/driver failure 不被普通业务错误吞并 |
| 数据/流/查询根 | snapshot、event time、backpressure、结束条件准确 | partial/empty/late 不伪装成完整 Final |

对某一真实产品，只实例化相交组合，并加入该 Requirement/Target/Provider 特有的正反例。**用例数量不是覆盖率，文档里列出的场景也不是产品 Evidence。** 真正通过必须绑定被测 revision、输入、环境、方法、观察范围和独立期望。

## 何时需要新增案例

只有满足以下至少一项才值得新增当前 Assurance 反例：

- 发现现有 owner 无法表达的独立可观察差异；
- 一个错误实现会同时满足现有正例，却在新的失败/并发/恢复路径上产生不同结果；
- 新 Provider/Target 引入了此前不存在的 authority、lifetime、ABI、资源或终态；
- 现有验证方法存在共同原因，新的独立 Oracle 能真正降低误判；
- 历史事故或现实失败记录暴露了当前 coverage 的盲区。

仅换语言、品牌、行业名、UI 页面、协议字段名或再列一个正常成功流程，不构成新增案例理由。历史矩阵可用于发现候选，但当前规范只保留实际仍有区分力的接缝。

### 回归门禁按覆盖性质分开，不合并成“总绿灯”

**G0 文本与身份保全**：每次交付按**该次真实直接父包**逐成员bytes/SHA对照（例如本次统一版的直接父包为Gift89），原路径全部可定位；删改需明确位置、意图、差异和相交反例，不能用字数增加抵销一个句子的条件丢失。原有正文是否保留原始前缀仅是个别append-only版本的证据，不得套用到实际改写既有句子的版本；**字节保全、规则保全与跨源语义保持是三个不同的证明目标**。

**G1 机器合同相容**：严格Schemas唯一来源、实际TS/Rust decoder roundtrip、公开六工具联合分支与字段默认、SourceProfile/lock/target/worker握手、CurrentHead/Operation准确旧版本读取，禁止自造第七工具或`gift.apply`新mode。

**G2 首条垂直用户用途**：P1 必须真实跑DEV-001—019、021、022、026（在明确库支持限制下）、027—029、035—036的相交部分，展示一个短源**实际生成/修改两次/检查/保存**，其中Check真实运行、source和目标分别可观察；没有实际Engine/TS消费者不能判绿。

**G3 失败与恢复**：真实并发/故障注入覆盖stale base、部分文件写入、Worker crash、旧handle、迟到结果、撤权、无法确认外部Effect、schema变化与读回；持久日志经单/多进程及冷重启复核。不能用mock-only发出生产保证。

**G4 性能与资源**：记录冷启动、warm预览、第二次增量修改、TS目标生成、检查、内存/CPU/IPC/DB占用；选择目标硬件/样本/百分位与约束后测量。Gift84离线知识工具既有性能门限失败不得删门限或称其已通过；它也**不等于**用户产品编译器吞吐的基准。

**G5 发布/多目标/生产资格**：实际目标工具、ABI、签名/产物、Provider及外部状态读回、独立信任边界、组合下多根保证、未知效果恢复；只能按实际覆盖升级Claim，绝不可从P1 Int示例推导到所有业务系统。

### 未实测与已定案各自记录

每例最小证据行必须有 `caseId | expectedBasis | actualInput | actualProducer | actualVersion | env | assertion | observedResult | coverage | log/artifactRef | verdict`。本页写出**期望**不构成实际结果，机器测试必须保存在真实可重跑仓库并出具指向受测代码revision的报告。某个失败若反证新设计不合理，回到责任owner修正并重跑相交门禁，而不是在旧设计旁边追加`exception: ignore`。

## 大型专业工程设计完整性与等价承诺的准确验收

### 首先判断请求出口是哪一种

本节的设计专用验收，适用于任务明确限定为“软件设计、开发者操作界面和工程蓝图”，且**不要求**生成TypeScript、运行`tsc`、启动进程或部署的情形。此时验收对象是确定的设计语义、接口与目标计划；若任务要求实际实现，必须另取相应运行与产品证据。设计层只允许根据当前 source/Requirement/Binding/Plan做静态一致性审查、覆盖映射、跨层反例和同源保全对比；即使真的对一份手写目标项目跑完测试，也不能证明 Gift 当前可生成或理解任意工程。只有未来真的产生可测试的 Artifact，才会产生相应运行/类型检查 Evidence。

### “完全等价”必须给出比较量词与适用边界

给定正式采用的要求集合 `R`、环境假设 `A`、观察接口及信息披露范围 `O`、目标集合 `T`、允许实现自由 `F`、被比较的主体与准确修订。对于每个被请求目标：

- **设计保持**：蓝图中每一项 `R` 都有准确的组件、接口、状态/效果/资源/版本义务及负责的作者或实现供给；不满足的硬要求不能被默认值、可用文件名或匿名 `any` 吞并。对应的设计完整性只证明规划是否充分、相交规范是否矛盾，不证明运行满足。
- **目标语义精化**（未来）：对所有满足 `A` 的请求输入与允许环境/调度，目标已实现产生的每条可观察轨迹都必须符合 `R` 的允许集合及安全/进展要求。若目标有规定的公平性、截止时间或故障模型，应加入相交观察；隐藏内部步骤只允许不改变要求观察。
- **双向等价**（当用户明确要求）：除上条外，还需要规范允许的相关观察在目标中能够对应实现，且必要的死锁/饥饿/错误与异常行为保持。只有单向 refinement 不能宣称完整交互互换，单次样例测试不能证明双向性质。
- **工程交付等价**（未来）：源布局虽可不同，但目标必须具有真实公开 API/ABI、配置与资产、合法依赖/许可、构建与打包、运行与持久化、升级/回退/运维、开发者可维护性，并在约定环境和版本下成立。源代码字节不要求一致，但公开兼容如被要求则不可任意丢失。
- **证据资格**：性质的证明、测试、静态分析、基准测量、部署读回、独立审查，分别对其准确对象、版本、输入、样本、环境及量词发言。作者目标和编译器自评不会自行升级为 PASS。图灵完备一般程序完全等价不可判定，不能要求一个无条件自动判定器替用户补足全部信息。

设计者可以要求“以后必须达到完全等价”，这会建立一条**未履行的实现/Assurance义务**；不能把未来承诺显示成当前已取得的证据。性能、安全、可靠性、真实硬件交互等存在环境依赖的要求，静态合同可以冻结其衡量方法与失败策略，但没有真正方法/供给时保持待证。

### 设计阶段的跨层拒绝门

| 门 | 当前能审查什么 | 不足时如何标注 | 绝不能代签什么 |
|---|---|---|---|
| G0 作者与权限 | 是否唯一owner/来源，真实作者接受是否发生 | Candidate/Conflict/Unknown | UI图节点成为作者权 |
| G1 内容 | 当前要求与规则能否组合为一致的系统合同 | Unsatisfied/Ambiguous/Need | 模型猜测替作者采纳 |
| G2 计算与协议 | 各组件数据、状态、事件、Effect/寿命、公开协议是否相容 | ContractConflict/Unsupported | `any`或黑箱脚本算完全语义表达 |
| G3 真实供给与Target | 选定库/方法/语言/运行端、工具和许可的资格及差额 | MissingSupply/Unsupported/Unknown | “目标语言有语法”算已实现 |
| G4 专业工程蓝图 | 作者/源码/构建/运行/资产/演进/验证多图能否交叉闭合 | PartialPlan/BlockingNeed | 画出文件树算生成应用 |
| G5 设计演进 | 新旧Revision、影响、迁移与不可逆边界有无合法处理 | Stale/Conflict/PlanNeed | 旧布局检查自动适用于新版本 |
| G6 未来实现证据 | 只列出需要独立取证的产品Claim和计划 | NotAcquired | `tsc`、测试、运行和部署仅凭设计文件获得PASS |

这些门是对现有 Assurance/Target/Workspace 对象的检查问题，不新增新的 `GateResult` 签发 authority。产品真实符合性测试仍沿已有方法、准入和 Evidence 生命周期，只有实际有可执行被测主体时才运行。设计审查不能以数出若干例数替代开放场景覆盖。

### 不回退的设计验收矩阵

至少使用四种方式检查本版与现有完整设计没有冲突：

1. **来源保全**：旧的独立规则及触发/结果/恢复边界在当前唯一owner可恢复；删除仅限有证明的同义重复，研究与反例不能悄悄升级成权威或被遗忘。
2. **正向映射**：从一个作者 `Requirement` 沿组件接口、实现供给、Target蓝图、未来可验证方法，能找到每个必要消费者及其未取得的资格。
3. **反向追因**：从一个目标源码/构建/运行/发布成员往回追到有权的作者事实和实际供给；任何悬空“生成”成员不得仅靠路径名自证来源。
4. **条件反例**：跨进程、跨租户、撤权、重启、并发编辑、目标语言差异、数据迁移、额外插件注册、不同环境升级时，仍保持身份、结果和权限制约。

具体验收记录应逐项写入准确输入版本、期待观察和尚未取得的证据。设计文档审查通过只说明检查过的设计问题，不等于 ProductGate 通过；实际源码尚未生成时，`TypeCheck(NotRun)` 应明确为未运行而非“空列表PASS”。[VS Code级综合设计用例](../../../fixtures/compositions/VSCode级开放工程设计覆盖与目标蓝图.md)和[开放系统反例](../../../witnesses/counterexamples/通用工程表达与专业蓝图失败反例.md)用于覆盖组合边界，它们均不取得第二份规范写权。

## 对开发者可见的结果与真实完成资格

开发者要求“生成完整专业工程”时，结果视图必须按所选根显示 `(设计已定义 / 目标已绑定 / 字节已生成 / 构建已检查 / 行为已验证 / 已获准应用或发布)` 的相互独立状态。产品蓝图若含未知Method/Target/toolchain，相关项显示精确缺项，不隐藏于一个总“预览成功”。

用户只要求设计时可合法在蓝图完成处停下，不应为展示绿色状态自动执行tsc或部署；实际有源码目标请求时不允许以人工编写的别的参考工程测试结果替代Gift生成的成品验证。

#### 验收承诺与实际状态的分界

对每个未来实现登记 `actualSourceRevision / authorOwner / sourceProfile / snapshot / exactDialect / binding / method / target / consumer / assertion / actualEvidence`。纯设计检查只能判断结构一致性、既有规范的组合与未决义务；原生实际语言服务器/编译器只能支持其真实报告范围。若未写产品代码，以上产品态案例一律**未执行**。在没有语义资格的 Profile 下，不执行无意义的目标 TypeCheck；在真实 Target 尚不存在时，不能借旧知识工具的 41 条测试、HTML 原型测试或本页反例数量填补证据。

**实现交接主序**：先完成唯一 `gift.project/1` 和新业务唯一候选 Writer `gift.author-module/2` 的读取/回写 Codec，并保持旧 `/1` 来源只读与显式迁移门禁、严格路径/Revision/SourceMap/导入锁、结构 Requirement 实例化及只读蓝图，再按实际任务纳入原生 TypeScript/Rust 适配、真实 Method/Target/Provider。Rust SDK 是可选共享语义客户端；新 `gift/author` 文本 Profile 在取得独立产品价值及可靠实现资格之前不占 P0/P1 必要门禁。各产品新增能力必须反映其真实合格范围，不能无条件宣称全语言/全系统等价。
