# 全域接合检查

本页只负责把**跨 owner 的真实接缝**路由到 canonical 合同与 Assurance 义务，不维护固定测试题库、行业矩阵或“全部都要跑”的检查清单。一个接缝只有在当前 Requirement/Claim/Target/环境实际相交时才实例化 ProofObligation；验证方法、工具、预算和 Evidence 由[验证计划](验证计划与证据编排.md)与[验证方法与故障设计](方法与独立证据.md)选择。

<a id="coverage-closure"></a>
## 覆盖声明与读取边界

Coverage 必须绑定准确任务、主体/revision、环境、已接受 Requirement/Claim、实际展开的合同和取得的 Evidence。目录出现、研究过、能解析、可保全、可实现、可组合、可生成、指定环境验证、现实用途成立与退出可恢复是不同状态；需要作者决定、供给、扩展、冲突、缺证据或未知也不能压成一个支持布尔。

领域研究与组合研究只负责发现候选区别和反例，不计入 Coverage。被实际 Claim 选中的研究推导、原始证明或实例见证可按准确义务与资格进入 Assurance；它可以只服务一个合法领域工程，不必先晋升公共 Core 区别见证。作为公共合同修改依据时，才另检查跨域稳定区别与 owner。资料存在不等于 Coverage，已有合格依据也无需为了进入流程重新运行。正式 CoverageAssessment 由[覆盖成熟度与验收范围](../保证/覆盖成熟度与验收范围.md)拥有。

<a id="test-subject-and-evidence"></a>
## 验收对象与证据生产

每个 ProofObligation 至少固定：被验证主体、revision/Binding/Target/环境、前提与输入域、要保持或拒绝的可观察结果、允许差异、失败/取消/恢复观察和 Evidence producer。只有实际执行/分析/证明并被接纳的 Evidence 支持对应 Claim；文档链接、字段存在、研究反例、工具数量和目录规模都不代签。

验证选择按**失效机制**而不是产品类别进行。通常先选择能击穿最强竞争错误实现的最小见证，再按 Claim 需要增加并发、故障、目标、现场或人类任务证据；不构造无意义的笛卡尔积，也不把“没跑不相交方法”记为失败。

## 高阶组合而不是题目笛卡尔积

两个机制各自合格不保证三方或跨层组合合格。只有存在**新的联合失效路径**时才增加组合 ProofObligation，例如：授权撤销 + 缓存 + 日志披露；恢复 + 容量 + 多层重试；共享资源 + 两个局部可行实现；旧代在途 + 新代切换 + 外部副作用。若组合只是各单项独立成立的并列，不新增案例。

同理，负例必须能区分错误实现；正常路径必须证明系统并非靠“全部拒绝”获得安全。方法数量、案例数量、行业数量、覆盖百分比或运行时长都不是独立的正确性指标。

<a id="gap-owner-and-reopening"></a>
## 未决、责任与重新打开

每个未决只记录：缺失的事实/实现、真实 owner、被阻断的动作或 Claim、仍可继续的范围、需要的决定性 Evidence 与失效/重开条件。一个缺口只撤回相交资格：缺强栅栏不否定离线分析，一种耦合失稳不否定所有数值计算，源码可复制不否定私有组合默认不公开。

只有出现新的公共区别、owner/合同变化、Provider/Target/环境变化、现实权利或权限变化、现有 Evidence 失效，或真实实现暴露新的联合失败机制时，才新增/重开相交 ProofObligation。规则已存在而实现未接通时修实现/消费者；研究只是换了行业名字时不增加 Assurance 工作。

## 跨领域组合验收的统一失败向量

产品级组合至少覆盖以下不允许整体PASS的情况：结构Rule合法但normal PredicateRef不存在；Callable类型匹配但错误路径无义务；Method声明覆盖却缺实际Publisher资格；Target画像存在但没有toolchain；TS目标生成源码而缺manifest/runtime资产；授权撤销后仍触发外部作用；远端超时后把取消当成回滚；旧缓存命中已删作者文本；Rust UTF-8字节索引与TS UTF-16索引混同；多文件源一半已提交而要求共同不变量。

每个见证必须注明期望阶段、可保留成果、阻断对象、具体残余及可恢复下一步，不能以“整体失败”抹去独立完成范围。 `fixtures/contract-closure/Gift95/`只检查前几个静态接口的有限形状，真实执行/Claim的组合测试仍是未来产品门禁。

<a id="design-b40"></a>
## 三条纵向合同的联合反证

支付与库存：库存预留和支付请求共享业务operation关联，但各自拥有真实尝试/幂等身份。支付Unknown时不得把订单判未支付后再次扣款，也不得把库存永远释放/占用却不记录后继；在明确保留期限与补偿政策下进入待结算，读回成功后提交库存，确定失败后释放，超时未确定按作者风险策略处理。没有共同事务参与者时，整体原子支付+库存的硬Claim不能通过两个本地PASS取得。

乱序流与修订发布：每个事件关联业务事件时间、去重身份及源修订；水位只是按已声明假设对完整性作判断。迟到纠正产生新结果revision和撤回/替代记录，经当前source/窗口epoch的CAS发布；旧worker最后完成不能覆盖更新revision。无限更新时仅保证不发布过期值，最终发布的进展须输入稳定/调度公平及任务能完成等假设，不能无条件承诺。

结构编辑与原生写权：语义工具从冻结source生成候选及受管target；用户同时修改原生region时，新的write-output只核并修改自身成员前像，不覆盖原生修改。若源映射逆写会跨入该region，返回OwnerConflict或采用为原生的明确候选。构建/检查只对同一实际快照有效，不能拿编辑前PASS给编辑后artifact签current。

上述每条结果保留根级coverage、每个Effect与Claim状态。一个世界域Unknown不把其它纯函数根判失败，但也不能让一个局部成功把联合请求全体涂成PASS。恢复围绕原身份和前像进行，不能在重试时建立一个看似全新的历史来丢弃已知部分。

**验证与反例**：三条具体事件序列分别触发局部正确而整体不满足；有限模型覆盖current/CAS与Unknown重启，外部支付/设备不实际派发。

**实际能力边界**：完整真实业务端到端与外部证据未运行；本次联合失败/恢复设计已写明。
