# 验证计划与证据编排

本页拥有 **VerificationPlan 的派生计划语义与证据编排接合**。Claim、ProofObligation、VerificationMethodSelection、Evidence、VerificationResult 与 Verdict 的字段及资格仍由各自 canonical owner 维护；物理 Action 的资源、重试、幂等和恢复仍由执行协议维护。因此 VerificationPlan 可以按需融合计算或缓存，不是第二套测试定义、第二个运行器或第二份裁决数据库。

<a id="gift-unit-20fd657871cf507e9cb409a7ecec47e1"></a>
## VerificationPlan：从 Claim 到方法与动作的派生计划

### 目的

`VerificationPlan`把目标程序、变更和工程声明编译为检查及证据依赖图，并仅对需要真实执行的方法物化动作。它明确要证明什么、在何种环境、使用何种方法、需要什么独立性和证据；纯求值、证明接纳和合法复用不伪装成运行。

### 核心对象

```text
Claim
Gate
ProofObligation
VerificationMethodSelection
VerificationAction
Observation
Result
Evidence
Aggregate
Review
Verdict
```

这些对象不能折叠为“测试通过”。

### 声明

`Claim`引用[唯一声明合同](方法与独立证据-义务方法与已有知识.md#canonical-claim)，包含有类型来源、owner、主体及修订、命题、适用域、假设、所需保证与生命周期／失效；本IR不再维护另一份只有自由claimId的接口。下游checker、gate和其他consumer是关系／索引owner维护的反向投影，不进入Claim identity。当前阶段可以保留所需字段的只读投影，但其来源仍固定到同一Claim修订。

声明可以是：类型性质、行为示例、状态不变量、关系超性质、统计性能、鲁棒性、恢复能力、供应链来源或运行效果。

### 验证要求

`VerificationRequirement`仅作为既有阶段中验证需求的称呼；其方法中立内容由[ProofObligation](方法与独立证据-义务方法与已有知识.md#verification-obligation-selection)承担，本次方法由VerificationMethodSelection承担，不单独持久化一套相同字段。引用必须解析到准确修订；输入缺项不能由默认值填成已满足。

不同声明需要不同证明方法。单元测试不能单独证明跨进程崩溃恢复；统计测试不能支配形式安全证明。

### 动作图

验证动作的选择与裁决流程唯一由[声明到裁决的证据链](方法与独立证据-义务方法与已有知识.md#声明到裁决的证据链)维护。本节消费其声明、对象、方法与范围，不再绘制另一条“所有测试→独立复核”的必经图。

实际执行的动作携带`ActionKey`、输入、资源、环境和完成状态；直接推导、已有证明及合格结果复用按各自依据关系处理，不伪造一次未发生的执行。
物理Action及ActionKey固定真实执行输入；准确义务和方法选择修订由逐义务Evidence接纳关系固定。只记录工具revision不能识别同工具下的Oracle、范围或证据资格变化，也不能为了不同义务重复相同物理计算。

### 结果状态

VerificationPlan 不定义独立 Result enum，只引用并投影[canonical VerificationResult](会话集成与结果复用.md#验证结果取得状态与聚合)及其 `VerificationEvidenceUse` / invalidation 关系；五个判断维度和状态含义不在计划层重复定义。现有 GateResult 的 `passed/reused` 只是物理兼容投影，不直接成为 Claim 资格。

因此，计划层不得把 canonical 的适用性、方法能力、取得方式、生产者结算和方法结论重新压成一个 pass/fail：`not-applicable`、`unsupported`、取消/超时/资源或基础设施失败、`indeterminate`、`supports/contradicts` 的精确含义均沿上述 canonical result。VerificationPlan 只据这些事实决定是否还需物化 Action、取得或复用 Evidence；只有当前合格的 `VerificationEvidenceUse` 才能参与 Verdict，Evidence 后来 stale/invalid 也只改变当前资格，不改写历史 producer/result 事实。

零个物化案例不能自行形成满足；但全部适用义务已由准确且仍有效的 DirectEvaluation／形式证据／历史Evidence解除时，可以没有新的 VerificationAction。执行器退出成功同样不自动形成 Verdict。

### 证据

依据类型和保留策略由[最小证据载荷](../保证/要求证据-追踪取证与裁决.md#设计判断运行事实与最小证据载荷)拥有。IR消费准确声明、对象、结果和适用条件，按来源保留不同内容：

| 依据来源 | 必要对应 |
|---|---|
| 实际执行 | 实际ActionKey、输入、方法、环境、观察及覆盖 |
| 可检查推导 | 所用规则、前提、推导关系及适用范围；不伪造一次执行 |
| 合格复用 | 原依据、前提匹配与本次范围 |
| 外部规范或资料 | 精确来源、支持命题、条件和限制；不冒充本地已运行 |

这些是原协议的消费关系，不定义另一份独立Evidence Schema。

需要长期采用的依据保存到可准确取得的内容及来源；临时CI页面不是唯一恢复来源。Evidence投影遵守保证规范的实际数据合同，不为每条纯表达式或设计推导强制创建持久证据图。

### 独立性

独立性按风险分级：

- 不同函数或模块；
- 不同进程和不可写候选；
- 不同实现；
- 不同身份；
- 不同环境和供应链；
- 外部认证。

候选产生者不能单独签发高风险发布裁决。

### 复用

验证结果只在以下闭包相同或有合法蕴含时复用：

```text
claim
+ subject revision
+ exact reachable inputs
+ test definition
+ toolchain
+ environment
+ policy
+ coverage
```

无关文档变化不应使编译测试失效；工具链、环境或权限前提变化必须局部失效。

### 发布资格

`Verdict` 可以作为提升输入，但合并或发布仍需要：

- 精确候选；
- 一次性授权；
- 当前目标前像；
- 分支或环境政策；
- 发布后权威读回。

### 验收

- 每个目标约束有 Claim 或明确非验证决定；
- 声明与测试方法匹配；
- 状态不压扁；
- 证据输入和环境闭合；
- 关键声明有独立复核；
- 复用合法；
- 陈旧传播局部；
- 合并和部署后读回；
- 验证器自身有符合性和故障测试。

### 组合执行与代际一致性

本篇VerificationPlan拥有验证含义和计划，不另写工具进程、资源、重试、幂等或恢复内核；这些动作通过已有操作执行协议完成。所有证据subject须解析到本次实际测试的模型/制品，不能仅绑定用户工作ID或最新分支名。

[发布资格](#发布资格)要求的发布后权威读回是该次发布的后置结算义务，不是发布尚未执行时的前置条件。生成结果、验证结论、当前写回状态和发布资格分别保存；同一请求总体显示Partial不能丢失已就绪输出，也不能把旧产物PASS借给新产物。跨对象映射以[流水线状态规则](../../30-实现解析/内核/输入与阶段总览-编译责任-阶段与目标.md#编译流水线与阶段边界)和[项目代际关系](../../10-作者与输入/作者源/工程源/身份断言与采纳.md#项目组成与表示等级)为准。

### 有限验收的subject与资格组合

`gift.acceptance/1`定义oracle出处描述、具名输入和预期结果；Int采用规范十进制字符串，Bool采用布尔值。Schema检查结构，应用另检查案例ID唯一性。它不包含执行授权、生产部署状态或任意代码脚本，不自动成为全部行为的形式规范。

构建记录绑定实际源码树及实际目标输出；行为记录进一步绑定完整代际引用、原始验收输入摘要、宿主身份和逐案例观察。应用只接受自己受信执行路径生成的证据，外部JSON或另一个会话的句柄不会成为通过证明。所需情境、允许的宿主与验收摘要由消费动作明确要求；缺少要求不等于偷偷推断某个全局安全等级。

同一subject和同一验收输入曾通过、后来失败时，不能用旧绿色遮住新失败。对同一分支的确定性验收，当前设计使用最后匹配记录处理该要求；统计或安全保证则按独立样本、时间、环境与撤销政策合成，不能把最后一次观察泛化成所有问题的真理规则。

有限验收可以失败而严格类型检查仍通过；未运行不是失败；目标运行异常与比较不满足分开保留。source→build→observed→verdict的单向引用避免自摘要和循环自证。回执完整性不等于签发者真实可信，跨系统消费必须采用实际签名/认证与资格检查。

## 从规范合约生成恰当的验证集，而非为文档数量造测试

先从每个启用的 operation/producer/consumer 合同抽出真实不变量、错误终态、物理适配能力和风险；再按可观察差异设计最小 Oracle。优先复用成熟标准、外部合格实现及其真实适用的测试；仅对新增语义、边界和已复现失败制作新的反例。`VerificationPlanItem{claimRef,exactSubject,producer,consumer,method,oracle,fixtureOrGenerator,environment,budget,expectedDistinguishingOutcome}` 必须有可判定的通过条件和不能通过的失败方式，不能写“全面测试”却没有可执行见证。

每种方法声明自己覆盖的维度：内容/来源保持、跨版本兼容、授权与撤权、故障注入点、增量/干净等价、目标行为差分、持续性能和供应链真实性。静态检查、契约级模拟、真正集成和物理现场 Evidence 不能相互代签。对同一缺陷不要在多个层重复执行无差别全库扫描；用依赖影响范围选择受影响的子门禁，最后独立跨源样本校核发布根。性能使用预先明确的硬件、重复次数、冷暖环境、置信统计和尾部阈值，报告失败不通过改阈值隐藏。

完整闭合验收包含 `PASS_FOR_EXECUTED_CHECKS`、`FAIL`、`INDETERMINATE_MISSING_EVIDENCE` 与 `NOT_RUN`，总门禁只对实际要求的 Claim 合成。任何手动豁免要记录责任、范围、理由、到期或重开条件，不作为可重用的普适证明。包含秘密或真实外部Effect的故障测试必须在受控环境/授权下执行，不能为验证而擅自触发生产支出或设备作用。
