# 实现解析与候选资格


### 减轻作者工作量的真正机制

开发者不应把目标先翻译成算法和框架名，Gift再逐句机械翻译成代码。业务定义应保留实现独立性；编译器从已解析的领域意义、完整角色、状态/事件/接口要求以及约束中查找适配的专业Method。Method是**实际已有**的代码、数据库/查询引擎、协议适配器、已实现的库能力、目标内建生成规则或合格原生实现；不是仅有名字的占位候选，也不是LLM自称会做的实现。


### 性能与可靠性优化边界

相同可观察行为才允许优化，必须包括错误/时间/副作用/资源等被业务声明为可观察的边界。SQL索引、缓存、并行、向量化、异步、批量执行、原生库调用等优化可能改变数据新鲜度、事件顺序、失败范围、事务原子性和成本；只有专业Method/Target确认约束成立才可采用。最终用户不被要求手写优化器IR；需要保护的业务性能限制应在Quality/Resource/Method合同里。

<a id="single-source-method-qualification"></a>
## 当前统一作者源下的实现资格入口

**在“可以表达”与“有可用实现”之间建立严格的独立界面。** 已绑定的一个 Requirement/Pattern/Workflow/CoreFunction 使用发生点，向 Method 仅提出 `RequiredSemantics`：名义签名、适用主体与世界范围、可观察结果、错误/终止、效果上界、数值/时序精度、资源约束、信任要求与目标限制。MethodSupply 的声明、代码来源和依赖锁只是候选来源；只有满足本次请求出口所需的硬条件，且准确保留后续 Provider/Grant/ABI 义务，才能建立该范围的合格绑定；[出口分层](#method-qualification-by-requested-exit)决定哪些必须现在满足。未选的候选不用为了显示列表而提前加入目标工程。

选择过程中，明确区分 `NoCandidateKnown`（未发现供应）和 `ProvenUnsat`（在已完整封闭的适用空间证明无满足解）；对于开放世界和预算中止，保持 `NeedsMoreSearch/UnknownQualification`。偏好只在相同硬语义约束内比较；不得因为某个库更快就容许改变错误行为或安全界限。多根共享实现可共用不可变代码但不自动共享运行实例、资源、授权或接受义务；各根的可见权/许可条件进入联合精化。


`gift.author-module/2`中无论是领域、工作流、产品还是四种旧意图Kind，都必须先达到实际的Meaning与联合Requirement资格。实现搜索只消费有来源的联合义务，不基于`kind`和供应名称选择模板。产品根的`workflowUses`、`policyUses`、`qualityUses`与`requirements`及组件实例的各类有类型参与关系，分别产生不同的实现与证明责任；仅存在供应Manifest或模块Export不等于`QualifiedBinding`。缺外部含义时`NEEDS_MEANING`，候选缺失时`NO_SUPPLY`，已证明约束矛盾时`UNSAT`，有限搜索未结束时`SEARCH_INCOMPLETE`；不得相互替换。

<a id="gift135-method-requires-semantic-qualification"></a>

业务作者不提供算法Expr时，Method选择仍不能靠字段名称推断实现。`capacityLiteral`、`thresholdLiteral`、`conditionRef`和`argumentBindings`只有先取得单位/名义/条件/主体/资源/观察等合格解释，才进入`MethodSpec`对前提、正常行为、异常、进展、并发与Frame的精化检查。`SupplyManifest`自述、Schema合法和找到同名实现都不能取得`QualifiedBinding`；真实供应缺失返回NoQualifiedMethod，语义缺失返回NeedsMeaning，合格搜索耗尽返回SearchIncomplete。业务作者无需因此改写为core:function。


<a id="method-qualification-by-requested-exit"></a>
## 合格绑定按请求出口分层，未决义务不跨阶段消失

先固定请求的根、Target、交付出口与要求的Claim，再判断每项义务的消费阶段。`QualifiedBinding`的资格范围必须带回这些输入；本章的“全部硬条件”指该出口现在必须满足的条件，不是预先取得整个部署未来的所有事实。义务阶段来自原Requirement、Method、Target和执行合同，不能由供给者为了通过检查随意延后。

- **源码生成**需要确定Meaning、真实实现或合格生成方法、类型/效果/接口与目标表示、完整内部成员及其保持责任。运行入口可以显式要求外部Provider、配置或Grant；前提必须有准确接口、检查位置、未满足时的阻止/失败行为和实际消费者。未知方法、空函数或缺内部成员不能转写成部署前提。
- **构建验证**另外消费实际工具链、构建依赖、获准工具执行和回执；生成锁定构建请求不等于这些工具已运行。生成方法若本身需要外部工具或Effect，必须先满足该生成动作自己的权限，不能借“只是生成源码”豁免。
- **部署或运行**重新消费当前环境、资源、秘密与Grant及其有效期，执行owner作最终准入。编译时持有的Grant不会变成制品中可永久复用的许可。
- **保证声明**按本次请求的证据强度消费独立依据。已有完整源码但尚无硬实时证明时，可交付准确源码与证据缺项；请求以硬实时保证为完成条件时，原请求仍未完成。生成可用不表示该硬要求被删除。

例如网络客户端的源码请求可以在没有生产凭证时完整生成：已有真实协议实现和目标依赖，运行时从受权句柄取得凭证并在未获准时阻止请求。若实现只有“未来调用网络”的描述，则仍为缺实现；若任务要求现在发送请求，则缺Grant直接阻断该动作。未知Provider行为、运行前可绑定的Provider实例和明确不合格Provider也分别保留，不能统一写成可稍后满足的假设。

后续补足义务只重评其准确依赖：Grant取得通常开启执行准入，不改源码身份；新ABI、Method或编译期环境事实会使相交Binding及目标贡献失效。恢复沿原阶段和当前基础继续，不能仅因Needs列表变空便沿用已失效的生成结果。跨阶段归因按[未决义务追踪](../../40-目标与制品/编译内核/诊断与追踪.md#need-provenance-and-resumption)保留。

## 新作者构造的Method资格输入边界

若本次已选根包含[开发者通用Definition提案](../../20-语义与组合/作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#developer-foundation-gift133)中的状态机、工作流、UI、查询、事务、外部Port或原生实现，Method解析必须针对**同一个联合Requirement和相交类型/effect/资源/时间/错误/权限**证明资格。新Kind可以被Schema读取，不等于存在匹配Method；找到Native符号或Manifest覆盖名称，也不等于生成的完整产品已经满足这些职责。缺已资格化的语义消费者先返回Need，不能提前转换成可执行候选。

<a id="gift131-method-root-coverage"></a>
## Method资格的根集合前提

### `Pattern`与`Method`的本质区别

`semantic:pattern`定义可复用的**业务/领域行为模式**，适用于多个实现策略；`Method`定义能够完成某个行为的**具体实现**。Pattern可组合成多步、跨实体、跨权限的行为，Method可以是一个细粒度库函数也可以是较大范围的引擎组合。一个模板不一定对应一个Method，一个Method不一定对应单个业务Kind。高复用价值来自Pattern接口、前提和结果准确，而不是把所有流行框架硬编码为语言关键字。

当一种新方法需要更精确的输入或限制，可按合格精化规则对Pattern要求提出交互，而不是静默更改原作者Meaning。同样，AI生成的建议实现只有经适用的供应与资格流程才能进入候选；在当前非计算设计阶段，不需要开发这套AI代码实现器。


方法搜索的输入不是“所有文件中找到的业务名”，而是当前Target与SourceRevision对应的一份已解释`JointObligationSet`，它必须保有`SelectedRootSet`中每个有效硬义务的来源与实际参数实例。Method覆盖关系要记录`selectedRoot → obligationOccurrence → candidateMethod → qualifiedBinding → targetMember`；若根集合新旧差异改变了已接受义务，旧绑定不得仅凭方法ID相同延用。没有合格RootUnion/Meaning/Norm/Observer消费者时，Method目录搜索最多返回带Needs的候选，不得先挑常见库再反向缩小作者意图。

空Composite或只匹配Manifest covers的候选不会满足其它独立Goal。更换Method之前的已派发Operation按执行Owner对账；纯计划失效与真实作用撤回分开。

## 可编码的Method检索与精化：输入、裁决和失败状态

**输入**：一份锁定的`JointRequirement`，包含强义务、软偏好、作用主体、资源/时间/Norm边及真实来源；另有固定候选供应登记、`TargetProfile`、环境/ABI、信任策略、搜索预算和已被作者固定的Control。**输出**只可能是：具有真实证明依赖的`QualifiedRealizationPlan`、经证明的`UNSAT`，或者明确的`NEEDS_MEANING/NO_SUPPLY/NOT_ELIGIBLE/SEARCH_INCOMPLETE/CONFLICT/ACCESS_DENIED`，不能统一成“失败且随便找别的方法”。

方法解析必须依次执行：①从供应声明找候选，但不授资格；②取得真实`MethodSpec`和实现字节/版本/许可；③核前置、输入输出、错误、可观察行为、Frame、并发、资源、终止/进展和外部效果；④按当前源、环境和Target建立资格化的实现对齐/桥接；⑤对全部相交目标联合验证组合行为，保留证明或未决；⑥先满足全部硬条件和作者固定选择，再按已授权的偏好比较。`SupplyManifest.covers`仅筛选，不证明第三步。绑定资格须记录所使用的SourceRevision、JointGraphRevision、MethodRevision、Target/Environment、ProofDeps和授权边界；复用缓存必须按这些准确依赖审查有效性。

当没有任何已取得的方法能处理未知领域，不得凭常见实现模板生成Stub；可以返回待补充Method需求，供专业供应者用TS/Rust/SQL/solver编写实现与测试。**可表达 ≠ 可自动合成**，搜索预算耗尽也不等于数学上不可解。对多目标选择，应验证共享资源和跨方法冲突，拒绝每个Method单独合格却联合违法的组合。完整用户范本故意不提供真实供应字节，因而不会签发Method资格。

## 供应声明、MethodSpec和正式精化签发之间的不可越权接口（Gift122）

实现资格有三个不可互代的对象：`SupplyManifest` 仅支持发现候选及读取供应自述；`MethodSpec` 指向实际实现并规定前置、后置、帧、异常、进展、效果、资源与版本合同；`QualifiedBinding` 才是在当前 Joint、环境、Target 与证据约束下取得的使用资格。`schema/supply/method-supply-1.schema.json` 中的 `covers/requires/contributes/preserves` 是声明字段，不是行为证明；字符串匹配和结构校验均不得单独签发 Method。

对每个真实候选`m`的正常路径和全部相关故障/并发路径，需要产生以下可检查的内部见证，均带`root/sourceRevision/methodDigest/targetLock/environmentScope/proofDeps`：

1. **输入覆盖**：在作者要求支持的域`U`内，所有已接纳输入满足`Pre_m`；方法对类型/单位/身份与无默认遗漏有真正处理。
2. **效果精化**：每种可观察结果与错误/取消/超时/未知均在 `Accept(J)` 允许的范围内，声明帧以外无未经授权的副作用；并行方法对共同资源保持联合不变量。
3. **非空洞进展**：受支持请求有正常成功/明确失败的完整定义；对于时间硬限制、有界资源、可恢复性等要求要有在对应环境下的实际论证。
4. **供应实物**：实现代码/库/ABI/运行时版本/调用主体及依赖真实可取得，锁与Target解析一致；仅有签名/范例/代码模板不符合这一条。
5. **证据与信任**：Method方的自述、工具构建结果、独立测试、权限和外部确认分开；至少取得对应资格等级的真实issuer及其检查记录。`EvidenceRef`字段本身不构成检查通过。
6. **搜索完整性**：可行方案、缺供应、已证范围内冲突、预算耗尽、未知前提、偏好不可比是不同结果；全局最优需额外完整候选域或限定策略证明。

Method 搜索不得改变任何已接受硬约束。候选即使分别履行不同意图，仍须把共享状态、资源、干扰、依赖、异常与最终装配纳入联合精化；局部通过记录不能直接拼为全局通过。无合格方法时保留 `AcceptedIntent` 与 `NeedsImplementation`，不得生成 Stub 代签、弱化规范，或强迫普通作者退回 Rust/TS 命令代码。新供应者可在不改行业 Kernel 的条件下补足 Method，但仍须独立核取安全、许可、效果和 Target 资格。

<a id="stable-method-refinement-contract"></a>
## 采用设计：从联合意图到合格Method集合的实际解析合同（R07）

Method选择读取[联合义务](../../20-语义与组合/组合/跨软件需求合同.md#stable-joint-requirement-contract)及当前Source、Policy、Target、环境、供应和证据锁；业务名称不构成选择依据。`MethodSpec`可由SQL事务、规则、状态机、工作流、优化器、UI或原生Rust/TS及受约束生成器提供，但每个候选必须指向实际能力与可检查的行为合同。只写`supports: xxx`属于目录声明，尚不能进入合格绑定。

| Method必须具备的合同端口 | 才能合法得出的推论 | 失效/反例 |
|---|---|---|
| 实际供应身份、内容Digest、发布者和可获取性 | 当前范围有可解析候选，不等于合格或可信 | 目录结果过期、供应包被撤销/不可用 |
| 输入/输出、类型、名义角色、域和量纲 | 接口调用可安全绑定及适配；正常输入覆盖须检查 | 仅相似字段或Type名不证明业务精化 |
| `preconditions`、`postconditions`、不变量和错误模型 | `AllowedInput ⊆ ValidPreconditions`且所有相关结果满足本次硬要求 | 只能处理成功输入、异常失真、缺正常功能 |
| `effects + Frame + readSet/writeSet + concurrency` | 具备作用顺序、无干扰、跨共享状态组合证据 | 两方法各合格但竞争同一资源时破坏容量 |
| progress/时限/资源上界（含需要的负载和环境） | 在明确假设与量化域下支持活性/硬实时/成本主张 | 仅平均耗时无法证明截止时间 |
| 权限/秘密/隐私/许可证/信任边界 | 所选Target/用途下能够合法调用，**不是**自动获取运行Grant | 合约由当前Provider/策略撤销 |
| 真实现方式、Target/ABI/依赖/配置与失败恢复 | 存在可完成的目标装配路径 | 有签名没有代码、可链接但缺恢复/数据迁移 |
| 证明/测试/外部资格及覆盖+新鲜度 | 对准确范围支持对应级别MethodClaim | Method作者自我声明不能给独立Assurance结果 |

`MethodSpec`里各条是逻辑字段；继续复用现有`method-supply-1`候选Manifest、MethodSpec、Claim与Binding owner，不新建业务作者必须填写的“方法配置”。原schema结构接受不是上述全部语义已证明。硬约束更严格的输入才可减少当前Method合法域，不允许因偏好或供应空缺改写硬意图。

### 资格算法和明确判决

<a id="method-discovery-eligibility-qualification"></a>
**三个结果类型绝不共用“available”布尔值。** `SupplyManifest` 仅说明某供应声称覆盖能力，`MethodSpec` 必须给出可检查的输入、前置、后置、Frame、异常、时序进展、并发原子性、资源、外部Effect和Target/ABI限制；`QualifiedBinding` 是在已冻结联合义务、Method版本、依赖、环境、证据和具体Target下取得的**有范围签发**。Schema匹配、字符串同名或供应自述不足以越过Method精化门槛。

搜索先固定所有实际根、候选目录与查询范围，再做有类型能力匹配和目标/许可/依赖约束。每个候选必要条件由已资格输入覆盖，所有相关可观察正常/异常/取消/并发行为必须满足硬义务、Frame与效果责任；时间/进展不满足则不能靠提高性能分数抵偿。联合资源求解覆盖**被选整组候选**；硬资格完全通过后，才根据作者授权的可比指标进行Pareto或顺序选择。输出必须区别`QUALIFIED`、`CONDITIONAL_NEEDS`、`NO_SUPPLY_IN_COMPLETE_CATALOG`、`PROVEN_UNSAT_IN_SCOPE`、`SEARCH_INCOMPLETE`、`PROVIDER_UNAVAILABLE`、`EVIDENCE_EXPIRED`；这些是概念性裁决种类，不与现有对外Error协议混写。发现新更优Method只撤回真实订阅最优性的资格，不能自动撤回仍满足功能的旧Binding。

无合格方法时，保留作者意图和未覆盖义务，返回精确Need供有权专业作者补方法；不能静默生成空函数、`throw NotImplemented`后仍签完整源码、或把原意图转回强制业务作者编写低层算法。只有在额外获得相应授权及当前适用检查时，候选实现才能进入下一阶段装配；Method资格本身不发行运行Grant。


```
resolve_methods(joint, candidateClosure, target, budget):
  A = discover_by_typed_capability(joint, locked_catalogs)   # record negative queries
  B = check_signature_versions_law_targets(A)               # reject known-ineligible
  C = check_semantic_refinement(B, joint)                   # pre/post/progress/errors/effects
  D = solve_joint_bindings(C, shared_resources_and_frames)  # no per-goal concat
  E = check_actual_supply_target_deps_evidence(D)           # capability vs obtained proof
  F = pareto_and_lexical_policy(E, hard_then_soft)          # incomplete ≠ global optimum
  return QualifiedPlan | ConditionalCandidate+Needs | ScopedConflict | IncompleteSearch
```

候选集为空时先区分：所声明搜索域是否完整、该域是否缺 Method、联合要求是否有真实硬冲突，以及搜索预算或能力是否不足；缺供应不得冒称 `UNSAT`。新领域可增加外部合格 Method，而不扩充 Kernel 行业枚举。只有生成出口的硬资格合格、内部实现及成员闭合的候选能进入完整源码产物；运行和强保证资格不得据此推定；未委派的价值取舍由有权作者选择，已授权的确定性政策则依稳定 candidate digest 与顺序键裁决，不能依赖目录遍历的偶然顺序。

### 精化的形式边界

在明确输入域 `U`、环境条件 `E`、观察域及证据级别下，至少需要：`∀u∈U . Pre_M(u,E)`、所有相关实现轨迹 `Beh(M,u,E)` 满足 `Accept(Joint,u,E)`，以及独立的正常功能、终止/进展和非空洞要求；单纯禁止性质可能让永不响应的实现虚假合格。真实外部 Effects、并发和时间须由其真实 Trace/Provider 合同证明，不能仅依据 TS 返回值。此处 Method 精化 Claim 不授予执行 Grant，也不等于现实完成。

**分层搜索与负依赖**：按无共享冲突的耦合组分解，保持跨组共同作用限制；每个候选扩展都记录真实依赖及排除证明，预算包含搜索/求解/基准/迁移。新增供应、负查找和旧绑定的不同失效按[局部失效](#method-catalog-invalidation)处理。任何fallback须重核前像/幂等/未结算原Operation，不能因新Method存在就重复旧Effect。

方法是否合格的唯一语义仍在本篇；实际候选目录、负依赖、资格过滤、组合搜索和缺项后继的实现算法见[实现选择施工设计](../../70-工程系统与演进/工程构造手册/05-要求实现候选与资格.md)。

当前责任是具体实现的发现、资格、约束协调、绑定失效与反馈；工程设计候选结构由[设计空间搜索与求解](设计空间搜索与求解.md#设计候选结构判定冻结与采纳)拥有。本篇不承接此前物理文件的历史说明。

## 实现解析算法

### 问题定义

实现解析对每个 `ImplementationRequirement` 在当前候选闭包中形成可解释的设计候选或动作绑定。设计候选明确假设和缺口；真正执行绑定需要满足该动作的硬约束、证据和目标条件。缺少生产资格不禁止输出实现设计，不能将设计选择和执行资格合成一个布尔值。

这里的实现候选（Provider / Realization / Binding）不同于[工程设计候选 `DesignCandidate`](设计空间搜索与求解.md#设计候选结构判定冻结与采纳)：只有责任分配或行为合同仍待设计时才进入后者；前者不因此取得修改已采纳 Requirement 的权力。设计提案的 `candidateRevision` 与 `basisReadSet` 要求在采纳前做前像及负依赖检查；采用设计后的正式事实可供本实现解析读取，但旧提案的有界评估不自动成为可执行 Binding 或供应链资格。

### 候选闭包

```text
CandidateClosure(requirement) =
  existing realizations
∪ built-in references
∪ reachable package candidates
∪ registered providers
∪ allowed synthesis candidates
∪ explicit user candidates
```

候选发现按能力关系而非品牌字符串。发现过程记录数据源、查询条件、版本范围、完整性和失败。

### 解析顺序

具体流程由本章[候选搜索与裁决](设计空间搜索与求解.md#候选搜索与裁决)及联合方案算法维护：已有合格绑定直接使用；真正缺少实现选择时才建立有限候选问题。声明、设计绑定与执行资格分别返回，本节不再维护第二幅竞争流程图。
硬约束不能被偏好抵消，但“尚无证据”不等于“已证不满足”。先限定当前动作与声明：设计可保留条件候选；执行仅采用其真实所需资格已满足的绑定。仅修改偏好不会凭空取得权限。

### 硬资格

至少检查：

- 语义契约覆盖；
- 目标语言、运行时和平台；
- 输入输出和错误模型；
- 效果、幂等、取消和读回；
- 数据、权限和隐私；
- 资源硬上限；
- 许可证与供应链；
- 版本和兼容；
- 当前可获取性；
- 所需符合性证据。

未知条件按具体动作判断：缺真实权限不准执行相应效果；缺业务语义不准声称生成正确；缺生产性能不阻止实现候选及获准基准实验。带假设的设计绑定记录未满足义务，不能冒充当前可执行绑定；硬性安全或权利约束不能被候选偏好抵消。

### 偏好比较

合格候选构成非支配集合。比较维度带单位和依据：

```text
运行时延迟
内存与 CPU
实现和迁移工作量
维护边界
恢复能力
供应商锁定
许可证义务
安全暴露
离线可用性
长期支持
```

只有有权策略可以定义词典序或标量权重。

### 决定确定性

相同：

- Requirement revision；
- 候选闭包及其 revision；
- 资格规则；
- 证据；
- 策略；
- 目标画像；

必须产生相同非支配集合和排序。若现有委派和偏好仍不能决定真实价值差异，算法返回准确的待决候选，由实际有权主体决定；已有合法选择规则时直接使用，不依赖集合遍历顺序，也不默认强制人工。

### 用户控制

用户可以：

- 增加或收紧约束；
- 表达偏好；
- 禁用候选来源；
- 显式选择合格候选；
- 要求自研；
- 接受限定风险。

用户不能通过名称锁定绕过安全、许可证、语义和权限硬约束。

### 多 Requirement 协调

独立逐项最优可能导致全局冲突，例如版本不兼容、重复运行时、共享资源或循环依赖。系统构造联合解析问题：

```text
JointResolution =
  per-requirement eligibility
+ cross-binding constraints
+ shared dependency constraints
+ target-wide cost vector
```

规模过大时使用分解、冲突回溯和近似，但必须声明完整性边界。

<a id="joint-control-qualification"></a>
### 联合控制的资格、时序与持续寻优

联合条件由真实共享关系形成最小耦合组：对象别名、资源池、初始化、ABI、原子可见关系、期限和允许观察分别作为边。不要求所有候选进一个全球求解器，也不能仅因文件不同就独立选择。子问题输出仍需满足跨组边界；新候选新增依赖时重建相交组。对串行可释放资源和同时存活峰值分别计算，不能把所有局部数值简单相加或取最大。

硬要求、禁止和精确pin共同约束可行集合；软默认按明确规则合并，偏好只在合法域排序。组合还需所请求证据资格与实际目标能力；数学可行、供给可取得、执行已授权和运行已生效不是一项结论。搜索预算结束保留已找到的合格赋值、未探索范围和缺证据，不生成UNSAT；只请求可行时不用强制求全局最优。跨域摘要只能在前提真实组合时用于剪枝，未知界只能调整探索顺序。

在线自适应的候选可以是完整的**政策**：固定目标、可调变量、观察定义、允许动作、成本／风险范围、停止与接管合同。编译期选择政策，实例内选择当时值；二者分属绑定与运行轨迹。政策的检查需覆盖允许变化及失败路径，或明确只验证了有限观察，不以初值合格证明全部未来轨迹。执行合同见[在线调节](../../50-执行运行与观测/运行生命周期/运行实例-订阅部署与调和.md#adaptive-runtime-control)，不另建一个编译器外的自主决策系统。

持续寻优只在明确订阅／委派范围内重新评价；记录真正读取的候选集合、筛选条件、负查找、成本模型、测量及比较规则。相关新候选使最优性证据重评，不必使旧合格实现的功能保证失效；显式pin且不观察候选目录的使用点不跟随目录变化。关键安全或语义资格被反证则立即限制相交新作用，不等待收益改善阈值。

探索成本包括枚举、求解、基准、模型调用、迁移、双版本共存和恢复预留。自动系统可以在委派内选择稳定合格解，不能通过新会话、换Provider或改实验名称刷新预算。比较结果受数据挑选、观测误差或反馈过拟合影响时，采用独立确认或任务允许的条件性结果；不把自带验证器和自报成本当独立资格。

解释给出要求与来源、适用域、已检候选、被排除条件、选择依据、未定比较和下一合法动作。只有已计算最小冲突核才称最小；敏感候选及其存在性遵守披露权限。用户可以固定实现、禁止候选、提供自写方案或调整有权修改的要求；自动方法不得代替用户进行未经委派的价值取舍。

### Binding 失效

以下变化触发局部重解析：

- Requirement 改变；
- 被选候选 revision 或能力改变；
- 相关证据陈旧；
- 目标画像改变；
- 许可证、安全或政策改变；
- 依赖不可获取；
- Provider 成熟度或健康下降。

未绑定的新候选出现是否触发重解析由“持续寻优策略”决定。

### Fallback

运行故障不会直接修改绑定。Fallback 流程先判定：

- 当前失败是实例故障还是候选能力失效；
- 原效果是否可能已发生；
- 是否允许同候选新实例；
- 替代候选是否满足相同硬约束；
- 数据、权限和兼容是否变化；
- 是否需要新批准。

### 解释输出

解析结果提供：

- 候选来源；
- 每项资格结果；
- 被拒绝原因；
- 非支配比较；
- 用户或政策决定；
- 假设和未知；
- 失效条件；
- 可替代候选。

### 验证

- 候选顺序随机化不改变结果；
- 不合格候选永不被偏好复活；
- 联合解析捕获跨绑定冲突；
- 候选撤销只失效真实消费者；
- fallback 不扩大能力；
- 不完整候选闭包不宣称全局最优；
- 决定可以从输入和回执重放；
- 恶意候选声明不能绕过证据。

### 有界求解和具体默认映射

[工程情境组合与能力协商](../../70-工程系统与演进/演进与实施/适用性与能力协商.md#工程情境组合与能力协商)给出请求闭包、开放事实与候选计划的有限交换格式；[物理实现画像与可逆落位方案](../../70-工程系统与演进/实现与装配/模块与运行实例-成品装配-实际对象作用域与入口闭合.md#物理实现画像与可逆落位方案)给出四种具体实现映射。该有限设计路径处理显式有界DAG和等值条件，不声明能够求解任意约束；当前设计包未提供相应Gift产品解析器。

生产扩展按以下顺序回溯：先剔除已证伪硬约束，再选择策略允许的候选；展开依赖出现冲突时撤销该候选的暂存绑定和独有依赖，保留共享已证实条件；尝试下一候选直至得到合法闭包或预算耗尽。结果包含已排除候选及理由、未搜索候选和已满足的独立输出。预算耗尽为unknown，不是无解；有可检查冲突核时才给相应不满足声明。

<a id="finite-abstraction-realization"></a>
#### 有限抽象方法进入原实现选择

[有限抽象与观察策略](../有限抽象与观察策略.md)唯一维护充分抽象判据、共同合法结果、反例具体化、精化和有限策略构造；本节只规定原实现选择的接入，不再复制第二套求交或固定点规则。普通固定绑定继续直接复用；只有相交任务确实要求合并表示、选择共同实现或验证有限抽象时才激活对应MethodSpec。

方法输入沿原Candidate、requirementRefs、ruleBindings、ReadSet和Obligations取得：准确合法域及枚举依据、完整观察合同、拟议投影、结果或合格结果判定、候选结果/方法的实际编码与绑定、资源预算，及允许改动的来源范围。隐含状态、环境和连续调用影响合同就进入模型或相应交互方法；缺少可靠枚举时使用合格符号方法、保留具体缺项或已有正确实现，不能只列样例后声明穷尽。

取得见证后将它绑定到原selectedUses/RealizationPlan的真实方法、参数与coupledGroups。类型、效果、阶段、分发、源映射、内存与ABI仍核实际目标；有限查表不提供任意未来T的原生泛型API。未物化的普通主体返回NeedsAuthorContent，缺目标方法保留Unsupported/Needs，数学存在性不冒充源码已取得。不同抽象类共享参数、状态或资源时必须接受同一组合检查。

失败由原协调器区分：真实冲突、抽象精度不足、无法取得的信息、供给缺失、预算结束。反例支持合法精化才重算相交类；不得放宽原要求、改变所需观察或把私有未来信息变成读取端口。精化停止/复用与有限/开放域的区别由方法正文定义；相同确定性失败不盲重试，已有独立合格结果仍保留。

发布前核要求修订、域/候选集合、解释和实际读集，包括成员全集与否定读取。相同结果只允许共享计算，不继承另一范围的完整性或采用资格。[特化与结构查询](../特化与结构查询.md)和[目标能力履行](../../40-目标与制品/目标/能力履行与接口差额.md)消费同一接合；参数包、反射、原生导出与资源缺项保持局部，不新增全局求解器。

## 固定输入下的实现选择算法

输入为实际语义要求R、目标T、已冻结候选目录C、已接受的选择政策P和搜索预算B。实现者可以用索引取得候选；索引只减少检索工作，不重新决定业务。普通源里的显式符号已绑定时直接使用该绑定，不再次调用AI或全库搜索。

**候选全域前提。（消费条件）：** 共享Provider容量和互斥关系可能跨多个发现源；枚举仅部分可见时，最多得出已见候选的有界选择，不得宣称全局最优或总不可能。 合同归属：[跨源读取的观察切面、因果闭包与不可见参与者](../../70-工程系统与演进/信息与生命周期/对象关系与配置基线.md#gift-joint-snapshot-closure)。

**候选否定资格。（消费条件）：** 查询缓存只能提供候选证据，不能把一次受限扫描的空结果提升为不可实现或最优结论。 合同归属：[负结果、开放供给与增量重用的证明范围](../增量与性能/查询固定点与缓存.md#gift-negative-dependency-proof)。

### 候选记录与资格

每个候选记录其实现身份/版本、提供和需要的合同、支持的数值/效果/目标范围、真实依赖、已知成本依据、可用性来源和验证义务。资格分别有“已满足、明确违反、仍需条件”三种结果；不存在用未知默认通过的第四种隐含路径。

**RES1 约束规范化。**核对单位、范围、目标角色和硬/软要求。把Require/Forbid/Pin转换为显式选择限制，Prefer保留为合格候选内的排序。不能由搜索器重新解释用户未委派的目标。

**RES2 确定候选范围。**从显式绑定、已接受定义提供者和所选目录读取候选；没有发现范围以外的实现不证明它不存在。读取的过滤条件、成员集合和阴性结果进入依赖，以便新增合格实现时正确失效。

**RES3 检查单项与组合。**先过滤明确违反硬条件者，再执行[组合边界闭合](../../20-语义与组合/共同语义/边界摘要与跨域组合.md#组合边界摘要与义务闭合算法)及其[支持与进展算法](../组合前提与进展闭合.md)。条件保证保留其未满足前提；无种子循环不得自证，合法反馈按真实初态/转移/进展方法处理。单项类型合格不能覆盖值域、初始化、权限、共同不变量与共享资源；缺证据仍可形成条件设计，不能成为无条件运行许可。任务要求修订保持独立，不能收紧入口来获得形式合格。

**RES4 搜索有界路线。**按已接受的优先序扩展候选，积累真正需要的依赖；有条件/量化/备选的作者输入按[作用域选择规则](#scoped-realization)保留整体关系。遇冲突回退到最近影响该冲突的选择，不整棵丢弃正确工作。循环实现依赖按调用、初始化、静态固定点或运行反馈分类，采用各自规则；没有合格解释时返回相交缺口，而非把所有环统一接受或拒绝。部分方案按J1—J6保留后续可观察边界，只有合格比较才剪枝。每步记录消耗的节点、字节、时间或实际工具预算；耗尽时输出已检路线与未决范围。

**RES5 裁决和固定。**候选涉及未完成的生态解析时，先走[解析回交](#ecosystem-resolution-reconciliation)，用实际闭包重核RES3/RES4及比较输入；未解析的成本只用于有界探索，不能冒充最终排名。用户要求或已接受的任务/项目政策确定偏好维度与可逆默认，不必由用户每次重填；有限数值偏好依[分层偏序](#preference-partial-order)区分支配、相等、折中与未知。多个合格候选且已委派选择时，先应用优先政策，再在政策允许的等价备选中以稳定规则选取；若差异影响未委派的业务或风险，则返回少量真实备选和要决定的维度。只有一条合格路线且已在接受的选择自由内时直接绑定，不为仪式增加批准；唯一性本身不代替相交选择权。

**RES6 产出可重建绑定。**只有本次用途必需的解析结果和相交资格已核对，才记录选定实现、参数、规则版本、实际依赖、拒绝原因和剩余验证义务。后端消费它，不再按live目录重新挑选。运行时可用性与授权在实际准入时复查，固定内容不等于永久可用。

绑定的用途与资格保持分开：验证候选可以形成真实可生成的选择以取得证据，不因此成为生产合格路线。生成遍的实际结果经[接纳与失效](../../40-目标与制品/编译内核/变换接纳与分析保持.md)返回；可选优化失败可以保持仍合格的旧选择，明确要求的优化或受影响原方法不允许借回退报完成。

<a id="realization-binding-handoff"></a>
### 选型结果、正式绑定与UseBinding之间的唯一交接

RES5拥有本次已委派范围的Decision，RES6形成不可变RealizationBinding；RealizationPlan/selectedUses是计划中的选择视图，UseBinding是该Binding在准确使用点的消费投影。三者不能各保存一份可独立改选的实现。`resolveUse`可以在一个函数内协调原RES算法，但不由UseBinding构造器、lowering回调或缓存另作选择。

正常已锁构建直接核现有Binding与本次用途资格，再形成UseBinding。需首次选型或新约束导致旧选择不合格时，RES按固定输入、目录和已接受委派产生Decision与新的Binding；此前的计划仅保留试探分支。没有相交委派则返回具体未决，不因为只剩一个候选就获得修改业务或扩大风险的权力；已委派且只有一个合格候选则无需仪式性确认。改变作者Requirement/Control仍由其原owner接受，与在其自由内选实现不同。

Binding的最小交接关系是实际Requirement/accepted contract、被选Candidate/Method/Provision及精确输入，Decision或适用既有委派依据，目标/使用范围，参数/适配和实际依赖，及本次用途资格与未决。可从已有对象引用取得，不复制全字段。`UseBinding.realizationBindingRef`必须可解析到这个准确不可变值，并与useRef、target、acceptedContract和实际方法相符；验证候选可以携带其真实未证义务，不能以引用存在代签生产资格。

纯compileFrozen内首次形成的Binding是**该结果的选择值**，随原分根结果与来源保留；它不写工作区锁、不推进全局current，也不热改输入EngineImage。需要持久采用时，application把它交原作者/锁保存协议；选择的资格与保存权分开。进程内可以直接引用不可变Binding及依据，不为每次函数调用生成持久Decision事件或中心数据库记录。没有待选替代的显式源调用只引用其现有源/导入绑定，不为每个调用重新搜索或强造一个独立Decision对象。

新适配、生态解析或公共布局引入更强条件时，回到相交RES3—RES6产生后继Binding，再重建UseBinding；旧引用仍解释旧选择。共同实例的多个use在同一组合闭包内核一致性，不能让每个lowerer先挑一个再把冲突留给链接器。失败保留原合格Binding和独立根；纯候选回退不重放已启动的外部Attempt。

### 搜索结束怎样回答

| 实际状态 | 返回结果 | 后续动作 |
|---|---|---|
| 找到满足硬条件且符合选择政策的路线 | 选定Binding、依据和所需后置验证 | 正常编译；运行前仍准入 |
| 路线可成立但有未证实的环境假设 | Conditional方案与逐项假设 | 可继续设计；相应保证待取得 |
| 所检有限范围内所有候选均有具体矛盾 | 局部冲突集与实际检索范围 | 修改约束、补实现或换目标 |
| 有多种未被政策裁决的非等价方案 | 有限备选及真正未决差异 | 取得明确选择，不任选业务 |
| 预算耗尽 | 已找到路线、当前最优性范围及未探前沿 | 目标只要求可行且已有合格路线时可用；要求最优证明时保留不足 |

“可行”与“已证明最优”分开。若无法统一比较费用、延迟与维护风险，就保留各维度，不制造通用权重。一个比较过程产生的最快方案也不自动满足原生兼容、隐私或恢复要求。

### 例：同一锐化算法选择目标

目标要求精确整数结果、Clamp边界和禁止网络；候选为CPU顺序实现、需要设备的GPU实现和远程API。远程路线因禁止网络被排除；GPU缺设备事实时保留条件方案；CPU在已知范围满足要求则直接选择。若用户Require GPU，CPU不再是回退，返回设备/提供者缺项但保留源候选。增加一个未匹配的排序库不改变这次绑定。

默认先使用完整且简单的有限搜索/规则匹配，再根据真实热点加入索引与学习排序。学习只影响查找顺序，最终资格仍由同一合同检查。更小替代是用户显式Pin一个已合格的实现；只有真实需要多候选时才进入搜索。

<a id="scoped-realization"></a>
### 有作用域的选择必须产生同一套实现

RES3/RES4消费[有限结构组合](../../10-作者与输入/作者源/结构化源码.md#finite-requirement-composition)及原领域RequirementTerm，保留合取、备选、条件、量化绑定和共同主体；不能先抹掉这些关系再把叶项独立选型。所选结果先沿[唯一交接](#realization-binding-handoff)形成Decision/RealizationBinding，再投影到原RealizationPlan、selectedUses和最终UseBinding；没有三个独立选择writer，也没有新的求解对象存储或公共工具。

**可满足的关系与可实施的策略。** 针对一个固定设计配置，要求的是“存在一套允许的方法、代码和运行策略，使其对该配置允许的全部输入与环境满足要求”。这不等于“每个输入各能找到一份不同程序”，也不等于“每个测试案例都有某个实现通过”。选择可以包含一个按运行输入调度的真实策略，但该策略本身须先被实现、固定，并遵守观察顺序、权限、状态和因果性；不能让生成程序请求知道未来才能决定的值。

例如要求在尚未取得下一次环境比特前输出与它相同的比特。每个单独未来场景都存在一个对应常量，不说明存在一个允许观察范围内的共同程序。这里不要求任意反应式问题可判定：有明确反证可判定该范围不可实现；没有策略或证明方法就保留缺项，不能将一次逻辑模型冒充可运行代码。相反，若输入已合法到达后才要求输出它，普通回传策略即可，不应因“存在所有输入”而一律拒绝。

**设计见证的作用域。** 有限forEach的每个已固定成员可以有本地exists见证；外层exists只有一个见证，须同时满足所有内部成员。固定后不依赖未取得的后续运行输入。两种排列不能交换；一组共享逻辑主体也不能靠在不同分支偷偷复制成两个实例来解除冲突。仅比较私有数值相同或类型签名相同，不足以合并主体。

**联合搜索的具体执行。** 先核根、域、参数、Rule含义和偏好范围。维护现有工作表中的作用域环境、共同约束、尚未选定分支、局部见证、真实读集及未解义务。all把条件加入同一个分支环境；已固定when只激活对应体；forEach按准确出现实例化；any/exists按已委派有限顺序探查，并在同一分支中核全部共享条件及方法前提。失败只回退依赖该选择的工作，完整输入不变的纯子结果可共享。条件未知、域不完整、语义未定义或预算不足均不作为排除候选的证明。

求解器可以传播条件或延迟枚举，不先扩成可能指数大小的DNF。每一项被剪去的范围需要真实反证或足以比较其**全部后续可观察边界**的依据；某个局部组件更便宜不够。两个分支都能单独工作却分别需要独占同一资源时，RES3必须在共同主体处拒绝直接组合，或取得真实的共享/串行适配并重新核约束。方法A假定B、B假定A的圈不能自证，仍需初态、保持与实际前提来源。

**完整性和返回。** 一个分支及其实现共同满足全部硬条件，才能作为可行方案；解释阶段只能证得有限逻辑一致时，结果仍是设计可满足，不是供给已实现。只在声明的候选与域覆盖完整、全部分支均有排除依据时，才返回该范围不满足。方法库空、局部超时或一个后端不支持，不足以宣称需求世界无解。找到可行者但未完成优化时保留可行成果及优化前沿；用户只要可行可以结束，要求最优证明则如实保留那项不足。

**生成与现实作用。** 见证、所选分支、方法参数和共享主体对应随原绑定固定。编译残余不能再挑一次另一个分支，也不能在字段目录/索引升级时换解释。探索时取得外部资料或执行测试，仍先形成原Needs/CheckRequest，经实际准入取得记录再进入后继输入；拒绝的分支不应先把其依赖全部装入用户工作区。丢弃搜索节点可以释放本任务私有临时资源，不能删除共享内容、已采用的源或在途执行记录。真实应用、安装和发布的权利与最终前像仍在原执行边界核验。

<a id="preference-partial-order"></a>
### 分层偏好比较：未知和折中不会自动降到下一层

本节给RES5及quality.Cost一个确定的有限比较算法，不引入通用“最优分”。首先分开硬资格成立、硬条件已违反和仍有假设的候选。需要无条件合格的任务只在第一组作最终选择；其余组可以保留条件方案，不能因性能数字较好越过资格。

一个偏好比较的输入来自原需求及成本记录：准确主体/工作负载、指标与单位、起止/采样/统计口径、越小或越大为优、优先级、约束或测量依据、实际比较范围。这些字段由既有定义和记录提供，不要求产品作者填一份平行成本表。工作负载、目标或统计口径不同的两个数不能硬比；平均、百分位、最坏界与硬期限不能互相顶替。

按priority从小到大比较两个合格候选：

1. 同层所有准则均有足以判定的同口径关系，且每项不劣、至少一项严格更优时，该层形成Pareto支配，决定这对候选的偏好关系。后层不能补偿已经确定的高层损失。
2. 同层全部已证明相等，才进入下一层；全部层相等则保留等价选择。
3. 同层存在互有优劣的折中，保留非支配，不用下一层消掉高层不同取舍。存在缺测、不可比较或重叠区间而不足以证明方向/相等时，保留该层未定，也不跳去下一层。区间有重叠不等于相等，有限样本无显著差异也不等于已证明同成本。
4. 有真实上下界时可以取得支配证明。例如同一指标最小化时A上界严格小于B下界，足以判定该指标A更优；不需要把所有区间任意压成平均值。没有合法全方向依据时只影响探索次序，不用于保证型剪枝。

同一准则通过多个use/forEach重复出现时，按主体、指标、工作负载和解释识别其关系并保留各来源；不因重复次数给它隐含加权。不同主体不是重复准则，若任务要求比较组合总成本，需要显式组合成本合同和共享资源的真实核算，不能直接把几个实例报告相加。

**可行选择与优越性结论分开。** 无法判定排序时，已有委派仍可使用原合格绑定、已声明保守策略或稳定次序选一个可行者；记录选择依据为该策略，不说“已证明更快/更省/最优”。公开业务差别或风险不在委派内时，保留真正需要决定的内容；不是所有未知测量都强迫反复问用户，也不是为保证每次有答案将未知填零。

算例只说明比较机制：M的驻留内存未知、延迟1ms，N为40MB、8ms，内存优先于延迟。缺少M内存时，不由延迟判M更优；若后续同口径确定M为60MB，则N在第一层胜出；若两者内存都确为40MB，则第二层判M更优。这些数字不是本工程实测、阈值或SLA。低内存和低延迟处于同一优先级时，60MB/1ms与40MB/8ms是折中，两者都保留。

偏好变更、工作负载变化或新证据只重开相交比较与绑定；普通重建不重新跑基准。已选内容仍沿准确锁重建，存在更新证据不会改写旧检查和运行来源。

<a id="gift-partial-optimality"></a>
### 开放候选域下的局部最优、不可实现与停止证书

实现选择需要明确**可搜索候选域**、资格判定是否完备、硬约束是否可判、资源上限及本次搜索预算。只有对有限闭合候选域获得全体资格判断及可比较目标时，才有资格写“该域的最优”；对不可判条件、外部未接入Provider或动态出现的新实现，只能返回已见可行候选、尚缺输入、搜索覆盖和改进余量的依据，不能把求解器timeout或`not found`当作全局不可实现证书。

硬约束、偏好与成本/性能目标不能互换。若两个候选部分维度不可比，维护Pareto有界前沿或要求真实作者做相交偏好决定；没有证据不发明一个综合评分把不同单位相加。允许在有资格的有限最优上继续工作，也允许明确选定“足够好”候选；后续新候选不自动撤销当前正式Binding，但请求重新评价或相关资格失效时须以新的准确basis执行决策。反例：只查询到两家供应商，其中一家缺报价；不能凭有报价那家较便宜就宣称全市场最优。

## 开发者不点名轮子时的正向实现绑定

默认输入是可解释的行为/接口要求、实际目标、现有工程依赖、禁止项与已委派的选择策略，不是每个功能的第三方库名称。作者主动指定的库、算法或框架是额外约束；自动实现选择是编译系统的正常责任，不被写成另一个需要作者完成的任务。

**SELECT0 确定选择槽。**分清用户Gift库引用、目标实现依赖、编译期生成器和实际外部服务。用户导入自己的语义库不意味着已选目标轮子。行为未知处不能只凭名称挑实现。

**SELECT1 优先现有合法绑定。**本次含义、目标与硬要求未变，旧绑定合格就重用；不重新联网寻找最新库。变化使绑定失效时，先从本地已允许能力和现有依赖查找。

**SELECT2 形成候选。**先取得当前绑定、目标标准能力、已用第三方库及允许供给中的相交实现，再取得必要组合或新主体候选。没有同名Gift库不是供给缺失；同名原生函数也不是语义相同。记录实际输入/输出、错误、顺序、状态、精度、初始化、部署、ABI和许可/数据限制。可由导出或类型工具准确取得的信息直接复用，行为未知保留，不能由签名推成纯函数。普通已写主体也能直接参选，不被迫先搜索整个世界。

**SELECT3 过滤并组合。**硬要求全部满足；一个库满足接口却要求网络，而任务离线，则不合格。格式、内存、线程和跨组件版本也一并检查。没有模板时仍可正常编译用户写的算法，不强制寻找轮子。

**SELECT4 在授权内选择。**已有绑定合法则保持。新选择默认优先目标标准能力与当前已有合法依赖，再按已版本化策略比较可接受的新依赖、适配和实现成本。“避免不必要依赖”不等于为了零依赖重写成熟解析、排序或数值库；安装、转换、维护、运行和源码交付限制一起判断，不能只计包数。独立观察完全一致且传递边界可直接使用时，不生成无收益的运行转发层。关键业务差异未委派时保留那个差异；实现非唯一而行为已完整时允许选一个合格实现。

**SELECT5 固定与产生候选。**外部依赖先消费下述ECO0—ECO7及回交闭环，条件设计与生产资格分开；锁记录精确内容与实际发生位置；生成直接调用、真实需要的转换、依赖清单和资源。没有手写包装职责时只建立绑定和派生签名，不生成一份应用作者包装代码。库引用、必要适配、锁和配置的共同结果进入同一候选；原外部实现不转存成竞争的Gift主体。取得/安装依赖需要外部作用时另行准入；设计和预览不伪造安装成功。

**SELECT6 检查与采用。**核对目标代码和对应合同，保留选择理由与未测成本。没有证据宣称性能更优，但可以采用满足已给要求的设计默认。新库后来可用不自动改变当前锁；显式升级、目标改变或旧资格失效时重新选择相交槽。

例：意图已精确规定稳定升序、不修改输入、等键保持原序。编译器可选合格标准排序或生成算法，不要求作者写实现品牌。若又要求不引入第三方依赖，该条件过滤候选；若要求必须使用现有库Q，则确认Q的语义和版本。Q不满足稳定性时返回具体冲突或显式稳定化适配方案，不能忽略要求或暗改源。契约只说“输出有序”而用户没有给稳定性要求时，不能凭空制造这一额外硬条件；采用定义的缺省并说明其来源。

[最小控制与目标能力](../../20-语义与组合/作者语义/README.md)负责控制冲突和映射；[全工程资产](../../10-作者与输入/作者源/工程源/资产与非源码.md)负责由选择导致的配置、锁和资源变化。两处不重新选择同一轮子。

## 完成语义与选择实现之间的可执行门槛

进入SELECT0—SELECT6前由[INT0—INT8](../../20-语义与组合/组合/跨软件需求合同.md#意图进入同一作者源的完成与缺省算法)说明：哪些行为已固定，哪些变动属于已允许的实现自由，哪些字段在目标运行时输入。选型只对真实自由作决定，不能把未说明的业务差别、无当前权限或不知道的外部事实一并当作调参。

相同公开要求下两个实现都合格时，可以依明确委派选择其中一个；不要求AI额外点名库。若一个实现要求更窄输入域，这条条件属于该实现的适用前提：能从原任务证明则采用，不能证明则换实现或明确返回缺项；不能把实现前提提升成用户新require以取得成功。

绑定记录保存实际内容和选择来源，不把完整搜索树变成作者资产。相同意图、不同目标可得到不同布局和依赖；解释、任务和资源限制仍保持。旧绑定因漏洞或硬资格失效时限制相交新采用；只存在更快候选时按现有优化采用规则重评，不在重复构建中自动升级。撤销本地控制不删除已开始操作的历史绑定。

## 关系计划的合法性先于代价

[关系方法](../../20-语义与组合/基础语义/状态关系与流/关系查询与维护.md)的候选包括本地完整循环、索引/排序、合格SQL和所选增量引擎。先核源读取许可、值域、空值、重数、错误屏障与所需快照，再比较下推、传输、初始化、内存和后续复用。已有合格绑定继续使用，不每次搜索全部数据产品。

局部输出同型不等于可替换：leftJoin的presence、Ordered的键与方向、回调定义域、源边界和RLS角色都是后续需要的属性。只要缺一项，就不能按某个节点成本小直接剪掉其他路线。目标不能表示NUL或任意Int时，合法编码/本地计算是不同候选；未经授权收窄用户输入不是优化。规则不支持时返回实际缺项，不重新发明数据库。

<a id="intent-realization-ownership"></a>

## 产品需求源不因缺供给而退化成实现源

来自design根的要求已有确定含义时，解析目标是固定满足它的实现，不是生成一张要求用户填写算法的任务表。既有RealizationPlan和selectedUses保持；供给创作可生成新的DefinitionRevision/实现方法并绑定准确需求、输入及证据。它的派生代码或采用的供给版本不是同一产品源的第二份可独立改义镜像。

NeedsAuthorContent必须标明缺的是需求含义还是实现定义：前者需要接受目标/条件，后者可以在已有委派内由实现合成或库适配继续完成。固定构建不重新AI采样，采用后的实现内容受原保留/来源规则保护。不可证明的更广行为不自动变成已证明；只要普通目标生成所需的真实资格已满足，也不要求先证明一般程序全域终止。无方法时留下原义务，不输出空体来满足“源码已生成”。

相交的具体正向步骤见[意图根降低](../内核/输入与阶段总览-编译责任-阶段与目标.md#intent-root-lowering)。整个成熟总成可同时满足多个要求，偏好选择要在共享模型、效果、错误和生命周期的联合条件下进行，不按每个关键词独立选一个库然后假定能拼装。

## 默认绑定与成品边界对方法选择的约束

本节消费[结构默认](../../10-作者与输入/作者源/结构化源码.md#closed-parameter-defaults)和[成品边界](../../20-语义与组合/交付语义/交付公共合同.md#gift-unit-501703299c2052ad9d1e9e2adc6ad993)，不新建搜索阶段。缺少实参但定义有合法default时，先按定义环境确定值；这个值不因某个实现更便宜就被求解器更换。作者明确开放any/exists才形成实现选择；显式同值与默认同值可以共享部分行为分析，但其采用与升级依赖保留。

匹配方法不仅比较输入/输出类型，还比较行为、错误、顺序、资源、宿主进口与完整目的。用于Library的方法可以保留准确进口；用于独立Command的方法还要取得相应驱动与退出合同。不能将一个只有类型声明的外部模块登记为完整实现，也不能要求每个库重复包装成工作台或拥有同名Gift主体。

候选比较在相同公开目的内进行。handler与自托管server、同步函数与消息worker具有不同环境及生命周期责任，不能因为均能取得一个数值结果就按耗时替换。用户已允许多个形式时，保留这些区别、成本和残余条件再决策；没有授权扩大网络暴露、安装或资源占用。

同一主体的冲突与同类型不同主体分别判断。多个Emit各自引用同一纯Transform可以形成多个合法交付；若它们必须共用不相容运行单例、ABI或环境，就需要联合适配或准确冲突。默认边界映射有多个候选时不能按字典序破平局，只有已证明等义的实现选择才可采用既定稳定顺序。

## 多载体方法和当前决策

多种[供给与替换](../供给与替换.md)由`MethodSpec`声明方法，由[合格选择](实现要求与正常绑定.md)形成`RealizationBinding`，具体使用点才派生`UseBinding`；这三个阶段不建立另一套注册中心。资格先于成本；比较包含编解码、跨边界、队列和峰值，原生或设备核名不带性能保证。生命周期切换与失败继续原操作，不用方法重选重放副作用。

## 部分适用方法的联合选择

单个候选只在某个值域/shape/平台上合格时，不把该限制升级成作者输入限制。采用[有条件实现GUARD0—GUARD8](../有条件实现与公共行为保持.md#guarded-selection)：以真实可定义守卫连接专用与通用方法，联合核完整域覆盖、原错误与求值、效果、资源、同步/异步及成本；所选方法与分支及其准确版本先固定在有权决策形成的`RealizationBinding`中；面向一个真实调用点派生的`UseBinding`只读包含需要的guard、分支、适配和依赖。

纯守卫不能调用目标先试一遍、不能把捕获输入求两次，也不能通过对秘密值分支违反非干扰或常时间要求。高性能成员若实际不更快可以保持通用合格方法；没有强保证的通用方法不能作为安全关键失败回退。已执行未知沿原操作恢复，不换方法再发。待验证方法仍可按明确验证目的生成和隔离检查，结果不自动获得生产资格。

## 性质、信任与证据对联合搜索的限制

RES3取得准确要求后按[性质保持与开放环境](../性质保持与开放环境.md)解释候选资格，RES5比较所用CostEvidence是否通过[自适应确认](../../60-保证与证据/验收/覆盖与收益判据.md#adaptive-confirmation)，RES6保留真实证据基础与残余义务。方法可以被沙箱允许执行，却还没有作为推理或生产供给使用的资格。

减少目标允许行为不能自动保持跨运行关系；模型中Int被换成位向量也不能靠新模型的正确证明覆盖旧域。已有直接合格绑定可无搜索使用；方法缺失、特定模板被证明无见证、真正要求冲突、超预算和未解释要求分别返回。即使约束求解器可判定，带程序语法空间的合成也不因此自动可判定；对具体实例可继续尝试合格搜索、枚举、组合或证书，不以类别未知停止可完成工作。

硬约束消解先于代价，但候选选择可能影响共享上下文、观察和联合分布。保持共享公式和有限前沿可以避免不必要展开，不保证任意耦合实例多项式完成。收缩候选空间是方法策略而非修改产品要求；无法找到实现时保留准确义务，不生成假TODO产品。数据反馈、检查次数、推理规则和域变化进入真实证据依赖，不一律把整个目录版本放入每次计算键。

<a id="deterministic-library-resolution"></a>

## 动态业务库与工具选择：数据驱动发现，确定性冻结，不建立第二包管理器

“所有业务库都能动态编译”不能解释成运行时任意下载、猜包名或把互联网当编译器的一部分。Gift采用**开放候选、有限解析、精确冻结、生态工具执行**四段式：系统可以不断接入新的库、框架、算法和生成器，但一次真实构建只消费已冻结的选择。

### SupplyCandidate 的最小资格

一个候选库／框架／生成器按以下合同进入研究、生成验证候选或生产选择；每个阶段只要求其用途必需的信息，缺项保持显式。生产Binding必须闭合相交硬资格，不能拿名称和搜索命中代替：

- 稳定 `providerRef / package identity / revision or version requirement`；
- 它解决的 Definition/Requirement/Method capability，而不是营销标签；
- 目标语言、平台、runtime/toolchain、features/flags 及互斥关系；
- 公开调用/生成接口、输入输出、错误、效果、资源与生命周期；
- 依赖要求、构建脚本／proc-macro／codegen 等是否产生Effect；
- license、来源、integrity/provenance、安全或组织政策等硬资格；
- 目标产物贡献：源码、配置、资源、link item、runtime member、build step；
- 可用于判断适用性的静态事实与仍须真实运行取得的 Evidence。

本次用途必需的语义或硬资格信息不完整时，可以保留待研究/待验证候选，但不能把相应未知签成生产合格；非必需元数据或未被要求的性能测量缺失不形成无限前置。库“很流行”“benchmark快”“同名API存在”都不是资格。

### ECO0—ECO7 解析与冻结算法

这是RES2—RES6在生态供给上的细化，不是另一个resolver；SELECT0—SELECT6是开发者不点名实现时对同一过程的入口说明。RES3/RES4取得或组合候选，ECO3/ECO4消费对应资格；RES5中的真实生态反馈落实为ECO6及下节；RES6只有ECO7条件成立才封存。三组局部步骤共享同一RealizationPlan、候选身份、预算与结果，不重复执行选择或维护三份绑定。

1. **ECO0 固定需求闭包。** 取得相交 Meaning、hard Requirement、Realization Control、TargetProfile、平台与已存在Binding；未指定的自由保持Auto，不凭当前生态默认补义。
2. **ECO1 复用当前Binding。** 若现有精确库/方法仍满足合同，默认复用，避免每次编译重新搜库。
3. **ECO2 建有限候选域。** 只从当前允许Registry、项目显式依赖、已锁内容及获准的Provider查询得到候选；记录查询revision、过滤条件与未搜索边界。网络发现是准备Effect，不属于纯编译。
4. **ECO3 硬资格过滤。** 同时检查语义覆盖、target/runtime、接口、license/security、资源与构建能力；一个硬失败不能由性能偏好补偿。
5. **ECO4 组合闭合。** 把候选新增的传递依赖、feature、runtime、native link、build generator和共享单例条件加入同一联合方案；不能分别挑局部最优后再拼出不兼容组合。
6. **ECO5 分层偏好／成本比较。** 只在硬合格方案中按现有Prefer、稳定性和可靠成本界比较。没有足够证据时保留Pareto/Unknown，不伪称全球最优。
7. **ECO6 固定生态解析请求并回交。** Gift把当前联合候选变成准确的package/toolchain解析输入，交给Cargo/npm等真实生态resolver；输出lock/graph及实际features／工具依赖后，按下节回交同一ECO3—ECO5状态。未取得解析结果的排名只能作探索顺序或有可靠界的暂定选择。Gift不重写semver或feature-unification规则，也不把resolver成功当业务资格成功。
8. **ECO7 形成Binding与DependencyBuildPlan。** 仅对已完成相交回交核验的选择，固定包内容、按构建域解释的features、工具链、生成器、构建输入、许可/来源、目标贡献及失效条件。所声明的是可行、被委派选中还是有证明范围的最优须分别记录。之后纯生成只读该Binding；升级形成新revision，不改旧对象。

<a id="ecosystem-resolution-reconciliation"></a>
### 生态解析回交：一个联合选择，不是先选库再被动接受锁

原RealizationPlan保留部分选择、约束和候选前沿；生态解析是其中一个有结果的子问题，不建立独立总协调器。输入至少固定本次目标／host、所选根和构建用途、原生manifest／lock及相交配置、resolver和工具版本、包来源与取得范围、当前候选引入的依赖和feature要求、禁止条件、共享名义类型／单例／native链接约束。字段从原输入和Binding取引用，不要求作者另写一份同义清单。

Provider回交准确请求身份、所消费输入、解析器结果、实际包内容身份、依赖种类与发生域、被启用功能及其来源、native链接／生成器贡献、错误和未观察范围。缓存中的旧结果只有这些实质输入未变且结果来源合格时复用；一个同名Cargo.lock或某次机器安装成功不满足这一条件。

回交顺序固定为：

1. **匹配请求。** 核结果确实来自当前固定输入。不同目标、package selection或解析上下文的结果不是可拼接的同一次解析；过时响应保留原绑定，不能推进当前计划。
2. **核新增事实。** 将实际依赖／features／link／生成期与运行期成员加入原联合约束。用户禁止的功能被其他依赖重新启用、同名类型来自不相容版本、共用native资源冲突等，都产生带来源的冲突，不偷偷改作者要求。
3. **重算资格与成本。** 只重算因回交变化的语义、平台、安全／许可、资源、表示、构建和成本项。共享依赖的成本按真正编译／运行单元计，不在每个候选重复计费，也不因版本相同就假设只构建一次。
4. **选择继续方向。** 已证明违反硬条件时，将准确冲突交回对应候选／组合选择点；更换方法、合法变体或隔离方案后再求解。只有原owner给出可泛化的冲突依据，才排除其他候选；某版本的一次失败不能禁止整个库。若只是缺输入、权限、证据或预算，则保持相应Need／Incomplete，不当作不可满足。
5. **稳定后封存。** 原联合选择与规范化的生态请求／响应在当前输入域下不再改变相交要求、成员和资格，才封存Binding。若用户明确允许先采用一个合格方案，保留选择政策和未探索前沿，不因此宣称最优。需要最优保证时，未解析方案必须有可靠界才能被剪除，否则继续保留比较未定。

“稳定”是已固定有限输入上的选择与约束一致，不是每轮文本hash偶然相同。相同规范化状态再次出现而无新事实／约束／候选进展时返回循环或规划未完成；不得无限调用生态resolver。逻辑搜索、Provider运行、网络等待和总任务分别计预算，墙钟耗尽不证明不可实现。中断续接保存原候选、已回交结果、必要引用和未决；不用新Registry快照混补旧尝试。元数据或权限确实变化时建立后继准备态，只失效相交结论。

生态调用若可能获取网络内容、写缓存或运行代码，先由application/execution准入；纯内核只消费固定结果。取消未封存选择不撤销已发生下载、费用或生成器作用，已启动Attempt由原owner读回／结算；独立源码生成仍可继续，不把一个待解析根拖成全工程阻塞。

### features、可选依赖和代码生成器不是字符串开关

Cargo feature、npm optional dependency、framework plugin、compiler flag按真实生态解析。**作者可见性、语义依赖和物理构建输入是三个边界**：改变公开行为、类型或安全前提的选项进入相交语义／资格；不改变这些含义但改变代码生成、二进制或构建行为的选项，仍进入DependencyBuildPlan、实际Action输入身份及相交Artifact/Evidence。它们可以不出现在作者默认设置页，却不能从物理缓存键消失。

未被该阶段实际消费且有保持依据的选项，才可从该阶段的键排除；不能统一用“Provider私有”或“semantic hash没变”证明所有结果可复用。也不能把所有feature预先做成核心Control，或让一个未解释的`features: [string]`绕过目标／依赖合同。Cargo的具体消费域由[Rust目标](../../40-目标与制品/目标/Rust目标画像与降低.md#cargo-resolution-context)拥有。

build.rs、proc-macro、schema generator、OpenAPI/protobuf生成器等必须声明输入与输出覆盖。纯确定生成器可以作为构建方法复用；有文件系统、网络、环境或执行效果的生成器由Execution/Provider在受控环境运行。其输出进入ArtifactSet/生成源闭包，不能在compiler-kernel内部隐式执行。

### 已知优秀实现如何供“直接学习／候选优化”使用

成熟实现可以有三种用途，必须分开：

1. **直接Supply**：库本身满足合同，产品直接依赖它；最优先，不复制源码。
2. **GenerationMethod / scaffold**：成熟生成器或框架模式产生项目结构，再由Gift检查并保持来源；不把其模板提升成业务语义。
3. **Reference / Evidence**：代码、算法或benchmark仅作为设计候选／验证依据；若要形成新的GovernedAuthored实现，必须经过许可、来源、适用性和独立检查，不能自动复制受限源码。

因此“让系统学习别人已有的完美代码”在确定编译路径中的准确实现是：**把成熟成果注册为可查询的Supply/Method/Reference，比较其可观察合同与成本，并在有权范围内选择或生成；不是在每次编译时让模型阅读互联网后自由改写。**

## 实现对象的机读字段与生命周期

实现解析把工程设计中的“需要什么能力”转换为“由哪个精确实现提供”。正式对象由 `ImplementationRequirement → Candidate/Eligibility/Decision → ImplementationBinding` 与任务内 `RealizationPlan` 承载，分别保留资格、限制、替代和失效条件；不再额外套一层 implementation umbrella。它不把“工具已安装”“用户偏好某库”“曾经成功运行”误当成有效绑定。

### 对象分离

```text
Requirement  需要满足的语义和非功能条件
Provision    某候选声明可以提供的能力
Candidate    可被评估的精确实现修订
Eligibility 候选是否满足全部硬约束
Decision     有权选择哪个合格候选
Binding      Requirement 到 Candidate 的稳定解析结果
Allocation   当前执行为该绑定保留的资源
Grant        当前执行对效果的授权
```

这些对象具有不同生命周期，不能合并成一个 Provider 记录。

### 实现需求

```ts
interface ImplementationRequirement {
  readonly requirementId: string;
  readonly semanticContract: ContractRef;
  readonly requiredCapabilities: readonly CapabilityConstraint[];
  readonly targetConstraints: readonly ConstraintRef[];
  readonly effectConstraints: readonly EffectConstraint[];
  readonly securityConstraints: readonly ConstraintRef[];
  readonly qualityClaims: readonly ClaimRef[];
  readonly compatibility: CompatibilityRequirement;
  readonly fallbackPolicy?: FallbackPolicyRef;
  readonly provenance: ProvenanceRef;
}
```

行为需求来自已冻结设计，不从某个实现库的偶然行为反推含义。作者另行明确接受的库/算法固定、禁止项或外部兼容约束，也进入相应targetConstraints和Binding输入；它们不必须先证明是外部兼容需求才能有效。某库名称既不补足未知行为，也不覆盖独立硬要求。

### 候选

候选来源包括：

- 当前工程已有实现；
- Gift 内建参考实现；
- 标准库或成熟第三方库；
- 外部 Provider；
- 模板或生成器；
- AI 或搜索生成的候选；
- 自研实现计划。

```text
ImplementationCandidate = {
  identity,
  revision,
  provisions,
  targetCompatibility,
  knownEffects,
  resourceProfile,
  securityProfile,
  licenseAndSupplyChain,
  maturity,
  evidence,
  limitations,
  lifecycle
}
```

候选声明不是事实；关键能力由符合性证据支撑。

### 资格

资格逐项返回：

```text
Satisfied
NotSatisfied
Unknown
NotApplicable
Stale
```

任何硬条件为 `NotSatisfied` 时候选淘汰；关键条件为 `Unknown` 时默认不进入生产绑定，可进入实验或影子验证。

### 解析决定

```ts
interface ResolutionDecision {
  readonly decisionId: string;
  readonly requirement: RequirementRef;
  readonly eligibleCandidates: readonly CandidateRef[];
  readonly selected: CandidateRef;
  readonly rejected: readonly CandidateRejection[];
  readonly objectiveComparison: ParetoComparisonRef;
  readonly authority: AuthorityRef;
  readonly assumptions: readonly AssumptionRef[];
  readonly validity: ValidityCondition;
}
```

决定只在合格候选间比较。排序、流行度、调用者提示和 fallback 不能绕过资格。

### 绑定

```text
ImplementationBinding = {
  requirementRef,
  candidateRef,
  provisionRef,
  adaptationPlan,
  semanticVersionRange,
  exactCandidateRevision,
  targetProfile,
  conformanceEvidence,
  limitations,
  invalidationInputs
}
```

绑定是编译输入，不是运行实例。Provider 进程重启只影响执行绑定，不改变实现绑定，除非能力 revision 或符合性发生变化。

### 适配

适配器只处理：

- 类型和协议表示；
- 错误映射；
- 生命周期和取消；
- 资源与配额；
- 身份和回执映射；
- 安全能力句柄。

适配器不能重新定义产品语义、放宽硬约束或自行选择 fallback。

### Fallback

Fallback 是重新解析：

```text
Binding invalid
→ Re-evaluate requirement against current candidates
→ Hard eligibility
→ New decision
→ New binding
```

不能在调用失败后暗中换 Provider。新绑定不得扩大权限、数据范围或降低验证标准。

<a id="method-catalog-invalidation"></a>
### 局部失效

候选更新使实际读取其修订、资格或目录匹配范围的结论及反向消费者陈旧；范围包括已绑定使用点，也包括曾因缺失、排除或歧义没有形成绑定的使用点。新增候选必须重验相交的负查找、完整性和选择依据；它不自动撤销仍合格的锁定绑定，未读取该候选域的目标也不受影响。显式订阅最优性另外重评比较结论。发现缓存失效、功能资格失效和需要重新发射是三个不同结果，不以一次目录更新强制全部重编。

### 验证：实现需求、候选、解析与绑定

- 不合格候选永远不能被偏好选中；
- 候选声明与真实符合性差分；
- Provider 漂移和撤销传播；
- fallback 权限与效果不扩大；
- 同一 Requirement 在相同候选闭包下解析确定；
- 候选闭包不完整时不宣称全局最优；
- 许可证、安全和供应链条件进入硬资格；
- 绑定的 exact revision 可重新获取或明确不可用。

## Method供应声明到实际资格的确定匹配

### 每个Method供应必须回答的内容

- **行为签名**：实际操作/输入输出、名义类型、角色、前提、完成定义、错误与副作用；数据/时空适用域明确。
- **效果与状态**：读写的资源、外部效果、事务与可观测前像、Frame、并发/幂等、取消、补偿/读回、进展保证。
- **能力范围**：可部署目标平台、语言/ABI、依赖环境、Provider前提、权限/凭证需求、状态规模、数量单位、限制与已知不能处理的输入。
- **质量边界**：性能和成本数据的真实适用条件、可比较指标和版本；候选有能力不等于在本目标硬限制下合格。
- **来源与维护**：供应ID、具体修订/依赖范围、绑定锁、作者/外部拥有权、升级/失效与兼容策略；外部库的著作权/许可证由依赖治理承担。

仅声明`methodSupply.json`或为函数命名，不等于该方法已存在、正确或获准使用。原生代码若由用户拥有可作为候选，真实ABI/效果/前提仍要与本次业务要求匹配，不因出自用户而有额外语义特权。


一个候选Method至少提供准确revision/source、`covers(RuleRef,domainRef)`、Target适用集合、所需能力/Provider/效果、实际成员贡献、preserves/residuals及Evidence义务。当前[Method供给Schema](../../../schema/supply/method-supply-1.schema.json)只约束供应声明的可序列化形状，不证明其源码已安装、覆盖声明真实或可用成本为零；Gift95旧提案不作为当前解码入口。

匹配顺序：固定冻结的RuleOccurrence与目标→核Rule输入/失败/帧/进展义务→核每个方法覆盖域是否包含要求域（需证明，未知为Need）→核所有前提、Capability、Provider/Target/ABI和许可→联合检查多个方法的状态所有权/效果/资源/失败耦合→选择符合硬约束的共同方案→保留所有residual→输出有来源的Binding。无方法和没有扫描完整候选域不同；搜索预算耗尽既不是不可满足证明也不是合理降级权。

已有合格Binding仅在其实际读集、Method revision、目标及消费者没有失效时可复用。新候选不自动替换用户已采纳实现；显式重新优化仍服从同一硬要求和真实证据。

## Rule、Method、Target 与原生程序的联合资格门禁

候选集合只有通过以下真实关系才能进入原 RES：① RequirementOccurrence 能解析成公开 Rule Definition、所有实参类型与 Hard/Soft 模式一致；② Rule 选用的准确 Profile 被所选 Target revision 接受；③ Method `covers` 的 Rule、适用 `domainRef` 及精确版本覆盖这次出现点与环境前提，`requires` 的能力、效果与 Provider/Native 输入有事实支持；④ 编译目标与作者目标键的 TargetProfile revision 相同，布局、ABI、数字/文本索引单位与工具链可用性不出现不受支持变换；⑤ 所有硬控制与安全/授权边界共同成立。每一项独立报告依据，不得把 `covers` 声明等同覆盖域证明。

若候选集合仅含一个匹配的描述文件，但其 `domainRef` 未被真实解析、谓词缺帧/进展保证、原生副作用未知或 lowering 不存在，则它属于“形状可读取、可进一步研究”的供给，**不是**可选的完整 RealizationBinding。解析器允许生成有 Need 的设计蓝图，不能将其签发为已完成软件。并行候选求解以固定同一 SourceSnapshot/EngineImage/Target basis 为前提；一条未知关键硬条件就阻止错误选择，预算结束表示搜索未完成，不证明不存在解。重试沿相同修订与 Need/候选约束继续或明确重新开新基础。

正常选择输出应含 `chosenMethodRef/revision`、Rule occurrence/ref、TargetProfile ref、完整适用域、实际资格/残余、Source/Target/Provider读集、硬条件的贡献来源及拒绝候选的可解释原因。实现偏好只能在资格化供给集合上决定稳定次序；另一项目中同名 TypeScript/Rust 源不可根据名字获取复用资格。

## 有实际生产者的第一组方法绑定与后续泛化条件（Gift 98）

`fixtures/contract-closure/Gift98/methods/registry.json`给出实际四个**本地试验公共方法**的绑定与源码路径及一个**通用Callable绑定入口**，而`compiler/runtime/{record,workflow}.ts`保有真实算法。当前读取器按精确`gift.std/VersionedRecord@1`、`gift.std/FiniteTransition@1`、`gift.std/TransitionOnRecord@1`和`gift.std/AllPredicate@1`匹配已知绑定；测试两种不同应用实例、显式存储/ESM硬条件和完整方法文件存在，再由发射器生成源码。它不是已发布的通用MethodRegistry，未实现启发式全局寻优，也不把存在一个registry JSON文件当真实Method资格。

每个需要生成行为的`use`先取得其实际Definition/语义版本与`UseBinding`。一般流程：

1. 固定作者source revision、Definition/类型codec、所有硬约束、目标及实际读集；不能从候选值猜正确版本。
2. 从精确Method供给形成候选，每个候选包含`methodId+revision+producerDigest`、适用输入/目标/运行环境、必需依赖、效果、错误、内存/时间资源界与尚须验证的义务；不能凭目录/名称相似自动选。
3. 对硬要求和资源范围做**可判定的资格筛选**；相交的未知义务保留`UNQUALIFIED/NEEDS_EVIDENCE`而不计为满足。仅对均合格的候选按作者偏好、目标策略与实际代价/保证维度比较；未能比较的维度不暗填零。
4. 没有候选返回`NEED_METHOD`并保留全部正常语义；有多个同等但选择政策未定义的候选返回明确选择待决；已经有合格绑定且输入前提未变化时优先复用，而非无理由重新搜索。
5. 交给目标生成器的是已选方法的真实调用/LoweringPlan和受信产出边界；Method不可在发射器内部偷偷更换，目标构造未覆盖语义时返回相交失败。变化只使真实消费者重求资格；实际输出与依赖版本记录在Artifact身份中。

现有试验能力的准确范围：**只支持一种被固定绑定的volatile单进程实现与TypeScript ESM**；所谓`METHOD_NOT_ELIGIBLE`的有限实现验证不等于多目标自动选择器已完成。真正要求persistent CAS、无限修订寿命、跨主机调用或安全级宿主隔离时不得回退到内存Map。当前artifact manifest包括作者、方法登记与真实输出字节摘要；完整生产级资格还缺真实规范版本固定、独立符合性、供应链来源签发与远程/动态Provider退出路径。

具体实现再增加**Method来源身份固定**：当前四项已知Method各自接受准确的运行时源路径，逐个验证登记版本、来源路径与实际内容，并在Artifact中记录`compilerSources/methodSources/methodRegistryDigest`。即使某路径文件存在，Registry把本来`VersionedRecord`的算法源重定向到错误文件仍返回`METHOD_BINDING_MISMATCH`，不从“文件存在”推断合格；开放Method资格、外部签名与独立证明仍未由这个有限门禁解决。

<a id="method-data-extended-callable-reference-boundary"></a>
## 新方法不改内核的有限绑定与生产资格缺口

现有参考编译器在`fixtures/contract-closure/Gift98`新增一个**方法实现供给的开放点**，不是新增第五种业务语义：`gift.core/BindCallable@1`保持固定的编译器连接规则，`methods/library.json`以准确`definitionRef`选择`source/sha256/export/parameters/returns/target/effect/qualification`。任意新参考函数只要满足此有限本地契约，即可由库作者增加登记与真实`.ts`函数体，由一般作者的`bind`引用，生成单独的目标封装；编译器不随每个库函数增加`if/else`分支。输入域当前限Text、Bool、SafeInt的TypeScript标量签名，不能推断任意泛型、效果或跨语言ABI；Provider来源仅为同包封闭的`methods/supplies/`路径，无远端安装与签名信任链。

具体拒绝与资格由层次区分：路径不能穿越根或经符号链接改指其他内容；实际字节必须等于登记摘要；目标必须为TS ESM；`effect`和`qualification`目前强制`unknown/reference-only`，拒绝仅修改标签就获得`pure/qualified`身份；封装在实际`tsc --strict`时检查导出及标量签名。以上证明的是**已读源码的身份与有限Target连接性**，不是该实现满足命名业务Definition、无副作用、可持久恢复、保证延迟或可信供应链。真正在生产系统开放Method时，必须读取发布的Semantic Definition合同，固定实参/错误/状态/效果/资源与Target资格，执行独立保证，精确记录未决需求；不支持者给`NEED_METHOD`而不是退化到任意名称相似的源码。

<a id="composition-method-qualification"></a>
## 可组合计算的Method资格与缺实现出口

原先的`BindCallable`仅固定**已有原生方法字节及签名**；它没有从作者计算语义获得函数体，且供应函数的导入时效果未知。新增有限`gift.core/Compute@1`则复用**一个公共计算代数的解释与Lowering**，不再按每个业务名注册Method；`gift.core/DataShape@1`负责可读闭合数据类型而不提供存储。真实Method资格应按`(准确Definition含义、值域、可观察错误、效果、资源界、Target/ABI、供应读集与证据)`匹配，而不是仅看两个函数输出类型相同。

选择先分为三种：作者声明的行为可由既有封闭计算代数完整构造时，选择其合格Lowering；已有但无法从此代数派生的成熟方法经完整语义/效果资格绑定；既不能派生又无合格供给时返回`NEED_IMPLEMENTATION`及缺失的可观察事实或供给，而不能生成空实现。历史有限参考编译器目前只有一种TypeScript ESM lowering，不提供多目标Pareto优化、多实现搜索、源码语义等价证明或独立供应证书；编译成功只能归入准确参考范围。

特别的负例：有`Compute`时，若同一生成模块还有`effect:unknown`的原生`BindCallable`，即使Pure Compute没有调用它，ESM的出口重导出也可能加载并运行供应模块的初始化代码，故参考解释器返回`UNQUALIFIED_EFFECT_COEXISTENCE`；未来只可通过经过证明的隔离/懒加载、准确的Effect声明与宿主边界扩展此资格，不得靠手写`pure`标签通过。

<a id="qualified-compute-method-choice"></a>
## 同一计算语义的多候选选择：可运行有限交接

**输入**：固定的 Compute 类型/效果/资源合同、目标 `typescript-esm`、作者控制 `computeMethod`（省略时 `auto`），及按准确内容摘要读取的候选库。**候选**：`gift.ts.compute/callback-kernel@1` 与 `gift.ts.compute/inline-scalar-loop@1`；这是两条已存在的本地 Lowering 机制，而不是外部不受控字符串即可加载执行的插件。前者覆盖 sum/count/all/any/map/filter/fold；后者只接受受界标量迭代 sum/count/all/any/fold 且没有 list-producing map/filter。

**具体决策**：先用与候选无关的定义规则完成调用无环、数据类型、错因、输入数据规模、表达式执行代价检查；然后限定目标、可处理运算、求值/错误顺序及硬控制；无资格时拒绝且报告 `COMPUTE_METHOD_INELIGIBLE`，不可悄悄降级；若作者锁定 callback/inline 就保持锁定。`auto` 目前使用可复核的结构启发式：仅当存在标量集合迭代且无 map/filter 时选择 inline，否则 callback。它没有以实测证明最快，不能由“更短代码”“更少回调”冒充低延迟或最低内存保证。

**输出**：每个 Compute 定义独立的 `{definition,candidate,strategy,qualification,reason}`，连同候选目录字节摘要写入 `gift.reference-artifact/1` Manifest。换方法只改变目标实现及实现输入，不改变业务语义投影摘要。生成器内部维护的候选数据并没有自动取得生产资格；对生产消费者仍需目标工具链、平台、输入/故障分布、资源测量、独立语义保持依据和失败恢复资格。

本地样本在两个候选上运行同一非业务特定折叠，并验证方法锁定的拒绝、来源身份与第二次精确更新；这是有限行为等价证据，不是任意计算图的形式证明、全局最优方法选择器、任意第三方新算法自动选择或完整 Gift `RealizationBinding` 求解。

<a id="prebootstrap-qualification-trust"></a>
## 方法接受、可生成与行为保证之间的精确门槛

作者定义合法、候选类型正确、目标源码可生成、原生构建通过、保证已成立分别是不同结果。普通程序允许保存和构建一般递归计算，不要求先证明所有函数终止；但其产物不得自动声称满足未证的进展、资源、安全或业务后置条件。当前所请求的质量/风险 Profile 决定哪些残余义务必须在采用前解决，缺它不是语言表达无效。

Method 资格检查至少分四组：语义适用（实际输入域、公开结果/错误、效果与帧）；实现供给（定义与代码摘要、实际消费者、可用依赖）；目标保持（类型表示、ABI、运行和资源条件）；保证依据（所需命题、观察/证明范围、前提、独立性和失效规则）。只有相交组都满足当前 Gate 才形成对应强度的 Binding。字段齐全或方法签名正确不是其语义正确的证据。

某些可执行前置条件可在作用发生前检查；某些后置条件可在结果交付前检查。采用运行断言必须保留拒绝/失败行为和成本，不把检查失败当成实现已满足原业务。隐私泄漏、真实付款、活性、长期稳定性等不能靠事后 Bool 检查修复，必须在执行前取得相应保证或拒绝强承诺。运行断言也不能抹除已发生的外部效果。

编译器内部优化和方法供应不能用自己生成的恒真 proof、测试预期或空域自证。证明/证据引用必须锁定被证命题及其完整定义，检验外部假设是否被允许。循环依赖的资格图不能形成“方法A信任B、B信任A所以两者都可信”；每条被要求的信任链需到明确接受的基础或实际独立证据。

错误保持要比较公开类别、来源、时机和可恢复性，不只比较正常输出。例如原函数非法输入应在网络调用前拒绝，候选先调用远端再返回同样错误不等价。内存不足或预算耗尽不能替代用户指定的无解、禁止或缺资源业务结果。目标环境改变导致异常通道或资源界不同，应重新资格化而非仅重新编译。

<a id="design-b14"></a>
## 方法资格先于偏好及稳定选择

候选Method必须指向实际实现Definition/原生绑定和明确的适用输入域、效果/错误/进展、资源及目标条件。资格判断分别返回满足、不满足、未知、未完成；只有全部当前硬义务满足且必要信任政策接受的候选才进入排序。缺证据但可生成草稿与可签硬保证分开显示。

排序使用作者明确接受的可比偏好和已知成本；不同比较工作负载、平台或误差口径不能合成一个伪精确总分。成本未知的候选保持partial order/需要测量，不因为缺数据被当成零成本。硬条件无差异且偏好相同，按固定Method逻辑键/版本锁做确定性tie-break；锁定构建不因目录后来新增方法悄悄换算法，显式再优化才重选。

目录发现查询记录负依赖：没有找到某域方法、新增目标能力、撤销供应或变更假设都可能使候选集变化。已有候选正确不等于搜索完备；选中了可行不等于全局最优。用户从非负图改为含负边时，原方法的输入域证明失效，不能保持同名shortestPath就继续使用。

**验证与反例**：负边使候选失格、同名不同ABI、资源硬界变化、未知成本、相同偏好tie、锁定构建遇新方法与显式重优化不同结果。

**实际能力边界**：实际Method目录和独立资格供应尚未建成。

## 抽象意图到具体 Method 的联合选择算法（设计已确定，未冒称生产实现）

### A. 输入不只是一个业务关键词

`RealizationQuery` 的逻辑形态为 `(acceptedRootRefs, elaboratedRequirements, frozenMeaningRefs, roleBindings, fact/observationSelection, policySelection, targetProfile, resourceLimits, supplyCatalogSelection, evidenceRequirements)`。前三项来自独立 owner 的接受/解释，后几项是本次真实选择；每项有作用域、修订/内容摘要和读取来源。实现解析**只消费**这些对象，不把 `intent:reserveBed` 或 Method 名字当隐藏的业务政策选择器。

一个 Method 可以提供计算、状态转换、SQL 事务、工作流、UI、协议适配或真实世界效果；多种方法同名并不表示可互换。方法描述至少承载 `(public capability, typed inputs, accepted domain, pre/post, permitted faults, frame/read/write, progress/temporal, effect/authority, resource/cost, target/ABI, dependencies, guarantees, evidence/provenance)`。其中声明与得到独立资格是两种状态。`claimedCoverage` 与许可证、`verified:true` 不直接变成 Evidence、Grant 或 Kernel 信任。

### B. 不把缺实现退化成伪代码的实现决议

```text
resolve(root, frozenContext):
  R := elaborate root (all hard/normal/progress/norm/observation duties)
  if unresolved meaning/binding/authority facts: retain exact Needs; never guess them
  C := discover candidates from exact catalog, no uncontrolled network in pure compilation
  C += typed composite candidates whose components satisfy their own declared contracts
  C += qualified bounded synthesis candidates for explicitly supported synthesis domains
  for each candidate c in stable order:
    check domain/roles/units/identity/frames/errors/effects and target support
    check under global shared resources, progress, time and authority assumptions
    check evidence required by this root (test/formal/model/external readback separately)
    if a hard obligation is unproven: c remains conditional, not HardPass
  choose among hard-qualified solutions using approved preference + cost policy
  freeze MethodBinding(s), locks/read-set, remaining Needs, proof obligations, alternatives
  if no completed solution but search incomplete: IncompleteSearch, not Unsat
  if complete applicable domain has proof of impossibility: ScopedUnsat + witness
```

**四条供应路径**：现成已合格方法、保序有型组合、域内有界算法合成、经有权专业作者新建 Method。第四条可以调用任何合适的 Rust/TypeScript/SQL/第三方语言（包括 Gift111 的可选参考计算子集），不强制为产品作者实现另一门计算语言。第一、二、三条若方法资格不满足也不因名称完整而自动前进。

### C. 精化检查与可行/最优的区别

硬资格要对使用点规定的所有输入、错误、状态、时序、权限与资源成立；局部安全保证可以与另外的共享资源冲突，必须求解全局方案。安全测试只覆盖执行的样本，证明只覆盖其公理/模式适用域；严格 TypeScript 编译只证明结构及类型层面的目标可构建。高质量源码不能只依赖码行数或“最快候选”，需要在要求的负载上比较时延、内存、复杂度、维护和部署成本；不可比成本或缺环境基线保留未知，不能强排。

同一明确条件下给出稳定候选序：先硬资格、后作者权重/语义优先级、后有来源的成本模型、再稳定 ID 序。预算停止只取得目前最佳可行，不可声称全局最优；严格最优声明需要目标函数/可行域/算法完整性与最佳性证明。新 Method 加入、旧库撤销、事实变化可能影响上次 `none found` 的**负依赖**，要准确重新选择，而不是沿用缓存。

### D. 结合全部系统的总可实施性

从业务角度，数据观察、约束判断、决策、状态更新、用户交互、外部效果、运维监控可以由不同合格供应者承担；选择时先按事务及故障域联合计算。仅因某个候选能实现 `set confirmed=true`，不代表其承担了现实支付/发货承诺。对不同 Provider 的“并行/重试/补偿”只有明确读取、前像、操作身份和恢复合同成立时才能装配。

返回值至少有 `QualifiedPlan + Scope + RemainingAssumptions + BindingRefs`、`NeedsMeaning/Fact/Method/Target/Grant`、`ConflictingRequirements + Witness`、`IncompleteSearch + Frontier` 等有型变体。业务作者能看到仍未承担的区别、谁可以补充及替代实施渠道；不能为了返回可发射代码而丢掉未履行的安全/规范义务。

<a id="gift119-method-qualification-contract"></a>
## Method 候选从业务合同到合格实现的完整字段与裁决

`MethodOffer` 来源于已锁定的 Provider/本地库/原生包/解释/受限合成器；**URI/名字/`supports:true` 不构成实现资格**。对具体 UseSite 的方法候选至少需能确定：签名及名义类型、输入覆盖与前置条件、正常/错误/取消行为、共享状态读写和 Frame、进展/期限、资源成本与上界、真实效果与幂等/恢复、观察/证据种类、目标/ABI 与工具链、依赖许可和锁、发行人与撤销状态。缺某字段时若相交硬义务需要它则为 `NeedsMethodEvidence`，而非由项目作者手填一个“兼容”。

施工接口（内部读模型，编码仍沿唯一 Method/Target 原有机器协议）：

```ts
type MethodUseCandidate = {
  methodRef:string; revision:string; sourceDigest:string; useSite:string;
  inputDomainRef:string; preconditionRefs:readonly string[];
  guaranteeRefs:readonly string[]; effectAndFrameRefs:readonly string[];
  progressAndCostRefs:readonly string[]; targetAndAbiRefs:readonly string[];
  assumptionRefs:readonly string[]; evidenceRefs:readonly string[];
  readSet:readonly string[]; negativeReadSet:readonly string[];
};
```

候选检查必须先完成硬条件：实例合法输入 ⇒ 实现可接受；实现后像 ⇒ 业务允许的后像；错误/拒绝/取消不能空洞实现；只修改合同允许的 Frame；资源、时钟、真实授权前提、实际输入来源、目标 ABI 和证据都合格。发生跨任务共享资源时方法局部合格不能直接签整体；必须将其效果和资源用量交回 JointProblem 重算。不存在合法候选时给准确缺项；求解器预算用完返回 `Incomplete`，不称“整体无解”；性能、许可及可信来源不可比时保留未决。稳定选择需冻结目录快照、候选身份/摘要、目标版本、比较规则和原作者控制；新增 Method 使负依赖失效，但不能静默改变已固定发行版的实现。

实现途径按已合格能力选用：纯查询→真实 SQL/查询引擎，规则决策→有明确命中策略的规则引擎或合格原生库，耐久工作流→具有历史/重试保障的 Workflow 方法，有限优化→有可核对模型的求解器，确有业务特殊计算→Gift111 子集或原生代码；**这些是候选映射原则，不是包内已有的生产适配器**。选择新外部 Provider 不能从 `permit` 自动取得 Grant。

## 抽象展开结果进入方法供给的硬门槛

由[抽象 owner](../../20-语义与组合/组合/抽象与开放定义.md#pattern-use-multiplicity-refinement-contract)产生的 `ELABORATED_UNQUALIFIED` 只表示引用/角色/静态意义已被安全整理为具名义务；它**不是** `QualifiedMethod`、`RealizationBinding` 或 `ScopedSatisfiable`。方法选择必须读取实际 Requirement 解释（特别是义务、许可、无界时间和条件触发）、全部硬要求、角色的类型精化见证、真实权限和目标负载条件。存在未解释的 `requirementRef`、`whenVariation` 或非法单位变换时返回 `NeedsRequirementInterpreter` / `NeedsQualifiedConditionalRequirement` / `NeedsTypeRefinement`，不得走同名模板或有限 Bool Setter 来填洞。

对每个候选先验证其前置域覆盖、异常/进展、状态保持与对共享资源的联合保证，再验证 Target/环境与证据。局部可行不代表全体意图可行；搜索超时不等于 UNSAT；不从 `selectionSourceRef` 推导出新的 Grant。读取集必须包含模式 Definition、所用 Meaning/Requirement、类型精化、差异选择、Method 目录范围和负依赖，相关变更只能重新资格化所交叉的使用点。

## 适用前提、限制与反例

以下按原版本保留相关定义、反例、判断和实测范围。版本名称仅表明形成来源；条款是否现行有效仍由本文件的当前合同、被引责任文件及实际消费者决定。

### Control 必须连到合格 Method，不能只有JSON值

对于来自当前 `gift.control-file/1` 的已解析实现限定，只接收解析到精确Descriptor revision、已检查作用域与值、已参与所有硬约束合取的贡献。真实Supply资格须有Method/Target/Provider 的消费者与版本、适用目标、资源及失败合同。没有消费者`CONSUMER_UNSUPPORTED`，有限候选为空`NO_ELIGIBLE_SUPPLY`，预算耗尽但仍有合法候选不得判为全域无解。具体[约束与阶段处理](../../20-语义与组合/组合/开发者决定到文件与执行的确定合同.md)定义这条接缝；测试有限枚举仅证明受限策略，不代替本owner真正求解器。

<a id="gift95-cross-contract-11"></a>
### Method 资格的数值域切片与差额清单

解析一个 `RevisionMonotonic` Requirement occurrence，不能只比较函数名、TypeScript `boolean` 返回型和 `covers`。候选必须同时满足：① 实际入口与 Rule 的正常/异常观测时点一致；② Provider 声明的可表示域包含本次作者可接受域，且**不能把 `uint64`、`number` 安全整数域和无界自然数视为同一域**；③ 参数 Codec 与 Target 数值 ABI/序列化无损；④ 在最大允许 revision 或 delta 溢出时，已证明可辨识的失败结果和“提交前拒绝”；⑤ 存储/并发效果满足所求帧条件，必要时具有真实同事务 CAS + 持久 idempotency；⑥ Rule、Method、Target 与工具链有效修订、环境、保证证据形成共同 read basis。

实现选择可区分三条互不等价的路线：(A) JS `number` + 每次安全整数/溢出边界校验，成本较低但只覆盖 `<= Number.MAX_SAFE_INTEGER`；(B) JS `bigint` + 正规十进制字符串 + 明确 `uint64` 上界与拒绝策略，覆盖整个 uint64 且需端到端保持 BigInt 精度；(C) 任意精度自然数，满足无有限上限的输入域但要求无界编码/资源配额/Target 资格。选择 A/B/C 必须由真实 Requirement Domain 与有资格的 Method Coverage 决定，不根据“更快”或“类型能编译”擅自扩大域。不存在一条路线天然满足所有外部 ABI。

当前 Gift97 仅提供 B 的单进程有限见证，不含生产 Target/Store 合格供应；关联 Gift96 的 `checkedInputDomain` 仍未通过真实消费者签名验证。前置 Need 分别为 AuthorDomainQualification、ValueCodecQualification、NativeBehavior、TransactionStore、Evidence，而非笼统一项“尚需优化”。
<a id="gift98-method-eligibility-executable"></a>
### 成熟引擎的能力供给必须有可证资格

Offer 的 `claimedCoverage`、供应 URI 与 TypeScript/Rust 签名一致只构成发现候选；资格还需匹配输入域、实际 observable guarantee、作用帧、并发/事务隔离、资源/时间、异常/重试、真实 Target 与受支持证据。规则决策、SQL 更新、耐久工作流、优化器和原生函数可以是不同的 Offer 类型，不强迫先变成 Gift111 的计算体。实际世界作用仍要求单独 Grant/Provider/读回。

一个方法对单一意图可用不表示它与另一个对共享状态的方法可合并；全局根所有强约束和子方法前提必须在同一联合解中成立。无资格可报告 `NeedsQualification`，不得用结构有效或方法自报 `verified=true` 放行。
### 模型方法接入目标时的独立资格

[本地持久有限模型消费者](../../70-工程系统与演进/工程构造手册/25-意图到本地持久程序-可运行装配施工.md)只接纳 `finite-model-only` 提供的已检查方法，且编译前全部 achieve/maintain/avoid 联合约束必须在明确模型中找到候选；未知观察、`oblige/permit/prefer` 没有合格 Provider 时拒绝真实装配。它的 SQLite transaction 只改变**显式有限模拟模型**，不会升级原 Method 为生产世界资格。正式引擎资格仍分别审查输入域、观察、权限、ABI、事务/恢复和安全证据。
