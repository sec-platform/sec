# 工作流执行关系与激活：`workflow:plan` 的唯一专业语义

本篇拥有**工作流定义及其发生点**的步骤、输入/结果流、分支、失败与恢复语义。状态机Owns状态和事件转移，UI Owns用户界面，Effect Owns现实端口操作，安全Owner裁定Grant，Method/Target Owns可实现性；本篇只通过有型引用使用它们，不复制它们的独立规则。写在同一个组件里不等于已经构成调用、先后或执行权限。当前机器Body由 [`universal-author-module-2.schema.json`](../../../schema/author/universal-author-module-2.schema.json) 的`Definition.kind=workflow:plan`及`$defs/WorkflowStep`限定；本文补足单靠形状无法定义的业务含义。设计未实施，不宣称存在生产调度器。

## 作者实际需要声明的最小独立决定

工作流定义拥有`input`、`output`、`errors`的准确Type，`steps[]`中的局部stepId、`entry`、可以合法终止的`completion[]`，以及应用于未被局部路径处理的`recovery`政策；如工作流依赖真实截止期、业务上下文，则增加`deadlineRef/contextRoles`。一个从未调用外部端口的纯工作流不因此需要资源Grant、补偿器或持久任务实例。

`steps[]`的**数组排列只供可读表示**，不承担执行顺序。控制关系由`entry`、`needs`、分支/结果后继及可用的输入数据共同决定。每一步`needs`可省略且精确解释为空先决集合；需要先于它完成的真实步骤才显式列出。空`needs`只是不加该类前置依赖，不表示可以越过来源、控制令牌、权限或资源限制。引用`ValueSource{source:"result",stepId,path}`时，该前驱必须已实际成功地产生所需输出；运行器从当前控制令牌的因果环境取得准确StepActivation，不能按stepId查全局“最新值”。尚未运行、兄弟分支、另一实例或另一循环轮次的同名结果不可读。

一个**静态合法的最短无副作用计划**可写为：

```json
{
  "kind": "workflow:plan",
  "body": {
    "input": {"tag": "scalar", "name": "unit"},
    "output": {"tag": "scalar", "name": "unit"},
    "errors": {"tag": "scalar", "name": "never"},
    "entry": "done",
    "steps": [{"id": "done", "kind": "terminal", "outcome": "succeeded"}],
    "completion": ["done"],
    "recovery": "fail"
  }
}
```

它是可放入Module某个`definitions[LocalName]`的定义对象，不是完整模块，也不触发外部效果；显式`onSuccessStep`、空`needs:[]`、空`contextRoles`都不是这个例子的必要作者输入。没有可观察业务作用时不应把它冒充“已经实现笔记保存”。

## Step判别联合与不同的控制合同

| Step.kind | 允许的独立语义及必须补齐的决定 | 不能自动推断 |
|---|---|---|
| `compute` | `functionRef`必须解析为可调用的有型纯/受限效果计算，`inputs`绑定准确函数实参；成功/故障结果进入明确后继或终止 | functionRef存在≠有目标实现；纯计算终止≠业务Goal实现 |
| `effect` | `operationUse.portRef`必须指向合格`effect:port`的具体`operation`，`operationUse.inputs`按该操作签名绑定；授权、幂等、结果和未知结算按EffectOwner | 端口有名≠已获得Grant；超时≠失败；声明Compensation≠真的回滚 |
| `wait` | `resumeKey`确定本次等待发生点，恢复输入的角色、时钟、来源与重复唤醒按被引用的时间/观察资格确认；取消等待不保证并发消息不再到达 | 继续可观察≠等待发生一次；绝不默认为精确一次交付 |
| `decision` | `routes[].whenUse`是有角色实参、Scope、可选Observer的谓词使用，逐分支取合格证据。多真值分支按`selectionPolicy`实现互斥证明或显式不重复优先级；NEITHER/BOTH按`evidenceOutcomes`分别处理 | Unknown不能当False；数组顺序不得冒充优先级；没有独立资格不能签发互斥性 |
| `human` | `actorRoleRef/approvalRef`指定决策或批准主体；身份、能力、拒绝、撤权、超时、审计及复核权由Norm/GrantOwner解释 | UI按钮不自动证明授权或同意；任务被接受不等于批准生效 |
| `subflow` | `subflowUse:DefinitionUse`定位准确子流程并显式绑定其角色；`inputs`独立绑定输入签名，子流程返回/错误与取消向外传播；循环/递归/跨范围资源须明确合法语义 | 同名上下文不自动继承；同名不同实例不互相读取运行帧；子流程终止≠外部结算 |
| `parallel` | 有限非空`branches[]`各为独立子工作流发生点，`join:"all"`，可选`maxConcurrency`；成功返回以branchId为字段的有型记录，非成功先停止派发并取消/结算已启动分支 | 图上并列不证明资源可共享；取消请求不证明活动已停止；没有race/any/quorum |
| `terminal` | `outcome`区分`succeeded/failed/cancelled/timed-out/unresolved`；成功的完整`result`符合`output`，失败的完整`error`符合`errors`，后三者用独立`reason`；出口属于`completion`与实际可到达控制关系 | succeeded不证明真实外部效果或Goal履行，业务结果的Conflict/Failed变体也可作为正常调用返回 |

一个WorkflowExecution的局部控制图每次只有一个活动控制令牌：从entry进入，普通步骤按真实结果选择至多一条同名后继，decision选择至多一个分支或证据处理目标，terminal消费令牌。并发仅由parallel建立独立子Execution；needs或数据引用不会生成第二条令牌，也不启动被引用的步骤。决策的分支选择和wait的已满足继续均是其成功控制出口，两种步骤的成功值均为Unit；它们的来源数据仍从原输入、状态或已成功步骤读取，不能把一个谓词证据对象当作业务返回值。

needs是当前令牌因果环境内的**成功前置集合**，不是等待尚未启动节点的调度表。每项必须可唯一关联到同一Execution中本轮有效且已成功的前驱激活；自身、未来节点、另一支路、已失效循环epoch或非成功激活都不满足。静态确定不成立时拒绝相应控制边；静态无法证明时保留准确数据/进展缺项，不以运行时永久等待掩盖。在单令牌图中把A.needs写为尚未进入的B，即使needs子图无环也不能拓扑启动B。错误处理terminal不得needs它正处理的失败步骤；应通过step-outcome取得错误值。

计算、等待或人工步发生超时、取消、外部错误时，只有相应Step明示且合法的`onSuccessStep/onErrorStep/onCancelStep/onTimeoutStep/onUnresolvedStep`才转移令牌；剩余路径由工作流`recovery`及被接受的执行策略处理。缺处理的错误不得悄悄向正常完成回退；若业务要求补偿、重试或人工介入但没合法机制，停止对应目标资格并保存源设计。未处理的已知调用错误只有在其完整类型可赋给workflow.errors时才能由recovery=fail原值传播；否则必须添加有型处理路径或更正公开错误合同，不能制造截断错误、Text占位或never的值。运行器自身故障和协议破坏不自动成为业务错误；由运行Owner保留故障与恢复事实，尚不能确定结果时保持unresolved。

## 谓词等待与决策的控制出口

四态证据及exclusive/explicit-priority的解释由[作者Profile](../作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#gift137-noncompute-decision-and-obligation)拥有，本篇确定它们怎样移动当前令牌。decision只评估routes[].whenUse，不存在另一个隐含共同conditionUse。每次评估固定相容的观察切面；任一UNQUALIFIED先保留Needs并停止相交准入，不把它作为F。合格结果中只要有BOTH就选择evidenceOutcomes.both；没有BOTH但有NEITHER时选择evidenceOutcomes.neither；保留全部分支证据，不丢掉同时发生的未知。只有所有相关条件均为T/F时才按选择政策取T路线，全部F才取otherwise。该BOTH先于NEITHER的次序只决定异常控制去向，不裁决哪条领域证据为真。

异常证据政策的控制含义如下：manual以unresolved结束当前激活并将同一令牌交给humanStep，step-outcome可取得ControlReason，人工判断仍需自己的权限与证据；wait保持当前激活挂起，resumeKey与准确Execution/StepActivation共同关联唤醒，重新取得观察后评估，不重放此前Effect；reject或缺少对应政策则保留unresolved控制结果和稳定原因，若该步骤有onUnresolvedStep则仅走该边，否则交原恢复Owner，不制造一个不在workflow.errors中的业务异常。显式manual已选humanStep时不再同时走onUnresolvedStep；任何证据处理只产生一个控制后继。缺少otherwise的全F结果以NoMatchingRoute保留未解决控制原因，不能把它当正常完成。若有真实业务拒绝结果，作者应经明确路线返回该业务值。多路线的证据处理目标必须参与控制图与类型/循环分析，不能只在UI显示“待人工”。

wait没有conditionUse时，只有resumeKey所绑定的合格恢复事件能使该步成功；不能仅因进程重启或同名消息到达而继续。有conditionUse时，T使其成功，F继续等待，NEITHER/BOTH沿显式evidenceOutcomes处理；未声明相应政策则继续保留带原因的挂起状态，等待新证据、取消或实际截止期，不能当成功/失败。wait的evidenceOutcomes中action=manual与reject的控制出口同上；action=wait仍是这次激活的重新观察，不创造新的循环轮次。期限缺失不推导有限等待保证，重复/迟到恢复事件不得再次消费一个已完成的激活。

## 输入、结果、上下文和类型不可混成万能值表

`ValueBindings`只是**在一个实际使用点**将形式参数映射到有型`ValueSource`，不构成全工程共享Key-Value状态：

- `literal`是明确类型的固定值；不能用不受约束的JSON替代目标类型精度/名义校核；不必为每个普通静态值新建`core:constant`。
- `input`读当前这次调用收到的、已按`workflow.input`验证的payload；路径按JSON Pointer解释，不允许动态代码求值。
- `context`从选定Root、ComponentInstance和被批准的RoleBinding取值；另一个实例的同名Role不得自动继承。
- `state`必须指向本组件确切`StateParticipation`并说明读一致性与权威，读取不等于持久事务已提交。
- `result`仅引用当前控制令牌所关联的**准确已成功激活**的Step输出；`path:""`为完整值，非空JSON Pointer只作有型投影。
- `step-outcome{stepId,outcome,path}`仅在同一WorkflowExecution中读取令牌关联的准确非成功StepActivation：调用步骤的`outcome=failed`载荷是被调用者声明的完整错误值；parallel的failed载荷按下节聚合类型精确导出；`cancelled/timed-out/unresolved`的载荷是控制原因。成功仍使用`result`。引用的outcome必须与该激活真实状态匹配。
- `resource`引用声明的资源/能力插槽，不代表宿主已发真实Lease/Grant。
- `ui-input`仅来自这次具体UI发生点的节点值，符合其输入模式及隐私读取规则；不能任意遍历别的界面或密钥。

`ValueBindings`的键由消费签名决定，不从运行JSON猜测：compute/human/operation消费自己的具名形参；ActivationRoute和subflow/parallel的workflow输入先解析准确Type。Unit只接受空映射；记录输入按声明字段绑定并通过已资格的输入codec形成完整值，必要字段不可漏、未知字段不可补入，名义记录仍校验其身份与构造约束；非记录输入使用且只使用单个`value`绑定传递完整输入值，不能把变体tag或序列元素拆成伪参数。`value`仅在该非记录输入位置是约定的单形参名，不是全局变量。省略映射等于空映射，绝不等于自动转送整个cause；Opaque/resource类型也不能借记录装配制造能力。每个来源先投影、验证类型与可见性，再进入被调用Workflow的独立input。

外部输入在运行时才知道，不能默默固化成编译期常量；不同ValueSource若字节相同但可信度、授权、时间或采样状态不同，不视为同一事实。`inputs`中的形参键必须与真实被调用操作/函数签名同一命名空间，且覆盖全部必要实参；冗余、漏参、名义不兼容、跨Scope或未经批准的来源应保持可诊断。

## 激活属于组件实例，不属于定义名字

`product:component.workflowUses`只声明某一Workflow定义**参加本组件的某次实例化**。真实起点还需该组件的`activationRoutes[]`有型因果边：路由局部`id`、某个`cause`和被声明的`workflowUseId`及必要`inputBindings`。五种原因保持各自不同资格：

- UI动作：`uiUseId/nodeId`准确定位实例内的UI发生点，节点`actionRef`只引用有业务意义的`domain:meaning`操作，不直接调用`effect:port`。
- Stream事件：`streamUseId`只能定位本组件已参与的事件流；投递、重复/缺失、版本和事件时间由StreamOwner处理。
- API入口：`protocolUseId/endpoint`定位实际由组件承担服务端职责的有型端点；客户端声明不自动产生服务端请求处理者。
- 状态事件：`stateUseId/event`要求宿主该状态发生点并取得合法的事件投递/状态切换关系。
- 调度时间：`scheduleRef`必须具有有权时钟、规则、时间域和有效范围；系统时间文本不构成已经批准的定时任务。

`inputBindings`是唯一当前映射字段，只做形参到有型来源的简单投影；空映射没有同名自动转送。路由处的`input`是本次cause载荷，工作流内的`input`是完成投影后的workflow.input，二者不混读。路由只允许literal、合格cause input、当前组件context/state及本次UI cause的ui-input；尚无StepActivation，不接受result或step-outcome，资源能力由原角色/授权入口传入。复杂格式转换、解析、分支或算法先路由到有准确输入的包装workflow，再显式compute或调用子流程；`domain:meaning`不是functionRef，Method存在也不把路由变成隐藏可执行映射。

单个触发源若路由到两个不同Workflow，必须定义是否扇出、顺序、失败互相隔离、共享上下文/资源及重入保护；不支持的多目标激活须报告具体激活策略缺项，不能借本文parallel语义自动授权扇出。重复的同源同目标路径不能因为数组位置不同而派发两次。一个定义用于两个组件实例或两个ProductRoot，应为每个真实发生点独立识别上下文、输入、权限和运行代际，不能跨实例“自动继续上一次流程”。

## 返回、错误与控制原因的完整值

`terminal`只结束当前WorkflowExecution；`completion[]`必须引用terminal，普通Step无后继不自动形成成功出口。`succeeded.result`是**一个完整ValueSource**，其解析值严格符合`workflow.output`，可以是记录、变体或标量；只有`output={tag:"scalar",name:"unit"}`可省略，此时返回Unit。`never`没有值，不能有可达的成功terminal；不可达声明也不能用来伪造进展保证。Schema可检查必填/互斥形状，跨引用名义类型、可达性和Unit/never的语义仍由绑定/类型/控制分析承担。

`failed.error`必须是符合`workflow.errors`的一个完整ValueSource；`errors=never`不得产生可达failed。`cancelled/timed-out/unresolved`必须提供`reason`，不能写`result`或`error`；reason解析为结构记录`{code:Text,detail:Text}`，其中code为稳定的原因类别，detail供解释。相同原因值仍由outcome区分取消、截止期和未决；不得将其隐式注入业务errors。实际Operation、取消请求、未停止活动、已取得观察和恢复责任仍保存在准确Execution/Settlement记录中，文本reason不替代这些记录，也不能据此释放资源。Execution所属运行Owner必须保留从准确StepActivation到`DurableOperationRef/Attempt`及其Settlement/Readback/continuation的可解析关系；取得本次控制结果后仍能按原身份恢复，具体持久载体由[外部效果与恢复Owner](../../50-执行运行与观测/持久化与恢复/事务提交-外部效果与幂等交付.md#unified-operation-unknown-recovery)维护，不新建影子账本。

例如保存调用的`SaveResult`包含`Saved|Conflict|Failed`，`succeeded`只表示按签名返回了其中一个值；只有符合SaveMeaning/Observation的`Saved`及相应结算才能支持“文档已保存”。[编辑器源码](../../../examples/current/notes-editor/design/interaction.module.json)的成功terminal明确以`{source:"result",stepId:"persist",path:""}`返回完整SaveResult，人工审阅后仍未取得结算则以unresolved和独立reason结束控制请求。已知调用错误、未知效果和业务Conflict不相互强制转换。persist之后的观察、决策或人工步骤失败不撤销它已发生的效果；该失败只改变当前控制结果，原Operation的Settlement及恢复责任继续存在。

## 控制令牌、循环与子流程的作用域

运行器为每次进入步骤派生准确激活身份，至少可区分`WorkflowExecution / invocation path / branch occurrence / loop activation / stepId / activation ordinal`；这些是运行事实，不要求作者重复写入源码。每个控制令牌携带所依赖激活的不可变因果环境；Step结果写入该激活的一次结果槽。每次循环重新进入一个Step产生新激活并遮蔽旧绑定；未经本轮实际产生的值不能沿全局缓存补入。旧轮次/别的分支值只有作为新调用的显式有型输入传入，才成为当前input，不能越界用stepId读取。

循环代际不能只靠一个未定义的“iteration”标签。当前局部控制图以有名结果后继、routes/otherwise及evidenceOutcomes.manual的humanStep为边，按entry计算可达性与支配关系；needs和ValueSource引用不是控制边，wait的原激活恢复也不是新一轮控制回边。目标支配来源的回边形成自然循环：自环区域仅含该节点；其余回边从来源沿前驱反向收集至header且不越过header。**同一header的全部回边先合并为一个循环区域**，再检查不同header的区域单入口且彼此不相交或严格嵌套；不能将同header的多个continue路径误判为交叉循环。首次进入和每次回边分别创建该循环的新epoch，进入新epoch时清空区域内旧StepActivation引用，区域外的共同前驱仍按原因果环境可用；嵌套循环重开同时废弃内层旧epoch。无法形成该结构的不可约多入口环、交叉循环或企图隐式携带旧步结果的回边不属于本有限Writer的已定义直接循环，给出准确图位置与结构不支持诊断；作者须改为具有显式inputs和角色的子流程/递归接口，或通过已声明状态合同传递数据，不能回退到“最后一次同名结果”。这种结构限制不证明终止，进展、取消和预算仍单独检查。

后继读取result或step-outcome时依次核同一Execution、令牌因果关联、准确激活/outcome、载荷类型与Pointer路径。分支合流若无法在所有可达路径唯一确定所指激活，属于缺失或歧义来源；不得任取最晚完成者。多条非成功路径合流后直接读取某一步failed，也须证明每条到达路径都携带同一合法来源；否则分别设置转发terminal或有型包装流程。错误处理路径不把failed伪装成成功result，非成功依赖也不靠“needs成功”补齐。

`subflowUse.ref`必须解析为`workflow:plan`；`subflowUse.bindings`逐一满足子定义的contextRoles，省略是空映射，即使父、子角色同名也不继承。`inputs`映射子流程输入，与角色绑定是两条独立关系。调用建立独立WorkflowExecution，父只能通过该subflow Step的有型返回或step-outcome消费子结果，不能引用子内部StepId。取消/截止期向已启动子流程提出请求；子流程的未停止活动或未知外部结算不能因父步骤已收到请求而消失。成功返回、已知失败或控制结果只在对应结算/交接条件满足后传播；精确递归调用仍需原有资源与进展资格。

## 有限parallel：独立子流程与all-join

`parallel`是本工作流的一步，不是全局fork/join图。`branches[]`为有限非空列表，每项`{id,subflowUse,inputs?}`；id在这一步内唯一，subflowUse与串行subflow采用相同角色规则。数组次序只用于有界派发的稳定候选顺序，不规定子流程真实完成次序；无跨分支业务先后保证。`maxConcurrency`若省略等于分支数，显式值须在1到分支数之间；大于分支数是冗余错误，不能成为动态无界扩张入口。仅`join:"all"`有效，不引入race、any、quorum、运行时增长分支或兄弟引用。

1. **进入与冻结。** 在该Step激活的同一父输入/因果切面解析各分支输入和显式角色；对状态来源使用已合格一致性策略。不能取得一致切面或独占资源分配时停止在准确资格缺项。子流程内部状态/外部输入仍按自己的运行合同取值，并不因此被冻结。
2. **隔离与派发。** 每个分支是独立子执行与结果槽。分支输入只能使用进入时可见的父来源，不能读取兄弟结果、兄弟私有状态或自己的未来结果。共享角色只有在读共享、互斥或其他并发/所有权合同实际允许时可复用，不能复制exclusive能力；无法安全并行时可选`maxConcurrency:1`，但仍须满足跨分支所有权与外部效果约束。
3. **成功join。** 仅全部分支成功且所要求的停止/结算成立时，parallel成功产生结构记录`{branchId: ChildOutput, ...}`，字段集由声明分支精确导出，每个值是完整子流程返回值。后继通过`result`读取该聚合记录或有型字段，不能引用兄弟的内部StepId。空/缺失分支结果不得补null，Unit也保留其字段和值语义。
4. **停止派发与结算。** 任一分支非成功，或父取消/截止期到达，原子停止未派发分支，向其余活动分支请求取消，按准确操作身份读取其停止/结算状态；已完成成功值和已发生效果仍保留。不能因超时立即将运行中分支记为cancelled。任一子流程已经返回unresolved，或存在未知外部结算、取消未确认、仍活动且未获权交接的分支，均使本步为unresolved，走onUnresolvedStep或原恢复合同；不走onErrorStep，不释放其实际资源或并发占用。
5. **合并非成功结果。** 只有各子流程已有确定的非unresolved控制结果，且全部已启动分支已停止或按原Owner获权交接、父步无未交接责任时，才进入已知结果分类。责任已交接只能使旧执行可以退出或释放其已转移占用，不能把一个子unresolved改成cancelled或failed。任一已知failed使本步failed；否则任一真实timed-out使本步timed-out；否则取消或因停止派发而未启动使本步cancelled。父取消/截止期亦参与这一控制原因判定：先确定failed，否则父截止期或子timed-out决定timed-out，否则父取消或子cancelled/NotStarted决定cancelled。成功发布与取消/截止期接收须在该激活上有唯一线性化次序；成功已发布后到达的请求不改写旧结果，若请求先被接受则不能因全部孩子随后成功而吞掉它。此处顺序是结果分类，不能擦除同时发生的其他原因或用于重放外部动作。整体failed载荷是结构记录`{branches:{branchId:BranchOutcome,...}}`：每个BranchOutcome是`Succeeded(ChildOutput)|Failed(ChildErrors)|Cancelled(ControlReason)|TimedOut(ControlReason)|NotStarted(Unit)`的封闭变体，省去ChildErrors=never的不可构造Failed支；至少有一个真实Failed。所有子错误均保留，禁止按竞速丢弃“次要”错误。若所有子errors均为never，该步的failed类型亦为never。其余三种整体控制出口传ControlReason，完整分支结果仍在Execution中保留。
6. **后继与回收。** 对外只发布一次已接受分类及载荷，后继按对应有名边进入；所有实际资源只有在真实停止、清理成立或已获权移交到明确恢复Owner后回收。unresolved之后取得新证据属于原Operation的结算/恢复，不能凭旧parallel StepId重新启动全部分支。若Target不能保留激活身份、有限并发、取消或结算责任，报告对应能力缺项，不生成看似并行的Promise数组冒充完整实现。

## 旧载荷的只读迁移与拒绝条件

当前Writer不再写`inputMappingRef`、`resultBindings`或`subflowRef`。旧内容连同来源revision只读保存，不能在同一当前Body中保留新旧两种活动含义：

- `inputMappingRef`只有在准确旧映射的输入/输出、callable身份、类型、错误、效果、角色和权限保持证据齐全时，才迁成简单inputBindings，或显式compute/包装workflow。仅有domain:meaning或同名Method不足以证明callable；缺依据保留`NeedsActivationMappingMigration`及具体缺项。
- `resultBindings`没有统一的旧返回、字段重命名或写状态含义。先确认真实旧读者及每项用途，再证明其能等价形成一个完整result/error/reason或原有有权状态操作；不能用键相似或把map放进result.value来猜。无法证明时保留`NeedsWorkflowResultMigration`，不将缺返回的非Unit成功接纳为当前有效程序。
- decision中的旧`conditionUse`以及步骤中旧`onUnknownStep`不再是当前Writer字段。分支条件使用routes[].whenUse，四态处理使用evidenceOutcomes；wait仍可使用conditionUse。旧decision的共同条件若没有明确真假后继和证据处理含义，不猜为与每条分支合取；保全旧源并报告`NeedsWorkflowPredicateMigration`。已知含义的共同前置条件可以形成显式单分支decision和准确后继，旧onUnknown只能在保全NEITHER/BOTH处理及真实人工目标/恢复键时迁移。
- `subflowRef`只有在旧调用签名、输入与角色来源可确定时迁到subflowUse；无contextRoles或已确证显式实参可形成空/准确bindings。依赖同名环境自动继承的旧调用须取得准确对象/作用域/权限证据并显式化；否则保留`NeedsSubflowBindingMigration`，不能偷偷扩大父可见范围。

迁移先形成单一候选并核对所有引用、结果类型、失败/控制出口、效果与恢复，再切换当前Writer；中断保留前像，不能让新旧运行帧互相读值。新Schema能接受结构不代表这些迁移证据已经取得。

## 控制、失败、恢复和资源的最小正确性条件

1. **图闭合**：所有`entry`、`completion`、`needs`、分支及后继stepId必须在本Definition中唯一解析；正常路径的不可达终止、无进展循环、分支不覆盖和未定义出口都必须明确限定为合法部分过程或设计缺额，不能无声拼接。
2. **数据闭合**：当前控制支路必须可以取得每项Result、StepOutcome、Input、Context、State或Resource来源，类型和效果在原签名及scope下合法；任何隐式跨root共享必须先取得真正对象同一性的证据。
3. **分支三/四态**：领域命题具有True/False/Unknown及矛盾或不可采纳的资格分界。互斥与覆盖不是由分支的排序、数量或一次模型运行证明；Unknown和Conflict必须流向明确定义的补取、人工处理或未决，不得强制归并False。
4. **并发与重试**：本地`needs`只表达静态数据/进展要求，不替代全局共享资源排他、原子事务、死锁避免和流背压。重试需要操作幂等身份和有效期；取消和超时只能改变控制请求状态，不能保证已经发出的外部效果没发生。
5. **恢复语义**：`recovery=fail`允许准确报告失败，不能在效果未知时声明失败且无作用；`retry`需要可判定是否安全再执行；`compensate`需要真正具资格、可观察的补偿操作，通常不恢复原状；`manual`要有真正的负责主体、可恢复状态与可审计的手动结算边。
6. **目标降低**：Method负责计算、控制、持久任务、宿主适配是否有合格供应；Target负责将选定计划映射为普通TS/Rust程序、真实事件处理入口、正确结果类型、合法异步/并发/存储和可靠恢复。只输出步骤数组或函数stub不是可执行的完整产品。
7. **生命周期**：WorkflowDefinition、某ComponentInstance的WorkflowUse、一次WorkflowExecution、外部Operation、Attempt和Settlement都是不同实体；冻结源和部署更新不会自动篡改已在运行的Execution版本。跨版本恢复须明确状态迁移、旧目标依赖和禁止重复作用的边界。

本规范的目标是让**同一个作者Body具有唯一可实现的业务意义或精确的Needs/Conflict边界**，而不是写检查器或宣称源已能直接运行。程序可以局部合法而整体目标未满足；定义/运行/观察/验收不能合并为一个布尔字段。
