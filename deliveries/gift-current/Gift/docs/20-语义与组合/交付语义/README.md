# 交付语义与消费边界

本目录拥有“作者已定义的工程含义最终怎样形成**可被真实消费者使用的交付边界**”这一组跨业务合同。它不提供业务模板，也不建立 Web、服务、游戏、仿真、训练器、GPU、固件等封闭的产品类型枚举。

Gift 的交付形态由相交 owner 的合同**组合得到**，而不是先选择一个 `ProductKind`：作者语义说明结果是什么；Requirement 说明必须保持什么；实现解析固定真实供给；Target/Artifact 说明目标成员；Execution/Host 说明实际生命周期和作用；Assurance 说明哪些 Claim 已有证据。任何常见名称都只是这些合同的一种投影。

## 正交组合面

一个交付只实例化实际相交的面；没有责任的维度不制造占位配置。

| 组合面 | 需要明确的问题 | 真实 owner |
|---|---|---|
| 语义根与公开结果 | 哪些 Definition/Requirement/接口语义必须被消费者观察 | 作者语义、组合与公共语义 |
| 消费入口 | 链接、调用、消息、流、界面、文件、设备入口或安装动作是什么 | 本目录与目标合同 |
| 生命周期 | 静态、一次性、会话、长驻、周期、可暂停/恢复如何结算 | 本目录、运行生命周期 |
| 状态与持久性 | 无状态、实例状态、持久状态、外部状态分别由谁拥有 | 语义/运行/持久化 owner |
| 时间、调度与并发 | 顺序、背压、deadline、并发额度、取消和终结含义 | 标准语义模块、运行与 Provider |
| 效果与权限 | 文件、网络、进程、设备、发布等真实作用在哪里准入 | Execution / Grant / Operation |
| 拓扑与隔离 | 同进程、工作进程、远端、设备、沙箱等物理边界 | Provider / Host / Target |
| Target / ABI / 数据表示 | 目标语言、布局、编码、调用约定和兼容条件 | Target 与目标表示 |
| Artifact 与发行 | 哪些成员必须共同封存、怎样被分发/安装/采用 | Artifact / 发布合同 |
| 升级、迁移与恢复 | 新旧定义/实例/数据怎样共存、切换、回退和退役 | 演进、持久化与恢复 |
| Evidence | 哪些设计/实现/运行性质必须在什么环境下证明 | Assurance |

这些面不是一张要求作者填写的巨型表，也不形成新的全局 `Deliverable` 真值数据库；它们是对已有准确对象和关系的组合视图。

## 冻结范本的角色

完整组合研究在同包[依据区](../../../fixtures/compositions/README.md)可查，可校准“某组合同能否组成一个完整交付”和构造验收载荷。所提及但未携带的冻结历史 JSON 原件仍须取得准确制品，不能把研究文字称作原件或现行规范。活动作者**不得**把历史范本中的 `definitions.json`、`model/*.json`、`公开边界.d.ts` 或任何同类旧文件当成当前默认定义库；它们也不能成为 resolver、生成器或 Workbench 的隐式输入。

若活动设计需要一个可复用标准 Profile，应在当前作者/模块体系中以新的准确 identity/revision 发布，并独立经过实现、目标和 Evidence 准入；不能因为冻结范本存在就视为已发布。

## 完整性边界

一个形态只有在其实际相交的公开边界、输入/输出、生命周期、失败、资源、权限、目标成员、兼容/迁移和验收责任都闭合时，才可称对应范围的设计完整。设计完整、实现完整、验证成立、已采用/部署仍是不同事实。

具体判据由[交付设计完整性合同](交付公共合同.md#gift-unit-fc3de891eb2355f1aa65579f2f2f8dd3)维护；[供给与实际发射](../../40-目标与制品/目标/交付消费合同与发射.md)负责把已固定语义和 Binding 形成真实目标成员及准确缺项。
