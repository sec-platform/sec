# 规范元模型与结果语义

<a id="gift137-evidence-versus-disposition"></a>
## 非计算业务判定的证据、处置和实际作用边界

`EvidencePair` 的四态只在锁定Meaning、角色、观察时空域及有权来源**均取得资格**后成立。`NEITHER` 不等于假，`BOTH` 不等于真；缺Meaning/Observer资格不能包装成第五个可由业务处理的“真值”。同一个决策动作需分别保存原始证据、解释范围、处置选择与处置授权，不能只留下最终跳转的 `nextStep`。具体工作流写源字段由作者Profile定义。

业务处置是作者接受的下一步责任，而非系统自动取得执行许可：`reject` 返回明确失败；`manual` 指向具有人类参与合同的工作流步骤；`wait` 需具备持久的恢复关联标识，避免重试跨请求串扰。合格的事实证据不自动取得政策许可，政策Permit不自动取得HostGrant；真实Operation是否发生、外部结算以及读回仍必须分别验证。

规范性规则的 `oblige` 至少须引用真实可履行内容，后继解释者须检验义务主体、触发、到期、解除、例外和规范来源。`first-applicable`、`deny-overrides`、`permit-overrides`、`explicit-priority` 不能一律解释为带权的布尔或序列遍历：跨签发者优先级、过期规则和多项相交义务必须由有权规范解释合同解决。一个 `obligationRef` 只是义务内容入口；若没有可证明的规范解释，停在 `NeedsNormMeaning`，不得自动履行。


## 规范元模型

### 核心范围

核心给工程实体、引用、修订、来源、类型化关系、诊断和变更提供共同协议，不预先枚举世界名词。程序语义仍由所选计算作者语义、原生方言和领域扩展共同定义。

`Subject/Statement/Relation/Constraint/Transition` 可以作为规范与知识的建模工具，但不要求每个表达式都包装成五类治理对象；编译器的表达式、语句、类型与符号应有适合遍历和类型检查的具体结构。

### 三种状态不混用

已接受程序定义有一个明确生效版本；观察可以多来源且冲突；AI 推断和搜索候选可并存。联邦知识模型可以容纳第三方规范冲突，但不能让一次普通构建的同一函数同时拥有互不相容的函数体。

### 共享合同

共同基础包括稳定引用、内容身份、语义修订、可达依赖、来源映射、问题定位、支持状态和演进关系。运行凭证、租约、进程号、临时路径和模型会话不进入程序语义身份。

语法合法、类型合法、目标可降低、测试通过与行为证明是不同状态。注册扩展只建立所选上下文中的可查找入口；结构理解、语义方法、目标支持和 Evidence 资格按实际消费者判断，不赋予任何源码写入或事实签发权。

### 理由与反证

公共内核只接纳跨消费者不可替代的引用、身份、组合或错误不变量。新增原语须给出：现有扩展/组合无法保持的具体差异、受影响消费者、类型与语义规则、迁移和删除后果。多消费者复用是正面证据，不设任意数量门槛；单个消费者揭示核心不可绕过的安全/身份缺陷也必须修复。局部领域概念、可组合规则及原生实现细节留在其所属 Profile。

若新增语言必须改通用 pass 的品牌分支，核心不够可扩展；若一个简单函数必须实例化社会选择与风险对象，核心过度抽象。

### 对象层与实现层的收敛约束

公共元模型只提升需要稳定引用、独立消费、编辑、证据或迁移的对象为显式工程实体。AST 临时节点、函数参数和纯派生结果默认保持轻量结构；派生视图只读，不能复制第二份可写源。权威、观察、派生及控制的职责见[统一架构](../../70-工程系统与演进/协作与状态边界.md)，表示细节归[中间表示族](../../40-目标与制品/表示/表示族与跨层保持.md#中间表示族与按输出阶段提升)。

## 错误、诊断、结果与可恢复性

### 设计原则

跨模块、跨进程及持久边界必须公布稳定的结果 variant、错误身份、诊断及恢复后继；进程内纯计算允许沿语言原生类型返回。各类纯值、MethodOutcome、事务提交、Operation 结算及验证判断由其 owner 定义；统一的是可观察区别和映射纪律，不要求每个函数返回同一个包装类型。

<a id="result-algebra-boundaries"></a>
### 结果类型

本页唯一规定错误身份、诊断来源与跨边界映射，具体结果沿[局部结果代数](#outcome-不是一个万能状态各因果角色拥有局部结果代数)解释；不新增 `Outcome<T>` 或全局执行完成枚举。`ok/failed/unknown` 仅在原 owner 的范围内有效，跨阶段须以合同显式转换。

| 生产者及结果 | 消费者必须保留的区别 | 合法的后继 |
|---|---|---|
| 纯方法的 `Done / Needs / Stopped` | Done 携带的是该方法结果，可以是有效性检查不通过；Needs 有精确缺项；Stopped 保留原输入无效、不支持、取消、预算或实现失败 | Application 形成后继输入或结束本次请求；不据此推进真实作用 |
| 查询、读取与观察 | 完整空集合、有限覆盖、不可见、不可读、陈旧和损坏不同；partial 必须绑定允许部分结果的用途与缺口 | 消费者按自己的完整性要求接受、补取或拒绝，不能从“没有返回值”证明不存在 |
| 状态提交、日志追加与外部作用 | 确认发生、确认本次未发生、部分发生和完成未知分别保留；原 Operation/Attempt 不因返回错误而消失 | 使用[存储端口](../../50-执行运行与观测/持久化与恢复/持久状态与存储协议.md#storage-port-results)和[尝试终局与重试](../../50-执行运行与观测/持久化与恢复/事务提交-外部效果与幂等交付.md#attempt-finality-and-retry)决定读回、等待、恢复或新尝试 |
| 验证方法与 Claim | applicable、capability、acquisition、方法结论和 Evidence qualification 分开 | 按[会话结果](../../60-保证与证据/验收/会话集成与结果复用.md)聚合；取得结果不等于 PASS，运行成功不等于 Claim 成立 |
| 目标程序的值、错误和异常 | 作者要求中的错误值、抛出、捕获、取消和资源释放语义 | 由所选语义与 Target 保持；不强制改写成 Gift 宿主工具的错误码 |

这些行是消费者关系，不是新增联合类型。结果引用 Evidence 时只表示关联，是否可用于某个 Claim 仍需独立资格判断。`partial` 只用于合同明确允许的部分值；持久效果不能以“有部分 value”掩盖不确定提交。一个调用已返回，不意味着相交 Operation、进程或恢复责任已结束。

**跨边界映射算法：** 先固定源协议/版本、subject、basis 和调用目的；按源 owner 解释局部 variant；保留该解释及原结果/回执引用；再逐项检查消费方的完整性、效果和保证要求，产生消费方自己的结果或准确缺项。无法证明映射前提时不得制造更强结论。映射记录只在跨进程、长寿命或审计需要时持久化；普通进程内调用使用类型化参数即可。

例如“验证方法执行成功且发现反例”是取得方法结果成功、方法结论失败；“提交成功但响应解码失败”是调用错误、效果待原身份确认；“观察者取消等待但 worker 仍运行”是请求结束、执行未终局。三者都不能由一个 `ok/error` 或严重度最大值无损表达。

### 错误分类

```text
InvalidInput
NotFound
Conflict
Unauthorized
Forbidden
Unsupported
Ambiguous
IncompleteObservation
UnsatisfiedConstraint
ResourceExhausted
DeadlineExceeded
Cancelled
DependencyUnavailable
ExecutionFailed
VerificationFailed
UncertainCompletion
DataCorruption
InternalInvariantViolation
```

上列名称是语义类别，不是全系统封闭枚举；稳定错误码由对应领域命名空间与 schema 定义。`NotFound` 只在该读取合同给出适用范围的权威缺失观察时成立；为防枚举而隐藏资源可以返回不披露结果，但不能让它成为内部的不存在证明。每个错误定义：

- 稳定错误码；
- 所属领域和 owner；
- 用户可见消息键；
- 结构化详情 schema；
- 重试建议、必须重新检查的前提及原 Operation/Attempt；建议不是执行许可；
- 效果观察的来源、覆盖和确认程度；不能仅凭错误类别断言无效果；
- 允许的恢复动作；
- 敏感字段和脱敏；
- 兼容与废弃策略。

<a id="error-envelope"></a>
### 公共 failure 的交换载体

需要交换或持久引用的公共 failure 使用下列 `ErrorEnvelope` 语义形状；具体 operation 的结果代数在自身失败分支引用它，不把每个普通值都包成 Envelope。代码字符串不能代替 schema 协商。

```text
ErrorEnvelope = exact {
  errorCode,
  errorSchemaRevision,
  operationAndSubjectRefs,
  failureClass,
  effectState,
  retryabilityAndPrecondition,
  recoveryActionRefs,
  diagnosticArgs,
  causeRefs,
  disclosureLevel
}
```

`operationAndSubjectRefs` 绑定实际对象、版本与已存在的操作/尝试；纯计算没有 Operation 时显式表明不适用，不伪造执行身份。`effectState` 引用原 owner 的效果观察及其范围；无效果只在纯合同或有效无效果依据下成立，回执未知仍为未知。`retryabilityAndPrecondition` 是候选建议与适用条件，不是布尔执行开关；产生新尝试仍必须消费原[RetryBasis](../../50-执行运行与观测/持久化与恢复/事务提交-外部效果与幂等交付.md#attempt-finality-and-retry)、当前授权、前像和预算。一个依赖暂不可用不证明先前提交未发生。

`recoveryActionRefs` 只定位候选恢复，不授予作用；`diagnosticArgs/causeRefs` 保留结构化因果与受控原始 Provider/errno 引用，不能把自由文本作为控制流。`disclosureLevel` 约束消息、参数、subject 与 cause 的可见范围；跨租户/客户端裁剪不能泄露秘密或存在性，也不能将被裁剪的信息改写为“确认没有”。不能披露的细节由有权 owner 保留，公开端只报告该用途实际可知的范围。Provider 文本、路径与修复描述仍是不受信数据，不能自动执行。

错误 schema 规定 code 命名空间、已知类别、参数编码、未知 code/variant 的保全与拒绝策略。新增 code **只有在消费者已声明兼容未知 code 且既有含义不变时**才是 additive；对封闭消费者、改变既有 code 含义/必需参数/效果解释的变更，必须协商或迁移。未知 code 可在已理解的上层 failure 合同中保留；未理解连同效果语义时停止依赖该解释的自动作用，按原身份查询，不默认 retry、成功或无效果。旧消费者可继续无关且已理解的只读工作。

此映射边界的原始反例见[gRPC 状态码与效果](../../../research/sources/语言编译与目标工具.md#rpc-status-effect-boundaries)和[未知枚举语义](../../../research/sources/语言编译与目标工具.md#enum-occurrence-preservation-sources)。它们支持必须区分的条件，不替 Gift 的实现或所有 Provider 签发符合性。

### 诊断模型

```ts
interface Diagnostic {
  readonly code: string;
  readonly severity: 'info' | 'warning' | 'error' | 'fatal';
  readonly messageKey: string;
  readonly primaryLocation?: SourceLocation;
  readonly relatedLocations: readonly SourceLocation[];
  readonly subjectRefs: readonly SubjectRef[];
  readonly causeRefs: readonly DiagnosticRef[];
  readonly explainGraph?: ExplainGraphRef;
  readonly possibleRepairs: readonly RepairCandidateRef[];
}
```

人类语言文本由 `messageKey + locale` 派生；错误码和结构化字段不翻译。

### 完成状态与错误分离

| 独立观察面 | 唯一解释来源 | 不蕴含什么 |
|---|---|---|
| 请求/等待者是否返回或取消 | Application 的本次请求寿命 | 不证明 worker 停止或写入撤销 |
| Attempt 是否已提交、仍在途或已经终局 | 实际 Provider 与执行 owner 的尝试记录 | 终局不必成功；另一次旧尝试也未必已结束 |
| 目标效果已发生、未发生、部分或未知 | 原 Operation 的回执、权威读回与覆盖 | 内容碰巧相同不能确认由该操作产生；一次负读回不能封闭迟到效果 |
| 资源、补偿及恢复责任是否结算 | 原 acquisition/recovery owner | 业务效果成功不证明资源释放；补偿不抹掉先前已经发生的事实 |
| 是否满足 Requirement/Claim | 精确对象的 Assurance 判断 | 不能由进程退出、操作成功或 Settled 自动升级 |

“超时”“取消”“连接断开”描述调用者观察，不直接说明效果完成状态。`Running → EffectMayHaveOccurred → Settled` 不能作为跨域总枚举：正在运行也可能已有部分效果，已返回也可能仍待恢复，失败但确认无效果的操作也可以正常结算。执行的具体转换由[提交与不确定完成](../../50-执行运行与观测/持久化与恢复/事务提交-外部效果与幂等交付.md)拥有，本页不复制一份竞争状态机。

### 异常边界

Gift 自身入口/适配器在声明的公共协议边界把宿主异常转换为该 operation 的局部结果和结构化诊断；保留原因、已产生作用的观察及释放责任。一个 await/调用抛出异常只证明正常返回路径中断，不能证明提交未发生。原生库内部或已明确协商的 ABI/语言调用边界可以按自身合同传播异常；只有有保持依据的边界才能捕获、重抛或转换，不能用“跨模块”一律禁用合法目标语义。

目标程序的显式错误值、异常展开、panic/abort、取消及析构/清理按所选语言/Target 合同处理，不强制变成 Gift 的 `ErrorEnvelope`。不可展开的 ABI、进程死亡和硬终止也不能伪造为“已捕获并完成清理”；把实际未结算交还原执行/资源 owner。禁止：

- 让客户端解析异常文本，或把所有错误映射为 `InternalError`；
- 丢失 Provider 原始受控回执，或用局部异常覆盖已确认效果；
- 把未知转为 false、把不支持/拒绝披露转为空集合；
- 仅凭退出码、catch/finally 已进入或调用已返回，判断持久效果和资源已结算。

FFI 的实际条件见[Rust/C++ 异常依据](../../../research/sources/Rust与C++映射依据.md#ffi-异常边界的相交复核)；源码语言具有相似语法不构成同 ABI、同展开或同清理保证。

### 因果链

错误包装保留：

```text
RootCauseObservation
→ AdapterDiagnostic
→ DomainError
→ ApplicationOperationResult
→ LocalizedPresentation
```

每层可以增加上下文，但不能删除原效果观察、重试前提和敏感边界。下游生成新的领域 failure 是一次有版本的映射，不原地改写上游回执。

### 修复候选

诊断可以包含可执行修复候选，但候选不是自动授权：

```text
RepairCandidate = {
  targetProblem,
  proposedDelta,
  assumptions,
  requiredAuthority,
  effects,
  risk,
  verificationPlan
}
```

选择后仍进入正常编译、计划、准入和验证链。

### 验证

- 每个 public operation 声明自身结果及允许部分值、未知 variant 和异常的边界；
- 封闭且已知版本的 union 由穷尽检查发现未处理分支；外部开放协议的未知 code/variant 由实际解码与协商处理，不能用编译期穷尽宣称远端永不新增；
- Provider 错误映射做黄金向量和故障测试；
- 敏感字段脱敏做负向测试；
- 取消、超时、响应丢失和进程死亡分别测试；
- 错误 schema 向后兼容；
- 本地化文本变化不改变错误身份；
- 恢复器只消费结构化状态，不解析日志；
- 分别检查“方法完成但 Claim 失败”“提交响应丢失”“取消等待但工作未停”“空页但扫描未完”“新增错误码被旧客户端误当可重试”，确保跨层映射不升级结论。

<a id="gift-failure-state-no-bool"></a>
### 失败返回的阶段、可继续性与非对称状态

统一交换外壳可以携带 `kind/subject/basis/cause/retryOrRepair`，不能因此合并不同owner的终态。至少区分**未开始、已准备但未提交、确定拒绝、正在运行、请求者不再等待、作用可能发生但未结算、已观察效果、证据不充分、证据判定失败、已部分交付**。其中`cancelled`通常说明消费者等待终止，不证明操作未发生；`timeout`是观察失败而非效果不存在；`incomplete`不必然是错误，却不能冒充完整目标成功。

结果必须把当下可做的下一步绑定原身份：纯查询可以在有效basis内重新求值；需要更多输入则返回准确Need；作用未知必须沿原Operation协调而非另建任务；Claim不足须补足相交证据。展示层可聚合为简单状态，但不得丢弃从该聚合恢复所需的真实局部状态、未结算义务和责任owner。若请求取消发生在已提交/不可逆操作之后，返回值要揭示生效范围，不能统一回滚。

## 不同控制与状态域不能按同名合并

语义身份使声明可以跨变更引用；它不要求每个目标数据元素都持久化。计算中的值依赖、循环携带、缓冲别名、同步关系与布局分别按其合同解释；业务实体关系、事务读写和消息因果关系也分别解释。它们可进入共同的类型化关系框架，但“有箭头”不允许同一种遍历/调度算法解释全部边。

一个大程序按真实消费者、不变量、数据结构、计算阶段和生命周期划分。边界需要细化时可以分层，但不把每个函数强制升格Domain或每个采样升格Operation。模块分区与实际事务/同步/部署域允许不同，不要求一对一。当前计算机制的唯一详细规则见[计算结构](../基础语义/计算基础/计算结构与算法.md)。

## Outcome 不是一个万能状态：各因果角色拥有局部结果代数

Gift 不定义 `UniversalResult`、`GlobalStatus` 或“取最差状态”的跨层枚举。不同 owner 的结果回答不同问题；相同单词 `unknown` 也必须带上**未知的对象与判断角色**。只有显式 typed relation 才能把一个结果作为另一层的输入，不能靠名字相同或严重度排序自动转换。

| 局部结果代数 | 它回答的问题 | 不能自动推导 |
|---|---|---|
| `MethodOutcome = Done / Needs / Stopped` | 一个纯方法在固定 basis 上是否产生了其合同结果、还缺什么、为何停止 | `Done` 不等于工程有效、Claim 通过或 Effect 完成；`Needs` 不等于错误 |
| Assertion/Resolution 的 `known / unknown / ambiguous / conflicting / stale / invalid` | 一个命题/解释在当前来源与解释域内可否被消费 | `known` 不等于有执行权限；`conflicting` 不等于某次 Operation 失败 |
| Operation/Attempt settlement | 真实作用是否 confirmed-applied、confirmed-not-applied、partial、completion-unknown，以及恢复责任 | 超时/未知不能转成业务 false、验证 failed 或安全重试许可 |
| Observation/readback completeness | 对现实状态实际观察到了什么、覆盖和新鲜度如何 | “没观察到”不等于不存在；readback positive 不等于 Requirement 正确 |
| Verification/Claim qualification | 某个精确 Claim 的 applicable/capability/acquisition/method conclusion/Evidence qualification 是否满足组合规则 | gate PASS、工具 exit 0、历史 Evidence、Operation success 都不能单独签发 Verdict |

跨层转换只允许由消费方的合同完成。例如 `MethodOutcome.Needs` 可以让 Application 取得输入并形成后继 basis；Operation 的 `completion-unknown` 可以驱动 readback/recovery；Observation 可以成为 Evidence 候选；Qualified Evidence 才可参与 Claim 聚合。每条转换保留原结果身份和来源，不“升级”原状态，也不把多个维度压成一个总体颜色。客户端若显示单个摘要，只是 Projection，必须可下钻恢复这些独立维度。

`Need` 本身是**某个消费者在固定 subject/scope/basis 下缺少输入、能力、解释、决定、证据或资源的关系**，不是新全局作者 Requirement，也不等于 `MethodOutcome.Needs` 这个本次方法结果 variant。每个 Needs 结果只能指向其本次 basis、消费者、缺失项/覆盖、阻断范围与可合法取得的后继；可由补取、解释裁决或消费者退出而解决/失效。若缺项实际暴露出产品定义未完整采纳，只能提出有来源的作者候选交有权采纳，Method/Resolver 不能把 Need 直接写成 Required 功能。Requirement 暂时未被实现也不会无条件产生一个无主体、无取得途径的通用 Need。

这条规则同样适用于错误、取消、unsupported、stale、not-applicable 和 partial：它们是**owner-local semantic variants**，不是全系统共享的严重度等级。要新增全局结果类型，必须证明多个现有结果在 identity、writer、生命周期、消费者和恢复语义上确实相同；仅为了统一 API 外观不成立。

## 公共契约外壳与作用资格的区分

- **Policy**：由[授权与执行准入](../../50-执行运行与观测/权限与资源/授权与执行准入.md)维护其实际状态、资格、失败与消费限制，公共 Contract 外壳不签发它。
- **Permission 与 Grant**：由[授权与执行准入](../../50-执行运行与观测/权限与资源/授权与执行准入.md)维护其实际状态、资格、失败与消费限制，公共 Contract 外壳不签发它。
- **Verification Requirement**：由[要求证据-要求主体与声明范围](../../60-保证与证据/保证/要求证据-要求主体与声明范围.md)维护其实际状态、资格、失败与消费限制，公共 Contract 外壳不签发它。
- **Support**：由[适用性与能力协商](../../70-工程系统与演进/演进与实施/适用性与能力协商.md)维护其实际状态、资格、失败与消费限制，公共 Contract 外壳不签发它。

### 一个万能 Contract 会失真

不同边界需要不同 payload，但共享可寻址承诺的 envelope。

```text
ContractDefinition = exact {
  contractRef,
  contractKind,
  semanticScopeAndResponsibilityRefs,
  payloadGrammarRef,
  producerAndConsumerRefs,
  authorityAndInformationCeilings,
  compatibilityEvolutionRetirementRefs,
  contractRevision
}
```

### Contract 种类

- semantic/public operation/result；
- durable schema；
- capability port；
- external protocol；
- policy；
- verification/assurance；
- support；
- migration/compatibility。

它们通过 typed refs 组合，不合并为巨型 DTO。

### 验证：契约、策略、权限、验证与支持语义

- contract identity 与文件路径分离；
- policy deny 优先；
- grant 过期；
- declaration 与 execution result 分离；
- unknown contract version fail closed；
- support 环境与验证环境错配；
- 一个内部 DTO 无独立 consumer 时不升级为 Contract。

## 设计蓝图的对象角色与非完成推断

一次专业软件工程的规范叙述至少涉及四组不同的主体：**作者事实**（谁要求什么、定义什么）、**派生判断**（关系、约束、实现选择、布局）、**未来作用对象**（待生成工程、待执行操作）、**实际证据**（生成、构建、运行及外部读回）。对象可以在同一个界面呈现，却不能混成同一个可写结构或一项泛化 `done`。

本系统设计阶段的终点是“所请求的目标设计义务已被满足”的**局部结论**，不是创建新的公开枚举。可以呈现 `Draft / AcceptedDesign / TargetPlanComplete / ImplementationReady` 这四种投影标签，但必须逐个读取准确源、Decision、TargetProgramPlan、Need 和相交实现供给；其共同含义及限制如下：

| 呈现 | 必备事实 | 不得推出 |
|---|---|---|
| Draft | 可回源的候选与来源/未决 | 作者已采纳、需求满足 |
| AcceptedDesign | 有权接受的真实作者修订及依赖基础 | 目标布局必然完整 |
| TargetPlanComplete | 针对明确产品根、目标画像与设计观察义务，存在闭合的派生布局、接口、环境/构建/维护规划；阻断性缺项为零 | 已生成代码、可运行或部署 |
| ImplementationReady | 本次要求实现的每个功能都有已确定算法或合格外部实现供给、目标能力/依赖资格、接口/错误/资源/变更处理，且交接输入可复查 | 具体生成器已存在、真实编译或产品验证通过 |

尚有阻断性未知时仍可以保存 `AcceptedDesign` 和已完成部分；所有已规划文件合在一起也不能让未知算法从无变有。展示层不能自己签发这些标签，必须给出来自原 owner 的当前 basis、coverage 和不满足的义务。断言应按请求的范围而非整个人类软件宇宙取得；已有项目只被 Gift 观察一小部分时，未观察范围不可反推为不存在。

需要区别两种等价目标：**精化**要求目标在已声明环境假设下不出现规范禁止的可观察行为；**双向行为等价**还要求相互匹配的观察与可允许行为/进展。文件名相同、单次测试通过与存在一套可接受行为都不能自动推出双向等价。语言/进程/环境不同导致的时间、调度、随机、路径和标识差异，只有在所采用观察合同明确允许隐藏或抽象时才能忽略。此处只定义比较角色，精确 Claim、适用证据和现实资格仍归 Assurance。

<a id="gift95-cross-contract-9"></a>
## 有限格式合法与完整Result不得合并

机器结构校验应返回 `STRUCTURALLY_VALID`及其实际范围；语义资格还要求BoundRule、主体、Method/Target/Toolchain及其适用域。目标缺失返回`NEEDS`而非`VIOLATED`；结构非法返回拒绝诊断而非`UNSUPPORTED`；编译方法选择耗尽预算返回`RESOURCE_LIMIT`而非`NO_SOLUTION`；真实外部作用未知返回`UNKNOWN_EFFECT`，不能被取消请求等同于“已撤销”。

这些名称作为当前判定概念，正式wire须与既有Result/Diagnostic判别联合准确对齐；不是在公开接口上自行增加一套未经协商的`success`字段。每个工具结果至少能指出object/revision、有效覆盖、未决义务、允许下一步和该阶段可提供的证据。
