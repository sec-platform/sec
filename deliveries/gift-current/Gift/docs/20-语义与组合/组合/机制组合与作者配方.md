# 机制组合与作者配方

<a id="gift-unit-author-composition-recipes"></a>
## 单一展开规则

本页定义可复用 author Profile/recipe 的**参数绑定、展开、来源与退出**合同；类型、状态、算法和实际 Method 资格仍由被引用的语义 Owner 决定。配方是有版本的作者库贡献，不额外持有业务真源、默认配置层或行业产品身份；机器发现遵循[意图描述](../作者语义/意图描述与作者投影.md)，修改遵循既有 AuthorDelta/Control/Requirement。

每份 recipe 须显式声明角色、类型/单位、适用域、默认来源、展开算法、产生的 Definition/Requirement、所需 Meaning/Method、可观察错误、兼容迁移及相交 Claim 模板。必需参数缺失返回对应 Needs；文本标签不授予补政策或替代有权选择的资格。只冻结本任务实际消费的配方、Method 与依赖，不能使全部库成为项目默认负担。

所有输出必须能够回到普通源/Requirement/Profile/Control；关闭或卸载配方 UI 后作者源仍完整。业务状态可以由真实 Provider/目标运行时拥有；配方描述符本身不拥有秘密、权限、动态健康、产品数据库或第二份意图事实。Provider/Target替换需要保持原义务，而非无条件承诺任意替换等价。一个库可以发布多个配方，不必每行对应独立包、SemanticModule或服务。

**语义消费校核：** **配方只是候选组合：** 某个配方当前实例化的成本较低，不表示开放Provider候选已穷尽，更不表示配方声明自动授予工具执行和外部数据传送权限。需要改变作者Requirement时回到有权的需求采纳；未能取得合格Provider则保留明确Needs与已有可用部分。 实现或验证此用例时分别消费[开放候选域下的局部最优、不可实现与停止证书](../../30-实现解析/实现选择/实现解析与候选资格.md#gift-partial-optimality)、[委派能力收窄、重定向与执行时再检查](../../50-执行运行与观测/权限与资源/授权与执行准入.md#gift-delegation-attenuation)的权威交接，当前机制只拥有本地行为含义。

## 身份、数据与接口

<a id="recipe-identity-tenancy"></a>
### Identity & Tenancy：身份、分区与隔离

作者声明主体角色、自然键/外部键、命名域、唯一性范围、共享对象与隔离对象、租户/组织关系、容量与披露边界。业务租户不是 Gift Runtime session，也不从登录名推断实际组织归属。

展开为普通 Subject/Type/Definition、身份/引用/分区 Requirement 和明确映射关系。天然共享的词汇/只读公开资产可以复用；数据、缓存、索引、密钥、连接池、日志、备份、恢复和计费分别带实际隔离范围。数据库/schema/进程/密钥分区是候选 Method，不固定全局 TenantManager。认证由所选产品 Provider 提供。

同串外部 ID 在两个发行方或租户中不能合并。负例是主表带 tenant 条件而排名缓存、唯一键或导出漏带；局部授权检查不证明全路径隔离。租户迁移/合并必须处理引用、密钥、历史证据和未结算操作，不能靠改一个 tenant 字段取得他人的数据。

<a id="recipe-persistence"></a>
### Persistence：持久化、查询与演进

作者给出实体/字段的语义类型、唯一性与关系约束、可查询形状、索引语义、保留/删除、分区、持久性、可见性、一致性、恢复点与演进要求。金额和时间不被编码选项降格为无语义 number。

全部形成普通 Requirement 与数据/查询 Definition；[持久状态端口](../../50-执行运行与观测/持久化与恢复/持久状态与存储协议.md)用于 Gift 自身控制或经明确适配的需要，不直接成为用户表模型。SQL/NoSQL/对象存储/本地文件由 Binding/Target 选择；目标 schema、索引、事务、迁移和部署贡献进入完整 ArtifactSet/OperationPlan。短内存计算无需耐久存储。

可串行化事务也不能替作者发明唯一性或跨系统原子性；Saga 不能满足要求不可见中间状态的原子合同。新增索引不能改变权限过滤或查询重数。部分迁移、未知提交、备份过期、被引用内容回收按原存储/RetryBasis处理；源中的新保留政策生效不等于旧数据已删除。

<a id="recipe-service-integration"></a>
### Service/API & Integration：接口与外部通道

作者声明 endpoint/角色、请求/响应/流/会话的类型与错误、编码和版本、认证/同意、送达要求、时限、幂等范围、签名/密钥用途、回执和后继状态。业务 API 与 Gift 六工具是不同协议和权限域。

生成协议/会话/Effect/兼容 Requirement、类型化调用和产物入口。HTTP、RPC、消息、邮件或设备通道由实际 Provider/Target 绑定；外部 endpoint 的当前响应是观察，不因存入来源就成为本地业务真值。普通纯序列化不走 Operation，真实发送/订阅/写入才准入。

受理不等于送达，送达不等于业务接受。重放签名、重复 webhook、伪造回调、重定向/解析变化、过期同意与日志泄密都要保留真实边界。重试沿原效果身份、目标去重/终局无效果/受保护收敛；外部不支持读回时保留未知，不将 HTTP 200、超时或 UI 提示当结算。

## 消息、流程、调度与副本

<a id="recipe-messaging"></a>
### Messaging：命令、事实事件、信号与通知

作者区分要求未来动作的 command、已发生事实的 event、允许丢弃/合并的 signal 或状态 notification，及需要耐久投递的消息。声明产生者、消费方、身份/批界、顺序域、投递/去重、保留、重放、死信与背压。

形成有类型 State/Stream/Effect/顺序和交付 Requirement，broker 只是 Provider。事件身份、提交 revision、批内 occurrence 与传输分片沿现有观察/日志合同；合并仅在消费语义允许时进行。可重建状态索引不用强制持久保存每次 dirty；不能重建的业务事件需要相应日志义务。

相同载荷的两次独立扣减不能去重；同一多对象提交的分片不能按 revision 提前丢弃后续项。消费者收到消息、应用成功、检查点耐久和外部效果已结算分别记录；重扫状态 A 无法恢复 A→B→A 中必须保存的 B 事件。

<a id="recipe-workflow"></a>
### Durable Workflow：跨故障流程与等待

作者给出 activity、timer、外部 wait、人工任务、截止/升级、流程状态、补偿关系、版本和责任移交。普通短流程优先原函数、状态或 async；只有要求跨重启/长等待恢复时才绑定耐久工作流供给。

配方将这些内容展开为普通定义、状态/时间/效果/恢复 Requirement；可选语义方法仅承担真正需共同解释的流程区别。Workflow history 是产品流程事实，Gift Operation 是获准外部作用，两者通过准确身份关系接合而非同一表。Provider 必须说明重放、activity重复、timer时钟、恢复和版本条件。

纯决策重放不能重新寄信/扣款。补偿是独立 Effect，不能抹掉历史；人工拒绝、超时、尚无人处理、已被撤销和执行未知不同。新流程版本可接新实例，旧实例按固定解释继续或显式迁移；删除图节点不能丢失旧等待/在途activity和责任。

<a id="recipe-scheduling"></a>
### Scheduling & Jobs：业务触发与执行资源

作者定义日历/事件/依赖触发、时区与 gap/fold 政策、错过触发处理、允许并发、去重、截止、优先级、公平性、费用和 SLA。产品定时任务状态与 Gift 内部 query 线程/队列是不同 owner。

生成时间/状态/Effect和配额要求，具体 host timer、队列或workflow由实现选择。业务允许运行不等于 Gift 资源已预留；当前时钟/队列/权限由 Execution读取。业务触发身份应含真正区分出现的规则版本和时间域，不能只用显示时间字符串。

夏令时重叠、时钟回拨、重启补跑与旧尝试迟到不得引发重复业务作用。调度取消只撤后续准入，已在途活动仍结算；硬时限必须具备真实可控停止/资源合同，不能把“标记超时”当释放容量。

<a id="recipe-sync"></a>
### Sync / Local-first：副本、离线权限与业务不变量

这是对Persistence、Messaging、Product Security等配方的可选组合，不要求新增同步内核或私有意图状态。作者声明副本/发行域、共同对象与成员身份、实际写者、可离线操作范围、合并/冲突政策、业务不变量、记录保留、删除/墓碑、离线委派的期限与用途，及重新加入和旧副本退役要求。presence、可重建投影、业务历史和不可重发命令不能因为都需同步而使用同一个事件语义。

展开为既有身份、状态、关系、复制/消息、权限、存储与恢复Requirement；CRDT、中心协调、分区预分配权利或保留冲突是候选Method，均须满足原业务合同。两个离线副本各自在本地不超容量，不证明合并后满足全局容量；没有合格的权利分配/协调时保留拒绝或冲突，不承诺“自动合且始终不超卖”。Gift作者协作与生成产品副本仍属不同subject，不能共享可写头或把客户端登录当产品同步权。

断线续接固定流代/基线和准确检查点；保留窗口外重建、已删除对象的迟到修改、撤销后离线提交、长期旧副本和部分数据可见均按原观察/迁移/当前准入处理。新同步规则不静默重解释旧历史，无法取得必要旧记录时说明受影响对象/用途；无关本地草稿和已合格独立结果保留。删除墓碑前必须满足实际旧写者不再恢复的条件，不能仅按墙钟年龄判断安全。

## 产品交互与呈现

<a id="recipe-ui"></a>
### UI Interaction：生成产品的交互

作者选择页面/视图、路由、表单、动作、输入/焦点、验证和状态绑定；这是生成产品本身，不是 Gift Workbench 的 UI。界面可独立有原生作者源，不能强迫所有目标框架改写一张万能 ViewTree。

有新公共交互区别时消费[可选产品交互语义](../可选语义/产品交互与呈现语义.md)；否则使用库/目标组件。Target 负责真实路由、组件、渲染、平台事件与资产；源所有权、局部用户改动和错误位置保留。

界面按钮可见不授予服务器权限；表单验证完成不等于提交已接受或已生效。焦点、输入法组合、异步验证旧响应、断线重发和关闭页面在交互语义与 Operation 对接时分别处理。

<a id="recipe-access-localization"></a>
### Accessibility & Localization：可访问与地区呈现

作者表达语义角色/标签、名称、键盘/焦点顺序、替代输入、反馈、可读性、locale资源、格式、历法、单位、双向排版与回退策略。仅相交需求展开，纯无界面算法不被强制填 UI 表。

作为 Interaction/内容/Publication 的 Requirement，目标 adapter 保持实际辅助技术、平台键盘和呈现合同。文本缺项的回退必须有明确范围；locale不是法域、授权、货币或单位选择的隐式来源。[时间/Locale](../基础语义/扩展语义与适配合同.md)仍拥有其本体语义。

标签存在不证明可访问性合格，自动检查不能替实际焦点路径与平台行为。RTL、换语言后光标/数字解析、缺字体、语义树与可见图不一致各有相交反例；原始数值/单位不随翻译发生隐藏转换。

## 安全、记录与业务规则

<a id="recipe-product-security"></a>
### Product Security & Privacy：产品用户与数据用途

作者定义产品 principal、credential/session、role/policy、资源/动作域、委派、撤销、同意、purpose、数据分类、保留/共享/删除和主体请求。产品权限与 HostExecutionAuthority 是两个明确 subject/domain。

生成产品安全/隐私 Requirement 和策略定义，使用成熟认证/密钥 Provider。Host Grant 只许可 Gift 的真实动作，不传给产品用户；产品管理员也不能因此读 Gift 宿主秘密。跨域委派需真实发行方、对象、用途和受众映射，策略模板不能自签权限。

隔离必须覆盖数据库、索引/排名、遥测、缓存、导出、备份和恢复。离线委派只能给有界有效能力，不能承诺失联即时撤销。删除确认不能超出实际受控副本范围，不可更改审计与合法删除冲突须由真实政策 owner裁决；不能用 immutable标签掩盖未处理要求。

<a id="recipe-audit"></a>
### Audit & Records：历史、归属、对账与更正

作者指定应记录的业务对象/事件/行动者、发生与观察时间、来源、不可变或可更正规则、保留、访问、脱敏、签署和对账。业务审计不同于调试日志，也不同于自动证明事实真实性。

组合普通记录类型、provenance、存储与 Effect/Evidence 引用；事件事实、对事实的断言、签名和证明资格保持各自 owner。允许更正时记录原条目及明确后继关系，不原地改写历史；有条件删除时保护必要责任材料。

日志漏记、迟到、重复、时钟不同步、签署仅覆盖部分内容和外部无法读回必须显式显示。得到完整日志页不证明从未漏报外部事件；追加去重保护按真实原子边界，不用客户端先查后写制造不可重复保证。

<a id="recipe-policy"></a>
### Policy / Pricing / Eligibility：规则与采用

作者声明条件、适用对象、有效期、版本、优先级/冲突、例外、批准和输出；计价只是可能的业务结果，不是 Gift Kernel 的行业函数。硬规则与偏好仍分开。

展开为 Rule/Condition/Requirement/Profile 与 Decision 的有类型关系；业务规则求值不等于 Gift 为它选实现，运行时变更域与编译时选择分开。币种、精度、税费/折扣规则由对应作者/领域库明确提供，系统不从locale推政策。

重放必须绑定原规则和数据基础，不能用 today/latest重算历史账单冒充原事实。例外需要真实批准依据，平台权限不等于业务批准；两项相同值不同来源不应去掉一项责任与撤回路径。

<a id="recipe-ledger-allocation-fulfillment"></a>
### Ledger / Allocation / Fulfillment：非成品业务的组合见证

账本以账户/entry/单位/posting/余额关系及对账为作者定义；预占以稀缺资源、hold/expiry/priority/fairness/matching/commit/release为定义；履约以路径/资源可用性/承诺/里程碑/异常/readback为定义。三者可组合但不能互相冒充。

复用数量、关系、规则、事务、幂等、时间、工作流、优化和外部回执；会计/公平/履约策略始终作者或领域库拥有。提供的是虚构通用资源的配方和符合性样本，不携带现成支付/电商/物流成品、不注册行业 Kernel enum，也不承诺“需要组合”能在法律或技术上阻止任何第三方商用。

测试双预占不超容量、过期释放不释放新hold、借贷平衡不等于外部转账已结算、规划有路径不等于已交付。未知效果沿原身份协调；补偿、部分履约和规则改版保留各自历史，不能用数据库成功覆盖这些业务不变量。

## 检索、学习与领域计算

<a id="recipe-search-analytics"></a>
### Search & Analytics：检索、聚合与时效

作者声明 corpus、查询意义、索引、召回/排序/过滤、时间窗口、聚合重数、freshness、ACL、重建、统计/不确定性与资源预算。查询、近似检索、排名和因果判断不是同一种结果。

逻辑查询/流/索引 Requirement 进入现有语义和实现选择；数据库、搜索引擎、向量或分析仓库为候选 Provider。源观察、索引检查点和应用进度沿原恢复合同，产品 Telemetry 只提供其实际测量范围。

权限过滤须覆盖候选召回、排序统计、计数与缓存；事后隐藏行可能仍泄露排名。重建中不拼不同切面分页，读集变化即使值相等仍更新。样本选择、迟到/重复事件和缺失数据影响结论，不能用 query success 推“全量/新鲜/因果”。

<a id="recipe-ml-experiment"></a>
### ML & Experiment：模型与推断依据

作者声明数据集/特征、模型修订、训练/推理/评估/监测，或总体、估计目标、分配/干预、测量和因果假设。两类可以连接但“模型预测准确”不等于“可识别因果效应”。

分别消费[学习语义](../可选语义/数据模型与学习语义.md)与[实验因果语义](../可选语义/实验设计与因果语义.md)；框架/设备/统计方法通过 Provider/Method。训练成本、外部数据取得和部署更新走真实作用；普通模型文件的静态分析可纯计算。

数据泄漏、训练/评估分布差异、特征版本错配、不可识别与环境假设不能被一个质量分数抹掉。模块有设计不等于已装配或通过目标/设备资格；随机重放范围、模型更新与效果回滚仍独立。

<a id="recipe-domain-models"></a>
### Simulation / Geometry / Media / Device：领域库的明确接缝

几何声明 CRS/单位/拓扑；媒体声明 codec/timebase/质量/同步/latency；仿真声明状态/时间/求解器/场景/seed/观察/终止；设备声明测量/校准/命令/安全/停止/围栏/读回。每一组有自己不同的可观察语义。

领域模块/作者库提供 facet、类型和 Method；Core 只保持已有类型、数量、状态、流、资源和作用关系。Tensor/AD/数值精度按现有模块选择，成熟引擎/求解器/编解码器/设备实现作为真实供给，不统统塞入标准运行时。

坐标系同单位不等于可互换；请求时间不等于实际成功时间；数值残差不等于现实模型误差；模型回滚不撤销物理作用；解码/格式成功不证明媒体质量或授权。保留完整同包[领域研究](../../../research/domains/README.md)和实际相交前提。

## 观测、组合与演进

<a id="recipe-telemetry-safety"></a>
### Telemetry / SLO / Safety：测量、服务目标与危害防护

作者定义产品 event/metric/trace、基数、采样/丢失、用途、隐私、保留、SLO 的时间窗/分母/错误预算；若涉及危害，再声明 hazard/scenario/control/安全状态/独立性/残余风险和批准。

产品 instrumentation进入Target贡献；Gift自身编译/运行日志保持平台事实。SLO是产品要求，不自动成为安全证明；[危害防护语义](../可选语义/危害防护与安全论证语义.md)从实际风险和共同原因派生独立义务。

采样丢失不能解释为零故障，错误预算允许短时违例也不许可安全禁区。服务健康与控制器联合稳定分开；进入安全状态需要有资源/时序/执行器反馈的过程，不靠Safe标签。任何未知仍按原Evidence及责任移交合同表达。

### 组合、更新与取得证据

组合时先保留各配方实际贡献身份、主体代换和来源，联合检查相同主体/资源/接口上的硬要求；不能先分别选好 Provider 再假定接口名字相同就可连接。来源相同的菱形传播与两次独立实例化区别仍由稀疏控制 owner处理。代码生成、运行适配和查询下推只能消费已合格的 Binding。

配方升级分表现变化、模板变化、作者源重新展开、持久产品数据迁移和运行实例切换。不能按最新版重解释已接受源或重写全部历史；保存差异、产物更新和现实迁移分别准入。安全撤销可以停止危险方法的新使用，但恢复材料和未结算责任不能随包卸载丢失。

[意图覆盖与纵向符合性](../../60-保证与证据/验收/意图覆盖与纵向符合性.md)为这些配方提供有明确正例/强反例/目标差异的代表样本。模板自动生成向量是测试材料，不是独立 Oracle；已合格证明/证据可复用，不为每次编辑重跑所有领域。这里不以16个名字、64个坐标或“零 Kernel 行业分支”的书面声明代签实际能力。

## 多个独立权威的联合合同

跨组织实例声明参与者、对象拥有者、付费者、风险承担者、政策来源、可披露信息、时间/身份转换及协议接受关系。一个组织授予读权不代表另一组织授予写权；多数投票不能默认覆盖不参加该投票的资源拥有者。联合任务的必要Grant按真实动作逐方取得，不设虚构全局管理员。

语义映射要保持单位、对象身份、状态时间和错误/最终性区别。A能解释B、B能解释C不自动保证A到C的映射可无损传递；组合需要检查侧条件和信息损失。政策冲突保留各自不可放松硬界与来源，只有有权主体可接受替代/降级；全局优化不能为某方获益违反另一方明确风险限制。

退出/撤销后停止新动作和披露，同时按事先接受的结算/保留/恢复协议处理已发生效果和共享状态。外部权威不可达时保持Unknown和局部可独立结果，不编造同意。联合发布、支付或设备动作若不可原子，显式部分完成与补偿责任；各方自己的PASS不直接合成联合承诺。

**验证与反例**：单方授权冒充全体、映射非传递、成本转嫁、联合任务撤回、外部权威不可达、局部优化破全局硬界。

**实际能力边界**：真实各方协议、权限、政策及责任输入未取得；本次无跨组织操作。

## 业务能力和系统意图的可实施组合闭包

一等 `intent:goal` 描述一个目标；它并不强制业务必须有分层目录。一个可复用业务能力对外只暴露自己承诺的输入/输出、资格前提、错误、进展、时间、状态/资源责任、观察与权限义务；内部可以来自现成组件、若干目标、规则引擎或原创方法。能力作为已采纳 `Definition` 导出稳定身份，`CapabilityUse` 存 DefinitionRef、参数/角色绑定与此次新增约束，不复制被引用定义的完整正文。

完整系统 Root 消费这些能力并补与交付有关的独立内容：用户通道与交互、系统外部协议、数据保留/迁移、依赖、平台/安装、权限/秘密、日志/诊断、可恢复性、性能/SLO、保证与演进。哪些属于作者明确要求，哪些可委派给已锁定 Profile，必须逐项保留来源。作者没有要求 web UI 时不生成 UI；要求持续订阅/通知时只交付单次执行的命令行程序不算完成。

系统拆分由公开接口与故障域决定，不按业务对象数量强制微服务：一个 SQLite 本地应用、一个进程中的纯规则服务、多个跨组织 Provider 都可能是合格实现；原子域、数据归属、进程边界、外部权限和故障恢复必须各自有依据。组合的输出是实现根及其依赖、能力覆盖、未履行义务、目标投影和对用户的可解释差额，不是预先写定的一组 `services/*` 模板。

一个业务 Definition 被修改：若仅更换保持所有公开合同的 Method，可保留上层意图而重新计算资格与目标；若公开 Meaning/前置/结果/异常改变，则所有相交能力、系统 Root、界面、代码、证据和运行兼容性按实际读集失效。并行版本可合法共存，运行中的旧订单/事件按其绑定修订解释，不能在后台用新定义倒改历史效力。

**完整系统的四个不同状态**：描述已闭合（无歧义的接受需求）；实现已闭合（Method/Target/构建依赖能覆盖根）；运行已结算（真实授权、状态/外部效果、读回与恢复可用）；保证已确认（准确 Claim 和独立证据在覆盖范围内成立）。任何一个不蕴含后面的状态。

### 产品配方首先组合业务意义与合格供给

跨产品配方不是通用 AST 语句模板。作者提供业务目标、共同主体、独特边界和权威；派生图把有实证语义等价/蕴含关系的能力需求接到 Rule、Query、Workflow、Optimization、UI 和 Native Method。两个各自成功的配方若共享资源、费用、时间、身份或主体权利，必须全局资格验证；自动展开不得继承不属于公共机制的行业规定。

只有在没有现成合格供给且获得实现委派时，才安排新算法/原生胶水；新计算体的存在不改变作者意图的唯一来源。已生成配方必须保留组件身份与第二次编辑的依赖图，拒绝跨用户受管源码覆盖。
