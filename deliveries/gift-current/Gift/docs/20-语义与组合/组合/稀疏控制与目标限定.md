# 稀疏控制与目标限定

## 最小必要信息：真实 owner 与稀疏差异

工具先读取已接受行为及真实上下文，计算可推导结果，再使用已委派的实现策略。作者只补三类当前无法合法省略的信息：真正独特的行为、不可推导的硬要求、主动固定或改变的选择。

每项控制逻辑上包含对象与作用域、精确控制定义/版本、适用Target、强制或偏好属性、显式值及作者决定来源；编辑界面可按有效上下文派生字段，不要求逐项手填。省略控制只表示采用对应Definition/Profile已接受的默认或继承，不等于`false`、空值、无界资源或额外权限。当前有效值与其来源、失效条件及所选实现均须可追踪。

控制合成不是 LastWriterWins，也不以作用域最窄者覆盖全部上层约束。每项 `DecisionContribution` 必须保留 producer、authority、scope 的传播及 Target 限定、`require/prefer` 强度、默认/推导依据，按[正交合成合同](#decision-contribution-algebra)联合求值。已接受的硬要求、公开合同以及安全/合法性约束同时成立；子级不能覆盖父级硬要求。软默认只补全其 Definition 许可的未决维度；数值相同的不同来源仍分别追踪撤销、审计与失效。

`reset`只移除当前对象拥有的覆盖，使有效值重新由当时的父级要求、默认和锁计算；不删除上级硬约束。预览必须显示新值、来源及受影响绑定，采纳后才改变真源。显式固定即使恰好等于默认，也可能表示“不随未来默认变化”，只有证实不存在该冻结意图时才能省略。

### 不同控制的事实归属

| 控制对象 | 典型内容 | 保持责任 |
|---|---|---|
| 计算与业务含义 | 算法、数值、身份、错误及事务结果 | 作者定义与语义，不由后端优化改写 |
| 实现选择 | 库、索引、求解和生成方法 | 编译与供给owner，满足完整前置、结果、失败及资源合同 |
| 目标表示与互操作 | ABI、公开名、布局、文件和初始化 | 目标规则及真实外部消费者，不按关键字近似 |
| 资源与调度政策 | 内存、并行、限流、公平性 | 请求与资源owner，检查共享额度、进展及取消 |
| 运行调节 | 批量、缓存及在线控制器 | 实例与执行owner，固定政策、真实观察、接管和结算 |
| 系统解释与治理 | 描述符含义、方法资格、权限及根接口 | 有权演进和恢复，候选不能批准自己的合法性 |

表中是现有责任的视图，不是六个新服务，也不是一种通用持久记录。操作授权、自动化预算、遥测与运行轨迹不写进`gift.control-file/1`；普通程序体仍在作者源。取消用户等待、阻止新任务、请求停止、确认终止、撤销未提交改动及补偿既有效果也不能合并为一个布尔值。

<a id="mixed-explicit-and-delegated-control"></a>
### 显式控制与自动选择的共同空间

控制粒度由本次对象和要求决定，不设置全工程的“手动／自动”二选一模式。作者可以固定一个使用点的方法与参数，同时仅约束另一处的资源上限，把其余合格选择委派给系统；也可以直接提供自定义算法、类型或原生实现，而不被限制在预置候选菜单中。普通定义足够时走原语言与库接口，真正缺少可观察区别时才按[扩展判据](语义扩展-执行许可与解释激活.md#extension-distinction-witness)扩展语义。

精确绑定、允许集合、禁止项与资源上下界均由相应类型化值及require表达；软偏好只在共同硬条件成立的集合中解释，不新增一组会与require/prefer/reset竞争的通用强度枚举。不同目标不能擅自改变共同源语义；某使用点的定制也不能直接修改共享实例而隐瞒其他消费者。无法分离时，预览说明共同影响、允许的专门化或冲突，而不是给出实际上未局部生效的成功。

“全部自动”只表示在已接受目的、硬条件和有效委派内补足未指定决定，不表示无限搜索、无限费用、自动安装、不受约束的目标修改或永久写权。自动选择的范围、探索成本和需要再采纳的变化由原政策／操作合同承担；作者控制表不保存实时Grant、观测流或当前线程数。用户能够从解释结果追到实际候选、排除条件和依据，并以新约束或显式绑定重新求解；不要求先阅读所有控制项。

某个细节尚无公共开关时，系统仍应提供其真实owner、影响与受权的扩展／源码修改路径，不能把“没有配置项”说成没有控制能力。反之，不影响已接受观察、约束或外部合同的局部实现细节可保持封装；把每个局部变量公开为稳定API会扩大兼容和组合义务，并不增加有用自由。

## 控制描述符与实际使用过程

控制描述符包括qualifiedId与版本、subjectKinds、typedValue、量纲/单位、scope、phase、语义强度、合法值与缺省、继承/合并/冲突规则、能力前提、目标映射、影响的行为/ABI/资源/排版，及应用后的检查、证据与失效消费者。`typedValue`只验证值的结构和值域，不把全部工程控制降成类型系统。源行为、实现选择、目标形式与当前权限不是一个可任意键值写入的字典；同一值在不同阶段、主体或强度下也不能仅因JSON相等就合并。已有正式描述符或被明确拥有的原生配置才能成为有效控制；未知名字保全并报告，不按拼写猜测。

<a id="effective-control-projection"></a>
### 有效控制投影：请求、有效、计划、施加与观察

REQ014要求作者既能保持自动委派，也能在需要时看到完整的决定链。客户端按需把现有事实投影成以下五个切面；它们不是五份配置、更不是新的状态机：

| 切面 | 回答的问题 | 不可混同 |
|---|---|---|
| 请求 Requested | 作者、独立要求或上层政策明确要求/禁止/偏好了什么 | 没写不等于false，也不等于宿主默认 |
| 有效 Effective | 经过作用域、继承、合取、禁止、默认和冲突检查后，当前真正成立的约束是什么 | 有效要求不等于已经找到实现 |
| 计划 Planned | 当前冻结候选准备采用哪个Supply/方法/目标/配置去履行这些要求 | 候选计划不等于已经写入、安装或运行 |
| 施加 Applied | 哪些决定已经实际进入生成源码、原生配置、构建输入、制品或运行环境 | 文件里出现一个键不证明Provider实际消费 |
| 观察 Observed | 编译、读取、运行或独立证据实际观察到什么 | 观察到结果不反向修改原请求或自动证明全部要求 |

Effective 投影须说明每一显示值的来源、作用范围和资格：显式控制、上层有效硬要求、严格推导、合格 Method 选择、Target/ABI 限制或有 Owner 的默认值。分类由原贡献推导，不要求作者复制保存。`Auto`只委派已证明合法域内的**实现选择自由**；它既非 Meaning 未知，也不授权解析器发明行为。Effective 结果仍缺硬依赖时返回 Needs/Unknown，不得把宿主环境的偶然默认写成稳定产品语义。

普通视图只显示任务相交的差异和少量理由；高级视图可以展开全部相交描述符、来源、被排除候选、当前Binding、原生配置位置、目标后置和Evidence。两种视图消费同一作者源、Binding与观察，不建立一份“effective config”可独立写回的竞争真源。作者要改变结果时修改真正拥有该决定的Requirement、Control或原生配置；派生投影只提供定位和受权编辑入口。

<a id="decision-contribution-algebra"></a>
### DecisionContribution：正交事实，不再维护“来源类型优先级”

Effective值可以同时由多个事实共同成立，但**贡献不是一条`sourceKind`枚举**。内部解释投影为每个贡献保留正交坐标：精确`producerRef`及revision、该生产者的B轴authority/owner、其A轴decision semantics（若适用）、所在setting scope与传播前驱、可选target限定、owner定义的require/prefer等mode、严格推导`derivationRef`、Profile展开`expansionRef`、原生表示ref及适用/有效性依据。字段只在相交时存在；这仍是派生解释，不要求所有owner持久化同一通用记录。

过去容易混成一列的名称按下表归位：

| 表面说法 | 唯一表达位置 | 为什么不再作为贡献类别 |
|---|---|---|
| Explicit | `producerRef`直接指真实作者Requirement/Control/Meaning等 | “显式”是生产方式，不是与Requirement竞争的新语义 |
| Profile | Profile use通过`expansionRef`展开为真实Definition/Requirement贡献 | Profile是bundle provenance；展开后按真实语义参与求值 |
| Inherited | `settingScope`＋`propagatedFromRef`记录沿获准scope图的传播 | 继承是传播路径，不是authority或新的值来源 |
| Derived | `derivationRef`指可复核推导及其输入 | 推导是关系；输入改变就失效，不能当可写配置 |
| Target-required | `producerRef`指目标/ABI等真实Requirement或capability合同，authority按真实owner | target是限定与生产者，不是一种覆盖优先级 |
| Default(owner) | `producerRef`指有revision/scope的descriptor/Definition默认规则 | 默认是版本化规则，只在其合同允许的未定空间生效 |
| External | B轴External authority＋实际producer/applicability | External描述authority，不描述merge优先级 |
| Native-representation | `sourceRepresentation`/native owner定位 | 表示载体不是decision semantics |
| Runtime | A轴Runtime Input＋Runtime/Execution authority及runtime scope | 运行输入有自己的scope图，不与作者scope按同名覆盖 |
| Client | A轴Presentation Preference＋Client authority及client scope | 客户端偏好不能混入工程Control |
| Selected Binding | `planned.bindingRef`及Explain/provenance | Binding是求解结果，不是输入贡献 |

求值因此没有全局“来源优先级”或last-write-wins：先解析Profile等复用结构并保留provenance，再按各自scope合同传播；全部hard Requirement/require约束共同成立才有合法集合，冲突就保留生产者并返回Conflict；descriptor自己的merge/default规则只处理其被授权维度；Prefer只在合法集合内比较；严格Derived结果只读；最后才形成Effective及后续Plan。两个贡献值相同也不能丢掉其中一个，因为它们可以有不同撤销、失效、权限与审计关系。

<a id="contribution-propagation-identity"></a>
#### 图上的传播去重、重复使用与环

同一个贡献沿两条传播路径抵达同一消费点，与两个作者分别作出同值决定，不是一件事。内部求值以**实际声明/展开使用点、准确revision与代换、接收scope/ModuleUse及target**辨别贡献出现；这些坐标是已有关系的投影，不增加作者必须维护的贡献ID表。相同值的不同producer仍全部保留。

默认的可达性传播对同一贡献只应用一次merge；菱形路径合流保留多条provenance，但不凭路径数增加偏好权重、预算或硬条件的次数。同一个Profile被两个真实use分别实例化、带不同参数或重复数量时，分别保留其出现，不能因同ProfileRef或同值去重。一个资源上限被两条路径继承仍是同一个上限；两个真实任务的资源需求也不能因数值相同合成一份。

先使用descriptor允许的scope边建立有限工作表；普通import、文件夹包含或UI树边不自动成为继承边。记录实际范围/成员/否定依赖，按贡献出现及接收上下文去重，再消费descriptor的合并规则。顺序敏感规则必须给出有语义的稳定次序；调度、注册顺序和哈希表迭代不能充当优先级。不同路径确实改变单位、参数或作用范围时，descriptor必须定义该路径变换及其输出身份，不能直接按可达性去重；也不为了保留来源而枚举无限多条完整路径。

遇到传播环，只有owner已定义相应单调固定点、有限收敛或其他合格求解合同才求值。缺省与派生互相依赖、非幂等累加或不断产生新出现时，不用“迭代到不变”冒充已定义语义；返回准确冲突/循环/预算未完成并保留不相交结果。删除一条路径后仍有合法路径支持的贡献保留；最后支持路径或producer删除后撤除贡献并重算，不能从旧Effective值反向恢复声明。

反例：Project的一个Prefer分别经两个根到同一受允许的共享消费点，不得因加载第二根使该Prefer权重翻倍；两个独立Prefer则仍是两项原意。两条相反hard约束不能靠对相同值去重或局部覆盖化解；多根私有场景的Effective值分别求，确实共享实例时才联合检查它们。

<a id="developer-control-ux"></a>
### 开发者控制操作：Auto、Require、Prefer、Pin、Forbid、Reset 的唯一含义

Workbench/CLI可以使用更符合开发习惯的动词，但持久记录的 mode 只有 `require / prefer`；reset 删除记录，普通作者/原生编辑仍走对应 owner。各客户端必须按下表降低，不能产生第二套priority或override规则：

| UX动作 | 持久/真实语义 | 禁止的错误实现 |
|---|---|---|
| **Auto / Delegate** | 删除本层对该维度的显式覆盖，或根本不创建记录；重新消费当前有效Requirement、默认和解析器自由 | 写`auto=true`压过父级要求；把Unknown当Auto；每次build重新随机选 |
| **Require** | 写当前subject/scope的硬Control或真实Requirement | 用本地require撤销父级hard requirement；把Preference升级成Requirement而不显示 |
| **Prefer** | 写软偏好，只比较已满足全部硬条件的候选 | 用score补偿硬冲突；没有候选资格仍“偏好成功” |
| **Pin** | 对支持精确引用的descriptor写精确`require`，例如ProviderRef/AlgorithmRef/target/toolchain revision | 发明新的`mode=pin`；直接改Binding lock而不改作者要求 |
| **Forbid** | 仅当descriptor定义Bool/allowed-set/denied-set等可判定语义时，降低为相应`require` | 建全局字符串黑名单；用“不显示候选”代替实际约束 |
| **Reset** | 删除当前layer自己的记录并按同一base重求Effective | 写`null/default`；删除父级Requirement或机器lock；撤回已经发生的Effect |
| **Choose Profile** | 增加对版本化Definition/Requirement bundle的use/引用；实现Control保持独立稀疏记录 | Profile成为不可展开魔法标签；在Profile里暗藏Provider/target Pin；与显式Require冲突时后写获胜 |
| **Edit native** | 走该native owner的精确源码/配置编辑 | 把任意原生键复制进`gift.control-file/1`；忽略未知字段/脚本/注释 |

客户端显示`Pinned`只是“当前存在一个精确硬绑定要求”的视觉状态；`Auto`只是“本层没有固定实现选择且解析器拥有相交自由”的视觉状态。二者都可由当前事实重新计算，不作为独立author data。

#### A轴Decision与允许动作矩阵

六个控制动作只属于Requirement/Realization Control的相交编辑，不是整个All Decisions的统一按钮栏：

| A轴decision semantics | 默认作者动作 | 六控制动作中可能合法的子集 | 说明 |
|---|---|---|---|
| **Meaning** | Edit Meaning、Use/Replace Profile、Go to native owner | 通常无；只有Meaning内部明确暴露为Requirement/Control的维度才转到对应行 | 改业务规则、类型、状态或公开行为不是Pin实现 |
| **Requirement** | Add/Edit/Remove Requirement、Use/Replace Profile | Require、Prefer、Reset；Forbid只在Requirement本身有明确否定/allowed-set语义时 | Auto表示本层不再额外要求，不等于放宽上层hard；Pin通常不是产品性质动作 |
| **Realization Control** | Edit precise Control | Auto、Require、Prefer、Pin、Forbid、Reset，具体可用项由descriptor声明 | 这是六动作的主要适用域；Pin/Forbid都只是有合同的降低 |
| **Runtime Input** | Provide / Replace / Clear local runtime value，或Bind Provider/SecretRef | 不直接使用六控制动作；若要把稳定运行政策固定为Requirement/Control，显式提升到对应A轴类 | 清掉本次输入不删除产品默认/Requirement |
| **Presentation Preference** | Set / Reset client preference | 不使用工程Control六动作 | 只影响client authority；团队共享presentation artifact仍不是Engineering Control |

External authority拥有的Requirement即使A轴分类是Requirement，也可以全部只读；`allowedActions`必须同时满足decision semantics、B轴authority、当前Grant和descriptor能力。A轴分类不自动意味着用户可编辑。

`Choose Profile`、`Edit Meaning`、`Provide Runtime Value`和`Set Client Preference`是owner-specific编辑动作，不加入“六控制动作”计数。

<a id="decision-setting-scope-semantics"></a>
### 三套作用域图不能混为一棵覆盖树

**作者/编译作用域**通常沿`Project → ProductRoot → Module → Definition → Use/Occurrence`逐渐收窄，`target`作为正交限定；只有descriptor声明允许的scope可以出现。所有hard requirements合取，局部层不能放宽父级hard；软default/preference按descriptor merge rule确定。

**运行作用域**沿`Deployment → Instance/Session → Operation/Attempt`，保存的是现实运行策略/输入/Grant相关决定；它不从Definition occurrence继承一个同名JSON键。**客户端作用域**沿`User → Workspace → Window/View`，只影响显示和开发偏好。跨三张图发生联系必须经过明确Binding，例如Project requirement限制Deployment region；不能靠“同名字段更近”自动覆盖。

### 当前持久控制编码的scope边界

当前作者/编译Control的唯一持久编码是`gift.control-file/1`：它用带tag的`scopeRef`精确表示`project / product-root / module / definition / occurrence`五种作者scope节点，覆盖D轴作者/编译图；`target`仍是正交限定，不变成scope层级。Runtime/Session/Operation输入继续由execution/runtime owner承担，客户端偏好继续由Client owner承担；ControlFile 因此闭合**作者Control**而不扩成UniversalConfig。历史`gift.controls/1`只表达module/definition/occurrence，是只读迁移输入，不能拿它的缺项推导Project/Product没有控制语义。

ControlFile 原生覆盖 Project 与有 target/rootId 的 ProductRoot；不能再用`moduleId="*"`、虚构definition、特殊target字符串或路径前缀模拟这两个scope。未来只有出现**现有五种作者scope之外**的新scope种类或持久语义时，才发布可迁移的新revision或明确向后兼容扩展，并同步更新descriptor适用性、合并、锁、读取器和旧客户端拒绝规则。

这不限制统一UX：All Decisions可以同时显示来自不同scope/owner的行；统一的是解释和编辑入口，不是强迫它们共用一个JSON数组。

### 控制描述符的最小专业合同

新descriptor只有同时定义以下内容才允许出现在开发设置面：

1. stable qualified identity与revision；
2. semantic definition：它究竟改变哪个可观察区别，而不只是UI名称；
3. applicable subject kinds、allowed scopes、optional target qualifier；
4. value schema、单位/量纲、canonical comparison与normalization；
5. strength support：是否允许require/prefer，是否存在可定义的negative/allowed-set；
6. inheritance/merge/conflict/reset规则；
7. activation phase：author/resolve/lower/build/deploy/run/instance/operation中的实际阶段；
8. consumers与actuation：哪个resolver/backend/config adapter/runtime真正消费；
9. support/qualification：哪些target/provider支持，缺能力时返回什么；
10. verification/observation：如何证明它已经Applied/Observed；
11. invalidation/impact：改变后哪些Binding/artifact/evidence/runtime失效；
12. migration/recovery：旧值、在途工作和不可逆点怎样处理。

只有`typedValue`、默认值和一个后端if分支不算完整descriptor。反过来，某个生态专有设置只在原生配置里有稳定owner且没有跨目标公共价值时，不必为了进入“All Decisions”强造descriptor；adapter可以按其真实A轴语义投影，并标注native `sourceRepresentation`与authoritative owner；不创造`Native-owned` decision class。

<a id="control-actuation-contract"></a>
### 描述、施加与观察分别闭合

描述符由所属定义包维护，沿既有锁解析；通用内核只识别类型化接口，不理解所有未来参数的业务意义。已列描述符信息还须能解析出以下相交合同。能从现有方法、目标画像和资源定义得到的应引用，不强迫复制字段；ControlFile 只负责作者/编译Control的声明位置和值，不吸收运行、客户端或外部authority事实。

| 合同面 | 必须可判断的信息 | 实际消费者与失败 |
|---|---|---|
| 值与范围 | 单位、精度、合法集合、适用主体、目标及范围是固定集合还是持续查询 | 语义解释器校验；同为数字不代表同单位，未知范围不按全部对象执行 |
| 生效阶段 | 设计选择、构建、会话启动、实例切换或运行调节；原子组与前置依赖 | 原编译／执行owner安排生效；保存新值不代表旧实例已经切换 |
| 执行能力 | 具体方法能观测、软调节、硬限制还是完全不支持；实际限制覆盖到哪一层 | 适配器给真实能力，assurance核要求；监测到超限不证明事前阻止超限 |
| 观察合同 | 观察方法、时间域、采样窗口、误差／缺测、覆盖对象及读权限 | 结果按其测量定义评价；平均值不能代替峰值，不可观测状态不能被猜成满足 |
| 耦合与失效 | 共享实例、资源、初始化、效果、顺序、负依赖及证据消费者 | 选择器处理真实共同条件，增量owner维护读集；不能分别选完后才发现共同不可行 |
| 变更与恢复 | 可重配置条件、在途工作、临时覆盖前像、旧读者、不可逆点 | 原迁移／恢复owner结算；撤销配置不推导历史作用被撤销 |

控制的完成链是“已表达—已解释—已选择—实际施加—取得观察—按要求裁决”，不是六个可以互相代替的布尔值。纯源码形态控制可在编译产物上观察，不要求启动运行控制器；运行预算若只能软调节，应保留可接受的软界及风险，或返回当前硬保证缺少执行能力。用户有权放宽要求时产生明确的新要求，不能在实现中暗自降级。

**观测不足也是控制边界。** 两个真实状态在所准许的观察中不可区分，却分别需要相反动作时，自动方法不能保证同时正确。应取得有权的新观察、选择对两者都安全的动作，或保留相交未知；不能靠提高采样频率假装补齐根本不存在的信息。强实时、保密和概率要求按各自观察与量词另检，不由返回值相等代签。

控制的解释预览同时展示作者要求、继承来源、解析后的有效约束、待采用绑定，及已有实际观察；不把“计划采用”标成“已生效”。UI、文本、CLI和AI消费同一候选与诊断，专用编辑器仅是投影。没有专用组件时保留类型化通用编辑或原文，不删未知内容；不可披露的候选和诊断按原读取权限裁剪，解释不能泄露他人私有数据。

### 请求：一次只改变明确对象的指定属性

下面使用已有propose.draft设计变体。c1、路径和java在此是范本中已存在的候选、定义及目标键，真实使用必须来自当前项目；这些调用未作为产品执行。

```text
gift.propose({
  draft: {
    kind: "control-change",
    base: "c1",
    subject: "src/select.gift::Item",
    target: "java",
    require: {
      "java.declaration.form": "class",
      "target.public-name": "SelectedItem"
    }
  }
})
```

原定位分支字段恰为kind、base、subject、可选target，及require/prefer/reset中的一个。已协商下文`gift.control-scope-edit/1`时，允许以`scopeRef`**替代**subject；二者恰选一个，不能都给、都省或合并范围。require/prefer是非空、按解码键无重复的控制名到值映射；reset是非空、无重复项的控制名数组。所有项在一个候选中共同改变，不部分发布。source/files、edits、editRef与draft继续按公共协议互斥。

`target`在这里是当前工程`targets`中的逻辑键，或临时上下文已绑定的同类目标键；不是磁盘目录、语言字符串的任意猜测或物理写入地址。目标相关描述符必须给出这个键，不能因当前只有一个目标就暗设为全部目标。与目标无关的描述符按其scope省略target；禁止无意义地给一个源行为属性附加目标，从而让不同后端解释同一源为不同需求。

subject先在base中解析为一个实际模块、声明或受支持区域，再绑定稳定身份。查询结果可以直接提供可用定位。后续重试不按当前路径重新寻找同名声明，也不因手工知道私有ID而绕过来源的访问范围。只有目标容器要求时，Item仍具有其原来的值语义；生成class不是声明可变对象身份。

<a id="control-scope-edit-protocol"></a>
#### 项目与输出根沿同一编辑入口

`gift.control-scope-edit/1`是`gift.ai-tools/2`内`propose.draft`的有限能力协商，不是第七个工具，消费当前 ControlFile 的 scope 与逻辑键。它复用下文唯一的`AuthorControlScopeRef`，让project/product-root及其余三种已有scope都可直接编辑；普通subject短定位继续有效，不要求每次先query。协议能力声明、descriptor适用性、读取器、writer和真正后端消费分别核对，服务只支持 ControlFile 读取不等于实现此请求分支。

```text
gift.propose({draft: {
  kind: "control-change", base: "c1", scopeRef: {kind: "project"},
  require: {"dependency.allow-third-party": false}
}})

gift.propose({draft: {
  kind: "control-change", base: "c1",
  scopeRef: {kind: "product-root", rootId: "desktop-a"},
  target: "java", reset: ["target.public-name"]
}})
```

这些请求假定 c1 中已存在模块、java Target 及 desktop-a 根发生点；真实请求必须先由实际基础取得这些身份。project隐含的是**base中唯一已绑定的控制存储工程**，不是会话当前工作目录。base含多个工程而上下文不能唯一确定writer时返回范围歧义，不能改父工程或所有工程；先使用已有明确工程上下文/基础或准确源编辑。product-root按 target/rootId 定位后由[根选择器](../../10-作者与输入/作者源/工程源/工程清单模块与绑定锁协议.md#output-root-selector-binding)取得BoundRoot；其余scope读取本工程稳定对象映射。跨项目/私有scope、任意ID、无目标支持或缺覆盖分别返回原拒绝/缺项，不因此获得更大写权。

处理仍走CTL0—CTL6：在base内固定scope、目标和descriptor，私有候选里按原本地键添加/替换或reset，再沿实际依赖重求DEC。root选择变化、默认/控制规则变化和跨对象约束在同一候选内检查；保存时沿原前像协议，不修改现有Grant、Binding锁或父级hard要求。删除已不存在的孤立控制只需准确本地记录及合法修改权，reset不必先让被删除对象可生成；它不能据此恢复对象或把失配记录重定向到同名新对象。此路径仍须能唯一定位并无损删除该记录；不理解整个控制文件时保全原载体并使用有能力的局部编辑，不能先丢弃未知内容再声称重置成功。

能力未知/未支持的旧客户端保留原subject分支，或用支持完整当前存储语义的files/edits修改准确控制文件并走同一校验；不能忽略scopeRef、改成`moduleId:"*"`或把project降为一个碰巧存在的模块。对只有旧字段解码器的服务不发送新形态。两种请求可能产生同一个逻辑差异，但不承诺短draft在响应/缓存丢失后保持原候选ID。需严格重放时，仅当完整变更分支已支持该实际变更种类、事前changeId及所需保留窗口，才使用其身份协议；缺该适配时准确报告此保证不支持，不能借不相交的semantic-change声明能力。真实保存的幂等仍归apply。

### 唯一持久编码：`gift.control-file/1`

独立实现/生成 Control 只写入由同一 `gift.project/1.sourceScopes` 发现的严格 JSON `gift.control-file/1`。Project 没有内联控制槽，也没有 `files[]`、`defaultFileId` 或第二份根注册表。没有独立 Control 就不必创建控制文件；源码函数体、实参、Meaning、require/ensure、产品 Requirement、原生配置仍由原 owner 保存。Runtime input、Grant、Client preference、External authority、Binding、Evidence 不进入 ControlFile。

**文件与发现。** 每个文件含 `schema`、当前 `projectId`、项目内唯一的 `fileId` 和 `records`。Project 以 `kind:"design"` 的 SourceScope（或已明确有资格的 Control SourceProfile）包含它，Reader 仅读取获准且冻结的成员，不能旁路扫描全磁盘。`fileId` 是载体身份，路径只是当前定位；移动文件保持 fileId，重新发现后更新 locator。新条目有唯一已授权写入文件时直接使用；否则由编辑者选择合法目的文件，不按文件排序猜位置。跨文件重复 fileId、遗漏已选择成员或路径逃逸均阻断相交读取/保存。

```text
AuthorControlScopeRef =
  { kind: "project" }
  | { kind: "product-root", rootId }
  | { kind: "module", moduleId }
  | { kind: "definition", moduleId, definitionId }
  | { kind: "occurrence", moduleId, definitionId, occurrenceId }
```

**根发生点与目标。** product-root 必须同时给记录的 `target`，以 `(projectInstance,target,rootId)` 在同一 SourceSnapshot 的 `targets[target].outputRoots` 中找到唯一选择发生点，再按[根选择器](../../10-作者与输入/作者源/工程源/工程清单模块与绑定锁协议.md#output-root-selector-binding)解析该发生点的完整导出集合。Control消费该完整BoundRoot集合，并核Descriptor所允许的subjectKinds、集合基数及传播合同；不能先筛掉不合适成员再宣称控制可用，也不因scope名为product-root就把普通库根或合格聚合根排除。需要单符号的target.public-name不得隐式广播给多个导出；作者可选择明确export并分配独立rootId，或使用真正支持集合的描述符。contextBindings的恰一product:system限制只约束角色实例化，不扩展为所有Control的基数规则。rootId 属于目标内根发生点的独立身份域，词法为 `[A-Za-z_][A-Za-z0-9_-]*`，最多128个字符；不是 Definition ID、导出名、路径或运行实例。Target 仍是正交限定，不成为全局 scope 层级；这里只因 rootId 的身份域局限于 Target 而必填。描述符不得把 product-root 声明为允许 scope 却禁止其 target 限定。

```text
冻结 Project/sourceScopes ──发现──> ControlFile(projectId,fileId,records)
                                  │ 按 scopeRef/target/controlRef 建唯一键
冻结 targets[target].outputRoots  │
  ├─ rootId=desktop-a ──选择 App──> BoundRoot A ← Control(target,desktop-a)
  └─ rootId=desktop-b ──选择 App──> BoundRoot B ← Control(target,desktop-b)
                                  │ 分别沿实际 Scope/ModuleUse 传播
                                  └─ 合取硬条件 → 合格候选 → prefer/Plan
```

同一个 Target 可用 `desktop-a`、`desktop-b` 两个 rootId 选择同一 `{moduleId,export}`，各自 Control 只沿该根的 BoundRoot/ModuleUse 传播；同值参数也不合并两个发生点。共享 Module 的 module 控制则对该 Module 的适用消费共同生效。Descriptor 限定 scope、主体种类与基数；一个省略 export 的集合根不能把单符号 `target.public-name` 自动施加到全部成员。空集合、多成员不满足单符号前提时返回适用性/基数诊断，不猜唯一导出。

```json
{
  "schema": "gift.control-file/1",
  "projectId": "project:selection",
  "fileId": "author-controls",
  "records": [
    {"scopeRef":{"kind":"project"},"controlRef":"dependency.allow-third-party","mode":"require","value":false},
    {"scopeRef":{"kind":"product-root","rootId":"desktop-a"},"target":"java","controlRef":"target.public-name","mode":"require","value":"SelectedItem"},
    {"scopeRef":{"kind":"definition","moduleId":"mSelection","definitionId":"dItem"},"target":"java","controlRef":"java.declaration.form","mode":"require","value":"class"}
  ]
}
```

这是字段示意，前提是同一项目确有相应 Target、rootId、Definition 与已绑定 Descriptor；名称存在不证明 Java Target 或消费者已经实现。

| 字段 | 当前确切合同 | 读取与保存责任 |
|---|---|---|
| `schema` | 必需，`gift.control-file/1` | 精确格式分派；不支持者拒绝相交消费 |
| `projectId` | 必需，等于所属 Project 的逻辑身份 | 必须再绑定实际 projectInstance，不能凭同名跨工程写入 |
| `fileId` | 必需，项目内唯一的载体身份 | 定位真实来源与前像；不参与控制优先级 |
| `records` | 必需数组，允许为空 | 空数组表示该文件当前不贡献 Control，不创建默认贡献 |
| `scopeRef` | 必需，上述五种 tagged union 之一 | 父身份完整；不得用通配符、路径或数组序号冒充 |
| `target` | 通常可选；product-root 必需，其余按 Descriptor | 绑定本工程逻辑目标键，不是 apply 物理 targetRef；不存在的目标保留 Needs |
| `controlRef` | 必需 Descriptor qualifiedId | 在发生位置的锁/上下文解析准确 revision，不把名称当内容摘要 |
| `mode` | 必需 `require` 或 `prefer` | require 加入硬条件；prefer 只在全部 hard 合法集合内比较 |
| `value` | 必需，按 Descriptor typedValue 解码 | 类型、单位、精度、范围及真实引用均检查；字符串不执行，缺席不写 null |

**唯一逻辑键。** 全项目的键为 `(scopeRef,target?,controlRef)`，其中 product-root 展开即 `(kind:"product-root",rootId,target,controlRef)`。fileId、路径、records 下标和 mode 不参与身份。不同文件同键也拒绝，即使同值；mode 改变是同键内容变化，数组顺序不是优先级。普通规范化可按 scope kind、域内身份、target、controlRef 确定排序，但不得改写不相关字节。独立的真实业务硬要求由各自 Requirement owner 保存，不能借重复 Control 制造两个独立生产者。

**读取、编辑与 reset。** SourceOwner 同时固定 Project、SourceScopes、所有相交 ControlFile、描述符及根绑定，取得同一 SourceSnapshot 和正/负读集。拒绝重复 JSON 键、错误项目/fileId、未知受控字段、非法 tag、越权路径、错误类型或未知可执行值；未知 Descriptor、缺解释器/Target/消费者分别保留 Needs/Unsupported，不能静默转成 Auto。硬 require 与产品/外部硬条件合取，再比较 prefer；默认仅填其 Owner 允许的未决空间。保存只改变作者声明，不表示已经 Applied/Observed。

reset 是带准确前像删除本层逻辑键的编辑动作，不持久化 `mode:reset` 或 `value:null`，不删除上层硬要求、锁或已发生 Effect。最后一条被删除时，**保留同一个合法文件及 `records:[]`**，按同一文件 CAS 保存；不隐式删除文件、不要求更改 SourceScopes。空文件仍占用其 fileId，后续 set 可写回它。是否仍有 Effective 值须重新求值，不能承诺恢复“系统默认”。无记录的 reset 可为 no-op，但仍核所指工程、准确键与合法编辑权。孤立控制允许被无损删除，不要求先恢复其已不存在的根或取得生成资格。

跨文件移动记录以同一有权源提交同时移除旧键、写入新文件，并校验双方前像和共同读集；不支持共同提交/恢复时只返回候选，不出现两处生效或伪造原子成功。JSON Pointer/Patch 只定位冻结前像中的字节；数组下标不是跨修订身份，Merge Patch 的 null 也不是这里的 reset。

#### 历史控制的迁移前提与拒绝

`gift.controls/1`、内联 `gift.controls/2`、`gift.control-files/1` 登记及旧 `gift.project/2` 只作为具名历史 Reader 的输入，不作为当前 Writer 或可并行生效的来源。迁移须固定全部旧成员、项目/Scope 图、Descriptor revision、Root 选择及源前像，并有目标 ControlFile 与 Project 编辑权：v1 的 module/definition/occurrence 按完整父身份映射；v1 不能合成 project/product-root，也不能用 `moduleId:"*"`、虚构 Definition 或特殊 target 补缺；原 target/controlRef/mode/typedValue、传播、接受来源和显式等值 Pin 保持。缺内容、未知字段/语义、无写权或不具备共同提交恢复时保全原件，拒绝自动采纳。

旧 product-root `{moduleId,export?}` 选择器必须在同一冻结 Target 的 outputRoots 中唯一匹配一个选择发生点才可取得 rootId；一根历史输入可按清单规则规范化为 `main`。多个根匹配同一选择器、target 不明、集合覆盖不等价或零匹配时返回 `NEEDS_CONTROL_ROOT_MIGRATION`，不得按数组首项、显示名或 Definition ID 猜根，更不得复制一条控制到所有匹配根。缺 Target 时仅在固定候选域能证明唯一目标与唯一根时补全；否则需明确决定。

迁移在同一前像和解释上下文核对全部适用消费点的控制集合及 Effective 结果双向等价；同键异值返回 `CONTROL_STORAGE_CONFLICT`，同键同值也须保留双来源并取得合并的明确采用决定，不能因值相等丢失来源/冻结意图。只有共同保存成功后才切换 Writer、撤除旧内联/登记入口；中断先读回提交身份与前后像，不盲目重放。旧 Reader 不支持新文件或新 rootId 语义时阻断相交生成，不忽略 Control 后宣称兼容。

### 临时覆盖、持续范围与返回基础

普通reset仍按上文删除本层记录。需要“临时覆盖后恢复先前选择”时，操作拥有者另外保留准确前像、覆盖产生的版本和期限：只有当前记录仍是该覆盖的后像，才可条件恢复；用户或另一个任务已续写时保留冲突，不能无条件写回旧值。过期只能使新使用失去该临时选择资格，不能假装已停止在途操作或撤回外部效果。

直接对象控制作用于本候选中准确绑定的稳定主体；outputRoots省略export时保留完整公开集合选择，product-root控制依Descriptor的主体、基数和传播规则消费该集合。后继基础须重取成员并重新判定；新增导出可能使单主体控制歧义或出现不适用成员，不能静默只保留旧成员、筛选同Kind或把单值控制广播成多份。其他要求未来新增对象也匹配的范围，应明确选择器的解释、成员变化、观察覆盖与授权范围；记录查询及其成员依赖，而不是把当前成员列表冒充未来完整范围。新增成员重新取得适用性和执行资格；旧授权不因选择器仍同名而扩大。删除再创建的同路径对象不是原实例。

跨对象和跨维度的批次在候选中共同预览、选择和检查，实际保存按原写入计划处理其原子能力。已接纳的共同约束不能被逐项reset或并行客户端更新绕开；没有共同事务的外部控制逐项报告生效与残余，不对整个批次签发虚假的原子成功。

### CTL0至CTL6：Control mutation 子协议，不是第二条Decision流水线

CTL0—CTL6只描述“一次Control编辑/生成请求怎样从定位到返回或保存”，嵌入[Developer Decision 的DEC0—DEC9统一求值](../作者语义/开发者决策模型与设定面.md#developer-decision-evaluation-lifecycle)，不与其竞争：CTL0/CTL1固定并定位DEC0—DEC3输入；CTL2产生新的Control候选，使相交Decision从DEC2重新求值；CTL3消费DEC2—DEC6得到新的Effective/Resolved结果；CTL4使用DEC6/DEC7计划进入相交生成/施加；CTL5取得DEC8/DEC9可观察结果或明确未检查范围，但不自行签发Assurance verdict；CTL6只负责候选返回、作者保存或目标写入的原操作边界，保存后形成新revision并从新的DEC0继续。没有Control变化的Decision完全可以只走DEC0—DEC9，不经过CTL子协议。

| 步骤 | 正常处理 | 相交失败和保持范围 |
|---|---|---|
| CTL0 固定 | 取得base、当前目的、源/控制/锁及读取范围 | 过期或串项目引用不换成latest；只设计/预览不写文件 |
| CTL1 定位 | 解析subject或已协商scopeRef、target与描述符，固定工程writer及实际对象/BoundRoot | 歧义、未知控制、无权限或不适用分别返回；reset可删除准确失配的本地记录，不借此重建或改绑对象 |
| CTL2 修改 | 在私有候选中形成唯一来源的稀疏差异 | reset只删本层；批次冲突不先应用半份 |
| CTL3 求有效值 | 合并仍有效的任务、公开合同、硬控制、软默认与推导 | 有冲突指明生产者与消费者，候选合法不表示原任务已满足 |
| CTL4 生成 | 固定合格实现/布局，产生代码及必要配置、资源 | 无合格后端则该根受阻；其他独立根按原任务条件返回 |
| CTL5 核结果 | 检查真实声明形态、公开名、表示及相交行为 | 只存字段或打印成功不能称履行控制；检查未做要准确标明 |
| CTL6 保存或结束 | 按请求返回候选/产物，或经现行save-source/write-output保存 | 保存源不写目标，写目标不接管源；旧操作仍依原可信意图结算 |

已知默认路径可以跳过无用选型，无需每次调用query。所有有效值均可通过现有contract/origin/impact局部取得；返回结果不强制携带全目录或内部证明图。

## class：先判断开发者要求的是哪种事

**仅需要容器。**开发者要求某个接口生成Java公共类、类名和构造入口，没有要求可变身份、继承或反射。控制声明外形、公开名、可见性和构造API；编译器从现有值语义生成私有最终字段与明确构造。隐藏表示的类型不能因选class就开放全部字段。

**需要对象行为。**开发者需要独立实例、共享可变状态、动态覆盖、父调用或运行反射。这不是布局开关。使用点需要下面的语义描述，才能完成作者能力和后端映射。当前基础函数/opaque不能冒称已实现它。

**保留既有原生类。**前端保留准确来源语义、语法与不支持区域。能够提升的部分进入中立模型；未知细节有字节/AST保全。要求同语言精确改写时按原语义处理，不用“中立层不观察”删除原有反射或初始化行为。

### 对象语义的有限核心设计

完整的当前对象机制由[对象构造与动态分派](../基础语义/对象与控制/对象构造与分派.md)拥有：实例身份、字段、初始化与this逸出、方法槽、覆盖合同、多接口与单实现父链、结构体和目标保持。这里不再维护第二份对象字段/构造算法。

任务只要求目标采用class容器时，继续使用本章目标结构控制；要求真实可变对象、身份和分派时，采用对象画像；已有原生类的反射或特有初始化按实际源语义保留。三个要求不互相代签。当前有限画像不包含全部语言的多继承、元类、动态修改和析构机制；需要时是具体语义扩展，不允许只用一个class控制字段假装支持。

### 目标能力的逐项对应

| 作者要求 | Java示例目标 | Go/Rust等没有同一class语法的目标 |
|---|---|---|
| 仅隐藏值表示 | 私有字段＋公共操作/工厂；类是目标容器 | 模块内表示＋公开操作，不必发明class |
| 独立实例状态 | 实例字段＋正确同步/生命周期 | 明确状态对象、句柄和接收者，保持别名与寿命 |
| 动态分派 | 虚方法/接口的真实分派 | 合格接口表/trait对象/显式派发；承诺的观察要同等成立 |
| 必须继承某个Java基类 | 真实extends、构造链和方法义务 | 目标专有硬要求；没有合法桥接则该目标不满足 |
| 必须反射为指定Java类 | 类型加载、可见名、成员和注解合同 | 不以一个同名记录冒充；保留Java实现边界或准确拒绝对应目标 |
| C兼容布局/字段偏移 | 合格ABI或外部桥接 | 实际布局和对齐合同，不由记录字段顺序猜测 |

Java、Python、Rust等的class/对象/布局不能按名称直接等同。Java类规范同时规定初始化、继承、覆盖与构造；Python类还有其数据模型和描述器机制；Rust的repr控制另有布局条件。目标没有同名关键词不意味着无法实现行为；没有相应保持关系也不能因为能拼出源码就称支持。

### 一条有限作者控制与产物轨迹

作者定义一个不透明的Range及make/includes。未规定外形时后端选满足公共合同的普通布局；指定Java class与稳定公开名后，生成对应类候选并验证构造/成员/私有字段。再要求它继承外部BaseRange时，工具取得BaseRange真实版本和构造/覆盖合同，重新检查；失败定位到新增要求而不是悄悄忽略extends。换成Go目标时，有合格后端的原纯Range行为可以生成；仅限定Java输出的形态要求不适用于Go产物。若接受任务本身仍要求Java继承/互操作，Go输出不能替代该任务，必须保留未满足项。不能悄悄给Go签发Java互操作保证。

此轨迹的控制合同和所选有限对象作者语法已有规范；读取器、目标实现和更广语言映射仍分别核验。它不要求Range使用者改写为class，也不以原生出口替代真正缺项；独立值路径可以继续。

## 首批控制描述符的精确角色

这是一组当前已设计的控制，不宣称完成所有目标能力。后续控制复用同一描述符协议；新增语义仍需实际规则，不因能存一个名称就视为支持。

| 控制名 | 值与适用对象 | 当前默认/前提 | 对应动作和失败 |
|---|---|---|---|
| java.declaration.form | class / interface / record；Java类型输出 | 未写时由语义与现有接口决定 | 选择合法声明形态并检查成员、继承与构造；record要求与行为不合时拒绝 |
| target.public-name | 非空Text；公开输出符号 | 现有公开名优先，新符号由稳定命名规则产生 | 按目标词法、命名空间、导出及反射要求检查，冲突不随机加后缀改公共API |
| java.superclass | 精确SymbolRef；对象类型或已合格类输出 | 未声明时不从名称推测父类 | 解析实际基类/构造/继承/覆盖要求，循环、final、不可访问或不满足时返回具体错误 |
| target.visibility | public / package / private；支持该可见性层级的声明 | 沿作者可见性与目标门面推导 | 只能在允许范围控制目标可见性，不通过设置public泄露中立私有表示 |
| implementation.provider | 精确ProviderRef；有可替换实现槽的定义/端口/输出 | 优先现有合格Binding，否则自动解析 | 校验接口、行为、版本、资产、许可与目标；未知实现不当已安装 |
| implementation.algorithm | 精确AlgorithmRef；具有声明等价/可选实现的计算 | 按定义或授权策略选择 | 作者固定算法时其可观察步骤和资源限制进入合同，不当纯偏好忽略 |
| dependency.allow-third-party | Bool；project/product-root/module scope，可按descriptor限定目标 | 沿项目接受策略；新纯函数默认不新增第三方依赖 | false排除新增第三方路线；已接受任务必需的现有依赖形成冲突，不暗删功能 |
| generation.structure-policy | preserve / canonical / reorganize；目标布局范围 | 有明确合格旧布局则preserve，新工程canonical | 按显式布局基础生成并检查保持；compareTo不改变布局，缺基础或硬冲突精确诊断 |

SymbolRef/ProviderRef/AlgorithmRef可以由已知导入或上下文短名在当前base中解析，内部转成精确内容及接口引用；普通作者不必手填哈希。每个控制在候选中明确require或prefer；不适用对象返回CONTROL_NOT_APPLICABLE，未知描述符返回CONTROL_UNKNOWN，硬要求冲突返回CONTROL_CONFLICT，已理解但目标没有实现返回CONTROL_UNSUPPORTED。名称是当前诊断设计，不是运行事实。

操作返回新候选及有效值、选中来源、相交差异和未决。普通默认结果可摘要，只有请求解释时展开选型轨迹；不得将所有描述符或候选集复制给模型。控制已接受而打印器没有履行时属于生成器缺陷，不允许把结构校验结果当成目标满足。

## 目标结构稳定的控制消费

在既有描述符机制中增加`generation.structure-policy`：值为`preserve/canonical/reorganize`，适用于模块、输出根或目标布局范围，解释阶段为布局，行为要求仍来自原源合同。默认由实际上下文确定：有已选合格布局基础则保留，没有历史的新工程采用当前规范布局。`require`固定指定政策，`prefer`只在硬要求内参与选择，`reset`只移除本层覆盖。

[完整算法与失败分支](../../40-目标与制品/目标/结构稳定与作者回源.md#跨次生成的结构稳定合同)由目标源码章拥有。本描述符不存第二份函数体；布局基础及相关映射进入Binding和生成键。基础缺失、公共约束冲突和后端不消费分别给准确诊断。公共名称、继承、ABI等已存在控制仍然是硬条件时，结构政策不得覆盖它们。

管脚、文本与JSON是不同操作/表示方式，不为每个方式复制控制描述符。结构端改同一控制记录，文本端有对应写法时也映射到同一记录；作者权保持一处。当前新描述符与结构编辑均是设计合同，未因出现表项就取得运行实现。

## 控制的装配版本与后端履行

控制描述符在本次EngineImage中固定。propose解析真实对象和值后形成作者控制变化；compiler根据描述符的目标、作用范围和硬/软含义进行选择；实际lower/emit方法消费有效控制；assurance检查所要求的产物性质。没有消费者的方法只能登记缺项，不能因为控制可以写入 ControlFile就宣称能力完成。

规则升级产生新解释和显式差异，不原地更改旧控制意义。reset只在它固定的基础上删除本层覆盖；同名新版控制不能借旧句柄生效。方法依赖包含实际消费的描述符版本，不将其他目标未使用的描述符加载成每个任务输入。公共精细控制的实现合同与存储均复用现有记录，不新增配置总线。

## 配方贡献的消费

[机制配方](机制组合与作者配方.md)只产生本页已有typed Profile/Control/Requirement贡献，不增加优先级源。facet默认、两次真实实例化、菱形传播及模板撤回沿本页实际贡献身份/作用域/目标/支持路径处理；编译期开关、产品运行开关与Gift当前资源/权限不因共用表单而合并。

## 控制约束对Requirement与目标Profile的精确消费

ControlFile 不保存“已由谁选中的Rope”这类派生事实。实现选择前，先取得**已接受的产品要求和全部适用硬控制**；硬条件合取与目标资格共同过滤候选。只有真实候选合格时才比较Prefer；未知成本不当成0。对于同一逻辑控制键 `(scopeRef,target?,controlRef)`，分片位置与JSON数组下标不参与身份/优先级。

控制Descriptor需要指明 `consumer`及其已绑定版本，否则控制数据是待解释作者声明而非可交付构建。某控制改变了实际可观察语义（例如公开撤销历史长度），应迁入Meaning/Requirement，而不能借 `example.editor.internal-history-reserve` 这种实现配置偷改用户功能。未知描述符与丢失分片不得静默变成Auto。

## 控制与目标供应交叉验证的确切顺序

控制来自作者已接受的 ControlFile 逻辑键，不来自目标描述文件声明的“默认成功”。具体消费点先验证 `controlRef` 与 Descriptor revision、有资格的 scopeRef/target、唯一键和强类型值；沿实际发生点的传播图聚合 hard 约束，将产品 Requirement、外部必要政策及 Target/Provider 硬事实合取；再验证每个候选真实带有消费能力。对 `example.typescript.module-format=require esm`，仅当 selected Target 在相同目标键 `ts` 上实际提供 `moduleMode=esm` 且声明/验证的消费者能力匹配，才允许进入候选计划。项目同时要求 `cjs` 与 `esm`、或目标不提供对应成员与消费者，结果分别是冲突、无合格候选或 Need，不能以一个实现偏好修复它们。

`Prefer` 只给所有硬条件已满足的合格候选排序，缺少可比较成本或 Method 证据不得发明数值评分。“省略”表示当前作用域无作者写入，不必填补成数万个显式 `Auto`；`Reset` 产生删除对应逻辑键的候选修改，随后重新求值从真实父 scope/默认导出有效值。所有贡献保存身份与读取基础，避免不同作者同值要求互相覆盖。未获得实际 Target lowerer 或外部执行证据时，只能返回 `PLAN_ONLY_NOT_APPLIED`。

有限 Control 求值也必须消费本次已锁定的准确 Descriptor，而不能在 Rule/Target Schema 内再硬编码一份“控制枚举”；历史样本目录不作为当前可用供给。历史分片与内联来源的迁移仅在同一有效控制语义下比较不同作者持久布局，项目级缓存不可改变继承/冲突结果。

上述每个示例在实际采用时仍须取得准确类型、作用域、target 限定、消费阶段、资格条件及真实 Provider/Target 关系；历史名字和本表数值不能代替版本绑定。例如 `example.storage.engine` 不能获得不存在的索引优化权、`example.typescript.module-format` 不改变数学数值语义、`example.editor.internal-history-reserve` 不构成作者要求的历史容量保证。

一个新的行业实现选项只有当真正影响某个目标消费者、其硬/软约束有可检查值域和消歧作用域，且 SourceProfile/Provider/Target 承认时才应发行相应版本化 Descriptor；即使用户有权决定，也不必把未经实现的维度提前塞成 ControlFile JSON 记录。这些有限示例只是局部设计见证，**未推出**“92 项意图均已有可执行消费”，也不以那三个被纠正的历史错误映射作为能力依据。

## 适用前提、限制与反例

以下只保留有限描述符的适用范围与失败见证；历史载体不提供当前写入合同。

### Control Descriptor 的可检查具体合同与有限求值见证

本规范的 ControlFile 唯一持久合同由上文定义。每个值的解释与实际消费沿[开发者决定到文件与执行的确定合同](开发者决定到文件与执行的确定合同.md)。该文固定描述符类型、适用范围、硬/软约束、消费者、实际应用与状态区别；当前 ControlFile 形状由[设计 Schema](../../../schema/controls/control-file-1.schema.json)表达，跨文件和实际消费资格仍归语义 owner。这些是接口设计，**不是已发布Control注册表**。未在绑定范围内取得有权描述符、合格Method或真正消费者时，不得从样例中借默认值。

具体消费保持三个不可绕过的要求：一是`require`先与全部同范围硬要求及适用外部条件合取，再考虑任何`prefer`；二是物理JSON顺序、文件位置和`scope`深度不提供新的覆盖优先级；三是已验证Control JSON只是Declared，绝不可自动签发Applied/Observed/Assurance。
