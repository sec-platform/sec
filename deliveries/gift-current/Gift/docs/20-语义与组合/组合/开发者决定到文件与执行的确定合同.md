# 开发者决定到文件、约束、实际消费者与证据的确定合同

> 状态：**作者控制设计合同，实际消费者资格仍须实现与核验**。本文建立在 [开发者决策模型与设定面](../作者语义/开发者决策模型与设定面.md)、[稀疏控制与目标限定](稀疏控制与目标限定.md)、[开发者意图控制与存储分配](../作者语义/开发者意图控制与存储分配.md)、[工程清单模块与绑定锁协议](../../10-作者与输入/作者源/工程源/工程清单模块与绑定锁协议.md)上。**继承这些文件的逻辑语义**，当前唯一控制载体为 `gift.control-file/1`，不新增全局配置中心、不将下文测试描述符当成正式发布的 Gift 控制目录。下文 `gift.control-descriptor-catalog/1` 给出有限描述符的机器形状与消费者义务；描述符绑定、Builder/Resolver/Target/Runtime 的真实能力须独立取得，不能把历史局部检查器或静态形状视为产品等价交付。

## 0. 最终技术选择：每种责任唯一物理主人

**当前非计算业务作者采用：** `gift.project/1`（工程清单）、`gift.author-module/2`（唯一候选新业务结构作者外壳；下方Gift94的`/1`实物仅历史样例）、`gift.requirement-structure`（已存在的要求与组合语言）、`gift.control-file/1`（唯一稀疏实现控制载体，由受控 SourceScope 发现）、原生 Rust/TS/SQL 等文件（其唯一作者区域）、原生 Target 配置、固定读上下文生成的解析锁/产物、Operation/Observation/Evidence 的分开结算。

**不采用：** 第二套全局 Gift 编程语言作为必经入口；统一 `intent.json` 接管所有事实；业务功能全塞入控制表；所有缺项自动填默认；`.gift` 与 JSON 对同一发生位置双写；让 Rust SDK 的任意代码执行自动成为有权作者事实；通过 UI 置灰代替拒绝不合格结果；把描述符注册/静态校验/样例 Resolver 当成已安装的 Target。

**需要实现的精确合同：** 描述符 catalog 的机器字段、严格控制类型校验、解释上下文的读集/身份、冻结贡献的处理、有限候选演示中的硬/软判定、提交与回读义务。它们必须由原有模块 owner 落地；不另设运行时与 IR。

## 1. 一句需求怎样路由到准确文件

自然语言请求先固定 `sourceSnapshot`、有权主体、目标对象发生位置、ProductRoot 与操作目的；随后把要求拆成实际不同的可观察含义，分别路由到 Requirement、Definition、Control、Native 或 Effect Owner。Control 仅保存属于实现选择的局部决定，不接管业务事实与运行结算。

| 作者意图与分界 | 具体写入操作 | 当前正式作者文件/非作者来源 | 成功前必须检查 |
|---|---|---|---|
| “支持撤销最近 256 次已提交编辑” | 在编辑器 `req:composite` 调用实际 `HistoryPolicy`，参数 `limit=256`；若已有唯一原生实现即在该 owner 的算法/公开合同做精确变更 | `design/editor.module.json` 或拥有真实行为的 `src/editor.ts`；不是控制项 `history-reserve` | 撤销失败语义、保存/重启承诺、容量限额与接口一致；设计未定义则 `NEED_MEANING` |
| “预分配至多 1024 项撤销缓存” | 有描述符时写 `example.editor.internal-history-reserve`、definition scope、`require` `1024`（示例为上界） | 受控 `gift/controls/editor.json` 的 `records[]`；仅表示实现资源限制 | 限定实际内存分配范围，绝不降低用户可撤销的 256 步 |
| “尽可能用 rope” | 模块范围的 `example.editor.data-structure` 记 `prefer:"rope"` | 同一稀疏控制表 | 只能在保证文本和撤销行为一致的候选中排序；无合格rope也可选合格替代 |
| “必须用 rope” | 同位置的 `require:"rope"`，取代本地 `prefer`，不同时持有两个记录 | 控制表中**同一逻辑键**仅一条 | 方法和目标不支持就阻断，不生成空模板 |
| “尽量离线，不依赖公共网络” | 明确区分：产品离线承诺→Requirement；第三方包政策→单独的实现控制；一次运行网络访问→Runtime Grant | `design/product.module.json`；`gift.control-file/1`；Runtime 外部授权三处有不同 owner | 不能仅设一个 `network=false` 就假装三者同时满足 |
| “错误必须返回 NotFound 而非 null” | 修改产品错误类型/函数合同、Rule 或 native 实现 | 当前作者 Definition / native 源 | `null`、缺席与错误保留区别，不是日志配置 |
| “使用 PostgreSQL，但部署不能泄露数据” | 引擎选择→精确 `storage.engine` 控制；安全→独立 Requirement 与部署政策；账户/密码→SecretRef/Grant | Control、Requirement、外部受权 Runtime | 有postgres候选并不等于已证明加密、持久性或访问隔离 |
| “本次运行最多使用 2 GB” | Operation 中提交额度请求，并取得环境准入；若为产品持续边界则另写 Requirement | 真实 Operation/Instance 输入，不写在编译 Control 中 | 额度请求≠已获真实额度；不可超当前 Grant |
| “构建最多 8 个并行任务” | 固定持续构建策略→control `example.build.parallelism` require 8；只影响这次调用则 Operation 参数 | Control / 一次工具调用 | 构建实际消费并记录有效设置，实际资源限制依运行环境 |
| “UI 使用深色主题” | 产品视觉设计→UI Definition/资产；Gift 编辑器外观→Client Setting | 产品作者源或本机开发者偏好 | 不因工作台主题变化改目标应用主题 |
| “发布并支付供应商” | 作者可请求 Deliver，实际需要有权 Operator Grant、幂等/结算与真实回读 | Operation/Attempt与外部支付事实 | 无授权直接拒绝；超时不写成执行失败或成功 |
| “测试明明没有通过，改成通过” | 没有对应作者写操作；可修改源/测试要求后重新评估 | Assurance Evidence 只读签发 | 不可篡改历史事实、不得静默换 Claim |

**歧义与拒绝**：同一请求若对应多个不等价的写入 Owner 或业务解释，返回带来源的候选和 Need，不暗选一个。高层 Profile 仅在定义闭合且有真实 Owner 时可展开；复合修改的各原子作用必须作为同一可审查候选列出。未声明 Control 表示本级没有额外限定，不表示 `false`、禁止或已授权。

## 2. 完整作者代码树——每个文件到底拥有什么

```text
studio/
├─ gift.project.json                     # 工程来源范围/根/Target 请求
├─ design/
│  ├─ policy.module.json                 # 复用的产品约束和默认参数
│  ├─ editor.module.json                 # 编辑器需求，HistoryPolicy的公开使用
│  ├─ extensions.module.json             # 插件能力及隔离要求
│  ├─ remote.module.json                 # 远端会话设计要求
│  └─ product.module.json                # 顶层复合、真正公开的产品根
├─ gift/controls/editor.json             # 有独立实现控制才创建
├─ src/editor.ts                          # 如果被采用，唯一的原生算法作者源
├─ package.json / tsconfig.json          # 本生态的真实作者/工具配置
├─ assets/                                # 保留本来就合理的资产表示
└─ gift.lock.json                         # 仅真实解析后生成；本范本故意不存在
```

上述树说明当前作者文件分工，不要求复制已移出的历史实验工程。候选供应样本只用于有限搜索输入，不是作者源、IR、MethodSpec 或已发行锁；运行调用、客户端偏好和观察分别由 Runtime、Client、Observation owner 保存，不能复制进入 ControlFile。历史内联输入只在完整迁移前提成立后转入当前外置载体。

工程清单中 `targets.ts.profileRef` 指向未发布的范例画像 `example.typescript.target-profile/1`。没有真实画像及绑定时，实际目标生成必须报告 `TARGET_PROFILE_UNRESOLVED`，不能因为样例中的 `outputRoots` 合法就宣称已具有 TypeScript Target。

## 3. 独立 ControlFile 的严格作者记录

控制文件由同一 Project 的 design SourceScope 发现，完整存储合同由[控制 Owner](稀疏控制与目标限定.md#control-storage-contract)唯一维护；以下为当前外置写法：

```json
{
  "schema": "gift.control-file/1",
  "projectId": "project:studio",
  "fileId": "editor-controls",
  "records": [
    {
      "scopeRef": {
        "kind": "project"
      },
      "controlRef": "example.dependency.external-allowed",
      "mode": "require",
      "value": false
    },
    {
      "scopeRef": {
        "kind": "module",
        "moduleId": "studio.editor"
      },
      "controlRef": "example.editor.data-structure",
      "mode": "prefer",
      "value": "rope"
    },
    {
      "scopeRef": {
        "kind": "definition",
        "moduleId": "studio.editor",
        "definitionId": "EditorSubsystem"
      },
      "controlRef": "example.editor.internal-history-reserve",
      "mode": "require",
      "value": 1024
    }
  ]
}
```

记录只能包含 `scopeRef`、可选 `target`、`controlRef`、`mode`、`value`。`mode` 只能是 `require|prefer`。不持久保存 `Auto`、`Pin`、`Forbid` 或 `Reset`。已持久化的逻辑键是按准确解析上下文的 `(scopeRef,target?,controlRef)`，不是数组序号或物理文件路径。相同键重复，即使同值也拒绝；全部被发现 ControlFile 间相同键也拒绝；旧内联源须迁移后才能切换当前 Writer，不能“后写覆盖”。

`scopeRef` 严格是五种带 tag 结构：`project`，`product-root(rootId)`，`module(moduleId)`，`definition(moduleId,definitionId)`，`occurrence(moduleId,definitionId,occurrenceId)`；不能用字符串通配符、隐式路径父级或无效 ID 模拟。Target 是正交限定，且必须在本项目 `targets` 中登记；不等于部署目标/写出路径。`product-root` 的 target 必填，以同一冻结 `(projectInstance,target,rootId)` 定位 BoundRoot；根选择器再解释 moduleId/export。两个 rootId 可选择同一 Definition 并分别控制，rootId 不是 Definition ID。

解析 JSON 必须拒绝重复对象键、非法 Unicode 代理项、非 JSON 数值、未知受控字段及不合约类型；非整数布尔不能充当整数；精度和单位必须由绑定的描述符决定。**精确整数、货币、非 IEEE754 可准确表示的数值**不能依赖不精确的通用浮点数字段；使用类型拥有者指定的字符串数值编解码。语义哈希基于**有版本的规范化**与领域编码，不能默认对任意大数使用通用 RFC 8785 JCS；哈希用途、原字节保全与解析语义哈希须分离。

## 4. 描述符规范：已选定的机器形状

建议由真正拥有实现限制的**库/Target/Provider** 提供 `gift.control-descriptor-catalog/1`，沿已有 Dependency/Binding Lock 精确绑定其版本。它不是项目作者的新“总配置真源”。**正式接入时每条描述符必须同时提供以下字段或有类型的精确引用**；本节示意不是已安装目录，也不依赖已移出的历史 Schema 文件：

```json
{
  "revision": "1",
  "decisionKind": "Realization Control",
  "meaning": "Preferred private document data structure, not product text semantics",
  "allowedScopes": ["module", "definition"],
  "targetQualifier": "forbidden",
  "valueDomain": {"kind":"enum","values":["rope","piece-table"]},
  "constraint": "equals",
  "modes": ["require","prefer"],
  "propagation": "author-scope-edges",
  "default": {"kind":"literal","value":"piece-table","sourceRef":"example.editor.profile-v1"},
  "phase": "resolve",
  "consumer": {"owner":"gift.editor-implementation-resolver","operation":"resolve-editor-storage"},
  "qualification": {"requires":[]},
  "verification": {"check":"inspect actual binding and observable semantics"},
  "invalidation": ["effective","plan","artifact","evidence"],
  "migration": {"policy":"re-resolve","rollback":"restore-source-preimage"}
}
```

这是 `example.editor.data-structure` **完整范例描述符**；只有在真实实现者提供具备相同接口能力的 consumer 与合格方法时才可以签发可用资格。所有范例名称保留 `example.*`，不冒充已发行核心配置。描述符的完整语义拥有者必须约束如下问题：

1. **`meaning`** 明确该实现自由度及不许改变的产品观察，不能只写 UI 标签。
2. **`allowedScopes`** 不是“越往下越自由”。只在真实候选路径中出现的 scope 才有资格贡献；`targetQualifier` 三种严格区别 forbidden/optional/required。
3. **`valueDomain`** 必须有布尔、限定整数（单位、上下界）、枚举、枚举集合、精确实现/Provider 引用等准确类型；本文有限值域示意只展开前四类。复杂引用需要绑定身份/版本/内容及合法编码，不接受裸字符串冒充准确 MethodRef。
4. **`constraint`** 不是代码直接执行的字符串，而是 `equals / upper-bound / allowed-set / denied-set` 这一有限测试子集；更复杂约束归实际语义 Type/Constraint Solver，必须登记语义和 witness，不允许新的 opaque predicate 不受限制执行。
5. **`modes`** 声明支持硬要求、软偏好或二者；`Pin` 降低为 `require`+精确引用；`Forbid` 仅在能构造有类型的 denied/allowed-set 时允许；否则前端显示“不支持此动作”。
6. **`propagation`** `none` 或沿已固定作者 scope 图的传播，具体图由已绑定的 `ModuleUse/BoundRoot/occurrence` 决定；重复使用按发生位置与来源去重，而不是物理目录父子关系。
7. **`default`** 必须有精确 owner/revision 与适用范围；`kind:none` 则保留 Auto 自由或 Need，不从机器环境偷偷导入默认。Default 的优先性永远低于硬要求和显式偏好。
8. **`phase/consumer/qualification`** 必须落到真实的 `resolve / lower / build / deploy / run` 消费者；没有 consumer 或实际 support 就 `UNSUPPORTED`，不能只通过模式校验宣布完成。
9. **`verification`** 指确切产物和真实观察方法；保存 JSON 仅证明声明存在，不证明后端已执行。
10. **`invalidation/migration`** 记录更改后哪些 Binding/目标/实例/保证失效，以及能否重解析、恢复旧源前像或必须与外部效果核对。

注意：正式产品还需与现有 Requirement、MethodSpec、TargetProfile、Provider ABI 的身份和资格机制合并；**不可由这个范例 catalog 创造一个独立注册中心**。

## 5. 六个控制动作的可编码裁决

| 作者动作 | 确切读写 | 约束与可观察结果 | 错误 |
|---|---|---|---|
| Auto/委派 | **不写**当前键，或删除该键后重算 | 保留上层 hard、Profile 约束与实际默认；不能写 `auto=true` | 本级无法撤销上层/外部要求 |
| Require | 本级 `mode=require` + descriptor 有类型值 | 候选必须落在合法集合；真实消费者支持后方可 Plan/Apply | `CONTROL_SCOPE_NOT_APPLICABLE`、`HARD_CONFLICT`、`NO_ELIGIBLE_SUPPLY` |
| Prefer | 本级 `mode=prefer` + 有类型值 | 合格候选内排序；硬约束未过不得选中 | 不支持 Prefer 则 `MODE_NOT_SUPPORTED` |
| Pin | 有类型精确引用的 `require` | 需要精确 Revision/Method/Provider 资格，不允许仅凭相同 displayName | `BINDING_UNRESOLVED` / `UNSUPPORTED` |
| Forbid | 降成允许集合/禁止集合的 `require` | 必须有有限可判定全集与明确否定语义 | 无否定合同则 `NEGATION_UNSUPPORTED` |
| Reset | 带旧源前像删除准确键并重算 | 不写 `value:null`、不清上层要求、不伪造已撤销外部效果 | `SOURCE_REVISION_MISMATCH` |

**局部覆盖规则：** 硬条件不是按 scope 深度覆盖，而是全部可适用硬贡献合取。软贡献在描述符给定的可比较域内按准确归属和范围求序，不能用最后一个 JSON 数组项获胜。只有所有硬条件通过后才计算偏好和成本；若多个候选不可比较，按定义的稳定消歧或返回 `AMBIGUOUS`，不能让任意 HashMap 遍历顺序决定输出。

## 6. 读—解释—计划算法（必须由原 owner 实现）

以下是真正的处理顺序，而不是“输入 JSON 然后 AI 决定”：

```
FIXED INPUT: sourceSnapshot, projectInstance, lockUse, sourceProfile,
             exact bound roots and module uses, purpose, authority/grants,
             environment/target facts and candidate supplies

0  Read/parse strict JSON and native authors. Any malformed file => reject its affected source.
1  Bind every source region to exactly one authority; reject duplicate writers.
2  Bind descriptorRef at its exact dependency occurrence/revision; missing => Need.
3  Type-check each control value and (scopeRef, target) applicability before planning.
4  Reject duplicate logical control keys across all selected ControlFiles.
5  Freeze bound scope graph and provenance; gather only reachable contributions.
6  Expand actually adopted Definitions/Profiles and join independent hard Requirements.
7  Intersect all relevant hard control constraints, external constraints and
   Target/ABI/Method qualifications; if contradictory => HARD_CONFLICT.
8  Apply only owned defaults in the remaining lawful freedom; do not materialize them.
9  Filter actual eligible supplies; empty => NO_ELIGIBLE_SUPPLY / NEEDS_SUPPORT.
10 Optimize preferences and costs ONLY over eligible supplies; deterministic
   identity/ordering and unchanged read set => reproducible selection.
11 Freeze Plan / Binding / artifact plan with exact inputs and invalidation read set.
12 If requested, only a duly authorized consumer lowers, builds, writes or runs.
13 Read actual outcome; produce Applied, Observed, Assurance as distinct states.
14 New edit => recheck old preimages; invalidate impacted consumers; commit only
   requested author changes atomically or return a candidate/Conflict.
```

有限候选枚举只能覆盖上述 3、4、5、7、9、10 在封闭值域中的条件；其输入供应若由样本人工给定，就没有证明 Method 发现、Requirement 求解、真实 Target 或并发写入。此类输出至多为 `PLAN_ONLY_NOT_APPLIED`，不能充当产品 `gift.preview` 的真实施加结果。生产算法仍须处理跨描述符耦合、负依赖、动态有效范围、时间/资源、不透明库资格及硬性外部权限。

## 7. 从声明到兑现的五种事实必须分别签发

| 阶段 | 正式输出 | 唯一签发者 | 缺证据时的可用状态 |
|---|---|---|---|
| Declared | 当前作者 Meaning/Requirement/Control/原生配置 | 实际源 owner | `MALFORMED_SOURCE`、`UNKNOWN_OWNER`、`DUPLICATE_WRITER` |
| Effective | 合取/传播/默认/源资格后的确定可行约束 | 语义检查与相关外部 authority | `HARD_CONFLICT`、`NEED_MEANING`、`EXTERNAL_FACT_UNKNOWN` |
| Planned | 精确 Method/Binding/目标制品和 read set | Resolver/Compiler | `NO_ELIGIBLE_SUPPLY`、`TARGET_PROFILE_UNRESOLVED`、`AMBIGUOUS_BINDING` |
| Applied | 实际目标配置/产物/运行消费者生效读回 | 对应 Target/Build/Runtime/Provider | `NOT_ATTEMPTED`、`PARTIAL_APPLIED`、`UNKNOWN_EFFECT` |
| Observed | 具体窗口/主体/仪器的测量与运行事实 | 真实执行/观测方 | `NOT_OBSERVED`、`STALE_OBSERVATION` |
| Assurance（另一个 authority） | Claim、Evidence、覆盖、Verdict | Assurance | `NOT_EVALUATED`、`INSUFFICIENT_EVIDENCE` |

状态不压成 `success=true`；某文件合法只能证明语法通过，不证明数值行为、安全、持久性、部署及运行符合要求。`require(prealloc <=1024)` 被解析成功，也不证明后端使用了不超过 1024 项预留，更不证明产品保留 256 步撤销。作用范围错误时，即使部分候选成功，也不能宣布整个 ProductRoot 完成。

## 8. 写入与冲突：真正原子边界

**控制配置与业务 Definition 不允许双重签名。** 把某条 Requirement 的默认参数改动写在 Definition 中，其使用方的继承关系需按参数绑定求值；把同一值写成另一个隐式 Control 影子，将导致两份真源在修改时分叉。Control 只能表达有权作者明确选择的目标/实现差异，不得重新存放业务目标的拷贝或自行创建真实 Grant。单个源文件的成功 CAS 不证明联合约束仍成立；若所选根依赖多个共享定义，改动应连同相交接受义务和锁定的供应关系一起判定，而不是将无关文件机械打包为必须一起重写。

**读端**必须固定 `projectInstance/sourceSnapshot/sourceRevision/lockUse/TargetProfile/descriptorRevision/rootBinding`，对依赖的新/旧源在同一读集内标识；项目清单、模块文件、控制分片、原生配置的相交更新作为一个有读集的变更候选审查。**写端**持有目的地 writer，逐文件检查前像、descriptor与外部安全要求，在同一个受支持的事务/协作协议下写入；无法对多文件保障共同不变量时不允许宣称“一次原子保存”，需拒绝或走有 journal/recovery 的可解释协议。

非协作进程绕过锁的写入不能靠本地锁本身保证安全。要有前像条件校验、共享事务 owner、写入栅栏/读后核对；在物理文件系统无法保证的情况下保留 `UNPROVEN_ATOMICITY`，不将 `os.replace` 单文件能力冒充全仓事务。外部效果须用 Operation/Attempt、幂等和读回结算，不能靠恢复本地 JSON 抹掉已发送的请求。

结构作者发生位置改名：原稳定 ID 不变时更新 locator 和引用；删除再重建同名 Definition 是新身份，旧 occurrence 控制不得自动继承。product-root 按 target/rootId 保持发生点，公开选择改变须重建 BoundRoot，不能沿用旧 Grant/资格；历史控制仅按[迁移条件](稀疏控制与目标限定.md#control-storage-contract)有条件转换，旧选择器多匹配返回 Needs；ControlFile 解释消费者尚未实现时**不得**静默忽略已选择的有型控制。

## 9. JSON 大型化的最终技术合同

作者应先决定哪些事实实际独立：

1. **同一可复用含义：** 用 `Definition/Profile + use(arguments)` 一次定义，多个 occurrence 保存差异，不复制每个算法或产品意义。
2. **范围内共同约束：** 仅在 descriptor 允许 scope 传播且确切成员一致时上移一层控制；不能因字符串相同就提升到 Project 层。
3. **未要求的值：** 不物化默认，也不保存自动解析结果。
4. **不同且必要的显式控制：** 保留多条记录；几 MB 的 JSON 不是换语言的充要条件。
5. **多人高频修改：** 外部分片是同一 `gift.project/1` 的有型可选 SourceUnit（必须有真实读取器、唯一编辑身份和迁移资格）；在线事务量大时选择具有明确定义的存储/导出快照，不强迫直接编辑一个巨大 JSON。
6. **复杂算法或二进制：** 使用原生源码、数据库、外部数据资产与 ContentRef；JSON 保留元数据、结构化声明和准确引用。
7. **可读性：** 提供局部结构编辑/紧凑只读投影，保持唯一底层作者源；如引入另一文本前端，必须证明解析、回写、注释保留、身份和迁移不丢信息。

**任何规模都不采取**“重新把系统所有事实统一为一种可执行 .gift 语言”的强制路线。是否引入非 JSON 作者存储取决于明确独立收益、负例与兼容成本，而不是 JSON 达到任意字节阈值。

## 10. 拒绝诊断与恢复动作

| 代码 | 触发 | 正确处理 |
|---|---|---|
| `MALFORMED_SOURCE` / `DUPLICATE_JSON_MEMBER` | JSON 不可唯一解释或含重复键 | 不产生可写候选；保持原字节供修复 |
| `DUPLICATE_WRITER` / `DUPLICATE_CONTROL_KEY` | 相同事实两个有权作者来源或同键重复 | 冻结冲突贡献并定位所有出现点，不能数组末项获胜 |
| `CONTROL_DESCRIPTOR_UNKNOWN` | 名称未绑定精确描述符 | 停止相交解析，不能当字符串向后端透传 |
| `CONTROL_SCOPE_NOT_APPLICABLE` / `TARGET_REQUIRED` | 作用域或 Target 不在描述符允许集合 | 请求正确 scope/Target，保留原候选 |
| `WRONG_VALUE_TYPE` / `VALUE_OUT_OF_RANGE` | 布尔当整数、非法 enum、单位错误、非规范集合 | 显示准确类型和源位置，不自动截断或取整 |
| `HARD_CONFLICT` | 真实相交的 hard 条件不可共同满足 | 显示每个 producer/sourceRef；禁止偏好补偿 |
| `NO_ELIGIBLE_SUPPLY` | 现有被检查供应中不存在合格候选 | 保留 Need，允许另选合法供应；不声明全域无解 |
| `CONSUMER_UNSUPPORTED` | 有语义描述却没有真实可用消费者 | 不宣称 Applied 或正式 Target 成功 |
| `TARGET_PROFILE_UNRESOLVED` | 清单目标画像无法精确解析 | 可设计但不能进入该目标生成 |
| `SOURCE_REVISION_MISMATCH` | 编辑时前像已变化 | 重建差异/人工合并，不无条件回滚覆盖他人修改 |
| `UNKNOWN_EFFECT` | 操作超时或回执不确定 | 检查 Attempt 和真实外部状态；不重发非幂等操作 |
| `NOT_EVALUATED` | 只获得格式/静态检查通过 | 保留缺失的运行、证据或产品等价资格 |

## 11. 发布前必须达到的接口与证据（责任不模糊）

- **contracts owner**：发布机器 Schema、descriptor binding、错误码的精确定义；严格 TS/Rust codec 对同一输入产出相同语义，不能以示例字符串取代正式 MethodRef。
- **workspace owner**：源权威、只读快照、控制文件的精确键/前像、共同提交和跨会话恢复；证明单文件与多文件边界差异。
- **semantics owner**：Requirement/Control 合取、默认/继承、无解/歧义/未知的区分及 source-based diagnostics；正反例覆盖。`req:rule` 的完整生产编码不由本页发明另一套私有体。
- **compiler/resolver owner**：真实 Method/Target 资格、硬约束和软偏好、缓存依赖、绑定锁与来源、优化预算退出和跨 Target 分别判定。
- **adapters/target owner**：值确实施加到原生配置、产物或运行环境；准确处理原生源的唯一作者权威和 ABI/编码变换。
- **execution owner**：Grant/Operation/Attempt/实际效果/撤权/恢复；运行输入不进入作者控制文件。
- **assurance owner**：针对确切 Claim 的独立证据、验收窗口和不足资格，不让自身验证通过代替原产品通过。
- **entry/client owner**：输入改哪处文件和哪个发生位置、只读导出 Effective/Plan/Observed、Reset 的本级回退和明确冲突；可以显示所有决定，但不拥有它们。

**已有且保留的基础**是五类决定、六类 authority、三张 scope 图、DEC0—DEC9、`gift.control-file/1`、工程文件及作者源唯一性。历史有限机械见证只覆盖描述符形状、控制数据与候选过滤，不签发当前源格式或生产资格。**仍未由本次完成的产品资格**包括：所有领域的生产级描述符和完整 Rule/TargetProfile、动态多方法求解、真实多文件协作事务、原生目标消费者、最终 Build/Runtime/Assurance。把这些未实现能力称为设计通过之外的已完工软件，违反本设计的分层保证。

## 12. 精确修改一条控制的请求载体：**逻辑键，而不是JSON数组下标**

直接把 `records[107]` 作为编辑目标是不安全的：记录按规范可重排，其他协作写者也可能增加或删除条目。Gift 对一次“设置/重置当前控制”的内部候选载体采用`gift.control-mutation/1` **设计 Schema**。它只是 `gift.propose` 的一个**有类型内部候选输入**，不新增第七个公共工具，不宣布已获得现有六工具的 wire 兼容资格。真实六工具的 envelope、事务和返回格式仍由原owner负责绑定。

```json
{
  "schema": "gift.control-mutation/1",
  "projectId": "gift94-editor-decision-contract",
  "sourceRevisionRef": "fixture-rev-001-not-real-source-id",
  "purpose": "author-control-edit",
  "candidateOnly": true,
  "actions": [
    {
      "kind": "set",
      "key": {
        "scopeRef": {"kind": "module", "moduleId": "studio.editor"},
        "controlRef": "example.editor.data-structure"
      },
      "mode": "require",
      "value": "piece-table"
    },
    {
      "kind": "reset",
      "key": {
        "scopeRef": {"kind": "project"},
        "controlRef": "example.build.parallelism"
      }
    }
  ]
}
```

以上 `sourceRevisionRef` 是**测试故意构造的非真实 RevisionRef**。生产实现必须引用受当前会话拥有和验证的真正快照/修订，不能接受用户随便提交同名字符串就当成合法 CAS。`candidateOnly:true` 明确禁止把此提案误读为已保存、已生效或已部署。

该候选载体消费 ControlFile 的同一逻辑键；product-root 的 key 必须含 target 和 scopeRef.rootId，不能以 module/export 或数组下标代替。两种动作定义如下：

- `set`：必需精确 `key={scopeRef,target?,controlRef}`，`mode=require|prefer` 及完整有类型 `value`；在候选作者Control存储中删除**同一逻辑键**的旧记录，插入唯一新记录；所有其余键逐字节/语义保持。必须先核对目标/描述符/权限，之后才求有效约束。
- `reset`：只携带 `kind` 与 `key`，**不得**有 `value/mode`；在候选里删除本来源该键（不存在时允许纯 no-op，但不能据此清父级、其他外部权威、其他Target、Runtime或Evidence）。Reset 后是否还存在一个有效值由求值结果决定；删除最后一条保留同 fileId 的 `records:[]`，在同一文件前像 CAS 下保存，不隐式删文件，绝不承诺恢复系统默认。

请求级不允许一个批次两次操作同一键（包括 set→set、set→reset、reset→set），不以数组后项作为赢家。整个 `actions` 作为一个作者变更候选：任何一个动作的值/类型/scope/资格不合法，整体返回诊断，不产生局部已提交文件。两个人同时编辑时每人必须有准确的源前像；对照失配返回 `SOURCE_REVISION_MISMATCH`，不直接重放在 `latest`，不无条件回滚覆盖对方。

候选构造只在私有副本上应用动作，原作者文件保持不变；必须检查逻辑键定位、批次重复、错项目、旧 Revision、Reset 非法字段、无描述符及非法 Pin mode。文件系统 CAS、权限和多文件提交仍由 Workspace/Application writer 承担。返回 `CANDIDATE_ONLY_NOT_SAVED` 不代表已保存或 Applied，后续真实消费者必须独立取得资格。

## 13. 重用最成熟的现成机制，但不把协议语义外包给工具偶然行为

- JSON 基础结构验证使用 JSON Schema Draft 2020-12，配合 Gift 自有的跨文件、稳定引用、author scope、单位和权限验证。Schema 不能自动检查整个工程 Method 是否真实存在。
- 逐项精确改变作者 JSON 可以由 CST-aware source editor 根据逻辑键定位并保留注释外的原始布局（规范JSON本身没有注释）；不能简单用 JSON Pointer 的数组下标做稳定对象身份。带 `test` 前置的 JSON Patch 可以辅助单文件 CAS，但跨文件共同不变量必须由原 Workspace writer 保证。
- 若需要带摘要的规范化 JSON，参考 RFC 8785 的适用数值与 Unicode 限制，且必须先明确 `source-bytes digest`、`author-semantic digest`、`Target artifact digest` 是三种不同身份/用途。含高精度数值和自定义Type的作者值只能由Type-owned codec提供准确 canonical 编码。
- 分片、缓存、数据库只用于与实际访问模式匹配的物理组织；同一事实在结构JSON/文本投影/内部IR中重复可写不是优化。

参考规范：

- JSON Schema Draft 2020-12：<https://json-schema.org/draft/2020-12>
- RFC 8785 JSON Canonicalization Scheme：<https://www.rfc-editor.org/rfc/rfc8785.html>
- RFC 6902 JSON Patch：<https://www.rfc-editor.org/rfc/rfc6902.html>
