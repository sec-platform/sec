# 声明、投影与系统编译

## 新语义从声明到真实消费者的闭合

已有有限枚举可以是一个固定画像的正确实现；将其改成 string 既不增加语义，也不自动解决扩展。先给出在当前画像中确需但无法表达/保持的具体使用点，再沿普通定义、合格原生供给、语义接口、Standard Semantic Module 和必要 Core Kernel 修订裁决。七个标签只用于检查闭合，不是已证明最小的本体或必须采用的目录。

| 交接 | 需要实际保留什么 | 失败与后继 |
|---|---|---|
| 定义/画像 → 解码与绑定 | 精确解释版本、名义身份、参数种类、作用域和未知载荷 | 可保全的未知不能被强语义 pass 当已理解；必需解释缺失返回缺项 |
| 签名/谓词 → 合法性与查询 | 实参/形参关系、效果和性质模型、真实读集及负依赖 | 不认识的谓词不能被当 false、真或无效果；完整声明与支持方法按同版接入 |
| 分析/转换 → 生成与证据 | 每个实际出口、组合条件、保持方向、来源与目标能力 | 消费者没有该接口则保留原区域或拒绝相交变换；不允许默认分支吞掉节点 |
| 编辑/序列化 → 持久及再次读取 | 原始字节、未知字段策略、绑定映射、原签名和当前迁移关系 | 旧读者不能改写后丢字段；新读取按原解释验真，再走合法迁移 |
| 引用/发布 → 运行及退役 | 真正调用者、旧实例及释放代码的寿命，实际 adopted revision | 新定义不热改旧实例；新增分支不抹掉旧恢复责任 |

schema、decoder、validator、签名解释、规则分派、变更请求、锁读取、目标生成和编辑消费者必须沿实际调用闭包核对；表是角色而非虚构当前文件均已迁移。只改一个校验集合、只加一个注册表或只放宽 JSON，不能宣称扩展已接入。数据入口仍严格解码，未知内容可以有独立保全路线；公开反射要有解释和权限，生成变换保持绑定卫生。

<a id="extension-closure-contract"></a>
### Extension Closure：扩展必须闭合同一系统，而不是外挂第二套系统

一个扩展只有在**本次实际使用所需的边**都能回到现有系统 owner 时才具备相应支持资格。不是每个扩展都必须实例化全部边，但缺少被本次 Claim/Target/Effect 消费的边必须精确表现为 Needs/Unsupported/Unknown，而不能靠注册成功或动态加载代签。闭合检查至少按需覆盖：

1. **Identity / interpretation**：namespace、版本、原字节/规范化语义身份、迁移与未知保全；
2. **Semantics / contracts**：类型、谓词、效果、资源、生命周期、Requirement 与合法性；
3. **Realization / methods**：可用实现、MethodSpec、Binding 条件、确定性查询依赖和失败；
4. **Target / artifact**：目标表示、lowering、ABI/布局/依赖、Artifact 与构建闭包；
5. **Effect / permission**：若会真实读写/运行/加载/发布，必须复用 Grant、Operation、Attempt、资源和恢复；纯编译扩展没有这项就不承担作用事务；
6. **Observation / evidence**：需要现实或正确性声明时，定义观察方法、coverage、Evidence qualification 与 Claim 组合；扩展不能用自己的“loaded/ok”自证；
7. **Evolution / exit**：版本升级、旧 snapshot、共存窗口、consumer migration、retirement 和恢复。

这七项是同一 L0—L6/Evolution 模型的按需闭包，不是扩展专用七层。禁止的是对**同一 canonical subject/scope/语义面**建立竞争 writer、未声明 precedence、伪造许可或自签最终资格，不是禁止扩展拥有自己的领域状态、数据库、原生 ID 或局部算法。确需新的业务对象或专业状态时先由作者 Definition/库拥有，只有公共消费者确实需要理解的新区别才进入 SemanticModule。只有能够给出“现有 Kernel 接口无法区分但系统级要求必须区分”的 witness，才允许修改 Core Kernel，而不是把所有未来差异提前塞进万能 payload。

<a id="extension-state-authority-boundary"></a>
#### 原生状态与系统权威的接口

| 扩展内对象 | 允许的主责任 | 接入时不能丢失的条件 |
|---|---|---|
| 局部类型/值、符号、算法与名义 ID | 原定义或模块命名空间拥有；不要求每个局部值持久化成 Kernel Entity | 跨边界引用带准确 issuer/namespace、种类、版本和解释；两个 Provider 的同串 ID 不自动同一 |
| 数据库、会话、仿真状态或领域 current 指针 | 作者程序或真实 Provider 可以拥有其领域数据和原生一致性 | 明确哪一语义面由谁写；Gift 观察该状态时捕获 revision/coverage/freshness，写入时走相交 Grant/Effect/恢复；不能镜像成第二份可写作者源 |
| 扩展的查询 memo、类型缓存与派生索引 | 可重建的 owner-local 加速实现 | 服从[固定输入与缓存](../../30-实现解析/增量与性能/查询固定点与缓存.md)，隐藏可变状态影响结果时必须变成受追踪输入或失去纯求值资格；不能用未跟踪的局部 current 偷换已固定 Binding |
| 外部权限、供应声明、证书和证明结果 | 真实外部 authority 的事实或合格方法输出 | 核来源、对象、范围与适用性；内部注册不能创造外部权力。扩展可提供验证 Method/Evidence，但不能绕过相应 Claim 的资格与采用规则 |

这条边界允许复用数据库、语言运行时和原生库，而不要求把其所有状态复制到 Gift。对不受信过程扩展，真实沙箱/隔离与宿主导入决定能否阻止副作用；声明 `pure` 或把代码放入插件目录不是隔离证据。实现信任与变换接纳继续由[遍管理与插件](../../40-目标与制品/编译内核/遍管理与插件.md)拥有。

纯小表达式只使用所需的内部值与规则，不持久化每个局部实体、事件和证书。新的语言分支有真实跨阶段合同才进入对应 owner；符号同名、源摘要一致或模型能运行，不创造逻辑健全性和现实权限。相交反例与限定结果见系统组合挑战。

<a id="heterogeneous-boundary-projections"></a>

## 按真实消费者取得局部语义投影

共同Engineering IR通过准确主体、解释与责任接合，不把控制流、关系查询、连续方程、事件协议和制造模型合并成一个万能Node。按用途取得公开值/结构、效果/资源/寿命、依赖/失效、来源/编辑、目标贡献/保持资格五类已有边界投影；它们引用原定义，不形成第二份可写真源或所有标量必填对象。

跨域转换必须保持其真正区别：数组到数据库需核顺序、重数、空值、数制和事务切面；连续信号到消息流需核采样、时间域、保持/插值与缺样；几何到制造清单需核身份、单位、数量、变型与容差。桥接可以复用成熟库或普通程序，但新增效果、误差和前提回原领域摘要检查。不同求解器交接准确命题、见证与前提，不交换自由文本PASS作为组合证明；不能交换可靠证明时保留独立证据和范围。

## 作者定义、语义模块、解释方言与通用接口

### 新业务不是新编译器方言

业务含义首先属于作者 Definition、普通程序和作者库。新增订单规则、游戏玩法、仿真模型、财务计算、工作流或行业对象，只要能由现有类型、函数、关系、状态、Requirement、库与 Provider 组合表达，就**不创建新的 SemanticDialect/Standard Semantic Module、不修改 Core Kernel，也不要求通用 pass 理解行业名词**。编译器只需保持这些普通构造已声明的类型、效果、资源、时间、失败和接口合同。

只有出现一种不可还原的语义区别，且 compiler／target／runtime／assurance 中至少一个通用消费者必须理解它才能避免错误变换、错误生成或错误证明时，才考虑语义扩展：可独立复用且无需所有工程共同理解的区别进入 **SemanticModule**；某组 Definition 需要精确解释规则时由 **SemanticDialect** 定义解释合同。只有身份、要求、绑定、现实作用、Evidence、恢复或演进等系统级关系仍无法正确表达时，才修改 **Core Kernel**。若差异只是“缺成熟实现”，进入 Method/Provider；若只是“目标平台不同”，进入 Target/lowering；若只是“需要更强验证”，进入 Claim/Method/Evidence。**业务数量不会推动 Kernel 类型数量增长。**

因此开放性不是“业务 or 写新编译器”的二分。正常顺序是：作者 Definition/库 → 必要的 SemanticModule/SemanticDialect → 只有系统级共同不变量不足时才演进 Core Kernel。绝大多数业务只走第一层；后两层必须由区别见证驱动。

### 目标

Gift 必须支持未来出现的 Web、数据、分布式、安全、硬件、工作流和未知业务，而不把所有名词预编码进产品核心。

```text
Core Kernel（系统级不变量）
+ Standard Semantic Modules（按需公共语义）
+ SemanticDialect（精确解释合同）
+ AuthorModule / 作者库（具体业务与程序）
+ 通用语义接口与显式绑定
```

### Core Kernel 与 Standard Semantics 的边界

**Core Kernel 只拥有所有扩展都必须服从的系统级不变量**：稳定身份/修订、Semantic Contract、Requirement、authority/provenance、引用与组合、Binding、Target/Artifact 身份、Operation/Attempt、Claim/Evidence 接合、受控变化、恢复与演进。它不因为状态机、流、AD、事务模式或仿真在许多项目中出现，就自动拥有这些应用/计算语义。

**Standard Semantic Modules** 承担可独立复用、需要通用消费者理解的计算/工程语义，例如类型与函数、对象/控制、状态、关系、流/时间、数值/AD。未使用模块不进入当前作者负担、目标闭包或运行时。模块必须复用 Kernel 的身份、权限、Evidence 和演进机制，不能建立第二控制面。

**AuthorModule (`gift.author-module/1`) 不是 SemanticModule。** AuthorModule 是作者 Definitions/imports/exports 的物理/逻辑容器，并引用精确解释合同；SemanticModule 是可复用语义能力及其公共消费者合同。一个 AuthorModule 可以只用基础语义，也可以同时引用多个 SemanticModule/Dialect。

### SemanticDialect：Definition 的精确解释合同，不是业务包

```text
SemanticDialect = exact {
  namespace,
  schemaRevision,
  semanticRevision,
  typeDefinitions,
  predicateSignatures,
  valueSchemas,
  invariantAndLegalityRules,
  interfaceImplementations,
  normalizationRules,
  migrationCompatibilityRetirement,
  ownerAndProvenance,
  conformanceClaimRefs
}
```

`conformanceClaimRefs` 只能引用由相应 Assurance owner 维护的 Claim；dialect 包本身不能以内嵌字段签发 Verdict，也不能因字段存在获得资格。

`SemanticDialect` 固定一组 Definition kind/值/类型/不变量怎样被解释、检查、规范化与迁移；它可以是 Standard Semantic Module 的解释面，也可以属于作者自定义的语义扩展。它**不是** `gift.author-module/1` 作者容器，不自带 Provider/Target/runtime，也不等于一个行业产品。

注册只建立在显式选定上下文中的可查找定义/实现入口；是否已理解结构和含义、满足合法性、可降低或可验证，要按本次实际消费者分别检查。注册不授予任何 Assertion authority。普通函数库沿已有语义构造表达，不为每个新包注册新方言；未经协商的方言不能改变当前作者、目标或运行资格。

### 通用接口

通用 pass 不写 `if web`、`if database`、`if hardware`，而消费版本化接口：

```text
Ownable
Containable
Callable
Stateful
Effectful
Permissioned
ResourceBound
Observable
Verifiable
Lowerable
LifecycleManaged
Translatable
```

接口只声明跨模块可观察合同；具体业务规则仍由作者 Definition/库拥有。

### 跨模块与跨语义关系

现实流程可能跨 HTTP、授权、数据库、消息、部署和遥测。连接必须使用稳定 identity 和 typed relation，不能用路径、显示名和自由字符串。普通库组合先在固定解释内处理。确需新增公共语义时，按下列顺序演进；这不是每次构建的搜索或插件加载流程：

```text
现有 relation/interface
→ 作者库中的局部 relation
→ Standard Semantic Module 中的新公共 relation/interface
→ Core Kernel 系统级 primitive（最高门槛）
```

<a id="extension-version-lifecycle"></a>
### 扩展生命周期

`proposed → experimental → corpus-validated → active → deprecated → retired` 描述一个发布责任下的维护成熟度，不是每个扩展必须经过的运行状态机，也不是全 Target/全部消费者的支持枚举。成熟度、已选解释、方法可用性、真实作用许可和 Evidence 资格分别判断；标签 active 不能代签任一项。

| 实际变化 | 必须保留/执行的动作 | 当前请求和旧消费者 |
|---|---|---|
| 发布新 revision | 固定新模块、导入、解释规则、目标方法和兼容范围；形成新的可选候选 | 不热改已经开始的 EngineImage、Binding 或 Snapshot；不相交请求不失效 |
| 为新请求采用新 revision | 对相交消费者核语义/错误/效果/布局/保证变化，按配置选择新版本 | 新请求用新固定闭包；旧请求继续原闭包，只要旧能力仍具备所需资格 |
| 改义、拆分、合并或替换持久消费者 | 在需要切换的范围生成新候选与明确迁移对应；读写兼容、信息保全和当前授权通过后才切换 | 原 Snapshot 仍按原解释只读；不批量改写所有历史快照，也不把仅保留为历史的版本强制迁移 |
| 停止新绑定/弃用 | 拒绝相应新准入，并列出实际旧实例、回调、数据、Artifact、恢复和编辑消费者 | 弃用不等于旧实例死亡；旧方法被安全撤销时可阻止其新执行，但仍保全数据并提供安全的解释/迁移/导出路径 |
| 卸载/退役 | 按[迁移切换与退役](../../70-工程系统与演进/演进与实施/兼容迁移/迁移切换与退役.md)确认旧代码、回调、资源和恢复责任已关闭、移交或具备合格替代 | 只有本次用途真正失去旧能力时才报告 unsupported/migration-required；缺能力不改变旧字节含义，不删除唯一恢复材料 |

升级本身不使旧 Snapshot 不支持；保留了合格解释器和依赖时，它仍可用于原合同允许的用途。相反，旧解释器可加载也不意味着允许继续执行一个已撤销的危险动作。持久兼容、运行许可、取证资格与旧引用寿命需要分别核查；不能用一条全局 active/retired 状态覆盖它们。

### 反特化验收

- 对宣称通用的 generic pass，至少以两个语义不同、具备相交接口的合法方言定义检查同一方法，不能把改名后的同一例子当第二见证；只有一个合格见证时保留覆盖限制，不虚构第二产品或已运行成绩；
- 新增方言不修改 Core 业务 switch；
- 加载顺序不改变 canonical bytes；
- 未注册/冲突/歧义语义 fail closed；
- 方言不能授权自己产生的 Fact；
- 升级但保留合格旧解释时旧 snapshot 仍可消费；真正失去所需能力时才准确返回 unsupported/migration-required；
- 按当前使用的跨域区别见证检查组合，不产生第二 Engineering IR；领域数量不签发覆盖率。

## SemanticModule 与系统定义编译

### 合同用途与存在理由

`SemanticModule` 是具有独立公共语义身份、至少一个真实公共消费者的可复用语义能力包。它让新语义在不修改所有通用算法的条件下进入 Gift；它不是 `gift.author-module/1`，不是自动获得宿主权限的任意代码插件，也不是把业务名词收集到 Kernel 枚举。用户可以提供一般程序体、新类型、新算子和过程型编译扩展；声明可表达、编译期可执行和宿主有权限是三个独立合同。只有具有实际类型、规则、接口、降低或验证消费者的语义集合才需要独立 SemanticModule；作者内部的小型类型和完整业务组合不必为了形式一致而发布公共语义包。

### 身份与版本

一个模块由命名空间、稳定模块ID、schema版本、语义revision、内容摘要和兼容说明定位。公开符号由模块身份、局部符号ID及语义revision引用；显示名和文件位置不参与稳定符号身份。导入使用冻结解析后的精确revision；版本范围只参与解析，不能直接进入可重建构建。

模块升级不默认重新解释旧模型。兼容关系针对输入模型、公开符号、规则行为与目标能力分别判断，不能只比较版本字符串。改名通过显式别名/迁移维持身份；别名有消费者和退役条件。

### 语义目录的逻辑字段

语义目录保存模块身份、精确导入、类型、关系、接口、规则、降低、迁移及所需能力。每类声明在自己的命名空间中解析，字段允许的引用种类由下文检查；缺失实现保持为明确义务，不生成成功占位。

这组逻辑字段用于语义能力定义与链接，不是一份可直接宣称已发布的 JSON 协议。作者内容容器采用[既定 AuthorModule 外壳与版本规则](../../10-作者与输入/作者源/工程源/工程清单模块与绑定锁协议.md#unified-current-author-writer)；需要独立交换语义目录时，按当前版本对应的方法合同定义实际编码与版本。来源可信、结构有效、模块启用、事实权威与效果许可分别检查，任一字段都不签发读取、写入或发布权。

### 公开类型与行为边界

类型包含值域、空值、相等、排序、编码、溢出、集合和引用语义。引用递归允许通过明确的名义类型出现；无限立即展开的值定义、无法终止的规范化规则和含糊联合分支被拒绝。任何使用方必须知道一种语义是完整支持、保守近似、原生保留还是不支持。

关系声明端点类型、方向、基数、上下文和是否规范/描述/派生。禁止用自由字符串推导关系含义。基数约束用于确定错误和依赖范围，不能把缺少观测自动解释成零条关系。

规范检查可引用声明式规则、受信解释器或受预算控制的过程实现。对规则的编译执行施加预算，不等于只允许有界目标程序；一般函数、递归与循环可作为用户程序语义保留到目标运行。模块注册不立即执行其安装脚本、宏、验证器或原生代码。需要过程能力的规则通过隔离执行产生不可变回执；其结果必须通过结构和语义边界校验。

### 链接算法

1. 读取请求中明确选择的模块及精确导入闭包，检测丢失、重复身份和内容不一致。
2. 在不执行扩展代码的前提下解析schema，拒绝未知规范字段、重复键和超限对象；扩展诊断字段必须显式命名且不得影响规范含义。
3. 建立每模块符号表并解析公开引用。局部同名符号错误；不同模块同名只在显式导入别名后进入作用域。
4. 构建类型、规则、接口与降低依赖图，分别检查环。递归类型不等于加载循环；声明链接可分两步，模块初始化的隐式效果不允许形成循环。
5. 检查接口方法的输入、输出、效果、失败与能力要求。结构签名相同不能证明语义等价；需绑定接口符合性声明和证据等级。
6. 固定同一阶段的规则选择。存在多个可用降低时按完整合同、目标、规则优先序和已委派稳定策略选择；同优先级但已存在合法平局规则时可以确定，不一律报歧义。真实行为或选择权未决才记录相交义务，不能依赖注册顺序。
7. 为每个请求输出生成所需模块视图与验证义务。未被任何请求使用的缺失可选能力不阻断无关输出。
8. 生成链接结果、符号来源、依赖边、诊断和摘要。原始模块不被链接器原地修改。

### 依赖方向与隔离

Kernel 依赖稳定扩展接口，不静态导入所有语言、框架、AI和宿主适配器。语义扩展实现依赖 Kernel 接口；组合根按冻结选择连接。通用 Pass 通过接口访问所需 SemanticModule，不写 `if domain == orders`。某项新业务若揭示真正新的公共语义区别，应按区别见证提出 SemanticModule 或 Kernel 演进，而不是向未类型化字段塞数据。

### 并发、失效和缓存

一次链接只使用冻结的模块内容，注册表变动不会热改当前实例。新增候选模块本身不必使既有绑定失效；只有选择策略或输入闭包明确观察候选全集时才触发重解析。移除正在被引用的模块revision先进入停止新绑定、保留旧解释器的排空阶段，不能销毁仍需读取的模型。

缓存键包括链接器revision、请求的符号/输出根、实际模块内容及策略。全局目录序号可作为保守失效提示，不应永久替代精确闭包。依赖证据不足时回退更宽计算，不能假命中。

### 错误与迁移

错误分为输入模式错误、未解析引用、身份冲突、规则歧义、非法递归、能力不支持、迁移缺失和证据不足。解析或规则超时属于预算结果，不是已证明无解。旧revision迁移产出新候选模型和保全对应；经重新校验与采纳后切换，旧读者按支持窗口保留。

### 验证与最强攻击

两个异质模块复用同一链接器；交换加载顺序不改结果；重复导出被拒绝；未登记引用不进入链接结果；注册模块不能取得Grant；缺失非必需目标能力不阻断别的目标；篡改相同revision字节被检测；递归类型与规则循环分开；恶意验证器不能在链接中获得宿主I/O。

更简单的静态内置模块在早期可行。本协议的成本是链接、版本和扩展符合性；其收益必须由真实第二领域或独立扩展证明，不能仅用模块数证明必要性。

### 引用域、内容绑定与依据

目录适配器把字段类型、关系端点、接口输入输出及降低输入解析为类型引用，把降低规则解析为规则引用。容器类型按所选画像递归解析；即使两个符号位于同一张表，也须核其种类，不使用同名通用字符串代替。

在选择该符号引用编码的目录中，未限定名称指向当前模块；`alias::Name`通过显式导入别名解析；`module#Name`跨模块同样要求直接导入。传递导入不自动暴露。采用有限全公开目录适配时，登记声明为可导出声明；私有或嵌套成员必须使用具有对应可见性规则的实际编码，不能默默压平为全公开。上述编码不改变基础文本的导入语法。

调用者可以通过冻结目录传入 `(moduleId, semanticRevision) → contentDigest`，检测同标签不同内容。没有传入该证据时，链接只证明本次观察内的结构与引用，不签发跨时间目录真实性。规则解释器、语义合同、效果、保持声明和目标画像仍属于外部义务，不因字符串可解析就通过验证。

没有终点的纯别名展开环被拒绝；通过名义记录的递归先完成结构链接。是否有有限可构造值、能否序列化及目标怎样保持含义，由相应类型与目标规则分别判断，不能由链接成功代签。

### 有限目录的链接检查

有限目录适配器分别建立类型、关系、接口、规则与lowering符号域，不把同名不同种类当作通用引用。该有限编码在单个导入上下文内对同一moduleId只绑定一个精确revision，`module#Name`必须无歧义；这不是全工程禁止多版本。已支持的多个[ModuleUse解析域](../../10-作者与输入/作者源/工程源/工程准备视图与编译输入.md#module-use-binding-domain)可分别绑定不同版本，并保持真实名义/链接约束；此有限适配器不能表达所需域时报告相交能力缺项，或使用已有明确公开边界/经协商的解析扩展，不能靠到达顺序挑选，也不因revision改变强制改稳定moduleId。

本地类型和字段重复、未知局部引用、种类错误、无声明直接导入、接口重复参数、纯别名展开环均可由有限检查裁决。名义记录递归保留，后续目标仍要验证布局与可构造性。外部模块内容、解释器、效果、规则语义与保持声明在没有上下文时报告 `context-required`；不把本地通过称为完整链接或认证通过。

若两个同优先级 lowering 的实际适用性不能在当前有限模型判断，记录歧义检查义务，不能直接猜一种，也不能把所有条件可能互斥的规则都判为冲突。

### 异质语义的接入与保全

模块提供解析、类型/关系检查、接口语义、降低、验证、迁移和来源对应中的明确支持子集；未提供的维度保持缺项，不能以通用JSON容器冒充理解。连续/概率/人类活动语义可以有自己的IR和验证方法，通过公共边界交换声明和制品，不必先伪装成离散状态机。

接口需要声明数值、时间、单位、错误、效果、状态、并发、观察和版本保持条件；无法证明保持的转换不自动执行。新增模块从这些可观察承诺、失败域、兼容/迁移关系和实际 Claim 派生 ProofObligation：Evidence 必须足以证明允许路径可用，并能排除会改变相交结论的错误实现；具体方法与案例数量由语义风险和可判定性决定，不用固定“正向/负向各一条”的配额代替覆盖。具体情境协议见[工程情境组合与能力协商](../../70-工程系统与演进/演进与实施/适用性与能力协商.md#工程情境组合与能力协商)；设计实例见[跨领域机制场景与实例化合同](../../70-工程系统与演进/演进与实施/作者定义组合与核心扩展.md#跨领域机制场景与实例化合同)。

交换格式只约束其实际字段和消费者，不替代完整的领域行为合同。真正新语义无法由现有扩展点保留时，提出核心接口修订并重新核对受影响消费者；不能为了维持既有内核不变而丢失含义。

### 一般定义包与模块实现

用户可通过数据、API、图形或可选语言前端定义类型、函数、操作及其程序体。能够由现有构造定义的语义先作为普通用户模块编译，不要求系统管理员修改内核、发布新内置领域或为每项需求写生成器。只有不能由已有语义保持表达、且通用消费者必须理解的区别，才需要新的 SemanticModule/Dialect 接口或 lowering；已有外部库仍可通过原生表示或明确签名接入，不能先要求一个业务 Adapter。

链接的详细可执行路径见[开放编译器内核](../../30-实现解析/内核/编译值服务.md#开放编译器内核设计)，扩展作者的完整合同见[用户定义语言语义与编译扩展](语义扩展-用户语言与语义晋级.md#用户定义语言语义与编译扩展)。递归模块先登记名字与显式/待推导签名，按有限补全核主体与效果；真正的递归类型缺口要求注解；模块之间只引用身份与精确revision，整个选定闭包另用锁表绑定内容摘要，避免互相把对方摘要嵌进自身而形成无法求解的哈希循环。摘要固定本次内容，不自行证明发布者权威。

### 扩展包描述、解释激活与可执行插件准入不是同一步

读取一个 SemanticModule 的**纯声明**，可以在对应只读权限和安全解析器下取得声明的签名、符号和依赖；它不会自动执行插件里的初始化脚本。注册一个声明也不意味着通过语义保持、Target适配或操作授权。只有某请求明确消费且必要资格成立时，解释器/编译器才调用被选方法；若Provider的“列举方法”本身会执行任意代码，该发现动作必须被归为真实执行能力，而不能留在纯数据读取阶段。

所选扩展可能改变运行时效果、错误、时间、资源、权限或隐私语义；编译器不能仅比较函数签名和返回类型认定可替换。解释器与其可能读取的宿主上下文必须作为准确方法输入/执行依赖；恶意插件返回假的证明、错误码或 provenance 仍只是不可信观察。扩展不可满足公开接缝合同但原生工具链可直接消费时，允许明确 `opaque/native` 使用及其有限保证，不凭顾客想要支持某领域就给 Core 添加全权业务协议。

反例：插件包有纯类型声明及“自动发现实现”的脚本，发现阶段会运行脚本读取用户环境变量。若本任务只有只读代码补全授权，则声明仍可受限显示，但执行发现被拒绝或改用已有静态目录；即使脚本执行并返回一个候选，也不能从返回成功推导其有资格成为正式 UseBinding。

## Extension Closure：开放扩展只能增加局部语义，不得增加第二套系统

Gift 的开放性不是“允许插件自己定义一切”。新增 capability、Profile、dialect、Provider、target 或领域机制时，只能增加现有模型无法表达、而真实消费者必须区分的可观察语义；扩展的身份、解释、Requirement/Contract、实现/Binding、目标/Artifact、现实 Effect/Grant、Observation/Evidence 及演进/退出仍分别回到现有 owner。具体准入、未知保全和消费者闭合由[语义扩展与外部定义接合](#extension-closure-contract)唯一维护。

扩展可以只实例化任务真实需要的边。例如纯编译 dialect 无需 Operation；只读外部 Provider 不因可发现而获得写 Grant；一个新 target 若复用现有 Requirement/Binding/Evidence 模型，也无需再造 target-specific configuration root。相反，只要本次能力会执行、发布、迁移或声称正确，就必须补齐相交的权限、恢复、Evidence 与退役责任，不能以“插件加载成功”“schema 已注册”或“Provider 在线”代签。

因此 Core 的扩展门槛是**区别见证**而不是名字或行业：必须说明现有 Entity/Statement/Configuration/Transition/Evidence/Projection、既有领域接口和 typed relation 无法保留哪项独立可观察区别，及不扩 Core 会导致什么错误结果。能够由既有组合表达的能力只新增 Definition/Method/Provider/Target 等实例；只有这个 witness 成立才允许修改 Core，并同步相交 owner 与验收。

扩展可以拥有自己的领域 State/Event/Value、命名空间和原生存储；禁止的是对同一 canonical subject/scope/语义面建立竞争 writer、隐含 precedence、伪造许可或旁路 Evidence 资格。[原生状态与系统权威](#extension-state-authority-boundary)统一规定接入边界，[版本生命周期](#extension-version-lifecycle)分别处理新采用、旧解释、实际执行和退役。Extension Closure 约束的是公开接缝，不把合法扩展内部实现或作者业务重新吞进 Kernel。

**语义消费校核：** **声明与激活分离：** 扩展描述能被解析、功能名被发现，不代表解释器、目标工具和操作权限均已取得。适配不认识的新语义字段时，不可静默忽略后继续宣称同一解释；能力不足按用途阻断，插件执行仍独立取得最小权限。 实现或验证此用例时分别消费[协议协商中的降级、未知字段与旧客户端保护](../../70-工程系统与演进/演进与实施/兼容迁移/生态协议与版本演进.md#gift-capability-downgrade)、[委派能力收窄、重定向与执行时再检查](../../50-执行运行与观测/权限与资源/授权与执行准入.md#gift-delegation-attenuation)的权威交接，当前机制只拥有本地行为含义。

## 语义模块发现与全域覆盖的关系

[全域共同合同](../共同语义/工程通用语义全域与闭合合同.md)只是对已/尚未识别的观察区别提供统一接缝，不能替代本页负责的解释器与 SemanticModule 合同。新增具体领域 Definition 无须向中央家族表注册一个 Core `kind`；只有现有解释语义无法保持真正的观察差异时，才按本页升级画像/消费者并重新检查既有保持性。
