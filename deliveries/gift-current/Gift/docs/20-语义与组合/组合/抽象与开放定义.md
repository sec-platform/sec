# 工程语言与用户定义


### 抽象应压缩共同机制，而非模糊不同约束

Gift的“极致抽象”不是把万物装入`objects[]`/`relations[]`或单个`UniversalNode`。只有输入形式、意义、使用资格和失败后果都一致的关系才可共享原语；否则共用可复用的基础类型/身份/作用域，具体角色仍在专业Kind中表达。统一的目标是**必要区别不丢失、重复决定不出现、组合时不依赖猜测**。

最小公共骨架：Type/Value、Definition、Use/Binding、Identity/Scope、Relation/Cardinality、Predicate/Evidence、Event/State/Time、Requirement、Authority/Resource、Effect/Observation、Qualification/Refinement。它们是正交的语义职责，不是编译器必须建立的十一个数据库表，也不等同作者显式填写的十一个字段。领域词汇（订单、病历、卫星、银行账本、关卡、材料）在这个骨架上由有权Meaning定义；缺少解释器时不得根据名称猜测。


### 四种容易造成伪抽象的混淆

**Definition / Use**：相同定义在一个系统中使用两次是两个Occurrence，其角色、时间和上下文可不同。Definition只定义不变合同；Use携带本次实际绑定和局部身份。

**Type / Identity / Value / Revision**：类型相同不代表两个对象同一；字符串值相同不代表同一租户或资源；逻辑身份保持并不代表内容Revision不变；内容Hash相同亦不代表相同权限来源。四者独立并分别具备解析域。

**Fact / Assumption / Norm / Desired Outcome**：观察的现实、条件假设、具有权威的规范和作者希望达到的目标，均可用命题表示但不能共用一个无来由`true`。即使语法形式类似，其来源、撤销、成立区间和证明义务也不同。

**Action / Capability / Grant / Effect / Settlement**：业务动作意义不是外部实现；拥有能力不代表当前授权；允许执行不代表执行发生；派发成功不代表结算成功。每一条跨越都需要相应专业资格，不能靠普通Ref当成已达成。


### 有类型通用关系的保留原则

- `DefinitionRef`解析到单一稳定声明；`DefinitionUse`携带发生点绑定、作用域、实际角色和必要使用ID；成员列表是组件/产品自己的关系表。
- `ComponentUse`将模板定义实例化为独立实例；其静态参数、运行上下文、状态、资源和部署实例都在相应根作用域中解析。
- `RequirementUse`从已接受Goal/复合约束派生使用时义务；同一要求文字、同一Def在不同主体和时段不能因文本相等自动去重。
- `QualifiedBinding`只绑定某一合同、Method、环境和Revision；专业证明不能被跨Scope拷贝。
- `ArtifactLink`是Source→Method→目标代码的派生映射，编辑目标文件不反写作者业务意图，除非显式进入受管回写流程。

这些可以共享引用协议和不可变来源标识，不建一个用户可写的全局`allRelations`或`metadata.any`。


### 基数、顺序与开放集合

`one`必须恰好一个合格实际，`optional`可明确缺席且缺席不等于null；`set`按规范身份去重，`bag`保留重复数，`sequence`保留位置和重复。一次外部扫描拿到某些元素不等于得到了集合的全域；需要证实完整性的量化/否定，应保留快照、分页、权限、时间范围和枚举范围。集合扩展时必须区分不完整观察、正常空集、未提供和值未知，不能通过默认空数组吞掉缺口。

业务对象的表示有独立身份及作用域，集合成员相等性可由名义Identity Provider或稳定ID定义；没有合格的跨域等价映射，即使两个根均含`document:123`也不能共享或折叠资源额度。


### 合成律：局部有效不等于整体成立

同一组合必须同时考虑类型兼容、签名角色、前/后条件、状态Frame、所有权、时序、共享资源、并发、权限、目标支持及实际可观测边界。两个局部满足的组件可以因竞争同一容量、循环等待、共享对象错误分区、权限相互排斥或数据一致性冲突而联合不可用。可交换/并行/去重/缓存仅在精确的行为与效果保持条件下成立；默认顺序、声明位置、文本相似度不构成这些条件。

### 抽象的八种实际动作与替代资格

抽象不是把名称相近的对象塞进一组。可以对已知 Definition 作**封装**（隐藏可替换内部）、**参数化**（提取共同可变处）、**泛化**（扩大适用输入域）、**特化**（收窄域并补前提）、**组合**（按类型化边建立新能力）、**投影**（只暴露已声明观察面）、**精化**（以能履行抽象合同的具体机制替代）、**替换**（在已证明相容边界内更换实现）。这些是对既有 Type/Meaning/Pattern/Requirement/Component 的操作，不强制发行八个顶层 Kind 或八张派生数据库表。

任意一个抽象操作至少保留四类条件：①输入/输出类型、基数、身份和权威范围；②允许的行为/状态/效果轨迹，包括错误与未定义输入；③资源、时间、授权、观察范围及已接受硬要求；④编辑与调用者能够看见的差异及版本迁移前提。精化不是“更详细的说明”：若原合同允许两个不同合法结果，具体实现必须选择其中确实合法的结果；若原合同禁止远端传输，新的云实现即使最终数据相同也不合法。投影隐藏内部实现不等于可以隐藏公开错误和效果。

模式的角色多重性不能压成一个布尔或一个对象：`zero-or-one`、`exactly-one`、`zero-or-more`、`one-or-more`、有确切上界或数量的集合分别具有不同存在性义务。空集合上的 `all` 可能形式上为真，但要求至少一个服务实例时仍不满足；一次 `PatternUse` 绑定多个主体必须保留一一/多对一约束。同名 DefinitionRef、相同 Type、相同空间坐标都不足以断言使用点指向同一业务实体。由抽象导出的相似实现可以共享代码，不能因此共享权限、状态或实时资源所有权。

由此，真正可复用的共通内核是有型角色与约束、绑定、替代关系、失败结果；具体业务对象、成本机制和真值来源仍由相应 Owner 定义。若发现一个新领域能力无法在共同关系中准确表达，先询问缺的是新领域 Meaning、一个现有 Type 的新运算、Method/Target 供应还是确实新的公共关系，再决定扩展点；不得以 `metadata:{...}` 把未知意义偷偷塞入消费者。


### 抽象不凭字段相似性建立：定义、精化和替代的方向

一种通用定义的复用必须通过精确的形式角色、输入前提、结果保证、可观察效果和可用的上下文范围。`abstract → concrete` 的精化意味着实现不得要求调用者额外承担原合同没有的前提，不得减少已经承诺的输出/安全义务；增强只允许是所选使用点已经要求且可以建立的更严格保证。向上抽象不可抹去决定实现资格的时间、资源、授权、错误类型或外部副作用。两个候选拥有同一 JSON Body 外观不意味着相同 Meaning；相同 Meaning 也不保证同一 Method 对两个 Target 都合格。

泛型类型替换与业务角色实参绑定不可混同：`TypeParam` 选择合法类型族，`BusinessRoleActual` 选择本次使用的真实对象及其证据范围；`ComponentInstance` 再赋予持久实例边界。不同角色间的协变/逆变受接口调用方向控制，能读的视图不因此获得写能力，资源的独占借用不能由普通结构子类型规则复制。为简化输入只允许省去派生的实例 ID、关系索引和显示视图，不允许省去改变行为的开放域假设、授权和共享状态归属。


### 合成的不是文档，而是有语义的使用关系

设已解析定义 `D` 是一个可复用合同，`Use(D,Bindings,Scope)` 是其具体发生点；`Instance(ComponentTemplate,Arguments,Context,Root)` 是系统中的组件实例；`SelectedRoot(Project,Target,Occurrence)` 决定一次输出/部署义务。**它们不是四种可以互换的对象**。某个 `workflow:plan` 被两个实例共用时，其Definition相同但调用状态、参数、资源及效果身份独立；共享需要另有显式协议。

通用**组合接口**仅复用可验证的结构条件：输入输出的类型、角色签名、能力方向、接口协议、上下文实际值、作用域、前后条件、要求与目标。各专业含义仍归原Owner。一次接合 `A.out -> B.in` 必须同时满足：名义/结构类型兼容、量纲/编码/版本一致、所有者与允许流向、必要权限、作用时刻可获得、资源和并发前提可满足；否则得到具体冲突或 `Needs`。字符串相等不属于完整接合证据。


### 主要组合操作及不同结果

| 组合 | 具体行为 | 不可混淆的错误 |
|---|---|---|
| 结构组合 | 产品包含组件实例、状态宿主、数据/协议/资源参与关系 | 模板存在不等于实例有所有资源 |
| 顺序 | A达到明确完成条件后才允许B；关联结果携类型与代际 | A的请求已发送≠外部效果已完成 |
| 并行 | 同一激活可分流多个可并发步骤，保留单次执行关联 | fork≠全部成功，join的 `all/any/quorum` 需声明；取消不等于回滚 |
| 选择 | 各谓词有资格且按互斥或明确优先级仲裁 | 多条件同时真、未知和冲突证据不由数组顺序决定 |
| 条件 | 根据有型领域/计算条件启用某分支 | 缺事实不等于条件假；没有合格读回不能选择 |
| 迭代/递归 | 在有界/允许部分终止的契约下重复工作 | 循环构造不自动保证进展或真实资源有界 |
| 状态转换 | 事件在指定状态与作用域下改变合法状态 | 缺失转移、歧义转移、跨并发竞争不同 |
| 消息/流 | 按投递、顺序、重放、时间水位与消费者使用 | 至少一次送达不能生成至多一次外部效果 |
| 联合要求 | 全部硬需求相交、软目标在硬可行集上优化 | 局部最优或不同根独立满足≠整体可行 |
| 组件/服务边界 | 提供/要求端口对齐，外部端口显式保留 | 隐式把未连接端口当宿主能力是错误 |
| 替换/适配 | 新Method在保留公开行为、不变量、效果权限前提下替换 | 性能更好不允许变更领域意义/失败结果 |
| 演进/迁移 | 旧存量与新方案在兼容窗口有确定关联 | 新代码生成不能假设旧数据不存在 |

### 上下文绑定顺序

按 `Project → target/outputRoot → ProductDefinition → componentInstance → component member Use → WorkflowActivation/Step` 取得有效绑定。内侧声明需要某角色时，它必须来自一个有权上层提供者或显式本地输入；相同角色名不会自动绑定。同一组件模板可以出现无数次，但每个实例各有静态参数、业务对象、运行代际、状态及触发路径。输出根不同的实例不得因共享Definition被隐式合并。


### 失败结果不是全局布尔值

至少分开：`InvalidSource`、`UnresolvedReference`、`TypeConflict`、`UnknownMeaning`、`ContradictoryRequirements`、`NoQualifiedMethod`、`TargetUnsupported`、`PermissionDenied`、`TimeoutOrUnknownEffect`、`ObservationIncomplete`、`ArtifactChanged` 和 `MigrationUnsafe`。这些名称是设计讨论中的结果类别，不是新的全局枚举文件；归属分别在Source、Meaning、Requirement、Method、Target、Runtime、Observation和Migration。各类结果记录影响对象/发生点、有效假设及可恢复动作；不应被一个万能 `status=failed` 覆盖。


### 完备性判据的准确含义

上述组合在**具有已解释的有限描述**且各使用边准确绑定时，可以无损构造任意大小的产品图，但这不是证明所有现实需求均可满足的形式定理。开放世界、不可计算要求、未提供方法、时间与资源的无限复杂性仍可能使判断无法完成。开发者体验可以极其简单，但不能将这些现实约束删除。

<a id="finite-abstraction-relations"></a>
## 一个有限机制，开放行业语义，不按类别数制造抽象

定义、实例化、细化和组合都在**同一个作者Definition/Occurrence/Reference**关系体系中解释。业务主体、类型、状态、规范、资源和证据是不同意义的属性或被引用定义，不对应一个可任意互转的“通用业务对象”。新领域只能增加有签名、版本、来源和解释资格的具体 Meaning，不能自动增加 Kernel 关键字。`/2`与旧`/1`的同名概念通过有凭据的引用和旧源适配器结合，绝不能用新Schema的字段数断言语义等价。业务抽象本身不要求作者写计算函数，但统一作者模块已经把按需计算纳入同一语言；计算解释和具体目标的生产资格仍是独立条件。

<a id="gift137-refinement-preserves-choice-and-norm"></a>
## 抽象与实例化必须保留选择和规范的语义区别

从几个具体业务流程抽象公共Pattern时，分支互斥/优先关系、`NEITHER`与`BOTH`的处理差异、政策义务内容、状态转换候选和组件端口方向均是必须保留或转化为显式差异槽的观察条件。将一个“人工复核冲突”流程抽成“未知即重试”，不是保持语义的抽象；将一个必须审计的 `oblige` 策略变成 `permit`，不是合法精化。公共Pattern、实际Occurrence及其参数必须分别保留原发布者、时空域、基数和权威来源。未能证明行为包含/不变量与规范保持时只允许得到有条件候选，不得签发合格Method或完整Target。


<a id="gift135-abstract-preserves-author-distinctions"></a>

非计算业务抽象在`abstract/instantiate/compose`之间必须保持实际量纲、名义对象、规则签发者、条件判断权、角色基数、资源身份、时间域、异常、观测完整性与作者来源。业务容量`capacityLiteral`不是可在未知来源间求值的Expr；两个组件槽`argumentBindings`指向同一共享资源并不制造两个资源实例。Pattern的共用条件与具体业务条件须独立绑定，缺领域解释只能得到`ELABORATED_UNQUALIFIED`或相应Needs；不以模板生成或函数定义绕过。字段入口由[唯一作者Profile](../作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#gift135-noncomputational-author-closure)拥有。

## 抽象与开放组合不强制作者编写通用计算

本阶段沿用已经定义的`define/abstract/instantiate/specialize/compose/refine/realize/observe-and-verify`，只要求业务主体、数量、时间、义务、权限、失败、来源和观察差异在抽象/实例化中得以保留。`refine`只规定专业Method必须满足的精化义务，不在此实现求解器；`realize`只规定完整Artifact合同，不输出假应用。新的专业业务意义由受资格的`domain:meaning`或Dialect供应承担，不能靠新增`core:function`或任意JSON字符串绕过。与其他作者构造的完整路由见[非计算作者合同](../作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#gift134-noncomputational-author-contract)。

<a id="gift136-noncomputational-composition"></a>
## 一套通用组合机制，不把每个属性升级为关键字

现有`define/abstract/instantiate/specialize/compose/refine/realize/observe-and-verify`是对业务语义结构的**关系与正确性操作**，并非八个开发者必须逐个书写的指令。`kind`指定Definition类型；Occurrence、`conditionUse.bindings`和`product:system.connections`分别表示“复用的定义在何处被使用”、“这次谓词属于哪些角色”、“哪个具体实例提供什么能力”。三者不能由同一个`Ref`字段无损代替。

定义层与使用层分离才允许同一个Meaning被不同业务主体、多次事务或两个产品实例复用，同时不混淆主体身份、硬约束、授权及证据。抽象时保留参数角色、基数、差异槽与适用域；实例化时按相应签名绑定；组合时汇合相交硬义务；精化资格和Target源码生成仍由后继Owner签发。未安装的新行业语义经开放Dialect/Meaning提供，不通过不断扩充Core的枚举解决。具体写源Schema和拒绝条件由[开发者通用定义Profile](../作者语义/开发者通用定义Profile-类型计算业务与系统构造.md#gift136-business-predicate-use)维护。

## 采用设计：八类抽象操作、模式复用与行为保持（R02–R04）

本节定义业务Pattern的开放抽象、角色绑定及精化保持条件；不增加普通作者必填的计算语言或重复60项公共接合角色。现行输入仍为`semantic:pattern/1`、`semantic:pattern-use/2`及锁定Definition引用。形状展开只生成待解释的派生要求；没有合格Meaning/Requirement消费者时，不得继续签发可实现或产品合格资格。

| 抽象操作族（纯分析除显式采纳） | 输入→输出 | 可检验的保持条件与拒绝 |
|---|---|---|
| `define` | 作者采纳的类型/Meaning/Pattern/公开合同→有身份Definition | 类型化签名、可观察区别、来源、权能、稳定identity；单个业务标签不足 |
| `abstract` | 多个带正反例的已接受具体合同+观察域→公共Pattern候选、差异槽、反例 | 所有被抽实例经精化后不丢其必要观察；未见领域只是待挑战，不自称最粗唯一 |
| `instantiate` | PatternRef+精确角色基数+必要差异+观察选择→DerivedObligations | 角色集合恰全、名义精化可信、每条共享要求保留；缺条件不删声明 |
| `specialize` | 更具体谓词/类型/资源/政策→收窄后的公开Definition或使用点 | 所有新成立前提有有权来源；子型可接受行为必须满足原公开合同，不能凭继承名继承权限 |
| `compose` | 多个Definition/Intent及共享关系→带有依赖/冲突的联合义务 | 全局交集、量词次序、效果顺序及跨主体共享不变量；两两兼容不保证整体可行 |
| `refine` | 抽象合同、具体Method/目标映射和证明义务→有范围的精化资格 | 显式输入覆盖、安全、进展、错误、资源、Frame和可观察性保持，未获证据返回Need |
| `realize` | 通过资格的计划+TargetProfile→完整ArtifactSet | 生成与引用的真实源码/适配器/依赖/迁移/构建均可用，不留假stub；无Grant也不假装已执行 |
| `observe-and-verify` | 范围化Observation与独立Evidence→特定Claim裁决 | observe只读取，verify仅判断证据资格；两者不能相互代签、不能改作者或现实操作 |

### 四组抽象正确性义务

**类型与基数保持**：`one`要求恰有一个合格对象；`optional`区分显式空和存在性未知；`set`按可信身份去重并拒绝重复声明；`bag`规定同一可信身份仅出现一项，重数为正整数；`sequence`保留位置及重复。JSON字节相同不能证明对象身份相同，不同身份域不得无见证归并。量化或否定需要完整成员域时，已读的部分样本不能替代全集。

**精化与观察保持**：从公共角色到实际对象的映射必须保存主体、作用域、时态、状态、错误、权限和来源差异。`RefinementWitness(sourceType,targetType,meaningUses,scope)`仅证明本次被消费的方向与范围；不得反向使用，也不自动证明值/单位转换。通用“预留容量”不蕴含临床确认、资金清算或防超卖规则；这些差异由有权领域合同显式绑定。

**行为及组合保持**：Pattern表达要求而非Method实现。精化须覆盖成功、正常进展、禁止行为、交叠资源、异常/未知结果、外部观察及完整性，不得以减少输出字段隐藏禁止的副作用。`RequirementRef`交由其合格消费者解释；复杂时态、规范及权限不能作为普通`predicateClaim`布尔式无损降低。

**版本与采纳保持**：已接受的作者源、PatternRevision及在途义务分别固定，不随新版Pattern发布自动替换。`abstract()`或局部模型验证只产生候选，不修改作者Definition；有权作者采纳后才更新唯一真源。ReadSet、负发现与SourceMap使实际依赖的消费者和资格按变化范围失效或重算。

### 最粗抽象、组合空间与反例的精确边界

只有在**有限对象域、已固定观察函数和保持关系**下，才可能求特定意义上的最粗合法抽象；跨环境、跨关系规格及开放实现域未必存在唯一最粗者。`abstract()` 返回有范围的候选、可能的非支配集合及反例，不凭行业样本宣称全域最粗。允许实现集 `{a,b}`、`{b,c}`、`{a,c}` 两两相交但全交集为空，因此 `compose()` 必须检查全局相容；有限部分观察另按知识集合/Pre不动点检查安全性，按适用 rank/公平条件检查完成与进展。

**设计产出与资格**：`PatternInstance` 是带确切来源的只读视图；`DerivedObligationSet` 仅在类型、差异和本次静态解释合格时得到 `ELABORATED_UNQUALIFIED`，不能提升为 Method、Built 或 Observed。复杂 Requirement 保持类型化引用与有来源的 Need，交由真正 Owner 消费。Rust Kernel 可实施纯静态实例化，遇新行业不增加 `switch(domainName)` 分派。

## 抽象可组合的准入与自由度

公开定义、局部具体化、原生绑定和领域扩展共用[组合边界摘要](../共同语义/边界摘要与跨域组合.md#组合边界摘要与义务闭合算法)。新增普通算法只增加作者内容，不扩大核心工具或解析器目录。更高层定义内部能读取的字段、资源和契约必须有声明/实际依赖；把全部用户程序藏成不透明字符串不构成可理解的高层语义。

定义实例化时先绑定输入与所需合同，再检查局部修改对公开保证、捕获、效果和后续使用的影响。改内部算法而保持使用点需要的全部关系，可以保留外部绑定；无法确定保持时只使相应结论未决，不强迫所有消费者读完整展开。若新需求有意改变公开合同，则生成明确合同差异并传播，不以“局部实现”掩盖真实广泛影响。

组合默认从合格调用与边界构建。一个库只给函数名而没有可检查输入/错误/效果规则时，可以保全和正常原生接入，但不能据此完成更强的中立组合承诺。库有完整行为而缺某个优化接口时，允许使用正确基线，不把优化缺项当成表达能力缺项。

摘要与展开都是派生视图；作者只维护定义和真实差异。摘要不足时精化当前使用点或下钻，不追加每个表达式都要填写的合同表。真正新语义不能由接口空实现代替，也不因库不断增长要求AI每次重新阅读全部能力。

## 有限核心、开放定义与版本化作者画像

### 不变的产品目标和五个独立坐标

Gift的公共身份、定义、关系、约束、行为、效果与变化合同不以TypeScript或任何目标语言为定义依据。**TypeScript先行只限定用户产物的首个通用目标次序，不决定Gift自身实现语言；Rust已进入用户产物目标计划，而compiler-kernel的Rust迁移由独立实施合同拥有。** Java、Go、C/C++、Python及其他语言是否进入通用目标或原生接合，分别按真实需求、保持条件和实现证据决定。支持一种语言必须按观察、分析、生成、运行检查和往返分别说明范围，不能用一张品牌列表冒充全部支持。

| 坐标 | 谁拥有含义 | 改变它时不应强迫改变什么 |
|---|---|---|
| Gift实现语言 | 编译器与工具实现；当前仓库采用什么由真实实施事实决定 | 已保存工程的业务含义与公共作者协议 |
| 作者表示 | 结构化作者模块、按需`.gift`计算文本或显式原生前端 | 共同语义身份、要求与当前任务权限 |
| 输入资产语言 | TS、Java、Python等原生源码及各自解释合同 | 不得将其宿主行为悄悄提升为全语言规则 |
| 目标语言与宿主 | 目标程序IR、后端、运行库、ABI和实际环境 | 不能修改上游要求来凑可生成结果 |
| 存储与交换 | 文本、JSON、二进制、数据库各自格式 | 不得因换编码重定义类型、控制流或授权 |

语言无关不等于没有明确的作者表示与前端合同，也不等于所有目标具有相同能力。正常主链是“工程语义作者源→目标无关语义→按目标降低→真实源码”；原生导入是并列入口，不是先让AI把所有要求写成TS再回猜业务。保留原生路径提供生态和不透明资产自由，不以它替代中立语义的直接创作。

### 必须固定什么，什么可以继续增加

版本内固定的是作者文法、核心构造含义、公开基础库合同、六工具协议；开放的是用户函数、类型、谓词、连接、实例和模块。增加一个业务定义，不增加工具或关键字。可选中立计算文本的具体范围见[作者合同](../基础语义/计算基础/文法类型与求值.md#语言无关的作者合同与当前规格)，原生前端单独绑定实际语言版本。

熟悉的调用、字段、条件与函数写法可以复用，但含义以所选作者表示及其前端合同为准。中立Int不是JS Number；中立记录没有隐含prototype/getter；原生TS的number、this、异常和初始化仍保留原生规则。相同外观不是语义等价证据。

### 八类工程构造的边界

**统一抽象的最小实义不是“把所有东西装入关系数组”。** 泛化从两个可比较的具体定义提取共享语义，并明确差异槽；特化固定槽位且只削减允许的自由度；参数化暴露需由实例提供的角色/值/类型；组合建立有方向的提供—消费或控制—数据关系；投影只保留获准对外观察，不宣称被隐藏信息不存在；精化把抽象满足关系映射到更具体实现，并带适用前提；替代以相同公开观察、误差、效果与失败承诺判断，而不是名称或签名相同；复用只建立一个新的使用发生点，不复制定义本体。

每一次组合的输入集合必须明确成员身份和数量、是否有顺序、权限/时间/资源作用域、冲突处理与是否需要独立供应；否则所谓抽象化会把实义问题变成无约束通用 `members[]`、`relations[]`。规范谓词与事实观察的方向不对称：`requires(A,B)` 并非 `provides(B,A)`；“组件宣称提供”也不等于已有受信实现或真正外部效果。对局部可行方案的合成，还必须追溯联合预算、跨实例状态、全局硬目标及共享外部副作用；不满足时保留精确缺件而不是简化目标。


这八类是共同模型的职责，不是八张必填表、八个业务原子或整个程序语言只有八个单词；它们通过[递归封装合同](定义与接口.md#block-composition-contract)构造开放定义，而不是对需求名称作集合并集。程序内部采用紧凑、有作用域的表达式和函数；仅需独立编辑、引用、共享约束或迁移的边界取得长期身份。

| 构造 | 输入与结果 | 不可省略的条件 |
|---|---|---|
| 声明 | 作用域、公开合同与定义体 | 类型、重复名、草稿；声明不隐式执行 |
| 引用 | 名称或稳定对象到实际绑定 | 可见性、版本、歧义、披露；引用不授予权限 |
| 实例化 | 定义及参数到本实例 | 参数含义、求值次数、实例寿命；同配置不必同状态 |
| 连接 | 类型化端口或关系及端点 | 类型、顺序、效果、共同不变量 |
| 约束 | 作用对象、谓词、要求与保证范围 | 要求不等于已验证事实；未知保留 |
| 绑定 | 要求与合格实现、后端或原生资产 | 保持、ABI、版本；偏好不覆盖硬条件 |
| 组合 | 成员、关系、局部定义和实现选择 | 卫生、不同种类的环、联合约束 |
| 输出 | 选定语义根、目标与必要布局 | 精确生产者、合法降低；输出声明不写磁盘 |

### 三种扩展不能都叫新增核心能力

新业务算法、类型、规则和组合由已有构造定义；新分析或后端通过明确接口接入；真正改变基本类型、时间、效果或解释规则时才升级语义画像。基础语法与基础库固定，不把“任意kind字符串”送进执行器。陌生方言可以保全，参与分析和生成须有已绑定的解释。

普通定义不能被新方言的发布门槛拖住；新方言也不能伪装成普通函数以绕过信任检查。当前未计划实现的强宿主能力不影响无外部作用的函数创作。

### 当前结构作者与可选计算文本的分工

产品意图主路径采用[作者基线](../../10-作者与输入/作者源/可替换表示与适用范围-语言定位与作者基线.md#source-profile-selection)选定的AuthorSourceProfile，直接保存定义引用、参数、连接与独特要求；严格JSON是合法profile但不再是语义本体，也不要求其他profile先转成JSON。明确选中的计算画像可以使用其紧凑文本；它与原生作者区域各自保持实际解释和唯一来源。AI只写相关定义与差异，不手填推导所得节点ID、类型树、哈希、后端AST和回执。已绑定符号由解析器处理，不要求每次搜索能力目录。自然语言是提案入口；其解释被接受后保存明确语义，重建不重新询问模型。

中立源、原生源、目标代码是不同角色。每个区域只有一个可写作者来源，其余分析/展开可重建；不是同一逻辑同时维护TS、JSON和Gift三份源码。文件后缀是定位提示，实际解释由明确的画像和源角色决定。

### 固定基础库不等于重新做全部生态

基础类型环境、导入规则和本期序列库面见[基础环境与导入](../基础语义/计算基础/名称导入与契约.md#基础环境与导入)。库不是关键词，不是已发布的软件，也无需注册成工具。缺少绑定时准确诊断；用户可以直接写函数定义，不强制检索替代库。

中立值语义与原生辅助库分开。原生getter/Proxy、稀疏数组、动态迭代器和SameValueZero必须按对应宿主合同处理，或经明确边界解码；readonly不是纯度证明。中立文本的固定环境不能因安装一份库就静默变化。

### 有限性与紧凑性的反例

必须拒绝：已知符号仍让AI查ID；无关库增长改变工具提示；同名原生函数被误当中立算子；纯生成加载整个语言宇宙；更换后端使业务语义变化；依靠原生TS逃生口声称中立算法已通用；没有目标实现却返回空函数。应允许：闭合短函数零工程目录、用户自定义算法与组合、库不合适时直接展开局部逻辑、不透明原生资产被保全但不获得虚假跨目标保证。

## 抽象工程语言与表达载体选择

### 一、中立语义与紧凑表示分别负责什么

Gift必须定义合法对象、关系、类型、行为、约束、作用域、错误及可编译含义。当前语义主线采用[中立作者规范](../../10-作者与输入/作者源/可替换表示与适用范围.md)及共同模型，不把TS语法/类型当工程真相；原生前端仍复用各语言成熟工具。紧凑作者表示不等于手填JSON IR，也不等于换文件后缀即可语言无关。

最小不可绕过约束是：每个可生成输出必须能追溯到本次冻结候选或已采纳语义、明确策略、精确绑定及确定推导规则。候选生成不以正式采纳为前提；实际业务差异不能靠生成时猜测补齐。该约束可以由结构化图、AST、关系模型和版本化协议满足。

### 二、四层分离

| 层 | 内容 | 变化的影响 |
| --- | --- | --- |
| 抽象语义 | 类型、控制/数据/状态语义、引用与约束 | 改义需版本兼容与迁移 |
| 编辑协议 | 查找、声明、连接、替换、删除、校验、采纳 | 接口兼容，不得改变同操作的含义 |
| 作者呈现 | 产品意图采用逻辑结构定义并由各区域SourceProfile承载；严格JSON、计算文本、原生区域及受管结构编辑按实际画像与源角色使用，自然语言形成待检查候选 | 前端表达范围、错误恢复、SourceMap与往返保全；受影响的消费者需重查 |
| 持久化格式 | 分片、版本化序列化、摘要和索引 | 格式迁移，不凭存储顺序改变语义 |

### 三、实际选择

目标主路径采用“AI/脚本的结构意图或局部差异＋可导出、可diff的组合定义与原生供给/作者资产”；首期不以交互式编辑器为前置。默认持久画像与区域来源规则由[工程实体与持久表示](../../10-作者与输入/作者源/工程源/README.md)明确。AI 无需手工拼全图 ID 和后台回执，工具从已观察上下文解析引用、补机械字段、返回候选差异；作者必须仍能看到未决假设和行为改变。

结构意图是当前产品主表示；计算文本是按需选择的区域表示，不承担所有产品创作的前置。不同投影按任务使用。文本适合算法密集、离线审阅、合并、专家快捷输入的场景；表格适合规则表和约束矩阵；图形适合拓扑、状态机和能力连接；中立基础构造可以直接定义独特算法；原生源码是用户可选的作者方式，不是独特算法的必经去处。没有原生作者区域的工程也合法。相同工程可以按区域使用不同表达，但混合并不自动优于单一作者源。

### 四、替代方案与成本

**只用自然语言**：创作门槛低，但每次重新理解会改变含义；应记录解析结果与采纳决定，不能把对话当唯一构建输入。

**直接编辑底层IR**：接口少，但阅读、引用、结构不变量和升级成本可能高。默认提供高层操作，同时允许有相应能力的开发者选择底层入口；不以尚未做收益实验作为禁止使用的理由。实际写入仍按同一任务、验证与权限处理。

**中立文本前端**：在所选计算画像内直接表达可移植语义，承担有限parser、类型/效果检查、格式与错误恢复成本；不是当前产品主面或可信种子的必需组件。语言中立由共同语义和目标保持承担，并不依赖所有作者先写该文本。原生和结构入口仍可用，不强迫存量资产迁写；成本不合理时改进相交表示，不未经需求决策撤销多语言语义主线。

**结构模型作为某区域作者源**：适合显式连接和规则表，可提供图形或机器编辑。必须保留紧凑表达式、结构检索、版本合并及有范围的文本导出。对全部任务强制画图才是被拒绝的方案，并非否决结构作者源；表达能力不足先补适配或保全，不强制转成原生代码。

**JSON/YAML 唯一作者界面**：机器互操作容易，但结构可读不等于语义易写；序列化格式不能代替面向任务的编辑协议。当前只把严格JSON保留为合格结构SourceProfile/机器codec，不把它设为所有产品意图的唯一作者源；YAML也不会因为更易读而自动取得另一前端资格。

### 五、行为不是只有 `fn/if/return`

基础专用解释没有`return`保留词；当前通用组合已按[局部控制合同](../基础语义/对象与控制/控制流与存储寿命.md)提供词法函数退出。此标题中的return仍表示一般行为退出，不能借它为未启用相应解释的旧源增加语法。高层作者能力按实际语义模块/库归属：有限层级/正交模型见[状态反应](../基础语义/状态关系与流/层级状态与事件.md)，有限多重集、连接与聚合见[关系查询](../基础语义/状态关系与流/关系查询与维护.md)；应用级 operation/subscription 则由作者库自行定义并接回公共 Operation/Attempt、持久化和交付合同。事务型应用组合只证明一种组合可能性。它们复用现有类型和表达式，不要求作者写目标代码生成器，也不允许任何一种完整应用形态占据公共高层入口。

行为可以由状态机、决策表、表达式、数据流、受控调用、事件处理、事务协议、领域算子、约束求解目标或绑定的原生实现表达。每种构造必须有明确输入输出、顺序/并发、错误和效果语义。领域构造可以向较低层程序 IR 降低，作者无需先展开所有胶水。

存在一般算法时，开发者可以直接使用中立基础语言定义它，不以模板或原生出口为前提；已有语言实现也是可选择的路线。基础层、领域层和实现策略必须相互接合，而不是为每个算法新增业务关键字。高层作者能力若缺失，应明确归入设计工作，不通过要求改写目标语言将缺口永久外包。

### 六、`.gift`计算文本前端的身份

整数、布尔、条件和函数的现行含义由[语言规范](../../10-作者与输入/作者源/可替换表示与适用范围.md)拥有。局部语法例仅用于说明，不构成第二份文法；不同前端的支持范围和当前采用由作者基线明确。

### 七、验收与反证

相同语义经不同入口应得到等价模型含义；只有语言合同明确为纯装饰的注释/布局才可排除相应业务摘要。文档输出、编译注解或目标空间布局的真实消费者仍参与依赖。新 API 必须测引用错误、陈旧变更、草稿不完整、非法连接、并发编辑和无改动往返。首个 headless 闭环应比较 AI 任务正确率、语义返工、上下文和多轮成本；已选人类客户端实际启用后再验证其交互体验与同义性。不能依据“看起来简单”决定主入口，也不能以尚未实施界面为由阻断当前机器路径。

## 通用表达与渐进具体化

### 当前目标不是只有模板和原生代码两档

保留一般计算底座，在其上提供可嵌套的行为/领域定义；允许同一候选的不同区域处于不同抽象深度。已知大功能直接实例化；特殊局部可以写紧凑表达式、组合已有规则、选定另一实现，或使用原生程序。原生是正常表示与接入路径，不是“没有模板就退出整个语义体系”的唯一分支。实现可复用成熟工具；当前中立计算层本身是高级语言的有界设计，不是机器级低级语言。它还不等于高层工程作者面。

高层可以比低层更短，一般计算也不因此被删掉；其构造和准确限制见理论界限。不同区域仍保有自己的类型、效果、目标和保证范围，不把一个原生出口算成所有高级语义已实现。

### 定义、要求与实现选择不再强绑在同一个大模板里

沿用现有Definition、Requirement和ImplementationBinding，不新建一套元模型。定义说明可观察行为或允许的行为集合；要求说明本实例额外必须满足的条件；实现选择说明采用哪种已合格的布局、算法、库和调度。纯计算不填空的事务和授权字段。

不是所有底层细节都属于用户意图。已由合同确定的值应推导；被项目政策允许的自由可以由固定策略选择；真正影响业务而尚未决定的部分才保持待决。用户要求指定算法或布局时，它成为实现要求，不能继续被优化器任意改掉。Halide的算法/调度分离只提供这种分离的具体参照，不证明任意业务都能这样分离。

一个定义可以引用其他定义、声明局部函数、绑定原生实现或携带可移植表达式。无需全局固定“一级意图/二级意图/原生”的深度，也不要求每次调用展开所有子图。公共合同与局部变化的边界决定需要读取和保留的层级。

### 看展开、改实例和接管源是不同操作

| 作者动作 | 保存的源及保持要求 | 失败或升级分支 |
|---|---|---|
| 查看展开 | 从精确定义/实例/策略产生只读视图；零修改时不新增作者副本，不改变行为 | 未支持的内部只能按可见合同查看，不凭投影视图冒称可编辑 |
| 修改参数或已公开扩展点 | 实例保留差异，重新检查参数与组合前提；子身份不随数组位置漂移 | 参数不足时允许向下具体化，不强迫不断向公共模板增加开关 |
| 局部具体化 | 对可编辑的选定子定义建立本实例拥有的实现选择或局部定义；记录精确基础及对应稳定来源 | 一对多或多对一映射不唯一时，选择更明确的作者边界或返回需选择；不直接修优化后的机器代码 |
| 采用原生或可移植程序 | 明确该区域的作者源、类型/效果/目标合同和需要的保证 | 原生不自动跨所有目标；可移植语义不足则扩展相应画像，不静默退化 |
| 提取复用定义 | 从多个真实结构或新设计建立参数化候选，重绑调用者并核查行为和副作用 | 不靠相似字符串宣布任意算法等价，不为一次短表达强建公共框架 |
| 脱离上游或升级上游 | 脱离即转移作者责任；继续跟随上游则按旧定义/本地差异/新定义做三方检查 | 不承诺既任意手改又无冲突自动吸收所有未来更新 |

局部具体化不等于把整个展开树复制成长期作者资产。可以保存有明确基础和结构选择器的小型差异；若差异持续依赖大量私有结构、频繁冲突或比局部完整定义更难理解，就转为独立局部定义并显式结束那部分自动跟随。相同实例配置不代表有状态实例可合并。删除、重命名、效果变化与共享约束仍可能扩大真实影响，不用“只改局部”掩盖它。

常见高层构造的展开应保持参数求值次数、名称卫生、错误与效果顺序。可分析的保持规则用对应检查，未证性质保留边界；这个协议不要求存在任意程序的等价判定器。用户主动改变行为时形成新需求/版本，不把它误标为保持原语义的精化。

### 再抽象必须有可核对的含义

从自己维护的精确定义、参数和已知展开轨迹恢复紧凑引用，可以在已声明范围内确定完成。从任意优化后程序反推唯一高层意图，不是本设计的普遍承诺。两者不能共用一个“折叠”按钮语义。

AI可以提出新的复用定义与组合规则，其验证和采纳仍按已有合同处理；通过后成为普通库定义，以后重建不重新向模型猜测。类型检查器、宏展开器和用户验证器的来源与共同错误要分别考虑。并非每个提取结果都需签名、发布到市场或生成新服务。

### 简化的验收不是是否提供了大功能名称

至少应设计检查：同一高层定义可正常使用；新增原来没有参数的局部条件无需核心业务分支；只查看展开不增加作者体量；局部修改后不手修派生源码；上游升级冲突可定位；无法压缩的独特程序可以紧凑保留；另一个作者可构造不同的复用定义。相同共享知识下与成熟原生方案比较，而非与故意展开的低层手写版本比较。

这些是现有六类接缝上的具体协议，不是新增第七个万能引擎。首期仍AI/脚本、单个成熟目标、模块化单体；分阶段把本协议的最小完整路径接入原生产链，不等待全语言或全功能库。

## 小程序与局部构造不是另一种产品

过滤、分组、变换、匹配、错误映射、调用连接和控制流定义，同样可以组合成十几行函数；它们不只服务完整应用。按语言规则选择参数、局部状态与实际依赖，必要时以正常原生表达式补充局部算法，不为每个表达式创建全局工程对象。

完整函数、表达式、语句区域和模块的差异在输入与输出闭包，不在能否进入Gift。“工程编译”意味着能够继续组合和保持跨产物合同，不意味着请求必须包含构建脚本、发布流程和全项目对象。临时单位、自由引用、控制退出及晋升持久模块由[单位输入合同](../../10-作者与输入/作者源/工程源/作者工程与输入边界.md#片段函数与工程使用同一输入合同)拥有。

高层组合的逐项语义必须足够明确。例如先过滤再去重，与先去重再过滤不同；保留最后一个值时，结果可以按首次键位置或最终保留元素位置排列，这两种业务不能被同一个模糊的“保持顺序”覆盖。组合定义写清顺序、键等价、回调求值和错误行为，后端才能决定融合循环。类型为readonly不证明原生getter、Proxy、迭代器或回调没有效果；缺少相应条件时保留原阶段顺序或明确所需假设，不为短代码制造不成立的优化。

查看高层、展开局部、使用普通代码和提取新定义，仍沿原渐进具体化合同。片段例不是新的内置行业分支，完整输入到目标示意见短函数完整设计例。

## 需求关系与程序构造分别复用

声明、引用、实例化、连接、约束、绑定、组合、输出是工程构造职责，不足以单独说明“需求如何抽象”。同一组构造可以承载不同的结果关系、状态演化、结构和进展要求；完整要求模型由[跨软件意图合同](跨软件需求合同.md#cross-software-intent-contract)给出。

共同抽象不要求所有需求都成为纯函数：逆关系与不变量不只是字段，时间协议不只是返回值，资源保持也不只是类型。普通函数、原生供给及领域结构可分别实现这些关系；在相同公开合同下可选择较小实现。不强制把每个需求标成block，也不因为未预装高级接口就将普通作者退到所有低层步骤。

“结果允许哪些”与“程序按照什么次序产生它”不相等。一个本来要求左到右求值和首个错误的实现，不能仅以最终正确值集合替代；反过来，原任务只要求一种满足约束的结果且已委派选择，就不强加某一种算法轨迹。作者的独立要求与实现主体各自有接受关系，细化不得伪造或收窄它们。

## 需求、行为、设计选择与实现的关系

需求说明希望满足的结果，行为模型说明被采纳的控制逻辑，设计选择说明某个非唯一方案为何被采用，规则或实现绑定说明如何物化它。四者可以共享引用，不能互相冒充。

```text
自然语言/图形/结构化输入
→ 需求、逻辑、假设和选择候选
→ 校验、冻结候选或按目的正式采纳
→ 明确版本与解释的工程模型
→ 按所请求输出规则推导及目标生成
```

AI 可以同时提出需求结构与行为设计，但必须保留用户要求与 AI 推断的区别。若用户只说“更安全”，系统应将可推导安全措施、待采纳风险政策和未知效果分开，而不是用一个默认模板宣称完成。

确定性规则能推导类型校验、序列化、常规状态更新和其他已建立合同的实现；未决业务条件、数据处理目的和不可补偿权利不能被编译器自行填补。固定政策可以确定选择合法实现，不要求人逐行决定。

已接受工程模型可以含未实现的合同和草稿；编译某个输出时只要求其必要语义与实现闭合。文本、图、JSON 都不是这个要求的替代品。表格可用于复杂政策与设计审查，但表格齐全不证明含义完整。

验收要求与实现候选分开维护。反例是 AI 为通过生成器测试擅自改业务阈值，或从同一错误行为生成“预期答案”。修复应回到需求来源与独立判断，不把全部生成测试当用户需求的真值。

## 作者语法与前端支持边界

当前基础文法由[中立作者规范](../基础语义/计算基础/文法类型与求值.md#闭合结构文法)唯一维护。一个前端的采用需要产生式、消歧、绑定、类型/效果、动态含义、库环境、错误及编辑接合共同成立；不能从一个kind名、范本或关键词数量推导支持。

基础语言支持一般程序，不等于全部工程领域的作者形式都已完成。新前端按[D02](../../90-治理与参考/决策/设计理由-产品作者与语义.md#d02-中立语义与可替换作者表示)作明确采用决定，并声明其同义范围、迁移和源码保持。当前不交付嵌套作者SDK。不同表面可以共用语义，但不按示例拼写自动开放未实现入口；作者成本在相同库与保证条件下比较。

## 算法、计算结构与作者应用组合的分工

高层工程表达有不同方向：状态、关系、流、数值、形状、访问映射、边界、递推、归约与调度都可以是第一类公共语义；完整业务应用则由作者把这些语义与普通库、Provider、权限和持久机制组合出来。不能用多写几个 `fn` 替代真正的新语义，也不能靠一个预制“业务声明族”吞掉所有应用。已有数值/效果/资源规则不重抄，完整的作者—目标—变更合同见[计算结构与算法实现设计](../基础语义/计算基础/计算结构与算法.md)。

普通新算法仍用现有函数、类型和用户定义组合表达；高层库可以保存独立的计算结构，并提供正确的展开/分析/降低。没有“算子目录预装全世界”前置，也不能把巨大内核硬编码为一个用户不可修改的原生调用。实际不足时区分表达不足、库合同不足、后端不足和目标能力不足；不能全部叫“业务缺信息”。

规则表、持久对象、应用操作和订阅都可以由作者库定义；Gift 不把 `decision/aggregate/operation/subscription` 固化成全局产品关键字。若某作者模块采用这些词，它们的含义由该模块 identity/revision 固定，并接回公共类型、效果、Operation/Attempt、持久化和交付合同。一般函数调用、循环、GPU 线程和事件循环不因同名词而取得现实操作身份。未选能力与当前无需部分的处置由[适用性协议](../../70-工程系统与演进/演进与实施/适用性与能力协商.md#不需要部分的处置与退出协议)拥有。

## 封装、类库与开放定义的共同位置

开放定义通过[库规范](模块封装与复用库.md)提供私有默认、opaque类型、包门面、实例、公开合同和升级。它不把复杂行为封成无法修改的字符串。类型修饰的语法由语言规范维护；其他表达式和作者自定义语义模块按各自合同解释。

一个高层意图可以由普通函数、契约、关系、结构计算或作者定义的应用操作形成公开定义；使用者传入差异，编译器记录展开与来源。库内部仍可自由编写中立算法，客户端通过公开操作使用它。源码可得时，有权创作者可以建立局部派生并明确新的维护责任；只查看展开不是改变原库，也不赋予外部代码私有类型权限。

类的封装、实例方法、接口多态和实现继承分别选择。当前用模块/opaque、实例参数或函数记录和明确资源满足相交能力；不因没有class关键字就说没有类库，也不把这些机制冒称已实现全继承和反射。原生类继续按其真实语言语义适配，公共中立规则不依赖Java/TS类对象。

固定表达规则、标准库、领域库与产品任务分开。首个计算库是验证载荷，不能消除工程意图、共享约束、真实作用和演进；同样，任何完整应用组合协议都不是普通算法的前置。

## 需求复合定义与实现主体分别闭合

`design`仍是同一个Definition的有类型需求角色，`use`复合后对外仍是可引用需求定义。运行函数、状态/关系模型和实现方法并列提供相应实现；复合闭包不等于所有require可计算为普通函数。产品作者没有提供算法体时不能自动判需求不完整，应区分含义、证据、方法和目标缺额。默认实现缺额由受委派供给承担，不将其展开为产品源的手工维护负担。原block及管脚的共享/隔离/状态/效果/寿命条件照旧。

## Gift 统一抽象演算：从具体业务区别到可替代的开放能力（当前采用的设计）

### 1. 抽象的对象、产物与不能抹去的信息

本节唯一拥有 `abstract / instantiate / specialize / generalize / compose / refine` 的**定义层意义**。作者如何书写一份具体 `intent:goal` 归[意图作者源](../作者语义/通用意图语言-意图源与语义组合.md#gift-intent-abstraction-application)，多个已采纳目标的系统合并归[跨软件需求](跨软件需求合同.md#gift-intent-composition-algorithm)，实现方法与搜索归[实现解析](../../30-实现解析/实现选择/实现解析与候选资格.md#gift-abstract-realization-selection)。本节不另建可写的业务模型、方法目录或持久 IR。

抽象输入不是“某行业的名词”或裸代码，而是**一组带主体、上下文和来源的可观察行为关系**。至少分离：身份/类型；适用输入；前置与环境假设；事实/观察及其完备性；结果及错误；过程、安全和进展；时间/资源；规范主体与授权；改变后必须不变的帧；证据强度。不同领域的输入只有一部分相似时，允许产生带显式差异槽的抽象，不允许把差异删除后自称等价。

为固定讨论，设一个实例规格 `S` 在环境假设 `E`、观察投影 `O` 下允许的轨迹/历史集合为 `Allowed(S,E,O)`。`O` 可包括返回结果、错误、可见状态、交互、物理作用、规定时间区间、权限决定，及必要时的**多个运行之间的关系**。这只给出安全性质的集合视图；输入接受域、正常功能与进展，及证据/规范层还需要独立义务。`Allowed` 不是总可计算函数，不能因为写下集合符号就宣称已可判定任何新语义。

跨领域公共模式的 `sharedClaims` 有**两条互斥承载路径**：有限谓词形状仅用于已支持的 `achieve/maintain/avoid`；规范义务、权限陈述、无界时序、优化与其它完整合同引用现行 `RequirementDefinition`，通过 `requirementRef + roleBindings + scopeRef` 绑定，解释版本及权限归原 owner。这样不复制一套新 Requirement 文法，也不把这些意义降为布尔；仅 Schema 结构接受不等于实际解析/资格通过。

一个模式（`Pattern`）是既有 `Definition` 中的**参数化公共含义**，而不是固定业务关键词。它至少包含角色与类型合同、可观测的共享要求、环境/时间范围、必选差异槽、约束/组合政策和源引用；具体行业通过绑定与特化实例化。它可以有零个、一个或多个 Method 供应，**模式存在不保证实现存在**。模式也不自动具有真实实体或权威：`Resource` 作为语义角色不是银行账户、病床或 GPU 的事实来源。

### 2. 八种操作及其精确输入/输出（语义接口，不是强制 JSON 关键词）

| 操作 | 输入与输出 | 关键合法性条件 | 失败与不可推得结论 |
|---|---|---|---|
| `define` | `(Owner, Namespace, MeaningBody, SourceRevision) -> DefinitionRef` | 签名、身份、解释范围、依赖、版本与可观察含义完整；名字不代替 Meaning | `NeedsMeaning`；定义不产生 Method |
| `abstract` | `(S₁…Sₙ, SharedObservation, CandidateMapping) -> PatternCandidate` | 每个输入到公共角色的映射保留选中观察，差异成为受约束的槽；共享规律有依据 | `UnsoundAbstraction`、`NeedsEvidence`；有限样本一致不等于普遍规律 |
| `instantiate` | `(PatternRef, RoleBindings, SlotBindings, Scope) -> DefinitionUse` | 类型/量纲/身份域、缺省来源、必填槽、观察投影逐项核对 | 未知槽保持 Need；绑定不自动激活世界资源 |
| `specialize` | `(DefinitionUse, AddedConstraints/StrongerClaims) -> SpecializedDefinition` | 声明适用域缩小或要求加强时，原合同与新增差异的兼容与继承方向明确 | 强化保证不等于已有 Method 仍合格；覆盖原安全规则要新版本/显式替代 |
| `compose` | `(AcceptedUses, JointContext, Policy) -> JointRequirementGraph` | 身份对应有权、范围/时间/权限及共享资源对齐，所有硬要求统一解释 | 有冲突→见证；无冲突不证明可实现；顺序、并行、规范组合不能一律取并集 |
| `refine` | `(AbstractContract, CandidatePlan, Environment/Target) -> RefinementObligations` | 具体方法完整接受合法输入，保持目标结果/错误、框架、进展、资源、效果、权限条件 | 仅类型匹配或源码构建不等于精化完成 |
| `realize` | `(QualifiedMethodBindings, Target, AssemblyPolicy) -> ArtifactPlan` | 依赖/ABI/目标操作全合法，选定合格实现供给，来源与生成区唯一 | 无 Method→`NeedsMethod`；缺 Target→`NeedsTarget`，禁止模板补洞 |
| `observe/verify` | `(Claim, Readback, Assumptions, EvidenceMethod) -> ScopedVerdict` | 观察来源、覆盖、时点、独立性和对具体命题的效力明确 | 不能以模型预测或生成代码充当已发生现实效果；未知仍未知 |

`generalize` 是有证据支持的 `abstract` 推广，不是“把字段换成更笼统的字符串”；`bind` 是 `instantiate` 的名称/角色接合，不创造含义；`decompose` 是为实现搜索建立可证明的子义务，并非作者必须重新手写整份意图。

### 3. 抽象正确性的四组义务

**A. 角色/领域保持。** 角色映射必须是一组带类型、单位、身份规则、重数和时域的部分函数/关系。不能把 `SeatId`、`BedId` 和 `GPUAllocationId` 因同为字符串而合并；可以声明它们分别实例化共同的 `AllocatableResource` 角色。绑定不要求实体同构，只要求选定公共义务的每个参数有正确解释。一个角色可以对应集合而不是单一对象，此时必须明确其聚合及重数语义。

**B. 观察保持。** 设 `α` 把具体情形映射到公共模式，`γ` 表示该模式允许的具体化集合。对选定观察 `O` 和适用环境 `E`，要求每个被声称覆盖的具体情形 `s` 落在 `γ(α(s))` 且不失去已声明的公开区别。若公共模式允许比原场景更多的行为（抽象过宽），则实例化后的**领域特化条件**必须重新排除那些额外行为，才可声称原具体合同得到满足。形式化地，一个候选实现 `m` 应满足 `Beh_O(m,E) ⊆ Allowed(S,E,O)`，并另外履行输入覆盖、正常产出、进展与效果结算；仅 `Beh ⊆ Allowed` 不能让永远沉默的程序过关。含时间公平性、规范义务、概率或非干扰的合同有各自的判定器，不可伪装为有限状态包含检查。

**C. 差异保持。** 生成模式时按每一输入场景记录 `common`（明确相同）、`parameter`（类型化可变）、`extension`（独立的新义务）、`conflict`（不可同时成为同一默认合同）、`unknown`（无足够证据）。这些是本次分析状态，不是必须长期持久的并行数据表。一个场景允许超售、另一个禁止超售时，不能把超售政策塞成无定义的 `optional` 然后预设为 `false`；需要明确是模式参数、特化约束还是根本不共享该模式。

**D. 替换/演进保持。** `Method A` 可替换 `Method B` 只在本使用点的输入域、返回/错误、进展、帧、时间/资源、安全及受权效果均得到覆盖时成立。新模式版本改变 Meaning、作用域、默认或观察时，所有具体 `DefinitionUse`、已选方法和相关证据要沿读集精确失效；显示名称相同、文档仍在或散列相同均不保证跨主体授权相同。

### 4. 跨域资源分配的可复算抽象推导

三个输入：床位分配、具排他策略的 GPU 配额、指定座位销售。候选角色为 `Requester / Resource / Quantity / Qualification / Allocation / Authority / ValidityInterval`。共同硬关系先写成带条件的约束，不预设所有 GPU 必须独占：当政策选择 `nonOversubscribed` 且同一容量域 `d` 的有效占用可按相同单位相加时，`Σ qty(activeAllocation(d,t)) ≤ capacity(d,t)`（对合同规定的 `t`）成立。容量可随时间变化，且在并发下要规定谁负责原子准入。若是具体座位，另加入 `∀ seat,t: cardinality(activeExclusiveOwners(seat,t)) ≤ 1`，总容量约束单独并不足够。

差异槽不能省略：病床有资格/医疗机构可用性和可能的人工确认；GPU 有抢占/分时/超售或亲和性；座位有具体 SeatId、售出与保留的不同效力、支付结算/超时规则。各自的“确认”可能是本地模型完成、签发许可或外部服务承诺；证据和效应不同。抽象只复用共同的合同逻辑，不能把外部承诺也泛化成 `set confirmed = true`。

正确的实例化必须逐项确认：单位换算不会改变容量；来源签发资格；时间区间重叠如何计算；失败后的占用是否持续；重复请求/并发竞争的幂等身份；覆盖旧状态还是追加记录；拒绝、取消和释放改变哪些义务。只要任意决定会改变业务允许行为且没有有权来源，返回对应 `Need`。若只在当前有限模型里验证，就标为 `ModelOnly`，不可升级为真实可用性保证。

### 5. 从业务模式到复合能力、再到完整系统

`BusinessCapability` 不是一个新核心名词枚举，而是具稳定作者身份的**目标/合同组合根**：`{publicInputs, publicOutputs, referencedDefinitions, hardClauses, policy, participantRoles, effects, compositionEdges, observation/assuranceRequirements}`。引用已有意图时只保存引用、此次绑定和差异，不再复制原条款。能力可以是原子意图的直接暴露，也可以有子能力关系。子能力共享资源或效果时，不能由“全部子项局部合格”推出整体合格。

`SystemIntent` 是完整交付范围的根：业务能力集合、跨业务不变量、交互边界、数据及外部协议、安装/迁移/部署约束、运维与故障策略、主体授权和最终验收。系统既能引用一个完整现成能力，也能引用多个领域能力；**不要求每一个意图强制经历固定五次逐层转换**。对没有 UI 要求的 CLI 工具不凭空生成界面；对指定无障碍交互的业务不能只发 REST API 冒充整体交付。

一个完整系统存在三类不自动合并的联合合同：逻辑一致（要求不冲突）、实现可行（在方法/资源/目标/环境下存在满足方案）、运行可交付（真实授权、作用、恢复和观察到位）。要把这三类分别返回、记录来源，禁止从第一类自动推得第三类。

### 6. 失效、反例、未来扩展和停止判据

- **词汇相似、语义不等：** `paid` 可以是授权、扣账、清算、用户声明；必须由同一观察者/承诺与相同的时域区分，不能只抽象出布尔值。
- **局部正确、联合错误：** 资源容量为 1 的两个请求分别有可行预留方法，合并超过容量；联合实例不能复用任何局部 PASS 作为整体保证。
- **规范与作用不等：** `permit(ship)` 只说明某主体在某政策下被许可，不产生仓库操作凭据或承运方接单。
- **抽象过宽：** `Stock` 可为离散件数、连续重量、可借款额度；未固定单位、缺货/负值语义或分配策略时，“库存不能为负”不是所有领域的默认公理。
- **相同结果、进展不同：** 任务一直等待不会违反“不得超分”安全条件，却不满足“稳定有效请求最终得到明确决定”的进展承诺。
- **事实不完备：** 没看到付款记录不能默认未付款；看到两份有冲突签名的记录也不能默认任选其一；事实模型应保留支持/反支持、来源及完整性范围。
- **目标语义不决定唯一源码：** 两个合格实现的不同内存布局、数据库或调度实现可以同时合法；作者未限制的内部选择由资格和稳定成本策略决定。

当且仅当新区别**无法**通过现有公开构造、类型化角色、约束、领域 Meaning/Method 或现成外部语义模块保持，才提交最小 Kernel 语义晋级候选。候选必须记录不可表达的精确反例、最小新操作、解释/组合/目标/证据消费影响、迁移及退出方案。新增具体行业名、概念数量增长、代码变复杂，本身不足以晋级内核。

## 可复算的抽象提出、特化与精化义务

`abstract(examples, observationScope, environment, budget)` 返回**候选及其待履行义务**，不能直接写入产品作者原件。真正的抽象不是结构相似度：先检查是否有名义类型、量纲、身份域、事实来源、Norm/Grant、时间/进展及可观察失败的保真映射。仅业务名称相似、三个案例恰好都输出 `true`、或仅在当前状态有效，都不足以采用公共模式。

建议给逻辑内部 `PatternCandidate` 携：

```ts
// 施工用概念数据；不是本轮新增公共持久 Schema。
type PatternCandidate = {
  proposedRoles: readonly {name:string; typeRef:string; cardinality:string; unitRef?:string}[];
  commonClaims: readonly {sourceRef:string; scopeRef:string; observableRef:string}[];
  variationSlots: readonly {name:string; ownerRef:string; required:boolean; typeRef:string; reason:string}[];
  mappings: readonly {exampleRef:string; roleBindings:Record<string,string>; assumptions:string[]}[];
  proofObligations: readonly {claimRef:string; verifierRef?:string; verdict:'pass'|'fail'|'unknown'|'unsupported'}[];
  negativeExamples: readonly string[]; environmentRef:string; observationRef:string;
};
```

严谨的采纳流程：①冻结所有例子的 Definition 版本和观察域；②按类型/单位/身份建立候选角色对应（不得只按同名）；③在该环境中求公共可观察关系，不抹去错误/进展/Frame/权限；④将各例独有规则划到必需差异槽、局部扩展或实际冲突；⑤校验每个被采纳实例 `Concrete → Pattern` 的角色映射是否语义保持；⑥寻找未参与归纳的新例与最强反例；⑦未获得解释/证明的性质留在 `NeedsMeaning/NeedsEvidence`，而非默认共同；⑧有权作者采纳后才形成一个 `DefinitionRef`；⑨原例与模式均保留来源、可撤销和升级边界。预算不足时仅给可复核候选，不声明推导出了“所有可能业务”的公理。

**形式方向：**相对同一环境 `E`、合法输入与高层观察投影 `O`，具体实例 `C` 若声称是模式 `A` 的有效实例，须证明该实例的可观察行为满足模式允许的关系，且其可接受输入域、异常、进展、保持条件均符合所声称映射。方法 `M` 实现已接受实例 `I` 时，不仅需 `Behavior(M)|O ⊆ Allowed(I)`，还须 `pre_I ⇒ pre_M`、正常输出覆盖、`post_M ⇒ post_I`、相同作用域的 Frame、进展、成本/资源硬界与 Effect/Grant 资格。这里蕴含式以合法输入和已声明环境假设为条件，不是对未知世界事实的形式证明。

**特化规则：**在保持原公开要求的前提下增加条件，可得到更受限的可用域；不能无证据扩大合法输入域、偷偷放宽安全禁令、删除规范义务或把世界来源改成字符串常量。若变化改变公开意义，应建立新 Definition revision 并传播影响，不能称之为“纯实现替换”。

**三类分歧必须保留：**病床的权威批准、具体座位的逐项排他和 GPU 的抢占/超额策略分别使用领域差异槽；不可超额和超售两种资源政策不是同一个强合同；法定义务来自适用权威而非同一个容量数学式。除非有完整前提、观测、错误与恢复对应，禁止抽成所谓万能 `reserve`。

`semantic:pattern-use` 的正式字段设计只由[结构化作者源](../../10-作者与输入/作者源/结构化源码.md#gift119-pattern-use-author-encoding)拥有：Pattern 仍唯一维护公共角色/硬义务/变化槽，此 Use 只维护绑定与有权选择，实例化派生结果不成为第二份作者源。Gift118 独立 Pattern Schema 不因 Gift119 增添 Use 而改变已发布含义。

## 抽象实例化的基数、类型精化与条件义务：严格的双阶段合同

本节**唯一拥有公共抽象到具体业务对象的语义保持规则**；结构编码由[作者源](../../10-作者与输入/作者源/结构化源码.md#pattern-use-versioned-encoding)、施工接口由[第28章](../../70-工程系统与演进/工程构造手册/28-抽象到业务系统-统一实施闭包.md#pattern-elaboration-implementation)拥有。Gift119 中 `semantic:pattern` 支持 `one/optional/set/bag/sequence`，但当时 `gift.semantic-pattern-use/1` 只能提供单个 `objectRef`，因此**不得声称这一历史候选已能实例化所有模式**。新 `gift.semantic-pattern-use/2` 是显式不同的**设计阶段作者编码**；未发布的生产 Reader 不能因为本文增加该编码便默认为支持。旧 `/1` 保持旧含义，只有确为 `one` 的实例在经锁定模式校验后才可显式迁移。

### 角色绑定代数：不能把五种基数压成单对象或布尔

| 抽象角色基数 | 使用者提供 | 语义不变量与拒绝 |
|---|---|---|
| `one` | `kind=one` 与一个 `object` | 必须解析到一个有类型的实际对象；`objectRef` 字符串本身不是身份或类型证据 |
| `optional` | `kind=optional`，`object=null` 或具体对象 | 缺席不同于不存在/未知；对缺席角色直接使用普通一元谓词必须拒绝或使用具有 Option 含义的 Requirement |
| `set` | `kind=set` 与一组 `members` | 去重按**解析后的稳定规范身份**而非名字或相同的 JSON 字节；顺序没有业务意义；一元谓词不得自动逐成员扩展 |
| `bag` | `kind=bag`，每个成员有精确十进制正整数 `count` | 同一规范身份只能出现一个计数项；量由明确字段表示，不能用 JS Number 截断；不把多重集改成集合 |
| `sequence` | `kind=sequence` 与有序 `members` | 保留顺序和重复出现；不能把序列排序/去重后继续声称相同的公开行为 |

以上是显式基数模型，不是五种固定业务类型。合法的模式定义允许任何基数，但实例化必须有**相应语义消费者**。例如有限 Meaning 的 `resource:CapacityResource` 是单对象谓词，不接受 `set<CapacityResource>` 的静默展开。若需要集合量词、迭代、聚合或长时序意义，使用相应已定义的 Requirement，保留其 owner、量词、时域和失效条件。

### 类型化精化必须有真正的见证

模式角色 `typeRef` 是公开抽象能力的名义要求；实际对象类型由**锁定的对象读取器**提供，而不是用户在使用处写一个可以自证的 `typeRef`。类型完全相同时直接检查；名义类型不同（例如抽象 CapacityResource 与 HospitalBed/GPUQuota）时，必须有经独立解释的 `typeRefinementRef`，并证明针对被消费的操作与不变量保持对应观察。字段刚好同名或同为整数不构成精化。`unitRef`、`identityDomainRef` 变化还需要各自的准确映射和证据；不能以一个万能类型见证吞掉容量单位和对象身份。

精化义务是带来源的有范围命题：实际类型/对象身份、抽象角色、方法/Meaning 所需观察与前置域、转换、异常、时间和资源差额、独立资格。调用者自己提交 `verified: true`、一个 URI 或一个 ref 字符串均不能创建该证据。未取得时返回 `NeedsTypeRefinement`/`NeedsUnitRefinement`/`NeedsIdentityDomainRefinement`；不默许向下转换。

### 差异、条件与观察范围不允许通过忽略实现

模式的 `variationPoints` 定义**全部必须由领域选择的差异槽**；使用处必须逐槽提供锁定 `definitionRef`、相符的 `typeRef` 与选择来源。`selectionSourceRef` 是可追踪来源，不是颁发的权限或现实事实。`authority`、`observation`、`resource-policy`、`time` 等槽各自进入本权威拥有的资格或 Requirement 检查，不能被编译器合并成任意配置文本。

历史 `whenVariation` 只携带一个名称，**不足以说明真实布尔条件、触发时间和评价者**。在取得限定解释以前，编译器不得默默忽略这个字段，也不得把它当作“只要槽已绑定就无条件成立”。新消费阶段应返回 `NeedsQualifiedConditionalRequirement`；具备条件语义的作者改用有真实解释的 RequirementRef，保持触发、终止、例外与观察条件。用户不能因为“差异槽已选中”而免除未附加的硬义务。

模式的 `observationBoundary.worldOrModel` 与使用处选择的真实观察域必须一致。`explicit-model-only` 的模拟不能用一个形如 `world:*` 的名字提升成现实执行资格；`external-observer-required` 必须由真实观察供给和有权主体履行。初步展开**只产生带来源的义务**，不产出“业务已实现”“授权已获得”或“Method 已合格”的结论。联合组合、实现选择、目标覆盖、现实执行和保证继续由它们各自的 canonical owner 完成。

### 静态展开的后继

输入：固定作者修订、锁定的模式 Definition/Meaning、对象身份与类型读取结果、经选择的差异定义、观察选择和可信外部精化判定器。输出：按原共享 Claim 的稳定顺序派生的具名义务、类型化角色及差异、实际读取集、来源摘要、仍待完成的资格。任何未决引用/不兼容必须返回准确 Need。对于 `requirementRef` 形式，保留其**原 Requirement 身份**，只绑定实际角色和作用域，交给原 Requirement reader；绝不根据名字或一段配置字符串猜测规范义务、时间规则或外部副作用。具体算法与负例见[施工入口](../../70-工程系统与演进/工程构造手册/28-抽象到业务系统-统一实施闭包.md#pattern-elaboration-implementation)。
