# Gift 通用意图语言：作者语义主源与开放组合


### 有限公式与领域判定

声明公式可由 `call(meaningRef,roleBindings)`、非空 `all`、非空 `any`、`not`、`implies`、局部有作用域`quantify`以及基于明示Clock/Window的`temporal`组合；这些只能连接经解释的谓词，不能变成偷偷执行TypeScript表达式的`eval`。带量化的要求须引用有型集合域，`forall/exists/exactly/atLeast/atMost`的判断必须保留域完整性、重复语义与作用时段；不完整/无限域不能任意展开成已全部检查过的有限数组。`not`是相应证据Profile的否定运算，不是把“没有记录”补成负证据；`implies`表述逻辑蕴含，不表述时间先后、权限或因果。

关系、事件、操作、度量可具有不同返回对象及证据能力，不要求强塞进单一Bool谓词。Meaning提供者必须定义输入、外延与内涵的必要边界、失败/不适用、版本、法域/上下文、事实/规范/估计的区别及是否可信。领域语义开放不等于允许没有解释器的字符串决定生产逻辑。


### 作者何时必须明确需求，何时可以默认

作者目标、禁止、法律/业务义务、安全条件、允许的成本/性能取舍是受其接受权限控制的选择；所有生效Hard要求必须保留来源和约束对象。Soft需要明确量纲和比较域，只有硬约束满足才参与排序。若系统预置某套行业默认，必须是有版本、授权适用且可查看/覆盖的Meaning/Policy供应，不能默默创造核心业务规则。

接受记录不是每次都要外部“签证”，也不是测试证据。作者可以通过明确保存或确认接受自己的工程目标；如果一个组织有审批权限，则该工作流必须遵守真实组织授权。应区分**源码中存在的要求**、**有权人接受的要求基线**和**编译时本次激活的义务集合**：删除已接受目标不能凭剩余JSON结构正常而宣称全部义务已满足；如果用户正式撤销该目标，旧义务依撤销生效范围停止对未来修改的约束，但不抹去已经发生的外部效果。


### 规范、事实、决定和有争议证据必须有不同真值域

一种现实陈述可能为真、假、既有支持又有反证、或既无支持亦无反证；另有根本没有取得领域解释资格的情况。后者不能直接降为证据中的 `NEITHER`。`permit` 描述某个规范来源的许可，不能取代安全认证或某次执行的真实授权；`oblige` 需要准确主体、受益者、触发条件、履行/违约观察与期限；`prohibit` 和例外必须明确适用层级、权威和有效期间。不同规范冲突不能由 JSON 数组次序、普通优先级整数或“最后一条覆盖”随意裁决。

多根业务的联合要求不能从根自己声明的 `requirements` 推出“原先全部承诺”。必须有独立接受事实：谁接受了什么条款、哪些约束仅为候选偏好、哪个根或全局Scope承受该义务。对 `forEach` 和 `exists` 要固定量化域、唯一性/Bag口径和完整性来源，空域上的全称成立与开放域中未观察到反例绝不可混同。权利主体不同的接受记录不能因为联合优化方便而被一个总分覆盖；无法比较或违反不可补偿底线时输出剩余权衡与冲突归属。


### 时间与时态

- 时间点、持续时间、业务日历、wall-clock、单调时钟、事件时、处理时和逻辑序号不能混用；每个比较明确时钟来源、时区、精度、漂移、开闭端点与转换。
- 目标Horizon可限定为模型步骤、某事件之前、实际时钟期限或无界；一次运行样本不构成无界性质保证。
- 事件延迟、乱序、重放和未来补录会改变“目前已知是否发生”的判定；不完整观察不能自动推出历史没有发生。
- Deadline、Timeout、Lease到期、Token/Grant撤销和业务义务逾期分别是不同机制；一次网络超时不表示受控的对方工作没完成。
- 状态停留、每秒处理、资源占用、消息TTL和用户会话寿命都有自身起止/恢复条件，不能由全局单一`currentTime`对象包办。


### 设计判定

Gift 的目标是使开发者以尽可能少的**不可推导业务决定**，精确地规定什么应存在、发生、保持、禁止、优化或由谁处理，再由可证明适用的专业语义与 Method 实现为普通软件。当前统一作者语言是 `gift.project.json` + `*.module.json` + 按需原生源码；不需要第二份自然语言程序、工作流 DSL、万能意图 JSON、全局“世界表”或持久中间表示。

“表达所有意图”必须有准确量词：

- 对**能够有限陈述并具有明确定义的领域或计算意义**的意图，作者模型必须能够保留全部必要的主体、对象、量词、时间、身份、权威、逻辑与结果区别，并且能组合；不得因为核心枚举没预置行业名词就无法写入。开放 Meaning/扩展和可计算函数用于覆盖这些未预置领域。
- 对**尚未定义意义**的自然语言、未知外部对象和矛盾要求，可以记录原主张与缺失条件并请求解释，但不得宣称已有唯一、可执行语义。
- 对**意义明确但没有任何足够的实现方法**的目标，表达不等于实现。某些目标甚至不可计算、不可满足或受真实物理/法律/权限限制；不能保证任何有限系统总能自动给出正确高质量程序。

由此取消“27个 Definition Kind 已经覆盖宇宙全部意图”以及“必须通过增加更多 Kind 才能覆盖新业务”的两种错误说法。Kind 是**消费入口**而非领域语义全集；核心约束应具有开放扩张能力，同时不给任意未解释 payload 自动签发意义。


### 一个意图必要的语义维度，不是另一种万能对象

一个具体意图在**所在专业结构**中，按需要保留下列正交信息；没有理由让每个意图填一张固定大表：

| 维度 | 业务上要回答什么 | 真正拥有者 | 不能被偷换的含义 |
|---|---|---|---|
| 指称 | 哪个类型、主体、对象、集合、事件或过程 | Type/Meaning/Source | 名称与现实对象、类型与实例不同 |
| 关系/命题 | 哪些事实成立、如何判定或比较 | Meaning/Condition | 观察不足、支持/反证冲突和不存在分别处理 |
| 模态 | 达成、保持、避免、履行义务、许可、偏好 | Goal/Norm/Requirement | 愿望不是指令，许可不是 Grant |
| 量化 | 对一个、全部、存在、恰好数量、集合成员 | Requirement/Type | 开放集合的 `all` 需要范围和完整性来源 |
| 范围 | 哪些租户、实例、用户、根、法域、环境 | Source/Scope/Policy | 同一逻辑定义在不同使用点不共享范围 |
| 时间 | 先后、期限、持续、窗口、事件时间/处理时间 | Time/Workflow/Event | 截止期不等于一次定时触发；没有全局理想钟 |
| 因果/执行 | 由何输入触发何业务行为、结果如何回传 | UI/API/Workflow/Effect | 声明按钮不等于已请求/完成效果 |
| 约束 | 不变量、允许值、容量、资源、权限 | Requirement/Resource/Policy | 局部满足不等于联合可满足 |
| 不确定性 | 未知、冲突、假设、估计、观察局限 | Meaning/Observation/Assurance | 未知不等于假，冲突不等于平均取中 |
| 实现选择 | 必须固定算法/库/环境还是允许候选竞争 | Method/Target | 未选实现不等于不知业务意义 |
| 现实证据 | 供应者、签发人、是否发生、可追溯修订 | Runtime/Observation/Source | 声明证据链接不等于已取得可信证据 |

这些**维度不是需要持久化的 IntentBase 类，也不是一份总集合**。`intent:goal` 拥有模态要求；`domain:meaning` 拥有专门关系；`req:composite` 拥有量化/联立；`workflow:plan` 拥有过程；`security:policy` 拥有规范；它们共享可寻址的Type/Scope/角色和绑定合同。


### 构造完备性的四个闭包

**语法闭包**：给定合法的模块与类型，能用定义/使用、嵌套有类型关系、角色绑定和导入生成更大的、仍可解释的系统；引用必须解析且类型吻合。不能靠同名或自由字符串把不同Kind组合起来。

**意义闭包**：组合前的关系各有精确解释和使用范围；组合后保留每个成员的身份、前置、权威、时间、证据资格与结果空间。对可证不兼容给出冲突，对未知给出明确Needs；不通过隐式默认、丢失约束或覆盖前者“完成”组合。

**行为闭包**：输入/事件/定时或明确调用，到流程/状态转换，再到纯计算或效果端口，每一步有确定的数据来源、控制交接、并发/取消/恢复和结果去向。运行行为和观察结果可以是非确定或失败，但它们的允许集合与后继含义必须明确。

**工程闭包**：被选根及其跨根共享义务落到 Method 能力和 Target 构造，得到公开接口、源代码、依赖、配置、迁移、安装/运行入口与受控修改。若供应不全，报告精确缺口而不生成占位函数冒充可用代码。

四者互不代签。领域开放定义可以使语言不断表达新意图，但是否可判定、可合成、可履行仍依赖真实资源与Method。


### 通用逻辑并非万能自然语言解释器

公共逻辑只负责明确的连接词/量化与解释义务：`all/any/not/implies` 和同一意图Body中增补的 `quantify/temporal`、条件应用、合取冲突、否定范围、存在性及计数的封闭域要求、时间上下文、真假支持/反证。具体业务谓词 `DocumentSaved`、`InvoiceSettled`、`PatientRecovered`、`RouteSafe` 的含义、观察与签发者并不由逻辑词提供，必须由有类型 Meaning 或带有可解释合同的原生/外部供应提供。

事实评价允许 `true-only`、`false-only`、`both`、`neither` 四类证据状态；无资格或无解释独立于这四态。对`oblige`不能仅用某布尔目标表达：需要债务主体、触发、履行、期限、解除与责任；`permit`限制合法请求，不等于真实授予；`prefer`表达软选择目标，不能冲破硬禁止。没有全局唯一的“当前世界真值表”。

### 表达范围与可判定范围分别开放

用户既可用结构化开放 Meaning 描述一个可判定的局部性质，也可提出涉及未知人类意图、无限未来或未列举对象的目标。前者在具备解释者和封闭输入域时可形成确定判断，后者仍可保留为有类型的规范/观察/研究目标，但不一定存在可终止的自动判定方法。将“不能判定是否达到”误作“语言不能表达”，和将“句法能容纳量词”误作“系统会求解所有无限量词”，都是错误判断。

一个新业务的最低解释者需公开名义对象/角色、谓词签名、实例化的作用域、是世界事实还是政策规范、需要什么观察或外部能力、缺失时的明确结果以及哪些变换保持其意义。程序可机械判定的仅是已具备前提的那部分。对因果、法律、社会评价等领域，Provider 可以给出受限制的估计/建议和证据缺口，但不能因为写入统一 `domain:meaning` 就把争议实体或开放世界真值变成定理。


### 用户提出“任何意图”的必要新增设计边界

仅有非计算业务 Profile 不足以表示**全新算法的程序本体**，例如自定义哈希构造、语言解析器、优化求解器、数值积分或任何前所未有的变换。这属于同一作者语言已纳入的按需计算责任，由 `core:function`、`core:constant`、`core:type` 和明确效果能力承接（见[值、类型与计算](../基础语义/计算基础/文法类型与求值.md)）。已确定的递归、词法及固定纯运算基底保持，尚缺标准库范围、Target和真实实现资格逐项保留；不另设暂停的第二计算Profile。这不要求开发者为了普通保存文档/显示界面而写函数，也不要求设计阶段实施求值器。

**不能用原生 TS/Rust 后门证明 Gift 语言自身的任意计算表达能力**。原生源码是允许的补充供应与实际迁出策略；它解决“开发者可完成工程”，但那一部分程序语义属于原生语言，不算 Gift 自有语法已完备。相反，递归、函数、代数数据类型、条件和最低限度可计算原语若被正式纳入，其解释/效果/目标映射必须明确，不能只在Schema里允许 `Expr` 便称功能闭合。

<a id="intent-current-module-owner"></a>
## 当前业务作者模块中的一等意图定义

`intent:goal`、`semantic:pattern`、`semantic:pattern-use`、`req:composite` 是已存在的四种**不同语义**；在唯一候选新写源容器 `gift.author-module/2` 中它们沿用原 Body Schema，不因模块容器升版而改成 `/2` 的意图语义。一个 `product:system.requirements` 指向公开 Goal/Requirement 的已绑定身份，表示此产品须联合消费这些要求；仅在工作区存有Goal、模块已导入它或作者另外选择了其他产品根，都不能自动证明这个产品已覆盖它。

开发者对于系统的业务硬目标只定义一次；新业务采用 `/2`，历史 `/1` 原文件原义保留并由只读适配器消费。`permit`只是规范许可，`oblige`包含主体、触发、履行及期限，均不直接授予执行Grant。跨文件的作用域和角色必须经过名义资格与条件解释，不能靠`kind`字符串或相同的`meaningRef`推定一致。

<a id="gift137-intent-truth-routing"></a>
## 六模态与非计算流程的证据交接

`intent:goal/1`中的 `achieve/maintain/avoid/oblige/permit/prefer`仍保持各自解释；`workflow:plan`的新 `evidenceOutcomes` 只决定合格业务条件得到 `NEITHER` 或 `BOTH` 时的后继，不自行发明Goal、改变规范义务或授予运行权。Goal采用的观察范围、硬义务和时限必须经实际根联合传入流程；流程内某次谓词为 `T` 也不能自动证明长期 `maintain` 或未来 `achieve`。具体 JSON 形状由[开发者Profile](开发者通用定义Profile-类型计算业务与系统构造.md#gift137-noncompute-decision-and-obligation)维护。


<a id="gift135-intent-and-noncompute-conditions"></a>

本阶段的业务Condition是有权领域意义的**引用**，不是新增通用计算式。`state:machine.transitions[].conditionUse`与`workflow:plan.steps[].conditionUse/routes[].whenUse`以明确角色实参定位待解释的业务条件；条件真值、未知与冲突、时态、主体、观察完整性由Meaning/Requirement所有者判定。`intent:goal/1`六模态与`req:composite/1`八Term仍按原结构解释：禁止、许可、保持、进展不能统一化简为`bool`，政策Permit不会产生运行Grant。具体候选字段及互斥规则见[开发者非计算写源合同](开发者通用定义Profile-类型计算业务与系统构造.md#gift135-noncomputational-author-closure)。


<a id="gift134-no-compute-intent-scope"></a>
## 意图语义不被计算函数吞并，计算在同一作者语言按需使用

业务作者使用已规定的`intent:goal/1`六模态及`req:composite/1`八Term表达可观察的业务满足条件、禁止、规范和偏好；其状态、协议、UI、资源、政策和产品组合由有资格的领域定义分别引用。[完整非计算开发面](开发者通用定义Profile-类型计算业务与系统构造.md#gift134-noncomputational-author-contract)承担作者覆盖规则，**不允许将模态压成`core:function`返回布尔值**。方法由Method供应或真实原生源码承担，不要求普通业务作者先学通用计算DSL。Goal被明确选择并解释后才进入联合Requirement，不能仅因模块文件存在就取得产品合格资格。

## 通用计算与业务意图的正式边界

[开发者通用定义Profile](开发者通用定义Profile-类型计算业务与系统构造.md#developer-foundation-gift133)允许在一份工程中通过提案 `/2` 声明类型、计算、状态、UI、协议与产品组件；**本页独占** `intent:goal` 六模态、角色、事实域、时序和规范的专业解释；旧 `/1` 只是历史载体，新 `/2` 可直接保存相同的意图Body。`core:function` 返回一个Bool不会自动变成四态Meaning、长期`maintain`或`oblige`。新 `/2` 系统根与同一 `/2` 容器内的 Goal（或者经显式兼容读取的旧根）必须按准确的 `outputRoots` 和独立接受义务纳入联合，而不是要求业务作者双写旧 `/1`；缺少该消费者时不能以产品结构完整代替实际业务义务覆盖。

<a id="gift131-intent-root-coverage"></a>
## 作者目标参与实际产品的必要连接

`intent:goal` 保存一等、长期可编辑的已接受意图，但“该 Definition 在某个模块中存在”不等于“本次Target采用它”。本次目标的接受范围来自明确 `outputRoots`及其有类型传递引用、另有权来源的独立硬要求；不得扫描 `goals.module.json` 等名称并自动增补。Goal被选中后，所有适用的`achieve/maintain/avoid/oblige/permit/prefer`须交给其各自解释器及一次联合Requirement，不能只提取方便实现的`achieve`，省去时序、norm或未知观察。未取得完整解释时，输出`unqualified selected clause`和具体缺件，不把字符串Clause ID当已履行要求。

多公开根仅表达作者的选择集合；多个业务根之间的类型、主体共享、规则适用与目标装配资格仍需当前TargetProfile的真实消费合同。对此版本不新增`intent:product`、`IntentIR`或第二根注册表；`req:composite`只在其Term确实贡献需求时约束其它Goal，空Term不产生假保证。

## 六模态在真实多文件工程中的具体作者接口与联合入口

六种模态只属于一个`intent:goal` Definition的`clauses`，不是六份必须建立的源文件。`roles`是该定义的本地名义实体槽，`meaningImports`选择经绑定的意义来源；公式`call`以角色名映射Meaning签名所要求的实参。对`achieve/maintain/avoid`，源码格式只接受有限`formula`并保留`horizon/scopeRef`，时间和世界观察的完整判断由已锁定Profile消费。对`oblige`，主体、触发、履行和deadlineRef都必须有Norm/时钟/授权来源；`permit`的`actionRef`表示规范许可而非HostGrant；`prefer`的质量度量只有在同类硬合格候选存在时才参与比较。没有合格的外部意义或权威，不得把这些字段字符串当成真值。

真实多文件Target可以选择多个公开根；编译准备阶段必须按准确SourceRevision将所有根的Goal、PatternUse、Requirement合并为同一相关义务集合，再核共享身份、时间、规范、资源、Frame和冲突。不要使某个`req:composite`在缺解释Profile时默认为`intent:goal`的独立包装或自动从文件名收集全部条款。若多根之间需要新的桥接语义，先取得显式已版本化的Meaning/Requirement接口，再允许实现解析。有限实例在`fixtures/author-workspace/Gift130/design/goals.module.json`给出了六模态合法结构，**它没有提供现实Norm与Meaning证明**。

## 六模态的具体满足判断和拒绝条件（Gift122）

六种模态的**适用性单位**必须独立，编译器不得将它们粗暴转为“单个布尔函数的返回值”：

| 模态 | 类型化解释的核心对象 | 条件/完成判定 | 未决或拒绝 |
|---|---|---|---|
| `achieve` | `Goal(F, completionEvent, H, actor, scope)` | 依锁定完成条件和Horizon验证F见证；对未来保证另需进展/环境证明 | 仅中间态满足、完成点未定义、期限不明或外部确认缺失时不能签达成 |
| `maintain` | `Invariant(F,H,transitionFrame)` | 对声明历史/转移闭包中的每个相关状态保持F，保留并发Frame和观察来源 | 有限快照只说明已读范围；无界H缺归纳或足够机制证明时保持未决 |
| `avoid` | `Forbidden(F,H,observationScope)` | 在所需完整的事件/状态/作用域内禁止F出现，负事实须有相应证据资格 | 未见违例不证明没发生；不可观察、开放域或未覆盖历史必须保留Need |
| `oblige` | `Duty(actor,trigger,fulfilment,deadline,authority,exceptions)` | 有权规则及触发成立后建立独立义务实例，依履行、期限、豁免和负证据分别判状态 | 未知触发不能签无义务；超时或静态Permit不能代替违约/Grant证据 |
| `permit` | `Permission(subject,action,authority,scope,exceptions)` | 按生效政策、例外及优先规则判断规范许可的精确适用域 | 权威冲突/撤销/缺时空范围时未决；不产生HostGrant或已执行事实 |
| `prefer` | `Preference(metric,compareDomain,order,policy)` | 硬合格候选之间按有权度量和偏序比较，无法全序时返回非支配集合 | 缺测、不可比或未委派的取舍不得选唯一最优，偏好绝不覆盖硬要求 |

`achieve`、`maintain`、`avoid`可复用有限公式的证据演算，但该演算只评价指定模型或已资格的观察范围。跨时段保持、无界未来和最终进展需要时态Profile及环境前提；`oblige`、`permit`需要有权规范及其适用条件，`prefer`需要质量单位、比较域与有权排序规则。六个枚举值只是合法输入形状，不证明六类语义均已有生产解释器。派生义务必须保留外部Meaning的解释版本和验证范围。

## 采用设计：六个模态与五个公式的精确语义（R02–R05）

下文是在**已绑定Meaning、主体/作用域和所需Profile**下的原 `gift.intent-body/1` 语义；严格Schema字段维持原样，不在同一`/1`下插入新必填键。实际输入引用已锁定Definition，`meaningImports`只锁解释版本，不承诺自动拥有语义执行、观察或法定权力。附属核心角色的完整表在[60项公共接合](../共同语义/工程通用语义全域与闭合合同.md#stable-finite-general-semantic-core)。

### 六种独立模态（硬约束与比较不互转）

### 作者意图的六种独立模态

六模态是业务责任，不是六个 `true/false` 开关。它们共享公式、引用和作用域，但具有不同的判定/实现语义：

| 模态 | 作者实际要求 | 专业判断的决定性信息 | 不能混淆 |
|---|---|---|---|
| `achieve` | 在指定完成时点或范围达成性质 | 完成点、主体、状态或事件公式、时限与进展 | 中途曾满足不必然等于最终成功 |
| `maintain` | 在要求的轨迹/区间始终保持性质 | 时间域、可达状态、Frame、不变量和干扰 | 一个快照成立不等于未来始终成立 |
| `avoid` | 不发生被禁止的状态、事件或效果 | 禁止的对象类型、范围、观察/推理完整性 | 没有发现≠确证未发生 |
| `oblige` | 条件满足后某主体必须履行 | 规则权威、责任主体、触发、期限、例外、履行证据 | 业务命令/允许并非规范义务成立 |
| `permit` | 有权规范对指定行为的许可 | 主体、行动、时空适用域、冲突/例外规则 | 规范允许≠宿主Grant≠真实发生 |
| `prefer` | 在硬约束合法候选间排序 | 质量指标、量纲、样本、目标方向、优先与不可比处理 | 偏好不可冲销硬约束，候选可不唯一 |

没有时限且没有已声明默认不能一律解释为“立即”或“永远”；未知/冲突条件不能按false落入`otherwise`。意图指向的领域Meaning需要明确适用主体、词法角色、解释来源、时间范围、观察边界与版本；否则只能保存意图主张或请求实际专业供给，不能自动生成正确行为。


| 模态及合法载荷 | 可接受性解释 | 何时只能留Need / 不可假装通过 |
|---|---|---|
| `achieve(formula,horizon?,scopeRef?)` | 有资格的完成观察点/明确期限内成功状态满足formula，并同时满足过程安全及已声明进展。当前有限 `model-steps` 参考以**计划选定终态**评价，曾经过一次真不等于终态成功 | horizon未给且未锁定默认时仅保存目标，不默造无界/即时；无时序/进展消费者不能签长时成功；空程序须证明目标已经成立且无未决义务 |
| `maintain(formula,horizon?,scopeRef?)` | 对声明的历史域所有相关状态及声明的变化/Frame均满足formula；由Trace Profile指定事件/过渡覆盖 | 快照真只能签那一刻；只有模型步骤不能签全部未来；并发副作用未检查时不可签保持 |
| `avoid(formula,horizon?,scopeRef?)` | 相关状态、事件和副作用**不满足禁止谓词**；如果formula仅定义状态谓词，则不得把禁止执行动作暗中等同于状态拒绝 | 没观测到违例≠证明永无违例，除非观察域完整或有合格归纳证明 |
| `oblige(actorRole,trigger,fulfilment,deadlineRef)` | 在有权规范/法域/有效期下生成义务实例；触发的时间/事实成立时激活；履行、解除、豁免、违约和未知由原Norm/Requirement解释；期限由明确时钟/规则核 | `permit`、资源Grant、数据库字段改变和发送指令都不能替代有权规范或实际履行证据；触发未观察不能擅判没义务 |
| `permit(actorRole,actionRef,scopeRef?)` | 在有权规范及其例外/禁止优先规则内对行动作**规范性许可判断**；未定义优先关系或规则冲突报告Need/Conflict | 永不发行HostGrant；不得用许可表示发生；规范主体、法域/时间缺失维持未决 |
| `prefer(qualityRef,direction)` | 对全部硬条件**已经资格化**的候选按精确质量量纲和`minimize/maximize`比较；无已授权相同量纲排序规则时输出非支配集合 | 不能冲掉硬约束/已锁定Pin/权利；未测量不能声称最优；不适用候选不参加排序 |

在当前有限 `model-steps` 参考模型内，`achieve`仅按已选路径的**计划终态**判定；若业务以合格事件曾发生或多个完成点之一为标准，须由锁定的事件/完成 Meaning 说明何者构成完成。`maintain`要求限定区间内持续为真，`avoid`要求相关禁止状态或事件不发生，二者的观察和失败责任不能靠布尔取反互换。`oblige`、`permit`只声明规范模态；规则权威、责任主体、期限与许可范围必须另由生效 Policy/Norm 资格提供。

### 公式演算与类型/证据规则

**公式的对象、作用域和时间不是隐式全局值。** `quantify` 的每一个变量必须由已定型的对象域、提供者与闭合性限定，`forall` 对已证明的有限空域为真、`exists` 为假；对于尚未完成发现或可能继续出现的对象，不能把目前查不到见证当作存在命题为假。`exactly` 和界限计数同时依赖集合去重/重复的约定、域快照和对象身份；`set`、`bag`、`sequence` 不能静默互换。嵌套量词使用显式局部变量，不捕获其他Root同名主体。

时间公式须显式选用事件时间/处理时间/物理截止时间及观察起止；`always`、`eventually`、`until` 的结论分别与全程覆盖、存在有资格的见证、以及直到终止的连续约束有关。开放未来的 `eventually` 在到期前不应判假，无界存活也不得仅因当前仍在运行判真。`not` 是否可对四态证据成立必须依据逻辑语义，不允许把 `NEITHER` 或 `UNQUALIFIED` 强制转成 false 后反转。业务义务的违反、已免责、目标不可证和实际能力缺失是不同结果；事实观察不自动构成授权或不可撤回的验收。


`call(meaningRef,bindings)`必须按已锁定签名绑定全部参数，逐项校验名义类型、单位、基数与词法作用域，结果由有资格的Bool/证据解释者提供。该`/1`公式Profile中的`all/any`需要非空子项，`not`交换支持与反证，`implies(A,B)`严格等于`any(not(A),B)`；这些逻辑连接词不表达因果、法定义务或跨轨迹非干扰。按[四态证据演算](../共同语义/工程通用语义全域与闭合合同.md#stable-finite-general-semantic-core)保留`T/F/BOTH/NEITHER`及观察完整性；只有适用投影有资格时才转成Bool/Unknown。无法解释的Meaning必须停止受影响推导，不能默认为假、空集合或同名目标函数。

时间解释按锁定 Profile 与观察范围执行。`model-steps`只评价所选模型轨迹；`until-event`要求事件身份、区间含端、取消与超时；`wall-clock`要求时钟基准、历法、时区、精度/容差及事件顺序比较；`unbounded`需归纳/形式化证据，否则 Claim 限于已观察前缀。有限测试不得证明无限未来。`horizon`省略仅可按固定版本的明确默认解释；法定时限、履行与违约另由有权 Policy/法域消费者裁决。

### 触发、例外、规范冲突及义务状态

对一次规范义务，实际主键来自规则锁、责任主体、触发事件或实例化身份及生效区间。`not-triggered`要求完整触发观察或可信规则证据；`pending`需要已知触发且期限未结；`discharged`需要合格履行证据；`violated`需要有效触发、时限和未履行且有充分负证据；`waived`需要有权豁免的证据；否则为`unknown/contested`。这些是解释结果的**语义分区**，不在本body另添一套持久Enum或改变现有Norm owner。一个义务可被履行而现实效果仍未获得最终结算，两个Claim分别签发。

**条件性模式**的`whenVariation`不是布尔值，应绑定已接受的条件Requirement/Policy的**准确类型化引用**，固定触发实例、评价时点、谁有权定义、完整性假设和例外。若只有槽名、缺这些定义，必须`NeedsQualifiedConditionalRequirement`，不能把条件真值猜成true或false。`valueConstraintRef`同样由实际约束解释者决定，不是作者提供一个字符串就算检查通过。

### 真实根联合的边界

<a id="intent-hard-soft-norm-satisfaction-contract"></a>
**六模态不得通过统一布尔函数抹平。** 每条正式意图先固定 `subject/roles + meaning lock + scope + horizon/clock + policy/authority + provenance` 中实际相关的部分，再依原模态判定；它们可在同一联合要求图中相交，但并不等价。`achieve` 需要声明的完成时点/轨迹目标及进展；`maintain` 是整个指定观察区间内的不变量；`avoid` 需要对禁止状态、事件或Effect取得充分否定覆盖；`oblige` 需要有权规范与触发/期限/履行证据；`permit` 是规范许可而非宿主Grant；`prefer` 只能比较满足硬义务的候选，并保留不可比或未知结果。

同一根的约束不能因Goal的词法顺序获得执行优先权。规范冲突由锁定的合法来源和明确的优先/例外规则决定，没有授权规则时返回`CONTESTED_NORM`；`BOTH`、`NEITHER`、不可解释或观察域不完整时按各自证据要求返回Need，不得用开世界缺失取代否定证明。任何自动选Method前，必须把所有相关硬要求、共享资源、时序、规范和作者不得让渡的控制范围组成一个联合问题；`prefer` 不可削弱安全或授权。

**跨层不变量**：用户接受的目标是唯一作者真源；派生 `JointRequirement` 只是带来源的消费快照；生成的SourceMap把具体源码和未覆盖义务反指到原作者决定。新现实事实触发再次求解时，不改变历史作者源；实际授权、Operation与Settlement仍属执行Owner。这里不新增第七种意图模态或第二份作者Intent文件。


`intent:goal`、多个 Goal、`req:composite` 和 PatternUse 必须在**同一锁定范围**组成一个 Requirement 闭包。相同对象先按身份合并，再联合检查共享资源、时序、Norm、效果与跨目标干扰；单独 Goal 全部通过不等于联合可行。仅语义展开时只得到有来源的派生义务和未决资格；完整产物的已选硬根须同时拥有合格解释、Method 与 Target 承担者，否则拒绝完整发行，而不暗中生成程序。

> 本文件是**已选择的工程设计**，不是 Gift111 参考实现已支持这些语义的证明。唯一拥有 `intent:goal` 作者表示、模型解释、业务语义资格的主责任；既有 `Definition / Requirement / Method / Target / Grant / Evidence` 的低层身份与消费者沿各自原主责任维护。本文件不引入第二套可写需求数据库。

## 一、必须纠正的架构方向

Gift 的主产品是**通用意图语言**（declarative intent language），不是新的全功能通用计算语言。用户主要描述哪些现实或软件世界中的结果应该成立、不应发生、何时成立、谁有权决定、哪些证据可以说明成立；系统负责找已有合格的机制、方法、组件或受控生成器来达到目标。写递归函数、泛型算法或目标语言源码，是专业实现供应的**可选退路**，不是新业务用户的标准开发方式。

旧版的计算语言参考实现可以保留，用于证明一部分由作者自写算法也能运行，但不把其构造覆盖率作为通用意图覆盖率。旧版 `IntentFacetDescriptor / Catalog / IntentIR` 继续是**发现与候选解释层**，不再是高层意图唯一的入口；已被有权作者采纳的意图应当拥有**一等 AuthorSource**，不是只在 UI 展示后散成未可逆的一堆计算方法。以新的 `intent:goal` Definition 保存原始接受内容，各 Requirement/Claim/MethodTask 是带精确来源的派生工作产品或引用，不是另一个长期真源。

**相同的词不等于相同语义。**一个 `paid` 字段可以是已授权、已扣款、已清算或用户声称支付，不得凭名字归一。必须采用有版本的 MeaningRef：主体类型、外延/内涵、适用时点、世界/模型范围、观测来源、例外与逻辑支持方法。缺其中决定接受集合的内容就维持 `NeedsMeaning`，不能偷偷让编译器设计业务政策。

## 二、通用的不是“业务名词全集”，而是开放的意图生成体系

传统计算语言的有限符号和表达式组合能表达很多计算，**但不能直接表达任何现实含义由谁负担、什么发生才叫支付完成、什么证据足以证明、许可来自谁**。Gift 应当把这类区别作为一等可组合的业务语义，而不是从函数名猜测。

下列是**跨领域构造责任**而非互相排斥的业务模板：

| 构造 | 表达什么 | 不能自动推出什么 |
|---|---|---|
| Entity/Identity | 主体、对象、资源、身份、分区和生灭 | 名称相似不等于同一实体或真实存在 |
| Property/Relation | 数据状态、集合/袋/序列、关系、依赖及量纲 | 观察某个字段不等于获得真实事实 |
| Knowledge/Observation | 观察、假设、推导、来源、覆盖及未知 | 没记录不等于否定；外部宣称不自动成为真值 |
| Goal/Outcome | 希望实现或保持的可观察结果 | 只给目标不自动产生合格实现 |
| Invariant/Prohibition | 永远要保持的性质与禁止的变化/作用 | 静态检查不证明运行时永不违反 |
| Obligation/Permission | 义务主体、触发、期限、法域、例外、许可 | 规范允许不授予物理执行权限 |
| Event/Transition | 事件、合法状态变化、守恒、先后、历史 | 把两个状态函数接起来不自动获得事务原子性 |
| Time/Progress | 时间域、窗口、持续、终止、截止、公平性 | 一次快照不证明未来一定成功 |
| Preference/Optimization | 满足硬约束后比较质量、费用或风险 | 找到可行方法不证明全局最优 |
| Resource/Ownership | 配额、占用、借用、释放和持久所有权 | 单个 API 请求不保证跨用户容量安全 |
| Interaction/Delivery | 用户可见呈现、交互、协议和接口承诺 | 提供数据 API 不等于交付完整 UI |
| Effect/Recovery | 权限化外部作用、幂等、读回、补偿及未知结算 | 编译成功或 HTTP 响应不等于现实效果发生 |
| Assurance/Evolution | 验收、证据、版本、兼容与受影响范围 | 同版本号或有测试不等于规范/产品正确 |

这些构造可以继续被新语义扩展，而不是一个宣称先验穷尽的十三类封闭字典。新行业实体/关系不修改 Kernel。新不可归约的观测、规范、因果或世界效果可由具有版本、解释及适用域的 `SemanticModule` 提供。无法取得合格意义时，语言仍允许保存意图草稿与 Needs，不允许凭新 URI 生成假源码。

**描述能力与自动实现能力独立。**通用意图可以精确描述一个目标而目前无法实现；也可能有很多可行实现，用户不需决定其算法。世界事实不能自动从编译器的抽象语法得出。一般输入上的完全自动合成、等价判定与最优性并没有统一的总能成功的方法。

## 三、意图模块是真正的作者源，不是“意图被拆回源码”的双份文件

保持既有 `gift.author-module/2` 工程外壳和 JSON 严格读取。新 `dialects.intent = { languageId: "gift.intent", constraint: "1" }` 的 `intent:goal` Definition body `representation: "gift.intent-body/1"` 是**已选设计的新增作者构造**。它在产品里仍待真实 Reader、语义消费者和方法实现；不把包内 Schema 及示例宣称为生产发布。

```text
AuthorModule { definitions: { id: {
  kind: 'intent:goal',
  name: string,
  body: IntentBody
}}}

IntentBody {
  representation: 'gift.intent-body/1',
  roles: Map<LocalRole, { typeRef: MeaningRef, objectRef: AuthorObjectRef }>,
  meaningImports: [{ libraryId: string, revision: string, contentDigest: sha256 }],
  clauses: [AchieveClause | MaintainClause | AvoidClause |
            ObligeClause | PermitClause | PreferClause],
  assumptions?: AssumptionRef[],
  observations?: ObservationNeed[],
  constraints?: ConstraintRef[],
  provenance?: SourceRef
}
```

`IntentBody` 必须能**独立、按需、精确地指向**引用的公共业务含义。`GoalClause` 表达触发条件（可省略时无条件）、目标谓词、可选时间域、范围和观测义务；`InvariantClause` 保持一种性质；`ProhibitionClause` 禁止一种状态、变化或作用；`ObligationClause` 绑定责任主体、触发、期限及可接受处理；`PermissionClause` 是规范层许可，不是当前 Host Grant；`PreferenceClause` 在所有硬约束可行后给出可比对象和顺序。表达的缺省、null 和未定义必须区分。作者只写该次**独特差异**，已锁定的库定义补充既定语义，不填一堆重复字段。

局部角色必须通过类型化 Binding 固定真实角色，`role` 不是可以任意取字段的 magic string。`meaningImports` 锁定实际解释者的语义版本、作用域、开放/封闭观察假设；词法名称通过既有 SourceScope/ModuleUse/DefinitionRef 解析。跨领域 Role 统一只因有明确身份映射而发生，不凭同名 `user/order` 合并。每条 Clause 具有稳定发生身份以便二次修改、证据与错误映射；模式化库实例引用已有 Definition，避免复制共同规则。

**没有任何字段要求产品作者写循环、递归、线程锁、SQL、Rust/TypeScript 表达式或 SDK 调用。**确实不能复用现有合格 Method 时，产生特定 `NeedsImplementation` 交给受委派实现供应；它可以使用成熟编程语言或 Gift111 的计算子集，但不会污染意图作者面。

### 固定逻辑组合，不以 JSON 的括号层数获得真语义

本 Profile 的有限布尔组合通过 `all/any/not/implies` 明确定义；谓词引用须有实际签名及解释支持，量词/时间/概率/非干扰等超过有限 Profile 的意义通过已锁定语义模块承载，不能用普通 JSON 数组偷偷代替无界全称量化。

一个有限快照可以构造**观察候选**：谓词在本次读取的、被明确允许的数据与观察条件下为真、假或未知。`Unknown` 不是业务 `false`。`maintain`、`never`、`eventually` 等跨时间/轨迹主张，即使当前快照符合，也不能由快照单独签发整个性质的 PASS。`oblige` 需要责任归属、触发和期限；`permit` 不产生 Grant；`prefer` 不能覆盖硬约束。

形式上，给定解释模型 `M`、环境集合 `E`、适用主体与时间窗 `C`，意图 `I` 定义一族**可接受的状态/轨迹/规范关系** `Accept(I,M,E,C)`；不等于唯一程序 `P`。只有在生成物或方法的相应行为被证明/有资格地检查包含于其合法接受域，且履行正常功能、进展、权利和实际 Effect 的边界时，才能说该 Method 实现这个意图。该解释是跨领域判定框架，不宣称每个 `I` 存在一个可判定的全能检查器。

## 四、跨业务的真正共用：复用“相同作用关系”，而不是复用“行业标签”

**预留** 可用于仓位、病房、座位和 GPU 资源，成立的共同部分是：某个主体对某个容量/时段请求独占或受限并发的占用，且不能超出有权批准的约束。但“预约确认”能否形成法律合同、超售是否允许、病房是否需要人工批准、GPU 是否支持抢占，是不同 Meaning/Authority/Effect。只能抽取共同可保持的 `capacity` 不变量与原子预留 Method，再分别绑定域差异，不能把“共享名词”当作充分证明。

**生命周期** 可以表达订阅、设备、订单、工作单和数据归档，但状态类型、转移权限、期限、回滚/补偿和终局由业务定义。**查询和规则** 可用于法规判定、科学筛选和游戏胜负，但开放世界假设、完备性、证据和冲突处理不一定相同。**优化** 可用于路线、排班、资源成本和模型推断，但目标、限制和不确定误差不可相互偷换。**作品/体验** 可以约束形式、语言、可访问性与可观测反馈，却不能把主观美感变成无来源的 Boolean 真值。

跨域核心统一表示应保留**语义差异**而不是在 schema 中枚举数十万业务谓词。结构化作者文件可以复用一个版本化的 `ReserveWithCapacity` Definition，仅补本例角色、容量来源、许可主体及异常条款；所有实现细节由对应 Method 与授权运行层承担。

## 五、从意图到现成构件，而不是意图逐句翻译成程序

```text
Raw request / structured AuthorSource
   → Candidate Interpretation (可保留歧义；AI 可提候选，不能直接采纳)
   → Accepted Intent Definition（唯一作者源，目标与主体已绑定）
   → Semantic Binding（MeaningRef+角色/量纲/时间/事实来源）
   → ObligationGraph（目标、安全、规范义务、观察/证据需求）
   → Goal Decomposition / Realization Match（有前提和保证的能力方法）
   → Existing Rule/Query/State/Workflow/Optimizer/UI/Native Method 等供给
   → Target assembly（组装、生成胶水及实际必要代码）
   → Qualified observation / reconciliation（如要求真实效果）
```

编译器**不得用固定行业名选择业务模板**。解析库方法采用明确定义的前提、保证、效果/读集、作用域、量纲、权限、异常、资源与 Target 条件；可以组合不同领域的机制（例如“支付确认”条件 + “原子容量预留” + “幂等事件消费”），但组合资格必须检查共享状态、时间、重复触发和证据假设。一般的 `reserve` 方法不直接取得结算银行卡的权限。

实现渠道应按可用性而非迷信编译器自研：

1. **可直接解释/执行的已锁定语义库**：事实查询、规则决策、有限状态、约束校验、参数配置等；
2. **现成成熟领域引擎和组件**：SQL 查询/事务、工作流、规则引擎、优化器、消息/权限/界面组件、控制或数值求解器；
3. **有约束的组合与搜索**：根据方法前提/后置/效果/依赖寻找组合，保留运行条件、失败/未知与反例；
4. **仅在确有新机制时交付实现工作**：由专业作者/生成工具在合格边界内创作原生实现，经验证后提供可复用 Method。

前 3 项才是 Gift 降低普通作者成本的核心。**从零实现通用语言编译器、SSA、LLVM、寄存器分配、内存模型不是作者意图表达的前提**。旧 Gift111 的 Python→TS 实验仅作为第 4 项或复杂实现方法的局部备选，不再是通用意图能力的主里程碑。

## 六、确定性的准确对象和错误结果

冻结 `AuthorSource + MeaningLibraries + Policy/MethodCatalog + TargetProfile + 受允许外部事实` 后，语义绑定、谓词含义、候选合格过滤、确定的候选比较与目标代码生成可有可复算的行为。**不表示所有目标都能自动达到**。现时物理运行、人的批准、市场价格、医院床位、设备执行和生成内容的主观评价都可能需要新的世界观察或授权。

与业务结果不同的分析状态：

- `NeedsMeaning`：意图谓词/模态/角色没有可解释的公开意义；
- `NeedsFact`：意义已知，但现实前像、可信观测或法域事实缺失；
- `AmbiguousIntent`：作者尚未采纳一种能改变业务后果的解释；
- `InconsistentIntent`：硬要求在声明假设内冲突且有可复核反例；
- `NeedsMethod`：意图精确，但当前目录没有相应合格实现；
- `NeedsEnvironment/Target/Grant`：候选实现需要真实供给或执行授权；
- `IncompleteSearch`：资源/时间/求解能力用尽，不等于无解；
- `QualifiedPlan`：有准确适用前提和对应证据的实现计划；
- `ObservedOutcome/UnknownOutcome`：真实运行后，按独立观察结算该主张。

这些是本设计的语义上必须可区分的诊断类别，**不是本文件另起一份与原 owner 冲突的持久 Enum**。消费者通过现行诊断、Needs、Binding、Claim、Operation 身份返回；只用于普通项目时不额外实例化所有状态类。

## 七、三种相似却必须被拒绝的“伪通用”路径

**伪通用 A：关键词词典。**把所有行业功能收集到 `shop.*`, `hospital.*`, `game.*` 并持续增加模板，会使新领域需要内核行业分派，不能满足开放意图。

**伪通用 B：把意图换成命令式 JSON。**若“预留 1 份库存”仍强迫作者选择数组、循环、SQL 事务、异常恢复等全部内部细节，实际上只是换了编程语言语法。

**伪通用 C：自然语言+黑箱代码生成。**若“订阅取消后不再扣费”在每次构建重新由模型推断成不同扣费窗口、未知例外，无法形成稳定可检查业务语义；受权 AI 可以提议解释或实现，但固定构建不能未经采纳改动用户政策。

Gift 的产品判断标准：新增未知领域概念能成为受类型和可观察含义约束的作者 Definition，不改 Kernel；作者能写目标和禁令而非算法；现成供应可自动解析组合；需要真实世界/新算法时给出精准缺项；旧源可二次修改仍保持原意。对这类用户价值的证据优先于又增加一个通用递归语言操作符。

## 八、反例与现实边界（保持差异，而不靠格式统一吞掉）

- 现金账户已授权 ≠ 资金已清算；不能将 `paymentConfirmed` 直接归并为 `paid=true`。
- 病人已被安排检查 ≠ 检查结果已生成；人工/专业批准需要现实权威。
- 事件当前为 `delivered` ≠ 未来不会重复收到；一次当前状态不等于轨迹不变量。
- 系统声称 `no data exfiltration` ≠ 一切第三方依赖无外传；取证与可信运行边界决定保障强度。
- 静态模型正确 ≠ 实时截止期可达；软/硬安全与动态模型不同。
- 一次创作结果符合形式长度 ≠ 具有审美价值；主观目标需要真实评价或显式未知。
- 没有找到方法 ≠ 本意无法实现；没有足够数据 ≠ 业务事实为假。

## 九、具体交付与采用规则

`schema/semantics/intent-body-1.schema.json` 是**本设计采用的结构形式说明**，`fixtures/intent-language/Gift112/` 提供独立跨域样例和只读的结构/有限观察检查器。结构及局部观察成功不等于产品编译器已支持 `gift.intent`，更不等于所有历史提议已自动升级；正式发布必须接入准确 `AuthorSource/Meaning/Requirement/Method/Target` 消费者、独立测试与真实资格。

通用意图主源成为普通新产品的优先入口；原 `s:function`、结构计算体、原生 TS/Rust 仍保留为 Method 供应方的工具与用户明确选择的复杂计算功能。**不再以“通用计算能力实现了多少”作为 Gift 对高层意图完成度的替代指标。**

## 十、已冻结的 Intent-only 结构样例及模拟边界

本轮离线作者 JSON 只接受一等 `intent:goal`，每个条款 `id` 在定义内唯一。`roles.<key>.typeRef` 必须引用被锁定 Meaning Library 的真实名义类型，`objectRef` 指向本工程已接受的模型主体；`meaningImports` 为精确 `(libraryId, revision, contentDigest)`，`formula.op=call` 的全部参数必须逐一通过类型化角色绑定。作者没有写出 `method:capacityReserveOne`、`addInt` 或事务指令；实现供给目录另行拥有这些内容。闭合、开放观测分别标记来源，未知值不会自动等于 `false`。

当前离线见证使用 `achieve/maintain/avoid` 和有限布尔组合；`oblige/permit/prefer` 可被结构读取，但**不由有限模型解释器判定履行**。`horizon.kind=model-steps` 只表达参考路径的采样状态，不能因此签发无界安全和最终进展。`IntString` 是被模型明确采用的无损十进制数字约定，不允许 1.0/1e0/01/-0 直接混用。

这份样本并不定义生产持久源码上所有可能的组合或世界语义：正式多 dialect AuthorModule、跨进程真实观察、领域意义锁与签发、真实 Method 目录接合、目标装配、Grant 与现实读回，仍须实际实施。结构有效只意味着输入语法正确；本地 `ModelPlanCandidate` 必须被显示为**模型候选**，从不升级为已确认现实作用或高质量生产源码。

[可重放样例与 25 项测试](../../../fixtures/intent-language/Gift112/README.md)验证了病床/GPU 在同一个容量含义上的复用、订阅义务停在未决、主观审美外部观察缺失、有限硬约束与方法供给、补丁后状态不污染作者快照。跨域复用必须发生在精确相同的语义/资源合同上，医院医嘱/超售政策/人工许可不得从 GPU 容量语义自动继承。

本轮离线 `contentDigest` 使用参考实现自身规定的 UTF-8、JSON 键排序、紧凑分隔符的局部归一化字节，并非 RFC 8785，也不被发布为跨语言官方哈希标准。正式产品需要已有工程中唯一的规范内容摘要合同，不能把“版本号没变”当成内容不变。未激活的外域 Method 不应要求启动其解释器或加载其领域 Meaning；参考消费者只在实际角色类型相交时检查 Method，避免“安装海量库就必须解析海量模块”。

## 持续执行的一个实物边界：Gift116 本地模型消费者

原有 `intent:goal`、角色类型、MeaningImport、目标和维持/禁止条件仍是唯一作者源。Gift116 在不改变这些语义的前提下，演示了**同一意图在不同操作时点基于当前状态重复求解**，而非用编译时一次性计划永久约束后续业务。它对所有已锁定意图保持局部模型 `maintain/avoid`，对本次选择的目标判断 `achieve`；已完成者可得到有身份的无变化回执。详见[持续执行与本地事务真实施工](../../70-工程系统与演进/工程构造手册/26-持续意图执行-每次重规划与持久事务.md)。当前没有动态实体、真正的外部领域事实、Permission/Obligation 解释器或现实 Effect，不能把一次有限模型的安全检查冒称时间上无限安全保证。

## 从开放领域模式到一等意图，再到复合业务能力：唯一作者源的实际合同

### A. 谁写什么及唯一写权

在本节原先的`/1`历史作者范本中，产品作者维护该版本被接受的 `intent:goal` 及所引用的领域 Definition；新业务项目应写唯一候选`gift.author-module/2`，旧`/1`不得回写。公共 Meaning 作者维护谓词、名义类型、观察及语义模式；Policy/Authority 主体只修改其自己有权的规范和 Grant；供应者维护 Method、Adapter、Target 等实现。系统的 RequirementGraph/Binding/Plan/SourceMap 是衍生物，**不能**让作者同时填写两份同义的业务规则。自然语言提示是解释候选，不自动成为已接受作者源；已接受作者意图不会因模型、Method 目录或时间变化被无授权改义。

表示与含义分开：现有 `gift.intent-body/1` 的 `roles` 绑定对象，`meaningImports` 锁定类型和谓词解释，`clauses` 定义作者改变的目标/禁令/规范/偏好。可复用的更高层业务模式仍是 `Definition`，作者引用其已锁定身份并补差异；不要求把公共抽象全文复制进每个意图 JSON。现有 Schema 未支持直接保存一般 `semantic:pattern` 为业务作者新 Profile；要接入新的模式作者源，必须按[统一结构作者与协议](../../10-作者与输入/作者源/结构化源码.md#gift-pattern-source-encoding)完成正式 codec/版本协商。当前已发布 `intent-body/1` 的字段不会在不变版本下被偷偷扩大。

### B. 从一个作者输入建立有类型义务

读取算法：

1. 固定 SourceSnapshot（真实 bytes/Revision/SourceProfile）、模块导入图、DefinitionId、Domain/Meaning locks、政策来源与观察范围；拒绝重复键、未知已激活字段和错误版本，但保留原草稿字节供作者修改。
2. 解析每一 `roles` 的真实 `typeRef/objectRef`，检查名义类型、单位、集合重数、身份发行域和 lexical binding；角色同名绝不允许自动跨意图合并为一个实体。
3. 对每个 `call` 解析 `meaningRef` 到精确函数/关系签名（含作用域、时态、观察域）；验证所有参数完整绑定与返回逻辑画像。无解释时给 `NeedsMeaning(ref, sourceSpan, requiredInterpreter)`，**不**按业务名猜一个字段。
4. 逐条形成义务：`achieve` 给目标条件和进展域；`maintain/avoid` 给适用历史范围；`oblige` 给规范责任主体、触发/完成/期限；`permit` 给许可陈述及其制度来源；`prefer` 给比较和优先层级。仅仿真可解释的部分标 `ModelOnly`，其他保持精确未决，不能默丢不认识的义务。
5. 将 `assumptions/observations` 加入上下文，同时记录**依赖与负依赖**（例如不存在 Method、缺外部观察者、缺目标能力）。导出只读的 `AcceptedIntentView`（来源+类型化义务+解释版本+Needs），绝不回写作者真实 `clauses`。

### C. 跨业务复用的最小作者差异

三个产品的作者表达可以都引用类型化“可用容量下分配”模式，但各自绑定实际 `Requester`、`Resource`、`ValidityInterval`、`QualificationAuthority` 和 `AllocationObservation`，并声明差异：医院的医生确认、票务的唯一座位与超时付款，或 GPU 的抢占。公共模式只能继承已满足的合同；选择了 “允许超卖” 的 GPU 场景不属于“不可超额分配”的该模式实例，除非明确更换策略与可观察要求。这样作者输入可以少写共享规律，但减少文本不意味着可以省掉改变业务结果的决定。

作者要求的原则层级也需明确：业务硬条件和禁令不可被 Method 降为软偏好；软偏好不能覆盖硬约束；未得到权威来源的自然语言规则/法定义务维持未决；实现供应的便捷默认只在不改变任何已声明可观察结果时合法。`unknown`、`null`、缺省、False、空集不是可互换的值。

### D. 业务能力不是固定要多一级 JSON

业务能力可以由一个 `intent:goal` 直接构成，也可由多份已接受意图以引用/绑定/关系形成复合 Root。该组合 Root 需要公开输入/输出、角色映射、相交时间/资源与总目标、联合不变量、完成/取消/失败合同；可以保存在原有模块 Definition 与 `Requirement`/机制组合体系中，不强制新建 `business.json`。当一个复合能力发布给别的作者时，其**公开合同**成为可复用 Definition；所选数据库、规划器或部署配置只是 Binding/Assembly 的证据，不能写回该业务 Definition 改变它的 Meaning。

### E. 从作者源到业务结果的十种拒绝路径

`AmbiguousIntent`（可改变结果的含义未被接受）、`NeedsMeaning`（无正式解释）、`NeedsBinding`（类型/身份/角色无法对齐）、`NeedsFact`（现实观察前像不足）、`ConflictingEvidence`（来源互相反对）、`InconsistentIntent`（已得到可核查的硬冲突）、`NeedsMethod`（含义有但无合格实现）、`IncompleteSearch`（有界搜索未结束）、`NeedsAuthority/Grant/Target`（确实缺运行及生成资格）、`UnknownOutcome`（已派发但结算不明）。这些名称对应实际诊断层的**区别**，不要求再持久一套枚举；部分状态可同时存在，调用者不得用单个 boolean `ok` 代替。`NoPlanInSuppliedFiniteModel` 不应提升成开放世界全局 `UNSAT`。

### F. 作者的验收不是“能解析 JSON”

检查项包括：跨两个此前未登记的领域定义时不增加 Kernel `switch`；把 `paid` 改成 `settled` 后不是只改显示名字而实际履行义务改变；将一个共享资源绑定到两个业务 Root 时能指出共同容量冲突；添加 Deadline/人工批准后有相应 Method/Observation Need；已有 Method 替换不修改已接受的意图源；二次修改触发相关绑定和证据失效；无界时间、主观审美或真实权利缺观察/法源时拒绝伪通过。只有这些可检查结果才能说明高层作者源真正起作用。

## 六种意图条款的施工语义与开发者实际输入

**真实现状边界：**`schema/semantics/intent-body-1.schema.json` 规定六种条款 `achieve/maintain/avoid/oblige/permit/prefer`，有限公式是 `call/all/any/not/implies`，horizon 结构列 `model-steps/until-event/wall-clock/unbounded`。这些是结构允许的表达，不代表 Gift117 已执行六种意义。当前模型解释器只有有限谓词、模型步骤和局部 Method；完整规范、无界时间、权限、外部结果需要对应 `RequirementDefinition`/有资格解释模块。不可为“兼容”而让旧 `gift.intent-body/1` 的 Reader 静默接受新的 `semantic:pattern`。

| 条款 | 作者不可省略的**独立选择**（可来自被采纳的已锁定库） | 意义检查与实际结果 |
|---|---|---|
| `achieve` | 公开目标谓词、对象/参数、适用时点/观察、异常 | 在给定范围内产生合法结果与必要进展，零动作计划仅在目标已满足且无未决义务时合格 |
| `maintain` | 维持谓词、历史/时域、条件与例外 | 检查每个相关状态/过渡；快照只能签快照，不签未来永远 |
| `avoid` | 禁止行为或状态、适用主体及时间 | 否定命题≠已执行撤销；对合法历史有安全义务 |
| `oblige` | 责任主体、触发、履行、期限、解除/违约与有权规则 | 建立可追踪的规范负担；数据库字段改变≠履行且 Permit/Grant 独立 |
| `permit` | 行为、主体、权限来源、作用域与例外 | 给规范许可结论，不发世界执行 Grant |
| `prefer` | 可比较质量维度、方向、层级及不确定性 | 只能在全部硬合格方案间排序；无可比证据不得自造全局最优 |

开发者的最短提交取决于**不可从库推导的本例差异**，而非强制其填写所有字段。至少要有有权接受的目标或公开能力引用；出现现实身份、时间、权利、数据来源、失败策略并影响业务后果时必须由有权来源补齐。已锁定库可定义常量/默认；省略 ≠ False/null/空集合/任意实现。业务模式引用只记录 `PatternRef + roleBindings + 需要的variationSelections`，复合能力可由现有 Definition/Requirement 组织，不新增强制 `business.json/system.json`。

在 UI、CLI、AI 工具中，对每个未完成点返回源位置、属于哪层责任、是否由作者决定、可用方法/默认的真实资格与预览差异。普通业务作者不应被要求写 AST、`MethodDigest`、事务隔离、Rust 函数、TypeScript 生成模板。被授权的 Method 作者则可选择已有计算/原生库。AI 可生成意图候选或实现候选，但不能越权采纳含义、创设真实 Grant 或把 Unknown 改成通过。

## 意图引用公共模式时的唯一作者意义

`semantic:pattern-use` **不是新的 `intent:goal` 同义写源**，也不能修改已采用的 `gift.intent-body/1` 的原义。作者只保存自己的具体对象选择、领域差异和观察来源，公共角色/共享规则仍由被引用 `semantic:pattern` Definition 管理；在固定版本上得到派生、不可直接编辑的 Requirement 使用集合。其基数、类型精化和条件拒绝由[抽象语义 owner](../组合/抽象与开放定义.md#pattern-use-multiplicity-refinement-contract)给出，文件载体与 v1/v2 版本路由由[结构化源码](../../10-作者与输入/作者源/结构化源码.md#pattern-use-versioned-encoding)给出。

普通业务作者不因这些内部检查而需要手填编译器 IR、证据摘要或低层 TypeScript/Rust。缺少领域政策、真实观察或有权批准时，保留意图和 `Needs*`；不得由编译器补成默认“允许”，也不得把仍为抽象义务的引用变成业务成功状态。

## 适用前提、限制与反例

以下按原版本保留相关定义、反例、判断和实测范围。版本名称仅表明形成来源；条款是否现行有效仍由本文件的当前合同、被引责任文件及实际消费者决定。

### 多个已采纳意图的统一业务语义与实现独立性

一个产品可拥有多个同时生效的 `intent:goal`；每个仍由其作者模块唯一写入，组合消费者在统一 SourceSnapshot/MeaningLocks/共享身份/时间与资源域上派生一个 `JointObligationGraph`。**不能分别为每个 Intent 签一个合格计划再连接计划列表。**所有 `maintain/avoid` 对每一次中间变化、`achieve` 对目标终态、规范义务与时间条件对其精确作用范围均须联立评价。两个独立请求均能预留一份容量，不推出同一个只剩一份的资源能满足两项请求。闭域有限求解失败只对该模型返回 `NoPlanInSuppliedFiniteModel`，超出搜索预算保留 `IncompleteSearch`。

默认业务作者不写通用计算体。`s:function/gift.semantic-body/1` 是**实现供应者可选择**的工具；若 SQL/规则/工作流/原生库已合格，就不要求通过自研计算语言或重新编译成计算 AST。作者可定义无限新业务概念，但必须提供或引用名义类型、观察含义、时间/主体/权利条件；新 URI 不自带真实业务意义。方法和世界执行许可的取得是两个不同责任。

实际编译算法、现成引擎的精确资格及产品装配分别见施工手册的联合组合、供给接合和产品生成章节。Gift113 的参考程序只验证给定有限模型的局部组合，不给出真实世界作用或长期安全证明。
### 意图与专业方法的实际装配见证（非新增语义上限）

一个 `gift.intent-body/1` 可以保留公开目标、保持和禁止条件，由 Meaning 库解释真值，并从供应的 Method 得到实现。新增[可运行的本地模型装配消费者](../../70-工程系统与演进/工程构造手册/25-意图到本地持久程序-可运行装配施工.md)生成严格 TypeScript 与 SQLite 事务；医院、GPU、文档三类不同作者输入均无需新增业务 Kernel 分派。这证明所检查**有限子域的可装配性**，不把此子域的 `literal/field/eq` 等有限计算表达式当作全部开放 Meaning 的定义；缺少外部观察、规范义务履行或真实 Provider 的意图仍准确拒绝。
