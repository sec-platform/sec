# 意图描述与作者投影

## 与已接受意图作者源的精确关系

本文件持续拥有**候选意图发现**、Facet/Catalog/Occurrence 的只读描述与卫生展开；但 Gift112 已决定允许普通新产品作者直接创建并持续编辑[一等 `intent:goal` AuthorSource](通用意图语言-意图源与语义组合.md)。已采纳意图**不是**只能被拆成一组来源不可逆的计算 Definition 后消失。IntentIR 候选不经授权便不得升级为该作者源；若已有 Requirement/Method 被其解释为派生义务，必须带精确来源且只由原 owner 维护。旧段落讨论的不建立“私有 IntentRecord”，仍只禁止与 AuthorSource 竞争的第二数据库，不禁止新作者 Definition kind。

<a id="gift-unit-intent-facet-projection"></a>
## 责任与成立范围

本合同拥有 `IntentFacetDescriptor` 的作者辅助含义、`IntentCatalogView` 的发现关系和 `IntentOccurrenceView` 的追踪关系。精确请求形状由[六工具意图扩展](../../80-开发者与接口/工具协议/意图发现与候选展开.md)拥有。它们不是新 IR、万能业务对象、运行状态机或第二份作者源；已有 [Definition/Requirement 与决策面](开发者决策模型与设定面.md)、[组合规则](../组合/README.md)及[实现选择](../../30-实现解析/实现选择/README.md)继续拥有事实与算法。

“意图”表示作者希望表达或完成的含义，不是编译器凭行业名猜出来的实现。目录是可选入口：已知准确 Definition、规则或原生源的开发者可直接编辑，不必先搜索目录、生成一张意图表或再次调用 LLM。人、CLI、AI、表单与图使用同一候选机制；确定性重建只消费已接受的源和固定解释，不再次推断自然语言。

**`Goal` 与 `non-goal` 的负向语义不能合并。** 目标是请求者希望得到的结果，`non-goal` 可以只是某个阶段**不承诺提供**某项能力，也可以是明确的**禁止条件**（例如不可外发数据）；两者对正常实现、验证、未来扩展和运行准入的影响不同。未经澄清，不得因为用户说“不要做 X”就在所有环境生成永久 hard prohibition，也不得把明确的安全禁令简化成“本期未排期”。在准确主体、适用期限和有权裁决下，前者可以成为有界产品范围/不承诺记录，后者才按其语义进入 Requirement/Policy/Control 等真实 owner；仍不明确则保留候选解释和 Need。`GOALxx` 这样的设计治理编号只是工作记录身份，不能代替产品 `Goal`、Requirement 或规范对象身份。

<a id="facet-descriptor"></a>
## 描述符：谁能表达什么，而不是谁现在被允许做什么

`IntentFacetDescriptor` 是所属模块或作者库内有准确内容修订的辅助合同；`facetRef` 引用该修订，不另给业务实例铸造新身份。其结构包含下列字段角色，具体公开编码随[机器合同](../../70-工程系统与演进/实现与装配/源码分区与机器合同.md#machine-contract-source)发布，未发布读取器不能宣称可调用。

| 字段 | 完整含义与约束 |
|---|---|
| `facetRef`、`ownerRef` | 准确描述符内容引用及提供它的 SemanticModule、AuthorLibrary 或定义集；同时保留实际 ModuleUse/命名域解析基础，不能靠同名 facet 合并不同库 |
| `subjectRoles` | 主体的有类型角色、基数、已有/待创建条件、同一性与分区要求；角色是模板位置，不是对真实人或组织的身份认证 |
| `parameters` | 作者参数身份、类型、单位、codec、缺失与显式默认的区别、默认提供者、作用域、约束、披露等级及是否必需；任意默认都服从原 descriptor-owned 默认和贡献代数 |
| `authorActions` | 允许的声明、引用、实例化、连接、约束、绑定请求、组合和输出动作；每个动作有输入角色、写入的作者区域、展开方法引用、预期贡献和保持条件，不含任意 shell/脚本指令 |
| `requirementTemplates` | 产生普通 RequirementTerm/Profile 的准确模板和主体代换；不能偷偷增加未展示的义务、删除原要求，或自造 profile precedence |
| `semanticNeeds` | 对方言/可观察语义的准确要求；结构格式可读取不等于完整语义已被解释 |
| `capabilityNeeds` | 实现阶段需要的能力合同及约束；不指定已选择实现，不绕过 Eligibility/Decision/RealizationBinding |
| `runtimeNeedTemplates` | 所需存储、网络、时钟、设备、密钥用途和运行资源的模板；是需求，不是当前在线状态、资源预留或 Grant |
| `claimTemplates` | 从实例和原要求产生相交 Claim/ProofObligation 的模板；模板没有 Evidence 资格，缺模板也不证明没有义务 |
| `migration` | 描述符自身与其展开产物的兼容/迁移方法引用及影响范围；表示标签变化、参数改义、展开改义和真实数据迁移分别处理 |
| `projections` | 名称、解释、分组、表单/图/文本/表格提示、排序与可访问性元数据；无事实写权、无执行授权，显示字符串仍是不受信内容 |

描述符不得保存当前权限、健康、报价/库存、实际执行结果、Evidence、秘密材料或选择完成的 Binding。价格公式或库存不变量可以是作者源中的合法业务规则；其当前求值及现实观察不回填 descriptor。Provider 可以拥有真实领域数据库与状态，禁止的是对同一对象/作用域/语义面建立竞争写者，不是禁止有状态产品。

仅需可发现表单/配方时用 AuthorLibrary/Definition metadata，不强制注册 SemanticModule。只有公共消费者必须理解新的可观察区别，才按[语义扩展](../组合/语义扩展与定义接合.md)建立可选语义方法；只增加新行业、新名字或新 UI 不足以修改 Kernel。64 类[发现坐标](../../00-系统与原则/设计方法/机制适用性与覆盖坐标.md)不是封闭 facet 枚举、安装清单或每项目启动集合。

<a id="catalog-view"></a>
## Catalog：固定读取基础、任务切片与真实覆盖

Catalog 由 application 在准确 `ProjectView + EngineImage`、明确导入/模块使用域和请求范围下派生。EngineImage 拥有已装配的静态方法/描述符索引；项目视图决定作者源、导入和可见名字；当前披露资格由真实调用上下文检查。不能为了查询目录扫描全生态、安装包、执行项目初始化代码或联网补齐引用。

每个条目返回准确 facet/owner/ModuleUse、作者参数与动作形状、所需依赖、支持的投影、静态缺项及实际覆盖。`已定义`、`已发现`、`已装配`、`方法符合静态要求`、`本次已绑定`、`当前准入`、`实际 Evidence` 是不同关系，不能压成一个 `available=true`。需要显示动态健康/许可时引用单独取得且有时效、范围的观察，不烘焙进不可变目录或据此许可未来操作。

查询按名字、任务、主体/类型、参数需要和已明确启用模块筛选；默认限量、分页、延迟加载。返回范围必须区分完整可见集合、仍可续页、预算截断、被限制/不可读及确实未装配。无命中不证明世界上不存在该能力。隐藏对象的名称、计数、排序和错误细节也受披露规则约束，不能通过“缺少三项”泄露不允许看的模块。

目录缓存记录实际描述符、导入成员和负依赖；无关图形或 ML 库不进入没有相交需求的项目闭包。分页游标绑定原视图/筛选/排序及连续范围；切换 EngineImage、导入或可见性后不能拼接为同一完整结果。重新披露与形成候选时都复核当前资格，旧游标不续授权。

<a id="intent-expansion"></a>
## 从一个动作到普通作者候选

一次展开固定基础、facet 修订、动作身份、参数值、主体代换、默认来源、实际作用域和展开方法。先严格解码与核角色，再按已有需求/Profile 规则卫生实例化，生成原 `AuthorDelta`。它可以引用或创建 Definition、Requirement、Control、原生作者区域和输出选择；结果包含准确源改动、贡献/缺项、实际读集及可供审查的来源，不引入私有 IntentRecord。

展开先在私有候选中完成；名称捕获、重复写入、跨模块身份、同主体约束和目标冲突交原 owner 判断。新声明使用原创建身份和请求去重规则，两次真实实例化不会因参数一样被误合并；同一请求的重放不能凭随机生成新名字造成第二次创建。Profile 菱形传播与真实多次使用沿既有贡献身份，而非按数值相等去重。

默认只补已有明确合同允许的内容。存在独立业务选择时返回准确缺项或候选，不以标签、示例、排名或 LLM 猜测替作者决定；已有有效委派允许的确定选择可自动完成，不增加无意义人工确认。绑定动作表达的是要求/选择请求；真正 Method/Provider 的采用仍由 Decision 与 RealizationBinding 形成，后端和 facet 不自行选库。

无法完成的开放引用/类型可保留为有诊断的合法草稿；协议非法、越权写入或破坏未知载荷保全的改动不能作为已接纳 AuthorDelta。需要真实工具、网络或昂贵外部求解时返回原 ActionPlan/Need，由 application/Execution 按权限取得输入形成后继固定基础；不能隐藏在目录 getter、表单默认、预览或纯内核里。

候选删除意图 UI 后仍有完整普通作者源；展开来源可作为原有 provenance/源映射引用保存，但不拥有可独立编辑的第二业务状态。模板更新不自动重写既有实例；重新应用或迁移必须展示准确差异、检查原前像与保持帧，用户定制不能被新版默认吞掉。

<a id="occurrence-view"></a>
## Occurrence：贯穿全链的有依据追踪，不反向发明原意

以已有 Definition/Requirement/Source/输出根为起点，追踪其有类型关系：作者基础与贡献 → 有效 RequirementInstance/语义 Needs → 合格候选/拒绝理由/Decision → RealizationBinding 与使用点 UseBinding → TargetProgramPlan/ArtifactSet → Claim/义务/方法/合格 Evidence/Verdict；存在现实作用时再接 Operation/Attempt/回执、实际效果、协调与资源结算。每条边保留对象修订、来源、关系种类、范围和可见性，不能按名称相似或时间接近拼成一条“成功链”。

原作者保存了展开 provenance 时，可以说明实例由某个 facet 动作派生；只有结构匹配时只能显示可能匹配、歧义或未记录来源。两个不同意图可以展开成同一结构，一个实例也可同时有多个 facet；不可逆映射不能声称唯一恢复用户原意。未有 facet 元数据的原生代码仍可查看、编辑和导出，不被视为非法工程。

本视图不新建一个跨层生命周期枚举。作者候选可未采用，纯检查可完成，目标工具可缺失，操作效果可未知，证据可部分合格，清理可仍在途；必须同时表达。一个 Requirement 可以由直接语义检查、证明、既有供给或新的实现/运行义务满足，不强制每条都新建 Binding。未发生的工具调用、外部操作或读回显示未请求/不可用/未取得，不伪造空回执。

动态操作与 Evidence 只读其真实 owner。记录了编译产物不等于当时运行过；Provider 健康不证明目标语义；运行成功不证明所有产品质量；单项证据不签发整体支持率。受限链段保持其范围缺口，不跨租户借证据补齐。

<a id="facet-evolution"></a>
## 演进、故障与可检查边界

表现名称/分组改变只失效实际消费它的呈现查询；参数含义、默认、需求模板和展开方法改变则失效相交展开/检查。完整 descriptor revision 可以作为粗粒度健全基础，允许在有精确子内容依赖时进一步复用，不能为减少失效省略依赖。原已接受源仍按原解释成立，更新目录不是强制迁移全部旧实例。

目录不可用只影响发现；准确已知源和已固定依赖的编译不被无关目录服务拖停。展开失败保留原候选/草稿，保存冲突按现有重基，不使用 LWW。权限撤销阻断新披露和相交动作，不删除在途恢复责任。关闭最后一个图面板不清理外部 Operation；worker 重启不把短句柄当长期 facet 或 source identity。

验证至少区分：同一动作从表单/CLI/AI形成同义源；旧 facet 修订重放；两个独立实例 vs 同请求重发；菱形贡献 vs 两次真实使用；隐藏条目与真实不存在；结构相同但原意不同；模板默认变化但用户定制保留；图禁写时文本合法编辑继续；编译结果/作用结果/证据资格分别展示。具体[纵向符合性](../../60-保证与证据/验收/意图覆盖与纵向符合性.md)复用既有研究与反例，不把目录数量当覆盖证明。

## 意图解释产物的机读边界

### 定位

`IntentIR` 保存用户、产品和工程主体提出的目标候选，不把自然语言直接当作可执行规范。它允许歧义、冲突、未知和多个解释分支，但禁止把实现细节误写成已接受目标。

### 结构

```text
IntentIR = exact {
  intentRef,
  actorAndAuthorityRefs,
  outcomeAndNonGoalCandidates,
  scopeCandidates,
  hardConstraintCandidates,
  preferences,
  requiredAndForbiddenCapabilityCandidates,
  acceptanceClaimCandidates,
  stakeholderAndRiskCandidates,
  assumptions,
  unresolvedTermsAndReferences,
  alternativeInterpretations,
  sourceAndProvenanceRefs,
  validityAndRevision
}
```

`outcomeAndNonGoalCandidates` 的 `non-goal` 不能自动转成 `forbiddenCapability`。意图解释要区分：不请求/不承诺、明确约束下禁止、条件例外、反事实例子与待决否定；保存原语言的歧义、条件范围、发话主体、来源和采纳权。只有有权采纳的准确解释才能写入各真实 owner；若“本版本不交付搜索”被误降低为“运行时必须禁止任何搜索”，将错误地限制其它已接受模块；若“禁止外发患者数据”被降低为“不提供外发功能”，又不能约束通过其它 API 发生的数据离域。两种错误都应由同一组对照用例拒绝。

### 语义层次

| 层次 | 允许 | 禁止 |
|---|---|---|
| raw utterance | 原始文本、图、表、点击和 API | 直接授权 Effect |
| parsed intent | 候选动作、对象、约束和范围 | 自动选择唯一解释 |
| normalized intent | 术语绑定、量纲、否定、时间和法域 | 把未知补成默认 |
| accepted intent | 有权主体完成采纳裁决后的**接受记录/投影**，精确引用由各自owner写入的Definition / Requirement / Claim / Preference revision | 自己成为第二个L1 writer；混入 Provider、路径、临时环境 |

### 歧义

```text
IntentKnowledgeState =
  exact
  | ambiguous { alternatives }
  | conflicting { witnesses }
  | incomplete { missing }
  | unsupported { construct }
  | rejected { constraint }
```

系统只能在安全且不影响目标的默认值上自动补位；会改变不可逆结果、权利、成本、作用域或技术路线的歧义必须保留或交给有权主体。

### 意图等价

两个自然语言表达只有在规范化 outcome、scope、constraints、acceptance、stakeholders 和 authority 相同后才可视为等价。字符串相似和嵌入相近不能建立语义身份。

### 降低

```text
IntentIR candidate / provenance
→ authorized adoption decision
→ Product/Domain Definition revisions + Requirement / Claim / Preference revisions（分别由其owner写入）
→ 已采纳模型的确定性编译，或在确有未决设计时形成 DesignSearchProblem
```

降低必须生成来源映射和未解析 frontier。`IntentIR`保留候选解释与来源，不拥有“已接受语义”的第二份 current state；采纳只通过各目标owner的typed transition形成新revision，接受记录引用这些revision。后续设计不能反向修改原始意图，只能提出 `IntentRevisionProposal`，再由有权主体决定是否形成新的作者事实。

### 验证：意图中间表示

- 否定、条件、例外和量词；
- 同名对象不同 scope；
- 用户要求与法律冲突；
- “尽量快”缺少质量边界；
- 要求具体框架但框架不合格；
- 多轮会话中目标变化；
- 模型生成的解释被错误当作用户确认。

<a id="universal-intent-completeness-rule"></a>
## 任意意图的接受、推导与缺失而非业务脚本黑箱

一句“设计一款像专业 IDE 的软件”是目标表达，不包含编辑模型、远程授权、插件兼容和离线行为的全部事实。意图辅助按已有 `Descriptor/Catalog/Occurrence` 和普通 Requirement/Definition 将用户说出的内容、既有作者源/第三方供给中已存在的内容及仍需决定的内容**分别定位**。仅具备候选证据的“常见 IDE 会……”不自动成为用户正式采用的 Requirement。

通用发现优先从以下独立问题类别扩展，而不是靠固定行业模板猜业务：对外功能与负行为、输入/输出/协议、状态和持久化、并发和时序、权限/信任/隐私、资源/性能/规模、运行目标、异常/退化/恢复、可维护与版本兼容、配置/资产/发布、真实供给/依赖、观察和验收范围。它们是发现视角，不是十二张强制表格；作者已明确且可复用的事实只引用，缺失不由模型编造。

一次 design-only 会话可在完成需求发现后直接结束于有条件的 TargetProgramPlan 查询，完全无需 `gift.preview` 生成代码，也不调用 `gift.check(types)` 或真实构建。用户后续选择“生成源/执行检查”才进入其他实际出口。AI 负责候选解释与发现，正式编译不在每次重现中再次要求模型决定同一需求；缺算法、关键性能约束或真实Provider时返回具体 Need，允许交付已闭合设计分区而不能假造完整业务。

## 意图投影应呈现真实业务问题而非计算语句

面向产品作者优先展示“谁/哪个资源/何时/什么必须成立或不可发生/如何确认/谁批准/失败怎么办”，并把从现成语义库自动继承的定义来源可展开。业务作者需确认具有实质差异的未知政策，不必填 `recursion/typeParameters/SQLTransaction` 这类实现字段；真正遇到 `NeedsMethod` 时给专业供应者创建入口，不能以“请改写成通用函数”取代正常交付。
