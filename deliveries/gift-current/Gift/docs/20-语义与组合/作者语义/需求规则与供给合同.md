# 需求定义与供给合同

本章唯一规定 **RequirementDefinition 的声明、实例化、组合、实现绑定与验证接口**。Gift Core 不内置 IDE、医疗、金融、制造、游戏等行业规则目录；具体产品词汇、对象、流程、硬约束及配方由有权作者或选定定义/库提供。领域增加新 Requirement 不要求新增 Kernel 的 ProductKind 分支。

一个完整的具体产品可以有成百上千条 Requirement，但这不会自动增加 Core 枚举。Core 只要求这些 Requirement 有稳定身份、类型化字段、明确主体与观察、可检查的正常/失败/帧/进展语义、真实实现责任和 Evidence 责任。复杂 IDE/Workbench 的旧具体规则若需追溯，在同包[组合研究](../../../fixtures/compositions/README.md)保留完整要求与例子，作为非权威研究输入；本合同只吸收其中可复用的区别，不让旧产品规则取得现行 authority。

<a id="requirement-definition-contract"></a>
## 定义不是营销名称，参数也不是任意JSON

一个可进入强编译/验证路径的 `RequirementDefinition` 至少固定：

| 维度 | 必须固定的内容 |
|---|---|
| **identity / revision** | 稳定 Definition identity、准确 revision 与来源；显示名不参与相等判定 |
| **subject schema** | 被约束对象的类型、允许的引用角色和必要关系；同类型不同主体不能按名字合并 |
| **field schema** | 字段身份、必需性、类型、值域、单位/编码/名义枚举或其他 Type-owned codec；未知字段的处理策略 |
| **observation domain** | 哪些输入、状态、事件、时间窗、资源或外部观察参与判定；没有定义观察域不能声称“满足” |
| **normal semantics** | 合法前提下必须产生的可观察行为/结果，而不是只列一个功能名 |
| **failure semantics** | 非法输入、资源不足、外部故障、取消、超时、未知结果等怎样区分；失败不能被吞成成功 |
| **frame / preservation** | 哪些对象、状态、顺序、效果或资源不得被该 Requirement 无意改变 |
| **progress / termination** | 是否要求终止、最终进展、持续服务、可取消或只允许有限停顿；不能用永不工作满足安全条件 |
| **composition rules** | 与同主体其他 Requirement 如何合取、冲突、条件化、量化或保留独立来源 |
| **realization obligation** | 什么样的方法可以声称消除了哪些义务、必须声明哪些前提/效果/依赖/残余 |
| **evidence obligation** | DesignSpecified、Implemented、Verified、Adopted 等既有状态需要什么来源；定义本身不签发实现或验证 |
| **evolution** | 字段/语义变化如何形成新 revision、兼容如何证明、旧消费者遇到未知能力怎样拒绝或保全 |

`SubjectRef<K>`、`DefinitionRef`、`RuleRef`、`PredicateRef<T>`、`Selector<T>` 都必须按各自签名解析为已有身份，不可仅凭 JSON 可序列化就强转为字符串或彼此互换。值类型与解释由[类型与值](../基础语义/计算基础/文法类型与求值.md)及实际 Definition 拥有，Requirement 层不设 Money/Coordinate/Tensor/Workflow/UIControl 万能负载。

字段顺序只是承载顺序，除非对应 Definition 明确赋予顺序语义。集合、列表、关系、多重集、事件流和时间序列不得按“都能放数组”互换。一个字段缺省是否有 default、default 从哪里来、是否被显式 Pin，由定义与作者源的唯一 owner 说明，不由实现方法补一个方便值。

未知 Definition、未知 revision、字段 codec 不可用、字段值非法、预算不足、读取不完整分别保留准确失败/Unknown；不能把它们降成 Text 或忽略后继续强编译。

## Requirement catalog 是开放定义空间，不是 Core 功能菜单

Gift 可以加载/引用很多 RequirementDefinition，但 catalog 的成员来自实际作者/库/Provider 及其锁定 revision，不来自一个全局 `ProductKind`、行业枚举或“官方 35 条规则”。

因此：

- 新增一个业务规则通常只新增 Definition，不改 Gift Core。
- 新增一个产品操作通常只新增主体/Requirement/接口与相应实现，不改 Core command enum。
- 新增一种行业对象通常只新增领域 Definition、Type、关系和 Provider，不改 Core object enum。
- 新增一种实现策略通常新增 `RealizationMethod`/Binding 候选，不改 Requirement 的 Meaning。
- 新增一个 Target/宿主只提供真实能力、ABI、资源与发射规则，不令同名 Requirement 自动满足。

Core 只在现有身份、组合、类型、作用、时间、证据或演进协议**无法无损保存一个跨任务稳定可观察区别**时才重开。具体提升条件由[核心提升规则](../../70-工程系统与演进/演进与实施/作者定义组合与核心扩展.md#core-promotion-rule)拥有。

<a id="requirement-subject-and-observation"></a>
## 主体、观察和义务必须分开

Requirement 约束的是逻辑主体及其可观察关系，不等于要求为每个 Requirement 启动一个服务或创建一个对象。多个 Requirement 可以共同约束同一主体，一个实现实体也可以同时履行多个 Requirement；反过来，同一类型的两个主体只要身份不同就不能共享状态结论。

一个 RequirementInstance 至少保存：

1. `definitionRevision`：准确 RequirementDefinition revision；
2. `subjectBinding`：它约束的主体及必要关系；
3. `fieldBindings`：全部必需字段的准确值和来源；
4. `occurrence/source`：作者在哪个接受范围引入这项义务；
5. `strength`：硬义务、偏好或其他已有合同允许的角色；
6. `scope/condition`：若由条件、有限量化或 selector 产生，保留其作用域和见证；
7. `obligations`：由 Definition 解释得到、等待实现/验证的规范义务。

不能把 `RequirementInstance` 简化成 `(name, JSON fields)` 后丢掉主体、来源、条件和 Definition revision。实现选择、Impact、Evidence、迁移都需要这些信息。

<a id="generic-requirement-constructors"></a>
## 通用组合只拥有结构，不拥有业务含义

Requirement 的组合代数只表达义务之间的逻辑/作用域关系。现行结构作者面的 `all / any / when / forEach / exists / use / require / prefer` 仍按[结构化作者源码](../../10-作者与输入/作者源/结构化源码.md#finite-requirement-composition)解释；它们不变成业务关键词。

可复用的通用构造具有以下边界：

| 结构 | 含义 | 不能偷做的事 |
|---|---|---|
| **All / conjunction** | 同一有效范围内全部义务共同成立 | 不按最后写入覆盖冲突 |
| **Any / alternatives** | 至少存在一个**完整**满足共同前提的方案 | 不能从各分支各挑一部分拼成从未定义的方案 |
| **When** | 在准确条件域下引入/选择义务 | 编译期未知不能当 false；运行期条件需要运行方法 |
| **ForEach** | 对已定义域中的每个成员实例化同一义务 | 动态域不能用构建时枚举冒充全部未来成员 |
| **Exists** | 在已定义域中保留一个满足义务的见证 | 见证不得依赖未声明的未来信息；空域不伪造成功 |
| **Use** | 复用一个已定义复合 Requirement/Definition | 不启动运行活动，也不复制 Definition authority |
| **Prefer** | 只在满足硬条件的候选之间表达有定义的比较 | 未测成本不当 0；偏好不能删除硬要求 |

诸如“noninterference”“statistical target”“transactional consistency”“render frame”“medical consent”等名字都不是 Core constructor。它们若有稳定语义，就作为普通 RequirementDefinition/Standard Semantic Module/领域定义进入；Gift Core 不因名字常见就把它们变成保留关键字。

## 类型化字段和开放 codec

Requirement 字段通过已存在的 Type/Definition 解码。基础 Bool/Int/Text 只是基础环境中的值类型；列表、集合、record/variant、数量、时间、URI、图、张量、领域对象等均由实际 Type 合同拥有 canonical value、相等、范围与 codec。

通用层只能在 Type 正式公开相应能力时执行：

- equality / ordering；
- canonical encoding；
- field/member projection；
- numeric or dimensional operations；
- serialization / transport；
- merge / migration。

没有公开能力时保持 opaque，不通过 JSON path、反射、字段同名或宿主语言对象布局窥探内部。Type revision 改变上述语义时，相交 default、Condition、Binding、缓存和 Evidence 按真实影响失效。

## 正常功能、失败、帧与进展不能被实现自行缩窄

一个 RequirementDefinition 可以有很强的前提，但这些前提必须是作者可见且语义上成立的定义域，不允许 RealizationMethod 为了容易实现而临时加上“输入永不为空”“不会并发”“只在 Linux”“永远联网”等隐藏条件。

实现方法可以声明自己只覆盖 Requirement 定义域的一部分，前提是：

- 该部分是 Requirement/Target/Provider 合法可表达的选择；
- 编译器把未覆盖部分保留为义务或选择其他方法；
- 最终声称完整支持时，所选根要求的定义域已全部封闭；
- 不通过总失败、无限等待、忽略输入、吞副作用或只生成接口骨架满足“安全”。

业务错误、资源错误、权限拒绝、目标不支持、取消、超时、未知结果和内部故障按相交错误协议区分；只要真实效果可能已发生，重试/恢复就必须消费原 Operation identity 与 read-back，而不是盲目重新执行。

<a id="realization-methods"></a>
## Requirement 到真实实现的方法合同

Gift 不维护 M01—M14 这类固定“产品实现步骤表”作为 Core。一个 `RealizationMethod` 的资格由其**实际输入/输出合同**决定，而不是方法编号或产品关键词。

一个可被选择的方法至少声明：

| 项 | 内容 |
|---|---|
| `methodRevision` | 方法本身的稳定身份、revision 与来源 |
| `covers` | 能消除的 RequirementDefinition/义务形态及定义域 |
| `subject/target constraints` | 可适用主体、Target、ABI、Provider、资源、平台或运行条件 |
| `reads` | 语义、实现、资产、配置、外部事实和版本读集 |
| `preconditions` | 必须已成立的前提；不能循环引用本方法将要证明的结果 |
| `inputs` | 准确 RequirementInstances、Binding、Type/Effect、Target/Provider facts 等 |
| `outputs` | 实现片段、映射、TargetProgram 贡献、资源/配置贡献或其他已定义实现结果 |
| `effects` | 编译期/运行期需要的外部效果、权限和生命周期 |
| `preserves` | 必须保持的行为、接口、来源、顺序、资源和兼容条件 |
| `residuals` | 本方法不能消除而必须继续传播的义务/Unknown |
| `evidence plan` | 采用前后需要的检查、证明、测量、符合性或运行 Evidence |
| `cost/quality facts` | 若参与优化，只记录真实已知口径；未知保持未知 |

多个 Requirement 可以由一个方法共同消除；一个 Requirement 也可以由多个方法组合完成。组合必须显式证明共享前提、数据/状态所有权、效果、资源、失败恢复和 Target 边界相容，不能因为两个方法分别“支持”就自动兼容。

实现选择只在满足硬条件的候选中进行。候选发现可以来自本地库、Provider、已有原生工程、生成方法或受控创作，但名字/下载存在/LLM 建议都不签发资格。采用后 Binding 固定准确 method/provider/input revisions；重建不重新解释自然语言或按当前网络环境随机换实现。

## Requirement、实现、Target 与 Evidence 的完成状态分离

以下事实不能互相代签：

- RequirementDefinition 已定义；
- 作者实例化了一项 Requirement；
- 找到候选 RealizationMethod；
- 方法通过静态资格检查；
- Binding 被采用；
- 目标成员已生成；
- Artifact 已封存；
- 运行/符合性 Evidence 已取得；
- 某个 Claim 在指定范围内成立。

现有系统各状态 owner 继续拥有这些事实；本页不新增一套平行状态机。UI/AI 可以投影成“缺实现/缺目标/缺证据”等便捷状态，但写回仍修改真实 owner。

## 演进、兼容与未知能力

新增 RequirementDefinition 不要求旧消费者理解它；旧读取器遇到未知 Definition/revision 应按协议保全并拒绝超出能力的强解释。Definition revision 发生语义变化时，既有 RequirementInstance、RealizationMethod、Binding、缓存和 Evidence 是否可复用必须逐相交关系判断，不能只因名字不变继续沿用。

兼容声明至少说明：

- 哪些旧实例在新 revision 下保持同义；
- 哪些字段/默认/主体/观察改变；
- 旧方法是否仍覆盖；
- 目标/Provider 是否需要重新协商；
- 已运行状态是否需要迁移；
- 旧 Evidence 是否仍支持原 Claim，还是只保留为历史观察。

删除 Definition 或某个值不会自动删除引用它的作者源和历史 Evidence；新的强构建应报告不可解析/需迁移，历史记录继续按原 revision 可追溯。

## 业务与产品组合如何进入，而不污染 Core

一个游戏、仿真平台、金融系统、IDE、编译器、医疗应用或任何其他产品都可以定义自己的主体、Requirement、Type、关系、算法、Target 与 Provider，并复用 Gift Standard Semantic Modules。它可以非常复杂，甚至形成完整第三方/私有领域库；复杂度不是把它提升为 Core 的理由。

只有当不同业务中反复出现的**同一个稳定区别**无法由现有 Definition/Requirement/Type/Effect/时间/资源/证据/组合协议表达，而且继续留在库层会导致编译器无法保持正确性时，才提出 Core promotion。提升的仍是最小通用区别，不是整个行业模型或成品模板。

工作台、IDE、Web、服务、GPU、ML、仿真、游戏等具体产品/行业材料应留在作者/库层或 同包 `research/`、`fixtures/`、`witnesses/` 的非权威研究中。只有从研究中提炼出的准确 Claim、验证义务或跨域区别才进入 Assurance；研究材料本身不证明 Gift 直接提供、实现或支持这些东西。

### 需求闭包的否定条件、缺省值与未知参与者

一个合格的 `Requirement` 不能仅凭枚举到的实例逐项通过，就推断“所有实例通过”。若 Requirement 的量词覆盖**目前及将来加入**的参与者集合，完成结论还需要该集合在评价时的已知完整性、适用域和版本/水位；枚举失败、权限过滤、未装入的模块不等于空集合。这一职责属于定义的适用语义，具体获取覆盖由 workspace/Provider 给出，Assurance 依据固定 Claim 评价。

例如 `forall worker in activeWorkers: supports(worker, cancel)`：初始只有 W1，检查 W1 通过。随后 W2 注册但缺少 cancel，先前结论只对旧冻结集合成立；它既不是新的 Requirement revision 自动出错，也不能被拿来证明最新动态集合。对需持续成立的要求，由消费方声明动态有效期、订阅/失效来源及重评策略；来源无法完整枚举时保留 unknown，而不是把未见 W2 解释成 W2 不存在。

参数默认、未知和开放选择也必须分离：省略而已有**被定义认可**的 default，是有确定值的作者语义；明确 `any/exists` 才允许有范围的实现选择；未决定、未获许可或缺资料不能转换成任何一种方便的默认值。替换实现不能修改量词的作用域、缺省的意义或业务实例的覆盖集合。

<a id="gift95-cross-contract-6"></a>
## RequirementDefinition机器读取的有限观察Profile与资格

**精确限定：** 新增 `gift.rule-call-observation/1` 是尚未发布的结构子Profile，机器形状在 `fixtures/contract-closure/Gift95/schemas/req-rule-call-body.proposal.schema.json`；它不是替换本篇开放RequirementDefinition的全部语义，也不升级为业务规则枚举。其四槽结构对应现有Rule：

`strength.allowedTermModes` 是定义允许的使用模式而非实例strength的影子；`fields`仅拥有字段类型/必需性，实际字段值与来源由引入该Rule的 `require`发生位置拥有；`semantics`持有 `observation`、`normal`、`failure`、`frame`、`progress`，每个谓词必须指向真实公开、类型匹配且在要求观察域内允许的纯Bool函数或合格形式化谓词；`implementation.capabilityRefs`只列所需Method能力。

**实际解释算法：** R0固定Rule Definition内容及导入；R1完整校验字段与参数默认；R2通过BoundRoot/ModuleUse查主体及callable公开签名；R3核观察槽是否都具备合格解释，检查签名、效果与分支绑定；R4把每个正常/失败/帧/进展表达成各有来源的ProofObligation；R5由resolver寻找覆盖**同一观察域**的方法；R6依据实际证据逐项结算。若任何观察槽声明为`unresolved`，保留设计但阻止相关完整实现和保证，不可用“Schema PASS”关闭。

`PredicateRef`指向普通原生函数时，拿到源码或调用它一次不足以证明对所有适用输入成立；谓词若可能读取时间、文件、外部状态则必须由其真实效果模型检查，不能假定纯。各Profile可以由合格库增加其他观察模型，但要给出相同的主体、定义域、失败、帧、进展、变迁与Evidence责任，不改变Core的Rule接口。

**组合与重开：** `all`保留所有义务；`any/exists`保留共同实现见证；`when`的未知条件保持未决；动态集合不能只按某次枚举完成。Rule revision变化使精确消费的实例、候选、目标成员与证据资格按读集失效，旧证据保持历史事实。

## call-bound Rule 的跨文件最低有资格条件

一条 `req:rule` 的调用观测必须区分**定义**与**具体出现点**。Definition 提供 `strength.allowedTermModes`、字段类型/必需性、语义 Profile、正常/失败/帧/进展观察和能力要求；Occurrence 用实际 import/export 绑定公开 Rule，选择 `require` 或 `prefer` 并提供类型正确的字段实参。新增/变动字段必须按照 Definition 的必需性与值域逐项验证，不能因为 TypeScript 的形参类型是 `number`，便允许布尔值、负的 `minimumDelta` 或 NaN 进入正整数参数。

`gift.rule-call-observation/1` 的有限正常观察采用 `observation.callable` 和 `normal.predicate` 的精确逻辑符号引用。给谓词的每个 `arguments` 槽只能来自已定义的调用输入、正常返回或 Rule 实参字段；错误分支使用独立 error/失败槽，不能借成功返回伪装失败。语言适配器要读取实际导出签名、参数位置、赋值相容性与求值方式；谓词返回的静态 `boolean` 类型**既非纯函数证明、亦非谓词成立证明**。还需以所选语言对别名/对象变异、异常、数字边界与观测前后时点的定义，建立输入快照和输出的实际对应。

`failure` 需明确哪些可观察错误允许、哪些应保持状态和补偿；`frame` 要指明不得修改的对象与可观测外部资源，`progress` 需要实际调度/时间/公平性前提。无法检查时保存 typed Need 及其主体/适用域，不得将 `unresolved` 改写为无条件 `true` 或把类型检查当作证明。状态迁移、事件流和开放世界等其他 Rule Profile 必须逐个声明观察域、时间/采样、资源、环境和判定方法；本子 Profile 不覆盖那些领域，也不强迫它们转成一次同步函数调用。

产生 Method/Target 资格时必须满足 `rule.semantics.profile ∈ target.accepts`，并与 Method 的覆盖域、能力、原生符号和已检查 Toolchain 版本共同取交集。提供同名函数或同名 Profile 而版本/作用域不同，返回不兼容或未知，不走字符串相似性降级。

### 真实数值反例：静态 boolean 谓词不能定义数学上的单调性

本目录 `Gift96/native-boundary-check.cjs` 对同一作者 `Document` 的原生 TypeScript 实现，实际给出边界输入 `before.revision=2^53`。因为目标 `native-number` 使用 IEEE-754 二进制双精度表示，`before.revision + 1` 舍入回同一个数；`replaceText` 返回的 `after.revision` 与前像相等，但作者的 `revisionIncreases` 比较同样被舍入的阈值，返回 `true`。所以当前 Predicate 甚至在正常返回分支也可能误报满足“revision 至少增长 1”。`Readonly` 与 TypeScript `number` 类型不能限定安全整数域，此例在**没有作者先决条件**时构成真实反例，不是性能或源码组织问题。

采用此 Method/Target 前必须由作者/可信域定义 `Document.revision` 的合法输入域、增量类型与溢出/舍入政策：若按数学自然数判断，可以选准确整数表示（例如符合目标约束的 `bigint` 或检查溢出的整型），或对 `number` 的每次输入/输出严格验证 `Number.isSafeInteger`、非负性及 `before + minimumDelta <= Number.MAX_SAFE_INTEGER` 并在越界时按明确定义的失败语义终止。后一种选择还须证明异步/共享可变对象不存在输入快照漂移。Method 中的 `example.spec/checkedInputDomain` 目前只是未解析的适用域引用，不证明真实预置条件；类型检查通过也不能消除该 Need。

## 调用观察规则的有限且非空洞语义

采用 `gift.rule-call-observation/2` 的精确调用子域设计，不将它冒称整个Requirement语言。一次观察绑定一个callable Definition、精确泛型实例及输入元组，包含调用前状态、正常返回或异常、调用后状态，及由独立观察方法提供的进展证据。输入域由显式前置关系定义；正常返回谓词参数必须匹配输入和结果，错误谓词必须匹配输入和声明的错误域。`Result.Err` 是普通代数返回值，只有语义声明为异常的事件才进入failure分支。

Predicate参数严格分相位：`input`索引在签名范围内；`return`只在normal中；`error`只在failure中；`before/after`只能引用已声明且可观察的subject；`field`必须指向该Rule字段。观察器不能为了检查frame越权读取私有状态。`preservedSubjects`与`allowedEffects`只是待核的集合，不能由列表为空直接推出纯性。运行后未读到状态是ObservationNeed，不是保持成功。

`not-applicable`必须有可核basis：例如语言定义及已核方法排除异常，或合同有意无正常返回。不能为了让坏实现过关把失败分支标不适用。`unresolved`产生对应义务并沿组合传播；普通未要求强证明的程序可以保持未证状态，但不能签该强Claim。

进展不是一次调用前后Bool足以覆盖的性质。第二版progress严格为 `{kind:"obligation",claimRef,checkerRef}` 或已有unresolved对象；claimRef解析到定义输入域/假设/进展性质的真实Definition，checkerRef解析到核验其类型化Evidence的checker，Evidence从Assurance供应取得而非由返回值代替。普通 `(inputs,result)->Bool` 不再是合法progress形状。真实运行中尚未返回时也必须由已绑定的进展证据/监测策略解释，而非永远等正常返回才检查。无限交互的fairness、最终响应及跨运行关系由claimRef所选轨迹语义Profile承担。

从历史Rule迁移时保持正常/错误/帧/进展的独立义务。新加入错误观察不是旧只有normal的规则“自动更严格且兼容”；按依赖重新核方法。对空合法域、有意永不正常返回和正常总函数分别建立合格/不适用/不可满足的判据。

Gift95的 `/1` proposal仍原样保留；迁到 `/2` 必须为旧progress谓词明确绑定性质与checker，不能自动将普通Bool函数换标签。normal/failure/frame字段的正确参数和观察保持；只是schema号相似不构成兼容。这一非兼容设计修复以精确内容锁及明确迁移区分，未对历史样本重写。

**验证与反例**：检查return/error错位、Bool签名正确但进展域错误、无basis的不适用、before越权、正常Result.Err与throw混淆、永不返回实现的非空洞性。

**实际能力边界**：生产轨迹观察器与独立证明checker未实现；schema通过不赋予进展资格。

### 精确 Revision64 值域、Rule 参数与失败语义的具体裁决

对“成功更新后数学意义上的 revision 严格增长”的 Requirement，作者须分别确立：允许的**输入域** `0<=revision<=2^64-1`、发生点 `delta` 的正整数范围、成功的结果关系 `after.revision=before.revision+delta`、越界的失败分支 `REVISION_EXHAUSTED`、失败是否允许任何作者可见状态变化，及 objectId/generationId 一致性。对 `delta=1` 的单次改写，若 `revision=2^64-1`，不可能在 Revision64 内实现“正常成功且更大”；解决方式是**拒绝正常提交并给出定义明确的失败**，不是让结果回绕为零。若产品要求在上界仍成功，必须换成无界整数或准确的世代切换协议，重新协商 Require，不得把有限成功的条件删掉后宣称语义等价。

`req:rule` 保持观察关系与成功/失败/帧/进展义务的唯一语义 Owner。数值编码方式和 `bigint` 是本次目标实现画像，**不是**把这两个词写进业务 Rule 就获得认证。参数 `minimumDelta` 的 JSON 正整数形式和目标 Runtime BigInt 必须由经过验证的 Codec 无损转译；若大于 Number 精确范围，不能先用 `JSON.parse -> number` 再转 BigInt。判断谓词本身不能作为自身正确性的唯一证明；独立 Oracle 至少在数学整数上比较两个准确的十进制值，另证调度与外部更新帧义务。

Gift97 的可执行规范**受限样本**是 `fixtures/contract-closure/Gift97/revision64/`，有独立 TypeScript 源、canonical decimal wire 和反例回归；它未改变 Gift96 原本 `number` 算法的事实，也没有使 Gift96 Rule 四类残余全部成为已证明。
