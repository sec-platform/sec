# 开发者意图、控制决定权与源码存储：具体分工合同

> **责任范围**：本页解释已定义的作者决定如何放入实际工程，不重定义[开发者决策模型与设定面](开发者决策模型与设定面.md)中五类决定、六类authority、三类scope及DEC0—DEC9的判断规则。行业案例用于检验开放语义的适用范围，不形成Core枚举；本页的“应”只规定设计，不证明生产Reader或Target已实现。

## 0. 一次实际改变先判断五件不同的事

1. **改变什么？** 是可观察的产品Meaning、可验收性质Requirement、合法实现空间Realization Control、当次现实输入Runtime Input、还是开发工具Preference？不能通过`timeout/limit/name/security`等键名猜类别。可能一个自然语言愿望需要拆为多项不同决定。
2. **谁拥有写权？** Author（含有相应角色的团队成员）、External（法规、标准、第三方供应及组织强制政策）、Compiler/Resolver（派生选择和锁）、Runtime/Execution（运行资源、授权和回执）、Assurance（证据与判定）、Client（只负责展示）。**作者提出某个愿望**不等于拥有外部规则、现实资源或测量结果的签发权；AI没有独立第七类authority。
3. **作用在哪里？** 作者/编译scope `Project → ProductRoot → Module → Definition → Use/Occurrence`加独立target限定；运行scope `Deployment → Instance/Session → Operation/Attempt`；客户端scope `User → Workspace → Window/View`。不同scope图不能靠“路径更深就覆盖”合并。
4. **当前是哪种事实阶段？** Declared、Effective、Planned/Resolved、Applied、Observed分别可同时存在；Evidence对精确Claim另行评价。作者可改Declared但不能手动改Planned/Observed/Evidence伪装结果已变。
5. **它应落在哪里？** 作者Definition/Requirement与合法原生源码、独立稀疏Control、项目manifest、target/native config、运行输入/Grant、客户端配置、外部权威资料、派生锁/制品或Evidence。**JSON只是若干落点的物理载体，并非统一语义类型。**

### 哪些信息必须由有权作者固定？

- 独有产品目的、主体身份、允许的输入/环境、正确结果、错误/进展与外部观察；现成Definition已完整规定的部分可以引用不复写。
- 在多种合格行为**有产品含义差异**且未明确委派时：需要作者选择/补写Requirement。不能由模型的“常见惯例”推断，例如货币舍入、Unicode索引单位、是否允许数据出境、异常时是否重试、用户能撤销多少次等。
- 不可补偿硬约束、可观察兼容性与法域/主体适用的政策；若是第三方强制要求，作者只可对自己的产品添加更强要求或改变目标范围，不能改写强制事实。
- 只有当前有权的人/系统才能批准的现实动作：生产发布、删除、付费、秘密读取和非可逆迁移。即使作者源表示“应该部署”，也不自动获得Runtime Grant。
- 明确Pin或实现限定只有在其对真实业务、互操作、运维有价值时才记录；对未要求的内部细节，**委派**Resolver在合格候选中选择并保留来源。

### 哪些不要求作者填写？

- 可从准确公开定义、输入、锁、目标能力和适用默认**严格推导**的内容，例如导入闭包、重复调用的实例化关系、Type/Effect检查、有效约束的合取和部分格式映射。
- 对已完整限定结果无观察区别的算法、容器、布局、优化Pass、文件私有命名、Worker个数等；按合格实现、稳定策略及成本目标选择，**不能越过硬约束**。
- 源码哈希、Binding结果、IR、缓存、依赖锁的解析结果、Artifact生成谱系、真实进程ID、费用和测试观察；作者只能改变合法输入或请求新操作/验证，不能编辑派生数据当事实。
- 外部现实和官方权威声明；作者能引用/质疑/选择供应，但不能凭本地配置改变第三方许可证、设备支持能力或现实读回。
- 运行时秘密的实际值及权限令牌，不应复制到作者控制JSON；参数schema和SecretRef可以分别由准确owner维护。

## 1. 明确的共同操作语言：不是一切都叫配置

| 用户意图 | 正式动作及真实writer | 结果与限制 |
|---|---|---|
| 新建数据类型、规则、算法、API、状态机、产品UI | `Edit Meaning`写Definition或原生源码的当前owner | 修改产品合同；若代码供给缺失，保持Need，不靠生成空函数成功 |
| 必须具备某性质 | 在主体/范围下写`Requirement`，或对**正式存在的**Control descriptor写`mode=require` | 硬条件合取；任何局部Require不得放宽外部或上层硬条件 |
| 更偏好某性质/方法 | 对产品性质用Requirement preference，对实现选项用Control `mode=prefer` | 仅比较全部硬条件合格的候选；不能用打分“补偿”硬失败 |
| 指定版本、Provider、算法 | `Pin`是对存在精确引用和值合同的descriptor做`require` | 原控制存储没有`mode=pin`；若引用失效则Need，不篡改锁 |
| 禁止某候选 | `Forbid`只在descriptor提供Bool/denied-set/allowed-set等确定性否定语义时转成相应hard | 禁止字符串黑名单、UI隐藏候选代替真实过滤 |
| 不再限定当前scope | `Auto`表示此处无本地控制；`Reset`是删除本层记录并重新求Effective | **不同于**写`null`或持久`auto=true`；父级hard仍生效 |
| 改现有Rust/TS工程源码或Cargo/npm配置 | 在真实native作者源做受控编辑，适配器回读 | 只有真正获得作者接管资格时才可将派生产物变成作者源 |
| 提供本次运行配置与凭证引用 | 走Deployment/Session/Operation输入和实际授权流程 | 不进入 `gift.control-file/1`；执行须有真实Grant |
| 改开发工具主题、过滤、窗口 | 走客户端偏好 | 不改变SourceRevision的工程语义部分或目标生成 |
| 修改“编译器选择了什么/测试结果是什么” | **没有这种直接作者动作**，应改根因后重求或重新验证 | 只读派生与观察不能取得第二写权 |

## 2. 35组具体权责与保存路径

本表中的“作者”是对相应对象有实际写权/采纳权的主体，不是仓库可读者；“本例”的归类只对所列可观察条件成立。决策族 `M/Q/C/R/P` 分别为 `M`=Meaning、`Q`=Requirement、`C`=Realization Control、`R`=Runtime Input、`P`=Presentation Preference，由自身 Owner/阶段保存；事实族 `X/D/E` 中的 `X`=External事实、`D`=派生事实、`E`=观察/证据受独立 authority 管辖，不是第六至第八种普通用户决策。新增场景须按实际行为重新判断归属，不能仅套同名字段。

### 01 工程边界

| 具体区别 | 类型 | 有权开发者能做什么 | 其他权威、默认或派生责任 | 正式位置与不得偷换 |
|---|:---:|---|---|---|
| 产品交付目的和接受范围 | M | 定义ProductRoot与所需公开功能 | 系统可展开已接受定义但不创造未给出的私人目标 | 作者模块和工程清单；不能由Target名称或示例目录猜产品范围 |
| 工程模块身份与公开出口 | M | 声明模块、导出、合法组合 | 解析器据源固定身份与引用图 | gift.project.json及作者模块；物理目录或文件名不自动等于语义身份 |
| 自动生成的模块拆分和私有文件布局 | D | 通过真正要求或有描述符的目标控制限制 | 规划器在允许空间内确定并记录来源 | TargetProjectPlan派生数据；不得回写为另一份作者模块 |

## 3. 对所有类别都适用的精确求值算法

### DEC与请求协议（复用现有owner，不另建状态机）

- **请求入场**：固定有权的AuthorSnapshot、主体与真实owner、目标和作用域、当前Schema/Descriptor修订、调用者权限、编辑前像。请求必须标出实际改变哪项Meaning/Requirement/Control/Runtime/Client。不能从UI字段标签猜，不能拿旧数字数组索引当对象ID。
- **解释硬义务**：解析模块、接口、独立领域Definition与外部强制条件；对同一生效主体的hard Requirement/Control按所属规则合取。任何冲突返回`CONFLICT`与准确贡献源；不能最后写入覆盖、不能soft score抵消。
- **推导与缺省**：来自已接受定义、同范围Profile、目标/ABI和精确版本Default的值必须列出producer/provenance。缺省不允许擦除显式Pin；`Unknown`不是`Auto`；默认没有合法owner时保留Need。
- **有限委派**：只有作者未固定且全部约束允许、Provider/Target真实支持、供应资格已检查的选项才供Resolver选择。偏好只能对合法选项排序。无候选返回`NEEDS_IMPLEMENTATION`/`UNSUPPORTED`，搜索预算耗尽返回明确未完成，不能宣称“已证明无解”。
- **冻结与执行**：产生Binding/TargetProjectPlan/ArtifactSet并锁其准确读集、输入和版本；保存/构建/部署分别需要真实消费者与授权。计划只是Planned；成功写文件只是Applied范围内的事实；运行表现需另外Observed。
- **保证**：验证报告对准确Claim、工具/版本、环境、覆盖、时间签发。作者只能规定门禁与验证任务；不直接写`PASS`。读集、Grant、约束或实测改变时局部重审对应结论。

### 用户什么时候必须被要求决定，而什么时候不应该打扰？

出现下列情况必须取得对应有权决定，否则将相交 Root 保持未决：尚未接受的外部可观察业务规则；真实 Effect 的合法 Grant；影响正确性/安全/兼容的必要硬参数；未经委派的互斥产品或不可逆取舍；费用或受保护数据披露授权；不存在合格现成 Method 而必须创作实现；相互冲突的权威仍需裁决。已由 Definition/Profile 确定的容器、线程或编译 flags 等实现细节，不得仅为填表而反复要求业务作者选择。

若作者确实委派了方案选择，系统可在授权预算和明确目标函数下自动选择；应记录准确候选集、被排除原因、适用范围及必要的恢复点。**允许AI自动提案不等于允许AI自动替用户签发决定、越权修改源码或发生不可逆操作。**

## 4. JSON到底承载哪些、哪些不能用JSON强装

| 正式信息或文件 | 是否可以用严格JSON | 谁是唯一事实权威 | 说明 |
|---|---|---|---|
| `gift.project.json` v1 | **是** | 工程manifest Author | SourceScopes发现范围、项目和实际目标请求；模块身份来自文件，不复制计算IR；0条控制不必建控制文件 |
| `*.module.json` | **是** | 作者模块 | Definition/Requirement/Composite/参数、引用、默认、导出、语义主体；不是全部都叫Control |
| 独立 `gift.control-file/1` + `sourceScopes` | **是，当前唯一控制设计载体** | 作者控制文件；fileId只标识载体 | 全项目逻辑键 `(scopeRef,target?,controlRef)` 唯一；product-root 必须以 target/rootId 定位；mode 只有 require/prefer；Reset 删除记录，最后一条留下合法 records:[]；不建立额外注册表 |
| `gift.lock.json` | **可序列化为JSON** | Resolver派生锁 | 作者可Pin需求但不能手工改解析结果以假装取得合格Binding |
| Rust/TS/SQL/CSS/图片和原生构建配置 | **不需转JSON** | 各自原生/资产作者 | 不做同义镜像；只有所需公开合同才进入Gift模块或受管索引 |
| 实际环境变量/端点/SecretRef | **可由专门运行接口使用JSON** | 实际运行调用者/Provider | 秘密实际值在受保护存储，不落入SourcePackage；运行Grant另校验 |
| GitHub PR状态、云实例状态、费用和测试结果 | **可作只读JSON查询/导出** | 外部/Runtime/Assurance | JSON表示不移交作者写权，也不表示已经发生 |
| 客户端主题、窗口、筛选 | **可由客户端自己选存储** | Client | 不成为工程构建输入；若目标产品本身UI由作者控制，改走Meaning而非Client |
| 海量权重、图像/视频、数据集、实时生产数据 | **通常不适合作为大型控制JSON数组** | 对应数据资产/运行数据库权威 | 使用ContentRef、领域数据格式、数据库、流/列存储并签发准确Schema、快照与授权 |

一个字段**应不应该写进JSON**，与它**是不是开发者控制的语义**是正交问题：作者可以通过结构化JSON提交公开协议，而真实编译器可派生JSON格式IR；前者有作者写权，后者没有。单纯用Rust写一个Builder API也不改变其产生的候选需要有权采用。

## 5. 为什么不制定“只要JSON再长也绝不换格式”的永久规则

**坚持的是统一语义与单一作者来源，而不是无条件坚持某种载体。**

1. **内容本质是树形声明/低频配置时**：保持严格JSON，先用导入复用、Definition/Profile参数、合法scope继承、稀疏差异减少真实记录，再用有型控制文件的按需分片和基于逻辑键的精确编辑减少编辑热点。数据量本身没有任意固定大小阈值；有数MB的JSON并不使意义失效。
2. **大量值其实是可复用算法/源程序时**：保持Rust/TS或其它现成源码、库/SDK和原有构建格式；不要把每个语句、循环、泛型实例和AST序列化成结构化作者JSON。这样做并非“换掉JSON”，而是使真实owner使用合适载体。
3. **内容是不可读大数据或有强随机事务更新的资料时**：使用类型化资源、数据库、JSONL/二进制列存储等合格SourceProfile或Asset；要求唯一键、原子快照、导出、迁移和作者版本。JSON可以仍用于小型manifest和引用，不能要求记录正文继续塞进manifest。
4. **内容主要由人高频手写，JSON符号负担和合并冲突成为实测瓶颈时**：可以设计HCL/CUE/其他完整、有版本的**可选**文本作者前端。但在获得parse→meaning→encode等价、稳定identity、注释和未知内容保留、前像/回写/迁移资格前，只能做只读投影，不能第二份双写真源。不要把CUE的默认/合取模型偷换成Gift的hard/prefer/reset。
5. **内容只是网络传输或机器缓存过大时**：允许使用gzip、分段、索引、内存映射、压缩索引等派生编码；这不必改变权威作者JSON，也不改变语义。缓存可丢弃重建，不能变成另一份可编辑truth。

改变的判断指标是：作者确需独立保存的事实条数与表达密度、增量编辑粒度、审查可理解度、合并冲突、解析与全局约束失效成本、内存与吞吐、权限隔离、版本迁移及生态现成工具的真实表现。**不要以ZIP体积或“JSON看起来长”一个维度裁决。**

### 严格JSON的实际硬条件

- UTF-8、拒绝重复对象键、严格检查未知字段/未知生效扩展（拒绝相交行为，不可默默忽略hard）；对象成员排列没有业务优先级；数组位置不是跨修订稳定身份。RFC 8259指出重复键可能导致解析器间不同结果，Gift需要比其可互操作建议更严格的拒绝策略。
- JSON Schema可以帮助约束已发布结构（如`unevaluatedProperties`），**但不能代替**真实Descriptor是否存在、单位/值域、作用域、共同硬约束、外部Grant和Target消费者。JSON Schema的`default`也不能被当成自动采用/覆盖的Gift Default。
- 需要精确整数、十进制、NaN/Inf位级身份、ContentRef时使用合同明定的有类型编码和真实解码，不让JavaScript Number悄悄改写数学整数或哈希；JCS、JSON Patch只在真实适用域内复用。
- JSON Patch的`test`可做冻结文件内操作前检查，但文件内数组下标不能成为逻辑对象身份；必须通过稳定对象键和受管事务检验共同前像。JSON Merge Patch的`null`删除语义不能代表Reset与合法`null` TypedValue的全部区别。

## 6. 一条具体工程修改轨迹：编辑器撤销历史与控制的错分

开发者说“编辑器必须能撤销过去的512次合法修改”：这是**可观察产品Requirement**（需定义历史计数、何为一次合法修改、持久化和容量不足语义）。应由产品模块Requirement/Profile负责。它**不是**可以随Target/Provider随意缩小的cache优化值。若开发者只是想内部预分配512个历史槽以减少分配，则在存在实际descriptor及Consumer时可成为可选Realization Control，并必须证明容量不足时仍满足撤销Requirement。

开发者又说“这个私有编辑模块更偏好rope而不是piece table”：若两者保持对外Meaning与全部hard，则是`mode:prefer`的实现控制，作用域可为该Module或Definition。系统可以在约束不成立时选择其它实现，并解释排除原因；若有合格精确Pin再写`require`。

开发者说“本次将文档同步服务迁移到区域A，执行生产发布”：前半句按是否长期的数据驻留政策拆成Requirement/部署输入，后半句是需要有权Runtime授权和实际Operation的**效果**。项目JSON中加入`region: A`不等于云实例已移动、旧数据已删除、审计已合格。

### 独立 ControlFile 的示意片段（不是已注册 Descriptor）

```json
{
  "schema": "gift.control-file/1",
  "projectId": "project:studio",
  "fileId": "editor-choice",
  "records": [
    {
      "scopeRef": {
        "kind": "module",
        "moduleId": "studio.editor"
      },

      "mode": "prefer",

    }
```

`example.*`仅是样本描述符引用。若没有已绑定的正式Descriptor（准确revision、typedValue、scope、merge、phase、consumer、验证、迁移），必须返回缺项，不能仅因这段JSON形状合法便宣称控制会生效。产品Meaning中的撤销次数不出现在这条实现控制记录内。

## 7. 冲突、角色和演进的拒绝见证

| 触发 | 必须出现的结果 | 禁止行为 |
|---|---|---|
| 作者设定`prefer`高于组织强制hard | 拒绝冲突候选或忽略其不合法排序贡献并解释 | 软权重越过硬政策 |
| ProductRoot有硬本地执行要求，Definition层控制外网Provider | 明确`CONFLICT`或无合格候选 | 越具体越优先消掉父级要求 |
| 没写金额舍入规则但目标只支持float | `NeedsMeaning`或外部已有准确Definition | 默用IEEE754且宣称等价 |
| 编辑器同一个historyLimit既作为用户可见约束又作为缓存设置 | 拆成独立Meaning/Control并建立保证义务 | 值名相同就复用一个Control |
| AI猜测用户要最长历史、自动选择云Provider | 保留Proposal；如需外部访问另申请Grant | 自动采纳未授权Meaning或执行 |
| 未注册Control descriptor却收到合法形状JSON | 报UnknownDescriptor/Unsupported | 跳过控制继续生成 |
| 缺少分片/清单未知版本 | 拒绝相交加载和构建 | 把丢失hard当默认Auto |
| SourceScope选中了ControlFile但Reader不支持，或旧选择器匹配多个rootId | 明确能力/迁移Needs，保留原源 | 忽略控制后生成、按首项猜根或复制到所有根 |
| 同一逻辑Control在两个分片都有声明 | `DUPLICATE_CONTROL_OWNER` | last-write-wins，即使值一样也不准 |
| 取消正在运行的付费或外部写入 | Operation进入取消请求/未知/结算过程 | 直接改Declared标记费用已返还 |
| 测试未运行但用户要求合格 | 创建Verify obligation，不产生PASS | 写入`evidence: pass`伪造证据 |
| Target只支持部分功能 | 只对支持范围生成，阻断依赖缺口的交付 | 自动缩小作者定义域并声称完全等价 |
| 开发工具主题更改 | 仅客户端偏好变动 | 无意义使Target/Artifact失效 |
| JSON→其他表示的双向迁移未获得原子写入 | 输出迁移候选与未支持原因 | 两份文件同时成为可写真源 |
| 大规模记录超过内存/时间预算 | 报准确`RESOURCE_BUDGET_EXCEEDED`、可恢复范围 | 静默丢掉后半部分控制 |
| 组织policy仍有效而维护者改变作者源码 | 依两种独立authority重新求合规 | 借作者修改伪造External已经改变 |

## 9. 仍需真实产品实现，而不能只凭本页宣布完成

独立 `gift.control-file/1` 是当前唯一控制持久合同，由同一 Project 的 SourceScopes 发现；旧内联输入只按完整前像和明确迁移条件读取。Control Descriptor的完整生产级机器注册/版本绑定、真实Rule及领域语义、原生工程双向适配、跨文件原子Snapshot、运行权限与费用结算、Target消费者、证据验证和大量工程压力测试都需要独立实现/验收。**明确“谁拥有写权”不等于这些执行者已具备实现。**

本篇不声称控制矩阵列完世界上所有未来行业对象。新领域出现时，先检查它实际新增哪种独立可观察区别及哪个owner能承担；然后按五类决定、六类权威、阶段、scope与保存位置判定。只有原模型不能表达新的区别才有资格扩充语义，而不是靠无限追加`controlRef`名称或要求所有作者继续维护更长JSON。

## 一句开发意图的可执行写源决策

实际写源由**改变的事实**裁决，不按输入媒介裁决。公开行为、错误、状态规则落已有作者Definition/Requirement或原生真实owner；要求某Target、Provider、算法与ABI的强/软限制落合格Control；SecretRef与单次运行参数归Deployment/Operation；图形布局归客户端。编译器锁与Evidence均不可当作作者可修改目标。

若一句话同时改变公开撤销限制与底层存储策略，应生成一个具共同前像的多owner候选、分别标出变更及受影响消费者；不能把两个决定写到同一个JSON控制键以图方便。无足够授权/描述符/回写映射时保存草稿并报告精确缺项，已独立闭合的作者部分仍可保留。

## 一条完整作者意图的真实文件落点与不能代替的事实

以“编辑 `Document` 后 revision 至少增加 1，并生成 ESM TypeScript”为例：前半句是由作者编写的产品 `Requirement`，在 `design/rules.module.json` 定义、在 `design/product.module.json` 的发生点填 `minimumDelta:1`；作者现有函数体只在 `src/document.ts`。后半句拆成作者目标请求 `gift.project.json.targets.ts` 和有准确描述符的独立 ControlFile 硬控制，不能把 ESM 当业务 Requirement，也不能把“revision 增长”塞进实现 Control。函数与规则的显式对应若缺乏原生 Profile 映射，才通过一份选择文件标明实际导出，选择文件不复制实现或伪造已解析证据。

Gift 读取后派生有效硬控制、必要能力、Method 候选过滤、Target 接受性、基础修订和未决义务；这些派生结果属于 Compiler/Resolver，不由开发者持久化 `status:PASS`。第三方可发布 Method/Target 声明，但声明合格性由独立检查而不是声明者赋权。用户要求“现在编译”“允许网络”“发布到某路径”分别是本次任务、带实际条件的 Execution Grant 与不可凭作者源码取得的外部作用；界面字体、展开视图、树结构则由 Client Preference owner 保存，不污染作者项目。

对开发者展示已持久化/有效/选中/已生成/已施加/已观察/已验证六种不同状态时，展示每项的真实 producer、basis、scope、target 和是否已获得独立证据。拒绝、缺能力与旧修订不能由 AI“建议用另一个实现”暗改硬要求；提议可作为新 Candidate，必须通过同一权威写入和重新解析。

### 意图作者主入口与供应者的决策隔离

业务作者控制对象、可观察行为、硬禁令、规范义务与例外、时点、费用和需要的证据；若某个决定会改变作者接受的业务结果，系统必须显示差异并取得有效授权/采纳。实现供应者控制在硬约束成立后的算法、数据库/规则引擎、线程布局、具体 UI 组件和优化策略；这种委派不是自动取得业务/世界授权。严格 JSON 作者模块仍是合法完整真源；从自然语言发现候选后必须经作者采纳方才入当前 AuthorSource。

不得因为 Gift111 已支持递归/泛型，就要求普通产品作者填写这些结构。仅当现成合格方法不足时，显示专业实现任务，允许由实现者使用原生语言或可选 Gift 计算体承担；内部代理不得发明法域/主体/权限事实。

#### 三类抽象的控制权不能合并

领域抽象决定概念/关系是什么，目标抽象决定哪些结果必须达成/保持/禁止，实现抽象决定怎么满足这些要求。三类选择可以由不同合法 Owner 提供。业务作者接受 Meaning/硬要求，供给者承担技术实现，现实 Grant 由实际权威发行；工具的“统一配置”不能把它们物理合并成一个随时可改的 JSON。抽象、特化和精化的程序见[抽象演算](../组合/抽象与开放定义.md#gift-abstraction-calculus)。
