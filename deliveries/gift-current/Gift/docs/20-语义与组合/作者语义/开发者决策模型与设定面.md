# 开发者决策模型与设定面


### 开发者的五类决定与默认生成

作者明确写：① **什么存在及何者相同**（类型、对象、角色、基数、实例）；② **想达成和保持什么**（Goal、禁止、规范、质量）；③ **动作/状态怎样合法发生**（工作流触发、条件、资源、事务边界）；④ **系统边界在哪里**（公开端口、能力、宿主和部署）；⑤ **必须锁死的选择**（授权、版本、精确Method、安全边界或算法）。

可机械推导的不让作者再写：重复Def名、成员索引、实际绑定图、缓存键、来源坐标、导出路径的派生副本、最终目标语法树、自动SourceMap、临时发现的Method候选。无法推导且会改变利益或现实行为的选择不能由系统暗设；提供有条件的默认值时须暴露其规范版本、前提和可覆盖位置。

### 一次决定只能有一个生效写入点；省略是有类型的

开发者对一个对象作出的决定，必须先定位其性质：定义产品世界的 `Meaning`、限定成功条件的 `Requirement`、压缩合法方法空间的 `RealizationControl`、具体部署/会话才获得的 `RuntimeInput`，以及仅影响工作台显示的 `PresentationPreference`。这是对已有写源的**查询视图**，不是五个新的 JSON 集合，也不要求所有文件出现五层。`Native` 指实现来源及写权，不是第六种业务决定；`Binding` 是实际解析结果，不是用户意图；`Evidence` 是对事实的支持，不是代码属性。

对每项可写控制，都指定具体生效范围和冲突方式。项目全局、目标画像、产品根、组件实例、方法使用点、一次执行不构成任意继承的单链：`A` 的子域仅在声明确实涵盖该子域时才能约束它；两个独立根共享 Method 不意味着根 A 的授权扩展到根 B。设定必须回答：控制对象和主体是谁、声明了哪条允许或禁止关系、默认值由哪个已经固定版本的合格提供者决定、作者怎样覆盖、Scope 冲突时拒绝还是组合、改变后哪些消费决定失效。若没有合格默认，缺项就是待决定事项，不得选择一个“看起来常见”的默认。

尤其要区分四种看似同样的省略：可合法推导而不必写；由已冻结默认补足；对应能力不被当前产品使用因而不存在；作者真实决策缺失且不可推导。工具不得只根据字段没填就推断作者“无所谓”。例如用户不指定数据库厂牌可以由 Method 选择，但用户指定`只能本地保存`是硬要求；没有外部服务器地址不能擅自发往某个云存储。长 JSON 的简化原则是减少**必须由人作出的独立决定**，不是把决定隐藏在不透明魔法配置或强迫所有属性都用 `undefined` 代替。

一次修改只写权威源，保存后的来源 Revision 和生效 Scope 明确；编辑器里的向导、自然语言草案、图片视图、AI 候选、结构化树是可丢弃的投影或明确可采用的提议，不是另一份和 `definitions` 并列的产品真相。若两个工具并发修改同一范围，必须提供共同基线、同一对象发生点及冲突处置；拒绝丢失更新，不以文件最后写入时间替代语义合并。


### 纯意图与具体方案如何共存

- **只规定结果**：作者声明Goal与已接受Requirement，允许实现解析依据范围内的合格Method选择；如果不存在合格供应则返回`NeedsMethod`。
- **规定必要过程**：作者声明Workflow/State/事件/审批和不可替换的算法或策略；解析器不能为“优化”绕过这些业务步骤。
- **直接提供程序**：作者使用计算函数或原生Source，通过类型、效果与供应合同公开给系统；已知接口不自动证明程序符合目标要求。
- **混合**：同一系统可对某模块固定原生算法，对其他模块只声明结果，目标生成保留这些边界并可以逐模块替换实现。

一个意图可能同时包含这些层面。没有一个独立的“意图层数栈”；业务从类型、角色、事实、行为、约束、组件与系统组合形成，任何层既可以被复用，也可在根上直接出现，前提是消费者能够解释其 Use。

<a id="gift135-developer-choice-scope"></a>

实际开发者可以指定业务资源容量、质量门槛、状态条件、工作流等待、政策规则、组件参数和系统目标而**不编写计算函数**。固定数值使用带单位的业务字面量；条件和外部事实使用经授权的Meaning/Observation引用；公开端口与组件按声明的名义签名匹配；实现算法/存储细节只有在作者显式硬限定时才成为必须遵守的选择。决定的写入权、源码位置和资格层不因工具界面预览而变化。文件与互斥规则见[非计算开发者Profile](开发者通用定义Profile-类型计算业务与系统构造.md#gift135-noncomputational-author-closure)。

## 开发者心智模型：不是一条层级栈，而是四类局部决策维度

> **与全局工程模型的关系**：这里的 A/B/C/D 四轴只拥有 **Developer Decision 领域的局部投影**，不是第二套全系统坐标。Decision引用[统一多层工程模型](../../00-系统与原则/统一多层工程模型.md)中已有的准确对象与事实；因果角色仅作为按需解释，不新增必填layer字段，也不为一个普通值物化所有核心形式；本节只把开发者需要操作和解释的部分投影为 decision semantics / authority / realization stage / inheritable setting scope。A/B/C/D 不能再物化成第二套持久对象或第二 writer。

开发者决策按四个互相独立的维度定位：**语义类别、事实Owner、落实阶段、作用域**。Meaning、ABI、Binding、Evidence与Workbench布局分别属于不同维度，不能逐项升级成统一堆叠的“层”；这一投影仅帮助查询与编辑已有L0—L6事实，不新增Ontology或存储。新领域先查已有权威对象、权限及适用域，仅当确有公共不可表达区别时才考虑增补。

### A轴：5类decision semantics；可写性由authority决定

| 类别 | 用户真正决定什么 | 典型内容 | 不属于这里 |
|---|---|---|---|
| **Meaning** | 产品世界、数据、行为、状态、关系、协议、错误和可观察交互本身是什么意思 | Money scale、状态转换、FIFO语义、查询关系、UI焦点顺序、业务错误 | 某crate、ABI、当前PID、测试结果 |
| **Requirement** | 对Meaning或最终产品必须/优先保持什么 | exact/durable/local-only、兼容、安全、性能边界、许可政策、偏好 | 实际选中哪个Provider或编译flag |
| **Realization Control** | 在满足Meaning/Requirement后的合法实现空间中显式收窄或排序 | Provider/algorithm/target/storage/representation/build/dependency policy | 自动Binding本身；测试Evidence |
| **Runtime Input** | 某Deployment/Instance/Session/Operation才取得且不重新定义产品Meaning的现实输入 | endpoint、SecretRef绑定、run args、当次资源额度、租户、当前Grant | 稳定业务常量；长期产品Requirement |
| **Presentation Preference** | 只改变开发工具显示与个人操作习惯 | theme、keybinding、panel/filter、Graph viewport/layout | 目标产品UI布局或任何Engineering semantics |

`Native-owned setting`不再被当成第6种“决定语义”：它是下面B轴的owner/representation。一个Cargo feature可能承载Realization Control，一个原生attribute可能承载Meaning或Requirement；先判语义，再判由谁准确拥有。`Resolved Binding`、`Observed fact`和`Assurance Evidence`也都不是新的decision class：Binding属于Planned/Resolved，Observation属于Observed，Evidence由Assurance authority针对Claim另行签发。A轴本身不授予写权：外部法规可以产生Requirement、Compiler可以给同一Realization Control形成Selected值，是否可写由B轴authority和当前权限共同决定。

**A轴分类判据按语义而不是字段名字：**

1. 改变它会改变产品公开行为、数据含义、状态/错误/顺序/接口等可观察语义 → **Meaning**；
2. 它声明“无论怎么实现都必须/最好满足”的性质 → **Requirement**；
3. 在Meaning/Requirement不变时，只限制Provider/算法/目标/表示/工具链等实现自由 → **Realization Control**；
4. 它允许每次Deployment/Session/Operation在不改作者含义的前提下提供不同现实值 → **Runtime Input**；若该值长期固定为产品政策，则应提升成Requirement/Control，而不是继续藏在运行参数；
5. 它只改变开发工具显示或个人交互 → **Presentation Preference**。

决定类别按**被约束的行为与阶段**划分，而不是字段名。`timeout` 可是公开 API 期限（Meaning/Requirement）、求解预算（Realization Control）或单次 Runtime Input；`region` 可是驻留硬约束（Requirement）或现场部署/观察值（Runtime/Observed）。客户端必须显示来源、Owner、作用域及写权，使同名字面不同语义可并存，不能用同一个全局配置键互相覆盖。

### Requirement preference 与 Realization preference 的分界

`prefer`作为作者组合或Control强度都表示**软偏好**，但A轴语义仍要区分：

- 偏好的对象是产品可观察性质、质量目标或验收结果，如更低延迟、更小能耗、更强兼容、较少数据离域 → **Requirement preference**；候选实现只是为了满足/比较这个目标；
- 偏好的对象就是实现选择本身，如优先Rust目标、优先某Provider、优先本地Supply、优先某布局/工具链 → **Realization Control preference**；它不允许反过来改变产品Meaning或把更差可观察结果称为等价；
- 若“偏好某实现”其实是因为许可、安全、平台支持等不可补偿条件，则应升级成hard Requirement/Control，而不是继续写Prefer；
- 若实现名字只是代理指标而真正关心延迟/成本，则优先表达真实Requirement并让Resolver比较证据，不把当前经验绑定成永久库偏好。

客户端显示`Prefer`时必须同时显示它偏好的 **decisionRef / semantic owner 与 subject**，不能只显示一个星标或priority数字。相同`priority`只在对应owner定义的同一比较层次内有意义，不跨产品质量、Provider选择和UI偏好任意求和。

### B轴：6类authority / owner

这一轴回答“**谁有资格写/签发这个事实**”，不再把文件格式和owner混在一起：

| Authority / owner | 拥有什么 | 常见表示/来源 |
|---|---|---|
| **Author authority** | Meaning、Requirement、显式Control、稳定Profile使用和作者资产 | 结构作者源、原生源码、Cargo/tsconfig/CMake等受管或作者配置；表示不同但author responsibility相同 |
| **External authority** | Gift不能自行改写的外部事实、标准、包/平台/组织政策和真实服务声明 | registry metadata、platform capability、标准/许可证/组织policy、远端provider contract |
| **Compiler / Resolver authority** | 从固定输入派生的实现选择、Binding、representation、target plan和Artifact生成关系 | RealizationPlan、binding lock、TargetProgramIR、ArtifactSet；默认只读 |
| **Runtime / Execution authority** | 实际Operation、Deployment、Instance、资源、Grant、Effect settlement和readback | PID/socket/device/cloud/resource/session/receipt |
| **Assurance authority** | Claim评价、Verification结果、coverage、freshness及Evidence关系 | CheckRecord、Evidence DAG、measurement/verification result |
| **Client authority** | 仅presentation/local interaction状态 | selection、filter、theme、layout、viewport、recent query |

结构JSON与原生源码不是两种authority；二者都可能由Author authority拥有。Artifact与Evidence也不能都叫“机器派生”：前者由Compiler/Resolver产生，后者由Assurance对准确主体/方法/环境评价。外部标准或provider声明不属于Author，也不能因为被导入工程就获得作者写权。

All Decisions可以把六类authority的事实投影到一张表，但编辑能力由owner决定：Compiler/Runtime/Assurance的派生结果通常只读，想改变它们应修改相交Author/Requirement/Control或发起新的合法Operation/Verification。

### C轴：5个落实阶段

| 阶段 | 回答的问题 | 典型对象 |
|---|---|---|
| **Declared / Requested** | 作者/策略/运行调用者明确给了什么 | Meaning、Requirement、Control、runtime input |
| **Effective** | 合并scope、Profile、硬条件、默认、native/target facts后当前真正成立什么 | effective requirement/control/value |
| **Planned / Resolved** | 系统准备怎样满足它 | Binding、representation、toolchain/config contribution、Operation plan |
| **Applied** | 哪些决定已经实际进入源码/配置/Artifact/Deployment/Instance | generated source、Cargo field、DDL、deployed config |
| **Observed** | 实际目标/环境在准确范围内观察到什么 | readback、measurement、runtime/test observation |

**Verified 不是第六种作者决定阶段。** Assurance 对精确 Claim 结合 Observation、形式结果及 Evidence 裁定支持、反驳或未知和 Coverage；Applied 的源/执行事实仍保留。多个 Claim 可检查同一次 Applied，验收不反向决定行为是否已经应用。Evidence 由 B轴 Assurance authority 拥有，引用 C轴各阶段结果，不折叠为同一个最后状态。

不是每个决定都有五阶段；Presentation通常没有Planned/Observed，纯Meaning可能没有独立Selected。阶段缺失表示不适用，不用`null`伪造。

### D轴：3张可继承设置scope图

D轴只把开发者会遇到的三张设置图作为定位维度暴露出来；它们的传播、hard/soft合并、跨图Binding、conflict/reset与descriptor适用性由[稀疏控制与目标限定](../组合/稀疏控制与目标限定.md#decision-setting-scope-semantics)唯一维护，本页不复制第二套求值规则。

- **作者/编译scope**：`Project → ProductRoot → Module → Definition → Use/Occurrence`，`target`是正交限定；
- **运行scope**：`Deployment → Instance/Session → Operation/Attempt`；
- **客户端scope**：`User → Workspace → Window/View`。

这三张图只负责**开发设置的scope定位**，不能被误叫“全系统所有scope”。External authority的issuer/jurisdiction/version/validity、Evidence的subject/environment/time/coverage、源码resource/range等仍由各自owner保存；开发面只通过明确Binding/引用把它们带入当前Decision或Verification。

### 核心四轴之外的辅助facets

A/B/C/D四轴只负责**决定语义、权威、落实阶段和可继承设置scope**。客户端和索引还需要其他正交查询facets，但它们不改变Decision本体：

| 辅助facet | 作用 | 为什么不是新的核心轴 |
|---|---|---|
| **Source representation** | structured author / native source-config / derived / external / runtime / client等实际载体 | 同一Meaning可以换表示而语义不变；表示由owner/adapter管理 |
| **Decision state** | current / unknown / unsupported / conflict / stale / forbidden | 这是当前资格/知识状态，会随输入变化；不是决定类型 |
| **Target qualifier** | 某决定只作用于特定target/target set | 已作为D轴author scope的正交限定；不形成新的继承树 |
| **Domain / Mechanism facet** | 专业语义检索和覆盖，如空间几何、校准、媒体、ML | 由领域Definition派生；不拥有值/写权/合并 |
| **Product / root / revision / configuration** | 选择当前查看的准确工程配置 | 是对象/版本选择，不是新语义类别 |
| **Disclosure / capability view** | Essential/Engineering/Implementation/Physical及权限裁剪 | 只影响显示，不改Effective值 |

因此“All Decisions有很多filter”不等于核心模型继续增长。一个新filter若只是从已有事实派生，就作为facet；只有它引入新的独立可观察语义、authority、stage或inheritance rule时，才需要重开核心轴。

### 六个真正的开发任务面

现有主链已把开发面定义为开发者**表达、理解、改变、检查、使用和交付**软件时直接消费的行为。最终产品保留这六类，不为了减少数字把独立任务混在一起：

| 开发面 | 开发者问题 | 包含的正常工作 |
|---|---|---|
| **Understand / 理解** | “现在这个工程是什么、为什么这样？” | open/import、search、navigate、inspect、hover、references、Explain、Graph、Impact、provenance、Needs定位 |
| **Author / 表达（创作）** | “我要的软件/规则是什么？” | 新Definition/Block/Profile、Meaning、Requirement、领域模型、原生独特算法/资产的作者输入 |
| **Change / 改变** | “我要修改现有软件或实现自由哪里？” | edit/refactor、接口迁移、Auto/Require/Prefer/Pin/Forbid/Reset、dependency/config/target/native change |
| **Verify / 检查** | “这次候选和当前产品是否满足要求？” | diagnostics、Plan/Review、Diff、Impact、tests、coverage、formal/static checks、measurement、Evidence |
| **Operate / 使用（运行）** | “我要实际生成、构建、运行和观察什么？” | generate/build/run/debug/profile/REPL/console/process/interactive input、运行时readback |
| **Deliver / 交付** | “我要把什么正式保存、集成、发布或部署？” | save/apply、stage/commit/merge/push、CI handoff、package/release/publish/deploy/migrate、handoff/retirement |

Recovery/Resume是六面的横切生命周期，不是第7面；Needs是横切缺项集合；Assistant是横切交互通道；Graph/Text/Table是表示；Explorer/Search/SCM/Terminal/Testing是宿主工具。一次任务可直接进入任意面，不存在强制六步Wizard。

### Author/Change内部的八类工程构造

现有[定义与接口](../组合/定义与接口.md#block-composition-contract)已把可复用工程构造归为**声明、引用、实例化、连接、约束、绑定、组合、输出**八类。这八类是作者变化的语义职责，不是八个新关键词，也不是新的全局 Reality 类型。

| 工程构造 | 用户实际在做什么 | 当前结构/控制落点 |
|---|---|---|
| **声明 Declare** | 建立新的Definition、Subject、Rule、类型、公开参数或领域对象 | `definitions`及相应领域Definition；不等于创建运行实例 |
| **引用 Reference** | 指向已有Definition、参数、Subject、资源、Profile或原生资产 | DefinitionRef、import/export、稳定asset/native ref |
| **实例化 Instantiate** | 在一个使用点给Definition绑定实参/主体并形成独立occurrence | `use + arguments`；状态实例身份与Definition身份分开 |
| **连接 Connect** | 让输出/Subject/事件/流/资源关系按有类型边界相接 | 表达式/领域连接/Port关系；不是任意Graph edge |
| **约束 Constrain** | 声明必须/偏好保持的Requirement、Condition和Control | `require/prefer`、Profile、Control descriptor |
| **绑定 Bind** | 明确选择实现/目标/Provider或接口实现关系 | 作者显式Pin/Target control；自动Binding本身仍由Compiler派生 |
| **组合 Compose** | 用All/Any/When/ForEach/Exists及复合Definition形成更大含义 | RequirementTerm/领域组合；不由UI布局决定求值顺序 |
| **输出 Expose/Select output** | 选择公开逻辑边界、Product root和目标可消费出口 | `exposes/exports`、ProductRoot、Target mapping；这不是Deliver面的publish/deploy |

普通作者并无需手工执行八步；一个Profile使用可能同时完成引用、实例化和约束，一个高层Definition也可能把内部连接和组合全部封装。八类只用于判断一个新作者机制究竟新增了什么责任，防止为“拖线”“模板”“插件”重复造同义核心。

### 关键词和结构词必须按角色分别计数

**普通Workbench/AI/CLI产品作者：0个必需文本语言关键词。** 他需要理解业务Definition/Profile和任务本身，不必学习`.gift`才能开发。

**控制UX：6个稳定动作**：`Auto / Require / Prefer / Pin / Forbid / Reset`。其中 ControlFile 持久 mode 只有 `require / prefer`，Reset 是删除记录的编辑动作；Auto是撤销本层固定，Pin/Forbid是有合同的UX降低，不能变成第二协议。

**直接手写`gift.requirement-structure` JSON时，真实负担不能只报8个Term。当前核心结构包括：**

- 5个`req:` Definition形态：`req:composite / req:rule / req:subject / req:value-type / req:enum-value`；普通应用作者通常只新建`req:composite`并复用后四类目录Definition；
- 8个RequirementTerm判别标签：`use / require / prefer / all / any / when / forEach / exists`；
- 3个Type构造：`ref / list / builtin`；
- 7种Value形态：`parameter / subject / bound / enum / literal / typed / list`；其中`typed`只承载由精确Type/dialect拥有的canonical codec值，不成为任意JSON逃生口；
- 5种Condition形态：`value / equal / not / all / any`；
- 当前 `/2` 模块外壳3个必需字段 `schema/moduleId/definitions`，按需填写 `namespace/dialects/imports/exports/annotations`；`req:composite` body有`parameters/subjects/exposes/terms`等schema字段。

这些schema键不是“语言关键词”，但直接JSON作者确实要理解，所以必须单列其学习成本，不能用“只有8个关键字”掩盖。

**可选`.gift`中立计算文本**只在明确进入计算主体时使用。基础保留词、共同计算扩展词与另行选择的领域dialect由[计算文法owner](../基础语义/计算基础/文法类型与求值.md)分别维护并可机械计数；本开发决策模型不复制词数，也不把某次词表统计变成普通产品作者的默认学习成本。事务、异步、流、资源等领域只有真实采用独立语法时才增加对应作者负担。

### 不同角色的实际学习负担

| 角色 | 默认必须理解 | 按需增加 | 不必学习 |
|---|---|---|---|
| **普通WorkBench/AI/CLI产品作者** | 六类任务目的；当前业务Definition/Profile；VOC0公共名词只显示相交子集 | 需要精细控制时显示相交控制动作；All Decisions按真实owner/descriptor完整发现，可选facet只辅助检索 | `.gift`语法、结构JSON机械schema、Binding/MethodSpec等内部对象 |
| **Requirement dialect高级结构作者** | 上述＋共享author-module外壳、`req` dialect的5种Definition形态、8种Term、3种Type、7种Value、5种Condition及引用/作用域规则 | Rule/Subject/Value目录、复杂Profile/量化 | `.gift`并非前置；不必手写machine Binding/IR |
| **领域/Definition库维护者** | 高级结构作者＋本领域Rule/Subject/Value/descriptor合同、方法/验证责任 | 新领域语义、Provider/target映射 | 其他不相交领域的全部词汇 |
| **`.gift`计算文本作者** | 其选中计算主体所需语法；精确词集与产生式由计算文法owner给出 | 另行选择的事务/异步/资源等dialect语法及相关库API按实际增加 | 结构JSON不是必须同步写的第二份源码 |
| **目标/FFI/物理工程作者** | VOC1高级控制、Target/ABI/Layout/Build/native owner及真实工具链词汇 | 平台/ISA/设备专有合同 | 无关业务领域或完整编译器内部协议 |

这里的“必须理解”是能独立完成该角色典型任务所需概念，不等于每次任务都要同时显示。一个普通作者可以长期只处理某几个Definition和Requirement；只有切到Physical/Assurance/Library维护时才承担对应词汇。

### 稳定基数与动态目录必须分开

只有**封闭的架构拓扑**才在本篇复制基数；开放目录、版本化语法和验收案例的条目数从各自canonical owner派生，客户端、schema和兼容判断不得硬编码某次统计。

| 封闭拓扑 | 基数 | 它回答什么 | 它**不是**什么 |
|---|---:|---|---|
| 正交语义轴 | **4** | 决定是什么、谁拥有、落实到哪、在哪个setting scope生效 | 4个页面、4步流程 |
| A轴decision semantics | **5** | Meaning / Requirement / Realization Control / Runtime Input / Presentation Preference | 五种writer权限；可写性由authority决定 |
| B轴authority类 | **6** | Author / External / Compiler-Resolver / Runtime-Execution / Assurance / Client | 文件格式、目录层级 |
| C轴落实阶段 | **5** | Declared/Requested → Effective → Planned/Resolved → Applied → Observed | 强制每项都走满5格；Verified另由Assurance评价Claim |
| D轴可继承setting scope图 | **3** | author-compile / runtime / client三种不同继承图 | 全系统所有coverage/scope |
| 开发任务面 | **6** | Understand / Author / Change / Verify / Operate / Deliver | UI导航项、流水线阶段 |
| Gift Primary Side Bar语义视图 | **5** | Project / Needs / Decisions / Review / Operations | 五种authority或五开发面 |
| Progressive disclosure深度 | **4** | Essential / Engineering / Implementation / Physical | 四份配置或四种编译模式 |
| Author/Change工程构造职责 | **8** | Declare / Reference / Instantiate / Connect / Constrain / Bind / Compose / Expose output | 八个关键词/八类世界原子 |
| 精细控制UX动作 | **6** | Auto / Require / Prefer / Pin / Forbid / Reset | 六种持久协议；持久 mode 只有 require/prefer，Reset 由源编辑 owner 删除记录 |

Common setting family、Mechanism facet、动作目录、主链案例、Requirement dialect词形、`.gift`词法、范本Rule和公共对象词表都属于**可演进目录或版本化schema内容**。其精确当前成员由对应表、语法或目录自身枚举；需要数量时由这些源机械统计。数量变化本身不创建新架构层，也不能成为数组长度、UI页数、协议兼容或“系统复杂度”的硬编码前提。

### 数字不是永久上限，扩展条件才是硬边界

六个开发面和四类局部决策维度是 Developer Decision 产品投影的稳定组织边界；新的领域通常新增Definition/Profile/Rule/Control descriptor/native adapter，而不是新增开发面或全局“层”。只有出现现有六面无法归类的新直接开发者任务，或本局部投影无法表达新的独立可观察区别时，才重开这一产品投影。

### 非计算开发面：本阶段的写权与来源收敛

已规定的五类决定（Meaning、Requirement、Realization Control、Runtime Input、Presentation Preference）、六类事实Owner及三种Scope图完整保留；它们是**判断写源归属**的视角，不增加统一配置表。所有业务作者可见的独立含义见[非计算作者合同](开发者通用定义Profile-类型计算业务与系统构造.md#gift134-noncomputational-author-contract)。当前不要求业务开发者编写`core:function`或通用Expr解释。业务逻辑未知时必须向领域库、规范权威或作者索取正确来源；缺少Method时允许专业供应或原生源码接管，不能由编译器编造计算实现。

<a id="gift136-author-syntax-and-decisions"></a>
## 字段数量不等于开发者需要作出的决定数量

写源的固定词汇（`kind`、`body`、`conditionUse`等）是表示合同；作者实际必须决定的，是没有合格公共库可替代的**业务差异**：主体、权威、范围、规范、状态与效果、UI义务、性能边界，以及必须固定的实现选择。一个Kind可有多个合法Occurrence；同一Meaning可被多个工作流条件独立使用，二者共享定义但不能共享业务主体。编译器有资格推导的结构不得要求作者双写，外部现实事实也不应由作者代签。

跨模块复用要保留三种边：`Meaning定义→PredicateUse角色实参`、`Component定义→具体实例`、`Provider实例端口→Consumer实例端口`。只有这样，`define/instantiate/compose`才不会把“保存文档的用户与文档”和“连接哪个运行实例”压成含糊的名称。具体形状和错误见[作者定义Profile](开发者通用定义Profile-类型计算业务与系统构造.md#gift136-author-qualifiers-and-instances)；设计本身不声称生产Reader已实现。

## 实际开发面全覆盖：每类需求应写在哪种源码中

下表是**作者任务到真实Owner/表示的路由**，不是强制20份文件、20种Dialect或已具备全部实现。当前用户可以直接编辑所拥有的结构JSON、原生源码和资产；某领域缺合格Definition/Dialect/Adapter时报告Needs，不能把新字面字段塞进现有四种意图Body后宣称已支持。

| 实际开发对象 | 作者准确决定的内容（Meaning/Requirement/Control/Runtime） | 真实源码归属、自动化与阻断 |
|---|---|---|
| 名义实体、身份、值与单位 | 对象是否同一、存在域、Money/Quantity精度、合法范围 | Type/Relation Definition或真实原生类型；仅有名字/无单位解释不能当已类型化 |
| 数据结构、泛型、算法、纯函数 | 功能合同、算法特有逻辑、复杂度或实现固定选择 | 复用Method优先；作者独特算法可由合格 `.gift`/TS/Rust原生源码拥有；不强制在JSON中打印函数AST |
| 状态机、事件、时序与历史 | 合法转移、禁止边、期限、取消、事件处理及观测 | State/Event/Temporal Definition或领域库；未定义时钟/完成条件不能被编译器猜出 |
| 集合、查询、关系与流 | 关系身份、基数、Join/过滤、观察一致性与顺序 | 已锁定Query/Relation/Stream Definition与SQL等Method；不把声明性集合自动视为完整数据库 |
| 工作流、任务、并发和事务 | 目标、顺序约束、共享资源、隔离性、失败与补偿 | Goal/Requirement/Workflow Definition、Method供应及原生事务实现；单操作通过不证明并发正确 |
| API、协议与客户端SDK | 请求响应、错误、兼容、认证、幂等与限额 | Type/Port/Protocol与Target/原生合同；不能仅凭函数导出就推HTTP端点 |
| UI、交互、样式与无障碍 | 用户可见状态、交互结果、焦点、布局约束和a11y要求 | UI/Interaction领域Definition、真实assets及Target；开发工具个人主题另属Presentation，不成为产品UI |
| 网络、远端、分布式和消息 | 交付语义、超时、顺序、重试、复制和故障域 | 领域Protocol/Effect Requirement及合格Provider/Method；没有部署时不强制分布式架构 |
| 数据库、索引、持久化、迁移 | 保留/一致性/事务/查询能力、版本与迁移约束 | Requirement定义产品性质；选定存储由Method/Target提供DDL/迁移；原生数据库既存Schema由其owner维护 |
| 资源、CPU/内存/存储与性能 | 硬预算、可达延迟、吞吐、能耗、质量偏好及观测统计口径 | K7/Requirement和Realization Control；测不到性能不能给最优结论 |
| 认证、授权、隐私和安全 | 主体、用途、约束、信任边界、密钥/撤销、安全要求 | Identity/Policy/Security Meaning和Requirement；运行Grant/SecretRef在实际环境，绝不从源码`permit`推导 |
| 真实设备、资金、外部操作 | 可接受作用、风险限制、恢复和不可逆后果 | Effect Intent、Norm、Method和Provider；操作另需授权、持久OperationId、结算读回 |
| 时间、规范、法律与组织 | 法域、政策版本、义务触发、责任、豁免和审计 | 原生或合格Norm/Policy定义，保存原真实来源；禁止作者或编译器凭一个字符串伪造权威 |
| 科学数值、概率、ML与控制 | 精度、误差域、模型范围、随机源、验证和漂移边界 | 专业SemanticModule、数据/模型资产、受限计算Method；公共Kernel不硬编码全部领域算法 |
| 图形、媒体、游戏和空间 | 时间线、坐标系、实时更新、交互、媒体来源和一致性 | 专业领域Definition/原生Asset/Engine；仅业务要求存在不自动意味着引擎可用 |
| Target语言、平台、包与部署 | 作者指定的硬/软平台条件、ABI、依赖许可及部署约束 | `gift.project.targets`、Control、原生生态配置和合格TargetProfile；禁止用文件扩展名猜平台能力 |
| 测试、验收、可观察性与证据 | 哪些行为必须被验证、环境/指标口径、资格覆盖 | Requirement与有权CheckProfile；实际CheckRecord由Assurance；作者不得手写一条`passed`当成证据 |
| 项目文件、版本、资产与文档 | 作者仓库位置、真实来源、公开边界、保留期限、编辑范围 | SourceScope/Module/Asset/Native Owner；`gift.lock.json`由解析器生成，派生目录/报告非作者真源 |
| AI、编辑器与个人自动化 | AI能提案什么、需要什么批准、目标如何展示与保存 | 六工具/Workbench/SDK通过SourcePatch操作；个人外观另为Presentation；AI提示文本不获得业务采纳权 |
| 运行参数、部署实例与现场调试 | 每次Operation/Session/Environment中真正不同的值与权限 | Runtime Input、Secret manager、Operation record、真实日志；运行时事实不是静态业务源码 |

**完整性的判定**不取决于表中一行是否有一个现成的Keyword，而取决于该业务真正需要的独立含义是否均能落到可信Definition、原生作者源、实际供应及有资格的观察/作用接口。能够从已接受源和合格库推导的常规代码由编译器产出；作者必须决定的政策和差异不得被自动默认吞掉。具体文件与现有有限Schema见[真实工程源码Owner](../../10-作者与输入/作者源/工程源/逐文件开发源码具体规格与完整实例.md#gift130-source-tree-authoritative)。

## 完整开发设定面：用户能决定什么，而不是再造一门编程语言

本节给“开发者实际能设置哪些东西”一个完整产品合同。这里的**设定（decision）**不是新的通用配置对象，也不是要求用户把全部字段填一遍；它是现有作者语义、Requirement、稀疏Control、原生配置、运行输入和客户端偏好的统一可见投影。任何一个最终结果相关决定都必须有唯一真实owner，Workbench/CLI/AI只负责把它定位、解释和修改回owner。

### 5类decision semantics；Native/Binding/Evidence不是并列decision class

本节直接复用上面的A/B/C轴，不再另建一份七类表：

| A轴决定类 | 用户在决定什么 | 常见owner/表示 | 典型例子 |
|---|---|---|---|
| **Meaning** | 产品本身是什么意思、允许什么行为 | Author authority；结构Definition或必要原生作者源 | 金额精确到分、状态转换、FIFO、UI焦点顺序、错误语义 |
| **Requirement** | 必须/禁止/偏好保持什么可验收性质 | Author authority或有来源External authority约束 | local-only、exact、durable、privacy、兼容、性能边界 |
| **Realization Control** | 在合法实现空间里固定/禁止/偏好什么 | Author authority；Control descriptor、target/native config等准确表示 | Provider/算法、target、storage、ABI/layout/build/dependency policy |
| **Runtime Input** | 某Deployment/Session/Operation才提供的现实输入 | Runtime/Execution authority，必要时作者保存schema/SecretRef | endpoint、SecretRef绑定、run args、当前资源额度/租户/region |
| **Presentation Preference** | 只影响开发工具显示/操作习惯 | Client authority | theme、keybinding、filter、Graph viewport/layout |

`Native-owned`是**B轴owner/representation属性**，不是第6种语义决定；同一个Cargo字段可能承载Realization Control，也可能只是原生态专有Meaning。`Binding/Artifact/Operation/Evidence`分别由Compiler/Runtime/Assurance等authority产生，属于C轴Planned/Applied/Observed事实或独立作用对象，默认不能直接编辑成“决定值”。

用户若想改变选中的crate、生成ABI或测试结果，必须回到真正的Meaning/Requirement/Control/runtime input，或发起新的合法Operation/Verification；不能直接改派生Binding/Evidence。

### 用户操作只有少数，但可控制的维度是开放的

用户无需为每种工程能力学习不同的“设置语法”。公共交互固定为：

- **Set / Edit meaning**：修改真实作者定义、关系、规则或原生作者源；
- **Require**：增加不可补偿硬条件；
- **Prefer**：只在满足全部硬条件的候选中参与选择；
- **Pin**：UX捷径，不新增持久mode；等价于对可精确绑定的descriptor写一个精确`require`，例如`implementation.provider = exact ProviderRef`；
- **Forbid**：UX捷径，只在descriptor有明确定义的否定/allowed-set语义时降低为`require`；不能靠字符串黑名单创造语义；
- **Auto / Delegate**：不写本层记录，把仍合法的自由交给解析器；不是写一个`auto=true`永久覆盖；
- **Reset to inherited**：删除本层覆盖，重新计算父级/定义/目标有效值；不是把值写成`null`；
- **Adopt native ownership**：只有显式接管流程才能把generated/derived范围转成原生作者区域；不是一个普通Control；
- **Provide runtime value**：给本次部署/会话/Operation绑定输入，不自动修改产品作者源；
- **Set client preference**：只写客户端设置，不进入Engineering hash。

因此`Pin/Forbid/Auto`是产品UX动作，不与ControlFile 的 require/prefer 记录及 reset 编辑协议竞争。新的可控维度通过正式语义、Requirement或Control descriptor扩展；不是继续增加一长串顶层动词。

### 作用域不是一个全局“更具体覆盖更一般”树

开发设定面直接消费[三套设置scope的canonical语义](../组合/稀疏控制与目标限定.md#decision-setting-scope-semantics)，不得在客户端重造“越具体越优先”或last-write-wins。UI/CLI在这一层只负责定位当前scope节点、显示每个贡献的producer/authority/provenance、给出当前允许动作并解释跨图Binding；真正的继承、合取、default/prefer、conflict与reset仍由控制语义owner求值。

因此开发者可以在同一All Decisions视图同时看见Project Requirement、Operation runtime input和Window preference，但同屏展示不赋予它们互相覆盖的关系。External authority、Evidence覆盖与源码resource/range同样只作为真实scope/适用性事实进入当前行，不被折成D轴层级。

### 开发面到具体设置的组织公式

正常交互不是先选30个类别，而是按当前任务逐步定位：

```text
DeveloperTaskSurface
  → current Subject/Product/Selection
  → Decision class (A轴)
  → authoritative owner (B轴)
  → actual semantic owner / optional owner-defined facets
  → scope (D轴)
  → Declared/Effective/Planned/Applied/Observed (C轴)
  → allowed action / next task
```

这不是把各轴做笛卡尔积。只有当前subject真实支持、当前target/provider能消费且有明确owner的组合才形成Decision。普通Author任务通常只看到Subject、Definition/Profile和Needs；All Decisions才展开A/B/C/D及物理来源。

这里不再维护一个中央 `familyRef` 目录。**Decision 的语义身份由它自己的 canonical owner 决定，导航分类只能是可重建投影。** 若为了 UI 搜索方便再给每一种控制项分配稳定 `gift.family.*` 身份，就会把“如何展示/发现设置”升级成新的平台本体：未来新增机制必须先修改中央目录，行业/技术分类又会反向污染 Core。Gift 需要稳定的是 Decision/Definition/Requirement/Control 的真实身份与责任，不是一个完整分类学。

<a id="decision-descriptor-and-facets"></a>
### 开放 DecisionDescriptor 与可选 facet

一个可控制维度由它的真实 owner 发布或派生 `DecisionDescriptor`。这是**如何取得、解释、求值和修改该 Decision** 的合同，不是一个 UniversalConfig 项，也不要求全部字段同时存在：

```text
DecisionDescriptor = {
  decisionRef,
  semanticOwnerRef,
  decisionClass,
  valueContractRef,
  applicableSubjectKinds?,
  allowedScopeGraphs?,
  targetApplicability?,
  contributionAndMergeRuleRef?,
  allowedActions,
  realizationConsumerRefs?,
  observationMethodRefs?,
  impactQueryRef?,
  facetRefs?,
  presentationHints?
}
```

`decisionRef` 必须属于真正拥有该语义的 Definition/Requirement/Control/native/external owner；它不能由客户端为了显示方便临时发明。`valueContractRef` 保留值域、单位、缺失/未知、规范形式与边界；scope、target、合并、动作和消费者只声明本 Decision 实际需要的部分。新增算法、框架、设备、业务或专业语义通常只新增自己的 Definition/descriptor/Provider，无需向 Gift Core 申请一个新“设置家族”。

`facetRefs` 是 **0..N 个可选、只读、可重建的检索/解释标签**。它们可以来自 SemanticModule、领域 Definition、机制 owner 或组织自己的分类体系；没有 facet 的 Decision 仍完全合法。facet：

- 不拥有值、writer、authority、scope、default、merge、Binding 或 Evidence；
- 不进入 Decision 的兼容身份，也不作为编译/运行正确性的必要输入，除非某个具体业务合同明确把该分类本身变成 Meaning；
- 可以多值，不要求“唯一 primary family”；同一 Decision 的多个真实关系由 typed Relation/Impact 表达，而不是复制 Decision；
- 新增、重命名或重新分组纯 presentation facet 只失效查询/客户端投影，不使工程语义或 Artifact 失效；
- 若某个所谓 facet 实际改变合法性、生成、运行或保证，它就不再只是 facet，必须回到拥有该区别的 Definition/Requirement/Control。

因此 All Decisions 的完整发现能力来自**遍历相交 owner 的 descriptor**，不是遍历一个预制类别表。客户端至少能按 decision class、authority、stage、scope、owner、SemanticModule、Target、Provider、state 和可选 facet 查询；任何没有被当前 UI 分类映射的新 descriptor 也必须出现，不能因为“不属于当前客户端已知facet/分组”被丢弃。

### 分类覆盖属于 Assurance，不属于作者协议

为了持续检查“有没有某类工程决定根本没有落点”，可以维护广泛的工程主题清单，但它的正确角色是 coverage corpus。当前完整清单已移到[工程决策覆盖清单](../../00-系统与原则/设计方法/工程决策覆盖坐标.md)：身份、数值、文本、状态、时间、资源、并发、持久化、安全、合规、依赖、目标、ABI、发布、部署、性能、观测、验证、AI 等都作为**攻击开放 descriptor/owner 模型的样本**保存。

这个清单不能取得以下权力：

- 不能规定 Core 有多少个 Decision family；
- 不能要求新领域先归类后才能表达；
- 不能作为 schema enum、兼容性键、缓存键或权限键；
- 不能因为某一主题没出现在清单里就证明系统不支持；
- 不能因为所有清单项“有文档落点”就证明所有未来工程已覆盖。

新压力样本若揭示一个现有 owner 无法表达的独立可观察区别，修对应 semantic owner / descriptor；若只是清单分组不够好，只改 Assurance 或客户端导航，不改 Core。

### 多责任要求先拆语义，不靠分类解决

例如“欧盟订单保留 7 年并加密备份”包含至少三个独立区别：外部法规适用及期限、数据生命周期/删除条件、备份的加密与恢复方法。它们可以共享一个高层来源并派生多个 Decision，但每个 Decision 保留自己的 owner、scope、失效和消费者；不能把整句话塞进一个 `compliance` family，也不能复制四份同义 Requirement。

同理，空间坐标、传感校准、媒体编码、模型谱系、因果假设、制造公差等专业主题可以通过领域 Definition/SemanticModule 产生稳定 facet 供检索，但真正的数值、来源、权限、Target、Evidence 等责任仍回各自 owner。**领域名是上下文，不是系统本体。**

### 语言原本能控制的细节必须有落点

任何目标语言/源码生态里的可观察能力都必须经过以下四分法，不能被“高层抽象”静默删除：

1. **稳定跨目标语义**：提升到共同Meaning/Requirement，例如错误顺序、数值overflow、资源ownership；
2. **目标专有但需要作者控制**：做成版本化target Control descriptor，例如Rust `repr`、panic/no_std、Java superclass/visibility、特定ABI；
3. **只由原生态准确拥有**：保留在native source/config，由adapter读取/验证，例如宏、复杂CMake表达式、语言插件专有语法；
4. **当前不能安全解释/保持**：明确`Unknown/Unsupported`，限制相交目标，绝不忽略。

典型映射：`repr(C)`属于布局/ABI控制；`strictNullChecks`属于TypeScript工具链配置而Optional/Null产品语义仍独立；`#pragma pack`属于原生布局配置/目标约束；unsafe/inline asm属于受控原生能力而不是全局“unsafe=true”；macro/metaprogramming在没有中立独立价值时保留原生语义。一个语言关键词可能跨多种责任，不能按词名机械一一造Control。

### 传统语言/工具能力的完整落位矩阵

下面回答“普通语言原本能控制的那些东西到哪里去了”。分类按**可观察语义责任**，不是按关键词数量；同一语言特性可以同时触发多行。

| 原语言/工具能力族 | 首选公共落点 | 何时保持Target/Native专有 |
|---|---|---|
| module/namespace/import/export/visibility | 工程身份、公开边界、依赖关系、visibility Requirement/Control | 条件导入、插件解析、build-system特有module规则保留native adapter |
| scalar/record/variant/nominal/opaque/reference | 数据Meaning与领域Type合同 | 目标repr、pointer宽度、host object model留Target/Native |
| generics/templates/traits/interfaces/protocols | 可复用Definition、约束、实例资格与调用合同 | specialization、monomorphization、GAT/variance等专有行为按目标/原生规则 |
| class/inheritance/virtual dispatch/mixin | 对象身份、初始化、分派和公共接口Meaning | 特定Java/C++/Python元对象或基类要求作为Target/native requirement |
| const/mutability/interior mutation | 状态/效果/alias/ownership语义 | `consteval`、语言专有mutable cell等只在真实专有观察存在时保留 |
| function/call/overload/operator/default args | callable contract、参数/结果/错误/效果、dispatch规则 | source-language overload resolution、operator lookup等需要原生往返时保留 |
| if/match/loop/recursion/control transfer | Program IR或领域行为方法；只有可观察顺序/终止成为Requirement | 原生goto/setjmp/异常展开等特殊控制保持目标/原生合同 |
| exception/Result/error code/panic | error taxonomy、failure precedence、cleanup/unwind contract | ABI exception model、panic strategy等属于Target Control |
| async/await/coroutine/generator | task/stream/cancellation/progress/lifetime Meaning | frame layout、executor ABI、language-specific suspension hooks属于Target/Native |
| thread/lock/atomic/memory order | concurrency/atomicity/progress/memory-order Requirement | 指令宽度、lock-free guarantee、platform intrinsic属于Target |
| ownership/borrow/move/copy/destructor | resource ownership、alias、lifetime、cleanup Meaning | Rust borrow syntax/C++ special member细节若需原文保持则native |
| reflection/dynamic lookup/runtime type | visibility、name/version、runtime observation与permission | 元类、descriptor、dynamic patching等专有模型按实际语言保存 |
| annotation/attribute/decorator | 若有跨目标语义则映Requirement/Control；若仅生态消费则Native setting | 框架注解、编译器attribute、tool-specific metadata通常保留native |
| macro/template metaprogramming/codegen hook | 可稳定提取的结果/合同进入共同语义 | 宏token行为、卫生、build.rs、proc-macro、C preprocessor等默认原生拥有 |
| compile-time evaluation/constexpr | 阶段求值及纯计算合同 | toolchain/语言特有求值限制、反射接口按Target/Native |
| pointer/raw memory/volatile/MMIO | resource、layout、device access、effect Requirement | raw address、register/clobber、device规范必须Target/native且受权 |
| SIMD/intrinsic/GPU/inline asm | 数值/并行/设备需求与TargetFeature控制 | 具体ISA intrinsic、shader/kernel dialect、asm template不提升成通用语法 |
| FFI/syscall/native module/plugin | public ABI、ownership、thread/error/lifetime/security合同 | 实际symbol、loader、system call、host plugin descriptor由目标/原生owner |
| serialization/wire/schema | interface/wire/persistence Meaning | protobuf/OpenAPI/SQL/平台manifest特有字段由对应adapter/native owner |
| compiler flags/pragma/feature/profile | Build/Target Control或native config | 无跨目标意义的flag只保留原配置；不能为每个flag造核心字段 |
| package/dependency/feature/registry | dependency/supply policy、exact binding与lock | npm/Cargo/Maven等解析与脚本细节归生态adapter |
| linker/script/symbol/export/install name | Target/ABI/build/deployment control | linker script、section placement、platform bundle metadata可native-owned |

若一个新语言能力无法落入任何一行，先问它新增了什么**独立可观察区别**；能由已有行组合就组合，不能才新增相交语义/descriptor。禁止以“这是某语言新关键词”为理由直接扩核心，也禁止以“高层无需”把其可观察行为删掉。

### Profile是可展开的复用定义，不是隐藏魔法

为了让普通作者不面对上表全部维度，系统允许可版本化Profile作为**普通Definition或Requirement bundle**：例如Money/Identifier/Timestamp等语义Profile，或portable/offline/deterministic/low-latency等工程政策Profile。Profile不携带隐藏的Realization Control；精确Provider/target/toolchain等实现选择继续由显式Control和其scope拥有。Profile必须能展开到真实owner及来源，不能在内部藏一套无版本默认；显式Require与Profile冲突时返回冲突，不按“后写覆盖”。

选择Profile不等于选择实现。`Money<CNY>`可以约束domain/scale/currency/rounding，但仍允许不同runtime/storage/wire表示；一个`offline`政策可以禁止network Supply，但不会自动指定SQLite。Profile删除后按正常继承重新求Effective值。

### 一个设定在UI中必须能回答的完整信息

Workbench/CLI的“All Decisions”投影对每个相交决定至少能回答：

```text
Decision / semantic meaning
Subject + scope + optional target
Owner / source revision
Value schema + unit/domain
Declared/Requested value
Effective value
Contributions (0..N): exact producerRef + authority/owner + scope/propagation + optional target + owner-specific mode + derivation/expansion/provenance + applicability
Allowed actions: Edit | Require | Prefer | Pin | Forbid | Reset | Provide runtime value | Read-only
Candidate choices / excluded reasons when relevant
Planned Binding / physical realization when relevant
Applied native file/config/artifact/runtime location
Observed facts/readback + freshness/coverage
Assurance Claim/Evidence/verdict when separately evaluated
Impact of changing it
Unknown / Unsupported / Conflict / Stale state
```

并非所有行都同时有五阶段；Meaning可能没有“Selected”，Workbench个人设置也没有“Evidence”。客户端只显示相交列，但必须能够定位全部事实。贡献信息采用[正交贡献与求值合同](../组合/稀疏控制与目标限定.md#decision-contribution-algebra)，不再把Profile、继承、默认、authority、表示和推导压成会互相重叠的一维“来源类型”。不能把一个漂亮的最终值隐藏其真实生产者、传播路径、目标差异和写入位置。

<a id="developer-decision-evaluation-lifecycle"></a>
### DEC0—DEC9：一个开发决定从“没写”到实际产物的统一求值

下面是跨 Decision 的产品算法；各 semantic owner 仍拥有自己的具体值语义和验证方法。

| 阶段 | 处理 | 失败/不能偷换的边界 |
|---|---|---|
| **DEC0 Subject** | 固定base、已解析的ProductRoot/ModuleUse、subject、scope、optional target和真实owner；选择器不当稳定对象ID | 同名/同路径不猜身份；旧revision不重定向latest |
| **DEC1 Meaning** | 取得Definition/领域语义/原生作者语义，明确哪些区别本身属于产品 | 缺Meaning不能靠Control或实现名补造 |
| **DEC2 Requirements** | 合取独立要求、Profile展开、上层政策和本层hard requirement | hard conflict直接Conflict；局部不能放宽父级hard |
| **DEC3 Authority/context facts** | 读取相交Author/native表示、External authority、target/platform capability及本次已提供Runtime前置事实 | 读不到保留Unknown；opaque不按常见默认解释；外部声明不因被读取就变成Author事实 |
| **DEC4 Derive** | 从已接受事实严格推导range、identity、依赖、合法候选限制等 | “通常如此”不是Derived；推导依据变化使结果stale |
| **DEC5 Defaults & delegation** | 只在有明确owner/revision/scope的default上补省略；其余保持Auto freedom或Unknown | 宿主偶然值、机器locale、CPU数、环境变量当前值不自动成为产品default |
| **DEC6 Resolve** | 过滤硬条件后按Prefer/成本/稳定策略选择Supply、representation、target method | 无合格候选=Needs/Unsupported；预算结束不宣称全局最优 |
| **DEC7 Freeze plan** | 固定Binding、toolchain/config contribution、artifact plan和来源 | 计划不是Applied；直接改lock不改变作者要求 |
| **DEC8 Actuate** | 生成/写入/build/deploy/start/reconfigure时由真实consumer施加 | 文件中有键不证明runtime已生效；不同phase分别结算 |
| **DEC9 Observe** | 用target inspection、runtime readback、test execution observation、measurement等取得Observed facts及其freshness/coverage | Observation不反写Requirement；未观察范围保持Unknown，不能在此步签发Verification verdict |

DEC0—DEC9完成的是一个Decision从输入到现实观察的求值/施加链。多路径贡献、重复use与有环范围按[贡献传播](../组合/稀疏控制与目标限定.md#contribution-propagation-identity)求值；类型化控制编辑按[scope入口](../组合/稀疏控制与目标限定.md#control-scope-edit-protocol)定位，不另建一套UI覆盖算法。**Assurance不作为DEC10：** 它由B轴Assurance authority针对精确Claim读取DEC0—DEC9事实、静态/形式结果和其他独立输入，产生Evidence/verdict/coverage；同一Observed fact可支持多个Claim，也可能不支持任何Claim。

任何后续变化都从受影响的最早阶段重算，不必全项目重跑。改变Graph布局只停留presentation；改变provider Pin从DEC2/DEC6的相交约束与选择开始；修改Money scale从Meaning开始并可能使storage/wire/migration及相交Evidence全部失效。

### 开发设定完整性门禁

对于一个被请求的ProductRoot，每个**会影响该根正确性或所承诺外部合同**的相交决定，在生成/执行前必须处于以下之一：

- 由明确Meaning/Requirement固定；
- 从固定事实严格Derived；
- 由有owner的Default补足；
- 在已委派自由中Selected并进入Binding；
- 被Target/ABI/外部协议强制且已接受；
- 由Native owner准确保留并被相交adapter消费；
- 在运行边界由明确Runtime input/Provider取得；
- 或明确`Unknown / Unsupported / Conflict / Forbidden`并阻断依赖它的那部分结果。

不存在“字段缺失但后端先随便选一个，之后再说”的合格状态。也不要求把每个私有局部实现决定都升级成稳定设置：只有它改变已接受观察、兼容、资源/安全保证、可重现性或作者明确要求时，才进入这条门禁。

### 精细控制只收窄相交范围，不污染整个工程

一个FFI边界Pin `repr(C)`、一个数值核Pin SIMD、一个模块要求`no_std`，都只影响真实相交闭包。编译器必须沿依赖/ABI/resource consumers扩大到必要范围，但不能把一个局部physical decision提升成全项目风格。反过来，若共享public type或共同allocator使它实际无法局部化，Impact必须明确展示共同范围，而不是UI仍显示“只改这里”。

### Progressive disclosure：简单不是删字段

默认开发面只显示三类内容：**作者独特Meaning、当前Needs、用户已显式固定的Requirement/Control**。用户展开`Engineering`看到接口/状态/资源/安全/一致性；展开`Implementation`看到Supply/target/dependencies；展开`Physical`看到ABI/layout/build/runtime；`All Decisions`提供完整搜索和来源链。

因此普通业务可以只写几个高层Definition/Profile和差异，专家又能下钻到位宽、rounding、ABI、compiler flag、allocator、memory order、FFI ownership等与原语言同等精确的控制；两者使用同一工程事实。**复杂需求不再默认退化为“自己写Rust/TS”**：只要差异可由已有 Definition/Requirement/Control/descriptor/adapter 准确表达，就补相应 owner；自定义程序只承担真正独特算法或必须原生拥有的语义。

## 业务目的的发现、展开与反向查看

作者可以通过[意图投影](意图描述与作者投影.md)发现已启用模块的角色/参数/动作和缺项，或直接使用已知源。发现和目录排序不替作者选择业务价值，facet声明不签发运行权限。All Decisions仍读取真实owner；IntentOccurrence只把本页决定接到实际Requirement/Binding/Artifact/Evidence与恢复责任，不另存可写决定。
