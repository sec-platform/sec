# 能力映射与表达边界

## 从20类开发者决定到有限作者构造的消费入口

[类型化通用定义的完整提案](开发者通用定义Profile-类型计算业务与系统构造.md#developer-foundation-gift133)曾把20类开发需求映射为23种新增候选Definition、19种Type、17种Expr、9种QueryTerm；这是**历史分类方案**而非当前完备证明。统一 `/2` 作者模块目前声明27种 `Definition.kind`（其中包含原意图四种以及类型、常量、函数等计算定义）；计算在同一语言内按需要使用，不另开并行Writer。27 是定义分支的现有数量，既不是最小语义公理数，也不是生产能力的完成数字。本页仍唯一维护跨语言能力的充分性标准；每类构造具体字段、静态类型/效果、组合、缺供给与目标拒绝路径由链接的提案Owner承担。旧 `/1` 作者模块仅在兼容Reader内保持原语义；已采纳要求和原生TS/Rust源码仍具有独立真实Owner，新写作者模块只用 `/2`。


## 开发端通用抽象的相对完备性与逐能力关闭规则

本节规定“开发者可表达全部可计算的软件需求”一类声明的**适用范围与举证义务**；完整能力清单仍由本页后文的“完整语言能力”与“实际开发面全覆盖”各自Owner维护，不把覆盖表提升为新语法或新实现。完备不得使用单一布尔值：

| 声明 | 需要证明的事实 | 当前不得替代它的事实 |
|---|---|---|
| **计算表达充分（Compute expressive）** | 固定源 Profile 能构造通用计算模型，或能无损保留并链接某合格的通用原生语言程序；给出可复验构造及语义保持范围 | 60个职责名、Schema能解析、一个生成案例、宣称理论上可以写Rust |
| **开发者决定可承载（Author decision coverage）** | 每项合法作者决定能定位到Meaning、Requirement、Realization Control、Runtime Input或Presentation以及对应的有权源码/外部记录；不属于作者决定的Observed/Binding/Evidence不得要求作者手写 | 把所有决定塞进四种`Definition`、在`extensions`里添加无人解释的字段 |
| **新领域可扩展（Open meaning）** | 新的类型、关系、操作、时序、规范或领域规则具有可绑定的签名、作用域、版本、解释器与观察/错误合同，并保留可复现的来源；没有解释器时有明确Needs | 名称中出现新业务术语、任意JSON对象、模型推测或领域目录的关键词 |
| **组合语义闭合（Composable meaning）** | 类型/身份、效果/资源、时间/规范、量化/知识、并发/错误等实际相交的构造有解释与拒绝规则；允许合法组合，错误组合不静默归一 | 单个功能的局部测试或两两资源不冲突 |
| **实现可得（Realization available）** | 相交义务具备满足它们的作者实现体、合格Method或限定合成；版本、Target、Provider及环境均允许；目标根联合取得资格 | 仅有Goal或供给名称、`covers`自述、原生源码文件存在 |
| **目标与现实资格（Product qualified）** | 所需Target实际生成完整制品并验证相关行为；需要外部效果时另有Grant、Settlement、Readback与独立Evidence | 语言图灵完备、构建成功或文档工具PASS |

设计目标采用**保守的作者输入总路由**，而非“每个业务都必须进入一个JSON大枚举”。输入经固定SourceProfile读取后，每项责任必须落在：①已有类型化作者构造；②明确的领域/语义扩展（取得语义与版本资格）；③有权原生源码或接口；④作者资产及外部来源；⑤运行时输入；⑥准确的Unsupported/Needs/Conflict/Incomplete出口。只保存未知草稿不代表接受未知语义。不得为逃避缺口让`extensions`字段、通用`Any`类型或一个万能`invoke`冒充完成解释和降低。

**有限核心的实际充分性**是“新功能能由已有计算构造、已定义的模型、受限外部接口和开放库组合，必要时允许真正的作者实现体”，不等于行业词汇全集。一个新用途若要求现有核心无法观察或控制的真实区别，必须提供新的有权SemanticModule/Method/Provider/Target扩展；这是开放能力，不应改为全局硬编码行业`switch`。对于当前机器Profile，不存在合格Interpreter的Definition不能进入`DESIGN_RESOLVED`。例如历史 `intent-module-mixed-1.schema.json`只约束旧四类定义；当前 `/2` 的 Definition Body 必须由唯一作者Schema及各Kind的专业语义Owner共同确定。声明Kind不等于已有有资格的Meaning解释、Method、目标降低或真实Provider。

**可计算范围与判定极限**：在理想化的无界存储语义下，足够的函数/递归或可变状态/循环可以表达所有部分可计算函数；现实执行受资源、权限和目标约束。即使函数可表示，也不存在对任意程序的终止、行为等价、所有非平凡性质同时总是正确且终止的通用判定器；只有局部可判定的子域才能主张完备自动求解。现实意义不从函数签名推得，愿望本身也可能矛盾、信息不足或超出物理能力。缺少实现时精确返回Needs，不要求普通业务作者重新发明全部库和专业方法。

**完成标准**：每个公开SourceProfile必须发布其构造/类型/作用域/效果/运行行为/组合/导入/演进规则及负例；每种高层领域Definition必须发布语义解释、签名、实例化、实现义务和拒绝路径；每个受支持Target必须证明相交操作全部合法降低。可满足目标缺实现、搜索未完成、证明无解、目标缺后端、外部能力不可得属于不同状态，不能合并成“语言表达不完备”。本页后续表中的“当前采用”只代表设计裁决，不授予任何尚无生产消费者的产品资格。

## 跨语言能力：当前采用与条件扩展

每项独立能力按真实消费责任归入已有语义、作者控制、Method、原生供给、Target 或保证；研究条目数量不决定 Kernel 原语数量。既有基础语义、十职责、六工具和单一作者源保持有效；成熟库、原生实现和静态展开可以完整承担合格实现。生成代码、原生公共接口、物理布局、错误/资源及采用权分别由对应 Owner 判定，连接关系见[能力履行](../../40-目标与制品/目标/能力履行与接口差额.md)。

## 意图可以精确表达，语义不是与意图竞争的另一套内容

本版通过[需求作者与实现精化](需求含义与实现责任.md)及完整产品源补足这一点：需求直接约束产品，不再以函数调用足够短证明抽象足够高。`design`是既有Definition的需求角色，`use`合取，`require`固定硬义务，`prefer`限定实现自由；它们不产生第二份作者源。旧INT0—INT8关于缺省、委派和不确定性的规则继续适用。

当前采用自己的Gift定义与封装作为需求和意图的表达，不新增Intent Language、Requirement Language或同义作者层。需求规定接受结果，意图表明本次目标与差异，语义规定这些表达允许什么；三者可以指向同一个类型、调用、参数和合同。真实独立要求另有来源时保留其接受关系，不能为了“一处源”让候选改掉原验收要求。

[封装协议](../组合/模块封装-功能复用与作者责任.md#需求封装的调用与具体化协议)负责选择已知定义、绑定实参、检查组合并进入真实实现。作者只补独特行为、不能推导的条件和主动控制；类、控制流、字段及底层库不是每项需求的必填内容。本章INT0—INT8继续负责省略、缺省、委派与未决，不再维护第二份需求解析器。

“排序”在没有已接受 Definition 时缺少可能影响结果的稳定性、比较、输入保留等规则；引用已经锁定“稳定升序”的 Definition 则复用其含义，不重复作者输入。满足同一行为的多个算法属于合法 Method 自由；缺行为解释或合格实现时保留 Needs，可保存设计但不能生成补零、空类或未采纳默认作为完成结果。

CUE支持有效而不完整的约束内容，并在具体输出尚未确定时拒绝相应导出。这只支撑“合法设计与可生成结果分开”，不证明Gift能够从任意谓词自动合成任意程序，也不要求采用CUE作为第二作者语言。

### 目标工程、作者源和需求抽象分别有位置

目标工程是实际交付的程序、配置和资源；作者源是被持续维护且用于重建这些结果的内容。“源”不等于必须写最细的算术或类：准确的领域关系、已有定义引用、参数、独立约束及少量策略同样可以承担源。操作、类型和实现明细不因存在于语言规范，就成为每个项目的必填。

当前采用递进的实现选择：已有供给完整符合时只保存公开根、真实绑定和必要控制；多个定义已足够时只维护所需组合及政策；真正独特的算法才维护普通主体；新的不可表达观察才演进相交语义。机制仍由[封装协议](../组合/模块封装-功能复用与作者责任.md#semantic-supply-boundary)和本章INT0—INT8承担，不新增一套“需求原子库”或另一份总控IR。

同一内容的表达高度不能只按有没有fn、class或JSON判断。一份选择规则已确定分组、优先与平局政策时，工具可以决定扫描和容器；若接口只说“得到最优结果”，但没有目标和约束，就仍然缺含义。成熟定义能够复用的含义不要再展开；原独立要求又不能被当前错误实现覆盖。

一个低层阈值函数可以作为编译/回写单元的验收对象，不能证明整个产品只有这一层，也不能证明需求抽象已足够。面对无来源的已有算法，应当主动沿[抽象恢复](../../80-开发者与接口/原生维护/原生来源与逆向边界.md#recovery-purpose)提出已知领域候选，而不是强制把它原样重写成Gift词法。能够保留目标需求但不承担独立价值的包装、模型和配置应删并。

最终目标源码中真实计算不会消失；当前方案减少的是重复决定和实现。没有供给的新行为仍需由获准AI/作者定义，但只补相交差额。用户要求“只用外部能力”且实际可以满足时，零算法作者文件是完整路径；实际不能满足时返回具体差额与实现选择，不能空称一组接口已完成需求。

## 控制覆盖、目标生成与逐字恢复是三项不同承诺

| 承诺 | 成立标准 | 失效时的正向处理 |
|---|---|---|
| 能生成等价目标行为 | 对任务允许的观察，有满足合同的目标结构或合法辅助实现 | 换合格策略；没有策略则限定该目标输出，保留作者源 |
| 能控制目标结构或特性 | 有实际可调用的类型化控制，且检查与后端消费它 | 给出对应控制缺项，不默默忽略后继续返回普通产物 |
| 能恢复或编辑既有源码细节 | 保留具体语法树、原字节、未知区及可修改位置，具备往返规则 | 原生内容可直接维护；无来源按恢复协议提出并核验行为/抽象候选；没有映射不伪称无损回源 |

编译无需关键词逐字一一对应：一个源构造可以降低为多个目标构造，多个源构造也可以共用一个目标机制。但开发者要求的可观察区别必须有可达表示和保持路径。接口、类初始化、泛型擦除、同步、对象身份、异常、内存布局等不能因为目标都有类似名称就合并。

“尽可能支持各种语言”采用能力并集与明确交集：公共含义在中立层；专有含义在带版本的源/目标语义扩展层；同一模块可以混合使用。可移植性附着于实际使用点，不给整个项目永久贴“可移植/不可移植”二值标签。使用一个Java专有互操作约束只限制其相交输出；不能把其他纯函数也强制绑定Java。

## 固定表达机制，不冻结全部可表达内容

研究语言时同时扫描关键词、上下文词、运算符、属性、类型、模块、标准协议、内存、异常、元编程、工具链和非源码配置。关键词是覆盖入口，必须研究；它不是机制的全部，也不是把所有词并入Gift语法的理由。

普通新增函数、类型和Gift库使用已有绑定、调用和组合。修饰、目标布局、编译选项及相交接口要求优先采用有类型的描述；真正改变求值、作用域、类型或效果的能力才由显式语言画像扩展。导入库不改变parser或给普通字符串执行权限。

每个扩展必须具有确定身份、版本、合法对象、值域、阶段、解释、消费者、冲突与失效范围。把所有未来特性塞进一个任意JSON对象并不构成完整扩展设计；从“有限通用操作”不能推出“所有领域语义已定义”。新增语法需要检查已有构造或统一修饰机制是否已足够，并同时给出完整语义与映射。opaque 作为已选定的表示隐藏能力保留，不再按每次问题临时增加关键词；名称数量不是不可改配额。

## 完整语言能力的当前裁决

Gift已自行规定值、类型、绑定、求值、控制、效果和模块，因此承担完整语言体系的设计责任；工程平台范围更大，并不取消这项责任。需求封装可减少调用方重复，但封装的作者仍需有直接、相容的程序能力。图灵可计算性只回答一类表达问题，不能认证源程序简洁、内存安全、ABI可用、诊断正确或生态齐备。

当前将三种范围分开：**研究面主动覆盖不同语言的机制；采用面给当前发行范围选择一套相容规则；实例成本面只装配实际使用的能力。**关键词、语法、库、类型、构建元数据都属于研究入口，不依靠用户逐个提醒。研究一个机制不自动采用它；已采用的能力也不能只列名称，必须有作者、静态判断、求值、目标和编辑合同。

### 跨语言对照怎样形成决定

以一个可观察机制为单位取原始规范，而不是每次只查当前缺失词。实际比较至少保留**原语法、绑定/类型、执行时点、状态和资源、错误、目标与编辑**。对同一个词的不同含义，先构造能区分它们的程序，再选择当前规则；对不同词但同一种机制，复用一次公共合同。语言文档的目录只是发现入口，不因标题齐全就宣称全部研究完成。

当前的明确选择包含：严格求值而非隐式惰性；可推导的局部类型而非任意隐式强转；业务Result而非新增通用异常语法；scoped资源而非照搬某语言finally；普通组合与有权展开而非任意模块eval；托管默认与受限底层能力共存。各选择可以在决定性反例出现时修订，但不能把相互冲突的模式混进同一未标记表达式。

Haskell的非严格求值、Go的defer调用时点、Python的finally控制出口、Rust的闭包调用类别、OCaml的值限制、Zig的编译期与指针合同、Julia的方法世界，及C++的词法/模板机制分别提供不同的反例来源。它们不是一个可直接拼装的并集。原始定位、实际采用和限制见[来源目录](../../../research/sources/语言编译与目标工具.md#语言编译与目标工具)。

### 组合准入：能力不是单项打勾后拼装

变更一项语言机制时，维护者在原规范内执行以下过程，不为每个表达式创建新记录：

**LANG0 固定变化。**列出已接受语义、实际构造、当前支持域、被修改观察及所需目标。词法改变、算法优化和来源更新不是同一种修改。

**LANG1 取真实交点。**对现有构造的绑定、类型、位置、效果、控制、清理、阶段、编码和版本接口求相交；同一闭包持有可变位置并跨清理域时，按这一真实三方组合审查，而不是无界枚举所有词的笛卡尔积。

**LANG2 判定组合。**明确为可直接组合、需要明示适配、在当前域不合法、尚缺设计或尚缺实现。没有审查过的交点不是自动支持；已有明确定义的非法程序也不应永远登记成未来功能。

**LANG3 取得成功与区分 Evidence。** 对每个相交机制证明允许路径能够进展，并针对会改变规则选择、资源/来源、时点、别名、错误或停止语义的竞争实现取得区分 Evidence。具体案例数量由 ProofObligation 决定；值相同但资源或来源不同仍可能是不同结果。

**LANG4 更新生产者与消费者。**先改拥有者，再改文本/结构前端、类型与效果、IR、降低、运行、编辑、验收及真实图示；不要求所有地方复制同一算法。被改变的既有检查资格不能直接继承。

**LANG5 收束范围。**设计子域有确定输入、状态、算法、出口、目标与例子后结束该设计子项；剩余实现进入[当前实施闭包](../../90-治理与参考/状态/实施闭包.md)，更广语义差异继续归对应语义 owner，不把两种义务写到一个问题号。每次修订还沿[全部来源的维护协议](../../90-治理与参考/维护/设计依据与资料边界.md#研究结论的保存复用与失效协议)复核相交依据，不等待用户再次点名。

一个有限发行可以在所选构造、组合和目标上给完整支持表；这不是对全部现存和未来语言的永久完备证明。编译器的资格检查使用这里选定的合同，不将文档维护表加入用户程序的运行依赖。

## 底层能力的具体落位与支持边界

当前采用“通用计算＋真实资源与目标专有能力”，不把公共语义压成所有语言的最小交集，也不将C/C++/Rust/汇编的全部词法并入。低层需求的每个使用点须沿实际类型和方法得到支持；不具备目标能力时限制相交产物，其他根继续。下表是当前采用的落位与交付边界，不是一份已实现的全平台能力清单。

| 需求 | 作者入口和必须表达的内容 | 编译／运行的具体责任 | 当前关闭范围 |
|---|---|---|---|
| 定宽数值与位操作 | 库中的I/U位宽类型；checked、wrapping、saturating操作；显式转换 | 检查除法最小值溢出、移位范围与有符号右移；不能将数学Int偷偷换成机器数 | 操作语义分工已定；各位宽库与目标方法逐项实现 |
| 字节、结构和编码 | Bytes或受限Buffer；字节序、字段表示、格式和边界 | 先核长度乘法及偏移，再读写；非对齐访问采用真实支持或明确拷贝 | 逻辑值和访问前提已定；具体格式适配按来源 |
| 内存布局与ABI | 固定的AbiRef、LayoutRef及调用接口；确需时指定对齐、偏移和调用约定 | 检查尺寸、填充、可寻址范围、调用与返回、错误不能跨FFI破坏栈 | 合同与校验流程已定；目标专属布局方法不可假造 |
| 分配策略 | 资源域选合法allocator/arena；普通程序不指定 | 托管值、拥有者、借用与物理位置分开；GC、区域和manual不能无条件互换 | 默认托管和有限作用域已定；硬无GC目标保留实现义务 |
| 指针与外部缓冲 | 受限的Own/Borrow或RawRegion句柄，不是普通Int地址 | 保留分配来源、代际、范围、对齐、初始化、别名和释放；跨调用保留者有独立结束合同 | 边界与默认安全接口已定；不承诺任意指针程序安全提升 |

| SIMD、GPU与特殊指令 | 具体数据形状、精度与功能；可选TargetFeature约束 | 自动选合格库或内在指令；保留设备传输、同步、工作区和后备实现 | 常见计算组合沿现有方法；特定指令不因名称存在而支持 |
| 外部函数、系统调用与回调 | 已固定公开合同、ABI、线程、所有权、错误和数据许可 | 同步/异步、回调重入、保存指针和代码卸载分别检查；使用窄适配而非万能执行 | 原生直连机制继续采用；每个实际函数绑定需闭合 |
| 内联汇编、系统入口、裸机 | 精确架构、操作数、寄存器约束、clobber、栈/段/链接及退出 | 只在合格目标方法内降低；普通字符串不是可执行能力，不自动吞掉源效果 | 尚未选定的机器指令模板、裸机启动和链接脚本保留目标义务 |

### 定宽整数与位操作的有限语义

当前数值实现不以一个带标志的机器Int替换数学Int。采用固定命名库类型U8/U16/U32/U64与I8/I16/I32/I64；它们可以由名义类型、精确Int和隐藏构造承载，合格后端再换成等价机器表示。不引入尚未定义的任意位宽值泛型、隐式数值转换或全局溢出开关。每个库公开fromInt、toInt、addChecked/addWrapping/addSaturating及所选减乘、除法和位操作；这是一份需要实现的有限库合同，不假称已安装。

w位无符号域为0到2^w−1，有符号域为−2^(w−1)到2^(w−1)−1。checked在数学结果越界时返回Overflow；wrapping先取非负模2^w的代表，再按有符号域解释；saturating夹到对应域边界。fromInt在域外返回RangeError，不截断。没有变更要求时，编译器不能把checked换成wrapping。

位与/或/异或和取反在恰好w位表示上定义，取反后屏蔽到w位；左移和逻辑右移使用无符号位串，有符号算术右移明确作符号扩展。常规移位只接受0≤count<w，越界返回ShiftRange；需要掩码计数时使用明确的另一函数，不能复用JS或CPU隐含掩码规则。除零始终为DivisionByZero；有符号最小值除以−1在checked中Overflow，在明确wrapping中为最小值，在saturating中为最大值；其余有符号除法向零截断。每个函数的Result出口与数学Int的计算故障不混同。

这些有限类型可以用于字节格式、校验和、压缩和FFI参数而不要求作者管理裸指针。BigInt、机器整数或外部库均可成为合格实现；平台只提供32位按位运算时，不能直接把它当成U64/I64。新增真实位宽需求按同一语义补类型与目标，不增加一种控制语言。

### 底层访问的一次完整边界

以“把一个本地缓冲交给C函数填充”为例：解析已锁定的函数与ABI；取得足够容量和对齐的Own缓冲；为调用建立写借用并固定其地址；检查长度能被目标参数类型精确表示；调用；核实际写入数量与错误；结束借用；按结果继续使用或关闭Own。C函数会保留指针时，普通同步Borrow不合格，改用具有回调/完成与取消规则的独立生命周期。

原地址被回收再分配，即使数字相同也不接纳旧回调；进程中的地址不进入可移植持久作者内容。JavaScript目标没有任意硬件地址访问时，不借一个Number伪装实现。只有可信外部实现真正承担时，才可沿FFI连接。

LLVM区分volatile和atomic：前者不提供一般跨线程同步；内联汇编还需要操作数与副作用约束。此机制支持能力分责，不能证明Gift已有对应机器后端。[LLVM原子说明](https://llvm.org/docs/Atomics.html) [LLVM内联汇编与volatile](https://llvm.org/docs/LangRef.html)。

### 对“几乎一切”的实施判定

理论可表达、已有便捷作者面、目标可实现、当前有运行能力是四项。每个被正式纳入的能力需要一个实际作者入口、精确语义、保持转换、失败合同和后端/宿主供给。没有定义的机器专有能力进入明确欠账，不写“只要一个unsafe就全部支持”；也不能因为某个目标没有MMIO，让其他独立纯函数都不可移植。

## 前端形式与目标控制不能互相代替

输入形式不会增加目标控制权限。当前文本、结构和editRef消费同一套控制描述符；宿主构造SDK不在本次采用域，不能以一种技术被提到为依据增加作者字段。

同一不透明类型由作者定义，要求Java class属于目标形态控制，不会自动赋予继承、可变身份或反射。真实文件读写仍依宿主准入；未知语义不以接口外形代签，内部替换按照已定的兼容范围处理。

## 无业务内核的构造性覆盖与扩展触发条件

**业务中立不是业务空白。** Gift Core 不声明 Editor、Terminal、Order、Invoice 或物理仪器作为内建行业对象；作者可以定义任意新的名义类型、函数、算法、关系、系统状态、协议与界面要求，再通过组合/库/Provider组织完整软件。实际专业工程之所以复杂，是组合数量、环境作用、异质技术和长期演进，不是因为每个行业都需要一种新元语言。

遇到此前没有见过的软件类别，审查路径固定为：①写出它在环境中产生的独立可观察区别；②定位数据/状态/事件/效果/资源/接口/时间/权限/错误/约束；③用已有 `Definition`、Requirement及方法组合出可解释结构；④明确外部实现与目标画像的供给差额；⑤检查作者是否仍能局部理解和修改。若已有核心可表达但需要一次性把一百万个节点手工填入 JSON，属于**作者表示与抽象成本缺陷**，不是图灵完备性的反例；可通过语言、库、增量投影和人类界面处理。

真正的新语义扩展必须提供：最小区别见证（相同既有解释在两个情形给出不同合法结果）、准确生产/消费对象、解释规则、与旧核心组合的保持条件、序列化/迁移及可检查负例。新的行业词、目标文件后缀、没有实现的“愿望接口”、一个框架 API 或新的优化算法名称，不能单独成为 Core 晋级理由。业务库可由社区和作者维护，Core 不预装领域政策，也不禁止使用原生源码作为真实作者源。

对原生工程必须同时报告两种覆盖：`byte/shape preserved`（原源码和文件/依赖可保全）与 `semantic understood`（已通过适配确实理解的语义子集）。两者非全包含关系；一个原生代码文件可被安全保留和构建，但其内部不透明插件逻辑不一定可静态分析或受管回写。未知的依赖、外部效果和自修改运行代码，不因静态工程树齐全就升级为“全工程已理解”。
