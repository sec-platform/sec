# 工程决策覆盖坐标

本页是**开放的工程决策发现坐标**。它保存一组高价值工程主题，用来检查 owner-defined `DecisionDescriptor`、Definition / Requirement / Control owner、Target / Provider 与 Evidence 接合是否遗漏稳定区别。它不是 Assurance 测试语料、Core `family` 枚举、schema registry、兼容身份、Workbench 固定目录或支持声明。

主题的作用只是帮助发现真实 Decision 应由谁拥有、在哪个阶段生效、影响哪些消费者。若一个主题无法被现有 owner/descriptor 准确表示，就形成区别见证并修真正缺口；若只是 UI 不好找，修投影；若只是新行业名，留在作者 Definition/facet 或研究材料，不扩 Core。

## 当前工程主题压力集

|---|---|---|
| **工程身份与组织** | project/module/definition/product/output-root身份、命名空间、公开/私有出口、版本、owner、复用边界 | 显示名不作identity；目录不自动成为模块/包；稳定ID和引用由系统维护 |
| **数据形状与身份** | 字段/variant、名义或结构身份、key、值相等/对象身份、optional/absent/null/unknown的区别、默认值成立条件 | 不把`null/undefined/absent/not-loaded`合并；物理struct/class由目标决定 |
| **信息来源、质量与谱系** | source/origin、采集/生成方法、lineage、completeness/freshness、duplicate/conflict、quality rule、schema/semantic drift、transformation history、dataset/model/asset provenance及可追溯性 | “文件存在/字段合法”不证明来源可信、完整或新鲜；派生结果保留输入/方法revision和coverage，未知谱系不补造 |
| **数值与单位** | 数学域、exact/approx、signedness、范围、单位/量纲、precision/scale、overflow、rounding、NaN/Inf/signed-zero、转换条件 | 未指定位宽不等于i64；可证明范围后才选定宽表示；SIMD/GPU是实现/目标能力 |

| **资源、所有权与寿命** | Own/Borrow/Share/Transfer、alias、allocation domain、pool/arena、resource lifetime、cleanup owner、fallible close、retain/callback、device/file/socket/db连接生命周期 | RAII/GC/refcount/manual close是实现策略；真实资源不能伪装普通record |
| **公开接口与协议** | public API、visibility、name、call style、request/reply/event/stream、sync/async边界、transport、wire encoding、error transport、version/negotiation、idempotency、session/reentrancy | HTTP/gRPC/IPC/native call是实现/目标；公共行为和wire/ABI分别拥有 |
| **产品交互、无障碍与本地化** | view/state/action、navigation/focus、input modality、keyboard/touch/pointer、feedback、accessibility role/name/state、locale/message/plural、number/date/unit formatting、theme/contrast、responsive/layout语义及产品资产 | React/SwiftUI/Compose/Web等UI toolkit属于Supply/Target；纯Workbench布局是客户端偏好，但目标产品实际布局/焦点/可访问性是产品Meaning |

## 使用规则

- 一个真实 Decision 可以同时与多个主题有关系，但不能因此复制多份 writer；真实关系用 typed Relation / Impact 表达。
- 一个主题可以由多个不同 owner 共同覆盖。例如“安全”可能涉及产品 Requirement、External authority、运行 Grant、Target capability 与 Assurance Claim；本页不把它们合并成一个 `security` 配置对象。
- 没有命中本页任何主题的新 Decision 仍然合法。首先确认其真实语义 owner；只有 owner 无法表达时才修语义合同。
- 本页不能成为 resolver、compiler、runtime、Workbench 或权限系统的输入依赖；实现不应读取 Markdown 标题来决定行为。
- 领域研究可以引用这些主题做人工映射，但行业名、业务流程和具体产品模板仍属于作者工程或非权威研究；只有提炼成真实 Claim/区别见证后才进入 Assurance。

## 对开放模型的反证

下列情况才说明作者/开发设定模型有结构性缺口：

1. 真实可观察区别无法由任何现有 Definition / Requirement / Control / Runtime Input / Presentation Preference 表达；
2. 已有 owner 能表达值，却没有办法声明其 scope、target applicability、合并/传播、允许动作或真实消费者；
3. 一个新 Decision 只有加入中央分类表后才能被 compiler/Workbench 发现；
4. 客户端不知道某个新 facet 时会静默丢掉 Decision；
5. 为了增加一个业务或 Provider，必须修改 Core switch；
6. 分类变化导致 Artifact、Binding、Evidence 或权限无语义原因地失效。

这些反例分别要求修 descriptor discovery、owner 接口或 Core promotion；不能靠扩充本清单“解决”。
