# 文档信息架构：责任主存储，任务与关系作多入口

> 本页解释文档组织为何选择责任归属及多入口；具体物理分区与维护规则由[文档架构](../90-治理与参考/维护/文档架构.md#物理位置与内容责任)唯一拥有。产品语义、编译、运行和保证的规则仍由各自owner维护。

## 最终原则

**统一读取路线**：先定位原Owner的规范身份，再查看被消费的有型合同、资格、版本和失败恢复；按需要将同一事实映射到V/K/L/G/CAP/COMP/S/D/R等多个视图。所有表、编号、总结、索引与目录的机器统计均由已有SourceSnapshot派生；这些候选只有经原Owner审核后才取得跨语义引用资格。目录`docs`负责规范，`schema`负责结构画像，`fixtures`为有限复现，`witnesses`记录反例，`research`为来源与竞争解释，`tools`为本资料包的工具，`_meta`及许可证保护来源与发行，不建立第二写源。具体分域和保留条件由[文档架构](../90-治理与参考/维护/文档架构.md)定义；真实关系与版本影响由[对象关系与配置基线](../70-工程系统与演进/信息与生命周期/对象关系与配置基线.md)定义。


Gift按准确对象、修订、适用范围和真实责任定位规范。`Layer × Concern × ASMRVE`可辅助提出因果角色与设计问题，但不是每篇文档、每个实体必须填写的坐标；**物理文档不以Layer作为唯一目录轴**。一个稳定concern可以跨多个因果角色，同一规范仍有明确修改协议。

因此最终采用：

```text
概念定位     = 准确对象/范围 + Concern(owner)；按需使用因果角色/ASMRVE视图
事实身份     = stable Entity / Statement / Transition / Evidence ref
维护单元     = stable Contract Unit（独立修改/验证闭包）
物理主存储   = 权威责任族中的高内聚容器；文件不是语义身份
阅读投影     = Layer、ASMRVE、任务、领域、生命周期、历史等派生视图
```

这同时避免两种错误：

- 按 owner 不分层，导致系统因果关系不可见；
- 按 layer 强迫存储，导致大量真正跨层的责任被扔进 `cross-layer` 杂物桶。

## 当前物理 owner families

准确目录、职责和现行入口只维护于[物理位置与内容责任](../90-治理与参考/维护/文档架构.md#物理位置与内容责任)。本页不再抄写一份随目录变更漂移的分区表。系统/原则、作者输入、语义组合、实现解析、目标制品、运行观测、保证证据、工程演进、开发接口与治理参考分别保留真实责任，不按某一个因果编号代替其内容范围。

目录数量不是领域或运行服务数量。只有真实独立责任需要新维护边界时才增加owner；新的因果角色、facet或读者视图通常只增加可重建索引。跨角色责任仍回其真实owner，不进入无定义的cross-layer杂物桶。

## 章节内部也按责任组织

仅移动文件不算正文信息重组。多个状态机、算法或consumer是检查责任聚合的线索，不是必拆证明：若共享不可分不变量、提交或恢复协调，保留一个owner和内部子合同可能更正确；若有独立写权、语义或替换边界，才沿真实边界拆分。已完成的章节分配证明位置保全，不自动证明所有语义等价；后续调整必须核对条件、反例、来源与消费者，不按文件大小返工。

反过来，只有标题不同、但共享 identity/writer/state/lifecycle 的小段不应为了整齐继续拆。**Contract Unit 是最低稳定维护身份，文件只是一个或多个 Unit 的编辑容器。** Unit 在物理合并、拆分或搬迁后保持自己的稳定身份；只有真实语义职责也发生合并/拆分时才改变 Unit 关系。一个树节点可以定位 Unit、章节或对象，不要求创建同名文件。

## ASMRVE 是横向闭合，不是目录复制

对独立concern，检查Architecture / Semantics / Mechanism / Realization / Verification / Evolution中实际相交的问题；可由本页完整章节或已有owner引用闭合。不适用的运行、迁移或持久化职责不强造字段/实例；确有义务的未知不能标不适用。禁止创建`A/S/M/R/V/E/`六棵重复正文树。

## 历史、状态、索引都不是第二 authority

当前设计必须自足。candidate、配置选中、当前用途资格与历史谱系按[选择与有效性](../70-工程系统与演进/信息与生命周期/对象关系与配置基线.md#selection-and-current-validity)分开；它们可有并行分支，不由时间戳、包编号或唯一线性链裁决。HTML、搜索索引、导航树和 Unit locator 在有完整作者输入时都可重建；它们属于包外 Projection/Cache。正式 source package 不因投影较小就默认运输它；普通读者直接读取 Markdown 作者源，机器导航和审计视图按需生成。是否存在缓存不改变规范信息集合。来源、范围、参考绑定及其他不能仅从当前正文无损重建的包级事实按其真实责任保留；本包的来源范围见包外 editorial，历史运输布局中的 `_meta/` 不是当前必需目录，也不签发语义权威。准确输入选择、来源、不可重建的迁移差额和未结算恢复回执有各自保留责任，即使不是产品规范也不能当缓存删除。历史核对材料可另行交付，不是阅读当前规范的前置。

## 同一组织合同的文档画像

源码和文档共用[多维组织与树形落位](../70-工程系统与演进/信息与生命周期/多维组织与树形落位.md)中的身份、成员、非树关系、约束分组、稳定布局、逆向映射和迁移检查，但各自保留不同的语义oracle。目录兄弟组按明确责任聚合；更深层可按真实子责任细分，不要求全树永久只用一个分类字段。

本包保留当前责任目录，不为模型术语变化重搬全部文件。手工规范是作者表示，根README/导航/派生图是阅读入口；固定版本范本、当前候选和历史审计明确分开。来源、承接、反例和证据强度是有效信息，不能为了当前正文简短而全部丢进archive。

## 具体落位与展开

本库的[归属判定](../90-治理与参考/维护/文档架构.md#documentation-primary-placement)先分清系统主体、事实职责和完整机制，再选择主维护处；同名工作台、配置或身份不因此属于同一页。[规范入口](../README.md)按当前规范目录逐层展开；[研究入口](../../research/README.md)列出资料唯一源；跨域发现由查询工具按需组合规范与研究结果，不再发布第二份联合目录。[因果角色与设计问题索引](导航/设计矩阵索引.md)跨目录回答相交问题，而不是再复制一个单层文件表。

开发工具自身如何展示共享引用、循环、分页和多选，另由[客户端树形合同](../80-开发者与接口/客户端/树形导航与结构投影.md)拥有。这是产品的设计；本库按[记录与检索合同](../90-治理与参考/维护/知识记录与分域检索.md)使用规范 Markdown、研究记录和可重建阅读链接组织全文，二者不混成同一执行系统。
