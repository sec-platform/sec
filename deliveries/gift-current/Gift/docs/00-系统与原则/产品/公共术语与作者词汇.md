# 公共术语、开发者词汇与命名边界

本合同只维护面向开发者与规范读者的公共词汇、对外名称和易混术语对应关系。具体身份、状态、控制、运行、Claim与Evidence的对象合同，必须在各自owner中定义；本页的词汇说明不构成第二套字段或状态机。产品能力、作者范围与方案评价分别见[产品能力](全体系能力与边界.md)和[质量评价](产品质量与架构评价.md)。

## 术语与命名

### 用词依据

“开源项目”描述协作、维护与分发方式；“软件系统”描述架构和行为；“软件产品”描述交付给使用者的能力及质量。开源与产品不是互斥分类。ISO/IEC 25010:2023 使用软件产品质量模型；Apache 的项目说明也区分项目社区与其发布的软件产品。这里只借鉴术语，不表示 Gift 获得任何组织认证。来源见[外部依据](../../../research/sources/构建分发与迁移.md#构建内容分布式与迁移)。

Gift 的稳定名称是 **Gift**，描述为**通用工程编译器**。讨论上游协作时用“Gift 项目”，讨论组件、协议和运行时用“Gift 系统”，讨论面向使用者的能力、质量和支持时可以用“软件产品”。不因当前输入方式、后端、研究方法或审计主题而更名。

### 稳定命名合同

现行设计只使用一套名称：系统、项目和产品统一称 **Gift**；机器可读协议、schema、命令空间和默认工具前缀统一使用小写 `gift`；可选的中立计算文本前端使用 `.gift`。这三个层次分别表示产品身份、机器命名空间和作者前端，不互相替代。

旧名称只允许作为不可改写的历史证据坐标出现，例如旧仓库 URL、旧提交、旧压缩包文件名或冻结参考原文；这类字面量必须明确处于历史/来源语境，不得继续定义现行 API、schema、文法、示例命令或设计标题。新增设计不得同时维护两套现行别名，也不得用“兼容旧名”规避迁移责任。若实现尚未完成重命名，记录为实现迁移差额，而不是把旧名重新提升为设计事实。

### 开发者公共词汇分级：普通用户不背内部编译器名词

Gift规范内部必须有精确对象名，但不能把全部内部名词变成普通作者的必学词。公共客户端按四级暴露；一个词进入更低级别不表示对象不存在，只表示默认界面用更直接的任务语言表达。

#### VOC0 日常核心：12个Gift专有名词

普通Workbench/AI/CLI用户需要稳定理解的Gift专有概念只固定以下12个；`file/source/diff/test/library/dependency/workspace`等通用工程词不计入Gift专有词表：

| 名词 | 普通用户含义 | 不等于 |
|---|---|---|
| **Project** | 一个用户目标工程及其作者内容、资产和交付范围 | Gift自身仓库、单一目录或单一Product |
| **Product** | Project中一个可独立请求/交付的产品概念；由一个或多个明确ProductRoot/公开出口形成 | 具体target、部署实例或商业SKU |
| **Definition** | 可复用的作者含义/合同单元 | 生成类、进程或每次使用实例 |
| **Requirement** | 必须或明确偏好保持的可验收性质 | 已选实现或测试结果 |
| **Profile** | 可版本化、可展开的Definition/Requirement复用组合 | 隐藏模板、实现包或不可解释preset |
| **Target** | 本次Product要产生/适配的具体目标语言、平台或成品画像 | 当前宿主机器、Provider实例 |
| **Need** | 当前范围缺少的输入、能力、解释或授权 | 错误总称；不相关缺项不阻断全部工作 |
| **Candidate** | 尚未采纳/作用的精确候选内容或变更状态 | 当前工程事实、已应用结果 |
| **Decision** | 一个用户可定位、可解释并有真实owner的工程决定 | 任意key/value、派生Binding或UI缓存 |
| **Artifact** | 生成/构建得到的精确产物成员或集合 | 已通过验证、已部署产品 |
| **Evidence** | 绑定主体、方法、环境和覆盖的验证/观察依据 | 永久真理、目标Requirement本身 |
| **Operation** | 会产生或协调现实作用、需要状态与恢复的一次操作 | 普通纯查询、UI按钮或任意函数调用 |

`Impact`、`Diff`、`Review`、`Result`等按普通工程含义显示，不要求成为新的Gift名义对象；当需要精确协议身份时再进入高级层。

#### VOC0在六面的按需暴露

VOC0=12表示**完整产品生命周期内稳定的公共对象名**，不是每个页面同时显示12个。客户端按任务只暴露相交子集：

| 开发面 | 默认出现的VOC0名词 |
|---|---|
| **Understand** | Project、Product、Definition、Need；查看生成/运行历史时才出现Artifact/Evidence/Operation |
| **Author** | Project、Product、Definition、Requirement、Profile、Need |
| **Change** | Definition、Requirement、Profile、Decision、Target、Candidate；Need只在有缺项时显示 |
| **Verify** | Candidate、Decision、Requirement、Evidence、Need；Plan作为普通审查视图词出现，Artifact只在验证具体产物时出现 |
| **Operate** | Product、Target、Artifact、Operation、Need；Evidence只在观察/检查目的需要时出现 |
| **Deliver** | Product、Candidate、Artifact、Operation、Evidence、Need |

普通页面优先使用自然动作句，如“修改要求”“运行这个产物”“查看为什么被阻断”，不为了术语教育把对象名塞进按钮。只有对象身份真的影响合法操作时才显式显示该名词；例如多个Product或Candidate同时存在时必须区分，单一上下文可只显示名称。

用户可以在Explain/Advanced中看到VOC1—VOC3的精确对象关系，但默认Author界面不显示ImplementationBinding/ProviderBinding、Provision、Generation、CheckRecord等内部词。

#### VOC1 高级工程控制：按需名词

只有进入Implementation/Physical/Assurance下钻的用户通常需要：`ProductRoot`（一个Product在作者/编译图中的逻辑根及Product级Requirement/Control scope）、`Control`（实现自由约束）、`Supply`（可供实现能力）、`Provider`（真实供给者）、`ImplementationBinding / ProviderBinding`（Requirement到精确实现闭包/供给的稳定选择关系）、`Scope`（决定适用范围）、`Revision`（同一对象修订）、`Claim`（Evidence要支持/反驳的精确命题）。这些词不进入Essential视图的普通创作任务；`Decision`已属于VOC0，因为默认All Decisions直接以它组织可控事实。

`Block`不是第13个核心实体：它是Workbench对一个Definition或其Use的视觉/封装投影；Machine contract以Definition/真实引用为准。`Implementation`是视图/角色普通词，不与Supply/Binding再造同义对象。

#### VOC2 定义库/领域维护者词汇

维护Requirement结构、Profile库或领域Definition的人才需要`Rule / Subject / Value Type / Enum Value / Use / Occurrence / Descriptor`等结构概念，及各领域自己的准确名词。它们用于定义公共能力，不要求每个应用作者理解字段目录内部。

#### VOC3 内部实现/诊断词汇

`OutputRootRef / RequirementTerm / MethodSpec / UseBinding / RealizationPlan / ArtifactSet / CheckRecord / EngineImage / SourceRef / CandidateRef / OperationRef`等是协议、实现、日志或高级Explain需要的精确对象名。`OutputRootRef`只定位`ProductRoot`或公开出口，不是ProductRoot身份的第二份可写副本，也不是物理输出路径。普通用户可以看到友好摘要和可导航ref，但不要求手工构造、抄写或以这些名字组织项目。

### 词汇升级规则

一个内部词只有同时满足“用户必须主动区分它与现有公共概念、该区别会改变合法操作/结果、无法通过上下文或普通工程词准确表达”才可升级到VOC0/VOC1。仅因为代码里有一个type、协议里有一个field、文档需要精确审计名，不构成公共词汇新增理由。

公共词汇改名必须区分显示别名和协议identity；不能为了减少名词搜索替换内部合同并破坏兼容。客户端默认用VOC0，进入All Decisions/Physical/Explain时按需展开VOC1—VOC3。

### 项目、工程与输出

| 术语 | 精确定义 | 排除的混淆 |
|---|---|---|
| Gift 项目 | 开发、维护和分发 Gift 的开源协作活动及其责任关系 | 用户目标工程的业务组织 |
| Gift 系统 | 工程表达、模型、编译、执行、验证和演进机制的组合 | 某份文档目录或某个后台进程 |
| Gift 开发仓库 | 实现 Gift 的源码、测试、设计和发布输入 | 用户导入的源码自动迁入的目录 |
| 用户目标工程 | 使用者希望分析、生成、修改或移植的工程及其依赖和资产 | 必须公开的上游贡献 |
| 工作区 | 具有明确内容层和写入边界的开发环境 | 项目身份、单一磁盘目录或 Git 提交 |
| 工程制品 | 编译、构建、迁移或发布输出的版本化结果 | 输出存在即表示已验证 |
| 发布 | 将精确制品向声明渠道提供的操作与状态 | Git 标签存在、测试通过或部署成功 |
| 部署 | 将精确制品绑定到具体运行环境 | 编译或源码导出 |
| 软件产品 | 向使用者提供的功能、质量、支持和交付能力的集合 | 商业付费、专有许可或企业管理平台的同义词 |

`ProductProfile` 等现有合同标识不因中文术语调整而全局改名。它描述目标能力、约束和支持选择，不是账单模型。若真实语义改变，按接口兼容流程迁移，而不是搜索替换字段。

### 模型、知识与含义

| 术语 | 定义 | 不能据此宣称 |
|---|---|---|
| AI 基础模型 | 提供理解、候选推理或编写能力的外部模型 | 拥有项目采纳或执行权 |
| 工程设计候选 | 尚未采纳的目标、逻辑、数据、约束或实现选择 | 已成为生效规范 |
| 已采纳工程模型 | 经采纳事务形成的当前工程含义 | 每个目标都已经有实现 |
| 观察 | 在指定输入范围、方法、环境和版本下取得的数据 | 不可观察部分不存在 |
| 断言 | 带来源和适用范围的命题 | 发布者身份能使其自动为真 |
| 需求 | 希望满足并可据以验收的结果或约束 | 已选定完整实现 |
| 中间表示（IR） | 服务特定分析或降低阶段的结构与语义 | 作者必须手写全部内部结构 |
| 源码方言 | 保留某种语言或领域独有含义的表示 | 已自动获得公共可移植语义 |
| 目标画像 | 目标语言、运行时、能力与约束的声明 | 当前宿主环境或临时 Provider 实例 |

“生成模型”不单独用于能力声明；分别说明候选生成、模型采纳、IR 推导或制品生成。“解析工程”区分字节捕获、语法解析、符号分析、语义提升和业务意图重建。

### 身份、状态与控制

| 术语 | 含义 |
|---|---|
| 身份（Identity） | 对象是谁；不由显示名或路径单独决定 |
| 修订（Revision） | 同一对象的一次明确内容或含义变化 |
| 代际（Generation） | 一组可共同解释或发布的修订集合 |
| 版本（Version） | 消费者用于区分兼容语法或协议的标识 |
| 纪元（Epoch） | 状态、执行或授权的一次代际标记；不是时间区间，也不替代持久模式版本 |
| 有效区间（Validity interval） | 在声明时钟与解释规则下的起止条件；与纪元、截止期限分别记录 |
| 前像（Preimage） | 计划或写入预期的原状态 |
| 权限授权（Grant） | 主体可对指定对象执行哪些操作的授权 |
| 能力供给（Provision） | 某实现可提供的能力及其条件 |
| 绑定（Binding） | 为某需求选定的精确实现闭包 |
| 资源分配（Allocation） | 当前执行的资源预算、租约或配额分配 |
| 副作用（Effect） | 超出纯计算返回值、需要管理的可观察状态改变 |
| 结算（Settlement） | 确认执行、子任务、资源与残留的实际状态 |
| 读回（Readback） | 从拥有实际状态的接口读取执行后事实 |
| 围栏（Fencing） | 由接收写入的一端拒绝过时执行者的机制 |

语义责任、代码维护责任、仓库权限和运行授权是不同关系。“owner”须按上下文译为定义责任方、状态写入方、资源管理方或代码维护者，不能用一个词代替所有权限。

### 证据与承诺

设计提出机制；实现提供可执行代码；测试提供特定输入下的观察；验证检查已定义声明；用户确认检查实际使用结果。某一项成立不自动推出其他项。

文中的“完整”须说明对象集合；“精确”须说明封闭范围；“原子”须说明观察者和提交点；“最小”须说明代价或偏序；“独立”须说明共同原因边界；“最优”须说明候选空间、目标和证明。缺少这些条件时改用可核验描述，不用形容词补证据。

### 命名兼容

术语表只解释语义，不批量迁移公开 API。文档标题变更保留链接映射；字段变更要有读写版本、迁移、错误和废弃策略。中文说明是当前维护源，标识符和协议字面量保留原文。

## 抽象、意图、业务和系统的术语界线

`Pattern`：原 Definition 的参数化公共含义，必须保留公共不变量、类型化角色、差异槽和观察域；不是 Method。`DomainDefinition`：具体领域对象/关系/事实的真实解释；不是代码函数签名。`Intent`：有权接受的目标/安全/义务/偏好及范围；不等于实现步骤。`BusinessCapability`：对外可复用的已接受合同，可只含一个意图；不是强制单独文件。`SystemIntent`：含跨能力约束和交付范围的整体目标；不等于当前运行 System Instance。`Realization`：有资格方法与目标装配的决定；不是世界 Effect。`Observation/Evidence`：真实/模型来源与 Claim 的有范围判断，不在业务作者源码中另写事实。定义/组合的精确规则见[抽象 owner](../../20-语义与组合/组合/抽象与开放定义.md#gift-abstraction-calculus)。
