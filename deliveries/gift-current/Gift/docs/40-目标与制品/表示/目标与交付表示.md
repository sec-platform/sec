# 目标程序与交付表示

<a id="codec-projection-artifact-boundary"></a>
## Codec、Projection 与 Artifact 不取得作者权

目标层只消费已固定SemanticModel/Binding及相交配置。JSON、CBOR、Protobuf、文本或二进制codec说明怎样编码某一已定义值；它们不会因为成为交换格式就升级为作者语义。阅读视图、调试展开和API模型属于Projection；目标源码、资源、包、镜像和报告属于Artifact。只有经过明确接管/迁移后，某个产物区域才成为后续AuthorSource。

生成器必须保留SourceMap/provenance，允许从产物定位来源和变换basis；这只支持解释、诊断和受管回源，不建立双写。Artifact被手改时，要么拒绝、要么形成候选并经过接管协议，不能静默把它变成第二writer。

本页只拥有 **L3 目标合法表示与交付计划的派生合同**。真实部署、运行与回滚由 L4 execution owner 执行，现实读回由 L5 observation owner 取得；支持承诺与验证裁决仍由各自 owner 签发。`TargetProgramIR`是具有独立目标合法性不变量的表示；`DeliveryProgram`是按需派生的计划值，不因为历史名称包含 IR 就要求永久物化或独立数据库。

## 目标程序中间表示

### 职责与输入

`TargetProgramIR` 从已采纳的目标无关语义、精确 `ImplementationBinding` 与目标画像降低而来，并明确目标类型、运行接口、调用约定、数据布局、错误和依赖。目标无关输入仍由现有 Semantic/Design/Implementation owner 持有，不另造第二份“portable”中间表示。后端将 TargetProgramIR 序列化为目标源码或制品，不能在这个阶段重新决定业务意图。

输入必须包含公共语义 revision、所选输出根、目标画像、已固定实现绑定、降低规则和保持声明。未知与未支持区域可以保留供诊断，但必须进入输出完成状态，不能生成空实现代替。

### 节点与引用

每个定义节点具有稳定语义来源和目标局部身份。声明、表达式、控制流、数据布局、外部导入、资源及制品依赖使用类型化引用。一个公共节点可以降低为多个目标节点；多个公共节点也可合成为目标结构，来源对应必须保留。

图允许目标语言合法的递归类型和调用，但不得把源码递归错误地转换成无法调度的构建任务环。递归解析与制品生成的依赖图分别检查。

### 目标闭合检查

| 检查 | 合法条件 | 失败结果 |
|---|---|---|
| 符号 | 每个必需引用可在选定目标命名空间解析 | 未绑定/歧义，附源节点 |
| 类型 | 赋值、调用、可空、集合、递归满足目标规则 | 类型诊断，不强制转换掩盖 |
| 数值与文本 | 溢出、精度、编码、单位按保持合同处理 | 无合法表示或需明确替代 |
| 控制流 | 返回、异常、取消和资源释放路径有定义 | 缺失路径或目标不支持 |
| 效果 | 文件、网络、状态与并发效果由明确绑定实现 | 未声明效果或权限义务 |
| 依赖 | 包/库/运行时内容与能力闭合 | 未解析、冲突或分发资格不足 |
| 目标源码 | 标识符、路径、语法、声明顺序符合目标 | 源映射诊断或拒绝完整输出 |
| 发布组合 | API、模式、运行库和迁移属于兼容的组 | 可单独生成但不可组合发布 |

必须在对应阶段检查，但不要求重复执行同一分析。可信检查回执绑定输入、检查器版本和范围，供后续消费者复用。

### 开放区域与输出分类

依赖模式（目标原生、显式混合、未确定）与完成范围（完整、局部、被阻断）正交记录；源码形式（表达式、区域、声明、模块、工程）是第三个独立坐标。片段可以完整满足片段请求，混合依赖也可以完整满足已接受目标。桥接仍需明确协议、数据与错误转换、性能、安全和生命周期，不是免费或无损转换。

只要缺口不进入所选输出及发布组，可以生成闭合部分；同一原子发布组不能把缺失部分隐藏后宣称完整。原生区域的编辑权、原字节与旧运行依赖继续追踪。

### 源码组织是目标表示的投影

目标声明、类型/运行引用、初始化依赖、局部/实例资源范围与输出所有权共同决定源码布局。实际投影记录符号到文件/作用域、命名和导入、公开导出、状态初始化位置、原生保留区及辅助库绑定，不复制作者业务定义。完整选择规则见[目标源码组织与生成策略](../目标/成员布局-完整装配与布局.md)。

片段前端可以在内存构造虚拟宿主进行所需检查，虚拟模块不是长期作者源。检查回执分别标出显式假设、已绑定上下文和独立输出条件；不把“在提供的Item类型下通过”扩展为“任意输入都安全”。插入现有源码时重新绑定真实位置、语法类别和控制出口，不能仅因两边拥有同名符号就替换。

### 源码映射与调试

映射记录源位置、语义节点、降低规则、目标范围、合成原因和信息损失。调试器和错误诊断可以定位原工程含义，不依靠目标行号作语义身份。优化删除或合并节点后仍需能解释来源；无法反向恢复的修改不得静默覆盖作者区域。

### 增量失效

目标画像、实际使用的表示规则、绑定内容或源语义变化使相应目标节点失效。其他目标的独有配置不污染本目标输入。共享运行库修复可能影响多个目标组，应按真实依赖扩大，不预先承诺每次只能改单文件。

### 边界测试

最低场景包括大整数与溢出、文本编码、求值顺序、异常、取消、递归、并发可观察顺序、未绑定外部调用、依赖冲突、目标保留名、大小写/Unicode 路径碰撞、桥接运行依赖和同组模式错配。跨语言差分只在声明的观察范围内比较；格式相同不证明行为相同，行为样例相同也不证明所有输入等价。

### 理由与替代

从公共模型直接拼接所有语言源码省去一层表示，但会使每个模板重复类型、效果与目标合法性判断。独立目标表示集中这些差异，代价是降低规则和映射维护。小型固定输出可以融合阶段实现，但逻辑检查边界和输出分类仍要保留，不能为遵守层数强制序列化每个中间结果。

### 一般程序后端与原生接入

目标表示必须能保留用户一般控制流、调用、数据和Effect，不得只容纳官方示例生成器。历史有限画像以精确整数/布尔/名义包装、函数与循环映射到TypeScript AST，并要求目标编译器严格检查；本包不附该实现；完整目标设计中的泛型、闭包、异步、类、模块与原生FFI仍按目标能力扩展，不因有限参照省略就删除设计承诺。

复用原生库优先保留其语言级签名、调用约定、依赖锁和错误/Effect边界。没有Gift业务语义适配器时仍允许原生工程保全与合法目标调用；未知属性限制对应分析和优化，不自动阻断所有编译。不能从签名正确推断事务、时间或权限保持。详见[开放编译器内核](../../30-实现解析/内核/编译值服务.md#开放编译器内核设计)与[用户定义语言语义与编译扩展](../../20-语义与组合/组合/语义扩展-用户语言与语义晋级.md#用户定义语言语义与编译扩展)。

## 发布、部署与支持中间表示

### 目的

源码编译成功与可发布、可部署、可运行、可支持是不同阶段。`DeliveryProgram` 把制品、环境、部署计划、验证和支持声明分离。

### 对象

```text
DeliveryProgram = exact {
  releaseArtifactRefs,
  artifactManifestAndSbomRefs,
  sourceAndToolchainClosureRefs,
  targetEnvironmentProfiles,
  deploymentTopology,
  configurationAndSecretBindingRequirements,
  rolloutAndRollbackPlan,
  healthAndReadbackClaims,
  compatibilityAndDataMigrationRefs,
  supportCommitmentCandidateRefs,
  observabilityAndIncidentRequirements,
  unknownFrontier
}
```

### Release 与 Deployment

Release Artifact 是内容寻址、可安装、可验证的制品；Deployment 是将 exact artifact 与 exact environment/config/secrets 绑定并产生运行状态的 Effect。上传文件不等于部署，部署成功也不等于用户支持。

### 支持声明只引用支持生命周期 owner

`DeliveryProgram`只保存`supportCommitmentCandidateRefs`，不在交付计划里复制支持声明字段。`SupportCommitment`的身份、范围、证据资格、支持窗口、撤销和历史解释由[支持生命周期与历史解释](../../70-工程系统与演进/演进与实施/兼容迁移/历史知识与支持.md#support-commitment-contract)唯一维护；package存在、测试通过或文档写明都不能自行生成支持承诺。

### 降低

DeliveryProgram 派生为 release build plan、deployment operations、configuration bindings、migration actions、verification sessions 和 monitoring setup。任何平台特化由对应 backend/provider 处理。

### 验证

- exact source tree 与 artifact 不匹配；
- clean install 失败；
- runtime asset 缺失；
- secret/config 错绑定；
- canary 不代表关键流量；
- rollback 与新 schema 不兼容；
- deployed but unsupported；
- upstream EOL 使旧 SupportCommitment 失效。

## 专业工程蓝图只读投影的身份、查询与失效

为开发者查看而汇合的 `TargetProjectPlan` 只使用当前 TargetProgramPlan/SourceLayoutPlan、Requirement、Binding、协议/部署计划、Claim和准确成员职责的**只读投影**。不创建与 `TargetProgramIR` 并列、可以脱离作者事实手改的“新蓝图源”；要修改布局、公共接口、目标画像或业务含义时返回准确的作者/Control/Binding owner。用户导出的 Markdown/JSON/图并非可自由回写的权威源。

投影定位应至少保留 `productRoot + targetProfile + authorRevision + bindingBasis + requestedDesignScope`；同名产品、相同成员路径或可视画布坐标不构成身份。对于完整/局部/未知的每项关系，必须携带来源覆盖和当前资格。修订导致的失效按真实read-set、受影响Target、显式负依赖枚举和联合公开边界计算；源内容被删、供给资格撤销、目标环境变更或迁移策略变化都可能让先前完整蓝图重新出现 Need，但不能偷偷改写旧的历史快照。

图形必须区别：author/import、semantic-dependency、service-interface、message/IPC、resource-ownership、build-before、release-together、observed-by、evidence-for。相同两节点间可能存在多条不同边，画布简化只允许隐藏已披露的视觉细节，不可把仅有 import 的关系误显示为部署依赖，也不可反向根据布局坐标推出调用先后。
