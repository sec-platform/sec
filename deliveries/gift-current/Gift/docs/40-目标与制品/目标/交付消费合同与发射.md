# 交付消费合同与发射

本篇在[交付语义](../../20-语义与组合/交付语义/README.md)和[交付公共合同](../../20-语义与组合/交付语义/交付公共合同.md#gift-unit-501703299c2052ad9d1e9e2adc6ad993)下，消费 `instantiate → resolve realization → lower/compose target → Artifact/Assurance/Execution` 的已选语义及绑定，实际装配 Target 文件、依赖、配置及入口。Library、CLI、Web、GPU 等名称不是公共产品枚举，不自动创建目录、Template、常驻进程或 Provider。

## 输入：消费准确根与相交约束，而不是消费“产品类型”

一次目标组成至少从当前根取得：

- 精确 Definition / Requirement /公开主体与接口；
- 实例化后的硬义务、偏好及其来源；
- 已采用 RealizationMethod / Provider /依赖及准确 revision；
- Target、平台、ABI、表示、资源与宿主事实；
- 本根需要的消费方式、生命周期、状态/持久化、并发/时间、外部作用和恢复语义；
- Artifact/发行边界与相交 Evidence 义务。

任何维度没有要求就不制造占位配置；任何必需维度未知就保留缺项。`root.name = "service"`、目录叫 `gpu/`、文件后缀或某个 Provider 已安装，都不能替代上述事实。

## 现有主链接口不新增“交付管理器”

`semantics/requirements/instantiate` 产生准确 RequirementInstances 与来源；`compiler/realization/resolve-use` 在目标和用途下选择/组合真实方法并保留 residual obligations；`compiler/target/compose` 消费 LoweringReceipt、TargetProgram 贡献及资源/配置/接口贡献，形成候选 Artifact closure。

实现可以物理融合实例化、Method 资格、目标降低和制品封存，但每种阶段结果必须保留独立证据及未履行义务，不得折叠成单个 `supported=true`。可供检查的候选允许有明确未证 Claim；生产采用及真实执行由对应 Assurance/Execution 门禁独立决定。

**可供复验的依赖锁。（消费条件）：** 完整ArtifactSet应能指回每项目标实际消费的精确包身份、工具链和生成脚本资格，不能只列可变的包名。 合同归属：[来源锁、包身份、构建脚本与被替换的下载终点](../../50-执行运行与观测/平台生态/依赖与生态解析.md#gift-supply-chain-identity)。

## 方法按“贡献”组合，不按产品家族分派

一个交付根实际需要哪些贡献，由 Requirement + Binding + Target 推导。常见贡献如下；它们是开放的责任维度，不是要求所有根都具有的固定字段：

| 贡献 | 必须说明的内容 | 典型缺口 |
|---|---|---|
| **public semantic/API** | 导出主体、函数/消息/流/资源边界、类型、错误、兼容 | 只有名字/类型骨架，没有正常功能或错误含义 |
| **entry/activation** | 谁、何时、以什么输入激活；一次性、会话、常驻、周期或外部回调 | 有实现片段但无真实可消费入口 |
| **host/provider adapter** | 需要哪些宿主能力、协议、设备、文件、网络或外部服务 | 把“本机存在”当可移植能力 |
| **state/persistence** | 状态身份、共享/隔离、快照、提交、迁移、恢复 | 把缓存当权威状态或遗漏恢复基线 |
| **time/concurrency** | 顺序、并发、背压、deadline、取消、终结和 stale 规则 | 异步旧结果覆盖新输入；无限队列 |
| **effect/grant** | 外部效果、授权点、Operation identity、read-back/compensation | 生成代码时提前执行；权限由配置自报 |
| **target/ABI/representation** | 目标语言/机器/协议、调用约定、布局、编码、资源约束 | 只生成源码但未闭合 ABI/格式 |
| **asset/resource** | 必需文件、模型、消息、主题、字典、许可证、运行库等准确成员 | 目录存在但缺关键成员或来源 |
| **artifact/distribution** | 哪些成员共同封存、身份/摘要、安装/装载/交付方式 | 半成品目录被当 Artifact；各成员解析不同 `latest` |
| **upgrade/recovery** | 新旧版本、状态/数据、切换、回退、未知结果和退役 | 指针回滚被误称撤销外部作用 |
| **evidence/provenance** | Requirement→Method→Target member→Evidence/Claim 的可追溯关系 | 一个绿色测试代签全部平台/输入 |

同一个方法可以贡献多列；一列也可以由多个方法共同完成。是否需要某列只取决于真实语义和目标。例如纯静态数据无需启动生命周期；长驻外部服务通常需要；设备内核可能没有 UI，但会有 ABI/资源/同步责任。系统无需先把这些结果分类成某个 ProductKind 才能编译。

## 公共进口只允许表达真实消费者责任

可复用库、组件或协议端可以合法保留公开进口，只要进口就是其消费者合同的一部分；独立封闭根不能把内部缺实现包装成“进口”。最终 Artifact closure 必须能区分：

1. **必须已经闭合的内部义务**；
2. **明确公开给消费者的进口/配置/能力需求**；
3. **部署或运行时由 Provider 绑定的环境事实**；
4. **尚未解决、因此阻塞当前完成范围的 Unknown/Needs**。

这四类不能都写成 `dependency` 后交给运行时碰运气。是否阻断本次源码、构建、运行或保证出口，消费[Method分层资格](../../30-实现解析/实现选择/实现解析与候选资格.md#method-qualification-by-requested-exit)；Needs以[原义务和消费根](../编译内核/诊断与追踪.md#need-provenance-and-resumption)传递，目标组合器不得仅凭未来Provider可能存在就清除未决。

## Target 事实必须来自真实画像和锁定输入

`gift.project.json.targets` 或后继 Target 选择只引用可解析的真实画像/定义，不接受任意产品字符串。一个 Target 至少需要相交的语言/工具链、平台/ABI、表示/接口映射、资源/加载/关闭能力和必要质量/安全边界；具体内容按真实 Target contract 增减。

离线设计包可以完整定义“需要取得什么事实”，但不能编造 `profileRef`、版本、库或平台能力让样本看似可生成。Target 未取得时，作者 Meaning 仍可完整保存；当前运行 Artifact 只能保持未完成。

## 多根联合交付只建立实际关系

一次 release 可选择多个根，但每个根保留独立 Meaning、Binding、Target、Artifact 与完成状态。共享内容只在真实 identity、许可、生命周期和兼容条件允许时复用；路径相同或字节相同不自动共享状态。

若消费者要求整组一致，则以明确 release manifest/selection 固定同一组 Artifact revisions；不让各成员独立解析 `latest`。混部、滚动升级、跨版本协议、共享数据库或设备状态均按实际兼容/迁移合同决定，不由“同一家族”推导。

## 联合产物的封存与实际发布是一对不同的原子边界

一个 `ArtifactSet` 同时闭合所有必需文件，只保证**构建视图**完整；把多成员分次上传到目录、渠道或客户端缓存，可能使真实消费者短时混读。需要整体一致的根集合应先以不可变成员建立候选集合，再由消费者能原子解析的 release selector/manifest 提交指向准确的一组摘要；旧消费者可继续读取旧集合直到按兼容政策迁出。目标发布端不支持原子可见性时，只能声明受约束的混部窗口、适配/拒绝旧组合或采用旁路 staging/切换，不能借ZIP内清单一致宣称发布瞬间原子。

一个服务前端依赖API@2及数据schema@2，但部署区域A仍运行API@1：即使静态联合包完整，跨区域运行组合仍须按接口和数据兼容矩阵接受。发布的可见组、被实际安装的组、环境状态、已发请求与正在持有旧版本的长连接是不同事实。回退selector不能撤回已施行的数据变换、已发送消息或已加载旧客户端；若没有兼容覆盖，采用有界排空、隔离、前滚修复或暂停特定消费入口。

判定一个联合根完成时，分别检查 `成员闭包、部署可见选择、运行绑定/配置、相交证据`；库仅公开进口时，进口满足责任留给其明确消费者，不能在库打包时伪造已安装服务。真实发行/迁移采用[兼容与切换](../../70-工程系统与演进/演进与实施/兼容迁移/迁移切换与退役.md)和[外部执行结算](../../50-执行运行与观测/持久化与恢复/事务提交-外部效果与幂等交付.md)的权威协议，而不是让Target静态封存自行发令。

## 变化与增量按依赖失效，不按形态标签重建

修改一个作者值、接口、Requirement、RealizationMethod、Provider、Target 或资产时，只让其真实依赖闭包失效。典型判断：

- 纯运行参数变化且不进入生成/优化，可以只产生新运行；
- 进入常量折叠、布局、静态配置或代码生成的值变化，使相交 Target member 失效；
- 实现替换若公开语义和 ABI 不变，可保持消费者源码，但实现 Artifact/Evidence 形成新版本；
- 接口、效果、失败、时序或状态兼容改变时，相交消费者必须重判；
- UI、Service、GPU 等标签不参与失效算法，真实读集/依赖关系才参与。

## 完成和验收按实际选择闭合

一个所选交付根至少要能追到：准确作者根 → Requirement instances → 被采用方法/供给 → Target/Provider 前提 → 全部必需成员 → 真实消费入口/公开进口 → 失败/取消/退出/恢复 → 来源与 Evidence。缺其中任何必需环节时，只报告准确缺项；不能通过 stub、TODO、隐藏按钮、空 handler、未运行代码或“支持该产品类型”声明完成。

静态文档/结构校验最多检查身份、引用、字段和成员闭包；真实 I/O、协议、焦点、驱动、调度、模型分布、部署、性能、安全或其他运行性质仍必须由对应 Evidence 方法验证。反过来，一个具体 Target/Provider 尚未实现，不会使独立作者 Meaning 消失，也不会迫使产品作者把成熟算法全部重写进自己的源。

## 从目标表示到发行/部署：Artifact、ArtifactSet、DeliveryProgram、ReleaseSnapshot 与 Deployment 不得互相代签

Gift 的产物链有意分开“想生成什么、生成出了什么、怎样交付、对交付观察到了什么、现实是否已部署”。这些对象即使都携带 digest/manifest，也不能合并成一个 `ArtifactStatus` 或“release object”。

| 角色 | owner / identity | 不能推出 |
|---|---|---|
| `ArtifactIntent` | CompositionPlan 内对一个待生成成员的期望：逻辑成员、producer、目标位置、expected content/mode/dependency/delete rule | 不是已经生成的 Artifact；expected digest 不是 readback |
| `Artifact` / `ArtifactSet` | L3 中固定输入/Target/Binding 后实际生成并封存的不可变成员或完整根集合；identity 绑定真实内容与生产输入 | 存在不等于构建通过、可发布、已签名、已部署或受支持 |
| `DeliveryProgram` | 从 exact ArtifactSet、环境/迁移/支持/验证要求派生的交付计划值 | 不是永久 IR、不是 Deployment 状态、也不拥有 SupportCommitment |
| `ReleaseSnapshot` | 对一次实际 release candidate/build 的供应链读侧快照：固定 candidate、capture basis/time、source/toolchain/input closure、artifact digests、inventory、SBOM/provenance/signature、已取得的 install/smoke Evidence、coverage/freshness | 不是 Artifact 的 identity，也不得包含由它支撑的 promotion decision；重建 snapshot 不改 artifact bytes，snapshot 内容不能自签功能正确 |
| `Release / Promotion` | 有权流程将 exact immutable Artifact/Package 采用到明确发行渠道/状态的 Operation/Decision | 上传/tag/workflow success 不自动等于 promotion；promotion 也不等于部署 |
| `Deployment` / runtime generation | L4 把 exact release artifact 与 environment/config/secrets/resource/Grant 绑定并产生现实运行状态的 Operation/Effect | 部署完成不等于健康、用户可达、Requirement满足或 SupportCommitment有效 |
| deployment/runtime `Observation` | L5 对安装、实例、流量、健康、版本、资源和外部效果的实际读回 | positive readback 只证明其覆盖内现实，不代签 L6 Verdict |

主链是：

```text
TargetProgramIR / bindings
→ ArtifactIntent(s) / CompositionPlan
→ sealed ArtifactSet
→ DeliveryProgram（若请求交付）
→ release build / ReleaseSnapshot / authorized promotion
→ deployment Operation + Attempt(s)
→ runtime/deployment Observation
→ Claim + qualified Evidence + Verdict
```

每个箭头都可以因任务裁剪而停止：源码/库交付可以停在 ArtifactSet；只规划交付可以停在 DeliveryProgram；离线发行可以有 Release 而无 Deployment。任何缓存、manifest、SBOM、签名、检查或状态字段只拥有自己的角色，不能把链条压缩成一个“artifact is ready”布尔值。

### ArtifactSet、发行引用与现场运行的三个不同完成条件

编译产生的`ArtifactSet`以准确**目标、输入选择、工具链、生成规则、成员内容/模式/权限及内部引用闭包**为身份基础；输出路径和ZIP名只是投影。被生成成员的字节校验、完整性与目标合法性由compiler/target评价，不能借发布标志代签。发行引用需另绑定被允许的目标、内容根、签发主体、策略与正式promotion；现场部署后还需要真实目标状态及运行实例代际读回。

一个整体Release同时包含多个Artifact根时，必须区分“共同依赖闭合”和“所有目标一瞬间共同生效”；仓储目录原子切换仅保证同一文件系统上的可见边界，不保证消息系统、浏览器缓存、远端设备和数据库事务也同刻切换。部分失败的输出保留确已封存的子根，但不改写原完整目标；补发布应带原选择basis和新增资格，而不是把缺少的目标静默删掉。验收案例：A目标产物完整并已发布，B目标因证书撤销无法部署，A现场仍运行旧版本；三者状态必须独立可读。

### 按请求强度判定实际交付完整性

交付目的先由请求冻结，不能按模板目录名、Target 是否存在或“生成成功”代签完成。下表规定不同出口最小的可声明内容；合同本身不允许编译器越权自动部署。

| 请求的实际出口 | 应提供或保全的准确内容 | 不得推导的额外状态 |
|---|---|---|
| 库或应用的完整源码 | 本次根的行为实现、源码／配置／资源／依赖与必要构建说明；外部前提显式保留 | 应用源码交付不要求启动服务、部署数据库或申请生产Grant |
| 构建计划或待验证可构建源码 | 准确工具／依赖请求与成员计划，以及已取得的静态资格 | 计划完整不等于实际构建通过；未运行时不能签发该结论 |
| 已构建制品 | 在获准环境执行build/link，确认准确输入、实际成员和结果；所声明检查另行取得 | 不自动安装、发布、部署或运行 |
| 发行、发布、部署或运行 | 只增加所请求出口对应的包装、许可、签名、传输、准入、作用及读回／恢复责任 | 发布不等于安装，部署不等于健康运行；各结果分别确认 |

正式保证由Assurance对准确Claim和实际输入评价，不要求每个源码预览具备生产发布Evidence。请求声明“可独立重建”时才必须随交付保全必要输入内容或明确取得方式及条件；只提供依赖名称不够。编译、构建、保全和现实采用的责任仍按[交付完成语义](成员布局-完整装配与布局.md#delivery-purpose-completeness)连接。

不为结构对称强造service、deployment或package，也不以减少步骤为由漏掉用户确实请求的完整行为、资源或交付成员。

## 源文件清单、完整ArtifactSet和实际目标消费

真实Target消费者拿到已固定的BoundRoot、Requirement闭包、Method Binding、目标画像和资产ReadSet后，应列出每个required member的role、生成者、目标路径、content digest、对哪个源码/Binding负责及不可再化简的残余义务。缺任一required成员只可返回部分计划或Need，不创建一个同名空文件冒充成员闭合。

产物封存与磁盘发布严格分开：前者输出准确ArtifactSet与其内部成员关系；后者经Execution执行目标路径CAS/许可/读回。多根部分完成逐根报告。静态Rule谓词存在不等于生成实现确实保持语义，必须在实际Target及运行条件下处理其ProofObligations。

## 最小完整 TypeScript 目标成员与源语义接合

目标接受性首先使用准确 Rule Profile ID，而不是一个看似近似的名称；本规范样本曾出现 `gift.rule-call-observation/1` 与目标 `gift.req-call-observation/1` 不一致，已修复独立 fixture 并新增强制比较。实际 Target 除 `accepts` 外，还必须将目标语言、`moduleMode`、text index unit、整数溢出/NaN、异常模型、ABI、Target lowering 及用到的 Host 功能与作者语义逐项对应；声明里 `members` 指预期路径角色，不证明字节已存在。

本次受限 TS Native passthrough 样本会写出 `src/document.ts` 的**原生同字节副本**、`package.json` 和 `tsconfig.json`，记录每一实际成员的长度与 SHA-256；它证明这一组选定原生作者文件可以装配为独立 TypeScript 工程，不证明通用 `req:rule` 已 lowering、所有 Observable Properties 已满足、工具链在每个宿主可用，亦不提供 `gift.binding-lock/1`。`tsc` 的成功结果必须绑定具体 Node/TypeScript 版本、目标选项、输入摘要和实际调用记录；后续执行的行为样本另签独立局部证据。由 Template 造空函数、补 TODO 或“只导出一个名字”不能满足 Method 的完整行为义务。

产品级 `ArtifactSet` 还要固定每个成员的 byte digest、permissions、路径规则、内容来源、导出/导入引用闭包、实际工具链及环境、未被满足的 Requirements、根与 Root 间依赖和签发生产者。存在一个有效输出根不代表其他根完成；需要发布工作树时从只读候选转入受权 Operation、CAS、效果读回与可恢复 publication。未明确授权时只能生成隔离候选制品，不改作者 Workspace。

### native-number 表示的真实反证与条件化 Target 接受性

`representation.integerMode=native-number` 是一个目标表示选择，不能自动承担源 Rule 的数学整数语义。当前原生样例在 `2^53` 边界出现实际不可区分的 `+1`，谓词甚至返回假阳性。Target 在 Profile 结构兼容之外，仍须取得数值域与溢出政策证明或改变准确表示；不同的 `bigint`、有界整数、带舍入浮点或任意精度整数不能仅因业务字段都叫 `revision` 就声明等价。若把越界改为 throw，需重新解释原 Rule 的 `failure` 分支、输出 API 与向后兼容。没有满足这些条件时，只能发射经限定的演示字节，不能授予全面 `ArtifactSet` 符合性。
