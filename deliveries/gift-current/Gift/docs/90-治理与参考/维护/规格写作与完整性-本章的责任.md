# 本章的责任；根方案比较不能缩成两个技术标签

## 本章的责任

本章定义Gift设计文档怎么组织、写作、修改、删并和交付。产品规则由对应领域规范拥有；本章不再复制它们。根原则在[原则总纲与归属](../../00-系统与原则/产品/原则总纲与归属.md)，外部资料的证据范围在[设计依据与资料边界](设计依据与资料边界.md)，当前未决状态在[设计状态与验证路线](../状态/README.md)。文档写法不是可执行的产品授权。

这些规则适用于本设计包；用Gift开发目标工程时，目标工程可以采用同样方法，但不强迫复制本包的全部目录和条目。Gift自身的开发工程、Gift产品模型、用户目标工程与当前文档制品是四个不同对象，不能由同一个“工程原则”标签代替其适用范围。

## 正向可实施规格与允许的详细程度

**完整设计正文可以长、可以多视图、可以逐步展开；任务输入与每次模型上下文才需要按需收敛。** 作者只写一个参数，不表示实现该参数语义的规范只能有一句话。篇幅由消歧、机制、边界和反证的实际需要决定。合并相同含义的重复，保留会改变裁决的条件；不以文件数、字数或禁令数量作为质量指标。

一条需求首先说明要达到什么结果；选定设计另外说明怎样达到。两者通过引用连接：用户要求中的非负金额不是数据库隔离级别，设计选用版本比较也不是用户必须填写的业务概念。需求层可以保留实现自由，设计层必须在其承担的范围给出可实施默认、替代和转换条件。[NASA需求写作指南](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/)要求责任明确、主动语态和可验证性，同时区分需求的what与实现how；本包的架构与算法章节专门承担后者，不能引用需求层的自由来省略设计。

### 每项设计怎样由目标落到行为

对正在定义的能力，按下列顺序组织相交内容。它是规范编写者的工作顺序，不是给AI开发者新增一份运行请求，也不要求普通类型字段创建持久记录。

1. **定义范围。** 写明谁使用、输入输出根、所选语义画像、观察者和环境假设。先举一个合法输入及其目标结果，明确这次不涉及的能力。
2. **固定数据与权威。** 逐个说明必要字段的类型、单位、来源、缺省、未知与有效范围。定义哪个状态由谁改变、哪些数据只是派生、哪些引用需要在何时解析。缺省必须能够定位到实际规则。
3. **描述正常路径。** 从前态和触发开始，写出读取、判定、计算、状态转换、提交或返回的顺序。每步说明输入、产出、承担者及传给下一步的条件。存在可替换算法时给当前采用的那个，而不只列候选名。
4. **规定变化边界。** 列明允许改动的字段和保留原样的内容。编辑候选的动作只创建新候选；真正写回才改变目标；“其余不变”要指向可识别的范围。
5. **划分异常与并发。** 按实际可观察谓词建立分支，说明错误优先级、部分结果、重试前提、取消点、恢复拥有者和结束条件。输入非法、未知、方法不支持、执行失败分别给下一步。
6. **限定资源与进展。** 给复杂度或工作量来源、预算的来源和计量位置。对有限输入、合格工具和满足调度条件的路径，说明如何在完成、显式缺项、失败或受控取消中结束；不要求任意作者程序都终止。
7. **给出复核对象。** 成功轨迹、边界输入、故障切点与预期状态要可由另一实现者复现。案例的期望来自该合同或独立推导，不以同一个生成器输出作为唯一答案。
8. **记录选择。** 比较最强替代，写清为何当前采用、付出什么成本，以及哪个事实出现后要重审。仅列“有优缺点”没有完成选择。

某项责任由其他规范完整承担时，链接其具体合同，说明当前传入什么和要求它返回什么。引用不替代调用方自己的前提与错误处理。纯类型定义可能只有前两项及构造/拒绝规则；事务协议通常八项都相交。省略必须由范围可解释，不强求每页同一长模板。

### 独立设计结构必须写出必要性，而不是只写“怎么实现”

只要某项正文新增或长期保留一个独立 architecture boundary、protocol、IR、state machine、service、persistent record、public control 或特殊 workflow，就必须按[canonical ASMRVE设计闭包](../../00-系统与原则/设计方法/设计综合与必要性.md#asmrve-design-closure)回答实际相交的完整义务；本篇不再重定义 A/S/M/R/V/E 的含义。ASMRVE仅辅助检查，不要求所有段都独立存在或已取得物理实现。已有设计族完整覆盖的部分可以引用父合同并只写本项差额；**不能让读者为了知道“为什么需要它”去翻旧聊天、旧PR或猜目录结构。**

具体写作至少要让实现者看见：不采用它会丢失的区别/保证、真正消费者、为什么现有更小机制不足、它引入的长期成本、什么证据会推翻选择、什么时候能合并/退役。纯派生字段、机械schema键和没有独立生命周期的内部helper不重复制造 ASMRVE 文档；它们的必要性由父 concern 和实际consumer覆盖。

组织重构时同样不能把“旧分类不够正交”当删除理由。被替代结构中的有效事实按 `preserved-exact / preserved-refactored / derived / superseded / retired / unresolved` 给出去向，未映射的独立内容不得删除。

### 禁令、正向行为、进展和保持范围分别检查

“不会越权”约束的是允许行为的集合；“合法请求在什么条件下会完成”约束的是系统能做到什么。一个永远拒绝请求的系统满足许多安全禁令，却不满足产品目的。一个不断返回相同待决状态的系统也可能保持全部不变量，却没有产生进展。因此，每个可执行能力同时审查：

| 规格面 | 需要的正向内容 | 检查反例 |
|---|---|---|
| 合法结果 | 合法输入、必要前提、动作和可观察结果 | 全部请求一律拒绝仍被标“符合” |
| 安全范围 | 被保护对象、准入点、可执行转换 | 显示层隐藏按钮但执行端仍接受调用 |
| 保持范围 | 哪些源、字段、身份和外部状态不变 | 成功生成顺手格式化无关作者文件 |
| 条件进展 | 有限工作和可用能力下的完成/明确退出路径 | 无变化地自动重试、永久pending |
| 外部限制 | 不响应、掉电、撤权等条件及有限责任 | 规范承诺外部世界永远配合 |

“没有反例”只有在已声明且完成的搜索域内才有相应含义；用一张负例表也不能自动得到完整正确设计。安全条件仍保留，补上的正向协议要与之同时成立，而非用成功路径取消保护。

### 数据、算法、状态表和示例怎样共同维护

规范中的对象名称、步骤号、状态与输出字段共用定义。先有数据和转换，再用状态表列出分支，用伪代码表达计算，用轨迹检查例子。图说明引用、数据、控制、等待还是失效关系，不凭箭头外观决定语义。每个视图标出自身省略了什么；概述链接到完整机制，不能反向改变完整机制。

同一规范内为解释算法、展示反例和帮助恢复而有必要重复，是允许的。第二份完整状态表、字段表若能够独立修改，则合并到唯一位置或建立明确的派生关系。任意自然语言与程序之间没有自动等价保证；本包采用对象/字段/步骤交叉核对，不写“已编译多视图”来冒充现有工具能力。

### 一个完整规格条目的最小示范

目标：将一个已固定作者候选生成内存源码。输入为不可变候选C、已选目标T、当前读取许可与编译预算。服务先固定C及其必要内容；按锁解析T；建立输出根与实际依赖；逐阶段检查并生成；将源码字节、实际绑定与必要诊断作为一个结果返回。源C、现有工作树、数据库与部署状态保持不变。

若C已不可解析，返回候选引用失效而不是替换为latest；若C内容合法但T缺少一个必需类型映射，保存C和已完成分析，说明哪个输出根不能生成；独立根可以有单独的结果。若工具本身崩溃，返回工具失败与已完成的观察，不修改C以获得绿色。预算结束时只发布已满足该输出合同的完整产物，其余保留为未完成分析。

对合法、有限且预算充足的输入，所选各阶段都能结束、所需提供者可用时，路径到达源码返回；任何前提破坏时到达与原因对应的诊断。合法零修改仍然返回原候选或等价引用和明确的“无变更”；不是无限等待，也不是强制制造一个文件修改。

该例的产品机制由[整体请求算法](../../80-开发者与接口/需求到交付主链.md#一次请求的正向执行模型)和[编译阶段协议](../../30-实现解析/内核/编译值服务.md#从作者候选到目标字节的阶段协议)拥有；本段仅说明如何写清设计，不新增一个预览实现或第七个工具。

## 按性质写够信息，不强迫统一长模板

| 文档性质 | 应完整表达 | 不应夹带 |
|---|---|---|
| 设计合同 | 责任、输入输出、适用条件、不变量、失败、并发、资源、版本和验收 | 无版本的历史测试绿色、平台权限承诺 |
| 架构解释 | 上下文、边界、依赖、数据/控制流、状态拥有者、部署变化与代价 | 第二套接口字段定义 |
| 决定理由 | 问题、约束、当前选择、替代、成本、反例与重开条件 | “最佳实践”“完美”替代论证 |
| 接口参考 | 字段类型、单位、默认、缺失与未知、错误、兼容及例子 | 用结构合法冒充行为正确 |
| 场景设计 | 初态、参与者、刺激、实际变化、竞争、失败与预期观察 | 将该业务变成所有工程的强制类别 |
| 当前状态 | 明确对象与版本、设计/实现/证据/采用的分维度状态 | 在稳定规范里散布短期SHA和单次检查次数 |
| 实验证据 | 真实输入、方法、环境、结果、日期与未测范围 | 把局部验证变成所有场景的保证 |
| 研究分析 | 命题、假设、资料、推导、反例、适用边界与采纳状态 | 研究标题直接覆盖已采纳架构 |

表格是审查标准，不是每页都要复制的目录。纯类型参考无需编造事故故事；涉及数据迁移的合同不能省略失败恢复；低频但会改变裁决的独立反例仍须保存。

### 高层抽象的可行性与主面采用分别裁决

对“需求block／原子”主张，必须说明原子的观察边界、共同构造及新增定义的规则，不给开放需求宇宙伪造一个总数。已有组合能否作为同类定义再次使用，能否只修改一个公开参数，能否按需要打开内部并回写原源，是具体审查对象。

接口范本必须同时区分调用方需写的内容与库内部一次维护的内容。若每个新需求又回到应用作者手写全部算法，检查缺少的是可复用关系、组合闭包、边界编辑还是实现在当前目标缺失，不只增加一个更大的函数名。反过来，不将每个运算节点全球化，也不把库实现和目标语义隐藏成无需承担的工作。相交图、源码、协议和问题应共同更新，未选语法和平台不随范本进入实施队列。

## 作者面设计不能只增加精确规则

语言或领域画像每增加一项必填、注解、文件、概念或操作往返，必须检查：作者独特决定是什么，已有内容能否推导，是否只在真实边界需要，是否与另处重复，缺省如何解释，增加了什么实际保证，及更小表示为何不足。该检查在对应规范和理由中完成，不创建每个表达式的审计账本。

规范为所有合法边界列出细节，不代表教程或工具每次复制这些细节。形式文法可以详尽，任务入口应只展开相交规则；完整报告可以按需读取，普通错误应定位到作者真实可修改的地方。案例若只证明细语义，须标明它不是最优作者界面；不能用更多产生式、更多静态检查或更长解释作为可用性改善的证据。

面对“为什么不用现有语言”的质疑，应比较同等输入/输出、保证、库、已有知识与连续变化，而不是马上另造一段更短DSL。公平基线可以更优；新的中立机制也可能有独立收益。不能先迎合裁决再从原文找理由，更不能靠改名或维护沉没成本免除比较。本规则本身不授予实验执行权限；没有运行就记录设计判断和未测范围。

### 作者主面的交付核对

当核心问题是“需求抽象或开发面”，先明确当前改进属于句法省略、参数化复用、跨软件关系、工程变更还是运行控制，不用其中一项代签其他项。交付必须给出**实际作者内容/关系与直接操作、真实语义和供给、机器怎样补全或构造、最终目标与下一次修改**；需要新源码时提供完整可审查主体，只需既有参数时不制造源码。不只减少工具信封字符，不以折叠完整源码替代删除重复作者信息，也不通过新增未实现短API假装行为已有人承担。

语言表面改变时，同次检查文法、静态/动态语义、结构编码、声明收集和类型算法、输出根、目标生成、错误草稿、源保全与回源、缓存及实施验收；每项有唯一拥有者和实际消费者。默认展示不代表默认改写，推导字段不自动进入作者文件。真正新责任要明示，不能用“不增加关键词”掩盖新增读取器/检查器工作。

证明跨软件抽象时至少选择有不同结构与生命周期的相交任务，解释共同形状和不能共用的区别，并提供同一次修改的具体规则；不能只更换一个计价/筛选例的名词，也不以几类通用字段宣称全部实现。已完成的有限表面与算法写回当前状态，不再保持“以后设计作者方式”；实现与实际收益准确留为对应义务。没有充分依据时不将用户提到的语言、SDK或图变成采用命令。当前门槛是同一来源能够正常工作并保持简洁，而不是又有一篇原则说明。

## 规范句子应可理解、可定位、可否证

规范强度首先服从真实来源和已接受含义。“必须/不得”标出适用域内的硬要求；“可以”表示已定义范围内的选择。不能仅因为用户或正文用了“应当”，就把原来必需的要求降格为可随意偏离的默认。可覆盖缺省须明确标记为“默认”，并说明允许覆盖的主体、范围及行为；建议应明确写为建议。引用英文标准保留其自身关键词约定，不能靠中文措辞替换其规范强度。重复次数、加粗和所在目录均不提升权威。

有约束力的规则要能回答：谁，在什么条件下，对什么对象，采取什么动作或保持什么不变量，怎样观察是否违反。将“系统必须安全重试”改为“响应未知但可能已产生效果时，执行器按稳定操作身份和目标合同选择查回或有去重保证的同键重试；两者都没有时不得自动重发”，才能指导设计与验收。

绝对词必须带范围。“完整”说明对象集合；“最小”说明偏序或代价；“原子”说明观察者与提交点；“精确”说明输入和假设；“独立”说明共同原因；“最优”说明候选、目标和证据。研究中被反驳的全称命题、数学量词和规范禁令不能按关键词一律删除。

## 一处拥有规则，必要重复用于理解和防错

规范正文拥有行为与不变量；正式机器合同拥有其声明的结构约束；理由解释选择；示例说明输入与结果。结构合同与正文矛盾就是缺陷，不能默选所谓更严格的一份。旧结构示例既不定义当前协议，也不得限制完整产品。

总览可以简短重述意义，危险动作旁可以重复关键前提，但链接唯一规范位置。完整字段表、状态机和例外不应在几页各自维护。合并文章以后，还应删除语义重复而不是只把旧篇章拼在一起；相似名字但不同量纲、主体、时序或状态不可强并。根规则变化时沿相交领域正文、图、理由和示例核对，不用一段“以新总纲为准”掩盖相反旧条文。删改过的理由要回查其独立例外与失败条件，不能把最后重复的模板字段连同独立知识一起删除。

图表达有类型的关系、顺序、状态或部署。图中箭头要说明是输入、控制、引用、前置还是失效；合法递归与执行死锁不能都叫“有环”。代码块可以是接口/算法设计，不因此变成已运行实现；演示语法必须标明非正式或候选。

## 稳定正文与工作记录分流

现行规范直接陈述**现在成立的设计事实**：当前采用什么、由谁拥有、输入输出和状态怎样变化、失败如何恢复、哪些条件会使选择重开。`本轮新增`、`这次整理`、`上一版遗漏`、修改文件数、测试次数、某次打包摘要或聊天过程属于工作记录／交付证据，不得作为理解当前机制的前置；需要追溯时进入对应 Evidence、历史来源或包外交付报告。真实协议版本、迁移前像和已发生但未结算的外部作用仍是产品事实，不因含有历史时间而删除。

`本次请求`、`本次运行`、`本轮循环`等词只有在它们确实是协议中的**请求/执行局部状态**时保留，并须能指出该局部范围的身份与生命周期；若句子只是在描述文档作者当前做了什么，改成稳定的现在时或移出规范。入口页的摘要描述责任和边界，不从正文机械截取前两个标题，也不反复粘贴“实现状态另查未决”之类通用免责句；设计、实施状态、证据和派生索引各自由唯一位置承担。

当前系统名统一为 `Gift`；机器协议与schema使用其已定义的 `gift.*` 命名空间，可选中立计算文本使用 `.gift`。旧项目名、旧路径和旧协议字面量只在历史来源、兼容/迁移合同或冻结证据中原样保留，并明确其角色；不得让历史坐标与现行命名在同一规范层并列成两套当前事实。

技术标识、API类型、标准术语和无法等价翻译的语言概念可以保留英文；普通叙述优先使用稳定中文术语。同一概念在同一责任层只保留一个主称谓，别名只用于检索、兼容或首次消歧。

## 根方案比较不能缩成两个技术标签

重新评估方案时先恢复原目标，区别作者语法、语义归属、生成机制、目标制品和持续编辑。比较普通框架与独立语言时，同样考虑受检宿主、阶段化、现有多目标编译器和语言工作台；VM、投影或求解器是不同责任，不能仅列在一张赢家表里就认定可以直接互换。

“当前两个入口旁再加一个”的判断与“从产品原点选完整替代”分别处理。沉没设计不能把替代永久判贵，刚取得的新网页也不能让所有旧目标退让。当前决定必须说明采用了哪个机制、实际保留／撤销了什么，及未取得哪些供给事实；比较新技术不自动增加依赖、API或任务。原本就存在的模块关系应如实说明是收束，不以重命名冒称新发明。
